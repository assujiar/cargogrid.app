**Owner:** DevOps / Security
**Since:** Phase 15 (`HDN-378`, Prompt 378 Security Hardening)
**Severity class:** Depends on scope — see §2. Adapted from the single-incident-shaped template: this runbook covers the general class "an identity, session, or channel is suspected compromised," not one specific historical incident. `docs/runbooks/secret-leak-incident-response.md` is the credential-specific sub-case of this general runbook — read that one first if the trigger is a leaked credential specifically; use this one for everything else (a compromised session, a suspicious impersonation window, a role/membership grabbed by the wrong identity, a suspected IP-restriction bypass).

> **Rehearsed once (§7), never against a real incident** — no real security incident has occurred in this repository's history (mirrors `docs/runbooks/secret-leak-incident-response.md`'s own honest disclosure). The one rehearsal to date ran at `HDN-384` against a disposable sandbox Postgres, exercising §3-§4 end to end. §7 records rehearsal evidence as it accumulates; this remains the pre-committed response contract, not a claim of real-incident-tested effectiveness.

## 1. Symptom / trigger

Any of: a user or tenant admin reports unrecognized activity on their account; an anomalous entry surfaces in `app.audit_logs` (unexpected actor, unexpected `action`, unexpected `occurred_at` window) found via ad hoc review or a future alerting pipeline; a support-access grant shows an open session (`app.support_access_sessions`) that the tenant did not expect or approve; a role assignment or principal membership appears for an identity nobody remembers granting it to; or a client reports being denied by an IP allowlist they believe should have let them through (or, worse, an allowlisted tenant reports traffic they don't recognize from an unexpected IP — see §2's IP-restriction caveat).

## 2. Impact

Depends entirely on what the compromised identity or channel could reach. Tenant-isolation implications (`AGENTS.md`): every RPC below is tenant-scoped by its own `p_tenant_id` parameter — confirm the actual blast radius is the tenant(s) the compromised identity actually held membership/authority in, not assumed to be single-tenant. A **Supreme Admin** identity or an open **support-access impersonation session** widens the blast radius to any tenant that identity's authority reaches — treat compromise of either as multi-tenant until diagnosis (§3) proves otherwise.

**Known limitation, disclosed as of this checkpoint (do not assume broader coverage than this):** IP-restriction enforcement (`app.assert_ip_allowed`, IAE-028) has just been wired into 4 admin-scoped RPCs this checkpoint (closing `ISS-2026-150`, see `docs/runtime/KNOWN_ISSUES.md`) — `app.decide_ai_output_approval` (AI:Approve), `app.activate_enterprise_idp_connection` (IAM:Configure), `app.approve_mfa_exception` (SEC:Approve), and `app.create_integration_connection` (INTHUB:Configure). Each gained a trailing, defaulted `p_client_ip text default null` parameter; when a caller supplies a real IP and the identity holds no active `app.ip_allowlist_bypass_grants` grant (`app.has_active_ip_allowlist_bypass`), the function calls `app.assert_ip_allowed(tenant, client_ip, 'admin', actor_label)` before its mutating action. **Only `app.create_integration_connection` has a live HTTP entry point deriving and passing a real client IP today** — `app/(tenant)/[tenantSlug]/integrations/actions.ts` reads `x-forwarded-for` and threads it through. The other 3 functions' TS mutation wrappers (`server/mutations/ai-governance.ts`, `enterprise-iam.ts`, `enterprise-mfa.ts`) already accept and forward a `clientIp` field, but **no `app/` route calls any of them at all** — there is no live UI path to reach `decide_ai_output_approval`, `activate_enterprise_idp_connection`, or `approve_mfa_exception` today, so `p_client_ip` is always `null` for them in production and the IP check is a structural no-op. Practically: **"revoke the compromised IP allowlist entry" (§4) is a real, provable block against a live caller only for `app.create_integration_connection` today** — the RPC-level gate on the other 3 is real and provable directly (via `db-test`) or via a future UI route, but treating it as an active production control for those 3 today would overstate the actual protection.

## 3. Diagnosis steps

1. **Pull the audit trail.** Call `app.query_audit_logs(p_requester_auth_user_id, p_tenant_id, p_limit, p_before_occurred_at, p_before_id)` (`supabase/migrations/20260810000000_harden_tenant_isolation_actor_identity_gaps.sql`, latest `CREATE OR REPLACE`) filtered by the suspected `p_tenant_id` and paginated backward from the incident window (`p_before_occurred_at`/`p_before_id`). It returns `setof app.audit_logs` ordered `occurred_at desc, id desc`, capped at 200 rows per call. The function itself gates on `app.is_support_grant_authority(p_requester_auth_user_id, p_tenant_id)` (Supreme Admin **or** tenant_admin authority for that tenant, not tenant_admin alone) and on `app.assert_actor_is_session_identity(p_requester_auth_user_id)` — the caller cannot forge a different `p_requester_auth_user_id` than their own live session (the `HDN-372` fix this function itself carries a code comment about). Every call to `query_audit_logs` is itself audited (`audit_query_caller`/`query_audit_logs` in `app.audit_logs`) — expect to see your own diagnosis pass show up in the trail. For a bulk pull spanning more than a spot-check, use the sibling `app.export_audit_logs` (same signature, `p_limit` default 500, same authority gate, distinct `export_audit_logs` audit action) instead of looping `query_audit_logs`.
2. Filter the returned rows by the suspected `actor_auth_user_id`, `action`, and `entity_type`/`entity_id` to reconstruct what the identity actually did in the window — `app.audit_logs` rows carry both a before/after diff shape (most mutating RPCs pass old/new `jsonb` into `app.capture_audit_event`) and a `status` (`success`/`failure`) field, so failed attempts (e.g. a denied privilege-escalation attempt) are visible alongside successful ones.
3. **Check for an open impersonation session at the time of the incident.** Query `app.support_access_sessions` directly (tenant-scoped, joined to `app.support_access_grants`) for any row with `ended_at is null` overlapping the incident window, or call `app.current_support_session(p_tenant_id, p_auth_user_id default auth.uid())` (`supabase/migrations/20260810400000_harden_crm_ops_actor_identity_gaps.sql`, latest `CREATE OR REPLACE`) for a specific identity — it returns the one open session (grant `status = 'approved'`, `revoked_at is null`, `expires_at > now()`, session `ended_at is null`) for that identity in that tenant, or no row if none is open. A live impersonation session at the time of a suspicious action changes the blast radius from "this one user" to "whatever the supporting identity's own grant scope reached."
4. Cross-reference the actor's current authority: `app.role_assignments` (via the audit trail's `role_lifecycle_history` rows) and `app.principal_memberships` for any grant that post-dates the identity's own known-good baseline — an attacker who compromised a session frequently also grants themselves a durable role/membership as a persistence mechanism, which the audit trail's `assigned`/`revoked` `role_lifecycle_history` events and `principal_membership_history` rows will show even after the original session is gone.

## 4. Resolution steps

1. **Pull authority the identity should not have — do this FIRST, it is the layer that is actually enforced.** `app.revoke_role_assignment(p_id, p_reason, p_requested_by)` (`supabase/migrations/20260716103445_create_roles_permissions.sql`) and `app.revoke_principal_membership(p_membership_id, p_reason, p_requested_by)` (`supabase/migrations/20260716100825_create_principal_memberships.sql`) are both idempotent (a repeat call against an already-revoked row returns it unchanged, no error) and both write their own `role_lifecycle_history`/`principal_membership_history` row. Neither function gates authority in its own body — the standing convention for this pair is RLS-enforced on the underlying table, the same defense-in-depth posture as the platform's own PLT-105/106/107/108/109/110 functions (see the code comment immediately following `revoke_role_assignment` in its migration) — so call them through a client/role that itself passes that RLS check, not as a bare service-role bypass. **This step, and IP-allowlist revocation (item 4), are the only two of this section's revoke primitives with a real, confirmed enforcement effect** — live-forced end to end at `HDN-384`'s own security-incident rehearsal (`docs/build-log/full-system-hardening/HDN-384.md` §4, `docs/runtime/KNOWN_ISSUES.md` `ISS-2026-264`).
2. **Also revoke sessions and API keys — audit-trail hygiene, not the primary lockout.** `app.revoke_all_actor_sessions(p_tenant_id, p_target_auth_user_id, p_reason, p_actor_auth_user_id, p_actor_label)` (`supabase/migrations/20260807100000_create_intelligence_enterprise_mfa_session_controls.sql`) revokes every `active` `app.user_sessions` row for that identity in that tenant **and** composes `app.revoke_api_key` for every `active` API key that identity itself created — returns the session-revoke count (the API-key count lands in the audit event only). Gated by `SEC:Configure`. For a single session instead of every session, use `app.revoke_user_session(p_session_id, p_reason, p_actor_auth_user_id, p_actor_label)` (same migration) — self-service for your own session, `SEC:Configure`-gated for someone else's. **Corrected at `HDN-384` Tier C, live-forced (`ISS-2026-264`/`HDN-BLK-035`, High): the `app.user_sessions.status` flip these two functions perform is pure bookkeeping — nothing in this codebase (no RLS policy, no RPC, `app.evaluate_permission` itself) ever reads it.** Do NOT treat this step as cutting off access on its own — item 1 (role/membership revocation) is what actually blocks the identity. The API-key revocation this step also performs IS genuinely enforced (a revoked key fails authentication), and genuinely invalidating a live Supabase JWT/refresh token is a separate Supabase Admin API call, not performed by either function (see each function's own `comment on function`) — if the compromised identity has a live, unexpired JWT already in an attacker's hands, escalate to the Supabase Admin API/dashboard for token-level invalidation in the same pass as item 1.
3. **If impersonation is implicated:** `app.revoke_support_access(p_grant_id, p_revoker_auth_user_id, p_revoked_by, p_reason)` (`supabase/migrations/20260716113048_create_audit_trail.sql`, latest `CREATE OR REPLACE`) is idempotent (already-revoked returns unchanged), requires the grant's current `status = 'approved'` to act, and is gated by `app.is_support_grant_authority`. It revokes the `app.support_access_grants` row **and** closes any open `app.support_access_sessions` row tied to that grant (`ended_at = now()`, `ended_reason = 'revoked'`) in the same call — you do not need a separate session-close step for the support-access case.
4. **If an IP-restriction bypass is suspected** (an attacker operating from an IP that should have been blocked, or a legitimate bypass grant that has outlived its purpose): `app.revoke_ip_allowlist_entry(p_entry_id, p_actor_auth_user_id, p_actor_label)` (`supabase/migrations/20260807200000_create_intelligence_ip_restriction_network_access.sql`) flips a `status = 'active'` `app.ip_allowlist_entries` row to `'revoked'`, `SEC:Configure`-gated. **Remember §2's caveat before treating this as a completed mitigation**: as of this checkpoint it is a real, live block only for traffic reaching `app.create_integration_connection` through its one wired UI route; it has no live enforcement effect on the other 3 newly-wired RPCs (no route threads a client IP to them yet) and none at all on any RPC not in that set of 4.
5. **Rollback procedure if resolution fails:** if a revoke call itself fails with `insufficient_authority`, escalate to an identity that genuinely holds the required grant (`SEC:Configure` for session/IP-entry revokes, `app.is_support_grant_authority` for audit/support-access actions) rather than working around the check — the check is the control, not an obstacle. If the compromised identity is itself the only holder of the required authority for its own tenant, escalate to a Supreme Admin identity, which `app.is_support_grant_authority` always satisfies.

## 5. Communication

**Communicate through `docs/runbooks/incident-communication.md`** — it carries the audience order, the message shape, and the `app.broadcast_incident_communication` call that records what was sent to whom. Notify DevOps/Security lead immediately once §3 confirms compromise is real (not a false-positive anomalous-looking-but-explainable audit entry). Multi-tenant blast radius (an open support-access session, a Supreme Admin identity, or authority spanning more than the originally-reported tenant) escalates beyond this runbook to `AGENTS.md`'s "Stop and escalate when" tenant-isolation criteria — do not resolve a multi-tenant incident unilaterally. Customer-facing communication is warranted only if the confirmed blast radius reached tenant data, per the same escalation path.

## 6. Post-incident

Record: which identity/session/grant was compromised, how (session theft, credential reuse, insider misuse), the full timeline reconstructed from `app.audit_logs` (§3), which of §4's revoke primitives were actually invoked and in what order, and whether the diagnosis step itself (§3) was sufficient to reconstruct the timeline or whether a gap in the audit trail's own coverage should be filed as a `KNOWN_ISSUES.md` follow-up. If the incident exploited the disclosed IP-restriction gap (§2 — a caller reaching one of the 3 not-yet-routed RPCs directly, bypassing the intended HTTP path entirely, e.g. via a leaked service credential), record that explicitly — it is independent evidence for prioritizing the deferred wiring work, not something to silently work around.
