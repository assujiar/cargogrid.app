## 1. Symptom / trigger

Prompt 384's own §20/§21/§27 name 5 outage classes to rehearse — database, **file**, provider, **job**, and security. This runbook organizes around the 4 named scenarios below; file (Storage) and job (background queue) outage are deliberately treated as consequences of the same Postgres-backed infrastructure covered by data corruption/major outage/provider failure, not given their own independent scenario, since (per `01_MODULE_DEPENDENCY_MAP.md` R7) the job queue is itself Postgres-backed and Storage restore is already tracked separately as an untested, sandbox-infeasible gap (`ISS-2026-255`). This mapping decision is stated explicitly here rather than left silent.

Four distinct scenarios, each with its own detection signal, are in scope per Prompt 384 §4/§20:

1. **Major outage** — the app-hosting layer, Supabase Postgres, or the network path between them becomes unreachable for all tenants simultaneously. No automated detector exists for this in this repository today (see §3 item 1) — the first signal is realistically a human noticing (a customer report, a manual check), not an alert.
2. **Data corruption** — canonical `app.*` table rows become wrong, inconsistent, or violate integrity expectations while the infrastructure itself stays up (a bad migration, a bad manual intervention, or an application bug). Detected by a row-count/integrity anomaly, an application error spike, or — critically — **not** detected by `app.audit_logs` if the corrupting action bypassed every RPC function (see §3 item 2's own live-proved detection gap).
3. **Provider failure** — Supabase itself (the single managed backend vendor for Postgres, Auth, Storage, and the PostgREST gateway) has an outage or degradation independent of anything CargoGrid's own code does. Detected via `/api/ready`'s real `503 {"status":"degraded","reason":["database_unreachable"]}` response (built at `HDN-382`) when the failure specifically affects Postgres reachability — but that route's own failure path is fully unlogged server-side (`ISS-2026-253`, open), so a responder cannot distinguish this from any other exception by server logs alone.
4. **Security incident** — a compromised identity, session, credential, or channel, matching `docs/runbooks/incident-response.md`'s own scope exactly. Detected via `app.audit_logs`/`app.query_audit_logs` (a genuinely real, queryable trail for anything that went through an RPC function).

## 2. Impact

A major outage or provider failure is inherently **platform-wide** — every tenant is affected simultaneously, with no per-tenant mitigation possible. Data corruption and security incident are usually tenant- or table-scoped, but can be platform-wide depending on blast radius (a corrupting migration touches every tenant; a compromised Supreme Admin session touches every tenant). CargoGrid has **no second infrastructure vendor** for its core stack (Next.js app-hosting + one Supabase project covering Postgres/Auth/Storage/PostgREST) — nothing in `docs/architecture/` describes a multi-region or multi-vendor failover path. **Tier C correction**: Supabase itself does offer a real, native cross-region mechanism (Read Replicas), but it is gated to paid plans and this organization is confirmed on the free tier, so it is structurally unavailable today rather than merely undocumented — and even on a paid plan, Read Replicas explicitly exclude Auth traffic and would not survive a full Primary outage, so this remains a genuine single point of failure for the major-outage and provider-failure scenarios regardless of plan tier. Registered as `ISS-2026-261` (see §6).

## 3. Diagnosis steps

1. **Confirm the sandbox/environment constraint before assuming any live mechanism is available.** Independently re-verified this checkpoint (not merely inherited from `HDN-380`/`HDN-383`): the Docker daemon is **absent entirely** in this environment (`docker ps` fails with "no such file or directory" — no socket at all, a step further than `HDN-380`'s reproducible `runc`/`RLIMIT_NOFILE` error), the Supabase CLI is not installed, and local Supabase gateway/Auth/Storage ports (54321-54324) are all closed. **The only *technically infeasible* surface here is the local Supabase gateway/Auth/Storage stack.** The real hosted project is a different matter — **Tier C correction, attack-surface lens**: this environment's own Supabase management connector reaches the real hosted project (`awdlicmwzdxquopwtcfd`, confirmed `ACTIVE_HEALTHY`) directly and successfully, including admin/management-plane calls (`execute_sql`, `query_logs`, and even `restore_project`, a real PITR trigger) — none of these were invoked, correctly, since `HARDENING_MATRIX.md` §14 item 6 forbids ever targeting the real project's own data for a rehearsal, but the barrier is a **policy decision this runbook and its own governing matrix correctly enforce, not a technical wall**. State this precisely rather than implying the real project is unreachable: it is reachable, and deliberately not touched. **The only live-executable substrate for an actual DR *rehearsal* is raw Postgres against a disposable sandbox database** — real SQL, real `app.*` RPC calls, real RLS — which is why major outage and provider failure stay tabletop-only for this checkpoint (§4 items 1/3): not because nothing is reachable, but because the one thing that would make them live-executable (the real project, or a full local Supabase stack) is either policy-forbidden or technically absent here.

2. **Data corruption — a real, live-proved detection gap: `app.audit_logs` is structurally blind to raw-SQL or infra-level corruption on ordinary tables.** Live-reproduced: a direct `DELETE FROM app.leads;` (no `WHERE` clause — the classic accidental-bulk-delete incident) against a seeded disposable database left **zero rows** in `app.audit_logs` matching the event, because `app.capture_audit_event` only fires from inside RPC functions — a raw SQL statement (a botched migration, or a support engineer's direct psql intervention) bypasses it entirely. **Detection for this scenario class must come from outside the database** — row-count monitors, replication-lag alarms, application error-rate spikes — not from the audit-log system this runbook and `database-restore.md` otherwise lean on for the post-restore security-state audit. **Tier C nuance correction (attack-surface lens): "blind for every table" overstates it slightly, and understates a worse gap.** `app.files` and `app.transaction_lineage_edges` each carry a narrow audit-capture exception on their own *legitimate* deletion path (a session authenticating as supreme admin, deleting a legal-hold-protected row, correctly captures an audit event on that specific code path) — so a raw `DELETE` against those 2 tables is not uniformly blind. But `database-restore.md` §4 item 4's own Tier C correction found the composed in-place restore procedure's `TRUNCATE` step bypasses even that narrow exception, on all 9 security/integrity-relevant tables including these 2 — `TRUNCATE` never routes through the trigger at all, regardless of which code path it would have taken. The real risk profile is more nuanced than "blind" or "protected": ordinary raw SQL is blind on most tables with a narrow exception on 2; the runbook's own sanctioned restore procedure is blind on all 9, always. Registered as `ISS-2026-259` (see §6), cross-referenced with `ISS-2026-265` (`database-restore.md` §4 item 4).

3. **Security incident — a genuinely real, RLS-enforced diagnosis surface exists, no Auth-service access needed.** `app.query_audit_logs`/`app.export_audit_logs` and `app.current_support_session` are live, callable, pure-Postgres RPCs — confirmed this checkpoint by actually running a diagnosis chain against a disposable database (see §7): a compromised identity's session/role/IP-allowlist history reconstructs correctly and completely from `app.audit_logs` alone. This is the one scenario where diagnosis does not depend on any infrastructure this sandbox lacks.

4. **Major outage / provider failure — no independent-of-Supabase health signal exists.** Per `01_MODULE_DEPENDENCY_MAP.md` R7 (cited at `HDN-382` §13.2), job queue, auth, and search are all Postgres-backed — a genuine Supabase-wide outage collapses every dependent surface at once, with no separate diagnostic path to distinguish "Supabase is down" from "our own code is broken." There is no runbook anywhere in this repository specifically for "the provider itself is unreachable," distinct from `database-restore.md`'s own restore mechanics, which all assume Supabase's control plane and Postgres server are reachable.

## 4. Resolution steps

**What is proven, live, this checkpoint (data corruption and a live-executable slice of security incident):**

1. **Data corruption — recover via `database-restore.md`'s own composed in-place restore procedure (§4 item 4 of that runbook), now fixed by this checkpoint's own live drill, itself further corrected at this checkpoint's own Tier C review.** Following the procedure exactly as first documented (batch-drop `app` schema → clear `auth.users` collisions → replay migrations → `pg_restore --data-only -j 4`) **failed live, with 80 silently-ignored errors** — two distinct, previously-undocumented causes: (a) migration-seeded reference/lookup tables (`finance_currencies`, `uoms`, `permissions`, `webhook_event_types`, and ~30 others) collide on primary key, since the migration replay re-seeds them and the backup being restored contains the identical rows; (b) a real parallel-restore FK race under `-j 4` — a dependent table's worker connection can commit before the table it depends on has committed in a different worker, silently leaving dependent tables (`users`, `api_keys`, `leads`, `org_units`, `principal_memberships`, and others) with **zero restored rows**, no error surfaced beyond a generic "errors ignored" count. **Fixed and re-verified live**: add a `TRUNCATE` (single statement, all `app.*` tables, `CASCADE`) immediately after migration replay, and pass `--disable-triggers` to `pg_restore --data-only` — 0 errors, every table verified with the correct row count. `database-restore.md` §4 item 4 has been updated in place with this fix and its own Tier C corrections (see that runbook's own §8 revision history, `0.4.0`) — **the `TRUNCATE` step, independently of `--disable-triggers`, was itself found at Tier C to silently bypass 9 security/integrity row-level triggers with zero audit trail** (`ISS-2026-265`), materialized views are never restored by `pg_restore --data-only` and need an explicit refresh step (`ISS-2026-266`), and no mutual-exclusion mechanism exists for two concurrent restore attempts (`ISS-2026-267`) — all three corrected directly in `database-restore.md` §4 item 4, not merely disclosed here. **Measured RTO for the full corrected procedure: a range, not a single figure** — first-round measurement ≈49.65s, 2 independent Tier C re-runs measured 56.88s and 59.74s (14-20% higher, driven by migration-replay variance) — cite ≈50-60s for this sandbox's own small seeded dataset, never a single point figure, and never extrapolated to production scale. **Measured RPO in this drill: 4m38s window** between the T0 backup and the simulated corruption — the correct, expected point-in-time-restore behavior (data created inside that window is lost; data created before it is not).
   - **The security-state-reversion risk (`ISS-2026-254`) applies identically to this in-place procedure, independently re-confirmed, not merely inherited.** Live-reproduced: revoked an API key, suspended a user, and placed a legal hold — all after the T0 backup point — then ran the corrected procedure to recover from the simulated corruption. All three security-state changes reverted silently (API key back to `active`, user back to `active`, legal hold gone entirely). Run the security-state-reversion precheck (`database-restore.md` §3 item 2) after every data-corruption recovery, regardless of which restore procedure was used.
   - **Post-recovery verification, live-confirmed correct**: target roles present (3/3), `select count(*) from pg_policies` returned the exact baseline count (448), schema whole (603 tables), and a real cross-tenant RLS probe (`set local role authenticated; set local request.jwt.claims=...`) confirmed each tenant sees only its own rows post-restore, with `service_role` correctly bypassing RLS. **Not verified in the first round, added at Tier C**: materialized views (e.g. `app.mv_report_usage_daily`) are silently left empty/stale post-restore unless explicitly refreshed (`database-restore.md` §4 item 4's own new step (h)) — add a materialized-view content check to this verification list going forward.

2. **Security incident — a real, live-executed revoke chain, but its own effectiveness is narrower than the first round claimed.** Diagnosed a simulated compromise (2 live sessions, 1 IP-allowlist entry, 1 published role assignment) via `app.query_audit_logs`, then resolved live: `app.revoke_all_actor_sessions` (2/2 sessions revoked in one call), `app.revoke_role_assignment` (re-confirmed via a fresh `app.evaluate_permission` call returning `allowed=false, reason='no_active_assignment'`, not merely trusted from the RPC's own return value), `app.revoke_ip_allowlist_entry` (confirmed via direct re-query of the underlying table).
   - **Tier C correction (attack-surface lens, live-reproduced): `app.revoke_all_actor_sessions`'s own session-status flip is pure bookkeeping — nothing in this codebase ever reads it.** A grep across all 329 migrations for `user_sessions` shows it referenced in exactly the one migration that creates the table. **No RLS policy, no RPC, and `app.evaluate_permission` itself never consults `app.user_sessions.status` anywhere.** The actual enforcement teeth `revoke_all_actor_sessions` has comes entirely from its own composed call to `app.revoke_api_key` where applicable — the session-status field itself has zero effect on anything. This directly contradicts `incident-response.md` §4 item 1's own framing ("stops future RPC calls that check session status") — no such RPC calls exist anywhere in this codebase to stop. **The real, effective lockout in this drill came entirely from `app.revoke_role_assignment` and `app.revoke_ip_allowlist_entry`** (both genuinely enforced, re-confirmed above) — a responder who revokes only sessions, a natural first reading of "cut off the attacker's access," would leave a still-valid JWT with full functional access indefinitely, since the role/membership underneath it remains intact. Registered as `ISS-2026-264`/`HDN-BLK-035` (High). **This runbook's own resolution step must always be: revoke the role assignment/tenant membership FIRST (the layer that is actually enforced), and treat session revocation as bookkeeping/audit-trail hygiene only, never as the primary lockout mechanism.**
   - All three RPCs are real, callable, RLS-enforced, with no dependency on the Supabase Auth service. **What is not live-testable here, disclosed rather than assumed**: actual JWT/refresh-token invalidation at the Supabase Auth-service level — that requires the Supabase Admin API, which this sandbox correctly avoids calling against the real project (see §3 item 1's own Tier C correction — it is reachable, but policy-forbidden for a rehearsal). Likewise, IP-allowlist enforcement that depends on a live HTTP request path is code-inspection-only here, not live-HTTP-tested (no app server reachable).

3. **Major outage — tabletop only, disclosed where the trail goes cold.** For the database specifically, `database-restore.md` is genuinely strong (real, live-timed schema and row-level restore procedures, explicit teardown-batching/`auth.users`-collision/target-role guidance). But: (a) **no automated detection or paging exists** — a responder has to already know to open `docs/runbooks/incident-response.md`/this runbook, since `app.raise_observability_alert`'s own `source_type` taxonomy (`job`/`webhook`/`api`/`integration`/`ai`) has no `infrastructure`/`provider` category and no live escalation dispatch even for what it does cover (`ISS-2026-251`, open — `owner_team`/`owner_email` fields on `app.alert_routes` are real but inert, no email/Slack/PagerDuty dispatch exists anywhere; see `ISS-2026-258`'s own cross-reference below); (b) **Storage restore, Auth-service-level restore, and any restore against the real hosted project remain untested and structurally infeasible in this sandbox** (`HDN-BLK-030`/`ISS-2026-255`, unchanged) — a responder would successfully rebuild schema and row data but have no tested procedure for restoring uploaded files or re-establishing Auth/session state; (c) **no customer-communication mechanism of any kind exists** (§5); (d) **Tier C addition — no mutual-exclusion mechanism exists for the composed in-place restore procedure a major-outage recovery would use** — a second responder starting the identical procedure concurrently, a realistic "on-call and their backup both jump in" scenario during a real outage, live-reproduced to race and abort a migration replay mid-script (`database-restore.md` §4 item 4's own Tier C correction, `ISS-2026-267`). Coordinate explicitly before starting the procedure; do not assume it is safe to retry from a second session.

4. **Provider failure — tabletop only, disclosed where the trail goes cold.** There is no CargoGrid-specific runbook for "Supabase itself is unreachable" as distinct from "our database has bad data" — every restore procedure in `database-restore.md` assumes Supabase's control plane and Postgres server are reachable to run `pg_dump`/`pg_restore`/migrations against. A genuine provider-wide outage has no tested playbook here; the responder would have to fall back entirely to Supabase's own status page/support channel, with the MVP-tier RPO/RTO promise (`docs/architecture/11_DEVOPS_WORKSTREAM.md` §8.1, 15-min/4-hr) resting on a Supabase-managed mechanism that was verified on 2026-09-01 and found NOT to be enabled: the project reports `pitr_enabled: false` with zero customer-restorable backups, on a free-plan organization where PITR is a paid add-on (`ISS-2026-256`, verification half closed, material half owner-required; re-derive with `pnpm run db:check-live-backup`). **The promise is not merely unconfirmed — it cannot currently be met.** **Tier C correction (attack-surface lens): the "no failover path" framing in §2/`ISS-2026-261` needs sharpening, not softening.** Supabase does offer a real cross-region mechanism (Read Replicas), confirmed via Supabase's own documentation — but it is gated to paid plans, and this repository's own organization is confirmed on the **free tier** (`get_organization`), so it is structurally unavailable today, not merely unconfigured. Even on a paid plan, Read Replicas explicitly do not serve Auth requests (all Auth traffic is handled by the Primary per Supabase's own documentation) and would not survive a full Primary outage — so upgrading the plan alone would not fully close this finding either. `ISS-2026-261` corrected accordingly (see §6).

Rollback procedure if any resolution fails: none of the above is destructive in a way that requires its own rollback beyond what `database-restore.md` §3/§4 already document (re-run the teardown batch script from scratch is itself the documented recovery from an interrupted attempt). Never leave a partially-torn-down `app` schema serving traffic — either complete the procedure or restore the pre-attempt backup.
