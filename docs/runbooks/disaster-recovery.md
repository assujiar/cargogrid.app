## 1. Symptom / trigger

Four distinct scenarios, each with its own detection signal, are in scope per Prompt 384 §4/§20:

1. **Major outage** — the app-hosting layer, Supabase Postgres, or the network path between them becomes unreachable for all tenants simultaneously. No automated detector exists for this in this repository today (see §3 item 1) — the first signal is realistically a human noticing (a customer report, a manual check), not an alert.
2. **Data corruption** — canonical `app.*` table rows become wrong, inconsistent, or violate integrity expectations while the infrastructure itself stays up (a bad migration, a bad manual intervention, or an application bug). Detected by a row-count/integrity anomaly, an application error spike, or — critically — **not** detected by `app.audit_logs` if the corrupting action bypassed every RPC function (see §3 item 2's own live-proved detection gap).
3. **Provider failure** — Supabase itself (the single managed backend vendor for Postgres, Auth, Storage, and the PostgREST gateway) has an outage or degradation independent of anything CargoGrid's own code does. Detected via `/api/ready`'s real `503 {"status":"degraded","reason":["database_unreachable"]}` response (built at `HDN-382`) when the failure specifically affects Postgres reachability — but that route's own failure path is fully unlogged server-side (`ISS-2026-253`, open), so a responder cannot distinguish this from any other exception by server logs alone.
4. **Security incident** — a compromised identity, session, credential, or channel, matching `docs/runbooks/incident-response.md`'s own scope exactly. Detected via `app.audit_logs`/`app.query_audit_logs` (a genuinely real, queryable trail for anything that went through an RPC function).

## 2. Impact

A major outage or provider failure is inherently **platform-wide** — every tenant is affected simultaneously, with no per-tenant mitigation possible. Data corruption and security incident are usually tenant- or table-scoped, but can be platform-wide depending on blast radius (a corrupting migration touches every tenant; a compromised Supreme Admin session touches every tenant). CargoGrid has **no second infrastructure vendor** for its core stack (Next.js app-hosting + one Supabase project covering Postgres/Auth/Storage/PostgREST) — this is a genuine, undisclosed-as-mitigated single point of failure for the major-outage and provider-failure scenarios specifically; nothing in `docs/architecture/` describes a multi-region or multi-vendor failover path. Registered as `ISS-2026-261` (see §6).

## 3. Diagnosis steps

1. **Confirm the sandbox/environment constraint before assuming any live mechanism is available.** Independently re-verified this checkpoint (not merely inherited from `HDN-380`/`HDN-383`): the Docker daemon is **absent entirely** in this environment (`docker ps` fails with "no such file or directory" — no socket at all, a step further than `HDN-380`'s reproducible `runc`/`RLIMIT_NOFILE` error), the Supabase CLI is not installed, and local Supabase gateway/Auth/Storage ports (54321-54324) are all closed. The real hosted project (`awdlicmwzdxquopwtcfd.supabase.co`) is reachable over HTTPS but `HARDENING_MATRIX.md` §14 item 6 forbids ever targeting it for a rehearsal. **The only live-executable substrate anywhere in this class of sandbox is raw Postgres** — real SQL, real `app.*` RPC calls, real RLS. Nothing requiring the Supabase Auth service, Storage service, or PostgREST gateway can be live-executed here, which is why major outage and provider failure stay tabletop-only for this checkpoint (§4 items 1/3).

2. **Data corruption — a real, live-proved detection gap: `app.audit_logs` is structurally blind to raw-SQL or infra-level corruption.** Live-reproduced: a direct `DELETE FROM app.leads;` (no `WHERE` clause — the classic accidental-bulk-delete incident) against a seeded disposable database left **zero rows** in `app.audit_logs` matching the event, because `app.capture_audit_event` only fires from inside RPC functions — a raw SQL statement (a botched migration, or a support engineer's direct psql intervention) bypasses it entirely. **Detection for this scenario class must come from outside the database** — row-count monitors, replication-lag alarms, application error-rate spikes — not from the audit-log system this runbook and `database-restore.md` otherwise lean on for the post-restore security-state audit. Registered as `ISS-2026-259` (see §6).

3. **Security incident — a genuinely real, RLS-enforced diagnosis surface exists, no Auth-service access needed.** `app.query_audit_logs`/`app.export_audit_logs` and `app.current_support_session` are live, callable, pure-Postgres RPCs — confirmed this checkpoint by actually running a diagnosis chain against a disposable database (see §7): a compromised identity's session/role/IP-allowlist history reconstructs correctly and completely from `app.audit_logs` alone. This is the one scenario where diagnosis does not depend on any infrastructure this sandbox lacks.

4. **Major outage / provider failure — no independent-of-Supabase health signal exists.** Per `01_MODULE_DEPENDENCY_MAP.md` R7 (cited at `HDN-382` §13.2), job queue, auth, and search are all Postgres-backed — a genuine Supabase-wide outage collapses every dependent surface at once, with no separate diagnostic path to distinguish "Supabase is down" from "our own code is broken." There is no runbook anywhere in this repository specifically for "the provider itself is unreachable," distinct from `database-restore.md`'s own restore mechanics, which all assume Supabase's control plane and Postgres server are reachable.

## 4. Resolution steps

**What is proven, live, this checkpoint (data corruption and a live-executable slice of security incident):**

1. **Data corruption — recover via `database-restore.md`'s own composed in-place restore procedure (§4 item 4 of that runbook), now fixed by this checkpoint's own live drill.** Following the procedure exactly as first documented (batch-drop `app` schema → clear `auth.users` collisions → replay migrations → `pg_restore --data-only -j 4`) **failed live, with 80 silently-ignored errors** — two distinct, previously-undocumented causes: (a) migration-seeded reference/lookup tables (`finance_currencies`, `uoms`, `permissions`, `webhook_event_types`, and ~30 others) collide on primary key, since the migration replay re-seeds them and the backup being restored contains the identical rows; (b) a real parallel-restore FK race under `-j 4` — a dependent table's worker connection can commit before the table it depends on has committed in a different worker, silently leaving dependent tables (`users`, `api_keys`, `leads`, `org_units`, `principal_memberships`, and others) with **zero restored rows**, no error surfaced beyond a generic "errors ignored" count. **Fixed and re-verified live**: add a `TRUNCATE` of every `app.*` table immediately after migration replay, and pass `--disable-triggers` to `pg_restore --data-only` — 0 errors, every table verified with the correct row count. `database-restore.md` §4 item 4 has been updated in place with this fix (see that runbook's own §8 revision history, `0.3.0`). **Measured RTO for the full corrected procedure: ≈49.65s** (batch-drop 1.789s + migration replay 45.316s + truncate 1.970s + restore 0.572s), the same order of magnitude as the drop-database variant's own ~44-46s + ~11s components. **Measured RPO in this drill: 4m38s window** between the T0 backup and the simulated corruption — the correct, expected point-in-time-restore behavior (data created inside that window is lost; data created before it is not).
   - **The security-state-reversion risk (`ISS-2026-254`) applies identically to this in-place procedure, independently re-confirmed, not merely inherited.** Live-reproduced: revoked an API key, suspended a user, and placed a legal hold — all after the T0 backup point — then ran the corrected procedure to recover from the simulated corruption. All three security-state changes reverted silently (API key back to `active`, user back to `active`, legal hold gone entirely). Run the security-state-reversion precheck (`database-restore.md` §3 item 2) after every data-corruption recovery, regardless of which restore procedure was used.
   - **Post-recovery verification, live-confirmed correct**: target roles present (3/3), `select count(*) from pg_policies` returned the exact baseline count (448), schema whole (603 tables), and a real cross-tenant RLS probe (`set local role authenticated; set local request.jwt.claims=...`) confirmed each tenant sees only its own rows post-restore, with `service_role` correctly bypassing RLS.

2. **Security incident — a real, live-executed revoke chain, confirmed effective.** Diagnosed a simulated compromise (2 live sessions, 1 IP-allowlist entry, 1 published role assignment) via `app.query_audit_logs`, then resolved live: `app.revoke_all_actor_sessions` (2/2 sessions revoked in one call), `app.revoke_role_assignment` (re-confirmed via a fresh `app.evaluate_permission` call returning `allowed=false, reason='no_active_assignment'`, not merely trusted from the RPC's own return value), `app.revoke_ip_allowlist_entry` (confirmed via direct re-query of the underlying table). All three real, callable, RLS-enforced RPCs with no dependency on the Supabase Auth service. **What is not live-testable here, disclosed rather than assumed**: actual JWT/refresh-token invalidation at the Supabase Auth-service level — `incident-response.md` §4 item 1 already discloses that revoking the `app.user_sessions` row does not itself invalidate a live Supabase JWT already in an attacker's hands; that requires the Supabase Admin API, unreachable in this sandbox. Likewise, IP-allowlist enforcement that depends on a live HTTP request path is code-inspection-only here, not live-HTTP-tested (no app server reachable).

3. **Major outage — tabletop only, disclosed where the trail goes cold.** For the database specifically, `database-restore.md` is genuinely strong (real, live-timed schema and row-level restore procedures, explicit teardown-batching/`auth.users`-collision/target-role guidance). But: (a) **no automated detection or paging exists** — a responder has to already know to open `docs/runbooks/incident-response.md`/this runbook, since `app.raise_observability_alert`'s own `source_type` taxonomy (`job`/`webhook`/`api`/`integration`/`ai`) has no `infrastructure`/`provider` category and no live escalation dispatch even for what it does cover (`ISS-2026-251`, open — `owner_team`/`owner_email` fields on `app.alert_routes` are real but inert, no email/Slack/PagerDuty dispatch exists anywhere); (b) **Storage restore, Auth-service-level restore, and any restore against the real hosted project remain untested and structurally infeasible in this sandbox** (`HDN-BLK-030`/`ISS-2026-255`, unchanged) — a responder would successfully rebuild schema and row data but have no tested procedure for restoring uploaded files or re-establishing Auth/session state; (c) **no customer-communication mechanism of any kind exists** (§5).

4. **Provider failure — tabletop only, disclosed where the trail goes cold.** There is no CargoGrid-specific runbook for "Supabase itself is unreachable" as distinct from "our database has bad data" — every restore procedure in `database-restore.md` assumes Supabase's control plane and Postgres server are reachable to run `pg_dump`/`pg_restore`/migrations against. A genuine provider-wide outage has no tested playbook here; the responder would have to fall back entirely to Supabase's own status page/support channel, with the MVP-tier RPO/RTO promise (`docs/architecture/11_DEVOPS_WORKSTREAM.md` §8.1, 15-min/4-hr) resting on a Supabase-managed mechanism that has never been operationally confirmed enabled on the real hosted project (`ISS-2026-256`, open, unchanged).

Rollback procedure if any resolution fails: none of the above is destructive in a way that requires its own rollback beyond what `database-restore.md` §3/§4 already document (re-run the teardown batch script from scratch is itself the documented recovery from an interrupted attempt). Never leave a partially-torn-down `app` schema serving traffic — either complete the procedure or restore the pre-attempt backup.

## 5. Communication

**No real, concrete DR communication mechanism exists anywhere in this repository — confirmed by reading every runbook, not inferred.** All 12 files in `docs/runbooks/` share the identical Communication-section shape: "notify DevOps/Security lead" or "notify DevOps/on-call," with no named individual, no channel (no Slack/PagerDuty/email/SMS integration), no notification order, and no customer-facing message template. `docs/architecture/11_DEVOPS_WORKSTREAM.md` §8.4 describes a designed-but-never-built incident/communication contract (6 support tiers, P1-P4 SLAs, an "Owner/Incident Commander" field, a defined Detect→Triage→Severity→Mitigation→Communication→Validation→Close→RCA flow) — this is architecture-planning prose, not an implemented mechanism; nothing in the actual codebase assigns an incident commander, tracks an SLA clock, or executes a communication step. **No customer-impact assessment tool exists at all** — a broad search (`customer_impact`, `status_page`, `service_status`, `maintenance_window`, `tenant_notification`, `broadcast_notice`, `system_status`) across `app/`, `server/`, and every migration returned zero matches. Registered as `ISS-2026-258` (see §6).

**Backup-file handling** (inherited from `database-restore.md` §5, applies identically to any DR event that touches a backup): a backup file carries the same confidentiality risk as the live secrets it contains (`ISS-2026-257`) — never distribute one through an incident channel or attach it to a ticket accessible to anyone not already entitled to raw webhook/integration secrets.

## 6. Post-incident

Record: which of the 4 scenarios was rehearsed/real, the detection method, whether the security-state-reversion precheck (data corruption) or session/role/IP revoke chain (security incident) was exercised, real observed RTO/RPO, and — for a genuine future drill against a real environment — call `app.record_dr_restore_test` (`IAE-035`) with real observed figures.

**A real, structural gap found this checkpoint: `app.record_dr_restore_test`'s own `p_component_scope` CHECK constraint (`'database'|'secrets'|'backup'|'observability'|'jobs_integrations'`) has no slot for 3 of the 4 DR scenarios this runbook covers.** It is a component/mechanism taxonomy (what part of the system was restored), not a scenario taxonomy. Data corruption maps reasonably to `'database'`/`'backup'`. Security incident, provider failure, and major outage have no natural slot — recording evidence for those would have to be shoehorned into an ill-fitting component scope, losing the scenario framing entirely. Registered as `ISS-2026-260` (see below). **This checkpoint's own live drills were executed against a throwaway disposable sandbox database, not a real deployed environment** — recording them via `app.record_dr_restore_test` would create records with no lasting evidence value, matching `database-restore.md` §6's own established discipline against fabricated pass evidence; the correct next real drill, against a genuine environment, should call this RPC with its own real figures.

**Findings registered this checkpoint** (`docs/runtime/KNOWN_ISSUES.md`):

- `ISS-2026-258` (High) — no DR communication mechanism exists (channel, template, notification order, customer-impact assessment).
- `ISS-2026-259` (Medium) — `app.audit_logs` cannot detect raw-SQL/infra-level data corruption; detection for this scenario class must come from external monitoring.
- `ISS-2026-260` (Medium) — `app.record_dr_restore_test`'s `component_scope` enum has no slot for 3 of the 4 DR scenarios.
- `ISS-2026-261` (High) — CargoGrid has no second infrastructure vendor; a genuine Supabase-wide outage has no failover path, only a wait-and-restore posture bounded by Supabase's own unconfirmed SLA.
- `ISS-2026-262` (Low) — `11_DEVOPS_WORKSTREAM.md` §8.5's own runbook catalogue names 6 files that do not exist anywhere in `docs/runbooks/` under those names.
- `ISS-2026-263` (Low) — an unreproduced anomaly in `app.transition_user_status` observed during this checkpoint's own live drill (2 identical calls failed with a CHECK-constraint violation naming a spurious `event_type`, a 3rd identical call then succeeded) — flagged for investigation, not confirmed as a defect.
