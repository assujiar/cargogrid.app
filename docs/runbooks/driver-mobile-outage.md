> Covers `POST /api/tracking/driver-mobile` (`app/api/tracking/driver-mobile/route.ts`, `ATW-226C`) and the `app.ingest_driver_mobile_report` RPC it calls — session/token issues, consent-check failures, and rate-limiting lockout specifically. It does **not** cover a Supabase-layer database outage affecting this same endpoint (`docs/runbooks/gps-ingestion-database-outage.md` already covers that, across all three ingestion modes) or the direct-device/third-party paths (`docs/runbooks/gps-gateway-outage.md`, `docs/runbooks/third-party-provider-outage.md`).

## 1. Symptom / trigger

A driver's mobile session stops accepting location reports: the HTTPS endpoint returns `401` with `{"ingestStatus":"invalid"}` (session/token/consent-class failures) or `429` with `{"ingestStatus":"rate_limited"}` (rate-limit lockout) instead of `200 {"ingestStatus":"ok", ...}`. From the RPC's own perspective (`app.ingest_driver_mobile_report`, `supabase/migrations/20260730360000_harden_advanced_tms_device_driver_mobile_tracking.sql`), every one of these outcomes is a clean returned status row — the function is documented to **never raise** for a per-request validation/business outcome, only a genuine transport-layer error would surface as an unhandled exception.

## 2. Impact

**Confined to the one driver/session in question — never tenant-wide, and never affects any other source type for the same vehicle.** A `driver_mobile` session failing to ingest does not touch `direct_device` or `third_party_platform` telemetry for that same vehicle; if a lower-priority source is configured and healthy, `app.arbitrate_and_project_vehicle_position` falls back to it per the tenant's own source policy. If `driver_mobile` is a vehicle's *only* configured source, that vehicle's current position simply goes stale (`app.vehicle_source_health` ages past `freshness_threshold_seconds`) until the session recovers.

**No local buffering exists for this path** (a real, disclosed limitation, not an oversight): unlike the GPS Gateway's own durable local buffer (`docs/build-log/phase-05/queue-dlq-replay-reconciliation-procedure.md` §3), a browser tab has no durable local storage for this purpose. A failed request is simply not ingested — the next successful report resumes the session; there is nothing to replay, because nothing was ever accepted server-side to begin with (`docs/runbooks/gps-ingestion-database-outage.md` §2's own identical framing for this source).

## 3. Diagnosis steps

Distinguish the three failure classes below by directly inspecting the relevant rows — do not guess from the HTTP status code alone, since `401` covers several distinct causes:

1. **Session/token issue** — query `app.driver_mobile_tracking_sessions` for the session in question: `status <> 'active'` (revoked) or `expires_at <= now()` (expired) both produce `invalid`. Confirm which by reading the row directly; the HTTPS response itself never distinguishes "no such token," "revoked," and "expired" from each other (`app.ingest_driver_mobile_report`'s own anti-enumeration design — a distinguishable error class/timing for an unauthenticated caller would itself be a security gap, the identical reasoning `app.lookup_public_shipment_tracking`, `OPS-180`, already established).
2. **Underlying tracking-session issue** — even with a valid, unexpired token, `app.ingest_driver_mobile_report` also live-checks the *owning* `app.shipment_leg_tracking_sessions` row's own `is_current`/`status = 'active'`. If a dispatcher already ended or handed off that leg's tracking session on the `ATW-225` side, ingestion stops the instant that happens — this is real-time consistency by design, not a bug, and no driver-mobile-specific action fixes it; the leg's own tracking session must be re-evaluated instead (`ATW-225`'s own capability).
3. **Consent revoked mid-session** (`CG-S10-ATW-027`, finding 4) — query `app.driver_operational_profiles` for the session's own driver (`app.shipment_leg_tracking_sessions.resource_master_id`): `status <> 'active'` or `mobile_tracking_consent = false` both now produce `invalid`, live-rechecked on **every** call, not merely once at session start. Before this hardening, revoking consent via `app.set_driver_mobile_tracking_consent` did not stop an already-issued session from continuing to ingest location — confirm the driver's own current consent value directly rather than assuming a prior "consent granted" state still holds.
4. **Malformed location** (`CG-S10-ATW-027`, finding 5) — a `location` report with out-of-range or malformed coordinates now also returns a clean `invalid` (previously this could raise uncaught and skip rate-limit bookkeeping entirely — see point 5). If a specific driver's device is producing garbage coordinates repeatedly, this now shows up as ordinary `invalid` attempts rather than a silent gap.
5. **Rate-limit lockout** — query `app.driver_mobile_ingestion_attempts` for the session's own `client_key` (a SHA-256 hash of the caller's best-effort IP, computed server-side — not the raw IP): 10 or more rows with `result = 'invalid'` inside the trailing 15 minutes (`occurred_at > now() - interval '15 minutes'`) trips `rate_limited` on the very next attempt, and every `rate_limited` response itself also inserts its own bookkeeping row. Distinguish "a device is legitimately misconfigured and repeatedly failing validation" (points 1–4 above, now correctly recorded even for the previously-uncaught geography case) from "a client_key is being reused across genuinely different devices/drivers behind the same NAT/proxy" (a real, disclosed possibility since `client_key` is IP-derived, not device-bound).

## 4. Resolution steps

1. **Expired or revoked token**: re-issue via `app.start_driver_mobile_session(p_shipment_leg_tracking_session_id, p_validity_hours, p_actor_auth_user_id, p_actor_label)` — `OPS:Edit`, and the actor must also pass the same record-access check (`app.can_access_record`) `ATW-225`'s own session-start RPCs already require. `p_validity_hours` must be between 1 and 168 (7 days) or the call is rejected `invalid_validity_hours`. If a session is still `active`, starting a new one is rejected (`driver_mobile_session_already_issued`) — revoke the old one first: `app.revoke_driver_mobile_session(p_shipment_leg_tracking_session_id, p_reason, p_actor_auth_user_id, p_actor_label)` (a non-empty reason is mandatory). The new raw token (`dmt_` prefix, 64 hex characters) is returned exactly once, in the call's own return row — there is no way to retrieve it again afterward. **Transmitting the new token to the driver's own device (QR code, SMS, or otherwise) is out of this repository's scope entirely** (`docs/build-log/phase-05/ATW-226C.md` §5) — this runbook covers issuing the credential, not the out-of-band handoff to the driver.
2. **Underlying tracking session ended/handed off**: this is not a driver-mobile-specific fix — confirm with the dispatcher whether the leg's own tracking session should be restarted (`ATW-225`'s own `app.start_leg_tracking_session`), and only then re-issue a driver-mobile session (step 1) against the new one.
3. **Consent revoked**: confirm with the driver/operations whether the revocation was intentional. If it was a mistake, `app.set_driver_mobile_tracking_consent(p_driver_profile_id, p_consent := true, p_expected_version, p_actor_auth_user_id, p_actor_label)` — `OPS:Edit` — restores it; `mobile_tracking_consent_at` is set to `now()` the moment consent is granted (and cleared to `null` the moment it is withdrawn). If the revocation was intentional (the driver withdrew consent, or off-boarded), do **not** restore it and do not re-issue a session — this is the control working as designed, not an outage.
4. **Rate-limit lockout**: **there is no manual override or reset RPC for `app.driver_mobile_ingestion_attempts` anywhere in this schema** — confirmed by direct inspection; no function truncates, deletes, or otherwise clears this table. The window is rolling, not fixed: each `invalid`/`rate_limited` row stops counting toward the limit 15 minutes after its own `occurred_at`, so the lockout clears on its own without intervention once bad attempts stop recurring. If the underlying cause is a genuinely misconfigured device retrying the same bad request in a loop, fix the underlying cause (steps 1–3 above) — the count will not clear meaningfully while the device keeps generating fresh `invalid` attempts every retry.
5. **Rollback procedure if resolution fails**: revoke the session (`app.revoke_driver_mobile_session`) rather than leaving a token active that keeps failing — a revoked session fails cleanly and predictably (`invalid`, matching point 1's diagnosis) rather than continuing to generate ambiguous rate-limit bookkeeping noise. No data rollback is ever needed at the database layer: every failure path here returns a clean status row before any raw report is ever inserted (the sole exception, malformed coordinates, is now also caught cleanly per §3 point 4 — nothing is left partially written).

## 5. Communication

Today: none required — no Driver PWA frontend exists, so no real driver has ever hit this path (this runbook's own "Severity class" disclosure, above). Once a Driver PWA ships: notify the affected driver's own dispatcher if a session needs re-issuing (they hold `OPS:Edit` and the shipment's own record-access grant already required to call `app.start_driver_mobile_session`); no customer-facing communication is warranted unless the affected leg carries a `customer_visible` tracking policy (`app.shipment_leg_tracking_policies`, `ATW-225`) for an active shipment and the outage is long enough to visibly stale the customer's own tracking view.

## 6. Post-incident

Confirm the new session's own first few reports return `ok` (not `invalid`/`rate_limited`), and that `app.driver_mobile_ingestion_attempts` shows a clean run of `success` rows for the new `client_key`/session going forward. If the root cause was a driver-facing app bug (not consent/session/rate-limit itself) — e.g. the device retrying a malformed payload — confirm that is tracked as its own client-side defect, not silently absorbed into this runbook's own scope.
