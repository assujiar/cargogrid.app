## 1. Symptom / trigger

**Scheduled:** a routine backup/restore-evidence rehearsal (this checkpoint, and `HDN-384`'s own upstream dependency on this runbook's proven procedure). **Real:** a genuine data-loss or corruption event requiring recovery — treat as immediate, coordinate with `docs/runbooks/incident-response.md` if the cause is a security incident rather than infrastructure failure.

## 2. Impact

Scope per Prompt 383 §24/`HARDENING_MATRIX.md` §14 item 4: database, files, configuration, secrets, jobs, deployment state. A restore is inherently **platform-wide**, not tenant-scoped — unlike every other runbook in this directory, there is no single-tenant framing here; restoring the database restores every tenant's data simultaneously (or none).

**Tier C correction (attack-surface adversarial testing lens, live-reproduced): a real database backup contains plaintext secret VALUES, not merely references.** The first-round text here claimed secrets are covered only "as references (never secret values)," mirroring `docs/runbooks/key-rotation.md` §4.2's own "credential value never in export" discipline — but that discipline governs *application-level* exports/audit payloads (which correctly never `SELECT` a raw credential column into a response or log). A full-database `pg_dump`/`pg_restore` is a structurally different mechanism: it operates at the superuser/table-owner level, bypasses RLS and grants entirely, and captures literal row bytes regardless of any application-layer protection. Live-proved: `app.integration_connection_credentials.credential_value`, `app.third_party_provider_connections.webhook_secret_value`, and `app.webhook_endpoints.secret_value` are all stored **retrievable, non-hashed, by explicit design** (the `third_party_provider_connections` migration states outright a signing secret "must be stored in retrievable form... never a one-way hash") — a canary value inserted into `secret_value` survived a full `pg_dump -Fc` → `pg_restore --data-only` cycle verbatim. **Treat every backup file with the same handling discipline as the secrets themselves** (access control, encryption at rest/in transit, retention per RPD-025) — a backup file is not a safe artifact to hand to anyone who wouldn't otherwise be trusted with every tenant's webhook signing secrets and integration credentials. This gap (no encryption-at-rest for these specific columns, unlike `app.vendor_financial_encryption_key()`/`pgp_sym_encrypt()`'s already-established pattern for vendor bank-account/tax-ID columns) is registered, not fixed by this checkpoint — see `KNOWN_ISSUES.md` `ISS-2026-257`.

## 3. Diagnosis steps

1. Identify the target restore point and confirm it is **never the live project's data** for a rehearsal (`HARDENING_MATRIX.md` §14 item 6) — state the target explicitly before executing anything.
2. **Security-state-reversion precheck (real, non-obvious risk; widened at this checkpoint's own Tier C review, still not compensated for anywhere in this repository — `ISS-2026-254`):** any deliberate security/compliance decision recorded as ordinary application data in the same schema being restored is silently *reverted* by restoring to a point before that decision was made. Live-reproduced for three distinct, previously-undisclosed cases, not merely reasoned about:
   - **Legal holds** (`app.legal_holds`) — restoring to before a hold was `placed_at` produces a database that has never heard of it; `app._is_under_legal_hold()` returns `false`, any archive/delete action correctly refused pre-restore (`blocked_legal_hold`) would silently succeed if re-attempted post-restore, and the `app.retention_archive_requests` refusal evidence is erased along with the hold.
   - **Revoked API keys / disabled webhook endpoints** (`app.api_keys.status`, `app.webhook_endpoints.status`) — live-proved: revoke a key (e.g. a suspected-compromised credential, per `docs/runbooks/key-rotation.md`), take no further action, restore a pre-revocation backup — the key comes back `status='active'`, fully authenticating again, `revoked_at`/`revoked_reason` both `NULL`.
   - **Suspended/offboarded user access** (`app.users.status`, `app.principal_memberships.status`) — live-proved: suspend an offboarded employee's account, restore a pre-suspension backup — the account comes back `status='active'`, access silently restored. Arguably the highest-blast-radius instance of this shape, since offboarding is a far more common operational event than a legal hold.
   
   **Ruled out, not the same risk (re-derived from the actual function bodies, not assumed from naming)**: IP-allowlist bypass grants (`app.has_active_ip_allowlist_bypass`) and MFA exceptions (`app.consume_mfa_exception`) both re-evaluate expiry live against `now()` on every read rather than trusting a stored terminal state, so a restored backup cannot resurrect an already-expired grant — one narrow residual: an MFA exception consumed (`'approved'→'used'`) between the backup point and the exception's own short-lived `expires_at` could theoretically be replayed if that exact window is restored into; bounded and Low severity, not the same indefinite-exposure shape as the three cases above.
   
   **No platform-wide compensating control exists today for any of the three real cases** — this repository's only read path for legal holds (`app.list_legal_holds_for_tenant`) is single-tenant, and no export tool of any kind exists for API-key/webhook/user-status state either. **The "cross-check against an independent export" mitigation this section previously suggested does not currently have a real tool to execute it with, and even if one existed, it would need a freshness bound** — an export taken before a hold/revocation/suspension was applied is exactly as blind to it as the restore itself. Until a real, platform-wide, live-queried precheck tool exists, treat any restore as requiring manual escalation and a full post-restore audit of every open legal hold, revoked credential, and suspended account made **after** the restore point, cross-checked against `app.audit_logs`/`app.capture_audit_event` history for the affected window (the one real, already-existing evidence source for "what security decisions were made since this restore point").
   - **`ISS-2026-254` partial resolution (Step 16 historical-issue-backlog remediation, 2026-08-25): a real, voluntary compensating control now exists — use it.** Before starting any restore, call `app.capture_security_state_snapshot(p_actor_label text)` (`supabase/migrations/20260826080000_harden_restore_security_state_reconciliation.sql`) and record the returned snapshot `id` — it captures the current IDs of every active legal hold, revoked API key, disabled webhook endpoint, and suspended/revoked user/membership into `public.security_state_snapshots` (deliberately in `public`, not `app`, so it survives step (a)'s `app`-schema drop below). After the restore completes, call `app.detect_reverted_security_state(p_snapshot_id uuid)` with that same id — it returns one row per legal hold/API key/webhook endpoint/user/membership from the snapshot that no longer holds true post-restore, a real live comparison rather than the manual audit-log cross-check above. **This is voluntary, not enforced** — no mechanism forces an operator to call it, since the actual restore procedure runs entirely outside any RPC this schema controls (raw `psql`/`pg_restore`); the manual post-restore audit above remains the fallback for a restore where no snapshot was taken.
3. Confirm which of the environmental constraints below apply and plan around them — all were re-verified **live** at this checkpoint, not merely re-read from the seeded description:
   - **Teardown-batching**: `HARDENING_MATRIX.md` §14 item 1's own "~1,400 objects" threshold is now **stale and understated**. Live schema census at this checkpoint: 603 tables, 2,149 indexes, 4,636 constraints (via `pg_constraint`, not `information_schema.table_constraints`, which over-counts `CHECK` constraints roughly 1.5×), 2,701 functions, 1,316 types, 305 triggers (via `pg_trigger`, non-internal; `information_schema.triggers` over-counts multi-event triggers), 37 views, 1 matview, 448 RLS policies — tables+indexes+views+matviews+sequences+triggers alone already total 3,098, well over double the old figure. `DROP SCHEMA app CASCADE` in one transaction was reproduced live and still fails identically: `ERROR: 53200: out of shared memory`, `HINT: You might need to increase max_locks_per_transaction`, rolling back cleanly with the schema intact. A working batching strategy was tested live: order all tables by **ascending inbound-FK count** (leaves first, `app.tenants` — 524 inbound FK references — last), issue one `DROP TABLE IF EXISTS ... CASCADE;` per table as separate auto-committed statements (no explicit transaction wrapper), then a final `DROP SCHEMA app CASCADE` to sweep remaining free-standing objects. Measured: **1.96s, 0 errors.** The algorithm (ascending-FK-order, per-statement auto-commit), not the specific object counts, is the durable fix — the counts will keep growing as future checkpoints/features add migrations. **Live-tested against a real circular-FK pair** (11 exist in the real schema today, e.g. `app.leads`↔`app.prospects`) — held up with no defect, since `DROP TABLE ... CASCADE` on one side of a cycle only cascades away the dependent FK *constraint*, never the other table, so no true blocking cycle exists at the DDL level. **Interruption mid-batch is a real, confirmed gap**: stopping partway through (e.g. 300 of 603 tables dropped) and then running only the documented final `DROP SCHEMA app CASCADE` sweep reproduces the *original* `53200` failure — 303 interdependent tables is still too many for one transaction. Correct resume procedure (live-verified): re-run the entire per-table batch script from scratch — safe because every statement is `IF EXISTS`, so already-dropped tables are free no-ops — then run the final sweep.
   - **Migrations are not idempotent** (`HARDENING_MATRIX.md` §14 item 2, unchanged) — `supabase_migrations.schema_migrations` is the only re-run guard.
   - **`auth.users` survives an `app`-schema reset and reruns collide on `users_pkey`** (`HARDENING_MATRIX.md` §14 item 3) — reproduced live and exactly: after a batched `app`-only teardown (schema `app` fully removed, `auth` untouched) and a full 329-migration replay, re-inserting the same `auth.users` id/email fails with `ERROR: duplicate key value violates unique constraint "users_pkey"`. Any restore/rerun cycle must explicitly clear `auth.users` in teardown or this blocks re-provisioning.
4. **Target-role precondition (real gap found and live-reproduced at Tier C)**: before restoring with owner/privileges included (§4 item 3's own fix for the `--no-owner`/`--no-privileges` footgun), confirm the target Postgres instance already has `anon`/`authenticated`/`service_role` provisioned identically to the source. Live-reproduced: restoring into a target where those roles don't yet exist does **not** fail cleanly — `pg_restore` exits with ~4,500 individual `role "..." does not exist` errors (easy to mistake for scrolling noise in an automated script), but all 603 tables and their row data restore successfully anyway, while **every single RLS policy silently fails to create and is skipped** (`select count(*) from pg_policies` → 0, even though RLS remains *enabled* on every table). This is fail-closed (no policies + no roles = inaccessible, not a bypass) but the data looks fully present and correct while the actual defect (zero RLS policies) requires a deliberate audit to notice. **Never skip this check** when restoring across different Postgres instances/projects — exactly the cross-environment scenario a real disaster recovery involves.

## 4. Resolution steps

**What is proven, live, this checkpoint (schema and row-level database recovery only):**

1. **Schema/structure recovery** (clean migration replay) — `scripts/db-tests/lib/setup-disposable-db.sh`'s own pattern (drop/create db, mirror Supabase's `search_path`/roles, apply all `supabase/migrations/*.sql` in order). Measured across 3 independent runs: **43.70s / 44.79s / 46.34s**, 0 errors each time, converging on **603 tables, 2,701 functions, 448 RLS policies** consistently. This is the same mechanism `scripts/db-tests/run.sh` exercises on every checkpoint and `HARDENING_MATRIX.md` §16 (`HDN-385`) independently cites as proven against both disposable databases and the real hosted project (306/306 migrations at the time of that citation) — it is real, repeated, already-proven evidence for schema/structure recovery specifically, now also explicitly cited here as HDN-383's own baseline RTO figure for structure-only rebuild: **~44–46 seconds from empty database to fully-migrated schema.**
2. **Row-level data recovery** (`pg_dump`/`pg_restore`) — seeded a representative slice (2 tenants, 2 users, 1 pending + 1 dead-lettered job, mirroring `scripts/db-tests/background-job.sql`'s own fixture pattern) onto a freshly migrated database, then: `pg_dump -Fc` (owner+privileges **included** — see the footgun below) → `DROP DATABASE` → `CREATE DATABASE` → `pg_restore -j 4`. Measured: dump 1.56s, teardown 0.66s, create 0.09s, restore 9.28s — **~11.6s total cycle, 0 errors.** Verified post-restore, all exact: object counts identical (603/2701/448); row counts identical (2 tenants, 2 users, 2 jobs, 2 `auth.users`); **job state preserved byte-for-byte** (`job_id`, `status`, `attempts`, `next_attempt_at`, `idempotency_key`, timestamps to the microsecond) — directly satisfies business rule §24's "restored jobs/webhooks must not replay duplicate transactions," since job state is ordinary table rows and the restore reproduced it exactly; RLS spot-checked post-restore via `request.jwt.claims`/`set local role` (a tenant member sees only their own tenant's jobs, a different tenant's admin sees zero rows, `service_role` bypasses correctly, `anon` is denied) — RLS is fully functional immediately post-restore **for a same-migration-version restore** (backup and target both at the current migration state), because RLS policies are `CREATE POLICY` statements committed inside the same migrations that just replayed (confirmed no imperative `ALTER POLICY`/`GRANT` path exists anywhere outside `supabase/migrations/*.sql`).
   - **Tier C correction (attack-surface lens, live-reproduced): this claim does NOT extend to a version-skewed restore** — restoring a backup taken at an *older* migration point than the target's expected current state. Live-reproduced using a real hardening migration (`20260810500000_harden_own_row_rls_membership_gap.sql`, fixing `ISS-2026-171`/`173` — a revoked ex-member could still read their own past rows): built a database at migration 311/329 (pre-fix), seeded a membership, revoked it, confirmed the pre-fix RLS bug was live-exploitable (a revoked user still saw 1 row); dumped and restored that pre-fix state — **the vulnerability restored right along with the data** (still 1 visible row), mechanically flawless restore, security regression carried forward intact. Applying the remaining migrations forward (catch-up replay) on the restored database closed the gap correctly (0 visible rows after). **Any restore from a backup older than the target's current migration state MUST be followed by a full forward migration replay to the current state before the database is considered safe to serve real traffic** — there is an undocumented window between restore completion and catch-up-migration completion during which the database runs under stale, already-superseded RLS policy. This is not optional and is not covered by "RLS is fully functional immediately post-restore" as stated in the first-round text.
3. **Known footgun, found live at this checkpoint**: a first `pg_dump` attempt used `--no-owner --no-privileges` (a common "avoid restore hiccups" habit) — this **silently stripped the schema/table `GRANT`s RLS itself sits on top of**, and the restored database returned a blanket `permission denied for schema app` for every role instead of RLS-scoped results. **Never pass `--no-owner`/`--no-privileges` to a real restore** — RLS enforcement becomes unreachable even though the policies themselves restore correctly, a silent, hard-to-diagnose failure mode.
   - **Tier C correction: including owner/privileges is necessary but not sufficient.** See §3 item 4 — restoring with owner/privileges into a target whose `anon`/`authenticated`/`service_role` roles don't already exist silently drops every RLS policy while the data restores successfully, the opposite failure mode from the one this footgun originally describes, equally silent. Verify target roles exist (§3 item 4) **and** verify `select count(*) from pg_policies` returns a real, non-zero count matching the source's own 448 (or current figure) immediately after any restore, before considering it complete.
4. **Composed in-place restore procedure** (Tier C addition, schema-wide completeness sweep lens — the two proven procedures above both sidestep `auth.users`/teardown-batching by dropping the whole database; a real hosted Supabase project cannot do that, only reset within schemas it owns, which is exactly the scenario `HARDENING_MATRIX.md` §15 tells `HDN-384` to inherit "verbatim"): for an `app`-schema-only restore where the database itself cannot be dropped, the composed sequence is: **(0) acquire the mutual-exclusion advisory lock, in a dedicated session held open for the whole procedure** (added — see the `ISS-2026-267` resolution below for why this must run first, before step (a), and exactly how); (a) batch-drop the `app` schema per §3 item 3's tested strategy; (b) explicitly clear any colliding `auth.users` rows per §3 item 3's own collision finding, before replaying migrations, not after; (c) replay all migrations to rebuild `app`'s structure; **(d) `TRUNCATE` every restored `app.*` table, in a single statement with `CASCADE`, before loading data** (added — see the Tier C corrections below for the exact invocation and its own real side effects); (e) restore data via `pg_restore --data-only --disable-triggers` (structure already rebuilt by the migration replay, so a full structure+data restore would conflict) with owner/privileges included; (f) verify target roles per §3 item 4 and the `pg_policies` count per item 3 above; (g) if the data being restored predates the target's current migration state, complete the catch-up replay per item 2's own correction before serving traffic; **(h) call `app.refresh_all_registered_analytics_views` to refresh every registered `app` materialized view** (added at Tier C — `pg_restore --data-only` does not restore materialized view contents at all; `ISS-2026-266`'s own resolution replaced the original raw per-view `REFRESH MATERIALIZED VIEW CONCURRENTLY` instruction with this governed, ledgered RPC); **(i) release the advisory lock acquired at step (0)** (added — see the `ISS-2026-267` resolution below); **(j) record a single explicit audit event for this restore** (added — see the `ISS-2026-265` resolution below).
   - **`HDN-384` correction (live DR rehearsal execution lens, live-reproduced): following steps (a)-(c) then a plain `pg_restore --data-only -j 4` FAILS with errors silently ignored, not a clean restore.** A live drill measured **80 silent errors** (`pg_restore: warning: errors ignored on restore: 80` — easy to miss, the same "errors ignored" shape already warned about for the target-role gap in §3 item 4) from two distinct, previously-undocumented causes: (1) **PK collisions on migration-seeded reference/lookup tables** — roughly 30 tables (`finance_currencies`, `uoms`, `permissions`, `ticket_status_transitions`, `config_objects`, `entitlement_modules`, `webhook_event_types`, and others) are seeded by the migrations themselves; step (c)'s own migration replay re-creates that seed data, and the backup being restored (a full `pg_dump` of the whole database) contains the identical rows, so `pg_restore --data-only`'s `COPY` collides on the primary key; (2) **a real parallel-restore FK race** — `-j 4` runs each table's `COPY` in a separate worker connection/transaction against a schema whose FK constraints are already live (unlike a from-scratch restore, where constraints are added only after data load); a dependent table's worker (`users`, `api_keys`, `leads`, `org_units`, `principal_memberships`, `tenant_user_identities`, and others) can commit before the table it depends on has committed in a different worker, silently leaving the dependent table with **zero restored rows** — live-reproduced with `tenants` restoring correctly (2/2 rows) while 6+ dependent tables restored with 0 rows, no error surfaced beyond the same generic "errors ignored" count. **Fixed and re-verified live**: `TRUNCATE` every `app.*` table immediately after migration replay, then `pg_restore --data-only --disable-triggers -j 4` — **0 errors**, every table verified with the correct row count. **Never trust `pg_restore`'s exit code or "N errors ignored" summary alone as a pass signal** — grep the restore log for `COPY failed` and verify row counts per table against the source.
   - **Tier C correction (schema-completeness sweep + attack-surface lenses, live-reproduced): step (d)'s own "`TRUNCATE` every `app.*` table" instruction is not directly executable as literally written, and — independent of `--disable-triggers` — silently defeats every row-level integrity/audit trigger in the schema, not merely FK enforcement.** `TRUNCATE app.<table>;` issued table-by-table fails immediately on the first FK-referenced table (`ERROR: cannot truncate a table referenced in a foreign key constraint`) — the correct, working invocation is a **single statement listing every `app.*` table together with `CASCADE`** (e.g. build the table list dynamically via `select string_agg(quote_ident(schemaname)||'.'||quote_ident(tablename), ', ') from pg_tables where schemaname = 'app'` and issue one `TRUNCATE <list> CASCADE;`), not a per-table loop. Separately, and more seriously: `TRUNCATE` never fires `FOR EACH ROW` triggers at all (standard, documented Postgres behavior) — this is a property of `TRUNCATE` itself, not of `--disable-triggers` on the later `pg_restore` step. Live-proved: inserted a `status='posted'` row into `app.finance_journals` (protected by a `BEFORE DELETE OR UPDATE` guard trigger that correctly blocks a plain `DELETE` with `finance_journal_posted_immutable`); `TRUNCATE app.finance_journals CASCADE;` on the same row **succeeded silently, 0 errors**, and left **zero rows in `app.audit_logs`** even though the same trigger function calls `app.capture_audit_event` on its own legitimate-deletion exception path. **9 tables carry a security/integrity-relevant `BEFORE DELETE` row trigger silently defeated by step (d)**: `app.files` (legal-hold delete protection, RPD-025), `app.finance_journals`/`app.finance_journal_lines` (posted-journal immutability, RPD-022/FIN-204), `app.loyalty_earning_events`/`app.loyalty_point_ledger_entries`/`app.loyalty_benefit_entitlement_events`/`app.loyalty_reward_stock_reservations`/`app.loyalty_redemption_events` (append-only ledger guarantees, CPL-325), `app.transaction_lineage_edges` (append-only lineage guarantee, HDN-375/OPS-184). Two of the nine (`app.files`, `app.transaction_lineage_edges`) have a narrow audit-capture exception on their own legitimate-deletion path when a session authenticates as supreme admin — but a `TRUNCATE`-based restore is blind even there, since `TRUNCATE` bypasses the trigger entirely rather than taking any code path through it. **If the restore is interrupted after step (d) completes but before step (e) (`pg_restore`) finishes, legally-held files and the append-only lineage/loyalty ledgers are gone with zero audit record** — a materially different and worse failure mode than `ISS-2026-254`'s own state-reversion risk (which concerns stale-but-present data, not an untraceable wipe). Registered as `ISS-2026-265`/`HDN-BLK-034` (High). In the successful, uninterrupted end-to-end case the final restored state is correct (all data reloads from the same consistent backup) — this is a procedural/forensic-trail gap, not a data-correctness defect in a completed restore.
   - **`ISS-2026-265` resolution (Step 16 historical-issue-backlog remediation, 2026-08-25): closes the "zero audit trail" half; does NOT and cannot close the underlying "`TRUNCATE` bypasses triggers" half — disclosed, not silently claimed as fixed.** `TRUNCATE` never firing `FOR EACH ROW` triggers is standard, documented Postgres behavior; no function-level change can make it fire a trigger it structurally never fires. What genuinely closes: **step (j), mandatory, after step (i)'s advisory-lock release** — a single, explicit `app.record_database_restore_event(...)` call (`supabase/migrations/20260826060000_harden_database_restore_audit_trail.sql`), recording who ran the restore, its scope, and how many tables were truncated, into `app.audit_logs` (`tenant_id = null`, the same convention already established for platform-level events). This gives a forensic investigator a real record that the restore happened at all — where today there is none — but the recorded event's own `after_value` payload explicitly discloses inline that it does not itself confirm any individual table's own security invariant (a legal hold, a posted-journal balance) survived. A structurally different mechanism — a pre-restore manifest of hold/immutability state to diff against post-restore — would be needed to close that remaining half, and is not attempted here.

   - **Tier C correction (attack-surface lens, live-reproduced): materialized views are not restored by `pg_restore --data-only`.** `pg_restore -l` in data-only mode carries no `MATERIALIZED VIEW DATA` TOC entry at all — live-proved with `app.mv_report_usage_daily`: seeded and refreshed it (1 row, correct aggregate), backed up, ran the full corrected in-place procedure (0 errors) — the underlying `app.report_runs` table restored correctly (all 3 seed rows), but the materialized view came back **empty**, silently left at whatever stale snapshot the migration replay's own `CREATE MATERIALIZED VIEW` left it at. `app.get_report_usage_daily` (the only tenant-isolation-safe read path to this data) would silently serve wrong/empty analytics after every in-place restore until manually refreshed. **New required step (h)**: after step (g)'s catch-up replay (if any), run `REFRESH MATERIALIZED VIEW CONCURRENTLY` on every materialized view in `app` (query `pg_matviews where schemaname = 'app'` for the current list) before serving traffic. Registered as `ISS-2026-267`/`HDN-BLK-036` (High — a second responder starting the same procedure concurrently can leave the schema in a race-order-dependent, partially-rebuilt state indistinguishable from the original `53200` failure this runbook already spent significant effort documenting a fix for).
   - **`ISS-2026-267` resolution (Step 16 historical-backlog remediation, 2026-08-25): a real mutual-exclusion primitive, not procedural discipline alone.** A session-level Postgres advisory lock (`pg_try_advisory_lock`/`pg_advisory_unlock`, built-in — no new schema object, so nothing about it is lost when step (a) drops the `app` schema) is the right tool for this specific case: this procedure is always run by a single human operator directly via `psql` (never through Supabase's own PostgREST connection pooler, where a session-scoped lock would be unreliable across pooled connections — see `20260730360000_harden_advanced_tms_device_driver_mobile_tracking.sql`'s own header for why a pooled-connection caller was correctly steered away from this same primitive), so one dedicated, held-open session for the whole procedure is exactly the operating model advisory locks are designed for. Fixed lock key, documented once here and never reused for anything else: `pg_try_advisory_lock(872314, 1)` (the pair is arbitrary — `872314` namespaces "CargoGrid restore procedures," `1` identifies this specific in-place procedure, in case a second, distinct lock is ever needed).

     **Step (0), mandatory, before step (a)**: in a dedicated terminal, kept open for the entire procedure, run
     ```
     psql "$DATABASE_ADMIN_URL" -c "select pg_try_advisory_lock(872314, 1) as lock_acquired;"
     ```
     If `lock_acquired` is `false`, **stop — do not proceed to step (a)**. Another restore is already in progress against this target; coordinate on the incident channel and wait. Keep this same session/terminal open, idle, for the duration of steps (a)-(h) — do not close it or open a second one.

     **Step (i), mandatory, after step (h)**: in that SAME still-open session, run
     ```
     select pg_advisory_unlock(872314, 1) as lock_released;
     ```
     then close the session. If the procedure is interrupted or the operator's session crashes at any point before step (i), Postgres automatically releases session-level advisory locks when the connection drops — the lock never gets permanently stuck ("stale forever") the way a manually-managed marker row would, so no separate stale-lock-clearing procedure is needed.

     **Live-proved, not merely asserted**: `scripts/db-tests/database-restore-lock.sql` runs two real, independent, concurrent `psql` processes against the same disposable test database (the identical two-process helper this repository already uses for its own concurrency-race regression tests, `scripts/db-tests/wms-picking-concurrency-helper.sh`) — one acquires the lock and holds it for 2 seconds before releasing, the other attempts to acquire the same lock while the first still holds it. Asserts: the first process's own acquisition succeeds (`lock_acquired = true`); the second process's concurrent attempt against the SAME key while the first still holds it correctly fails (`lock_acquired = false`), proving genuine mutual exclusion, not merely "worked once, by luck of timing"; a third, later attempt (issued only after the first process has released and disconnected) succeeds, proving the lock is not left stuck. Full local `db-tests` suite re-run, `ALL PASSED`.
