## 1. Symptom / trigger

**Scheduled:** a routine backup/restore-evidence rehearsal (this checkpoint, and `HDN-384`'s own upstream dependency on this runbook's proven procedure). **Real:** a genuine data-loss or corruption event requiring recovery — treat as immediate, coordinate with `docs/runbooks/incident-response.md` if the cause is a security incident rather than infrastructure failure.

## 2. Impact

Scope per Prompt 383 §24/`HARDENING_MATRIX.md` §14 item 4: database, files, configuration, secrets **references** (never secret values — mirrors `docs/runbooks/key-rotation.md` §4.2's "credential value never in export" discipline), jobs, deployment state. A restore is inherently **platform-wide**, not tenant-scoped — unlike every other runbook in this directory, there is no single-tenant framing here; restoring the database restores every tenant's data simultaneously (or none).

## 3. Diagnosis steps

1. Identify the target restore point and confirm it is **never the live project's data** for a rehearsal (`HARDENING_MATRIX.md` §14 item 6) — state the target explicitly before executing anything.
2. **Legal-hold precheck (real, non-obvious risk, found at this checkpoint's own Tier C-equivalent investigation, not yet compensated for anywhere in this repository):** confirm the restore point postdates every currently-active `app.legal_holds` row's own `placed_at`. A legal hold is itself ordinary application data, stored in the same schema being restored — restoring to a point *before* a hold was placed produces a database that has never heard of the hold, and `app._is_under_legal_hold()` returns `false` against that restored state for a record a court/regulator currently expects protected. Any archive/delete action correctly refused pre-restore (`blocked_legal_hold`) would silently succeed if re-attempted post-restore, and the `app.retention_archive_requests` evidence trail of that refusal is erased along with the hold itself. **No compensating control exists today** — cross-check the restore point against a hold export taken independently of the backup being restored before proceeding; escalate rather than restore silently past an active hold.
3. Confirm which of the environmental constraints below apply and plan around them — all three were re-verified **live** at this checkpoint, not merely re-read from the seeded description:
   - **Teardown-batching**: `HARDENING_MATRIX.md` §14 item 1's own "~1,400 objects" threshold is now **stale and understated**. Live schema census at this checkpoint: 603 tables, 2,149 indexes, 4,636 constraints, 2,701 functions, 1,316 types, 305 triggers, 37 views, 1 matview, 448 RLS policies — tables+indexes+views+matviews+sequences+triggers alone already total 3,098, well over double the old figure. `DROP SCHEMA app CASCADE` in one transaction was reproduced live and still fails identically: `ERROR: 53200: out of shared memory`, `HINT: You might need to increase max_locks_per_transaction`, rolling back cleanly with the schema intact. A working batching strategy was tested live: order all tables by **ascending inbound-FK count** (leaves first, `app.tenants` — 524 inbound FK references — last), issue one `DROP TABLE IF EXISTS ... CASCADE;` per table as separate auto-committed statements (no explicit transaction wrapper), then a final `DROP SCHEMA app CASCADE` to sweep remaining free-standing objects. Measured: **1.96s, 0 errors.**
   - **Migrations are not idempotent** (`HARDENING_MATRIX.md` §14 item 2, unchanged) — `supabase_migrations.schema_migrations` is the only re-run guard.
   - **`auth.users` survives an `app`-schema reset and reruns collide on `users_pkey`** (`HARDENING_MATRIX.md` §14 item 3) — reproduced live and exactly: after a batched `app`-only teardown (schema `app` fully removed, `auth` untouched) and a full 329-migration replay, re-inserting the same `auth.users` id/email fails with `ERROR: duplicate key value violates unique constraint "users_pkey"`. Any restore/rerun cycle must explicitly clear `auth.users` in teardown or this blocks re-provisioning.

## 4. Resolution steps

**What is proven, live, this checkpoint (schema and row-level database recovery only):**

1. **Schema/structure recovery** (clean migration replay) — `scripts/db-tests/lib/setup-disposable-db.sh`'s own pattern (drop/create db, mirror Supabase's `search_path`/roles, apply all `supabase/migrations/*.sql` in order). Measured across 3 independent runs: **43.70s / 44.79s / 46.34s**, 0 errors each time, converging on **603 tables, 2,701 functions, 448 RLS policies** consistently. This is the same mechanism `scripts/db-tests/run.sh` exercises on every checkpoint and `HARDENING_MATRIX.md` §16 (`HDN-385`) independently cites as proven against both disposable databases and the real hosted project (306/306 migrations at the time of that citation) — it is real, repeated, already-proven evidence for schema/structure recovery specifically, now also explicitly cited here as HDN-383's own baseline RTO figure for structure-only rebuild: **~44–46 seconds from empty database to fully-migrated schema.**
2. **Row-level data recovery** (`pg_dump`/`pg_restore`) — seeded a representative slice (2 tenants, 2 users, 1 pending + 1 dead-lettered job, mirroring `scripts/db-tests/background-job.sql`'s own fixture pattern) onto a freshly migrated database, then: `pg_dump -Fc` (owner+privileges **included** — see the footgun below) → `DROP DATABASE` → `CREATE DATABASE` → `pg_restore -j 4`. Measured: dump 1.56s, teardown 0.66s, create 0.09s, restore 9.28s — **~11.6s total cycle, 0 errors.** Verified post-restore, all exact: object counts identical (603/2701/448); row counts identical (2 tenants, 2 users, 2 jobs, 2 `auth.users`); **job state preserved byte-for-byte** (`job_id`, `status`, `attempts`, `next_attempt_at`, `idempotency_key`, timestamps to the microsecond) — directly satisfies business rule §24's "restored jobs/webhooks must not replay duplicate transactions," since job state is ordinary table rows and the restore reproduced it exactly; RLS spot-checked post-restore via `request.jwt.claims`/`set local role` (a tenant member sees only their own tenant's jobs, a different tenant's admin sees zero rows, `service_role` bypasses correctly, `anon` is denied) — RLS is fully functional immediately post-restore, because RLS policies are `CREATE POLICY` statements committed inside the same migrations that just replayed (confirmed no imperative `ALTER POLICY`/`GRANT` path exists anywhere outside `supabase/migrations/*.sql`).
3. **Known footgun, found live at this checkpoint**: a first `pg_dump` attempt used `--no-owner --no-privileges` (a common "avoid restore hiccups" habit) — this **silently stripped the schema/table `GRANT`s RLS itself sits on top of**, and the restored database returned a blanket `permission denied for schema app` for every role instead of RLS-scoped results. **Never pass `--no-owner`/`--no-privileges` to a real restore** — RLS enforcement becomes unreachable even though the policies themselves restore correctly, a silent, hard-to-diagnose failure mode.
4. **What is NOT proven by this checkpoint, disclosed rather than fabricated**: no full Supabase stack (Auth service, Storage, PostgREST gateway) is reachable in this sandbox — confirmed live (a direct connection attempt to the local Supabase gateway port fails), matching `HDN-380`'s own documented `RLIMIT_NOFILE`/`runc` container-runtime constraint. Consequently this runbook proves database-schema and database-row-level backup/restore only — **not** Supabase Storage file restore, **not** Auth-service-level restore (session/MFA/identity state beyond the raw `auth.users` table row), and **not** a real hosted-project PITR restore. A genuine production-like restore drill covering Storage and Auth remains a real, disclosed, Step-16-blocking gap (§5).

## 5. Communication

**RPO/RTO defaults** (never independently confirmed operationally enabled on the real hosted project — cite honestly, do not promise beyond tested evidence per business rule §24): `docs/architecture/11_DEVOPS_WORKSTREAM.md` §8.1 states MVP-tier defaults of 15-minute RPO / 4-hour RTO via Supabase-managed automated backup + PITR "where plan supports" — a proposed default (RPD-031/RPD-037), not a signed SLA, and never operationally verified as active on `awdlicmwzdxquopwtcfd`. RPD-025's 35-day backup retention is the outer bound for how far back any restore can reach, regardless of tier. **This checkpoint's own measured figures** (~44–46s schema rebuild, ~11.6s row-level dump/restore cycle) are real but describe a small, disposable-sandbox dataset, not a production-scale one — do not extrapolate them as a production RTO commitment.

**Release-gating consequence**: absent production-like restore evidence for Storage and Auth is a named release blocker, not an internal note — `00_EXECUTION_INDEX.md` §8.1 items 6 ("Backup and restore tested") and 9 ("Runbooks available") are 2 of the ten non-negotiable Step 16 eligibility gates (§12); §7's severity policy bands an unenforced-but-plausible recovery path as High, release-blocking unless explicitly ruled an accepted exception at `HDN-387`/`HDN-389`.

## 6. Post-incident / post-drill

Record: which environmental constraint class was hit (§3's batching/idempotency/`auth.users` items), whether the legal-hold precheck (§3 item 2) found any at-risk hold, RLS/policy reconciliation result, and the drill's real observed RPO/RTO figures. `app.record_dr_restore_test` (`supabase/migrations/20260808300000_create_intelligence_disaster_recovery_enterprise_support.sql`, `IAE-035`) is this repository's own existing, structurally-enforced evidence primitive for exactly this purpose — a `'passed'` result requires real, non-negative, finite `observed_rpo_minutes`/`observed_rto_minutes` (a `CHECK` constraint closes a Tier C-found NaN/negative bypass), a `'failed'` result requires a real `failure_reason`/`recovery_steps`/future `retest_scheduled_at`; `p_tenant_id => null` records a platform-wide (shared-deployment) test, `p_component_scope => 'database'` or `'backup'` fit this runbook's own scope. **This checkpoint's own live drill was executed against a throwaway disposable sandbox database, not the real deployed environment** — recording it via `app.record_dr_restore_test` against a disposable database would create a record with no lasting evidence value (and this repository's own culture forbids fabricated pass evidence); the correct next real restore drill, run against a genuine environment, should call this RPC with its own real observed figures rather than this checkpoint's sandboxed numbers.
