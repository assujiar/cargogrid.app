# Data migration rehearsal — Runbook

**Template ID:** `CG-DOCS-RUNBOOK-001` (instantiated from `docs/templates/SUPPORT_RUNBOOK_TEMPLATE.md`)
**Template version:** `0.1.0`
**Audience:** DevOps/on-call, Migration/Onboarding, Finance, Security — see `docs/standards/DOCUMENTATION_STANDARDS.md` §2
**Status:** `ACTIVE`
**Owner:** DevOps / Migration
**Since:** Phase 15 (`HDN-385`, Prompt 385 Data Migration Rehearsal)
**Severity class:** **Mixed, disclosed per data scope, not uniformly rehearsed.** The generic Import/Export Job Framework and one real domain adapter (`employee_import`) are `REHEARSED` — live-executed and measured this checkpoint against a real disposable Postgres, including a real defect found and fixed (§4). Master-data import, tenant-setup import, and bulk financial opening-balance import are `NOT_YET_BUILT` — no mechanism exists for any of the three today, confirmed by direct code inventory, not merely untested. This is a disclosed, structural gap, not a rehearsal failure.

## 1. Symptom / trigger

Any real data migration into CargoGrid — a new tenant's own master data during onboarding, a bulk correction/backfill to existing master data, or financial/inventory/leave opening balances at a cutover — is the trigger for this runbook. `docs/ai-agent-build-prompt-package/15-hardening/385_DATA_MIGRATION_REHEARSAL_PROMPT.md` §21/§22 frames the expected flow: import mapped data into a safe environment, validate/reconcile it, and prove rollback/rerun before any real cutover.

## 2. Impact

A migration is tenant-scoped by construction (every real RPC in this framework is `tenant_id`-gated), but its consequences are not: a bad master-data import corrupts the tenant's own operational data going forward, and a bad financial opening-balance import corrupts every downstream ledger/reconciliation report for that tenant. Business rule (Prompt 385 §24) states "financial opening balances require exact reconciliation" and "no destructive production import without preview, backup, approval and rollback" — this checkpoint's own live rehearsal found neither claim is currently backed by real tooling for the financial case (§4 item 3).

## 3. Diagnosis steps

1. **Identify what actually exists before assuming a migration path is available.** The real, generic mechanism is the **Import/Export Job Framework** (`app.jobs`/`app.import_staging_rows`, `supabase/migrations/20260719170000_create_import_export_job_framework.sql`) — built as `PLT-131` at **Phase 1, Platform Core**, not Phase 5 as this checkpoint's own seeded matrix originally (incorrectly) stated; Phase 5/6/7 modules are later *consumers* of it, not its origin. The generic framework's own `app.commit_import_job()` never writes to any canonical business table by its own design — "commit" there means only "finalize validation." **Only 4 real domain adapters exist, each with its own bespoke `commit_*_import_job()` doing the actual write**: `vendor_rate_import` (Procurement, PRC-255), `employee_import` (HRIS, HRT-274), `attendance_device_import` (HRIS, HRT-278), `timesheet_import` (HRIS, HRT-281). No fifth adapter exists anywhere in the 329-migration tree.

2. **Confirm which of the 3 data scopes named in Prompt 385 §4 ("tenant setup, master data, transactional opening balances/files") have a real path, before promising a migration is possible.**
   - **Master data (customers, vendors, items)**: **no bulk-import mechanism exists at all.** `vendor_rate_import` only imports vendor *rates* — it requires the referenced vendor to already exist as a `master_records` row and rejects unresolved vendor codes outright. There is no `customer_import`, `vendor_import` (master), or `item_import` schema anywhere.
   - **Tenant setup**: no dedicated mechanism. `PLT-120.md` (Master Data Foundation) self-discloses at build time: "Import hooks... are disclosed `NOT_RUN` — IMPEXP/JOB (`PLT-131`/`132`) do not exist yet." This was never retrofitted by any later checkpoint.
   - **Transactional opening balances**: no bulk path exists, structurally disconnected from the Import/Export Job Framework entirely. See item 3.

3. **Financial opening-balance import — the most consequential gap this checkpoint found.** `app.post_finance_ar_open_item()`/`app.post_finance_ap_open_item()` (`20260729100000`/`20260729130000`) accept `source_document_type = 'opening_balance'`, gated behind `FIN:Approve`, and are genuinely idempotent (retried calls on the same `source_document_id` return the existing row, live-confirmed — see §4 item 3). But they are **single-record RPCs** — no staging/mapping/preview pipeline, no batch wrapper, no CSV/file ingestion path exists anywhere. `FIN-202.md` **self-discloses** that an `opening_balance`-sourced AR/AP item "does not yet emit a subledger batch" — meaning an opening balance posts to the AR/AP subledger but **never reaches the GL journal**, and `FIN-202`'s own reconciliation function explicitly excludes `opening_balance`-sourced items from its comparison rather than breaking on them. The identical shape (a bespoke, non-bulk, single-record `opening_balance` primitive, disconnected from `PLT-131`) repeats independently in Inventory (`opening_balance` movement type) and HRIS (leave/permit balances, payroll loan cutover flags) — none of the four are wired to the generic framework. For a real migration needing to load thousands of opening-balance records, there is today no bulk path at all, and the one domain (Finance) where "exact reconciliation" is explicitly required by business rule §24 has a self-disclosed gap in reaching the GL at all.

4. **Duplicate-handling consistency across the 4 real adapters — materially inconsistent, a direct business-rule §24 concern ("duplicate handling is deterministic and reviewable").** Three different patterns exist:
   - `vendor_rate_import` — the strongest pattern, and the one this checkpoint's own fix (§4 item 2) now generalizes to `employee_import`: a documented, already-fixed defect (its own migration's inline comment) shows an *earlier* version silently swallowed any `unique_violation`, including a genuine collision; fixed to discriminate by constraint name, re-raising anything that isn't its own known-safe idempotency guard.
   - `employee_import` — **carried the identical, unfixed defect until this checkpoint** (§4 item 2).
   - `attendance_device_import`/`timesheet_import` — a third pattern: a per-row insert failure marks the *staging row itself* invalid with the real error message, more reviewable than a silent skip but still inconsistent with the other two adapters' own behavior.

5. **The migration-seeded-PK-collision defect class HDN-384 forward-linked (`database-restore.md`'s own `TRUNCATE` finding) does not transfer to this framework as originally feared, for a structural reason, not because import tooling handles it gracefully.** Every table this framework or its adapters write to uses `id uuid primary key default gen_random_uuid()` — no function anywhere accepts a caller-supplied UUID for a new row's own primary key, and no hardcoded UUID literal exists in any `INSERT` statement across all 329 migrations. **But the same underlying risk reappears in a different, real, live-reproduced form**: migration-seeded, natural-key-PK'd reference/lookup tables (`app.finance_currencies`, `app.uoms`) have **no import/registration RPC at all** — a naive migration script attempting to `INSERT` a pre-existing currency/UOM code hits a raw, unclassified `duplicate key value violates unique constraint` error, and a multi-row batch insert rolls back the *entire* batch on one collision, including genuinely-new rows in the same statement (live-reproduced, §4 item 4). `INSERT ... ON CONFLICT (code) DO NOTHING` — a pattern already used elsewhere in this same codebase (e.g. `import_export_schemas` seeding) — would handle this gracefully, but nothing routes a real import through it for these tables.

## 4. Resolution steps

**What is proven, live, this checkpoint:**

1. **The generic framework's full pipeline (mapping → preview → validation → commit) is real and live-tested**, via `app.commit_employee_import_job` (the only adapter this checkpoint exercised end-to-end as the de facto migration-commit path, per its charter). Live drill: `app.provision_tenant` ×2 → `app.create_org_unit`/`app.invite_user`/role setup → `app.publish_import_export_schema` (tenant-scoped column mapping) → `app.initiate_file_upload`/`app.record_file_scan_result` → `app.create_import_export_job` → `app.stage_import_rows` (7 rows: 3 valid, 1 in-batch duplicate, 1 formula-injection payload, 2 missing-required-field cases) → `app.validate_employee_import_row` → `app.preview_import_job` → `app.commit_employee_import_job`. The formula-injection row was correctly rejected (`value begins with a disallowed formula/spreadsheet-injection prefix`); missing-field rows were correctly rejected structurally; committing without `p_allow_partial` was correctly refused (`import_export_job_has_invalid_rows`); committing with `p_allow_partial=true` created exactly the 3 valid rows.

2. **A real, live-reproduced defect found and fixed: `app.commit_employee_import_job` silently swallowed a genuine `employee_number` collision instead of surfacing it.** Root cause: its `app.master_records` insert's own `unique_violation` handler caught *any* violation unconditionally and silently skipped — but `app.master_records` carries no `source_import_staging_row_id` column and therefore has no legitimate self-idempotent-replay case at that insert (unlike `app.employees`' own handler, which correctly guards a real idempotency constraint). Every `master_records_tenant_code_unique` violation there means a genuine collision. **This is the identical defect class `app.commit_vendor_rate_import_job` (PRC-255) already found and fixed in its own migration** — `employee_import` simply never received the same fix. **Fixed this checkpoint** (`supabase/migrations/20260817000000_harden_employee_import_duplicate_swallow.sql`): the `master_records` insert now raises a clear, named `employee_import_duplicate_employee_number` error and aborts the whole commit on any collision, mirroring `vendor_rate_import`'s own proven "any other unique_violation is a real failure" philosophy; the `app.employees` insert's own handler is narrowed to skip only its own true idempotency guard (`employees_source_staging_row_unique`), raising everything else. Live-reproduced before the fix: 2 rows with the identical `employee_number` in one job reported `status=completed` with only 1 of 2 rows written, no error, no per-row flag — indistinguishable from a fully successful import. Re-verified after the fix: the identical scenario now aborts the entire commit with a named error, and the job correctly remains `in_progress`, not falsely `completed`. Regression test added to `scripts/db-tests/hris-employee-master.sql`.

3. **Not fixed this checkpoint, a harder, related gap: an auto-generated (no explicit `employee_number` supplied) row has zero duplicate detection on a fresh re-import.** Live-reproduced: re-ran the identical un-keyed row ("Citra Amelia," no `employee_number` in the source data) in a brand-new job — `app.next_employee_number()` generated a *fresh* code each time, so the `master_records` insert never collides, and a second, genuinely duplicate employee record was created with zero error, zero skip, zero flag (`EMP-2026-000001`/`EMP-2026-000002`, identical name and email). Root cause: `app.employee_duplicate_candidates` — this schema's own real dedup-review mechanism — is never populated by any commit path; `app.flag_employee_duplicate_candidate` is called only by a separate, manually-invoked RPC. This is a genuine business-key-matching design decision (what identity signal — `work_email`? `full_name`+DOB? — should trigger a flag), not a mechanical copy of an already-proven fix like item 2 above, and is registered rather than fixed in-band (`ISS-2026-269`, see §6).

4. **The migration-seeded-reference-table collision, live-reproduced.** A single-row insert of a pre-existing `finance_currencies`/`uoms` code raises a raw, unclassified `duplicate key value violates unique constraint`; a multi-row batch insert with one colliding row rolls back the entire batch, including genuinely-new rows in the same statement. No RPC exists to import/register a currency or UOM safely. Registered, not fixed (`ISS-2026-270`, see §6) — building a real `import_currency`/`register_uom`-style RPC with `ON CONFLICT DO NOTHING` semantics is a real, scoped feature addition, not a mechanical fix.

5. **Financial opening balance — the single-record path works correctly and is genuinely idempotent.** Live-tested: 3 `app.post_finance_ar_open_item()` calls (`source_document_type='opening_balance'`) posted correctly; a reconciliation query against the resulting open items matched exactly (USD 19250.50, SGD 9999.99, 3 open items); a retried call on the identical `source_document_id` returned the identical row, no duplicate. Confirmed live, matching `FIN-202`'s own disclosed gap: `app.finance_subledger_batches` remained at 0 rows for these postings — opening balances do not reach the GL journal, so reconciliation today only holds at the open-items-table level, not full double-entry. This is a self-disclosed, pre-existing gap (not newly found), but its severity for THIS checkpoint's own charter — "financial opening balances require exact reconciliation" — is confirmed directly rather than assumed. **No bulk path exists to test at all** (item 3 above).

6. **Rollback — no formal mechanism exists; a manual rollback is mechanically clean but leaves 2 real residues.** No `rollback_import_job`/`undo_import_job`/`revert_import_job` RPC exists anywhere (confirmed by grep across all 329 migrations); `app.cancel_import_export_job` explicitly refuses a completed job (`import_export_job_already_terminal`); `app.jobs.status`'s own CHECK constraint has no "rolled back" value. A manual, FK-ordered raw-SQL delete (lifecycle events → employees → master_records → staging rows → job row) succeeded cleanly in 60.99ms with no blocking triggers encountered — but this was easy only because the test records were still in fresh `draft` lifecycle; a record with downstream references (payroll, position assignments) would likely hit real FK blocks not exercised here. Two residues confirmed live: (a) `app.audit_logs` rows permanently reference a `resource_id` that no longer exists (no FK on that column, by design) — a dangling, unresolvable audit-trail entry; (b) `app.employee_number_counters.last_seq` is untouched by rollback, so a burned auto-generated number is never reclaimed. Registered, not fixed (`ISS-2026-271`, see §6).

## 5. Communication

No migration-specific communication mechanism exists beyond the generic gaps already registered at `HDN-384` (`ISS-2026-258`, no real DR/incident communication channel/template exists anywhere in this repository — the identical absence applies here: a failed migration has no dedicated notification path, only the generic "notify DevOps lead" pattern common to every runbook in this directory). Prompt 385 §22's own alternative flow ("dirty source data fails validation; migration blocks with error report, owner and remediation plan") is honored at the mechanism level (invalid rows are queryable per staging row with a real error message) but has no owner-assignment or remediation-plan tooling — a human must manually triage `app.import_staging_rows` and assign an owner out-of-band.

## 6. Post-incident

Record: which of the 4 real domain adapters was exercised, the duplicate-handling outcome (deterministic-and-reviewable vs. silently-skipped, per adapter), reconciliation result (open-item totals for Finance; row counts for HRIS), and whether rollback was required and how clean it was.

**No mechanism tracks "migration rehearsals completed" for enterprise tenants.** Business rule §24 states "Enterprise tenants require at least two rehearsals where contracted" — `app.enterprise_onboarding_checklists` (`IAE-035`) tracks exactly 6 fixed items (`sso_verified`, `api_verified`, `integrations_verified`, `dr_evidence_verified`, `support_entitlement_verified`, `hypercare_plan_acknowledged`), none for migration rehearsals, and the enum is closed (requires a schema migration to extend, not a config change). This is the identical structural pattern `HDN-384` already found for DR communication (`ISS-2026-258`) and for `app.dr_restore_tests`' own `component_scope` enum (`ISS-2026-260`). Registered as `ISS-2026-272` (see below) rather than fixed — extending the checklist enum is a real schema decision better made alongside whatever future task builds the master-data/opening-balance import mechanisms this runbook found missing.

**Findings registered this checkpoint** (`docs/runtime/KNOWN_ISSUES.md`):
- `ISS-2026-269` (High) — auto-generated-employee-number rows have zero duplicate detection on a fresh re-import; a real business-key-matching design decision.
- `ISS-2026-270` (Medium) — no safe import/registration path exists for migration-seeded reference tables (currencies, UOMs); a raw insert collision rolls back an entire batch.
- `ISS-2026-271` (Low) — manual import rollback leaves a dangling audit-log reference and a permanently-burned employee-number counter value.
- `ISS-2026-272` (Medium) — no mechanism tracks "migration rehearsals completed" for enterprise tenants, mirroring `ISS-2026-258`'s own DR-communication gap shape.
- `ISS-2026-273` (High) — no bulk financial opening-balance import path exists at all; the one domain (Finance) requiring "exact reconciliation" by business rule §24 has no batch mechanism to reconcile in the first place, and the existing single-record path self-discloses never reaching the GL journal.
- `ISS-2026-274` (Medium) — no master-data (customer/vendor/item) or tenant-setup bulk-import mechanism exists anywhere.
- `ISS-2026-275` (Medium) — `app.finance_journals_protect_posted` never fires on `INSERT`, only `UPDATE`/`DELETE`; a direct bulk insert of an already-`'posted'`, unbalanced, source-less journal (the realistic shape of a migration script preserving historical data) is completely unguarded at the database layer — the same root cause as `HDN-384`'s own `ISS-2026-265` (`TRUNCATE` bypass), reached via `INSERT` instead.
- `ISS-2026-276` (Low) — no `'migration'`/`'import'` source-type vocabulary exists in Finance's own lineage model (`finance_journals.source_type`, HDN-375's orphan-source trigger); a migrated financial record has no legitimate way to preserve its true provenance.
- `ISS-2026-277` (Low) — `app._is_under_legal_hold()` is a single-call-site function (only `app.request_retention_archive`), not a generic write guard; no structural protection exists against a migration/import writing over a legally-held record.
- `ISS-2026-278` (Low) — no MFA/step-up/elevated-authorization gate exists on any import-commit RPC, unlike the 4 functions `HDN-378` specifically hardened for this exact risk class (privileged/financial/export actions).
