## 1. Symptom / trigger

Calendar cadence (no fixed interval ratified yet — set one appropriate to the tenant's own compliance posture until a platform-wide policy exists, same open-cadence gap `docs/runbooks/key-rotation.md` §6 discloses for key rotation) — or ad hoc, triggered by an offboarding, a role-model change, or a request from a tenant's own security contact.

## 2. Impact

None directly — this is a detective control, not a corrective one. Its value is entirely in what it surfaces: authority that has drifted from what it should be (stale role assignments, unrevoked support-access grants, MFA exceptions that outlived their justification, Supreme Admin absolute-CRUD actions that were never independently reviewed). Anything the review finds gets resolved through `docs/runbooks/incident-response.md` §4's revoke primitives, not through this runbook directly.

## 3. Review steps (adapted from "diagnosis")

1. **Supreme Admin absolute-CRUD review.** Query `app.query_audit_logs` (`docs/runbooks/incident-response.md` §3) filtered by `action` for the literal audit-action tag `'supreme_admin_absolute_crud'` — confirmed emitted by the row-level triggers on `app.finance_journals`/`app.finance_journal_lines` (posted-journal integrity, `supabase/migrations/20260729180000_create_finance_posted_journal_integrity.sql`), the append-only loyalty ledger (`supabase/migrations/20260801280000_harden_customer_portal_loyalty_ledger_supreme_admin_override.sql`), the append-only transaction-lineage edge table (`supabase/migrations/20260812000000_harden_data_lineage_audit_findings.sql`), and legally-held file deletion (`supabase/migrations/20260814000000_harden_storage_signed_url_audit_findings.sql`/`20260814100000_harden_storage_signed_url_audit_tierc_fixes.sql`). Every row this filter returns is, by definition, a Supreme Admin exercising **RPD-022** — the ratified, standing, accepted risk that Supreme Admin holds absolute CRUD authority including over audit/ledger/final records, and that this authority **must never be described as tamper-proof** (`AGENTS.md`, `docs/runtime/KNOWN_ISSUES.md` §2, `docs/discovery/06_SECURITY_BASELINE.md`). Reviewing this class of entry means confirming each one had a legitimate business reason on file (a support ticket, a correction request) — it does **not** mean the review itself can certify these records are tamper-evident beyond what the audit log captured, because RPD-022's own accepted-risk framing is precisely that a Supreme Admin could, in principle, also alter or delete the audit trail of their own absolute-CRUD action. Treat an unexplained `supreme_admin_absolute_crud` entry as the highest-priority finding in any review cycle.
2. **Support-access grant/session review.** Query `app.support_access_sessions` (joined to `app.support_access_grants`) for the review window — look for grants approved but never used (dormant authority nobody revoked), sessions that ran unusually long, or a session count exceeding what the tenant's own support-ticket volume would explain. Any grant that should no longer stand goes through `app.revoke_support_access` (`docs/runbooks/incident-response.md` §4.3).
3. **Role-assignment review.** Pull `app.role_assignments` (via `role_lifecycle_history`'s `assigned` events in the audit trail, §3 step 1's query pattern generalized to that action) for assignments made in the review window; cross-check each against a real, current business justification (a hire, a role change) — an assignment with no corresponding HR/ticket trail is a finding. Revoke via `app.revoke_role_assignment` / `app.revoke_principal_membership` (`docs/runbooks/incident-response.md` §4.2) for anything that no longer belongs.
4. **MFA-exception review.** Query `app.mfa_exceptions` for rows with `status = 'approved'` — each one is a standing break-glass factor-recovery grant (mirrors `PLT-115`'s own shape). `app.approve_mfa_exception` (`supabase/migrations/20260807100000_create_intelligence_enterprise_mfa_session_controls.sql`, latest `CREATE OR REPLACE` at `supabase/migrations/20260815000000_harden_ip_restriction_iss150_closure_wiring.sql`, this checkpoint) is `SEC:Approve`-gated and forbids self-approval (`v_exception.requested_by_auth_user_id = p_actor_auth_user_id` raises `mfa_exception_self_approval_forbidden`) — confirm every approved exception in the review window shows a distinct approver from its requester in the audit trail, and that the underlying justification (why that identity needed a break-glass MFA bypass at all) is still on file. An approved exception with no clear expiry/consumption path is itself a finding worth flagging even with no rule violation.
5. **IP-allowlist-bypass review.** Query `app.ip_allowlist_bypass_grants` for `status = 'approved'` rows. Approval itself runs through `app.approve_ip_allowlist_bypass(p_grant_id uuid, p_actor_auth_user_id uuid, p_actor_label text)` (`supabase/migrations/20260807200000_create_intelligence_ip_restriction_network_access.sql`) — confirmed the real name by reading that migration directly rather than assuming it; `SEC:Approve`-gated, self-approval forbidden (`ip_bypass_self_approval_forbidden`) the same shape as MFA exceptions. Every active bypass grant is, by construction, an identity for whom `app.has_active_ip_allowlist_bypass` causes the 4 newly IP-wired RPCs (§6) to **skip** the IP check entirely — confirm each still-active bypass has a real, current reason (e.g. a known-mobile admin who legitimately can't sit behind a stable IP) rather than one that was granted once and never revisited.

## 4. Resolution steps

Every finding from §3 resolves through `docs/runbooks/incident-response.md` §4's own revoke primitives (`app.revoke_role_assignment`, `app.revoke_principal_membership`, `app.revoke_support_access`, `app.revoke_all_actor_sessions`/`app.revoke_user_session`, `app.revoke_ip_allowlist_entry`) — this runbook does not duplicate that list, it points to it. There is no separate "revoke an MFA exception" or "revoke an IP-allowlist-bypass grant" primitive as of this checkpoint (confirmed by grep — only `request_ip_allowlist_bypass`/`approve_ip_allowlist_bypass`/`has_active_ip_allowlist_bypass`/`list_ip_allowlist_bypass_grants_for_tenant` exist for that table); a bypass grant found stale in review has no dedicated revoke function to call yet — file this as a `docs/runtime/KNOWN_ISSUES.md` follow-up if the review needs it and none already exists, rather than working around the gap with a direct table UPDATE.

Rollback procedure if a resolution step fails: same as `docs/runbooks/incident-response.md` §4's own rollback note — an `insufficient_authority` failure means escalate to an identity that genuinely holds the grant, never work around the check.

## 5. Communication

Findings involving a genuine RPD-022 absolute-CRUD anomaly (§3 step 1) or a multi-tenant blast radius escalate to `docs/runbooks/incident-response.md` §5's own communication plan. Routine findings (a stale-but-benign role assignment, an MFA exception past its natural use) are recorded in the review's own output (§6) without special escalation.

## 6. Post-review — two disclosed gaps this runbook's own scope is affected by

A privileged-access-audit runbook that omitted these two live gaps would overstate what "privileged access" actually means to review today — both are already registered in `docs/runtime/KNOWN_ISSUES.md`, cited here rather than re-derived:

**(a) `app.create_integration_connection`'s step-up-MFA gate remains unwired — `ISS-2026-151`** (`docs/runtime/KNOWN_ISSUES.md`, around line 1062). Three of the four platform-default high-risk action categories (`app.decide_ai_output_approval`, `app.activate_enterprise_idp_connection`, `app.approve_mfa_exception`) now have real, live-tested MFA step-up enforcement (`app.assert_current_step_up_authorization`, wired at `supabase/migrations/20260809200000_harden_intelligence_iae039_closure_step_up_wiring.sql`). `app.create_integration_connection` (`INTHUB:Configure`) does **not** — its real blast radius, re-measured precisely at this checkpoint, is **43 real call sites across 16 already-`VERIFIED` db-test fixture files**, collapsible into 27 distinct step-up sequences, deliberately deferred as its own future bounded task rather than rushed into this checkpoint's budget. **What this means for this review:** reviewing `INTHUB:Configure` grants and integration-connection creation events tells you *who was authorized*, but today authorization alone — with no current MFA step-up verification — is sufficient to actually create an integration connection; RPD-023's "MFA/current authorization for privileged... integration... actions" mandatory ruling is only 3/4 enforced for this specific action.

**(b) IP-restriction is wired into 4 admin RPCs, but only 1 of the 4 has a live HTTP route today.** As of this checkpoint (`ISS-2026-150` closure, `supabase/migrations/20260815000000_harden_ip_restriction_iss150_closure_wiring.sql`), `app.decide_ai_output_approval`, `app.activate_enterprise_idp_connection`, `app.approve_mfa_exception`, and `app.create_integration_connection` all gained a real `app.assert_ip_allowed` check (§3's exact mechanism is described in `docs/runbooks/incident-response.md` §2). Only `app.create_integration_connection` is reachable from a live UI route that derives and threads a real client IP (`app/(tenant)/[tenantSlug]/integrations/actions.ts`). **What this means for this review:** an approved IP-allowlist policy or bypass grant (§3 step 5) is a real, provable control today only for integration-connection creation — reviewing IP-restriction posture for the other 3 action categories is reviewing a control that is correct and provable directly against the RPC (`db-test`), but has no live production path exercising it, so an "everything's covered" conclusion from this review would be wrong for those 3.
