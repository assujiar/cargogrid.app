## 3. §4 — the one real gap found and fixed

`app.audit_logs` (`PLT-116`) grants `authenticated` no direct table privilege; the only read paths, `app.query_audit_logs`/`app.export_audit_logs` (`20260716113048_create_audit_trail.sql`), gate on `app.is_support_grant_authority()` alone — Supreme Admin **or tenant_admin**, never a domain-specific permission. FIN-212's own `app.calculate_finance_job_profitability` recorded the entire calculated fact (`to_jsonb(v_fact)`, including `revenue_amount`/`cost_amount`/`profit_amount`/`margin_percent`/`source_invoice_ids`/`source_cost_version_ids`) into that log. A `tenant_admin` who has never been granted the protected `FIN:View margin` permission could therefore read every Job Order's full profitability figures via the generic audit-log export — an inference leak through the log channel (Prompt 214 §23's named "critical/high" class).

**Fixed** (`supabase/migrations/20260729280000_create_finance_field_level_security.sql`, `create or replace function` — identical signature, byte-for-byte identical body up to the audit call): the audit payload is now an explicit allowlist (`id`, `job_order_id`, `version_number`, `is_current`, `status`, `blocked_reason`, `revenue_basis`, `calculated_at`) — never the financial figures or the source-document id arrays (which would themselves leak scale/existence information). Supreme Admin's own unrestricted visibility is unaffected and expected (RPD-022) — this narrows a `tenant_admin`-only channel, not Supreme Admin's. Proven by a real, executable regression guard in `scripts/db-tests/finance-job-profitability.sql` (a `tenant_admin` with no `FIN:View margin` grant reads the real audit events via `app.query_audit_logs` and every payload is confirmed free of every sensitive key, against a fixture with at least one real positive `revenue_amount`, not a vacuous all-null check).

## 4. Adoption gate (`pnpm run data-classification:check`)

`scripts/data-classification/check-registry.ts` mechanically enforces: every seeded `protected: true` `FIN` permission action (`View cost`, `View margin`) that at least one real Finance migration references by name has a `FINANCE_REGISTRY` entry naming it as that entry's own `protectedAction`. A future Finance capability that starts enforcing `FIN:View cost` (or any newly-seeded protected action) without adding a matching registry entry fails this gate — the mechanical instance of Prompt 214 §23's "no unclassified sensitive field ships" rule, extended from Phase 0's env-var-only scope (§7/§8 of `DATA_CLASSIFICATION_STANDARDS.md`) to Finance's own domain fields, as that document's own §8 named as deferred to "each domain's own owning Phase 1+ prompt."

## 5. What remains out of scope, disclosed (not silently claimed complete)

- **No REST/GraphQL surface exists for any domain yet** (§2 above) — this document cannot audit parity for a surface that has not been built. Whichever prompt first wires a Finance REST/GraphQL route must re-verify this matrix's own field-group table against that route's own serializer.
- **No Customer Portal exists yet** (Step 13) — every "customer sees only their own allowed invoice/payment fields" rule (Prompt 214 §24) is enforced today only in the sense that no customer-facing surface exists at all to leak through; this is not evidence the rule will hold once Step 13 ships, and Step 13's own prompt must re-derive it.
- **`FIN:View cost` remains seeded but unenforced by Finance** (§1) — tracked, not a defect, since nothing currently exposes cost data under a Finance-specific gate narrower than `FIN:View`.
- **MFA for privileged Finance approvers** (Prompt 214 §16/§26) is a Platform Core (`PLT-1xx`) concern this checkpoint did not re-verify in depth — no new Finance-specific MFA requirement was introduced or found missing; the platform-wide MFA control (if and when enforced) applies uniformly, not per-domain.
