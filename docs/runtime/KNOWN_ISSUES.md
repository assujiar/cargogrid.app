### ISS-2026-002 — Parallel-session collision (no single-writer discipline)

Two sessions ran Prompt 21 concurrently on separate branches (`…-oanf5a`, `…-b492y3`); both merged to `main` and the merge corrupted the discovery baseline and duplicated the context set (see `ERROR_LEDGER.md` ERR-2026-001). Root cause: no lock/convention preventing concurrent execution of the same runtime step. **Handling:** designate one authoritative build branch per runtime step; do not launch parallel agent sessions on the same step; a future prompt must verify checkpoint lineage before writing. Status `OPEN` until a written single-writer convention is adopted (candidate: note in `AGENTS.md`).

**Recurrence (2026-07-14, third session):** a third branch, `claude/eloquent-mayer-s40hn4`, was cut from `main` at `d587445` *before* this reconciliation (`CG-S2-DISC-001-R1`) had merged. It independently discovered the same underlying corruption and — not knowing about `-R1` — resolved it the opposite way (root-level context kept canonical, `docs/runtime/*` marked superseded) while also completing Step 2 discovery Prompts 22–34. On merge with `main`, that branch's canonical-location choice was reverted in favor of this ratified decision (`docs/runtime/` canonical); its Step 2 discovery deliverables (Prompts 22–34, `docs/discovery/02_*.md`–`14_*.md`) were kept and layered on top of the reconciled baseline (see `TASK_LEDGER.md` `CG-S2-DISC-002..014` and `CHANGE_MANIFEST.md` `CHG-2026-003`). This is the second occurrence of this exact issue and reinforces that it remains `OPEN` until a single-writer convention is actually enforced, not just documented.

**Recurrence (2026-07-15, fourth occurrence — reconciliation never actually performed):** a fourth branch, `claude/sleepy-ride-4vxsk6`, diverged from `origin/main`@`27389a4` (PR #8, Prompt 45) and independently executed Prompts 46–51, Phase 0 kickoff (80), and Prompts 81–82 — nine commits, three full architecture documents, a full Phase 0 kickoff, and two Phase 0 capability prompts — in parallel with this branch (`agent/cargogrid-autonomous-build`) doing the equivalent Prompts 49–51/80/81. The two lineages' outputs for the same task IDs materially differ (e.g. 607 vs. 401 traced requirement items for the "same" Prompt 49/CG-S3-ARCH-014 output). A prior session halted further Phase 0 execution on discovering it and recorded `BLOCKED_WORKTREE` in `HANDOFF.md`, pending an explicit operator decision among three reconciliation options. Full detail: `ERROR_LEDGER.md` `ERR-2026-002`.

**Recurrence (2026-07-15, fifth occurrence — corruption now committed to `main`, escalated to Sev-1):** without that operator decision ever being recorded, PR #10 and then PR #11 (this run's designated branch) were both merged into `main` (`a8a197f`, `b7653cb`). Because neither merge produced git conflict markers (both lineages' edits were pure insertions relative to their shared base), git silently concatenated both divergent lineages' full content into the same files. `docs/architecture/14_REQUIREMENT_PHASE_TRACEABILITY.md`, `15_RISK_RANKED_CRITICAL_PATH.md`, and `16_STEP3_CLOSURE_REPORT.md` each now contain two complete, contradictory copies of the same document (confirmed: two `## 1.` sections in each, 607-item vs. 401-item traceability totals). `docs/runtime/HANDOFF.md`, `CARGOGRID_BUILD_STATUS.md`, and `TASK_LEDGER.md` show the same stacking pattern for narrative/status content. ### ISS-2026-008 — `check-secrets.ts`'s generic-assignment pattern is narrower than sibling foundations' PII coverage (RESOLVED, Low)

Discovered `2026-07-16` during `CG-S5-PH0-020` (Prompt 99, Phase 0 Integrated Verification), via `scripts/verification/phase0-integration.test.ts`'s cross-foundation sensitive-key-pattern consistency suite — a test that runs the *same* representative key names (`password`, `npwp`, `bankAccountNumber`, `salary`) through all three independently-authored pattern lists together, something no single module's own isolated test suite (each written at a different prior checkpoint — `PH0-93`, `PH0-94`, `PH0-97`) could have caught on its own. Result: `scripts/observability/logger.ts`'s `redact()` and `scripts/product-analytics/analytics.ts`'s `findProhibitedProperties()` both correctly flag all four representative keys; `scripts/security/check-secrets.ts`'s `GENERIC_HARDCODED_SECRET_ASSIGNMENT` pattern (`secret|password|token|api[_-]?key|private[_-]?key`) flags only `password`, not `npwp`/`bankAccountNumber`/`salary`. Prompt 99 explicitly deferred the scope judgment call to a dedicated task rather than deciding it unilaterally during verification (§11: "default no repair").

**Resolved `2026-07-16` during `CG-S5-PH0-021` (Prompt 100, Phase 0 Hardening)** — the dedicated task Prompt 99 named. Decision: **keep `check-secrets.ts` scoped to credential shapes; do not widen it to general PII detection.** Rationale: (1) industry-standard secret scanners (gitleaks/trufflehog/detect-secrets) target key/token/password shapes, not arbitrary PII — widening the scope would make `check-secrets.ts` a second, overlapping PII scanner, which Prompt 100 §24's "no new capability" rule forbids; (2) this repository already has three real, tested, purpose-built PII-handling mechanisms for their own respective data-flow surfaces — `scripts/data-classification/registry.ts`/`check-registry.ts` (schema-field classification), `scripts/product-analytics/analytics.ts` (event-property rejection), `scripts/observability/logger.ts` (log-field redaction) — so a hardcoded PII literal in source is correctly out of `check-secrets.ts`'s lane, not an uncovered risk; (3) a real PII value should never be a literal in tracked source regardless of its key name, which is a code-review/data-classification concern, not a key-name-pattern-matching one. **Evidence:** `docs/standards/SECURITY_STANDARDS.md` §3 now states this boundary explicitly; `scripts/security/check-secrets.ts` carries a one-line scope comment; `scripts/verification/phase0-integration.test.ts`'s dedicated test was rewritten from "documents a disclosed gap" to "proves the intentional boundary holds in both directions" (asserts `check-secrets.ts` still does not match the PII-shaped keys, and that `logger.ts` still redacts them regardless — the PII-handling responsibility is proven to land somewhere, not merely absent from one module). Full detail: `docs/build-log/phase-00/PH0-100.md`. **Status `RESOLVED`** — a documented design boundary, not a defect; no code behavior changed, `pnpm run security:check` still reports zero findings.
