# Phase 7 (HRIS and Ticketing) Operational Runbooks

**Produced by:** `CG-S12-HRT-024` (Prompt 296 — HRIS and Ticketing Documentation and Handoff), per Prompt 296 §20's own "publish runbooks for time/payroll exceptions, privacy requests, ticket/SLA/link failures and support access" deliverable, mirroring `docs/build-log/phase-06/PROCUREMENT_VENDOR_RUNBOOKS.md`'s own structure and density one phase up.

**What a runbook is here:** a step-by-step description of how a real, already-`VERIFIED` Phase 7 capability resolves a named operational scenario — citing the real RPC/table/permission-action sequence an HR/payroll staffer, service/support agent, or Platform Support engineer actually walks through. **This document does not describe any behavior that is not already built and independently gate-suite-verified** — every RPC/table named below is drawn directly from its owning capability's own build log (`docs/build-log/phase-07/HRT-274.md` through `HRT-295.md`) and the standing `docs/runtime/KNOWN_ISSUES.md` ledger, not invented. Where a scenario touches a real, disclosed, still-`OPEN` limitation, that limitation is stated plainly rather than smoothed over.

**Sanitization (spec §24, taken literally):** every identifier, name, amount, and reason string below is fictional and deterministic — `Jane Doe`, `EMP-0001`, round IDR figures, synthetic tenant/employee codes drawn from each capability's own already-sanitized db-test fixtures (`emp1`/`emp3`/`emp5`, `pay1`, `esc1`, `lnk1`, etc.) where a concrete worked example is useful. No raw payroll figure, PII value, ticket body, support-access token, or private URL appears anywhere in this document. Where a real historical defect's own reproduction in `docs/runtime/KNOWN_ISSUES.md` used a realistic-sounding sensitive-shaped reason string (medical/disciplinary narrative, used there purely as an illustration of a masking bug), this document never repeats that text verbatim — it is paraphrased or replaced with a clearly fictional placeholder.

**Status of this document itself:** documentation-only, part of `CG-S12-HRT-024`'s own checkpoint. Nothing here should be read as `PHASE_7_VERIFIED` being set — only Prompt 297 (Closure Verification) may set that.

**Companion document:** `docs/build-log/phase-07/HRIS_TICKETING_ROLE_GUIDES.md` — what each role can see/do, the real UI routes/actions, and common errors. Read that first if you are trying to understand what a specific person in the system is entitled to do; read this document when something has already gone wrong and you need to diagnose it.

## 0. Common conventions across every runbook below

- **Permission actions** are `HRS:Create`/`Edit`/`View`/`View personal data`/`View payroll`/`Approve`/`Reject`/`Override`/`Import`/`Export`/`Download` for HRIS, and `TKT:Assign`/`Close`/`Reopen`/`Edit` for Ticketing — both evaluated by the same repository-wide `app.evaluate_permission` RBAC gate every other phase uses. `HRS:View payroll` and `HRS:View personal data` are the two *protected* HRS actions (`protected=true` in the seeded catalogue) — see `docs/standards/HR_PAYROLL_FIELD_POLICY_MATRIX.md` for the full registry and the Role Guides companion document for the concrete two-tier explanation.
- **Masking is defense in depth, not a single layer.** Every classified field is masked at (a) the raw-table grant (column-restricted `GRANT SELECT`, never a whole-table grant on a table carrying a sensitive column), (b) the owning RPC's own `case when v_unmasked then <col> else null end` projection, and (c) the UI, which renders the RPC's own server-computed `*_masked`/`*_visible` flag — never a client-side guess. A gap in any one layer is a real, distinct finding; "the RPC masks it" does not by itself prove the raw table does too, and vice versa.
- **Every governed decision that can be self-decided is structurally blocked.** Payroll run finalization, leave/overtime/timesheet decisions, KPI calibration/appeal decisions, succession-candidate decisions, escalation suppression — every one of these independently checks that the requester and the decider are not the same identity, even when that identity separately holds the deciding permission.
- **`app.capture_audit_event`'s `p_reason` parameter is never redacted** by `app.redact_audit_payload` (which only ever touches the jsonb `before_value`/`after_value` payloads) — this is a repository-wide structural gap (taxonomy class `C-24`), not unique to HR. Every HR/payroll/ticket capability closes it locally, call site by call site, by passing `null` for the reason argument and keeping the real value exactly once in its own already-masked domain table — never by a central fix to `capture_audit_event` itself, which is Platform Core-owned, shared by every domain (Finance, Commercial, Procurement, HR), and out of any one domain's own bounded mandate. `app.cancel_approval_request` (PLT-123, the shared cross-domain approval-cancellation primitive) still carries this exact gap today (`ISS-2026-093`, `OPEN`, Medium) — disclosed, not fixed, because closing it correctly requires a dedicated Platform Core follow-up, not a per-domain patch.
- **PLT-132 (the Background Job Framework) backs every asynchronous batch in this phase**: payroll calculation, leave accrual/carry-forward, roster generation, training-certificate expiry/reminder, ticket SLA evaluation, ticket escalation evaluation. `app.jobs.status` moves through `pending → in_progress → completed`, or, on a genuine per-item/mid-loop failure, `pending`/`dead_letter` via `app.record_job_failure`. **No live cron/poll scheduler exists anywhere in this repository** — every one of these batch RPCs is a real, callable, adversarially-tested entry point; nothing invokes any of them periodically. Until a scheduler exists, someone (an operator, a script, or a future scheduling capability) must call them.
- **Anti-enumeration is the norm, not an exception.** A cross-tenant probe, a forged id, a genuinely nonexistent id, and "exists but you may not see it" are folded into the identical not-found error almost everywhere in this phase (`*_not_found`, `record_not_eligible`, `ticket_not_found`) — a differently-shaped error for a real-but-unauthorized id versus a fake id is itself treated as a defect (see `ISS-2026-043`/`048`-class findings across the build). Do not read "not found" as proof a record does not exist.

## 1. Time/payroll exceptions — a payroll run producing an unexpected figure

**Scenario:** a payroll run's calculated gross/net pay for one or more employees looks wrong — too high, too low, or inconsistent with what HR expects for the hours worked.

**The real diagnostic path** (`supabase/migrations/20260731000000_create_hris_payroll_foundation.sql`, `docs/build-log/phase-07/HRT-282.md`):

1. **Identify the frozen input, not the run output, first.** Every payroll run's own per-employee time inputs are frozen once, at `app.freeze_payroll_period_inputs` time, into `app.payroll_input_snapshots` (one row per `(payroll_period_id, employee_id)`, versioned — a re-freeze supersedes, never mutates, the prior version). Read the snapshot directly: `regular_minutes`, `overtime_weekday_minutes`, `overtime_holiday_minutes`, `source_attendance_session_ids`, `source_overtime_request_ids`, `source_entry_ids` (timesheet entries). This is the authoritative record of what Payroll actually paid *for*, independent of the calculated amount itself.
2. **Trace the snapshot back to its own real sources.** `app._resolve_payroll_time_inputs_for_period` is the ONE function that computes `regular_minutes`/`overtime_*_minutes` from two upstream domains: `app.timesheet_entries` (HRT-281, authoritative wherever a real, approved timesheet entry exists for a work_date) and `app.attendance_sessions` (HRT-278, a fallback contributing REGULAR minutes only for any work_date NOT covered by a timesheet entry — never overtime). Cross-check the snapshot's own `source_*_ids` arrays against the real rows in `app.timesheet_entries`/`app.attendance_sessions`/`app.overtime_requests` for the same employee and period.
3. **Check specifically whether a work_date carries BOTH a real attendance session AND an approved overtime request but NO timesheet entry.** This exact composition — genuine, HR-approved worked time recorded via Attendance, with the SAME day's overtime hours separately approved via Overtime/Timesheet, and no timesheet entry to reconcile the two — is the precise shape a real, historical, live-reproduced Critical defect lived in (`ISS-2026-105`, closed at `HRT-295`). The correct value for such a day's own `regular_minutes` contribution is the session's raw clock span MINUS that day's own already-approved overtime minutes, floored at zero (`greatest(0, raw_span - overtime_minutes)`) — never the full raw span counted a second time on top of the overtime, and never zero (an earlier, superseded fix wrongly excluded the whole day, silently underpaying it — both directions were found and closed only by re-deriving the correct arithmetic against a real fixture, not by inspection alone). If a live snapshot's `regular_minutes` for such a day does not match this arithmetic, this is a genuine regression — escalate immediately as Critical (see below), do not attempt a local workaround.
4. **Re-derive the expected figure by hand for the flagged employee/period**, one work_date at a time: timesheet-covered days use the timesheet entry's own `approved_minutes` directly; attendance-fallback days with no overtime overlap use the session's raw clock span; attendance-fallback days WITH an overlapping approved overtime request use the subtraction rule in step 3. Compare against the snapshot.
5. **Check whether the manual/imported timestamp itself is correct.** `app._ingest_attendance_event` (HRT-278) stamps `work_date`/`raw_clock_in_at`/`raw_clock_out_at` from the caller-supplied historical timestamp for the `manual_hr`/`device_import` channels specifically (fixed at `HRT-295`, `ISS-2026-106` — prior to that fix, these two channels always used the real server "now," making a backdated correction structurally impossible). If the underlying attendance data itself looks like it landed on the wrong calendar day, this is the first thing to check on a tenant running an older, unpatched checkpoint.

**Resolution:**

- **If the period is still `open` or `input_frozen` (not yet `finalized`):** `app.reopen_payroll_period_inputs` (`HRS:Override`) reopens a frozen period; correct the underlying attendance/timesheet/overtime record through its own governed correction workflow (`app.request_attendance_correction`/`app.decide_attendance_correction`, or a fresh timesheet entry); re-run `app.generate_payroll_time_input`; re-freeze via `app.freeze_payroll_period_inputs`; recalculate via `app.calculate_payroll_run`. `generate_payroll_time_input` is content-based idempotent — a genuinely unchanged recompute returns the SAME active version; a real change supersedes with `version + 1`, never a silent in-place rewrite.
- **If the run is already `finalized`:** finalized run history never recalculates in place (a deliberate decision — see `HRT-282.md` decision 11). Create a **correction run** — a NEW `app.payroll_runs` row with `adjusts_run_id` pointing at the finalized run, going through the identical `create_payroll_run → calculate_payroll_run → submit_payroll_run_for_finalization → finalize_payroll_run` lifecycle, including the SAME PLT-123 maker-checker gate (finalize requires a distinct eligible approver, self-approval structurally blocked, live-proven with a genuine two-OS-process concurrent-finalize race at build time). A correction run's own `adjusts_run_id` is validated to point at a genuinely finalized run in the SAME period — a mismatch is rejected (`payroll_run_adjust_period_mismatch`).
- **After a correction run finalizes**, a NEW Finance handoff batch is generated (`app.prepare_finance_payroll_disbursement_handoff_from_payroll_run`, idempotent per run id) — reconciling the correction with whatever the original, already-disbursed handoff represented is Finance's own downstream process, not HR/Payroll's.
- **Who can even see the figure while diagnosing it:** payroll compensation visibility is deliberately NOT inherited from `HRS:View personal data` and NOT from manager-of-employee scope (`HRT-282` decision 5) — only the employee themself OR a genuine `HRS:View payroll` holder sees `app.payroll_run_employee_results`/`app.payroll_payslips`/`app.payroll_input_snapshots` at all, including via a raw table read (`app.payroll_periods`/`_components`/`_component_versions` are gated on `HRS:View payroll` even for their own existence/metadata, not merely tenant membership — a period's own existence can disclose whether/when a compensation cycle ran). A direct manager with only `HRS:View personal data` sees none of a report's payroll data.

**Known, disclosed, still-`OPEN` limitations relevant to this scenario** (do not mistake either for a new bug):
- `app.calculate_payroll_run` is crash-SAFE (a mid-calculation crash rolls back atomically, zero corruption) but not genuinely crash-RESUMABLE — `app.claim_next_job`/`app.record_job_failure` are never invoked; the whole job lifecycle runs inside one function call (`ISS-2026-079`, Medium, `OPEN`).
- `app.request_payroll_run_calculation_cancellation` is a real, tested RPC/TS wrapper with no UI trigger yet — reachable only via a direct call today (`ISS-2026-080`, Low, `OPEN`).
- Component/assignment/reimbursement/loan lines are summed without validating every line already shares the run's own currency — a disclosed, latent, not-live-exploited gap for any tenant that ever assigns a multi-currency component (taxonomy `C-22`, `HRT-282` §10).

**Escalation path:** first-line — HR/Payroll staff holding `HRS:View payroll` reruns the diagnostic above. If the snapshot arithmetic itself looks wrong against the rule in step 3/4, escalate to the Payroll capability owner (`HRT-282`/`HRT-295`) citing `ISS-2026-105` and the two migrations that closed it (`supabase/migrations/20260731240000_harden_hris_attendance_payroll_double_count_backdate_hrt295.sql`, then the corrected `20260731280000_harden_hris_payroll_overtime_regular_minutes_hrt295_tierc.sql`) — a genuine regression against this arithmetic is Critical by definition (a live-reproducible, unflagged monetary miscalculation reaching a finalized run). If the figure is correct but a tenant needs the numbers explained to an employee, use the payslip's own `line_items` (an explicit, non-sensitive `jsonb_build_object` allowlist — never a raw row snapshot) as the reproducible, auditable source of truth.

## 2. Privacy requests/leaks — HR-sensitive data found somewhere it should not be

**Scenario:** a masked or restricted HR field (national ID, date of birth, personal contact/address, a lifecycle/termination reason, a leave reason, a performance score or rationale, compensation data, a candidate's assessment notes) turns up somewhere a caller without the right permission should not have been able to see it — a raw table read, an audit-log entry, a report, or a ticket.

**The real masking model** (`docs/standards/HR_PAYROLL_FIELD_POLICY_MATRIX.md` is the canonical, authoritative registry — read it first): every classified field belongs to one of five registries (`HRS_REGISTRY`, `PAYROLL_REGISTRY`, `PERFORMANCE_REGISTRY`, `TRAINING_REGISTRY`, `TICKETING_REGISTRY`), each row naming its own owning table/RPC and its own `protectedAction` (`HRS:View personal data`, `HRS:View payroll`, or `HRS:Override` for the three `talent_*` rows). `app.has_view_personal_data()` and the domain-specific `app.can_view_hris_payroll_row`/`app.can_view_hris_person_scoped_row`/`app.can_view_talent_review_row` helpers are the real gates every masked RPC calls.

**Diagnosis — work through the 8-dimension parity, in this order:**

1. **Name the exact surface.** A raw `SELECT` via a direct Postgres/PostgREST connection? An RPC's own return value? `app.audit_logs`? A report/export? Free text quoted into a ticket? Each has a genuinely different diagnostic path — do not assume a fix for one closes the others.
2. **Raw-table leak:** run `has_column_privilege('authenticated', '<table>', '<column>')` for the exact column. It should be `false` for every registry-classified column — every masked table's own grant is `revoke select on <table> from authenticated; grant select (<explicit non-sensitive column list>) to authenticated;`, never a blanket whole-table grant. If it returns `true` for a classified column, this is the exact shape a real, live, Critical finding took at `HRT-293` (Finding A — `app.employees`' five reason columns were unconditionally readable via raw SELECT despite RLS being broad-and-correct at the row level) and its self-found siblings (`app.employee_position_assignments`, `app.job_applications`, `app.interviews`, `app.candidate_duplicate_candidates`, `app.employee_duplicate_candidates`, closed at `20260731200000`), plus the Tier C-found `app.ticket_links`/`app.ticket_link_events` and `app.approval_requests` raw-SELECT gaps (`ISS-2026-094`/`098`, both CRITICAL, both closed) and the still-`OPEN` `app.employee_change_requests.reason`/`decided_reason` sibling (`ISS-2026-092`, closed in part by `ISS-2026-099`'s new `app.get_employee_change_requests` RPC).
3. **RPC-level leak:** even with the raw grant correctly restricted, an owning read RPC can still leak the field if it never wraps it in `case when v_unmasked then <col> else null end`. Compare the RPC's own projection against its table's registry row. This was the shape of the `HRT-276` Tier C finding (interview feedback rating/recommendation/notes, offer compensation, assessment score/notes all readable raw despite the column restriction already being correct at the grant layer — two independently-correct-looking layers, one genuine gap).
4. **Audit-log leak:** query `app.audit_logs` directly for the value or a distinctive fragment of it, across `reason`/`before_value`/`after_value`. `capture_audit_event`'s `p_reason` argument is NEVER passed through `app.redact_audit_payload` (§0 above) — this was the exact shape of `HRT-293` Finding B, a live, cross-permission leak spanning 37 call sites across Employee Master, Leave, Recruitment/ATS, Onboarding, Attendance, and Shift/Roster, readable by ANY plain `tenant_admin` via `app.query_audit_logs` regardless of `HRS` permission. The closure pattern, if you find a live instance: change the specific call site to pass `null` for the reason argument — the real value already lives, exactly once, in the domain's own already-masked table. **Never** attempt to fix this centrally in `app.capture_audit_event`/`app.redact_audit_payload` without a dedicated Platform Core-scoped task — the blast radius crosses every domain in the repository, and `ISS-2026-093` (`app.cancel_approval_request`, the shared PLT-123 cancellation primitive) is disclosed as exactly this kind of gap, deliberately left open pending that owner.
5. **Ticket free-text leak — a structurally different shape, read this carefully before "fixing" anything.** If the leaked content was quoted verbatim into a ticket subject, body, note, or escalation reason, this is **not** the same defect class as steps 2–4. Ticket free text is governed entirely by `is_ticket_staff`/ticket-scoped RLS, never by any `HRS` permission, by design — a ticket-staff gate is the correct, complete control for ticket content *in general*. The specific gap where an HRS-masked value, once quoted into a ticket, becomes readable by any ticket-staff member without `HRS:View personal data` is a real, live, **formally risk-accepted** gap (`ISS-2026-111`, `ACCEPTED_RISK`, Medium, closed at `HRT-295`) — not a bug awaiting a fix. Two candidate technical fixes were deliberately rejected after full analysis: blanket-gating every ticket free-text read behind `HRS:View personal data` (would break the overwhelming majority of ordinary, non-HR-sensitive ticket content for any manager lacking that unrelated permission), and a content-classification scanner (no per-field content-sensitivity mechanism exists anywhere in this repository, and building one is a new capability, not a bounded repair). The accepted compensating control is **authoring discipline**: HR staff and managers must never quote HRS-personal-data-masked content verbatim into a ticket subject/body/note/escalation reason — paraphrase, or reference the underlying HR record by id. If you find this has actually happened in a real ticket, that is the formal risk acceptance's own named **reopen trigger (a)** — escalate as a genuine incident, not a Medium-severity backlog item.

**Resolution, by shape:**

- **Missing column restriction (a whole-table grant that should be column-restricted):** `revoke select on <table> from authenticated;` then `grant select (<explicit list excluding every classified column>) on <table> to authenticated;`. `service_role` retains full, unrestricted access always. Register the field in the relevant registry if it is not already there (a real, disclosed, bounded gap — several already-masked HR reason columns remain unregistered though correctly grant-restricted and RPC-masked, `HR_PAYROLL_FIELD_POLICY_MATRIX.md` §5).
- **Missing RPC-level masking:** wrap the field in the RPC's own `case when v_unmasked then <col> else null end`, matching every sibling masked field in the same function exactly.
- **Audit-log leak:** fix at the specific call site (pass `null` for the reason argument), never centrally, unless the gap is in Platform Core infrastructure (`app.cancel_approval_request`-class) — in which case disclose and route to the Platform Core owner, do not attempt a domain-scoped patch on shared code.
- **Ticket free-text leak:** apply the authoring-discipline policy going forward (paraphrase, reference by id); if real production content was found already quoted, treat it as an incident per the risk acceptance's own reopen trigger and notify HR Data Governance jointly with the Ticketing capability owner (the two named joint owners of this accepted risk).
- **Every fix must be regression-tested with BOTH a real forged low-privilege session (confirms the leak is closed) AND a real forged authorized session (confirms self/`HRS:View personal data`/`HRS:View payroll` holders still see the field unchanged — a masking fix that also blinds a legitimate reader is itself a new defect).**

**Escalation path:** HR Data Governance (the `HR_PAYROLL_FIELD_POLICY_MATRIX.md` masking-policy owner) for any policy/registry question; the owning HRT capability's engineering owner for a domain-scoped raw-grant or RPC-masking gap; the Ticketing capability owner jointly with HR Data Governance for the ticket-free-text seam; a dedicated Platform Core (PLT-1xx) owner for any gap in `app.capture_approval_request`/`app.capture_audit_event`/`app.redact_audit_payload` themselves.

## 3. Ticket/SLA/escalation job failures

**Scenario:** a ticket that should have breached its SLA, escalated to the next level, or had its leave accrual/roster/certificate-expiry batch run does not appear to have happened — or a batch job appears to have vanished.

**The real job framework** (PLT-132, `app.jobs`; every batch below reuses it, never a second mechanism):

1. **Find the job row first.** Query `app.jobs` for the relevant `job_type` (`ticket_escalation_evaluation`, `ticket_sla_evaluation`, `leave_accrual`, `leave_carry_forward_expiry`, `roster_generation`, `training_certificate_expiry`/`training_certificate_expiry_reminder`, `payroll_calculation`) and the batch's own semantic `idempotency_key` (typically derived from tenant + period/date + rule set, never a caller-supplied literal — every one of these RPCs is content-based idempotent by construction).
2. **`status='completed'` with a nonzero `failed_count` in its own audit event:** the batch finished; some individual items failed and were skipped. Query `app.audit_logs` for the matching `..._item_failed` action (e.g. `run_ticket_escalation_evaluation_batch_item_failed`) — it names the exact failing `resource_type`/`resource_id` and the underlying `sqlstate`/reason. This is the intended, correct outcome of a genuine per-item failure since `HRT-295`: the job never disappears, the healthy sibling items still complete, and the failure is durably visible for an operator to act on.
3. **`status='dead_letter'`:** a genuine, retryable job-level failure (typically a hard, statement-level cancellation mid-loop, not an ordinary per-item data problem). Check `attempts` and the paired audit events (an `..._interrupted` marker plus `app.record_job_failure`'s own event) for correlation, then call `app.requeue_dead_letter_job` followed by re-running the batch RPC — the remaining work completes from where it left off (the underlying per-item work is itself idempotent, so a retry never double-applies an already-completed item).
4. **No job row exists at all for a batch you believe was run:** on a checkpoint at or after `HRT-295`, this should not happen — every one of the five inline-batch RPCs now wraps its own per-item loop in a nested exception boundary and always reaches a real terminal `app.jobs` state (`completed` or `dead_letter`) even under a genuine mid-loop `query_canceled`. Before `HRT-295`'s own Tier C follow-up, this WAS a real, live, reproducible defect (`ISS-2026-112`, High, closed via `supabase/migrations/20260731260000_harden_plt132_inline_batch_dead_letter_hrt295.sql` then `20260731290000_harden_plt132_batch_interrupt_preservation_hrt295_tierc.sql`) — a genuine cancellation rolled back the ENTIRE transaction including the job's own `enqueue_job` insert, so the job never existed in any state, not `pending`, not `dead_letter`. **If you reproduce a vanished-job symptom on a current checkpoint, treat it as a possible regression against this exact fix and escalate as Critical/High**, citing `ISS-2026-112` and the two migrations above.
5. **Nothing at all seems to be evaluating — no jobs, no escalations, no accruals, ever:** the most likely cause is not a defect but the standing, disclosed operational gap that **no scheduler exists anywhere in this repository**. Every batch RPC named above is real and callable but nothing invokes it periodically. Confirm by manually calling the relevant batch RPC (`app.run_ticket_escalation_evaluation_batch`, `app.run_ticket_sla_evaluation_batch`, etc.) directly — if it runs and produces a correct, real result, the gap is operational (nobody/nothing is triggering it on a schedule), not a code defect.
6. **A specific ticket didn't escalate when you expected it to, even though the batch clearly ran:** check `cooldown_minutes` on the matching escalation level — cooldown paces how soon the NEXT (higher) level may fire after the CURRENT level's own last trigger, not how soon the SAME level may re-fire (a same-level re-trigger within one cycle is structurally impossible by the natural-key uniqueness on `(ticket, policy_version, trigger, level, reopen_count)`). Also check `app.ticket_escalation_suppressions` for an active, unexpired suppression on that ticket (`TKT:Assign`-gated, mandatory reason+expiry) — a suppressed ticket correctly does not escalate, and the suppression itself is never hidden (the `suppressed`/`suppression_ended` ledger rows are always written). And check whether the ticket was recently reopened — a reopened ticket starts a genuinely NEW escalation cycle (its own `reopen_count`), so "it already escalated once before" does not carry forward automatically.

**Resolution:**

- **`dead_letter` job:** `app.requeue_dead_letter_job` + re-run the batch RPC.
- **Missing job row (post-`HRT-295` checkpoint):** re-run the batch RPC manually to confirm; if it reproduces the vanished-job symptom again, this is a genuine regression — escalate immediately, do not attempt a manual workaround that papers over it.
- **No scheduler wired:** this is a known, disclosed, repository-wide operational gap across every job type in this phase. Until a real scheduler exists, an operator (or an external cron/script calling these RPCs directly) must trigger them on the tenant's own desired cadence. This is not something Phase 7's own documentation can close — flag it as a platform-scheduling follow-up, not an individual "failure" per occurrence.
- **Cooldown/suppression/reopen-cycle behavior:** none of these are bugs — they are the documented, deterministic, live-tested precedence/pacing rules. Re-read the policy's own `cooldown_minutes`/level configuration and the ticket's own current suppression/reopen state before assuming a failure.

**Escalation path:** the Ticketing capability owner (`HRT-289`/`HRT-291`) for SLA/escalation-specific batch behavior; the HR capability owner (`HRT-280`) for leave accrual/carry-forward; the Shift/Roster owner (`HRT-279`) for roster generation; the Training/Talent owner (`HRT-284`) for certificate expiry/reminder; a Platform Core (PLT-132) owner if the shared job-framework primitives themselves (`enqueue_job`/`claim_next_job`/`complete_job`/`record_job_failure`) misbehave, since that is infrastructure every domain in the repository depends on, not a Phase 7-local concern.

## 4. Support access grants — time-bound, case-bound (PLT-115)

**Scenario:** a CargoGrid Platform support engineer needs (or already has) access to a tenant's business data to investigate a case, and either the access does not seem to be working as expected, or someone is worried it is broader than it should be.

**The real mechanism, unchanged by any Phase 7 checkpoint** (PLT-115, `app.support_access_grants`): `app.request_support_access` → `app.approve_support_access` (by the tenant's own authority) → `app.start_support_session` → `app.revoke_support_access`. Every grant is **case-bound by construction** (`case_id` is `NOT NULL`) and **time-bound** (a real expiry). Phase 7's own only touchpoint with this mechanism is the Tenant-to-CargoGrid Helpdesk channel (`HRT-288`), and it is deliberately **display/audit-only, never a second grant mechanism**.

**The two independent guarantees to keep straight when diagnosing anything here** (both live-proven repeatedly, at `HRT-288`'s own build and again independently at its Tier C review):

1. **A support ticket alone grants no tenant business-data access.** Holding a live, approved, active, unexpired PLT-115 grant confers **zero** `is_ticket_staff`/`can_access_ticket` status on a correlated helpdesk ticket — the grant and the ticket are two structurally independent mechanisms.
2. **A ticket correlation confers no live access.** `app.link_helpdesk_support_grant` (Supreme-Admin-gated) attaches a `support_access_case_ref` to a helpdesk ticket for *display and history* only, after validating a real `app.support_access_grants` row exists for `(tenant_id, case_id)` — it never itself grants, extends, revokes, or bypasses anything. A grant that is later **revoked** through the ordinary kill switch still stays correlated (the historical display is legitimate; access itself is not), and `app.get_platform_helpdesk_ticket` always shows the real, current status (approved/expired/revoked), never hides it.

**Diagnosis:**

1. Query `app.support_access_grants` directly for the case/tenant in question: `status` (requested/approved/active/expired/revoked), `approved_by`, `expires_at`. This is the one authoritative record — do not infer grant state from ticket behavior.
2. **"The support engineer has a grant but can't see the tenant's data":** confirm the grant is genuinely `approved`/active and not yet expired; confirm the session identity matches the grantee exactly; confirm the grant's own `tenant_id` matches the tenant you're trying to reach. If all three check out and access is still denied, this is a genuine PLT-115 mechanism issue, outside Phase 7's own scope — escalate to Platform Access Governance directly.
3. **"The support engineer can see/reply on the helpdesk ticket — does that mean they have tenant data access?":** no. Helpdesk-ticket staff status (`app.is_ticket_staff` for a `channel='helpdesk'` ticket) is **Supreme-Admin-authority-only**, by deliberate, disclosed design (`HRT-288` decision B) — there is no dedicated non-Supreme-Admin "Platform support agent" role in this repository yet. Ticket staff status and PLT-115 grant status answer two completely different questions.
4. **"A Supreme Admin without a real tenant relationship seems to have acted as the tenant side of a helpdesk case":** this should be structurally impossible. `app._is_tenant_helpdesk_authorized` deliberately does NOT route through `app.evaluate_permission` (whose RPD-022 Supreme-Admin bypass would otherwise incorrectly count a Supreme Admin with zero real tenant membership as the tenant-side requester party) — it queries `app.principal_memberships`/`app.role_assignments` directly for a genuine `tenant_admin` membership or a real, tenant-scoped, published `TKT:Edit` grant. If you reproduce a Supreme Admin acting as a tenant's own requester without either, this is a genuine, serious regression against a defect this exact design was built to prevent at `HRT-288` — escalate as Critical.
5. **"A correlation reference looks wrong or was accepted for a grant that shouldn't exist":** `app.link_helpdesk_support_grant` rejects a forged/nonexistent case reference outright (`support_grant_not_found`) — if a bad correlation was somehow accepted, this is a genuine defect in the Helpdesk capability itself (`HRT-288`), not the PLT-115 mechanism.

**Resolution:**

- Ordinary grant lifecycle problems (not yet approved, expired, revoked in error) are resolved entirely through the existing, unmodified PLT-115 flow — request/approve/start/revoke — owned outside Phase 7.
- A helpdesk-ticket-staffing need for someone who is not a Supreme Admin has no workaround today: **do not invent a "temporary" role assignment or a bypass** — this is a deliberate, disclosed, bounded-scope decision, not an oversight (`HRT-288` §3 decision B). Route the request through the org's own Supreme Admin process, or flag the need for a future, dedicated non-Supreme-Admin support-agent role as its own capability addition.
- A correlation-mechanism defect is a Ticketing/Helpdesk (`HRT-288`) engineering issue.

**Escalation path:** Platform Access Governance / PLT-115 owner for grant lifecycle questions; the Ticketing/Helpdesk capability owner (`HRT-288`) for correlation-display or tenant-authorization-model issues.

## 5. Linked-record denial — a ticket linked-record read returns "not eligible"

**Scenario:** attempting to search for, link, or read a typed linked record (shipment, invoice, warehouse, vendor, customer/account, or user) on a ticket returns `record_not_eligible` (or the candidate search returns nothing), and it is unclear which of the six domains is actually denying it.

**The real mechanism** (`HRT-292`, `app.ticket_links`/`app.ticket_link_events`): every read and write path funnels through ONE shared adapter, `app._ticket_link_resolve_candidate`, which composes each domain's own **existing, already-applied** access predicate — never a new authorization rule invented for ticketing. In rough correspondence: shipment/warehouse reuse Operations' own `app.can_access_record`; invoice reuses Finance's own `app.check_finance_invoice_authority`; vendor reuses Procurement's own `app.evaluate_permission(actor, tenant, 'PRC', 'View')`; customer/account and user reuse tenant-membership/account-scope checks. For a `customer_user`-layer caller specifically, shipment/invoice/warehouse ALSO get a genuinely new, narrow OR-branch composing `app.resolve_customer_owner_account_scope`/`app.customer_warehouse_eligibility_active` (both reused verbatim from ATW-242) — the record must belong to an account the caller is CURRENTLY, actively a member of.

**`record_not_eligible` is deliberately, structurally anti-enumerating** — the identical error covers a forged id, a genuinely nonexistent id, a cross-tenant real id, a hard-deleted source record, and a record the caller has since lost eligibility to (revoked account scope). It never tells you which. Diagnosis is done by directly re-checking the underlying causes as a privileged operator, not by asking the RPC for more detail.

**Diagnosis, in order:**

1. **Channel first, if this is a helpdesk-channel ticket.** `app._ticket_link_actor_may_view_tenant_data` runs BEFORE any per-domain predicate for a helpdesk ticket, and requires the caller to hold at least ONE of: a real `app.tenant_user_identities` membership in that tenant, a live `app.support_access_grants` grant (PLT-115, case-bound — see runbook 4) into that tenant, or an active `customer_user` membership in that tenant. This closes a genuinely NEW exposure the linked-records capability would otherwise introduce (any Supreme Admin browsing any tenant's shipments/invoices/vendors/accounts/users merely by opening a helpdesk ticket into it) — it is stricter than what a Supreme Admin could already do elsewhere in the app, by design. If none of the three conditions hold, `record_not_eligible` is the correct, expected outcome — the resolution is requesting/approving a real support-access grant (runbook 4), never a workaround.
2. **Entity-type registry, if the caller is a `customer_user`.** A customer-layer caller's candidate search is structurally narrowed to `shipment`/`invoice`/`warehouse`/`customer` — never `vendor`/`user` (no existing customer-facing read path for either exists anywhere in this repository; exposing one would leak internal supplier/staff-directory structure). An out-of-registry attempt is a DIFFERENT, distinguishable error (`entity_type_not_permitted`), not `record_not_eligible` — if you see the latter for a customer against vendor/user, re-check that the caller is genuinely resolved as a `customer_user`.
3. **The specific domain's own real predicate, checked directly, as a privileged operator, against the same identity and record:** does `app.can_access_record`/`app.check_finance_invoice_authority` admit this identity to this exact row through normal internal-staff scope? If the caller is a `customer_user`, does `app.resolve_customer_owner_account_scope` (shipment/invoice) or `app.customer_warehouse_eligibility_active` (warehouse) currently admit them — i.e., is the specific record owned by an account they are an ACTIVE member of right now, not merely historically? For vendor, does `app.evaluate_permission(actor, tenant, 'PRC', 'View')` return `allowed=true`?
4. **Source availability, for an EXISTING link that now shows `unavailable`** (as opposed to a NEW link attempt returning `record_not_eligible`): a link's `safe_snapshot` (`{label, detail, status}`) is captured ONCE at link time for history only and is NEVER re-read as currently authoritative — every live read of `app.list_ticket_links` re-resolves fresh. If the underlying source record was hard-deleted, or the caller's own eligibility (e.g. a warehouse customer-eligibility grant) was revoked since the link was created, the link correctly shows a generic `unavailable` status with no label/detail leaked — this is expected, correct behavior, not a bug.
5. **Tenant match, always.** A cross-tenant real id produces the identical `record_not_eligible` a forged id would.

**Resolution:**

- **If the caller genuinely should have access and the diagnosis above shows a real domain-predicate denial:** this is almost never a Ticketing/`HRT-292` defect — it means the OWNING domain's own access control (Operations, Finance, Procurement, or account-membership scope) denies them, correctly, by that domain's own rules. The fix belongs to that domain's own configuration (grant the right account membership, grant the right PRC permission, correct the record's own tenant), not to the linked-records capability.
- **If it's the helpdesk support-grant gate:** resolve via runbook 4.
- **If a customer is attempting an out-of-registry entity type:** by design, no workaround exists.
- **If the diagnosis above finds no real cause — the identity IS genuinely, currently eligible by every domain check and still gets `record_not_eligible`:** this is a genuine defect in `HRT-292`'s own composition. Escalate with the exact actor/tenant/entity_type/entity_id and the full check trail above, so engineering can trace which composed predicate is unexpectedly returning `false`.

**Known, disclosed, still-`OPEN` limitations relevant to this scenario** (not bugs, but worth knowing while diagnosing):
- `app.list_ticket_link_events` (the link/unlink audit ledger) is built and tested but has no UI caller yet — reachable only via a direct RPC call today (`ISS-2026-100`, Medium, `OPEN`).
- A customer viewing `app.list_ticket_links` sees the raw `entity_type`/`entity_id` for an out-of-registry link type (vendor/user) even though they could never have searched or linked it themselves — an internal-identifier-shaped leak, not a business-data leak (`ISS-2026-102`, Low, `OPEN`).

**Escalation path:** for a domain-access denial, the owning domain (Operations for shipment/warehouse, Finance for invoice, Procurement for vendor, Commercial for account/customer scope); for the linking mechanism itself (search/link/unlink behavior, safe-snapshot freshness), the Ticketing/`HRT-292` owner; for the helpdesk-channel gate, Platform Support/Access Governance (also runbook 4).
