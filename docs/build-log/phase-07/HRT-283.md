## 1. What this checkpoint builds

HRT-283 is the twelfth Phase 7 (HRIS/Ticketing) capability, built directly on HRT-274 (Employee Master, `VERIFIED`), HRT-275 (Organization and Position Linkage, `VERIFIED`), and HRT-278..282 (Attendance/Roster/Leave/Overtime-Timesheet/Payroll, all `VERIFIED`), reusing the established manager-scope (self/direct-manager/HRS:View) pattern those checkpoints already set rather than reinventing it. It implements a versioned KPI library, a reusable weighted-goal-slot template, performance cycles with an explicit stage state machine (draft → goal_setting_open → self_assessment_open → manager_assessment_open → calibration → acknowledgement → closed), weighted goal assignment with exact-total validation and not-applicable rebalancing, self/manager/reviewer (360) assessment stages with purpose- and stage-bound visibility, an explainable exact-decimal scoring formula, a governed calibration adjustment step (HRS:Override + mandatory reason + structural self-calibration block), acknowledgement, and an appeal/reopen workflow. Aggregate reporting carries a genuine k-anonymity floor (k=5). No code path in this migration writes to `app.employees.lifecycle_status`, any `app.payroll_*` table, or any role/permission table — performance outcomes never automatically alter pay, employment, or access.

## 3. Source/config decisions (disclosed, not left implicit)

Recorded in full in the migration's own header comment — summarized here.

### Decision 0 — no new permission row; reuse `HRS:View personal data`

`app.permissions.action` is closed by a repository-wide, deliberately fixed `permissions_action_check` CHECK constraint (`20260716103445_create_roles_permissions.sql`) that every capability since HRT-274's own explicit disclosure (mirroring ADR-0020's identical discipline) has reused rather than altered. **Live-confirmed the hard way, not merely read about**: a first draft of this migration attempted `insert into app.permissions (action, ...) values ('View performance', 'HRS', ...)` and was rejected by that constraint on first apply — corrected to reuse the already-legal, already-seeded `HRS:View personal data` action (already used by HRT-274 for national_id/dob/personal_address masking) as this capability's own protected "see individual performance content beyond self/manager/reviewer" gate. Every reference to "HRS:View performance" that would otherwise appear throughout this codebase reads `HRS:View personal data` instead.

### Decision 1 — no rating-band/label subsystem; the outcome's own exact `final_score` IS the explainable output

Prompt 283 never names a qualitative rating-scale/banding requirement. Building one would invent unspecified business configuration (band count, labels, boundary tie-break rule) this checkpoint has no mandate to decide — the same proportionate-effort call HRT-282 made declining a generic formula evaluator. `app.performance_outcomes.score_breakdown` (an explicit, non-free-text jsonb allowlist of `goalAssignmentId`/`kpiDefinitionId`/`weight`/`rawScore`/`weightedContribution` per goal, **never** `to_jsonb(whole_row)` — taxonomy C-07) plus the exact numeric `final_score` already satisfy "explainable exact-decimal scoring" (section 24) without a label layer.

### Decision 2 — the manager assessment is the SOLE source of the computed score

Self and reviewer (360) assessments are real, captured, visible inputs but do not themselves feed `app._compute_performance_outcome_baseline`'s weighted-sum formula. Prompt 283 names self/manager/reviewer stages but never specifies a blending algorithm — inventing one (e.g. a fixed self/manager/reviewer split) would be unsupported business configuration. Manager-assessment-authoritative is the standard, defensible shape and keeps the formula reproducible from ONE assessment's own per-goal `raw_score` values. **Live-proven, not merely asserted**: emp1's self-assessment scored sales_target at 90 and quality_score at 70 (self-weighted would-be 82.000); the manager assessment scored the SAME two goals at 100 (capped) and 80; the computed `baseline_score`/`final_score` was exactly `92.000` — provably derived from the manager's own scores only.

### Decision 3 — direct-manager-only "effective team" scope, reused verbatim (mandatory reading item)

Every list/visibility predicate uses the identical `e.manager_employee_id = v_self.master_record_id` single-level direct-report shape `app.list_overtime_requests`/`app.list_leave_requests`/`app.list_attendance_sessions` already established — never a recursive org-tree walk, never a second manager-hierarchy mechanism.

### Decision 4 — calibration and appeal-decision use direct HRS:Approve/Override gating with a structural self-decision block, NOT PLT-123

HRT-282 decision 6 reserved PLT-123 maker-checker for the one genuinely irreversible, batch-wide, fund-disbursing moment (payroll run finalization). Nothing in this capability is batch-wide or irreversible in that sense — every outcome remains reversible through this capability's OWN appeal/reopen workflow, itself governed. Calibration requires `HRS:Override` + a mandatory reason + a structural self-calibration block (an actor may never calibrate their own outcome, mirrors `decide_payroll_reimbursement_request`'s self-approval block); appeal decision requires `HRS:Approve` + a mandatory reason + a structural block against the appellant deciding their own appeal. **Both live-proven**: emp1 (deliberately granted the Approver role for exactly this test, per the same shape HRT-282's own "hr also holds Payroll Approver role" self-block test used) was rejected calibrating their own outcome (`self_calibration_not_permitted`) and rejected deciding their own appeal (`self_approval_not_permitted`); a distinct Override/Approve holder succeeded on both.

### Decision 5 — manager/reviewer assignment is resolved ONCE and frozen; reassignment is explicit and audited (mandatory reading item — "manager reassignment does NOT silently transfer already-submitted reviews")

`app.performance_reviewer_assignments.assigned_to_employee_id` is frozen at the moment it is created (auto-resolved from the employee's CURRENT `app.employees.manager_employee_id` the first time a goal is assigned, via `app._ensure_performance_manager_assignment`, or explicitly via `app.assign_performance_reviewer`) — never re-derived live from the org chart on every read. `app.reassign_performance_reviewer_assignment` (`HRS:Override`, mandatory reason) is the only way to change it: it marks the OLD assignment `status='reassigned'` and creates a BRAND NEW assignment + a fresh `not_started` assessment for the new assignee — the old row and any submitted assessment tied to it are NEVER mutated or deleted. **Live-proven end to end** (§9): mgr1's already-submitted manager assessment for emp1 (comment `"strong performer"`, status `submitted`) was reassigned to reviewer1; the OLD assessment's status, assignee, and comment were confirmed byte-for-byte unchanged after the reassignment, a fresh `not_started` assessment existed for reviewer1, and the outcome's own `manager_assessment_id` still pointed at mgr1's original submission — the already-computed score was untouched.

### Decision 6 — a genuine k-anonymity-style floor (k=5, fixed) on the one grouped report this checkpoint builds

`app.report_performance_cycle_score_distribution` groups outcomes by department and returns every group's real `employee_count`, but suppresses (nulls) the disclosive statistic itself — `avg_final_score` — for any group with fewer than 5 employees, marking `suppressed=true`. Enforced INSIDE the `SECURITY DEFINER` function itself — no caller, including a genuine `HRS:View personal data` holder, can retrieve a small cohort's average through this RPC. **Live-proven with a genuinely tiny real cohort, not a contrived one**: DEPT-SMALL (emp1 + emp2, both real employees carried through the actual goal/assessment lifecycle above) returned `employee_count=2, avg_final_score=NULL, suppressed=true`; a synthetic 5-person DEPT-BIG returned `employee_count=5, avg_final_score=73.00, suppressed=false`, an exact match for `(71+72+73+74+75)/5`.

### Decision 7 — taxonomy C-24 audit-masking discipline applied from the start (this phase's third-in-a-row recurring defect: HRT-280 → HRT-281 → HRT-282)

Every one of the 25 `capture_audit_event` call sites in this migration passes `p_reason => null` unconditionally, and every `after_value` jsonb is built from an explicit, reviewed allowlist that NEVER includes a `raw_score`/`baseline_score`/`calibrated_score`/`final_score`/`weight`/`target_value`/`actual_value` or any free-text field (`score_rationale`, `overall_comment`, `adjustment_reason`, `appeal_reason`, `decision_reason`, `na_reason`, `note`) — only ids, enum status/decision strings, and counts. Grep-verified (`grep -n "perform app.capture_audit_event(" -A 4 ... | grep -E "'success',"` against every call site) and live-proven in the db-test's own calibration block: after a real calibration adjustment carrying the free-text reason `"calibration committee: normalized against peer cohort"` and scores 92.000/95.500, `app.audit_logs` was queried directly and confirmed to carry neither the reason text nor either score value — only `{"outcome_id": "..."}`.

### Decision 8 — no autonomous downstream action (business rule, section 24)

Grep-verified before commit: this migration contains no `update app.employees set lifecycle_status`, no `insert into app.payroll_` / `update app.payroll_`, and no `insert into app.role_` / `app.permissions` write of any kind. **Also proven live inside the db-test itself** (§9, final block): a structural scan of every write function's own `pg_get_functiondef` source confirms none of the three forbidden write shapes appear anywhere.

### Decision 9 — data-classification: reuse category `pii`, do not invent a new `performance` category ad hoc

`scripts/data-classification/registry.ts`'s `CATEGORIES` const has no `performance` entry (unlike `payroll`, which HRT-274 explicitly reserved ahead of time). Adding a new shared category is a cross-cutting taxonomy change outside this single capability's own mandate — `pii` (restricted-level personal data about a specific employee) is the closest existing fit. `PERFORMANCE_REGISTRY` (4 entries) is wired into the combined `REGISTRY` in `check-registry.ts` — see §10 for a disclosed observation this checkpoint made about `PAYROLL_REGISTRY` never having received the same wiring.

### Decision 10 — deliberately NOT built, disclosed rather than silently dropped (taxonomy C-23 discipline)

No staged-import (PLT-131/132) crosswalk for historical ratings/goals (section 19's own migration-impact note, not named in section 20's "detailed implementation tasks" bullets) — matches HRT-275's identical "no staged-import crosswalk" disclosure. ## 4. Security/access model

- **RLS:** `performance_kpi_definitions`/`_kpi_definition_versions`/`_templates`/`_template_kpi_items`/`_cycles` (non-person-scoped metadata, mirrors HRT-275's own `positions`/`position_grades` precedent — no individual sensitive data lives on these tables) use the hardened default-deny form: `(app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id)) or app.is_supreme_admin()`. Person-scoped goal/progress tables use `app.can_view_hris_performance_row` (self/direct-manager/assigned-reviewer/`HRS:View personal data`). Assessment/score tables use the assessment-type-aware `app.can_view_performance_assessment_row` (self assessment: self+manager always; manager assessment: employee ONLY once submitted; reviewer assessment: the employee's manager once submitted, NEVER the employee directly). Outcome/appeal tables use `app.can_view_performance_outcome_row` (self/direct-manager/`HRS:View personal data` — deliberately NOT extended to reviewers). Calibration-adjustment history is HR-only (`HRS:View personal data`), excluding even the outcome's own employee and manager — the RESULT is visible via the outcome, the deliberation is not.
- **RBAC:** every write RPC gates through `app.check_performance_authority` (`SECURITY DEFINER` from the start, avoiding HRT-281's own self-found-defect-3 class) or the assessment's own assigned-actor identity check.
- **Concurrency:** every version-guarded write locks `FOR UPDATE` then re-checks `record_version` at the terminal `UPDATE`; check-then-insert authoring functions with no coarser serializing lock (`create_performance_kpi_definition`, `create_performance_kpi_definition_version`, `create_performance_template`, `create_performance_cycle`, `assign_performance_reviewer`) carry real exception handlers, live-proven with genuine concurrent OS processes (§8) — taxonomy C-01/C-02 applied from the start, not retrofitted.
- **Internal engine functions** (`_is_direct_manager_of_employee`, `_ensure_performance_self_assessment`, `_ensure_performance_manager_assignment`, `_assert_performance_assessment_scores_complete`, `_compute_performance_outcome_baseline`, `compute_kpi_raw_score`) are granted `service_role` only, never `authenticated` — live-verified in `scripts/db-tests/hris-kpi-performance.sql`, including the `revoke execute on all functions in schema app from public` belt-and-suspenders statement this migration also carries (found missing on first apply — see §7 item 1).
