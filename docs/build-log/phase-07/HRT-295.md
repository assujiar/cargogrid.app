## 3. Tier C findings fixed this pass — root cause, fix, regression evidence

### 3.1 `ISS-2026-105` (Critical) — payroll exclusion converted overstatement into understatement

**Root cause:** `20260731240000`'s own fix excluded a work_date entirely from the attendance-fallback whenever an approved overtime request covered it (closing the double-count), but the finding's own definition of "correct" requires that day's real, non-overtime, worked minutes still be paid — not zeroed. Independently re-derived on the existing `emp3` fixture: day A's real regular portion is 690 (raw) − 150 (overtime) = 540 minutes; the shipped fix paid 0.

**Fix:** `supabase/migrations/20260731280000_harden_hris_payroll_overtime_regular_minutes_hrt295_tierc.sql`. `v_covered_dates` (full exclusion) reverts to timesheet-covered dates only. A work_date covered by an approved overtime request with no timesheet entry is no longer excluded — the attendance-fallback query subtracts that day's own real `approved_minutes` from the session's raw span, floored at zero (`greatest(0, raw_span - overtime_minutes)`), using the same `approved_minutes` column already trusted for the overtime totals — never a second config value, and never the "capping" alternative the original fix's own header rejected (subtraction has neither of that alternative's two failure modes: no ambiguous config source, and `greatest(0, ...)` is safe even when a day's minutes are fully consumed by overtime).

**Regression evidence:** `scripts/db-tests/hris-payroll.sql` — `emp3`'s existing assertions corrected in place to their genuinely correct values (regular_minutes=1020, gross/net=850,000 IDR, both attendance sessions present in `source_attendance_session_ids`); a new, independent `emp5` fixture (different dates, a partial-claim overtime request that reconciles to a policy-capped 180 minutes against a 735-minute raw span) proves the fix is keyed to the day's own real `approved_minutes`, not a coincidental config value (correct regular=555, live-confirmed). Both fixtures pass end to end through the real `generate_payroll_time_input → freeze_payroll_period_inputs → create_payroll_run → calculate_payroll_run` pipeline.

### 3.2 `ISS-2026-112` (High) — `query_canceled` mid-loop still destroyed the job row

**Root cause:** `20260731260000`'s own inner `when query_canceled then raise;` correctly refuses to absorb a genuine cancellation as a per-item failure, but nothing outside the loop caught the re-raised exception — it still propagated out of the whole function, rolling back the entire transaction including `app.enqueue_job`'s own earlier `INSERT`, reproducing the finding's exact original result (zero `app.jobs` rows) for this one failure mode. Separately, `20260731260000`'s own header and the `KNOWN_ISSUES.md` resolution text both falsely claimed a regression fixture existed in `scripts/db-tests/hris-leave-permit-business-trip.sql` for 2 of the 5 functions — that file's `git diff` was empty; the underlying code was independently confirmed correct, only the test was missing.

**Fix:** `supabase/migrations/20260731290000_harden_plt132_batch_interrupt_preservation_hrt295_tierc.sql`. Each of the 5 functions' own "loop + `complete_job` + success audit" block is wrapped in a new outer boundary catching (only) the re-raised `query_canceled`. On catch: calls `app.record_job_failure` (the real PLT-132 retry/dead-letter primitive — safe to call here since, unlike `complete_job`, it does not require an already-held lease), records a richer audit event with partial progress counts, and — critically — does **not** re-raise. Live Postgres-semantics verification (a standalone probe) confirmed this is the only way recovery work can persist: `statement_timeout`'s one-shot alarm is armed once per top-level client statement and consumed by its first firing; catching without re-raising lets the same top-level call continue and commit normally, while catching-then-re-raising rolls the recovery work back too. Net effect: a genuine mid-loop cancellation now makes the caller's RPC call return normally with a partial `evaluated_count`, and the job survives in a real, retryable terminal state instead of vanishing.

**Regression evidence:** `scripts/db-tests/ticketing-escalation.sql` section 14 (new) — a real, forced `set statement_timeout` cancellation via a deterministic sentinel-ticket trigger delay (the delay is two orders of magnitude longer than the timeout budget, so cancellation reliably lands regardless of scan order or machine speed — a tighter, tuned-millisecond pairing was live-caught during authoring as itself flake-prone under a full cumulative fixture and widened). Confirms: the call returns without error; the job reaches `dead_letter` with `attempts=1`; both the new `..._interrupted` audit event and `record_job_failure`'s own audit event are durably present; a `requeue_dead_letter_job` + retry genuinely completes the remaining work (full recovery cycle). `scripts/db-tests/hris-leave-permit-business-trip.sql` (new block) closes the false-claim gap: a temporary `NOT VALID` sentinel `CHECK` constraint forces a genuine `check_violation` for both `run_leave_accrual_batch` and `run_leave_carry_forward_batch`, confirming the job reaches `completed` with the healthy sibling employee's own posting intact and a durable `..._item_failed` audit row.

Disclosed, bounded scope: the 3 other functions share byte-identical outer-catch control flow with the two live-verified above (confirmed by direct code read) and were not separately statement-timeout-tested live in this pass, mirroring `20260731260000`'s own disclosed treatment of 3 of its 5 item-failure fixtures.

### 3.3 `ISS-2026-110` fix regression (High) — `list_customer_ticket_links` broken for ordinary customer sessions

**Root cause:** `20260731270000`'s own "live re-check" design for genericizing a link's creator (`app.is_ticket_staff(p_ticket_id, l.created_by_auth_user_id)`) passed the link's CREATOR, not the calling actor, into `app.is_ticket_staff → app.check_ticket_authority → app.evaluate_permission → app.assert_actor_is_session_identity` — the primitive `20260730440000` (ATW-031) hardened specifically to reject any call where the claimed actor differs from the real session identity. Live-reproduced with a real forged customer session: `ERROR: actor_identity_mismatch: the authenticated session is <customer> but this call claims to act as <the link creator>`. This broke the whole customer ticket detail page (messages included, both RPCs awaited in one `try/catch`) for every ticket with a link created by anyone other than the reading customer — the ordinary case, not an edge case. The repair group's own regression fixture (`ticketing-linked-records.sql` section 18) never forged a session for this call, so it never exercised the real RLS-bound path.

**Fix:** `supabase/migrations/20260731300000_harden_ticketing_customer_links_creator_role_hrt295_tierc.sql`. A new `app.ticket_links.created_by_role` column (`'staff'`/`'requester'`, mirroring `app.ticket_messages.author_role`) is captured once at link-creation time by `app.link_ticket_record`, reusing the already-computed `v_is_staff` value that function already trusts for its own authority check on the real calling actor. `app.list_customer_ticket_links` reads the stored column instead of re-deriving live. Existing rows backfilled at migration-apply time (a genuine no-actor-identity context).

**Regression evidence:** live forged-session reproduction (tenant `lnk1`) against both a pre-existing backfilled link and a link created fresh after the fix — `list_customer_ticket_links` now returns `'Support Team'`/the customer's own real label correctly with zero error, for both.

### 3.4 `ISS-2026-108` fix (High) — rehire reactivation practically unreachable

**Root cause:** the database mechanism (`app.reactivate_user_after_rehire`, its TS wrapper, and a unit test) was genuinely correct and tested, but no server action or UI caller anywhere in the app ever invoked it — unlike every sibling lifecycle action.

**Fix:** wired `reactivateUserAfterRehireAction` (`app/(tenant)/[tenantSlug]/hris/employees/actions.ts`) into the employee detail page and lifecycle-actions panel (`app/(tenant)/[tenantSlug]/hris/employees/[masterRecordId]/page.tsx`, `employee-detail-panel.tsx`) — a "Restore Platform access (rehire)" action alongside the employee's other lifecycle actions, gated on `lifecycle_status='active'` (there is no client-visible signal distinguishing a normal always-active employee from a rehired one whose access is still revoked; the RPC's own already-tested `no_rehire_event` validation surfaces plainly when the action does not apply). No database migration needed.
