## 1. What this checkpoint builds

HRT-277 is the FOURTH Phase 7 (HRIS/Ticketing) capability, built directly on HRT-274 (Employee Master, `VERIFIED`), HRT-275 (Organization and Position Linkage, `VERIFIED`), and HRT-276 (Recruitment/ATS, `VERIFIED`). It is EXACTLY the checkpoint ADR-0023 Part B reserved for the governed candidate→employee→Platform-user conversion: an accepted job offer (HRT-276's own `app.job_offers.status='accepted'`, which explicitly creates no `app.employees`/`app.users` row) converts, exactly once, idempotently, into a linked employee record, and the resulting onboarding/offboarding case drives a versioned checklist workflow (asset/access/training/payroll/Operations handoffs) through to a PLT-123-routed finalize approval. This capability writes through Platform identity/access authority (invite, role grant, revocation) — the specific reason this task runs as its own single-prompt Tier-C batch rather than joining a larger batch.

## 3. Source/config decisions (disclosed, not left implicit)

### 3.1 The employee/user conversion reuses existing Platform primitives exactly — never a second flow

This is the single most load-bearing decision this checkpoint makes, and it was verified by direct code read, not merely asserted:

- **`app.start_onboarding_case`** calls `app.create_employee_draft` (HRT-274) to create the linked employee row — never a raw `app.master_records`/`app.employees` INSERT. Idempotency for the `job_offer` source path is structural (a unique `source_job_offer_id`), so retrying against the same accepted offer always resolves to the same case/employee, never a duplicate.
- **`app.request_onboarding_access_provisioning`** — the real Platform-identity-authority write this whole prompt is chartered around — accepts an *optional* `p_target_auth_user_id`. `app.invite_user` (PLT-107) itself requires an already-linked `auth.users` identity; the standing, repository-wide "invite-by-email-before-signup" gap (re-confirmed this checkpoint: zero `auth.admin.*`/`inviteUserByEmail` call sites exist anywhere in `app/` or `server/`) is not attempted to be closed here — closing it would be a first-of-its-kind auth-identity-creation mechanism, squarely out of this single-prompt batch's own scope. When the caller (HR/IT) already has a resolved auth identity (the realistic case: IT completes the cold-start invite out-of-band and hands the `auth_user_id` back to HR), this RPC performs a REAL, synchronous, governed grant through `app.invite_user` → `app.link_employee_user` → `app.assign_role` (PLT-107/110/111), never a direct `app.users`/`app.role_assignments` INSERT. `app.assign_role` requires the target `app.users.status = 'active'` — a freshly-invited user is `'invited'` until they accept — so this RPC never force-activates an unconfirmed account (that would be an undisclosed authentication bypass); role grants are deferred and disclosed in the task's own `evidence_note` when the target is not yet active, never silently dropped. When no auth identity is resolved yet, the request is recorded (`app.onboarding_task_provisioning_requests`, `status='requested'`) and the task stays `in_progress` — section 22's own "preboarding without user access" alternative flow.
- **`app.request_onboarding_access_revocation`** calls `app.transition_user_status(..., 'revoked', ...)` (PLT-110) directly — already cascades identity and principal-membership revocation on its own, no separate role-revocation loop needed.

### 3.2 Case finalize is precondition-check-only against the employee's own lifecycle FSM, never a chained mutation of it

`app.submit_onboarding_case_for_finalize_approval` requires `app.employees.lifecycle_status = 'active'` for an onboarding case, or `in ('terminated','archived')` for an offboarding case, BEFORE routing to PLT-123 — HR drives the employee's own governed lifecycle transition (via HRT-274's own existing RPCs, with HRT-274's own existing authority gates) exactly once. An earlier design considered having `app.decide_onboarding_case_finalize_approval` itself call `app.terminate_employee` at approval time — rejected during drafting: the PLT-123 approver eligible to decide the case's own finalize step is not guaranteed to hold `HRS:Override` on the employee row, an authority-chaining fragility with no clean failure mode. Precondition-check-only avoids this entirely.

### 3.3 Rehire is a genuinely new employee-lifecycle transition, added additively

`app.reactivate_employee` (HRT-274) only restores from `'suspended'` (verified by direct reading of `20260730830000:1389-1462`) — no terminated/archived → active path exists anywhere. `app.rehire_employee` (terminated → active only; archived stays genuinely terminal, matching HRT-274's own explicit "terminal administrative closure" design intent) is added here as a new, additive function on the pre-existing `app.employees` table — the same kind of downstream extension HRT-275 itself already made when a later capability's own chartered scope genuinely required it. HRT-274's own migration file is not edited.

### 3.4 Employment-type vocabulary mismatch is mapped explicitly, never silently truncated

`app.job_offer_versions.employment_type` (`full_time`/`part_time`/`contract`/`internship`/`temporary`) and `app.employees.employment_type` (`full_time`/`part_time`/`contract`/`intern`/`probation`/`daily_worker`) are genuinely different vocabularies (independently confirmed by reading both CHECK constraints) — `app.map_offer_employment_type_to_employee` maps `internship→intern`, `temporary→contract` (the closest real fit), applied in `app.start_onboarding_case`.

### 3.5 Sensitive HR fields are column-restricted from this, the first, migration

`app.onboarding_offboarding_cases.exit_reason` and `app.onboarding_case_tasks.evidence_note`/`waive_reason` are excluded from the plain `authenticated` column grant (the PLT-114/`app.candidates`/`app.employees` pattern) from this migration's own first grant block — never a blanket grant later narrowed by a review-round retrofit, the exact class HRT-276's own Tier C review found and had to fix after the fact.

### 3.6 Cancellation genuinely cancels an in-flight approval, with a deliberate lock-order

`app.cancel_onboarding_case` calls `app.cancel_approval_request` on any still-`pending_finalize_approval` case's finalize-approval request BEFORE cascading the case to `cancelled` — the exact behavior HRT-276's Tier C review found missing (findings 7/8) and had to retrofit via a corrective migration after live-reproducing a two-process race. Applied here from the first migration. The lock order is deliberate: a plain (non-locking) read of the case decides whether to cancel an approval, deferring all `app.onboarding_offboarding_cases` locking to the terminal `UPDATE` — mirroring HRT-276's own fixed `app.reject_application`/`app.withdraw_application` lock order exactly, so this domain does not reintroduce the identical lock-order-cycle deadlock that fix's own comment documents finding in an early draft.

### 3.7 Checklist templates are bespoke, versioned, tenant-scoped tables — not routed through PLT-121

Mirroring HRT-275's own position/grade catalogue shape (directly tenant-scoped, `record_version`, an active lifecycle) rather than PLT-121's Configuration Engine — a checklist is domain workflow structure with its own task/dependency graph, not a flat key/value config payload.

### 3.8 Asset/training/payroll/Operations handoffs share one task type, not four

`task_type` is a closed, small set (`document`/`access_provisioning`/`access_revocation`/`handoff`/`generic`); asset/training/payroll/Operations handoffs are modeled as `task_type='handoff'` with an explicit `handoff_category` column (`asset`/`training`/`payroll`/`operations`) rather than four separate task types/RPCs — all four are, from this domain's own point of view, an identical shape: an external acknowledgement with evidence, never assumed success. `access_provisioning`/`access_revocation` get their own dedicated RPCs because, unlike the other four, they are the actual Platform-identity-authority writes this whole prompt is chartered around.

## 4. Security/access model

- **RLS:** every one of the 9 new tables carries the hardened default-deny form (`(app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id)) or app.is_supreme_admin()`), proven live against `anon` (schema-privilege denial) and cross-tenant staff (not-found folding) in `scripts/db-tests/hris-onboarding-offboarding.sql`.
- **RBAC:** every write RPC gates through `app.evaluate_permission(actor, tenant, 'HRS', action)` (`Create`/`Edit`/`Approve`/`Override` depending on the action's own sensitivity — waive/cancel require `Override`, the same bar as `app.terminate_employee`), routed through a single shared preamble, `app.resolve_onboarding_case_task_for_write`, for every task-mutation RPC — a composite-OUT-parameter function directly assignable via `:=`, mirroring `app.assert_employee_editable_for_child_crud` (HRT-274), so the same real row locks (case then task) are taken exactly once per call, avoiding an inconsistent lock order across sibling functions.
- **The "fold non-member into not-found" primitive is applied uniformly** — every primary-row lookup follows `if not found or not app.has_active_tenant_membership(v_row.tenant_id, p_actor_auth_user_id) then raise ..._not_found`, so a cross-tenant caller receives a uniform not-found, never a real tenant_id/row-existence disclosure. Applied from the start in this checkpoint (the systemic gap HRT-276 found and had to sweep across ~30+ functions after the fact never recurred here).
- **Column-restricted grants** (§3.5) — `authenticated` has no column-level SELECT on `exit_reason`/`evidence_note`/`waive_reason`; `service_role` has full access. Verified live via `has_column_privilege` in the db-test suite.
- **Concurrency:** every write RPC locks its target row(s) first, folds a non-member caller into not-found, checks authority before `record_version`, and repeats the version predicate in the terminal `UPDATE`'s own `WHERE` clause.
- **The Platform-identity-authority writes** (§3.1) are the actual security-sensitive surface of this checkpoint: `app.request_onboarding_access_provisioning` never force-activates an unconfirmed account to grant a role, and `app.request_onboarding_access_revocation` reuses `app.transition_user_status`'s own already-verified cascade rather than a bespoke, unverified revocation path.

## 7. Self-found defects (found and fixed during this checkpoint's own adversarial db-testing, before commit)

Found via iterative, honest `psql`-driven testing against a live disposable Postgres 16 database, not shipped and found later:

1. **Wrong column name in `app.preview_onboarding_case_start`.** An early draft referenced a column that did not exist on the template-version row being previewed. **Fixed** by correcting the reference to the actual column name.
2. **`app.assign_role`'s active-status precondition (§3.1).** Verified explicitly, not merely discovered by accident — designed the provisioning RPC to check `v_user.status = 'active'` before attempting any role grant and to defer/disclose otherwise, then proved both branches (immediate grant vs. deferred grant) live in the db-test suite.
3. **An over-broad `exit_reason` `CHECK` constraint blocked ALL offboarding case creation, not just invalid reasons.** The original constraint's boolean logic effectively rejected every `case_type='offboarding'` row regardless of the `exit_reason` value supplied — a real bug that would have made offboarding entirely non-functional. **Fixed** by narrowing the constraint to its intended shape and adding a genuine `p_exit_reason` parameter to `app.submit_onboarding_case_for_finalize_approval` (the actual point in the flow where an offboarding case's exit reason is recorded), rather than requiring it at case-start time.
4. **The recurring ambiguous-bare-`id`-against-`RETURNS TABLE`-output bug** (the same class HRT-274/275/276 each independently found and fixed) — a bare column reference inside a function body was ambiguous against that same function's own `RETURNS TABLE` output column of the identical name. **Fixed**, swept across 4 affected functions via table-aliasing, verified each was the only remaining occurrence.
5. (Counted together with 4 above as one swept class, per this repository's own HRT-275/276 precedent for reporting a single recurring bug class found in multiple functions as one item with a shared root cause.)
6. **`ATW-032` (`rbac-enforcement.sql`) gate failure on `app.list_my_onboarding_tasks`.** The self-scoped "my tasks" read RPC was flagged as reachable by `authenticated` with no authority check the automated call-graph scanner recognized (it correctly requires no `HRS` permission — a task owner sees only their own assigned tasks by identity match). **Fixed** by adding an explicit `app.has_active_tenant_membership(...)` call, a genuine, meaningful safety improvement (confirmed via a live query against the closure-computing CTE that this made the function pass), mirroring HRT-276's own identical fix for `get_my_assigned_interviews`.
7. **Postgres `CHECK`-constraint NULL-vs-FALSE gotcha on `handoff_category`.** An early constraint shape used a boolean expression that silently passed when `handoff_category` was `NULL` for a non-`'handoff'` task type in a way that did not correctly reject a `NULL` `handoff_category` on an actual `'handoff'` task, due to Postgres's three-valued CHECK-constraint logic (a `NULL` operand makes the whole expression `NULL`, which CHECK treats as satisfied, not failed). **Fixed** by restructuring the constraint to explicitly enumerate the required and disallowed `NULL` states per `task_type`, rather than relying on implicit boolean short-circuiting.
8. **`INNER JOIN`-from-tasks bug in `app.get_onboarding_checklist_template_version` hid an empty draft version entirely.** The original query joined from `onboarding_checklist_template_tasks` outward to the version row, so a version with zero tasks yet (a brand-new draft, before any task is added) returned no row at all — making a freshly-created draft version invisible to its own read RPC. **Fixed** by restructuring the query to `LEFT JOIN` from the version row outward instead, and added `record_version`/`task_id` output columns that were also missing.
9. **The major, self-found taxonomy-C-01 defect (§6).** `start_onboarding_case`'s idempotency replay matched on key alone; a same-key call with a materially different request (different `case_type`/`source_type`/target employee) would silently return the first case, masking a real caller error. Found during this checkpoint's own mandatory Tier B taxonomy walk, not by a db-test failure. **Fixed** with `app.assert_onboarding_case_start_idempotent_replay`, wired into all 3 replay sites, plus new regression tests proving both a safe identical-replay and a rejected conflicting-replay.
10. **Two `assert.throws`-instead-of-`assert.rejects` test bugs** in `server/mutations/onboarding.test.ts` — `assert.throws` does not correctly catch a rejected Promise from an async function; both call sites silently passed for the wrong reason (the assertion never actually executed the rejection path). **Fixed** by switching both to `assert.rejects`.
11. **A missing `SUPPRESS(...)` governance-metadata comment** on a deliberate `@ts-expect-error` test fixture (proving the Zod schema, not merely TypeScript, rejects malformed input at runtime) — flagged by `scripts/standards/check-suppressions.test.ts`'s own repository-wide governance scan. **Fixed** by adding the required `SUPPRESS(owner=hrt277-onboarding, reason=deliberate runtime-schema-validation test fixture, expires=NONE, adr=NONE)` metadata comment.

Consistent with this repository's own disclosed history (HRT-274 found 7, HRT-275 found 2, HRT-276 found 12), this checkpoint's own honest adversarial pass — including its own mandatory Tier B taxonomy self-check, which caught the single most significant defect (item 9) that live db-testing alone had not yet surfaced — found and fixed 11 real defects before commit.

### 12.1 Finding (CRITICAL, privilege-escalation) + Finding (CRITICAL, authority-bar-mismatch, same root cause reported independently by the security and cross-prompt-integration lenses) — `app.request_onboarding_access_provisioning` let an HRS:Edit-only actor grant ANY published tenant role, including cross-domain FIN/PRC/OPS Approve/Override/Delete, to themselves or a third party

**CONFIRMED**, independently re-derived and live-exploited twice against a fresh disposable database. Created a tenant, an "HR Ops" actor holding only HRS Create/Edit/View (confirmed `evaluate_permission(..., 'FIN', 'Override').allowed = false`), started a `direct_hire` onboarding case with an `access_provisioning` task, published a "Finance Controller" role carrying `FIN:Approve/Override/Delete`/`PRC:Approve`/`OPS:Override` (none flagged `protected=true` — that flag covers only View-class field-masking permissions, confirmed by reading the permissions seed). Called `app.request_onboarding_access_provisioning(..., p_target_auth_user_id=<unrelated tenant member>, p_role_version_ids=[<finance-controller-role>], ..., <HR Ops actor>)` — succeeded. `evaluate_permission(<target>, tenant, 'FIN', 'Override').allowed` flipped to `true`. Repeated as a self-grant (`p_target_auth_user_id = <the HR Ops actor's own id>`) — also succeeded. Root cause: `app.assign_role`'s only in-function guard (self-escalation) fires solely on a SELF-target grant of a `protected=true` permission — never a third-party grant, never an Approve/Override/Delete-class permission either way — and the RPC wrapping it gated only on ordinary `HRS:Edit`, the same bar as editing an employee's home address.

**Fix:** two independent, defense-in-depth layers, both scoped to this RPC's own consumption of `app.assign_role` (the shared PLT-111 primitive itself is untouched — redesigning it is a broader refactor requiring its own ADR per `AGENTS.md`): (1) an actual role grant (`p_role_version_ids` non-empty) now requires `HRS:Override`, matching the bar `app.request_onboarding_access_revocation` already correctly used for the less-escalatory direction (closing the exact asymmetry the review flagged); (2) a new helper, `app.assert_actor_holds_role_version_permissions`, rejects any grant where the actor does not already hold, in this tenant, every permission the requested role version carries — closing the escalation regardless of which HRS-level bar the actor clears, since HRS authority says nothing about FIN/PRC/OPS authority. The `p_role_version_ids`-empty path (record/defer with no auth identity resolved) is unchanged — still `HRS:Edit`, genuinely less sensitive since no authority is actually granted.

**Re-verified against the SAME live attack, both directions, plus adjacent scenarios (per task instruction):** (a) the original third-party exploit — now `insufficient_authority` (HRS:Edit-only actor); (b) the original self-grant exploit — same result; (c) adjacent: an actor holding `HRS:Override` but still zero FIN permission — blocked with `insufficient_authority_to_delegate` for BOTH third-party and self-grant; (d) positive/legitimate path: an actor holding `HRS:Override` AND the target role's own FIN permissions (a real "HR director equivalent" persona) — succeeds, and the target's `evaluate_permission` genuinely flips to `true`; the earlier blocked target never received the permission.
