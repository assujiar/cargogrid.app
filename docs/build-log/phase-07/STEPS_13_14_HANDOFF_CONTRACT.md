## 1. What this contract is, and is not

Phase 7's own relationship to Steps 13–14 is **materially different in shape from Phase 6's own identical pairing one step earlier**, and this asymmetry is the single most important thing to understand before reading either section below:

- **Step 13 (§2):** unlike Phase 6 (which shipped **zero** built contract for any of Steps 12–14 — vendor governance and customer-facing surfaces never touched), Phase 7 ships a **genuinely bounded, real, already-`VERIFIED` customer-facing slice**: a customer ticket channel, customer-safe SLA/escalation-status projections, and customer-safe linked-record summaries (`HRT-287`/`289`/`291`/`292`). This is a real, load-bearing relationship, not a disclosed non-relationship — §2 documents exactly what exists, citing the real routes/RPCs/masking, and exactly what is explicitly named as Step 13's own scope and deliberately not built here.
- **Step 14 (§3):** Phase 7 ships **zero** built AI/autonomous-decision contract — the same honesty shape Phase 6's own document used for all three of its pairings. What Phase 7 does uniquely well here is **name, explicitly, in its own source spec's business rules, exactly which twelve capability-level AI/autonomous boundaries are deferred to Step 14** — a materially more specific disclosure than Phase 6's own single "a metric catalogue exists" observation, because Phase 7's own prompt package itself repeatedly names "Step 14" as the literal reason a capability stops short of prediction/autonomy. §3 catalogues every one of these disclosures, not only the two the source spec of this documentation task names by name (`HRT-291`/`292`).

Nothing below should be read as a design proposal for Step 13 or Step 14 — every "what might a future step read" note is a disclosed plausible-future observation or a genuinely open question, never a built or committed shape. Where Phase 7 built real customer-facing surface, §2.1 says so plainly and cites it; where nothing exists, this document says that plainly too, exactly as `STEPS_12_14_HANDOFF_CONTRACT.md` §2/§3/§4 disclosed "no relationship built" for its own three downstream pairings rather than overclaiming one.

## 2. Step 13 (Phase 8, Customer Portal/Loyalty) — a real, bounded relationship exists; documented exactly, not overclaimed

### 2.1 What exists today — real routes, real RPCs, real masking

**UI routes** (`app/(tenant)/[tenantSlug]/customer-tickets/`, `HRT-287`, re-confirmed live in the route manifest by every Ticket-workstream checkpoint's own `next build` since):
- `customer-tickets/{page,loading,actions,customer-tickets-panel}.tsx` — bounded create/list surface.
- `customer-tickets/[ticketId]/{page,loading,customer-ticket-detail-panel}.tsx` — bounded detail/thread surface (reply, cancel/reopen, SLA status badge, escalation badge, linked-record section).
- Guarded exclusively by `lib/portal/customer-ticket-guard.ts`/`customer-ticket-guard-deps.server.ts`/`resolve-customer-ticket-access.server.ts` — admits `customer_user`-layer principals only, structurally distinct from `lib/portal/ticket-guard.ts` (the internal `org_user`/`tenant_admin` guard).

**Real RPCs — the customer-safe write surface** (`app.tickets`/`app.ticket_messages`, extended by `HRT-287`):
- `app.create_customer_ticket` — self-service creation; `p_account_id` always validated against `app.resolve_customer_owner_account_scope` (reused verbatim from `ATW-242`) before use, so a forged/unowned account id gets the identical `account_not_available` a genuinely nonexistent one would (anti-enumeration). No `p_queue_id` parameter exists — the queue is always the chosen category's own `default_queue_id`.
- `app.reply_to_customer_ticket` — a thin defense-in-depth wrapper over the shared `app.reply_to_ticket` engine; hardcodes `p_visibility := 'public'` and independently re-verifies `channel = 'customer'`.
- `app.transition_ticket_status` — reused **verbatim**, no new transition RPC — a customer's self-cancel/self-reopen is authorized by the exact same generic mechanism an internal requester already uses, once `app._is_ticket_requester_party` resolves via the customer branch (`HRT-287` §3).

**Real RPCs — the customer-safe read surface, all dedicated, never a staff RPC with fields merely dropped client-side** (`server/queries/ticketing.ts`'s own header comment states this convention explicitly, per `HRT-295`'s own §3.3 resolution note): `app.get_customer_ticket`, `app.list_customer_tickets`, `app.list_customer_ticket_messages` (hard-filters `visibility='public'`, replaces a staff author's real name with a fixed `'Support Team'` label), `app.list_customer_ticket_categories`, `app.list_customer_accounts_for_actor`.

**Real RPC — customer-safe SLA status** (`app.get_ticket_sla_status_for_requester`, `supabase/migrations/20260731120000_create_ticket_sla.sql:1623`, `HRT-289`): returns only a target/status-shaped projection — never the underlying policy/calendar version ids, `started_at`, or breach/reminder timestamps a staff caller sees via `app.get_ticket_sla_clock`. A Tier C review (`HRT-289` §14.1 finding 1) found and fixed a real CRITICAL gap where a customer's own forged session could read the full raw `app.ticket_sla_clocks` row directly via RLS before this fix — the raw-table exclusion is now correct and re-verified.

**Real RPC — customer-safe escalation status** (`app.get_ticket_escalation_status_for_requester`, `supabase/migrations/20260731160000_create_ticket_escalation.sql:1750`, `HRT-291`): returns **`is_escalated` only** — no level, target, trigger, or acknowledgement detail, a structurally different RPC from the staff-facing `app.get_ticket_escalation`. Live-proven: a customer requester reads `is_escalated` before/after a real staff escalation and is refused on every staff-only projection. **Disclosed, still-`OPEN` gap** (`ISS-2026-101`, Medium): this RPC has no UI caller reachable by a real `customer_user` principal yet — the mechanism is real and tested, the customer-facing badge is not yet wired into `customer-ticket-detail-panel.tsx`.

**Real RPC — customer-safe linked-record summaries** (`app.list_customer_ticket_links`, `HRT-292`, hardened at `HRT-295` — `supabase/migrations/20260731270000_...sql:462` then corrected at `supabase/migrations/20260731300000_harden_ticketing_customer_links_creator_role_hrt295_tierc.sql:236`): a customer-layer caller's registry is narrowed to exactly four entity types via `app.ticket_link_customer_safe_entity_types()` (`supabase/migrations/20260731170000_create_ticket_linked_records.sql:308`) — **shipment, invoice, warehouse, customer; never vendor or user** (no existing customer-facing read path for either exists anywhere in this repository, both structurally excluded from their own RLS). Every summary is a bounded three-field `{label, detail, status}` snapshot, re-resolved live on every read, never a stale cached value; an unavailable/revoked/deleted source shows a generic `unavailable` status with no leaked stale content. Staff identity on a link is genericized to `'Support Team'`, mirroring the message-author convention exactly — a real High-severity regression this exact fix introduced (`actor_identity_mismatch` breaking the RPC for ordinary customer sessions when a live re-check design was first tried) was found and closed by the same `HRT-295` Tier C follow-up via a stored `created_by_role` column, not a live re-derivation.

**Masking guarantees specific to the customer surface, all live-tested:**
- `resolution_summary` is **always `null`** to the customer (unconditionally staff-authored by construction — `_ticket_transition_authority` never admits a requester into `resolved`/`closed`), a deliberate scope narrowing disclosed as `ISS-2026-088` (Low).
- `cancelled_reason`/`last_reopen_reason` are echoed back to the customer **only when the customer themself authored that specific text** (tracked via `cancelled_reason_authored_by_customer`/`last_reopen_reason_authored_by_customer` columns) — a real, live-reproduced HIGH staff-rationale leak (internal-sounding resolve/cancel/reopen text reaching the customer verbatim) was found and closed at `HRT-287`'s own Tier C review before this checkpoint ever shipped.
- Every staff-facing read RPC (`get_ticket`/`list_tickets`/`list_ticket_messages`/`list_ticket_watchers`/`list_ticket_events`/`export_tickets`) is hardened to refuse a `customer_user`-layer caller entirely.
- Raw-table RLS on `app.tickets`/`app.ticket_messages`/`app.ticket_watchers`/`app.ticket_events`/`app.ticket_sla_clocks`/`app.ticket_escalations`/`app.ticket_escalation_events`/`app.ticket_links`/`app.ticket_link_events` additionally excludes the `customer_user` layer on every table — the `SECURITY DEFINER` customer RPCs named above are the **only** sanctioned customer read path anywhere in Phase 7; a direct `.from()`/PostgREST read returns zero rows for every one of them.

**Account/company/site identity mapping** (`HRT-287` §4): `app.accounts` (`COM-155`) is the **one** canonical customer/account master, already self-referencing via `parent_account_id`. No new "company" or "site" table was created for Phase 7's own ticket channel. A `customer_user`'s own membership scope (`app.grant_principal_membership`, PLT-108, unmodified) determines exactly which account row(s) a given identity may file/see tickets against — **deliberately no implicit hierarchy-cascading access** (a parent-account grant does not automatically see child-account tickets).

**Real HR-domain boundary, stated explicitly by the standing field-policy matrix** (`docs/standards/HR_PAYROLL_FIELD_POLICY_MATRIX.md` §5): *"No Customer Portal exists yet (Step 13) — no HR/payroll field is customer-facing today; nothing to audit for that surface."* No employee, candidate, or payroll table or RPC is reachable by a `customer_user` actor anywhere in Phase 7; the typed-link registry's own customer branch structurally excludes the `employee`/`user` entity types for exactly this reason (`HRT-292` decision 3).

### 3.4 Explicitly forbidden mutations

None of the twelve deferrals above name a specific forbidden mutation of their own (no AI/autonomy mechanism exists to widen), so the general rule Phase 6's own §4.2 established applies identically here: **any future Phase 9 capability must be read-only against every Phase 7 table**, and must respect the same `HRS:View payroll`/`HRS:View personal data`/`TICKETING_REGISTRY`/RLS/RBAC boundaries `docs/standards/HR_PAYROLL_FIELD_POLICY_MATRIX.md` describes when aggregating data that touches sensitive fields. - **No future analytics/AI aggregation path may read `app.payroll_*` tables unmasked for training or aggregation.** `payroll_component_versions`/`payroll_employee_component_assignments`/`payroll_run_employee_results`/`payroll_payslips` and siblings are `HRS:View payroll`-gated even for their own existence/metadata, deliberately stronger than plain tenant membership or `HRS:View personal data` — only the employee themself or a genuine `HRS:View payroll` holder may see this data at all (`HRT-282` decision 5, re-confirmed unchanged by `HRT-294`'s own Critical Flow 1 live reconciliation).
