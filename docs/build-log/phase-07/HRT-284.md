## 1. What this checkpoint builds

HRT-284 is the thirteenth Phase 7 (HRIS/Ticketing) capability, built directly on HRT-274 (Employee Master), HRT-275 (Organization and Position Linkage), HRT-283 (KPI and Performance — `app.training_development_plans.linked_performance_outcome_id` references its `app.performance_outcomes`), and PLT-128 (private/scanned file evidence) and PLT-131/132 (durable job framework), both reused unchanged. It implements: a competency/skill catalogue; a two-tier versioned course catalogue (course + course version, exactly one published version at a time — mirrors HRT-283's KPI-definition-version shape); internal/external providers; direct course prerequisites, enforced inside the enrollment RPC; scheduled sessions with a real, lock-protected capacity/waitlist mechanism; enrollment (self-service, manager/HR-assigned, and a real bulk mandatory-compliance-training batch), with an enrollment-approval gate, decision, cancellation-with-waitlist-promotion, and reschedule; attendance and completion recording; multi-attempt assessment with a deterministic computed pass/fail; certificates (internal issuance, historical import with source/verification labeling, private malware-scanned evidence attach, verify, revoke, renew) plus real durable-job-based expiry and expiry-reminder batches (PLT-131/132, widening `app.jobs.job_type`/`app.generic_job_types()` a fifth time); development plans and their actions, optionally cross-referencing a specific performance outcome; and a RESTRICTED talent workspace — review cycle/assignment/review (assigned-reviewer-only visibility, explicit non-mutating reassignment), talent pools, and succession candidates — every talent-domain write gated on `HRS:Override`, with a genuine k-anonymity floor (k=5) on the one aggregate report. No code path in this migration writes to `app.employees.lifecycle_status`, any `app.payroll_*` table, any `app.performance_*` table, or any role/permission table — training/talent records never automatically alter pay, employment, or position.

## 3. Source/config decisions (disclosed, not left implicit)

All 12 decisions are recorded in the migration's own header comment — summarized here.

1. **Competency is a single status-lifecycle catalogue row (draft/published/archived), not a two-tier parent+version model.** Unlike a KPI definition or payroll component, a competency here carries no scored/weighted configuration a later edit could retroactively disturb — it is a reference taxonomy tag a course links to (`training_course_competencies`). Course curriculum content is where the genuine two-tier versioning need lives (decision 2).
2. **Course/course-version is a two-tier versioned catalogue, mirrors HRT-283's KPI-definition/version and HRT-282's payroll-component/version exactly** — exactly one published version at a time; every session and enrollment freezes the specific version it was scheduled/enrolled against.
3. **Capacity, waitlist, and prerequisite enforcement all happen inside the enrollment RPC under a session-row lock (taxonomy C-04)** — never a UI-side check. Every function that touches both a session and its enrollments locks the session (parent) before any enrollment (child) row, in the identical order throughout; the one function touching two sessions (reschedule) locks both, ordered by ascending id, to avoid a cross-function deadlock against a concurrent reverse-direction reschedule (taxonomy C-21, applied from the start).
4. **Certificate/provider evidence reuses the established PLT-128 private, malware-scanned `app.files` gate (taxonomy C-10) exactly as `app.record_gps_device_installation`/every onboarding-task-evidence RPC already does.** A certificate is created first, then evidence is attached via a dedicated RPC re-validating tenant, record scope, and clean-scan status at the accepting RPC itself — mirrors `app.attach_payroll_component_version_evidence`'s (HRT-282) two-step shape, avoiding the chicken-and-egg problem of uploading a file scoped to a record that does not exist yet.
5. **Certificate expiry and reminder both reuse the established PLT-131/132 `app.jobs` durable-job framework** (enqueue → self-claim → scan → complete), the identical inline-batch shape `app.run_leave_accrual_batch`/`app.run_leave_carry_forward_batch` (HRT-280) already established — never a second job mechanism.
6. **Talent review/pool/succession is the most restricted tier in this checkpoint: every write gates on `HRS:Override`, and read access is narrower still.** A review cycle/assignment is readable by an `HRS:Override` holder OR the specific employee assigned as reviewer for that case ("restricted talent reviewers see assigned cases", section 26, taken literally). A talent pool and a succession candidate carry no per-case reviewer concept and are `HRS:Override`-only, full stop — never self- or manager-visible, deliberately narrower than every other person-scoped table in this migration.
7. **Talent-domain decisions (succession candidate confirm/withdraw) require a mandatory reason and a structural self-decision block**, mirroring HRT-283 decision 4 — never PLT-123 maker-checker (nothing here is the batch-wide, irreversible, fund-disbursing moment HRT-282 decision 6 reserved that for).
8. **A genuine k-anonymity floor (k=5) on the one aggregate report: talent pool distribution by department.** `member_count` (the raw headcount itself, the disclosive fact in this domain) is nulled and `suppressed=true` for any department with fewer than 5 active pool members, enforced inside the `SECURITY DEFINER` function itself.
9. **Taxonomy C-24 audit-masking discipline applied from the start** — every `capture_audit_event` call passes `p_reason => null` and a reviewed, non-sensitive `after_value` allowlist, never `potential_rating`/`readiness_note`/`risk_of_loss`/`decision_reason`/score/notes/any raw `p_*_reason` parameter.
10. **No rating-band/predictive subsystem**; `potential_rating` is a small, closed, human-entered enum (low/moderate/high), never a computed score. No predictive/AI-driven talent ranking (Step 14 boundary).
11. **Deliberately not built, disclosed rather than silently dropped**: no employee-level competency-proficiency-rating subsystem (only a course-to-competency catalogue link — section 13 never names a persisted "employee skill rating" record of its own); no REST/GraphQL adapter (repository-wide precedent); no per-date multi-day attendance granularity (one summary `attended`/`hours_attended` pair per enrollment); no live notification DISPATCH for certificate expiry reminders — the durable job produces a real, queryable `training_certificate_expiry_reminders` record (the actual scan/detection/dedup mechanism section 20 requires) but does not call `app.queue_notification`, since doing so would require this checkpoint to also author and publish a Platform notification-type config version, a cross-cutting concern with zero precedent anywhere in the repository (grep-confirmed: zero other capability calls it either) — disclosed exactly like PRC-261's identical gap for vendor-contract expiry.
12. **`talent_review_assignments` models exactly one active reviewer per (cycle, subject)** — a disclosed V1 simplification, never a multi-reviewer 360 for talent review (unlike HRT-283's own performance-assessment reviewer model, which does support multiple).

## 4. Security/access model

- **RLS:** catalogue tables (`training_competencies`, `training_courses`/`_course_versions`/`_course_competencies`, `training_providers`, `training_course_prerequisites`, `training_sessions`) are broadly tenant-member-readable ("training may be broadly visible", section 16) — mirrors HRT-283's `performance_kpi_definitions`/`_templates` precedent exactly, hardened against a `customer_user`-layer principal. Person-scoped tables (`training_enrollments`, `training_assessments`, `training_certificates`, `training_certificate_expiry_reminders`, `training_development_plans`/`_plan_actions`) use `app.can_view_hris_training_talent_row` (self/direct-manager/`HRS:View personal data`) — "results... are purpose- and field-restricted" (section 16). Talent-domain tables use `app.can_view_talent_review_row` (review cycle/assignment/review) or a direct `HRS:Override` check (pools/pool-members/succession-candidates) — decision 6's deliberately narrower model, never self, never direct manager.
- **RBAC:** every write gates through `app.check_training_authority` (`SECURITY DEFINER` from the start — HRT-281/282/283's own established lesson).
- **Managers do NOT see talent-domain data by hierarchy at all** — the deliberate narrowing beyond even HRT-282's decision 5.
- **Concurrency:** every version-guarded write locks `FOR UPDATE` then re-checks `record_version` at the terminal `UPDATE`; capacity-affecting functions lock the session row first, always in the same order across every function that touches both a session and its enrollments — live-proven with two genuinely concurrent OS processes, §8.
- **Internal engine function** (`_enroll_employee_in_training_session_internal`, `_training_prerequisites_met`, `compute_training_assessment_passed`) is granted `service_role` only, never `authenticated` — live-verified in `scripts/db-tests/hris-training-talent.sql`.
