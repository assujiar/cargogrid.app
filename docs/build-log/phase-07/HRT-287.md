## 3. Identity-model resolution (ISS-2026-085) — the single most important section in this report

**The exact shape of the fix**, matching every element ISS-2026-085's own analysis named as required:

1. `app.tickets.requester_employee_id` relaxed from `NOT NULL` to nullable (`alter table ... alter column ... drop not null`).
2. A new nullable `requester_customer_account_id uuid references app.accounts (id)` column added.
3. A structural CHECK, `tickets_requester_identity_shape`, enforces exactly one of the two, matching `channel` — the database itself makes an internal ticket with a customer requester (or vice versa) impossible, not merely discouraged by RPC discipline.
4. `channel` CHECK widened to `('internal', 'customer')`.
5. `app._create_ticket` given a real `p_channel` parameter (and `p_requester_customer_account_id`) — the OLD 10-argument overload is explicitly `drop function if exists`-ed first, never left as a stale, ambiguous second overload alongside the new 12-argument one.
6. The three `INNER JOIN app.employees` reads ISS-2026-085 named (`get_ticket`, `list_tickets`, `export_tickets`) converted to `LEFT JOIN`, `coalesce`d against a new `LEFT JOIN app.accounts` for the requester's display name.
7. **Generalized, not duplicated** (per HRT-286 Tier C's own integration-lens Finding 2 suggestion): a single new helper, `app._is_ticket_requester_party(ticket, auth_user_id)`, dispatches on `ticket.channel` — employee-match (`app.get_self_employee`) for `internal`, membership-scope match (`app.resolve_customer_owner_account_scope`, ATW-242's own already-VERIFIED primitive) for `customer`. It REPLACES the inline `app.get_self_employee`-based check everywhere it previously appeared: `app.can_access_ticket`, `app.reply_to_ticket`, `app.add_ticket_watcher`/`app.remove_ticket_watcher`, `app._ticket_transition_authority`. This is the ONE structural-scope predicate for both channels — never a fourth, ticket-specific access-evaluation shape (the integration lens's own explicit ask).
8. **Provably byte-for-byte unchanged for the `internal` channel** — not merely asserted. `scripts/db-tests/ticketing-internal.sql`'s full 15-assertion-group suite was re-run against the post-migration schema (fresh disposable database, full migration set including `20260731080000`) and passed identically, confirmed twice across this session.

**Where the new customer-facing surface lives (never a second ticket table/service):**
- `app.create_customer_ticket` — self-service creation. `p_account_id` is a real parameter (a customer admin may hold membership on several accounts and must choose which one), but it is ALWAYS validated against `app.resolve_customer_owner_account_scope(actor, tenant)` before use — a forged/unowned account id gets the identical `account_not_available` a genuinely nonexistent one would, so a caller cannot distinguish "not yours" from "does not exist" (anti-enumeration, mirrors ATW-242's own established discipline). No `p_queue_id` parameter exists at all — the queue is always the chosen category's own `default_queue_id`, so a customer can never probe or forge an internal queue id.
- `app.reply_to_ticket` is REUSED directly (channel-agnostic once decision 7 above lands) for the write path; `app.reply_to_customer_ticket` is a thin defense-in-depth wrapper that independently re-verifies the ticket is genuinely `channel='customer'` and hardcodes `p_visibility := 'public'` at the SQL call site, on top of `reply_to_ticket`'s own internal `not staff → no internal` guard — two independent enforcement points for one guarantee.
- Close/reopen-as-configured reuses `app.transition_ticket_status` VERBATIM — no new transition RPC at all. Once `_ticket_transition_authority`'s own `v_is_requester` resolves via `_is_ticket_requester_party`, a customer's cancel/reopen (both `requester_allowed=true` in the pre-existing `app.ticket_status_transitions` graph) is authorized by the exact same generic mechanism an internal requester already used.
- Reads are ALL new, dedicated, customer-safe projections — `app.get_customer_ticket`, `app.list_customer_tickets`, `app.list_customer_ticket_messages`, `app.list_customer_ticket_categories`, `app.list_customer_accounts_for_actor` — never the staff `get_ticket`/`list_tickets`/`list_ticket_messages` with fields merely unused client-side. Each deliberately excludes queue/assignee identity; `list_customer_ticket_messages` hard-filters `visibility='public'` (no visibility parameter exists to forward) and replaces a staff author's real name with a fixed generic `'Support Team'` label.
- The staff-facing `get_ticket`/`list_tickets`/`list_my_tickets`/`list_ticket_messages`/`list_ticket_watchers`/`list_ticket_events`/`export_tickets` were ALL explicitly hardened to refuse a `customer_user`-layer caller entirely (`app.actor_holds_customer_user_layer` guard added) — required because widening `can_access_ticket` to legitimately admit a customer to their OWN ticket would otherwise have let that same customer call the STAFF projection directly.
- Raw-table RLS on `app.tickets`/`app.ticket_messages`/`app.ticket_watchers`/`app.ticket_events` additionally excludes `customer_user`-layer entirely (`not app.actor_holds_customer_user_layer(...)` added to all 4 SELECT policies, mirroring the already-established `20260730311000` ATW-023 hardening precedent exactly) — the SECURITY DEFINER customer RPCs above are the ONLY sanctioned customer read path, never a raw `.from("tickets")` call.

## 4. Account/company/site mapping decision (disclosed, since the prompt's own section 13 names all three)

`app.accounts` (COM-155) is the ONE canonical customer/account master and already carries `parent_account_id` — a real, self-referencing hierarchy. **No new "company" or "site" table was created.** "Account," "company," and "site" are all represented by the SAME `app.accounts` row shape, related via `parent_account_id`: a tenant's Commercial team can create a parent "company" account and child "site" accounts underneath it using COM-155's own existing mechanism, unchanged here. A `customer_user`'s own membership scope (`app.grant_principal_membership(..., 'customer_user', tenant_id, account_id::text, ...)`, PLT-108, unchanged) determines EXACTLY which account row(s) — parent, child, or several — that identity may file/see tickets against. **Deliberately no implicit hierarchy-cascading access**: a customer admin granted membership on a parent account sees only that one account's tickets, not its children's, unless separately granted on each child. This is a genuine, disclosed design decision (implicit cascade would silently widen scope beyond what was explicitly granted) — a future prompt could add an explicit `p_include_child_accounts`-shaped parameter deliberately, never inferred silently.
