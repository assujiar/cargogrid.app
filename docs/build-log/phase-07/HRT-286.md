## 3. Schema/naming decisions (disclosed — Prompt 287/288 depend on reading this)

### Decision 1 — directory naming: `ticketing`, not `internal-ticket`

`server/contracts/ticketing/`, `server/queries/ticketing.ts`, `server/mutations/ticketing.ts`, and the `TICKETING_REGISTRY` all use the domain name `ticketing`, not `internal-ticket` — because the underlying RPCs, contracts, and row types are already channel-agnostic (only `channel`'s own CHECK constraint and the identity-resolution path that populates `requester_employee_id` differ per future channel). Prompt 287/288 are expected to ADD to these same three files (new mutation wrappers calling a channel-specific creation RPC that shares `app._create_ticket`'s engine), not create parallel `customer-ticket`/`helpdesk-ticket` files. The UI route family is `app/(tenant)/[tenantSlug]/tickets/` (a dedicated top-level portal, sibling of `hris/`, matching the workstream's own name "Ticket Channels and Conversation" and this repository's own precedent of one guard/route-family per top-level portal section) — not nested under `hris/`.

### Decision 2 — channel extensibility is a pure additive CHECK-widen

`app.tickets.channel` is checked against `('internal')` only, in this migration alone. Every column the canonical model will ever need for `customer`/`helpdesk` already exists (the requester/participant/conversation/attachment/status shape is generic) — only the allowed `channel` value and the requester-identity-resolution entry point differ. Prompt 287/288 are expected to `alter table ... drop constraint tickets_channel_check, add constraint ... check (channel in ('internal','customer'))` (or `,'helpdesk'`) in their OWN new migration, plus their own `create or replace function` for a channel-specific creation entry point that calls the SAME shared `app._create_ticket` engine with a different `p_channel` — never a second ticket table, never a redesign. This mirrors the precedented "widen the CHECK constraint and the reference table together, in a later migration" pattern `app.jobs.job_type` already used repeatedly.

### Decision 3 — requester/assignee/watcher/queue-staff identity: `app.employees`, not a Platform-Layer-3-only identity — a deliberate, disclosed departure from this phase's own original planning note

**This is the single most important disclosure in this report.** `docs/build-log/phase-07/00_EXECUTION_INDEX.md` §5 (written 2026-08-09, BEFORE HRT-274/Employee Master existed) states: *"`HRT-286`'s own §9 reads 'HRT-273; Platform user/org/workflow/file/notification/job foundations...' — it does NOT cite HRT-274 or any HR-track prompt. This matches `272_HRIS_TICKETING_README.md` §7's own architecture note that internal ticket assignees resolve through Platform Layer-3 user identity, not the not-yet-built Employee Master table."* That note's own stated purpose was to let the Ticket track build in parallel with, independent of, the HR track.

This checkpoint does NOT follow that original plan. Every identity reference on the canonical ticket model — `tickets.requester_employee_id`, `tickets.assignee_employee_id`, `ticket_queue_members.employee_id`, `ticket_watchers.employee_id` — is a real FK to `app.employees(master_record_id)`, resolved via `app.get_self_employee` (HRT-278's own established helper), exactly as this task's own mandatory reading instructed verbatim: *"Requester is a Layer 3 tenant user (an app.employees-linked identity, reusing the established employee/user link, never a new identity concept)."*

**Why this is the right call now, even though it contradicts the original plan:** the original plan's own reasoning (parallel buildability) is moot — by the time this checkpoint ran, HRT-274 through HRT-285 were already `VERIFIED`/`COMPLETED` on this same branch, so the Employee Master table is not "not-yet-built" and never was during this checkpoint's own execution. Every other Phase 7 capability (leave, attendance, overtime, KPI, training, self-service) resolves self-identity through this exact same `app.get_self_employee` path — inventing a SEPARATE, Employee-Master-bypassing identity resolution for tickets alone would itself be the "second identity mechanism" this whole build has consistently forbidden, and `app.employees` already carries exactly the department/manager/org-unit context a ticket queue/requester genuinely needs. The execution index's own §5 explicitly frames this as "disclosed but not acted on... a re-evaluation trigger, not a current blocker in substance," not a hard prohibition.

**Practical consequence, disclosed:** `docs/build-log/phase-07/00_EXECUTION_INDEX.md` §5's dependency graph, which currently shows the Ticket track (`HRT-286→292`) as independent of the HR track and reconverging only at `HRT-293`, is now stale against this checkpoint's own actual implementation — `HRT-286` genuinely depends on `HRT-274` (Employee Master) as built. **This checkpoint does not edit that file** (out of this task's own allowed-files scope and not requested); it is flagged here explicitly so a future execution-index update, or Tier C review, corrects the graph rather than re-discovering the same tension independently. This is a real, disclosed design deviation from original planning, not a silent one.

### Decision 4 — access model: two independent dimensions (structural scope + RBAC)

`app.can_access_ticket`/`app.is_ticket_staff` decide WHO can see/touch a ticket at all (requester, assignee, active watcher, or active queue member of the ticket's queue — mirrors `app.can_access_record`'s PLT-114 ownership-vs-shared-scope split). `TKT:Assign`/`TKT:Close`/`TKT:Reopen`/`TKT:Edit` (all already seeded at PLT-111) gate the higher-stakes actions on TOP of that structural scope. Plain queue membership (no extra permission) is sufficient for ordinary ticket work (read internal notes, reply, transfer, reclassify); the seeded named permissions are reserved for assign/resolve/close/reopen and for queue/category CONFIGURATION. **Deliberately no blanket "any `TKT:View` holder sees every ticket" clause** (`TKT:View` is seeded but never referenced by `can_access_ticket`) — section 26's "managers see scoped reports" is disclosed as NOT built this prompt (a genuinely different, dashboard-shaped capability), rather than faked via an over-broad permission check that would have made this prompt's own core isolation guarantee untestable.

### Decision 5 — the opening message IS the ticket body; attachments are multi-file (`uuid[]`), not single-file

`app._create_ticket` inserts the ticket row AND its own first `ticket_messages` row (`visibility='public'`, `author_role='requester'`) in one transaction — there is no separate `description` column on `app.tickets` to keep in sync. `ticket_messages.attachment_file_ids` is a `uuid[]` (a deliberate departure from the single-`evidence_file_id` convention most other HRT capabilities use) because a real support conversation routinely needs more than one file per reply.

### Decision 6 — C-24 discipline: `app.ticket_audit_projection` excludes every free-text column

`app.tickets.subject`/`resolution_summary`/`cancelled_reason`/`last_reopen_reason` and `app.ticket_messages.body` are ALL free text that can carry anything a real service conversation carries. `app.ticket_audit_projection()` is an explicit, allowlisted, structural-fields-only projection (mirrors `app.leave_request_audit_projection`) — never `to_jsonb(row)`. Every `capture_audit_event` call site for messages logs only `{ticket_id, visibility, attachment_count, is_redacted}`, never `body`, not even on redaction. `app.ticket_events` (the ticket-scoped status/assignment/transfer/classification/watcher history) is deliberately different: it IS allowed to carry the real transition `reason` text, because its own RLS is the exact same `app.can_access_ticket` predicate as the ticket itself — no broader audience than the ticket already has, unlike `app.audit_logs` (readable by any tenant's plain `tenant_admin`).

## 4. Security/access model

- **RLS**: every new table has `enable row level security` plus an explicit `select` policy. Catalog tables (`ticket_queues`/`ticket_categories`/`ticket_queue_members`) use the standard tenant-membership-minus-customer-layer predicate this repository uses everywhere. `tickets`/`ticket_messages`/`ticket_watchers`/`ticket_events` use `app.can_access_ticket`/`app.is_ticket_staff` — the SAME predicate every read RPC's own WHERE clause independently applies (defense in depth: RLS protects a raw `.from()` read, the RPC's own predicate is what actually enforces scope for RPC callers, since a `SECURITY DEFINER` function does not automatically inherit RLS).
- **Writes**: exclusively through `SECURITY DEFINER` RPCs; no `insert`/`update` grant to `authenticated` on any table.
- **C-13**: every RPC taking `p_actor_auth_user_id` calls `app.assert_actor_is_session_identity` first (verified by a mechanical scan of the whole migration — the only 3 functions without it are `check_ticket_authority`/`_create_ticket`/`_ticket_transition_authority`, all internal helpers whose own callers already assert it).
- **C-12**: every `SECURITY DEFINER` function granted to `authenticated` performs a real check (`evaluate_permission`, `can_access_ticket`, `is_ticket_staff`, or tenant membership) before returning/mutating data.

## 5. Tier B — recurring defect taxonomy self-check (`docs/standards/RECURRING_DEFECT_TAXONOMY.md` §4)
