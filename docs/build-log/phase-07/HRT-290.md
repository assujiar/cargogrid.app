## 3. The three-channel routing/assignment shape — exact decision

Re-confirmed by direct code read (not assumed) before writing a single line: `app.assign_ticket`/`app.transfer_ticket_queue` (HRT-286, re-shaped by HRT-287/288) already reject nothing for `channel='customer'` — a customer-channel ticket routes/claims/assigns through the identical internal staff/queue mechanism as an internal ticket; only the customer-facing READ surface (HRT-287's own `get_customer_ticket`/`list_customer_tickets`) omits assignee/queue identity. Helpdesk is different in kind, not merely narrower: `app.is_ticket_staff` is hardened (HRT-288 decision 3) so a helpdesk ticket's staff bar is Supreme-Admin-only, with dedicated, unmodified `app.assign_helpdesk_ticket`/`app.transfer_helpdesk_support_queue` siblings. This checkpoint's entire new routing-rule/eligibility/ledger/claim/accept/decline/auto-route machinery is therefore bounded to `internal`/`customer` channels — every new function explicitly, cleanly rejects a helpdesk-channel ticket (`channel_not_supported`, pointing at the existing helpdesk RPCs), never fighting or duplicating that shape. Disclosed, bounded limitation: no non-Supreme-Admin "Platform support agent" eligibility model exists yet for helpdesk; a future prompt introducing one could extend `app.ticket_routing_rule_versions.channel`'s CHECK the same additive way HRT-287/288 widened `channel` itself.

## 4. Routing precedence and concurrency — the exact decisions

- **Precedence** (`app._resolve_ticket_routing_rule_for_ticket`) mirrors HRT-289's `app.resolve_effective_sla_policy_version` verbatim in shape: `rank()`-ranked by specificity (category set > priority set > explicit `precedence_rank` tie-break — only two scope dimensions vary here since the queue is the engine's OUTPUT, not an input), a genuine tie raises `ticket_routing_rule_ambiguous_match` rather than picking arbitrarily — live-reproduced (two different rules, identical scope, identical rank) and live-resolved. `app.publish_ticket_routing_rule_version` supersedes the SAME rule's own prior published version under a parent-row lock, applying HRT-289's own self-found Tier C fix (`app.publish_sla_policy_version`'s "a revised version tied against its own predecessor") **from the start**, not rediscovered.
- **Concurrency**: optimistic-version-plus-row-lock, matching every prior ticket RPC — no advisory lock introduced. `app.claim_ticket` takes `select ... for update` exactly like `app.assign_ticket` always has; the record_version check is ordered immediately after existence/access/(queue-membership authority), before every business-rule check that depends on a fresh read, mirroring the established order every sibling RPC in this migration set already uses (channel-reject → authority → version → business rule). Live-reproduced with two real, concurrent OS `psql` processes (`scripts/db-tests/wms-picking-concurrency-helper.sh`, reused verbatim): exactly one winner, the loser's own captured error is a clean `stale_version`/`serialization_failure`, never a raw constraint violation. A separate, narrower `ticket_already_assigned` conflict exists for the genuinely different "caller supplies a current version but the ticket is already owned by someone else" case — both are clean, discriminated errors.
- **Workload cap**: hard block, no override, on self-service `app.claim_ticket`; an explicit, TKT:Assign-authorized, disclosed override (`p_override_workload_limit`) on manager-driven `app.assign_ticket` — a manager legitimately needs to push a genuinely urgent ticket onto someone already at capacity; a self-serving agent should not load-balance around their own configured limit. Eligibility (see §5), by contrast, is a hard block on BOTH paths with **no** override anywhere — live-proven: `assign_ticket` with `p_override_workload_limit=true` still refuses an on-leave employee.

## 5. Effective eligibility and "delegation" — exact decisions

`app._is_employee_ticket_eligible` reuses ONLY existing canonical concepts: `app.employees.lifecycle_status='active'` (HRT-274) AND no currently-dated, `status='approved'` `app.leave_requests` row (HRT-278/280) — no parallel "agent status" column or table invented. "Delegation" (section 13's own named requirement) is honestly disclosed as N/A for ticket routing rather than silently dropped: this repository's one existing delegation concept (`app.approval_delegations`, PLT-118) is scoped to approval-DECISION authority, a materially different shape from ticket routing, where "coverage while an agent is away" is already provided by queue-membership breadth itself — any other active, eligible member of the same queue may already claim/be assigned any ticket in that queue, with no named 1:1 backup required. Reusing the wrong existing concept would not have been better than disclosing none.

## 6. Workload snapshot — exact decision

`app.get_ticket_queue_workload` is a live `COUNT(*)` aggregation over `app.tickets`/`app.ticket_queue_members`, computed on every call — never a second, separately-maintained counter that could drift from the real current-owner columns (section 13's own "never a second source of truth for who's assigned"). The same live-count helper (`app._count_employee_active_ticket_assignments`) backs the workload cap check, `app.list_ticket_assignment_candidates`, and `app.get_ticket_queue_workload` — one source, three consumers.

## 9. Disclosed scope boundaries (C-23 discipline — named, not silently dropped)

- **"claim/unclaim" (section 14's own API-impact wording) is unified into ONE mechanism** (`app.decline_ticket_assignment`), not two near-duplicate RPCs. Both a self-initiated give-back and a "return this to the backlog" action are the identical state transition (`assignee_employee_id → null`, current-assignee-only, ledger-logged) — a mandatory reason is required for either case, a deliberate, minor discipline choice (audit value regardless of who initiated it), not a functional gap.
- **"Bulk reassignment after revocation" (section 22's own alternative-flow wording) is not built.** When an employee is removed from a queue (`app.remove_ticket_queue_member`, unchanged) or becomes ineligible (suspended/terminated/on-leave), their EXISTING already-assigned tickets remain assigned to them — visible as an ineligible current owner in the candidate/workload views, but not automatically swept. A bulk/automatic reassignment is a genuinely separate, batch-shaped operation with its own partial-failure/concurrency semantics, and touching potentially many `app.tickets` rows from within the existing, already-`VERIFIED` `app.remove_ticket_queue_member` would be a significant, out-of-mandate behavior change to that function. A manager can already compose today's primitives (`app.list_ticket_assignment_candidates`/`app.get_ticket_queue_workload` to find affected tickets, `app.assign_ticket` to reassign each) — just not as one atomic bulk call.
- **Round-robin (section 22's own wording) is deliberately implemented as deterministic LEAST-LOADED, not literal rotation** — `assignment_mode='least_loaded'`, not `'round_robin'`, named accurately rather than overclaiming a rotating-pointer algorithm this checkpoint does not build. Both are legitimate instances of "configured deterministic routing" (the spec's own broader category); least-loaded was chosen as the more useful default and is fully deterministic/explainable/tie-broken, matching every acceptance-criteria requirement that actually applies.
- **A dedicated "queue backlog" list view with an inline per-row claim action is not built as a separate page.** The existing `tickets/page.tsx` "Queue" tab (HRT-286) already lists every visible ticket; claim/accept/decline/auto-route/candidates/workload live on the ticket detail page (`tickets/[ticketId]`) instead, reachable in one click from that list. A future prompt could add an inline quick-claim affordance to the list rows themselves; this checkpoint's own bounded slice covers the full capability through one additional click rather than duplicating it in two places.
