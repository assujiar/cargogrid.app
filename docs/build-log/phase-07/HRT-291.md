## 3. Scope decisions — exact, disclosed

1. **Channel bounded to internal/customer, mirroring HRT-290's own precedent-setting decision 2 exactly.** Every new table carrying a channel column restricts it to `('internal','customer')`; every RPC that operates against a real ticket explicitly rejects `channel='helpdesk'` (`channel_not_supported` for `escalate_ticket`, the identical `ticket_not_found` an RLS predicate would produce for acknowledge/suppress/resolve, matching the established anti-enumeration shape those RPCs already use elsewhere). A Supreme-Admin-only helpdesk escalation path was NOT built — disclosed, deliberate: it would double the RPC/db-test/UI surface for a channel with no non-Supreme-Admin staffing model of any kind (HRT-288 decision 3, HRT-290 decision 2); a future prompt can add one additively without touching this shape.
2. **Target is queue or employee only — no role/team target type.** HRT-290's own Tier C review (`ISS-2026-089`) already disclosed no team/team-membership entity exists anywhere in this repository, and that queue-based grouping is the correct, working team-analog every other capability in this phase uses — reused identically here. A "role" target (broadcast-notify every current role holder) is a genuinely different fan-out shape from every other target-resolution concept in this codebase (which always resolves to exactly one accountable employee or one queue) and was deliberately not built — disclosed, not silently dropped.
3. **Escalation may notify and/or reassign, exactly as independently configured per level — "create an approval/task" was deliberately NOT built.** This repository's approval engine and every ticket workflow concept model a fundamentally different, typed-target object shape; wiring ticket escalation into it is a real, separate integration a future prompt should own deliberately. `action_notify`/`action_reassign` are the two real, independently-configured, live-tested actions this checkpoint ships.
4. **Reassignment reuses `app._apply_ticket_assignment` (HRT-290) directly — never a second per-ticket assignment mechanism.** When a level's `action_reassign` fires against an eligible employee target, `app._apply_ticket_escalation` calls the SAME shared engine `claim_ticket`/`assign_ticket`/`auto_route_ticket` already call, so the resulting reassignment is logged to the existing, already-VERIFIED `app.ticket_assignment_events` ledger exactly like any other reassignment — live-proven in db-test §6 (`assignee_employee_id` updated, a real `event_type='reassign'` row present in `app.ticket_assignment_events`, AND a `event_type='reassigned'` row in the new escalation ledger).
5. **A missing/ineligible/revoked target is a disclosed, ledger-recorded outcome, never a silent no-op or hard failure** — mirrors `auto_route_ticket`'s own "no eligible candidate" precedent (HRT-290) exactly. `app._ticket_escalation_target_eligible` (reusing `app._is_employee_ticket_eligible` from HRT-290 verbatim for an employee target) gates every target at both authoring time (existence/tenant-scope) and trigger time (liveness/eligibility); a trigger-time miss records `reassign_skipped`/`notification_failed` with a real, human-readable reason. `app.escalate_ticket` itself hard-rejects (`escalation_target_not_eligible`) a manual escalation to a missing/ineligible target outright — live-proven in db-test §2.
6. **Idempotency is the natural key (ticket, policy/version, trigger, level) PLUS the ticket's own `reopen_count` at trigger time.** A reopened-and-rebreached ticket is honestly a new escalation cycle (HRT-286's own `reopen_count` column, reused verbatim, never a parallel "cycle" column). The real guarantee is a real partial unique index (`ticket_escalation_events_triggered_unique`) backed by a real `exception when unique_violation` handler in `app._apply_ticket_escalation` (C-01/C-02 mandate) — **a genuine bug in an early draft was self-found and fixed here**, see §6.
7. **Resolution/closure/cancellation resolves an open escalation on the NEXT batch evaluation pass — an honest, disclosed latency**, never a hidden hook into `app.transition_ticket_status` (untouched), matching HRT-289's own decision 1 ("every cross-cutting ticket concern is an explicit, separate, periodically-evaluated consumer, never a trigger"). `app.resolve_ticket_escalation` additionally gives staff an immediate, explicit, real-time manual de-escalate action (section 14's own named "resolve/de-escalate" API operation) — `event_type='recovered'`, structurally distinct from the auto-evaluator's own `event_type='resolved'`.
8. **Cooldown is a real, load-bearing per-level pacing gate, not a decorative column.** Because a level's own `triggered` event can only ever fire once per (ticket, policy_version, trigger, level, reopen cycle) by construction (decision 6), a naive "block a repeat of the SAME level" reading of cooldown would be permanently unreachable (taxonomy C-20). `cooldown_minutes` instead gates how soon the NEXT (higher) level may fire after the CURRENT level's own last trigger — live-proven in db-test §7 (a two-level policy: level 1 fires, a fresh evaluation pass within the 60-minute cooldown window does NOT advance to level 2; backdating `last_triggered_at` past the window lets level 2 fire on the next pass).
9. **First real domain consumer of PLT-127's notification engine** (its own migration header disclosed zero domain consumers existed yet). Bootstrapped via direct INSERT into `app.notification_types`/`app.config_types`/`app.config_objects`/`app.config_versions`/`app.config_items` — migration-apply context has no live actor session, so `app.register_notification_type`/`app.create_config_draft`/`app.publish_config_version` (all Supreme-Admin- or scope-authority-gated) cannot be called here, mirroring HRT-286's own established `ticket_attachment` document-type bootstrap exactly. `channels=['in_app']` ONLY (no live email provider exists anywhere in this repository, PLT-127's own disclosed boundary). Notification context carries ONLY `ticket_number`/`escalation_level`/`trigger_type` — deliberately never the ticket's own subject/reason free text, satisfying both this prompt's own "minimized fields" security requirement and guaranteeing `app.render_notification_template`'s own angle-bracket/link-scheme safety checks can never be tripped by user-authored content.
10. **Batch-triggered escalation events attribute `actor_auth_user_id`/`actor_label` to the REAL identity that invoked the evaluation batch — never a fabricated "system" auth identity.** `app.queue_notification`'s own authority gate (`app.check_notification_trigger_authority`) requires a genuine, currently-tenant-active (or Supreme Admin) actor; no anonymous system-actor concept exists anywhere in this schema. `app.run_ticket_escalation_evaluation_batch`'s own TKT:Edit-holding caller is threaded through `app._evaluate_ticket_escalation` into every ledger row and notification call it produces.
11. **Suppression is authority-gated (TKT:Assign, materially higher than plain `is_ticket_staff`), requires a real reason and a real future expiry, and never hides the underlying ledger** (business rule, literally) — live-proven in db-test §4: an active suppression blocks a NEW manual escalation but the `suppressed`/`suppression_ended` ledger rows are always written regardless. A stale, unrevoked, already-expired suppression is auto-revoked (`revoked_reason='expired'`) the next time it is checked — live-proven with a genuinely backdated `expires_at`.
12. **Customer-visible status is a single boolean, structurally separate from every internal field** (security impact section 16). `app.get_ticket_escalation_status_for_requester` returns `is_escalated` ONLY — no level, target, trigger, or acknowledgement detail — a DIFFERENT RPC from the staff-facing `app.get_ticket_escalation` (mirrors `app.get_ticket_sla_status_for_requester`, HRT-289, exactly). Live-proven in db-test §11: a customer requester reads `is_escalated` before/after a real staff escalation and is refused (zero rows / `ticket_not_found`) on every staff-only projection.
13. **A dedicated breach/stuck queue view (`app.list_ticket_breach_queue`) was built rather than widening `app.list_tickets`/`app.list_my_tickets`.** Those two RPCs are already-VERIFIED, applied migrations this task may never edit in place; widening either `RETURNS TABLE` shape would be a genuine drop+create (HRT-290's own `assign_ticket` precedent for a signature change) rippling through `TicketListRow`/`MyTicketListRow`, every existing caller, and every existing test, for a shape change no other capability needs. A minimal, dedicated, staff-scoped (`is_ticket_staff` per row, mirroring `app.list_tickets`' own `can_access_ticket`-per-row shape) cursor-paginated view was built instead, plus its own dedicated page (`tickets/breach-queue/page.tsx`) rather than a third tab bolted onto `tickets/page.tsx`'s existing "My Tickets"/"Queue" toggle.
14. **Locking discipline (C-04):** every RPC that mutates escalation state for a given ticket takes `select ... from app.tickets ... for update` FIRST, consistently, before locking any child row (`app.ticket_escalations`/`app.ticket_escalation_suppressions`) — including `app.revoke_ticket_escalation_suppression`, which takes `p_ticket_id` as an explicit parameter (rather than deriving it from the suppression row) specifically so it preserves this same ticket-first lock order and never risks a reversed-order deadlock against `app.suppress_ticket_escalation` (C-21 discipline, applied from the start, not rediscovered).
15. **C-24 discipline.** Every free-text column (escalation reason, suppression reason) lives ONLY on `app.ticket_escalation_events`/`app.ticket_escalation_suppressions`, both governed by the exact same RLS as the ticket itself (`app.can_access_ticket`) — mirroring `app.ticket_events`/`app.ticket_assignment_events` exactly, never `app.audit_logs`. `app.ticket_escalation_audit_projection` is an explicit structural-fields-only allowlist; every `capture_audit_event` call site in this migration passes it or an explicit `jsonb_build_object` allowlist, never `to_jsonb(row)` and never a raw `p_reason`.

## 6. Self-found defects fixed before finishing

1. **(C-01/C-02, self-found by my own db-test §5, not by a separate review pass)** — an early draft of `app._apply_ticket_escalation` wrapped only the FIRST insert (into `app.ticket_escalations`) in a real `exception when unique_violation` handler; the SECOND insert (the `triggered` row into `app.ticket_escalation_events`, the table that actually carries the natural-key unique index) had NO exception handler at all. A direct, deliberate double-call with the identical natural key raised a raw, uncaught `unique_violation` instead of being treated as a clean, idempotent no-op — exactly the C-01/C-02 gap this task's own mandatory reading named. Fixed by wrapping the `triggered` insert in its own `exception when unique_violation then v_already_triggered := true;` block, and skipping the notify/reassign sub-actions entirely on a detected duplicate (they already ran on the original trigger; re-running them on a retry would itself be the "retry creates a duplicate action" the business rule forbids). Re-verified live: the identical direct double-call now produces exactly one `triggered` row and returns cleanly.
2. **(A genuine regression against an already-published job type, self-found by my own full `pnpm run db:test` pass, not a targeted review)** — `app.generic_job_types()`/`jobs_job_type_check` are FULL replacements, not additive. An early draft of this migration's section 0 copied HRT-289's own SLA migration (`20260731120000`) list verbatim and, in doing so, silently DROPPED `kb_article_expiry` (added one migration later, by `20260731130000`, after `120000` was already written) from both the CHECK constraint and the function — which broke `scripts/db-tests/ticketing-knowledge-base.sql`'s own step 3 (`job_invalid_type: kb_article_expiry is not a known generic job type`) the moment this migration applied, live-caught by a full `pnpm run db:test` pass. Fixed by carrying forward the FULL current list (`120000` + `130000`'s own additions) plus this migration's own new type, never re-deriving from a single prior migration in isolation. Re-verified: a fresh, full `pnpm run db:test` run now shows `==> db-tests: ALL PASSED` with every one of the 166+ test files, including `ticketing-knowledge-base.sql`, passing.
3. **(A table-shape bug, self-found live when the migration was first applied to a disposable database)** — `app.ticket_escalation_levels` was given a `touch_ticket_row()` trigger (the shared `updated_at`/`record_version`-bump trigger every other versioned table in this migration correctly uses) despite deliberately carrying NO `record_version` column of its own (decision: a level is only ever mutated while its parent policy_version is draft, gated by the PARENT's own version check — no independent optimistic-concurrency contract on the child). The trigger function unconditionally references `record_version`, so the very first `add_ticket_escalation_level` upsert-in-place call failed with `record "new" has no field "record_version"`. Fixed by removing the trigger and setting `updated_at = now()` explicitly in the UPDATE branch instead.
4. **(A CHECK-constraint design bug, self-found live in the same first-apply pass)** — `app.ticket_escalation_suppressions` originally carried `constraint ... check (expires_at > created_at)`. Since both values are captured in the same INSERT statement (`created_at default now()`, `expires_at` validated `> now()` by the RPC itself), this constraint could never be meaningfully violated at INSERT time — but it DID block the legitimate later state "time has since passed and this row is now expired," which both `app.suppress_ticket_escalation` (auto-revoking a stale row) and `app._evaluate_ticket_escalation` (the batch's own suppression-expiry check) need to simulate/detect via a genuine backdate. Fixed by dropping the CHECK constraint entirely (the real invariant is enforced by the RPC at insert time, not by a table-level comparison of two same-instant values) and documenting the reasoning on the column itself.
