## 3. Source/config decisions (disclosed, not left implicit)

All twelve numbered decisions are recorded directly in the main migration's own header comment (`supabase/migrations/20260730910000_create_hris_shift_roster_scheduling.sql:1-131`) and the binding migration's own header (`20260730920000:1-30`) — summarized here:

1. **Shift definitions are versioned exactly like `app.attendance_policies`/`app.attendance_policy_versions` (HRT-278 decision 3).** `app.shift_templates` is the scope pointer; `app.shift_template_versions` is the effective-dated ruleset; a real child table, `app.shift_segments`, carries the work/break segment list — never a flat jsonb blob.
2. **Segment ordering/cross-midnight rule.** At most the LAST segment in sequence order may cross midnight; every earlier segment must have `end_time > start_time` and the next segment's `start_time >= ` the previous segment's `end_time` (no overlap, strictly chronological). Models fixed/split/cross-midnight shifts correctly with one provable rule — disclosed V1 simplification (no requirement anywhere names more than one midnight crossing per shift).
3. **Rotating roster is a real, separate two-table construct** (`app.roster_cycles`/`app.roster_cycle_slots`), not folded into shift versions. A cycle must publish (every `day_offset` 0..`cycle_length_days`-1 filled, including explicit "day off" nulls) before `app.generate_roster_schedule_assignments` may consume it.
4. **`app.schedule_assignments` is BOTH the live assignment record AND the published snapshot** section 13 names — no second, duplicating snapshot table. `status='scheduled'` is an editable HR draft; `status='published'` is the immutable-by-normal-role governed truth `app.resolve_effective_schedule_assignment` (and, via the binding migration, `app.attendance_sessions`) binds to. Every real transition is a NEW row (`previous_assignment_id` links lineage) — never a destructive UPDATE of a published row's own shift/date. V1-bounded to one active-or-published assignment per (employee, work_date), mirroring `app.attendance_sessions`' own identical bound.
5. **Authority bar matches blast radius, not surface category** (HRT-277's own worst finding, designed against from the start). Superseding/cancelling a still-DRAFT (`scheduled`) row is HRS:Edit; superseding/cancelling an already-PUBLISHED row requires HRS:Override — a genuinely disjoint EITHER/OR pair (an Override holder is not required to also hold Edit), matching this repository's own established "approver holds Approve/View/Override, not Edit" role shape. Publishing a batch of draft assignments is HRS:Approve.
6. **Cancel genuinely cancels, never leaves a dependent process live.** Cancelling a schedule assignment that a still-pending swap request depends on cancels that swap request too, via a direct, unlocked, conditional UPDATE.
7. **Lock order (C-21), stated explicitly and live-tested.** The two functions that ever touch both a `schedule_assignments` row and a `schedule_swap_requests` row always lock the ASSIGNMENT row(s) first, the SWAP REQUEST row second. `app.decide_schedule_swap_request` does a plain unlocked read of the swap request first only to discover which two assignment ids to lock (mirrors HRT-276's own "plain-read-before-lock" precedent), locks both assignment rows in global ascending-uuid order, THEN locks the swap request row. `app.cancel_schedule_assignment` locks its own target assignment first, reaches the dependent swap request via an unlocked conditional UPDATE. **Live-reproduced with two real, independent `psql` OS processes, three separate iterations, zero deadlocks** (§8).
8. **Batch schedule generation reuses PLT-132's real background-job framework, the first HRIS-domain adopter of its own generic job_type list.** `app.jobs.job_type` and `app.generic_job_types()` (the real ATW-031/ISS-2026-012 single source of truth) are both widened to add `roster_generation` — `app.enqueue_job`/`app.dispatch_event_as_job` themselves are untouched, since ATW-031 already collapsed their own literals into a call to `app.generic_job_types()` (a first draft of this migration mistakenly widened `app.enqueue_job` directly from the ORIGINAL, now-superseded PLT-132 literal, silently reverting two later-added job types — self-found and fixed, §7 item 1). `app.generate_roster_schedule_assignments` self-claims the SPECIFIC job row it just created (by `job_id`, under its own row lock) rather than the generic queue-wide `app.claim_next_job`, then calls the SAME `app.complete_job()` any future live poller would call.
9. **Attendance integration is additive, structurally optional, and in its own migration.** `app.attendance_sessions.schedule_assignment_id` stays null when no published roster assignment exists — never blocking, never a fabricated link. Deeper binding of exception-detection formulas to a specific shift's own segment times is deliberately NOT built here (reserve-the-field discipline, mirrors HRT-274/278's own identical choice).
10. **RBAC.** Zero new `app.permissions` rows.
11. **Sensitive free-text fields are column-restricted from THIS, the FIRST, migration** — `cancel_reason`/`reason`/`decided_reason`, never projected by any read RPC (structural masking by omission, mirroring `app.attendance_correction_requests`' own established convention).
12. **Coverage preview doubles as the "Operations... workforce availability projection" surface** (section 26) — aggregate headcount counts only, never employee-level identity. No new cross-domain Operations permission invented (mirrors HRT-278's own Payroll forward-contract framing).

## 4. Security/access model

- **RLS:** every one of the 9 new tables carries the hardened default-deny SELECT policy, proven live against `anon` (schema-privilege denial) and a forged cross-tenant staff session (zero-row RLS-level denial) in `scripts/db-tests/hris-shift-roster-scheduling.sql`.
- **RBAC:** every write RPC gates through `app.evaluate_permission(actor, tenant, 'HRS', action)`. Blast-radius-matched bars, including two genuine EITHER/OR pairs (Edit-or-Override) for `assign_employee_schedule`/`cancel_schedule_assignment`, corrected to their real disjoint semantics after a self-found near-miss during the checkpoint's own C-05 hardening pass (§7 item 7).
- **The "fold non-member into not-found" primitive is applied uniformly** across every primary-row lookup, live-verified with a forged `shr2` session probing a `shr1` shift template id (`shift_template_not_found`, never a permission-denied that would confirm the row's existence).
- **Column-restricted grants** — `authenticated` has no column-level SELECT on `cancel_reason`/`reason`/`decided_reason`; `service_role` has full access. Verified live via `has_column_privilege` in the db-test suite, both directions.
- **Three genuine C-05 findings, self-found during this checkpoint's own Tier B taxonomy walk (not by a db-test failure) and fixed before commit** — see §7 items 5-7 for full detail: `request_schedule_swap` disclosed row status before authority; `assign_employee_schedule` disclosed an arbitrary employee's lifecycle_status (active/terminated/suspended/on_leave) to any zero-permission tenant member before any authority check; `cancel_schedule_assignment` let a zero-permission caller infer row status from which specific permission name appeared in its own rejection message. All three fixed with a coarse "holds at least one relevant permission" floor evaluated before any row-state disclosure.
- **Concurrency:** every write RPC with a version parameter repeats `record_version = p_expected_version` in the terminal `UPDATE`'s own `WHERE` clause; every decision-bearing function locks its target row(s) `FOR UPDATE` before deciding. The schedule-assignment first-creation race (no pre-existing row to lock) is closed by the `schedule_assignments_employee_workdate_active_unique` partial index as the real structural safety net — **live-reproduced with two genuinely concurrent OS processes: exactly one succeeded, the loser received a real, uncaught Postgres `unique_violation`, zero duplicates** (§8).

## 7. Self-found defects (found and fixed during this checkpoint's own adversarial testing, before commit)

Found via iterative, honest `psql`-driven testing against a live disposable Postgres 16 database, including real concurrent OS processes, not shipped and found later:

1. **`app.enqueue_job`/job_type widening from a STALE, superseded base.** A first draft widened `app.jobs.job_type`'s CHECK constraint and re-declared `app.enqueue_job` directly from the ORIGINAL PLT-132 migration's own now-superseded literal list, silently reverting the `route_load_planning`/`print_label` job types two LATER migrations had already added — **live-caught twice, independently**: once by `pnpm run db:test`'s own unrelated `advanced-tms-label-barcode-operations.sql` file failing on its own `print_label` usage, and again by `background-job.sql`'s own standing ATW-031 drift-gate assertion. **Fixed** by discovering the real current single source of truth (`app.generic_job_types()`, established by `20260730410000_harden_job_type_single_source_of_truth.sql`) and widening ONLY that function plus the table's own literal CHECK — leaving `app.enqueue_job`/`app.dispatch_event_as_job` completely untouched, since ATW-031 already collapsed their own independent literals into a single call to it.
2. **`app.assign_employee_schedule`: insert-before-supersede ordering violated its own new partial unique index.** The prior row was marked `superseded` via an UPDATE issued AFTER the new row's own INSERT, so for a moment both rows held a status covered by the SAME partial unique index for the SAME `(tenant_id, employee_id, work_date)` — a genuine constraint violation on the very first supersede attempt, live-caught by the db-test suite itself. **Fixed** by reordering: mark the prior row superseded BEFORE inserting the new one.
3. **`app.assign_employee_schedule`: a real authority-bypass-shaped bug from reusing the bare `FOUND` special variable across two sequential, unrelated `SELECT`s.** The decision-5 authority branch (`if found then ... check HRS:Override for a published row ... else ... check HRS:Edit`) read `FOUND` after the C-01 idempotency-replay block had ALREADY run its own `SELECT ... INTO v_replay`, silently overwriting `FOUND` with THAT query's own result. In practice, any caller supplying a non-null `p_idempotency_key` would almost always see `FOUND = false` (a fresh key normally finds nothing), so the function would incorrectly take the "no existing row, HRS:Edit suffices" branch even when superseding an already-PUBLISHED row — an HRS:Edit-only actor supplying any idempotency key could have bypassed the HRS:Override requirement entirely. **Live-caught by the db-test suite's own supersede-blast-radius assertion failing** (the wrong branch was silently taken). **Fixed** by capturing the original select's own `FOUND` into a dedicated `v_existing_found boolean` variable immediately, never relying on the bare special variable again after any intervening `SELECT`.
