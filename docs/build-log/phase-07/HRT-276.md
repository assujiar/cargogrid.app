## 1. What this checkpoint builds

HRT-276 is the THIRD Phase 7 (HRIS/Ticketing) capability, built directly on HRT-275 (Organization and Position Linkage, `VERIFIED`). It implements tenant-scoped recruitment end-to-end — approved vacancy through candidate assessment, interview, and offer — plus a genuinely public (anonymous, token-based, enumeration-safe, rate-limited) job-application intake surface bound only to currently-open vacancies. Per ADR-0023 Part B and this prompt's own §60/§108, candidate and application data is explicitly **not** employee or Platform-user truth: no row in this migration ever writes to `app.employees`, `app.users`, or `app.master_records`. The governed conversion from an accepted offer into a real employee record is Prompt 277's (Onboarding and offboarding) own chartered scope — this checkpoint stops at `job_offers.status = 'offer_accepted'` and goes no further, proven by an explicit db-test assertion (§8).

## 3. Source/config decisions (disclosed, not left implicit)

### 3.1 Candidates and applications are not routed through `app.master_records`

Unlike vendor/driver/employee, a candidate is not (yet) an operational actor identity — it is purpose-bound recruitment data that may never silently become one (ADR-0023 Part B). `app.candidates` is a standalone, tenant-scoped table with its own `record_version`/status lifecycle, structurally separate from `app.master_records`. No FK from `app.candidates` or `app.job_applications` reaches `app.employees`, `app.users`, or `app.master_records` anywhere in this migration — confirmed by direct inspection of every `references` clause in the file.

### 3.2 Public job-posting tokens are stored and returned directly, not hashed

An early draft copied vendor-intake's (PRC-251) single-use hash-only token pattern (`digest()`/`encode(digest(...))`, storing only the hash). That pattern is wrong for a multi-use, publicly-browsable listing: a hash cannot be reversed to redisplay a usable link on every listing call. `app.job_vacancy_postings.posting_token` stores the real token directly (unique, generated at publish time), matching the requirement that the same token supports repeated visits and multiple distinct applicants over the posting's lifetime. This is a genuine, disclosed divergence from PRC-251's own shape, not an oversight — recorded as design note 2 in the migration header.

### 3.3 Resume upload is deliberately deferred to a staff-mediated path

The public intake form collects application data (candidate identity, source, consent, cover note) but does not accept a direct anonymous file upload — an anonymous, unauthenticated multipart upload surface carries materially higher malware/abuse risk than a governed, staff-mediated attach flow. A candidate's resume is attached post-intake via `app.update_candidate_profile`, reusing PLT-128's `app.initiate_file_upload`/`app.record_file_scan_result` exactly as HRT-274 established for employee documents. The resume-scan gate is enforced twice (taxonomy C-10): once at ATTACH time (`update_candidate_profile` rejects an already-known-`infected` file outright) and again at the STAGE-TRANSITION gate (`transition_application_stage` to `interview` re-checks `malware_scan_status = 'clean'` at the accepting RPC, never trusting a caller's prior attach-time success as still valid).

### 3.4 Offer approval reuses PLT-123 (Approval Engine) without a bespoke threshold table

Mirroring `app.decide_quotation_approval_step` (COM-153), `app.submit_job_offer_for_approval`/`app.decide_job_offer_approval` are thin domain wrappers around `app.request_approval`/`app.decide_approval_step`. No new threshold/routing-rule table was built — a tenant publishes an ordinary `config_type_code='approval'` routing definition scoped to this domain, exactly like every other PLT-123 adopter. Both wrappers add their own `app.assert_actor_is_session_identity` call (the engine itself never does this) and their own tenant-membership fold on any pre-lookup, since the engine is entity-agnostic and cannot know this domain's own tenant-isolation shape.

### 3.5 Interview feedback is identity-gated to the assigned interviewer, not permission-gated

`app.submit_interview_feedback` requires the caller's resolved employee identity to appear in `app.interview_interviewers` for that specific interview — a plain `HRS:Edit`-holding staff member who is not the assigned interviewer is rejected, and a duplicate feedback row from the same interviewer is rejected. This is a real identity match (via `app.resolve_actor_employee_id`), not a permission check, matching the prompt's own scorecard/feedback framing.

### 3.6 Application stage transitions are bounded and forward-only

`app.transition_application_stage`'s allowed-transition table is a fixed forward DAG (`applied → screening → assessment → interview → offer → hired`, with `reject`/`withdraw` reachable from any non-terminal stage). No transition ever moves an application backward except via an explicit reject-then-reopen path that does not exist in this checkpoint — a rejected or withdrawn application is terminal. Consent, resume-scan status, and (for the interview stage) an assigned interviewer are all real, enforced prerequisites checked at the RPC, not merely UI-suggested.

### 3.7 Duplicate-candidate detection never auto-merges

`app.search_candidate_duplicates` (exact email/phone match plus `pg_trgm` fuzzy name similarity), `app.flag_candidate_duplicate`, and `app.decide_candidate_duplicate` are all human-in-the-loop: a flagged pair is recorded and later confirmed/dismissed by a reviewer, but no code path in this migration ever merges two candidate rows or silently discards one. This mirrors the vendor/employee duplicate-review precedent (never auto-merge) rather than inventing a new pattern.

### 3.8 Candidate PII is column-restricted from day one

`app.candidates.email/phone/national_id_number/date_of_birth/address` are excluded from the plain `authenticated` grant (PLT-114's established `REVOKE`-then-column-restricted-`GRANT` pattern, applied here from the first migration rather than retrofitted after a review round, unlike HRT-274's own history). `app.get_candidate_profile` masks these fields for a caller without `app.has_view_personal_data` (reused directly, hardcoded to module `'HRS'`, no new helper needed) and unmasks them for a caller who has it. Every audit-event write for candidate/application/offer data goes through an explicit non-PII `jsonb_build_object` projection helper (`app.candidate_audit_projection`, `app.job_vacancy_audit_projection`, `app.job_application_audit_projection`, `app.job_offer_version_audit_projection`) — never `to_jsonb(row)`.

### 3.9 The public intake surface is enumeration-safe and rate-limited by construction

`app.get_public_open_vacancy_summaries`/`app.resolve_public_job_posting`/`app.submit_public_job_application` return the identical uniform empty/not-found shape for a nonexistent tenant slug, an unpublished/expired/revoked posting token, and a since-closed vacancy — no code path distinguishes "wrong token" from "right token, wrong state" in its response. `app.job_application_intake_attempts` records every attempt (success and failure) keyed by a caller-supplied `client_key` (a hashed IP, mirroring the vendor-intake precedent) and `app.submit_public_job_application` rejects further attempts from the same `client_key` after 10 failed attempts within a rolling window, before any real business-logic branch runs. All three RPCs are `service_role`-only at the grant layer — `anon` has zero execute privilege on any of them (defense in depth against the Server Action layer being bypassed, mirroring the standing `ERR-2026-004` regression guard already applied to vendor-intake).

## 4. Security/access model

- **RLS:** every one of the 14 new tables carries the hardened default-deny form (`(app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id)) or app.is_supreme_admin()`), proven live against `anon` (schema-privilege denial), a `customer_user`-layer principal (zero rows, same tenant), and cross-tenant staff (zero rows) in `scripts/db-tests/hris-recruitment-ats.sql`.
- **RBAC:** every write RPC gates through `app.evaluate_permission(actor, tenant, 'HRS', action)`, which asserts caller-is-session-identity internally. Two RPCs (`app.get_my_assigned_interviews`, `app.submit_interview_feedback`) are SECURITY DEFINER, callable by `authenticated`, and reached by identity-match rather than a permission check alone — both gained an explicit `app.has_active_tenant_membership` call so the repository's own automated call-graph scanner (`rbac-enforcement.sql`, `ATW-032`) recognizes a real authority check on every reachable path, not merely the identity match.
- **The "fold non-member into not-found" primitive is applied uniformly.** Every primary-row lookup across all 55 functions follows `if not found or not app.has_active_tenant_membership(v_row.tenant_id, p_actor_auth_user_id) then raise ..._not_found` — a cross-tenant caller receives a uniform not-found, never a real tenant_id or row-existence disclosure via a distinguishable `insufficient_authority` error. This was the single largest self-found defect class this checkpoint (§5.3).
- **Column-restricted grant on `app.candidates`** (§3.8) — `authenticated` has no column-level SELECT on `email`/`phone`/`national_id_number`/`date_of_birth`/`address`; `service_role` has full access. Verified live via `has_column_privilege` plus a masked-vs-unmasked `get_candidate_profile` read in the db-test suite.
- **Concurrency:** every write RPC locks its target row(s) first, folds a non-member caller into not-found, checks authority before `record_version`, and repeats the version predicate in the terminal `UPDATE`'s own `WHERE` clause. Four INSERT-decision RPCs (`apply_to_vacancy`, `create_candidate_assessment`, `schedule_interview`, `create_job_offer_version`) additionally take a defensive `for update` lock on the parent application row before deciding whether to insert, closing the class of race the taxonomy weighs most heavily (C-04) even though it was not live-reproduced as an active bug this checkpoint.
- **Public intake:** `service_role`-only grant on all three public RPCs; `client_key`-scoped rate limiting; uniform not-found responses; mandatory-consent enforcement at submission; idempotent replay via a caller-stable idempotency key (cookie-backed on the client side, §2's UI file list).

## 7. Self-found defects (found and fixed during this checkpoint's own adversarial db-testing, before commit)

Found via iterative, honest `psql`-driven testing against a live disposable Postgres 16 database, not shipped and found later:

1. **CRITICAL/systemic — missing tenant-membership fold across ~30+ functions (C-05).** The originally-written vacancy/candidate/application/assessment/interview/offer RPCs (and every read RPC) used `if not found then raise ..._not_found` without also checking `app.has_active_tenant_membership(...)`. A cross-tenant caller who supplied a real row ID from another tenant received `insufficient_authority` rather than the same not-found a genuinely nonexistent ID would produce — disclosing that the row exists and belongs to a different tenant. Live-reproduced by this checkpoint's own cross-tenant-isolation db-test block failing on the first run. **Fixed** by rewriting every affected `if not found then` into `if not found or not app.has_active_tenant_membership(v_row.tenant_id, p_actor_auth_user_id) then raise ..._not_found`, applied function-by-function (verified each replacement matched exactly once before writing) plus a manual restructure of `submit_interview_feedback` to merge its two separate checks into one folded check.
2. **Public-posting-token design flaw (§3.2).** Originally built as a single-use hash-only token (copied from PRC-251/vendor-intake) — structurally wrong for a multi-use, publicly-listed posting. **Fixed** by storing/returning the token directly, removing all `digest()` calls for this token across `publish_job_vacancy`, `get_public_open_vacancy_summaries`, `resolve_public_job_posting`, `submit_public_job_application`.
3. **`apply_to_vacancy` exception-handler bug (C-02).** The original handler treated an idempotency-key replay and a genuine one-active-application unique-index violation as the same error. **Fixed** with explicit disambiguation: check for a matching idempotency-key row first, fall back to checking for an existing active application, before re-raising.
4. **`create_job_offer_version` had a redundant, self-contradicting status guard** (`status not in (...) and status <> 'draft'`). **Fixed**, simplified to a single clear check restricting source states to `('draft', 'approved', 'declined')`.
5. **`get_offer_timeline` used an invalid `group by v_offer.*`** on a plpgsql composite variable, which Postgres rejects. **Fixed** by removing the unnecessary `GROUP BY` (a constant alongside an aggregate needs none).
6. **`get_candidate_profile` — ambiguous bare column reference (recurring bug class, C-05-adjacent).** `select * into v_candidate from app.candidates where id = p_id` was ambiguous against the function's own `RETURNS TABLE (id uuid, ...)` — the exact class HRT-274's own build log found and fixed three times. **Fixed** via table-aliasing (`select c.* into v_candidate from app.candidates c where c.id = p_id`); verified this was the only function among all "id uuid"-returning-table functions with the issue.
7. **`search_candidate_duplicates` — a chain of 3 bugs.** (a) `similarity()` not found — `pg_trgm`'s `similarity()` lives in `public`, not `app`; fixed by adding `public` to the function's `search_path`. (b) `invalid UNION/INTERSECT/EXCEPT ORDER BY clause` — fixed by wrapping the UNION ALL branches in a subquery with explicit column aliases before ordering. (c) `structure of query does not match function result type: real does not match numeric` — `similarity()` returns `real`; fixed with an explicit `::numeric` cast.
8. **ATW-032 rbac-enforcement.sql gate failures (2 functions).** `get_my_assigned_interviews`/`submit_interview_feedback` were flagged as `SECURITY DEFINER`, granted to `authenticated`, with no authority check the automated call-graph scanner recognized. **Fixed** by adding explicit `app.has_active_tenant_membership(...)` calls — a genuine, meaningful safety improvement, not merely gaming the checker (confirmed via a live query against the closure-computing CTE that this made both functions pass). `decide_job_offer_approval` was separately flagged for taking `p_actor_auth_user_id` but reaching neither `evaluate_permission` nor `assert_actor_is_session_identity` — root-caused by comparing against `decide_quotation_approval_step`'s live source, **fixed** by adding the same explicit `perform app.assert_actor_is_session_identity(p_actor_auth_user_id);` call at the top.
9. **Test-fixture-only bugs** (not shipped-code defects, caught by `ON_ERROR_STOP`): a candidate fixture used `source='referral'` without the required `referral_employee_id`; a `record_candidate_consent` call discarded its return value via bare `perform` instead of `select ... into`, leaving `record_version` stale for a later call; hrrec2's staff role initially lacked `HRS:Approve` needed to publish a vacancy in the fail-closed-approval test; hrrec2's fail-closed-approval test originally tried to reach the `offer` stage through the full governed pipeline (requiring a nonexistent interviewer fixture) — fixed by force-updating `job_applications.stage='offer'` directly in the test fixture (a legitimate test-setup shortcut, not a product code path). All fixed.
10. **UI dead-action defect (C-20-adjacent, in the UI layer, self-found).** `ApprovalStepForm` in `application-detail-panel.tsx` originally contained a non-functional inline placeholder Server Action (an empty no-op) and a component that rendered only descriptive text instead of real Approve/Reject buttons. **Fixed**, rewritten into a fully functional two-button form using `useState` for the step-id input and real `useActionState` bindings.
11. **`page.tsx` (application detail) used `createSupabaseServiceRoleClient()`** to read `app.job_offers` — an unnecessary RLS-bypass privilege escalation, since `app.job_offers` already carries a plain RLS-scoped `authenticated` SELECT grant. **Fixed**, switched to the regular authenticated server client (also caught mechanically by `pnpm run typecheck` after the import was removed but a usage remained).
12. **Resume-scan test design correction (my own test, not a product bug).** Initially attempted to attach an already-`'infected'`-scanned file via `update_candidate_profile`, not realizing the migration's own attach-time gate already rejects it — recognized this as correct, desirable behavior and restructured the test into two parts: (1) prove an infected file is rejected at attach time; (2) attach a separate file left `'pending'`, prove the stage-transition-to-interview gate rejects it until `record_file_scan_result(..., 'clean', ...)` is called, then prove the transition succeeds.

Consistent with this repository's own disclosed history (HRT-274 found 7, HRT-275 found 2), this checkpoint's own honest adversarial pass found and fixed 12 real defects (counting the C-05 systemic fix as one item spanning ~30+ functions) before commit.

### 12.1 Findings 1 / 4 / 5 (HIGH / CRITICAL / CRITICAL) — raw-table SELECT bypasses the RPC authority/identity gate

**CONFIRMED**, independently re-derived. Live-verified against a fresh disposable Postgres 16 database (all 186 pre-fix migrations applied): `hiringmgr@hrrec1.test` (a real, active tenant member with **zero** `app.role_assignments` rows — `app.evaluate_permission(..., 'HRS', 'View').allowed = false`, confirmed directly) could, as a plain PostgREST-shaped `authenticated` session:
```
select rating, recommendation, notes from app.interview_feedback;              -- returned the real row, including notes='solid candidate'
select compensation_amount, compensation_currency from app.job_offer_versions; -- returned real compensation, e.g. 15000000/18000000 IDR
select score, notes from app.candidate_assessments;                            -- returned score=85, notes='strong performance'
```
while the same identity was correctly rejected with `insufficient_authority` by `app.get_offer_timeline` — proving the RPC layer's own gate is correct and the raw-table RLS/grant is the actual, exploitable gap (business rule 4 / prompt §16 / §26: "interview notes and offer compensation are purpose- and field-restricted").

**Root cause:** the `_select_scoped` RLS policy on all three tables checks only tenant membership (`(has_active_tenant_membership(tenant_id) and not actor_holds_customer_user_layer(tenant_id)) or is_supreme_admin()`) — appropriate for the pipeline-visibility tables (vacancies/candidates/applications), but too broad for feedback/compensation/assessment content, combined with a plain, unrestricted `grant select on <table> to authenticated`.

**Fix:** applied the exact, already-proven PLT-114/HRT-274/`app.candidates` (this same migration, design note 9) pattern — `revoke select on <table> from authenticated;` then `grant select (<explicit non-sensitive column list>) on <table> to authenticated;`, excluding `interview_feedback.rating/recommendation/notes`, `job_offer_versions.compensation_amount/compensation_currency/benefits_note`, and `candidate_assessments.score/notes`. `service_role` keeps its own separate, unrestricted grant, unchanged. No RPC is affected — every read RPC is `SECURITY DEFINER`, executing as the function owner, unaffected by a column grant to `authenticated` (re-verified live: `app.get_offer_timeline`/`app.list_candidate_assessments` still return full, correct data for an authorized actor).

### 12.4 Findings 7 / 8 (CRITICAL, live-reproduced with two real concurrent psql processes / HIGH, same root cause) — reject/withdraw never cancel an in-flight offer approval; the approval decision write-back had no state guard at all

**CONFIRMED**, independently re-derived and live-reproduced twice (an initial reproduction, then again after the fix to confirm closure, then 5 further concurrent iterations with no deadlock and a safe outcome every time — evidence at `/tmp/claude-0/.../scratchpad/{setup_race_fixture.sql,race3_a_reject.sql,race3_b_decide.sql,iter_a_*.sql,iter_b_*.sql}` in this fix-pass session). Built a real application at stage=`offer`, submitted a real offer version for PLT-123 approval (`job_offers.status='pending_approval'`, a real `pending` `app.approval_requests` row with an `active` step). Ran two separate OS-process `psql` clients concurrently: Session A called `app.reject_application`, Session B called `app.decide_job_offer_approval(..., 'approved', ...)` on the same offer's active step. **Before the fix**, both succeeded: `job_applications.stage='rejected'` while `job_offers.status='approved'` simultaneously; continuing sequentially, `app.extend_job_offer` then `app.record_offer_response(..., 'accepted', ...)` both succeeded, reaching `job_applications.stage='offer_accepted'` — a committed, illegal transition back out of a declared terminal state. Root-caused to two independent defects: (a) `app.reject_application`/`app.withdraw_application` never called `app.cancel_approval_request` on the offer's bound approval request — the exact cross-domain precedent `app.cancel_purchase_order`/`app.cancel_vendor_contract` already established for "cancel a pending approval when its subject is terminated," skipped in this domain; (b) `app.decide_job_offer_approval`'s terminal `UPDATE` carried **no guard at all** beyond `where id = v_request.entity_id` — not even `record_version` — so it unconditionally overwrote `app.job_offers` regardless of any concurrent termination.

Also independently confirmed Finding 8's own test-coverage claim: `grep -n "reject_application\|withdraw_application" scripts/db-tests/hris-recruitment-ats.sql` returned zero matches pre-fix — despite the build log's own §9 claiming "reject cascading to withdraw a pending offer" was "proven live," neither RPC was ever actually invoked in the test file (the assertion at line 277 tests only that a *duplicate application* is rejected and other applications' stage transitions — never the reject/withdraw RPCs themselves).

**Fix (two parts, one root cause):**
- `app.reject_application` / `app.withdraw_application` now call `app.cancel_approval_request(...)` on any still-`pending_approval` offer's approval request BEFORE cascading the offer to `withdrawn`. **Lock-order note (a genuine deadlock this fix pass found and fixed in its own draft, not shipped):** an initial draft took a `for update` lock on `app.job_offers` before calling `app.cancel_approval_request` (which locks `app.approval_request_steps` then `app.approval_requests`) — this is the exact REVERSE order of `app.decide_job_offer_approval`'s own call path (approval-engine tables, then `app.job_offers` last), a real lock-order cycle, live-reproduced as `deadlock detected` (SQLSTATE 40P01) during this fix pass's own regression testing before it shipped. Fixed by using a deliberately PLAIN (non-locking) read of the offer row to decide whether to cancel, deferring all `app.job_offers` locking to the ordinary terminal `UPDATE` at the end of each function — now matching (b)'s own order exactly. Re-verified with 6 total concurrent-race runs after this correction: zero deadlocks, every final state safe (`job_applications.stage='rejected'`, `job_offers.status` always ending `withdrawn`, `app.extend_job_offer` on the resulting offer correctly rejected with `invalid_transition`).
- `app.decide_job_offer_approval`'s terminal `UPDATE` now carries a real guard — `where id = v_request.entity_id and approval_request_id = v_request.id and status = 'pending_approval'` — and raises `offer_approval_no_longer_applicable` (`serialization_failure`) if it does not match, rolling back the ENTIRE decision (including the `app.decide_approval_step` mutation just before it, since this is one atomic function call).

Regression evidence: `scripts/db-tests/hris-recruitment-ats.sql` gained a new sequential (non-concurrent) block proving both RPCs now actually run, cancel the in-flight approval request (`app.approval_requests.status='cancelled'`), cascade the offer to `withdrawn`, and correctly reject a late `app.decide_job_offer_approval` call on the now-cancelled step with `approval_step_not_active`. The full 6-iteration concurrent-race evidence lives in this fix-pass session's scratchpad (not committed — matches this repository's standing convention that `db:test` regression evidence is deterministic/sequential; genuine two-process concurrency evidence is recorded in the build log narrative, as HRT-276's own Implement-stage §9 already did for other concurrency claims).
