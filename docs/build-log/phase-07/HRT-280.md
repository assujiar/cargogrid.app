## 1. What this checkpoint builds

HRT-280 is the seventh Phase 7 (HRIS/Ticketing) capability, built directly on `HRT-274` (Employee Master, `VERIFIED`), `HRT-275` (Organization and Position Linkage, `VERIFIED`), `HRT-276` (Recruitment/ATS, `VERIFIED`), `HRT-277` (Onboarding/Offboarding, `VERIFIED`), `HRT-278` (Attendance, `COMPLETED`), and `HRT-279` (Shift/Roster/Scheduling, `COMPLETED`). It implements versioned leave/permit/business-trip type and policy authoring, an auditable append-only balance ledger (no silent field mutation of a running total), a governed request → submit → decide → cancel workflow routed through PLT-123, precomputed coverage-aware approval (reusing HRT-279's own schedule resolution), and async accrual/carry-forward-expiry batches reusing PLT-132's real generic job queue. It additively binds into `HRT-278` attendance exception detection (an approved leave/permit day suppresses the attendance exception it would otherwise register) and into `HRT-279` scheduling (an approver may explicitly, never automatically, cancel a conflicting published shift when approving overlapping leave).

## 3. Source/config decisions (disclosed, not left implicit)

All numbered decisions are recorded in the main migration's own header comment (`supabase/migrations/20260730930000_create_hris_leave_permit_business_trip.sql:1-140`) and the binding migration's own header — summarized here:

1. **Leave types are versioned exactly like `app.attendance_policies`/`app.attendance_policy_versions` (HRT-278 decision 3) and `app.shift_templates`/`app.shift_template_versions` (HRT-279 decision 1).** `app.leave_types` is the scope pointer (code/category/evidence requirement); `app.leave_type_policy_versions` is the effective-dated ruleset (accrual frequency/amount, carry-forward cap, min-notice, max-consecutive, eligibility tenure, negative-balance-allowed). `app.resolve_effective_leave_type_policy_version` picks the correct version for a given as-of date and optional branch org unit, mirroring both prior checkpoints' own resolution shape exactly.
2. **The balance is a real, append-only ledger (`app.leave_balance_ledger`), never a mutable running-total column anywhere.** Every accrual, opening load, request debit, cancellation credit-reversal, carry-forward-cap forfeiture, and manual HR adjustment is its own signed-`units` row with an `event_type`. `app.get_employee_leave_balance` sums the ledger as of a date — the single source of truth, computed fresh every read, never cached in a way that could drift.
3. **Ledger rows are structurally append-only at the grant level** — `service_role` holds `INSERT`/`SELECT` on `app.leave_balance_ledger`; no role anywhere holds `UPDATE`/`DELETE`, verified live (§10). A wrong ledger entry is corrected with a compensating row, never an edit.
4. **The balance debit on approval is the AUTHORITATIVE check**, closing the C-04-shaped oversell race the submit-time check alone would leave open: `app.decide_leave_request` takes an `pg_advisory_xact_lock` keyed on `(employee_id, leave_type_id)` before re-reading the current balance and posting the debit, serializing two concurrent approvals of the same employee's same leave-type balance even though the ledger itself has no single row to lock (decision 9 restates this at the concurrency-specific level).
5. **Overlap prevention uses the established `btree_gist` EXCLUDE pattern**, not an application-level check. `app.leave_requests` carries a generated `validity_range daterange` column and `leave_requests_no_overlap` — `EXCLUDE USING gist (tenant_id WITH =, employee_id WITH =, validity_range WITH &&) WHERE (status IN ('pending_approval','approved'))` — mirroring `app.employee_position_assignments_no_primary_overlap`/`app.vendor_rate_versions_no_ambiguous_overlap`/`HRT-279`'s own `schedule_assignments_employee_workdate_active_unique` shape. Scoped to `pending_approval`/`approved` only (a `draft` may freely overlap another draft; the real conflict is only enforced at `submit`, which is where a `draft`'s status actually transitions into the guarded set) — **live-reproduced with two genuinely concurrent OS processes on this exact constraint, §8**.
6. **Approval is MANDATORY through PLT-123, never a bespoke mechanism** — the exact bug class this task's own instructions named as independently found in both `HRT-276` and `HRT-277`. `submit_leave_request` calls `app.request_approval`; `decide_leave_request` calls `app.decide_approval_step` FIRST, before any leave-specific business logic (coverage check, balance debit) runs — the real authority gate is PLT-123's own, leave-specific logic runs only after that gate clears; `cancel_leave_request` calls `app.cancel_approval_request` for any request still in `pending_approval` before its own status transition, so a cancelled leave never leaves a dangling live approval step.
7. **Cancel genuinely cancels, dated by real-world consequence.** Cancelling a still-`pending_approval` request cancels its own PLT-123 approval request and simply reverts to `cancelled` (no balance was ever debited). Cancelling an already-`approved` request whose leave has not yet fully elapsed posts a real credit-reversal ledger row dated `current_date` (restoring the balance immediately, mirroring decision 9's own "decision-date, not leave-date" dating rule) and, if a schedule assignment was overridden for it, does NOT automatically restore the shift (a disclosed, deliberate scope boundary — re-scheduling is an HR act, not a side effect of a cancel). Cancelling an already-past, already-approved leave (`date_to < current_date`) is rejected — no meaningful compensating action exists for time already taken.
8. **Coverage-aware approval reuses `HRT-279`'s own schedule resolution, never a second lookup mechanism.** `app._leave_coverage_impact` (internal, `service_role`-only) counts other employees still scheduled on the affected branch/day against `app.roster_coverage_requirements`' own `min_headcount`; `decide_leave_request` blocks an approval that would drop coverage below the minimum unless the approver also holds `HRS:Override` — a genuine authority-tiered override, evaluated only AFTER `app.decide_approval_step` has already proven the caller a legitimate approver of this step (closing a C-05 shape: coverage detail is never disclosed to a caller who has not yet cleared the real authority gate).
9. **A leave day never automatically cancels a scheduled shift** — `app.cancel_conflicting_schedule_assignment_for_leave` is a distinct, explicit, `HRS:Override`-gated action an approver may call separately after approving overlapping leave, never an implicit side effect of `decide_leave_request` itself. Mirrors this task's own instruction ("should be able to override... coverage awareness", not "must always override").
10. **Self-service requests take no `employee_id` parameter to spoof** — `app.create_leave_request`/`app.submit_leave_request`/`app.cancel_leave_request` resolve the acting employee via `app.get_self_employee(actor_auth_user_id)` (reused unchanged from `HRT-278`), never a caller-supplied id; `app.create_leave_request_for_employee` is the distinct, `HRS:Edit`-gated HR-on-behalf entrypoint that does take an explicit `employee_id`.
11. **Sensitive free-text fields are column-restricted from THIS, the FIRST, migration** — `reason`/`destination`/`decided_reason`/`cancel_reason` (`leave_requests`) and `reason` (`leave_balance_ledger`) are never projected to `authenticated` at the grant level; masked/re-exposed only inside the read RPCs to self-or-`HRS:View-personal-data`, mirroring `HRT-278`'s/`HRT-279`'s own established convention. `leave_types.evidence_classification` (e.g. `medical`, `personal`) is a real, queryable enum column — not free text — registered in `scripts/data-classification/registry.ts` as its own row so medical/personal evidence requirements are structurally distinguishable from a routine annual-leave type.
12. **Medical/personal evidence reuses `PLT-128`'s malware-scan pattern exactly**, never a bespoke re-implementation — `app.leave_types.requires_evidence`/`evidence_classification` gate `submit_leave_request` on a real `evidence_file_id` whose `app.files` row is re-validated for tenant scope, record-type/record-id match, and `malware_scan_status = 'clean'` at submit time (taxonomy C-10), the identical re-validation shape `HRT-276`'s resume-scan gate already established.
13. **Accrual/carry-forward-expiry reuse PLT-132's real generic job queue**, the second HRIS-domain adopter after `HRT-279`'s `roster_generation`. `app.jobs.job_type`'s CHECK constraint and `app.generic_job_types()` (the actual ATW-031/ISS-2026-012 single source of truth) both widen to add `leave_accrual`/`leave_carry_forward_expiry` — `app.enqueue_job`/`app.dispatch_event_as_job` are untouched, since ATW-031 already collapsed their own literals into a call to `app.generic_job_types()`. `run_leave_accrual_batch`/`run_leave_carry_forward_batch` self-claim the SPECIFIC job row they just created (by `job_id`, under its own row lock), guard the claim/loop/complete logic behind `if v_job.status = 'pending'`, then call the SAME `app.complete_job()` any future live poller would call — bounded, idempotent, safe to replay (self-found gap, §7).
14. **RBAC.** Zero new `app.permissions` rows — the eleven `HRS` actions `HRT-274` already seeded (`Create`/`Edit`/`View`/`View personal data`/`Approve`/`Override`/`Import`/`Export`, etc.) cover every write this checkpoint adds.

- **Concurrency:** the overlap EXCLUDE constraint is the structural safety net for submit-time double-booking (no pre-existing row to lock for the FIRST overlapping submission); the advisory-lock-serialized debit is the structural safety net for the balance itself (no single row exists to lock on an append-only ledger). **Both live-reproduced with two genuinely concurrent OS processes** (§8).
