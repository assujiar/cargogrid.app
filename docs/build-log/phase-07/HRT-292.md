## 3. Scope decisions — exact, disclosed

1. **A uniform, bounded three-field safe-snapshot shape — `{label, detail, status}` — for all six entity types, never six differently-shaped per-type jsonb schemas.** The business rule names the safe fields per type (shipment number + status label; invoice number + amount + status; warehouse/vendor/customer name; user display name); this checkpoint maps each type's own fields into the same three generic slots (e.g. invoice: `label`=invoice number, `detail`="USD 1100.00", `status`=lifecycle status) rather than inventing six independent shapes. Simpler to validate (C-07: a single, easily-audited bound), simpler to render (one UI code path for all six types), and still carries exactly the business-rule-named content, never more.
2. **The persisted `safe_snapshot` is captured ONCE at link time, for history only, and is NEVER read back as currently-authoritative.** Every live read (`list_ticket_links`, and implicitly every re-authorization inside `link_ticket_record`/`search_ticket_link_candidates`) re-fetches fresh from the source table through the ONE shared adapter, `app._ticket_link_resolve_candidate`. An unavailable record (hard-deleted OR the current caller's access has since been revoked/expired) shows a generic `unavailable` status with NO label/detail at all — never the frozen historical value, which would otherwise leak "this record still exists, here is what it used to look like" past a caller who has since lost the right to know that. Live-proven twice (db-test §10 revoked eligibility, §11 hard-deleted source) plus a third, narrower proof that a genuinely AVAILABLE link's displayed content is the FRESH value, not the stale snapshot (§12, a live warehouse rename).
3. **Customer (`customer_user`-layer) callers get a narrower entity-type registry — shipment, invoice, warehouse, customer; never vendor or user** (`app.ticket_link_customer_safe_entity_types()`). No existing customer-facing read path for `app.vendor_profiles`/`app.users` exists anywhere in this repository (both structurally exclude `customer_user` via `NOT app.actor_holds_customer_user_layer` in their own already-applied RLS) — exposing either would leak internal supplier/staff-directory structure to an external customer. This is gated on the ACTOR (`app.actor_holds_customer_user_layer`), not the ticket's channel column, which is the structurally correct predicate: a helpdesk-channel ticket's own requester party is a real `tenant_admin`/`TKT:Edit`-holding TENANT identity, not a `customer_user`, and correctly gets the FULL registry.
4. **A genuinely new, narrow customer-owner-scope composition for shipment/invoice/warehouse — disclosed as new capability, not merely "reused."** Direct inspection (not assumed) found `app.shipment_orders`' own RLS policy passes `NULL` for `can_access_record`'s customer-account-ref argument (a `customer_user` actor is structurally denied ANY shipment via raw RLS today) and `app.finance_invoices`' own RLS carries no customer branch at all — there is genuinely no existing customer-facing read path for either table in this repository. Since the business rule explicitly expects a customer to see their OWN account-scoped shipment/invoice/warehouse links, this checkpoint composes `app.resolve_customer_owner_account_scope` (ATW-242, unmodified) against each table's OWN existing owner-account column as an additional OR-branch, and reuses `app.customer_warehouse_eligibility_active` (ATW-242) verbatim for warehouse — never a new authorization primitive. This can only ever admit a genuine, active `customer_user` membership scoped to the row's own owning account; it never widens what an INTERNAL actor could already see.
5. **A real, disclosed, capability-specific gate closes a genuine C-08 widening for the helpdesk channel: `app._ticket_link_actor_may_view_tenant_data`.** Staff status on a helpdesk ticket is Supreme-Admin-only (HRT-288 decision 3), and `app.evaluate_permission`/`app.can_access_record`/`app.has_active_tenant_membership` all structurally bypass EVERY check for a Supreme Admin (confirmed by direct inspection). Composing six domains' worth of read access through one new capability would otherwise let ANY Supreme Admin browse ANY tenant's shipments, invoices, vendors, accounts and users merely by opening a helpdesk ticket into that tenant — a genuinely NEW, broader exposure this capability itself would introduce, not a pre-existing one it merely inherits. Closed by requiring the caller to ALSO hold a real `app.tenant_user_identities` membership, a live `app.support_access_grants` grant (PLT-115, case-bound by construction — `case_id` is `NOT NULL`), or an active `customer_user` membership in that tenant — checked BEFORE any per-type domain predicate runs. Live-proven in db-test §8: a Supreme Admin with no grant sees zero candidates and is denied `record_not_eligible` identically to a forged id; the SAME Supreme Admin, after a real `app.request_support_access` emergency grant, succeeds.
6. **Link/unlink authority mirrors `app.add_ticket_watcher`'s own established rule exactly — staff OR requester-side party, never a plain watcher.** `app.is_ticket_staff OR app._is_ticket_requester_party`, the identical predicate HRT-286's own watcher-management RPCs already use. A plain watcher (no staff standing, not the requester) may still SEE links (read access follows `app.can_access_ticket` alone) but may not add/remove one — mirrors `WatcherList`'s own established `canManage` UI convention verbatim.
7. **Relationship is a small, fixed four-value enum** — `primary_subject`, `related`, `affected`, `context` — chosen as a reasonable, ticket-appropriate set (a ticket-to-record link is never itself a "duplicate_of" relationship the way ticket-to-ticket dedup would be) rather than an open-ended free-text field.
8. **`source` is CHECK-constrained to `('manual', 'system')`, but every RPC in this migration inserts `'manual'` only.** No autonomous/system linker exists or is invoked anywhere in this checkpoint — AI-suggested related records is explicitly Step 14 (out of scope, business rule), and no other automatic-linking trigger (e.g., ticket-created-from-shipment-exception) exists elsewhere in this repository to wire into. The `'system'` value exists so a genuinely future automatic linker has a real column to populate without a schema change — disclosed as a real, unused extension point, not a placeholder pretending to be built.
9. **This capability's own append-only ledger, `app.ticket_link_events`, IS the audit trail — never `app.audit_logs`.** Mirrors `app.ticket_escalation_events`' own decision 15 (HRT-291) exactly: governed by the SAME RLS as the parent ticket (staff-only, `customer_user` excluded), carrying real reason/relationship/actor free text safely because its readership never exceeds the ticket's own staff population. No `app.capture_audit_event` call exists anywhere in this migration — link/unlink are themselves the only mutations, both ticket-scoped exactly like escalate/acknowledge/suppress, which HRT-291 also routed to its own ledger only.
10. **A dedicated `app.record_ticket_link_access_denial`/`app.record_ticket_link_summary_access` pair, mirroring `app.record_customer_inventory_access_denial` (ATW-242) exactly**, because a RAISE inside `app.link_ticket_record`/`app.search_ticket_link_candidates` aborts the whole transaction — an audit INSERT performed moments earlier in the SAME call can never survive it (ATW-242's own design note 9, empirically proven there, reused here rather than rediscovered). `search_ticket_link_candidates` itself does NOT raise on a tenant-data-view-gate failure (decision 5) — it returns zero rows and durably logs `search_denied` inline (a normal, committing return, not a rollback).
11. **No new UI route.** The linked-records panel is a section inside the two already-existing ticket detail views (`tickets/[ticketId]/ticket-detail-panel.tsx` for staff/internal-requester viewers, `customer-tickets/[ticketId]/customer-ticket-detail-panel.tsx` for the customer viewer) — matching this task's own explicit "or a section inside the existing ticket-detail-panel.tsx" allowance and every prior HRT-289/290/291 checkpoint's own precedent of adding a section to this same file rather than a parallel page.
12. **A "deep link" to each of the six source domains' own detail pages is NOT built.** `app.record_ticket_link_summary_access`'s `deep_link_opened` access type and the underlying audit mechanism are real and tested (db-test §16), but the UI does not attempt to construct or navigate to a real cross-module URL for each of the six domains — several of those detail routes exist in this repository (e.g. `operations/shipment-orders/[shipmentOrderId]`, `procurement/vendors/[masterRecordId]`) but a few do not have a stable per-record route this checkpoint could target without risking a broken link for at least one type. Disclosed, not silently dropped: the "Mark viewed" control fires `summary_viewed`, proving the audit mechanism end-to-end; wiring real per-type deep-link hrefs is a reasonable, bounded follow-up.

## 6. Self-found defects fixed before finishing

1. **(A genuine authorization-bypass-via-duplicate-check ordering bug, self-found live by my own db-test §9, not by a separate review pass)** — an early draft of `app.link_ticket_record` checked for an already-active link on the natural key FIRST and returned it unconditionally on a match, BEFORE re-validating the CURRENT caller's own eligibility through `app._ticket_link_resolve_candidate`. Concretely: staff1 (a real ticket-staff queue member with no OPS/FIN/PRC role) attempted to "link" a shipment ALREADY linked by an authorized admin earlier in the same test run, and — because the duplicate-policy short-circuit ran first — received the existing link row (including its `safe_snapshot`, the shipment number and status) despite having NO independent domain authorization of their own. This is exactly the "a link grants access" violation the business rule forbids, and directly the kind of bug the mandated adversarial db-testing exists to catch. Fixed by re-ordering `app.link_ticket_record` so the anti-enumerating eligibility check ALWAYS runs first, for every call including a fully idempotent replay — the duplicate-policy short-circuit now only returns the existing row once the CURRENT caller's own eligibility has already been independently proven. Re-verified live: staff1 is now correctly denied `record_not_eligible` for the same shipment; the identical scenario for a genuinely-authorized caller still replays idempotently (db-test §3).
2. **(A genuine PostgreSQL volatility-category bug, self-found live the moment the migration was first exercised end-to-end, not by static review)** — `app.search_ticket_link_candidates` was originally marked `stable` despite performing a real `INSERT` (the `search_denied` ledger write on a tenant-data-view-gate failure, decision 10). Postgres rejected this outright at call time ("INSERT is not allowed in a non-volatile function") the first time the helpdesk-no-grant scenario (db-test §8) was actually exercised. Fixed by dropping the `stable` marker — the function has a genuine side effect and must be volatile, matching PostgreSQL's own rules; every other read-only function in this migration correctly keeps `stable`.
3. **(Two genuine repository-wide security-sweep failures, self-found by a full `pnpm run db:test` pass against `scripts/db-tests/rbac-enforcement.sql`, ATW-032/ISS-2026-033 and ISS-2026-032 — not by this migration's own review)** — an early draft of `app.record_ticket_link_access_denial` was granted to `authenticated` with no authority check of any kind reachable in its call graph, and separately took `p_actor_auth_user_id` (a claimed-actor parameter, per the standing sweep's own classification) with no check proving that identity matched the caller. Concretely, this would have let ANY authenticated identity inject a fabricated ledger row into an UNRELATED tenant's `ticket_link_events`, attributed to an arbitrary colleague's identity, merely by calling the RPC directly. Fixed by adding `app.assert_actor_is_session_identity(p_actor_auth_user_id)` (closes the claimed-actor gap, mirrors every other function in this migration) and `app.assert_session_identity_in_tenant(p_tenant_id)` (closes the no-tenant-standing gap, mirrors `app.record_customer_inventory_access_denial`'s own identical, already-reviewed fix, ATW-242, verbatim). Re-verified: a full `pnpm run db:test` pass now shows both sweeps passing cleanly alongside every other db-test file.
4. **(A non-deterministic db-test query, self-found live — a TEST bug, not a product bug)** — db-test §12 (stale-cache resistance) originally selected "the ticket's active warehouse-type link" by `entity_type` alone; by that point in the suite the internal ticket also carries a SECOND active warehouse link (§11's own `WH-LNK1-DEL`, deliberately left active-but-unavailable after its source was hard-deleted), so the query non-deterministically picked either row and failed roughly half the time depending on physical row order. Fixed by filtering on the specific `entity_id` too. No product code changed for this item.
