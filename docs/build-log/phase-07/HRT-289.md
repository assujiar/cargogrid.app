## 3. Migration split decision

Two migrations, one per sub-capability, matching the prompt's own "your call, document it" instruction: the SLA and Knowledge Base schemas share zero foreign keys with each other (a `kb_ticket_article_links` row references `app.tickets` and `app.kb_article_versions` only; no SLA table references any KB table or vice versa), so splitting them keeps each migration's own blast radius, rollback unit, and future superseding-hardening-migration scope cleanly independent — exactly the same reasoning HRT-286/287/288 already applied to keep each ticket channel in its own file.

## 4. SLA policy precedence — the exact decision

`app.resolve_effective_sla_policy_version` (section 24's own business rule, "never silently ambiguous," taken literally) ranks every published policy version whose scope structurally matches the ticket — `channel` is a required exact match; `category_id`/`priority`/`customer_account_id`/`queue_id`/`support_queue_id` are each either `NULL` (wildcard) or an exact match — by specificity in one fixed, named order:

1. `customer_account_id` set (most specific — a per-customer override)
2. `queue_id`/`support_queue_id` set
3. `category_id` set
4. `priority` set
5. the version's own explicit `precedence_rank` (author-assigned tie-break for two versions of otherwise-equal specificity)

Implemented with `rank()` over that ordering so genuine ties share `tie_rank = 1`. If, after the full ordering, more than one candidate remains at `tie_rank = 1`, the function **raises `sla_policy_ambiguous_match`** rather than picking one arbitrarily. Zero candidates returns `null` (the "no matching policy" alternative flow — `app.start_ticket_sla_clock` raises a distinct `sla_policy_not_matched`, and a ticket may still be created without an SLA clock; a missing policy is never a hard ticket-creation failure).

**Self-found bug, fixed before commit**: `app.publish_sla_policy_version` initially did NOT supersede a policy's own prior published version (deliberately, matching the *cross-policy* non-supersede design below) — but that meant publishing a revised version of the SAME policy left its own predecessor also `published`, and the two then tied against EACH OTHER at resolution time — a false `sla_policy_ambiguous_match` neither version deserved. Found live in this checkpoint's own adversarial pass (section 3 of `ticketing-sla.sql`), fixed by adding a same-`policy_id` supersede step (mirrors `app.publish_sla_calendar_version`'s own supersede, under the same parent-row lock), re-verified. Publishing a version of one policy deliberately still does NOT supersede a sibling, DIFFERENT policy's own published version — two different policies may legitimately publish overlapping-scope versions (e.g. two teams each define a channel-wide default); that risk surfaces at resolution time via the ambiguous-match guard above, never suppressed at publish time.

## 5. Knowledge-article audience model — the exact decision

Three independent boolean flags on `app.kb_article_versions` — `audience_internal`/`audience_customer`/`audience_helpdesk` — deliberately mirroring `app.ticket_categories.customer_visible`/`helpdesk_visible` (HRT-287/288) rather than inventing a parallel vocabulary. A published version requires at least one flag true (an unpublishable-to-anyone version is a dead state, structurally rejected by a CHECK constraint). Draft/review/publish is a real, explicit five-state graph (`draft → in_review → approved → published → archived`, `in_review → draft` on `changes_requested`) enforced by each transition RPC's own guard on the FROM status — publish **requires** `status = 'approved'`, with **no bypass path** (read literally from section 24's own business rule, "Knowledge articles require ... reviewer, published version"). Self-review is structurally blocked at both submit time (`p_reviewer_auth_user_id = author` rejected) and review time (the acting reviewer identity re-checked against both the assigned reviewer AND the author independently — even a Supreme Admin acting as reviewer cannot approve their own authored version).

Audience-safe search/read is the security-critical half, enforced identically at two independent layers: RLS on `app.kb_article_versions` gives a customer-layer identity **zero raw-table access under any status** (customer reads exist only through `app.search_customer_knowledge_articles`/`app.get_kb_article_for_customer`), and those RPCs apply the identical `status='published' AND audience_customer=true AND not expired` filter a second time in their own `WHERE` clause. The helpdesk read surface repeats the same discipline with `audience_helpdesk`. No caching/autocomplete/snippet table exists anywhere — search is always evaluated live against this same predicate, disclosed explicitly so a future capability does not accidentally build a cache that skips the filter and reopens this exact leak class.

## 6. Job-framework honesty disclosure (mandatory per this task's own instructions)

Both durable jobs (`app.run_ticket_sla_evaluation_batch`, `app.expire_kb_article_versions_batch`) reuse `app.jobs` (PLT-131/132) exactly — `job_type` widened (`ticket_sla_evaluation`, `kb_article_expiry`), `app.generic_job_types()` kept set-equal by the standing ATW-031 drift gate, no second job mechanism invented.

**What is genuinely guaranteed, live-proven**: a retried evaluation cannot insert a second `met`/`breached` row for the same `(clock, phase)`, nor a second reminder at the same `(clock, phase, threshold)` — enforced by a real partial unique index on the natural key **plus a real `exception when unique_violation` handler**, not a pre-check `SELECT` (the exact C-01/C-02 gap this task's own mandatory reading flagged). This was proven with **two genuinely concurrent OS `psql` processes** evaluating the identical clock at (as close as two processes can get to) the same instant, launched via `scripts/db-tests/wms-picking-concurrency-helper.sh` (reused directly, its own generic `PG_TEST_DB`/`RACE_SQL_A`/`RACE_SQL_B` contract) — after both completed, the ledger held exactly one `response/breached` row, never two. The expiry job's own idempotency is a plain, re-runnable `UPDATE` (published+expired → archived) — running it twice for the same `as_of`/`period_label` is a genuine no-op, no exception handler needed (mirrors `app.run_training_certificate_expiry_batch`'s own disclosed reasoning for why an UPDATE-shaped batch needs none), also live-verified (second call returns `expired_count=0`).

**What is NOT claimed**: neither job claims genuine multi-step, crash-mid-calculation resumability. Each evaluation call (`app._evaluate_ticket_sla_clock`) is a single, short, all-or-nothing transaction with no internal checkpointing — if the process crashes mid-transaction, nothing commits, and a retry simply redoes the (idempotent) work from scratch. This is a materially narrower guarantee than "resumable," stated that way deliberately, per the explicit HRT-282/`ISS-2026-079` lesson this task's own mandatory reading named — no genuine multi-transaction crash-resumability is claimed anywhere in this checkpoint, because none was built.

**No live cron/poll scheduler exists anywhere in this repository** — the same disclosed `NOT_RUN` class PLT-123/PLT-125/PLT-132/HRT-284 already carry. `app.run_ticket_sla_evaluation_batch`/`app.expire_kb_article_versions_batch` are real, callable, tested entry points a future scheduler would invoke periodically; this checkpoint proves the mechanics live (including the concurrency guarantee above), not a running scheduler.

## 7. Other structural decisions (disclosed)

- **Zero modification to any HRT-286/287/288 function.** `app.start_ticket_sla_clock`/`pause`/`resume` are explicit, separate RPCs a UI calls as a SECOND step right after ticket creation succeeds — never a trigger, never woven into `app._create_ticket`/`app.transition_ticket_status`/any `reply_to_*` function. Response-met is DERIVED (read-time, from the first `visibility='public', author_role='staff'` row in `app.ticket_messages`) and resolution-met is DERIVED (from `app.tickets.resolved_at`, already set by the existing `app.transition_ticket_status`) — the evaluation job reads these signals, it never writes a hook into either function. This was a deliberate design choice to keep this checkpoint's blast radius at zero regression risk against three already-`VERIFIED` migrations — re-confirmed by re-running all three prior channel db-test files byte-for-byte unmodified (§9).
- **Business-time engine is a real day-by-day walk**, not a placeholder: `app.compute_sla_business_minutes` walks each calendar day between two timestamps in the calendar version's own timezone, treats a holiday date as zero business minutes unconditionally (overrides `is_24x7`), sums per-weekday business windows otherwise. V1 supports exactly one business-hours window per weekday (no split-shift/lunch-break carve-out) — disclosed, not hidden; deferred, not forgotten.
- **A clock retains the EXACT policy-version and calendar-version row ids** it started against — real foreign keys to specific version rows, never the parent policy/calendar. Live-tested directly: a clock started under calendar version 1 and a wide SLA policy, then BOTH a new calendar version 2 (24x7) and a new, tighter policy version were published — the already-started clock's own frozen `sla_calendar_version_id`/`sla_policy_version_id`/targets were unchanged, while the calendar's own "current published version" correctly advanced to v2 for future clocks.
- **Compliance is reproducible from the ledger, not the cache.** `app.reconcile_ticket_sla_clock` rebuilds `status`/`response_status`/`resolution_status`/`*_at` purely from `app.ticket_sla_clock_events`. **Self-found bug, fixed before commit**: the first implementation reconciled `response_status`/`resolution_status` from the ledger but left the CLOCK'S OWN overall `status` column untouched — after a corrective ledger edit reverted a phase back to `pending`, `status` stayed stranded at `completed`, which then wrongly short-circuited `app._evaluate_ticket_sla_clock`'s own `status not in ('running','paused')` guard and silently prevented re-evaluation. Found live during the concurrency-race test setup in this checkpoint's own adversarial pass, fixed by widening `reconcile_ticket_sla_clock` to also derive `status` (cancelled > completed > paused/running, from the most recent pause/resume event) — the reconciliation function is now genuinely, fully ledger-derived, not partially.
- **Pause/resume is EXPLICIT staff action, never tied to ticket status.** `on_hold`/`pending` ticket status and SLA pause/resume are deliberately decoupled — pausing requires a closed set of reason codes (`waiting_on_customer`/`waiting_on_third_party`/`internal_investigation`/`other`), validated structurally, not merely a free-text field. Disclosed as a deliberate departure from an implicit status-triggered pause, chosen specifically to avoid touching `app.transition_ticket_status` at all.
- **ERR-2026-004 (self-found, live, in this checkpoint's own full `db:test` run)**: neither new migration initially carried the `revoke execute on all functions in schema app from public;` statement every prior ticketing migration (HRT-286/287/288) includes — Postgres grants `EXECUTE` to `PUBLIC` by default on function creation, so three service-role-only-intended functions (`app.resolve_effective_sla_policy_version`, `app.replay_ticket_sla_clock_elapsed`, `app.reconcile_ticket_sla_clock`) were still effectively callable by `authenticated` (and, transitively, `anon`) despite their own explicit narrower grant — caught by `scripts/db-tests/rbac-enforcement.sql`'s own live `has_function_privilege('authenticated', ...)` sweep (ATW-032/`ISS-2026-032`), which checks EFFECTIVE privilege, not just direct ACL entries. Fixed by adding the same revoke statement to both new migrations (mirrors every prior ticketing migration exactly) and additionally hardening the three functions' own comments to explain WHY they are service-role-only (each takes a bare id parameter with no tenant/actor check of its own, so `authenticated` access would be a real cross-tenant read). Re-verified: `anon` and `authenticated` both hold zero effective `EXECUTE` on any SLA/KB function not explicitly granted to them; the full `db:test` harness passes clean.
