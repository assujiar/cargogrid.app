## 3. Source/config decisions (disclosed, not left implicit)

### 3.1 `master_type_code='employee'` — registered

ADR-0023 Part B left this open for this checkpoint's own decision ("recommended, not forced"). **Decision: register it**, mirroring `app.vendor_profiles`/`app.driver_operational_profiles`'s established 1:1-extension-of-`app.master_records` pattern exactly. Reasoning: (a) the `driver` master-type row was already seeded at Phase 3 with `owner_module_code='HRS'` — Operations itself anticipated eventual HR ownership of this shape; (b) `app.master_records` already carries a stable natural code (the employee number) and `canonical_status`/`deactivated_*`/`merged_into_id` (soft-lifecycle/dedupe-lineage primitives, "never hard-delete" per section 24) for free; (c) future capabilities (Recruitment/ATS onboarding conversion at Prompt 277, Payroll at Prompt 282) can resolve "is this master_record_id an employee" uniformly. The alternative (a bespoke `app.employees`-only table with its own code/uniqueness/lineage machinery) was rejected as the "duplicate root" ADR-0023's own reasoning forbids for a structurally identical question.

**CORRECTION (§11's own review round):** this paragraph originally also claimed `master_records.effective_from`/`effective_to` satisfied section 13's "effective dates" requirement. Live verification found that claim false — no function in the migration reads or writes those two columns for any employee purpose, `app.employees` itself carries no effective-dated column, and no write RPC accepts an effective-date parameter. The migration's own header comment is corrected in place (`CREATE OR REPLACE`-free — the same uncommitted migration file); this build log's claim is corrected here rather than left standing. Disclosed as `ISS-2026-065` (High, OPEN) — see §7 and §11.

### 3.2 Company/branch/department/position/manager — real, nullable, validated columns now

Per Prompt 274 §10's own instruction to consider downstream impact for HRT-275..297: `company_org_unit_id`/`branch_org_unit_id`/`department_org_unit_id` are real FKs into `app.org_units` (never a second hierarchy), structurally validated for `unit_type` and tenant/ancestor consistency by `app.enforce_employee_org_unit_shape()`. `manager_employee_id` is a real, self-referential nullable FK to `app.employees(master_record_id)` — an employee's manager is another employee, not merely a Platform user — cyclic reporting lines rejected by `app.assert_no_employee_manager_cycle()` (bounded 200-hop chain walk), called from every RPC that can set it. `position_title` is a plain, ungoverned free-text column: Prompt 275 ("Organization and Position Linkage") is the formal position/grade/eligibility table's own chartered scope; adding a governed `position_id` FK now would anticipate a not-yet-built capability's own design. When Prompt 275 ships, `position_title` remains a display fallback and a new additive `position_id` column is expected then, never retrofitted speculatively here.

### 3.3 Employee numbering — fixed default + explicit override, not a template engine

`app.next_employee_number()` generates `EMP-YYYY-NNNNNN` (mirrors `app.next_vendor_code` exactly, same atomic counter shape, internal-only). A caller may supply an explicit number instead, validated for tenant-uniqueness by `master_records`' own unique index. This is a bounded, disclosed interpretation of section 13's "configurable format" — no tenant-configurable template-string engine exists anywhere in this repository to reuse, and building one is disproportionate scope for this checkpoint.

### 3.4 Lifecycle state machine

`draft → submitted → approved → active`; `active ↔ on_leave`; `active ↔ suspended`; `{active, on_leave, suspended} → terminated` (terminal, requires reason + `employment_end_date`, preserves all history); `{draft, submitted, approved, terminated} → archived` (terminal administrative closure — reachable both from a never-activated profile AND from a terminated one, per section 22's "suspend OR archive with preserved history" naming two sibling closure paths); `{submitted, approved} → draft` (reject, with `revision_reason`, never a separate terminal status, mirrors PRC-251's identical choice). Never a hard delete anywhere. `on_leave`/`suspended` are coarse HR-set states only — a full leave-request approval workflow (accrual, balances, multi-day requests) is Prompt 280's own chartered scope, not anticipated here.

### 3.5 Duplicate detection — human-reviewed only, never auto-merged

`app.search_employee_duplicate_candidates` (exact `national_id_number`/`work_email`/`personal_email` match, score 1.0, OR `pg_trgm` fuzzy `full_name` match) is a manual search HR staff runs; `app.flag_employee_duplicate_candidate` records a candidate pairing; `app.decide_employee_duplicate_candidate` records `linked`/`dismissed`, never invoking `app.merge_master_records` itself. `app.submit_employee_for_approval` blocks while any `pending` candidate remains — mirrors PRC-251 exactly.

### 3.6 Staged import — the fifth-plus real PLT-131/132 domain-write adapter

`employee_import` schema code + `employee_document` document type are registered directly (structural rows, mirroring `vendor_rate_import`'s own direct-INSERT convention — the registering functions gate on Supreme Admin and a migration-apply context has no live actor). Each tenant separately publishes its own `import_export:employee_import` column definition and `document:employee_document` MIME/size/retention/classification policy via the existing Configuration Engine before importing — the same per-tenant onboarding step every other schema/document type in this repository requires. `app.validate_employee_import_row` calls `app.validate_staging_row` unchanged first, then adds a formula/spreadsheet-injection rejection pass (identical prefix set to `app.validate_vendor_rate_import_row`, PRC-255) plus org-unit-code resolution. `app.commit_employee_import_job` is idempotent per staging row (`source_import_staging_row_id` unique-when-set on `app.employees`, defended by a pre-check AND a nested `unique_violation` handler) and job-scoped-advisory-lock serialized, mirroring `app.commit_vendor_rate_import_job` exactly. Every imported row lands as a real `draft` employee — submit/approve/activate remain separate, deliberate HR actions, never auto-activated by import.

### 3.7 Sensitive-field classification

`national_id_number`, `date_of_birth`, `gender`, `personal_address_*`, `personal_phone`, `personal_email` (on `app.employees`) and `phone`/`email` (on `app.employee_emergency_contacts`) are masked by `app.has_view_personal_data` (PLT-114, reused unchanged — `HRS:View personal data` was already seeded at PLT-111) unless the caller is reading their own linked profile. `HRS_REGISTRY` (`scripts/data-classification/registry.ts`) carries 5 entries, category `pii` (never `payroll` — that category is reserved for the future Payroll capability; Employee Master carries zero bank/tax/payroll-shaped columns). `work_email`/`work_phone` are deliberately unmasked (corporate identity fields, not personal data).

## 4. Security/access model

- **RLS:** every new table carries the hardened default-deny form (`app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id) or app.is_supreme_admin()`), proven live against a `customer_user`-layer principal in the same tenant (zero rows on `app.employees`/`app.employee_change_requests`).
- **RBAC:** every write RPC gates through `app.evaluate_permission(actor, tenant, 'HRS', action)`, which itself calls `app.assert_actor_is_session_identity` internally (wired at `20260730440000`) — covering the identity-spoofing check for every RPC that reaches it. The two RPCs that do NOT reach `evaluate_permission` (`app.get_my_employee_profile`, `app.request_employee_change`, `app.list_my_team_employees` — all identity-match-gated, not permission-gated) each carry an explicit `perform app.assert_actor_is_session_identity(...)` call, matching the established classification-pass discipline (`20260730510000`). **This exact gap was independently re-caught live**: the repository's own `scripts/db-tests/rbac-enforcement.sql` transitively walks the `evaluate_permission`/`assert_actor_is_session_identity` call graph and failed the first draft of this migration (`app.validate_employee_import_row` was granted to `authenticated` while reaching neither check) — fixed by restricting that grant to `service_role`-only, matching `app.validate_staging_row`/`app.validate_vendor_rate_import_row`'s own established convention.
- **Field masking:** `app.get_employee_profile` returns `personal_data_masked` computed server-side (never a client-side guess); `app.list_employee_emergency_contacts` masks phone/email identically to `app.vendor_contacts` (PRC-251). `app.list_employees`/`app.export_employees`/`app.list_my_team_employees` carry zero PII columns in their projections at all — masking is not needed there because the sensitive columns are simply never selected.
- **Concurrency (row lock + repeated version predicate):** every write RPC `SELECT ... FOR UPDATE`s the target row first, folds a non-member caller into the same `*_not_found` branch a genuinely missing row would produce (never discloses a real `tenant_id`), checks authority BEFORE `record_version` (never discloses a real version to an unauthorized caller), and repeats `record_version = p_expected_version` in the terminal `UPDATE`'s own `WHERE` clause as a second guard — the fully-hardened shape this repository converged on via `20260730480000`/`20260730820000`, adopted here from day one rather than retrofitted.
- **Files:** documents reuse `app.files` directly (`record_type='employee'`), never a second file table; a real `employee_document` document type is registered with its own per-tenant MIME/size/retention/classification policy.

## 11. Same-checkpoint adversarial review round: findings, fixes, and disclosures

After the original build (§1–§10 above, §7.1's 7 self-found defects) passed every automated gate, three independent adversarial review lenses (security/RLS/tenant-isolation; correctness/concurrency; spec-completeness) re-examined the full changeset against a live, disposable Postgres 16 database. This section is the fix pass's own record: every CONFIRMED finding, independently re-derived (not blindly trusted) before being fixed, its exact fix, and the two items disclosed rather than force-fixed.

### 11.1 Findings fixed

1. **CRITICAL — raw `SELECT` of classified pii columns bypassed all RPC-side masking.** `grant select on app.employees to authenticated` (and the same shape on `app.employee_emergency_contacts`/`app.employee_change_requests`) was a full, unrestricted column grant; the RLS `USING` clause only checked tenant membership, never `HRS:View personal data`. RLS filters rows, not columns — any `authenticated`-role session (a real Supabase JWT via a direct Postgres/PostgREST connection) could `SELECT national_id_number, personal_email, ... FROM app.employees` and get real values regardless of HRS permission. Independently re-derived live: a zero-HRS-permission tenant member (`admin@hrmemp1.test`, a `tenant_admin` assigned no role in the test fixture) reading `national_id_number`/`personal_email` off the raw table before the fix would have succeeded. **Fixed** using `PLT-114`'s own already-proven pattern (`app.users`/`app.users_directory`, `20260716110430`): `grant select (<explicit non-pii column list>) on app.employees to authenticated;` (and the equivalent for the other two tables), full unrestricted `select` retained for `service_role` only. `supabase/migrations/20260730830000_create_hris_employee_master.sql`, grants section (§14). Regression evidence: `has_column_privilege` structural assertions plus a live session-simulated raw `SELECT` denial, both in `scripts/db-tests/hris-employee-master.sql`.
2. **CRITICAL — unmasked pii copied into `app.audit_logs`.** `create_employee_draft`/`update_employee_draft`/`transfer_employee`/`add_employee_emergency_contact`/`update_employee_emergency_contact`/`request_employee_change` each passed `to_jsonb(<raw row>)` into `app.capture_audit_event`. `app.redact_audit_payload`'s key-name-pattern redaction (`secret|password|token|key|authorization|cookie|ssn|npwp|bank|account_number|salary|payroll`) does not match `national_id_number`/`personal_email`/`personal_phone`/`date_of_birth`/`gender`/`personal_address_*`/emergency-contact `phone`/`email`/`employee_change_requests.current_value_snapshot`/`requested_value` — every one of these was written to `app.audit_logs` in plaintext, readable by any tenant_admin via `app.query_audit_logs` regardless of `HRS:View personal data`. The finding's own evidence named only create/update/transfer; **swept the full call graph** and found the identical defect in `add_employee_emergency_contact`/`update_employee_emergency_contact` (contact phone/email) and `request_employee_change` (whose table's ONLY two free-text columns are, by the table's own CHECK constraint, always a classified pii value). **Fixed** by adding `app.employee_audit_projection`/`app.employee_emergency_contact_audit_projection` (explicit non-pii `jsonb_build_object` helpers) and using them (or an inline non-pii projection for `request_employee_change`) at all 6 call sites — never `to_jsonb()` of a raw row again. Regression evidence: a new db-test block creates/updates/adds-a-contact/requests-a-change with distinctive pii values and asserts `app.audit_logs.after_value` never contains the corresponding jsonb key.
3. **HIGH — idempotency-key replay compared only `full_name`.** `create_employee_draft`'s idempotency check (both the pre-check and the `unique_violation` retry handler) compared only `full_name`; a replayed call with the same key and name but different `employment_type`/contact/national-id/org-unit/manager/user/number/`intake_source` silently returned the FIRST call's stale data with no error — a "leading-subset, not full-tuple" idempotency defect, the same class this repository's own PRC batches had already found and fixed elsewhere. Live-reproduced before the fix per the finding's own repro steps. **Fixed** with a new shared helper, `app.assert_employee_draft_idempotent_replay`, comparing the FULL 17-field input tuple (including the employee number, resolved via a join to `app.master_records.code`), applied at both call sites. Regression evidence: a same-key/same-`full_name`/different-`employment_type`-and-contact-fields replay now raises `idempotency_key_conflict`; a genuine same-tuple replay still returns the same row unchanged.
4. **MEDIUM — `record_version` disclosed before the authority check on emergency-contact writes.** `update_employee_emergency_contact`/`remove_employee_emergency_contact` both resolved the target contact (unfiltered by RLS, since the function runs `SECURITY DEFINER`), then compared `record_version` (raising `stale_version` with the row's REAL current version) BEFORE calling `app.assert_employee_editable_for_child_crud` (the tenant-membership+`HRS:Edit` check) — a zero-relation Tenant B caller could extract a Tenant A contact's real `record_version`, and on a follow-up call with that version, the real owning employee's `master_record_id`, before ever being told they lack authority. Every other write RPC in the file already folds the not-found/authority check ahead of the version check (decision 9's own stated discipline); only these two regressed. **Fixed** by reordering: resolve the contact (folds `contact_not_found`) → `assert_employee_editable_for_child_crud` (folds tenant-membership + `HRS:Edit`) → THEN `record_version`. Regression evidence: a Tenant B actor with zero hrmemp1 relation gets `employee_not_found` (never `stale_version`) from both functions, and the contact is verified byte-for-byte unchanged.
5. **HIGH — inactive org units were assignable.** `app.enforce_employee_org_unit_shape()` validated `unit_type`/tenant/ancestor-path consistency but never checked `app.org_units.status`, so an employee could be created into, or transferred into, a company/branch/department that had been set `inactive` via `app.set_org_unit_status` — a live, direct violation of section 23's "block ... inactive organization" rule. **Fixed** by adding a `status <> 'active'` check (raising a new `org_unit_inactive` error) for each of the three unit references, inside the same trigger. Regression evidence: both a `create_employee_draft` and a `transfer_employee` against a real, freshly-deactivated company are rejected; the transfer target is verified unchanged.
6. **HIGH — staged import had zero TypeScript service-layer wiring.** `app.validate_employee_import_row`/`app.commit_employee_import_job` existed only as raw RPCs, exercised only via SQL in the db-test file — no `server/mutations/employee.ts` wrapper existed, unlike the PRC-255 precedent (`validateVendorRateImportRow`/`commitVendorRateImportJob`) this migration's own header claims to mirror "exactly." **Fixed** by adding `validateEmployeeImportRow`/`commitEmployeeImportJob` to `server/mutations/employee.ts` (plus matching Zod schemas in `server/contracts/employee/employee.ts`), mirroring `procurement-rate.ts`'s shape precisely, with unit-test coverage. **Not fixed** (disclosed instead, §7): a Server Action/UI trigger surface — because, independently verified, NO PLT-131/132 adopter in this repository has one yet, including the PRC-255 precedent itself (`grep -rln "commitVendorRateImportJob" app/` returns zero matches) — so this is not a regression against an established pattern, and building a first-of-its-kind import UI is a genuinely new capability, not a bounded fix.
7. **LOW — a concurrent/duplicate explicit employee number surfaced as a raw `unique_violation`.** Neither `create_employee_draft`'s `app.master_records` insert nor `commit_employee_import_job`'s per-row equivalent caught `unique_violation`, so a duplicate explicit employee number produced an unclassified driver-level error message with no domain prefix, which `server/mutations/employee.ts`'s `classifyError()` could not map to a specific code. **Fixed** in both places: `create_employee_draft` now raises a friendly `employee_number_conflict` error; `commit_employee_import_job`'s per-row insert now treats the collision as a per-row skip (consistent with the nested `app.employees` `unique_violation` handler immediately below it, and strictly better than the original single-insert behavior, which would have aborted the entire job on one bad row). `employee_number_conflict` added to `EMPLOYEE_KNOWN_MUTATION_ERROR_CODES`. Regression evidence: the existing duplicate-employee-number db-test block now asserts the friendly message text, not merely the bare SQLSTATE.
8. **LOW — `reactivate_employee` always restored `active`, losing `on_leave`.** `app.suspend_employee` correctly allows suspension from either `active` or `on_leave` and records the true `from_status`; `app.reactivate_employee` never consulted it, always writing `active` — an employee suspended while on leave silently lost that state. **Fixed** by reading the most recent `employee_lifecycle_events` row with `to_status='suspended'` for the employee and restoring its `from_status` (falling back to `active` only if none is found, defensively). Regression evidence: create → activate → start leave → suspend → reactivate now asserts the employee reads `on_leave`, not `active`.
9. **LOW — stale summary line in `00_EXECUTION_INDEX.md`.** Line 217's `Summary:` line still read "1 COMPLETED (this kickoff), 1 READY (274), 23 BLOCKED (275–297)" after the same checkpoint's own edit had already updated the §10 table two lines above it to `274=COMPLETED`/`275=READY`. **Fixed**: corrected to "2 COMPLETED (273, 274), 1 READY (275), 22 BLOCKED (276–297)."

### 11.2 Finding disclosed rather than force-fixed

**HIGH — no effective-dated employee identity/lifecycle mechanism (`ISS-2026-065`, OPEN).** Section 13 (line 60), section 17 (line 76), section 18 (line 80), and section 20 (line 91) of Prompt 274 all name "effective dates"/"effective-dated"/"effective version" as required; ADR-0023 Part B's own invariant language ("per effective context") is time-boxed phrasing a permanent, unconditional partial-unique-index structurally cannot represent. The original migration's own decision note claimed this was satisfied because `app.master_records` already carries `effective_from`/`effective_to` — live grep confirmed this is false: those two columns are referenced nowhere outside that one comment, `app.employees` has no effective-dated column of its own, and no write RPC accepts an effective-date parameter. **Disposition:** implementing genuine effective-dating (a real temporal mechanism with "as of" query semantics touching the schema, every lifecycle RPC, and every read projection) is a materially new capability, not a bounded fix within a review pass — attempting it here risked introducing new correctness bugs across the whole surface with no time to prove them as thoroughly as the rest of this checkpoint. **Handling:** the false claim itself IS fixed (the migration's own header comment, this build log, `00_EXECUTION_INDEX.md`, `CARGOGRID_BUILD_STATUS.md`, and `TASK_LEDGER.md` all now accurately describe the lifecycle as point-in-time, not effective-dated) and the gap is filed as `ISS-2026-065` (High, OPEN) in `docs/runtime/KNOWN_ISSUES.md`, owned by a future HRT task before `HRT-293`/`HRT-294`.
