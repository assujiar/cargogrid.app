## 3. Design decisions (summary — full reasoning in the migration's own header)

1. **New table naming/shape**: `app.employee_lifecycle_versions`, a full point-in-time snapshot per version (not a delta), mirroring `app.employee_position_assignments` exactly.
2. **Status enum** (`scheduled`/`active`/`superseded`, not the task's literally-suggested `scheduled`/`active`/`superseded`/`cancelled`): `cancelled` folded into `superseded` since both mean "no longer part of the authoritative timeline" — the one fact every consumer needs. A `materialized_at` timestamp gives a defense-in-depth signal independent of the status label, avoiding the "status column silently drifts stale without a live scheduler" anti-pattern `app.employee_position_assignments`' own header explicitly disclosed avoiding.
3. **Supersede-before-insert**, applied to every write uniformly (immediate, future, and backdated alike) — the direct precedent HRT-279's own self-found "supersede then insert" ordering defect is deliberately avoided repeating. A stale row entirely displaced by the new effective date is marked `superseded` (dates untouched, for audit); a stale row that straddles it is truncated (status unchanged — remains genuinely correct history for the range it still covers).
4. **Backdate authority**: gated at least as strictly as `HRS:Override` (`suspend`/`terminate`/`reactivate` already are, unconditionally — nothing widens for them; `create`/`update`/`transfer`/`archive` gain an explicit, additional `HRS:Override` check reached only on the backdated branch). Mandatory reason on every backdated call.
5. **`create_employee_draft`/`update_employee_draft` always materialize immediately**, regardless of `p_effective_date`'s relation to `current_date` — a deliberate, narrower carve-out from the other 5 RPCs' true future-scheduling, reasoned explicitly (a draft's row unavoidably exists the moment it's created; deferring its own version to the sweep would risk the sweep later clobbering a state the unmodified `submit`/`decide`/`activate` chain had since legitimately advanced past). `p_effective_date` is still recorded for historical-truth/"as of" purposes.
6. **`get_employee_lifecycle_as_of`**: mirrors `get_employee_current_assignment` exactly. `decided_reason` masked to self-or-`HRS:View personal data`, mirroring `get_employee_profile`.
7. **`activate_due_employee_lifecycle_transitions`**: mirrors `activate_due_employee_position_assignments` exactly, including its own established "skip a cyclic row, disclose via a failure audit event, never abort the whole sweep" discipline — proactively re-adopted here (not waited-for-rediscovery). C-21 lock order (`app.employees` then version rows) stated explicitly and verified consistent between the sweep and every write RPC.
8. **HRT-295 composition timing** — the single most safety-critical decision. Immediate/backdated branches of `suspend`/`terminate`/`reactivate` are byte-identical to HRT-295's own shape; `app.transition_user_status` is called ONLY there. A future-scheduled transition never calls it at scheduling time — deferred entirely to the sweep, at the same point the version's fields materialize onto `app.employees`. Both directions live-tested (§4).
9. **Downstream consumers unmodified, confirmed by direct grep**: every "right now" eligibility check (attendance/leave/overtime/payroll) correctly continues to read `app.employees.lifecycle_status` directly — additive, not breaking.
10. **No speculative redesign**: `app.submit_employee_for_approval`/`decide_employee_approval`/`activate_employee`/`link_employee_user`/`start_employee_leave`/`end_employee_leave`, `employee_position_assignments`, payroll effective-dating, and ticket capabilities are all untouched — genuinely out of this task's own bounded scope.

## 4. Live verification of the two riskiest paths (task's own explicit instruction)

Both live-tested against real Platform identity/access state in `scripts/db-tests/hris-employee-master-lifecycle-effective-dating.sql`:

- **Immediate path** (no `p_effective_date`, or one equal to `current_date`): `suspend_employee` couples to `app.transition_user_status('suspended', ...)` in the same transaction; `app.users.status` flips to `suspended` immediately. `reactivate_employee`/`terminate_employee` mirror it (`active`/`revoked`). Regression-proven identical to pre-migration behavior.
- **Future-scheduled path**: `suspend_employee(..., current_date + 5)` leaves `app.employees.lifecycle_status` AND `app.users.status` both completely untouched (live-asserted `= 'active'` immediately after the scheduling call — no premature revocation, the live-availability-bug risk named in the task). A time-travel simulation (the same established `effective_start_date` rewrite trick `hris-organization-position-linkage.sql`'s own maintenance-sweep test uses) then makes the row due; `app.activate_due_employee_lifecycle_transitions` activates it, and only THEN does `app.users.status` flip to `suspended` — proving the security-fix-regression risk (never revoking) is also avoided. The mirror-image reactivate scenario proves the same in the restoring direction. The sweep is idempotent (a second call is a no-op).

Re-verified live after the fix: `anon`/`authenticated` hold zero unintended execute on any of the 11 new/changed function objects; `authenticated`/`service_role` retain exactly their intended grants.
2. **Test-authoring defects in the new dedicated db-test file, fixed before being reported as a result** (mirrors this repository's own "no defect silently fixed without disclosure" discipline, HRT-274 §7.1's precedent): three separate "time-travel simulation" blocks initially moved only ONE side of a truncated-predecessor/successor pair backward in time, producing a spurious `employee_lifecycle_versions_no_overlap` exclusion violation against an ALREADY-correctly-truncated neighbor row untouched by that same shift — a test-fixture arithmetic error, not a migration defect (the underlying supersede-before-insert logic, exercised through the real RPC calls, was correct in every case; only the raw-SQL simulation of "time has passed" needed to shift every affected row's boundary consistently, not just one side of it). ### 11.2 The fix, in one paragraph

`app.record_employee_lifecycle_version`'s supersede-before-insert loop is now **direction-aware**. Bucket (a) — the stale row has not even started as of the new write's date (a still-pending plan) — refuses to silently supersede a differently-reasoned OPEN row unless the new write is terminal (`terminate`/`archive`) or the stale row is genesis lineage (`hire`/`correction`); this is the dangerous direction findings #1/#2 live-proved. Bucket (b) — the stale row already began (ordinary chronological succession) — remains unrestricted regardless of `change_reason` (this is how a normal status timeline advances, and blocking it broke the ordinary `suspend → reactivate` sequence, finding #7), **except** when the stale row is an open-ended TERMINAL state, which a non-terminal write must never be allowed to truncate (finding #3). Both refusals raise a new, explicit `lifecycle_conflict` error (`check_violation`) rather than silently guessing — the caller must resolve the conflicting version explicitly. Independently, `app.activate_due_employee_lifecycle_transitions`' `UPDATE` and `app.get_employee_lifecycle_as_of`'s `p_as_of >= current_date` read are both now `change_reason`-scoped against `app.employees`' own current-state columns (findings #4/#5/#6) — never a blanket full-snapshot trust, on either the write or the read side.
