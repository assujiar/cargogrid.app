## 1. What this checkpoint builds

HRT-282 is the tenth Phase 7 (HRIS/Ticketing) capability, built directly on `HRT-274` (Employee Master, `VERIFIED`), `HRT-278` (Attendance, `COMPLETED`), `HRT-280` (Leave, `COMPLETED`), `HRT-281` (Overtime and Timesheet, `COMPLETED`), and reusing PLT-123 (Approval Engine) and PLT-131/132 (durable job framework) without inventing a second copy of either. It implements: payroll calendar/period; versioned component/formula; employee component assignment; a frozen, per-(period, employee) input snapshot that reconciles TWO previously-competing HRIS time sources (the ISS-2026-074 resolution, §3 decision 2 below); a maker-checker-governed run/batch lifecycle with calculation lines, per-employee results, and review/exception handling; private, per-employee payslips; governed reimbursement and loan lifecycles; and a Payroll-owned Finance handoff that proves — by construction, not merely by header claim — that Payroll never writes to any Finance-owned ledger table.

### Decision 1 — HR Payroll vs Finance ownership, the exact handoff contract (mandatory reading item 6)

**The one cross-module authority gate in this whole checkpoint:** `app.acknowledge_payroll_finance_handoff_batch` requires `FIN:Edit`, never any `HRS:*` action — proven, not merely claimed, live in `scripts/db-tests/hris-payroll.sql` (an HR actor holding full Payroll authority but zero `FIN:Edit` was rejected acknowledging; a `FIN:Edit` holder succeeded).

**Structural proof, not just a header claim:** `scripts/db-tests/hris-payroll.sql`'s own final section runs a live SQL query against `pg_proc.prosrc` for every one of the 4 handoff-facing functions, asserting none contains `insert into app.finance_`, `update app.finance_`, or `delete from app.finance_` anywhere in its own source. ### Decision 4 — RPD-023 MFA gap disclosure (mandatory reading item 5)

No per-action step-up MFA mechanism exists anywhere in this repository yet (`FIN-216`'s own disclosed finding, re-confirmed still true through `HRT-281`). This checkpoint does not build a bespoke one for Payroll alone — doing so would create a second, payroll-only authentication primitive, exactly what this task's own instructions and Prompt 282's forbidden-scope language warn against. ### Decision 5 — Payroll compensation visibility is NOT inherited from org-hierarchy manager scope

The deliberate divergence Prompt 282 §26 requires. Every other Phase 7 capability reuses a self-or-direct-manager-or-`HRS:View` predicate for its person-scoped tables. Payroll's own person-scoped tables use `app.can_view_hris_payroll_row` — self OR the PROTECTED `HRS:View payroll` permission specifically, NEVER plain `HRS:View`, NEVER a manager-of-employee predicate (the same narrower-than-`HRS:View` shape `HRT-281` already established for `app.payroll_time_inputs`, extended here as this capability's own uniform person-scoped visibility rule). **Live-proven**: `scripts/db-tests/hris-payroll.sql` has emp1's direct manager (mgr1, zero `HRS:View payroll` grant) query `app.payroll_run_employee_results`/`app.payroll_payslips` filtered to emp1's own `employee_id` and confirms zero rows returned — while separately confirming mgr1 correctly retains self-visibility into their OWN (zero-value) row, proving the block is specific to the manager-of-report relationship, not an accidental blanket denial.

### Decision 6 — PLT-123 maker-checker is used for RUN FINALIZATION only

Component-version approval, employee-component assignment, reimbursement decision, and loan issuance all use direct `HRS:Approve` gating (the same single-approver-tier, self-approval-blocked shape `decide_overtime_request`/`decide_timesheet_entry` already established) — each is an independently reversible, per-item HR decision, not a batch-wide fund-disbursing event. PAYROLL RUN FINALIZATION is the one decision genuinely irreversible in effect (freezes a period's pay figures, triggers the Finance handoff) and is the step Prompt 282's own main flow (§21) names explicitly. `app.submit_payroll_run_for_finalization`/`app.finalize_payroll_run` route through `app.request_approval`/`app.decide_approval_step` exactly like `app.submit_leave_request`/`app.decide_leave_request` (HRT-280), `entity_type='payroll_run'`. **Live-proven**: self-approval blocked (the maker, who also independently held the approver role for test purposes, was still rejected on their own submission — `approval_self_approval_denied`); a distinct eligible approver succeeded, finalized the run, locked the period, and generated a real payslip; and a genuine two-OS-process concurrent-finalize race on the SAME approval step (§8) serialized cleanly through PLT-123's own mechanism with zero corruption.

## 4. Security/access model

- **RLS:** `payroll_periods`/`payroll_components`/`payroll_component_versions` (non-person-scoped but still compensation-structure-sensitive) are gated on `HRS:View payroll` specifically, NOT plain tenant membership — a deliberate, disclosed strengthening beyond every sibling HRIS capability's own tenant-membership-only metadata policy, since even a period's existence/status can disclose whether/when a compensation cycle ran. Person-scoped tables (`payroll_employee_component_assignments`, `payroll_input_snapshots`, `payroll_run_employee_results`, `payroll_calculation_lines`, `payroll_reimbursement_requests`, `payroll_loans`, `payroll_loan_installments`, `payroll_payslips`) use `app.can_view_hris_payroll_row` (decision 5). The Finance-handoff tables are readable by either side of the boundary (`HRS:View payroll` OR `FIN:View`), never plain tenant membership.
- **RBAC:** every write RPC gates through `app.check_payroll_authority`/`app._check_payroll_component_authority` (both `SECURITY DEFINER` from the start, avoiding `HRT-281`'s own self-found-defect-3 class — a bare `SECURITY INVOKER` wrapper around `app.evaluate_permission` fails inside an RLS policy expression) or, for the one cross-module action, direct `app.evaluate_permission(..., 'FIN', 'Edit')`.
- **Managers do NOT see compensation by hierarchy alone** — decision 5, live-proven §3/§9.
- **Concurrency:** every version-guarded write locks `FOR UPDATE` then re-checks `record_version` at the terminal `UPDATE`; `finalize_payroll_run` re-locks the run row AFTER `app.decide_approval_step` clears (taxonomy C-04, defends a concurrent second finalize attempt racing the same approved step) — live-proven with two genuinely concurrent OS processes, §8.
- **Internal engine functions** (`_resolve_payroll_time_inputs_for_period`, `_build_payroll_input_snapshot_for_employee`, `_calculate_payroll_run_for_employee`, `_generate_payroll_payslip`, `_check_payroll_component_authority`) are granted `service_role` only, never `authenticated` — live-verified in `scripts/db-tests/hris-payroll.sql`.
