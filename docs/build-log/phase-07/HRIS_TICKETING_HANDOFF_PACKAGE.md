### 2.1 The two-track DAG (architecture-level fact every downstream reader needs first)

Phase 7 is **not** one linear 22-capability chain. `docs/build-log/phase-07/00_EXECUTION_INDEX.md` §5 records it as two independent linear sub-chains that reconverge:

```
HRT-273 (kickoff)
   │
   ├──► HR/Workforce track (12 capabilities, strictly sequential)
   │    HRT-274 → 275 → 276 → 277 → 278 → 279 → 280 → 281 → 282 → 283 → 284 → 285
   │
   └──► Ticket track (7 capabilities, planned as independent of the HR track)
        HRT-286 → 287 → 288 → 289 → 290 → 291 → 292
                                                    │
        HR track (…285) ───────────────────────────┤
                                                    ▼
                                          HRT-293 (Sensitive HR/Payroll Data
                                          Controls — the convergence point)
                                                    │
                                                    ▼
                              HRT-294 → 295 → 296 (this doc) → 297 (closure track, serial)
```

**Disclosed deviation from the original plan, load-bearing for any future reader:** the execution index's own §5 (written before HRT-274 existed) predicted the Ticket track would build independent of the HR track, resolving ticket requester/assignee/queue-staff identity through bare Platform-Layer-3 user identity. **HRT-286 did not follow that plan.** By the time HRT-286 ran, HRT-274 (Employee Master) was already `VERIFIED`, so every identity reference on the canonical ticket model (`tickets.requester_employee_id`, `tickets.assignee_employee_id`, `ticket_queue_members.employee_id`, `ticket_watchers.employee_id`) is a real FK to `app.employees(master_record_id)`, resolved via `app.get_self_employee` — the same helper every other Phase 7 capability uses for self-identity, deliberately avoiding a second, ticket-only identity mechanism (`HRT-286.md` decision 3). **The Ticket track therefore genuinely depends on HRT-274, contradicting the diagram the execution index itself still carries** — disclosed there as "a re-evaluation trigger, not a current blocker in substance," and repeated here since a downstream reader tracing dependencies from that diagram alone would draw the wrong conclusion. The three ticket channels layer on top of this: HRT-286 (internal, `channel='internal'`) → HRT-287 (customer, adds a genuinely new Layer-4 `customer_user` requester shape, `channel='customer'`) → HRT-288 (helpdesk, adds a genuinely different tenant-itself-as-requester/Supreme-Admin-as-staff shape, `channel='helpdesk'`) — each an additive `channel` CHECK-widen over one canonical `app.tickets` table, never a second ticket table (§3.2 below).

### 3.5 The field-policy/masking model — canonical reference, summarized not duplicated

- **No employee bank account/tax-ID data exists anywhere in this repository** (verified CLEAN at HRT-293) — `bank_reference_masked` on the payroll finance handoff is structurally always null. Nothing to leak on that surface.
- **RPD-025 retention/legal-hold classification is unbuilt** for every Phase 7 HR/payroll structured-data table (`ISS-2026-091`, OPEN Medium — see §5/§7).

### 3.7 API/service-layer conventions

- **No REST/GraphQL surface exists for any Phase 7 capability** (§3.2 above) — identical posture to every prior phase. Every page reads/writes through a Server Component/Action calling the `server/queries/`/`server/mutations/` layer directly, which in turn calls the RPC.
- **`server/contracts/<domain>/<domain>.ts`** — Zod input/output schemas, one file per domain, each header-commented with its owning migration and RPC list (e.g. `server/contracts/employee/employee.ts`: *"Mirrors `supabase/migrations/20260730830000_create_hris_employee_master.sql`'s `app.employees`/... shapes and their RPCs. Follows the exact directory convention PRC-251 established."*).
- **`server/queries/<domain>.ts`** — thin, typed read wrappers (list/get/export RPCs), each paired with a `.test.ts` file.
- **`server/mutations/<domain>.ts`** — thin, typed write wrappers around every lifecycle/decision RPC, each exposing an enumerated `*_KNOWN_MUTATION_ERROR_CODES` array `classifyError` uses to turn a raw Postgres error code into a typed, UI-safe error. **A real, disclosed gap in this convention was found and fixed at HRT-294** (`ISS-2026-114`, RESOLVED): five `harden_*_review_fixes` migrations each added a new `raise exception` error code to an existing RPC without the corresponding TS array being revisited, so `classifyError` silently fell through to the generic `"mutation_failed"` — closed by five one-line additive edits, zero logic change.
- **Query wrapper is a pass-through, never a second authority layer:** every `server/queries/*.ts`/`server/mutations/*.ts` wrapper matches Finance's own established "RPC owns authority" convention — no query wrapper adds or removes a check the underlying RPC doesn't already enforce (`HR_PAYROLL_FIELD_POLICY_MATRIX.md` §2).
- **Two-client architecture, unchanged:** every domain uses the same `authenticated` (RLS-scoped) vs. `service_role` (internal-engine-function-only) client split every prior phase established — confirmed for Payroll's internal engine functions (`_resolve_payroll_time_inputs_for_period`, `_build_payroll_input_snapshot_for_employee`, etc., `service_role`-only, live-verified in `hris-payroll.sql`) and for Ticketing's `_create_ticket`/`_is_ticket_requester_party` internal helpers identically.

### 5.3 `ISS-2026-105` deserves prominence beyond a table row — the one Critical this phase produced

**A real, live-verified, exact monetary miscalculation reached a FINALIZED payroll run and its Finance handoff with zero warning anywhere.** `app._resolve_payroll_time_inputs_for_period`'s original exclusion logic covered only timesheet-entry-derived work_dates; a work_date covered ONLY by an approved overtime request (no timesheet entry) was counted **twice** — once via its own full raw attendance-session span inside `regular_minutes`, again via `overtime_weekday_minutes` from the approved overtime request. Live-reproduced: one employee, one overtime day, a **125,000 IDR overstatement** that propagated unchanged through `calculate_payroll_run` → `finalize_payroll_run` → the real Finance disbursement handoff, all three internally "reconciled" to the same wrong number. **The first HRT-295 fix (excluding the day entirely) overcorrected** — independently live-reproduced by all four Tier C review lenses as a **450,000 IDR understatement** for the identical scenario (a genuinely worked, non-overtime portion of the day was now paid as zero). **Resolved for real** by a second, additive migration (`20260731280000`): the attendance-fallback query now subtracts the day's own real, already-claimed `approved_minutes` from the raw span, floored at zero — never a second, independent "standard workday minutes" config value, and unconditionally double-count-safe including the full-day-holiday-overtime edge case the original "capping" alternative would have mishandled. Live-reconfirmed on three independent fixtures (different tenant/rate/dates each). **Any future payroll-time-input change must re-read this fix's own migration header before touching `_resolve_payroll_time_inputs_for_period` again** — this function has now been the site of a Critical defect, an interim fix that introduced a large-magnitude opposite-direction defect, and a final correct fix, all inside one checkpoint.
