## 3. Scope decisions — exact, disclosed

1. **Root-cause fix chosen for Finding B over a central-redaction alternative.** `app.capture_audit_event`'s `p_reason` parameter is never redacted for ANY caller in this repository (only `before_value`/`after_value` jsonb payloads pass through `app.redact_audit_payload`). A central fix (suppress `p_reason` inside `capture_audit_event` itself, keyed on `p_resource_type`) was considered and rejected: it would touch a single foundational function used by every domain (Finance, Procurement, Commercial, Operations, Platform), requiring re-verification far outside this checkpoint's own Phase-7-HR-scoped mandate, and departs from this batch's own established convention (HRT-291's `app.ticket_escalation_audit_projection`: fix at each call site, never a shared redaction hook). Every one of the 37 fixed call sites instead now passes `null` for the reason argument — the real value already lives, exactly once, in that capability's own properly access-controlled domain table.
2. **Live verification over trusting the audit's own citations.** Every one of the ~40 functions this checkpoint touches was extracted via `pg_get_functiondef` against a fully-migrated, from-scratch database (all 182 pre-existing migrations applied) BEFORE being amended — not reproduced from the migration file that originally created it. This caught a real, load-bearing discrepancy: the audit's own Finding B citation of `app.start_employee_leave` no longer matched that function's current live body (superseded by a Batch 278-280 refactor into a thin wrapper around `app._transition_employee_leave_status`) — the REAL live leak was in the shared engine, not the wrapper the audit named. Blindly reproducing the audit's stale citation would have shipped a no-op fix while leaving the actual vulnerable code path open.
3. **A systematic sweep beyond the audit's own named sites, bounded to the SAME capability set the audit already scoped.** A repository-wide grep of every function's live body for the `'success', p_<param>` shape (the universal convention this codebase uses for `capture_audit_event`'s positional reason argument), filtered to HR/payroll table names, found 8 further Phase 7 HR sites not individually named by the audit (§7's own self-found-defects list) plus 5 further tables sharing Finding A's exact raw-table-grant shape (migration 3). Both sweeps were bounded to Phase 7 HR/payroll — genuinely out-of-domain hits (Finance/Procurement/Commercial/WMS sites using the identical `'success', p_reason` shape, and `job_vacancies`' own hold/close/cancel reasons, which are operational REQ-level text, not personal data about an identifiable individual) were deliberately left untouched and not further investigated, matching this checkpoint's own bounded charter.
4. **One self-found gap deliberately NOT fixed at the same layer: `app.cancel_approval_request` (PLT-123).** Discovered while writing the onboarding regression test (§7 self-found defect 2): the shared, cross-domain approval-cancellation primitive every "cancel with reason" HR function calls internally independently logs the identical raw reason under its own `action='cancel_approval_request'` audit row. This is Platform Core infrastructure shared by Finance/Commercial/Procurement/HR, not owned by this checkpoint's Phase-7-HR mandate — fixing it would require re-verifying every OTHER domain's own approval-cancellation call sites, a genuinely larger-blast-radius change. Disclosed as `ISS-2026-093`, not fixed.
5. **Registry additions (Finding C) bounded to what the audit explicitly named**, not extended to every unregistered-but-masked field this checkpoint's own Finding B sweep touched (job application/interview/onboarding-task/position-assignment reason columns are already correctly column-restricted and RPC-masked, but remain unregistered) — disclosed as a bounded registry-editing scope in the matrix deliverable's own §5, not silently claimed complete.
6. **Finding E (RPD-025 retention/legal-hold) and Finding F (RPD-023 step-up MFA) disclosed, not fixed** — both explicitly named Medium/Low in the audit, both require either a genuine multi-table schema addition (E) or a platform-wide mechanism this repository does not have anywhere yet (F, already disclosed since HRT-282), both outside this checkpoint's own Critical/High-focused, migration-plus-docs-bounded mandate. §5 of `HR_PAYROLL_FIELD_POLICY_MATRIX.md` and `KNOWN_ISSUES.md` `ISS-2026-091` carry the full reasoning.
7. **File count (16) exceeds the "normally 5-15" guidance by one file**, consistent with the task's own explicit "if audit findings would require far more than that, triage: fix Critical/High for real" instruction — every one of the 3 migrations is the expected corrective-fix mechanism (not scope creep), and 6 of the 11 edited files are db-tests providing regression evidence for the fixes rather than production surface expansion.

## 5. Self-found defects fixed before finishing

1. **`app._transition_employee_leave_status` — the REAL live site behind the audit's own stale `app.start_employee_leave` citation** (§3 item 2). Found by extracting the CURRENT live body via `pg_get_functiondef` rather than trusting the original migration text; fixed in the same migration as `app.start_employee_leave` itself.
2. **8 further Finding-B-shaped sites in the same HR domains the audit already scoped**, found by a systematic `'success', p_<param>` sweep against every function's live body: `app.decide_employee_position_assignment` (2 call sites), `app.cancel_employee_position_assignment`, `app.waive_attendance_exception`, `app.waive_onboarding_task`, `app.request_onboarding_access_revocation`, `app.cancel_conflicting_schedule_assignment_for_leave`, `app.record_offer_response`, `app.load_opening_leave_balance`. Two of these (`app.record_offer_response`/`app.load_opening_leave_balance`) were initially drafted from memory rather than the verified extraction and contained real transcription errors (wrong authority-check action, wrong status-transition guard, a missing optimistic-lock predicate) — caught by re-extracting and diffing against the actual live body before the migration was ever applied anywhere, corrected before finishing.
3. **A genuine implementation bug in this checkpoint's OWN first draft of `app.get_employee_lifecycle_history`'s fix**: a `select (a, b, c)::app.employee_lifecycle_events from …` row-constructor cast inside `RETURN QUERY` against a `RETURNS SETOF <composite>` function is rejected by Postgres ("Returned type … does not match expected type … in column 1") — a single composite-typed output column, not the flattened column list `RETURN QUERY` requires. Caught live, on the very first adversarial probe run against a real database (§9), before this migration was considered done. Fixed with a plain flat column list, identical masking, identical unchanged signature.
4. **A genuine implementation bug in this checkpoint's OWN first draft of `supabase/migrations/20260731200000`**: a bare `revoke select (<col>) on app.<table> from authenticated` against a table whose ORIGINAL grant was a plain whole-table `grant select on app.<table> to authenticated` is a documented Postgres no-op (column-level and table-level ACLs are tracked independently; there is no column-level ACL entry to remove). Caught live via `has_column_privilege` returning `true` after the revoke ran with no error at all. Corrected to the same revoke-whole-table-then-regrant-explicit-column-list shape `app.employee_lifecycle_events`'s own fix (`20260731180000`) already used correctly for the identical starting condition.
5. **Two overly-generic regression-test strings that produced false-positive collisions with unrelated, correctly-non-sensitive fixture data** in `hris-onboarding-offboarding.sql` (`'reorg cancelled the exit'` — actually a real, separate, disclosed leak in `app.cancel_approval_request`, §3 item 4/`ISS-2026-093`) and `hris-shift-roster-scheduling.sql` (`'no longer needed'`, coincidentally reused as a fixture string by ~9 unrelated capabilities' own db-tests, e.g. `app.release_inventory_reservation`, `app.set_warehouse_status`). Both caught by actually running the new assertions live against the full test-file sequence (not merely in isolation) before finishing; both fixed by scoping the check to the specific `action` name each fix targets rather than a bare reason-string match.
6. **`PAYROLL_REGISTRY` silently excluded from `check-registry.ts`'s own `REGISTRY` constant** (§2/§4 above) — found the moment the new HRS adoption gate was first exercised (it reported `HRS:View payroll` as unclassified despite `PAYROLL_REGISTRY` already naming it five times over).
