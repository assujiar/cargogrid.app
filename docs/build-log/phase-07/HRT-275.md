## 3. Source/config decisions (disclosed, not left implicit)

### 3.1 ADR-0023 Part A implemented exactly as decided

`app.org_units.unit_type` gains `team` as an additive fifth value; `app.enforce_org_unit_parent_shape()` gains one new branch (`team`'s parent must be `department` or `business_unit`; `team` is a leaf type and may never itself be a parent — a genuinely new universal-leaf guard, since no prior type was ever forbidden as a parent outright). This is this checkpoint's own chartered implementation of an already-ratified decision, not a re-litigation. Regression-proven: `scripts/db-tests/org-hierarchy.sql`'s own pre-existing assertions (company/branch/department/business_unit shape, move/cycle/deactivation guards) run unmodified against the widened function and still pass.

### 3.2 Position/grade are HR-governed, tenant-scoped catalogue data — not routed through `app.master_records`

Unlike vendor/driver/employee, a position/grade is structural configuration describing a slot in the org chart, not an operational actor identity needing merge/dedupe/lifecycle across external sources. `app.positions`/`app.position_grades` mirror `app.org_units`'s own simpler, directly-tenant-scoped shape (code+tenant unique, `record_version`, `active`/`inactive` status lifecycle) rather than the `master_records`-extension shape vendor/driver/employee use. Organization write itself stays Platform-governed and completely unchanged — this migration adds no new grant, policy, or RPC touching `app.org_units` write paths; `app.create_org_unit`/`app.move_org_unit`/`app.rename_org_unit`/`app.set_org_unit_status` remain `service_role`-only, exactly as PLT-109 left them.

### 3.3 `app.employees.position_id` — additive current-pointer, `position_title` untouched

Per HRT-274's own build log §10 recommendation. `position_id` is nullable, references `app.positions(id)`, and is synced exclusively by `app.decide_employee_position_assignment` (immediate case, `effective_start_date <= current_date`) and `app.activate_due_employee_position_assignments` (future-dated case, once due). It is never hand-edited by HRT-274's own `app.update_employee_draft`/`app.transfer_employee`, which remain valid, unchanged, free-text-only paths for a position-less employee.

### 3.4 A genuinely new table, not a mutable column — `app.employee_position_assignments`

Effective-dated history cannot live in a single mutable column (section 13's own explicit reasoning). Every transfer/promotion/hire/secondary-assignment is a new row; a prior row's substantive fields are never mutated (only `status`/`decided_*`/`effective_end_date` on the SAME row ever change, via the decide/cancel RPCs). `app.employees`'s own position/manager/org-unit columns are a best-effort, eagerly-synced convenience cache — the assignment table is the source of truth for point-in-time-correct reads (`app.get_employee_current_assignment`, `p_as_of`-parameterized, reads `validity_range` directly and is always correct even before any sync/sweep has run).

**Two real, DB-enforced `btree_gist` EXCLUDE constraints** (mirroring `app.vendor_rate_versions_no_ambiguous_overlap`, PRC-255, `20260730620000`) — not merely application-layer discipline:
- `employee_position_assignments_no_primary_overlap`: an employee may never hold two overlapping ACTIVE primary assignments.
- `employee_position_assignments_no_duplicate_secondary`: an employee may never hold two overlapping ACTIVE secondary assignments to the SAME position (different concurrent secondary positions remain legal by design).

`status` deliberately uses only two temporally-static-enough values plus two decision outcomes (`pending_approval`/`active`/`rejected`/`cancelled`) rather than a separately-drifting `scheduled`/`active`/`ended` state machine — "is this assignment in effect right now" is always answered by `validity_range @> current_date` at read time, so no live scheduler is required to keep a status column fresh. The one case that DOES need a real actor-driven transition — withdrawing a not-yet-effective proposal or approved-but-future assignment — is `app.cancel_employee_position_assignment`, gated so an already-effective assignment can never be cancelled retroactively (section 23's "keep the current effective assignment intact").

### 3.5 Two-step propose/decide workflow — zero new `app.permissions` rows

`app.propose_employee_position_assignment` (HRS:Edit) creates a `pending_approval` row; `app.decide_employee_position_assignment` (HRS:Approve) approves (re-validating position status, manager-cycle, and capacity authoritatively, closing the prior open-ended primary predecessor, syncing `app.employees`' cache if already effective) or rejects (terminal, mandatory reason, prior active assignment left completely untouched). Both `HRS:Edit` and `HRS:Approve` were already seeded at PLT-111 (`20260716103445:61-63`) — this migration adds no new permission action at all, closing the task brief's own "you likely need Approve... if not already sufficient" question: it already was. `app.preview_employee_position_assignment_impact` is deliberately callable standalone, before any proposal exists, matching section 21's own preview-before-propose ordering.

### 3.6 Capacity and overlap are both real guards, validated at the correct point in the flow

Overlap (section 25) is enforced by the EXCLUDE constraints above, which only apply to `status='active'` rows — a proposal does not yet commit any real headcount/timeline. Capacity (section 25 "capacity", section 23 "position over-capacity") is validated at DECISION (approval) time — matching section 25's own literal "before activation" framing — under a position-scoped `pg_advisory_xact_lock` (mirroring `app.commit_vendor_rate_import_job`'s own job-scoped-advisory-lock precedent), so two racing approvals against the same position cannot both pass the count check before either commits. A same-position correction/promotion (the employee's own existing occupancy of THIS SAME position being closed and immediately replaced) does not double-count its own soon-to-be-closed predecessor against the position's own capacity — a real bug caught and fixed during this checkpoint's own db-testing (§6 below), not shipped as an oversight.

### 3.7 Manager-cycle prevention — HRT-274's own disclosed placeholder decision, formalized without a materialized closure table

HRT-274's build log §10 explicitly left this decision to this checkpoint. **Decision: keep `app.assert_no_employee_manager_cycle`'s bounded 200-hop chain walk, unchanged and reused directly** (not reimplemented), rather than building a materialized reporting-line transitive-closure table. Reasoning: (a) real organizational reporting depth is bounded by a small constant in every plausible tenant — 200 hops is already two orders of magnitude beyond any realistic org depth; (b) a materialized closure table requires a rebuild-on-every-manager-change trigger cascade with real storage/write-amplification cost, for a check that already runs in O(depth) time with a single indexed-column walk; (c) `app.employee_position_assignments` already gives manager-chain HISTORY for free via its own effective-dated rows — a materialized-closure alternative would duplicate information this table already carries. The chain walk is reused at both `app.propose_employee_position_assignment` (early UX feedback) and `app.decide_employee_position_assignment` (the authoritative gate, re-checked against fresh state) — cheap defense in depth, not a new mechanism. `app.get_employee_manager_chain` (the new "hierarchy read" RPC, section 14) reads the CURRENT chain from `app.employees.manager_employee_id`, matching `app.list_my_team_employees`'s own established precedent.

### 3.8 Impact preview computes real data only

Direct repository inspection this checkpoint confirmed approval-queue routing has no org-unit-scoped concept anywhere in this repository (`app.evaluate_permission` is tenant+module+action only), and Payroll (Prompt 282) / Ticketing (Prompt 285+) tables do not exist yet. `app.preview_employee_position_assignment_impact` computes every signal that genuinely exists today (target position/grade/org path via `app.resolve_org_unit_lineage`, capacity remaining, would-be-cyclic manager chain, this employee's own real direct-report count, real pending change-request/duplicate-candidate counts) and returns an explicit `downstream_disclosure` text field naming the not-yet-integrated systems, rather than inventing a placeholder number for any of them.

### 3.9 No compensation/salary/pay-band field anywhere

Section 13's own scope is position/grade STRUCTURE. `app.position_grades.rank` is a bare ordering integer, never a pay figure. `scripts/data-classification/registry.ts`'s `HRS_REGISTRY` needed no new entry — no column on any table this migration creates is PII- or payroll-classified, confirmed by re-running `data-classification:check` clean with zero new registry rows.

### 3.10 Deliberately out of scope, disclosed as `ISS-2026-066`

No staged-import (PLT-131/132) crosswalk for position/grade/assignment rows (section 19's own bulk-migration capability, a genuinely new, unrequested-here build); no bulk/multi-employee reorganization wizard (every RPC and the UI wizard are single-employee); no live cron/scheduler invokes `app.activate_due_employee_position_assignments` automatically (no scheduler infrastructure exists anywhere in this repository yet, the same standing `ISS-2026-015` gap); no Playwright/axe-core E2E spec for the three new page families. Full detail and severity/owner assignment in `ISS-2026-066`.

## 4. Security/access model

- **RLS:** `app.position_grades`/`app.positions`/`app.employee_position_assignments` all carry the hardened default-deny form identical to HRT-274's own (`app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id)) or app.is_supreme_admin()`), proven live against both `anon` (schema-privilege denial) and a `customer_user`-layer principal (zero rows, same-tenant) in `scripts/db-tests/hris-organization-position-linkage.sql`.
- **RBAC:** every write RPC gates through `app.evaluate_permission(actor, tenant, 'HRS', action)`, which itself asserts caller-is-session-identity internally (unchanged, wired at `20260730440000`, covering every RPC that reaches it). The two RPCs that do not reach `evaluate_permission` — none in this migration; unlike HRT-274, every RPC here (including the two "self-service-ish" reads, `app.get_employee_position_assignment_history`/`app.get_employee_current_assignment`) is HRS:View-gated, HR-scoped data, not identity-match-gated. The one genuinely self-service read, `app.get_my_employee_position_assignment_history`, is identity-match-gated exactly like HRT-274's own `app.get_my_employee_profile`, with its own explicit `app.assert_actor_is_session_identity` call.
- **No column-restricted grants needed.** Unlike `app.employees`, none of the three new tables carry a classified column (decision 3.9), so plain `select` to `authenticated` (RLS-row-scoped) is correct and sufficient — mirroring `app.org_units`'s own established precedent rather than HRT-274's PII-driven column restriction.
- **Concurrency (row lock + repeated version predicate + advisory lock for capacity):** every write RPC locks its target row(s) first, folds a non-member caller into the same not-found branch, checks authority before `record_version`, and repeats the version predicate in the terminal `UPDATE`'s own `WHERE` clause — the same fully-hardened shape HRT-274 itself used from day one. `app.decide_employee_position_assignment`'s approve path additionally takes a position-scoped `pg_advisory_xact_lock` before its capacity count, and translates both `exclusion_violation` and `deadlock_detected` (a GiST EXCLUDE insert under real contention can legitimately surface either sqlstate for the identical business conflict — PRC-255's own established two-sqlstate handling) into the same friendly `assignment_overlap` error.

## 6. Real defects found and fixed during this checkpoint's own db-testing

Found and fixed before this checkpoint's own commit, via iterative `psql`-driven adversarial testing (not shipped, then found later):

1. **Capacity double-counted an employee's own soon-to-be-closed predecessor on a same-position correction/promotion.** The original ordering computed the capacity headcount BEFORE looking up the predecessor to close, so a capacity=1 position could never process a legitimate "same position, corrected grade/manager" re-assignment for the employee already occupying it (their own still-active predecessor row counted against their own new request). Live-reproduced in the "capacity" test block. **Fixed** by reordering: look up the predecessor first, then compute headcount via `app.count_position_active_primary_headcount`'s new `p_exclude_assignment_id` parameter, excluding the predecessor only when it occupies the SAME position as the new proposal (a transfer to a genuinely different position is never given this exclusion, correctly).
2. **A bare `manager_employee_id` reference in `app.get_employee_manager_chain`'s own chain-walk loop was genuinely ambiguous against the function's own `RETURNS TABLE` output column of the identical name** — the exact class of bug HRT-274's own build log §7.1 already found and fixed three times in different functions, reproduced live again here by this checkpoint's own db-test suite. **Fixed** by table-aliasing the reference (`select e.manager_employee_id ... from app.employees e where e.master_record_id = v_current`).
3. **Test-fixture-only:** an early UUID range chosen for the two-tenant fixture (`...0000027501`-`...0000027507`) collided with `scripts/db-tests/finance-invoice.sql`'s own already-claimed range — caught immediately by `pnpm run db:test`'s own `ON_ERROR_STOP` behavior on the very first run; renumbered to `...0000027511`-`...0000027529`, a verified-free range.
4. **Test-fixture-only:** three `create_position_grade`/`create_position` calls in the fixture setup and CRUD test block used the fixture's `tenant_admin` actor, who holds no `HRS` role in this fixture (only the `staff` actor does) — `insufficient_authority` on the very first setup call. **Fixed** by using the `staff` actor for every `HRS:Create`/`HRS:Edit` action, matching HRT-274's own fixture's identical actor-role separation.

No CRITICAL or HIGH finding this checkpoint — the RLS/RBAC/audit/masking discipline HRT-274's own review round hardened is reused verbatim (no new PII/masking surface exists here to regress), and the capacity/overlap/cycle guards were designed with PRC-255's own overlap-handling precedent in hand from the start rather than retrofitted after a live failure.
