## 1. What this checkpoint builds

HRT-281 is the eighth Phase 7 (HRIS/Ticketing) capability, built directly on `HRT-274` (Employee Master, `VERIFIED`), `HRT-278` (Attendance, `COMPLETED`), `HRT-279` (Shift/Roster/Scheduling, `COMPLETED`), and `HRT-280` (Leave/Permit/Business Trip, `COMPLETED`). It implements overtime request/approval (planned and emergency-after-the-fact), actual-time reconciliation against `HRT-278`'s own `app.attendance_sessions`, manual/import/attendance-derived timesheet entry against eligible schedule/job/shipment references, server-authoritative configurable rounding/minimum/daily-cap/weekly-cap rules, a period definition + per-employee summary approve/lock/reopen workflow, and ONE versioned, content-based-idempotent payroll-input handoff record per (period, employee) — emitting approved TIME and classification only, zero rate/amount/currency columns anywhere, since payroll calculation itself is `HRT-282`'s (Prompt 282, not yet built) responsibility. Requested, actual, eligible, and approved/paid time are kept as distinct, versioned, traceable values on every row — never collapsed into one mutable field.

## 3. Source/config decisions (disclosed, not left implicit)

All numbered decisions are recorded in the migration's own header comment (`supabase/migrations/20260730980000_create_hris_overtime_timesheet.sql:1-243`) — summarized here, including two decisions (18, 19) added during this checkpoint's own Tier B self-review:

1. Requested/actual/eligible/approved/paid time are distinct, versioned, traceable columns on `app.overtime_requests`/`app.timesheet_entries` — never collapsed into one mutable value. `requested_minutes` is a generated column from the requested start/end; `reconciled_actual_minutes` is set only by reconciliation against Attendance; `eligible_minutes`/`eligible_classification` are set only by `decide_*`; `approved_minutes` defaults to eligible but may be reduced (never increased) by an explicit override, CHECK-enforced (`approved_minutes <= eligible_minutes`).
2. One rounding/cap policy surface (`overtime_policies`/`overtime_policy_versions`) governs BOTH overtime and timesheet eligibility computation — never two independently-configured rule sets that could silently drift apart.
3. `app.attendance_sessions` (`HRT-278`) is reused read-only for reconciliation evidence; no bind/harden migration was needed since this checkpoint only reads, never writes, that table.
4. Baseline-workday preference: schedule assignment (`HRT-279`) when one exists, else the policy version's own `standard_workday_minutes` fallback — never a third, independent baseline source.
5. Direct propose/decide (submit/decide), NOT PLT-123-routed — overtime/timesheet decisions are routine, high-volume, single-approver-tier workflows, matching `HRT-278`/`HRT-279`'s own established shape, distinct from Leave's PLT-123 routing (`HRT-280` decision 6), which exists for leave's own multi-step, policy-varying routing needs.
6. `app.round_minutes` is the ONE rounding function every eligibility computation uses (nearest/up/down against a configurable increment) — never reimplemented inline.
7. Caps/thresholds/rounding/eligibility are entirely server-computed inside `decide_overtime_request`/`decide_timesheet_entry` — zero client-side calculation authority.
8. Operations references (`job_order_id`/`shipment_order_id`) are authorized independently via `app._validate_overtime_timesheet_operations_reference` — a minimal, existence-and-tenant-scope-only check that never selects a financial/customer/quotation column from either table, so this capability cannot leak Operations data it has no scope to reveal.
9. Weekly-cap enforcement is `pg_advisory_xact_lock`-serialized, keyed on `(tenant, employee, ISO year-week)`, mirroring `HRT-280`'s own identical shape for its balance debit — **live-reproduced with two genuinely concurrent OS processes, §8**.
10. Locked/approved records change only through a governed reopen, never silent overwrite — period reopen (`HRS:Override`) and summary reopen (`HRS:Override`) are DISTINCT, separately governed actions; reopening a period does NOT silently revert an already-approved summary.
11. The payroll-input handoff is content-based idempotent: no caller-supplied idempotency key — `generate_payroll_time_input` always recomputes fresh from the current approved rows, compares the result against the current active version's totals, and returns the existing version unchanged if identical, else supersedes it with `version + 1`. Immune to the C-01 idempotency-key-reuse class by construction (there is no key to reuse).
12. Pay rate/value fields are withheld from anyone without payroll permission — structurally: `app.payroll_time_inputs` carries ZERO rate/amount/currency columns anywhere (grep-verified, §6/§9), gated additionally by `HRS:View payroll` at the RLS layer via the new `app.can_view_hris_payroll_time_input_row` helper.
13. Break-time deduction (`unpaid_break_minutes`) is a real, configurable, per-record field on both `overtime_requests` and `timesheet_entries`, subtracted before rounding/cap application.
14. Multi-job timesheet allocation is real: `app.timesheet_entries` carries NO uniqueness on `(employee_id, work_date)` — several entries may exist for the same workday across different `job_order_id`/`shipment_order_id` references (live-tested, §9). `overtime_requests` DOES carry a partial-unique active-slot index — one active (draft/pending/approved) request per employee-workday.
15. Timesheet-entry reconciliation against Attendance is informational-only (never blocks approval); overtime approval hard-blocks on missing/mismatched attendance evidence UNLESS the decider also holds `HRS:Override` (exception flow) — a deliberate asymmetry: overtime is exceptional pay that should default to evidence-backed, routine time entry should not.
16. Overtime approval's hard-block re-reconciles with the FRESHEST evidence at decide time (not the submit-time snapshot), since evidence can arrive between submit and decide.
17. RBAC: zero new `app.permissions` rows — the twelve pre-seeded `HRS` actions (View/Create/Edit/Delete/Approve/Export/View payroll/View personal data/Reject/Import/Download/Override) cover every write. Blast-radius-matched: period/summary reopen and the attendance-override approve path both require `HRS:Override`, never merely `HRS:Edit`/`Approve`.
18. Self-approval is blocked on every governed decision (taxonomy C-18): `decide_overtime_request`, `decide_timesheet_entry`, `approve_timesheet_period_summary` AND `reject_timesheet_period_summary` all block an actor deciding their own request/entry/summary even when they also hold the gating permission — designed in from the start, and, for the reject counterpart, closed by this checkpoint's own Tier B self-review before commit (§7 item 8).
19. "Revision/resubmission" (spec §22) is create-new, never in-place edit, once a request/entry has been decided — a rejected `overtime_requests`/`timesheet_entries` row is a terminal leaf (`submit_*`/`update_timesheet_entry_draft` all require `status='draft'`, no path back from `rejected`), deliberately, per decision 1's own "never collapsed into one mutable value" principle applied to a decided record's own history. The real resubmission path is create-a-new-request/entry for the same work_date — live-verified, §7 item 10, §9. The period-SUMMARY layer is the one place true in-place resubmission exists (a recomputed rollup, not an independent source-of-truth record).

## 4. Security/access model

- **RLS:** `overtime_policies`/`overtime_policy_versions`/`timesheet_periods` (non-person-scoped, policy/period metadata) use a tenant-membership-only SELECT policy, matching `HRT-278`'s own `attendance_policies` shape. `overtime_requests`/`timesheet_entries`/`timesheet_period_summaries` (person-scoped) reuse `app.can_view_hris_person_scoped_row` UNCHANGED from `HRT-278`'s own fix migration — never reinvented. `payroll_time_inputs` uses a NEW, dedicated `app.can_view_hris_payroll_time_input_row(tenant_id, employee_id, auth_user_id)` (self OR `HRS:View payroll` specifically) rather than the reused person-scoped helper, since payroll-input visibility is intentionally a NARROWER bar than plain `HRS:View`.
- **RBAC:** every write RPC gates through `app.evaluate_permission(actor, tenant, 'HRS', action)` at the correct blast-radius bar, or (for pure self-service create/submit/cancel) `app.assert_actor_is_session_identity` plus `app.has_active_tenant_membership` with the acting employee resolved via `app.get_self_employee` — never a caller-supplied `employee_id`.
- **Managers see their effective team** by reusing the IDENTICAL self-or-direct-manager-or-`HRS:View` predicate `app.list_attendance_sessions`/`app.list_schedule_assignments`/`app.list_leave_requests` each independently compute — never a second manager-hierarchy mechanism.
- **Column-restricted grants**: `authenticated` has no column-level SELECT on `reason`/`decided_reason`/`cancel_reason` (`overtime_requests`) or `notes`/`decided_reason`/`cancel_reason` (`timesheet_entries`); `service_role` has full access. Verified live via `has_column_privilege`, both directions.
- **`app.payroll_time_inputs` carries zero rate/amount/currency columns** — structurally impossible to leak pay VALUE through this capability (word-boundary-regex-verified against `information_schema.columns`, §9); it emits eligible TIME and classification only.
- **Internal engine functions** (`_create_overtime_request`, `_reconcile_overtime_request_actual`, `_create_timesheet_entry`, `_reconcile_timesheet_day`, `_compute_timesheet_period_summary`, `_generate_payroll_time_input`, `_validate_overtime_timesheet_operations_reference`) are granted `service_role` only, never `authenticated`.
- **Concurrency:** the weekly-overtime-cap race is closed by `pg_advisory_xact_lock`, keyed `(tenant, employee, ISO week)` — **live-reproduced with two genuinely concurrent OS processes** (§8). The payroll-input handoff race is closed by a second, independent `pg_advisory_xact_lock` keyed `(period, employee)`.

## 7. Self-found defects (found and fixed during this checkpoint's own adversarial testing, before commit)

Found via iterative, honest `psql`-driven testing against a live disposable Postgres 16 database, including a real two-process concurrency race and a mandatory Tier B taxonomy walk — not shipped and found later. Ten production-code items plus one grouped test-fixture-bug item:

1. **Missing touch-row trigger — `record_version` never advanced on UPDATE for any of the 6 versioned tables**, making every optimistic-lock check structurally inert (a stale-version check could never actually fire, since the version literally never changed after the initial INSERT). Discovered when `decide_overtime_request` accepted a stale `p_expected_version` unconditionally. 2. **Version-bump self-collision (4 call sites) — an internal reconcile/compute call's OWN UPDATE (now correctly bumping `record_version` after fix #1) collided with that SAME function's own terminal versioned UPDATE**, producing a false `stale_version` error on every legitimate call. **Live-reproduced**: `decide_overtime_request` failed "expected version 2 but found 3" on a completely untouched-by-any-external-process row. **Fixed** in `submit_overtime_request`, `decide_overtime_request`, `submit_timesheet_entry`, `approve_timesheet_period_summary` by either reordering the function's own status-flip UPDATE to run FIRST (using the caller's still-valid original `p_expected_version`, safe since the row has been locked since the top `SELECT ... ## 8. Live concurrency evidence (real OS processes, not reasoned about)

Required by this task's own instructions ("adversarially test your own migration with real psql sessions... concurrency on overlap/cap enforcement"), executed against a disposable database (`cargogrid_race_ot`, since dropped) seeded with a minimal, isolated fixture (one tenant, one employee, a published overtime policy with `weekly_overtime_cap_minutes = 120`, two DRAFT-then-submitted overtime requests already sitting at `pending_approval` for two different days in the SAME ISO week, each independently eligible for 90 minutes before the weekly cap is applied):

- **C-04/decision-9, weekly-cap race on the advisory-lock-serialized sum-and-compare inside `decide_overtime_request`.** Two genuinely concurrent `psql` OS processes simultaneously called `app.decide_overtime_request(..., 'approve', ...)` on the two different pending requests for the same employee's same ISO week — both would independently compute `eligible = 90` (under the DAILY cap) if the WEEKLY cap were evaluated against a stale, unlocked read of "how much is already approved this week," since neither request's own row lock prevents the OTHER request's row from being read. **Result: the two decisions serialized cleanly on the advisory lock** — the first to acquire it computed `min(90, 120 - 0) = 90` and committed; the second, only able to proceed after the first released the lock at commit, then correctly read the FIRST request's now-committed 90 minutes in its own weekly sum and computed `min(90, 120 - 90) = 30`, not the naively-double-counted 180. Verified directly against `app.overtime_requests` after the race: the two `eligible_minutes` values were 90 and 30, summing to exactly the 120-minute weekly cap, never exceeding it under genuine concurrent pressure. No process errored; both decisions succeeded correctly.
