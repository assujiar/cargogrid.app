## 3. Design decisions (disclosed — the four this task's own report format requires)

### Decision A — the Platform-support-queue design: a genuinely parallel, Platform-wide catalog, never a widened `app.ticket_queues` row

`app.support_queues` is a NEW table with NO `tenant_id` and NO `org_unit_id` — CargoGrid support is not an org unit of any customer's tenant, and `app.ticket_queues`'s own `tenant_id`+`org_unit_id`-both-required shape structurally cannot represent it (HRT-286's own diagnosis, `docs/build-log/phase-07/HRT-286.md` §3, confirmed correct here, not rediscovered from scratch). `app.tickets.support_queue_id` (new, nullable) is the helpdesk-channel counterpart to `queue_id` (now relaxed to nullable), with a new structural `tickets_queue_shape` CHECK enforcing exactly one of `queue_id`/`support_queue_id` populated, matching channel — mirroring `tickets_requester_identity_shape`'s own established "structural shape CHECK" discipline. `support_queue_id` is deliberately populated only by staff triage AFTER creation (`app.transfer_helpdesk_support_queue`), never chosen or forged by the filing tenant — `app.create_helpdesk_ticket` has no `p_support_queue_id`/`p_queue_id` parameter at all.

### Decision B — the Platform-support-staff-role decision: Supreme-Admin-authority actors ONLY, a deliberate, disclosed, bounded-scope choice

Per this prompt's own mandatory reading, there is currently no dedicated "Platform Support Team" role distinct from Supreme Admin, and `app.principal_memberships`'s four layers (`supreme_admin`/`tenant_admin`/`org_user`/`customer_user`) are deliberately closed (that migration's own header). Inventing a fifth, global, non-tenant-scoped layer for "Platform Support Staff" would be real, unreviewed identity-model surgery on a foundation table three unrelated capabilities already depend on — wildly out of this single prompt's own bounded scope. **Decision: `app.is_ticket_staff` is hardened so that, for a `channel = 'helpdesk'` ticket specifically, staff status is `app.is_supreme_admin(actor)` and NOTHING else** — explicitly excluding the tenant-wide `TKT:Edit` fallback, queue-membership fallback, and assignee-employee fallback that legitimately apply to internal/customer tickets. `app.support_queues`/`support_queue_id` are therefore pure routing/triage metadata, never membership. **Disclosed limitation**: this prompt does not build a narrower, non-Supreme-Admin "support agent" role; a future prompt wanting one should add it as its own deliberate principal-layer or grant-table decision, never inferred from this migration's queue catalog.

### Decision C — the tenant-requester identity resolution: `app.principal_memberships`/`app.role_assignments`-based, deliberately employee-independent

A tenant must be able to file a Platform support case regardless of HR-track onboarding state (a brand-new tenant with zero `app.employees` rows must still be able to ask CargoGrid for help) — per this prompt's own explicit instruction, NOT HRT-274's employee model. The new `app._is_tenant_helpdesk_authorized(tenant_id, auth_user_id)` helper answers "is this identity a real, active `tenant_admin` membership, OR a real, tenant-scoped, published `TKT:Edit` role grant" via a DIRECT query against `app.principal_memberships`/`app.role_assignments` — never via `app.get_self_employee` (no `app.employees` row required) and, just as importantly, **never via `app.check_ticket_authority`/`app.evaluate_permission`**, whose RPD-022 Supreme-Admin bypass would otherwise make a Platform Supreme Admin ALSO satisfy "is the tenant-side requester party," conflating the two sides of the exact boundary this migration exists to keep separate. This was found and fixed DURING this migration's own design (reasoning about the RPD-022 bypass interaction before writing any test), then live-adversarially confirmed broken-if-naive and correct-as-shipped in `scripts/db-tests/ticketing-helpdesk.sql` test 4 — a Supreme Admin not enrolled in a given tenant is genuinely rejected from opening a helpdesk case "as" that tenant.

### Decision D — the correlation-not-access-grant proof

`app.tickets.support_access_case_ref` (new, nullable text) may be set ONLY by `app.link_helpdesk_support_grant` (Supreme-Admin-gated), which validates a REAL `app.support_access_grants` row exists for `(tenant_id, case_id = the given ref)` before accepting it (typo/forgery defense) — NOT required to be an ACTIVE grant, since displaying a past/expired/revoked case's correlation is legitimate history, never itself a live grant. NO function in this migration reads `app.support_access_grants`/`app.support_access_sessions` for any purpose OTHER than this one read-only, LEFT-JOINed display in `app.get_platform_helpdesk_ticket` (grant status/expiry/revocation shown for triage convenience) — and NO function in this migration or anywhere else grants, extends, revokes, or otherwise mutates a support access grant. The existing, UNMODIFIED PLT-115 flow (`app.request_support_access`/`app.approve_support_access`/`app.start_support_session`/`app.revoke_support_access`) remains the ONLY path to actual tenant business-data access. Live-adversarially proven in `scripts/db-tests/ticketing-helpdesk.sql` test 12: a forged case ref is rejected (`support_grant_not_found`); a real grant, approved by the tenant's own `tenant_admin`, then REVOKED via the existing kill switch, is still successfully linked for display (`get_platform_helpdesk_ticket` shows the real `revoked` status, never hides it); and an identity (`support-agent`) holding an ACTIVE, approved, unexpired support-access grant into the ticket's own tenant is confirmed to hold ZERO `is_ticket_staff`/`can_access_ticket` status on the correlated helpdesk ticket purely from that grant, both BEFORE and AFTER the correlation is linked.

## 4. Other structural decisions

- **Tenant-visible vs. Platform-internal**: the SAME `ticket_messages.visibility`/`app.is_ticket_staff` mechanism HRT-286 already built, reused verbatim — no new visibility column, no new message table. `app.reply_to_helpdesk_ticket` (tenant-side entry point) is a thin defense-in-depth wrapper mirroring `app.reply_to_customer_ticket` exactly (hardcodes `visibility := 'public'`, re-verifies `channel = 'helpdesk'`). Platform staff (Supreme Admin) posts internal notes through the EXISTING, unmodified `app.reply_to_ticket` directly.
- **The three existing generic staff-lifecycle RPCs** (`assign_ticket`/`transfer_ticket_queue`/`update_ticket_classification`) and `redact_ticket_message` were extended (never bypassed or silently misused) to explicitly reject/restrict a helpdesk-channel ticket, with dedicated, Supreme-Admin-gated siblings built instead (`assign_helpdesk_ticket`/`transfer_helpdesk_support_queue`/`update_helpdesk_ticket_classification`) — never a shared RPC silently branching two different authority models together. `redact_ticket_message` specifically required a NEW guard (Platform-staff-only for a helpdesk ticket) because its original design let ANY tenant-wide `TKT:Edit` holder redact content on a ticket they could structurally access, regardless of message visibility — on a helpdesk ticket this would have let a tenant destroy Platform-internal diagnostic notes it cannot even read (self-found during design, live-confirmed fixed in test 10).
- **Staff-facing read RPCs hardened with a PER-TICKET-CHANNEL exclusion** (`get_ticket`/`list_tickets`/`list_ticket_messages`/`list_ticket_watchers`/`list_ticket_events`) — deliberately NOT a per-actor-layer exclusion (HRT-287's own `customer_user`-layer pattern), because the SAME `org_user`/`tenant_admin` actor legitimately needs the staff projection for their tenant's own internal-channel tickets but never for a helpdesk case where they are the requester side, not staff. A helpdesk ticket is reachable through these RPCs by `app.is_supreme_admin(actor)` only.
- **`get_ticket`/`list_tickets`' own `app.ticket_queues` JOIN converted from INNER to LEFT** — `queue_id` is now nullable (helpdesk); an unconverted INNER JOIN would have silently excluded every helpdesk ticket from these RPCs even for a correctly-admitted Supreme Admin caller — the exact "INNER JOIN silently drops a legitimately-nullable-FK row" class ISS-2026-085 already named and HRT-287 already fixed once for `app.employees`, applied here to `app.ticket_queues`.
- **Raw-table RLS hardened**: `tickets`/`ticket_messages`/`ticket_watchers`/`ticket_events` SELECT policies additionally exclude a helpdesk-channel ticket for a non-Supreme-Admin actor (a new `app.ticket_channel_of(ticket_id)` helper feeds the three tables with no channel column of their own) — mirroring the ATW-023/HRT-287 hardening precedent exactly, but keyed on ticket channel rather than actor layer.
- **`cancelled_reason_authored_by_customer`/`last_reopen_reason_authored_by_customer`** (added at the HRT-287 Tier C batch review) are reused, not duplicated: `app.transition_ticket_status`'s gating widened from `channel = 'customer'` to `channel in ('customer', 'helpdesk')`. Column names still say "customer" (an already-`VERIFIED` column, not renamed to avoid unwarranted churn) — disclosed via a fresh `comment on column`.
- **Severity/product-area/environment/reference** are generic, nullable columns on `app.tickets` (not channel-restricted by CHECK) — populated only by helpdesk entry points today, left `null` for internal/customer tickets, disclosed as honestly-unused-elsewhere-today.
- **Diagnostic attachments reuse PLT-128 verbatim** — `app.reply_to_ticket`'s existing `p_attachment_file_ids`/malware-scan-gating logic is already channel-agnostic (keyed on ticket id, not channel); both `app.reply_to_helpdesk_ticket` and direct `app.reply_to_ticket` calls inherit it unchanged. No new document type registered.
