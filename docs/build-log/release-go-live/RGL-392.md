### 4.1 `RGL-BLK-004` root cause confirmed end-to-end by a controlled experiment

`RGL-391` diagnosed the `db:test` failure as an hour-of-day dependency in
`app._calc_vendor_kpi_rate_validity`'s denominator, and proved the arithmetic by evaluating it
across all 24 hours. This checkpoint closed the loop **empirically, on the real suite**, rather
than leaving a simulation as the proof:

| Run | Session timezone | Local hour at run | Result |
|---|---|---|---|
| `RGL-391` baseline | `Etc/UTC` | **02:32** — inside the 01:00–03:59 dead band | **FAILED** at file 203, `procurement-vendor-performance.sql:978` |
| This checkpoint, controlled | **`PGTZ=Asia/Singapore`** (UTC+8) | **~10:55** — outside the band | **`==> db-tests: ALL PASSED`**, 230/230 files, **0 errors** |

Nothing but the session timezone differed: same tree, same 333 migrations, same 230 test files,
same disposable-database harness, same wall-clock instant. **The diagnosis is confirmed
end-to-end, not merely by simulation.**

### 4.2 What the controlled run establishes, and what it does not

**Establishes:**

1. **`RGL-BLK-004`'s root cause is exactly as diagnosed.** The only variable changed was the
   session timezone, and the suite went from aborting at file 203 to `ALL PASSED` across all 230.
2. **There is no second, hidden failure behind the first.** This matters: `run.sh` uses
   `set -euo pipefail`, so the baseline run's abort at file 203 left **27 files unexecuted** and
   their state genuinely unknown. They are now known — all green, 0 errors, on this exact tree.
   The freeze can therefore record a **complete** matrix instead of a truncated one.
3. **The 333 migrations apply cleanly from zero** to a fresh disposable database, twice in one
   session. That is Prompt 412 required-verification item 5's evidence, produced here rather than
   carried forward — though `RGL-396` still owns it properly.

**Does not establish, and must not be read as establishing:**

1. **That the suite is green.** It is green **for 21 hours of every 24** and red for the other
   three, on any tree, until `RGL-BLK-004` is fixed. A gate with a daily three-hour failure window
   is not a passing gate; §4's matrix stays **RED** on that basis.
2. **That CI is fixed.** `RGL-BLK-005` is a different defect with a different mechanism
   (`pg_read_file` reading the server's filesystem, file 34 of 230) and is entirely unaffected by
   timezone. CI remains red.
3. **That shifting the timezone is a remedy.** It is a diagnostic instrument, used once, under
   control. Setting `PGTZ` to dodge a failing window would be exactly the fake-pass this range
   forbids, and no lane may do it. The fix is to correct the denominator arithmetic — owner
   `RGL-394`.

**Registered against Step 15's own standing warning.** Step 15 §9 required every checkpoint to
disclose which dimensions of the wall-clock/day-of-week flake class its run actually exercised,
and repeatedly noted that a green suite at one hour proves nothing about other hours. This is the
first checkpoint in the build to **control** that variable deliberately rather than observe it.
`RGL-395` owns whether a release gate may retain a wall-clock dependency at all.
