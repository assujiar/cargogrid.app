**`function_search_path_mutable`, checked rather than waved past.** A mutable `search_path` on a
SECURITY DEFINER function is a genuine privilege-escalation vector, so the 649 were counted
directly rather than assumed benign:

| Schema | Security mode | Functions | With mutable `search_path` |
|---|---|---|---|
| `app` | DEFINER | 2,059 | **0** |
| `app` | INVOKER | 687 | 646 |
| `public` | DEFINER | 1,859 | **3** |
| `public` | INVOKER | 1,262 | 718 |

All three `public` DEFINER functions are PostGIS's own `st_estimatedextent` overloads, owned by
`supabase_admin` — not this repository's code and not ours to alter. **Every one of the 2,059
application-owned SECURITY DEFINER functions has a pinned `search_path`.** The invoker-mode
counts are not a finding: an invoker function runs with the caller's own rights and resolves
through the caller's own `search_path` by definition.

## 3. What the sweep found that was mine — `ISS-2026-309`

`public.evaluate_ip_access` (from `20260830170000`) and the 7-argument
`public.raise_observability_alert` (from `20260830180000`) shipped **`anon`-executable** on the
live project. Both SECURITY DEFINER. Both created hours earlier by this session.

Cause: `revoke execute on function public.<f>(...) from public` revokes the PUBLIC pseudo-role,
not the `anon`/`authenticated` roles, which Supabase's `ALTER DEFAULT PRIVILEGES` had already
granted explicitly at `CREATE FUNCTION` time.

These two were genuinely exploitable where most would not be: they carry no actor parameter and
no `app.assert_actor_is_session_identity` guard, by design, so **the grant is their entire
access control**. Full detail, including the four pre-existing widenings kept separate from
these two and the environment defect that let a correct gate pass green, is in
`docs/runtime/KNOWN_ISSUES.md` → `ISS-2026-309`.

Closed by `20260830200000`, applied live, verified by re-running the same query: **zero
`public.*` wrappers remain wider than their `app.*` counterpart.**

## 5. `ISS-2026-300` — the drift is 84 rows, not 9

The entry records 9 ledger rows carrying Supabase's wall-clock version instead of the
repository's filename version. Measured directly against the full ledger and the full migration
set, the real figures are:

- ledger rows: **399**
- repository migration files: **390**
- **repository versions absent from the ledger: 84** — every one of which `supabase db push`
  would attempt to re-run as non-idempotent DDL against an already-migrated schema
- ledger rows with no matching repository file: 93

`ISS-2026-300` is understated by an order of magnitude, and this session added 11 more drift
rows to it by applying migrations through the MCP tool. The entry is corrected in place.

**Reconciliation prepared and fully verified, not executed.**
`scripts/release/reconcile-migration-ledger.sql` contains 84 `update` statements. Verified
before generation:

1. every drift row maps to **exactly one** repository file (zero ambiguous, zero unmapped);
2. **no target version collides** with any existing ledger row;
3. the set of 84 targets **equals exactly** the set of 84 repository versions missing from the
   ledger — the arithmetic closes with nothing left over in either direction.

Nine rows are deliberately left as orphans: the live project applied three migrations in parts
(`finance_authority_chain_security_definer` p1–p6, its tier-C completeness p1–p3, two
settlement-reversal follow-ups) which the repository carries consolidated into single files.
The first part of each group is remapped to the consolidated file; the rest stay. `supabase db
push` ignores ledger rows with no matching repository file, and deleting them would be larger
and less reversible than the problem warrants.

**Not executed, and the reason is not timidity.** `ISS-2026-300` itself records that this write
"should require an explicit human decision, not agent judgment alone". That is a decision
already recorded in this repository, and a prepared, verified script plus an explicit ask is
the correct way to honour it. The script is reversible: every statement's `where` clause states
the exact pre-change `(version, name)`.

## 6. Live health probes — and what they actually found

The three endpoints (`/api/health`, `/api/ready`, `/api/v1/status`) could not be probed
unauthenticated. That is not a fault: the Vercel project has
`ssoProtection: enabled, all_except_custom_domains`, so every `*.vercel.app` URL returns `302`
to an SSO challenge. Probing them requires either a custom domain or an authenticated session.

Establishing why led to two findings that matter more than the probe would have:

**a) There is no production deployment.** The 20 most recent deployments are all previews
(`target: null`) from `claude/step-17-implementation-0fbul7`, all `READY`. Zero have
`target: production`. The project reports `"live": false`. This is consistent with
`RGL-BLK-001` being genuinely closed — `vercel.json` disables `main` auto-deploy and the
go-decision gate stands in front of production.

**b) `cargogrid.app` does not point at this Vercel project, and is not empty.** The Vercel
project's domains are only `cargogrid-app.vercel.app`,
`cargogrid-app-saiki-tech.vercel.app`, `cargogrid-app-git-main-saiki-tech.vercel.app` — no
custom domain attached. `https://cargogrid.app/` returns `200` served by **Cloudflare**, not
Vercel, rendering a different site built with a website builder (`/__l5e/assets-v1/…` asset
paths). `https://cargogrid.app/api/health` returns `404`.

**This changes what "deploy and publish" means, and it is an owner decision, not a technical
step.** Promoting a Vercel production build does not put CargoGrid on `cargogrid.app`. Doing
that additionally requires attaching the domain in Vercel and repointing DNS at Cloudflare —
which **replaces the site currently live there**. That is a cutover, not a deploy, it is
outside this session's access, and it must not be done as a silent side effect of a deploy.
Registered as `ISS-2026-311` and carried into `COMMERCIAL_LAUNCH_READINESS.md`.

**c) Node runtime divergence.** `package.json` declares `engines.node: 22.x` and CI resolves
its Node version from that file, so every green CI run is proof about **Node 22**. The Vercel
project is configured `nodeVersion: 24.x`, so builds and serves on **Node 24**. Previews build
clean, so this is not breaking today — but the runtime that serves users is not the runtime the
test suite proves. Registered as `ISS-2026-310`.
