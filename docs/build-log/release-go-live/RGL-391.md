## 5. `RGL-BLK-004` — a real product defect found by this checkpoint's own baseline

Found by **running the gate**, not by reading code. Full entry in `BLOCKER_LEDGER.md`; the
reasoning is recorded here because it is this checkpoint's only technical finding.

**The defect.** `app._calc_vendor_kpi_rate_validity`
(`supabase/migrations/20260730740000_create_procurement_vendor_performance.sql:1186`):

```sql
generate_series(p_window_start::date, (p_window_end - interval '1 day')::date, interval '1 day')
```

For a sub-24-hour window, `(p_window_end - 1 day)::date` can precede `p_window_start::date`,
yielding an **empty** series → `v_den = 0` → `is_computable = false` → `computed_value = NULL`.

**It contradicts its own documented guarantee.** The function's `comment on function` asserts
*"is_computable is true whenever the window itself is non-empty (window_days is always > 0)"*.
That is false. A real caller requesting a short intraday window receives a silent "no data"
instead of the real 0% the design promises — so this is a **product** defect, not merely a
fixture problem.

**Empirical reproduction, not inference.** Evaluated across all 24 hours on the live local
Postgres (`Etc/UTC`):

| Hour of day | `window_days` |
|---|---|
| 00 | 1 |
| **01, 02, 03** | **0 — not computable, assertion fails** |
| 04 … 23 | 1 |

The suite ran at **02:32 UTC**, inside the dead band:

```
psql:scripts/db-tests/procurement-vendor-performance.sql:978: ERROR:  assertion failed:
  expected New Vendor rate_validity to be computable (a real 0%, not a missing-data case)
```

**Blast radius.** `run.sh` uses `set -euo pipefail`, so the suite **aborts** at the first failing
file: **202 of 230 files passed, file 203 failed, 27 never ran**. `ALL PASSED` never printed, and
the disposable database is left undropped because the drop follows the loop.

**Why it was not fixed here.** Pre-existing (migration dated 2026-07-30, long before this range);
`AGENTS.md` restricts a checkpoint to task-caused failures and directs pre-existing ones to a
registered recovery task; and Prompt 391's charter is zero code, zero migration — a repair would
need an additive migration this checkpoint is not authorized to ship. Owner `RGL-394`.

**Consequence for the range, recorded so no later lane can miss it.** Step 15's
`230/230 ALL PASSED` **cannot be carried forward**. It was true at the hour it ran. `RGL-392` must
freeze a red test matrix; `RGL-395` cannot certify the CI gate; `RGL-404` cannot reach a go
decision — while this is open.

## 5.1 `RGL-BLK-005` — the CI gate has been red for 30 consecutive runs, and nobody looked

**The most serious integrity finding of this checkpoint.** Found by querying the GitHub Actions
API — not by reading `.github/workflows/ci.yml`, which is what a code-reading check would do and
what every prior checkpoint effectively did.

**Every one of the 30 most recent CI runs failed**, `push` and `pull_request` alike, continuously
from at least **2026-08-10** through the current `main` HEAD `2670cb5` (run 114, conclusion
`failure`). During that same window, 21 Step 15 checkpoints reported green gate suites.

**Both statements are true, and the gap between them is the finding: the gates were green
*locally*; the *CI* gate — the one Prompt 412 required-verification item 4 actually names — was
red the whole time.** Nothing in the reporting chain distinguished "I ran the suite here" from
"the repository's release gate passed."

**Root cause, diagnosed exactly rather than guessed.** Only the `db` job fails now — `quality` and
`e2e` pass, so `HDN-386`'s lockfile-drift fix genuinely worked:

```
psql:scripts/db-tests/advanced-tms-wms-outbound.sql:850: ERROR:
  could not open file "/tmp/cargogrid-wms-outbound-race-a.out" for reading:
  No such file or directory
CONTEXT: select pg_read_file('/tmp/cargogrid-wms-outbound-race-a.out') || ...
```

`scripts/db-tests/wms-picking-concurrency-helper.sh` is launched through psql's `\!`
meta-command, so it executes on the **client** and writes its race-output files to the
**client's** `/tmp`. The assertion then reads them with **`pg_read_file()`, which reads the
*server's* filesystem.**

| Environment | Client and server | Result |
|---|---|---|
| Local (this checkpoint, and every prior one) | same host, same `/tmp` | **passes** — confirmed firsthand: the local run sailed past file 34 and reached file 203 |
| CI | Postgres is a Docker **service container** with its own filesystem | **fails** — the file genuinely is not on the server |

This is the **exact inverse** of the "CI-mirrors-hosted" property Step 15 §2.2 elevated to a
standing constraint on every lane. That constraint was written about extension layout and
`search_path`; the same class of divergence was sitting in the test harness all along.

**Blast radius — why this is Critical and not just a broken test.**
`advanced-tms-wms-outbound.sql` is **file 34 of 230** in glob order, and `run.sh` runs under
`set -euo pipefail`:

> **196 of the 230 database test files have had zero CI enforcement for the entire window** —
> every migration-integrity, RLS, tenant-isolation, RBAC and financial-posting assertion they
> carry.

A release gate that executes 15% of its suite and then dies, while every status report reads
`230/230 ALL PASSED`, is functionally a disabled test suite. The `230/230` figure was never
false; it was simply never a **CI** figure.

**What this finding does *not* claim.** No product defect is proven by it. Those 196 files pass
locally. Even the failing block's own substantive guarantee is proven — the winner /
one-confirmation / one-consumption-movement assertions all pass; only the assertion about the
*losing process's output text* fails. Proposed **Critical** on release-gate integrity grounds, not
on product-correctness grounds. `RGL-394` owns the binding ruling and may reasonably land on High;
what it may not do is treat it as a flake.

**Also disclosed, folded in rather than inflated into a separate blocker:** every recent
checkpoint commit fails this repository's own `check-commit-message.ts` gate, which CI runs on PR
head commits — verified directly against `3fe4bf6`, `00403cb` and `568be15`. This checkpoint's own
first commit had the same shape and was **amended to comply** before anything was pushed. It is a
sub-case of the same "nobody was reading CI" root cause; `RGL-395` owns deciding whether the
convention or the history is what should change.

**Not fixed here.** Pre-existing, outside a zero-code kickoff's charter, and the fix is a real
design choice (rewrite the assertion to avoid `pg_read_file`, or run the helper server-side)
rather than a mechanical edit. Owner `RGL-395`.
