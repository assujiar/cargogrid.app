## 1. What this ruling covers

Before treating the current branch head as a re-verified deploy candidate, the full local gate

## 2. The finding: `security:audit` — 2 blocking high-severity `browserslist` advisories

`scripts/security/check-dependency-audit.ts` failed for the first time this session:

```
✖ 2 blocking dependency vulnerability/vulnerabilities (critical/high):
    high browserslist <=4.28.6 -> >=4.28.7
      Browserslist: Unbounded memory growth (no cache eviction) via distinct query results
      https://github.com/advisories/GHSA-c83g-rgw3-j3cx
    high browserslist <=4.28.6 -> >=4.28.7
      Browserslist: Uncaught crash / prototype write via untrusted browserslist-stats.json
      https://github.com/advisories/GHSA-73wf-gq98-2v4g
```

This is not a defect introduced by this session's own changes — `browserslist` is a transitive
dependency pulled in by `next` (via `styled-jsx`) and `eslint-config-next` (via
`eslint-plugin-react-hooks` → `@babel/core` → `@babel/helper-compilation-targets`), not a direct
dependency of this repository. `pnpm why browserslist` confirms a single resolved version,
`4.28.6`, reached only through those two paths. The advisories were published after `RC-2026.08.25-1`
was last audited clean; this is newly-disclosed upstream risk, not regression.

**Fix.** The repository already has a working pattern for exactly this shape of problem —
version-range `pnpm.overrides` entries in `package.json` for transitive packages this repo does
not import directly (`brace-expansion`, `postcss`, `sharp`, `@eslint/plugin-kit`, `js-yaml`,
`nanoid`). Added the same shape:

```json
"browserslist@<4.28.7": ">=4.28.7"
```

`pnpm install` re-resolved `browserslist` to the patched `4.28.7+` range; `pnpm why browserslist`
confirms it is still the sole resolved version everywhere it is required, so there is no split
between the direct-tree and transitive-tree copies. `security:audit` now passes clean:

```
✔ dependency audit passed (no advisories).
```

## 3. Why this needed a freeze amendment

The override changes `pnpm-lock.yaml`'s resolved dependency set, which is exactly what
`lockfileSha256` in `scripts/release/check-release-freeze.ts` exists to freeze (see that file's
own class-level doc comment, "lockfile" bullet). `migrationSetSha256` and `dbTestSetSha256` are
unaffected — no `supabase/migrations/` or `scripts/db-tests/` file changed.

This is the **first** amendment to `lockfileSha256` since the original freeze — every prior pass
recorded in that file changed only the migration and/or db-test digests.

authority as every other pass recorded there (ADR-0027 Part A — remediation-phase scope covers
fixing newly-surfaced, pre-existing gate failures found while finishing the backlog).

`d48b589018321bba1c1fbb12f8befd7664b4fc34` (`RGL-414`), which is now over 150 commits behind this
branch's head — `scripts/release/check-go-decision.ts` will correctly refuse a production build
at the new head until a fresh, explicit go decision is recorded for it. That is the gate working
as designed (see `RGL-414.md` §3), not a defect this ruling closes.
