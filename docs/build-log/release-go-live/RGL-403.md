## 3. Live-target latency — the first real measurement against a deployed target in this range

Per the execution index's own §10 authorization ("a real running application now exists at a real
public URL... can therefore be Executed against a genuine target"), and consistent with §12's
production-mutation ban, this checkpoint measured **read-only** latency for 3 endpoints against
the live production deployment (`cargogrid-app.vercel.app`) — 10 samples each, `curl -w
%{time_total}`, no write, no load/concurrency generation (which would risk degrading a production
system this checkpoint has no authority to affect):

| Endpoint | What it does | n | p50 | p95 | max |
|---|---|---|---|---|---|
| `GET /api/health` | Liveness only, zero dependency check (`app/api/health/route.ts`'s own header) | 10 | 195ms | 243ms | 243ms |
| `GET /api/ready` | Readiness — calls `app.ping()` via the service-role client, a real Supabase round trip | 10 | 837ms | 1,698ms | 1,698ms |
| `GET /api/v1/status` (no auth, denial path) | Full API-gateway request path, short-circuits before any RPC call | 10 | 463ms | 838ms | 838ms |

**Applicable budget** (`08_API_INTEGRATION_WORKSTREAM.md` §12): "Common REST/GraphQL query: 500ms
(query-plan threshold)"; "Complex report query: 2s."

**`/api/health`** and **`/api/v1/status`** both sit comfortably inside the 500ms common-query
budget at p50, and `/api/v1/status`'s p95 (838ms) and max stay well under the 2s ceiling.

**`/api/ready`'s p50 (837ms) exceeds the 500ms common-query budget; its max (1,698ms) stays under
the 2s complex-query ceiling.** The ~640ms delta versus `/api/health` (which does zero database
work) is attributable to the real Supabase round trip `app.ping()` performs — plausible for a
cross-region call (Vercel's own deployment region vs. Supabase `ap-northeast-1`) but not
independently confirmed against a region-latency baseline this checkpoint has no tool to measure.
**This is a genuine, disclosed observation, not a fabricated pass.** Registered `ISS-2026-297`,
**Low**, `OPEN` — not a blocker: `/api/ready` is an internal orchestrator health probe, not a
customer-facing capability the 19-row Blueprint §21.1 table names; the sample size (n=10) is too
small to be a confident SLA measurement; and no functional failure occurred (every probe returned
`200 {"status":"ok"}`). Owner `RGL-404`/`RGL-406`, for awareness at go/no-go and re-measurement
once `RGL-015` actually deploys this branch to production.

## 5. Verdict

**No `NO_GO`.** No budget violation rises to Critical/High per the severity model (§8.1 of the
execution index): the one observation (`/api/ready`'s p50) is Low, affects an internal probe not a
customer-facing capability, and stays within the complex-query ceiling even at its observed max.
The three pre-existing evidence gaps remain open, Medium/Low severity, each already carrying a
named future owner and an explicit non-blocking disposition from the checkpoint that first
registered it — this checkpoint re-confirms that disposition rather than re-litigating it.

**What this checkpoint does not claim.** It does not claim Phase 8/9 routes have been
load-tested (they have not — `ISS-2026-141`/`148` remain the accurate record). It does not claim
production has been load-tested at any real concurrency (§12 forbids generating load against
production; only read-only single-request latency was measured). It does not claim the disposable-
Postgres numbers in §2 predict live production behavior under real tenant-scale data, since
production itself holds zero tenant rows (`RGL-398`) and the load-test harness runs against
synthetic seeded volumes, not live data.
