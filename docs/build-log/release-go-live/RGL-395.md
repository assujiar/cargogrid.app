## 2. Root cause and blast radius

**Already diagnosed at `RGL-391`/`RGL-394`, restated for completeness.**
`pg_read_file()` is a Postgres **server-side** function — it reads the filesystem of the machine
running the Postgres server process. The concurrency-race test helpers
(`scripts/db-tests/wms-picking-concurrency-helper.sh`,
`scripts/db-tests/automation-rule-engine-concurrency-helper.sh`) are launched through psql's `\!`
meta-command, which runs the command on the psql **client**, so the race-output files they write
land on the **client's** filesystem. Locally, client and server share a host, so
`pg_read_file()` happens to find the file — this is coincidence, not correctness. In CI, Postgres
runs as a separate `postgis/postgis:17-3.4` Docker **service container** with its own filesystem,
so the file genuinely does not exist server-side, and the assertion fails with `could not open
file ... No such file or directory`.

**Blast radius, found this checkpoint by grepping rather than assuming.**
`scripts/db-tests/run.sh` runs under `set -euo pipefail`, so CI's `db` job aborted at the *first*
occurrence of this pattern — `advanced-tms-wms-outbound.sql`, file 34 of 230 — and nothing after it
had ever actually executed in CI. Searching every file under `scripts/db-tests/` for
`pg_read_file(` found the same pattern in **6 files total**, not 1:

| File | Helper used |
|---|---|
| `advanced-tms-wms-outbound.sql` | `wms-picking-concurrency-helper.sh` (the one CI had actually reached and failed on) |
| `advanced-tms-wms-packing.sql` | `wms-picking-concurrency-helper.sh` |
| `advanced-tms-wms-picking.sql` | `wms-picking-concurrency-helper.sh` |
| `automation-rule-engine.sql` | `automation-rule-engine-concurrency-helper.sh` (3-process variant) |
| `procurement-vendor-contract.sql` | `wms-picking-concurrency-helper.sh` (PID-suffixed paths) |
| `public-api-platform.sql` | `wms-picking-concurrency-helper.sh` |

The other 5 were **latent, unreached bugs of the identical class** — fixing only the file CI had
actually named would have moved the abort point to the next one and produced a second, third,
fourth, fifth "new" CI failure over five separate cycles. All 6 are fixed in this same checkpoint.

## 3. Fix — structural, not coincidental

Rather than asking the *server* to read a *client*-local path, the race-output file's **content**
is captured **client-side**, in the same psql process that already has the correct environment,
using psql's `` \set var `shell command` `` syntax: the backtick subshell inherits psql's own
process environment (including anything set via `\setenv`), so
`` \set loser_out `cat "$RACE_OUT_A" "$RACE_OUT_B"` `` reads the files from the exact host that
wrote them — sidestepping the client/server split by construction, not by relying on the two hosts
happening to coincide.

- For a top-level `select` (`procurement-vendor-contract.sql`), `:'loser_out'` interpolates
  directly.
- For an assertion inside a `do $$...$$` block (the other 5 files), psql does not interpolate
  `:variables` inside a `do` body — a pre-existing, already-documented limitation in this codebase
  (`ISS-2026-023`/`CG-S10-ATW-027`). The existing bridge pattern
  (`select set_config('cargogrid.x', :'var', false);` before the block,
  `current_setting('cargogrid.x')` inside it) is reused, repurposed to carry **content** instead of
  a path — `advanced-tms-wms-picking.sql` already had this exact bridge for the *path*, and this
  checkpoint changes what it carries rather than adding a new mechanism.

No test assertion, RLS policy, or security check was weakened — the fix changes only *how the
loser's output text reaches the assertion*, not what is asserted about it.
