## 3. `RGL-BLK-004` fix — the one defect this task repairs directly

**Root cause.** `app._calc_vendor_kpi_rate_validity` (PRC-264,
`20260730740000_create_procurement_vendor_performance.sql:1186`) computed the number of calendar
days in a window as:

```sql
generate_series(p_window_start::date, (p_window_end - interval '1 day')::date, interval '1 day')
```

`- interval '1 day'` correctly finds the right upper-bound date only when the window's length is a
whole number of 24-hour periods aligned to a day boundary. For any other window shape — in
particular any window under 24 hours, or one that does not start/end at midnight — subtracting a
flat 24 hours can walk the upper bound's date to *before* the window's own start date, so
`generate_series()` returns nothing. `v_den` collapses to 0, `is_computable` becomes `false`, and
`computed_value` becomes `NULL` — directly contradicting the function's own documented guarantee
("`is_computable` is true whenever the window itself is non-empty — `window_days` is always > 0").
Empirically, this fired for exactly 3 of 24 wall-clock hours against the test file's own
`now()`-relative window shape (`date_trunc('hour', now()) - 1h` to `+ 20h`), matching
`RGL-BLK-004`'s own original reproduction table exactly.

**Fix**, additive
(`supabase/migrations/20260826020000_harden_vendor_kpi_rate_validity_window_calc.sql` — the
already-applied `20260730740000` file is not edited, per this repository's standing rule):
replace the upper bound with `(p_window_end - interval '1 microsecond')::date` — the calendar date
of the *last instant actually inside* the exclusive-end window. This is provably identical to the
old formula's result for every whole-day-aligned window (`Jan3 00:00 - 1 microsecond` and
`Jan3 00:00 - 1 day` land on the same date, `Jan2`), and is provably never earlier than the
window's own start date for any other window shape, since `window_end > window_start` holds for
every real caller.

**Regression proof, added the same checkpoint, hour-independent by construction.** A new assertion
block in `scripts/db-tests/procurement-vendor-performance.sql` calls the function directly
(bypassing the vendor/tenant fixture machinery entirely, so it cannot be disturbed by anything
else in the file) with two hardcoded windows:

1. A 21-hour, non-day-aligned window (`2026-01-15 01:00` to `2026-01-15 22:00`) — the exact shape
   that used to collapse. Asserts `is_computable = true`, `raw_denominator = 1`.
2. The original whole-day-aligned 2-day window shape (`2026-01-01 00:00` to `2026-01-03 00:00`) —
   asserts `raw_denominator = 2`, still exactly correct, proving the fix does not change behavior
   for the case the old formula already handled correctly.

Both are fixed literals, not `now()`-relative, so they fail or pass identically at every hour of
the day — this is the "regression test that pins the hour" `docs/runtime/TASK_LEDGER.md`'s own
next-action note asked for. The three pre-existing `now()`-relative scenario blocks in the same
file are left unmodified; with the underlying arithmetic bug gone, they now pass at every hour
rather than 21 of 24 (proven by §4's own full-suite run, not merely reasoned about).
