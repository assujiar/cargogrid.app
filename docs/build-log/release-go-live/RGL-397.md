## 3. Fix — all 10 applied to live, in order

Applied to `awdlicmwzdxquopwtcfd` via `apply_migration`, in exact chronological order, each file
read in full immediately before applying (this range's own established transcription-risk
discipline for financially/security-sensitive content).

**Two files exceeded a single-response output-token limit when reproduced whole**
(`harden_finance_authority_chain_security_definer`, 249KB/5,192 lines;
`harden_finance_authority_chain_tierc_completeness`, 104KB/2,386 lines). Each was split at clean
top-level SQL statement boundaries (verified in advance — every boundary falls exactly at a
`CREATE OR REPLACE FUNCTION`/`ALTER FUNCTION`/etc. start, never mid-statement) into 6 and 3
sequential `apply_migration` calls respectively, applied strictly in order. This is a chunking
technique for getting the exact, unmodified content into the database — not a content change, and
not a new technique for this repository: it mirrors `RGL-BLK-002`'s own precedent of chunking a
migration too large for `apply_migration`'s request-size limit, except here the constraint was the
generating model's own response-size limit rather than the tool's request limit.

**Consequence, disclosed rather than hidden**: live's migration registry now carries **17 rows for
these 10 files** (6 + 1 + 3 + 1 + 1 + 5 single-file migrations = 17), not a clean 10-to-10 mapping.
Functionally immaterial — Postgres applied the exact same DDL regardless of how many
`apply_migration` calls carried it — but the registry no longer has a 1:1 correspondence with
`supabase/migrations/` filenames for these two files specifically. Confirmed via
`select version, name from supabase_migrations.schema_migrations` after the fact: all 17 rows
present, in the correct chronological order, each auto-assigned a version timestamp by the
apply mechanism (consistent with this range's own established observation, first noted at
`RGL-BLK-002`, that live-registered version numbers do not always match the local filename's own
timestamp prefix for migrations applied via `apply_migration`/the Management API rather than the
Supabase CLI).
