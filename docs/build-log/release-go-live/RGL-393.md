This is the load-bearing section, and the answer is uncomfortable.

| 1 | Direct push to `main` | GitHub branch protection | **NONE.** All **47** branches, `main` included, report `"protected": false` |

| 4 | `main` → production deploy | Deployment approval | **NONE** — Vercel auto-deploys, ungated (`RGL-BLK-001`) |
| 5 | Migration/db-test/dependency drift | *(added this checkpoint)* | **`pnpm run release:check-freeze`** — §4 |
| 6 | Feature flag toggle | n/a | **No flag service exists** (§5) |

**Four of the six paths have no control at all.** A change can go from a keyboard to the public
production URL without a review, a passing test, or an approval — and this is true *right now*,
during a declared freeze.

### 3.1 The repository predicted this, and the deferral was never picked up

`docs/git/GIT_STRATEGY.md` is unusually honest about it. §3 ratifies *"a pull request is mandatory
for every code change"*, and then its own scope note records:

> "this task documents policy and adds non-destructive local validation scripts only. It does
> **not** configure GitHub branch protection, required-status-checks, CODEOWNERS enforcement …
> those require external repository mutation, which is explicitly forbidden for this task."

§4 then defers it explicitly: squash-merge becomes the default *"once GitHub branch protection is
actually configured (`PH0-088`, CI/CD Baseline — out of scope here)"*.

**`PH0-088` produced `.github/workflows/ci.yml` and did not configure branch protection either.**
The deferral was never picked up by anyone, and nothing since has re-checked it. `GIT_STRATEGY.md`
was right to refuse to "invent unavailable protection" — the defect is that the follow-up owner
never closed the loop, which is the **same shape** as `ISS-2026-284` (an environment fact frozen
once at Phase 0 and never re-verified against the provider).

Registered as `ISS-2026-289`, owner `RGL-404`. **Configuring branch protection is a repository
setting outside this repository's contents and outside this lane's authority** — `RGL-404` holds
the release-decision authority that would justify requesting it.

### 3.2 What this means for the rule this lane exists to enforce

**The no-new-feature rule is real policy and is now mechanically enforced for content (§4). It is
not, and cannot be from inside this repository, enforced against ingress.** Any later lane that
reports "no new features entered the candidate" is reporting an *observation*, verifiable via §4's
digests — never a *guarantee*, because nothing prevents it.

Stating that plainly is this lane's most useful output. `RGL-404` and `RGL-412` must not treat a
green `release:check-freeze` as proof the candidate was sealed.

## 4. The control added — `pnpm run release:check-freeze`

**A freeze that exists only as prose is not a control.** `RGL-392` recorded digests; nothing
compared anything to them. This checkpoint makes the freeze mechanical.

| Item | Detail |
|---|---|
| Script | `scripts/release/check-release-freeze.ts` |
| Test | `scripts/release/check-release-freeze.test.ts` — **8 tests, 8 pass** |
| npm script | `release:check-freeze` |
| CI | new step in the `quality` job, after `threat-model:check` |
| Behaviour | Recomputes the sha256 of the migration set, the db-test set and `pnpm-lock.yaml`; **fails closed** (exit 1) on any drift, reporting expected *and* actual for every drifting axis |

**Scope choices, each deliberate:**

- **Guards migrations** — schema is the least reversible thing a release can change, and *"never
  edit an applied migration"* has real incident history here.
- **Guards db-tests** — freezing the schema while leaving its proof mutable would let the
  candidate's evidence change under it.
- **Guards `pnpm-lock.yaml`, not `package.json`** — `RGL-392` §2 anchored the dependency freeze on
  the lockfile because six manifest entries are caret-ranged and only the lockfile pins them. This
  checkpoint **validated that choice by accident**: adding an npm script changed `package.json`,
  the lockfile was untouched, and the gate correctly stayed green. A `package.json` digest would
  have produced a false freeze violation on a change that alters no dependency.
- **Does not guard `docs/`** — every Step 16 lane must write there by charter. A freeze forbidding
  its own evidence trail would be unusable.
- **Enumerates via `git ls-files`, not a directory read** — so an untracked scratch file cannot
  silently change a digest, and a *deleted* tracked file does.

### 4.1 The gate's first run caught a real error in `RGL-392`'s own freeze record

Recorded rather than quietly corrected, because it is exactly the class Tier C exists to find —
and it was found by the control, one checkpoint after the record was written.

`RGL-392` §3 froze the db-test set as **230 files**, sha256 `2c3389a8…`, computed with
`cat scripts/db-tests/*.sql` — a **top-level shell glob**. The gate enumerates with
`git ls-files -- 'scripts/db-tests/*.sql'`, which matches subdirectories too, and immediately
reported drift: **231 files**, sha256 `4df2ae90…`.

The 231st file is **`scripts/db-tests/fixtures/auth-schema-stub.sql`**.

**The gate's broader scope is the correct one, and the freeze is widened to match rather than the
gate narrowed to agree.** That fixture is loaded into *every* disposable database by
`cargogrid_setup_disposable_db` before any test runs — it stubs the Supabase-managed `auth` schema
that a bare Postgres does not have. Its content therefore changes what all 230 tests run against.
It is also demonstrably not inert: `HDN-369` had to correct a stale, load-bearing claim inside
this exact file during Step 15's own state freeze.

Had the freeze kept the narrower digest, **the one file capable of silently changing every
database test's meaning would have been the one file outside the freeze.**

| | Before | After |
|---|---|---|
| Files | 230 (runner-executed only) | **231** (runner-executed + the fixture it loads) |
| Digest | `2c3389a8…` | **`4df2ae90…`** |

`RGL-392.md` §3 is annotated with this correction; its original figure is left visible as the
record of what that checkpoint actually computed, per this build's append-only discipline.

### 4.2 Is adding this script itself a "new feature"? — asked and answered

A lane enforcing a no-new-feature rule that ships code owes an explicit justification.

**No.** It adds no product capability, no route, no schema object, no user-visible behaviour, and
no runtime dependency. It is **release-gate tooling**, which Prompt 393 §4 names as this lane's
own charter ("Enforce no-new-feature discipline") and Prompt 393 §28 requires ("Gate-specific
automated or manual evidence checklist… Evidence that commands fail closed and no pass is
fabricated"). Prompt 393 §11 authorizes release-evidence files. It changes `package.json` (one
script line) and `ci.yml` (one step) and **does not change the lockfile**, so the frozen dependency
set is untouched — verified by the gate's own green run after the edit.
