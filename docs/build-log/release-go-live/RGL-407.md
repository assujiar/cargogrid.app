## 4. Rollback decision authority, execution steps, data reconciliation, communication, retry conditions

Authored as a real, consolidated, cited-not-re-derived runbook rather than restated inline here,
per Prompt 407 §31's own "update... runbooks" instruction and this repository's own "one rollback
procedure, not two independently-authored ones" discipline (`11_*.md` §4.4):
**`docs/runbooks/deployment-rollback.md`** (new).

Summary of what it establishes, evidence-grounded where this checkpoint could verify it live and
honestly marked otherwise:

- **Decision authority**: Infrastructure-escalation tier (DevOps/SRE), per the existing,
  already-ratified Blueprint §30.1 support-tier model (`11_*.md` §8.4) — this runbook does not
  invent a new authority structure.
- **Rollback triggers**: the Tech Arch §28.3 per-layer table (Frontend/API/DB-schema/Config/
  Feature/Data), each with its own concrete condition and action, not a single generic "roll back
  if bad" rule.
- **Execution steps**: real, verified Vercel instant-rollback mechanics for the Frontend/API
  layer (confirmed live — a genuine `isRollbackCandidate: true` deployment exists right now, §2);
  the established forward-fix-preferred discipline for the DB-schema layer, reusing this
  repository's own already-proven `harden_*.sql` migration pattern; config-version rollback and
  feature-flag disable for the Config/Feature layers; an explicit "never a destructive data
  rollback for a routine posting error" constraint for the Data layer.
- **Data reconciliation**: the DB-schema row's own forward-fix-first sequencing, plus a direct
  cross-reference to `database-restore.md` for the genuine-disaster case rather than duplicating
  that runbook's own already-detailed reconciliation procedure.
- **Communication**: reproduces Blueprint §26.3/§30.3 verbatim (freeze/communicate in parallel
  with fix work, not sequenced after it; the same 12-field incident record every other incident
  uses, not a lighter-weight rollback-specific one).
- **Retry conditions**: mandatory RCA before any retry (Blueprint §30.5 — "production rollback" is
  one of six explicitly-named mandatory-RCA triggers), capturing whether the forward-fix-vs-down-
  migration choice was correct in hindsight and what preventive action would have caught the
  regression pre-Production.
- **Honestly marked as not yet rehearsed**: no end-to-end rollback (an actual Vercel promotion, a
  forward-fix migration under simulated incident conditions, or a full cutover-rollback drill) has
  ever been executed against this project. The runbook's own §7 records this explicitly — the
  *mechanism* is verified live and available; its *execution* is not, and is not fabricated as
  such. Scheduled against the existing quarterly DR-rehearsal cadence (`ADR-CAND-ARCH-023`), not
  invented as a new one.

This also closes the `deployment-rollback.md` half of `ISS-2026-262`'s own disclosed gap for
real (previously `RESOLVED` at `HDN-388` only via a reconciliation *note*, not an authored file) —
see that entry's own updated text in `docs/runtime/KNOWN_ISSUES.md` for the full accounting, and
`docs/runbooks/README.md` for the updated index.
