**No SQL injection actually executes anywhere in this codebase.** Every domain write/read goes
through a parameterized RPC call (`client.rpc(name, params)`); Postgres's own type system rejects
a non-UUID string at the bind-parameter layer before any query text is ever constructed from it.
What #6/#10 found is not an injection vulnerability — it is an **unhandled-exception /
insufficient-input-validation** defect: the TypeScript-side Zod `.uuid()` validation correctly
*rejects* the malformed value, but its `.parse()` (throwing) call was never wrapped in the route's
own error handling, so the rejection itself crashed the request instead of producing the clean
error response the code already intended.

## 3. `RGL-BLK-008` — all 3 webhook ingestion routes crash with `500` on a malformed `connectionId`

### 3.1 Discovery

Probes #6/#10 (§2) found `POST /api/webhooks/third-party-gps/<connectionId>` returns an uncaught,
empty-body `500` for any `connectionId` that is not a well-formed UUID — whether SQL-injection-
shaped, path-traversal-shaped, or simply malformed. This route requires **no credentials at all**
at the HTTP layer (a third-party provider's authenticity is established entirely by its HMAC
signature, verified inside the RPC) — meaning any anonymous internet caller can trigger this.

### 3.2 Root cause and blast radius

`app/api/webhooks/third-party-gps/[connectionId]/route.ts` passed the raw, unvalidated URL path
segment straight into `ingestThirdPartyProviderWebhookEvent()`
(`server/mutations/third-party-provider-adapter.ts`), which begins with
`IngestThirdPartyProviderWebhookEventInputSchema.parse(input)` — a **throwing** Zod parse, and the
schema's `connectionId` field is `z.string().uuid()`. A malformed `connectionId` fails this
validation and throws a `ZodError` *before any RPC call is ever made* — the route's own call site
did not wrap this in a `try`/`catch`, so the exception propagated uncaught to Next.js, which
returned its generic `500`.

**Confirmed identical in all 3 webhook ingestion routes**, by direct code inspection (not
individually live-reproduced a third time, since the code is byte-identical in shape):

| Route | Mutation | Schema field |
|---|---|---|
| `app/api/webhooks/third-party-gps/[connectionId]/route.ts` | `ingestThirdPartyProviderWebhookEvent` | `IngestThirdPartyProviderWebhookEventInputSchema.connectionId: z.string().uuid()` |
| `app/api/webhooks/finance-payment-gateway/[connectionId]/route.ts` | `ingestFinancePaymentGatewayWebhookEvent` | `IngestFinancePaymentGatewayWebhookEventInputSchema.connectionId: z.string().uuid()` |
| `app/api/webhooks/logistics-partner/[connectionId]/route.ts` | `ingestLogisticsPartnerWebhookEvent` | `IngestLogisticsPartnerWebhookEventInputSchema.connectionId: z.string().uuid()` |

All three routes' own header comments already document the intended contract — *"Never throws for
a bad signature/malformed payload/unmapped vehicle/duplicate event... Only a genuine
transport/serialization error throws"* — but did not account for a Zod validation failure on the
route's own path parameter, which is exactly this class of "genuine... error" the comment
anticipates throwing, just not one the route handler itself was prepared to catch.

**Not the same root cause as `RGL-BLK-007`** (a `23514` Postgres check-constraint violation inside
a completed RPC call), but the **same failure class**: an uncaught exception converting an
intended clean `4xx` denial into a generic `500`. Confirmed via `grep` that no other HTTP route in
this repository shares this exact "unvalidated path param passed straight into a throwing
mutation-level parse" shape — the customer/vendor `/api/v1/**` routes all wrap their equivalent
calls in a local `try`/`catch` already (verified by reading all 6 non-webhook, non-status
`/api/v1/**` route files; see §3.3).

### 3.3 Why this class was structurally invisible to existing tests

No route-level HTTP-layer test existed for any of the 3 webhook routes before this checkpoint
(confirmed: `find tests -iname "*webhook*"` returned only the unrelated
`tests/api/v1/webhook-event-types.test.ts`, a different endpoint). The `db-tests` suite exercises
`app.ingest_third_party_provider_webhook_event` (and its 2 siblings) directly with well-formed
UUIDs, never through the TypeScript route layer where the defect actually lives.

### 3.4 Fix

Wrapped each route's own ingest call in a local `try`/`catch`, returning the same
`{ ingestStatus: "invalid" }`, `400` shape each route already uses for its other early-rejection
cases (missing signature/timestamp/empty body) — the smallest, most local fix, consistent with
each route's own existing convention, touching no contract, mutation function, or migration.

### 3.5 Verification

New test files (none existed before): `tests/api/webhooks/third-party-gps.test.ts`,
`finance-payment-gateway.test.ts`, `logistics-partner.test.ts` — 4 tests per route (non-UUID
`connectionId` never reaches the RPC and returns `400`; a path-traversal-shaped one likewise; a
well-formed UUID with an `ok` RPC outcome still returns `200`, proving the fix does not regress the
happy path; a well-formed UUID with an `invalid` RPC outcome still returns `401`, proving the
denial-status mapping is unchanged). `node --experimental-strip-types --test tests/api/webhooks/*.test.ts`
— **10/10 pass**. Full suite: `pnpm run test` — **5463/5463 pass** (5453 + 10 new). `typecheck` 0;
`lint` 0 errors/337 warnings (unchanged).

**Not deployed to production this checkpoint.** Prompt 402 §12 forbids production mutation in this
prompt; the fix lives on this branch only until `RGL-015` ships it — the identical disposition
`RGL-401`/`RGL-BLK-007` already established. Registered `RGL-BLK-008`/`ISS-2026-296`, High,
`RESOLVED` in code, `NOT YET DEPLOYED`, owner `RGL-404`/`RGL-015`.

## 4. Retest: `RGL-BLK-002` Option 2's own security posture, live re-verified

The execution index's own checkpoint-freeze table (§2) carried a stale claim from Step 15 that
`app` is "not exposed through the Data API" — no longer accurate in the way that row originally
meant it, since the `RGL-BLK-002` Option 2 remediation (out-of-sequence, before `RGL-004`)
deliberately exposed `app`'s *functionality* (never its raw tables) through 2,367 `public.*`
security-mode-matched wrapper functions. This checkpoint re-verified, live, that this deliberate
exposure has not regressed:

- **No `app` table is directly reachable.** `information_schema.tables` for `table_schema='public'`
  returns exactly one row, `spatial_ref_sys` (PostGIS's own reference table) — zero application
  table exposed.
- **`public.ping()` (the Option 2 remediation's own canary) is still `service_role`-only.**
  `has_function_privilege('anon', 'public.ping()', 'EXECUTE')` and the same for `authenticated`
  both return `false`; `service_role` returns `true`.
- **13 `anon`-executable `SECURITY DEFINER` functions exist, every one individually accounted
  for**: 5 are this build's own intentional, unauthenticated ingestion/lookup surface
  (`ingest_driver_mobile_report`, `ingest_third_party_provider_webhook_event`,
  `ingest_finance_payment_gateway_webhook_event`, `ingest_logistics_partner_webhook_event`,
  `lookup_public_shipment_tracking` — each documented in its own capability's build log as
  deliberately anon-callable, authorization enforced inside the RPC itself via a bearer
  token/HMAC signature, never a Supabase Auth session); 5 are intentional pre-login resolution
  reads (`evaluate_tenant_brand`, `resolve_enterprise_idp_by_email_domain`, `resolve_locale_context`,
  `resolve_tenant_by_domain`, `resolve_tenant_locale` — needed before a session exists, e.g. to
  render a tenant's branding or resolve its SSO IdP on the login page); the remaining 3 are
  PostGIS's own stock `st_estimatedextent` overloads, confirmed via direct catalog inspection
  (`proowner = supabase_admin`, PostGIS's own stock function comment) to be a pre-existing
  extension default unrelated to this build's own code, in the same disclosed class as
  `spatial_ref_sys`'s own already-known `rls_disabled_in_public` finding. **Zero unexplained or
  newly-introduced anon-executable privileged function found.**
- **No storage bucket exists.** `select * from storage.buckets` returns zero rows — there is
  nothing to probe for the "file access" area; this is the expected, safe pre-launch state
  (consistent with `RGL-398`'s own finding that every tenant-scoped table is empty).
- **Spot-checked RLS on 5 sensitive tables** (`app.finance_journals`, `app.tenant_user_identities`,
  `app.accounts`, `app.api_keys`, `app.api_logs`): the first 3 have RLS enabled with exactly 1
  policy each (unchanged from `RGL-397`'s own verification); the latter 2 have RLS *disabled*, but
  hold **zero grants of any kind** to `anon`/`authenticated`/`PUBLIC` — confirmed via
  `information_schema.role_table_grants` — so the RLS-disabled state cannot be reached by any role
  PostgREST would authenticate as; only `service_role` (which bypasses RLS regardless) and direct
  superuser access can reach them. Not a defect: a table with zero client-role grants correctly
  has nothing for RLS to additionally restrict.
- **Fresh security-advisor pull** (2,523 lint entries, `get_advisors type=security`): 1
  pre-existing `ERROR` (`spatial_ref_sys`, `rls_disabled_in_public`, PostGIS's own table, already
  disclosed at `RGL-BLK-002`'s own review, unrelated to application code) — **no new `ERROR`-level
  finding**. 1,742 `WARN` `authenticated_security_definer_function_executable` (expected, the
  intentional Option 2 DEFINER-conversion pattern, count consistent with `RGL-397`'s own
  disclosure that this count is expected to grow, not a new defect class); 645 `WARN`
  `function_search_path_mutable` (pre-existing, unrelated to this checkpoint); 120 `INFO`
  `rls_enabled_no_policy` (tables with RLS enabled and zero policies — a fail-closed, not
  fail-open, posture: nothing can read them via PostgREST regardless, consistent with this
  schema's own "governed RPC only, no direct table access" architecture); 1 `WARN`
  `auth_leaked_password_protection` (pre-existing, unrelated); 1 `WARN` `extension_in_public`
  (PostGIS, pre-existing, unrelated).

**No regression found in the Option 2 remediation's own security posture.** The execution index's
stale schema-state row (§2) has been corrected in place, with the correction disclosed rather than
silently edited (see the row itself).

## 6. What this checkpoint is not — the tracked gap

Blueprint §20.3 (cited by `docs/architecture/10_TESTING_WORKSTREAM.md` §8.2) requires penetration
testing "using OWASP ASVS as the baseline control reference," describing it as **"independent
external verification"** — a third, separate lens from architecture design and delivery-scenario
review. **No such external engagement exists, has ever existed, or was attempted by this
checkpoint** — confirmed by repository-wide search (`grep -rin "penetration\|pentest"` across
`docs/build-log/full-system-hardening/`) finding zero prior pentest evidence anywhere, despite
`docs/security/THREAT_MODEL.md`'s own aspirational line 4 claiming Step 15 hardening would close
this out (it did not; no penetration-test record exists in that step's own build logs either).

This mirrors the exact posture `RGL-399` (no staging tier) and `RGL-400` (no UAT tier/acceptor)
already established for this range: an agent cannot produce or simulate independent third-party
verification. What this checkpoint *could* do — and did — is execute genuine, live,
read-only/negative security probes against the real production target (§2–§5), which found and
fixed one real defect. That is real evidence, but it is not a substitute for an independent
external pentest, and is not represented as one.

**Tracked gap, recorded formally:**

|---|---|
| Gap | No licensed, independent, third-party penetration-test engagement exists or has ever been performed against this system |
| What would resolve it | A named external security firm or independent tester executes an OWASP-ASVS-baselined engagement against a real (ideally staging, per `RGL-399`'s own still-open gap) target, and delivers a findings report |
