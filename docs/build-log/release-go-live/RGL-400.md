## 3. What was prepared — the human-independent half of readiness

**Scenario catalogue.** Built from Prompt 400 §29's own named regression/E2E flow list — the exact
flows this build's own `db-tests`/`e2e` suites already exercise mechanically, reframed here as
business-facing acceptance scenarios an acceptor would walk through, not new test authorship:

| # | Scenario | Golden path | Primary role(s) |
|---|---|---|---|
| 1 | Lead to job | Lead capture → qualification → prospect → quotation → customer conversion → job order | Sales rep, Sales manager |
| 2 | Shipment to billing readiness | Job order → shipment order → milestones → EPOD → billing-readiness evaluation | Ops coordinator, Finance |
| 3 | Actual cost to AP settlement | Actual cost capture → vendor bill → AP open item → settlement | Ops, AP clerk |
| 4 | Invoice to journal | Invoice issue → AR open item → journal posting → period close | Finance, Controller |
| 5 | WMS inbound to outbound | Inbound order → receiving → putaway → picking → packing → outbound ship-confirm | Warehouse staff, Warehouse supervisor |
| 6 | Portal visibility | Customer-portal shipment tracking, invoice/billing visibility, document center | Customer-portal user |
| 7 | Loyalty liability | Points earning → redemption → liability reconciliation | Loyalty program admin |
| 8 | Ticket SLA | Ticket creation → assignment → SLA clock → escalation → resolution | Support agent, Support manager |
| 9 | Tenant A/B isolation | Every above flow repeated for two tenants, confirming zero cross-tenant visibility | Supreme Admin (verification only) |

**Representative (non-real) data plan.** Reuses `RGL-398`'s own verified-safe conventions rather
than inventing a new data-generation approach: synthetic fixture domains (`.test` TLD, matching the
convention `RGL-398` confirmed clean across the whole `db-tests`/`load-tests` suite), placeholder
Indonesian NPWP-shaped tax IDs (sequential/repeating digits, the same pattern already validated),
and volumes modeled on `scripts/load-tests/seed.sql`'s own disclosed figures (1-2 tenants, a
handful of accounts per scenario, enough transactional rows per flow to be representative without
requiring bulk-load scale). No real tenant, customer, or personal data would be used, consistent
with Prompt 400 §27's own explicit requirement.

**Roles/accounts plan.** Maps directly onto this schema's own already-implemented role model — no
new role or permission would need to be invented: `tenant_admin`/org-scoped roles for scenarios
1-5 and 7-8, a `customer_user`-layer principal for scenario 6, and Supreme Admin for scenario 9's
cross-tenant verification only (never as a substitute for a genuine tenant-scoped actor in scenarios
1-8, consistent with RPD-022's own disclosed cross-tenant-access caveat).

**Evidence-capture method.** Each scenario's walkthrough would be captured as: the actor's role and
tenant, the exact UI screens/actions taken (or API calls, for portal/webhook-only flows),
before/after state for the record(s) touched, and the acceptor's own explicit accept/reject
decision per scenario with a reason — mirroring this repository's own `app.capture_audit_event`
shape (actor, tenant, action, entity, outcome, reason) so acceptance evidence is structurally
consistent with everything else this build already audits.

## 4. `UAT_READY` — not set, reasoned explicitly

`UAT_READY` is not set by this checkpoint. Prompt 400's own objective bundles environment deployment
together with data/roles/scenarios/evidence-capture ("deploy or refresh the... UAT environment and
prepare representative data...") — a single combined readiness state, not five independent ones.
§3 above genuinely completes the human-independent half (data/roles/scenarios/evidence-capture
method), but the environment half cannot be completed: there is no UAT-isolated environment to
deploy or refresh into (§2), and `RGL-399`'s own checkpoint already established that the one
available substitute (a Vercel preview) cannot be safely used without proof this session's tools
could not obtain — the identical constraint applies here, since UAT would need the same isolation
staging did.

Setting `UAT_READY` while the environment component is missing would be exactly the kind of
"genuinely true" violation §7.2 itself warns against — so it is left unset, alongside a clear
statement of what would need to be true for it to become genuinely set: a real, isolated
environment (the same missing piece `RGL-399` already tracked, owner `RGL-404`).

## 5. `UAT_ACCEPTED` — tracked gap, escalated, never simulated

**This is the load-bearing constraint of this entire checkpoint.** `UAT_ACCEPTED` is a human
business sign-off — a statement that a real person, acting for the business, exercised the
scenarios in §3 and accepted the release candidate as fit for go-live. No agent run, however
thorough, is evidence of that; an agent-executed end-to-end pass proves the flow *works*, never
that a business *accepts* it. Conflating the two would be, in the execution index's own words,
"the single most damaging false claim available in this range" — so it is not made here, in any
form, under any framing.

**Tracked gap, recorded formally:**

| Field | Value |
|---|---|
| Gap | No named business acceptor exists anywhere in this repository; `UAT_ACCEPTED` cannot be produced |
| What would resolve it | A named human, empowered by the business, walks the §3 scenario catalogue (or an equivalent) against a real or substitute environment and records an explicit accept/reject decision |
| Owner | `RGL-404` (Go/No-Go) and `RGL-412` (Closure Verification) — both must treat a missing `UAT_ACCEPTED` as an **open go-live gate**, per execution index §7.2's own binding instruction, not a formality to wave through |
| Escalation | To the operator — this is stated here and will be restated plainly in this session's own end-of-turn report, not left to be discovered only by reading this build log |
