# CPL-305 — Tracking

**Prompt ID:** `CG-S13-CPL-007` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/305_TRACKING_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (2026-08-17 — batch Tier C review across `CPL-305..309` complete; see §14)

## 1. What this checkpoint builds

CPL-305 gives a scoped customer-portal user a read-only, customer-safe composed view of a single shipment order's tracking state: the customer-visible milestone timeline, the arbitrated vehicle position (entitlement- and policy-gated), a coarsened ETA, and a freshness/degraded marker. This is a **pure read-composition capability over already-existing, already-VERIFIED canonical Operations/Advanced-TMS data** — zero new tables. `app.get_customer_shipment_tracking` never re-derives arbitration, milestone semantics, or ETA math; it composes `app.get_shipment_milestone_timeline`'s own filter shape (replicated, since that function is itself staff-gated), `app.get_vehicle_current_position` (the one sanctioned arbitrated-position read), and `app._compute_shipment_leg_eta` (the same internal function the already-VERIFIED anonymous public tracking link, `app.lookup_public_shipment_tracking`, already composes).

## 2. Design decisions (cited to the orchestrating task's own explicit list where given; disclosed where this checkpoint had to resolve something itself)

1. **One new RPC, `app.get_customer_shipment_tracking(p_tenant_id, p_actor_auth_user_id, p_shipment_order_id)`** — `assert_actor_is_session_identity` first (CPL-300's own Tier C lesson, applied from the first draft, read RPC included), then the IDENTICAL anti-enumerating scope check `app.get_customer_shipment_order` (CPL-304) already uses against `app.shipment_orders.shipper_account_id`.
2. **No new list RPC** — `app.list_customer_shipment_orders` (CPL-304) already exists; this capability's own list surface, per the orchestrating task's own instruction, reuses it. Only detail/timeline composition is new.
3. **Return shape is a new named composite TYPE (`app.customer_shipment_tracking_result`), not `returns table(...)`.** CPL-304's own migration disclosed a real, live-caught defect: `returns table(...)`'s own implicitly-named OUT parameters collide with same-named real columns referenced unqualified inside the body. This function's own field names (`shipment_order_id`, `tracking_entitled`, ...) genuinely collide with real columns elsewhere in the composition (`app.milestone_events.shipment_order_id`, `app.shipment_leg_tracking_policies.tracking_required`) — a plain `RETURNS <composite type>` function declares NO implicit OUT parameters at all, removing the defect class structurally rather than by remembering to alias every reference.
4. **Milestone timeline (a): replicates `app.get_shipment_milestone_timeline`'s own join/filter/order shape directly**, since that function is itself `OPS:View`-gated and not customer-callable — never calls it. Projected to an explicit customer-safe field allowlist (`code`/`name`/`category`/`eventTime`) inside a `jsonb_build_object`, never `to_jsonb(whole_row)` (C-07 discipline). Excluded, on direct inspection of `app.milestone_events`' full, ATW-228-widened column list, as staff-internal/internal source-conflict detail (source prompt §16): `received_time`, `location` (matches `app.lookup_public_shipment_tracking`'s own identical exclusion — this checkpoint's own deliberately conservative choice, the closest already-reviewed customer-facing precedent), `source`/`reason`/`corrects_event_id`, `idempotency_key`/`sequence_no`/`created_by`, and the four ATW-228 `source_class`/`source_confidence_score`/`source_freshness_status`/`source_candidate_id` provenance columns (source prompt §24's own "safe generic label" rule — no such label-configuration surface exists anywhere in this repository yet, so the raw source class is omitted entirely rather than inventing a new disclosure this checkpoint has no mandate to design).
5. **Milestone visibility is gated ONLY by `app.milestone_codes.is_customer_visible`, independent of tracking-package entitlement.** The orchestrating task's own design decision 6 scopes ONLY the vehicle-position/ETA portion to the entitlement gate; the milestone timeline is not raw telemetry and is not named as "live map/history" (source prompt §20/§24).
6. **Vehicle position (b): composed via `app.get_vehicle_current_position` only**, resolving the shipment's own active leg exactly like `app.lookup_public_shipment_tracking` does (`leg_status in ('dispatched','in_transit')`, earliest by `sequence_no`), then the leg's own current vehicle assignment (`app.resource_assignments`), included ONLY if that leg's own `app.shipment_leg_tracking_policies.customer_visible` flag is true — byte-for-byte the same eligibility test the already-reviewed public tracking link uses. Exposed field set (`vehicle_position_geojson`/`vehicle_position_updated_at`/`vehicle_position_status`) matches `app.lookup_public_shipment_tracking`'s own exactly — no `speed_kmh`/`heading_degrees`, no raw `source_type`.
7. **ETA (c): `app._compute_shipment_leg_eta` is the confirmed, real, currently-VERIFIED function** — grep-confirmed. `app.get_shipment_leg_eta_projection` (ATW-228) is a thin `OPS:View` + record-scope-gated wrapper around it and is NOT customer-callable, the identical situation as the milestone timeline (decision 4). This migration calls the internal function directly — the SAME function `app.lookup_public_shipment_tracking` already composes, granted to `service_role` only but callable here because this `SECURITY DEFINER` function runs as its own owner. Coarsened to `eta_status`/`eta_at` with the identical `<= 30` minutes "still on_time" banding `app.lookup_public_shipment_tracking`'s own already-reviewed `live_eta_status`/`live_eta_at` widening uses (ATW-228 design note 7) — never a raw `remaining_distance_km`/`delay_minutes` figure.
8. **Freshness/degraded marker (d): `vehicle_position_status`, computed against the TENANT's own configured `freshness_threshold_seconds`** (`app.resolve_tenant_tracking_source_policy`, ATW-226A — explicit override or the system default of 300 seconds), with the identical 1x/3x banding `app.get_vehicle_source_health`/`app.lookup_public_shipment_tracking` already use — a reused, tenant-configurable threshold, never a new hardcoded constant.
9. **`position_unavailable_reason` is a disclosed addition beyond the orchestrating task's own literal (a)-(d) list** — mirrors `app._compute_shipment_leg_eta`'s own "never a fabricated estimate, always a named reason" discipline and the source prompt's own alternative flow (§22). One of `tracking_not_entitled` / `no_active_leg` / `no_vehicle_assigned` / `not_customer_visible` / `no_live_position`, or `null` once a real position is included.
10. **Subscription/package entitlement gates the vehicle-position/ETA portion on the EXISTING tenant-level `app.is_shipment_tracking_entitled`** (source prompt design decision 6; `00_EXECUTION_INDEX.md` §3 item 8's own disclosed deferral). No new customer-portal-specific entitlement tier is invented — a tenant not entitled to live tracking at all means no customer of that tenant is either.
11. **No table this migration touches gains a new RLS policy** — no table is created or altered. The function reads canonical tables directly as its own `SECURITY DEFINER` owner with its own explicit scope check in code (ADR-0024 Part A).
12. **REST/GraphQL transport (ADR-0024 Part C):** service layer + Server Actions/RSC fetch + UI only, no `app/api/` HTTP route — identical in kind to CPL-300..304's own disclosed residual gap.
13. **No edit to `scripts/db-tests/rbac-enforcement.sql`** — verified by direct analysis, not merely assumed: the ISS-2026-033 sweep's own `base` CTE matches any function whose `prosrc` text contains the substring `resolve_customer_account_scope` (already a recognized base keyword since CPL-300); `app.get_customer_shipment_tracking`'s own body literally calls `app.resolve_customer_account_scope(...)`, placing it directly in `base` (not merely reached via the call-graph closure). The separate ISS-2026-032 "side-effecting function" sweep filters on `provolatile = 'v'` (volatile) — this function is declared `stable`, exempting it from that sweep entirely, mirroring every other Phase 8 read RPC. Confirmed live: the full `rbac-enforcement.sql` gate passed in this checkpoint's own `db:test` run with zero edits to that file.
14. **UI: extends the existing `customer-shipments/[shipmentOrderId]` detail page (CPL-304)** with a new sub-component (`customer-shipment-tracking-panel.tsx`) plus a small single-vehicle map companion (`customer-shipment-tracking-map.tsx`, reusing `operations/fleet-control-tower/vehicle-map.tsx`'s own dynamic-Leaflet-import technique for one point rather than a fleet list) — per the orchestrating task's own design decision 7, not a new sibling route. `customer-shipment-detail-panel.tsx` (CPL-304, already `VERIFIED`) is completely untouched; only `page.tsx` is edited, to fetch tracking non-fatally and render the new panel alongside the existing one.
15. **Exception banners and ePOD/document actions named in the source prompt's own §15 UI/UX impact are deliberately NOT built here** (disclosed, C-23 discipline) — Shipment Monitoring (Prompt 306), ePOD Access (Prompt 307), and Document Center (Prompt 308) are this same batch's own next capabilities, explicitly chartered for exactly that surface (see §4 "Workstream 3" of `00_EXECUTION_INDEX.md`). Composing that data into this checkpoint's own RPC would risk the "duplicate composition, second independently-evolving read path" anti-pattern ADR-0024 Part A already rejected once.
16. **Read-access auditing (source prompt §18: "Audit customer tracking access, map access, exports, denials...") is not built this checkpoint** (disclosed, C-23 discipline) — mirrors CPL-300/CPL-304's own established, unbroken precedent that customer-facing READ RPCs are not individually recorded via `app.capture_audit_event` in this repository (only WRITE RPCs are, e.g. CPL-304's own `request_customer_shipment_order_change`/`respond_to_customer_shipment_order_change_request`). Building a genuinely new per-read audit primitive would be a repository-wide precedent change no existing Phase 8 read RPC has made, beyond this bounded capability's own mandate.
17. Per `ERR-2026-004` (`docs/runtime/ERROR_LEDGER.md`): this migration carries its own explicit `revoke execute on all functions in schema app from public` statement before its final grant.
