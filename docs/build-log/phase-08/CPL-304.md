# CPL-304 — Shipment Order

**Prompt ID:** `CG-S13-CPL-006` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/304_SHIPMENT_ORDER_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (2026-08-16 — Batch 1's own Tier C review closed across all of CPL-301..304 together; see §14 for the 4-lens review/fix record — a Critical cross-account IDOR and a High concurrency/race defect were found and fixed at root cause — and the orchestrating session's own independent gate re-run)

## 1. What this checkpoint builds

CPL-304 gives a scoped customer-portal user a read-only, customer-safe view of every shipment order across their account/site scope, plus a narrow "request a change" write surface — while Operations remains the sole owner of shipment execution. Structurally different from CPL-302/303: this is a READ PROJECTION over the already-existing, Operations-owned `app.shipment_orders` table (OPS-169), not a parallel shipment-truth table. `app.confirm_shipment_order`/`app.cancel_shipment_order` stay completely untouched, staff-only.

## 2. Design decisions (cited, not re-derived — full rationale lives in the migration's own header)

1. **Read RPCs are a customer-safe PROJECTION, never `app.shipment_orders` itself and never `select *`.** The full column list of `app.shipment_orders` (20260727100000, read in full) was confirmed directly; nothing on it is a tariff/rate/margin field (per that table's own design comment — cost/selling data lives in `app.job_orders`' own `revenue_snapshot`/`credit_snapshot`), but several columns are staff-internal by inspection and excluded from the 21-column customer-safe `returns table(...)` shape: `idempotency_key` (technical dedup token), `owner_user_id`/`org_unit_id` (internal record-scope/ownership plumbing), `created_by` (a staff actor label), `split_reason` (a literal staff-authored "reason" column), and `basis_quantity`/`basis_weight_kg`/`basis_volume_cbm` (internal cross-shipment allocation bookkeeping for the parent Job Order's total split basis, not a fact about this shipment's own cargo). `allocated_quantity`/`allocated_weight_kg`/`allocated_volume_cbm` (this shipment's own real cargo figures) ARE kept. `job_order_id`/`shipper_account_id` are kept as opaque reference ids (CPL-303's own `linked_job_order_id`/`linked_shipment_order_id` already return exactly this class of reference verbatim — not a new disclosure).
2. **`app.confirm_shipment_order`/`app.cancel_shipment_order` are never called from anything in this migration** — grep-confirmed (and live-proven structurally, §11 below). Both stay OPS:Edit-gated, staff-only, byte-for-byte untouched.
3. **`app.customer_portal_shipment_change_requests` is a new, portal-owned "request a change" table**, per the given column list (id, tenant_id, account_id, shipment_order_id, requested_by_auth_user_id, request_type, details, status, idempotency_key, record_version, timestamps, staff_response/staff_responded_by/at). Disclosed refinements:
   - **`account_id` is derived from the shipment order's own `shipper_account_id` at create time, never customer-supplied** — unlike CPL-303's own `p_account_id` (customer-supplied, cross-checked separately), the shipment order here already structurally names its own account, eliminating the whole account-mismatch bug class rather than re-deriving the same guard.
   - **The shipment-order lookup inside the create RPC combines "genuinely nonexistent" and "exists but out of scope" into ONE `shipment_order_not_found` error** — the identical anti-enumeration technique CPL-303's own `create_customer_booking_request_draft` already applies to a referenced (non-primary) record.
   - **No dedicated append-only history table** (contrast with CPL-303's 6-status machine). This table's own 4-status machine (`submitted`/`acknowledged`/`resolved`/`rejected`) is exactly as simple as CPL-302's own 4-status table, which also has no dedicated history table — `capture_audit_event` on every mutation plus the row's own real timestamps are the transition record, mirroring CPL-302's precedent.
   - **The staff respond RPC takes `p_expected_version`** (record_version optimistic concurrency, the general house style), locks the row, and is idempotent only for a retry landing on the exact SAME target status AND response text — mirrors `app.submit_customer_booking_request`'s status-check-before-version-check shape. Unlike CPL-303's own staff link RPC (deliberately no `p_expected_version` — a one-directional terminal-ish conversion), this RPC's `acknowledged → resolved|rejected` middle state is a genuine second race a concurrent staff actor could hit, so the version guard is load-bearing here.
   - **One additional customer RPC beyond the two explicitly named ones**: `app.list_customer_shipment_order_change_requests`. Neither the shipment order projection nor the change-request table gives the customer any way to read back a request it already submitted or a staff response once given — this closes that "submit into a void" gap (`RECURRING_DEFECT_TAXONOMY.md` C-20, applied to the read side of a write flow). Disclosed as an addition, not a deviation — the two named RPCs are otherwise built exactly as specified.
4. **Alternative flow needs no new "locked" concept.** `app.shipment_orders.status` (`draft`/`confirmed`/`cancelled`) is rendered plainly; a `confirmed`/`cancelled` shipment is already immutable from the customer side (no customer RPC ever mutates `app.shipment_orders`), and the change-request path is exactly the alternative action named. No ticket-creation INTEGRATION is built (Prompt 313's own job) — the detail UI carries a plain link to the existing `customer-tickets` route.
5. **RLS: `authenticated` holds ZERO direct grant** on the new change-request table, mirroring CPL-300/302/303. `app.shipment_orders` itself is completely untouched — no RLS policy on it is edited, narrowed, or widened; it already correctly denies `customer_user` by default per `CG-S10-ATW-032` (re-verified live in this checkpoint's own db-test).
6. **Two new, purely additive covering indexes on the EXISTING, already-applied `app.shipment_orders` table** — `(tenant_id, updated_at desc, id desc)` and `(tenant_id, shipper_account_id)` — mirrors ATW-023's own companion pagination-index-migration precedent, built inline.
7. **REST/GraphQL transport (ADR-0024 Part C)**: service layer + Server Actions + UI only, no `app/api/` HTTP route — identical in kind to CPL-300/301/302/303's own disclosed residual gap.
8. **No edit to `scripts/db-tests/rbac-enforcement.sql`** — every new function calls `app.assert_actor_is_session_identity` directly as its own first statement (reads and writes alike), or is covered transitively by `app.resolve_customer_account_scope`/`app.evaluate_permission` (both already-recognized base keywords) — mirrors CPL-303's own identical, already-verified "no edit required" precedent.

## 3. A real defect this checkpoint's own migration authoring found and fixed before shipping

The first draft of `app.get_customer_shipment_order` used an unqualified `where id = p_shipment_order_id and tenant_id = p_tenant_id` against `app.shipment_orders`. Because this function's own `returns table (id uuid, tenant_id uuid, ...)` shape creates implicitly-named OUT parameters (`id`, `tenant_id`, ...) visible inside the function body, Postgres genuinely could not resolve whether an unqualified `id`/`tenant_id` inside the query meant the OUT parameter or the table's own same-named column — live-caught on the very first db-test run (`ERROR: column reference "id" is ambiguous`), not reasoned about in advance. **Fixed** by adding an explicit table alias (`from app.shipment_orders so where so.id = ... and so.tenant_id = ...`) and qualifying every reference. `app.list_customer_shipment_orders` (the sibling `returns table(...)` function) was already written with a qualified alias throughout from the start and needed no fix — this defect is disclosed as an authoring-time catch, not a design flaw repeated across both functions.

## 6. Schema

`app.customer_portal_shipment_change_requests` (id, tenant_id, account_id, shipment_order_id → `app.shipment_orders`, requested_by_auth_user_id, request_type `check in ('reschedule','cancel','other')`, details, status `check in ('submitted','acknowledged','resolved','rejected')`, idempotency_key, record_version, created_at, updated_at, staff_response, staff_responded_by, staff_responded_at). Constraints: request_type/status checks; `details` mandatory non-empty; `staff_response`/`staff_responded_by`/`staff_responded_at` mandatory together iff status ≠ `submitted`, and all three null while `submitted`. Unique `(tenant_id, idempotency_key)`, partial (not-null). Status-transition trigger: `submitted → acknowledged|resolved|rejected`; `acknowledged → resolved|rejected`; `resolved`/`rejected` terminal. Combined touch-row trigger (updated_at + record_version). Covering index `(tenant_id, updated_at desc, id desc)`; supporting indexes on `shipment_order_id`/`account_id`.

Two additive covering indexes on the existing `app.shipment_orders` (design decision 6): `(tenant_id, updated_at desc, id desc)`, `(tenant_id, shipper_account_id)`.

## 7. RLS

`app.customer_portal_shipment_change_requests`: `enable row level security`; `grant select, insert, update, delete ... to service_role` only — `authenticated` holds **zero** direct grant (live-verified in the db-test: a real `set local role authenticated` session raises a genuine `insufficient_privilege` permission-denied error on a raw `select`). `app.shipment_orders` itself is completely untouched by this migration — its own pre-existing `shipment_orders_select_scoped` policy (`app.can_access_record`) still correctly denies a `customer_user`-layer principal with no staff org-unit/owner relationship (live-verified in this checkpoint's own db-test, not merely assumed unchanged). The 5 RPCs above are the only sanctioned customer-facing access path to shipment order data.

## 11. Adversarial testing — live, against a real disposable Postgres 16 database (not reasoned about)

All of the following used `postgresql://127.0.0.1:5432`, a freshly created disposable database, the full migration set (through `20260801050000`) applied, using the standard `set_config('request.jwt.claims', ...)` + `set role authenticated` forged-session technique where a real session was needed.

1. **Get is anti-enumerating and returns only the customer-safe projection** — alpha-admin successfully reads their own confirmed Alpha shipment order (real `allocated_weight_kg`/`mode`/`origin`/`destination` values verified); a genuinely nonexistent id and beta-admin reading Alpha's own shipment order both raise the IDENTICAL `record_not_found`. A direct catalog inspection (`pg_get_function_result`) proves the function's own declared return shape structurally excludes `idempotency_key`/`owner_user_id`/`org_unit_id`/`created_by`/`split_reason`/`basis_*` — not merely that the TypeScript contract happens not to map them.
2. **List keyset pagination, account/status filters, deny-by-default, cross-tenant isolation** — pagination at `limit=1` for alpha-admin visits exactly 1 row (Beta's own shipment, a different account, correctly excluded); an explicit account filter returns exactly 1; a `draft`-status filter returns 0 (fixture is confirmed); a cso2 identity and a zero-scope impersonator both see 0 rows, never an error; a half-supplied cursor raises `invalid_cursor`.
3. **Request-a-change validates request_type/details, is scope-checked with a combined anti-enumerating error, derives `account_id` server-side, and is idempotent** — an invalid request type and whitespace-only details are both rejected; beta-admin acting on Alpha's shipment order and a genuinely nonexistent shipment order id both raise the IDENTICAL `shipment_order_not_found`; a repeated call with the same idempotency key but a DIFFERENT request_type/details returns the ORIGINAL row unchanged, and exactly one row exists for that key; the created row's own `account_id` matches the shipment order's real `shipper_account_id`, never a client-supplied value.
