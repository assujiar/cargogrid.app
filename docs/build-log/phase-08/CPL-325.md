### 6.2 `now()`-vs-`clock_timestamp()` ordering defect, `app.get_customer_portal_account_profile` (Medium → Fixed)

`supabase/migrations/20260801290000_harden_customer_portal_profile_change_request_latest_pending_ordering.sql` — live-reproduced: two `app.submit_customer_profile_change_request` calls in one transaction produced byte-identical `now()`-frozen `created_at` values; the "latest pending" resolver (`order by created_at desc limit 1`, no tiebreak) reported the wrong row as latest. ### 6.3 Redemption hold-vs-composition TOCTOU race (High → Fixed)

`supabase/migrations/20260801300000_harden_customer_portal_loyalty_redemption_hold_race.sql` — `app.hold_loyalty_account_tier_benefits`, `app.release_loyalty_account_tier_benefits`, `app.submit_loyalty_redemption`, and `app.decide_loyalty_redemption`'s approve branch now all take a per-loyalty-account `pg_advisory_xact_lock(hashtextextended(loyalty_account_id::text, 6))` before their own hold-check/hold-write, mirroring this repository's own already-established per-entity advisory-lock convention exactly (salt 3 = CPL-317's tier recalculation; salt 4 = CPL-318's point consumption; salt 6 here, a new, independent lock domain so this fix does not also serialize against unrelated calls). The lock is held for the remainder of each call's own transaction (auto-released at commit/rollback, reentrant within one transaction), so a hold-open/release and a redemption submit/decide for the SAME account can no longer interleave: whichever transaction reaches the lock first completes its own full check-then-act sequence before the other proceeds. `app.open_loyalty_fraud_review_case` (CPL-322) composes `app.hold_loyalty_account_tier_benefits` directly, so this fix covers that path too with no change needed to the fraud-review migration.

Live-verified: a new deterministic, genuinely two-process race (`scripts/db-tests/customer-loyalty-redemption.sql`, launched via the repository's own established `wms-picking-concurrency-helper.sh`) races `app.hold_loyalty_account_tier_benefits` against `app.decide_loyalty_redemption(approve)` on the same account; the post-fix invariant (a `fulfilling` redemption's own `decided_at` must be strictly before the hold's own `held_at` — never the reverse) holds under a real concurrent race.

### 6.4 Liability reconciliation non-atomic snapshot (High → Fixed)

`supabase/migrations/20260801310000_harden_customer_portal_loyalty_liability_reconciliation_snapshot_atomicity.sql` — `app.execute_loyalty_liability_reconciliation_run`'s 3 separate top-level source-read statements (points/entitlements/redemptions), plus a 4th separately-snapshotted nested point-balance-cache lookup, are replaced with **one single top-level SQL statement** — three independent `jsonb_agg()` scalar-subquery expressions in one `SELECT`'s own target list, each drawing from its own CTE, with the point-balance cache lookup inlined as a correlated subquery in the same statement. Under READ COMMITTED, a single statement takes exactly one MVCC snapshot for its own execution including every subquery nested inside it, restoring the function's own already-documented invariant ("a run reflects a normal MVCC-consistent snapshot," `20260801250000`) which the prior 3(4)-statement shape did not actually deliver. Every downstream loop body (mismatch detection, total accumulation) is byte-identical to the prior logic — only the data source changed, from a live-table query to an already-snapshotted `jsonb_to_recordset()` projection of the same rows/columns.

Live-verified via a real, deterministic, lock-gated three-process race (`scripts/db-tests/customer-loyalty-liability-reconciliation.sql`, a new dedicated helper `scripts/db-tests/loyalty-liability-reconciliation-atomicity-gate-helper.sh` extending the repository's own 2-process concurrency-helper convention to a 3rd "gate" party): a gate session holds an `ACCESS EXCLUSIVE` lock on `app.loyalty_benefit_entitlements` while a mutator reverses a fulfilling redemption (touches points/redemptions, not entitlements, so it commits freely under the gate) and a reader runs the reconciliation function (blocks on the gate, since its own single statement reads entitlements too). Two independently-computed reference runs (strictly before and strictly after the reversal) bound the only two valid combined totals; the raced run's own combined total matched the fully-after snapshot exactly — never a third, torn value — live-confirmed (`PASS: the raced reconciliation run's own combined total (515) exactly matches one of the two valid consistent snapshots (before=505, after=515)`).
