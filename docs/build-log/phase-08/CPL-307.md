# CPL-307 — ePOD Access

**Prompt ID:** `CG-S13-CPL-009` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/307_EPOD_ACCESS_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (2026-08-17 — batch Tier C review across `CPL-305..309` complete; see §14)

## 1. What this checkpoint builds

CPL-307 gives a scoped customer-portal user read access to the delivery evidence (ePOD — electronic proof of delivery) Operations already captured for their own shipment orders: receiver name, capture timestamps, and the signature/photo evidence files themselves, once independently re-verified as scan-clean. This is a **pure read composition over already-existing, already-VERIFIED canonical Operations/Platform data** (`app.epod_captures`, OPS-177; `app.files`, PLT-128) — zero new tables, one new RPC. Operations remains the sole owner of ePOD capture, review, and revision; nothing here mutates `app.epod_captures` or `app.files`.

The capability's own defining constraint (disclosed in full, migration design decision 2) is that `app.epod_captures`/`app.start_epod_capture` never populate `app.files.customer_account_ref`, so the generic `app.can_access_record` customer branch — and therefore `app.authorize_file_access` itself — can never authorize a customer_user actor for an ePOD evidence file. Rather than backfilling that column retroactively (an out-of-scope data-migration task of its own) or widening `app.authorize_file_access`, this checkpoint builds a dedicated, self-contained authorization path that independently re-derives the same facts a backfill would have encoded, narrower but exactly as safe.

## 2. Design decisions (cited where given by the orchestrating task; disclosed where this checkpoint had to resolve something itself)

1. **One new RPC, `app.get_customer_epod(p_tenant_id, p_actor_auth_user_id, p_shipment_order_id)`.** Zero new tables. `assert_actor_is_session_identity` is the first statement (CPL-300's own Tier C lesson, read RPCs included).
2. **The known blocking gap, confirmed live by direct read of OPS-176/177 and PLT-128 in full (not assumed from the orchestrating task's own kickoff-research summary alone)**: `app.epod_captures`/`app.start_epod_capture` never write `app.files.customer_account_ref`, so `app.authorize_file_access`'s own `app.can_access_record` branch structurally cannot match an ePOD evidence file for a `customer_user` actor. Backfilling that column is explicitly out of this bounded task's own scope (its own data-migration task, per the orchestrating task's own instruction) — `app.epod_captures`, `app.files`, and every OPS-176/177 function are byte-for-byte untouched, grep-confirmed. Instead, `app.get_customer_epod` independently performs (a) caller-is-actor, (b) the same anti-enumerating shipment-order scope check `app.get_customer_shipment_order` (CPL-304) already uses, (c) latest-completed-capture discovery, (d) a LIVE, direct re-verification of every referenced evidence file against `app.files` (tenant, record scope, soft-delete state, `malware_scan_status = 'clean'`) — never via `app.authorize_file_access` — and (e) a durable access-audit row plus a customer-safe metadata projection, never a fabricated signed URL (decision 8 below). Disclosed as a deliberate, narrower-but-safe alternative, matching CPL-300's own precedent of disclosing design alternatives explicitly.
3. **`app.file_access_logs` (PLT-128) is reused directly** — its own shape (`tenant_id`, `file_id`, `accessed_by_auth_user_id`, `access_type` incl. `signed_url_issued`, `result` granted/denied, `reason`, `correlation_id`) fits exactly; no parallel audit table is built. One row per referenced evidence file, inserted directly by this `SECURITY DEFINER` function. For the two states with no real file to log against (nonexistent/out-of-scope shipment; a shipment with no completed capture yet), `app.capture_audit_event` carries the outcome instead, `p_reason` always a short machine-readable code, never free text (C-24 discipline). **Disclosed deviation from CPL-300/304/305's own "read RPCs are not individually audited" precedent** — deliberate, since ePOD evidence is content access in PLT-128's own sense, not an ordinary business-data read.
4. **Anti-enumeration is NOT uniform across every failure mode** — a nonexistent shipment order and an out-of-scope one collapse into ONE `record_not_found` (mirrors CPL-304 byte-for-byte), but once scope is genuinely established, "no completed capture yet" (`not_available`) and "a completed capture's evidence is quarantined" (`quarantined`) are real, distinct, non-error `epod_status` values on the SAME returned row — never collapsed into each other or into a generic error. The source prompt's own alternative flow requires exactly this ("show exact status"), and collapsing them would buy no real security benefit: both states are only reachable once the caller's own legitimate scope on this exact shipment order is already an established fact.
5. **`epod_status` is a whole-capture verdict, not a per-file one.** If ANY referenced evidence file fails live re-verification, the entire capture reports `quarantined` and `files` returns empty — never a partial list mixing safe and unsafe evidence.
6. **Customer-visible fields minimize personal data (source prompt §24).** `receiver_name`/`captured_at`/`server_received_at` are shown in every reachable state (trusted `app.epod_captures` columns, never derived from file content, so withholding them while quarantined buys no safety). Excluded: `receiver_position` (no customer-facing purpose), `delivery_geog` (a precise `geography(Point,4326)` — the exact "minimize personal data" concern; omitted entirely rather than inventing a new coarsening function this bounded task has no mandate to design), `reviewed_by_auth_user_id`/`reviewed_at`/`review_notes` (staff-internal review workflow — `review_notes` is free-text staff commentary, the same exclusion class CPL-304 already applies to "internal notes/reason columns"), and `milestone_event_id`/`version_group_id`/`version_number`/`idempotency_key`/`created_by`/`record_version` (technical/staff plumbing).
7. **`returns table(...)` with every reference qualified by a table alias from the first draft** — applying CPL-304's own live-caught lesson (an unqualified `shipment_order_id` reference is genuinely ambiguous against this function's own same-named OUT parameter) proactively rather than retrofitting after a failure.
8. **No signed URL is fabricated.** Direct inspection of this entire repository (every `.ts`/`.tsx` file, every migration, `supabase/config.toml`) confirms zero live Supabase Storage integration or provisioned bucket exists anywhere. `app.authorize_file_access`'s own doc comment names itself "the single gate a real signed-URL-issuing server action calls BEFORE generating one," and its own closest, only real consumer (`app.access_vendor_compliance_document_evidence`, PRC-253) stops at exactly that boundary too. Building a new `supabase.storage.from(...).createSignedUrl(...)` call now, against a bucket that has never been provisioned anywhere in this repository, would not be composing an existing mechanism — it would be inventing new, unprovisioned infrastructure no other capability (including PLT-128, Storage's own canonical owner) has built, the exact scope-creep the orchestrating task's own "compose it, do not reinvent Storage signing" instruction warns against. This migration composes up to the SAME disclosed boundary PLT-128/PRC-253 already established and stops there — authorize, log, return safe file metadata (`fileId`/`role`/`originalFilename`/`mimeType`/`sizeBytes`), never `storage_path`, never a URL.
9. **RLS: this migration touches ZERO table.** No new table; no RLS policy on `app.epod_captures`/`app.files`/`app.file_access_logs` is edited. Both source tables' own pre-existing policies already correctly deny a bare `customer_user` by default (re-verified live in this checkpoint's own db-test).
10. **REST/GraphQL transport (ADR-0024 Part C)**: service layer + Server Action + UI only, no `app/api/` HTTP route — identical in kind to CPL-300..306's own disclosed residual gap.
11. **No edit to `scripts/db-tests/rbac-enforcement.sql`** — `app.get_customer_epod` calls `app.assert_actor_is_session_identity` directly and `app.resolve_customer_account_scope` (both already-recognized base-regex authority primitives since CPL-300) — confirmed live, no edit required.
12. **UI: extends the existing `customer-shipments/[shipmentOrderId]` detail page** (CPL-304, already extended by CPL-305/306) with a new sub-section — never a new sibling route.
13. **The "Download" action is a real, audited Server Action, never a decorative stub.** Given decision 8 (no working file URL exists to hand back), the UI's "Download" button is a real `useActionState`-bound Server Action that re-invokes `app.get_customer_epod` — a genuine, freshly-audited access attempt (a second, distinct `app.file_access_logs`/`app.capture_audit_event` entry beyond the page's own eager load) — and displays the confirmed-fresh, customer-safe file metadata inline, mirroring `DocumentVersionPanel`'s own established "View evidence" pattern (the only other real "download" flow in this repository). A purely inert/disabled button would have been a placeholder action, which `AGENTS.md` forbids on a completed task; this design gives the control a real, verifiable effect instead.
14. Per `ERR-2026-004` (`docs/runtime/ERROR_LEDGER.md`): this migration carries its own explicit `revoke execute on all functions in schema app from public` statement before its final grant.

### 10.1 A real defect this checkpoint's own first live db-test run found and fixed before shipping

The first draft of `app.get_customer_epod` appended a plain string literal directly to a `text[]` variable (`v_file_roles := v_file_roles || 'signature';`). Because an unadorned string literal is `unknown`-typed in Postgres, `text[] || unknown` resolved to the array-concatenation operator (which expects an array-literal *string*) rather than the array-append-element operator — live-caught on the very first `psql -f` run against a real disposable database (`ERROR: malformed array literal: "signature"`), not reasoned about in advance. **Fixed** by explicitly casting every such literal to `text` (`'signature'::text`/`'photo'::text`) to force scalar-append resolution, with a comment left in the migration itself naming the exact defect class for future authors. The harness was then re-run in full (§10 above) and passed clean.
