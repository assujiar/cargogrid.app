# CPL-309 — Warehouse Inventory Visibility

**Prompt ID:** `CG-S13-CPL-011` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/309_WAREHOUSE_INVENTORY_VISIBILITY_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (2026-08-17 — batch Tier C review across `CPL-305..309` complete; see §14)

## 1. What this checkpoint builds

CPL-309 gives a scoped customer-portal user read-only visibility into WMS-owned warehouse inventory (stock balances by SKU/lot/serial/status/location) and their own warehouse eligibility grants — but its real job is closing a genuine, disclosed scope-composition gap between two already-shipped, already-VERIFIED capabilities:

- **ATW-023** (Phase 5) built the first customer-facing inventory-read RPC layer, but every one of its RPCs resolves scope via `app.resolve_customer_owner_account_scope`, which reads ONLY the legacy single-account `app.principal_memberships.customer_account_ref` marker.
- **CPL-300** (Phase 8) introduced a NEW real many-to-many grant table (`app.customer_portal_account_memberships`) and a NEW resolver (`app.resolve_customer_account_scope`) that returns the UNION of the legacy marker and the new grant table.

A customer_portal user granted access to a SECOND account only through CPL-300's new grant table — never through the legacy marker — is invisible to every ATW-023 RPC: `app.resolve_customer_owner_account_scope` has no way to see a grant that exists only in the new table. This is an under-scoping (false-negative) gap, already registered as `ISS-2026-117` (Medium, `OPEN`), disclosed at CPL-301 as "composed around, not fixed." This checkpoint is that fix, scoped to warehouse/inventory visibility per its own charter — a new, additive migration that composes two already-verified, unmodified primitives (CPL-300's widened resolver + ATW-023's own warehouse-eligibility predicate) that were simply never wired together, mirroring ATW-023's own RPC surface exactly.

## 2. Design decisions (cited where given by the orchestrating task; disclosed where this checkpoint had to resolve something itself)

1. **ADR-0024 Part A governs the shape** — a new `SECURITY DEFINER` RPC composing a scope resolver and a domain-specific eligibility predicate, deny-by-default, anti-enumerating, keyset-paginated. Raw-table RLS is never reopened. Every Phase 8 capability from CPL-300 onward already follows this; this checkpoint is no exception.
2. **The fix is composition, not a third re-derivation.** `app.evaluate_customer_portal_inventory_access` is a new, narrow gate function that composes `app.resolve_customer_account_scope` (CPL-300, unmodified) and `app.customer_warehouse_eligibility_active` (ATW-023, unmodified, reused verbatim — no new table). Identical shape to ATW-023's own `app.evaluate_customer_inventory_access`, only the resolver call differs. ATW-023's own applied migration is never edited (`AGENTS.md`: never edit an applied migration).
3. **Projection-for-projection parity with ATW-023.** `app.get_customer_portal_inventory_balance`/`app.list_customer_portal_inventory_balances` carry the byte-identical 13-column projection (`id`/`warehouse_id`/`owner_account_id`/`item_master_id`/`location_id`/`lot_number`/`serial_number`/`status`/`on_hand`/`reserved`/`held`/`available`/`record_version`/`updated_at`), the same all-zero-row exclusion, and the same per-row/per-warehouse decomposition for list-level performance (the owner-scope array is resolved ONCE per call via `app.resolve_customer_account_scope`; the warehouse-eligibility check runs per row, since it genuinely varies per row and cannot be precomputed). `app.list_customer_portal_warehouse_eligibility` mirrors `app.list_customer_warehouse_eligibility` exactly (same columns including `revoked_reason`, no OPS RBAC gate at all).
4. **Every RPC below calls `app.assert_actor_is_session_identity` as its OWN literal first statement** — not merely relying on the transitive check already inside `app.resolve_customer_account_scope` (which itself calls it, per CPL-300's own design). Applied from the first draft, per the explicit, repeated lesson from every prior Phase 8 batch (CPL-300 Tier C Finding 1; CPL-305/307/308's own identical discipline).
5. **Anti-enumeration mirrors ATW-023 design note 5 exactly** — `app.get_customer_portal_inventory_balance` raises the IDENTICAL `record_not_found` (errcode `no_data_found`) whether the balance genuinely does not exist, belongs to a different tenant, or exists but fails the gate.
6. **No new denial-audit RPC.** `app.record_customer_inventory_access_denial` (ATW-023, generic actor/resource-type/resource-id, already granted to `authenticated`) is reused exactly as-is. `server/queries/customer-portal-inventory.ts` calls it the same way `server/queries/customer-inventory-access.ts` already does: a separate follow-up RPC call, in a new transaction, after catching the get RPC's own anti-enumerating error — never inside the same transaction as the `RAISE` (ATW-023 design note 9's own proven constraint).
7. **RLS on `app.inventory_balances`/`app.warehouse_customer_eligibility` is confirmed UNCHANGED, not assumed** — direct read of each table's own already-applied RLS `SELECT` policy (`20260730190000_create_advanced_tms_inventory_ledger.sql:851-859`, `20260730140000_create_advanced_tms_warehouse_zone.sql:1040-1048`) before writing a line of this migration: both pass `null` as `app.can_access_record`'s own `p_customer_account_ref` argument — no owner-scope branch at all, staff-only via org-unit membership. `authenticated` DOES hold a table-level `SELECT` grant on both tables (confirmed by direct read of each table's own closing `GRANT` block) — so a raw read is not blocked at the grant level, but a `customer_user` actor (no `org_unit_id`) is silently filtered to ZERO rows by RLS on every read, live-verified in this checkpoint's own db-test (§11 below), not merely asserted from the migration text.
8. **No new table; zero RLS policy added or changed anywhere in this migration.** A projection over `app.inventory_balances` (ATW-015) and `app.warehouse_customer_eligibility` (ATW-229), both already read (unmodified) by ATW-023.
9. **Movement-summary drill-down, lot/serial identity drill-down, and export are explicitly OUT OF SCOPE** (the source prompt's own instruction). The required UI columns (SKU/item, lot, on-hand/reserved/held/available, location, aging) are already satisfiable from the balance projection alone via `lot_number`/`serial_number`/`updated_at`. Disclosed as a new, sequential `ISS-2026-119` entry (Low, deliberate scope decision, mirrors `ISS-2026-118`'s own structure) — see §9 below.
10. **No fabricated "freshness/staleness" field.** Every RPC reads `app.inventory_balances`/`app.warehouse_customer_eligibility` live, on every call — there is no persisted projection to go stale. "Aging"/"freshness" for the UI (source prompt §22 Alternative flow) is derived entirely from each row's own real `updated_at`, plus the page's own request timestamp for the top-of-page banner — never a fabricated separate source-version field, mirroring CPL-301's own "no persisted dashboard cache" precedent (design decision 1, `20260801020000_create_customer_portal_dashboard_summary.sql`) for the identical reason: this repository has no scheduler/job-refresh infrastructure to keep a separate cache fresh.
11. **REST/GraphQL transport (ADR-0024 Part C):** service layer + Server Component fetch + UI only, no `app/api/` HTTP route — identical in kind to CPL-300..308's own disclosed residual gap.
12. **No edit to `scripts/db-tests/rbac-enforcement.sql` required** — verified by direct analysis of that file's own closure sweep (`base`/`edge`/`closure` CTEs), then live-confirmed: `base` already recognizes any function whose `prosrc` contains `resolve_customer_account_scope` or `customer_warehouse_eligibility_active` (both already-recognized keywords since CPL-300/ATW-023). `app.evaluate_customer_portal_inventory_access` calls both directly (lands in `base` directly); `app.list_customer_portal_inventory_balances`/`app.list_customer_portal_warehouse_eligibility` both call `app.resolve_customer_account_scope` directly (also `base` directly); `app.get_customer_portal_inventory_balance` calls `app.evaluate_customer_portal_inventory_access` (covered transitively via the `edge`/`closure` recursion). Confirmed live: `rbac-enforcement.sql` re-run against a fresh disposable database with this checkpoint's own migration applied passed clean, zero edit (§11 below).
13. **UI: a new standalone-but-shell-linked route, `app/(tenant)/[tenantSlug]/customer-inventory/`**, named per the orchestrating task's own suggested convention. Unlike CPL-302..308's own deliberately standalone route families, this route carries `CustomerPortalNav` (CPL-301's shared shell) — a natural sibling of the account-access/dashboard screens that nav already links between, and the orchestrating task's own explicit instruction ("Add the nav entry to `components/domain/customer-portal-nav.tsx` following its existing pattern"). `CustomerPortalNav`'s `current` union is widened from `"scope" | "dashboard"` to include `"inventory"` — a pure addition; `customer-portal/page.tsx`/`customer-portal-dashboard/page.tsx` need no edit to pick up the new "Warehouse inventory" link, since they only ever pass which tab is `current` and the component itself renders every tab.
14. **Warehouse/location/item identifiers are shown as short, opaque ids, never resolved to a name/code.** No RPC anywhere in this migration or ATW-023's own carries a warehouse name, item SKU code, or location rack/bin label in its projection (design decision 3 — projection parity with ATW-023, whose own column set already excludes these). Business rule 3 ("Location detail must not expose internal warehouse layout beyond approved customer-safe level") makes the raw opaque id the deliberately SAFE choice here, not a placeholder — resolving it to a real name/code would need a new customer-facing name-lookup RPC this bounded checkpoint has no mandate to design.

## 3. A real defect this checkpoint's own db-test authoring found and fixed before shipping

The db-test's own first draft seeded `customer-multi`'s NEW-grant-table-only membership on Account Gamma via `app.grant_initial_customer_portal_account_admin` (the CPL-300 staff bootstrap RPC). The very next assertion — "expect ZERO legacy `app.principal_memberships` row for customer-multi/Gamma" — failed live with `got 1`. Direct re-read of `app.grant_initial_customer_portal_account_admin`'s own body (`20260801010000_create_customer_portal_account_scope.sql`) confirmed it deliberately ALSO calls `app.grant_principal_membership` for the same account (CPL-300's own design: "the point at which the identity first becomes entitled to live WMS/inventory... access through the legacy resolver") — and so does `app.accept_customer_portal_invite`, CPL-300's other real write path. **Neither of CPL-300's own shipped write RPCs can produce a genuinely new-grant-table-only membership** (no legacy marker at all for that account) — that state is only reachable through a service-role-level direct table write (a future capability, a migration backfill, or a support/reconciliation action). **Fixed**: the fixture now seeds Gamma's membership via a direct `INSERT` into `app.customer_portal_account_memberships`, mirroring this file's own already-established "direct fixture insert, bypasses the full pipeline" convention for setup plumbing that does not need to re-prove an already-`VERIFIED` RPC's own behavior. The now-unused `CPT:Create` staff-bootstrap setup (a tenant admin, a "Portal Admin" role/version/permission/assignment) was removed from the fixture rather than left as dead code.

A second, smaller live-caught fix: the raw-table RLS defense-in-depth assertion originally expected a `permission_denied` exception on a raw `authenticated` `SELECT` against `app.inventory_balances`/`app.warehouse_customer_eligibility`. Both tables DO grant `SELECT` to `authenticated` at the table level (confirmed by direct read of each table's own closing `GRANT` block) — RLS filters matching rows to zero, it does not raise an exception when the table grant itself is present. **Fixed**: the assertion now checks `count(*) = 0` for a real `authenticated` session, not a caught exception.
