No raw payroll, PII, ticket content, voucher code, support-access token, or private URL appears anywhere in this document. Where a real `KNOWN_ISSUES.md` entry uses a realistic-sounding "CONFIDENTIAL" placeholder string to prove a masking guarantee, this document never repeats that text — it is described, not quoted.

## 0. Common conventions across every runbook below

- **Every Phase 8 customer-facing RPC calls `app.assert_actor_is_session_identity` as its own literal first statement** (established at `CPL-300`'s own Tier C review, Finding 1, and applied from the first draft by every capability shipped afterward). A forged/impersonated actor id under a real session is rejected with `actor_identity_mismatch` before any row is read — this is a distinct gate from the scope check that follows it, and a session correctly acting as itself but genuinely out of scope is instead denied by the scope check (a different, anti-enumerating error), never `actor_identity_mismatch`.
- **Customer scope is resolved server-side, never taken from browser state, URL, filter, or payload.** `app.resolve_customer_account_scope` (`app.customer_portal_account_memberships` + a legacy-marker gap-filler, `supabase/migrations/20260801010000_create_customer_portal_account_scope.sql`) is the one shared read-scope primitive almost every Phase 8 capability composes; `app.actor_is_active_customer_portal_account_admin` is the one shared write-authority primitive CPL-300's/CPL-315's own account-management RPCs use. Neither is ever re-derived independently by a downstream capability.
- **Anti-enumeration is the norm, not an exception.** A genuinely nonexistent id, a cross-tenant id, a same-tenant-but-out-of-scope id, and (for several capabilities) "exists but the underlying record was hard-deleted" collapse into the identical error almost everywhere in Phase 8 (`record_not_found`, `document_not_found`, `loyalty_redemption_not_found`, `record_not_eligible`, etc.) — a differently-shaped error for a real-but-unauthorized id versus a fake id is itself treated as a defect class (this is exactly the shape `CPL-300`'s own Finding 1 and `CPL-313`'s own Finding 1 closed). Do not read "not found" as proof a record does not exist.
- **No live Supabase Storage bucket or signed-URL mechanism exists anywhere in this repository.** Every file-touching Phase 8 RPC (ePOD, Document Center, ticket attachments, reward media) returns customer-safe *metadata* only (`fileId`/`originalFilename`/`mimeType`/`sizeBytes`), never `storage_path`, never a working download URL — confirmed by direct repository-wide inspection at `CPL-307`/`CPL-308` and unchanged since. `app.file_access_logs.access_type` for every one of these reads is the literal `'metadata_view'`, never `'signed_url_issued'` — see runbook 5.
- **Loyalty balances are derived from append-only ledger events for every normal role.** `app.loyalty_point_ledger_entries`, `app.loyalty_earning_events`, `app.loyalty_benefit_entitlement_events`, `app.loyalty_reward_stock_reservations`, and `app.loyalty_redemption_events` are all `INSERT`-only for `authenticated`/ordinary staff. Since `supabase/migrations/20260801280000_harden_customer_portal_loyalty_ledger_supreme_admin_override.sql` (`ISS-2026-130`, `RESOLVED` at `CPL-325`), a genuine Supreme Admin may `UPDATE`/`DELETE` a row on those five tables specifically — a `BEFORE UPDATE/DELETE` trigger (`app.protect_loyalty_ledger_append_only`) blocks everyone else and captures a best-effort `app.audit_logs` row with before/after values for the Supreme Admin exception. This is a **detective, disclosed, never tamper-proof** control (RPD-022's own standing residual risk, `RISK-004`, unchanged) — never claim immutable-for-all. `app.loyalty_account_tier_movements` (CPL-317) carries the identical structural immutability but was **not** included in that migration's 5-table scope — tracked separately as `ISS-2026-137` (Low, `OPEN`) — so a Supreme Admin has no override path on that one table at all today, which is a stricter, not weaker, posture.
- **No live scheduler/cron exists anywhere in this repository.** Every Loyalty batch primitive named in this document (earning evaluation, tier recalculation, points-lot conversion, expiry sweeps, liability reconciliation, engagement metrics) is a real, callable, adversarially-tested RPC — but nothing invokes any of them periodically. Until a scheduler exists, an operator (or a future scheduling capability) must call them on demand. This is the same disclosed `NOT_RUN` class Phase 1/7's own `PLT-123`/`125`/`132`/`HRT-289`/`291` batches already established, extended here across `ISS-2026-126`/`127`/`128`/`129`/`132`/`133`/`134`.
- **Already-applied migrations in Phase 8's own range (`20260801010000` through `20260801320000`, 31 files) are never edited in place.** Every fix described below is a new, additive migration — see runbook 6 for the full convention.

## 1. A customer reports their portal scope/account access looks wrong

**Scenario:** a customer says they can't see a shipment/invoice/document they expect to see for their own company, or they can see something that looks like it belongs to a different company, or a colleague who was removed from the account still appears to have access, or an invited colleague can't log in at all.

**The real scope mechanism** (`supabase/migrations/20260801010000_create_customer_portal_account_scope.sql`, `docs/build-log/phase-08/CPL-300.md`):

1. **Pull the account's own real membership roster first**, as a privileged operator, directly against `app.customer_portal_account_memberships` (or via `app.list_customer_portal_account_memberships`, account_admin-authority-gated): `role` (`account_admin`/`member`), `status` (`invited`/`active`/`suspended`/`revoked`), `invited_at`/`accepted_at`/`suspended_at`/`revoked_at`. This is the one authoritative record — do not infer membership state from what the customer says they clicked.
2. **Check `app.customer_portal_account_membership_history`** (append-only, one row per state transition, `reason`/`requested_by` captured) for the exact sequence of what happened to the specific identity in question and when.
3. **If the complaint is "I was invited but nothing works yet":** confirm the row's own `status`. An `invited` row genuinely grants **zero** downstream access — by design, `app.grant_principal_membership` (the legacy Layer-4 marker every downstream capability's WMS/ticket-channel access ultimately still checks) is called only from `app.accept_customer_portal_invite`, never from `app.invite_customer_portal_user` itself (`CPL-300.md` §14 Finding 2). The invited identity must call `app.accept_customer_portal_invite` themselves — an admin cannot force `invited → active` on their behalf (`accept_required` is the correct, intended rejection if someone tries).
4. **If the complaint is "a revoked/suspended colleague still sees things":** confirm the membership row's own current `status` first. If it is genuinely `suspended`/`revoked`, this should be structurally impossible — every read RPC in this whole capability re-checks status **live**, never from a cached session claim (`CPL-300.md` design decision 7). If the row is genuinely `suspended`/`revoked` and the identity still has live WMS/inventory access (ATW-023), live ticket-channel access, or live customer-portal entry, this is the exact shape a real, historical, live-reproduced Critical defect took (`CPL-300.md` §14 Finding 2, closed): confirm `app.set_customer_portal_account_membership_status`'s own revoke/suspend branch actually called `app.revoke_principal_membership` on the matching legacy `app.principal_memberships` row — a regression here is Critical (a live cross-capability access leak), not a documentation gap.
5. **If the complaint is "I see a company I shouldn't" or "I don't see my own child/parent site":** re-read `app.accounts`' own `parent_account_id` relationship for both accounts in question. Parent → child account scope is **deliberately non-cascading** (`ADR-0018`, independently re-confirmed at `docs/build-log/phase-07/HRT-287.md` §4) — a membership grant on a parent account never implies access to a child account, and vice versa. This is very frequently mistaken for a bug by a first-time reader; it is the intended, disclosed model. A genuine cross-tenant or cross-account leak (an account the customer's own identity holds **no** membership row for at all, in either the new grant table or the legacy marker) is the real defect class to escalate — re-run `app.resolve_customer_account_scope` directly for the identity/tenant pair and confirm the unexpected account id is genuinely absent from the returned array before escalating.
6. **If the complaint is "an admin action is locked out" or "we have no way to add a new admin":** check whether the account has **zero active `account_admin` rows**. This is a real, live, self-inflictable (never cross-tenant/cross-account) authority gap: nothing in `app.set_customer_portal_account_membership_status` (CPL-300, already `VERIFIED`, may not be edited in place) stops the sole active admin from suspending/revoking themselves or the account's only other admin, and `app.grant_initial_customer_portal_account_admin` is a no-op once any row already exists for that identity+account — it will **not** re-promote or reactivate it. Disclosed as `ISS-2026-125` item 3 (Medium, `OPEN`). There is no self-service recovery path for this specific state today; it requires direct operator/database intervention or a future dedicated fix migration (see runbook 6). Note the narrower, already-fixed sibling: `CPL-315`'s own **new** `app.update_customer_portal_account_membership_role` RPC does have a working last-active-admin guard (rejecting a demotion that would leave zero admins, race-safe via a locked `FOR UPDATE` count of the full active-admin set) — only the older CPL-300 suspend/revoke path still has the gap.
7. **If the complaint involves a specific downstream domain (shipments/documents/warehouse/invoices) rather than the portal shell itself:** confirm which resolver that specific capability's own RPC actually composes. `CPL-300`'s own widened `app.resolve_customer_account_scope` is used by most later capabilities, but several — most visibly the three **pre-existing** `app.ticket_links` entity types (`shipment`/`invoice`/`warehouse`, HRT-292, Phase 7) — still resolve scope through the **legacy** `app.resolve_customer_owner_account_scope` (ATW-242) and are not yet updated to recognize a membership granted *only* through CPL-300's own new table. This is a real, disclosed, narrow under-scoping gap (`ISS-2026-117`, `ISS-2026-119`, `ISS-2026-121` design decision 13, `ISS-2026-122` item 4) — a customer granted a second account *only* via the new CPL-300 grant table (never the legacy marker) will correctly see that account's data through every capability CPL-309/310/311 onward already migrated onto the new resolver, but may see **zero** rows through the small set of older read paths still on the legacy resolver. This is under-scoping (a false negative), never a leak — check the exact RPC named in the customer's own complaint against the table below before assuming a cross-account leak.

**Resolution:**

- **Invite not accepted:** ask the customer to complete `app.accept_customer_portal_invite` themselves (the portal's own "Accept invite" action); an admin cannot do this on their behalf.
- **Revoke/suspend not propagating (Critical, if reproduced on a genuinely current checkpoint):** escalate immediately citing `CPL-300.md` §14 Finding 2 and the exact migration (`20260801010000`) — this is a regression against an already-fixed, adversarially-proven defect.
- **Parent/child non-cascading scope:** explain the intended model; grant an explicit membership on the specific account/site the customer actually needs (`app.invite_customer_portal_user`, account_admin-gated).
- **Zero active admins:** no self-service fix exists; escalate for direct correction, and consider filing a bounded follow-up migration against `CPL-300` per runbook 6 mirroring `CPL-315`'s own already-proven guard shape.
- **Legacy-resolver under-scoping on `shipment`/`invoice`/`warehouse` ticket links:** not a leak; explain the current, disclosed boundary (`ISS-2026-122` item 4) and, if a fix is warranted, route to a new additive migration `CREATE OR REPLACE FUNCTION`-ing `app._ticket_link_resolve_candidate`/`app.search_ticket_link_candidates` (HRT-292) to compose the widened resolver — never an edit to the already-applied `20260731170000_create_ticket_linked_records.sql`.

**Known, disclosed, still-`OPEN` limitations relevant to this scenario** (do not mistake any for a new bug): `ISS-2026-116` (a genuinely non-guessable `p_membership_id` produces a distinguishable not-found vs. unauthorized error — accepted, low risk, no practical enumeration path); `ISS-2026-125` items 1-2 (no MFA/step-up mechanism and no session/token-revocation primitive exist anywhere in this repository — every read re-checks live status on every call instead, the closest structural equivalent this architecture provides).

**Escalation path:** first-line — any tenant staff member with read access to `app.customer_portal_account_memberships`/`app.customer_portal_account_membership_history` reruns the diagnostic above. A genuine revoke/suspend-propagation regression, or a genuine cross-account leak (step 5), is Critical/High and must stop the affected flow and preserve the membership-history evidence before any further customer-facing action. A "zero active admins" lockout or a legacy-resolver under-scoping gap is Medium/Low and routes to a future bounded migration, not an emergency.

## 2. A loyalty point-balance figure looks wrong (ledger discrepancy investigation)

**Scenario:** a customer's displayed points balance (`app.list_customer_portal_loyalty_point_balances`) doesn't match what they expect — too high, too low, or missing a recent earn/spend.

**The real diagnostic path** (`supabase/migrations/20260801200000_create_customer_portal_loyalty_points_ledger.sql`, `docs/build-log/phase-08/CPL-318.md`, `CPL-323.md`):

1. **Read the append-only ledger directly, not the cached balance, first.** `app.loyalty_point_ledger_entries` (staff: `app.list_loyalty_point_ledger_entries`, `LYL:View`, includes `reason`; customer-safe: `app.list_customer_portal_loyalty_point_ledger_entries`, structurally never carries `reason`) is the authoritative record of every posting for the account — `earn`/`consume`/`reversal`/`expiry`/`adjustment` entries, each signed (originals positive, reversals/consumption already negative). `app.post_loyalty_point_ledger_entry` is the **single** posting primitive every other function in this domain composes — there is no second write path into this table.
2. **Sum the ledger and compare against the cached balance.** This is exactly the live check `app.execute_loyalty_liability_reconciliation_run` (`CPL-323`) performs for every account with any ledger row — a live `SUM(amount)` over `app.loyalty_point_ledger_entries` must equal `app.loyalty_point_balances.available` exactly. If you have `LYL:Edit`, running a reconciliation for the relevant currency is the fastest authoritative check (it independently re-derives the total and raises a real, typed `point_balance_derivation_mismatch` exception — with both the expected and actual values recorded — the moment the two disagree); the same arithmetic can also be reproduced by hand from the raw ledger rows.
3. **If the ledger and the cached balance genuinely disagree**, this is a real defect — escalate as High/Critical (a live, undetected balance-manipulation-shaped finding, per this domain's own standing "balance/liability manipulation always escalates" rule, `CPL-324.md`/`CPL-325.md` §4's own governing instruction) and preserve the exact ledger rows/reconciliation-exception row as evidence before any correction.
4. **If the ledger and the cached balance agree but the customer still disputes the total, check for one of these real, non-bug explanations, in order:**
   - **A reversal, not an edit.** A correction is **never** an in-place edit to a prior ledger row — it is a new, separate, negative-signed ledger entry (`app.reverse_loyalty_points_earned`, `LYL:Configure`, references the original event via `corrects_event_id`). Look for a paired original + reversal, not a "missing" original.
   - **A manual point adjustment.** `app.request_loyalty_point_adjustment`/`app.decide_loyalty_point_adjustment` is a real, governed maker-checker pair (`LYL:Edit` requests, `LYL:Configure` decides, self-approval structurally blocked — mirrors PRC-264's own precedent) for a direct correction outside the normal earn/consume flow. Check `app.get_loyalty_point_adjustment_request` for a matching row and its own mandatory reason.
   - **Points not yet converted from an earning event.** `app.post_loyalty_points_earned` (converts a `points`-type `app.loyalty_earning_events` row into a real point lot + earn ledger entry) is **on-demand/staff-triggered only** — no scheduler wires it automatically (`ISS-2026-128` item 1). A recent paid invoice's earned points genuinely will not appear until a staff member calls this RPC (or a future scheduling capability does). Confirm by checking whether a matching `app.loyalty_earning_events` row exists with no corresponding ledger entry yet.
   - **Expiry not yet swept.** `app.expire_loyalty_point_lots` (composed by `app.run_loyalty_expiry_sweep`, `CPL-322`) is also on-demand/staff-triggered only (`ISS-2026-128` item 1, `ISS-2026-133` item 3). A lot whose own `expires_at` is already in the past but has not yet been processed by a real sweep call will still count toward `available` — check `app.jobs` for the most recent `job_type = 'loyalty_expiry_sweep'` row and its own `payload`-recorded counts before assuming the balance is wrong; it may simply be stale pending a sweep.
   - **FIFO consumption order.** `app.consume_loyalty_points_fifo` always consumes the **soonest-to-expire** lot first, live-proven negative-balance-safe under both a single-session over-consumption attempt and a genuine two-process concurrent race. A customer who assumes their most-recently-earned points were spent first (LIFO) will see an apparently-wrong remaining balance that is in fact correct FIFO behavior — explain the ordering, do not treat as a defect.
   - **A held account.** A fraud hold (`CPL-322`) blocks **redemption**, never the balance or ongoing earning — tier tracking/points accrual and benefit-hold are deliberately orthogonal (`CPL-317.md` design decision 5, live-proven: an account's tier and points continue to move while held). If the actual complaint is "I can't redeem," that is runbook 3, not this one.
   - **A genuine, audited Supreme Admin correction.** Since `20260801280000` (`ISS-2026-130`, resolved at `CPL-325`), a Supreme Admin may directly `UPDATE`/`DELETE` a row on `app.loyalty_point_ledger_entries` — always captured to `app.audit_logs` with before/after values. Check there for an unexplained direct mutation before assuming a code defect.

**Resolution:**

- **Ledger vs. cached-balance mismatch, confirmed real:** escalate as a genuine defect; do not attempt a manual balance correction outside the governed `app.request_loyalty_point_adjustment` maker-checker path even under time pressure, since a raw balance edit outside the ledger would itself create a second, worse discrepancy.
- **Any of the six non-bug explanations above:** explain to the customer using the real ledger entries/reconciliation-exception detail as the reproducible, auditable source of truth (never a raw row snapshot — the customer-facing ledger projection structurally omits `reason`).
- **Pending conversion/expiry:** trigger the relevant on-demand RPC (`app.post_loyalty_points_earned` / `app.run_loyalty_expiry_sweep`) if a staff actor with `LYL:Edit` is available and the tenant's own operational cadence calls for it now, rather than waiting for a future scheduler.

**Escalation path:** first-line — staff holding `LYL:View` reruns the ledger-vs-balance comparison above. A genuine `point_balance_derivation_mismatch` (or, more broadly, any confirmed ledger/cached-balance disagreement) escalates to the Loyalty capability owner (`CPL-318`/`CPL-323`) citing the exact reconciliation-run id and exception row. A dispute resolved by one of the six documented non-bug explanations does not require escalation.

## 3. A redemption is stuck in `pending_approval`, or a fraud hold blocked something unexpectedly

**Scenario:** a customer's reward redemption has been sitting in `pending_approval` for longer than expected, or a redemption attempt was rejected with an "account on hold" message the customer doesn't understand.

**The real mechanism** (`supabase/migrations/20260801230000_create_customer_portal_loyalty_redemption_approval_fulfillment.sql`, `20260801240000_create_customer_portal_loyalty_expiry_fraud_prevention.sql`, `20260801300000_harden_customer_portal_loyalty_redemption_hold_race.sql`; `docs/build-log/phase-08/CPL-321.md`, `CPL-322.md`, `CPL-325.md`):

1. **Pull the redemption row directly** (`app.get_loyalty_redemption`/`app.list_loyalty_redemptions`, `LYL:View`): `status` (`pending_approval`/`rejected`/`fulfilling`/`fulfilled`/`cancelled`/`failed`; `approved` exists in the CHECK constraint's own vocabulary but no current RPC emits it as a standalone, separately-observable state — approval and composition happen atomically inside `app.decide_loyalty_redemption`), `fulfillment_status` (`not_applicable`/`pending`/`in_fulfillment`/`fulfilled`/`failed`), `reward_type`.
2. **If `reward_type = 'discount_voucher'` and the submitter was a genuine, unassisted customer, `pending_approval` is the correct, intended, documented outcome — not a delay to fix.** `app.submit_loyalty_redemption` always creates the real portal-owned intent record, then attempts immediate composition — but that inline auto-approve only succeeds synchronously for a caller who **independently already holds staff/system `LYL:Edit`** authority (confirmed structurally: `app.role_assignments` has exactly one `INSERT` call site anywhere in this repository, a staff-only administrative RPC the customer-portal invite flow never touches — a genuine `customer_user` identity can never hold `LYL:Edit`). A raw customer submission of **any** `reward_type` gracefully, correctly falls back to `pending_approval`, requiring one real staff decision. Disclosed as `ISS-2026-132` item 1 — explain this to the customer rather than treating the wait itself as a defect.
3. **If `reward_type = 'physical_item'`/`'service_credit'`, `pending_approval` (then `fulfilling`/`in_fulfillment`) is *always* the correct path regardless of who submitted it** — this checkpoint's own design deliberately never auto-fulfills a physical/service reward inline (`CPL-321.md` design decision 3). Check the fulfillment queue (`admin/loyalty-redemptions`) for whether staff have simply not yet acted, rather than a system fault.
4. **Check for an account-level fraud hold.** Query `app.loyalty_account_tier_holds` directly (`is_held`/`hold_reason`/`held_by`/`held_at`), or the customer-safe `app.list_customer_portal_loyalty_account_hold_status` (returns only a generic `is_on_hold`/`hold_notice` — **never** the real internal reason, live-proven adversarially: the customer-facing denial message is directly asserted, in this capability's own db-test, to never contain any fragment of the real internal hold text). A held account blocks **both** `app.submit_loyalty_redemption` and `app.decide_loyalty_redemption`'s own approve branch — this is the correct, intended behavior of a genuine, real fraud hold, not a bug.
5. **If a hold is active, find the owning fraud review case** (`app.get_loyalty_fraud_review_case`/`app.list_loyalty_fraud_review_cases`, `LYL:View`): `status` (`open`/`under_review`/`confirmed`/`cleared`). `open`/`under_review` are both valid pre-decision states (a case may be decided directly from either). `confirmed` means the hold correctly **stays in place** — the decision performs no autonomous cascading action beyond recording it. Only `decide_loyalty_fraud_review_case('clear')` genuinely composes `app.release_loyalty_account_tier_benefits` and lifts the hold; `'confirm'` never does. If staff believe a case was cleared but the hold is still active, confirm the actual decision recorded was `'clear'`, not `'confirm'`.
6. **Check for an active fraud-review suppression** (`app.list_loyalty_fraud_review_suppressions`, `LYL:View`) if staff expected a **new** case to be opened but none was — an active, non-revoked, non-expired suppression on the account blocks opening a further case (mirrors HRT-291's own `app.ticket_escalation_suppressions` shape exactly). A stale suppression auto-revokes itself the next time it is checked.
7. **If the redemption is stuck in `pending_approval` with NO hold and NO obvious staff-queue backlog:** confirm the intent record itself is still genuinely present with `stock_reservation_id`/`benefit_entitlement_id` both `null` — this is the correct, current shape after `CPL-321`'s own Tier C fix (a Critical finding, now resolved) closed a real defect where a **staff/system** actor's own failed auto-compose attempt (e.g., the reward genuinely out of stock, or a misconfigured `discount_voucher`'s `internal_cost`) could silently roll back and destroy the redemption row itself, along with its `'submitted'` audit event, with zero trace. If you are on a checkpoint *before* this fix and reproduce a genuinely vanished redemption (a customer swears they submitted, no row exists at all, `app.loyalty_redemption_events` shows nothing), this is a serious regression — escalate as Critical citing `CPL-321.md` §14 and the exact fix migration.
8. **When staff finally call `app.decide_loyalty_redemption`, it independently, freshly re-validates** reward status/effective-window/hold/tier/points at the current moment (never trusting the submission-time snapshot) — a redemption that was eligible when submitted can legitimately fail at decide time (e.g., `insufficient_reward_stock` if the reward genuinely sold out in the interim). This correctly leaves the redemption `pending_approval` (or moves it to `rejected` if staff explicitly reject with a mandatory reason) rather than silently succeeding on stale data.
9. **A distinct governance concern, not a customer-visible symptom but worth checking if a redemption appears to have skipped review entirely:** `app.submit_loyalty_redemption`'s own scope check treats bare staff `LYL:Edit` (not the elevated `LYL:Configure` the actual `app.decide_loyalty_redemption` governance action requires) as sufficient to submit **and** instantly auto-fulfill a `discount_voucher` redemption for **any** loyalty account in the tenant, in one call — collapsing maker and checker into a single, lower-privileged actor, with `app.decide_loyalty_redemption` never invoked at all on that path. This is real, deliberate, already-tested behavior (`CPL-321.md`'s own "main flow A"), but it is also a disclosed governance gap distinct from item 2 above: it lets one `LYL:Edit`-only actor bypass the `LYL:Configure`-gated decision path for someone else's account (`ISS-2026-139`, Medium, `OPEN`). If a redemption's own event history shows a `fulfilled` outcome with no corresponding `app.decide_loyalty_redemption` call ever having occurred, this is the expected shape of that path — not evidence of tampering by itself, but check who submitted it and whether that matches the account's own owning customer or a legitimate staff workflow before closing the inquiry.

**Resolution:**

- **`discount_voucher`/`physical_item`/`service_credit` genuinely awaiting staff decision:** route to the admin approval queue (`app/(tenant)/[tenantSlug]/admin/loyalty-redemptions`); a staff member with `LYL:Configure` calls `app.decide_loyalty_redemption(approve|reject)` (reject requires a mandatory reason).
- **Held account:** resolve via the fraud-review workflow — claim the case (`app.claim_loyalty_fraud_review_case`, `LYL:Edit`) then decide it (`app.decide_loyalty_fraud_review_case`, `LYL:Configure`); only `'clear'` lifts the hold.
- **Genuine fulfillment failure on a `physical_item`/`service_credit` reward:** `app.mark_loyalty_redemption_fulfillment_failed` (`LYL:Edit`, mandatory reason) genuinely reverses composition — releases the stock reservation and credits the points back, live-proven via before/after balance assertions.
- **Suspected vanished redemption (pre-fix checkpoint):** escalate immediately per item 7 above; do not attempt a manual re-creation of the intent record — trace which migration is applied first (see runbook 6).
- **Suspected maker-checker bypass (`ISS-2026-139`):** not currently fixable via a bounded code change without a real product/RBAC decision (require `LYL:Configure` for the auto-compose branch, or add an explicit self/other-account check) — escalate to the capability owner for that decision; do not attempt an ad hoc RPC-level patch.

**Escalation path:** first-line — staff holding `LYL:View`/`LYL:Edit` reruns the diagnostic above. A genuinely vanished intent record on a current checkpoint, or a live cross-tenant/cross-account redemption leak, is Critical — stop, preserve `app.loyalty_redemption_events`/`app.file_access_logs` (if a voucher code or attachment is involved) as evidence, and escalate to the Loyalty capability owner (`CPL-321`/`CPL-322`/`CPL-325`) citing the exact redemption id and event history. A held-account or governance-gap question routes to the same owner as a Medium item, not an emergency.

## 4. A liability reconciliation run's own total looks wrong or an exception was raised

**Scenario:** a staff member runs `app.execute_loyalty_liability_reconciliation_run` and either the resulting total for one of the five liability lines looks implausible, or one or more exceptions were raised and `app.certify_loyalty_liability_reconciliation_run` is blocked.

**The real mechanism** (`supabase/migrations/20260801250000_create_customer_portal_loyalty_liability_reconciliation_analytics.sql`, `20260801270000_harden_customer_portal_loyalty_liability_reward_fulfillment_currency_scope.sql`, `20260801310000_harden_customer_portal_loyalty_liability_reconciliation_snapshot_atomicity.sql`; `docs/build-log/phase-08/CPL-323.md`, `CPL-324.md`, `CPL-325.md`):

1. **Confirm the run's own currency scope first.** `app.execute_loyalty_liability_reconciliation_run` is **currency-scoped** via a required `p_currency` parameter — cashback/discount/voucher/reward-fulfillment totals only ever include entitlements/redemptions whose own `currency` matches the run's currency; a multi-currency tenant genuinely needs **one run per currency** for full coverage, mirroring FIN-209's own per-scope (`ar`/`ap`) precedent exactly (`ISS-2026-134` item 1). `points_liability_total` is **never** currency-denominated at all (a raw, dimensionless points sum — no point-to-currency conversion rate is configured anywhere in this repository's real Loyalty schema) — it must never be summed with, or compared against, any of the four currency-denominated lines.
2. **If `reward_fulfillment_liability_total` looks doubled or duplicated across two currency-scoped runs of the same tenant:** confirm the fix migration (`20260801270000`, closing `ISS-2026-136` item 1) is applied. Before that fix, this one line — unlike the other four — carried no currency predicate at all (`app.loyalty_rewards` has no currency column of its own) and would appear **identically** on every currency-scoped run of the same tenant, silently double-counting if a staff member summed multiple per-currency runs' totals exactly as this migration's own documented workflow instructs for the other four lines. Post-fix, `internal_cost` is treated as denominated in the tenant's own resolved `default_currency` (`app.resolve_tenant_locale`) and only contributes to a run whose own `p_currency` matches that resolved value — a run in any other currency correctly reports `0` for this line.
3. **Check `app.list_loyalty_liability_reconciliation_exceptions`** for the run: three real, typed exception types exist. `point_balance_derivation_mismatch` (a cached `app.loyalty_point_balances.available` disagrees with a live re-derived `SUM` over the ledger — see runbook 2), `entitlement_state_derivation_mismatch` (a cached `app.loyalty_benefit_entitlements.status` disagrees with the status independently re-derived from `app.loyalty_benefit_entitlement_events`' own latest event), and `redemption_liability_status_mismatch` (a cached `app.loyalty_redemptions.status` disagrees with the status re-derived from `app.loyalty_redemption_events` — added at `CPL-323`'s own Tier C review, `CPL-323.md` §14, after a live-reproduced Critical finding that the reward-fulfillment line originally trusted the cached status column directly with no re-derivation and no detection, unlike every sibling liability line). **Every liability total is recomputed live from the raw ledger/event tables on every run — never trusted from a cached, mutable column without independent re-derivation** (design decision 3, `CPL-323.md`); a mismatch exception is the reconciliation system working correctly, not a bug in itself.
4. **Do not read `p_as_of` as a historical bound.** It is recorded as the run's own point-in-time *label* only — every total genuinely reflects the **current** state of the source tables at execute time, regardless of the `as_of` value (`ISS-2026-134` item 2, a real, disclosed, structural limitation — `app.loyalty_point_balances`/`app.loyalty_benefit_entitlements` have no historical-snapshot capability for any date other than "now"). A run's own `as_of` label not matching a genuinely historical total is expected, not a defect.
5. **A `null internal_cost` on an open `physical_item`/`service_credit` redemption silently contributes `0`** to the reward-fulfillment line, with no third exception type raised for it (`ISS-2026-134` item 3) — a real, disclosed, low-likelihood staff data-entry gap (a reward published without a real `internal_cost`), not a code defect.
6. **If `app.certify_loyalty_liability_reconciliation_run` (`LYL:Configure`) is blocked**, this means at least one exception on the run still has `status = 'open'`. Resolve each one individually via `app.resolve_loyalty_liability_reconciliation_exception` (`LYL:Edit`, mandatory reason) — the run automatically transitions from `exceptions_pending` back to `open` (ready to certify) the moment the **last** open exception is resolved.
7. **If a mismatch was found and re-run against the SAME instant produces a genuinely different combined total than expected**, check whether a real concurrent mutation (a reversal, an expiry sweep, a redemption decision) landed *during* the run. Since `20260801310000` (closing a real, deterministically-reproduced High finding), the entire live-recomputation is one single top-level SQL statement, giving it one true MVCC snapshot under READ COMMITTED — a run's own combined total will always exactly match either the fully-before or fully-after state of a concurrent mutation, **never** a torn, in-between value. If you are on a checkpoint *before* this fix and reproduce a total that matches neither valid bound, this is a serious regression — escalate as High/Critical citing `CPL-325.md` §6.4.

**Resolution:**

- **Currency-scoping confusion:** re-run once per currency the tenant actually uses; never blend `points_liability_total` into a currency total.
- **Reward-fulfillment double-count on an older checkpoint:** confirm/apply `20260801270000`; do not attempt a manual subtraction from a stale run's own total.
- **A genuine mismatch exception:** investigate the underlying cause (a direct table correction outside the owning RPC — check `app.audit_logs` for a Supreme Admin mutation per runbook 3's item 4 pattern, or a genuine defect in a composed primitive) before resolving with a real, specific reason; never resolve an exception with a placeholder reason merely to unblock certification.
- **Blocked certify:** resolve every open exception first; certify is intentionally, permanently blocked until then — there is no override.
- **Torn/inconsistent total under concurrency (pre-fix checkpoint):** escalate immediately citing `CPL-325.md` §6.4; do not treat as measurement noise.

**Known, disclosed, still-`OPEN` limitation relevant to this scenario:** mismatch **detection** itself (as opposed to the liability totals) is tenant-wide, not currency-scoped — a single corrupted row is re-flagged as an open exception on **every** currency-scoped run of the tenant, not only the run in its own currency, requiring it to be independently `resolve`d once per run before each can certify (`ISS-2026-136` item 2, Low, `OPEN`, real but bounded operational noise, not a wrong-number defect). No live Finance-side liability-handoff mechanism (a handoff-batch table, an idempotent generator, a Finance acknowledgement RPC — the HRT-282-family shape `ADR-0024` Part D names) exists yet anywhere in this repository (`ISS-2026-134` item 5) — this reconciliation evidence is certified entirely within Loyalty's own tables; propagating it to Finance today is a manual staff reporting step, never an automated financial commitment.

**Escalation path:** first-line — staff holding `LYL:Edit`/`LYL:View` reruns the diagnostic above and resolves genuine exceptions with real reasons. A confirmed liability-understatement path with zero detection, a torn total under concurrency, or any finding that meets this domain's own standing "balance/liability manipulation" escalation bar is Critical/High regardless of its original severity label — escalate to the Loyalty capability owner (`CPL-323`/`CPL-324`/`CPL-325`) citing the exact run id, exception rows, and migration chain applied.

## 5. A suspected file-privacy leak (ePOD/Document/Ticket/Invoice/Reward attachment)

**Scenario:** a file that should have been blocked (wrong scope, or a non-`clean` malware-scan status) appears to have been visible to a customer, or a customer reports they cannot see a file they believe they should.

**The real, shared discipline across every file-touching Phase 8 capability** (`docs/standards` file-access convention, PLT-128 `app.files`/`app.file_access_logs`): every accepting RPC independently **re-verifies** the file's own tenant/record-scope/soft-delete state/live `malware_scan_status` directly against `app.files` at **read time** — never cached from a prior call, never trusted from the owning capability's own list projection. No live Storage bucket exists anywhere in this repository, so a "leak" here can only ever be of **metadata** (filename/mime/size/scan status) or a wrongly-exposed non-`clean` file's *existence* — never raw file bytes.

**Diagnosis — name the exact surface first, each has a genuinely different code path:**

1. **ePOD** (`app.get_customer_epod`, `supabase/migrations/20260801080000_create_customer_portal_epod_access.sql`, `CPL-307.md`): the **whole capture** collapses to `epod_status = 'quarantined'` (files withheld entirely) if **any** referenced evidence file fails live re-verification — never a partial list mixing safe and unsafe evidence. Trusted, non-file capture metadata (`receiver_name`/`captured_at`) is still shown even while quarantined (these come from `app.epod_captures` directly, never from file content, so withholding them buys no additional safety). Confirm the correct `access_type` in `app.file_access_logs` for a granted read is `'metadata_view'` (a real, live-reproduced defect at this capability's own Tier C review, `CPL-307.md` §14, was that the first shipped version wrote `'signed_url_issued'` — a durably misleading audit-trail literal for an access that never issued a URL — fixed, and independently mirrored/fixed at `CPL-308` too).
2. **Document Center** (`app.get_customer_document`/`app.list_customer_documents`, `supabase/migrations/20260801090000_create_customer_portal_document_center.sql`, `CPL-308.md`): malware/quarantine status is surfaced **per document**, never collapsed the way ePOD collapses per-capture — a `list` call shows every in-scope document's real, live `malware_scan_status` honestly (including `pending`), and `get_customer_document` for a non-`clean` file returns a normal, **successful** row (with the real status) plus a durably-committed **denied** `app.file_access_logs` row — it deliberately never raises a database exception for this case (a live, self-found defect during this checkpoint's own authoring: an earlier draft raised an exception immediately after the log `INSERT`, which rolled the log write back too, atomically, silently destroying the very audit trail the denial was supposed to produce — fixed by moving the actual `document_not_downloadable` refusal one layer up, to the TypeScript service boundary, strictly after the RPC's own row has already durably committed).
3. **Ticket attachments** (`app.list_customer_ticket_messages`/`app.list_ticket_messages`, hardened by `supabase/migrations/20260801320000_harden_customer_portal_ticket_attachment_file_privacy.sql`, `CPL-325.md` §6.5): before this migration, ticket attachments were the **one** file-exposing surface in the whole repository that never re-verified live scan status at read time and never wrote any `app.file_access_logs` row at all — a real, live, High-severity gap found and fixed at `CPL-325`'s own dedicated file-privacy-audit lens. Post-fix, every referenced `attachment_file_ids` entry is re-verified at read time exactly like ePOD/Document Center; a file that fails re-verification is silently **filtered out of the returned array** (never an error, never a dropped message — a whole page/message should not fail to load over one bad attachment), and one `app.file_access_logs` row (`granted`/`denied`) is written per referenced file. Confirm this migration is applied if a ticket attachment's scan status appears stale or unaudited.
4. **Reward Catalogue** (`app.get_customer_portal_loyalty_reward`, `CPL-320`): "plus the malware-scan-gated file reference" for reward media — the same live re-verification discipline applies; there is no separate, weaker path here.
5. **Invoices/Billing** (`CPL-311`/`CPL-312`): these capabilities project structured invoice/payment data, not file attachments — a "file" complaint on this surface most likely actually concerns a Document Center row filtered by `source_module = 'invoice'`, which is **recognized but permanently empty today** (no invoice document source has been wired into Document Center as of this checkpoint) — confirm the customer isn't expecting a document type that genuinely doesn't exist as a source yet, per `CPL-308.md` §2 design decision 2, before assuming a scope bug.

**Diagnosis — the checks common to every surface above:**

6. **Confirm `app.file_access_logs.access_type` is `'metadata_view'`, never `'signed_url_issued'`**, for every one of these reads — a mismatch here indicates either a stale, pre-fix checkpoint (ePOD/Document Center) or a genuine new defect in a capability not yet audited for this discipline.
7. **Confirm `malware_scan_status` directly on `app.files`** for the file in question, live. A file re-flagged `infected` after an earlier `clean` state (the only way this state is reachable today outside a genuine malware-scan-provider result — `app.record_file_scan_result` structurally refuses to re-resolve an already-`clean` file, so a direct table correction simulating the disclosed RPD-022 Supreme Admin path is the only route) must disappear from every affected capability's own read on the **very next call** — never served stale.
8. **Confirm anti-enumeration held.** A genuinely nonexistent file id, a cross-tenant id, and an out-of-scope-but-real id should all collapse to the identical `document_not_found`/`record_not_found` — a differently-shaped response for a real-but-unauthorized file is itself the defect to escalate (this is the exact class `CPL-313.md` §14 Finding 1 closed for the ticket-linked-record invoice-status gate — a *different* file-privacy-adjacent leak where a customer could discover and durably link a pre-issuance invoice through the ticket linked-records search before `CPL-311`'s own visibility rule was retrofitted onto that search branch, fixed via a new, additive migration, `20260801160000`, `CREATE OR REPLACE`-ing the two already-applied HRT-292 functions — never an edit to the original `20260731170000` file).

**Resolution:**

- **Confirmed stale checkpoint (a known-fixed pattern not yet applied):** confirm/apply the corresponding hardening migration named above; this is not a new defect to re-diagnose from scratch.
- **A genuinely new gap in a capability not covered by any pattern above:** treat as a Critical/High file-privacy incident per source spec §23 — stop the affected flow, preserve `app.file_access_logs`/`app.audit_logs` evidence exactly as it stands, and follow runbook 6 to add a new additive migration mirroring the established re-verification-plus-audit-log discipline; never attempt an in-place edit to the vulnerable migration.
- **Recognized-but-empty document source (invoice/ticket in Document Center):** not a bug; explain the current, disclosed scope boundary.

**Escalation path:** the owning capability (`CPL-307` for ePOD, `CPL-308` for Document Center, `CPL-313`/`HRT-292` for ticket-linked-record file/invoice exposure, `CPL-325` for the ticket-attachment fix itself, `CPL-320` for reward media) for a capability-scoped gap; a repository-wide PLT-128 (`app.files`/`app.file_access_logs`) owner if the shared malware-scan/audit primitives themselves misbehave, since that infrastructure is shared by every domain in the repository, not a Phase-8-local concern.

## 6. Rollback/recovery procedure for a bad migration in Phase 8's own range

**Scenario:** a genuine defect is traced to one of the 31 real migrations in Phase 8's own range (`supabase/migrations/20260801010000_create_customer_portal_account_scope.sql` through `supabase/migrations/20260801320000_harden_customer_portal_ticket_attachment_file_privacy.sql`), and it needs to be corrected.

**The one, non-negotiable rule, stated explicitly:** **an already-applied migration is never edited in place.** Every single fix Phase 8's own closure checkpoints made — across `CPL-300`'s own Tier C review, `CPL-313`'s Finding 1, and every repair `CPL-324`/`CPL-325` shipped — followed this rule without exception. A new, additive migration is the only fix path. This is not merely a style preference: `AGENTS.md`'s own standing discipline, and this repository's own `git:check-paths`/migration-integrity gates, treat an edit to an already-applied migration file as a forbidden action, and doing so would silently desynchronize any environment that already ran the original file from one that runs the edited version.

**The real, already-proven fix shapes, in order of how often each actually applies:**

1. **`CREATE OR REPLACE FUNCTION` against an unchanged signature (the most common shape — zero TypeScript-layer ripple, ACL-preserving).** Used for a pure logic correction where the function's own parameter list and return shape do not need to change. Real precedents: `20260801160000_harden_customer_portal_ticket_link_invoice_status_gate.sql` (`CPL-313`'s Finding 1, `CREATE OR REPLACE`s two already-applied HRT-292 functions, `app._ticket_link_resolve_candidate`/`app.search_ticket_link_candidates`, to add one missing status predicate); `20260801260000_harden_customer_portal_optimistic_concurrency_null_bypass.sql` (`CPL-324`, widens the NULL-check on 12 functions across 5 different capabilities' own migrations in one new file); `20260801270000_harden_customer_portal_loyalty_liability_reward_fulfillment_currency_scope.sql` (`CPL-324`'s own follow-up, one function); `20260801290000_harden_customer_portal_profile_change_request_latest_pending_ordering.sql`, `20260801300000_harden_customer_portal_loyalty_redemption_hold_race.sql`, `20260801310000_harden_customer_portal_loyalty_liability_reconciliation_snapshot_atomicity.sql`, `20260801320000_harden_customer_portal_ticket_attachment_file_privacy.sql` (all five of `CPL-325`'s own repairs). `CREATE OR REPLACE FUNCTION` on an identical signature preserves every existing `GRANT` automatically — no re-grant statement is needed.
2. **A new `CREATE TRIGGER` (plus the matching `GRANT`) for a genuinely new protective mechanism.** Real precedent: `20260801280000_harden_customer_portal_loyalty_ledger_supreme_admin_override.sql` (`ISS-2026-130`) — one shared `BEFORE UPDATE/DELETE` trigger function applied to five existing tables via five new `CREATE TRIGGER` statements, plus additive `GRANT UPDATE, DELETE ... TO service_role` (a grant those tables never had before, on any role).
3. **`ALTER TABLE ... DROP CONSTRAINT` / `ADD CONSTRAINT` to widen an existing CHECK, in a NEW migration, never touching the table's own original `CREATE TABLE` file.** Real precedents: `CPL-321`'s own `20260801230000` widened `app.loyalty_reward_stock_reservations`' own `quantity > 0` CHECK (from `CPL-320`'s already-applied `20260801220000`) to `quantity <> 0`, via a real, additive `ALTER TABLE` statement inside CPL-321's own new file — CPL-320's own file was never touched; `CPL-322`'s own `20260801240000` widened `app.jobs.job_type`'s CHECK constraint (Platform Core-owned, `PLT-132`) using the established repository-wide `DROP CONSTRAINT`+`ADD CONSTRAINT`, full-literal-list-carried-forward pattern.
4. **A wholly new, small, parallel table/RPC family, when a genuine registry conflict makes widening the existing one unsafe.** Real precedent: `CPL-313`'s own `app.ticket_portal_links` table — a first draft attempted to widen HRT-292's own `app.ticket_links.entity_type` CHECK constraint, but this was discovered, live, to conflict with two real, already-passing, protected test assertions (`scripts/db-tests/ticketing-linked-records.sql:254`, `server/contracts/ticketing/ticketing.test.ts:630`) that hard-assert the original six-value registry verbatim — widening it would have broken both. The correct fix was a small, additive, parallel table, never a forced widening of a registry two other tests already depend on staying fixed.

**Diagnostic steps to identify which migration genuinely owns a defect, before writing any fix:**

1. **Confirm the exact owning capability and migration file.** Read the relevant `docs/build-log/phase-08/CPL-3NN.md` build log's own "Files changed"/"RPC surface" sections, or `grep` `supabase/migrations/` directly for `create function <name>`/`create table <name>` — every Phase 8 build log names its own migration filename explicitly.
2. **Check whether the behavior is already a documented, deliberate scope boundary before assuming it is a bug.** A very large share of "wrong" behaviors reported against Phase 8 are real, disclosed, intentional limitations, not defects — the entire `ISS-2026-126`/`127`/`128`/`129`/`132`/`133`/`134` "on-demand/staff-triggered only" family, the currency-scoping/point-non-conversion decisions, the parent/child non-cascading account model, and the discount_voucher auto-approve/pending-approval split are all examples. Read `docs/runtime/KNOWN_ISSUES.md` in full for the relevant `ISS-2026-1xx` entries before writing a fix migration for something that is already correctly working as documented.
3. **Confirm the defect reproduces live**, against a fresh, disposable Postgres 16 database with the full migration chain applied — every real fix in Phase 8's own history was live-reproduced first, never fixed from reasoning alone (e.g., `CPL-321.md`'s own Critical finding was independently reproduced by three of four Tier C review lenses before being trusted).

**The fix procedure itself:**

1. **Never `git revert`/hand-edit the original migration file.** Never run a destructive `DROP`/`git reset --hard` against any shared or persistent database.
2. **Write one new, additive migration**, named per this repository's own `YYYYMMDDHHMMSS_harden_<capability>_<defect>.sql` convention, carrying its own explicit `revoke execute on all functions in schema app from public` statement before any new grant (`ERR-2026-004`, if the fix touches a function's grant at all — `CREATE OR REPLACE FUNCTION` on an unchanged signature needs none), and a header comment naming the defect and citing this document/the relevant `ISS-2026-1xx` entry.
3. **Add a live regression proof to the OWNING capability's own `scripts/db-tests/*.sql` file — never delete or weaken an existing assertion, only append a new block.** Every one of `CPL-307`/`CPL-308`/`CPL-313`/`CPL-321`/`CPL-322`/`CPL-323`/`CPL-325`'s own fixes added a new, dedicated regression section proving the specific bug is closed, alongside every pre-existing assertion left untouched.
4. **Re-run the affected `db-test` file(s) fresh, against a disposable, drop-and-recreate database, at least 3 independent times** — this repository's own standing convention for any migration-touching repair (`CPL-321`/`CPL-322`/`CPL-323` each ran 4-5 independent fresh runs; `CPL-325` ran its two genuine concurrency-race fixes against a real multi-process harness, not merely a sequential re-run).
5. **Re-run the full repository gate suite** (`pnpm run typecheck`, `pnpm run lint`, `pnpm run test`, and the full `bash scripts/db-tests/run.sh` harness, excluding only the already-registered, unrelated, day-of-week-dependent HRIS fixture flakes per `ISS-2026-115`/`103`/`135`) before considering the fix complete.
6. **Update `docs/runtime/KNOWN_ISSUES.md` additively** — mark the original entry `RESOLVED`/`SUPERSEDED` in place, citing the new migration; never delete or silently rewrite a prior entry's own text. Note: per this document's own standing scope discipline, `docs/runtime/KNOWN_ISSUES.md`, `docs/runtime/TASK_LEDGER.md`, `docs/runtime/CARGOGRID_BUILD_STATUS.md`, `docs/runtime/HANDOFF.md`, and `docs/build-log/phase-08/00_EXECUTION_INDEX.md` are the orchestrating session's own files to update at a real checkpoint boundary — an individual bounded fix pass drafts the disclosure and hands it to that session rather than editing those five files directly.

**Resolution path summary:** identify the real owning migration → confirm it is genuinely a defect, not a documented boundary → reproduce it live → write one new additive migration in the smallest correct shape from the four listed above → add a regression proof to the existing test file → re-run the full gate suite fresh → disclose additively. This is the complete, exact procedure every real fix in Phase 8's own history followed — no other path exists, and no Phase 8 migration has ever been edited in place after being applied.
