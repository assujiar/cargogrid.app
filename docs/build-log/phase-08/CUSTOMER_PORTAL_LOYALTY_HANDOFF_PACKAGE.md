### 2.1 The single-root dependency DAG (architecture-level fact every downstream reader needs first)

Unlike Phase 7's two-independent-chains shape, Phase 8 converges through one mandatory root, per `00_EXECUTION_INDEX.md` §5:

```
CPL-299 (kickoff)
   │
   ▼
CPL-300 (Customer User Scope) ── the mandatory scope primitive; gates every capability below
   │
   ├─► CPL-301 (Dashboard)
   ├─► Commercial Self-Service:      CPL-302 → 303 ⇢ 304
   ├─► Shipment Visibility:          CPL-305 → 306, CPL-307 → 308 (needs 304 named, not schema-dependent)
   ├─► Warehouse Visibility:         CPL-309 → 310
   ├─► Finance Visibility:           CPL-311 → 312
   ├─► Service/Account:              CPL-313, CPL-314 → 315
   └─► Loyalty:                      CPL-316 → 317 → 318 → 319 → 320 → 321 → 322 → 323
                                                                              │
                                                                              ▼
                                              CPL-324 → 325 → 326 (this doc) → 327
                                              (closure track, strictly serial, never batched)
```

**Disclosed correction, load-bearing for any future reader** (`00_EXECUTION_INDEX.md` §5's own post-implementation note): the 302→303 edge is a **real** schema dependency (`app.customer_portal_booking_requests.linked_quote_request_id` is a live FK into `app.customer_portal_quote_requests`). The 303→304 edge, despite being drawn solid and despite both the prompt package and `CG-S13-CPL-006`'s own predecessor row naming it, is **not** a real schema/data dependency — `20260801050000_create_customer_portal_shipment_order_access.sql` is grep-confirmed to contain zero references to `app.customer_portal_booking_requests` anywhere in its body; CPL-304 reads only the pre-existing `app.shipment_orders` (Phase 5/OPS-169) plus CPL-300's own scope resolver. The predecessor rows in §2's own table above still correctly encode release/execution **order**, not a schema dependency claim.

## 4. Step 14 handoff boundary (AI/predictive/reporting/automation/enterprise expansion — Phase 9, Intelligence/Enterprise)

This section documents **what is true today**, per source spec §20's own "prepare Step 14 handoff boundaries" instruction — it is boundary documentation, not a design proposal, and invents no roadmap Phase 9 has not been scoped for.

### 4.1 Concrete extension points that already exist

A future analytics/reporting/AI layer can read the following **append-only** tables directly (via a new, dedicated read-only RPC layer — never raw-table access, since `authenticated` holds zero grant on any of them, ADR-0024 Part A) **without any new schema**:

- **Loyalty ledgers (6 tables, source of truth for every Loyalty total in this repository):** `app.loyalty_earning_events`, `app.loyalty_point_ledger_entries`, `app.loyalty_account_tier_movements`, `app.loyalty_benefit_entitlement_events`, `app.loyalty_reward_stock_reservations`, `app.loyalty_redemption_events`. Five of these six are Supreme-Admin-override-protected (§3.7/§3.8 above — genuinely audit-logged if ever mutated by that one accepted-risk path); `app.loyalty_account_tier_movements` is not yet (`ISS-2026-137`). All six are insert-only in ordinary operation — safe to aggregate, safe to build a materialized/derived reporting layer over, exactly as `CPL-323`'s own `app.execute_loyalty_liability_reconciliation_run` already does by recomputing every liability total live from these same rows rather than trusting any cached column.
- **Customer-portal request/intent tables** (all append-only-in-spirit, state-machine-governed, never silently overwritten): `app.customer_portal_quote_requests`, `app.customer_portal_booking_requests`, `app.customer_portal_profile_change_requests`, `app.loyalty_point_adjustment_requests`, `app.loyalty_fraud_review_cases` — each carries a full, queryable status-transition history (either its own `_events`-table sibling or `app.audit_logs`), a plausible source for a future "customer self-service funnel" or "loyalty fraud pattern" analytics feature.
- **Existing pre-Phase-8 append-only ledgers already reusable the same way:** `app.inventory_movements`/`app.inventory_balances` (Phase 5, the pattern Loyalty's own ledgers mirror), `app.ticket_events`/`app.ticket_escalation_events` (Phase 7), `app.audit_logs` (Platform Core, every Phase 8 privileged action's own audit trail — `app.assert_actor_is_session_identity` is confirmed the literal first statement in every privileged RPC checked at CPL-325).
- **A real, working liability/engagement analytics precedent to extend, not replace:** `app.get_loyalty_engagement_metrics`/`app.get_customer_portal_loyalty_summary` (CPL-323) are genuine, tested, currency-scoped aggregation RPCs — a Phase 9 analytics layer composing them (rather than re-deriving the same totals a third way) avoids the exact "second, independently-evolving enforcement point" class ADR-0024 Part A warns against (a defect of this shape was found and fixed once already, inside CPL-323 itself, at its own Tier C review).
- **The `app.jobs`/PLT-132 background-job framework** already exists, already runs `app.run_loyalty_expiry_sweep` on-demand — a future scheduler wiring (not built anywhere in this repository yet, for any domain) could reach every one of the six "on-demand/staff-triggered only" Loyalty primitives (§5 below, `ISS-2026-126`/`127`/`128`/`129`/`132`/`133`/`134`) through this same, already-proven, additive `job_type`-widening mechanism, without inventing a second job system.

### 4.2 Concrete gaps a Phase 9 agent must NOT assume are solved

- **RPD-023 (MFA/step-up-authorization) does not exist anywhere in this repository.** Not for Loyalty reward approval, not for fraud-case release, not for any privileged customer-admin/export/support action — confirmed by direct repository-wide grep this checkpoint, unchanged since Phase 1. `app.assert_actor_is_session_identity` (the "current-auth" half of RPD-023) **is** real and is confirmed the first statement in every privileged RPC checked, but re-authenticating an already-live session at the moment of a high-risk action is not built anywhere. **A Phase 8-specific disclosure-completeness gap compounds this**: `ISS-2026-138` (§5 below) found the RPD-023 disclosure practice itself was silently dropped for CPL-314 and all of CPL-316–323 — including reward approval (CPL-320/321) and fraud release (CPL-322), the two categories source spec §20 item 4 names by name — and that `ISS-2026-125`'s own citation of a CPL-314 disclosure is false (CPL-314's build log contains zero MFA/RPD-023 mentions). **A Phase 9 agent must not read Phase 8's own uneven citation pattern as evidence the underlying gap narrows anywhere it stops being mentioned** — the gap is uniform and repository-wide regardless of which build log happens to name it.
- **No live GraphQL server exists anywhere in this repository.** REST/GraphQL parity is satisfied by shared contract-shape reuse only (ADR-0024 Part C, §3.10 above) — a Phase 9 agent building any GraphQL-shaped consumer over Phase 8 data starts from zero live infrastructure, not from an existing-but-Phase-8-scoped GraphQL layer.
- **No session/token-revocation primitive exists anywhere in this repository** (`ISS-2026-125` item 2) — a revoked customer-portal member loses access only because every read RPC re-checks live status on every call, never because a session/JWT/token itself was invalidated. A Phase 9 real-time/streaming/webhook consumer must not assume a revoked identity's existing session/token stops working immediately by any mechanism other than the next RPC call re-checking scope.
- **No automatic trigger wires any of six real, complete, idempotent Loyalty primitives to the business event that should invoke them** — earning evaluation is not wired to a paid-invoice event (`ISS-2026-126`), tier recalculation is not wired to a new earning event (`ISS-2026-127` item 1), points lot-conversion/expiry (`ISS-2026-128` items 1–2), benefit issuance/expiry (`ISS-2026-129` item 2), a genuine customer self-service instant redemption (`ISS-2026-132` item 1), and the expiry sweep (`ISS-2026-133` item 3, `ISS-2026-134` item 4) are each on-demand/staff-triggered only. **A Phase 9 automation layer must not assume any of these fire on their own** — building the missing scheduler/trigger wiring is itself a real, named, not-yet-built extension point (§4.1 above), not a solved problem.
- **No Finance-side liability handoff exists yet** (`ISS-2026-129` item 1, `ISS-2026-134` item 5) — Loyalty stays its own source of truth; nothing pushes a certified liability total into any `app.finance_*` table. A Phase 9 (or earlier) Finance-integration effort starts from CPL-323's own certified-run evidence, not from an existing handoff contract.
- **The three disclosed residual issues from CPL-325 (`ISS-2026-137`/`138`/`139`) are all still `OPEN`** as of this checkpoint (§5 below verifies this fresh) — none was silently closed between CPL-325 and this documentation pass.
- **No predictive/rule-engine fraud-signal detection exists** — every `app.open_loyalty_fraud_review_case` call today is itself staff-initiated (source spec's own explicit "predictive fraud depth remains Step 14" business rule, `00_EXECUTION_INDEX.md` §6). A Phase 9 agent building that engine must give it its own distinct `opened_by` identity separate from any human `LYL:Configure` actor, and should structurally block a human from deciding a case they personally opened once such an engine exists (currently unblocked for human-opened cases, `ISS-2026-133` item 1) — named here as the concrete shape of the gap, not as a scoped Phase 9 requirement.
- **This is not a production/pilot/GA/market-ready system** (RPD-034/036, restated per this document's own governing instruction) — no live Supabase project, no real sign-in flow, no real deploy pipeline exists anywhere in this repository, unchanged since every prior phase's own identical disclosure.
