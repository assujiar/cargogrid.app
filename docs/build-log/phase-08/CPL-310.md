## 1. What this checkpoint builds

CPL-310 gives a scoped customer-portal user read-only visibility into WMS-owned warehouse outbound orders and their own real fulfillment status (draft/confirmed/cancelled, mapped to a customer-visible label) — but its real job, exactly like CPL-309 the checkpoint immediately before it, is closing the SAME `ISS-2026-117` scope-composition gap, applied here to warehouse orders instead of inventory balances:

- **ATW-023** (Phase 5) built the first customer-facing order-read RPCs (`app.get_customer_outbound_order`/`app.list_customer_outbound_order_lines`/`app.list_customer_outbound_orders`), but every one of them resolves scope via `app.resolve_customer_owner_account_scope`, which reads ONLY the legacy single-account `app.principal_memberships.customer_account_ref` marker.
- **CPL-300** (Phase 8) introduced the widened resolver, `app.resolve_customer_account_scope`, returning the UNION of the legacy marker and the new multi-account `app.customer_portal_account_memberships` grant table.
- **CPL-309** already built and proved the fix shape for inventory balances/warehouse eligibility, including the one shared gate primitive, `app.evaluate_customer_portal_inventory_access`, that this checkpoint reuses byte-for-byte, unmodified, with zero new gate primitive of its own.

A customer_portal user granted a second account only through CPL-300's new grant table would be invisible to all three of ATW-023's original order RPCs — the identical under-scoping (false-negative, never a leak) gap CPL-309 already closed for balances. This checkpoint closes it for warehouse orders, by mirroring ATW-023's three order RPCs column-for-column onto the already-proven CPL-309 gate.

## 3. A real defect this checkpoint's own db-test authoring found and fixed before shipping

The db-test's first draft tried to prove "a live status transition (draft → confirmed) is immediately visible, with a genuinely bumped `record_version`/`updated_at`" inside a SINGLE `do $$ ... $$` block: create the order, read it (draft), call `app.confirm_wms_outbound_order`, read it again (confirmed), and assert `updated_at` had advanced. It failed live: `expected updated_at to genuinely advance after confirm (before 2026-08-17 04:20:41.851986+00, after 2026-08-17 04:20:41.851986+00)` — byte-identical timestamps. Root cause: Postgres's `now()` (which the shared `touch_wms_outbound_orders_row` trigger calls) is fixed for the entire duration of one transaction, and a single `do $$ ... $$` block IS one transaction — a `pg_sleep()` inside it does not help, since wall-clock time passing does not change what `now()` returns within that same transaction. **Fixed** by splitting the create+first-read and the confirm+second-read into two genuinely separate top-level statements (psql's own default autocommit boundary), each therefore getting its own real, later `now()`. Re-run passed clean. A second, purely mechanical issue surfaced while making that fix: the new inline comment describing the two-statement split itself used the literal characters `do $$ ... $$` inside a SQL comment, which prematurely terminated the enclosing dollar-quoted `do $$ ... $$` block's own string (a `$$`-inside-a-`$$`-quoted-comment collision) — caught immediately by a `syntax error at or near ".."` on the very next scratch run, fixed by rephrasing the comment to avoid the literal substring.
