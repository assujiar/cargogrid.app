# CPL-301 — Customer Portal Dashboard

**Prompt ID:** `CG-S13-CPL-003` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/301_CUSTOMER_PORTAL_DASHBOARD_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (2026-08-16 — Batch 1's own Tier C review closed across all of CPL-301..304 together; see §14 for the 4-lens review/fix record and the orchestrating session's own independent gate re-run)

## 1. What this checkpoint builds

CPL-301 is the second Phase 8 capability, the second member of Workstream 1 ("Customer Access Foundation") alongside CPL-300. It builds the full customer portal dashboard card grid CPL-300's own build log explicitly deferred ("the full dashboard is Prompt 301's own job"): one new, live-aggregating `SECURITY DEFINER` RPC (`app.get_customer_portal_dashboard_summary`) composing every real, already-shipped customer-facing data source in this repository, plus a new UI route (`customer-portal-dashboard`) rendering nine cards — three real, six honest stubs — each independently showing its own available/degraded/unavailable state.

## 2. Design decisions (cited, not re-derived — full rationale in the migration's own 10-point header)

1. **No new dashboard read-model/cache/snapshot table.** "Pre-aggregated dashboard read models" (source prompt §13) is implemented as a LIVE, `stable`, uncached aggregating RPC — this repository has no scheduler/cron-style job-refresh infrastructure to keep a cache fresh, and building one is explicitly out of this task's own scope.
2. **Composes ONLY real, already-existing customer-facing data sources.** The three real cards are `accounts` (CPL-300's `app.get_customer_portal_scope_context`), `warehouse_inventory` (ATW-023's `app.list_customer_inventory_balances` + `app.list_customer_outbound_orders`, ONE combined card per the task's own "e.g." framing), and `tickets` (HRT-287's `app.list_customer_tickets`). Every other named card (`bookings`/`shipments`/`invoices`/`payments`/`loyalty`) is returned `available=false`, `summary={}`, `detail_path=null` — never fake data. `alerts` (named in the source prompt's own §15 but not in the orchestrator task's explicit stub enumeration) is included as a ninth, disclosed stub card rather than silently dropped (recurring-defect-taxonomy C-23) — it is cross-cutting (a future shipment-exception alert is CPL-306's own job, a ticket-SLA-breach alert is CPL-313's own), not owned by any single future capability, so it is disclosed here rather than assigned.
3. **Anti-enumeration/scope (ADR-0024 Part A).** `app.assert_actor_is_session_identity(p_auth_user_id)` is the first statement. The canonical resolver `app.resolve_customer_account_scope` is called directly and used as a genuine, additional per-row filter on every real card's own composed data — belt-and-suspenders defense in depth on top of what each composed RPC already enforces internally, since this RPC takes no client-supplied account-id parameter to distrust in the first place.
4. **Two of the three composed RPCs (`app.list_customer_inventory_balances`, `app.list_customer_outbound_orders`) do not call `app.assert_actor_is_session_identity` themselves** — a real, pre-existing, disclosed gap (`ISS-2026-117`, not caused by this task, not fixed here since an applied migration may not be edited in place). This checkpoint's own composition is safe regardless: it always passes through its own already-cross-checked `p_auth_user_id`, never a second, client-suppliable identity.
5. **Per-card resilience.** Each real card's own composed-RPC call is wrapped in its own nested `BEGIN...EXCEPTION WHEN OTHERS...END` block — one source's genuine failure marks only that card `degraded=true` with a safe zero default; every sibling card is unaffected. Live-proven with a real, reversible technique (session-scoped `ALTER FUNCTION ... RENAME`, never committed to any migration) — not reasoned about.
6. **Bounded, disclosed-approximate counts.** No dedicated count-only RPC exists for any composed source, so each count pages the existing list RPC at its own 200-row hard cap and flags `...Capped=true` when the raw page itself came back full (meaning more may exist beyond this one bounded read) — never silently reported as exact.
7. **`source_updated_at`** reflects the real underlying data's own recency where the composed RPC exposes one (`GREATEST` of both halves for the combined `warehouse_inventory` card); `accounts` uses `now()` since `app.get_customer_portal_scope_context` (an already-applied CPL-300 migration) exposes no per-row timestamp of its own, and this migration deliberately does not open a second, competing raw-table read path against `app.customer_portal_account_memberships` to manufacture one.
8. **`detail_path`** is a real route or `null`, never a dead link. `accounts` → `customer-portal`; `tickets` → `customer-tickets`; `warehouse_inventory` → `null` (ATW-023 built no UI route by its own design — that is Prompt 309/310's chartered scope, not this one's, and building it here would be a forbidden "duplicate warehouse root"). Every stub card is also `null`.
9. **No mutation, no idempotency key** — a pure `stable` read.
10. **ATW-032 authority-surface sweep compliance, automatic.** The new function's own body directly calls `app.resolve_customer_account_scope(...)`, an already-recognized base-regex authority primitive (CPL-300's own widening) — `scripts/db-tests/rbac-enforcement.sql` credits it transitively via substring match, with no edit to that shared file required. Verified live (§10 below).

## 8. A design question this checkpoint had to resolve that was not fully specified

The task's own instruction #4 asked to "check whether a shared `layout.tsx` makes sense for future Phase 8 routes under this same directory tree and add one if it clearly reduces duplication, but do not over-engineer." This gets the de-duplication benefit today without moving any already-`VERIFIED` file, and is explicitly disclosed here as a deliberate, bounded choice rather than a missed opportunity — a real `layout.tsx` becomes clearly worth the structural change once a third Phase 8 route lands under this same tree (Prompt 309 onward), at which point three-or-more siblings make the shared-shell case unambiguous.

## 11. Adversarial testing — live, against a real disposable Postgres 16 database (not reasoned about)

All of the following used `postgresql://127.0.0.1:5432`, a freshly created disposable database, the full migration set (through `20260801020000`) applied, using the standard `set_config('request.jwt.claims', ...)` + `set role authenticated` forged-session technique where a real session was needed.

1. **Happy path** — a real account_admin with real inventory/outbound-order/ticket data sees all 9 documented `card_key`s; the three real cards carry correct counts, non-null `source_updated_at`, and correct `detail_path`; a cancelled outbound order and a cancelled ticket are correctly excluded from their own open counts; the six stub cards are structurally honest (`available=false`, `summary={}`, `detail_path=null`, `source_updated_at=null`).
2. **Deny-by-default** — an identity invited to the tenant but never granted ANY customer-portal scope of any kind (not merely revoked — genuinely zero relationship) sees the same 9 cards, real cards present with zero counts, never an error.
3. **Cross-tenant isolation** — an identity with real data in tenant `cpd1`, queried against a completely separate tenant `cpd2`, sees zero on every real card.
4. **Revocation immediate effect** — an account_admin's own real counts (1 account) before revoke; the SAME identity, same session, sees zero immediately after `app.set_customer_portal_account_membership_status(..., 'revoked', ...)` — no caching, exercising CPL-300's own Tier C legacy-marker-sync fix transitively.
5. **Actor-identity session cross-check** — a genuinely different authenticated session claiming to act as another identity is rejected with `actor_identity_mismatch` before any card is computed.
6. **A REAL `authenticated`-role session (not merely a superuser-driven call) gets identical real data** — a positive-path proof this checkpoint's own investigation found no prior Phase 8 db-test had exercised (every prior positive-path assertion in `customer-portal-scope.sql` runs as the connecting superuser with explicit parameters, never under a real RLS-active `authenticated` session). Confirms `SECURITY DEFINER` ownership-bypass genuinely holds end-to-end, not merely by source-code inspection.
7. **Raw grant defense-in-depth** — `anon` holds no `EXECUTE` on the new function; `authenticated`/`service_role` both do.
8. **Per-card resilience, live-forced** — `app.list_customer_tickets` temporarily renamed away (session-scoped `ALTER FUNCTION ... RENAME`, reverted before the test file exits); the resulting fresh call marks ONLY the `tickets` card `degraded=true` (with a safe zero count, `available` still `true`) while the sibling `accounts`/`warehouse_inventory` cards return their own fully correct data, unaffected. Design-time technique validation (scratch-only, never committed): before writing the migration's own db-test, the `ALTER FUNCTION ...
