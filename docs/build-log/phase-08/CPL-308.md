# CPL-308 — Document Center

**Prompt ID:** `CG-S13-CPL-010` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/308_DOCUMENT_CENTER_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (2026-08-17 — batch Tier C review across `CPL-305..309` complete; see §15)

## 1. What this checkpoint builds

CPL-308 gives a scoped customer-portal user one unified, searchable/filterable view across every real, already-existing customer-facing document source — quote-request attachments (CPL-302) and ePOD evidence files (CPL-307) today — plus a scoped, audited per-document access ("download") action. This is a **composition/index capability over already-existing sources**, per the source prompt's own database-impact line ("file bytes remain Platform-owned") — zero new file store, zero new upload path, zero duplicated metadata truth. Two new functions, zero new tables.

## 2. Design decisions (cited where given by the orchestrating task; disclosed where this checkpoint had to resolve something itself)

1. **Live UNION ALL, never a durable index table.** The orchestrating task offered both options explicitly. This migration picks the live UNION, mirroring CPL-301's own already-established precedent (`20260801020000_create_customer_portal_dashboard_summary.sql` design decision 1: no persisted dashboard cache, "this repository has no scheduler/job-refresh infrastructure to keep a cache fresh"). A durable `app.customer_document_index` table would need its own write-time population hook at every one of `app.initiate_file_upload`, `app.complete_epod_capture`/`app.record_file_scan_result`, and every future document source (Prompts 311/313) — a second, independently-evolving source of truth that could silently drift, the exact class `20260730310000_create_advanced_tms_customer_inventory_access.sql` design note 6 already named and `20260730311000` had to correct once. A live UNION reads the four source tables directly on every call, so it can never be stale. **Trade-off, disclosed**: a durable index would paginate more cleanly across heterogeneous sources once there are many of them — accepted for now, at 2 real sources, revisit if/when Prompts 311/313 land and the arm count grows enough that live composition stops being genuinely simpler (the same latitude CPL-301's own design decision 1 already accepted for the dashboard).
2. **Two real source-module union arms today; two more recognized but honestly empty.** `quote_request` (an `app.files` row under `record_type='customer_portal_quote_request'`, scoped via `app.customer_portal_quote_requests.account_id`, mirroring `app.list_customer_quote_request_files`'s own join shape exactly) and `epod` (an `app.files` row referenced by `app.epod_captures.signature_file_id`/`photo_file_ids` for a `completed`, `is_latest_version` capture on an in-scope shipment order, mirroring `app.get_customer_epod`'s own discovery logic, minus that function's own whole-capture quarantine collapse — see decision 5). `invoice` (Prompt 311) and `ticket` (Prompt 313) do not exist as document sources anywhere in this repository yet (grep-confirmed) — both are still recognized, validated `p_source_module` values that deterministically return zero rows, never an error, exactly like CPL-301's own honest "not yet available" stub-card pattern applied to a filter option instead of a dashboard card. `app.customer_portal_booking_requests` (CPL-303) and `app.customer_portal_shipment_change_requests` (CPL-304) are deliberately **not** a fifth/sixth arm — neither ever registers a PLT-128 document type or calls `app.initiate_file_upload`, so neither is a genuinely "already-existing document source" this capability could compose without inventing a new upload path — out of scope, not a silent omission.
3. **No new upload path.** Business rule 1 and the orchestrating task's own "composition/index capability" framing together mean this migration adds no `initiate_file_upload`-calling wrapper. A customer adding a new quote-request attachment still does so on the existing `customer-quotes/[requestId]` page (CPL-302); ePOD evidence is staff-captured and was never customer-uploadable (CPL-307). Document Center is read-only plus a scoped download/access action.
4. **`app.get_customer_document` takes the underlying `app.files.id` directly as `p_document_id`, never a synthetic composite key.** Both real sources are, structurally, `app.files` rows. The function independently re-derives which source a file belongs to (from its own `record_type`) and re-applies that source's own scope check from first principles — it never trusts a client-supplied source hint, because business rule 4 ("a document link grants no access to its source record or other linked documents") means a forged hint must never widen access. A `record_type` this capability does not compose, or a `shipment_order`-typed file not actually referenced by any completed ePOD capture, is treated identically to a nonexistent file.
5. **Malware/quarantine states are surfaced PER DOCUMENT on the list, never collapsed** — a deliberate, disclosed divergence from `app.get_customer_epod`'s own whole-capture quarantine collapse (CPL-307). `app.list_customer_documents` returns every in-scope document's own real, live `malware_scan_status`, never filtered or defaulted to `clean`. **Tier B self-catch, this migration's own first live db-test run**: `app.get_customer_document`'s "refuse a non-clean download" behavior is deliberately **not** expressed as a raised database exception. A `raise exception` immediately after its own `app.file_access_logs` INSERT would roll that same INSERT back the moment an uncaught caller (the ordinary `client.rpc(...)` shape) lets the exception propagate — PostgreSQL rolls back a failed statement's entire side-effect set atomically, and this repository has no autonomous-transaction primitive to isolate the log write from the raise. The function instead always returns a normal, successful row once scope is established (writing a GRANTED or DENIED `app.file_access_logs` row accordingly) — the actual `document_not_downloadable` refusal is enforced one layer up, at the TypeScript service boundary (`server/mutations/customer-document.ts`), **after** the RPC's own audit trail has already durably committed. This is a correction made mid-checkpoint, live-caught, not reasoned about in advance — see §3 below.
6. **Anti-enumeration shape mirrors CPL-307's own non-uniform precedent.** `app.list_customer_documents` is deny-by-default. `app.get_customer_document` combines "genuinely nonexistent," "wrong tenant," "a file type this capability does not compose," and "exists but out of scope" into ONE anti-enumerating `document_not_found` — the *only* case this function raises at all. A non-`clean` scan status is reachable only after scope is genuinely established — never a distinguishable signal for an out-of-scope caller.
7. **`app.file_access_logs`/`app.capture_audit_event` reused directly, exactly like CPL-307** — no parallel audit table. `app.get_customer_document` writes exactly one `app.file_access_logs` row per matched call as part of its own normal, successful return, and one `app.capture_audit_event` row for the zero-match "not found" case. That raising path's own audit durability is a shared, pre-existing question across every "capture_audit_event then raise" call site this repository's Phase 8 capabilities already use identically (e.g. CPL-307's own `record_not_found` path) — not unique to or newly introduced by this migration, and out of this bounded capability's own scope to redesign repository-wide (disclosed, not fixed, §8). `app.list_customer_documents` is a plain, unaudited read, matching every other Phase 8 list RPC's established precedent.
8. **`p_source_module` validation is application code, not a CHECK constraint** — zero new table means no column to constrain. The 4-value enum is enforced by an explicit guard inside `app.list_customer_documents`, cross-checked at the TypeScript boundary by a matching Zod enum.
9. **No new index.** Every join predicate is already covered by an existing, already-applied index (`files_tenant_record_idx`, `cpqr_account_idx`, `epod_captures_tenant_shipment_idx`, `epod_captures_one_latest_version_idx`, `shipment_orders_tenant_shipper_account_idx`). At this capability's own bounded, per-identity scope, no new covering index is justified — mirrors CPL-307 (also zero new index).
10. **RLS: this migration touches ZERO table.** No new table; no RLS policy on `app.files`/`app.epod_captures`/`app.customer_portal_quote_requests`/`app.shipment_orders`/`app.file_access_logs` is edited. Every one of those tables' own pre-existing policies already correctly denies a bare `customer_user`-layer principal by default (re-verified live).
11. **REST/GraphQL transport (ADR-0024 Part C)**: service layer + Server Actions + UI only, no `app/api/` route — identical in kind to CPL-300..307's own disclosed residual gap.
12. **No edit to `scripts/db-tests/rbac-enforcement.sql`** — both new functions call `app.assert_actor_is_session_identity` directly and `app.resolve_customer_account_scope` (both already-recognized base-regex authority primitives) — confirmed live, no edit required.
13. **UI: a new standalone route, `app/(tenant)/[tenantSlug]/customer-documents/`**, per the orchestrating task's own instruction — list with filters, no detail sub-route (each row's own scoped download action is sufficient; business rule 4 is satisfied precisely by not building a document detail page that would need to re-project the source entity's own other fields).
14. Per `ERR-2026-004`: this migration carries its own explicit `revoke execute on all functions in schema app from public` before its final grants.

## 3. Real defects this checkpoint's own authoring/testing found and fixed before shipping

1. **`returns table(...)` OUT-parameter/CTE-column ambiguity (the exact class CPL-304/CPL-307's own headers warn about) — live-caught, not reasoned about in advance.** `app.list_customer_documents`'s own `returns table (..., account_id uuid, ...)` shape creates an implicitly-named OUT parameter `account_id`. The first draft's `epod_file_refs` CTE referenced `shipment_order_id`/`account_id` unqualified against the `epod_captures_scope` CTE, and the `combined` CTE referenced every column unqualified via `select *` against `quote_request_docs`/`epod_docs` — both genuinely ambiguous to the planner (`ERROR: column reference "account_id" is ambiguous`). **Fixed**: every reference in both CTEs now uses an explicit table alias (`ecs.`/`q.`/`e.`), applying CPL-304/307's own lesson from a live failure this migration's own first db-test run reproduced directly, not merely cited.
2. **A raised `document_not_downloadable` exception silently discarded its own preceding audit-log INSERT — live-caught by this checkpoint's own db-test assertion, not reasoned about in advance.** The first draft's `app.get_customer_document` inserted a DENIED `app.file_access_logs` row, then `raise exception`d `document_not_downloadable`. The db-test's own assertion ("expect exactly 1 denied log row") failed with `got 0` — because the enclosing `exception when ... then` block (or, in real usage, PostgreSQL's own atomic statement-rollback-on-error) rolled the INSERT back along with the raise. **Fixed at the root, not merely re-disclosed** (design decision 5 above): the RPC never raises for a non-`clean` scan status — it always returns a normal, successful row with the correct GRANTED/DENIED log already durably written; `document_not_downloadable` is now raised one layer up, in `server/mutations/customer-document.ts`, strictly after the RPC call has resolved successfully. Both the SQL migration's own header and the TypeScript wrapper's own doc comment record this correction explicitly. `server/mutations/customer-document.test.ts` and `scripts/db-tests/customer-document-center.sql` were both updated to assert the corrected shape (a successful row carrying the real `pending`/`infected` status, plus a durably-committed denied log row) rather than a caught exception.
3. **A db-test's own `invalid_cursor` assertion had its cursor arguments backwards.** The first draft supplied `p_cursor_created_at` alone (no `p_cursor_id`) expecting `invalid_cursor` — but the function's own validated shape (matching every other Phase 8 list RPC) only rejects `p_cursor_id` supplied *without* `p_cursor_created_at`; the reverse combination is harmlessly ignored by the `WHERE` clause's own `p_cursor_id is null or (...)` short-circuit. **Fixed**: the test now supplies a real `p_cursor_id` with a `null` `p_cursor_created_at`, matching the function's actual validated shape.
4. **`app.register_document_type('epod', ...)` requires a genuine Supreme Admin actor, unconditionally — even when the code is already registered by an earlier-running db-test file.** The db-test's first draft called it with a plain `tenant_admin` staff identity (mirroring the wrong precedent), raising `insufficient_authority`. **Fixed**: added a real Supreme Admin identity to the fixture (mirroring `scripts/db-tests/customer-epod-access.sql`'s own exact pattern) and used it for that one call.
