# CPL-316 — Loyalty Program and Earning (Prompt 316, `CG-S13-CPL-018`)

**Status:** `VERIFIED` (Batch 4's own Tier C review, across `CPL-315..319`, closed — see §14)

## 1. What this checkpoint builds

The FIRST-EVER Loyalty domain schema in this repository (ADR-0024 Part D). Four new tables — `app.loyalty_programs`, `app.loyalty_program_rule_versions`, `app.loyalty_accounts`, `app.loyalty_earning_events` — plus a real, idempotent earning-evaluation RPC that reads Finance's already-committed `app.finance_ar_open_items` state (never writes to it) and records a customer's loyalty earning as an append-only ledger event. This checkpoint owns program configuration, effective-dated rule versioning, enrollment, and the raw earning-event ledger only — a derived points balance (CPL-318) and cashback/voucher entitlements (CPL-319) are explicitly out of this checkpoint's own scope, per the batch's own dependency graph.

## 2. Design decisions

1. **At most one ACTIVE `loyalty_account` per (tenant, customer_account_id), tenant-wide, across every program** (`constraint la_status_check` + partial-unique-shaped enforcement) — this is what makes "the customer's active loyalty_account" well-defined for `app.evaluate_customer_loyalty_earning_for_paid_invoice`, which takes no `p_program_id` parameter by design. A customer may still hold multiple historical (suspended/closed) rows across different programs.
2. **`app.loyalty_earning_events` mirrors `app.inventory_movements`' shape exactly** (`supabase/migrations/20260730190000_create_advanced_tms_inventory_ledger.sql`, the pattern ADR-0024 Part D names): append-only, `unique (tenant_id, idempotency_key)`, `corrects_event_id uuid references app.loyalty_earning_events (id)` for reversal (a new linked row, never a status flip or delete on the original), `reason` mandatory only when `corrects_event_id is not null`.
3. **No derived balance table in this checkpoint.** `app.loyalty_earning_events` is the raw, reward-type-tagged earning ledger every subsequent Loyalty prompt reads from; deriving a points balance (CPL-318) or cashback/voucher entitlement (CPL-319) is explicitly those prompts' own scope, not duplicated or anticipated here.
4. **Reward type is constrained to `('points', 'cashback')`** on both `loyalty_program_rule_versions.reward_type` and `loyalty_earning_events.reward_type` — discount/voucher issuance (CPL-319) is config-driven separately from a raw earning event, not a third reward type flowing through this table.
5. Rule versions are **effective-dated and immutable once published** (`status: draft -> published -> superseded`) — `app.update_loyalty_program_rule_version_draft` only permits edits while `status = 'draft'`; `app.publish_loyalty_program_rule_version` supersedes the program's prior published version (never mutates it) and stamps `published_by`/`published_at`. A historical `loyalty_earning_events` row keeps the `rule_version_id` it was evaluated under permanently — a later rule change never retroactively rewrites a recorded earning amount.
6. **`earning_basis` is an explicit, checked vocabulary** (`per_paid_invoice_amount` is the only basis this checkpoint's evaluator computes) rather than a free-text field silently accepted and silently ignored — an unsupported basis raises `unsupported_earning_basis` rather than defaulting to zero or skipping evaluation.
7. **Eligibility minimum is read from `eligibility_config->>'min_invoice_amount'`** (jsonb), a real, enforced check (`ineligible_amount_below_minimum`), not a documented-but-unenforced convention.
8. **Reward amount rounding**: cashback rounds to 2 decimal places (currency-shaped); points round to the nearest whole unit (`round(amount * rate)`, no fractional points) — disclosed explicitly since the two reward types have genuinely different natural precision.
9. **On-demand/staff-triggered earning evaluation only** (`app.evaluate_customer_loyalty_earning_for_paid_invoice`, gated `LYL:Edit`, called from a new admin UI action) — no automatic job or Finance-side hook wires it to the moment `app.finance_ar_open_items.status` actually flips to `'paid'`. A real, working, complete RPC exists; the automatic-trigger wiring is deliberately deferred, disclosed as `ISS-2026-126` (Low, `OPEN`), not silently omitted.
10. **Idempotency key is deterministic and source-derived** (`'ar-open-item:' || p_ar_open_item_id::text`), never client-supplied and never `Date.now()`-based — calling the evaluator twice for the same paid invoice is a safe no-op returning the original event.
11. **Authority check runs before the idempotent short-circuit SELECT** (mandatory Phase 8 pattern) — a caller without `LYL:Edit` is rejected before the function reveals anything about whether an earning event already exists for that invoice.
12. **A real `exception when unique_violation` handler**, not merely a pre-check SELECT, guards the INSERT in both `evaluate_customer_loyalty_earning_for_paid_invoice` and `reverse_loyalty_earning_event` — a genuine concurrent double-submit converges on one row.
13. **`app.reverse_loyalty_earning_event` is a governed, staff-only correction** (`LYL:Configure`), inserting a new event with `corrects_event_id` set and a mandatory `reason` — the original event is never updated or deleted.

## 14. Tier C review and fix (Batch 4 close, `CPL-315..319`)

Four independent Tier C review lenses (spec-compliance, security/RLS, correctness/concurrency, cross-prompt-integration) examined all five Batch 4 migrations together. Findings specific to this capability's own migration (`20260801180000_create_customer_portal_loyalty_program_earning.sql`), disposition, and reasoning:

- **Fixed (Medium/High — flagged independently by all four lenses): `now()` used instead of `clock_timestamp()` throughout, the exact defect class CPL-315 self-found and fixed in this same batch.** This migration was written and merged BEFORE CPL-315's own fix existed, and — unlike CPL-317/318/319, all written after 315 and each explicitly citing it — was never revisited. Concretely, live-reproducible: `app.publish_loyalty_program_rule_version` updates two rows (supersedes the prior published version, publishes the new one) in one transaction; with `now()` frozen for the transaction, both got a byte-identical `updated_at`, making `app.list_loyalty_program_rule_versions`' `order by updated_at desc, id desc` non-deterministically tie-break on a random uuid on every republish. Fixed by switching every `default now()` column (`loyalty_programs`/`loyalty_program_rule_versions`/`loyalty_accounts`'s `created_at`/`updated_at`/`enrolled_at`, `loyalty_earning_events.created_at`), all three touch-row triggers, and the two explicit `now()` assignments inside `app.publish_loyalty_program_rule_version` (`v_effective_from`'s own fallback, `published_at`) and `app.set_loyalty_account_status` (`closed_at`) to `clock_timestamp()` — mirroring CPL-317/318/319's own already-applied pattern exactly. Disclosed as design decision 16 in the migration's own header. Did NOT affect the financially-authoritative "which rule version is currently active" resolution (governed by the `status = 'published'` partial unique index, never timestamp ordering) — only listing/history order was ever at risk. Live-reproduced and proven fixed with a new regression assertion in `scripts/db-tests/customer-loyalty-program-earning.sql`: republishing over a prior version now yields genuinely distinct `updated_at` values, and `app.list_loyalty_program_rule_versions` correctly sorts the just-published row first.
- **Fixed (Medium — correctness/concurrency lens): `p_expected_version IS NULL` silently bypassed optimistic concurrency in 4 functions** — `app.update_loyalty_program_status`, `app.update_loyalty_program_rule_version_draft`, `app.publish_loyalty_program_rule_version`, `app.set_loyalty_account_status`. Each function's own early `record_version <> p_expected_version` check evaluates to SQL NULL (treated as false) when `p_expected_version` is NULL, and none of the four UPDATE statements repeated the version predicate, so a NULL applied the write completely unchecked. Fixed by adding `and record_version = p_expected_version` to each UPDATE's own WHERE clause (a NULL then matches zero rows, falling through to the same `stale_version` error) — mirrors the shape `app.decide_loyalty_point_adjustment`/`app.reverse_loyalty_benefit_entitlement` (CPL-318/319) already used correctly. This repository's own TS contract layer already requires a positive integer for every one of these parameters, so the app's own callers were never exposed — but every one of these RPCs is `grant execute ... to authenticated`, reachable directly by a Supabase client, and this repository's own stated architecture treats RLS/SECURITY DEFINER functions as self-defending, not merely protected by the app layer. Live-reproduced and proven fixed with 4 new regression assertions in `scripts/db-tests/customer-loyalty-program-earning.sql` (one per function: NULL is rejected with `stale_version`, and the target row is confirmed unchanged).
- **Verified sound, no fix needed:** `app.evaluate_customer_loyalty_earning_for_paid_invoice` (the HIGH-SCRUTINY item) — confirmed genuinely idempotent (deterministic `'ar-open-item:' || id` key, real `unique_violation` handler), confirmed zero writes to `app.finance_ar_open_items` anywhere in this file (grep-verified, one plain `SELECT` only), confirmed a rule-version republish never retroactively alters a historical earning event (`rule_version_id` is frozen on the event row forever; publish only creates a new row, never mutates a prior one).

**Full-batch verification, run fresh after all fixes:** `bash scripts/db-tests/run.sh` against a fresh scratch database — `ALL PASSED`, exit 0. `pnpm run typecheck` — 0 errors. `pnpm run lint` — 0 errors, 301 pre-existing warnings (none new). `pnpm run test` — 4683/4683 pass.
