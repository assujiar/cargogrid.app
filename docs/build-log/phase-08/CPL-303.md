# CPL-303 — Booking

**Prompt ID:** `CG-S13-CPL-005` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/303_BOOKING_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (2026-08-16 — Batch 1's own Tier C review closed across all of CPL-301..304 together; see §14 for the 4-lens review/fix record — a Critical cross-account IDOR and a High concurrency/race defect were found and fixed at root cause — and the orchestrating session's own independent gate re-run)

## 1. What this checkpoint builds

CPL-303 lets a scoped customer-portal user book a shipment — either from an already-accepted (staff-converted) quote request or as a direct service booking — with pickup/delivery, schedule, and instructions, tracked through Operations acceptance. It is the second Phase 8 capability ADR-0024 Part B (customer writes) governs end to end after CPL-302: a new portal-owned request/intent table, a real staff-gated conversion acknowledgement, and zero widening of any canonical Commercial/Operations RPC or RLS policy. Unlike CPL-302, this checkpoint's own staff conversion RPC can (and does) structurally verify account ownership, because `app.job_orders`/`app.shipment_orders` carry real `account_id`/`shipper_account_id` FKs that `app.quotations` does not.

## 2. Design decisions (cited, not re-derived — full rationale lives in the migration's own header)

1. **A new portal-owned booking table, never a direct call into `app.job_order_handoffs`/`app.job_orders`/`app.shipment_orders`' own staff-gated creation RPCs.** `app.prepare_job_order_handoff` (COM:Edit), `app.prepare_job_order`/`app.create_shipment_order_from_job` (both OPS:Create) were read in full and confirmed staff-RBAC-gated; none is called from any function in this migration. `linked_quote_request_id` (nullable) supports the accepted-quote origin; a null value supports the direct-service-booking alternative flow — both first-class.
2. **pickup/delivery are bounded jsonb address+contact snapshots**, mirroring CPL-302's own origin/destination design decision exactly — no canonical address/contact master exists yet.
3. **"Accepted quote" means the linked quote request has already reached CPL-302's own `converted` status** — the closest concept this repository has to acceptance (CPL-302 has no separate "accepted" state). A still-draft/submitted/cancelled quote request is rejected (`quote_request_not_accepted`). Also enforced: same-account (`quote_request_account_mismatch`) and in-scope (anti-enumerating `quote_request_not_found`). **Disclosed interpretation**, not given verbatim by the source prompt.
4. **Submit has no second idempotency key**, deliberately simpler than CPL-302's own two-key split — the given column list for this table carries exactly one `idempotency_key` column (create-stage only). `app.submit_customer_booking_request` is a pure status flip with no other side effect, so a genuine retry is made safe by treating an already-submitted row as an idempotent no-op return (status check, not key comparison) rather than raising `invalid_transition`.
5. **Status machine is the given 6-value set**: `draft → submitted | cancelled`; `submitted → cancelled | converted | reschedule_requested`; `converted → reschedule_requested | cancel_requested`; `cancelled`/`reschedule_requested`/`cancel_requested` are all terminal **within this checkpoint's own RPC surface** (see decision 9). **Disclosed interpretation the checkpoint had to resolve**: draft/submitted (no operational truth committed yet) cancel straight to `cancelled`; `converted` (real `app.job_orders`/`app.shipment_orders` rows already exist) instead becomes `cancel_requested` — matches "changes after operational assignment become requests, not direct edits to dispatch/WMS/Finance" literally, mirroring the source prompt's own explicit `reschedule_requested` mapping.
6. **`cancelled_reason` is reused for both `cancel_requested` and the final `cancelled` outcome** — the given column list carries exactly one cancellation-reason column. "Mandatory new requested date" is interpreted as "at least one of pickup or delivery must be supplied."
7. **The staff conversion RPC structurally verifies account ownership**, unlike CPL-302's own disclosed inability to do so for `app.quotations`. `app.job_orders.account_id` and `app.shipment_orders.shipper_account_id` are both live FKs (confirmed by direct migration inspection) — `app.link_customer_booking_request_to_operational_records` verifies both equal the booking's own `account_id`, and that the supplied shipment order's own `job_order_id` equals the supplied job order id, before linking.
8. **Both `p_job_order_id` and `p_shipment_order_id` are mandatory, set together in exactly one atomic call** — mirrors "both set only by staff conversion, mirroring CPL-302's own `linked_quotation_id` pattern" literally. **Disclosed boundary**: a Job Order later split into several Shipment Orders is not modeled — this table links to at most one representative Shipment Order per booking.
9. **Credit gate deliberately NOT surfaced from any customer RPC** — `app.check_customer_credit` (COM-157) is FIN/COM-gated internally and never called here, per the orchestrating task's own explicit instruction. Staff linking a booking to real operational records implicitly asserts credit was already checked through the normal internal flow; a customer-visible "credit hold" display belongs with Prompt 311/312's own Finance-visibility work.
10. **Reschedule/cancel-request are terminal within this checkpoint (disclosed boundary)** — no RPC in this migration transitions `reschedule_requested`/`cancel_requested` onward. Real, persisted, staff-actionable-in-principle states, not a dead end — a future Operations-facing booking-management checkpoint's natural job, mirroring CPL-302's own "no staff UI to accept/link yet" precedent.
11. **A dedicated append-only history table** (`app.customer_portal_booking_request_history`), mirroring `app.customer_portal_account_membership_history` (CPL-300) exactly — not literally given by the task's own column list, but every sibling status-machine table in this Phase 8 slice keeps one, and this table's own 6-status machine (including two "stuck" states) benefits from a real transition timeline more than CPL-302's 4-status one did.
12. **RLS: `authenticated` holds ZERO direct grant**, mirroring CPL-300/CPL-302 exactly.
13. **REST/GraphQL transport (ADR-0024 Part C)**: service layer + Server Actions + UI only, no `app/api/` HTTP route — identical in kind to CPL-300/301/302's own disclosed residual gap.

## 3. A real defect this checkpoint's own migration authoring found and fixed before shipping

The first draft of `cpbr_converted_requires_links` was a **biconditional** CHECK (`status = 'converted' ⟺ both linked ids set`), mirroring CPL-302's own `cpqr_converted_requires_link` literally. CPL-302's `converted` is terminal, so its own biconditional is safe. This table's `converted` is **not** terminal — `converted → reschedule_requested | cancel_requested` (design decision 5) — so a converted booking that later moves to `cancel_requested` correctly *keeps* its `linked_job_order_id`/`linked_shipment_order_id` as real historical evidence while `status` is no longer literally `converted`. The biconditional would have rejected that legitimate transition (`(status='converted') = false` vs `(both ids set) = true` → constraint violated). **Fixed** before shipping by changing the constraint to a one-directional implication (`status <> 'converted' OR (both ids set)`) — live-verified in the db-test (§11 below, the `cancel_requested` assertion inside the staff-link test block).

## 6. Schema

`app.customer_portal_booking_requests` (id, tenant_id, account_id, requested_by_auth_user_id, status `check in ('draft','submitted','reschedule_requested','cancel_requested','cancelled','converted')`, linked_quote_request_id → app.customer_portal_quote_requests, cargo_description, pickup jsonb, delivery jsonb, requested_pickup_at/requested_delivery_at timestamptz, special_instructions, idempotency_key, linked_job_order_id → app.job_orders, linked_shipment_order_id → app.shipment_orders, record_version, created_by, created_at, updated_at, submitted_at, cancelled_at, cancelled_reason, reschedule_requested_pickup_at/reschedule_requested_delivery_at/reschedule_reason/reschedule_requested_at). Constraints: status check; pickup/delivery must be JSON objects; delivery ≥ pickup when both set; cancelled_reason mandatory iff status in (cancel_requested, cancelled); reschedule fields mandatory iff status=reschedule_requested; `cpbr_converted_requires_links` — a **one-directional implication** (`status <> 'converted' OR both linked ids set`), not a biconditional (§3 above). Unique `(tenant_id, idempotency_key)`, partial (not-null). Status-transition trigger mirrors CPL-302's own exactly, extended for the 6-value machine. Combined touch-row trigger (updated_at + record_version). Covering index `(tenant_id, updated_at desc, id desc)`.

`app.customer_portal_booking_request_history` — append-only, mirroring `app.customer_portal_account_membership_history` (CPL-300) exactly (design decision 11).

## 11. Adversarial testing — live, against a real disposable Postgres 16 database (not reasoned about)

All of the following used `postgresql://127.0.0.1:5432`, a freshly created disposable database, the full migration set (through `20260801040000`) applied, using the standard `set_config('request.jwt.claims', ...)` + `set role authenticated` forged-session technique where a real session was needed.

1. **Create is scope-checked, idempotent, and validates a linked quote request's own account/status** — alpha-admin creates a draft on Account Alpha linked to a genuinely converted quote request; beta-admin is rejected with `account_not_available` on Account Alpha; a repeated call with the same idempotency key returns the identical row; invalid pickup shape/date order are rejected; a dual-scoped actor (alpha-admin, also a member on Account Beta) citing an Alpha-owned quote request while booking against Account Beta is rejected with `quote_request_account_mismatch`; citing a still-draft quote request is rejected with `quote_request_not_accepted`; citing a nonexistent/out-of-scope quote request id is rejected with the anti-enumerating `quote_request_not_found`.
2. **Update is draft-only, account-grain, not requester-grain** — alpha-**member** (a different identity than the original requester alpha-admin) successfully edits the draft; a stale `expected_version` is rejected; beta-admin editing an Alpha booking gets `record_not_found`.
3. **Submit is idempotent with no separate key** — a genuine retry (same version) on a now-submitted row is a true no-op; a THIRD call with a doubly-stale version is likewise a no-op (status-checked before any version comparison, never a spurious `stale_version`).
4. **Reschedule requires submitted/converted, mandatory reason + at least one new date** — a still-draft booking is rejected with `invalid_transition`; a submitted booking with neither new date is rejected with `reschedule_date_required`; an empty reason is rejected; a real reschedule request records the new date/reason and is terminal (a second reschedule attempt on an already-`reschedule_requested` row is rejected).
5. **Cancellation branches by status** — draft/submitted cancel directly to `cancelled` (mandatory reason enforced, terminal-state refusal proven); a **converted** booking's cancellation becomes `cancel_requested`, not `cancelled` directly — live-asserted as part of the staff-link test block.
6. **Staff conversion RPC (OPS:Edit) with real structural verification** — a still-draft/still-submitted-without-prior-submit booking cannot be converted; a staff actor without OPS:Edit is rejected; both job/shipment order ids are mandatory (`job_order_id_required`/`shipment_order_id_required`); a job order belonging to a **different account** (a completely independent Commercial→Operations pipeline built for Account Beta) is rejected with `job_order_account_mismatch`; a shipment order not belonging to the given job order is rejected with `shipment_order_job_order_mismatch`; a real conversion succeeds and sets both linked ids; re-linking the SAME pair is a no-op; re-linking to a **different** pair on an already-converted request is rejected (`already_converted`); unknown booking/job-order/shipment-order ids each raise their own distinct not-found error.
7. **Anti-enumeration on get** — the SAME `record_not_found` message prefix/errcode for a genuinely nonexistent id and an out-of-scope (Beta reading Alpha's) id.
8. **List keyset pagination, deny-by-default, cross-tenant isolation** — pagination at `limit=1` visits every fixture row exactly once, no duplicate/skip; a cbr2 identity sees zero cbr1 rows; an identity with zero customer-portal scope sees zero rows (never an error); a half-supplied cursor raises `invalid_cursor`.
