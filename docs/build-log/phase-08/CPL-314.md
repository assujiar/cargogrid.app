## 1. What this checkpoint builds

CPL-314 is the first Phase 8 capability to let a customer propose a change to `app.accounts` (COM-155, ADR-0018) — the canonical customer/account/site master. Mirroring CPL-302's own established shape (ADR-0024 Part B), it is a new, additive, portal-owned request/intent table (`app.customer_portal_profile_change_requests`), never a direct customer write into `app.accounts` itself:

- A customer admin/member can propose a change to their own account's `trade_name` or `billing_address` — the two fields genuinely safe to self-serve. `legal_name`/`tax_id` (legal identity/KYC) and every structural field (`parent_account_id`/`merged_into_id`/`org_unit_id`/`owner_user_id`) are deliberately excluded from the writable set, enforced by a real table `CHECK` constraint, not merely UI/RPC-layer validation.
- A staff actor holding `COM:Approve` reviews each pending request and approves or rejects it. Approval applies the change to the real `app.accounts` row in the SAME transaction as the decision; rejection leaves `app.accounts` completely untouched. Self-approval is structurally blocked as defense-in-depth (not currently reachable by any real caller, mirroring HRT-282's own C-18 guard).
- A read-only current-state profile projection (`legal_name`/`trade_name`/`tax_id`/`billing_address`/`customer_status`) plus a summary of the account's own open change requests.
- A read-only projection of the account's own linked contacts (`app.contact_links`, `related_type='account'`) — satisfying the source prompt's own "contact... profile screen" requirement without inventing a second, portal-owned contact-change-request table this checkpoint's own bounded scope does not cover.
- A new customer-facing route, `app/(tenant)/[tenantSlug]/customer-profile/`, with editable-field forms for trade name/billing address, a pending-request banner + withdraw action, change-request history, locked/read-only display for legal name/tax ID, and a contacts list.

## 2. Design decisions (full rationale in the migration's own 18-point header comment; summarized here)

1. **A new portal-owned change-REQUEST table, never a direct write into `app.accounts` from a customer-initiated RPC** — ADR-0024 Part B, mirrors CPL-302's `app.customer_portal_quote_requests` exactly. The ONLY function in this migration that ever writes to `app.accounts` is `app.decide_customer_profile_change_request`, staff-gated (`COM:Approve`).
2. **Writable field set is deliberately narrow: `trade_name` and `billing_address` only.** `legal_name`/`tax_id` are excluded — a deliberate compliance/KYC-boundary decision, disclosed as `ISS-2026-123`, not an oversight. `parent_account_id`/`merged_into_id`/`org_unit_id`/`owner_user_id` are excluded because they carry zero customer-facing meaning. There is no credit field anywhere on `app.accounts` — credit lives on the separate, staff-only `app.credit_profiles` table (COM-157), confirmed by direct read of `app.accounts`' full column list before writing this table, not assumed.
3. **`legal_name`/`tax_id` ARE included in the READ projection, deliberately, disclosed.** A customer's own registered legal identity is not proprietary CargoGrid data — hiding it from a "profile" screen the customer already partially controls would be a confusing, broken UX. The source prompt's own §15 UI/UX impact explicitly asks for "denied/locked states for the non-editable fields," which presupposes those fields are still shown, just non-editable.
4. **Contacts: a read-only projection, no change-request path — a deliberate, disclosed scope decision (`ISS-2026-123`), not a silent skip.** `app.accounts` has no inline contact columns; contacts are the separate, already-polymorphic `app.contact_links` table (`related_type` now includes `'account'`, added by COM-155 itself). One new read-only RPC, `app.list_customer_portal_account_contacts`, satisfies the source prompt's own "contact... profile screen" requirement per ADR-0024 Part A's read/write split. A customer-initiated contact change-request path (mirroring this same checkpoint's own account-profile shape) was considered and rejected as a genuinely new, capability-sized addition beyond this prompt's own bounded scope.
5. **Confirmed, not assumed: no Commercial/Operations/Finance table denormalizes account name/address instead of referencing `account_id`** (source prompt §24: "do not rewrite historical shipment/invoice records"). Direct read before writing this migration: `app.quotations.customer_snapshot` (COM-151) is copied from `app.prospects` at DRAFT time and never re-derived from `app.accounts` afterward; `app.job_orders`/`app.shipment_orders` inherit that SAME frozen snapshot or reference `shipper_account_id` by id; `app.finance_invoices.customer_account_id` (`20260729110000_create_finance_invoice.sql:84`) references by id only, carries no denormalized name/address column. This migration's own `UPDATE` to `app.accounts` (approve path only) therefore cannot and does not rewrite any historical record anywhere in this repository — the business rule holds structurally.
6. **This migration is the FIRST mutator of `app.accounts.trade_name`/`billing_address` anywhere in this repository, post row-creation** — confirmed by grep (zero `set trade_name`/`set billing_address` against `app.accounts` anywhere in `supabase/migrations/` before this file). `app.accounts`' own pre-existing `accounts_touch_row` trigger already provides the "effective version" the source prompt's own business rule requires ("Changes carry effective version") — no new versioning column is invented.
7. **Every actor-taking function calls `app.assert_actor_is_session_identity` as its own literal first statement** — the batch's own single most common Critical defect class, applied from the first draft.
8. **Idempotency**: `app.submit_customer_profile_change_request`'s scope/authority check runs BEFORE the idempotent short-circuit `SELECT`; the `INSERT` itself carries a real `exception when unique_violation` handler, not merely a pre-check.
9. **Anti-enumeration (C-05)**: `app.get_customer_portal_account_profile`/`app.withdraw_customer_profile_change_request` raise the IDENTICAL `record_not_found` whether the target genuinely does not exist, belongs to a different tenant, or is out of scope. `app.decide_customer_profile_change_request` folds a standing check (staff tenant membership OR the row's own account being in the caller's own resolved customer scope) into its own not-found branch, BEFORE the `COM:Approve` check, mirroring `app.link_customer_quote_request_to_quotation`'s (CPL-302) identical dual-reachability fold.
10. **Self-approval is blocked structurally as defense-in-depth, even though not currently reachable** — mirrors `app.decide_payroll_reimbursement_request`'s own C-18 guard (HRT-282). `requested_by_actor_auth_user_id` is set only by the customer-facing submit RPC, which has no staff caller (a `customer_user` identity's own `app.tenant_user_identities` row is never `'active'`, consistent with `ISS-2026-040`'s own "not currently exploitable" standing status).
11. **Status machine**: `pending -> approved | rejected | withdrawn`, all terminal, enforced by a `before update of status` trigger mirroring CPL-302 exactly.
12. **Scope grain is the account, not the original requester** — any active member of the account may submit/withdraw a profile change request, mirroring CPL-302's own "any account member" precedent.
13. **`review_reason` is mandatory for BOTH approve and reject** (mirrors `app.decide_payroll_reimbursement_request`'s own unconditional reason requirement), and is never routed into `app.capture_audit_event`'s own before/after jsonb unredacted — applied from the first draft, not retrofitted.
14. **`withdraw` carries no separate reason column** — the table's own given column list has no `withdrawn_reason` field; a deliberate, bounded simplification matching the literal given schema.
15. **RLS: `authenticated` holds ZERO direct grant** on the new table, mirroring CPL-300/CPL-302 exactly. `app.accounts`' own RLS is untouched by this migration.
16. **REST/GraphQL transport (ADR-0024 Part C)**: service layer + Server Actions + UI only, no new `app/api/` HTTP route — identical in kind to every prior Phase 8 capability's own disclosed residual gap.
17. **No edit to `scripts/db-tests/rbac-enforcement.sql` required** — every authority primitive composed (`app.assert_actor_is_session_identity`, `app.resolve_customer_account_scope`, `app.has_active_tenant_membership`, `app.evaluate_permission`) is already a recognized keyword in that file's own closure sweep — confirmed live in this checkpoint's own scratch-database run (§9 below), not merely assumed.
18. Per `ERR-2026-004`: this migration carries its own explicit `revoke execute on all functions in schema app from public` statement before its final grants.

1. **Forbidden field_name rejected at BOTH layers** — `app.submit_customer_profile_change_request` rejects `legal_name`/`tax_id`/`org_unit_id` with `invalid_field_name`; a raw superuser `INSERT` bypassing the RPC entirely (naming `field_name='legal_name'` or `field_name='owner_user_id'`) still fails the table's own `cppcr_field_name_check` CHECK constraint — the required "rejected at the database level, not just the UI" proof.
