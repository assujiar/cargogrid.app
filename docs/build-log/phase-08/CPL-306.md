# CPL-306 — Shipment Monitoring

**Prompt ID:** `CG-S13-CPL-008` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/306_SHIPMENT_MONITORING_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (2026-08-17 — batch Tier C review across `CPL-305..309` complete; see §14)

## 1. What this checkpoint builds

CPL-306 gives a scoped customer-portal user control over which shipment alerts they receive (6 alert types: milestone delay, exception, no-fresh-position, tracking restored, delivery, document available) and a read history of alerts they have actually been sent. This is deliberately **a subscription/preference + alert-history capability, never a telemetry capability** (source prompt §13, absolute: "Do not store raw GPS events") — it creates exactly one new table (`app.customer_shipment_alert_subscriptions`), registers 6 notification types as data, and composes the already-VERIFIED, layer-agnostic PLT-127 notification engine (`app.notification_types`/`app.notifications`/`app.queue_notification`/`app.list_notifications_for_recipient`) for history rather than reinventing delivery, rendering, dedupe, or preference storage. **Emission — the actual triggering of an alert from a real milestone/exception/tracking-health event — is explicitly out of scope this checkpoint**, disclosed with the same clarity CPL-300's own MFA gap used (§9 below), including a second, deeper, live-verified finding beyond "no scheduler exists."

## 2. Design decisions (cited where given by the orchestrating task; disclosed where this checkpoint had to resolve something itself)

1. **`app.customer_shipment_alert_subscriptions` is a new, portal-owned preference table**, per the orchestrating task's own literal column list (id, tenant_id, account_id, shipment_order_id → `app.shipment_orders`, auth_user_id, alert_type, status, created_at, updated_at, record_version). `account_id` is derived from the target shipment order's own `shipper_account_id` at subscribe/unsubscribe time, never customer-supplied — the identical technique CPL-304's own `request_customer_shipment_order_change` already established for a portal-owned record referencing a canonical shipment order.
2. **No status-transition-enforcement trigger.** Unlike CPL-300's membership table (a real terminal-on-revoke state machine) or CPL-304's change-request table (a one-directional workflow), `status` here is a genuine, reversible two-value preference toggle (`active` ↔ `unsubscribed`, every transition valid both ways) — there is nothing for a transition matrix to reject. A combined touch trigger (`updated_at` + `record_version`) is still applied on every UPDATE, matching the general house style.
3. **Subscribe/unsubscribe are `INSERT ... ON CONFLICT (natural key) DO UPDATE`, never a client-supplied-idempotency-key short-circuit — structurally immune to Batch 1's own Tier C lessons (a)/(b), not merely re-checked against them.** The natural uniqueness key — `(tenant_id, shipment_order_id, auth_user_id, alert_type)` — is not an opaque, caller-chosen string decoupled from the operation's real target the way `p_idempotency_key` was in the Batch 1 defects: `auth_user_id` is `p_actor_auth_user_id`, already verified by `app.assert_actor_is_session_identity` to be the caller's own real session identity, and `shipment_order_id`/`alert_type` are the explicit target of this exact call, scope-checked before the upsert runs. `INSERT ... ON CONFLICT ... DO UPDATE` is also a single atomic statement — live-verified race-safe in this checkpoint's own ad hoc concurrency reproduction (§11 below), not merely reasoned about.
4. **Every one of the 4 RPCs is scope-checked against the shipment order's own `shipper_account_id` via `app.resolve_customer_account_scope`, LIVE on every call** (orchestrating task's own instruction; source prompt §24, "Each emission revalidates scope"). Subscribe/unsubscribe combine "shipment order genuinely nonexistent" and "exists but out of scope" into one `shipment_order_not_found` anti-enumerating error. The two list RPCs live-rescope every returned row against the caller's current `resolve_customer_account_scope` result on every call — live-verified: suspending alpha-admin's own account membership immediately hides an otherwise-completely-untouched subscription row (§11 below).
5. **`app.list_customer_shipment_alerts` is a thin, honestly-bounded wrapper composing `app.list_notifications_for_recipient` (PLT-127) — never a second notification store.** Self-only by construction, filtered to this capability's own 6 `notification_type_code` values, with this wrapper's own keyset pagination layered on top since the composed engine RPC has neither a type filter nor a cursor/limit of its own. **Disclosed, not fixed**: this wrapper necessarily fetches the recipient's entire in-app notification history on every call and filters/paginates the result set in-query — widening the shared, already-VERIFIED PLT-127 RPC is beyond this bounded task's own migration budget.
6. **The optional `p_shipment_order_id` filter matches `context->>'shipmentOrderId'`, a disclosed convention this migration defines but does not itself ever populate** — `app.notifications.context` is explicitly informational only, never a structural FK (PLT-127's own header), so this migration cannot and does not add a real FK column to that shared table.
7. **6 new `app.notification_types` rows, registered by direct `INSERT`, mirroring that table's own already-established direct-INSERT bootstrap precedent** (`20260731160000_create_ticket_escalation.sql`, HRT-291 decision 9, itself mirroring HRT-286's `'ticket_attachment'` bootstrap) — `app.register_notification_type()` is Supreme-Admin-gated and migration-apply context has no live actor session. Also mints the paired `'notification:<code>'` `app.config_types` row for each. **Deliberately stops there** — no `config_objects`/`config_versions`/`config_items` (no published template), since this checkpoint builds no emission caller at all.
8. **EMISSION IS EXPLICITLY, ABSOLUTELY OUT OF SCOPE — stated with the same clarity CPL-300's own disclosed MFA gap used.** Nothing in this migration ever calls `app.queue_notification`. A real trigger linking `app.milestone_events`/`app.operational_exceptions` to `app.queue_notification` requires either a new database trigger or a new scheduled job — no live scheduler exists anywhere in this repository (`ISS-2026-015`, standing, not new here). **A second, deeper, live-verified finding this checkpoint's own investigation surfaced**: `app.queue_notification`'s own recipient-authorization check (`app.has_active_tenant_membership`) tests a STAFF membership concept (`app.tenant_user_identities.status = 'active'`); every customer_user identity's own row is created only via `app.link_auth_identity(..., 'invited')` and no Phase 8 RPC anywhere transitions it further — live-reproduced (§11 below): `app.queue_notification` unconditionally rejects a customer_user recipient with `notification_recipient_unauthorized`, for any notification type, not only this capability's own 6. Grep-confirmed no existing capability (procurement sourcing, HRIS onboarding/training, ticket escalation — the only other 4 `app.queue_notification` callers) has ever attempted a customer_user recipient either. Neither `app.queue_notification` nor `app.has_active_tenant_membership` is touched by this migration — both are untouched, already-VERIFIED shared primitives this task has no mandate to widen. What is built and real end to end: the subscription CRUD (independent of emission entirely) and the alert-history read path (correct against any row that exists for this capability's own 6 type codes, regardless of how it was written) — proven in this migration's own db-test against a row placed directly, the only viable path today.
9. **No table this migration touches beyond its own new one gains a new RLS policy or a new column.**
10. **RLS: `authenticated` holds ZERO direct grant** on the new subscription table, mirroring CPL-300/302/303/304's own convention.
11. **REST/GraphQL transport (ADR-0024 Part C)**: service layer + Server Actions + UI only, no `app/api/` HTTP route — identical in kind to CPL-300..305's own disclosed residual gap.
12. **Every RPC calls `app.assert_actor_is_session_identity` as its own first statement — read RPCs included** (CPL-300's own Tier C lesson, applied from the first draft).
13. **No edit to `scripts/db-tests/rbac-enforcement.sql`** — every new function calls `app.assert_actor_is_session_identity` directly and/or `app.resolve_customer_account_scope`, both already-recognized base-regex authority primitives since CPL-300 — confirmed live in this checkpoint's own db-test, no edit required.

## 11. Adversarial testing — live, against a real disposable Postgres 16 database (not reasoned about)

All of the following used a freshly created disposable database, the full migration set (through `20260801070000`) applied, using the standard `set_config('request.jwt.claims', ...)` + `set role authenticated` forged-session technique where a real session was needed.

1. **Subscribe/unsubscribe validation and anti-enumeration** — an unrecognized `alert_type` is rejected (`invalid_alert_type`) before any row is touched; beta-admin subscribing to Alpha's own shipment and a genuinely nonexistent shipment order id both raise the IDENTICAL `shipment_order_not_found`.
