## 1. What this checkpoint builds

CPL-313 is overwhelmingly additive wiring over Phase 7's already-`VERIFIED` customer-ticket capability (HRT-287, HRT-289 SLA, HRT-292 Typed Ticket-Linked Records), exactly as the orchestrating task's own kickoff research predicted:

- A **generic linked-record picker on the ticket CREATE form** — a customer can search and pre-select their own shipment, warehouse order, invoice, or document *before* the ticket exists, independent of (and in addition to) CPL-311's own existing "dispute this invoice" deep-link mechanism.
- **SLA/status display wired into the customer ticket detail page** — `app.get_ticket_sla_status_for_requester` (HRT-289, already `VERIFIED`, already had a customer-safe projection RPC) is now actually called and rendered there; it was not called from any customer-facing page before this checkpoint.
- **The customer portal nav wired onto the ticket center** — `CustomerPortalNav` is now rendered on both `customer-tickets` routes, the first checkpoint to do so (HRT-287's own route family predates the shared nav component).
- **Closure confirmation UX** — an explicit banner explaining the resolved/closed state and the real, already-existing reopen action, since the canonical Ticketing lifecycle (HRT-286) never lets a customer close their own ticket (staff-only, by design).
- **A new, genuinely additive `app.ticket_portal_links` table + 5 functions**, extending typed ticket-linked records to two entity types the existing HRT-292 registry cannot reach at the right granularity: `warehouse_order` (CPL-310's own `app.wms_outbound_orders`, distinct from the existing `warehouse` type, which resolves to the facility master record) and `document` (CPL-308's own two real document sources, not previously reachable from `app.ticket_links` at all).

## 2. Design decisions (cited to the orchestrating task's own explicit design section where given; disclosed where this checkpoint had to resolve something itself)

1. **ADR-0024 Part A governs the shape** — every new read is a `SECURITY DEFINER` RPC composing a scope resolver and a domain-specific eligibility predicate, deny-by-default, anti-enumerating, keyset-paginated where applicable.
2. **A parallel table, not a widened `app.ticket_links` registry — discovered necessary, not chosen.** The orchestrating task's own research suggested widening `app.ticket_links.entity_type`'s CHECK constraint (the sanctioned HRT-275-style additive widening) to add `warehouse_order`/`document`. Direct inspection *before writing any code*, per the task's own explicit instruction to check `app._ticket_link_resolve_candidate`'s actual body first, found this path foreclosed by two real, already-passing, protected tests: `scripts/db-tests/ticketing-linked-records.sql:254` and `server/contracts/ticketing/ticketing.test.ts:630`, both hard-asserting the six-value registry verbatim. Both are existing test files this task's own instructions forbid deleting or modifying, and widening the shared registry would break both — a real regression. This checkpoint's own migration (`supabase/migrations/20260801140000_create_customer_portal_ticket_linked_records.sql`) therefore leaves every pre-existing HRT-292 object completely untouched (grep-confirmed: zero `alter table`/`create or replace function` against any of them) and adds a small, parallel `app.ticket_portal_links` table + `app.ticket_portal_link_entity_types()`/`app._ticket_portal_link_resolve_candidate`/`app.search_ticket_portal_link_candidates`/`app.link_ticket_portal_record`/`app.unlink_ticket_portal_record`/`app.list_ticket_portal_links` instead — mirroring the ORIGINAL HRT-292 shape structurally (natural-key uniqueness, anti-enumeration ordering, idempotent link, ticket-first lock order on unlink), never its values. Live-reproduced and re-confirmed correct in this checkpoint's own db-test (§11 item 1) — the migration was authored, then this exact conflict was discovered mid-authoring when the pre-existing db-test's own hardcoded assertion failed against a first draft that DID widen the registry; the draft was reverted to the parallel-table shape before this checkpoint's own db-test was even written, so the final shipped migration never widened `app.ticket_links` at all.
3. **`warehouse_order` composes real, existing predicates for BOTH a staff and a customer branch** — the staff branch mirrors `app.wms_outbound_orders`' own real RLS `SELECT` policy verbatim (`not app.actor_holds_customer_user_layer(...) and app.wms_pick_record_scope_ok(...) and app.actor_can_view_owner_scoped_row(...)`, read directly from `20260730311000_harden_customer_inventory_access_rls_isolation.sql` before writing this branch); the customer branch reuses `app.evaluate_customer_portal_inventory_access` (CPL-309) verbatim — the SAME gate `app.get_customer_portal_outbound_order` (CPL-310) already uses for the identical table, so a candidate this checkpoint's own search surfaces to a customer is always the same candidate CPL-310's own detail page would also show them.
4. **`document` composes `app.customer_portal_quote_requests`/`app.epod_captures`/`app.shipment_orders` directly, mirroring CPL-308's own two real union-arm predicates inline — never calling `app.list_customer_documents`/`app.get_customer_document` themselves.** Calling `app.get_customer_document` as a reauthorization primitive was considered and rejected: that function's own design always writes a durable `app.file_access_logs` GRANTED/DENIED row on every call (CPL-308 design decision 5) — calling it merely to validate a link candidate (search, or a link-time re-check) would fabricate false "access" audit rows for documents nobody actually opened. Calling `app.list_customer_documents` was also rejected: it has no `p_document_id` single-row lookup or `p_search_text` filename filter, and widening it (DROP+CREATE, this repository's own established convention for adding a parameter to an existing signature) purely to serve this checkpoint would touch an already-`VERIFIED` capability's own function outside this task's bounded scope. Inlining the SAME two real predicates mirrors exactly how `app._ticket_link_resolve_candidate`/`app.search_ticket_link_candidates` already duplicate each of their own six domain predicates independently between "get one" and "search many" — the established convention in this exact file family, not a new pattern.
5. **`document` is customer-portal-only by design, disclosed, not silent.** `app._ticket_portal_link_resolve_candidate`'s `document` branch has no staff `OR`-branch, because no staff-facing document-browse/access predicate exists anywhere in this repository (CPL-308's own already-disclosed boundary). A staff caller would see zero candidates, always — safe deny-by-default, not a leak. Recorded as part of `ISS-2026-122`.
6. **Both new entity types use the CPL-300 widened resolver (`app.resolve_customer_account_scope`) in every new function this checkpoint adds — never the legacy `app.resolve_customer_owner_account_scope` the pre-existing `shipment`/`invoice`/`warehouse` branches in `app.ticket_links` still use.** Disclosed explicitly (`ISS-2026-122`): this makes the two NEW entity types `ISS-2026-117`-clean from their first line, while the three PRE-EXISTING `app.ticket_links` branches remain on the old resolver — a real, pre-existing gap in a file this task does not own and may not edit (HRT-292, Phase 7, already `VERIFIED`).
7. **The ticket CREATE form's own precreate search (`app.search_customer_ticket_link_candidates_precreate`) spans BOTH registries in one call** — `shipment`/`invoice` (reusing the SAME `app.resolve_customer_owner_account_scope` predicate `app.link_ticket_record` will actually re-check once the ticket exists, for consistency) and `warehouse_order`/`document` (the new registry). A customer creating a ticket has no reason to see two different search surfaces merely because the eventual link call routes to two structurally different tables underneath.
8. **Every actor-taking function calls `app.assert_actor_is_session_identity` as its own literal first statement** — the batch's own single most common Critical defect class, applied from the first draft.
9. **Idempotency (C-01/C-02)**: a real partial unique index on `(ticket_id, entity_type, entity_id) where status='active'`, backed by a real `exception when unique_violation` handler in `app.link_ticket_portal_record` — mirrors `app.link_ticket_record`'s own established shape verbatim.
10. **Anti-enumeration (C-05) mirrors `app.link_ticket_record` exactly** — `app._ticket_portal_link_resolve_candidate` collapses "nonexistent," "cross-tenant," "deleted," and "exists but unauthorized for THIS caller" into ONE outward `record_not_eligible`, checked before the duplicate-link short-circuit.
11. **RLS is staff-only (customer_user excluded) on the new raw table** — mirrors `app.ticket_links`' own established policy shape verbatim; every genuine customer read goes through the `SECURITY DEFINER` RPCs.
12. **No dedicated append-only event ledger for `app.ticket_portal_links`** (a deliberate, bounded simplification, disclosed as part of `ISS-2026-122`) — the row's own `created_by`/`removed_by`/`removed_reason`/timestamps/`record_version` already carry real, queryable history for every actual link/unlink; a pre-creation SEARCH has nowhere to durably log a denial anyway, since `app.ticket_link_events.ticket_id` is `NOT NULL` and no ticket exists yet at search time, and inventing a second ledger table purely to log that one moment was judged out of this checkpoint's own bounded scope.
13. **"Bind portal categories to canonical Ticketing types and SLA policies" — confirmed structurally, not newly built.** Every category a customer sees in the ticket-creation dropdown IS a real, canonical `app.ticket_categories` row (`customer_visible=true`, HRT-287) — there is no parallel portal-only taxonomy for "complaint/claim/service request/feedback" anywhere in this repository, and none was invented here; a tenant names its own categories however its business requires. Once a ticket's SLA clock starts (a staff/system action, unchanged, outside this checkpoint's own scope), its target/status is deterministically resolved by channel/category/priority via the existing, unmodified HRT-289 policy-matching machinery. This checkpoint's own job — and the only piece that was NOT already wired — is surfacing that already-computed status on the customer-facing detail page (design decision 14 below).
14. **SLA display sourced ONLY from `app.get_ticket_sla_status_for_requester` (HRT-289, already `VERIFIED`)** — never a new SLA source or a second computation. Grep-confirmed before this checkpoint: that function had a real TS query wrapper (`getTicketSlaStatusForRequester`, `server/queries/ticketing.ts`) but zero caller anywhere under `app/(tenant)/[tenantSlug]/customer-tickets/`. This checkpoint's own change is a pure composition — one new `Promise.all` fetch in `[ticketId]/page.tsx`, one new presentational component in the detail panel. `slaStatus === null` (no clock started yet, the common case immediately after filing) renders an honest "not yet tracked" state, never a fabricated target.
15. **Closure confirmation UX — a real, disclosed design boundary, not a workaround.** `app.ticket_status_transitions` (HRT-286, `supabase/migrations/20260731060000_create_ticketing_internal.sql:366-381`) does NOT mark `resolved -> closed` `requester_allowed` — only staff may actually close a ticket, a canonical Ticketing lifecycle decision this checkpoint's own bounded scope does not reopen or widen (doing so would require either an `UPDATE` to an already-applied migration's seed data, forbidden, or a new migration widening a canonical Ticketing authority rule, out of this portal-wiring task's own chartered scope). "Closure confirmation" from the portal side is therefore an explicit banner (`ClosureConfirmationBanner`) plus the ALREADY-existing reopen action (`resolved`/`closed -> open`, `requester_allowed=true`) — a customer who does not reopen is treated as having implicitly confirmed the resolution; a customer who disagrees has a real, working, already-tested action.
16. **No new notification channel (email/push) exists anywhere in this repository for tickets, confirmed by grep before writing this checkpoint** — "SLA/status notifications" is satisfied by the in-portal status DISPLAY built here (design decision 14), consistent with how every other Phase 7/8 capability's own dashboard/status surfaces have already substituted a live display for a live push/email channel neither Phase 7 nor Phase 8 has built.
17. **REST/GraphQL transport (ADR-0024 Part C):** service layer + Server Actions + UI only, no new `app/api/` route — identical in kind to every other Phase 8 capability's own disclosed residual gap.
18. **No edit to `scripts/db-tests/rbac-enforcement.sql`** — every new function calls `app.assert_actor_is_session_identity` directly as its own first statement; confirmed live in this checkpoint's own scratch-database run, no edit required.
19. Per `ERR-2026-004`: this migration carries its own explicit `revoke execute on all functions in schema app from public` statement before its final grants.

### Finding 1 — CRITICAL (security/RLS lens): a customer_user could discover and durably link a draft/submitted/approved invoice through this checkpoint's own new precreate search, defeating CPL-311's core Finance-visibility gate

**Root cause.** `app.search_customer_ticket_link_candidates_precreate`'s own `'invoice'` branch (function 5 of this migration) was authored by mirroring `app.search_ticket_link_candidates`' own PRE-`CPL-311` `'invoice'` customer branch (HRT-292, Phase 7) verbatim — correct at HRT-292's own time, since Finance had zero customer-facing visibility rule of any kind then. `CPL-311` (earlier in this same batch) is what first establishes, as a hard security boundary, that `draft`/`submitted`/`approved` invoices "must never leak to a customer" (`20260801120000_create_customer_portal_invoice_billing_visibility.sql` design decision 4). This checkpoint's own new branch — new code, authored after that rule already existed — never applied it. The security lens live-reproduced the full exploit: a customer_user could search and see their own account's pre-issuance invoice through this RPC, then durably link it via the ALREADY-APPLIED, unmodified `app.link_ticket_record` (HRT-292) — which resolves the candidate through `app._ticket_link_resolve_candidate`, an HRT-292 function that has the IDENTICAL missing status filter, independent of anything this checkpoint built. The resulting `app.ticket_links` row permanently captures the pre-issuance invoice's number/currency/amount/status in its `safe_snapshot`, readable thereafter by both the customer and ticket staff.

**Fixed, at two sites, in the two files that actually needed it:**
1. **This checkpoint's own file** (`supabase/migrations/20260801140000_create_customer_portal_ticket_linked_records.sql`): `app.search_customer_ticket_link_candidates_precreate`'s `'invoice'` branch now adds `and fi.status in ('issued', 'void')`, matching `CPL-311`'s own rule exactly. See design decision 12 (newly added to this file's own header) and the function's own inline comment for the full citation.
2. **A new, separate, additive migration** (`20260801160000_harden_customer_portal_ticket_link_invoice_status_gate.sql`) — NOT a change to this checkpoint's own file, and NOT an edit to the already-applied `20260731170000_create_ticket_linked_records.sql` (forbidden) — `CREATE OR REPLACE`s the two pre-existing HRT-292 functions (`app._ticket_link_resolve_candidate`, `app.search_ticket_link_candidates`) to add the identical status filter to ONLY their `'invoice'` branch's customer-owner-scope arm (the staff arm, `app.check_finance_invoice_authority`, is deliberately left unfiltered — real FIN:View authority must still see every lifecycle state). This is the fix that actually closes the durable-write exploit path (`app.link_ticket_record`), since that RPC and its own candidate resolver are what this checkpoint deliberately never touches. This mirrors this repository's own already-established `harden_*_tierc.sql` pattern for exactly this situation (e.g. `20260731300000_harden_ticketing_customer_links_creator_role_hrt295_tierc.sql`, itself a `CREATE OR REPLACE` against two of this SAME HRT-292 migration's functions for an unrelated Tier C fix).

**Test coverage that did not catch this, and what was added.** `scripts/db-tests/customer-complaint-ticket-portal-wiring.sql`'s own precreate-search section (§2) never exercised `p_entity_type = 'invoice'` at all (zero `finance_invoice` reference in the file) — this is why the batch's own required db-test gate did not catch it.
