## 1. What this checkpoint builds

Cashback/discount/voucher benefit entitlements as auditable, mutable current-state records (never a duplicate financial truth) linked to eligible source transactions, with issuance, redemption (by id or by a hash-only-stored voucher code), reversal, tenant-wide expiry, and fraud hold/release — the FOURTH Loyalty-domain capability in this repository (ADR-0024 Part D). Two new tables (`app.loyalty_benefit_entitlements`, `app.loyalty_benefit_entitlement_events`) plus 10 new `SECURITY DEFINER` RPCs and one pure, non-actor-taking code-generation helper. Reads (never writes) CPL-316's own `app.loyalty_accounts`; does not read or write CPL-317's tier tables or CPL-318's points tables at all.

**Explicit scope boundary (orchestrator-directed, disclosed, not silently narrowed):** ADR-0024 Part D's own general shape for Loyalty-liability-to-Finance names a handoff-batch table, an idempotent generator, and a FIN-209-shaped reconciliation pair. None of that is built here — it is `CPL-323`'s own future scope ("Liability Reconciliation Analytics"), per this checkpoint's own orchestrating task instruction. This checkpoint's own job is narrower and complete on its own terms: record entitlement value/currency/status/issued_at/source cleanly and accurately (`app.loyalty_benefit_entitlements`/`app.loyalty_benefit_entitlement_events`) so a future `CPL-323` can reconcile against Finance later. Recorded as `ISS-2026-129` item 1.

## 2. Design decisions

Full rationale in the migration's own header comment (14 numbered points); summarized here.

1. **Two tables, but not the same append-only-ledger/derived-balance split CPL-316/317/318 each used.** `app.loyalty_benefit_entitlements` is the single, MUTABLE, authoritative current-state row per issued benefit — it already needs direct `UPDATE`s for its own status lifecycle (`issued → redeemed/reversed/expired/held → issued`), mirroring `app.loyalty_point_lots`/`app.inventory_balances`/`app.inventory_reservations`' own already-established "mutable current-state row" shape, not `app.loyalty_point_ledger_entries`' append-only shape. There is no separate aggregate "wallet balance" table — each entitlement is its own complete value/status unit (the source prompt's own schema never asks for a rolled-up per-account total). `app.loyalty_benefit_entitlement_events` is the genuinely append-only lifecycle log (no `UPDATE`/`DELETE` grant to any role anywhere in this migration, not even `service_role`, mirroring `app.loyalty_point_ledger_entries`' own identical choice).
2. **Voucher/coupon code generation is a NEW design decision, explicitly disclosed as such, not a claimed reuse of the repository's existing hashed-bearer-secret pattern.** `app.api_keys`/`app.quotation_acceptance_tokens`/`app.shipment_tracking_tokens` (grep-confirmed, all three) each mint a 48-64 character machine-oriented secret (`encode(gen_random_bytes(24 or 32), 'hex')`), never meant to be hand-typed. This checkpoint's own code is deliberately SHORTER and human-typeable: a real, from-scratch RFC4648 base32 encoder (`app.generate_random_base32_voucher_code`, computed via `get_byte`/bigint bitwise ops — PostgreSQL core's own `encode()` has no `base32` target, live-caught the first time this checkpoint ran its own db-test) over a 5-byte (40-bit) random draw, formatted `'CGV-' || 4 chars || '-' || 4 chars` (e.g. `CGV-K7M2-QX9B`, ~1.1×10¹² possible codes). The SAME hash-only-storage principle those three precedents established still governs: only `code_hash` (`sha256`) is ever stored, globally unique (never tenant-scoped, mirroring `key_hash`/`token_hash`), and the raw code is returned exactly once by `app.issue_loyalty_benefit_entitlement`'s own return row on a genuine first issuance only — never on an idempotent replay, never logged (grep-confirmed: touches no `capture_audit_event` call).
3. **Fraud hold mirrors CPL-317's own GOVERNING PRINCIPLES, adapted to a different append-only/mutable table boundary — not its literal separate-table mechanism copied unconditionally.** CPL-317 built a separate `app.loyalty_account_tier_holds` table specifically because its own core object (tier movements) is append-only; an inline hold column there would mutate a past, posted row. That constraint does not apply here — `app.loyalty_benefit_entitlements` is already mutable (design decision 1), exactly as mutable as CPL-317's OWN `loyalty_account_tier_holds` itself. This prompt's own literal schema also lists `'held'` as a real `status` value and `is_fraud_hold`/`hold_reason` as columns directly on the entitlement row — a third, independently-drifting hold table beside a status column that can ALSO say `'held'` would be exactly the double-bookkeeping CPL-317's own reasoning warns against. This checkpoint keeps CPL-317's real rules — mandatory non-empty reason, `held_by`/`held_at`/`released_by`/`released_at` provenance, redemption blocked while held, a customer-safe generic notice that never carries the real internal `hold_reason` — inline, with a real `CHECK` constraint (`lbe_status_hold_consistency_check`, `(status = 'held') = is_fraud_hold`) as the single source of truth.
4. **The CPL-318 ledger-insert-before-mutation ordering lesson has no directly analogous balance/cap mutation step here, disclosed explicitly.** CPL-318's own bug class was a separate aggregate-balance table mutated before the append-only ledger row's own idempotency-establishing insert. This checkpoint has no analogous separate balance table (design decision 1) — the entitlement row IS the balance. The same underlying discipline is applied defensively anyway: in every function, the entitlement row's own `INSERT`/`UPDATE` (which doubles as the idempotency claim on issuance and the atomic status-transition guard on every other mutation) always happens strictly before the corresponding `app.loyalty_benefit_entitlement_events` insert.
5. **Redemption is the FIRST genuinely customer-initiated write anywhere in the Loyalty domain** (CPL-316/317/318 each explicitly disclosed zero customer-initiated writes). This prompt's own explicit instruction ("customer-facing benefit wallet ... redeem action for vouchers") asks for exactly that. Reasoned as compatible with ADR-0024 Part B, which governs a customer directly calling a staff-RBAC-gated CANONICAL mutation of an ALREADY-EXISTING, DIFFERENT domain (Commercial/Finance/Ops) — redeeming one's own Loyalty-owned entitlement is this domain's own internal action, not a bypass of another domain's canonical record. `app.redeem_loyalty_benefit_entitlement` is ONE function (the source prompt's own literal signature, `p_entitlement_id_or_code`) with two lookup shapes: an **ID path** (staff `LYL:Edit` or the entitlement's own owning customer, ordinary distinguishable errors — the caller already legitimately knows this id) and a **CODE path** (voucher-only, `code_hash = digest(code, 'sha256')`, never plaintext, reachable by staff or ANY customer, FULLY anti-enumerating — every failure mode collapses into one identical `voucher_redemption_failed` error, proven live and adversarially across six distinct failure causes in this checkpoint's own db-test).
6. **`p_expected_version` is nullable on redemption specifically** — the one deliberate departure from every other real, non-null optimistic-concurrency check in this domain. A caller redeeming by a bare voucher code has no visibility into the target row's own current `record_version`; the underlying `update ... where id = ... and status = 'issued'` transition is already a complete, race-safe concurrency guard on its own (PostgreSQL's own row-level locking serializes concurrent updates against the identical row). When a caller DOES know the version (the wallet's own per-row "Redeem" button; staff admin by id), it is passed and genuinely checked.
7. **`value_cap` enforcement is BOTH a real procedural guard (authoritative) AND a real table `CHECK` constraint** (`lbe_value_cap_bound_check`) as a defense-in-depth backstop — the same dual shape CPL-318 established for negative-balance prevention. Proven live, adversarially (a rejected over-cap issuance and a genuine at-cap-boundary success).
8. `clock_timestamp()`, never `now()`, throughout (the CPL-315 self-found defect class, applied proactively).
9. Every actor-taking function calls `app.assert_actor_is_session_identity` first; C-05 authority-before-fetch throughout, including redemption's own dual authority resolution (both `v_is_staff` and `v_customer_scope`) before any entitlement row is touched.
10. **LYL permission mapping, reused unchanged.** Issuance/the tenant-wide expiry scan → `LYL:Edit`. Reversal and hold/release (governance-grade) → `LYL:Configure`. Staff reads → `LYL:View`. Redemption is the one dual-authority function. Customer-facing reads → `app.resolve_customer_account_scope` only.
11. Never mutates a derived/state field outside its own owning function; never deletes/rewrites an `app.loyalty_benefit_entitlement_events` row.
12. RLS: `authenticated` holds ZERO direct grant on either new table, mirroring CPL-316/317/318 exactly.
13. Zero reads or writes against CPL-317's/CPL-318's own tables — grep-confirmed.
14. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public` before final grants.
