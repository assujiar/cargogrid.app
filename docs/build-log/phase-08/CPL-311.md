# CPL-311 — Invoice and Billing Visibility

**Prompt ID:** `CG-S13-CPL-013` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/311_INVOICE_BILLING_VISIBILITY_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty), Batch 3 · **Status: `VERIFIED`** (Batch 3 Tier C review closed — see §14)

## 1. What this checkpoint builds

CPL-311 gives a scoped customer-portal user read-only visibility into Finance-owned invoice/billing data (issued invoices, charge/tax lines, payment/aging status) without allowing portal edits to posted/finalized Finance records, plus a real "download" (structured JSON export) and a real "dispute" action wired to the already-shipped customer-ticket flow. This is the **first Finance-facing customer-portal RPC layer in Phase 8** — no ATW-023-style precedent exists to extend; Finance built zero customer-facing read path before this migration (confirmed by direct read of `app.finance_invoices`/`app.finance_ar_open_items`'s own RLS: `has_active_tenant_membership(tenant_id) or is_supreme_admin()` only). Follows ADR-0024 Part A's shape exactly, mirroring CPL-309/310's own house style, built fresh for Finance.

## 2. Design decisions (cited where given by the orchestrating task; disclosed where this checkpoint had to resolve something itself)

1. **"Finance scope" is deliberately simpler than the warehouse gate — account scope alone, no second eligibility layer.** `app.evaluate_customer_portal_invoice_access` is `p_customer_account_id = any(app.resolve_customer_account_scope(...))` alone. Checked directly before writing this gate (per the task's own explicit instruction to confirm against CPL-300's own membership/role model): `app.customer_portal_account_memberships.role` is CHECK-constrained to exactly `account_admin`/`member`, no domain sub-scope column exists anywhere. Disclosed as `ISS-2026-121` (new `KNOWN_ISSUES.md` entry) — a `member`-role user granted access to an account for any purpose also sees that account's own invoices, matching every other Phase 8 domain's identical account-scope-alone granularity (not a new widening this checkpoint introduces).
2. **MANDATORY PATTERN, applied from the first draft**: every actor-taking function — including the gate primitive itself — calls `app.assert_actor_is_session_identity` as its own literal first statement. `app.evaluate_customer_portal_invoice_access` is `language plpgsql` (not `language sql`, a disclosed deviation from the source prompt's own illustrative signature text) specifically to carry this check, mirroring CPL-300's own `resolve_customer_account_scope` `language sql -> language plpgsql` conversion for the identical Tier C reason, and widening CPL-309's looser precedent (whose own gate primitive relies on a transitive check).
3. **One shared, internal-only gate+fetch helper — `app._resolve_customer_portal_invoice`** — composed by all three read RPCs, never re-derived three times. Not granted to `authenticated` (service_role only, mirrors `app._ticket_link_resolve_candidate`/`app._is_ticket_requester_party`'s own established convention) — every public entry point still asserts identity itself before calling it (decision 2), so the helper's own omission of the check is never "relying on a transitive check."
4. **DESIGN DECISION: only `status IN ('issued', 'void')` is portal-visible.** `draft`/`submitted`/`approved` are internal pre-issuance lifecycle states that must never leak. An issued-but-later-voided invoice stays visible so the customer understands why it disappeared from billing — disclosed as forward-compatible, defensive design: no RPC anywhere in this repository today actually drives `issued -> void` (`app.discard_finance_invoice_draft` only operates on `draft`/`submitted`; `app.finance_lifecycle_editability` marks `('invoice','issued',...)` with an empty allowed-actions array), matching FIN-197's own disclosed "governed reversal remains FIN-206's own scope" note. The status filter is applied inside every RPC, never trusted to a caller-supplied filter alone.
5. **Anti-enumeration (C-05): one shared `record_not_found` message**, reused verbatim by every get RPC. Non-existence, cross-tenant, pre-issuance status, and scope-denial all collapse into the identical outward error inside `app._resolve_customer_portal_invoice`.
6. **Projection never exposes internal linkage.** `company_id`/`job_order_id`/`billing_readiness_handoff_id`/`posting_period_id`/`ar_open_item_id` never appear in the invoice projection; `tax_code_id`/`tax_rule_version_id` never appear in the lines projection. Neither `app.finance_invoices` nor `app.finance_invoice_lines` carries any GL/journal/margin/vendor-cost column at all (confirmed by direct read of both tables' own full DDL) — field-masking for that class of data is therefore not a concern for this migration's own projection design, only access/lifecycle-state masking is.
7. **Payment/aging status is a separate, narrow read RPC — `app.get_customer_portal_invoice_payment_status`** — sourced from `app.finance_ar_open_items` via the invoice's own (never-exposed) `ar_open_item_id`, never a persisted aging column (none exists — FIN-210's own header: "aging numbers themselves are never stored, only computed"). Satisfies section 15's "payment status" (open/partial/paid) need the invoice's own `status` column alone cannot answer. A void-before-ever-issued invoice (no `ar_open_item_id`) resolves `payment_status = 'not_posted'` with null amounts — a real, honest state, never a fabricated zero.
8. **No idempotency-key parameter anywhere** — every RPC is a pure `stable` read; the mandatory idempotency rule does not apply to a migration with zero INSERT/UPDATE statements.
9. **Cursor pagination (tenant_id, updated_at desc, id desc), never OFFSET** — `app.list_customer_portal_invoices` mirrors `app.list_customer_portal_inventory_balances`/`app.list_customer_portal_outbound_orders`'s own established cursor shape exactly.
10. **`scripts/db-tests/rbac-enforcement.sql` compliance, verified by direct analysis before writing this migration, then live-confirmed (§10 below).** The `base` CTE already recognizes `resolve_customer_account_scope`. `app.evaluate_customer_portal_invoice_access` calls it directly (lands in `base` directly); `app._resolve_customer_portal_invoice` calls the gate primitive, and each of the three public read RPCs calls the helper (or, for the list RPC, `resolve_customer_account_scope` directly) — the `edge`/`closure` recursive CTE walks this call graph transitively, so all four public functions land in `closure` without any edit. The separate side-effecting-actor-authority sweep only flags `provolatile = 'v'` functions — every function in this migration is `stable`, exempting all of them.
11. **RLS on `app.finance_invoices`/`app.finance_invoice_lines`/`app.finance_ar_open_items` is UNCHANGED** — confirmed by direct read of each table's own already-applied RLS `SELECT` policy: `has_active_tenant_membership(tenant_id) or is_supreme_admin()` — no owner/customer branch of any kind. A `customer_user` principal holds no `app.tenant_user_identities` row, so all three tables are already unconditionally denied by construction — this migration's own RPCs are the only sanctioned access path.
12. **'Download' is a real, working structured JSON export**, composed at the TS service layer from the three read RPCs above — no new RPC, no fabricated PDF/document-generation/signed-URL pipeline. Confirmed by direct repository-wide search before writing this migration: zero Storage-bucket integration, zero PDF-generation dependency, zero existing signed-URL pattern for any Finance document anywhere in this repository. Matches the same class of disclosed transport/tooling gap ADR-0024 Part C already accepts for GraphQL parity.
13. **'Dispute' composes the ALREADY-VERIFIED HRT-287 customer-ticket flow via the ALREADY-VERIFIED HRT-292 `app.ticket_links` mechanism — no new table, no new RPC.** `app.ticket_links.entity_type` already includes `'invoice'`; `app.ticket_link_customer_safe_entity_types()` already includes it. A genuine, disclosed gap this migration does NOT fix (out of this prompt's own bounded scope, editing HRT-292's applied migration is forbidden): `app._ticket_link_resolve_candidate`'s own `'invoice'` branch composes `app.resolve_customer_owner_account_scope` (the LEGACY resolver), not this checkpoint's own CPL-300 widened one — the identical `ISS-2026-117` under-scoping shape, now surfacing for invoice ticket-links specifically. The invoice detail page's "Dispute" link is a real, working deep link into the customer-tickets create form (pre-filled subject/body, hidden `disputeInvoiceId`), and `createCustomerTicketAction` (extended, `app/(tenant)/[tenantSlug]/customer-tickets/actions.ts`) auto-links the created ticket via the already-shipped `linkTicketRecord`/HRT-292 RPC — a real, working composition, not parallel machinery.

No table is created, altered, or dropped by the migration. No existing RLS policy is touched. Purely additive: 5 new functions (1 internal), their grants, one explicit `revoke execute on all functions in schema app from public`.
