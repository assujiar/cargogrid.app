# Phase 8 (Customer Portal and Loyalty) Role Guides

**Produced by:** `CG-S13-CPL-028` (Prompt 326 — Customer Portal and Loyalty Documentation Handoff), per Prompt 326 §31's own documentation-update list, mirroring `docs/build-log/phase-07/HRIS_TICKETING_ROLE_GUIDES.md`'s own structure one phase up.

**Companion document:** `docs/build-log/phase-08/CUSTOMER_PORTAL_LOYALTY_RUNBOOKS.md` — scenario-based diagnosis/resolution for when something has already gone wrong. This document answers a different question: for a given real Phase 8 role/scope, what can they see and do, through which real route/RPC, and what does a given error actually mean.

**How to use this document:** each section names the real, live, `VERIFIED` UI route and the real RPC/permission action behind it — never an aspirational or planned surface. Every capability cited is drawn directly from its owning build log (`docs/build-log/phase-08/CPL-300.md` through `CPL-325.md`). Where a role's access is narrower than it might look, that narrowing is stated explicitly.

**Sanitization:** every example below (`PT Amanah Logistics`, `CV Sinar Abadi`, `Dewi Lestari`, `Fajar Nugroho`, `Rina Kartika`, round point/IDR figures) is fictional and deterministic. No raw payroll, PII, ticket content, voucher code, support-access token, or private URL appears anywhere in this document.

**Standing, repository-wide facts every role guide below assumes:** no MFA/step-up-authorization (RPD-023) mechanism exists anywhere in this repository — every "privileged" action below is gated by a real, live, server-side authority check, never by a second factor (`docs/runtime/KNOWN_ISSUES.md` `ISS-2026-125` item 1, `ISS-2026-138`). No append-only ledger table in this repository is immutable-for-all or tamper-proof — Supreme Admin retains an audited, RPD-022-accepted override path on five of Phase 8's own six Loyalty ledger tables (§5 below). No REST/GraphQL HTTP route exists for any Phase 8 capability — every route below is a Server Component/Action calling the `server/queries/`/`server/mutations/` layer, which calls the RPC directly (ADR-0024 Part C, disclosed identically at every one of `CPL-300` through `CPL-323`).

## 1. Customer User — `account_admin` (Layer 4, the account's own administrator)

**Entry point:** `app/(tenant)/[tenantSlug]/customer-portal/` (`CPL-300`) — the scope-preview screen; an account/site switcher when more than one account is active. Every downstream Phase 8 customer route (below) is reached from the shared `CustomerPortalNav` component.

**What distinguishes `account_admin` from `member`:** `app.customer_portal_account_memberships.role` is a flat, **two-value** CHECK constraint (`account_admin`/`member`) — there is no third, higher role anywhere in this schema (independently confirmed, not assumed, at `CPL-315.md` §2 item 2, via a direct `pg_constraint` read). Every capability below that an **ordinary member** can also reach is marked so explicitly; everything else in this section is `account_admin`-only, gated by the one shared authority primitive `app.actor_is_active_customer_portal_account_admin` (`CPL-300` design decision 5).

| Task | Real route | Real action |
|---|---|---|
| Invite a new portal user for the account | `customer-portal-users` | `app.invite_customer_portal_user` (`CPL-300`) — takes the invitee's real CargoGrid `auth_user_id` directly (a UUID), never an email; no email-to-identity resolution mechanism exists anywhere in this repository (the same standing convention `app.invite_user`, PLT-110, already has) |
| Change a member's role (`account_admin` ↔ `member`) | `customer-portal-users` | `app.update_customer_portal_account_membership_role` (`CPL-315`) — rejects a demotion that would leave the account with **zero** active `account_admin` rows (`last_account_admin`), race-safe via a locked count of the full active-admin set |
| Suspend / reactivate / revoke a member | `customer-portal-users` | `app.set_customer_portal_account_membership_status` (`CPL-300`) — **no last-admin guard exists on this specific RPC** (a real, disclosed, unfixed gap in an already-applied migration, `ISS-2026-125` item 3 — see the companion runbooks document, runbook 1) |
| Record an access-review attestation on an active member | `customer-portal-users` | `app.record_customer_portal_account_membership_access_review` (`CPL-315`) — a closed, two-value enum (`confirmed_appropriate`/`flagged_for_follow_up`); an attestation only, never itself a corrective action; a real, append-only, idempotency-keyed event, never a mutable "last review" column |
| View the full membership roster and access-review history | `customer-portal-users` | `app.list_customer_portal_account_memberships`, `app.list_customer_portal_account_memberships_for_access_review`, `app.list_customer_portal_account_membership_access_reviews` (`CPL-300`/`CPL-315`) |

**Every task an ordinary `member` can also do (see §2 below) is available to `account_admin` too** — the account-management table above is the *only* thing `account_admin` can reach that `member` cannot.

**Common errors and what they mean:**
- `accept_required` — attempting to force an `invited` membership straight to `active` via the status-update RPC. Only the invited identity itself, via `app.accept_customer_portal_invite`, may do that.
- `last_account_admin` — attempting a role-change that would leave the account with no admin (via `app.update_customer_portal_account_membership_role` — this specific guard does **not** exist on the older suspend/revoke path, per the disclosed gap above).
- `idempotency_key_conflict` on an access-review record — the same idempotency key was reused against a genuinely different membership; supply a fresh key.
- `invalid_review_target` — attempting to record an access review against a membership that is not currently `active` (a pending invite or a suspended/revoked row).
- `customer_portal_membership_not_found` on any by-id RPC — covers both a genuinely nonexistent id and a real-but-out-of-scope one (a disclosed, accepted anti-enumeration boundary, `ISS-2026-116`, since `p_membership_id` is a non-guessable UUID a caller can only legitimately already possess).

**Scenario walkthrough:** `Dewi Lestari`, `account_admin` for `CV Sinar Abadi` on tenant `PT Amanah Logistics`, needs to onboard a new colleague, `Fajar Nugroho`, and quarterly-review the account's own existing member list. She calls `app.invite_customer_portal_user` with Fajar's real `auth_user_id` and role `member`; Fajar receives an `invited` row and must accept it himself before any downstream access activates. A month later Dewi opens the access-review section, sees each active member's own most-recent review (or none, if never reviewed), and records `confirmed_appropriate` for Fajar with a real idempotency key — this is a durable attestation only; if Dewi instead wanted to change Fajar's role or suspend him, she would use the separate role-update/status actions, independently audited.

**The one thing an ordinary `member` (or `account_admin`, acting as a plain customer) can *never* get from a genuine, unassisted redemption: instant, synchronous fulfillment.** `app.submit_loyalty_redemption` always creates the real request record, then attempts immediate composition — but that attempt only succeeds inline for a caller who already, independently holds staff/system `LYL:Edit` authority, which a `customer_user` identity structurally can never hold in this repository (no provisioning path grants it). Every genuine customer submission — regardless of `reward_type` — correctly, gracefully falls back to `pending_approval`, requiring one real staff decision (`ISS-2026-132` item 1). This is documented, intended behavior, not a delay to escalate.

**Common errors and what they mean:**
- `record_not_found` / `document_not_found` / `loyalty_redemption_not_found` / `ticket_not_found` — the identical, anti-enumerating not-found shape covers a genuinely nonexistent id, a cross-tenant id, and a same-tenant-but-out-of-scope id everywhere in Phase 8. Do not read it as proof a record does not exist.
- `account_on_hold` — the loyalty account has a real, staff-opened fraud-review hold; the message shown is always generic, never the real internal reason.
- `reward_redemption_unavailable` — a misconfigured `discount_voucher` reward (no positive `internal_cost` configured) — a real, customer-safe rejection rather than a fabricated value.
- `invalid_transition` on a ticket action — an illegal status jump, or (since a Phase-7-established rule) an attempt to link a new record/add a watcher on an already `closed`/`cancelled` ticket; unlinking or removing a watcher remains permitted there.
- `entity_type_not_permitted` on a ticket linked-record search — a `customer_user` caller attempted an out-of-registry entity type (e.g. `vendor`/`user`); the customer-facing registry is structurally narrower than the staff one.

**Scenario walkthrough:** `Fajar Nugroho` (`member`, `CV Sinar Abadi`) files a complaint ticket about a delayed shipment, linking the specific shipment order to the ticket at creation time via the precreate picker. He also notices his loyalty points balance looks low and checks `customer-loyalty-points` — the ledger shows a recent `earn` entry for a paid invoice and a separate `expiry` entry for an older lot, both correctly signed and summing to the displayed balance. He redeems a `discount_voucher` reward he is eligible for; the redemption lands `pending_approval` (the correct, expected outcome for a genuine customer submission) and he sees it reflected in `customer-loyalty-redemptions` with a cancel option while it waits for a staff decision.

## 3. Tenant staff holding `CPT:*`-family permissions

**What `CPT` is, precisely:** `CPT` (`Customer Portal`) is a real, seeded Platform Core module (`docs/build-log/... 20260716094432_create_entitlements.sql`) with five anchor families (`CPT-QBK`/`CPT-TRK`/`CPT-WHS`/`CPT-BIL`/`CPT-CX`) and four real permission actions: `View`/`Export`/`Download` (seeded at Platform Core, `20260716103445_create_roles_permissions.sql`) plus `Create` (added additively by `CPL-300`, `('Create', 'CPT', 'standard', false)`, the identical technique earlier phases already used for a one-off new permission on an existing module).

**What this role is, structurally: this is NOT the customer's own role, and it is NOT how staff read a customer's data day-to-day.** Every Phase 8 customer-facing read/write is scoped through the customer's own `customer_user` Layer-4 identity and `app.resolve_customer_account_scope`/`app.actor_is_active_customer_portal_account_admin` — never through `app.evaluate_permission`/staff RBAC (`CPL-300` design decision 5, `ADR-0024` Part B). Ordinary Phase 8 operational staff work (reviewing a quote request, deciding a booking, approving a profile change, deciding a redemption) is instead gated by each **owning domain's own** staff RBAC action — `COM:Approve` for a profile change (`CPL-314`), `LYL:Configure`/`LYL:Edit`/`LYL:View` for every Loyalty action (§4 below), the existing Ticketing `TKT:*` actions for staff ticket work (HRT-286, Phase 7). `app.grant_initial_customer_portal_account_admin` (the one, deliberate bootstrap exception, `CPL-300` design decision 6) is the single Phase 8 write RPC actually gated on `CPT:Create` — a Supreme-Admin-authority-independent, tenant-staff-callable way to seed the very first `account_admin` for a brand-new customer account, since no `account_admin` can exist yet to invite themselves.

**Where `CPT:View`/`Export`/`Download` are actually consumed today:** these three actions were seeded at Platform Core specifically for this module and named in the source blueprint's own anchor families, but **no live Phase 8 RPC in this repository currently gates a read on `CPT:View`/`Export`/`Download` directly** — every real customer-portal-adjacent staff read (a tenant admin browsing a customer's own booking/shipment/invoice/document/loyalty history through the ordinary internal staff surfaces) goes through that domain's own existing RBAC action (e.g. Commercial's `COM:View` for the underlying `app.accounts`/`app.quotations` rows, Finance's `FIN:View` for `app.finance_invoices`, Operations' own access checks for shipment/warehouse data) — the customer-portal-specific RPCs this document catalogues are for the `customer_user` identity's own use, not a staff-facing "view as customer" surface. A role assignment carrying `CPT:View`/`Export`/`Download` today grants standing on the module/action pair itself (visible in role administration) without yet having a Phase 8 RPC that checks it — this is a real, structural fact about the current build, not a defect to chase.

**Common errors and what they mean:**
- `insufficient_authority`/`account_not_found` on `app.grant_initial_customer_portal_account_admin` — either the staff caller lacks `CPT:Create`, or the target account id does not exist in the caller's own tenant (the authority check runs **before** the account-existence check, closing a real, disclosed IDOR-shaped finding from `CPL-300`'s own Tier C review, §14 Finding 3 — a staff caller without `CPT:Create` cannot use this RPC to distinguish a real cross-tenant account from a fake one).
- A repeated bootstrap call for an identity that already has a membership row returns the **existing** row unchanged, never a duplicate and never a re-promotion of a demoted/suspended row — this is the exact reason `account_admin`-lockout recovery has no self-service path (see the companion runbooks document, runbook 1, item 6).

**Scenario walkthrough:** `Rina Kartika`, a tenant staff member holding `CPT:Create`, onboards a brand-new customer account, `CV Sinar Abadi`, that has just converted from a prospect (Commercial's own COM-155 flow). No `customer_user` identity exists yet with any membership row for this account, so no one can self-invite. Rina calls `app.grant_initial_customer_portal_account_admin` for the account's own designated first user — this seeds exactly one `account_admin` row, idempotently, and from that point forward every further invite/role-change/access-review action is that customer's own `account_admin`'s job (§1 above), never Rina's again for this account.

## 4. `LYL:View`/`LYL:Edit`/`LYL:Configure` staff tiers — the real distinction

**The four real `LYL` permission actions** (`Loyalty and Rewards`, module code `LYL`, seeded at Platform Core, `20260716103445_create_roles_permissions.sql`): `View`, `Create`, `Edit` (all `standard`), and `Configure` (`admin`). **There is no separate `LYL:Approve` action** — this was confirmed, not assumed, at `CPL-323`'s own design decision 11: `Configure` is the deliberate, already-established stand-in for every governance-grade decision across this whole domain, mirroring how FIN-209's own distinct `FIN:Approve` certify gate is realized here.

**`LYL:View` — read-only, non-privileged staff visibility.** Every `list_*`/`get_*` staff RPC across all eight Loyalty capabilities (`CPL-316` through `CPL-323`) is gated on this alone. It sees full internal projections other than the customer-safe ones — including, for example, `app.list_loyalty_point_ledger_entries`' own `reason` column, `app.get_loyalty_fraud_review_case`'s own `risk_signal_type`/`risk_signal_detail`, and `app.list_loyalty_rewards`' own `internal_cost`/`vendor_ref`.

**`LYL:Edit` — ordinary posting-tier authority.** This is the tier that actually **executes** most of the domain's own transactional work: `app.post_loyalty_points_earned`, `app.consume_loyalty_points_fifo`, `app.evaluate_customer_loyalty_earning_for_paid_invoice`, `app.recalculate_customer_loyalty_tier`, `app.issue_loyalty_benefit_entitlement`, `app.expire_loyalty_point_lots`/`app.expire_loyalty_benefit_entitlements`, `app.run_loyalty_expiry_sweep`, `app.reserve_loyalty_reward_stock_unit`/`app.release_loyalty_reward_stock_reservation`, `app.execute_loyalty_liability_reconciliation_run`, `app.resolve_loyalty_liability_reconciliation_exception`, and — the load-bearing one for this section — the ordinary lifecycle half of redemption (`app.submit_loyalty_redemption` on the staff/system side, `app.mark_loyalty_redemption_fulfilled`/`_failed`), and `app.claim_loyalty_fraud_review_case`.

**`LYL:Configure` — the elevated, governance-grade gate.** Reserved consistently, across every one of the eight capabilities, for the highest-blast-radius, hardest-to-reverse action in its own domain: **publishing** a program rule version / tier definition / reward (`app.publish_loyalty_program_rule_version`, `app.publish_loyalty_tier_definition`, `app.publish_loyalty_reward`) and every subsequent lifecycle transition on a published reward (`pause`/`resume`/`archive`); **reversing** an earning event or a points-earned entry (`app.reverse_loyalty_earning_event`, `app.reverse_loyalty_points_earned`); **asserting/releasing** a benefit-entitlement hold or an account-wide fraud-review hold (`app.hold_loyalty_benefit_entitlement`/`release_...`, `app.hold_loyalty_account_tier_benefits`/`release_...`); **deciding** a point adjustment (the checker half of the maker-checker pair, `app.decide_loyalty_point_adjustment`); **opening/deciding** a fraud-review case (`app.open_loyalty_fraud_review_case`, `app.decide_loyalty_fraud_review_case`) and suppressing/revoking a suppression; and **deciding** a redemption (`app.decide_loyalty_redemption`) and **certifying** a liability reconciliation run (`app.certify_loyalty_liability_reconciliation_run`).

**The real distinction the source spec asks this document to cite explicitly, established at `CPL-321`/`CPL-322`: `Edit` is sufficient to auto-compose (execute a transactional posting), but only `Configure` gates a genuine *decide*.** The clearest concrete illustration is redemption itself (`CPL-321`): `app.submit_loyalty_redemption` is reachable by anyone holding bare `LYL:Edit`, and for a `discount_voucher` reward specifically, a submission by such an `LYL:Edit` holder auto-composes **inline, synchronously** — reserve stock, consume points, issue the entitlement — with `app.decide_loyalty_redemption` (the `LYL:Configure`-gated action) **never invoked at all** on that path. This was originally designed and disclosed purely as the mechanism that lets a genuine `customer_user` submission gracefully fall back to `pending_approval` (`ISS-2026-132` item 1) — but `CPL-325`'s own dedicated privileged-action-hardening lens found and disclosed the **other** side of the same mechanism: a staff actor holding **only** `LYL:Edit` (never `LYL:Configure`) can submit — and thereby instantly, unilaterally fulfill — a `discount_voucher` redemption for **any** loyalty account in the tenant, in one call, completely bypassing the `LYL:Configure`-gated decision path the rest of this domain otherwise treats as the mandatory checker step (`ISS-2026-139`, Medium, `OPEN`). Every **other** maker-checker pair in this domain (point adjustment, customer profile-change) enforces a hard two-actor rule even among already-privileged staff; this redemption path is the one deliberate, tested, disclosed exception, and it is a real governance gap, not a mechanical bug — closing it requires a genuine product decision (require `Configure` for that one auto-compose branch, or add an explicit self/other-account check), not a unilateral migration. A tenant relying on the `Edit`/`Configure` split as a hard governance boundary for redemption specifically should be aware of this exact, narrow exception.

**A second, related, disclosed gap in the same family:** fraud-review case self-approval is **not** structurally blocked — `app.open_loyalty_fraud_review_case` and `app.decide_loyalty_fraud_review_case` both require the same elevated `LYL:Configure` (deliberately matched, not a lower outer gate with a nested re-check — `CPL-322` design decision 4), but nothing stops the **same** `LYL:Configure`-holding staff member from opening a case and then deciding their own just-opened case (`ISS-2026-133` item 1, Low, `OPEN`). This is bounded to already-privileged actors and is disclosed as acceptable *because* no live rule/signal-detection engine exists anywhere in this repository to open a case autonomously — every case today is genuinely staff-initiated, so the SYSTEM/RULE-vs-HUMAN-REVIEWER maker-checker framing this domain otherwise relies on does not yet have two independent parties to enforce.

**Common errors and what they mean:**
- `insufficient_authority` — almost always the wrong **tier**, not a wholly missing permission (e.g., holding `LYL:Edit` but attempting `app.decide_loyalty_redemption`, `app.publish_loyalty_reward`, or `app.certify_loyalty_liability_reconciliation_run`, all `Configure`-gated).
- `self_approval_not_allowed`/`self_calibration_not_permitted`-shaped rejections — structurally blocked everywhere **except** the two disclosed gaps named above (redemption's own `discount_voucher` auto-compose path, and fraud-review case self-decision).
- `stale_version` — a NULL-bypass optimistic-concurrency regression was found and fixed across every `p_expected_version`-taking function in this domain at `CPL-324`/`CPL-325` (`20260801260000`) — a `NULL` (or omitted) `p_expected_version` is now correctly rejected everywhere, never silently accepted as "don't check."

**Scenario walkthrough:** `Rina Kartika` (this time holding `LYL:Edit` only, not `LYL:Configure`) reviews a `pending_approval` `physical_item` redemption queue and correctly finds she cannot call `app.decide_loyalty_redemption` — `insufficient_authority`. A colleague holding `LYL:Configure` decides it (`approve`), and Rina then completes the operational fulfillment step herself (`app.mark_loyalty_redemption_fulfilled`, `LYL:Edit`-gated, correctly reachable) once the physical item ships. Separately, Rina notices she *can* submit a `discount_voucher` redemption on a customer's behalf and watches it complete instantly, with no `Configure`-gated decision step at all — this is the real, disclosed `ISS-2026-139` shape, not a permissions misconfiguration.

## 5. Supreme Admin — the RPD-022 absolute-CRUD exception path

**What this role is, precisely, in Phase 8's own scope: the one identity class exempt from the append-only-forever rule on five of Phase 8's own six Loyalty ledger tables, and nothing more.** Supreme Admin authority in Phase 8 does **not** grant any special customer-portal read access (every customer-facing RPC still requires a genuine `customer_user` membership row, resolved the same way for everyone) and does **not** bypass any of the ordinary `LYL:*`/`COM:*`/`CPT:*` staff RBAC gates named in §§3–4 above for ordinary reads/writes — those are unaffected by Supreme Admin status. The one thing Supreme Admin status changes in Phase 8 is a single, narrow, audited mutation path on the domain's own append-only ledgers.

**The real mechanism** (`supabase/migrations/20260801280000_harden_customer_portal_loyalty_ledger_supreme_admin_override.sql`, `docs/build-log/phase-08/CPL-325.md` §5/§6.1): a shared `app.protect_loyalty_ledger_append_only()` `BEFORE UPDATE/DELETE` trigger is attached to `app.loyalty_earning_events`, `app.loyalty_point_ledger_entries`, `app.loyalty_benefit_entitlement_events`, `app.loyalty_reward_stock_reservations`, and `app.loyalty_redemption_events`. It blocks any `UPDATE`/`DELETE` on any of those five tables **unless** `app.is_supreme_admin(auth.uid())` is true — in which case the mutation is permitted and a best-effort `app.audit_logs` row is captured, with before/after values. `authenticated` holds **zero** direct grant on any of the five tables regardless of Supreme Admin status (every real mutation in this repository — including a genuine Supreme Admin one — runs as `service_role`, which the same migration additively grants `UPDATE`/`DELETE` on all five, a grant that literally did not exist on any role before this fix, meaning even a genuine Supreme Admin had no exercisable override path until `CPL-325` built one).

**Why this exists, and why it is explicitly NOT a claim of immutability:** `docs/architecture/06_RLS_RBAC_WORKSTREAM.md` §8 (RPD-022, binding, read verbatim at `CPL-325` rather than accepted from any paraphrase) requires exactly this shape for every table in the repository's own `append_only_ledger` policy family — "a distinct [mechanism]... that grants `UPDATE`/`DELETE` to the Supreme Admin role specifically, alongside (not instead of) the normal-role policy that denies it" — and §13 names the per-table policy a **release blocker** for any phase that has not yet closed. `CPL-325` independently, explicitly ruled on this (three of its own four adversarial review lenses converged on the same answer before comparing notes) rather than deferring it a third time: the mechanism is built now, scoped to Phase 8's own five tables, deliberately **not** retroactively covering `app.inventory_movements` (a pre-existing, already-`VERIFIED` Phase 5 ledger with the identical gap) or any other pre-Phase-8 ledger — that remains a future, dedicated, cross-cutting task's own scope. **§8's own residual-risk language (`RISK-004`) describes the accepted risk of the mechanism once it exists — an audit-logged Supreme Admin mutation is still, itself, alterable by the same authority — it is never license to claim the ledger is tamper-proof, immutable-for-all, or beyond a privileged administrator's own reach.** This document, and every runbook in its companion, states that explicitly rather than implying otherwise.

**The one table this document must name as the disclosed exception to the exception:** `app.loyalty_account_tier_movements` (`CPL-317`) carries the identical structural append-only shape (`select, insert` granted to `service_role` only, zero `UPDATE`/`DELETE` to any role) but was **not** included in `CPL-325`'s own five-table remediation scope — it was named in `ISS-2026-130`'s own original four-table list before `CPL-320`/`CPL-321` existed, but the fix migration's own explicit scope substituted the two newer Batch-5 tables instead, omitting this one. Tracked as `ISS-2026-137` (Low, `OPEN`) — today, a Supreme Admin has **no** override path on this one table at all, which the same disclosure frames correctly: the absence makes this ledger **more** immutable, not less secure, but it is a real, disclosed gap in the override mechanism's own coverage, not a design decision to leave it out permanently.

**Common errors and what they mean:**
- A raw `UPDATE`/`DELETE` attempt against any of the five protected tables by any non-Supreme-Admin identity — including an ordinary `LYL:Configure` staff actor — is blocked by the trigger itself, independent of and in addition to the normal RLS/grant layer; live-verified at `CPL-325` that `LYL:Configure` alone is **not** sufficient, only genuine Supreme Admin status.
- An attempted correction on `app.loyalty_account_tier_movements` has **no** mutation path today, for anyone, including Supreme Admin — this is the disclosed `ISS-2026-137` gap, not a misconfiguration to troubleshoot.

**Scenario walkthrough:** a data-quality investigation (the companion runbooks document's own runbook 2/4) finds a genuinely corrupted `app.loyalty_point_ledger_entries` row — the row's own `amount` was mis-posted by an already-superseded, buggy code path before a fix landed, and the account's own reconciliation now correctly, permanently flags a `point_balance_derivation_mismatch` exception referencing it. A Supreme Admin, acting under this repository's own standing RPD-022 accepted-residual-risk framework, directly corrects the row; the mutation succeeds (blocked for every other identity), and a full before/after `app.audit_logs` entry is captured automatically — a detective control, reviewable after the fact, never a preventive guarantee that the correction itself could not later be altered again by the same authority.
