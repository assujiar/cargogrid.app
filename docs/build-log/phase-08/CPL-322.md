**Prompt ID:** `CG-S13-CPL-024` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/322_EXPIRY_FRAUD_PREVENTION_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (Batch 5's own Tier C review, `CPL-320..323`, closed — see §14)

Third prompt of Batch 5 (`CG-S13-CPL-022..025`, Prompts 320-323), run as its own small, single-agent workflow — not batched with the rest of Batch 5 — specifically to limit the amount of in-flight work lost if the container is restarted mid-run, the same strategy CPL-317/318/319/320/321 already used successfully. `CPL-320` (Reward Catalogue) and `CPL-321` (Redemption Approval and Fulfillment) both `COMPLETED`, not yet `VERIFIED` — this checkpoint's own upstream dependencies, both read in full (migration + build log) before writing any code, per this task's own explicit mandatory-reading instruction.

## 1. What this checkpoint builds

Expiry orchestration and governed fraud-prevention controls — the SEVENTH Loyalty-domain capability in this repository (ADR-0024 Part D), and the first Loyalty checkpoint to touch `app.jobs`. Two new tables (`app.loyalty_fraud_review_cases`, `app.loyalty_fraud_review_suppressions`) plus 11 new `SECURITY DEFINER` functions: a real, storm-controlled expiry-sweep orchestration RPC composing CPL-318's `app.expire_loyalty_point_lots` and CPL-319's `app.expire_loyalty_benefit_entitlements` (never reimplementing either), a governed fraud review-case workflow composing CPL-317's `app.hold_loyalty_account_tier_benefits`/`app.release_loyalty_account_tier_benefits` (never a second, competing account-hold table), a suppression/cooldown mechanism mirroring HRT-291's `app.ticket_escalation_suppressions` exactly, and a customer-safe generic hold-status read. Widens `app.jobs.job_type`'s own CHECK constraint (the established drop/add-constraint pattern) and `app.generic_job_types()` to add `'loyalty_expiry_sweep'`.

## 2. Design decisions

Full rationale in the migration's own 18-point header comment; summarized here.

1. **`app.run_loyalty_expiry_sweep` mirrors `app.run_ticket_escalation_evaluation_batch`/`app.run_ticket_sla_evaluation_batch` exactly** — a real `app.jobs` row tracked through the actual PLT-132 lifecycle (enqueue → self-claim → loop → complete). `p_run_label` (a disclosed 5th parameter beyond the source prompt's own literal 4) defaults to the calendar day of `p_as_of`, giving calendar-day idempotency for free while still letting a deliberate same-day rerun happen under its own distinct key. Storm control is the SAME real guarantee the mirrored precedents already rely on, worked through explicitly and live-proven: a genuinely concurrent second call for the same tenant+run_label BLOCKS on `app.enqueue_job`'s own real `unique(tenant_id, idempotency_key)` constraint until the first transaction (the WHOLE sweep, one transaction per call) commits, then correctly no-ops once it sees the job already `completed` — a real two-process race in this checkpoint's own db-test proves both processes return the IDENTICAL completed job with the SAME counts, never double-processing. Real counts (`lots_expired_count`/`entitlements_expired_count`) are counted from each composed function's own actually-returned row set and recorded on the completed job row via `app.jobs.payload`, extended additively (no dedicated result-count column exists on the repository-wide shared `app.jobs` table; its existing `total_rows`/`valid_row_count`-family columns are grep-confirmed used only by import/export-flavored call sites).
2. **`'loyalty_expiry_sweep'` is a genuinely NEW job_type literal, disclosed as NOT a reuse of the pre-existing, never-realized `'loyalty_expiration'` placeholder** (seeded speculatively by PLT-132's own original migration, grep-confirmed never the target of a real `enqueue_job`/`dispatch_event_as_job` call anywhere in this repository, including nowhere in Loyalty's own five prior checkpoints). Mirrors this domain's own established precedent of adding increasingly specific new literals even where a broader generic one already existed. Widened via the established drop/add-constraint pattern, full current list carried forward verbatim (grep-verified against every prior `drop constraint jobs_job_type_check` migration, HRT-291's own the most recent) plus this checkpoint's one new value — never a narrowing ALTER. `app.generic_job_types()` (ATW-031/ISS-2026-012 single source of truth) widened identically in the same migration.
3. **Fraud hold: the account-level primitive is composed, never reinvented.** `app.open_loyalty_fraud_review_case` composes `app.hold_loyalty_account_tier_benefits`; `app.decide_loyalty_fraud_review_case`'s own `'clear'` branch composes `app.release_loyalty_account_tier_benefits`. Neither function ever writes `app.loyalty_account_tier_holds` directly — the SAME table CPL-321's own `app.submit_loyalty_redemption`/`app.decide_loyalty_redemption` already read directly as the account-wide "is this account blocked" gate, and the SAME table CPL-317's own customer-facing tier card already reads to suppress benefit display with a generic notice. A fraud hold this checkpoint opens is therefore immediately, structurally effective against redemption AND immediately visible on the already-shipped, unmodified `customer-loyalty-tier` page — zero new coupling code anywhere, live-proven with a real cross-prompt regression test.
4. **Authority for `app.open_loyalty_fraud_review_case`: `LYL:Configure`, the SAME elevated authority its own composed `app.hold_loyalty_account_tier_benefits` independently requires** — deliberately not a lower `LYL:Edit` outer gate with a nested re-check (CPL-318/321's own established shape). Reasoned explicitly: opening a case immediately applies a real, non-trivial, account-wide restriction, so gating the outer action lower than what its own inner composition needs would only ever succeed for an actor who also independently holds the higher authority anyway — worse, it would let a lower-authority actor's call fail confusingly deep inside a nested composition after already inserting a real case row. Matching outer/inner authority sidesteps the whole class of problem.
5. **`app.loyalty_fraud_review_cases.status` maker-checker framing is SYSTEM/RULE (opens, provisional) vs. HUMAN REVIEWER (decides, final), not two different humans** — no live rule/signal-detection engine exists anywhere in this repository (source prompt: "predictive fraud depth remains Step 14"), so every `open_loyalty_fraud_review_case` call today is itself staff-initiated. No self-approval block is built for this reason — a real, disclosed, narrow gap (`ISS-2026-133` item 1), bounded to already-`LYL:Configure`-privileged actors.
6. **`app.claim_loyalty_fraud_review_case` (open → under_review) is a disclosed 3rd function**, beyond `open_loyalty_fraud_review_case`/`decide_loyalty_fraud_review_case` the source prompt names literally — mirrors CPL-320's own disclosed `resume_loyalty_reward` 6th-function precedent. `under_review` genuinely reachable without being load-bearing for anything else — `decide_loyalty_fraud_review_case` accepts a decision from EITHER `open` OR `under_review`.
7. **Suppression/cooldown mirrors `app.ticket_escalation_suppressions`' own exact shape (HRT-291)** — `LYL:Configure`-gated, mandatory non-empty reason, mandatory future `expires_at`, at most one non-revoked row per `loyalty_account_id` at a time, an already-expired-but-unrevoked row auto-revoked the next time it is checked (inside `app.open_loyalty_fraud_review_case` itself, the one place it matters), never hides the underlying case/hold history. One deliberate, disclosed departure from the precedent's own literal choice: `clock_timestamp()`, never `now()`, throughout (this domain's own already-established convention since CPL-315/317, applied even though the mirrored precedent predates it).
8. **Entitlement-level fraud hold: not built, account-level coverage is sufficient for this checkpoint, disclosed rather than silently skipped** (`ISS-2026-133` item 2) — an account-level hold already blocks every redemption; CPL-319's own entitlement-hold primitives already exist and are already independently staff-callable today; a second, parallel case-and-decide mechanism scoped to entitlements would widen this migration's already-substantial scope with no concrete business need calling for it.
9. **Redaction (business rule: "fraud signals and thresholds are restricted internal data... never exposed to a customer_user caller, not even in an error message").** `risk_signal_type`/`risk_signal_detail`/`review_reason`/`reviewed_by` exist only on `app.loyalty_fraud_review_cases`, read only by the three `LYL:View`-gated staff RPCs. `app.list_customer_portal_loyalty_account_hold_status` never references that table at all — structurally, grep-provably impossible to leak any fraud-review field, returning only `is_on_hold`/a generic `hold_notice` sourced from `app.loyalty_account_tier_holds.is_held` (mirrors CPL-317/319's own already-proven generic hold message exactly).
10. **No autonomous punitive action.** `open_loyalty_fraud_review_case` applies only a provisional, reversible hold. `'confirm'` performs no action beyond recording the decision — the hold, already applied at open time, simply stays; no cascading escalation, no automatic account closure (grep-confirmed: the confirm branch touches no table besides `app.loyalty_fraud_review_cases` itself).
11. Every actor-taking function calls `app.assert_actor_is_session_identity` first; every staff mutate/get-by-id RPC checks `LYL:*` authority BEFORE fetching its target row (C-05).
12. **Idempotency**: `open_loyalty_fraud_review_case` carries a real `unique(tenant_id, idempotency_key)`, the authority check running before the idempotent short-circuit (which verifies the full target tuple — `loyalty_account_id`/`risk_signal_type` — on a key match), a real `exception when unique_violation` handler that distinguishes a genuine idempotency-key race from the partial "one active case per account" index conflict by re-checking the idempotency key first (mirrors `app.issue_loyalty_benefit_entitlement`'s own identical shape, CPL-319), and the case row's own INSERT happens strictly before composing the hold.
13. **Optimistic concurrency (`claim`/`decide`/`revoke`): the NULL-bypass fix applied from the start** — every function rejects `p_expected_version is null` explicitly, and every UPDATE repeats `and record_version = p_expected_version` on the statement itself (CPL-321's own double-defended shape), live regression-proven per function.
14. `clock_timestamp()`, never `now()`, throughout.
15. **LYL permission mapping, reused unchanged.** Sweep/claim → `LYL:Edit`. Open/decide-case and suppress/revoke (governance-grade) → `LYL:Configure`. Staff reads → `LYL:View`. Customer-facing hold-status read → `resolve_customer_account_scope` only.
16. RLS: `authenticated` holds zero direct grant on either new table.
17. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public` before final grants.
18. Cursor pagination: `(tenant_id, updated_at desc, id desc)` for cases/expiry-runs (both carry `updated_at`); `(tenant_id, created_at desc, id desc)` for suppressions (no `updated_at`, mirrors `app.list_loyalty_account_tier_movements`'s own precedent).
