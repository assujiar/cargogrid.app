# CPL-302 — Request Quotation

**Prompt ID:** `CG-S13-CPL-004` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/302_REQUEST_QUOTATION_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (2026-08-16 — Batch 1's own Tier C review closed across all of CPL-301..304 together; see §14 for the 4-lens review/fix record — a Critical cross-account IDOR and a High concurrency/race defect were found and fixed at root cause — and the orchestrating session's own independent gate re-run)

## 1. What this checkpoint builds

CPL-302 lets a scoped customer-portal user submit and monitor a quote **request** — cargo, route, service, dates, notes, attachments, status timeline — that hands off to Commercial's own canonical quotation pipeline (COM-151) without ever creating a second, competing quote truth. It is the first Phase 8 capability ADR-0024 Part B (customer writes) governs end to end: a new portal-owned request/intent table, a real staff-gated conversion acknowledgement, and zero widening of any canonical Commercial RPC or RLS policy.

## 2. Design decisions (cited, not re-derived — full rationale lives in the migration's own header)

1. **A new portal-owned request table, never `app.quotations`.** `app.customer_portal_quote_requests` carries no tariff/margin/tax field of any kind. `linked_quotation_id` is the only bridge to canonical truth, set exactly once by the one staff-gated RPC.
2. **`origin`/`destination` are bounded jsonb snapshots**, not a location master (none exists yet — the same disclosed boundary COM-151's own `customer_snapshot` already established).
3. **Two distinct idempotency keys** (`idempotency_key` for create, `submitted_idempotency_key` for submit — unique per `(tenant_id, account_id)`), not one reused column — reusing one column would let a genuine retry of the *original* create call fail to find its own match once submit had overwritten it, and insert a duplicate draft. Disclosed, deliberate elaboration of the source prompt's own "idempotency_key on every create" + "idempotency_key unique per tenant+account" text, not a silent deviation.
4. **File attachments reuse the Platform Document/File Engine (PLT-128) exactly as instructed** — `app.initiate_file_upload` with `record_type='customer_portal_quote_request'`, `record_id`=the request id — with two small, necessary, disclosed additions:
   - (a) a new `quote_request_attachment` document type + `document:quote_request_attachment` config type, registered by direct `INSERT ... ON CONFLICT DO NOTHING` at migration-apply time (migration-apply has no live actor session to satisfy `app.register_document_type`'s own Supreme-Admin gate) — mirrors `app.tickets`' own `ticket_attachment` precedent (`20260731060000_create_ticketing_internal.sql` design decision 8) exactly, including that a tenant must still separately publish a real MIME/size/retention/classification definition before any upload succeeds (a standing, repository-wide PLT-128 precondition, not unique to this capability).
   - (b) `app.check_file_action_authority` (PLT-128, service_role-only, never reachable directly by `authenticated`) is widened by `CREATE OR REPLACE` (identical signature, grant untouched) to also recognize an active `customer_user`-layer principal. **Verified necessary, not assumed**: a `customer_user` identity's own `app.tenant_user_identities` row is linked at `status='invited'` by CPL-300's own invite/accept/bootstrap flow and is **never** transitioned to `'active'` by any function in this repository (only the staff-only `app.transition_user_status` does that) — so the unwidened predicate (`has_active_tenant_membership OR is_supreme_admin`) was unconditionally `false` for every customer identity that has ever existed here. Leaving it unwidened would make a genuinely customer-attributed upload permanently, silently impossible — the exact "no placeholder/fake persistence" failure `AGENTS.md` forbids. Live-verified before/after in the db-test (§11 below). Safe because every composing function (`initiate_file_upload`/`record_file_scan_result`/`authorize_file_access`) is `service_role`-only, never `authenticated` — this widening only changes which already-server-mediated calls succeed, opening no new direct-client surface.
   - **Disclosed, deliberately not built** (the source prompt's own explicit escape hatch): scan-status gating on submit, and `app.authorize_file_access` composition from the portal. On the second point specifically: live inspection shows `app.authorize_file_access`'s own record-scope branch (`app.can_access_record`, PLT-114) **also** hard-requires `has_active_tenant_membership` (`... AND (has_active_tenant_membership(...) AND (...))`), so even after this migration's widening, a customer co-worker who did not personally upload a file would be incorrectly denied by `can_access_record`'s own `customer_account_ref` branch — a genuine, pre-existing, cross-cutting Platform primitive gap (PLT-114/PLT-128), not caused by this migration and outside this capability's own allowed file scope to fix. This capability's own new `app.list_customer_quote_request_files` is therefore the **only** sanctioned customer-facing attachment read path — a `SECURITY DEFINER` RPC composing this capability's own account-scope resolver directly, never `can_access_record` — and is, unlike `authorize_file_access`, genuinely correct for every account member, not only the uploader (live-verified in the db-test).
5. **RLS: `authenticated` holds ZERO direct grant**, mirroring CPL-300's `app.customer_portal_account_memberships` convention exactly.
6. **Staff conversion acknowledgement is the ONLY place this migration touches staff RBAC** — `app.link_customer_quote_request_to_quotation`, gated by the already-existing `app.evaluate_permission(actor, tenant, 'COM', 'Edit')` (the same module/action `app.add_quotation_line`/`app.submit_quotation` already require — reused, no new module/action). **Disclosed scope boundary**: `app.quotations` carries no `app.accounts` reference at all (only `opportunity_id → prospect_id`, predating COM-155's own account conversion), so this function cannot structurally verify the linked quotation belongs to the same customer as the request — it relies on the COM:Edit-holding staff actor's own authority over that quotation, exactly the trust `app.add_quotation_line`/`app.submit_quotation` already extend unconditionally. Matches the source prompt's own framing: "Staff-side conversion acknowledgement, minimal."
7. **Status machine**: `draft → submitted | cancelled`; `submitted → cancelled | converted`; `cancelled`/`converted` both terminal. Enforced by a `before update of status` trigger + one combined touch trigger (`updated_at`+`record_version`), mirroring CPL-300 exactly. Every optimistic-concurrency check follows CPL-300's own `select ... for update` + explicit raise shape.
8. **Anti-enumeration**: `app.get_customer_quote_request` raises the identical `record_not_found` (errcode `no_data_found`) whether the id genuinely does not exist, belongs to another tenant, or is out of scope — mirrors ATW-242's `app.get_customer_inventory_balance` exactly (ADR-0024 Part A's own named precedent). `update`/`submit`/`cancel` reuse the same message for the identical reason.
9. **Scope grain is the account, not the original requester.** Any active member of the account (account_admin or member) may view/edit/submit/cancel a draft/submitted request on that account — mirrors HRT-287's own "any account member sees the account's tickets" precedent. `requested_by_auth_user_id` is informational/audit provenance only.
10. **REST/GraphQL transport (ADR-0024 Part C)**: service layer + Server Actions + UI only, no `app/api/` HTTP route — identical in kind to CPL-300's and CPL-301's own disclosed residual gap, itself identical to every Phase 1-7 capability's own standing disclosure (no REST/GraphQL adapter exists anywhere in this repository for any internal or portal workflow — every one goes through Server Actions/RSC fetches over the same typed service layer).

## 3. A real, live-verified defect found and fixed during this checkpoint's own implementation

While writing `app.list_customer_quote_request_files` (a `RETURNS TABLE(id uuid, ...)` function), PL/pgSQL auto-declares a variable named `id` matching that output column. The function's own internal single-row lookup (`select * into v_request from app.customer_portal_quote_requests where id = p_request_id and tenant_id = p_tenant_id`) used a bare, unaliased `id` — ambiguous against both the auto-declared OUT variable and the real table column. Live-reproduced: `ERROR: column reference "id" is ambiguous` on the very first db-test call. This is the exact defect class CPL-300's own migration header cites as having "made 7 RPCs 100% non-functional" in an earlier checkpoint (bare identifiers inside a function whose own signature shadows a real column name). **Fixed** by adding an explicit table alias (`r0`) before shipping — verified directly in the migration; the function's own comment documents why the alias is load-bearing, not stylistic.

## 6. Schema

`app.customer_portal_quote_requests` (id, tenant_id, account_id, requested_by_auth_user_id, status `check in ('draft','submitted','cancelled','converted')`, cargo_description, origin jsonb, destination jsonb, service_type, requested_pickup_date date, requested_delivery_date date, notes, idempotency_key, submitted_idempotency_key, linked_quotation_id → app.quotations, record_version, created_by, created_at, updated_at, submitted_at, cancelled_at, cancelled_reason). Constraints: status check; origin/destination must be JSON objects; delivery date ≥ pickup date when both set; cancelled_reason mandatory iff status='cancelled'; `linked_quotation_id is not null` iff `status='converted'` (`cpqr_converted_requires_link`, a symmetric row-level guarantee). Unique `(tenant_id, idempotency_key)` and `(tenant_id, account_id, submitted_idempotency_key)`, both partial (not-null). Status-transition trigger mirrors CPL-300's own transition trigger exactly. Combined touch-row trigger (updated_at + record_version) mirrors CPL-300's own exactly. Covering index `(tenant_id, updated_at desc, id desc)` for keyset pagination across every account in scope at once.

Additive rows: `app.document_types`/`app.config_types` get one new `quote_request_attachment` entry each (`ON CONFLICT DO NOTHING`).

## 8. Tier B — recurring defect taxonomy self-check (`docs/standards/RECURRING_DEFECT_TAXONOMY.md` §4)

- **C-01 (idempotency target verified, not just the key)** — `create_customer_quote_request_draft` matches on the full `(tenant_id, idempotency_key)` tuple before returning the existing row (the same tuple the unique index enforces). `submit_customer_quote_request` explicitly checks the row's own `status`/`submitted_idempotency_key` match before treating a call as a no-op retry, and separately checks for a colliding key against a **different** row — live-reproduced both branches in the db-test (idempotent retry returns the unchanged row; a colliding key against a different draft raises `idempotency_conflict`, never silently misattributed). Reviewed separately for a scope gap: `create`'s idempotent short-circuit (line ~329 of the migration) returns the found row *before* re-checking `p_account_id`/scope against it, matching the identical, pervasive, already-adversarially-reviewed convention every other idempotency-keyed create RPC in this 235-migration repository already uses (e.g. `app.initiate_file_upload` itself does the same — idempotency_key uniqueness is scoped per-tenant, not re-authorized on the short-circuit path, since a caller who does not already possess/generate the exact matching key has no way to trigger the short-circuit branch at all). ## 9. Residual/disclosed limitations

- **No REST/GraphQL HTTP route** — service layer + Server Actions + UI only (design decision 10), identical in kind to CPL-300/CPL-301's own disclosure and every Phase 1-7 capability's own standing one.
- **Scan-status gating on submit is not built** — a submitted request may reference an attachment still `pending`/`infected` scan status; the source prompt's own explicit escape hatch names this as acceptable for this checkpoint's file budget. The UI surfaces the real scan status per file so this is visible, not hidden.
- **`app.authorize_file_access` is deliberately not composed from the customer portal** — its own `can_access_record` composition is unconditionally unable to grant a non-uploader account co-worker access (a genuine, pre-existing, cross-cutting Platform primitive gap in PLT-114/PLT-128, not caused by this migration, out of this capability's own allowed file scope to fix). `app.list_customer_quote_request_files` is the correct, sufficient, sanctioned substitute for this capability's own attachment metadata read.
- **No staff-facing "accept this quote request" UI** — `app.link_customer_quote_request_to_quotation` has a real, tested service-layer wrapper with no UI caller yet (C-20, disclosed above) — the Commercial-side surface for this is a natural follow-up, not named in this capability's own chartered UI scope.
- **No client-side unsaved-changes protection** on the draft edit form — matches the established baseline every other Phase 7/8 customer-portal-facing form in this repository (customer-tickets, CPL-300/301) also does not implement; a deliberate, bounded scope decision, not an oversight specific to this checkpoint.
- **`components/domain/customer-portal-nav.tsx` is not extended** — deliberately, to avoid colliding with CPL-301's own concurrently in-flight, uncommitted edits to that file; that component's own header already defers a third tab to "Prompt 309 onward." This capability's routes are fully standalone, reachable directly (and, in the future, linkable from wherever a future checkpoint wires a "quote requests" dashboard card).
- **A new, disclosed KNOWN_ISSUES.md-worthy finding this checkpoint did not itself register** (to avoid a write-collision with CPL-301's own concurrent, uncommitted edit to that shared file): `app.can_access_record`'s `customer_account_ref` branch is unreachable in practice for any `customer_user`-layer principal today, because it unconditionally requires `has_active_tenant_membership`, which no `customer_user` identity's own `app.tenant_user_identities` row ever satisfies. This affects every existing and future consumer of `app.authorize_file_access`/`app.can_access_record` from a customer-portal context, not only this capability. Recommended for the orchestrating session to register as a new `KNOWN_ISSUES.md` entry (suggested class: Medium, Platform/PLT-114) once the shared ledger is free to edit.

## 11. Adversarial testing — live, against a real disposable Postgres 16 database (not reasoned about)

**Finding 1 (CRITICAL, correctness-concurrency) — cross-account IDOR via idempotency-key collision on `app.create_customer_quote_request_draft`.** The idempotent short-circuit (`select ... where tenant_id = p_tenant_id and idempotency_key = p_idempotency_key`) returned whatever row matched BEFORE ever checking that row's own `account_id` against the caller's intended `p_account_id` — live-reproduced: `beta-admin` creates a draft on Account Beta with a real key; `alpha-admin` (zero relationship to Beta) then calls create with the SAME key against Account Alpha and received Beta's full row (cargo, notes) verbatim. The real client key generator (`` `create-quote-${authUserId}-${Date.now()}` ``, `app/(tenant)/[tenantSlug]/customer-quotes/actions.ts`) is deterministic and account-blind, not a private secret, so this is a live, not merely theoretical, exposure — including a genuine non-adversarial data-integrity hazard for a dual-account actor double-clicking/retrying within the same millisecond. This checkpoint's own Tier B self-check (migration header design decision 3, `CPL-302.md:13` original text) explicitly considered and dismissed this exact gap with reasoning the live reproduction disproves. **Fixed at root**: the account-scope check (`p_account_id` must be in `resolve_customer_account_scope`) now runs BEFORE the idempotency pre-check; the pre-check itself now compares the found row's `account_id` against `p_account_id` and raises `idempotency_key_conflict` (never silently returns) on a mismatch — `supabase/migrations/20260801030000_create_customer_portal_quote_requests.sql`, `app.create_customer_quote_request_draft`.
