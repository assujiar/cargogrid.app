## 1. What this checkpoint builds

A configurable reward catalogue with eligibility, stock, effective dates, and customer-safe presentation — the FIFTH Loyalty-domain capability in this repository (ADR-0024 Part D), and the first of Batch 5. One new table, `app.loyalty_rewards` (a draft/published/paused/superseded/archived reward-definition lineage per `(program_id, reward_name)`, mirroring CPL-317's own tier-definition versioning shape widened with the two extra lifecycle states this prompt's own alternative flow requires), plus a second, append-only table, `app.loyalty_reward_stock_reservations` (the real, race-safe stock-reservation ledger, design decision 7 below), 12 new `SECURITY DEFINER` functions, and both a staff admin UI and a read-only customer-facing catalogue/detail UI. Reads (never writes) CPL-316's own `app.loyalty_accounts`, CPL-317's own `app.loyalty_tier_definitions`/`app.loyalty_account_tier_movements` (tier-based eligibility), CPL-318's own `app.loyalty_point_balances` (points-based eligibility), and PLT-128's own `app.files`/`app.file_access_logs` (reward media/terms document). Zero read or write against any CPL-319 table.

**Explicit scope boundary (per this checkpoint's own orchestrating task instruction, disclosed exactly like CPL-319's own identical Finance-handoff disclosure shape):** this checkpoint builds the CATALOGUE only — reward definitions, eligibility criteria, stock/availability CONFIGURATION, effective-dated scheduling, terms, and customer-safe presentation. It does NOT build the redemption/consume-stock transaction that would decrement stock and create a redemption record — that is explicitly `CPL-321`'s own future scope ("Redemption Approval and Fulfillment"). This checkpoint's own job is to model stock as a real, race-safe primitive (`app.reserve_loyalty_reward_stock_unit`, never called by any production path in this checkpoint) so `CPL-321` has something real to compose from, and to compute a live "is this reward currently in stock" read for catalogue display. Recorded as `ISS-2026-131`.

## 2. Design decisions

Full rationale in the migration's own 17-point header comment; summarized here.

1. **Table naming: `app.loyalty_rewards`** (my own call, disclosed) — the shorter of the two names the source prompt itself offered.
2. **`reward_type` vocabulary: `('discount_voucher', 'physical_item', 'service_credit')`** — the source prompt's own literal example, grounded in CPL-319's own `benefit_type` (`cashback`/`discount`/`voucher`), with the forward mapping disclosed but not enforced by a database constraint (CPL-321's own job to actually compose it): `discount_voucher` → CPL-319 `voucher`/`discount`; `service_credit` → CPL-319 `cashback`; `physical_item` has NO CPL-319 counterpart at all (out-of-band fulfillment, not an entitlement-ledger event — a real, disclosed boundary, not a silent gap).
3. **Eligibility criteria: typed columns (`min_tier_id`, `min_points_required`), not a jsonb `eligibility_config`** — chosen over CPL-316's own jsonb precedent because both eligibility dimensions this checkpoint needs are already precisely modeled, typed columns elsewhere in the SAME domain (`tier_rank`, `available`). Both may be null (open reward) or both set (AND-combined — a customer must meet BOTH to be eligible; OR-combined eligibility was considered and rejected as unneeded complexity beyond this checkpoint's own literal ask).
4. **`min_tier_id` references a SPECIFIC `app.loyalty_tier_definitions` row, but eligibility is evaluated by comparing `tier_rank`, never by exact tier-identity match** — tier-definition rows are immutable once created except `status`/`effective_to` (CPL-317's own invariant), so the reference stays a stable rank anchor even after a later republish supersedes it. Fraud holds (`app.loyalty_account_tier_holds`) are deliberately never read here — a hold suppresses tier BENEFIT DISPLAY, it does not retroactively change attained standing.
5. **Effective-dated draft/published/paused/archived lifecycle, ONE lineage per `(program_id, reward_name)`** — mirrors CPL-317's own `(program_id, tier_name)` shape widened with `paused`/`archived` (this prompt's own "admin pauses it" alternative flow). `pause`/`resume`/`archive` are plain status flips on the SAME row (never a new version) — mirrors CPL-317's own supersede-in-place pattern. A second partial unique index, `lr_single_live_per_reward` on `(program_id, reward_name) where status in ('published', 'paused')`, guarantees at most one "live" row per lineage at a time.
6. **`app.resume_loyalty_reward` is a disclosed 6th function, beyond the 5 the task text names literally.** Mirrors CPL-317's own `review_period_days` precedent — the literal ask ("pauses it") is meaningless unless reversible; `publish_loyalty_reward` cannot resume a paused reward (it requires `status = 'draft'`). `resume_loyalty_reward` is the exact structural inverse of `pause_loyalty_reward`, never touching `published_by`/`published_at`.
7. **Stock mechanism (this checkpoint's own most consequential design call) — a real, race-safe, append-only reservation ledger (`app.loyalty_reward_stock_reservations`) plus a LIVE computed aggregate, never a cached counter column.** The task's own instruction offered two named shapes; this checkpoint builds the ledger-plus-real-primitive shape rather than bare `total_stock` exposure, since a bare column would not be "a real primitive... to consume from later" (the scope boundary's own literal requirement). Race-safety comes from a `select ... for update` lock on the TARGET REWARD ROW (never the ledger table) taken before the reservation-total aggregate is read — every call for the same reward serializes on that lock, so two concurrent callers can never both oversubscribe. `stock_available` is NEVER a stored/generated column — always a live `total_stock - coalesce(sum(quantity), 0)` aggregate, evaluated fresh on every read, eliminating the whole "two numbers that could drift" defect class structurally rather than by discipline. Live-proven under a REAL two-process concurrent race (reusing `scripts/db-tests/wms-picking-concurrency-helper.sh`, CPL-318's own established helper). `app.reserve_loyalty_reward_stock_unit` is never called by any production path in this checkpoint — only its own db-test, ready for `CPL-321` to compose (`ISS-2026-131` item 2).
8. **Internal cost/vendor fulfillment data is hidden from customers — STRUCTURALLY, grep-provably.** `internal_cost`/`vendor_ref` exist ONLY on the staff-facing row shape; both customer-facing RPCs' own explicit `returns table (...)` column list never names either — there is no code path that could leak them even by accident, directly asserted in this checkpoint's own db-test via `to_jsonb(...) ? 'internal_cost'`.
9. **Reward media/terms document reuses `app.files`/`app.file_access_logs` directly (PLT-128) — never a second file/upload table.** Mirrors CPL-307/CPL-308's own established "no signed-URL primitive exists in this repository, never fabricate one" discipline exactly: `app.get_customer_portal_loyalty_reward` writes one `app.file_access_logs` row per call when `file_id` is set (`access_type = 'metadata_view'`), returns a clean file's own customer-safe metadata, and a non-clean file's own real, honest `malware_scan_status` with no metadata attached. The LIST rpc never touches `app.files`/`app.file_access_logs` at all (mirrors CPL-308's own "only the per-document access action carries the audit discipline" precedent).
10. **`clock_timestamp()`, never `now()`, EVERYWHERE in this migration — including the two customer-facing read RPCs' own effective-dated visibility filters, a real self-found-and-fixed defect, not an a-priori design choice.** This migration's own first draft used `now()` for `effective_from <= now()`, reasoned (wrongly) as a "single-statement boundary comparison" outside the CPL-315 defect class. Live-caught during this checkpoint's own db-test authoring: `app.publish_loyalty_reward` stamps `effective_from` via `clock_timestamp()` (which advances in real time); `now()` (`= transaction_timestamp()`) is frozen at the enclosing transaction's own start. A caller that publishes a reward and then lists the catalogue WITHIN THE SAME transaction (this checkpoint's own db-test batches both inside one `do $$ ... $$` block, matching a real future caller doing the same for atomicity) saw `effective_from` (stamped moments into that transaction) land after the transaction's own frozen `now()` — spuriously hiding a reward the SAME transaction just published. Fixed at the root by switching both filters to `clock_timestamp()` in both customer-facing RPCs, which advances within a transaction exactly like the `effective_from` value it is compared against. Live regression proof: every eligibility/lifecycle db-test section publishes and immediately lists/gets within the same transaction, and all pass.
11. **Optimistic concurrency: the NULL-bypass fix applied from the start**, on every one of the five version-checked functions (`update_loyalty_reward_draft`/`publish_loyalty_reward`/`pause_loyalty_reward`/`resume_loyalty_reward`/`archive_loyalty_reward`) — every UPDATE's own WHERE clause repeats `and record_version = p_expected_version`, proven with a live regression assertion per function, chained through a single reward's own full lifecycle in this checkpoint's own db-test.
12. **LYL permission mapping, reused from CPL-316/317/318/319 unchanged.** Draft CRUD → `Create`/`Edit`. Publish/pause/resume/archive (governance-grade) → the elevated `LYL:Configure`. Ordinary stock-reservation posting → `LYL:Edit`. Staff reads → `LYL:View`. Customer-facing reads → scoped via `app.resolve_customer_account_scope` only — zero customer-initiated write exists in this checkpoint (a catalogue, not a redemption capability).
13. Every actor-taking function calls `app.assert_actor_is_session_identity` as its own literal first statement; every staff mutate/get-by-id RPC checks `LYL:*` authority BEFORE fetching its target row (C-05).
14. Zero writes against any CPL-316/317/318 table (plain `select` only); zero reads or writes against any CPL-319 table at all — grep-confirmed.
15. RLS: `authenticated` holds ZERO direct grant on either new table. `app.loyalty_reward_stock_reservations` is append-only (no `UPDATE`/`DELETE` grant to any role, not even `service_role`).
16. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public` before final grants.
17. Cursor pagination `(tenant_id, updated_at desc, id desc)` on every list RPC, never `OFFSET`.
