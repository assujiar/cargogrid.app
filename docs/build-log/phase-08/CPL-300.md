## 1. What this checkpoint builds

CPL-300 is the mandatory Layer 4 scope primitive every other Phase 8 capability (301-327) depends on (`docs/build-log/phase-08/00_EXECUTION_INDEX.md` §5/§9: "the sole critical-path root"). It resolves the site-scope open question the kickoff explicitly deferred (00_EXECUTION_INDEX §3 item 5) and implements ADR-0024 Parts A/B for the first time in Phase 8: a new, real many-to-many customer portal account/site membership grant table, a widened scope resolver, and a self-contained Layer-4 account_admin authority chain for self-service invite/suspend/revoke — never a raw RLS reopen, never staff RBAC for ordinary member management.

## 2. Design decisions (cited, not re-derived)

1. **No new "company"/"site" table.** `app.accounts` (COM-155, ADR-0018) stays the one canonical customer/account/site master — flat, self-referencing `parent_account_id`. "Company," "account," and "site" are the same row shape. Per `docs/build-log/phase-07/HRT-287.md` §4 (itself citing ADR-0018), parent → child scope is explicitly non-cascading — a grant on a parent account never implies access to a child. This resolves `00_EXECUTION_INDEX.md` §3 item 5 exactly as that item's own "CLEAR, deliberately left to Prompt 300's own checkpoint" framing anticipated.
2. **`app.customer_portal_account_memberships` is a real, new many-to-many grant table.** `app.principal_memberships.customer_account_ref` (PLT-108) stays exactly as built — the single free-text Layer-4 CHECK-constraint-required marker, never removed/renamed, still a real, additive dependency every write RPC below composes via `app.grant_principal_membership`.
3. **Read access shape follows ADR-0024 Part A exactly**: every customer-facing read is a new `SECURITY DEFINER` RPC, deny-by-default; RLS enabled on both new tables with `authenticated` granted nothing directly (mirrors `app.principal_memberships`'s own convention verbatim, per the prompt's own explicit instruction — a stricter posture than ATW-023's own four tables, which still grant `authenticated` a narrowed `SELECT`).
4. **`app.resolve_customer_account_scope` composes, never re-derives, `app.resolve_customer_owner_account_scope`** (ATW-242, unchanged, still correct for its own already-shipped WMS/inventory callers). See §3 below for the one genuine design refinement this checkpoint's own live testing forced: the new grant table is authoritative for any account it has a row for (any status), the legacy marker only fills gaps.
5. **Write authority is Layer-4-only** (`app.actor_is_active_customer_portal_account_admin`, the one shared authority primitive every write/list RPC composes, mirroring ATW-023 design note 4's "one shared eligibility predicate, never re-derived" shape) — never `app.evaluate_permission`/staff RBAC, except the one deliberate bootstrap exception (decision 6).
6. **`CPT:Create` is a new permission row on the already-existing `CPT` module**, not a new module code — checked `app.entitlement_modules`/`app.permissions` before inventing one, per the task's own instruction. Additive `insert`, the identical technique `20260724300000` (`'View margin'`/`COM`) and `20260727150000` (`'View cost'`/`OPS`) already used.
7. **Revocation takes effect immediately by construction** — every read RPC re-checks `status = 'active'` live, never caching; no separate session-invalidation mechanism built (none exists anywhere in this repository).
8. **Triggers mirror `app.users`/`app.principal_memberships` exactly** — one combined touch-row trigger (updated_at + record_version), the real precedent every prior lifecycle table in this repository uses, not two separate triggers.
9. **Plain, non-partial unique constraint `(tenant_id, auth_user_id, account_id)`**, mirroring `app.users`'s own terminal-on-revoke shape (not `principal_memberships`'s re-grantable partial-unique shape) — matches the given status machine literally (revoked has no outbound transition).
10. **ATW-032 authority-surface sweep compliance planned up front.** Two new authority primitives (`app.resolve_customer_account_scope`, `app.actor_is_active_customer_portal_account_admin`) added to `scripts/db-tests/rbac-enforcement.sql`'s own `base` regex keyword list — mirrors HRT-287/288's own established, disclosed technique exactly. `app.accept_customer_portal_invite` (a raw self-row-identity equality check, the same class `app.get_self_employee`/`app.is_ticket_queue_member` already document) added to that file's own `v_expected` list with a written reason.

## 3. A real defect this checkpoint's own live testing found and fixed before shipping

Live db-test authoring (not paper review) surfaced a genuine design gap: `app.invite_customer_portal_user`/`app.grant_initial_customer_portal_account_admin` both compose `app.grant_principal_membership` (decision 2) to satisfy the Layer-4 CHECK marker, which creates a **legacy-shaped** `app.principal_memberships` row pointing at the same account. A naive `UNION` resolver (legacy branch ∪ new-table-active branch) therefore kept resolving scope for a revoked/suspended account, because revoking the new table's own row never touches that legacy marker (and per decision 4, `app.resolve_customer_owner_account_scope` is deliberately never touched by this migration — it must stay correct for its own already-shipped WMS callers, unaffected by this new capability's own lifecycle).

**Fix (final, shipped shape):** the legacy marker contributes an account to `app.resolve_customer_account_scope`'s result **only if the new grant table has no row at all** for that exact `(tenant_id, auth_user_id, account_id)` triple. Once the new table has any row for a triple — regardless of its status — it is authoritative for that triple; the legacy branch is purely a gap-filler for accounts the new table has never touched (the genuine legacy-only case, e.g. a customer whose sole grant predates this migration, ATW-016/ATW-023-era). Live-verified: a revoked new-table membership now correctly drops out of scope immediately, a legacy-only grant (no new-table row at all) still resolves correctly, and an identity holding both a legacy marker and an active new-table row for the same account resolves to that one account exactly once, never duplicated.

## 6. Schema

`app.customer_portal_account_memberships` (id, tenant_id, auth_user_id, account_id, role `check in ('account_admin','member')`, status `check in ('invited','active','suspended','revoked')`, invited_by/invited_at, accepted_at, granted_by/granted_at, suspended_by/suspended_at/suspended_reason, revoked_by/revoked_at/revoked_reason, record_version, created_at, updated_at). Unique `(tenant_id, auth_user_id, account_id)`. Status-transition trigger mirrors `app.enforce_user_status_transition` exactly (invited→active|revoked; active→suspended|revoked; suspended→active|revoked; revoked terminal). Combined touch-row trigger mirrors `app.touch_principal_membership_row`. Covering indexes: `(tenant_id, auth_user_id, status)` (scope resolution), `(tenant_id, account_id, updated_at desc, id desc)` (admin list).

`app.customer_portal_account_membership_history` (id, membership_id, auth_user_id, tenant_id, account_id, from_status, to_status, reason, requested_by, created_at) — append-only, written by every state-changing RPC. Index `(membership_id, created_at desc)`.

`app.permissions`: one new additive row, `('Create', 'CPT', 'standard', false)`.

## 7. RLS

Both new tables: `enable row level security`; `grant select, insert, update, delete ... to service_role` only — `authenticated` holds **zero** direct grant on either table (mirrors `app.principal_memberships`'s own convention verbatim, stricter than ATW-023's own four RLS-narrowed-but-still-`SELECT`-granted tables). The 8 new RPCs are the only sanctioned access path — live-verified (`scripts/db-tests/customer-portal-scope.sql`'s own defense-in-depth section): a real `set local role authenticated` session raises a genuine `insufficient_privilege` permission-denied error on a raw `select` against `app.customer_portal_account_memberships`, not merely an RLS-narrowed empty result.

**Finding 2 (CRITICAL, security lens) — revocation did not propagate to the legacy `app.principal_memberships` marker this migration itself writes**, so a suspended/revoked customer_user kept live WMS/inventory access (ATW-023's `app.resolve_customer_owner_account_scope`/`app.evaluate_customer_inventory_access`), live ticketing customer-channel access (`app._is_ticket_requester_party`), and live customer-portal entry (`app.actor_holds_customer_user_layer`) — directly contradicting §3/decision 7's own claim that "revocation takes effect immediately by construction... no separate session-invalidation mechanism... none exists anywhere in this repository," which was true only for this migration's own new resolver.
