## 2. Design decisions

Full rationale in the migration's own 18-point header comment; summarized here.

1. **`tier_rank` convention: higher rank = more prestigious tier** (Bronze=1, Silver=2, Gold=3, …) — my own call, disclosed, per the source prompt's own "ordering, lower/higher = your call, disclose it."
2. **Versioning granularity: one draft/published/superseded lineage PER `(program_id, tier_name)`**, not one lineage per whole program — each row IS one version (mirrors CPL-316's own `loyalty_program_rule_versions` collapse, applied one level finer). `unique(program_id, tier_name, version_number)`; at most one draft and one published row per `(program_id, tier_name)` at a time (partial unique indexes); a SECOND partial unique index, `ltd_single_published_rank` on `(program_id, tier_rank) where status = 'published'`, additionally prevents two DIFFERENT tier_name lineages of the same program from both holding the same rank while published — a genuine hardening beyond the prompt's own literal ask.
3. **`to_tier_id` and `tier_definition_version_id` always carry the identical value** in this checkpoint's own flattened tier-identity/version design (design decision 2 — no separate parent "tier identity" row exists for `to_tier_id` to differ against). Both kept as distinct, independently-named columns per the source prompt's own literal schema, for forward extensibility (disclosed as `ISS-2026-127` item 3, not a live gap) — enforced identical by a real table `CHECK` constraint, `latm_version_id_matches_to_tier_check`.
4. **A real, explicit, working downgrade-timing policy** (source prompt's own Alternative flow: "Downgrade occurs at review period end… according to configured policy"). `app.loyalty_tier_definitions.review_period_days integer not null default 0` — a genuine addition beyond the prompt's own literal column list, required to make the policy real (disclosed, mirrors CPL-316's own `eligibility_config` precedent). Every `app.loyalty_account_tier_movements` row stamps its own `next_review_at` (`created_at + review_period_days` of the tier it moves the account INTO) at insertion time — self-contained, immutable once written. Policy: an UPGRADE applies IMMEDIATELY, every call. A DOWNGRADE candidate is gated on the CURRENT movement's own stamped `next_review_at` — before that moment, a safe no-op; at or after, the downgrade applies to whatever is CURRENTLY eligible (never a stepwise walk). `review_period_days = 0` (the default) means no grace — a downgrade applies on the very next call once eligibility drops.
5. **Tier tracking and benefit-hold are deliberately ORTHOGONAL.** Recalculation runs (and posts movements) regardless of whether benefits are held — a fraud investigation freezes redemption of benefits, not the underlying earning-based standing computation. Live-proven in this checkpoint's own db-test (Beta's tier changes Bronze→Silver while held; benefits stay suppressed throughout).
6. **Fraud hold: option (a) from the source prompt's own two named precedents** — an orthogonal `is_held`/`hold_reason`/`held_by`/`held_at`/`released_by`/`released_at` column set on a NEW table this migration owns (`app.loyalty_account_tier_holds`), never altering CPL-316's already-applied `app.loyalty_accounts`. A THIRD shape — an inline `is_fraud_hold_suspended` boolean directly on `app.loyalty_account_tier_movements` (which the source prompt's own literal column list also parenthetically offers) — was considered and REJECTED: movements are append-only, but a hold's own state is inherently current/mutable; an inline column would require mutating a past, posted movement row every time a hold is asserted/released, directly violating the append-only mandate. One row per `loyalty_account_id`, created lazily on first hold. A held account's benefits are suppressed (`{}` plus a customer-safe generic message, NEVER the real internal `hold_reason`) in `app.list_customer_portal_loyalty_tier_cards` — proven live in this checkpoint's own db-test.
7. **`threshold_dimension` is free `text` at the schema level, but the evaluator only implements `'earning_amount_ytd'`** — mirrors CPL-316's own `earning_basis`/`unsupported_earning_basis` shape exactly. Sums `app.loyalty_earning_events.amount` (originals positive, reversals already negative — nets out correctly with no special-casing) from `date_trunc('year', now())` forward. Any OTHER dimension present on a currently-published tier definition of the account's own program raises a clear `unsupported_threshold_dimension` BEFORE any eligible-tier resolution is attempted.
8. **Eligible tier resolution**: the highest-`tier_rank` currently PUBLISHED tier definition whose `threshold_value <= computed amount` (inclusive boundary — exactly AT a threshold qualifies; this checkpoint's own db-test proves both the exactly-at and one-unit-below edges). A program's own published tier set is expected to include a `threshold_value = 0` base tier; if none qualifies, a real `no_eligible_tier_definition` error is raised rather than silently applying nothing (disclosed as `ISS-2026-127` item 2).
9. **Idempotent recalculation is BEHAVIORAL, not idempotency-key-based** — unlike `evaluate_customer_loyalty_earning_for_paid_invoice` (keyed on a real external event), a recalculation call has no natural external event key. Idempotency is achieved by construction: when the eligible tier equals the account's own current tier, the call is a genuine no-op, returning the existing latest movement, never inserting a new row. Concurrency-safety: a real, live `pg_advisory_xact_lock(hashtextextended(p_loyalty_account_id::text, 3))` (salt `3`, mirroring `20260730320000`'s own established per-entity advisory-lock precedent) serializes concurrent recalculation calls for the SAME account.
10. **`app.loyalty_account_tier_movements.created_at` defaults to `clock_timestamp()`, not `now()`** — this table's own ordering ("latest movement per account" resolves current tier) is exactly the self-found CPL-315 defect class (§11.1 of that build log). Applied PROACTIVELY here, not discovered by a failing run — and applied uniformly to every OTHER "record when this happened" timestamp this migration stamps (`loyalty_tier_definitions`' own `created_at`/`updated_at` and its touch-trigger, `loyalty_account_tier_holds`' own `created_at`/`updated_at` and its touch-trigger, every `held_at`/`released_at`/`published_at` assignment). The one deliberate exception: `date_trunc('year', now())`, the YTD window boundary inside recalculation — a frozen, single-transaction-consistent snapshot is the semantically CORRECT choice there.
11. Every actor-taking function calls `app.assert_actor_is_session_identity` as its own literal FIRST statement; every staff mutate/get-by-id RPC checks `LYL:*` authority BEFORE fetching its target row (mirrors CPL-316's own design decision 3 exactly — C-05).
12. **LYL permission mapping, reused from CPL-316 unchanged.** Tier definition draft CRUD → `Create`/`Edit`; PUBLISHING a tier definition and asserting/releasing a fraud hold both map to the elevated `LYL:Configure` (governance-grade actions, mirroring CPL-316's own `publish_loyalty_program_rule_version`/`reverse_loyalty_earning_event`); ordinary recalculation posting maps to `LYL:Edit`.
13. **On-demand/staff-triggered recalculation only** — mirrors CPL-316's own already-accepted `ISS-2026-126` precedent exactly. A real, complete, idempotent RPC exists; only the scheduling mechanism is deferred (disclosed as `ISS-2026-127` item 1).
14. Never mutate a derived/ledger row outside its own owning function, never delete/rewrite a posted `app.loyalty_account_tier_movements` row — no `UPDATE`/`DELETE` grant to `authenticated`.
15. RLS: `authenticated` holds ZERO direct grant on any of the 3 new tables, mirroring CPL-316 exactly.
16. Zero reads or writes against `app.loyalty_accounts`/`app.loyalty_earning_events` beyond plain `SELECT` — grep-confirmed before this file was finalized.
17. Per `ERR-2026-004`: this migration carries its own explicit `revoke execute on all functions in schema app from public` statement before its final grants.
18. **A live-found-and-fixed defect during this checkpoint's own db-test authoring**: `app.get_loyalty_account_tier_state`'s own `RETURNS TABLE(...)` clause implicitly declares `loyalty_account_id`/`is_held`/`hold_reason`/`held_by`/`held_at` as PL/pgSQL variables in scope; its own body originally referenced those names bare inside a `WHERE` clause against tables carrying identically-named columns, producing a genuine `column reference "loyalty_account_id" is ambiguous` error at call time (caught live, in a scratch database run, before this checkpoint reported done — see §9.1 below). Fixed at the root: every such reference is now qualified with an explicit table alias (`m.loyalty_account_id`, `h.loyalty_account_id`, etc.). `app.list_customer_portal_loyalty_tier_cards` (the OTHER `RETURNS TABLE` function in this migration) was independently audited and confirmed already fully alias-qualified throughout — no live defect there.

### 9.1 Self-found-and-fixed defects (disclosed, per this batch's own standing "do not report done on a single passing run" discipline)

1. **`app.get_loyalty_account_tier_state` ambiguous-column defect** (a real code bug, migration design decision 18) — `RETURNS TABLE(loyalty_account_id uuid, ..., is_held boolean, hold_reason text, held_by text, held_at timestamptz)` implicitly declares those five names as PL/pgSQL variables in the function's own scope; the function's original body referenced `loyalty_account_id` bare inside two `WHERE` clauses against `app.loyalty_account_tier_movements`/`app.loyalty_account_tier_holds` (both of which carry that exact column), producing a live `column reference "loyalty_account_id" is ambiguous` error the very first time this function was called through `app.list_loyalty_account_tier_movements`'s own db-test section. Root-caused by direct `\sf` inspection of the deployed function against the scratch database, fixed by qualifying every such reference with an explicit table alias (`m.tenant_id`/`m.loyalty_account_id`, `h.tenant_id`/`h.loyalty_account_id`). The sibling `RETURNS TABLE` function in this migration, `app.list_customer_portal_loyalty_tier_cards`, was independently audited and confirmed already fully alias-qualified throughout its own CTEs and main query — no defect there.
2. **Test-authoring bug, not a code defect** — the original db-test fixture gave Beta (the fraud-hold test's own subject) a $500 invoice, expecting it to cross Silver's threshold and prove "recalculation still applies while held" (design decision 5). But by the time that test section runs, an EARLIER test section (proving design decision 4/10's own "a tier-definition version change does not retroactively rewrite a historical movement") had already published a new Silver v2 with its own threshold raised to 600 in the SAME shared "Tier Rewards" program — a real, intentional, already-committed change by that point in the script's own linear sequence. Beta's $500 therefore no longer crossed the CURRENT (600) threshold, so recalculation correctly produced a no-op rather than the test's own (now-stale) expectation of an upgrade — the code was correct throughout; the test's own expected value was wrong. Root-caused via a manual, step-by-step reproduction with `RAISE NOTICE` instrumentation against the surviving scratch database (the harness deliberately does not drop the database on a mid-script failure, since cleanup is the LAST line and `set -euo pipefail` stops the script at the first non-zero `psql` exit). Fixed by raising Beta's own fixture invoice to $700 (clearly above 600) and updating the post-upgrade benefits assertion to match Silver v2's own actual benefits (`{"free_shipping": true, "lounge_access": true}`, not v1's `{"free_shipping": true}`) — both real, deterministic corrections, not a loosened assertion.

### 9.2 Adversarial testing — live, against a real disposable Postgres 16 database (not reasoned about)

1. **(a) Threshold-edge correctness** — a dedicated, isolated Edge account proves 999 (one unit below the 1000 Gold threshold) does NOT qualify for Gold, and 1000 (exactly at the threshold) DOES, with the evaluation snapshot's own `computed_amount` asserted at each step. The same exactly-at-threshold pattern is independently reproduced for Alpha's own Bronze→Silver (500) and Silver→Gold (1000) upgrades.
2. **(b) Tier-definition version change does not retroactively rewrite a historical movement** — publishing Silver v2 (threshold raised 500→600) leaves Alpha's already-recorded downgrade-to-Silver movement's own `to_tier_id`/`tier_definition_version_id`/`evaluation_snapshot` byte-for-byte unchanged; Silver v1's own `tier_rank`/`threshold_value` are never mutated, only `status`/`effective_to`; a NEW recalculation afterward correctly re-evaluates against the CURRENT (v2) threshold.
3. **(c) Idempotent recalculation** — Alpha's first recalculation (sum=0) produces exactly one `initial` movement; a second call with nothing changed returns the IDENTICAL row, row count unchanged; the same idempotent-no-op proof is repeated after the Gold→Silver downgrade.
4. **Downgrade grace-period policy** — a downgrade candidate is a safe no-op while inside Gold's own 30-day review window (verified: same movement id, row count unchanged); once the window is simulated as elapsed (a direct fixture-level `next_review_at` backdate, never through the RPC, which never lets a caller set that field directly), the SAME recalculation call performs the downgrade to whatever is CURRENTLY eligible; the original Gold movement row's own `movement_type` stays `upgrade` (append-only — the downgrade is a NEW row).
5. **(d) Fraud hold** — Beta's benefits are real (`{"newsletter": true}`) and not suspended before any hold; hold requires `LYL:Configure` (Plain User denied) and a non-empty reason; after hold, the customer-facing card shows `{}` benefits and a GENERIC customer-safe message that never contains the real internal hold_reason ("Suspected fraud…"); a repeat hold with a DIFFERENT reason is a no-op preserving the ORIGINAL reason; recalculation (Bronze→Silver, on a $700 invoice crossing Silver v2's 600 threshold) still applies normally while held (orthogonality, design decision 5) — the card shows the NEW tier name but benefits remain suppressed; release restores the real Silver v2 benefits (`{"free_shipping": true, "lounge_access": true}`); releasing a NEVER-held account is rejected (`loyalty_account_tier_hold_not_found`); releasing an already-released account is a safe idempotent no-op.
6. **`app.loyalty_account_closed`** — recalculation is rejected once the underlying loyalty account (CPL-316's own table) is closed.
7. **`no_eligible_tier_definition`** — a program with no base (`threshold_value = 0`) tier raises a real error for a zero-earning account rather than silently applying nothing.
8. **`unsupported_threshold_dimension`** — a published tier definition using a dimension this checkpoint does not implement is rejected loudly, before any eligible-tier resolution is attempted, regardless of the account's own actual earning sum.
9. **`tier_rank_conflict`** — a second tier_name attempting to publish at an already-published rank is rejected; `draft_already_exists` — two open drafts for the same tier_name; `stale_version` on both update and (implicitly, via the same lock-then-compare shape) publish.
