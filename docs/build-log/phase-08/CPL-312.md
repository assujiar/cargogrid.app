# CPL-312 — Payment Visibility

**Prompt ID:** `CG-S13-CPL-014` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/312_PAYMENT_VISIBILITY_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty), Batch 3 · **Status: `VERIFIED`** (Batch 3 Tier C review closed — see §14)

## 1. What this checkpoint builds

CPL-312 gives a scoped customer-portal finance user read-only visibility into a specific invoice's own payment/allocation status (paid/partial/open, whether the balance is on hold, and which receipts have been applied against it) plus a standalone list of the customer's own receipts — while Finance retains exclusive ownership of posting, allocation, reversal, and reconciliation. It depends directly on CPL-311 (Invoice and Billing Visibility, this same batch, implemented immediately before this prompt) and REUSES that checkpoint's own `app.evaluate_customer_portal_invoice_access` gate primitive and `app._resolve_customer_portal_invoice` internal gate+fetch helper by direct call — neither is re-derived, neither is `CREATE OR REPLACE`d.

## 2. Design decisions (cited where given by the orchestrating task; disclosed where this checkpoint had to resolve something itself)

1. **Gate reuse, not re-derivation — the batch's own explicit instruction for this prompt.** `app.get_customer_portal_payment_status` calls `app._resolve_customer_portal_invoice` (CPL-311's own internal, `service_role`-only gate+fetch adapter) DIRECTLY — the identical anti-enumerating `record_not_found` shape, the identical `app.evaluate_customer_portal_invoice_access` gate, composed rather than copied. The smallest shared primitive genuinely available (the internal helper) is composed rather than CPL-311's own public sibling RPC (`app.get_customer_portal_invoice_payment_status`), because that public RPC deliberately never returns `ar_open_item_id` — exactly the internal linkage this migration's own join needs (server-side only, never returned to the client) to reach `app.finance_receipt_allocations`. The AR-open-item lookup itself (`status`/`original_amount`/`open_amount`/`is_held`) is therefore duplicated from CPL-311's own sibling RPC's body (~10 lines) rather than composed by calling that public RPC a second time — a small, disclosed duplication in exchange for a strictly smaller dependency surface. `app.list_customer_portal_receipts` calls `app.resolve_customer_account_scope` (CPL-300) directly, the same widened resolver every other Phase 8 list RPC composes.
2. **The invoice<->payment link is a real two-hop join — confirmed by direct DDL read before writing a line of this migration, not assumed.** `app.finance_invoices.ar_open_item_id` -> `app.finance_ar_open_items.id` <- `app.finance_receipt_allocations.ar_open_item_id` <- `app.finance_receipt_allocations.receipt_id` -> `app.finance_receipts.id`. There is no direct receipt->invoice foreign key anywhere in this schema.
3. **MANDATORY PATTERN, applied from the first draft**: both public functions call `app.assert_actor_is_session_identity` as their own literal first statement, never relying solely on the transitive check already inside the composed helpers.
4. **`bank_account_label` is never selected anywhere in this migration** — structurally, not merely filtered. Neither function's own `RETURNS TABLE`/jsonb payload shape has any column or key capable of carrying it.
5. **`payer_name` — an explicit, disclosed judgment call, not a silent guess.** `app.finance_receipts.payer_name` is free text with no structural marker distinguishing "the customer's own name" from "a real third party's name" (a factor, guarantor, forwarder, or an affiliated-but-distinct entity) — confirmed by direct DDL read: a bare nullable `text` column, no `payer_type`/`is_self_pay` flag, no FK to `app.accounts`. Because there is no reliable way to prove a GIVEN row's `payer_name` is safe, `payer_name` is HIDDEN GLOBALLY from both new functions — never returned, regardless of whether a given row's value happens to match the customer's own name. This is the conservative reading of "hide payer_name only if it can reveal a third party's identity": treating every row identically is the only choice that cannot leak a third party's identity by mistake. `receipt_reference` (a bank/transaction reference the customer would recognize from their own remittance) is kept — it identifies the payment, not a third party.
6. **`hold_reason` is never exposed — mirroring CPL-311's own already-established precedent for the identical column.** `hold_reason` is free text written by Finance staff with no CHECK-constrained vocabulary to safely generalize. `app.get_customer_portal_payment_status` surfaces only the boolean `is_held` — a real, honest, customer-safe "this balance is on hold" signal — never the raw reason text. The existing invoice detail page (CPL-311) already renders a "Payment on hold" banner from this exact boolean; this checkpoint adds no second masking scheme.
7. **There is no `reconciliation-status` column anywhere in this schema — confirmed by direct DDL read of `app.finance_receipts`/`app.finance_receipt_allocations`/`app.finance_ar_open_items` before writing a line of this migration.** The source prompt's own §13/§15/§22 use the phrase loosely; this migration maps it to the real status values that exist, stated explicitly rather than inventing a column:
   - `app.finance_receipts.status` (`captured`/`void`) — whether the receipt itself is a live, uncancelled cash receipt.
   - `app.finance_receipt_allocations.status` (`applied`/`reversed`) — whether a specific allocation currently counts. `app.get_customer_portal_payment_status` includes ONLY `status = 'applied'` rows in its own `allocations` array — a `reversed` allocation is, by construction, no longer part of the invoice's real payment history (`app.finance_ar_open_items.allocated_amount` is already decremented the moment a reversal posts), so surfacing it would show the customer money that no longer counts. Live-proved in this checkpoint's own db-test (a genuinely reversed allocation on the exact same AR open item as an applied one is created, and confirmed absent from the returned array — §11 below).
   - `app.finance_ar_open_items.status` (`open`/`partial`/`paid`) plus `is_held`/`hold_reason` — the real source for the source prompt's own "paid/partial/unpaid" and "blocked" UI language, reused verbatim from CPL-311's own identical mapping.
   - "Pending reconciliation" (source prompt §22 alternative flow) has no dedicated status value anywhere in this schema either — the closest honest equivalent this migration's own data can support is a receipt whose `unapplied_amount > 0` (cash captured, not yet, or not fully, applied). `app.list_customer_portal_receipts` returns `unapplied_amount` precisely so the UI can render that state honestly, without inventing a status value the database does not have.
8. **Both real receipt statuses (`captured`/`void`) are portal-visible on the list — a deliberate divergence from CPL-311's own invoice status filter, disclosed here, not a copy-paste of that filter.** CPL-311 hides `draft`/`submitted`/`approved` invoices because those are genuinely not-yet-real financial obligations. A receipt has no equivalent pre-capture lifecycle stage — `app.finance_receipts.status` defaults straight to `'captured'` on insert and only ever transitions to `'void'` as a later correction. A voided receipt genuinely happened and was later voided — showing it (with its own real, unmistakable `void` badge) is honest disclosure, not a leak of an unfinalized figure, the same reasoning CPL-311 itself already applied to keep a voided INVOICE visible rather than hidden.
9. **jsonb payload keys inside the `allocations` array are camelCase, not snake_case** — a deliberate, precedented divergence from this migration's own top-level `RETURNS TABLE` columns (which stay snake_case, matching every other Phase 8 RPC's plain column-projection convention). Mirrors an already-established, non-Phase-8 precedent in this exact repository: `app.get_billing_readiness_detail` (`20260728140000_create_operations_billing_readiness.sql:207`) already builds a `jsonb_agg(jsonb_build_object('checklistItemId', ...))` payload with camelCase keys for the identical reason — a synthesized jsonb payload has no underlying column of its own to name after, so choosing the TypeScript-side field name directly at the SQL layer avoids a redundant remap step at the contract boundary.
10. **RPD-032 ("payment documents follow scan and signed URL rules") — a disclosed gap, not fabricated, mirroring CPL-311's own identical disclosure for invoice PDFs.** Checked directly before writing this migration: `app.finance_receipts` carries no `file_id`/attachment column of any kind (FIN-198) — there is no receipt-attachment upload path anywhere in this repository to compose. CPL-308's own Document Center (already applied, Batch 2, `VERIFIED`) recognizes a fixed 4-value `p_source_module` enum (`quote_request`/`epod`/`invoice`/`ticket`); `receipt` is not a recognized value there, and this checkpoint does not add one — doing so would require a `CREATE OR REPLACE` against an already-applied, already-`VERIFIED` migration's function, forbidden by `AGENTS.md`'s "never edit an applied migration" rule, and is genuinely out of this prompt's own bounded scope (a receipt-attachment upload pipeline is a capability-sized addition in its own right). No signed URL, no scan-status field, no fabricated attachment list is invented anywhere in this migration. Not registered as a new `KNOWN_ISSUES.md` entry — this is the identical class of disclosed, non-blocking tooling gap CPL-311 already recorded inline (its own design decision 12) without a dedicated ledger entry, and CPL-308's own `invoice`/`ticket` placeholder gap already covers the general "not every document source is wired yet" shape.
11. **No idempotency-key parameter anywhere** — both functions are pure, `stable` reads.
12. **Cursor pagination (`tenant_id`, `updated_at desc`, `id desc`), never `OFFSET`** — `app.list_customer_portal_receipts` mirrors `app.list_customer_portal_invoices`'s own established cursor shape exactly. One new covering index, `finance_receipts_tenant_updated_id_idx` on `app.finance_receipts (tenant_id, updated_at desc, id desc)`, added inline (mirrors CPL-300's own "inline covering index, not a companion migration" precedent) — FIN-198's own two indexes do not cover this ordering.
13. **`scripts/db-tests/rbac-enforcement.sql` compliance, verified by direct analysis of that file's own closure sweep before writing this migration, then live-confirmed (§12 below).** The `base` CTE already recognizes the literal substring `resolve_customer_account_scope`. `app.list_customer_portal_receipts` calls it directly (`base` directly). `app.evaluate_customer_portal_invoice_access` (CPL-311) is already in `base`; `app._resolve_customer_portal_invoice` (CPL-311) lands in `closure` via one recursion step; `app.get_customer_portal_payment_status` (this migration) calls `app._resolve_customer_portal_invoice` directly, landing IT in `closure` via one more recursion step — zero edit to that shared file required. Both new functions are `stable`, exempting both from the separate side-effecting-actor-authority sweep (`provolatile = 'v'` only).
14. **RLS on `app.finance_receipts`/`app.finance_receipt_allocations`/`app.finance_ar_open_items` is UNCHANGED BY THIS MIGRATION** — confirmed by direct read of each table's own already-applied RLS `SELECT` policy: `has_active_tenant_membership(tenant_id) or is_supreme_admin()` — no owner/customer branch of any kind, so a `customer_user` principal is already unconditionally denied at the raw-table layer. This migration's two new functions are the only sanctioned customer-facing access path added.
15. **REST/GraphQL transport (ADR-0024 Part C):** service layer + Server Component fetch + UI only, no `app/api/` HTTP route — identical in kind to CPL-300..311's own disclosed residual gap.
16. **UI: no new "Payments" tab component — a new section on the already-existing invoice detail page, plus a standalone `customer-receipts` list route, both a pure widening of established patterns.** The source prompt's own §21 main flow ("customer finance user opens an invoice and sees payment allocation and receipt status") is satisfied by adding a "Payments & receipts" section to `app/(tenant)/[tenantSlug]/customer-invoices/[invoiceId]/customer-invoice-detail-panel.tsx` (CPL-311, this batch) rather than building a literal tab-widget component this repository has no existing pattern for — the existing detail page is already organized as stacked `<section>` blocks (Charges & tax lines / Download / Dispute), and this checkpoint's own new section follows that same house style. `app/(tenant)/[tenantSlug]/customer-receipts/` is a new standalone route carrying `CustomerPortalNav` (widened `current` union, a pure addition mirroring CPL-310/311's own identical widening) — no per-receipt detail sub-route, mirroring CPL-308's own Document Center "list with filters, no detail sub-route" precedent, since a receipt's own allocation-to-invoice detail is already better surfaced from the invoice side, and a receipt can apply to more than one invoice so there is no single natural per-row link target.
17. **§22 alternative flow ("pending reconciliation... submit proof through document/ticket workflow") reuses the SAME existing dispute link CPL-311 already built, rather than a second, near-duplicate ticket-linking entry point.** The invoice detail page already has a "Questions about this invoice?" section with a working deep link into the customer-ticket flow, auto-linked via the already-`VERIFIED` HRT-292 `app.ticket_links` mechanism. A payment-specific question on that SAME invoice has no need for a second link; the new "Payments & receipts" section links down to it. No new ticket-link entity type is added (there is no `receipt` `ticket_links.entity_type` value, and adding one would require editing HRT-292's own already-applied migration, forbidden).
18. **The invoice's own "Download invoice data (JSON)" export (CPL-311) is deliberately left unmodified** — it still composes exactly the three CPL-311 read RPCs it always has. Extending it to also embed this checkpoint's own allocation detail is optional polish with no explicit instruction behind it; leaving it alone avoids touching CPL-311's own already-`COMPLETED` file and its own existing test coverage for a feature this prompt did not ask for.
19. Per `ERR-2026-004` (`docs/runtime/ERROR_LEDGER.md`): this migration carries its own explicit `revoke execute on all functions in schema app from public` statement before its final grants.

No table is created, altered, or dropped by this migration beyond the one new index (decision 12). No existing RLS policy is touched, and no pre-existing function is `CREATE OR REPLACE`d — grep-confirmed zero such statement anywhere in the migration file.
