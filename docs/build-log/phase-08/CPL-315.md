## 1. What this checkpoint builds

CPL-315 is overwhelmingly an additive extension of CPL-300's own already-`VERIFIED` invite/accept/status-management machinery (`supabase/migrations/20260801010000_create_customer_portal_account_scope.sql`, read in full, not edited). CPL-300 already shipped invite/accept/suspend/revoke; it deliberately shipped no role-update RPC and no access-review surface, disclosing both as this prompt's own chartered scope (§9 of that build log). This checkpoint closes both gaps, plus wires the first real invite/role-change/revoke UI onto CPL-300's own already-tested-but-never-called service-layer wrappers:

3. **The first real UI** for invite/role-change/suspend/reactivate/revoke/pending-invites/access-review — a new customer-facing route, `app/(tenant)/[tenantSlug]/customer-portal-users/`, composing both this checkpoint's own new mutation wrappers and CPL-300's own pre-existing (previously UI-less) `inviteCustomerPortalUser`/`setCustomerPortalAccountMembershipStatus`.

## 2. Design decisions (full rationale in the migration's own 12-point header comment; summarized here)

1. **Gap 1 — role update**, mirroring `app.set_customer_portal_account_membership_status`'s own shape exactly (same authority primitive, `app.actor_is_active_customer_portal_account_admin`, never re-derived; same optimistic-concurrency shape; audit write into the existing `app.customer_portal_account_membership_history` table — no new role-history table).
2. **Role-hierarchy finding, checked and disclosed per this task's own explicit instruction, not assumed.** `app.customer_portal_account_memberships`'s own `cpam_role_check` CHECK constraint (read directly from the applied CPL-300 migration, and re-confirmed live/structurally by this checkpoint's own db-test) admits EXACTLY two values, `account_admin`/`member` — a flat, two-level model, not a ranked hierarchy. Every write RPC in this whole capability already requires the caller to hold an ACTIVE `account_admin` row — the higher of the two values — so a caller who reaches this authority check at all already holds the maximum authority this role model has. There is no third, higher role to escalate into, so no additional "may not grant more authority than my own" check is added — it would defend against a case this schema cannot construct. Mirrors `app.invite_customer_portal_user`'s own already-shipped, already-accepted behavior of letting an account_admin invite a brand-new member at EITHER role value.
3. **A genuine, disclosed hardening beyond the literal mirror: the last-active-account_admin guard.** Live reasoning while designing decision 1 surfaced that nothing stops the sole active account_admin on an account from demoting themselves, after which the account has no self-service recovery path (`app.grant_initial_customer_portal_account_admin` is a no-op once any row already exists for that identity+account — it does not promote it). `app.update_customer_portal_account_membership_role` rejects such a demotion (`last_account_admin`). Race-safety: the demotion branch locks the FULL active-admin set for the account (`for update`) before counting, not merely the target row already locked — closing a genuine TOCTOU window a bare `count()` would leave open (two concurrent demotions of two different admins on a 2-admin account could each read "one other admin remains" before either commits). Disclosed, not claimed load-tested: this checkpoint's own db-test proves the guard's sequential correctness, not a genuine multi-process concurrent race (that infrastructure is `scripts/load-tests/`'s own dedicated job, ATW-024, not an ordinary capability db-test's).
4. **Gap 2 — access review: a NEW, SEPARATE table, never an `ALTER TABLE`** on CPL-300's own applied `app.customer_portal_account_memberships`. Disclosed reasoning: a new additive table carries zero risk of colliding with that table's own already-`VERIFIED` shape, its status-transition trigger, or any already-shipped caller's `select m.*` assumption; it is also the more correct model for "record a review action" read literally — an access review is naturally append-only evidence (each occasion is its own row), which a bolt-on `last_reviewed_*` column set could not represent (it could only ever show the most recent review, never the full history).
5. **Access-review outcome is a closed, two-value enum** (`confirmed_appropriate`, `flagged_for_follow_up`) — an ATTESTATION, never itself a corrective action. A reviewer who concludes a change is warranted performs it through the existing, unmodified role-update/status RPCs, kept deliberately separate and independently audited.
6. **Idempotency, this batch's own mandatory pattern, applied to both new mutating RPCs.** `update_customer_portal_account_membership_role` is idempotent by construction (identical target role for an already-at-that-role membership is a genuine no-op — no touch-row bump, no spurious history entry). `record_customer_portal_account_membership_access_review` is a genuine append-only event, so it carries a real, caller-supplied, NOT NULL `unique (tenant_id, idempotency_key)` constraint (never nullable/partial — this batch's own ledger-grade mandate), the scope/authority check running BEFORE the idempotent short-circuit SELECT, and a real `exception when unique_violation` handler around the INSERT — mirrors `app.submit_customer_profile_change_request`'s (CPL-314) established shape, including verifying the full target tuple (`membership_id`) on a key match, not only the key (C-01).
7. **Every actor-taking function calls `app.assert_actor_is_session_identity` as its own literal first statement** — applied to all four new functions from the first draft, including both reads (mirroring CPL-300's own Finding-1 Tier C fix for exactly this class).
8. **Disclosed, NOT fixed here (forbidden — applied migration): the identical last-account_admin gap this checkpoint closes for `update_role` also exists, unfixed, in CPL-300's own already-`VERIFIED` `app.set_customer_portal_account_membership_status`.** Registered as `ISS-2026-125` rather than silently left.
9. **Anti-enumeration (C-05), a disclosed continuation of an already-accepted precedent, not a new regression.** Both new mutation-by-id RPCs fetch their target membership (to learn its own `tenant_id`/`account_id`, required to run the authority check at all) before the authority check, raising a distinguishable `customer_portal_membership_not_found` vs. `insufficient_authority` — the identical shape CPL-300's own `set_customer_portal_account_membership_status`/`accept_customer_portal_invite` already have, already reviewed and accepted as `ISS-2026-116` (Low, `OPEN`): `p_membership_id` is a random, non-guessable UUID a caller can only ever have via legitimate visibility.
10. **Two new read RPCs, both composing `app.actor_is_active_customer_portal_account_admin` directly — automatically covered by `scripts/db-tests/rbac-enforcement.sql`'s own ATW-032 base-regex closure sweep with ZERO edit to that shared file required**, verified live in this checkpoint's own scratch-database run (not merely assumed) — mirrors CPL-314's own identical "no edit required" outcome.
11. **No REST/GraphQL HTTP route, no MFA/step-up-auth mechanism added** — both standing, repository-wide gaps, identical in kind to CPL-300's/CPL-314's own prior disclosures. See §11 below and `ISS-2026-125`.
12. Per `ERR-2026-004`: this migration carries its own explicit `revoke execute on all functions in schema app from public` statement before its final grants.

**Invite-by-`authUserId` UX limitation (disclosed, not novel to this checkpoint):** `app.invite_customer_portal_user` (CPL-300) takes `p_auth_user_id` directly, not an email — an already-established repository-wide convention (`app.invite_user`, PLT-110, has the identical shape, and grep-confirmed has zero live UI caller anywhere for the same reason). No email-to-`auth_user_id` resolution mechanism exists anywhere in this repository. This checkpoint's own invite form therefore asks the account admin for the target user's already-known CargoGrid account ID (a UUID), with an explanatory label — the same accepted simplification every prior invite-shaped RPC in this repository already carries, not a new gap this checkpoint introduces.

## 11.1 Post-implementation defect — non-deterministic "most recent review" resolution, self-found and fixed

This session's own container was restarted mid-batch by the host environment shortly after this checkpoint's own implementation completed. Before trusting the on-disk output, the orchestrating session re-ran `scripts/db-tests/customer-user-management.sql` against 3 independently fresh, fully-migrated disposable databases (not the single run this build log's §9 originally reported) — **2 of 3 fresh runs failed**, always at the same assertion:

```
psql:scripts/db-tests/customer-user-management.sql:550: ERROR:  assertion failed: expected alpha-member's own row to show
its MOST RECENT review (flagged_for_follow_up, the second review occasion), got last_review_outcome=confirmed_appropriate
```

**Root cause:** `app.list_customer_portal_account_memberships_for_access_review`'s LATERAL join resolves the "most recent review" via `order by rr.reviewed_at desc, rr.id desc`. The test fixture records two reviews for the same membership inside one `do $$ ... end $$` block — a single implicit transaction — so both rows' `reviewed_at` (`default now()`) were byte-identical, since `now()` is frozen at transaction start, not per-statement. The tie then fell to `id desc`, a random `gen_random_uuid()` value carrying no insertion-order signal, making "most recent" a coin flip. A genuine ordering defect in this checkpoint's own schema, not an artifact of the test harness or the restart.

**Fix (root cause, not a query-side patch):** `app.customer_portal_account_membership_access_reviews.reviewed_at`'s default changed from `now()` to `clock_timestamp()` — the standard PostgreSQL idiom for exactly this class of problem, since `clock_timestamp()` advances on every call regardless of transaction boundaries, guaranteeing two reviews recorded in the same transaction still get distinct, correctly-ordered timestamps. The `INSERT` in `app.record_customer_portal_account_membership_access_review` relies on the column default and needed no change. `created_at` (audit-trail insertion time, never used for ordering) deliberately keeps `now()`.

**Independently re-verified after the fix:** 5 further fresh-database runs of `scripts/db-tests/customer-user-management.sql`, all exit 0, `ALL PASSED`, zero failures (up from 1-of-3 before). `pnpm run typecheck`/`pnpm run lint` re-confirmed clean (0 errors each, no new files affected by this migration-only fix). This checkpoint's own status remains `COMPLETED`, not `VERIFIED` — this fix is disclosed here as the honest record of what was actually found and repaired before Batch 4's own Tier C review runs, not presented as if the original implementation pass had already caught it.
