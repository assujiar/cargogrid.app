# CPL-321 — Redemption Approval and Fulfillment

**Prompt ID:** `CG-S13-CPL-023` · **Package document:** `docs/ai-agent-build-prompt-package/13-phase-08-customer-portal-loyalty/321_REDEMPTION_APPROVAL_FULFILLMENT_PROMPT.md` · **Phase:** 8 (Customer Portal and Loyalty) · **Status: `VERIFIED`** (Batch 5's own Tier C review, `CPL-320..323`, closed — see §14)

Second prompt of Batch 5 (`CG-S13-CPL-022..025`, Prompts 320-323), run as its own small, single-agent workflow — not batched with the rest of Batch 5 — specifically to limit the amount of in-flight work lost if the container is restarted mid-run, the same strategy CPL-317/318/319/320 already used successfully. `CPL-320` (Reward Catalogue) just landed, status `COMPLETED`, not yet `VERIFIED` — this checkpoint's own primary upstream dependency, read in full (migration + build log) before writing any code, per this task's own explicit mandatory-reading instruction.

## 1. What this checkpoint builds

A real, transactional redemption request/approval/fulfillment capability — the SIXTH Loyalty-domain capability in this repository (ADR-0024 Part D). Two new tables, `app.loyalty_redemptions` (the mutable redemption-request record, its own `pending_approval → {approved-shaped-composition}/rejected/cancelled → fulfilling → fulfilled/failed` state machine) and `app.loyalty_redemption_events` (append-only lifecycle audit log, mirrors `app.loyalty_benefit_entitlement_events` exactly), plus one additive, disclosed `ALTER TABLE` widening CPL-320's own `app.loyalty_reward_stock_reservations` CHECK constraint (`quantity > 0` → `quantity <> 0`, design decision 8 — never editing CPL-320's own applied migration file), and 13 new functions (11 public RPCs, 2 private, no-grant helpers). Composes, at the actual moment of redemption, CPL-320's own `app.reserve_loyalty_reward_stock_unit` (its first production caller, closing `ISS-2026-131` item 2), CPL-318's own `app.consume_loyalty_points_fifo`, and CPL-319's own `app.issue_loyalty_benefit_entitlement` — never a second, parallel mechanism. Reads (never writes) CPL-316/317's own tier/hold tables and CPL-318's own point-balance table for eligibility/fraud-hold re-validation.

**Explicit scope boundary and the checkpoint's own central architectural resolution:** composing two real, unmodifiable, staff/system-only (`LYL:Edit`-gated) primitives from a genuinely customer-initiated flow is not directly possible without either widening their own RBAC gate (forbidden by ADR-0024 Part B) or inventing a new system-identity mechanism (out of this prompt's own bounded scope). This checkpoint's own resolution — a real, literal "auto-approve inline" path for a `discount_voucher` reward submitted by an actor who independently holds `LYL:Edit` (staff/system), and a graceful `pending_approval` fallback for a genuine, unassisted `customer_user` submission of any reward_type — is worked out in full, with live-tested evidence, in the migration's own design decision 5, and disclosed as `ISS-2026-132`.

## 2. Design decisions

Full rationale in the migration's own 18-point header comment; summarized here.

1. **`points_cost = min_points_required`** (my own call, disclosed) — the reward's own eligibility threshold doubles as its redemption cost, the natural, simplest reading, and the one CPL-320's own catalogue UI copy already implies ("Requires 500 points (you have 650)"). A null `min_points_required` reward costs 0 points. Chosen over adding a new, separate `points_cost` column to avoid unnecessary schema surface on a table this checkpoint does not own.
2. **`reward_type = 'discount_voucher'` → CPL-319 `benefit_type = 'voucher'`** (mints a real, hash-only-stored redeemable code), never `'discount'` — CPL-320's own design decision 2 explicitly deferred this choice to this checkpoint; a minted code matches the reward_type's own literal name more precisely.
3. **`physical_item`/`service_credit` fulfillment tracking is genuinely new, first-of-its-kind scope** — no shipment/service-credit-application integration exists anywhere in this repository for Loyalty to hook into. A real `fulfillment_status` column (`not_applicable`/`pending`/`in_fulfillment`/`fulfilled`/`failed`) lives directly on `app.loyalty_redemptions`, transitioned exclusively by this checkpoint's own new RPCs — no external system call, no fabricated shipment record. `discount_voucher` is always `not_applicable` (entitlement issuance IS the fulfillment moment for that type).
4. **Discount-voucher entitlement `value_amount = internal_cost` (staff-only, CPL-320 design decision 8), `currency` = the tenant's own resolved `default_currency` (`app.resolve_tenant_locale`, PLT)** — a genuinely new composition. CPL-320's own reward row has no dedicated customer-facing monetary value column; `internal_cost` is the only numeric, monetary-shaped field available. A misconfigured reward (null/non-positive `internal_cost`) is rejected with a distinct, customer-safe `reward_redemption_unavailable` error rather than a fabricated value.
5. **This checkpoint's own most consequential design decision — the auto-approve/pending-approval split.** `app.submit_loyalty_redemption` is dual authority (customer_user own account scope OR staff `LYL:Edit`, mirrors CPL-319's `app.redeem_loyalty_benefit_entitlement`). It always creates the real intent record after full re-validation, then attempts immediate composition (reserve stock → consume points → issue entitlement for `discount_voucher`) using the submitting actor's own identity — succeeding synchronously only when that actor independently holds `LYL:Edit` (confirmed structurally: `app.role_assignments` has exactly one INSERT call site in the whole repository, a staff-only administrative RPC the customer-portal invite flow never touches). A genuine customer submission of ANY reward_type gracefully falls back to `pending_approval` (a savepoint-scoped catch of exactly `insufficient_authority`, never any other exception). Full reasoning, including a live-tested confirmation that `auth.uid()` is unaffected by nested `SECURITY DEFINER` calls, in the migration's own header. Disclosed as `ISS-2026-132`.
6. **Fraud hold composed via a direct read of `app.loyalty_account_tier_holds`**, never the staff-gated `app.get_loyalty_account_tier_state` — mirrors CPL-320's own direct-table-read precedent for tier/points eligibility. A held account's redemption attempt is blocked with a customer-safe generic message that never reveals the real `hold_reason` — live-proven adversarially in this checkpoint's own db-test (the message is asserted NOT to contain the fixture's own planted confidential hold reason text).
7. **Self-approval structurally impossible for `app.decide_loyalty_redemption`** (`LYL:Configure`-gated), confirmed directly via the same role-assignment-provisioning grep as design decision 5 — mirrors CPL-315's own "checked, not re-derived" role-hierarchy methodology. Live-proven: a customer_user actor attempting `decide_loyalty_redemption` on their own submitted redemption is rejected `insufficient_authority`.
8. **`app.loyalty_reward_stock_reservations`' own CHECK constraint widened (`quantity > 0` → `quantity <> 0`) via a real, additive `ALTER TABLE` in THIS migration** — CPL-320's own applied migration file is never edited. A release posts a negative-quantity row into the SAME ledger; CPL-320's own already-shipped `coalesce(sum(quantity), 0)` aggregate nets it out automatically, zero change to either of CPL-320's own read RPCs. `app.release_loyalty_reward_stock_reservation` (new) is the one function that ever posts a negative row — the structural inverse of `app.reserve_loyalty_reward_stock_unit`. Re-confirmed live: CPL-320's own db-test (which only ever posts positive reservations) re-run alongside this checkpoint's own, both pass clean.
9. **Server-side re-validation at the CURRENT checkpoint, applied twice, independently** — `app.submit_loyalty_redemption` and `app.decide_loyalty_redemption`'s own approve branch each independently re-check reward status/effective-window/hold/tier/points, fresh, inside their own transaction — never trusting a client-supplied or submission-time snapshot.
10. **NULL-bypass optimistic concurrency, applied from the start and self-found-and-fixed during this checkpoint's own db-test authoring** — the FIRST db-test run caught a real gap: `app.decide_loyalty_redemption`'s own preliminary version check (`if v_redemption.record_version <> p_expected_version`) silently passed a NULL `p_expected_version` through on the approve branch, since its actual mutation delegates to a private helper that never references the caller's own `p_expected_version` at all (unlike the reject branch, which repeats the predicate on its own direct `UPDATE`). Fixed at the root (`if p_expected_version is null or ...`), applied consistently across all four version-checked functions, including one genuine ordering fix in `app.cancel_loyalty_redemption` (the explicit NULL check now runs BEFORE the reversal call, which has a real side effect, not only before the final `UPDATE`). Live-proven: a NULL `p_expected_version` rejected with `stale_version`, row byte-for-byte unchanged, before the real-version call succeeds.
11. **Idempotency throughout** — `app.submit_loyalty_redemption` carries a real `unique(tenant_id, idempotency_key)` on `app.loyalty_redemptions`, the standing check running BEFORE the idempotent short-circuit (which also verifies the full target tuple — `loyalty_account_id`/`reward_id` — on a key match, C-01), a real `exception when unique_violation` handler, and the idempotency-establishing INSERT strictly before any downstream stock/points/entitlement mutation (CPL-318 ordering lesson). Every downstream composed call derives its own deterministic key from the redemption's own id.
12. **Atomicity, live-proven adversarially** — every failure branch inside the private composition helper is an uncaught exception that aborts the whole transaction. Proven with a misconfigured `discount_voucher` reward (no `internal_cost`, real finite stock, real points cost): the reservation, the point consumption, AND the redemption row's own INSERT all roll back together — a strictly stronger proof than the mandated "reservation and point consumption together."
13. **LYL permission mapping, reused unchanged.** Ordinary lifecycle (submit's intent creation, mark fulfilled/failed) → `LYL:Edit`. The governance-grade decision (`decide_loyalty_redemption`) → `LYL:Configure`, additionally, explicitly re-checking `LYL:Edit` before delegating to composition (mirrors CPL-318's own design decision 16 precedent). Staff reads → `LYL:View`. Customer submit/cancel → dual authority; customer reads → `resolve_customer_account_scope` only.
14. Every actor-taking function (11 public RPCs + 2 private helpers) calls `app.assert_actor_is_session_identity` as its own literal first statement; every staff mutate/get-by-id RPC checks `LYL:*` authority before fetching its target row (C-05).
15. RLS: `authenticated` holds zero direct grant on either new table. `app.loyalty_redemption_events` is append-only (no UPDATE/DELETE grant to any role, not even `service_role`) — per `ISS-2026-130`, no Supreme-Admin-override mechanism is implemented, an already-accepted, standing gap.
16. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public` before final grants.
17. Cursor pagination `(tenant_id, updated_at desc, id desc)` on every list RPC, never `OFFSET`.

## 11. Residual/disclosed limitations

- **`ISS-2026-132`** (`docs/runtime/KNOWN_ISSUES.md`, new, Low, `OPEN`) — three items: (1) this checkpoint's own central RBAC-composition resolution — a genuine, unassisted customer_user self-service redemption never auto-approves synchronously, regardless of reward_type, always requiring one real staff decision; (2) discount_voucher entitlement value/currency sourced from the reward's own `internal_cost`/the tenant's own resolved default currency, a disclosed modeling decision closing a real CPL-320 schema gap; (3) no notification/retry/DLQ mechanism, mirroring the established "on-demand/staff-triggered only" precedent family.
- **No REST/GraphQL HTTP route** — service layer + Server Actions + UI only (ADR-0024 Part C), identical in kind to every prior Phase 8 disclosure.
- **No separately-observable "approved" persisted status** — `app.loyalty_redemptions.status`'s own CHECK constraint admits `'approved'` (the literal vocabulary this task requires), but no RPC in this checkpoint currently emits it as a standalone, externally-observable committed state — composition and its resulting `fulfilling`/`fulfilled` transition happen atomically within the same `decide_loyalty_redemption` call. A future checkpoint could add a dedicated "start fulfillment" staff action if separately tracking "approved but not yet picked" from "actively being prepared" becomes a real operational need.

## 14. Tier C review and fix (Batch 5 close, `CPL-320..323`)

Four independent Tier C review lenses (spec-compliance, security/RLS, correctness/concurrency, cross-prompt-integration) examined all four Batch 5 migrations together, each live-testing against a fresh disposable Postgres 16 database. All four lenses independently converged on the SAME Critical finding in this capability's own migration; the orchestrating session had already flagged the same mechanism as its own item 1 during its own spot-verification. Finding, disposition, and reasoning:

- **Fixed (escalated to Critical per this review's own governing "lost/duplicated redemption" instruction — every lens rated it Critical/High).** `app.submit_loyalty_redemption`'s own inline auto-approve attempt (design decision 5) wrapped its call to `app._compose_loyalty_redemption_decision` in a `begin...exception when others then if sqlerrm like 'insufficient_authority%' then null; else raise; end if; end;` block — catching ONLY the one, well-known condition a genuine, unassisted `customer_user` actor hits (the realistic, currently-shipped caller), and re-raising every other exception. Live-reproduced by three of the four lenses independently, and confirmed directly by this fix pass: a staff/system actor who DOES hold `LYL:Edit` (this checkpoint's own designed, tested, first-class "Main Flow A" caller — the RPC is `grant execute ... to authenticated`, not gated behind any UI wrapper) whose composition attempt fails for an ORDINARY, non-authority reason — the reward genuinely out of stock (`insufficient_reward_stock`, live-reproduced with zero test-fixture misconfiguration required, a routine "sold out" state), the account genuinely short on points, or a misconfigured `discount_voucher` reward's own `reward_redemption_unavailable` (the shipped db-test's own original fixture) — hit the `else raise;` branch. Because that re-raise was never caught anywhere else in `submit_loyalty_redemption`, it aborted the WHOLE top-level statement, rolling back not only the composition's own partial work (correct, by design) but the redemption row's own `INSERT` and its `'submitted'` event too — BOTH of which happened strictly BEFORE this savepoint-scoped attempt, in the SAME transaction. This silently destroyed the customer's own otherwise-entirely-legitimate request with zero audit trail, directly contradicting this migration's own documented, unconditional invariant (design decision 5's own literal text: "every submission, regardless of caller, ALWAYS creates the real, portal-owned intent/request record") — the shipped db-test's own "adversarial atomicity proof" had actively encoded and celebrated this row-loss as a "strictly stronger" atomicity proof, a genuine internal contradiction between two of the migration's own design decisions (5 and 13), never disclosed as such anywhere the checkpoint's own `ISS-2026-132` would otherwise have caught it.

  **Reachability, per this review's own explicit charge to determine it directly rather than assume:** NOT reachable via any currently shipped UI path — grep-confirmed the sole production caller of `submitLoyaltyRedemption`/`submit_loyalty_redemption` anywhere in `app/`/`server/` is `app/(tenant)/[tenantSlug]/customer-loyalty-rewards/actions.ts`, which always passes the calling customer's own identity; the admin UI (`admin/loyalty-redemptions/actions.ts`) only calls `decideLoyaltyRedemption`/`markLoyaltyRedemptionFulfilled(Failed)`, never `submitLoyaltyRedemption`. It IS, however, reachable today by any staff session holding `LYL:Edit` calling the granted RPC directly (a natural, small extension of the already-wired admin decide/fulfill actions — "submit a redemption on this customer's behalf" — or any direct API/service/support-tooling access), per this repository's own standing "RLS/`SECURITY DEFINER` functions are self-defending, not merely protected by the app layer" doctrine (CPL-316/318's own precedent).

  **Correctness, regardless of reachability:** silently losing the intent record is wrong for ANY caller, staff or system — not merely a latent gap. The fix widens the catch in `app.submit_loyalty_redemption` to swallow EVERY exception the composition attempt can raise (dropping the `sqlerrm like 'insufficient_authority%'` filter entirely), leaving the redemption row exactly where it already is — `pending_approval` — regardless of why the auto-approve attempt failed. A human then resolves it via the unmodified `app.decide_loyalty_redemption`, whose own independent, fresh re-validation (design decision 9, already built) surfaces the identical current-state condition (stock/points/reward configuration) at decision time — exactly the uniform recovery path every OTHER failure mode already used. Verified safe by direct PL/pgSQL semantics reasoning (a caught, non-re-raised exception only unwinds to the implicit savepoint at the CATCHING block's own entry — which is strictly AFTER the redemption row's own `INSERT` and `'submitted'` event, so widening the catch changes nothing about the composition's own downstream atomicity, design decision 13, while correctly preserving the outer row) and by live re-execution. The migration's own header (design decisions 5 and 13) and every affected function/private-helper comment are corrected in-file (this migration remains uncommitted/editable) to state the fixed behavior accurately, replacing the now-false "the row is rolled back too... a strictly stronger proof" claim design decision 13 originally made.
