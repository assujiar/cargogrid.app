## 2. Design decisions

Full rationale in the migration's own 20-point header comment; summarized here.

1. **The mandatory, disclosed design question this task's own brief required resolving: points liability is reported as a RAW POINTS total, never converted to currency.** No point-to-currency conversion rate is configured anywhere in this repository's real Loyalty schema (grep-confirmed again at this checkpoint). `points_liability_total numeric` is dimensionless, never force-summed into any currency-denominated line. `app.loyalty_rewards.internal_cost` (CPL-320) has no currency column either — this checkpoint EXTENDS CPL-321's own already-disclosed "currency = the tenant's own resolved default_currency" assumption (design decision 4 there) to value the reward-fulfillment-exposure line, rather than inventing a new one.
2. **Mirrors FIN-209's exact three-function execute/resolve-then-certify shape as this migration's OWN new, Loyalty-owned functions and tables** — never calling FIN-209's own functions directly (a different domain, no natural Loyalty-liability row to reconcile against there). Unlike FIN-209, no separate `check_authority()` wrapper function is introduced — every CPL-316..322 function in this domain already inlines `app.evaluate_permission(...)` directly; this migration continues that established convention.
3. **Every liability total is recomputed LIVE from the raw ledger/event tables on every execute call — never trusted from a cached, mutable snapshot column without independent re-derivation** (the task's own mandatory business rule). Points sum live over `app.loyalty_point_ledger_entries.amount` per account; cashback/discount/voucher sum `app.loyalty_benefit_entitlements.value_amount` only for entitlements whose CURRENT status is independently re-derived from the append-only `app.loyalty_benefit_entitlement_events` log (never trusted from the entitlements row's own mutable `status` column).
4. **`p_as_of` is recorded as a run's own point-in-time label but does NOT bound which raw rows are included** — every total reads the full current state of the source tables at execution time, disclosed as a real, bounded scope decision (`ISS-2026-134` item 2), since `app.loyalty_point_balances`/`app.loyalty_benefit_entitlements` are both current-state-only with no historical-snapshot capability for any date other than "now" — a genuine historical bound would make the exactness cross-check structurally meaningless.
5. **Liability model covers points, cashback, discount, voucher (the brief's own literal 4) plus a 5th, disclosed addition: `reward_fulfillment_liability_total`** — the source prompt's own section 20 literally names "points, cashback, vouchers AND REWARDS." A `physical_item`/`service_credit` redemption (CPL-321) never mints an entitlement row, so a committed-but-unfulfilled one (`status = 'fulfilling'`) is a real liability with no representation anywhere in the entitlements total. Valued at the reward's own staff-only `internal_cost` (design decision 1's extended assumption); a null `internal_cost` contributes 0 (`ISS-2026-134` item 3).
6. **Cashback/discount/voucher totals are CURRENCY-SCOPED via a required `p_currency` parameter** (my own disclosed addition beyond the brief's own literal 4-parameter execute signature) — entitlements in a different currency are excluded from this run entirely, never blended. A tenant with multi-currency entitlements needs one run per currency, mirroring FIN-209's own per-scope (`ar`/`ap`) precedent exactly.
7. **Entitlement CURRENT STATUS is independently re-derived purely from `app.loyalty_benefit_entitlement_events`** via a deterministic latest-event-type → status mapping (`issued → issued`, `redeemed → redeemed`, `reversed → reversed`, `expired → expired`, `held → held`, `released → issued`) — never trusted from the entitlements row's own mutable `status` column. A mismatch produces a real `entitlement_state_derivation_mismatch` exception, and the LIABILITY TOTAL itself uses the re-derived status — a corrupted status column can never silently understate or overstate a certified total.
8. **The formal, runnable closure of `00_EXECUTION_INDEX.md` section 11's "Loyalty ledger exactness" evidence unit, for points**: for every `loyalty_account_id` with any ledger row, this run asserts live `SUM(amount)` equals `app.loyalty_point_balances.available` exactly, recording a real `point_balance_derivation_mismatch` exception for any account where it does not (including a missing cached-balance row entirely).
9. **The ledger-insert-before-mutation ordering discipline (CPL-318's own self-found double-counting-race lesson) does NOT directly apply here — disclosed explicitly, not silently omitted**, per this task's own instruction: this is a pure read/aggregate/record operation, never mutating any other domain's row. The same underlying discipline is still applied where it matters: the run row's own INSERT (idempotency-establishing, exception-handler-backed) always happens before any exception row, which references it as a foreign key.
10. **Idempotency key defaults to `'liability-recon:' || as_of::date || ':' || currency`** when not supplied (mirrors CPL-322's own `run_label`-defaulting precedent exactly) — calendar-day-and-currency-scoped idempotency for free, an explicit distinct key still allowed for a deliberate same-day rerun.
11. **Authority mapping: execute + resolve = `LYL:Edit` (ordinary posting-tier); certify = `LYL:Configure` (the elevated, governance-grade action every other Loyalty capability already reserves for irreversible-in-effect actions)** — LYL has no distinct `Approve` action (confirmed again), so `Configure` is the natural, already-established mirror of FIN-209's own distinct `FIN:Approve` certify gate. Running a reconciliation does NOT require the same elevated bar as certifying it — my own disclosed call, matching FIN-209's own precedent exactly.
12. **Double-defended NULL-bypass optimistic concurrency** on both `resolve`/`certify`, applied from the start — the exact CPL-321/322 shape (an explicit up-front NULL check plus the identical predicate repeated on the UPDATE itself).
13. **Resolving the LAST open exception on a run automatically transitions it from `exceptions_pending` back to `open` (ready to certify)** — a disclosed nicety beyond FIN-209's own literal shape (no such intermediate state exists there to auto-clear).
14. **`app.certify_loyalty_liability_reconciliation_run` carries NO separate `p_reason` parameter**, departing from FIN-209's own mandatory certify-reason precedent — the brief's own literal 5-parameter signature omits it; my own disclosed call, since every exception is already individually reasoned via its own mandatory `resolution_reason`.
15. **`app.get_loyalty_engagement_metrics` is Step-13-scope BASIC analytics only** — one tenant-wide aggregate row, structurally incapable of naming a specific customer or exposing `internal_cost`/`vendor_ref`/margin. A `customer_user` caller is rejected outright (`insufficient_authority`), never merely handed an empty row.
16. **`app.get_customer_portal_loyalty_summary` COMPOSES (never duplicates)** `app.list_customer_portal_loyalty_tier_cards`/`..._point_balances`/`..._benefit_entitlements`/`..._redemptions`/`..._account_hold_status` — the already-existing, already-tested per-domain customer reads (CPL-317/318/319/321/322) — into one consolidated row for the caller's own single loyalty account. `active_entitlements_summary` is grouped by `(benefit_type, currency)` — design decision 1/6's own "dimension, never force-sum across currencies" discipline applied a third time.
17. `clock_timestamp()`, never `now()`, throughout.
18. Every actor-taking function calls `app.assert_actor_is_session_identity` first; every staff mutate/get-by-id RPC checks `LYL:*` authority BEFORE fetching its target row (C-05).
19. **RLS: `authenticated` holds ZERO direct grant** on either new table (mirrors CPL-316..322 exactly — a deliberate departure from FIN-209's own more permissive `grant select ... to authenticated` plus a select-scoped RLS policy, since ADR-0024 Part A governs this capability, not FIN-209's own pre-ADR-0024 precedent). Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public` before final grants.
20. Cursor pagination `(tenant_id, updated_at desc, id desc)` on every list RPC, never `OFFSET`.

**Explicit scope boundary (disclosed, not silently narrowed):** no Finance-side handoff-batch table/idempotent generator/Finance acknowledgement RPC (the HRT-282-family shape ADR-0024 Part D names) is built. No Finance-side liability-handoff contract exists anywhere in this repository for Loyalty to hand off TO yet — fabricating one would invent a Finance-side contract Finance itself never asked for. This checkpoint instead builds the reconciliation evidence layer entirely within Loyalty's own already-real tables, closing `ISS-2026-129` item 1 on its own terms. Recorded as `ISS-2026-134` item 5.
