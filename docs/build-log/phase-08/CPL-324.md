## 7. Repairs made this checkpoint (bounded, additive-only)

### 7.1 Optimistic-concurrency NULL-bypass on 12 customer-portal mutation RPCs (Medium → Fixed)

**Root cause:** `if v_row.record_version <> p_expected_version then raise ...` evaluates to SQL `NULL`, not `TRUE`, when `p_expected_version` is `NULL` — the raise never fires, and in these 12 functions the subsequent `UPDATE` did not repeat the version predicate, so a caller supplying `NULL` (or omitting the parameter) silently defeated the optimistic-concurrency guard. **Not** a tenant/account-scope escalation — every function still independently enforces its own RBAC/ownership check first (re-confirmed this checkpoint via the same adversarial battery). Six of the twelve instances were live-reproduced directly (before/after row state captured) before this fix was written; the remaining six were confirmed by direct code inspection of the identical shape.

**Fix:** one new additive migration, `supabase/migrations/20260801260000_harden_customer_portal_optimistic_concurrency_null_bypass.sql` — `CREATE OR REPLACE FUNCTION` against all 12 functions, adding `p_expected_version is null or` to each early check and repeating `and record_version = p_expected_version` in each `UPDATE`'s own `WHERE` clause (with a matching `if not found then raise 'stale_version...concurrently modified'` fallback) — the exact two-part pattern this same migration set already uses correctly in CPL-320/321/322/323 and in `app.unlink_ticket_portal_record`/`app.update_customer_portal_account_membership_role`. No other line of any function was touched. No new `GRANT`/`REVOKE` needed (`CREATE OR REPLACE FUNCTION` on an identical signature preserves ACLs).

Functions fixed: `app.accept_customer_portal_invite`, `app.set_customer_portal_account_membership_status` (CPL-300); `app.update_customer_quote_request_draft`, `app.submit_customer_quote_request`, `app.cancel_customer_quote_request` (CPL-302); `app.update_customer_booking_request_draft`, `app.submit_customer_booking_request`, `app.request_customer_booking_reschedule`, `app.request_customer_booking_cancellation` (CPL-303); `app.respond_to_customer_shipment_order_change_request` (CPL-304); `app.withdraw_customer_profile_change_request`, `app.decide_customer_profile_change_request` (CPL-314).

Functions independently re-confirmed **already safe**, deliberately left untouched: every mutation in CPL-316/317/318 (double-defended UPDATE predicate), every mutation in CPL-320/321/322/323 (already uses the `is null or` early-check pattern), `app.redeem_loyalty_benefit_entitlement` (CPL-319, deliberately nullable version + an independent atomic `status='issued'` UPDATE guard), `app.reverse_loyalty_benefit_entitlement` (CPL-319, early check has the old shape but the UPDATE's own repeated predicate + `IF NOT FOUND` already double-defends it — net safe, no fix needed), `app.unlink_ticket_portal_record`, `app.update_customer_portal_account_membership_role`.

**Regression coverage:** a new NULL-bypass regression block was added to each of the 5 affected files' own `scripts/db-tests/*.sql` (`customer-portal-scope.sql`, `customer-quote-requests.sql`, `customer-booking-requests.sql`, `customer-shipment-orders.sql`, `customer-profile-visibility.sql`), mirroring `customer-loyalty-redemption.sql`'s own established "NULL-bypass regression proof" shape — each proves NULL is rejected with `stale_version`, the row is byte-for-byte unchanged, then the real version succeeds. Verified clean 4 times total this checkpoint (once inside the full 193-file suite, three additional standalone runs against a freshly-migrated database).

### 7.2 CPL-304 stale `SHIPMENT_ORDER_STATUSES` contract enum (High → Fixed)

**Root cause:** `server/contracts/customer-shipment-order/customer-shipment-order.ts` defined `SHIPMENT_ORDER_STATUSES = ["draft", "confirmed", "cancelled"]`, the pre-OPS-170 set, never updated when the real `app.shipment_orders_status_check` constraint (and the sibling staff-facing `server/contracts/shipment-order/shipment-order.ts`) was broadened to 11 values at OPS-170. `getCustomerShipmentOrder`/`listCustomerShipmentOrders` (`server/queries/customer-shipment-order.ts`) parse the RPC's raw row through this schema with no fallback; `listCustomerShipmentOrders` uses `.map(parseCustomerShipmentOrder)` with no per-row `try/catch`, so one shipment in any of the 8 missing statuses discarded the caller's entire shipment list.

**Fix:** widened `SHIPMENT_ORDER_STATUSES` to the full 11-value list (`draft, confirmed, planned, assigned, dispatched, in_transit, delivered, epod, closed, held, cancelled`), byte-identical to the already-correct staff-facing contract. Added a regression test (`customer-shipment-order.test.ts`) asserting the full 11-value set and that every one parses without throwing. **Also fixed, discovered only after this change via a fresh `typecheck` run:** two customer-facing UI files (`app/(tenant)/[tenantSlug]/customer-shipments/customer-shipments-panel.tsx`, `.../customer-shipment-detail-panel.tsx`) each maintained their own local `Record<ShipmentOrderStatus, ...>` tone/label map, also stuck at the stale 3-value set — TypeScript's own exhaustiveness check on the now-11-value union correctly flagged both as incomplete. Widened both maps to all 11 statuses, reusing the tone/label choices already established by `components/domain/status-tone-map.ts`'s own `SHIPMENT_ORDER_STATUS_TONE_MAP` (the staff-facing shipment list's already-correct mapping for the identical status set) for the 8 new entries, leaving the original 3 entries byte-identical to avoid an out-of-scope visual change to already-correct behavior.

**Verification:** `pnpm run typecheck` clean before writing the build log (0 errors); `node --test` on the contract's own test file: 18/18 pass, including the new regression test.
