## 2. Design decisions

Full rationale in the migration's own 14-point header comment; summarized here.

1. **Signed-amount convention** on `app.loyalty_point_ledger_entries.amount`: positive increases available balance (earn; a reversal crediting back a consumed lot), negative decreases it (redemption; expiry; a reversal clawing back an earn; a negative adjustment). `total_earned` = running sum of every positive amount ever posted; `total_consumed` = running sum of the absolute value of every negative amount ever posted; `available` (generated) = `total_earned - total_consumed` always equals the arithmetic sum of every posted amount — a clean, auditable reconciliation invariant. My own disclosed design call (the source prompt's own literal column list does not fix a sign convention); it is what lets ONE posting primitive serve all five event types uniformly.
2. **A real, self-found-and-fixed double-counting race, caught during this checkpoint's own design pass (not a live failing run) — disclosed as its own numbered design decision, not silently corrected.** A first draft of `app.post_loyalty_point_ledger_entry` mutated the balance/lot BEFORE the ledger `INSERT`, with the `INSERT` wrapped in an `exception when unique_violation` handler per the mandatory pattern. Worked through explicitly: under a genuine concurrent duplicate-idempotency-key race, the LOSING transaction's own balance/lot mutation would still commit (only the `INSERT`'s own exception is caught, not anything run before it) while its ledger insert is gracefully swallowed and the WINNER's row returned instead — silently double-counting the balance for one logical event backed by only one ledger row. Fixed at the root before this file was ever run: the ledger `INSERT` happens FIRST (establishing the idempotency claim), balance/lot mutation happens AFTER — a losing racer's exception fires before it has mutated anything, eliminating the race structurally. This is the single most safety-critical design decision in this checkpoint, given the task's own "highest financial-integrity-risk prompt" framing.
3. **Negative-balance prevention is BOTH a procedural guard** (the authoritative check, evaluated before every write, mirrors `app.post_inventory_movement`'s own `insufficient_stock` precedent) **AND a real table `CHECK` constraint** (`lpb_available_nonnegative_check`, `total_earned >= total_consumed`) as a defense-in-depth backstop that should never actually fire for a legitimate call — my own disclosed choice between the two options this task's own instruction offered. Proven live with both a real attempted over-consumption (single-session) and a real two-process concurrent-race attempt (reusing `scripts/db-tests/wms-picking-concurrency-helper.sh`, a generic two-psql-process helper despite its WMS-picking filename).
4. **Lot expiry window is a caller-supplied, bounded parameter** (`p_expiry_days`, 1-3650, default 365) on `app.post_loyalty_points_earned`, not a persisted per-(tenant,program) config table — a real, working, bounded policy, but a lighter-weight scope decision than CPL-317's own persisted `review_period_days` precedent, disclosed as `ISS-2026-128` item 2.
5. **`config_version`** (the source prompt's own §13 "config/source versions" business rule) is a forward-compatible posting-LOGIC-version marker, a real parameter (`p_config_version integer default 1`) constant `1` in this checkpoint since no persisted, versionable point-earning configuration exists yet.
6. **One lot per points-type ORIGINAL earning event only** (`unique (tenant_id, source_earning_event_id)`) — `app.post_loyalty_points_earned` rejects a reversal-shaped CPL-316 earning event, pointing the caller at `app.reverse_loyalty_points_earned` instead, which finds the ORIGINAL event's own lot via the reversal event's own `corrects_event_id` and posts a reversal capped at `least(lot.remaining_amount, abs(reversal_amount))` — some of the lot may already have been legitimately spent/expired before the earning event was reversed at the CPL-316 level; this checkpoint claws back only what the lot still actually holds, disclosed rather than silently over/under-reversing.
7. **`app.consume_loyalty_points_fifo` is a real, complete, live-proven FIFO-by-expiry multi-lot consumption primitive**, not merely a documented policy claim — posts one `redemption` entry per lot touched, oldest-expiring first, serialized per `loyalty_account_id` via `pg_advisory_xact_lock(hashtextextended(id::text, 4))` (mirrors CPL-317's own salt-3 precedent, salt 4 here). No reward/voucher catalog exists yet to trigger it from a real customer checkout (CPL-316's own "discount/voucher issuance is CPL-319's own scope" precedent) — disclosed as `ISS-2026-128` item 3.
8. **`app.expire_loyalty_point_lots` scans (tenant-wide) lots past `expires_at` with `remaining_amount > 0`**, posting an `expiry` entry per lot; idempotent per lot by construction (an expired lot no longer matches the scan predicate). Each lot's own posting call is independently fault-isolated (`begin...exception when others then continue`) so one lot racing against a concurrent operation never aborts an otherwise-successful batch for every other due lot.
9. **`app.request_loyalty_point_adjustment`/`app.decide_loyalty_point_adjustment` DIRECTLY mirror PRC-264's `app.request_vendor_kpi_manual_adjustment`/`app.decide_vendor_kpi_manual_adjustment`**: mandatory non-empty reason, self-approval blocked, `record_version` optimistic concurrency, a partial unique index enforcing at-most-one-pending-adjustment-per-account, both write `app.capture_audit_event` with a REAL before/after (an improvement over PRC-264's own `null`-before precedent). **One deliberate improvement beyond PRC-264's own decide-function signature shape**: `app.decide_loyalty_point_adjustment` takes `p_tenant_id` explicitly and checks `LYL:Configure` BEFORE fetching the target row (C-05), rather than PRC-264's own fetch-then-check shape — mirrors CPL-316/317's own already-established stricter precedent, applied here to the one function this task explicitly asked to "directly mirror" an older, less strict one.
10. Every actor-taking function calls `app.assert_actor_is_session_identity` as its own literal FIRST statement; every staff mutate/get-by-id RPC checks `LYL:*` authority BEFORE fetching its target row.
11. **LYL permission mapping, reused from CPL-316/317 unchanged** (LYL has no `Approve` action). Ordinary posting (the core primitive, earn/expire/FIFO-consume wrappers, the maker's own request) → `LYL:Edit`. The two governance-grade actions — reversing an already-posted lot's worth of points, and DECIDING a point adjustment — both map to the elevated `LYL:Configure`.
12. **`clock_timestamp()`, never `now()`**, for every timestamptz column whose ordering matters or whose table could plausibly receive more than one row/update within the same transaction — the CPL-315 self-found defect class, applied proactively throughout (including `app.loyalty_point_ledger_entries.created_at`, which genuinely can receive several rows in one transaction via a single `consume_loyalty_points_fifo` call).
13. **RLS: `authenticated` holds ZERO direct grant** on any of the 4 new tables, mirroring CPL-316/317 exactly. `docs/architecture/06_RLS_RBAC_WORKSTREAM.md` §8/§4 already explicitly names `point_ledger`/`cashback_ledger` inside the repository's `append_only_ledger` policy family disclosure (Supreme Admin absolute CRUD, RISK-004, standing accepted residual risk) — cited directly in the migration header, not re-derived. `app.loyalty_point_ledger_entries` is this checkpoint's own concrete realization of that already-disclosed `point_ledger` family member. Consistent with — not a new gap beyond — CPL-316's/317's own identical choice for their own sibling ledger tables, no concrete Supreme-Admin-override mechanism (the FIN-204 trigger-based kind) is implemented here either; `service_role` itself holds no UPDATE/DELETE grant on the ledger table, so today literally no ordinary role can mutate a posted row.
14. Per `ERR-2026-004`: this migration carries its own explicit `revoke execute on all functions in schema app from public` statement before its final grants.
