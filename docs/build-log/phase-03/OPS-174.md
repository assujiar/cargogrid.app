## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Taxonomy scope.** Type (delay/hold/damage/loss/incident) and severity (low/medium/high/critical) are fixed CHECK-constrained enums, not a permanent cross-tenant registry table like `OPS-173`'s milestone codes — this "basic exception/incident taxonomy" (§20 task 1) is the same bounded shape `OPS-169` already used for `app.shipment_orders.mode`. Inventing a second registry mechanism for an equally small fixed set would be unjustified scope.
2. **SLA/escalation policy IS real and versioned** (§24: "pinned at detection unless explicit reevaluation occurs"). Mirrors `OPS-173`'s own considered choice over Configuration Engine reuse: a directly tenant-scoped versioned-definition table (`app.exception_sla_policy_versions`, one row per `(tenant_id, type, severity)`). "Pinned at detection" is a real governed snapshot — `app.report_exception` copies the resolved policy's own `sla_hours`/`id` onto the exception row at creation time; a later republish never retroactively changes an already-open exception's own due date.
3. **Sensitive-field masking** (§16/§26: "restrict... damage/loss details, claim amount") reuses the exact precedent `COM-148`/`COM-156` already established. This migration registers one new permission catalogue row using the **already-approved, fixed 19-action vocabulary** `PLT-111` closed (`action in (...)`) — `('View cost', 'OPS', 'sensitive', true)` — a distinct catalogue row from `COM:View cost` (permissions are keyed on `(resource_module_code, action)`, never a name collision). `app.exceptions_directory` masks `internal_notes`/`damage_loss_details`/`claim_amount`/`claim_currency` for any actor lacking it, the same "authenticated has no direct grant on the base table, forced through the masked view" guarantee `OPS-168`'s own `app.job_orders_directory` proved. Writing those same fields (`app.set_exception_sensitive_fields`) requires both `OPS:Edit` and `OPS:View cost`.
4. **Automatic, time-driven escalation** ("SLA jobs enforce reminders/escalation," §14) is the same "mechanism real, live scheduler wiring deferred" posture already disclosed at `PLT-129`/`PLT-132` — `app.escalate_exception` is a real, callable, reason-required step any caller (human today, a future job) can invoke; no fake scheduler is built to call it automatically.
5. Full claims adjudication, insurance settlement and financial posting are explicitly out of Phase 3 scope (§24) — `claim_amount`/`claim_currency` are a recorded, non-authoritative estimate only, never posted to any ledger, never a float (`numeric(14,2)`, the same precision every other money-shaped column in this repository uses).

### 3.2 Schema — `supabase/migrations/20260727150000_create_operations_exception_escalation.sql`

One new permission (`OPS:View cost`). `app.exception_sla_policy_versions` (draft → published → archived, at most one draft/published per `(tenant, type, severity)`) with `app.create_exception_sla_policy_draft`/`app.set_exception_sla_policy_terms`/`app.publish_exception_sla_policy_version` (`OPS:Create`/`OPS:Edit`-gated). `app.operational_exceptions` (governed SLA snapshot at creation; dedup unique index on `(tenant_id, shipment_order_id, correlation_key)` for `source='system'`) with `app.report_exception` (`OPS:Create`-gated, idempotent dedup), `app.assign_exception_owner` (`OPS:Assign`-gated, reason mandatory only on reassignment), `app.acknowledge_exception`/`app.escalate_exception`/`app.resolve_exception`/`app.reopen_exception` (`OPS:Edit`-gated) and `app.close_exception` (`OPS:Close`-gated — the first real consumer of this pre-seeded action), `app.set_exception_sensitive_fields` (`OPS:Edit` + `OPS:View cost`-gated). `app.exception_escalations` (append-only history). `app.exceptions_directory` (masked view). `app.get_exception_escalation_history` (authority-gated read).

## 8. Errors / recovery / risks / issues

Several real issues found and fixed before the full suite passed: (1) the initially-invented permission action `OPS:View sensitive` violated `app.permissions`' own fixed, closed `CHECK` constraint (exactly 19 approved action strings, sourced from `06_RLS_RBAC_WORKSTREAM.md` §5.1) — corrected by reusing the already-approved `View cost` action paired with the `OPS` module instead of inventing a new action string, renaming the helper function to `app.has_view_exception_cost` throughout; (2) a SQL string-literal quoting bug in a `comment on function` statement (an unescaped `'{}'::jsonb` inside a single-quoted comment) was caught and fixed before ever running `db:test`; (3) a genuine, real defect was found and fixed in a **prior checkpoint's own test file**, not this one's: `operations-job-order.sql`'s `job_orders_directory` masking assertion used an unqualified `select id into v_job_order_id from app.job_orders limit 1` with no tenant filter — this had silently relied on incidental row-insertion-order luck across the shared disposable test database (every `db-test` file runs against one continuously-migrated database) and broke the moment this checkpoint's own new, alphabetically-earlier-sorting `operations-exception-escalation.sql` file created its own job order first. Root-cause fixed by scoping that query to `where tenant_id = v_tenant1`, matching every other query in that same file. Zero Critical/High-severity issue remains open. Zero regression to any prior capability once both root causes were corrected.
