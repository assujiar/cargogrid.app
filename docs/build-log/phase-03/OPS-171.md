## 3. Implementation

### 3.1 Scope boundaries (disclosed, migration header)

1. Vehicle/vendor/carrier references are deliberately plain text, never a foreign key into a vehicle/vendor master — no such master type has ever been registered anywhere in this repository (`app.master_records`, `PLT-120`, has only ever seeded `vendor_rate`). Binding these fields to real canonical vendor/fleet/vehicle/driver references is `OPS-172`'s (Resource Assignment) own explicit scope, not anticipated or duplicated here.
2. Exactly one mode's own column group is ever populated per profile — the other two modes' columns are structurally null, enforced by a real multi-column `CHECK` constraint (`shipment_mode_profiles_mode_fields_check`), never merely a UI or application-layer convention. `sea_container_number`/`sea_container_type` stay optional (LCL cargo may carry neither); every other field its own mode requires is mandatory.
3. **Mode change policy** (Prompt 171 §22/§23): `app.change_shipment_mode` is the one path that may alter `app.shipment_orders.mode` itself, allowed only while the shipment is `draft` (`confirmed_mode_change_blocked` otherwise) — it explicitly reconciles the prior, now-incompatible profile by deleting it, never leaving stale mismatched field values behind. Editing the profile's own field *values* for the shipment's current, unchanged mode (`app.set_shipment_mode_profile`) is a separate, less restrictive path, blocked only once the shipment is cancelled.
4. Multi-leg, multimodal, multi-pickup/drop, consolidation, route/load optimization and GPS/telematics all remain explicit Phase 3/5 (Advanced TMS/WMS) scope, never anticipated here.

### 3.2 Schema — `supabase/migrations/20260727120000_create_operations_mode_baseline.sql`

`app.shipment_mode_profiles` (one row per Shipment Order, unique on `shipment_order_id`, a real 1:1; 15 mode-specific columns across land/air/sea column groups, plus the multi-column mode-fields `CHECK`). `app.set_shipment_mode_profile` (`OPS:Edit`-gated, idempotent create-or-update via `ON CONFLICT`, mode always read from the linked shipment itself, never caller-supplied — a profile can never drift out of sync with its own shipment's mode). `app.change_shipment_mode` (`OPS:Edit`-gated, draft-only, optimistic concurrency, reconciles the prior profile).

### 3.3 Service layer and UI

`server/contracts/shipment-mode-baseline/shipment-mode-baseline.ts` — a real TypeScript discriminated union (`land`/`air`/`sea`) over the shared database row, even though storage itself is one table with mutually-exclusive columns. `server/queries/shipment-mode-baseline.ts` (`getShipmentModeProfile`). `server/mutations/shipment-mode-baseline.ts` (`setShipmentModeProfile`, `changeShipmentMode`).

UI: the Shipment Order detail page (`OPS-169`/`170`) gained a "Mode profile" section (`mode-profile-form.tsx` — only the fields relevant to the shipment's own current mode are ever rendered, irrelevant fields hidden rather than deleted, per Prompt 171 §15) and a "Change mode" control (`change-mode-form.tsx`, shown only while `status === 'draft'`).
