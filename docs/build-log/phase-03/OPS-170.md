## 2. Baseline reconciliation

`docs/build-log/phase-03/OPERATIONS_EXECUTION_INDEX.md` row `004` was `READY` — dependency `OPS-168..169` `VERIFIED`. Read in full: `170_SHIPMENT_LIFECYCLE_PROMPT.md`.

**Engine-reuse research performed before any schema was written** (Prompt 170 §4 asks for "a canonical shipment lifecycle whose status projection is driven by validated transitions" — the same shape Platform Core's own generic Workflow Engine, `PLT-122`, and Status Engine, `PLT-124`, already offer as reusable substrates elsewhere in this codebase). Investigated both directly before committing to a design:

- **Workflow Engine (`PLT-122`, `20260717140000_create_workflow_engine.sql`)**: has the closest functional shape (`app.start_workflow_instance`/`app.transition_workflow_instance`, optimistic concurrency, idempotent start, guard evaluation, instance history) — but its own §12 explicitly states "domain workflows beyond [its own isolated] example... broad module adoption" are out of scope, and it remains disclosed as having zero real consumers (`docs/build-log/phase-01/PLT-122.md` line 80). Binding Shipment Lifecycle to it would contradict its own stated boundary.
- **Status Engine (`PLT-124`, `20260719100000_create_status_engine.sql`)**: a label/presentation registry only — no `entity_type`/`entity_id` polymorphism, no transition matrix, no optimistic concurrency, no append-only history, no per-entity current-state projection. Its own build log names Shipment explicitly as a future *consumer of status labels*, never as the substrate for transition/lifecycle logic itself.
- **Every real status transition already shipped** (`COM-153`'s own `approval_status`, `OPS-168`'s `job_orders.status`, `OPS-169`'s own `shipment_orders.status`) is independently hand-rolled per capability — no capability anywhere in this repository has ever bound to `PLT-122`/`PLT-124` for its own domain lifecycle.

**Conclusion**: this checkpoint follows the same established, consistent precedent — a bespoke, Operations-owned transition system — rather than force-fitting an engine whose own header disclaims this exact use.

## 3. Implementation

### 3.1 Scope boundaries (disclosed, migration header)

1. `app.shipment_orders.status` (broadened from `OPS-169`'s original `draft`/`confirmed`/`cancelled` via `DROP CONSTRAINT` + `ADD CONSTRAINT` in this new migration — never an edit to `OPS-169`'s own file) is the current-state projection; `app.shipment_status_transitions` is the append-only evidence explaining it, never the other way around.
2. `held` suspends from any active non-terminal status and records `held_from_status`; a held shipment may only resume into that exact recorded status, never an arbitrary one.
3. `closed` may only reopen into `delivered`/`epod` — a bounded, one-step-back correction, restricted to Supreme Admin (`app.is_supreme_admin`, the RPD-022 disclosed absolute-CRUD exception every other hardening checkpoint already relies on). Normal users cannot rewrite history (Prompt 170 §24) — only Supreme may reopen, and even then only into the two states immediately preceding closure, never arbitrary rollback.
4. `evidence_ref` (a bounded, disclosed placeholder text reference, mirroring `app.job_orders.downstream_reference`'s own "structurally ready, not yet populated by a real consumer" disclosure) is required entering `delivered`/`epod`/`closed` — no real ePOD/document capability exists yet (`OPS-176`/`177`, out of this session's authorized range).
5. Milestone/exception/assignment/billing gates (Prompt 170 §20 task 3) are explicitly **not** implemented here — `OPS-172`/`173`/`174` and Finance's own billing readiness do not exist yet; this transition function is the one stable entry point those future capabilities will call into, not a placeholder they must rebuild.

### 3.2 Schema — `supabase/migrations/20260727110000_create_operations_shipment_lifecycle.sql`

`app.shipment_orders_status_check` broadened to the full 11-state canonical set (additive constraint replacement on an existing table, not an edit to `OPS-169`'s migration file). New column `held_from_status` (nullable, CHECK-constrained to the 5 active states it can hold from). `app.shipment_status_transitions` (append-only, idempotent on `(tenant_id, shipment_order_id, idempotency_key)`, the same "unique_violation caught, current row re-selected" pattern `OPS-168`/`169` already established). `app.transition_shipment_order` (`OPS:Edit`-gated, optimistic concurrency, the full hardcoded canonical matrix, reason mandatory entering held/cancelled, evidence mandatory entering delivered/epod/closed, Supreme-only reopen). `app.get_shipment_status_history` (authority-gated, ordered oldest-first, mirroring `app.get_workflow_instance_history`'s own established shape). `app.confirm_shipment_order`/`app.cancel_shipment_order` (`OPS-169`) remain unchanged and still valid — this migration does not remove or redirect them, it only adds the fuller matrix alongside.

### 3.3 Service layer and UI

`server/contracts/shipment-lifecycle/shipment-lifecycle.ts` (transition/history schemas). `server/queries/shipment-lifecycle.ts` (`getShipmentStatusHistory`). `server/mutations/shipment-lifecycle.ts` (`transitionShipmentOrder`, reusing `server/contracts/shipment-order`'s own `parseShipmentOrder` for its return shape rather than duplicating it). `server/contracts/shipment-order/shipment-order.ts` updated: `SHIPMENT_ORDER_STATUSES` broadened to the full canonical set, `heldFromStatus` field added — a TypeScript contract file, not a migration, so directly editable (only applied SQL migrations are immutable).

UI: the Shipment Order detail page (`OPS-169`) gained a "Status timeline" section (`status-timeline.tsx`, ordered oldest-first) and a unified "Transition" section (`transition-shipment-order-form.tsx`) offering only the permitted next states for the shipment's current status (`lifecycle-transitions.ts`, a UI-affordance-only restatement of the database's own canonical matrix, never authoritative). ## 4. Tests

### 4.1 Real database tests (`scripts/db-tests/operations-shipment-lifecycle.sql`, via `pnpm run db:test`)

Setup: one tenant, a company/team-a/team-b org hierarchy, a bootstrap tenant-admin, a rep, an OPS-viewer-only actor, a sibling-team outsider, a global Supreme Admin, one confirmed Job Order, and two confirmed Shipment Orders (one driven through the full lifecycle walk, one kept simple for auxiliary checks). Assertions: authority-gated (OPS:View-only denied); an illegal skip-ahead transition (confirmed → delivered) rejected; `reason_required` entering held without a reason; a valid `confirmed → planned` transition; hold/resume (`planned → held` records `held_from_status`, resume into an arbitrary wrong target rejected, resume into the correct `held_from_status` succeeds and clears it); the remaining forward path (`planned → assigned → dispatched → in_transit`); `evidence_required` entering delivered without an evidence reference; a valid `in_transit → delivered → epod → closed` walk; a closed shipment is terminal for an ordinary attempt, reopening (`→ delivered/epod`) is denied for an ordinary rep and succeeds for Supreme Admin; idempotent retry (same key returns the unchanged current row); a stale `expected_version` rejected; a cancelled shipment is terminal; record-scope isolation (sibling-team outsider denied via both `transition_shipment_order`/`get_shipment_status_history`); cross-tenant isolation; schema-privilege defense in depth (`anon` holds zero `EXECUTE` on either new function); `get_shipment_status_history` returns exactly 10 ordered transitions for the walk shipment, oldest confirmed→planned first, most recent the Supreme reopen (closed→delivered) last; audit trail (exactly 12 `transition_shipment_order` events across both fixtures — 10 walk + 2 auxiliary, idempotent retries and the post-cancel invalid-transition attempt are both no-ops).
