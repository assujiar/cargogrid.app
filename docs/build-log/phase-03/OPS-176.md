## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

This capability never re-implements file storage, malware scanning, or the private/signed-URL access gate — all of that is the Platform Document/File Engine's own job (`PLT-128`, `app.files`/`app.document_types`, already shipped). OPS-176 owns exactly one new thing: *which* document type is required for *which* shipment, and the *review* verdict once a file has been linked. A checklist item references `app.files.id` and re-reads that row's own `malware_scan_status` live — never a second copy that could drift.

Requirement definitions are versioned, tenant-scoped `draft -> published -> archived` rows, one active match per `(tenant_id, mode, service_type, applicable_status, party, document_type_code)` — the same considered choice `OPS-173`/`174` already made over Configuration Engine reuse. `mode`/`service_type` are nullable wildcards.

The checklist is pinned once per shipment, re-synced only on explicit request (`app.pin_shipment_document_checklist` is additive-only — never removes or overwrites an already-pinned row). A rejected/expired document is replaced, never deleted: every link/review decision is preserved in the append-only `app.document_checklist_events` table, even after a checklist item's own `file_id` pointer moves on.

Approval requires a clean scan; rejection does not (RPD-032, "unsafe files never satisfy requirements") — `app.review_document_checklist_item` refuses to approve a checklist item whose linked file has not resolved to `malware_scan_status='clean'`. Completeness (`app.evaluate_shipment_document_checklist_completeness`) is a pure, `STABLE`, side-effect-free read — the disclosed forward seam ePOD (`OPS-177`) and Billing Readiness (`OPS-181`) will call, mirroring `OPS-175`'s own `app.evaluate_dispatch_readiness` precedent.

`effective_status` (`missing`/`pending_review`/`approved`/`rejected`/`expired`) is always computed live from `review_status`/`expires_at`/the linked file's current scan status — never a fourth stored column a scheduler-less repository would have to sweep.

### 3.2 Schema — `supabase/migrations/20260728090000_create_operations_document_requirement.sql`

`app.document_requirement_definitions` (versioned draft/published/archived, unique partial indexes on the match key per status), `app.shipment_document_checklist_items` (pinned snapshot, `unique(tenant_id, shipment_order_id, requirement_definition_id)`), `app.document_checklist_events` (append-only pin/link/approve/reject history). Functions: `app.create_document_requirement_draft`, `app.publish_document_requirement_version` (archives the prior published match), `app.pin_shipment_document_checklist` (additive-only sync), `app.link_document_to_checklist_item` (tenant/record/type-mismatch validated), `app.review_document_checklist_item` (scan-gated approval), `app.get_shipment_document_checklist` (live effective-status projection), `app.evaluate_shipment_document_checklist_completeness` (pure completeness evaluation). All authority-gated via `app.evaluate_permission(..., 'OPS', 'Create'|'Edit'|'View')` plus `app.can_access_record` record-scope, matching `OPS-174`/`175`'s own pattern exactly.
