## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

No new table, no duplicate analytics store: every read composes only already-`VERIFIED` tables (`app.shipment_orders` OPS-169, `app.shipment_milestone_projections` OPS-173, `app.operational_exceptions` OPS-174, `app.epod_captures` OPS-177, `app.shipment_actual_costs` OPS-178, `app.billing_readiness_evaluations` OPS-181). Every function is `security definer` with its own explicit, re-stated `app.can_access_record(...)` row filter, mirroring `COM-158`'s own Commercial Dashboard precedent exactly (this repository's Commercial Dashboard header already proved empirically why an invoker-mode read fails for the identical reason). `app.dashboard_scope_org_unit_ids`, already created at `COM-158`, is reused directly for the optional branch/department drill-down filter — no duplicate wrapper.

Cost variance is field-masked via `app.has_view_actual_cost` (`OPS-178`) — the same gate `app.shipment_actual_costs_directory` already uses; a masked row returns `null`/`true`, never a zero. Only approved (`is_current`, `status='approved'`) actual-cost rows carrying a non-null, non-zero `estimated_amount` contribute — a shipment with no estimate is simply absent, never a fabricated 0% variance. Milestone SLA only considers shipments still in transit (`status not in ('closed', 'cancelled')`); a shipment with no projection row at all gets its own explicit `no_projection` bucket. Billing readiness summary reads the current evaluation only (`is_current=true`), scoped via `app.job_orders`' own record-scope columns. No caching layer, no privileged-access audit trail — the same two disclosed boundaries `COM-158`'s own header already established.

## 8. Errors / recovery / risks / issues

One real record-scope discovery during fixture authoring, not a migration bug: `app.create_shipment_order_from_job` (`OPS-169`) never stamps `org_unit_id` on the Shipment Order it creates (only `owner_user_id`), so `app.can_access_record`'s shared-org-unit branch can never admit a non-owner teammate to a shipment — only direct ownership or the Supreme Admin bypass grants access. An initial db-test design assumed a same-team "restricted" actor (not the record's own creator) would see cost-variance rows in masked form; this actor saw zero rows instead. Corrected by dropping the separate restricted-actor role entirely and instead downgrading **rep's own role** (a new role version omitting `OPS:View cost`, published after every fixture row already existed) — rep remains the owner throughout, so record-scope is unaffected, while the masking gate now correctly triggers; this is a more realistic scenario than the original design ("a role's permissions changed after data already existed") and needed no fixture actor added. Also caught and fixed: an accidental tenant-slug/email collision with `COM-158`'s own `commercial-dashboard.sql` fixture (both independently chose `acmedash`/`rep@acmedash.test`), renamed to `acmeopsdash`. Zero Critical/High-severity issue remains open. Zero regression to any prior capability.
