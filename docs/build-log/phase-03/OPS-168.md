## 3. Implementation

### 3.1 Scope boundaries (disclosed, migration header)

1. Every snapshot column (`customer_snapshot`/`cargo_service_snapshot`/`revenue_snapshot`/`contract_snapshot`/`credit_snapshot`/`acceptance_snapshot`) is a verbatim `jsonb` copy of the handoff's own already-canonical payload sub-object — never re-derived or re-typed. `account_id` is a live canonical FK, not a copy.
2. Idempotency key is `(tenant_id, source_handoff_id)` — one Commercial source/version/purpose yields exactly one Job Order outcome, including under a concurrent-insert race (`unique_violation` handler re-selects rather than raising).
3. Sensitive-field masking reuses Commercial's own two entitlement dimensions directly (`app.has_view_selling_price`/`app.has_view_cost`) rather than inventing a redundant OPS-level pair — "conversion never broadens Commercial access" (Prompt 168 §16) means an `OPS:Create` holder without `COM:View selling price` still cannot see `revenue_snapshot`/`credit_snapshot` after conversion, the same as before it.
4. The one bounded correction path (`app.override_job_order_field`) is restricted to `customer_snapshot`/`cargo_service_snapshot` only — `revenue_snapshot`/`contract_snapshot`/`credit_snapshot`/`acceptance_snapshot` remain immutable financial/acceptance evidence; a pricing or acceptance correction is a new Commercial quotation version (`COM-152`), never an Operations override.

### 3.2 Schema — `supabase/migrations/20260727090000_create_operations_job_order.sql`

`app.job_order_number_counters`/`app.next_job_order_number` (atomic `JOB-YYYY-NNNNNN` allocation). `app.job_orders` (the canonical Operations execution root — first Operations-domain table in this repository). `app.job_order_overrides` (append-only, always-reasoned evidence). `app.get_job_order_conversion_readiness` (structural pre-check, reason codes only). `app.prepare_job_order` (`OPS:Create`-gated, idempotent conversion). `app.confirm_job_order` (`OPS:Edit`-gated, draft→confirmed, optimistic concurrency). `app.override_job_order_field` (`OPS:Override`-gated, mandatory reason). `app.job_orders_directory` (field-masked projection). RLS on both tables uses the real `app.can_access_record(...)` check (not `using(false)`) — a design error caught and corrected during authoring by checking `app.quotations`' own `COM-151` precedent before finalizing (see §8). `revoke execute on all functions in schema app from public` present per ERR-2026-004.

### 3.3 Service layer and UI

`server/contracts/job-order/job-order.ts` (Job Order/override/readiness schemas). `server/queries/job-order.ts` (server-paginated `listJobOrders` mirroring `listLeads`' own `range()`/`count` shape, plus `getJobOrder`/`getJobOrderForHandoff`/`getJobOrderConversionReadiness`). `server/mutations/job-order.ts` (`prepareJobOrder`/`confirmJobOrder`/`overrideJobOrderField`).

## 8. Errors / recovery / risks / issues

Two issues found and fixed during authoring, before any db-test was run:

1. **RLS design error**: the first draft of `job_orders_select_scoped` used `using (false)` (blocking all direct `authenticated` access, forcing every read through `app.job_orders_directory`) paired with a redundant grant-all-then-revoke-two-columns statement. Caught by checking `app.quotations`' own `COM-151` precedent before running any test — it uses the real `app.can_access_record(...)` check plus an explicit column-level grant excluding the sensitive columns directly, since a bare column-level `REVOKE` cannot carve an exception out of a broader table-level `GRANT`. Corrected to match exactly.
2. **Self-escalation guard on first `db:test` run**: `scripts/db-tests/operations-job-order.sql`'s "full-access rep" role carries protected permissions (`COM:View selling price`/`COM:View cost`) and was originally self-assigned (same identity as both target and granter), tripping `app.assign_role`'s `self_escalation` guard (`p_actor_auth_user_id = p_auth_user_id` plus a protected permission). Fixed by adding a dedicated bootstrap tenant-admin identity (granted via `app.grant_principal_membership` directly, not `assign_role`) to act as the granter for that one assignment, mirroring `COM-163`'s own hardening-test fixture. A second, related fix: `app.create_rate_version`/`app.approve_rate_version` require Supreme/tenant_admin authority, not `COM:Create` — the same bootstrap admin identity was used as actor for those two calls too, matching every other Commercial pipeline fixture's own precedent (e.g. `commercial-job-order-lineage.sql`).

Zero Critical/High-severity issue remains open. Zero regression to any prior capability.
