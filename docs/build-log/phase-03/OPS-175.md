## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **List/queue dispatch only** (§24: "not dispatch board, route/load/capacity optimization or telematics"). `app.dispatch_ready_queue` is a plain, RLS-scoped view over `app.shipment_orders` joined to a real readiness computation — no load-planning, routing, or telematics surface is built.
2. **Dispatch is a thin, readiness-gated wrapper, never a second parallel state machine** (§24: "a validated lifecycle command, not direct status edit"). `assigned -> dispatched` has been a legal edge of `OPS-170`'s own `app.transition_shipment_order` matrix since that capability shipped; `app.dispatch_shipment_order` adds exactly one new thing in front of it — a real, re-checked-at-commit-time readiness gate (§25: "recheck authorization/readiness at commit time") — then calls `app.transition_shipment_order` internally for the actual state change. Hold/release/reassign for an already-planned-or-later shipment already have their own real, validated commands (`app.transition_shipment_order` for hold/release, `OPS-172`'s own `app.reassign_resource`); neither is rebuilt here.
3. **Bounded, disclosed readiness checklist** (§20 task 1): (1) `status = 'assigned'`; (2) at least one current, active resource assignment (`OPS-172`'s own `app.resource_assignments`) — a per-mode required-role matrix (e.g. land requires vehicle+driver) is explicit Phase 5 (Advanced TMS) scope, not built here; (3) no blocking operational exception (`OPS-174`'s own `app.operational_exceptions` in `open`/`acknowledged`/`reopened`); (4) `planned_pickup_at` is set. Required-document readiness (§13/§20 task 1's "doc... controls") is explicitly `NOT_RUN` — no Document Requirement capability (`OPS-176`, out of this session's own authorized range) exists yet to check against, the same "mechanism proven, live wiring deferred once the real dependency ships" posture already disclosed at `PLT-107`/`PLT-120`.
4. **Bounded, per-record atomic/idempotent bulk dispatch** (§20 task 3/§24: "per-record atomic/idempotent... explicit partial result"). Capped at 50 records per call; every record is independently permission/record-scope/readiness-rechecked and independently idempotent through the exact same `app.dispatch_shipment_order` path — one record's failure never aborts another's, and the caller always receives a full, explicit per-record result row, never a silent partial success.
5. **Idempotency-first ordering.** `app.dispatch_shipment_order` checks `app.dispatch_commands` for an existing `(tenant, shipment, idempotency_key)` row **before** any readiness recheck, so a genuine retry of an already-succeeded dispatch always returns the prior result rather than incorrectly re-evaluating readiness against a shipment that has since moved past `assigned`.
6. **Failure audit capture was designed, then deliberately removed** after discovering it could never persist: a `raise exception` unwinds to the nearest enclosing exception block (the caller's own, or `app.bulk_dispatch_shipment_orders`' per-record catch), which rolls back to an implicit savepoint and silently discards any insert made before the raise. Blockers are surfaced only in the raised exception message itself, matching every other validation-failure path in this repository (none of which persists a failure audit row for a raised-and-caught exception either).

### 3.2 Schema — `supabase/migrations/20260727160000_create_operations_basic_dispatch.sql`

## 8. Errors / recovery / risks / issues

Several real issues found and fixed before the full suite passed, all confined to this checkpoint's own new files: (1) a db-test authoring bug — `select record_version into v_shipment` (a single-column select) assigned into a full `app.shipment_orders`-typed row variable, corrupting the row and later raising `invalid input syntax for type uuid`; corrected to `select * into v_shipment`. (2) A real migration bug in `app.dispatch_shipment_order`'s own failure-path `capture_audit_event` call: a stray text-message argument was passed into the function's `jsonb` `p_before_value` parameter, raising `invalid input syntax for type json`. (3) After fixing (2), a second real bug surfaced in the same call: `v_readiness.blockers` (a jsonb **array**) was passed directly to `app.redact_audit_payload`, which only accepts a jsonb **object** (it iterates via `jsonb_each`); raised `cannot call jsonb_each on a non-object`. (4) Investigating further revealed the entire failure-audit-capture design was unreachable: Postgres exception-block semantics roll back any insert made before a caught `raise exception` to the enclosing block's own implicit savepoint — true both in the db-test's own `exception when others` wrapper and inside `app.bulk_dispatch_shipment_orders`' per-record catch. Root-cause fixed by removing the failure-path `capture_audit_event` call entirely (blockers are carried in the raised exception message instead) and correcting the db-test's own audit-trail assertion from an expected "3 failure events" to the architecturally-correct "0 persisted failure events." (5) A db-test column-name bug (`outcome` instead of the real `app.audit_logs.result` column) in the same audit-trail assertion. (6) Two vendor-resource-conflict/actor-choice fixture bugs during authoring (documented in-session): reusing one vendor master record across multiple ready fixtures tripped `OPS-172`'s own `assignment_conflict` rule (fixed with 4 distinct vendor records); and 4 `get_dispatch_readiness` read-success assertions initially used the "viewer" (`OPS:View`-only, same-team) actor, which fails record-scope despite shared team membership — corrected to the actual shipment owner (`rep`), matching this session's own established "viewer is negative-tests-only" convention. Zero Critical/High-severity issue remains open. Zero regression to any prior capability once all root causes were corrected.
