## 4. Findings and fixes

**Finding 1 (Critical)** — `app.prepare_job_order` (`OPS-168`) checked only tenant-wide `OPS:Create`, never `app.can_access_record` against the source `app.job_order_handoffs` row (which carries `owner_user_id`/`org_unit_id`) before copying its revenue/contract/credit snapshot payload into a new Job Order the calling actor now owns. Any actor holding tenant-wide `OPS:Create` could convert any handoff in the tenant, including ones outside their own org-unit/ownership scope. The same bug class as `OPS-185`'s own finding (`app.record_transaction_lineage_override`), found in a different function.

**Finding 2 (Critical)** — `app.create_shipment_order_from_job` (`OPS-169`) checked only tenant-wide `OPS:Create`, never `app.can_access_record` against the source `app.job_orders` row, before creating a Shipment Order that inherits its customer/cargo snapshot.

**Finding 3 (High, bounded)** — `app.detect_transaction_lineage_anomalies`'s (`OPS-184`) two single-record orphan diagnostics (`orphan_shipment_order`, `orphan_billing_readiness`) returned every orphan tenant-wide with zero record-scope filtering, unlike its own sibling `app.get_transaction_lineage` in the same file. Fixed by filtering each on its own row's (or, for billing-readiness, its Job Order's) owner/org columns. The other two diagnostics (`duplicate_target`, `cross_tenant_mismatch`) are deliberately left tenant-wide: both compare two edges that, by definition, may belong to different owners/org units, so no single record scope applies — an earlier attempt to filter these two broke a real, correct pre-existing assertion in `OPS-184`'s own db-test, confirming the distinction is genuine, not merely theoretical.

**Finding 4 (Medium, financial precision)** — `app.job_profitability_snapshots.revenue_amount`/`cost_amount` (`OPS-179`) had no `>= 0` check constraint, unlike every other monetary column in the Operations schema. `margin_amount` correctly remains unconstrained (a genuine loss is a legitimate negative margin).

**Categories swept with zero findings** (disclosed, not padded): audit capture (every mutating function across all 18 files calls `app.capture_audit_event`); money precision beyond Finding 4 (zero `float`/`double precision`/`real` columns anywhere in the Operations schema); anon-facing surface (`app.lookup_public_shipment_tracking` remains the one and only `anon`-granted function, already rate-limited and attempt-logged per `OPS-180`'s own db-test); IDOR/enumeration (every authenticated-facing function already uses the consistent `X_not_found`/`insufficient_authority` two-step pattern).
