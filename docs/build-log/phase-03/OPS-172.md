## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Master-type binding decision.** `OPS-171` deliberately left `vehicle_ref`/`vendor_ref` as plain text, disclosing that "binding these fields to real canonical vendor/fleet/vehicle/driver references is `OPS-172`'s own explicit scope." Rather than inventing a bespoke reference table (an unauthorized "new master lifecycle," Prompt 172 §24), this migration registers four new master types into the already-built generic master-data registry (`app.master_types`/`app.master_records`, `PLT-120`) — `vendor` and `fleet` and `vehicle` (`owner_module_code` `PRC`) and `driver` (`owner_module_code` `HRS`) — seeded via a direct `INSERT`, the same way `PLT-120`'s own `vendor_rate` was seeded. This satisfies Prompt 172 §20 task 2's "candidate lookup against existing canonical references without new master lifecycle" literally: `app.master_records` IS the existing canonical reference system. This migration adds zero create/update/deactivate/merge path over `app.master_records` itself — those remain exclusively `PLT-120`'s own `app.create_master_record`/`app.update_master_record`/`app.deactivate_master_record`/`app.merge_master_records` (service_role-gated, tenant_admin/Supreme-authorized).
2. **PII minimization** (Prompt 172 §26: "driver/vendor PII and cost fields require explicit permission"). `app.master_records.attributes` is a broad, tenant-membership-scoped-readable jsonb bag (`PLT-120`'s own `master_records_select_scoped` policy, unmodified here) that may come to hold driver PII once a real HRIS/Procurement capability populates it. This capability's own new surface honors §26 directly: `app.resource_assignments.resource_snapshot` is limited to `{code, name}` only, never the full `attributes` blob, and `app.find_assignment_candidates` projects only `{id, code, name}`, never `attributes`. Broadening or narrowing `app.master_records`' own base-table RLS is `PLT-120`'s own capability surface and is not reopened or silently patched here.
3. **Assignment model** (Prompt 172 §24/§25). `app.resource_assignments` is a hybrid append-only/in-place table. `is_current` marks the one row (if any) currently occupying a `(shipment_order_id, role)` slot — enforced by a real partial unique index (`resource_assignments_current_role_unique`, partial on `is_current`, not `status`, so a held assignment still occupies its slot), never merely a convention. `app.reassign_resource` is the one path that creates a genuinely new row (preserving the prior row's own outcome/effects per §25 — `superseded_by_id` links backward, the prior row is never deleted or overwritten); `app.hold_resource_assignment`/`app.resume_resource_assignment`/`app.unassign_resource` are in-place status flips on the one current row.
4. **Conflict detection** (Prompt 172 §20 task 1's "availability/conflict checks") is deliberately bounded and simple for this "basic" capability: a `resource_id` may not hold a live (`is_current` and `status='active'`) assignment on more than one non-terminal Shipment Order at once, across any role. Multi-resource scheduling, calendars, capacity/utilization optimization and true time-window overlap arithmetic all remain explicit Phase 3/5 (Advanced TMS) scope, never anticipated here.
5. This capability does not own vendor onboarding or fleet/driver master lifecycle (Prompt 172 §24) — those remain `PLT-120`'s own scope, unchanged.

### 3.2 Schema — `supabase/migrations/20260727130000_create_operations_resource_assignment.sql`

Four `app.master_types` seed rows (`vendor`/`fleet`/`vehicle` → `PRC`, `driver` → `HRS`). `app.resource_assignments` (role check in `vendor`/`fleet`/`vehicle`/`driver`, status check in `active`/`held`/`unassigned`, `resource_snapshot` limited to `{code, name}`, `superseded_by_id` self-FK, partial unique index on `(tenant_id, shipment_order_id, role)` where `is_current`). Seven functions: `app.find_assignment_candidates` (read-only, minimized-projection candidate lookup, `OPS:View`-gated), `app.assign_resource` (`OPS:Assign`-gated — the first real consumer of this pre-seeded permission action — `already_assigned`/`assignment_conflict`/`invalid_resource` distinctly raised), `app.reassign_resource` (reason-mandatory, releases the prior row before inserting the new one so the partial unique index is never violated even momentarily), `app.hold_resource_assignment`/`app.resume_resource_assignment` (`OPS:Edit`-gated in-place status flips, mirroring `OPS-170`'s own hold/resume-as-transient-substate precedent), `app.unassign_resource` (`OPS:Assign`-gated, releases the role slot), `app.get_resource_assignment_history` (authority-gated, ordered oldest-first). RLS mirrors `OPS-171`'s own `shipment_mode_profiles` pattern (join to `app.shipment_orders`, `can_access_record` + `lead_record_scope_org_unit_ids`). Per `ERR-2026-004`: explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` before final grants.

### 3.3 Service layer and UI

`server/contracts/resource-assignment/resource-assignment.ts` — role/status enums, `ResourceSnapshotSchema` (`.strict()`, rejecting any key beyond `{code, name}` — a real defense-in-depth check against an attributes leak, not merely documentation), `ResourceAssignmentSchema`, `AssignmentCandidateSchema`, and one input schema per mutation/query. `server/queries/resource-assignment.ts` (`findAssignmentCandidates`, `getResourceAssignmentHistory`). `server/mutations/resource-assignment.ts` (`assignResource`, `reassignResource`, `holdResourceAssignment`, `resumeResourceAssignment`, `unassignResource`).

UI: the Shipment Order detail page (`OPS-169`/`170`/`171`) gained a "Resource assignments" section — one `ResourceAssignmentPanel` per role (vendor/fleet/vehicle/driver), each showing the current assignment (if any) with its minimized snapshot and status, and the one action set available for its current state (assign from the tenant-scoped active-candidate list; or reassign/hold-resume/unassign once a current row exists) — plus a read-only, oldest-first `ResourceAssignmentHistory` list.

## 4. Tests

### 4.1 Real database tests (`scripts/db-tests/operations-resource-assignment.sql`, via `pnpm run db:test`)

Setup: one tenant, a company/team-a/team-b org hierarchy, a bootstrap tenant-admin, a rep (`COM` full + `OPS:Create/Edit/View/Assign`), an OPS-viewer-only actor, a sibling-team outsider, one confirmed Job Order, three Shipment Orders off it (main/conflict/cancel), and five master records (3 active vendors, 1 fleet, 1 vehicle, 1 driver, plus one deactivated decoy vendor). Assertions: `find_assignment_candidates` rejects `invalid_role`, returns only active vendor candidates (decoy excluded); `assign_resource` is authority-gated (`OPS:View`-only denied `OPS:Assign`), rejects `invalid_resource` for a role/master_type mismatch, creates a real row with a `{code,name}`-only snapshot, rejects a repeat call as `already_assigned`; `assignment_conflict` when the same vendor is already active on a different, non-terminal shipment; `hold_resource_assignment`/`resume_resource_assignment` reason-required, `invalid_transition` outside the expected starting state, and a held assignment still occupies its slot (`already_assigned` blocks a fresh assign); `reassign_resource` reason-required, `no_current_assignment` on a role never assigned, a valid reassign creates a new row and marks the prior row `is_current=false`/`superseded_by_id` set while preserving its own historical reason; `unassign_resource` reason-required, releases the slot, and a subsequent assign creates a fresh row; blocked (`invalid_transition`) once the shipment is cancelled; `get_resource_assignment_history` ordered oldest-first; record-scope isolation (sibling-team outsider denied); cross-tenant isolation; schema-privilege defense in depth (`anon` holds zero `EXECUTE` on all 7 new functions); audit trail (6 `assign_resource`, 1 `reassign_resource`, 1 `hold_resource_assignment`, 1 `resume_resource_assignment`, 1 `unassign_resource` events). All 58 db-test files pass together, zero regression.

## 8. Errors / recovery / risks / issues

Several test-authoring fixture collisions found and fixed before the full suite passed: (1) the initial "held assignment still occupies its slot" assertion attempted to assign a vendor that was already actively assigned elsewhere, triggering `assignment_conflict` before the intended `already_assigned` check could be reached — fixed by adding a third, otherwise-unused vendor fixture (`VEND-3`) reserved for that exact assertion; (2) the same collision recurred in the `reassign_resource` test for the identical reason — fixed by reassigning to `VEND-3` instead of the already-elsewhere-assigned `VEND-2`; (3) an initial `no_current_assignment` test accidentally exercised a real, successful reassignment instead (reassigning a resource to itself is not itself an error condition) — replaced with a genuine no-current-assignment scenario on the conflict shipment's never-assigned `fleet` role. Zero Critical/High-severity issue remains open. Zero regression to any prior capability.
