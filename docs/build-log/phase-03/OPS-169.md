## 3. Implementation

### 3.1 Scope boundaries (disclosed, migration header)

1. Every Shipment Order belongs to exactly one Job Order and requires that Job Order be `confirmed` (`job_order_not_confirmed` otherwise) — the one gate `OPS-168` itself named as making a Job Order eligible for this.
2. `shipper_account_id`/`cargo_service_snapshot` are inherited verbatim from the Job Order (a live FK and a governed snapshot respectively); `consignee_snapshot` defaults to the Job Order's own `customer_snapshot` but may differ (e.g. a drop-ship destination) since it is not forced through the same account reference.
3. **Allocation-basis design decision (disclosed)**: Commercial's own `JobOrderDraftInput.cargoService` is deliberately untyped jsonb — no guaranteed quantity/weight/volume sub-field exists to derive a job-level cap from. Rather than inventing one against an unknown source shape, the *first* Shipment Order ever created for a Job Order declares that Job Order's own allocation basis via its own `basis_quantity`/`basis_weight_kg`/`basis_volume_cbm` columns (each dimension independently, nullable = advisory-only for that dimension); every later Shipment Order's own `allocated_*` is simply its own share, checked against the running sum via `app.get_job_shipment_allocation_balance`. No override path exists in this bounded slice — an over-allocation attempt is a hard, structural block.
4. Mode/service stay a simple top-level classifier (`mode`/`service_type` text columns) — the per-mode typed baseline (land vehicle/vendor/route; air AWB/flight/airport; sea BL/booking/vessel/port/container) is `OPS-171`'s own explicit scope, not anticipated here.

### 3.2 Schema — `supabase/migrations/20260727100000_create_operations_shipment_order.sql`

`app.shipment_order_number_counters`/`app.next_shipment_number` (atomic `SHP-YYYY-NNNNNN`). `app.shipment_orders` (basis_*/allocated_* per dimension, idempotent on `(tenant_id, job_order_id, idempotency_key)`). `app.get_job_shipment_allocation_balance` (reads the basis from the very first row ever created for the job, regardless of that row's own current status, so a later cancellation of the first row never erases the declared basis). `app.create_shipment_order_from_job` (`OPS:Create`-gated, requires a confirmed Job Order, split-reason-required/allocation-balance-checked once a prior Shipment Order exists). `app.confirm_shipment_order`/`app.cancel_shipment_order` (`OPS:Edit`-gated, optimistic concurrency, record-scope-checked, mirroring `app.confirm_job_order`). No directory view — no masked column exists on this table (cost/selling data stays in `app.job_orders`' own `revenue_snapshot`/`credit_snapshot`, never duplicated here), so RLS plus a plain full-column grant is correct, matching `app.leads`'/`app.opportunities`' own convention for a table with nothing sensitive to carve out.

## 4. Tests

### 4.1 Real database tests (`scripts/db-tests/operations-shipment-order.sql`, via `pnpm run db:test`)

Setup: one tenant, a company/team-a/team-b org hierarchy, a bootstrap tenant-admin (Supreme/tenant_admin-gated rate authority only), a rep (`COM:Create/Edit/Approve/View/View cost` + `OPS:Create/Edit`), an OPS-viewer-only actor (`OPS:View`, no `Create`), a sibling-team outsider, and two independent Job Orders (one confirmed, one deliberately left in draft). Assertions: `get_job_shipment_allocation_balance` returns a null basis/remaining before any Shipment Order exists; `create_shipment_order_from_job` is authority-gated (an `OPS:View`-only actor denied), requires a confirmed Job Order (`job_order_not_confirmed` for the draft fixture), creates a real row with shipper/cargo inherited verbatim and consignee defaulted, is idempotent on `(tenant_id, job_order_id, idempotency_key)`; a second Shipment Order against the same Job Order requires a non-empty `split_reason`, is allocation-balance-checked (`over_allocation` blocked, a valid split succeeds and is reflected in the balance); `confirm_shipment_order` (stale version rejected, draft→confirmed, a second confirm rejected); `cancel_shipment_order` (empty reason rejected, a valid cancel releases its own allocation from the running balance); record-scope isolation (sibling-team outsider denied via both mutation functions against a fresh draft fixture); cross-tenant isolation (a tenant-2 admin with zero membership in the Job Order's own tenant denied via both `get_job_shipment_allocation_balance`/`create_shipment_order_from_job`); schema-privilege defense in depth (`anon` holds zero `EXECUTE` on any of the 5 new functions); audit trail (exactly 5 events — 3 real creates, 1 confirm, 1 cancel, since the idempotent retry is a no-op). All 55 db-test files pass together, zero regression.

**One design flaw found and fixed during test authoring, before any assertion was written to prove it wrong**: the first draft defined the allocation basis as "the first non-cancelled Shipment Order's own `allocated_*` values" — which is self-contradictory, since the very first shipment's own allocation would then *equal* the entire basis by construction, leaving zero headroom for any split ever. Caught while writing the split-allocation test scenario (the intended remaining balance came out negative). Fixed by adding three dedicated `basis_quantity`/`basis_weight_kg`/`basis_volume_cbm` columns, populated only on the very first Shipment Order created for a Job Order (via three new `p_basis_*` function parameters, structurally ignored on any later call), decoupling "the declared total capacity" from "this one shipment's own share of it."
