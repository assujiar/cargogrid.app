## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

Enforces complete, no-reentry lineage across the full Phase 3 quote-to-billing chain: Commercial's own accepted-quote handoff (`app.job_order_handoffs`, COM-160) -> Job Order (OPS-168) -> Shipment Order (OPS-169) -> ePOD (OPS-177) / Actual Cost (OPS-178) -> Job Profitability (OPS-179) -> Billing Readiness (OPS-181).

No prior migration is edited (the immutable-migrations convention every Phase 2/3 checkpoint has honored) -- this migration is purely additive: one new append-only edge table (`app.transaction_lineage_edges`) plus six new `AFTER INSERT` triggers on the six already-existing tables above. A trigger is the only way to capture "atomic lineage creation at each domain transition" (Prompt 184 §20.2) without reopening OPS-168/169/177/178/179/181's own migration files; every trigger function is a thin wrapper around one shared `app.capture_transaction_lineage_edge` insert-and-audit primitive.

No new permission-catalogue row: reads (`app.get_transaction_lineage`) reuse the identical `app.can_access_record` row-filter every OPS-182 dashboard function already uses (never a broader `evaluate_permission` gate on the read path); the correction/reconciliation actions (`record_transaction_lineage_override`, `detect_transaction_lineage_anomalies`, `backfill_transaction_lineage`) reuse the already-seeded `OPS:Override` action (OPS-181's own gate) rather than inventing a redundant lineage-specific permission.

Milestones (OPS-173) are deliberately **not** modeled as a persisted lineage edge: a shipment can accumulate many milestone events, and persisting one edge per event would be exactly the "unbounded graph query" Prompt 184 §17 forbids. The traversal folds in the shipment's own current `app.shipment_milestone_projections` row (already bounded, one row per shipment) as an attribute of the shipment node instead.

Customer/public-facing lineage is out of scope by design: OPS-180's own public tracking token already serves the "purpose-limited sanitized timeline, not the internal lineage graph" requirement (Prompt 184 §26) for external parties; `app.get_transaction_lineage` is for internal, tenant-authenticated roles only.

### 3.2 Schema — `supabase/migrations/20260728170000_create_operations_transaction_lineage.sql`

One new table, `app.transaction_lineage_edges` (append-only, unique on `(tenant_id, source_type, source_id, target_type, target_id, relation_type)` -- the "no silent re-entry" guarantee; a check constraint pins the exact `(relation_type, source_type, target_type)` triple for each of the 6 relation kinds). Seven new functions:

- `app.capture_transaction_lineage_edge` -- the shared idempotent insert-and-audit primitive (never granted to `authenticated`/`service_role`; only reachable via the triggers or the backfill function).
- Six trigger functions (`app.trg_capture_lineage_quote_to_job`/`job_to_shipment`/`shipment_to_epod`/`shipment_to_cost`/`job_to_profitability`/`job_to_billing_readiness`), each an `AFTER INSERT` trigger on its own already-existing target table.
- `app.get_transaction_lineage(p_job_order_id, p_actor_auth_user_id)` -- bounded, permission-aware traversal rooted at one Job Order, returning a single `jsonb` manifest.
- `app.record_transaction_lineage_override(...)` -- `OPS:Override`-gated, reason-mandatory corrective mapping.
- `app.detect_transaction_lineage_anomalies(p_tenant_id, p_actor_auth_user_id)` -- `OPS:Override`-gated read-only reconciliation diagnostic (orphan Shipment Orders, orphan billing-readiness evaluations, duplicate targets, cross-tenant mismatches).
- `app.backfill_transaction_lineage(p_tenant_id, p_actor_auth_user_id, p_actor_label)` -- idempotent brownfield reconciliation, reusing the capture primitive's own `ON CONFLICT DO NOTHING`.

### 3.3 Service layer and UI

No new route -- this is additive to an already-`VERIFIED` page, unlike every prior Phase 3 checkpoint's own new route.

## 4. Tests

### 4.1 Real database tests (`scripts/db-tests/operations-transaction-lineage.sql`, via `pnpm run db:test`)

Setup: one tenant, a rep (COM full + OPS full incl `Override`), a restricted actor (no `Override`), a sibling-team outsider (full grants incl `Override`, wrong record scope), and two independent accepted-quote funnels (funnel A drives a full shipment/ePOD/cost/profitability/billing-readiness chain; funnel B stays a bare confirmed Job Order, used only as the corrective override's new source). Proves: all six relation types auto-capture with zero manual RPC call anywhere in the fixture's own domain-transition code (the `quote_to_job` edge's hash is asserted equal to the handoff's own `payload_hash`); `app.get_transaction_lineage` is record-scope-gated (the sibling outsider denied despite full grants incl `Override`), raises `job_order_not_found` for an unknown id, and returns the complete manifest (1 shipment with its ePOD/cost/milestone children, profitability, billing readiness, all 6 edges) for the owning rep; `app.record_transaction_lineage_override` is `OPS:Override`-gated, reason-mandatory, rejects an already-existing pairing (`transaction_lineage_edge_already_recorded`), and a real corrective consolidation mapping (job B also claims job A's shipment) succeeds without touching job A's own original edge; `app.detect_transaction_lineage_anomalies` is `OPS:Override`-gated and correctly reports the override above as a genuine `duplicate_target`, a simulated data-loss delete as `orphan_billing_readiness`, and a directly-inserted mismatched-tenant row as `cross_tenant_mismatch`; `app.backfill_transaction_lineage` is `OPS:Override`-gated, idempotent (a second call backfills zero), and re-derives the exact edge the data-loss simulation deleted; RLS row-scoping and schema-privilege defense in depth (`anon` holds zero `EXECUTE` on all 4 new functions); audit trail. All 70 db-test files pass together, zero regression.

One fixture-authoring fix during setup: `app.calculate_job_profitability` also requires `OPS:View margin` (`app.has_view_job_margin`) in addition to `OPS:Edit` -- the rep's role was missing that action and was corrected before use, not a migration bug.

One design correction found during authoring: the first `cross_tenant_mismatch` query draft filtered by the edge's own stamped `tenant_id = p_tenant_id`, which can never find a row whose entire point is that it was stamped with the *wrong* tenant. Corrected to filter by the referenced Job Order's own actual `tenant_id = p_tenant_id` instead, so a caller investigating their own tenant's data can find an edge that incorrectly claims to belong to someone else's tenant.
