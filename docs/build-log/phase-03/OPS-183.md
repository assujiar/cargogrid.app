## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

Every report reuses an `OPS-182` `app.get_ops_dashboard_*` function as its one query engine, verbatim — this migration adds no new aggregation SQL. Of the seven report subjects Prompt 183 §4 names, the six `OPS-182`'s own dashboard already computes are implemented (shipment status, milestone SLA, exceptions, ePOD completion, cost variance, billing readiness); profitability has no existing governed *summary* query to reuse (`OPS-179`'s own `app.job_profitability_directory` is a per-Job-Order detail read, never an aggregate the dashboard computed) and is a disclosed, out-of-scope gap — the same class of gap `COM-159`'s own header disclosed for conversion/costing/pricing.

`app.report_types`/`app.report_runs`/`app.record_report_run` are **reused directly from `COM-159`** — no duplicate table, no duplicate bookkeeping function. These were already generic, schema-wide infrastructure despite their originating checkpoint, the same "reuse a prior checkpoint's own generic utility, don't fork it" precedent `OPS-182` already established for `app.dashboard_scope_org_unit_ids`. Report codes are globally unique (`code` is the table's own primary key) — no per-module namespacing needed. `app.record_report_run` performs no module-specific check at all (only tenant membership), so it applies unchanged to an Operations preview.

Export is the one genuinely new function: `app.enqueue_ops_report_export`, gated on `OPS:Export` (already seeded in the original `PLT-111` catalogue, previously unused by any Operations capability — the same "reuse an already-seeded, previously-idle permission action" choice `COM-159` made for `COM:Export`). It is a distinct, parallel entry point to `COM-159`'s own `app.enqueue_report_export` (which hard-codes `COM:Export`), not a modification of that immutable migration — both enqueue the identical `report_generation` job type via `PLT-132`'s own `app.enqueue_job` and insert into the identical shared `app.report_runs` table. No live worker processes a `report_generation` job anywhere in this repository — the same disclosed `NOT_RUN` condition `COM-159`'s own migration already carried, unchanged.

### 3.2 Schema — `supabase/migrations/20260728160000_create_operations_reports.sql`

One new function: `app.enqueue_ops_report_export` (`OPS:Export`-gated). No new table.

### 3.3 Service layer and UI

Reused directly (no new file): `server/contracts/report/report.ts`, `server/queries/report.ts`, and `recordReportRun` from `server/mutations/report.ts`. New: `server/mutations/ops-report.ts(.test.ts)` (`enqueueOpsReportExport`, the one genuinely new mutation).

UI: a new catalogue page `/[tenantSlug]/operations/reports`, a detail/run page `/[tenantSlug]/operations/reports/[reportCode]`, `run-report.ts` (dispatches a report code to its `OPS-182` dashboard query), `actions.ts`/`export-report-form.tsx` — all mirroring `commercial/reports/*`'s own exact structure (COM-159).

**One cross-module UX fix required, not a migration bug**: since `app.report_types` is one shared, global table, the pre-existing Commercial Reports catalogue page (`commercial/reports/page.tsx`, unfiltered) would have started listing this checkpoint's six new Operations codes too (and vice versa) — a direct-URL visit to an Operations report code from the Commercial route would render an empty table (COM-159's own `runReportByCode` switch defaults to `[]` for an unrecognized code, never a crash, but confusing UX). Fixed by adding an explicit known-code-set filter to both `commercial/reports/page.tsx` and `commercial/reports/[reportCode]/page.tsx` (the latter via a `notFound()` guard), and building the new Operations pages with the mirror-image filter from the start.
