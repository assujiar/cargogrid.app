## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Engine-reuse research performed before any schema was written**, the same discipline `OPS-170` established: the Configuration Engine (`PLT-121`) is the standing reuse vehicle every prior versioned-tenant-definition capability has used (Status Engine, Numbering Engine, Notification Templates, Feature Flags), but its own precedence model resolves across company/branch/role/user, an org-hierarchy dimension — this capability's own versioning axis is `mode` (land/air/sea), which does not fit any of Configuration Engine's real precedence dimensions. Concluded: mirror `COM-150`'s own simpler, directly tenant-scoped versioned-definition pattern (`app.margin_rule_versions`: draft → published → archived) instead, extended by one dimension (`mode`).
2. Milestone *codes* are a separate, permanent, platform-wide registry (`app.milestone_codes`), the same "canonical meaning is permanent, presentation/template membership is the only configurable surface" split Status Engine (`PLT-124`) already established for statuses. `is_customer_visible`/`affects_eta`/`is_terminal` are permanent properties of the code itself, never overridden per tenant.
3. Event time and received time are two distinct, both-retained columns on `app.milestone_events`. Corrections are additive — a correction is a new row whose own `corrects_event_id` points at the event it corrects, with a mandatory non-empty reason; the original row is never mutated.
4. `app.shipment_milestone_projections` is fully recalculated from every event on a shipment each time a new event is ingested (never an incremental patch), so duplicate/out-of-order/replayed events always converge to the same result.
5. External-source authentication is not reinvented — `app.ingest_milestone_event` still requires a real actor identity passing `OPS:Create`; `source` is a descriptive/audit classification, never an alternate authentication path. A real scoped-credential-to-identity binding for API/webhook callers is Platform Core's own already-shipped `app.api_keys`/webhook infrastructure (`PLT-129`), not duplicated here.
6. This capability does not build a second parallel shipment state machine — `app.shipment_orders.status`/`app.transition_shipment_order` (`OPS-170`) remains the one authoritative canonical lifecycle; milestone events are a supplementary, deterministic visibility/ETA projection layer.

### 3.2 Schema — `supabase/migrations/20260727140000_create_operations_milestone_management.sql`

`app.milestone_codes` (permanent registry, Supreme-only, idempotent `app.register_milestone_code`). `app.milestone_template_versions` (tenant-scoped, versioned per mode, draft → published → archived, at most one draft/published per `(tenant_id, mode)` via partial unique indexes): `app.create_milestone_template_draft` (`OPS:Create`-gated, idempotent), `app.set_milestone_template_sequence` (draft-only, validates each code immediately), `app.publish_milestone_template_version` (`OPS:Edit`-gated — no `OPS:Approve` action exists in the seeded permission catalogue, so `Edit` is the correct gate here — publish-time structural gate: non-empty, every code real, no duplicate, optimistic concurrency, supersedes the prior published version). `app.milestone_events` (append-only, idempotent on `(tenant_id, shipment_order_id, idempotency_key)`, server-assigned `sequence_no`): `app.ingest_milestone_event` (`OPS:Create`-gated, blocked once cancelled, correction requires a reason and a real prior event). `app.recalculate_shipment_milestone_projection` (internal, service_role-only, called by every real ingest). `app.get_shipment_milestone_timeline`/`app.get_shipment_milestone_projection` (`OPS:View`-gated reads).
