## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

A minimal, fast, read-only tracking surface — an unguessable per-shipment opaque token resolves to a sanitized status/timeline/ePOD-availability projection, never a live Customer Portal (that is out of scope, a later Phase). Token-based public access reuses `COM-154`'s own established pattern exactly: `token_hash = encode(digest(raw_token, 'sha256'), 'hex')`, the raw token minted with `encode(gen_random_bytes(32), 'hex')` and returned exactly once, at issuance — never stored, never retrievable again.

`app.lookup_public_shipment_tracking` is the one function in this entire schema granted `EXECUTE` to `anon` directly (disclosed exception to the standing `ERR-2026-004` "revoke from public, explicit re-grant" convention) — authorization is the token itself, not `auth.uid()`, since the party presenting a tracking link holds no CargoGrid account. It is deliberately designed to **never raise for a normal/expected outcome** (`not_found`/`invalid`/`rate_limited`): it always returns exactly one row with a `lookup_status` column, every other column null unless `lookup_status='ok'`. This is a direct application of the defect class `OPS-175` first discovered and documented for its own dispatch failure-audit design — a `raise exception` caught by (or aborting) the enclosing transaction rolls back **any insert made earlier in that same transaction**, so a "log the failed attempt, then raise" pattern would silently never persist `app.tracking_lookup_attempts`. Returning a status column instead lets the attempt-log insert commit as part of the function's own normal, successful return, which is the entire point of keeping that log at all.

Rate limiting counts `not_found`/`invalid` attempts for a caller-supplied `client_key` (a hash of the caller's own IP, computed by the calling Server Action / page — never a raw IP stored server-side) in the trailing 15 minutes; 10 or more flips the outcome to `rate_limited`. The sanitized milestone timeline reuses `OPS-173`'s own `app.milestone_codes.is_customer_visible` disclosed-visibility flag rather than inventing a second visibility predicate. `epod_available` is a boolean derived from `OPS-177`'s `app.epod_captures` (`is_latest_version and status='completed'`) — never the ePOD evidence itself (no signature/photo file, no receiver PII) is exposed on this surface.

### 3.2 Schema — `supabase/migrations/20260728130000_create_operations_public_tracking.sql`

`app.shipment_tracking_tokens` (`token_hash` unique, at most one `active` token per shipment via a partial unique index, `status` check `active`/`revoked`). `app.tracking_lookup_attempts` (append-only anti-enumeration evidence, distinct from `app.audit_logs`/`app.file_access_logs`; `client_key`, `result` check `success`/`not_found`/`invalid`/`rate_limited`, `occurred_at`). `app.issue_shipment_tracking_token` (`OPS:Edit` + record-scope gated; revokes any prior active token first). `app.revoke_shipment_tracking_token` (`OPS:Edit` + record-scope gated; reason mandatory). `app.lookup_public_shipment_tracking` (the one public RPC, described above). RLS on `shipment_tracking_tokens` scoped to `authenticated`; `grant execute on function app.lookup_public_shipment_tracking(text, text) to anon, authenticated, service_role` is the one clearly-disclosed exception in an otherwise `revoke ... from public` + explicit re-grant migration.

## 4. Tests

### 4.1 Real database tests (`scripts/db-tests/operations-public-tracking.sql`, via `pnpm run db:test`)

Setup: one tenant, a company/team-a/team-b org hierarchy, a bootstrap tenant-admin, a rep (`OPS` full), a sibling-team outsider (full grants, wrong record scope), two confirmed/assigned/dispatched Shipment Orders (one driven all the way through a completed ePOD capture, one left mid-transit), a mix of customer-visible and internal-only milestone codes. Assertions: issuing a token is authority-gated (`OPS:Edit` + record-scope) and returns a raw token exactly once; issuing again revokes the prior active token (`superseded_by_new_issuance`) — at most one active token per shipment at a time; a valid token resolves `lookup_status='ok'` with the sanitized projection (only `is_customer_visible` milestones appear; internal-only milestones are absent); `epod_available` reflects the completed-ePOD shipment as `true` and the mid-transit shipment as `false`; an unknown/garbage token resolves `'invalid'` without raising; a revoked or expired token resolves `'not_found'`/`'invalid'` without raising; 10 consecutive bad-token lookups from the same `client_key` within the rate-limit window flip the 11th lookup to `'rate_limited'`, and each of those 11 attempts is independently visible in `app.tracking_lookup_attempts` (confirming the attempt-log insert survives every non-`'ok'` outcome — the exact regression this checkpoint's redesign targets); revoking requires a non-empty reason and fails when no active token exists; schema-privilege defense in depth (`anon` holds `EXECUTE` on `lookup_public_shipment_tracking` only, zero `EXECUTE` on `issue_shipment_tracking_token`/`revoke_shipment_tracking_token`, and zero direct table access to `shipment_tracking_tokens`/`tracking_lookup_attempts`); record-scope/cross-tenant RLS on the management RPCs; audit trail (≥2 persisted events for issue/revoke). ## 8. Errors / recovery / risks / issues

One architecturally significant correction made during authoring: `app.lookup_public_shipment_tracking` originally used `raise exception` for `not_found`/`invalid`/`rate_limited` outcomes, each preceded by an insert into `app.tracking_lookup_attempts`. Testing showed the rate limiter never actually triggered after 10 failed lookups, because the raised exception rolled back every prior insert in the same transaction — the identical defect class `OPS-175` documented for its own dispatch failure-audit design. Fixed by redesigning the function's own return contract to a `lookup_status` column that is always returned, never raised, cascading into a rewrite of the db-test assertions and the TypeScript query layer to match. Two smaller `plpgsql` defects were also caught and fixed during authoring: an ambiguous-column reference inside `issue_shipment_tracking_token`'s own `update ... where shipment_order_id = ...` (the function's `returns table(...)` declares an OUT column of the identical name — fixed by aliasing the update target), and untyped `null` literals in the early-return branches failing to structurally match the declared `returns table(...)` types (fixed with explicit casts). Zero Critical/High-severity issue remains open. Zero regression to any prior capability.
