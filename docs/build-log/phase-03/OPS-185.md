## 5. Finding and fix (the primary result of this checkpoint)

**Discovery:** the end-to-end record-scope isolation block above caught that `app.record_transaction_lineage_override` (`OPS-184`) checked only tenant-wide `OPS:Override` permission -- it never checked whether the calling actor could actually access the specific Job Order/Shipment Order/handoff record named as the correction's source or target. Since `OPS:Override` is a tenant-wide role grant, not a record-scoped one, any actor holding that permission anywhere in the tenant could have injected a lineage correction referencing a record they own no ownership/org-unit stake in and are denied on every other read/write path for. This is exactly the "existence/count/errors cannot reveal inaccessible records" and record-scope discipline every other Operations mutation function already enforces, missed at `OPS-184`'s own authoring because that checkpoint's own db-test only ever exercised the override function with an actor who legitimately owned every record involved.

**Fix (new migration, not an edit to `OPS-184`'s applied migration):** `supabase/migrations/20260728180000_harden_operations_transaction_lineage_override.sql` -- `CREATE OR REPLACE FUNCTION app.record_transaction_lineage_override` with the exact same name/signature, adding a record-scope check (`app.can_access_record`) on whichever side(s) of the edge resolve to a real `job_order`/`shipment_order`/`job_order_handoff` row (every one of the six relation types has at least one such anchor on its source or target, per the table's own `transaction_lineage_edges_relation_pair_check` constraint). `CREATE OR REPLACE FUNCTION` preserves the function's identity, so the grants already issued at `OPS-184`'s own migration remain unchanged -- no new grant/revoke statement needed. This is the same "extend via a new migration, never edit an applied one" discipline every prior checkpoint has followed, applied here to a function body rather than a table.

This is a real, disclosed, Critical/High-severity-class fix resolved within this same checkpoint rather than deferred to `OPS-186` (Security/Financial Hardening) -- bounded, well-understood, and directly blocking this checkpoint's own integrated test, matching Prompt 185 §23's "critical migration/security failure blocks hardening" exception flow. `OPS-186` remains free to run its own broader security/financial sweep next; this specific gap does not need to wait for it.
