## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

No new permission action: evaluation/handoff reuse `OPS:Edit`, the same general write gate every prior Operations lifecycle mutation already uses; override/revoke-override reuse `OPS:Override` (already registered for `OPS` at `PLT-110`, already exercised by `OPS-168`'s own `app.override_job_order_field`) — matching `OPS-178`'s own "reuse an existing action when one already fits" precedent.

Evidence is checked per Shipment Order belonging to the Job Order (cancelled shipments excluded): delivery+ePOD completion (`status in ('epod', 'closed')` — the only two statuses reachable via `OPS-177`'s own `app.complete_epod_capture`), the document checklist (`OPS-176`'s own missing-mandatory-items query, inlined rather than a second RPC round trip), no active operational exception (`OPS-174`'s own `status not in ('resolved', 'closed')`), and an approved actual cost (`OPS-178`'s own `is_current and status = 'approved'`). The customer billing-profile check reuses `app.job_orders.credit_snapshot` verbatim — the exact `{outcome, checkedAt}` object `COM-164`'s own `app.prepare_job_order_handoff` already pinned from the account's most recent credit check, at handoff time — the same "read the governed snapshot verbatim, never re-derive" discipline `OPS-179` established for `revenue_snapshot`; no new live cross-module read is invented. `outcome = 'allow'` is ready; a null snapshot (`billing_profile_missing`) or any `blocked_*` outcome (`billing_profile_not_cleared`, the exact outcome recorded) is not ready.

No configurable rule-engine table: `rule_version` is a fixed, disclosed placeholder (`1`) recorded on every evaluation, the same class of disclosed simplification as OPS-179's "no FX conversion" boundary.

Versioned, `is_current`-exclusive, never rewritten in place: the first evaluation needs no reason, every subsequent evaluation while a current row exists requires a non-empty `reevaluation_reason` — the same discipline OPS-178/OPS-179 already established. A reevaluation always resets any prior override (evidence changes do not silently preserve readiness). Override is bounded to forcing an evaluated `not_ready` row to an effective `ready` outcome, never the reverse — `effective_status` is a **generated column** (`ready` while `is_overridden`, else the evidence-based `evaluated_status`), so the raw evidence result remains visible even while overridden. The Finance handoff (`app.billing_readiness_handoffs`) is a stable, idempotent record, not a live Finance integration (Phase 4 does not exist yet) — the same "structurally ready, not yet populated by a real consumer" disclosure `app.job_order_handoffs` already established for the Commercial→Operations boundary.

### 3.2 Schema — `supabase/migrations/20260728140000_create_operations_billing_readiness.sql`

`app.billing_readiness_evaluations` (versioned, `effective_status` generated column, `unique` partial index on `is_current`) and `app.billing_readiness_handoffs` (append-only, idempotent on `(tenant_id, job_order_id, idempotency_key)`). `app.evaluate_billing_readiness` (`OPS:Edit` + record-scope gated; the one evidence-reading, versioning entry point), `app.override_billing_readiness` (`OPS:Override`-gated, reason mandatory, bounded to a `not_ready` row, optimistic-concurrency-checked), `app.revoke_billing_readiness_override` (`OPS:Override`-gated, reason mandatory), `app.handoff_billing_readiness` (`OPS:Edit`-gated, idempotent, requires `effective_status = 'ready'`). RLS-scoped base tables via a join back to `app.job_orders` (no masked directory view — no money amount is ever exposed by this capability).

## 4. Tests

### 4.1 Real database tests (`scripts/db-tests/operations-billing-readiness.sql`, via `pnpm run db:test`)

Setup: one tenant, a company/team-a/team-b org hierarchy, a bootstrap tenant-admin, a rep (COM full + OPS full incl. `Override`), a restricted actor (OPS `View`/`Edit` only, no `Override`), a sibling-team outsider (full grants incl. `Override`, wrong record scope), a credit approver, a one-step credit-approval routing definition, one confirmed Job Order with an active/`allow`-outcome credit profile, and two Shipment Orders (one driven fully compliant, one left with a deliberately open exception). Assertions: a draft, shipment-less Job Order evaluates `not_ready` with `job_order_not_confirmed`+`no_shipments`; reevaluating without a reason once a current row exists is rejected; a confirmed job with undelivered shipments reports `shipment_not_delivered`/`epod_incomplete`/`actual_cost_not_approved` per shipment; once both shipments are closed/checklisted/costed but one carries an open exception, evaluation isolates exactly one blocker (`active_exception`); handoff is refused while not ready; override is authority-gated (denied without `OPS:Override`), reason-mandatory, stale-version-checked, and bounded (`billing_readiness_override_not_needed` once already effectively ready) — it flips `effective_status` without mutating `evaluated_status`; handoff succeeds while overridden and is idempotent on the same key (exactly one handoff row survives a retried call); revoking the override (reason mandatory) restores `not_ready` and preserves `override_reason` for lineage; resolving the exception for real and reevaluating produces a genuine evidence-based `ready` (not overridden) with the evidence object referencing exactly the 2 shipments/costs/ePOD captures involved; a fresh handoff with a new idempotency key succeeds (2 handoff rows total); record-scope/cross-tenant RLS on both new tables; schema-privilege defense in depth (`anon` holds zero `EXECUTE` on all 4 new functions); audit trail (≥4 evaluate, ≥1 override, ≥1 revoke, ≥2 handoff events). All 67 db-test files pass together, zero regression.

## 8. Errors / recovery / risks / issues

Several fixture-authoring issues were found and fixed while building the db-test, none in the migration's own logic once corrected: (1) a `RAISE EXCEPTION` format string had a `%` placeholder with no argument (`billing_readiness_override_not_needed`), caught immediately at migration-apply time and fixed by passing `p_job_order_id`; (2) the fixture's tenant-admin actor was missing its `app.grant_principal_membership(..., 'tenant_admin', ...)` call, needed before `app.create_config_draft` (credit-approval routing) would authorize; (3) the fixture's rep role initially lacked `COM:View cost`/`OPS:View cost`, both required by `app.select_vendor_rate`/`app.create_actual_cost_draft` respectively; (4) the same vendor master record was initially assigned to both Shipment Orders concurrently, tripping `OPS-172`'s own `assignment_conflict` rule (fixed with a second vendor, the same fix class documented at `OPS-177`/`OPS-178`/`OPS-179`); (5) `app.submit_epod_capture` requires at least one evidence file (a null `signature_file_id` with empty `photo_file_ids` is rejected as `epod_missing_evidence`), fixed by uploading and scan-clean-marking a real signature file per shipment; (6) the 'pod'/'epod' document types and their tenant-scoped `document:<code>` config definitions were not yet registered in this fresh tenant fixture, fixed by registering them via `app.register_document_type`/`app.publish_document_type_definition` before pinning the checklist. Zero Critical/High-severity issue remains open. Zero regression to any prior capability.
