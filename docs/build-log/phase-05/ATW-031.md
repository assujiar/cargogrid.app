## 2. The two findings that matter most

### 2.1 Finance reversals could silently not happen (`ISS-2026-029`)

`app.apply_finance_ar_allocation` and `app.reverse_finance_ar_allocation` write the **same
table** under the **same** `(tenant_id, open_item_id, idempotency_key)` unique key. Neither
compared `event_type` on its replay short-circuit. So reusing a key to *reverse* an
allocation it had previously *applied* silently did nothing and returned the open item
unchanged — the reversal never posted, on a Finance-schema record, with the caller seeing
success. `app.apply_finance_ap_settlement`/`reverse_finance_ap_settlement` and
`prepare_finance_journal_reversal`/`prepare_finance_journal_adjustment` share that exact
shape.

`p_idempotency_key` is user-typed free text in this product — the Finance UI reads it
straight from `<input name="idempotencyKey" type="text" required>`. This needs an operator
typo, not an attack.

27 functions, 29 short-circuits, using the guard pattern already ratified at
`ATW-020`/`021`/`022`.

**Three functions were deliberately left alone**, and the reasoning matters as much as the
fix. `app.dispatch_shipment_order` and `app.allocate_finance_receipt` already scope their
lookup to their unique index and have no further distinguishing parameter — there is
nothing to guard. `app.provision_tenant` is unscoped and *looks* like the starkest case in
the set, but its ignore-later-arguments semantic is ratified in its own committed
`comment on function` and asserted explicitly by `scripts/db-tests/tenant-lifecycle.sql`
("Same idempotency key, deliberately different slug/name -- must be ignored"), and it is
`service_role`-only so it carries none of the free-text-key exposure. `AGENTS.md` puts
ratified decisions above an audit's own inference; flipping it silently would have been
the wrong call even though the code shape matches.

**The test suite had baked the defect in.** `scripts/db-tests/document-file.sql`'s "replay"
call passed a fresh `gen_random_uuid()` as `p_record_id` — so it was never a replay at all.
It was an upload against a genuinely different record that the unguarded short-circuit
answered with the *first* record's file row, and the test asserted that as correct
behaviour. That is why no prior checkpoint caught this class: the suite encoded the same
assumption as the code. Fixture corrected, and a real conflict assertion added beside it.

### 2.2 Cross-tenant authorization holes nobody had catalogued (`ISS-2026-033`)

A structural sweep of the live schema found **91** functions that are `SECURITY DEFINER`,
granted `EXECUTE` to `authenticated`, and contain **no authority check of any kind** — no
`evaluate_permission`, no `can_access_record`, no membership or supreme-admin test anywhere
in the body. **30 of them are `VOLATILE`.** Because `SECURITY DEFINER` runs as the owner and
bypasses RLS, any logged-in user of any tenant can call one with another tenant's ids.

Four were spot-verified directly against the live schema:

| Function | Effect |
|---|---|
| `app.recalculate_quotation_totals` | rewrites any tenant's quotation money columns |
| `app.generate_route_planning_candidates` | destroys and rewrites another tenant's route plans |
| `app.evaluate_dispatch_readiness` | reads any tenant's shipment state |
| `app.next_quotation_number` | burns another tenant's number sequence |

Not all 91 are defects — `app.lookup_public_shipment_tracking` is a deliberately public
sanitized projection, `app.ingest_driver_mobile_report` and
`app.ingest_third_party_provider_webhook_event` authenticate by token/signature rather than
RBAC, and `app.record_gps_device_installation` delegates to a callee that does check. The
work is per-function triage, not a blanket edit, which is exactly why it is **not** attempted
here: adding authority checks to 30 write paths across five already-`VERIFIED` phases needs
its own prompt, its own regression coverage, and its own baseline.

This is the highest-value follow-up in the register and should be treated as blocking for
any deployment that grants a real `authenticated` session.

## 3. The rest of the closures, briefly

- **`ISS-2026-020`** — `app.list_allocation_candidates` had no unique ordering key, so two
  lots registered in one transaction (frozen `now()`, identical `updated_at`) came back in
  implementation-defined order. Re-scoped while fixing: never only a test flake — FIFO/FEFO
  decide which physical lot and which expiry date ships, so an arbitrary order among
  same-timestamp lots means the policy was not actually being implemented. Added
  `registration_seq` (`generated always as identity`) to both identity tables — the same
  remedy `ATW-024` used for `handoff_seq` — and made the sort a total order.

- **`ISS-2026-030`** — a torn final line (crash mid-`appendFile`) made every subsequent
  `flush()` and `pendingCount()` throw permanently. Unparseable lines are now quarantined to
  a `.corrupt` sidecar, counted, and logged at error; intact batches keep flushing.

- **`ISS-2026-012`** — the `job_type` list had genuinely drifted across its four copies
  (12/10/8/8). `route_load_planning` and `print_label` were accepted by the CHECK constraint
  and `enqueue_job` but rejected by `dispatch_event_as_job` and the TypeScript union, so
  neither could ever be dispatched from an event. Collapsed onto `app.generic_job_types()`,
  plus a db-test drift gate. The table CHECK deliberately keeps its literal list — a CHECK
  that calls a function is never re-validated when that function changes, which would
  recreate this issue while looking solved.

- **`ISS-2026-028`** — fixed at the **grant boundary**, in the database, not the UI.
  `app.transition_gps_device_status` was reachable by any `OPS:Edit` holder, so a UI-only fix
  would have left the hole open. Its client grants are revoked (it becomes a shared internal
  core, the `ATW-021` pattern), and a new granted entry point refuses `installed`. Chosen
  over a `set_config` trusted-caller flag (only as strong as the caller's inability to set
  it) and over an installation-row precondition (which would have forced seven unrelated
  fixtures to stand up a document-type configuration and evidence upload).

- **`ISS-2026-025`** — the plausibility rule was defeating itself: an `impossible_movement`
  rejection still advanced the baseline the next report is measured against.
  Integrity-rejected reports no longer seed it; arbitration-rejected ones deliberately still
  do, because freezing a legitimate secondary source's baseline would make its first
  accepted report after becoming authoritative look like a teleport.

- **`ISS-2026-017`** — enforced at `app.evaluate_permission`, the single authority gate 416
  functions already call, confirmed by sweep to be always called with the request's own
  actor. A no-op whenever `auth.uid()` is NULL, so `service_role`, superuser, the gateway
  client and every db-test are untouched.

- **`ISS-2026-027`** — a real `OPS:Override`-gated, tenant-scoped, bounded, audited purge,
  keyed on `received_at` (server clock) never `event_at` (device-supplied). It deliberately
  does **not** add a scheduler: none exists repository-wide (`ISS-2026-015`). The policy is
  now enforceable and tested, not yet automatically enforced — stated plainly rather than
  blurred.

## 4. `ISS-2026-007` was hiding live vulnerabilities

`pnpm audit` had been failing with `410 Gone` since `PH0-094`, which correctly refused to
wire a fabricated passing gate. Nobody re-tested whether the endpoint came back. It has.

Running it found **20 real advisories — 11 high**, including four in Next.js itself: App
Router middleware/proxy bypass, SSRF in Server Actions, SSRF in rewrites, and a Server
Actions DoS. All fixed in `16.2.11`; this repository pinned `16.2.10`. They had been sitting
unseen for exactly as long as the gate was missing.

Bumped `next`/`eslint-config-next` to `16.2.11` and added `pnpm.overrides` for the
transitive rest. `pnpm audit` now reports zero at every severity.

One detail worth recording: the `brace-expansion` override is scoped to `>=2.0.0`. Covering
the 1.x line first made the audit read clean and **broke lint outright** — `minimatch@3`
needs `brace-expansion@1`'s export shape and no patched 1.x exists on the registry (1.x tops
out at `1.1.9`, below the advisory's `1.1.17` floor). A green audit that breaks the
toolchain is not a fix.

New gate `scripts/security/check-dependency-audit.ts`, wired into CI. It fails on
critical/high and **also fails when the advisory service is unreachable** — a gate that
could not check must never report clean.

## 7. Recommendation for Prompt 249

Prompt 249 is Phase 6's package-level README — a reading task with no runtime surface. It is
**not blocked** by anything above.

**Prompt 250 (the first real Phase 6 task) should be.** `ISS-2026-033` is cross-tenant read
and write reachable by any authenticated principal, and Phase 6 will add more functions in
the same style to the same schema. Closing it first is cheaper than closing it later across
a larger surface, and it is the difference between "no confirmed exploit because nobody has
tried" and "no exploit because the check is there".

Suggested order: `ISS-2026-033` → `ISS-2026-034` verification pass → `ISS-2026-010` →
everything else.
