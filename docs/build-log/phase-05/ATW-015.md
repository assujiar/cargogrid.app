## 2. Design decisions (disclosed, migration header)

Prompt 234 §9 itself names `ATW-229..233` as upstream, including `ATW-232`/`233` (WMS Receiving/Putaway) — but both of those in turn require posting real ledger movements (their own §4/§21), creating exactly the circular dependency this session's own gap audit recorded as `ISS-2026-011`. The operator's own explicit instruction resolves it by building this capability immediately after `ATW-231` and before `232`/`233`. This migration's own real upstream is therefore `ATW-229..231`/`011A` ("approved item/UOM/owner/status identity," §9's own substantive clause), not `232`/`233` themselves, which do not exist yet. This override is disclosed directly in the migration's own header comment, not silently substituted.

Nine further design notes are disclosed in the migration header itself:

1. **A real, race-safe balance mutation via `SELECT ... FOR UPDATE` + explicit insert/update** — see §3 below; this superseded an initially-drafted `INSERT ... ON CONFLICT DO UPDATE` design after a real defect was found and fixed during this checkpoint's own db-test authoring (§4).
2. **Lot/serial/expiry are real, nullable dimension columns on movement lines and balances now, not deferred to `ATW-235`** — `app.item_masters` (`ATW-011A`) already carries `lot_controlled`/`serial_controlled`/`expiry_controlled` flags; the ledger must carry the matching dimension columns from day one so `ATW-235` (the very next task in this session's own sequence) can *govern* them (a dedicated control/identity table, uniqueness, lifecycle) rather than retrofit a schema change onto an already-`VERIFIED` ledger. They are plain `text`/`date` columns here, not yet foreign-keyed to any lot/serial identity table.
3. **Balance uniqueness uses a `coalesce`-normalized functional unique index**, not a bare column-list unique constraint — PostgreSQL's own `UNIQUE` semantics treat every `NULL` as distinct from every other `NULL`, so a bare unique index on `(..., lot_number, serial_number)` would silently allow multiple `on_hand` rows for the same item/location when both are `NULL` (the common no-lot/no-serial case).
4. **`app.post_inventory_movement` is the one generic posting primitive every future WMS capability composes**, not a movement-type-specific wrapper per capability — `ATW-232`/`233`/`236`/`239` are each expected to call this function with their own `movement_type`/`source_type`/`source_id`, never to insert into `app.inventory_movements`/`app.inventory_balances` directly.
5. **`location_id` is mandatory** — a receipt not yet put away still has a real location (the dock/staging area itself, `ATW-230`'s own six-value `location_type` taxonomy already includes `dock`/`staging`), never a null placeholder.
6. **A `transfer` movement must balance to exactly zero across its own lines** (Prompt 234 §23: "unbalanced transfer") — enforced as a real runtime check, not merely documented.
7. **Reservation is a distinct ledger-adjacent table (`app.inventory_reservations`), not a derived count** — mirrors `ATW-227`'s own `app.vehicle_capacity_reservations` shape (reserve/consume/release, `status` lifecycle, idempotent on source). Consuming a reservation posts a real negative movement atomically in the same function call, never a bare balance decrement.
8. **Customer-owner-scoped read projections (Prompt 234 §26) are explicitly deferred** — `ATW-242` (Customer Inventory Access Contract) does not exist yet; this migration's own reads are staff-facing (`OPS:View`, warehouse-record-scoped) only.
9. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 3.3 Two real defects found and fixed during this checkpoint's own db-test authoring (before any commit)

1. **False-positive `insufficient_stock` on a perfectly valid decrement.** The migration's first draft posted balance changes via `INSERT ... ON CONFLICT DO UPDATE SET on_hand = app.inventory_balances.on_hand + excluded.on_hand`, mirroring `ATW-226F`'s own current-position upsert pattern. Direct db-test execution proved this structurally unsound for this table specifically: PostgreSQL validates a table's own `CHECK` constraints against the **raw candidate row** before `ON CONFLICT` ever redirects execution to the `UPDATE` branch. A transfer of `-20` against an existing `on_hand` of `100` (a perfectly valid resulting balance of `80`) was rejected outright, because the doomed `INSERT` attempt's own raw candidate row (`on_hand = -20`) tripped `inventory_balances_on_hand_check` before the update computation ever ran. Confirmed by direct `psql` reproduction against the disposable test database (same failure with a fresh, never-conflicting `id` and `record_version = 1` in the constraint violation's own `DETAIL`, proving the `INSERT` branch — not the `UPDATE` branch — was what failed). **Fix:** replaced the upsert with an explicit `SELECT ... FOR UPDATE` against the coalesce-normalized dimension tuple (locking the row, or proving none exists), computing the resulting `on_hand` in PL/pgSQL, and only ever writing that already-validated value — the table's own `CHECK` constraint becomes a pure defense-in-depth backstop it can no longer trip for a legitimate movement. A concurrent first-insert race is resolved by retrying through the same loop on `unique_violation`, the identical pattern `app.create_warehouse_location` (`ATW-011`) already established.
2. **`inventory_movements_correction_shape_check` violated on every real reversal.** `app.reverse_inventory_movement` called `app.post_inventory_movement` with `movement_type = 'reversal'` but `app.post_inventory_movement` never accepted or wrote a `corrects_movement_id` — every reversal attempt violated the table's own `check (movement_type <> 'reversal' or corrects_movement_id is not null)` constraint. **Fix:** added `p_corrects_movement_id uuid default null` to `app.post_inventory_movement`'s own signature (trailing, backward-compatible), wired it into the `INSERT`, added symmetric validation (required for `reversal`, forbidden otherwise), and updated `app.reverse_inventory_movement`'s own call site plus the function's `GRANT` signature and this checkpoint's own db-test schema-privilege assertion to match the new 11-parameter signature.
