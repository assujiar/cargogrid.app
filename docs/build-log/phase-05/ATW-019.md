## 2. Design decisions (disclosed, migration header)

1. **A new, separate table, `app.wms_outbound_shipments`** (`staging` → `loaded` → `shipped`, or `cancelled` from staging), referencing `outbound_order_id` — mirrors `ATW-014`/`017`/`018`'s own precedent of a task-level table referencing an upstream header, rather than widening `app.wms_outbound_orders`' own closed `draft`/`confirmed`/`cancelled` CHECK. Multiple shipments per order are explicitly allowed, supporting partial fulfillment/backorder over time.
2. **Staging performs no physical movement** — picked/packed stock already sits at `ATW-017`'s own staging destination location; modeling a movement there would be physically fictional. `app.load_wms_outbound_shipment` is the first genuinely new physical relocation (a real transfer to a validated dock location, mirroring Putaway's own transfer precedent). A plain, disclosed `vehicle_ref` text field satisfies the "no live dispatch integration" scope decision.
3. **Ship-confirm atomicity — a genuine, disclosed correction of the task brief's own literal instruction.** `app.consume_inventory_reservation` (`ATW-015`) is deliberately never called: direct inspection of `ATW-017`'s own already-applied `app.confirm_wms_pick_task` showed that once a pick task fully resolves, its own reservation is set to `'released'` (not `'active'`) via a raw `UPDATE` — incompatible with `consume_inventory_reservation`'s one-shot-active-reservation assumption. Calling it would either hard-fail or, worse, over-consume the reservation's original un-decremented quantity at the wrong location for a still-partial task. Instead, `app.ship_confirm_wms_outbound_shipment` posts **one** batched, direct `app.post_inventory_movement` (`movement_type='consumption'`) built set-based from the exact `app.wms_package_lines` rows in the shipment, at the shipment's own dock location. Traceability back to the originating pick task/reservation is preserved via a new append-only `app.wms_shipment_issue_lines` table. Custody capture, the one consumption movement, issue-line inserts, the confirmation evidence row, the billing-eligibility event, and the status transition to `'shipped'` all commit inside **one** transaction under **one** idempotency key.
4. **Double-ship-confirm prevention**: the shipment header row is locked before computing the partial-fulfillment aggregate and the status check, so two concurrent ship-confirm calls against the *same* shipment serialize — proven live with a real two-process psql race.
5. **Partial fulfillment/backorder**: a computed package-count reconciliation (never the caller's unverified claim) requires explicit `p_is_partial_fulfillment=true` plus a non-empty reason whenever real packages remain unshipped.
6. **`app.wms_billing_eligibility_events`** — a genuine new table (confirmed via grep: no `app.billing_event` exists anywhere in this repository) carrying package/line/quantity counts and a real per-UOM-code weight aggregate (never a single collapsed total mixing incompatible units). Rate/currency/pricing is deliberately left to a future Finance-domain consumer; this migration never writes to any Finance table.
7. **`app.reopen_wms_package` (`ATW-018`) widened** via same-signature `CREATE OR REPLACE` to reject reopening a package already linked to any shipment — closing the gap where a staged/loaded/shipped package's contents could silently change after real ledger/traceability records already exist.
8. **Custody evidence** is bounded to actor-label + reason + timestamp, captured directly as ship-confirm parameters — satisfying §24's "ship confirmation, custody event and inventory issue commit atomically" in one call, not a separate evidence/photo subsystem.

### 3.3 Two defects found by adversarial review, both fixed

**1. [HIGH, security-authority-owner-scoping] Missing `OPS:Override` gate on partial/backorder ship-confirm.** `app.ship_confirm_wms_outbound_shipment` gated the entire call — including a partial/backorder ship — behind plain `OPS:Edit` only, contradicting Prompt 238 §26's explicit access rule ("supervisor approves partial/backorder/override") and this session's own established precedent (`ATW-017`'s `record_wms_pick_task_short` gates comparable risk behind claimant-or-`OPS:Override`). Confirmed real by direct inspection of the function and, damningly, by the implementer's own db-test fixture: a plain `rep` actor (no `OPS:Override`) successfully ship-confirmed a real acknowledged partial fulfillment while a fully-provisioned supervisor fixture sat unused. **Fix:** added a real `OPS:Override` check, gated strictly on the aggregate-derived `v_is_partial` (never the caller's own claim), raising `insufficient_authority` when the actor lacks it; updated the db-test to prove a plain `rep` is now rejected on the partial path and switched the successful-partial-ship assertions to the supervisor fixture.

**2. [LOW, correctness-concurrency-atomicity] Cross-shipment aggregate race for orders split across multiple shipments.** The partial-fulfillment aggregate locked only the shipment being confirmed, not sibling shipments of the same outbound order — so two *different* shipments of the *same* order, ship-confirmed concurrently, could each independently under-count the order's already-covered packages under `READ COMMITTED` and both be spuriously rejected `partial_fulfillment_not_acknowledged`, even though combined they fully complete the order. Live-reproduced with two real concurrent psql processes; confirmed to fail safe (zero consumption movements, zero billing events from the race — no double-issue), but a genuine, distinct race from the same-shipment double-confirm guard design note 4 already defends against. **Fix:** a session-transaction advisory lock (`pg_advisory_xact_lock`, keyed per outbound order) acquired immediately before the partial-fulfillment aggregate, fully serializing every ship-confirm against any shipment of the same order — re-verified live with the identical repro, confirming every outcome now matches a valid serializable ordering.
