## 2. Design decisions (disclosed, migration header)

Twelve design notes are disclosed in the migration header (`supabase/migrations/20260730210000_create_advanced_tms_wms_putaway.sql`), opening with an explicit accounting of the four bug classes ATW-013's own review found and how each was proactively closed here — not rediscovered by a reviewer:

- **(a)** idempotent-replay short-circuits always run strictly after authority/tenant-scope is confirmed, never before, in every mutation.
- **(b)/(c)** `SELECT ... FOR UPDATE` on the very first read of any row a mutating function will update, held through the final UPDATE/INSERT — including `app.generate_wms_putaway_task` locking the source `app.wms_receipt_lines` row before computing remaining un-put-away quantity.
- **(d)** `app.generate_wms_putaway_task`'s own create-once idempotency check wraps its INSERT in a nested `begin/exception unique_violation` recovery block, mirroring `app.start_wms_receipt_session`/`app.capture_lead`'s own proven pattern.

The most consequential design-boundary notes:

1. **One task per (receipt line, destination) generation call**, never a single header row with a caller-opaque array of destination lines — "split across eligible bins" (Prompt 233 §22) is modeled as repeated `app.generate_wms_putaway_task` calls against the same `receipt_line_id`, each independently idempotent and each locking the source line first, so concurrent/duplicate generation can never jointly over-allocate a line's `accepted_quantity`.
2. **A second, distinct append-only table (`app.wms_putaway_confirmations`)** records every real confirm-scan event, one row per successful (or idempotently replayed) `app.confirm_wms_putaway_task` call, each with its own real `(tenant_id, idempotency_key)` unique constraint — a task can legitimately be confirmed more than once, partially, across separate physical scans. This is also the audit evidence Prompt 233 §18 requires.
3. **A task's own `status` is never directly caller-settable to `confirmed`** — Prompt 233 §24's "task completion derives from exact remaining quantity, not manual status" is enforced structurally: `status` transitions to `confirmed` exclusively when `confirmed_quantity` (after the update) equals `task_quantity` exactly, computed by the function itself.
4. **Destination validation mirrors ATW-013's dock/staging-only receiving gate exactly inverted**: a putaway destination must be `location_type in ('rack', 'shelf', 'bin')` and `putaway_enabled = true` (a real `ATW-230` column, unused by any capability until now). Capacity is a real, bounded check against `app.inventory_balances`'s own existing per-location `on_hand` aggregate — disclosed simplification: a flat cross-item quantity ceiling, no UOM-aware conversion across differently-UOM'd items sharing one bin.
5. **Suggestion is real decision support, never authoritative** (Prompt 233 §24 verbatim) — a caller-supplied suggestion is sanity-checked only for existing-and-same-warehouse at generation time; the *only* authoritative destination validation in the whole capability is the one `app.confirm_wms_putaway_task` itself runs against the real `p_actual_location_id` at confirm time.
6. **The transfer movement's own `source_type`/`source_id` reuses `wms_inbound_order`/the original inbound order id**, never a new enum value — `app.inventory_movements`'s own closed five-value `source_type` CHECK (ATW-015, already applied) is never widened.
7. **A putaway confirmation is only ever executed by its own claimant** — a real identity comparison (`p_actor_auth_user_id = task.claimed_by_auth_user_id`), never a bare `OPS:Edit` role check alone — the first capability in this repository to need real per-task assignment, not merely role authority.
8. **`app.reassign_wms_putaway_task` is the one supervisor override/reassign mechanism**, gated on `OPS:Override`, reusing the identical authority `app.approve_wms_receipt_overage`/`app.resolve_wms_receipt_hold` (ATW-013) already established.
9. **Task generation is a real, synchronous, idempotent RPC**, never an async background job/scheduler — this repository has no scheduler/worker runtime yet (disclosed, `ISS-2026-015`).
10. **No REST/GraphQL surface, no scan-first PWA UI** — matches `ATW-012`/`013`/`015`'s own disclosed boundary.
11. **Environment-requirement matching (Prompt 233 §15) is disclosed as deferred, not built** — no item-level environment/temperature-requirement column exists anywhere yet.

### 3.3 A novel race condition found and fixed by adversarial review, distinct from the four pre-briefed bug classes

The implementing agent was explicitly briefed on and proactively applied all four bug classes ATW-013's own review found (§2 above, design notes (a)–(d)) — no repeat of any of those four surfaced this checkpoint. The three-lens adversarial review nonetheless found **one genuine, novel defect** neither the implementer nor its own pre-briefing covered, because it is a structurally different bug shape: a race against a *cross-row aggregate*, not a single row's own lock.

**The defect:** `app.confirm_wms_putaway_task`'s destination-capacity check (`select coalesce(sum(on_hand), 0) into v_occupied from app.inventory_balances where location_id = ... and status = 'on_hand'`) was a plain, unlocked read with no row/location-level lock. `app.wms_putaway_tasks`'s own `FOR UPDATE` lock (design note (b)/(c)) only serializes two confirms against the *same task row*; `app.post_inventory_movement`'s own balance lock is keyed per (item/lot/serial/location) dimension tuple, not per location. So two *different* putaway tasks (different items, or the same item under different lots) racing the same capacity-limited destination could both read the same stale occupancy and jointly overshoot `capacity_value` before either had posted its own transfer movement.

**Verification:** two independent reviewers (spec-compliance and correctness/concurrency lenses) both flagged this at the identical location; the fix agent independently re-confirmed it real by running two genuinely concurrent psql sessions against an instrumented copy of the function (a `pg_sleep` injected between the occupancy read and the compare/write) — confirming two different putaway tasks (different receipt lines, different claimants) to a capacity-5 rack, both passing the unlocked check and both posting, leaving `on_hand=8` against `capacity_value=5`, an empirically proven overshoot.

**Fix:** added `SELECT ... FOR UPDATE` on the destination `app.warehouse_locations` row in both branches of the destination-validation block inside `app.confirm_wms_putaway_task`, before the capacity aggregate is read — a second concurrent confirm targeting the same destination now blocks until the first transaction commits, then its own occupancy read observes the real post-commit effect. Re-ran the identical two-session repro against the patched function: the second session correctly blocked, then was rejected `destination_full` once unblocked, and final `on_hand` stayed within capacity. A new sequential db-test (`L4b`) was added proving the aggregate capacity check is correct across two different tasks/items/claimants sharing one destination — the prior `L4` test only re-confirmed a single task against itself and did not cover this. Independently re-verified by this checkpoint's own orchestrating session by reading the fixed function directly (§5).

Five smaller defects were found and fixed by the implementing agent during its own authoring, before any external review: a PL/pgSQL row-assignment bug in the auto-suggest query (`select l.*, <scalar> into ...` is invalid — `l.*` cannot share an INTO list with a scalar target); a missing `if not found` guard on the "same destination as before" confirm branch; a scalar-into-composite mismatch in the db-test's own fixture code; a test-fixture quantity-accounting bug (two sections drawing from the same 10-unit receipt line); and a test-ordering issue. None of these reached the review phase.
