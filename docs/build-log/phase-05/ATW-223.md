## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Vehicle and driver identity stays in `app.master_records` (PLT-120)** — this checkpoint never creates separate vehicle/driver identity tables. `app.vehicle_operational_profiles`/`app.driver_operational_profiles` each hold a 1:1 operational extension keyed by `vehicle_master_id`/`driver_master_id` (`master_type_code` values `'vehicle'`/`'driver'`, registered idempotently). Registering a profile internally calls `app.create_master_record`, which is hard-gated to tenant_admin/Supreme Admin authority regardless of any `OPS` role grant — an existing PLT-120 constraint, not a new one introduced here.
2. **No telemetry ingestion, no live position, no provider webhook** — this is a fleet/asset baseline only (`ATW-226`'s own scope, unchanged greenfield confirmation from `ATW-220`). `app.provider_vehicle_mappings` and `app.vehicle_tracking_source_priorities` are real, queryable configuration tables a future `ATW-226` capability will read from, not yet written to by any ingestion path.
3. **Device-vehicle assignment is append-only history, never an overwrite** — `app.device_vehicle_assignments` follows the exact `is_current`/`superseded_by_id` precedent `app.resource_assignments` (OPS-172) already established: `app.assign_device_to_vehicle` marks the prior current row `is_current = false` **before** inserting the new one (matching `app.reassign_resource`'s own statement ordering), never violating the partial unique index `device_vehicle_assignments_current_device_unique on (device_id) where is_current`.
4. **GPS device status is an explicit 8-state machine** (`stock → assigned → installed → active ⇄ offline/suspended/maintenance → retired`, `retired` terminal) — every transition is validated server-side by `app.transition_gps_device_status`, never inferred from assignment state alone.
5. **SIM-to-device is a strict 1:1, mutually exclusive assignment** — a SIM already carrying `current_device_id` cannot be reassigned without an explicit unassign first (`device_already_has_sim`), and a retired device cannot receive a SIM or a device assignment (`device_retired`).

### 4.1 Real bugs found and fixed during development (not pre-existing test fragility — genuinely new to this checkpoint's own code)

1. **`app.assign_device_to_vehicle`: `FOUND` reflected the wrong statement.** An early draft checked `if found then` immediately after the `INSERT` of the new assignment row to decide whether a prior assignment existed — but `FOUND` always reflects the *most recent* executed statement, not the earlier `SELECT` that actually located the prior row. Fixed with an explicit `v_had_prior boolean := false;` captured right after the `SELECT`, before any further statement could overwrite `FOUND`.
2. **`app.assign_device_to_vehicle`: insert-then-update ordering would have transiently violated the partial unique index.** An early draft inserted the new `is_current = true` row before marking the prior row `is_current = false`, which momentarily double-books `device_vehicle_assignments_current_device_unique on (device_id) where is_current`. Fixed by following `app.reassign_resource`'s (OPS-172) own precedent exactly: UPDATE the prior row to `is_current = false` first, then INSERT the new row, then UPDATE the prior row's `superseded_by_id`.
3. **Db-test fixture: `register_vehicle_operational_profile`/`register_driver_operational_profile` rejected the intended "Fleet Rep" actor.** These functions call `app.create_master_record` (PLT-120) internally, which hard-requires tenant_admin/Supreme Admin authority — an `OPS:Create`-only role grant is insufficient regardless of module-level permissions. Root-caused by reading the exact `insufficient_authority` error text back against PLT-120's own migration. Fixed by also granting the same `OPS` role to the tenant_admin fixture user (via Supreme Admin grant, avoiding self-assignment) and switching the register-call actors in the test to that tenant_admin identity.
