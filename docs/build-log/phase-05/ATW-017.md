## 2. Design decisions (disclosed, migration header)

Fourteen design notes are disclosed in the migration header (`supabase/migrations/20260730240000_create_advanced_tms_wms_picking.sql`), opening with an explicit accounting of the six known bug classes from `ATW-013`/`014`/`016`/`016A`'s own reviews and how each was proactively closed here:

- **(a)** idempotent-replay short-circuits always run strictly after authority/tenant-scope confirmation, never before, in every mutation.
- **(b)/(c)** `SELECT ... FOR UPDATE` on first read of every row a mutation updates (the outbound order line, every task row, the reservation and its backing balance row pair, the destination location row), held through the final `UPDATE`/`INSERT`.
- **(d)** create-once idempotency inserts (`wms_pick_tasks`, `wms_pick_waves`) wrap in nested `begin/exception unique_violation` recovery.
- **(e)** the double-allocation race — this checkpoint's own headline instance — is closed by locking the target `app.wms_outbound_order_lines` row *before* computing `sum(task_quantity - short_quantity)` over that line's own non-cancelled pick tasks as "already allocated," serializing concurrent generation attempts against the same line. Proven with two real, independent psql client processes racing against two *different* balance locations (so the proof demonstrates the line lock specifically, not merely `ATW-015`'s own narrower per-balance lock).
- **(f)** owner-account read scoping applied to every read RPC via `app.actor_can_view_owner_scoped_row` (`ATW-016`, reused directly), with the owner's own `owner_account_id` passed as `p_customer_account_ref` into every `app.can_access_record` call.

The most consequential design-boundary notes:

1. **Wave shape**: `app.wms_pick_waves` is a lightweight, state-machine-free grouping header (real referential integrity + a human-readable generated number via a counter idiom) — no `status` column; a wave's completion is always derived by querying member `wms_pick_tasks`, never tracked separately.
2. **Reservation/transfer interaction** (the load-bearing mechanism keeping `inventory_balances_reserved_held_bound_check` — `reserved + held <= on_hand` — satisfied throughout a pick-confirm): inside `confirm_wms_pick_task`'s one transaction, `reserved` is decremented on the source balance *first*, then `app.post_inventory_movement` (`movement_type='transfer'`) decrements `on_hand` by the identical amount. This order is algebraically necessary — reducing `reserved` first only widens slack (`reserved - q <= on_hand` trivially, since `reserved <= on_hand` always holds); reversing the order would transiently violate the check.
3. **Reservation bookkeeping decoupling**: `app.inventory_reservations.reserved_quantity` stays exactly as originally set (`ATW-015`'s own "never mutated in place" convention); the *live* `inventory_balances.reserved` is decremented incrementally per confirm/short event instead. Neither the shared `app.release_inventory_reservation` nor `app.consume_inventory_reservation` is called mid-pick (both assume one-shot full-amount transitions); `app.consume_inventory_reservation` is never called at all this checkpoint — picked stock has only moved to staging, not left the warehouse, an explicit scope boundary. `app.cancel_wms_pick_task` is the one place that does call the shared `app.release_inventory_reservation` directly, safe only because cancel is gated to zero-progress tasks.
4. **Short-pick handling**: confirming less than the remaining quantity is a legitimate partial pick, never an error; a distinct `app.record_wms_pick_task_short` RPC releases exactly the short amount (excluded from the double-allocation aggregate, so it is structurally free to be re-allocated). Confirming/shorting *more* than remaining is a hard rejection in both RPCs, never silently clamped.
5. **Substitution bound (disclosed)**: `app.approve_wms_pick_substitution` is `OPS:Override`-gated, callable only while a task has zero progress — avoids ever unwinding a partially-posted transfer. Requires the substitute item to share the task's own base UOM (no cross-UOM conversion attempted). No auto-suggest-substitute engine is built — substitute is always caller/supervisor-nominated, per the task brief's explicit bound.
6. **`app.cancel_wms_outbound_order` widening**: widened via a same-signature `CREATE OR REPLACE` in this new migration — the exact obligation `ATW-016A`'s own design note 8 named, mirroring `ATW-013`'s identical widening of `ATW-012`'s cancel RPC. Now blocks cancelling a confirmed outbound order while any non-cancelled pick task still references one of its lines.
7. A real, disclosed, additive expand-migration adds a genuine `wms_outbound_order` member to `app.inventory_reservations`/`app.inventory_movements`' own `source_type` closed CHECK enums (never editing the original `ATW-015` file) — serving Prompt 236 §33's "every pick is scan/source/ledger traceable" with an accurate label, rather than reusing a semantically misleading existing value.

## 3. Implementation

### 3.1 Schema — `supabase/migrations/20260730240000_create_advanced_tms_wms_picking.sql`

Five new tables (`app.wms_pick_waves`, `app.wms_pick_tasks`, `app.wms_pick_task_confirmations`, `app.wms_pick_task_shorts`, `app.wms_pick_substitution_approvals`) plus a numbering-counter table, 9 mutation RPCs and 6 read RPCs. Every stock-affecting mutation composes exclusively against `app.reserve_inventory`/`app.release_inventory_reservation`/`app.post_inventory_movement` (`ATW-015`) and `app.list_allocation_candidates` (`ATW-016`) — no direct write to `app.inventory_movements`/`app.inventory_balances`/`app.inventory_reservations` anywhere.

### 3.2 Service layer

`server/contracts/wms-picking/wms-picking.ts`, `server/queries/wms-picking.ts`, `server/mutations/wms-picking.ts` (plus their `.test.ts` files), mirroring the established `wms-putaway`/`wms-outbound-order` pattern exactly. No UI route.

### 3.3 Defects found by adversarial review, all fixed

**1. [HIGH] `app.confirm_wms_pick_task` never verified the item actually scanned.** No `p_scanned_item_master_id` parameter existed — only source location and (conditionally) lot/serial were verified. Since warehouse locations are not item-dedicated (multiple distinct items can share one bin, as the db-test's own fixtures already demonstrate), a picker could scan the correct location but physically grab the wrong item, and the call would succeed — the ledger would then misrepresent what physically moved. Directly violates Prompt 236 §21/§23, which name "item" explicitly alongside location/lot/serial. **Fix:** added a required `p_scanned_item_master_id` parameter and a hard `item_mismatch` rejection; added a new `scanned_item_master_id` column on the confirmations table; updated the service layer and all db-test call sites; added a dedicated `item_mismatch` regression test (a picker scans the correct location but a different real item balance sharing that bin).

**2. [MEDIUM] Owner-scoped RLS `SELECT` policies were fail-closed for the exact actor class they exist to admit.** The four new tables' policies nested a raw, non-`SECURITY DEFINER` `select 1 from app.warehouses` inside their own `USING` clause — but `app.warehouses`' own RLS policy always passes `p_customer_account_ref = null`, so that nested subquery is itself invisible to a `customer_user`-layer actor regardless of true ownership, making the outer `EXISTS` always false. Live-reproduced (a disposable test DB, `SET LOCAL ROLE authenticated` with a real customer-scoped JWT, a raw `SELECT` on the actor's own owned row — 0 rows, versus 1 row for the identical staff actor). Not a cross-owner leak (fail-closed, denies legitimate owners), but it silently breaks the "customers see only permitted fulfillment status" guarantee for any future direct-table read — currently latent since every shipped read path composes only the `SECURITY DEFINER` RPCs. **Fix:** added `app.wms_pick_record_scope_ok(auth_user_id, warehouse_id, owner_account_ref)`, a small `SECURITY DEFINER` helper that resolves the warehouse's own tenant/org-unit and evaluates `app.can_access_record` while bypassing `app.warehouses`' own RLS (the same bypass every RPC in this migration already relies on); rewrote all four owner-scoped policies to call it instead of the raw nested subquery. Re-verified live: customer_user now gets 1 row on their own owned task, cross-owner isolation intact.

**3. [MEDIUM] The idempotency-race recovery claim held only at the outermost insert, not at composed inserts one level down.** `app.generate_wms_pick_task`'s call to `app.reserve_inventory`, `app.confirm_wms_pick_task`'s calls to `app.post_inventory_movement` and its own confirmations insert, and `app.record_wms_pick_task_short`/`app.approve_wms_pick_substitution`'s own inserts each had no `unique_violation` recovery — only the outermost `wms_pick_tasks`/`wms_pick_waves` inserts were protected. Live-reproduced with two real concurrent psql processes sharing one idempotency key across two *different* rows (no shared lock to serialize them): the loser raised a raw, uncaught `duplicate key value violates unique constraint` straight out of the unprotected insert. The safe single-entity retry case (identical target row and identical key) was unaffected, since it is caught by the top-of-function idempotent-replay short-circuit first. **Fix:** widened `app.reserve_inventory` and `app.post_inventory_movement` (`ATW-015`, already applied) via same-signature `CREATE OR REPLACE` within this new migration — never editing the original file — wrapping their own previously-unguarded insert in a nested `begin/exception unique_violation` block that raises a new, clean, classified `idempotency_key_conflict` exception instead of leaking the raw Postgres message; applied the identical pattern to this migration's own three remaining unguarded inserts. A new two-real-process regression test proves exactly one process wins and the loser surfaces `idempotency_key_conflict`, never the raw constraint-violation string.

### 3.5 A fifth defect, found and fixed by this checkpoint's own orchestrating session: `scripts/git/check-protected-paths.ts` itself was structurally broken

While independently re-running `git:check-paths` against the actual *staged* diff (not merely the pre-staging invocation this session's own prior checkpoints had used), the check reported the new `supabase/migrations/20260730240000_create_advanced_tms_wms_picking.sql` — a brand-new file, `git status A`, never previously committed — as `FORBIDDEN: applied migration — never edit, add a new migration instead`. Direct inspection of the check script confirmed this is a genuine, pre-existing implementation defect, not specific to this checkpoint: `checkProtectedPaths` matched only a bare file path against `/^supabase\/migrations\/\d.*\.sql$/`, with no way to distinguish a newly-*added* migration from a *modification* to an already-applied one — `git diff --cached --name-only` (the CLI's own input) carries no status information at all. The check's own existing unit test was itself misleading: titled "flags an applied migration as FORBIDDEN, but not a new/unapplied one," it only ever asserted the first half of that claim. Because no pre-commit hook invokes this script (confirmed: no `.husky/`, no `.git/hooks/pre-commit`), this defect had gone undetected across every one of this session's own prior checkpoints (`ATW-012`–`016A`), each of which added a new migration — the check was always run *before* staging in this session's own prior verification passes, so the real, staged-diff failure mode was never actually triggered until now.

**Fix:** `checkProtectedPaths` now accepts either a bare path (preserving the old, conservative "flag regardless" behavior for a caller with no status information) or a `{path, status}` entry; the migrations rule is exempted only when `status === "A"`. The CLI's own `changedPathsFromGit` now calls `git diff --cached --name-status` instead of `--name-only`, correctly threading real git status through. Added a new assertion to the existing test (the one whose own title already promised this behavior) proving a `status: "A"` migration is not flagged while `status: "M"` still is. Re-ran the full gate suite after this fix — all still green, including `git:check-paths` itself now correctly passing against this checkpoint's own real staged diff (16 files checked, 3 `CAUTION` flags on `docs/runtime/*`, 0 `FORBIDDEN`).
