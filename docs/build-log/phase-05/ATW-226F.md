## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Widens three already-applied ingestion functions, does not fork them.** `app.ingest_driver_mobile_report` (`226C`), `app.ingest_direct_device_telemetry_batch` (`226D`), `app.ingest_third_party_provider_webhook_event` (`226E`) are each re-declared via `CREATE OR REPLACE FUNCTION` with their own exact, unchanged signature (a body-only widening, unlike `226C`'s own `end_leg_tracking_session` signature-widening DROP+CREATE) — one addition each: a call to `app.arbitrate_and_project_vehicle_position()` immediately after the raw report insert succeeds. Every existing db-test for `226C`/`226D`/`226E` re-passes unmodified.
2. **Canonicalization never breaks raw ingestion.** Vehicle resolution (`app.resolve_vehicle_for_driver_mobile_session`/`app.resolve_vehicle_for_gps_device`) returns `null`, never raises, when no current resource assignment/device-vehicle mapping exists; the widened bodies simply skip arbitration in that case, always after the point where the raw insert (and, for `226C`, the anon-facing `'success'`/`'ok'` status) has already committed.
3. **Deterministic, reproducible, auditable arbitration.** `app.arbitrate_and_project_vehicle_position()` evaluates, in order: source-priority-disabled, heartbeat-carries-no-location, accuracy-below-threshold, stale-event-time (never move current position backward), impossible-movement, then same-source-continuation or cross-source-switch (gated by `226A`'s own `freshness_threshold_seconds`/`switch_hysteresis_seconds`). Every rejected candidate is still stored with its own `rejection_reason` — never silently dropped.
4. **Per-vehicle priority (`ATW-223`) wins over the tenant default (`226A`).** `app.resolve_vehicle_source_priority_rank()` checks the per-vehicle override first; explicitly disabled there means a source can never win arbitration for that vehicle regardless of the tenant default.
5. **Current position is separate from history.** `app.canonical_telemetry_events` (append-only, every accepted candidate, applied or not) *is* the history tier; `app.vehicle_current_positions` is a single row per vehicle. No third, redundant "position_history" table; route-segment aggregation is left to a future read-side consumer.
6. **Impossible-movement uses a fixed 200 km/h implied-speed ceiling**, compared against the *same source's own* last-known position (`app.vehicle_source_health.last_location`) — not the current winning position, which could belong to a completely different, independently-clocked source. A real defect found and fixed during authoring (§4.1) established this design.
7. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 4.1 Real defects found and fixed during authoring (before any full-suite gate run)

1. **`CREATE FUNCTION` instead of `CREATE OR REPLACE FUNCTION`** for the three widened ingestion RPCs — the migration failed immediately with `function ... already exists with same argument types`. Fixed by using `CREATE OR REPLACE` as the design always intended (the header's own design note 1 was correct; the literal SQL keyword was not).
2. **Impossible-movement compared against the wrong baseline.** The original design compared a candidate report against the *current winning position*, regardless of source — but two independently-clocked sources (e.g. a fresh third-party report following a stale direct_device one) produce a meaningless "implied speed" when compared against each other, causing a legitimate cross-source arbitration candidate to be spuriously flagged `impossible_movement` instead of reaching the real switch-suppression logic. Caught by a failing db-test assertion. Fixed by adding `last_location` to `app.vehicle_source_health` and comparing each candidate against that *same source's own* last-known position instead — a source's very first-ever report has no history to compare against and is correctly never flagged.
3. **Test-timing collision with hysteresis, not an arbitration bug.** The db-test's own stale-fallback scenario (test 4) ran within `switch_hysteresis_seconds` (120s) of the bootstrap switch (test 1) — real vehicles separate these by far more than two seconds of wall-clock script execution; fixed by explicitly backdating `vehicle_source_switches.switched_at` in the test fixture (the identical technique already used for the later driver_mobile-reclaim scenario), not by changing the arbitration logic itself.
4. **Two pre-existing, unrelated test-fragility defects found and fixed, not this checkpoint's own code defects** (the identical class of issue `ATW-222`'s own build log already documented for a different file): `scripts/db-tests/advanced-tms-device-installation-evidence.sql` (`226B`) and `scripts/db-tests/advanced-tms-driver-mobile-tracking.sql` (`226C`) each selected a fixture row via `select id from app.<table> ... limit 1` with **no tenant-scoping WHERE clause**. This never failed before because no earlier-sorting db-test file had ever inserted into those same shared tables (`app.gps_device_installations`, `app.shipment_leg_tracking_sessions`) — this checkpoint's own new file (`advanced-tms-canonical-telemetry-arbitration.sql`, alphabetically sorting before both) does, for its own device-installation and driver-mobile-session fixture setup, exposing the pre-existing fragility for the first time. Fixed by scoping both queries to their own file's own tenant (`acmeinstall`/`acmemobile` respectively) — a 2-line change to each file, verified by re-running the full `db:test` suite clean afterward, and by direct reproduction (running the two files back-to-back in a disposable database) before and after the fix.
