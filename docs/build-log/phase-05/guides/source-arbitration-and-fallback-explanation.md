# Source Arbitration and Fallback Explanation

**Produced by:** `CG-S10-ATW-028` (Prompt 247, Advanced TMS/WMS Documentation and Handoff).
**Audience:** anyone who needs a plain-language answer to "which GPS source is CargoGrid trusting right now, and why" — dispatchers, support, and developers.
**Source of truth:** `supabase/migrations/20260729390000_create_advanced_tms_canonical_telemetry_arbitration.sql` (`ATW-226F`, base), `20260730320000_create_advanced_tms_shipment_tracking_health_writer.sql` (`ATW-024`, concurrency locks), `20260730350000_harden_advanced_tms_third_party_hybrid_tracking.sql` (`ATW-027`, the 24-hour future-timestamp bound). This guide reuses the design-note prose already written into these migrations' own comments rather than re-deriving the logic from scratch — where this guide paraphrases, the migration's own inline comment is the exact, authoritative wording.

## 1. The problem this solves

A single vehicle can report its position from up to three independent sources at once: a driver's phone (`driver_mobile`), a hardware GPS unit wired into the vehicle (`direct_device`), and a third-party fleet-telematics platform CargoGrid has a data-sharing agreement with (`third_party_platform`). These sources disagree with each other constantly — different update frequencies, different accuracy, occasional bad fixes, network delay causing out-of-order arrival. `app.arbitrate_and_project_vehicle_position` is the one function that decides, on every single incoming report, whether that report becomes the vehicle's new official position — and it is the **only** place this decision is made anywhere in the schema (`226_GPS_TELEMATICS_INTEGRATION_PROMPT.md` §14: "all modes call one canonical normalization and source-arbitration service").

## 2. The rule in plain language

Every incoming report is checked, in order, against a series of reasons it might be rejected. The first reason that applies wins — the report is stored either way (see §5), but only an unrejected report can become the vehicle's new official position:

1. **Is this source turned off for this vehicle?** A per-vehicle override (`app.vehicle_tracking_source_priorities`, set by fleet ops, `ATW-223`) always wins over the tenant's own default priority list (`app.tenant_tracking_source_policies`, `ATW-226A`). If the source is explicitly disabled, or simply absent from the tenant's default priority array, it can never win — full stop, regardless of freshness or accuracy.
2. **Is this just a heartbeat with no location attached?** A heartbeat proves the source is still alive but cannot become a position.
3. **Is the timestamp implausibly far in the future?** Added at `ATW-027` — see §3.
4. **Is the reported accuracy worse than the tenant's own threshold?** (Default: 100 meters.)
5. **Is this report older than the position we already have?** The vehicle's official position must never move backward in time just because a report arrived late — a report timestamped earlier than the current position's own timestamp is always rejected, regardless of source.
6. **Does this report imply an impossible speed?** Compared only against this *same source's* own last known position (not the current winning position, which might be a different source entirely — two independently-clocked sources cannot be fairly compared for implied speed against each other). If the implied speed exceeds 200 km/h, the report is rejected.
7. **If none of the above rejected it, and a different source currently holds the position:** the new source only takes over if it has genuinely higher priority, or the current source has gone stale (no update for longer than the freshness threshold, default 300 seconds) — **and** no source switch has happened for this vehicle within the last 120 seconds (the hysteresis window, preventing rapid oscillation between two sources that are both intermittently available).
8. **Otherwise** (no current position yet, or the same source is simply continuing to report): the report is accepted.

## 3. What `ATW-027` changed: the 24-hour future-timestamp bound

Before `ATW-027` (Prompt 246, Integrity and Security Hardening), the "is this older than what we have" check (§2 rule 5) had **no upper bound at all** on how far in the future a timestamp could claim to be — and the very first report ever received for a vehicle (the "bootstrap" case, when there is no current position to compare against) applied **unconditionally**, with no plausibility check whatsoever.

A dedicated adversarial-probe agent live-reproduced the consequence: a single forged report with `event_at` set to a date far in the future (`2099-01-01` was the actual probe payload) — submitted either as a brand-new vehicle's very first report, or as a normal stale-fallback takeover on an already-healthy vehicle — permanently became the stored comparison baseline. Every subsequent *real* report from *every* source, including the tenant's own highest-priority source, was then rejected as "older than what we have," forever — and there was no repair RPC anywhere in the schema to undo it. This was one of the two most severe findings of the entire Phase 5 build (rated HIGH, "de facto Critical combined with" the CRITICAL webhook-secret finding also found that checkpoint — see `ADVANCED_TMS_WMS_HANDOFF_PACKAGE.md`'s own residual-risk section).

**The fix**, now a permanent part of `app.arbitrate_and_project_vehicle_position`'s own decision chain (evaluated third, before accuracy/staleness/movement checks, and — critically — evaluated even on the bootstrap path): any report whose `event_at` is more than **24 hours** ahead of the server's own real clock is rejected outright with reason `event_time_implausible_future`, and can never become the stored baseline.

**Why 24 hours, not the 5-minute bound originally suggested** (mirroring `docs/adr/ADR-0011-webhook-signature-and-auto-disable-thresholds.md`'s own webhook-timestamp-tolerance convention): direct inspection of every already-`VERIFIED`, already-passing db-test suite that exercises this function found real, legitimate fixture data using synthetic `event_at` offsets up to roughly 9.3 hours ahead of "now" — a pre-existing, unrelated convention several test files use to represent a long simulated vehicle journey across many checkpoints without literal `sleep()` calls in a transaction-per-statement test script. A literal 5-minute bound would have broken that already-shipped, unmodified test coverage. 24 hours was chosen instead: comfortably clear of every real fixture found anywhere in the repository (largest: ~9.3 hours), while still being a small, explicit, finite, **self-healing** bound — the probe's actual forged payloads (decades in the future) are rejected by an enormous margin under either value, and any candidate that does land inside the 24-hour window can only ever pre-empt real traffic for that bounded window, never permanently. Real-time reports naturally catch up and immediately resume winning once wall-clock time passes the stored value — closing the true defect (permanent, unbounded lockout), not merely narrowing it.

## 4. The disclosed residual: `ISS-2026-025` (the "salami-slicing" gap)

This is a genuinely open, disclosed issue — not fixed as of this checkpoint. Carry it forward honestly.

`app.vehicle_source_health.last_location`/`last_seen_event_at` (the per-source "is this source alive" record used by rule 6 above) is updated **unconditionally on every incoming candidate, whether it wins arbitration or not** — by original, deliberate design: "even a rejected/disabled-source report is real evidence the source is alive" (`20260729390000`'s own table comment). This is correct and intentional for the liveness purpose it serves.

The adversarial-probe agent that found the future-timestamp defect (§3) also observed a **separate, still-open** consequence of this same unconditional-update design: an attacker who already holds a valid, already-authenticated source credential could submit a sequence of small, individually-plausible position deltas — each one losing arbitration outright and never becoming the vehicle's official position — to gradually walk the per-source impossible-movement baseline (rule 6's own comparison point) arbitrarily far from the vehicle's true position, **without ever needing a future-dated timestamp at all**. This is distinct from, and not closed by, the `ATW-027` fix in §3: the 24-hour bound only closes the future-timestamp angle; this vector requires no future timestamp.

**Why it remains open:** two independent fix agents worked this same checkpoint, each covering a disjoint half of the GPS/tracking surface — one covering Direct Device + Driver Mobile, the other covering Third-Party Platform + Hybrid arbitration. Each reasonably assumed the other's scope covered this specific vector; neither did, because fixing it means touching `app.arbitrate_and_project_vehicle_position` itself, which was explicitly named off-limits to the device/mobile agent (assigned to the other agent's file boundary) while the sibling agent's own bounded finding set — defined before this cross-agent gap became visible — never named it either. The orchestrating session discovered the gap while reconciling both agents' final reports, and deliberately did not patch it ad hoc under time pressure to a function that had already been widened twice in the same checkpoint.

**Severity and exploitability, honestly stated:** Medium. It requires sustained, repeated, patient interaction from an *already-credentialed* source — not a single-shot or unauthenticated exploit — and it only weakens one secondary, defense-in-depth signal (the same-source impossible-movement check) while primary authentication/authorization/signature/consent/tenant isolation controls remain fully intact. There is no confirmed live exploit chain today.

**The bounded fix already recorded** (for whichever future checkpoint picks this up, per `docs/runtime/KNOWN_ISSUES.md` `ISS-2026-025`): gate the `vehicle_source_health.last_location`/`last_seen_event_at` upsert on the candidate not having been rejected for a position-integrity reason specifically (`impossible_movement`/`event_time_implausible_future`), while still updating unconditionally for reasons unrelated to position trust (e.g. `duplicate_event`, a lower-priority-but-plausible report) — preserving the original "source is alive" liveness-tracking intent for every rejection reason that does not itself represent a position-trust concern.

## 5. Rejected does not mean discarded

Every single candidate report — accepted or rejected, for whatever reason — is permanently stored in `app.canonical_telemetry_events` with its own `rejection_reason` column populated when it lost. Nothing is silently dropped (`226_*.md` §23's own business rule: "never silently drop accepted data"). This means the full history of every arbitration decision, including every source that lost and why, is always queryable — `app.get_vehicle_telemetry_history` returns it (bounded to 500 rows regardless of the caller's own requested limit), and `app.get_vehicle_source_switches` returns the audit trail of every time the *winning* source actually changed, with the exact ranks/thresholds/elapsed-seconds evidence the decision used recorded as `jsonb` — "reproducible from stored policy and evidence" (`226_*.md` §25), never a bare free-text explanation.

## 6. Concurrency: why two simultaneous reports for the same vehicle cannot corrupt the result

Found and fixed at `ATW-024` (Prompt 243): the read-decide-write shape of this function (read the current position, decide whether to apply, then write) is inherently racy under genuine concurrency — two reports for the same vehicle arriving at nearly the same instant could both read "no winner yet" or "source X currently wins," both decide independently, and then commit in the *reverse* of their own timestamp order, letting an older report silently overwrite an already-committed newer one. This was live-reproduced with two real concurrent database sessions and closed with a per-vehicle `pg_advisory_xact_lock`, held for the whole duration of one arbitration attempt (dedup check through final write) — proven under real concurrent load against 59,534 conflicting-source transactions with zero backward-movement and zero lost update (`scripts/load-tests/pgbench/hybrid-arbitration.sql`).

## 7. Fallback in one sentence

"Fallback" means the currently-winning source has gone stale (no update for longer than the tenant's freshness threshold) and a different, available source is allowed to take over — `app.vehicle_source_switches.reason = 'current_source_stale_fallback'` is the exact, queryable record of every time this happened, always hysteresis-gated so two flaky sources cannot ping-pong the winning position back and forth every few seconds.
