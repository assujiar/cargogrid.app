## 1. The three HTTP endpoints (`services/gps-gateway/src/health.ts`)

A tiny, dependency-free `node:http` server, deliberately not the Next.js app's own API route surface — this package is independently deployed and must expose its own liveness/readiness signal to whatever container/VPS platform ends up hosting it. Bound to `GPS_GATEWAY_HEALTH_HOST:GPS_GATEWAY_HEALTH_PORT` (default `0.0.0.0:8080`).

| Path | Method | Response | Meaning |
|---|---|---|---|
| `/healthz` | any | `200 text/plain "ok"` | The HTTP server itself is up and answering. Always `200` once bound — this endpoint does not check readiness, only that the process is alive. This is what the Dockerfile's own `HEALTHCHECK` polls (`docs/build-log/phase-05/guides/teltonika-codec8e-gateway-deployment-guide.md` §1.1). |
| `/readyz` | any | `200 text/plain "ready"` or `503 text/plain "not_ready"` | Reflects the `getReady()` callback `src/index.ts` wires — `false` until both the TCP listener and this health server have both finished binding, and set back to `false` the instant `SIGTERM`/`SIGINT` shutdown begins (before either server is closed) so a load balancer/orchestrator stops routing new connections during a graceful shutdown. |
| `/metrics` | any | `200 text/plain`, one `gps_gateway_<key> <value>` line per counter | A plain-text dump of `GpsGatewayServerMetrics` (below) — not Prometheus-exposition-format-labeled, just `gps_gateway_connectionsOpened 42`-style lines, one per field, generated by `Object.entries(metrics).map(...)`. |
| any other path | any | `404 text/plain "not_found"` | — |

### 1.1 The exact `/metrics` counters (`GpsGatewayServerMetrics`, `services/gps-gateway/src/server.ts`)

```
gps_gateway_connectionsOpened     -- every TCP connection accepted, regardless of outcome
gps_gateway_handshakesAccepted    -- IMEI handshakes that resulted in accepted=true
gps_gateway_handshakesRejected    -- IMEI handshakes rejected (unknown IMEI, wrong tenant,
                                      not-ingestible status, already-connected IMEI, or a
                                      bad gateway API key)
gps_gateway_packetsDecoded        -- AVL data packets successfully decoded (CRC-valid,
                                      structurally correct)
gps_gateway_packetsRejected       -- connections closed for a malformed/oversized packet
                                      or handshake
gps_gateway_reportsIngestedLive   -- individual telemetry reports written directly to
                                      Supabase this process's own lifetime
gps_gateway_reportsBuffered       -- individual telemetry reports that fell back to the
                                      local durable buffer because a live write failed
```

Counters are process-lifetime cumulative (reset only on restart), not a rate — a monitoring system scraping `/metrics` should compute its own rate-of-change if that is what it needs.

## 2. TCP listener port and firewall requirements

| Port | Default env var | Direction | Who needs access |
|---|---|---|---|
| `6060` (raw TCP, Teltonika Codec 8 Extended) | `GPS_GATEWAY_TCP_PORT` | Inbound | Every device's own cellular/APN network path must be able to reach this port on the gateway's own public/static endpoint (`docs/ai-agent-build-prompt-package/10-phase-05-advanced-tms-wms/219_ADVANCED_TMS_WMS_README.md` §4.3: "static public network endpoint and configurable raw TCP ports") |
| `8080` (HTTP health/readiness/metrics) | `GPS_GATEWAY_HEALTH_PORT` | Inbound | Restrict to the orchestrator/monitoring network only — this endpoint carries no authentication of its own (no bearer token, no API key check anywhere in `health.ts`) and should never be exposed to the same public network the device port is on |

No outbound firewall rule beyond ordinary HTTPS to the configured `SUPABASE_URL` is required — the gateway's own `GpsGatewayIngestClient` (`services/gps-gateway/src/ingestClient.ts`) is the only outbound network dependency besides the inbound device connections themselves.

`/metrics` and `/readyz` having zero authentication is a real, disclosed design choice (matching the shape of `/healthz` on every other service in this repository) — it is safe **only** if network-layer access to port `8080` is actually restricted as recommended above. Nothing in the code enforces that restriction; it is an operational requirement, not a code guarantee, exactly the same category of disclosed gap as the IMEI-spoofing residual (`docs/build-log/phase-05/guides/teltonika-codec8e-gateway-deployment-guide.md` §6).

## 3. Connection cap and idle timeout (`CG-S10-ATW-027`, finding 6 — TCP socket exhaustion)

Before this hardening, no idle-read timeout or `maxConnections` cap existed on the raw gateway TCP server — a device (or an attacker) that opened a connection and never sent anything, or opened connections faster than they were ever closed, could hold sockets open indefinitely and exhaust the process's own file descriptors/memory. Two independent, env-overridable bounds now exist (`services/gps-gateway/src/server.ts`):

- **Idle timeout** (`GPS_GATEWAY_IDLE_TIMEOUT_MS`, default `60000` = 60s): `socket.setTimeout(idleTimeoutMs, () => closeWithLog("idle_timeout"))`. Node resets this timer on every `'data'` event on its own, so a genuinely connected, healthy device — whose own configured ping interval is typically well under a minute — is never at risk of tripping it. A connection that dials in and never sends a byte, accidental or a deliberate slow-connection-flood attempt, is closed rather than held open forever.
- **Max connections** (`GPS_GATEWAY_MAX_CONNECTIONS`, default `10000`): `this.server.maxConnections = options.maxConnections ?? DEFAULT_MAX_CONNECTIONS`, Node's own documented `net.Server.maxConnections` semantics — a connection beyond this cap is destroyed before the `'connection'` event handler ever runs, bounding worst-case resource exhaustion from a connection flood.

Both defaults are described in the source as "deliberately generous but bounded" — 10,000 connections is sized for a large single-tenant-per-gateway deployment's own real fleet size while still bounding the worst case, not derived from a specific customer's measured fleet size (none exists yet). If a real deployment's fleet approaches this default, raise `GPS_GATEWAY_MAX_CONNECTIONS` explicitly rather than assume headroom that was never measured against a live fleet.

## 4. What has actually been load-tested (real numbers, not projected ones)

`scripts/load-tests/gps-telemetry-load.ts` spins up a **real, in-process `GpsGatewayServer`** and drives it over real loopback `node:net` sockets with real IMEI handshake bytes and real Codec 8 Extended AVL frames (including real CRC-16) — the exact same `GpsGatewayServer` class production runs, the exact same wire-format encoder/decoder. Its own ingest **client** is replaced with a fast in-memory fake (identical in spirit to `services/gps-gateway/test/server.test.ts`'s own fake), since no live Supabase project exists anywhere in this repository's environment (`ADR-0010`). **This measures the real TCP/protocol/decode/buffer layer under real concurrent load — it does not, and cannot, measure live Supabase RPC latency**, which remains a separate, already-disclosed `DEFERRED_EXTERNAL_HARDWARE_EVIDENCE`/`CONDITIONALLY_SKIPPED_PROVIDER_UNAVAILABLE` boundary this scenario does not newly cross.

### 4.1 Direct Device Gateway scenario — real, current numbers

From `scripts/load-tests/results/RESULTS_CG-S10-ATW-024.txt` (the currently committed evidence file, run finished `2026-08-05T04:47:42Z`), Scenario 4 ("GPS telemetry ingestion load"), defaults `LOAD_GPS_DEVICES=50`, `LOAD_GPS_PACKETS_PER_DEVICE=20`, `LOAD_GPS_RECONNECT_DEVICES=10`:

```
devices=50 packetsPerDevice=20 totalPackets=1000 reconnectDevices=10

total_packets=1000 errors=0 malformed_frame_rejected_cleanly=true
ack_latency_ms: p50=3.309 p95=4.926 p99=7.042 avg=3.157 max=7.476
overall_duration_ms=128.6 throughput_packets_per_sec=7774.7
reconnect_attempts=10 reconnect_failures=0
server_metrics={"connectionsOpened":81,"handshakesAccepted":81,"handshakesRejected":0,
  "packetsDecoded":1020,"packetsRejected":1,"reportsIngestedLive":1010,"reportsBuffered":10}

GPS_TELEMETRY_LOAD_SCENARIO: PASS
```

Read this precisely: **50 concurrent simulated device TCP connections**, 20 AVL packets each (1,000 total), zero dropped or corrupted frames, ACK round-trip latency (send packet → receive ACK, in-process/loopback) p50 3.3ms / p95 4.9ms / p99 7.0ms / max 7.5ms, sustained throughput ~7,775 packets/second against the real decode/buffer pipeline. A separate deliberately-malformed connection was rejected cleanly without affecting the other 80 concurrent connections. Ten devices disconnected and reconnected with the same IMEI with zero reconnect failures, proving the gateway holds no per-IMEI session state that would block a genuine reconnect.

**These are in-process loopback numbers against a fake ingest client, not a live network/live-Supabase measurement.** They bound the TCP/protocol/decode layer's own real overhead; they say nothing about wide-area network latency to real cellular devices or real Supabase RPC round-trip time, neither of which has ever been measured because neither a live device network nor a live Supabase project exists in this repository's environment.

### 4.2 The same scenario's own outage/recovery sub-case

The same run, immediately after the above:

```
outage_devices=10 acks_during_outage_failed=0 (expected 0 -- ACK still sent, custody transferred to the durable buffer)
reports_buffered_during_outage=10 pending_after_outage=10 (expected 10 each)
flushed_after_recovery=10 pending_after_flush=0 live_batches_ingested_by_flush=10 (expected 10/0/10)
OUTAGE_BUFFER_RECOVERY_SCENARIO: PASS
```

Ten devices sent real AVL packets while the ingest client was forced to fail every call; every one still received its ACK (the gateway's own durable buffer is the real point of custody transfer — see `docs/build-log/phase-05/queue-dlq-replay-reconciliation-procedure.md`), all 10 were durably buffered, and all 10 flushed and were ingested once the simulated outage cleared, with zero dead-lettered. This is real, load-driven (not single-connection unit-test-only) recovery evidence for the exact behavior `docs/runbooks/gps-gateway-outage.md` and `docs/runbooks/gps-ingestion-database-outage.md` describe.

### 4.3 The downstream canonical-arbitration layer's own concurrency evidence (a different layer — context, not a gateway metric)

Separately, `scripts/load-tests/`'s own Scenario 8 measures `app.arbitrate_and_project_vehicle_position` (`ATW-226F`, the function every one of the three ingestion paths — including the gateway's own `app.ingest_direct_device_telemetry_batch` — ultimately calls) directly against a real Postgres database via `pgbench`, simulating multiple source types racing for the same small set of "hot" vehicles. This is **not** a gateway/TCP-layer metric — it measures the database write path once telemetry has already left the gateway. From the same currently-committed results file:

```
clients=20 duration_seconds=15 hot_vehicles=20
number of transactions actually processed: 46849
number of failed transactions: 0 (0.000%)
latency average = 6.401 ms
tps = 3124.503553 (without initial connection time)
canonical_telemetry_events written this scenario=46849 arbitration_throughput_events_per_sec=3123.2
vehicles_with_backward_movement_or_lost_update=0 (expected 0)
source_switch_hysteresis_violations=0 (expected 0)
HYBRID_ARBITRATION_LOAD_SCENARIO: PASS
```

This `pgbench` scenario is duration-bound (runs for a fixed 15 seconds, not a fixed transaction count), so the exact transaction count varies run to run — a separate real run recorded in `docs/build-log/phase-05/ATW-024.md` §4 measured 59,534 transactions under the identical scenario. Both are real; neither is "the" permanent number. Treat this figure as "tens of thousands of concurrent conflicting-source arbitration transactions per 15-second window, zero backward-movement/lost-update/hysteresis violations across every run measured so far," not as a single fixed benchmark.

## 5. Scaling guidance grounded in what has actually been measured

- **A gateway instance is a single process with in-process state.** The concurrent-IMEI-handshake rejection (`docs/build-log/phase-05/guides/teltonika-codec8e-gateway-deployment-guide.md` §6) depends on `activeImeis`, an in-memory `Set` scoped to one running process — running more than one gateway instance behind a shared public endpoint (for horizontal scaling or high availability) would **not** share that state across instances, silently reopening the exact concurrent-connection-impersonation gap `CG-S10-ATW-027` closed for the single-process case. This is disclosed directly in the migration header (`supabase/migrations/20260730360000...`, design note 2): in-process state was chosen specifically because the gateway is architected as a single always-on process, and a Postgres advisory lock was explicitly rejected as unreliable for this gateway's own stateless-per-RPC-call architecture. **Do not horizontally scale `services/gps-gateway` to more than one concurrently-running instance without first re-deriving this design decision** — doing so is a real security regression, not merely a capacity question.
- **Vertical headroom, based on §4.1's own real numbers:** 50 concurrent connections sustained ~7,775 packets/second of decode+buffer throughput with sub-8ms p99 ACK latency, entirely in-process. The `GPS_GATEWAY_MAX_CONNECTIONS` default of 10,000 (§3) is **not** validated against a load test at that concurrency — the largest concurrency actually exercised is 50 real sockets (plus 81 total connections counting reconnects and the outage/malformed sub-scenarios). Treat 10,000 as a conservative resource-exhaustion ceiling, not a proven-healthy operating point; if a real fleet approaches even a few hundred concurrent devices, run `scripts/load-tests/gps-telemetry-load.ts` directly (`LOAD_GPS_DEVICES=<N> node --experimental-strip-types scripts/load-tests/gps-telemetry-load.ts`) against that target concurrency before assuming it will behave identically to the 50-connection number above.
- **What is honestly `NOT_RUN`, not merely unmeasured-and-assumed-fine:** live network latency to real cellular devices; live Supabase RPC latency under load (the load test's own ingest client is a fake, §4); sustained/soak duration beyond the few hundred milliseconds each load-test run actually executes for; behavior under a real, live outage of the *device* network (as opposed to the simulated Supabase-outage sub-case, §4.2); and multi-gateway-instance deployment of any kind (disclosed as a real security regression above, not merely untested). Do not represent any of these as tested in any capacity-planning or customer-facing material.
