## 3. Findings and fixes

### 3.1 CRITICAL — `webhook_secret_value` readable by any authenticated tenant member

A table-wide `grant select ... to authenticated` on `app.third_party_provider_connections` (`20260729380000`) bypassed the intended secret-column protection — RLS scopes rows by tenant, never columns. Live-reproduced: a zero-permission tenant member could read the raw secret directly, then use it to compute a valid HMAC-SHA256 signature and inject accepted forged telemetry. **Fixed**: `revoke select ... from authenticated` + an explicit 14-column `grant select (...)` excluding `webhook_secret_value`, mirroring the already-established `app.users`/`email` column-grant precedent. **Independently re-verified by this checkpoint's own orchestrating session** (not accepted on the fix agent's own self-report alone): `information_schema.column_privileges` confirms zero grant on the secret column for `authenticated`/`anon` while all 14 other columns remain granted; a direct raw-SQL probe as `authenticated` against a live fixture row raised `permission denied` on the secret column while an ordinary column proceeded to normal RLS filtering.

### 3.2 HIGH — unbounded future `event_at` permanently poisons arbitration

`app.arbitrate_and_project_vehicle_position`'s `stale_event_time` guard had no upper bound on caller-controlled `p_event_at`, and the bootstrap (first-ever-report) path applied unconditionally with zero priority gating — a single forged far-future timestamp permanently became the comparison baseline, locking out every future real report from every source, with no repair RPC anywhere. **Fixed**: a new `event_time_implausible_future` rejection branch, evaluated unconditionally (including on bootstrap) before a candidate can win arbitration or become the stored baseline. **Deviation, disclosed and reasoned**: used a 24-hour tolerance rather than the suggested 5-minute ADR-0011-style bound, since several already-`VERIFIED`, unmodified db-test fixtures use synthetic `event_at` offsets up to ~9.3 hours to represent elapsed journey time without literal sleeps — 24 hours is comfortably clear of every real fixture repository-wide while remaining a small, named, finite, self-healing bound (never permanent) rather than the original unbounded defect. Regression tests reproduce the exact bootstrap and stale-fallback probe scenarios and confirm normal service resumes immediately once wall-clock time passes.

### 3.3 HIGH — cross-tenant IMEI collision → permanent DoS against a victim device

`app.gps_devices` uniqueness was `(tenant_id, imei)` only, with no cross-tenant check on registration; `app.resolve_gps_device_for_handshake` unconditionally refuses (`imei_ambiguous_across_tenants`) the instant `>1` tenant registers the same IMEI — with no admin remediation RPC anywhere in the schema. Live-reproduced: any tenant could self-register another tenant's real, active device's IMEI and permanently break that victim's every future handshake. **Fixed**: `app.register_gps_device` now rejects (`imei_registered_to_another_tenant`) registering an IMEI another tenant already holds, serialized via a per-IMEI `pg_advisory_xact_lock` closing the TOCTOU window; a new, narrowly-scoped `app.deregister_gps_device` (`OPS:Override`-gated) soft-retires a spurious registration (no raw delete); `resolve_gps_device_for_handshake`'s ambiguity check now excludes retired rows. A real compatibility issue was found and fixed along the way: 5 pre-existing db-test fixtures across 3 files coincidentally reused the same literal IMEI under different tenants (harmless before this fix, would have broken under the new guard) — each given a unique IMEI.

### 3.4 HIGH — concurrent-connection IMEI impersonation

Two simultaneous raw TCP handshakes with the identical IMEI both succeeded — no exclusivity check existed, and IMEIs are not secret (printed on hardware). **Fixed** (bounded, in-scope half): `services/gps-gateway/src/server.ts` now tracks in-flight IMEI→connection state in-process and rejects a second concurrent handshake for an already-open IMEI — chosen over a Postgres advisory lock because each handshake/batch is a separate, stateless, pooled PostgREST call that would not reliably span the TCP connection's own lifetime. **Residual, disclosed, not fixed here**: a patient/plausible sequential spoof (not concurrent) still beats the impossible-movement check — an inherent Teltonika Codec8E protocol limitation (no hardware exists in this sandbox to test a stronger scheme against, per Prompt 246's own External-evidence policy), disclosed in the migration header and `services/gps-gateway/README.md` as an accepted residual risk requiring compensating network-layer controls, not attempted as a speculative PKI/device-cert redesign.

### 3.5 HIGH — durable buffer poison-pill

`DurableTelemetryBuffer.flush()` halted its entire queue on the *first* failure regardless of whether it was permanent or transient — a single suspended device's own correctly-rejected batch permanently blocked every other device sharing the same gateway process's buffer. **Fixed**: failures are now classified permanent (`device_not_ingestible`/`tenant_mismatch`/`device_not_found`/structural-validation, dead-lettered and skipped) versus transient (halts-and-retries, preserving ordering for genuinely recoverable cases).

### 3.6 HIGH — revoked driver mobile-tracking consent never honored mid-session

`app.ingest_driver_mobile_report` never re-checked `mobile_tracking_consent` after session start — revoking consent mid-session did not stop location collection. **Fixed**: the function now live-rechecks the session's own driver's current consent/profile-status on every call, cleanly rejecting (not raising) once consent is withdrawn.

### 3.7 MEDIUM — malformed-but-signed fields crash the RPC (both third-party and driver-mobile)

Both `app.ingest_third_party_provider_webhook_event` and `app.ingest_driver_mobile_report` had partial exception coverage — a validly-signed/tokened but malformed payload (out-of-range coordinates, non-numeric fields) raised an uncaught exception instead of the documented "never raises" contract, and because the failure was uncaught, it was invisible to both functions' own rate-limit/auto-disable bookkeeping. **Fixed**: both exception boundaries widened to cover every field extraction/cast through the final INSERT, always falling through to a clean `invalid` result with the bookkeeping row still recorded.

### 3.8 MEDIUM — rate limiting keyed on caller-controlled signal

The third-party webhook's 15-minute rate limiter counted only a caller-supplied `client_key` (derived from a spoofable `x-forwarded-for` header) — trivially bypassed by varying the header per request. **Fixed**: the count now matches `connection_id` (the caller's own unavoidable attack target) in addition to `client_key`.

### 3.9 MEDIUM — TCP socket exhaustion

No idle-read timeout or `maxConnections` cap existed on the raw gateway TCP server. **Fixed**: `socket.setTimeout` (default 60s, env-overridable) plus a `server.maxConnections` bound (default 10,000, env-overridable).

### 3.10 LOW — `anon` lacked schema `USAGE`, undermining the documented "anon-callable" claim

`anon` held `EXECUTE` on the driver-mobile/webhook ingestion RPCs but no `USAGE` on schema `app` at all — fails safe today (the real route always uses a service-role client) but would silently break a future direct-PostgREST/anon-key caller, and the repeatedly-documented claim had never been live-verified. **Fixed**: `grant usage on schema app to anon`, confirmed to grant no new object-level privilege on its own (only makes an already-granted `EXECUTE` actually reachable).

### 3.11 LOW — gateway log redaction bypassed by the dominant logging pathway

`services/gps-gateway/src/logger.ts`'s redaction only inspected an optional structured-fields object's keys; every real call site routed dynamic/error-derived content through the free-text `message` string instead, which was never scanned, and a thrown decode error could embed an unbounded attacker-controlled payload verbatim. **Fixed**: redaction now scans string values (including `message`) against 5 credential-shaped patterns, and `message` is truncated to 2,000 characters after redaction.

### 3.12 Real cross-finding interaction found and fixed during the fix pass itself

Binding the third-party rate limiter to `connection_id` (§3.8) meant connections that had already accumulated invalid attempts in earlier tests within the same shared fixture could trip `rate_limited` prematurely in later, unrelated tests reusing the same connection. Fixed by isolating rate-limit-specific tests to their own dedicated connections and backdating one pre-existing test's bookkeeping timestamps out of the 15-minute window, consistent with this repository's own established "backdate via direct SQL" convention.

### 3.13 Deliberately not fixed this checkpoint — new findings registered

- **`ISS-2026-025` (Medium, new)** — `app.vehicle_source_health.last_location`/`last_seen_event_at` still update unconditionally on every candidate regardless of arbitration outcome (deliberate original design: "even a rejected report is real evidence the source is alive"). This checkpoint's own §3.2 fix analyzed and disclosed the adjacent future-timestamp angle of this and correctly concluded it does not reopen the permanent-lockout defect — but that analysis does not cover a separate, still-open "salami-slicing" vector the device-probe agent originally observed: repeated, individually-plausible, always-arbitration-losing position deltas from an already-credentialed source can still walk the same-source impossible-movement baseline, with no future timestamp required at all. Neither fix agent closed this specific vector — each reasonably believed the other's scope covered it. Discovered as a genuine coverage gap by this checkpoint's own orchestrating session while reconciling both final reports; deliberately not patched ad hoc under time pressure to a function already widened twice this same checkpoint. A bounded fix direction is recorded in the issue for a future task.
- **`ISS-2026-026` (Low, new)** — `getThirdPartyProviderConnection` (`server/queries/third-party-provider-adapter.ts`) does `select("*")` against the now column-restricted table; zero live callers today (confirmed dead code, only its own mocked unit test exercises it), so no live regression, but would need an explicit column list the moment a real caller is wired up.
- **`ISS-2026-024` (Medium, new, unrelated)** — see §5 below; an incidentally-discovered, pre-existing flake in an unrelated, already-`VERIFIED` file, surfaced while re-verifying the `ISS-2026-023` fix.
