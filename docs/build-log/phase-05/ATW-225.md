## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **A tracking POLICY and SESSION-ORCHESTRATION layer, never a telemetry ingestion path** (§14's own "do not ingest telemetry here"). A "tracking session" is an intent-level orchestration record — who/what *should* be the authoritative tracking source for a leg, and why — never a position, ping, or raw telemetry row. Raw ingestion, normalization, and source arbitration remain `ATW-226`'s own scope (specifically `ATW-226C`/`226F`), not built yet.
2. **`app.shipment_leg_tracking_policies` is one row per leg, upserted, with an explicit not-required state.** `tracking_required = false` combined with empty `allowed_sources`/`fallback_order` and a null `preferred_source` is the only valid "not required" shape (enforced by `shipment_leg_tracking_policies_not_required_clean_check`) — never an implicit default reached by leaving fields blank while `tracking_required = true`.
3. **Entitlement is disclosed, never a hard gate.** `app.is_shipment_tracking_entitled` (`ATW-222`'s own stub, always `false` until `ATW-226A` ships real entitlement evaluation) is snapshotted onto every session as `tracking_entitled_at_start` for honest audit disclosure, but orchestration bookkeeping itself is not blocked by it — real eligibility is what gates `start`/`handoff` (`app.check_leg_tracking_source_eligible`), checked against the shipment's own current `app.resource_assignments` (`OPS-172`) plus `ATW-223`'s own driver consent/vehicle device/provider-mapping data. A session that could never receive live telemetry today is still a real, provable orchestration decision worth recording.
4. **Session history follows `app.resource_assignments`/`app.device_vehicle_assignments`/`app.route_planning_selected_plans`'s own `is_current`/`superseded_by_id` precedent** — a session is never overwritten in place, always superseded (`handoff`) or closed (`end`).
5. **No-signal escalation is a real, provable orchestration-level staleness check, not a raw GPS-timeout detector.** `app.evaluate_leg_no_signal_escalation` compares a still-active session's own `started_at` against the policy's own `no_signal_escalation_seconds`; a genuinely stale session is ended (`end_reason = 'stale_source'`) and a real `app.operational_exceptions` row is raised via the already-verified `app.report_exception` (`OPS-174`), deduplicated on `correlation_key`. There is no live telemetry feed yet to measure "last ping," so staleness is measured against session `started_at` — an honest, currently-reachable proxy, not a claim of ping-level freshness detection.
6. **`unauthorized_override` is a genuinely distinct, gated end path.** `app.end_leg_tracking_session` requires `OPS:Override` (the same gate `ATW-224`'s own override path uses) plus a mandatory, non-empty reason note for that one end reason; `leg_completed`/`manual_stop` require only `OPS:Edit`.
7. **Start/end triggers (`leg_dispatch`/`first_stop_arrival`, `last_stop_arrival`/`leg_complete`) are declarative policy metadata only.** They are not wired into `app.transition_shipment_leg` (`ATW-221`, an already-applied migration this checkpoint never edits) — automatic session start/end on leg transition remains a disclosed future obligation, not silently claimed as done.
8. **Record-scope reuses `app.can_access_record`** joined through `shipment_legs` → `shipment_orders`, identical to `ATW-221`'s own `shipment_legs`/`shipment_leg_stops` policy shape.
9. Permission catalogue: reuses the already-seeded `OPS` action set (`Edit`, `Override`) — no new `app.permissions` row, no new module code.
10. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 4.1 Real bugs found and fixed during development (not pre-existing test fragility — genuinely new to this checkpoint's own code)

1. **`app.resolve_leg_tracking_policy`: `malformed array literal` from `v_eligible := v_eligible || 'driver_mobile'`.** PL/pgSQL cannot disambiguate a bare string literal as an array element via the `||` operator — it attempts to parse the right-hand string itself as an array literal. Root-caused directly against a real Postgres 16 instance (`malformed array literal: "driver_mobile"`), not assumed from documentation. Fixed by replacing all three occurrences (`driver_mobile`, `direct_device`, `third_party_platform`) with `array_append(v_eligible, '<source>')`.

### 4.2 Db-test fixture defect found and fixed (not this checkpoint's own production code)

This checkpoint's own db-test fixture initially reused a tenant slug (`acmemile`), email domain (`miletest.test`), company name ("Mile Test Co"), and code (`MTC`) that collided with an already-existing, unrelated Phase 3 test file (`scripts/db-tests/operations-milestone-management.sql`), which independently used the identical strings.
