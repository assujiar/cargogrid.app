# CG-S10-ATW-032 — post-Prompt-248 codebase audit: verification and repair

**Checkpoint:** `CG-S10-ATW-032`
**Predecessors:** `CG-S10-ATW-030`, `CG-S10-ATW-031`
**Trigger:** an explicit instruction to audit the whole codebase as implemented through Prompt 248, report every issue, and repair them so Prompt 249 begins from a clean base.

## 1. What this checkpoint is

`ATW-031` ended with a register of **60 candidate findings** in
`ATW-031-DEEP-AUDIT-FINDINGS.md`. That register was never verified — the fan-out that produced
it stalled after its finder phase, so it was, by its own front matter, a list of claims.
`ISS-2026-034` was opened to hold it, with one instruction attached: *do not fix from the
register directly.*

This checkpoint is that verification, plus the repairs that survived it. Two disciplines
governed the whole pass, and both changed outcomes:

1. **The ratified design decides what is correct, not intuition.** `docs/blueprint/`,
   `00-control/02_CONFIRMED_DECISION_REGISTER.md` (CPD/RPD/INV) and
   `docs/architecture/06_RLS_RBAC_WORKSTREAM.md` were read before judging. Several findings
   are not defects at all once the design is read — §4 of the RLS workstream assigns each
   table exactly ONE policy family, and only `customer_portal_scoped` (shipments, invoices,
   tickets, warehouse_orders) keys on `customer_account_id`, so "policy X is tenant-only" is
   correct behaviour everywhere else.
2. **The live catalogue decides what the code does, not the file.** Every claim was
   re-derived from `pg_get_functiondef` against a database with all migrations applied. The
   single largest cause of false positives was a claim describing code a later migration had
   already changed.

## 2. Measured outcome of the verification

The register's false-positive rate is high, and that is the finding to record first.

| **ALREADY-FIXED** — a later migration had closed it | 7 |

## 3. The two findings this checkpoint found in its own predecessors

Both matter more than any single register entry, because both mean an already-shipped repair
was not doing what its migration said it did.

**An idempotency guard that raises `unique_violation` inside a block whose own handler traps
`unique_violation` is inert.** `ATW-030`/`ATW-031` added 55 such guards. All 55 were swept
structurally — block nesting parsed, not grepped, because a `raise exception` line contains
the word "exception" and a naive scan mistakes it for a block's exception section, which is
precisely what hid this. Two functions have a guard inside a handled block:
`start_wms_receipt_session` is already correct (its handler re-checks and re-raises, and an
exception raised inside a handler is not re-caught by it); `ingest_milestone_event` was
genuinely inert, so a `DELIVERED` submission reusing an earlier `DEPARTED_ORIGIN` key returned
that event with no error and the delivery was silently discarded.

**A version-predicated UPDATE that matches nothing must say so.** `20260730480000` repaired
the 64 functions with neither a lock nor a version predicate, and named the residual it left:
the predicate alone still needs every call site to handle the zero-rows case. 74 functions did
not. Execution fell through with an unset composite, so `capture_audit_event` wrote a
fabricated `success` row with a NULL tenant_id, the function returned an all-NULL composite
the TypeScript guard does not catch, and anything already written in the same transaction —
a transition-history row — committed describing a change that never took effect.

## 4. Issues closed

- **`ISS-2026-032`** — the actor-identity residual. The classification pass the issue asked
  for, run against the live catalogue: 761 functions take `p_actor_auth_user_id`; 566 reach an
  actor check transitively; of the remaining 195, 119 have no `authenticated` grant and 43 are
  pure reads. **33** were side-effecting, client-callable and unchecked. Each already
  validated authority but asked "is the CLAIMED actor allowed?" rather than "is the caller
  that actor?" — `approve_rate_version` gated on
  `is_support_grant_authority(p_actor_auth_user_id, ...)`, so any session knowing a
  tenant_admin's UUID could approve a vendor rate as them. The issue's own estimate was ~315;
  the real actionable bucket was 33.

## 5. Standing gates added

`scripts/db-tests/rbac-enforcement.sql` gained a gate that recomputes the same transitive
closure and fails if any side-effecting, client-callable function taking
`p_actor_auth_user_id` reaches neither `app.evaluate_permission` nor
`app.assert_actor_is_session_identity`. It joins the actor-identity proof, the
SECURITY DEFINER authority-surface sweep and the optimistic-concurrency gate added earlier in
this audit — four standing regression gates rather than four one-off repairs.

## 6. A repair this checkpoint got wrong first, and how it was caught

The 74-function sweep initially re-granted `authenticated, service_role` to every function it
replaced, as a matter of course. That was wrong: `app.transition_gps_device_status` carries no
client grant by design, and `advanced-tms-device-installation-evidence.sql:323` asserts
exactly that. The suite failed and the grant block was removed entirely — `CREATE OR REPLACE`
preserves an existing ACL, so there was nothing to restore. A blanket grant inside a
mechanical sweep is how an internal helper quietly becomes a public API, and the standing
assertion that caught it is the reason this repository writes such assertions.
