## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Entitlement/package/limits are not a new schema.** `ATW-222`'s own migration header (`20260729300000`, `app.is_shipment_tracking_entitled`'s disclosed-stub comment) already named the intended mechanism verbatim: "the real `tracking.*` entitlement keys in the Configuration Engine (`PLT-121`)." This checkpoint honors that citation exactly — it reuses `app.config_types`'s already-seeded bare `'feature'` type via a tenant-scoped `config_object` with `tracking.enabled`/`tracking.package`/`tracking.limits` items, resolved through the existing `app.resolve_config()` RPC. No new `config_type` is registered and no per-tenant data is seeded in the migration (there is no tenant to scope it to yet); a tenant admin assigns a tracking package later via `PLT-121`'s own already-shipped `createConfigDraft`/`setConfigItems`/`publishConfigVersion` service-layer mutations, exactly as any other Configuration Engine consumer would. Deliberately **not** `app.evaluate_entitlement` (`PLT-106`, the coarse module-level SaaS subscription gate — checked and ruled out, since `ATW-222`'s own citation named Configuration Engine, not Entitlement) and **not** Feature Flags (`PLT-133`, which mints its own `feature:<flagKey>` config_type per flag for kill-switch/rollout/cohort concerns this capability does not have).
2. **Source priority is not a new schema either.** `ATW-223`'s own `app.vehicle_tracking_source_priorities` (`20260729310000`) already declares a per-vehicle primary/fallback source preference, with its own comment disclosing that "live hybrid arbitration using freshness/accuracy/health at runtime is `ATW-226F`'s own scope." What is genuinely new here is the **tenant-level default** those per-vehicle rows fall back to when a vehicle has none, plus the freshness/accuracy/hysteresis thresholds no existing table carries at any grain — a distinct grain (tenant vs. vehicle) and a distinct field set, not a fork of `ATW-223`'s table. Checked directly against `AGENTS.md`'s "do not create duplicate... policy engines" rule before writing any schema.
3. **`app.is_shipment_tracking_entitled` is replaced via `CREATE OR REPLACE FUNCTION`** with an identical signature (never edit an applied migration) — its existing `authenticated`/`service_role` `EXECUTE` grant from `20260729300000` is preserved automatically and is not re-granted here.
4. **Both new resolver functions always return exactly one row** (`resolve_tenant_tracking_package` via a dummy-row `LEFT JOIN`, `resolve_tenant_tracking_source_policy` via `COALESCE` over a `LEFT JOIN`) with an honest, disclosed default (`enabled=false`/`is_explicit=false`) rather than `NULL` or a raised error — so every later `ATW-226` child can call either unconditionally.
5. **Array uniqueness cannot be expressed in a Postgres `CHECK` constraint** (subqueries are forbidden there); element-set validity (`<@` containment) is a structural `CHECK`, but duplicate-element rejection is validated in `app.upsert_tenant_tracking_source_policy`'s own function body — the same function-body-validation idiom `ATW-223`'s `app.set_vehicle_tracking_source_priority` already established for its own `priority_rank`/`source_type` checks.
6. Authority: `app.upsert_tenant_tracking_source_policy` reuses `app.evaluate_permission(..., 'OPS', 'Edit')` — the single most common tier across this domain (55 of ~200 call sites repository-wide use exactly this pair) and the identical gate `ATW-223`'s own vehicle-level source-priority function uses, so tenant-level and vehicle-level tracking policy share one authority tier rather than inventing a new one.
7. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.
