## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Materialized path/depth, reusing `app.org_units`'s own proven mechanism (PLT-109) verbatim** — the identical trigger pair (shape/cycle validation, then path/depth recomputation) and the identical descendant-path-splice cascade `app.move_org_unit` already proved, rather than inventing a second hierarchy mechanism or adopting `ltree` (absent from this repository).
2. **`location_type` is a real closed CHECK enum, unlike `zone_type`/`service_type` (`ATW-229`'s own free-text design note 2).** Prompt 230's own §4 objective, §13 database impact, and §27 test-data requirement all independently name the identical six-value set ("rack, shelf, floor, staging, dock and bin") — a repeated, closed, sourced taxonomy, not a single test-data mention — so this migration constrains it directly.
3. **Depth is bounded by a governed constant function** (`app.warehouse_location_max_depth()` = `8`) — a disclosed reasoned default, the same class `ATW-224`'s own `app.route_planning_default_speed_kmh()` already used without minting a fresh ADR, since no architecture document names an exact maximum rack/shelf/bin depth.
4. **A location's `zone_id` is optional and validated only against its own warehouse**, not inherited/enforced across an entire subtree — Prompt 230 §22's own "use floor/staging/dock location without rack" alt flow implies some locations legitimately have no zone context at all; a zone, when given, must belong to the same warehouse and be active.
5. **A location may never move to a different warehouse, and moving is restricted to a `draft`-status node** — Prompt 230 §22's own alt flow names "relocate an *empty unused draft* node with impact preview" verbatim.
6. **Deactivation dependency-impact checking is real where a real dependency exists, disclosed as deferred where none does yet** — identical boundary to `ATW-229`'s own design note 7. A location cannot deactivate while any `draft`/`active` child location still exists under it (a real, checkable dependency); stock/task-level dependency checking is **not** implemented, since no inbound/inventory/task table exists yet (`ATW-231` WMS Inbound is the very next task).
7. **A barcode resolves a candidate location; it never itself authorizes anything** (Prompt 230 §24 verbatim) — `app.resolve_warehouse_location_by_barcode` is a plain, record-scope-gated read, structurally incapable of performing or authorizing any putaway/pick/inventory action.
8. **Restricted-zone/secure-area access beyond standard record-scope is disclosed as deferred, not built** — no per-user zone-restriction-grant mechanism has ever been requested or built anywhere in this repository; a location's own authority is exactly its warehouse's own company-org-unit record scope.
9. **List reads are bounded, one level at a time, never a full recursive tree fetch** — Prompt 230 §17's own explicit "no full warehouse tree in browser" anti-pattern.
10. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 3.2 Schema — `supabase/migrations/20260730150000_create_advanced_tms_bin_racking.sql`

One new table (`app.warehouse_locations`, self-referencing `parent_id`, materialized `path`/`depth`, a partial unique barcode index scoped tenant-wide), one new composite type (`app.warehouse_location_deactivation_impact`), and seven new RPCs: `app.create_warehouse_location`/`app.update_warehouse_location`/`app.move_warehouse_location`/`app.set_warehouse_location_status`/`app.get_warehouse_location_deactivation_impact` (lifecycle), `app.list_warehouse_locations` (bounded one-level read), `app.resolve_warehouse_location_by_barcode` (informational scan resolution). Two triggers (`app.enforce_warehouse_location_parent_shape`, `app.recompute_warehouse_location_path`) mirror `app.org_units`'s own shape/cycle-guard-then-path-recompute pair exactly. RLS is `app.can_access_record`-scoped by the location's own warehouse's company org unit, matching `ATW-229`'s own precedent. Mutation authority is `OPS:Create` for location creation, `OPS:Edit` for update/move/status-change, `OPS:View` for reads; `app.resolve_warehouse_location_by_barcode` requires only active tenant membership plus the location's own record scope (no module action beyond membership, since it is a pure lookup).

### 4.1 Real defects found and fixed during authoring (before commit)

1. **A test-authoring mistake, not a schema/RPC defect**: the db-test's own first-drafted cross-warehouse-move assertion targeted `(select id from app.warehouse_locations where warehouse_id = v_wh_b_id limit 1)` — but `WH-B` had zero locations at that point in the fixture, so the subquery returned `NULL`, and moving a node to `parent_id = NULL` is always legal (it means "move to root"), so the move silently succeeded instead of raising `cross_warehouse_parent`. Fixed by creating a real root location in `WH-B` first (`WHB-ROOT`) and targeting it directly, so the assertion actually exercises the cross-warehouse guard rather than a no-op.
