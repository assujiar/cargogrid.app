## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **The Shipment Order remains the single canonical root and lifecycle.** `app.shipment_orders` gains one new nullable column, `leg_network_status` (`null|draft|confirmed`) — an additive planning-state projection, never a second state machine. The already-governed `app.transition_shipment_order` (OPS-170) is untouched; a leg's own `leg_status` is a smaller, leg-scoped state machine that never mutates the parent shipment's canonical `status`.
2. **Carrier reference reuses `app.master_records` directly** (`master_type_code in ('vendor','fleet')`), the identical party-shaped-reference template `app.resource_assignments.resource_id` (OPS-172) and Finance's own `app.finance_vendor_bills.vendor_master_id` already established — no new vendor/fleet master table.
3. **Location uses the PLT-134/ADR-0014 `geography(Point,4326)` convention.** A real defect was found and fixed before commit: `app.validate_geography_point`/`app.geojson_point_to_geography` (PLT-134) have no explicit `set search_path`, so they resolve the bare `geometry`/`geography` types under the *caller's* active search_path at execution time. Any of this migration's own `security definer` functions restricted to `set search_path = app, pg_temp` (the ERR-2026-004 convention) that insert into or validate against `shipment_leg_stops` therefore needed `public` added to their own search_path (`add_shipment_leg_stop`, `migrate_legacy_shipment_to_leg_network`) — otherwise the insert's own CHECK constraint invocation of `app.validate_geography_point` fails with `type "geometry" does not exist`. Every other function in this migration keeps the tighter `app, pg_temp` path since none of them touch a geography-bearing table.
4. **Cargo allocation is one row per leg** (a governed 1:1, the same bounded-slice discipline `app.shipment_mode_profiles` already applies) — splitting cargo across multiple lines within a single leg is out of this task's scope, disclosed rather than silently expanded.
5. **Aggregate network state (`app.get_shipment_leg_network_state`) is live-derived, never stored** — `not_started`/`blocked`/`in_progress`/`completed`, computed fresh on every read from the current leg set, so it can never drift from the underlying legs (Prompt 221 §24's "aggregate shipment state is derived from canonical leg states under a versioned rule").
6. **`app.migrate_legacy_shipment_to_leg_network` is the one required expand-only backfill** (Prompt 221 §19) — idempotent, creates one `is_legacy_compat` leg (sequence 1) plus two stops (pickup at origin, delivery at destination) mirroring the shipment's own mode/schedule/allocation, and immediately confirms the (trivially valid, single-leg) network. Not run automatically by this migration against any existing row — no live Supabase project/data exists yet to backfill (repository-wide disclosed condition, unchanged); the function is proven directly by this checkpoint's own db-test fixture instead.
7. **Adding or cancelling a leg after the network was confirmed resets `leg_network_status` back to `draft`** — a confirmed network is a validated snapshot of a specific leg set; any membership change must be re-validated before execution resumes (Prompt 221 §22's "add an approved transshipment... with impact preview" alternative flow).
8. **A leg cannot leave `planned` for `dispatched` until its own shipment's leg network is `confirmed`** — dispatch requires a validated network, enforced structurally in `app.transition_shipment_leg`, not merely by convention.

### 3.2 Schema — `supabase/migrations/20260729290000_create_advanced_tms_multi_leg_shipment.sql`

One additive column on `app.shipment_orders` (`leg_network_status`) plus four new tables: `app.shipment_legs` (sequence/mode/status/carrier/schedule, unique on `(tenant_id, shipment_order_id, idempotency_key)` and `(tenant_id, shipment_order_id, sequence_no)`), `app.shipment_leg_stops` (pickup/transfer/delivery, `geography(Point,4326)` location), `app.shipment_leg_cargo_allocations` (one per leg), `app.shipment_leg_custody_events` (append-only, server-assigned `sequence_no`). Ten mutating functions (`add_shipment_leg`, `cancel_shipment_leg`, `add_shipment_leg_stop`, `allocate_shipment_leg_cargo`, `confirm_shipment_leg_network`, `transition_shipment_leg`, `record_shipment_leg_custody_event`, `migrate_legacy_shipment_to_leg_network`) plus two read functions (`get_shipment_leg_network_state`, `get_shipment_leg_stops` — the latter security-invoker, serializing `location_geog` to GeoJSON via `app.geography_to_geojson_point` rather than exposing the raw geography wire format through a direct table select). RLS on all four tables joins through to the parent Shipment Order's own `tenant_id`/`owner_user_id`/`org_unit_id` via `can_access_record`/`lead_record_scope_org_unit_ids`, the identical pattern `app.shipment_mode_profiles` (OPS-171) and `app.milestone_events` (OPS-173) already use for a child table with no owner/org-unit column of its own. Reuses the pre-seeded `OPS` permission action set (`Create`/`Edit`) — no new `app.permissions` row, no new module code (confirmed by direct inspection: `OPS` was documented at `PLT-106` to span "Job/Shipment, TMS, WMS, Milestone, ePOD" — the whole Operations domain including Advanced TMS/WMS). Per ERR-2026-004: explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` before final grants.

UI: the Shipment Order detail page (`app/(tenant)/[tenantSlug]/operations/shipment-orders/[shipmentOrderId]/page.tsx`) gained a "Multi-leg network" section (`leg-network-panel.tsx`) showing the network/aggregate-state badges, an ordered leg list (each with its stops, cargo allocation, and custody-event log), and forms for add-leg / add-stop / allocate-cargo / confirm-network / transition-leg / cancel-leg / record-custody-event / migrate-legacy, wired through eight new Server Actions in the route's own `actions.ts`. Scope boundary disclosed: this task delivers list/timeline rendering only — an interactive map view is deferred (no map library exists in this repository yet; adding one is a separate, larger UI decision this bounded task does not make unilaterally). Longitude/latitude are shown as plain coordinates in the stop list instead.

## 4. Data migration and compatibility

Existing single-leg Shipment Orders are left with `leg_network_status = null` until `app.migrate_legacy_shipment_to_leg_network` is explicitly invoked for one — reversible in the sense that no Shipment Order column is altered, only additive rows (one leg, two stops, one cargo allocation) are created. Proven end-to-end by this checkpoint's own db-test: a bare confirmed Shipment Order with zero legs is migrated, produces exactly one `is_legacy_compat` leg and two stops, immediately confirms its own network, and a repeated migration call is idempotent (returns the same leg, does not create a second one).
