## 2. Design decisions (disclosed, migration header)

Disclosed in the migration header (`supabase/migrations/20260730220000_create_advanced_tms_lot_batch_serial_expiry.sql`), opening with an explicit accounting of all five known bug classes from `ATW-013`/`ATW-014`'s own reviews and how each was proactively closed here:

- **(a)** idempotent-replay short-circuits in `register_lot_identity`/`register_serial_identity`/`set_lot_identity_status`/`set_serial_identity_status` always run strictly after `app.evaluate_permission`, never before.
- **(b)/(c)** `SELECT ... FOR UPDATE` on first read, held through the final `UPDATE`, in both status-setter RPCs.
- **(d)** create-once races (`register_lot_identity`'s natural key, `register_serial_identity`'s idempotency key) wrap the `INSERT` in a nested `begin/exception ... unique_violation` recovery block, mirroring `app.create_item_master`/`app.start_wms_receipt_session`.
- **(e)** (`ATW-014`'s newest lesson) real serial-number uniqueness is enforced by a genuine Postgres `UNIQUE` index (`serial_identities_governed_scope_unique`), not a cross-row aggregate/TOCTOU check — Postgres itself serializes concurrent registrations; the FIFO/FEFO candidate query is read-only decision support with no write to serialize.

The most consequential design-boundary notes:

1. **`app.item_control_policy_versions`** — a versioned draft→published→archived control-policy table scoped by `item_master_id`, mirroring `app.publish_margin_rule_version`'s (`COM-150`) own lifecycle shape, carrying only the genuinely new policy surface (`allocation_rule` fifo/fefo, `hold_on_unknown_lot`, `near_expiry_warning_days`) — never a second copy of `app.item_masters`' own `lot_controlled`/`serial_controlled`/`expiry_controlled` flags (`ATW-011A`), which every register/publish RPC reads live and composes against.
2. **`app.lot_identities`** — real uniqueness `(tenant_id, owner_account_id, item_master_id, lot_number)`, mirroring `app.item_masters`'s own owner-scoped uniqueness precedent; a bounded, disclosed genealogy via a single nullable `parent_lot_id` self-FK, settable only with `source_type = 'split'`, structurally required to share tenant/owner/item with its child — no multi-generation traversal API.
3. **`app.serial_identities`** — real uniqueness `(tenant_id, item_master_id, serial_number)` via a genuine unique index, distinct from and never modifying `app.post_inventory_movement`'s (`ATW-015`) own bounded on-hand≤1 check; a separate real `idempotency_key` unique constraint disambiguates a race/retry (return existing) from a genuine `duplicate_serial` (a different key colliding on the natural key).
4. **One generic status-lifecycle RPC each** (`set_lot_identity_status`/`set_serial_identity_status`, active/held/quarantined/expired/consumed, `OPS:Override`-gated) rather than four separate hold/release/quarantine/expire functions, mirroring `app.set_item_master_status`/`app.set_warehouse_location_status`'s established shape.
5. **No scheduler marks anything expired** (no worker runtime exists yet, `ISS-2026-015`) — `app.list_allocation_candidates` structurally excludes any lot/serial whose real `expiry_date` has passed regardless of stored `status`, so the "expired stock cannot be allocated silently" criterion holds for any *registered* identity without a cron job.
6. **`ATW-013` widening — deliberately not done, disclosed deferral.** Widening `app.commit_wms_receipt_line`/`app.record_wms_receipt_line_count` to auto-register captured lot/serial identities was evaluated and rejected: the already-`VERIFIED` `ATW-013`/`ATW-015` db-test fixtures post lot/serial text through those functions with no registration step, and any widening risks silently changing already-verified behavior for a benefit achievable by an independently-callable RPC instead. `app.register_lot_identity`/`app.register_serial_identity` are real, standalone, proven RPCs; live wiring into receiving capture is disclosed as deferred, mirroring `ATW-012`'s own "mechanism proven, live wiring deferred" precedent. **Direct, load-bearing consequence, confirmed by this checkpoint's own adversarial review and left as-is per that same explicit precedent:** `app.list_allocation_candidates` can only exclude a held/expired identity once it has actually been registered through this capability's own RPC — since nothing in the live system calls those RPCs yet, the exclusion is real but currently inert end-to-end. Logged as a new disclosed known issue, `ISS-2026-016` (§6 below), not silently dropped.
7. **`app.list_allocation_candidates`** (FIFO/FEFO) is real, `stable`, read-only decision support — never reserves/consumes; `app.reserve_inventory`/`app.consume_inventory_reservation` (`ATW-015`) remain the only real allocation-execution mechanism, unmodified, correctly left to `ATW-236` (Picking). FIFO orders by identity `created_at` (disclosed proxy for "received first"); FEFO orders by `expiry_date` ascending, nulls last; `near_expiry` is a genuinely computed output from the policy's own `near_expiry_warning_days`.
8. Reused `app.wms_receipt_sessions`/`app.wms_putaway_tasks`'s idempotency-column convention and `app.item_masters`'s tenant-wide (not warehouse-scoped) record-scope precedent for the new tables.

### 3.3 Defects found by adversarial review, all fixed

The implementing agent was explicitly briefed on and proactively applied all five known bug classes from `ATW-013`/`ATW-014` (§2 above) — none of those five recurred; independently re-confirmed by all three review lenses. The three-lens review nonetheless found **two genuinely new defects**, plus three smaller spec/coverage gaps, none of them repeats of the five pre-briefed classes:

**1. [CRITICAL] Cross-owner data leak on every read RPC — live-proven, not theoretical.** None of the six read RPCs (`get_item_control_policy`, `list_item_control_policy_versions`, `get_lot_identity`, `list_lot_identities`, `get_serial_identity`, `list_serial_identities`) enforced any owner-account scoping — each gated solely on tenant-wide `OPS:View`, so any actor holding that permission, including a `customer_user`-layer actor scoped to a single owner via `principal_memberships.customer_account_ref`, could read every *other* owner's lot/serial/policy data in the same tenant, directly violating Prompt 235 §26 ("customers see only their owner-scoped permitted trace data"). The security-authority review lens live-reproduced this: a synthetic customer-portal actor scoped to owner "Alpha" successfully called `app.list_lot_identities`/`app.get_lot_identity` and received owner "Beta"'s full lot data (lot number, dates, `hold_reason`, `owner_account_id`). `get_lot_trace`/`get_serial_trace` compounded the same gap from the opposite direction — both hardcoded `p_customer_account_ref => null` in their `app.can_access_record` call, so the one legitimate customer-scope branch could never match either, meaning the capability neither protected owner data nor let a real customer actually see their own.

   **Fix:** the fix agent designed and implemented the missing owner-scope resolution the review's own finding assumed already existed but does not (confirmed by grep: `principal_memberships.customer_account_ref` is documented, `PLT-108`, as "a reserved scope-dimension placeholder ... not a live foreign key," never previously wired to `app.accounts`). Added `app.resolve_actor_owner_account_scope(auth_user_id, tenant_id)` (Supreme Admin/staff → `null`/unrestricted; a `customer_user` membership → the real `array_agg` of that actor's own `customer_account_ref` values cast to `uuid`, guarded by a regex format check so an unrelated capability's non-uuid-shaped `customer_account_ref` label can never collide or throw) and `app.actor_can_view_owner_scoped_row(...)` as the single shared predicate, applied to all six read RPCs, both trace RPCs (replacing the hardcoded `null`), and the RLS `SELECT` policy on all three new tables (finding below). Staff/Supreme Admin/no-membership actors remain unrestricted, unchanged from before.

**2. [HIGH] RLS `SELECT` policies had zero owner predicate.** All three new tables' `_select_scoped` policies gated only on `has_active_tenant_membership`/`is_supreme_admin` — no owner-account scoping at all, so the defense-in-depth RLS layer this codebase's own architecture treats as a real last line of defense provided zero owner protection (the RPCs are `SECURITY DEFINER` so RLS doesn't gate them today, but a future non-`SECURITY DEFINER` read path would have leaked immediately). **Fix:** added `app.actor_can_view_owner_scoped_row(auth.uid(), tenant_id, owner_account_id)` to all three policies — the identical predicate the RPC layer now shares, one source of truth.

**3. [HIGH, independently live-reproduced by two separate reviewers] `app.publish_item_control_policy_version` never incremented `record_version`.** The migration header claimed to mirror `app.publish_margin_rule_version` (`COM-150`) "verbatim," but `COM-150` does `record_version = record_version + 1` on both its archive and publish `UPDATE`s while this function did neither. Both the spec-compliance and correctness-concurrency review lenses independently live-reproduced this with two real concurrent psql sessions: a second, racing publish call with the same stale `expected_version` succeeded silently instead of raising `stale_version`, re-publishing the row and overwriting `supersedes_version_id`/the audit trail — the shipped db-test only ever probed `stale_version` with an obviously-wrong sentinel (`999999`), never a genuine same-value collision, so it never caught this. **Fix:** added `record_version = record_version + 1` (alongside `updated_at = now()`) to both `UPDATE` statements, now genuinely matching `COM-150`; the fix agent re-ran the full db-test suite including `COM-150`'s own db-test file unmodified and still green.

**4. [MEDIUM] `effective_from` captured but never enforced.** `get_item_control_policy`, the `register_lot_identity`/`register_serial_identity` policy lookups, and `list_allocation_candidates` all read the published policy without filtering by `effective_from <= now()`, unlike this codebase's own established convention for this exact pattern elsewhere — violating Prompt 235 §25 ("policy version matches owner/item/effective time"): a policy published with a future `effective_from` took effect immediately instead of on schedule. **Fix:** added `and effective_from <= now()` to all four lookups, with a new db-test proving a policy published 30 days in the future is `policy_version_not_found` until then.

**5. [LOW, cosmetic] Mismatched error code.** `register_lot_identity`/`register_serial_identity` both raised `invalid_near_expiry_warning_days` when rejecting an irrelevant `expiry_date` on a non-expiry-controlled item — a code otherwise used for the policy's own `near_expiry_warning_days` field. **Fix:** renamed to `expiry_date_not_applicable`, added to the server-layer known-error-code list, with new db-test coverage for both call sites.

**Non-finding, deliberately left as-is:** the review also independently confirmed design note 6's disclosed limitation (allocation-candidate exclusion is inert for any never-registered balance) as real but explicitly pre-authorized scope, per the same `ATW-012` "mechanism proven, live wiring deferred" precedent — not rebuilt, logged instead as `ISS-2026-016` (§6).

One defect was found and fixed by the implementing agent itself, before any external review: a db-test fixture bug where an earlier test block's published `hold_on_unknown_lot=false` policy leaked an extra un-held lot into a later FIFO/FEFO candidate-count assertion — fixed by explicitly setting status via `set_lot_identity_status`/`set_serial_identity_status` rather than relying on a since-superseded default, with new assertions on actual default status added so the fixture cannot silently drift again.

## 6. New disclosed known issue

**`ISS-2026-016`** (added to `docs/runtime/KNOWN_ISSUES.md` this checkpoint): `app.register_lot_identity`/`app.register_serial_identity` are real, correct, independently-callable RPCs, but nothing in the live system calls them yet — `ATW-013`'s receiving-capture RPCs still only store lot/serial as plain, ungoverned text, exactly as before this checkpoint (design note 6 above, a deliberate, explicitly pre-authorized deferral, not an oversight). Direct consequence: `app.list_allocation_candidates`'s real held/expired/duplicate-serial exclusion is correct but currently inert for any balance whose lot/serial identity was never separately registered through this capability's own RPCs — Prompt 235 §33's "expired/held or duplicate-serial stock cannot be allocated silently" does not yet hold end-to-end against live `ATW-013` receiving traffic. Not a blocker for this checkpoint (the mechanism is real, proven, and correctly scoped per its own disclosed boundary) but must be resolved — either by wiring registration into receiving capture or by an explicit design decision that some other capability owns that wiring — before `ATW-236` (Picking) or any capability that actually executes allocation begins.
