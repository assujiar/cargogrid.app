## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Confidence/freshness provenance is computed once, at confirmation time**, from the real canonical telemetry event backing a candidate/signal — never fabricated for a manually-filed record. `app.evaluate_telemetry_confidence_and_freshness` is the one shared formula both `app.confirm_milestone_candidate` and `app.confirm_exception_signal` (both `226G`) now call, reusing `app.resolve_tenant_tracking_source_policy` (`226A`) thresholds and `app.get_vehicle_source_health`'s own 1x/3x banding (`226F`).
2. **`app.milestone_events`/`app.operational_exceptions` are widened additively** — four new nullable columns each. `milestone_events` is append-only (`OPS-173`); these columns populate only at INSERT time for new rows, every historical row stays honestly null (`228_*.md` §19).
3. **A real, disclosed defect in `app.evaluate_leg_no_signal_escalation` (`ATW-225`) is fixed, not worked around**: it measured a session's own staleness from `now() - started_at`, not from the vehicle's own actual last-received telemetry — at `225`'s own authoring time, `226F`'s canonical telemetry health did not exist yet. A long-running-but-healthy session was incorrectly flagged stale purely for running long. Widened (`CREATE OR REPLACE`, identical signature) to prefer `app.vehicle_source_health.last_seen_received_at` when one exists, falling back to `started_at` only for a session with no telemetry at all or a `driver`-kind session (`226F`'s health table is vehicle-keyed only).
4. **A second, complementary tracking-health mechanism, staged like every other `226G` signal**: `app.evaluate_leg_no_signal_escalation` is a human-triggered, single-leg, directly-authoritative check. This migration adds a tenant-wide, scan-based, `service_role`-only detector (`app.detect_shipment_leg_tracking_health_signals`) staging a new signal type (`tracking_health_no_signal`, additive `CHECK` widening on the existing `app.shipment_exception_signals.signal_type` — reusing that table, never a second staging table), reviewed through the exact already-`VERIFIED` `app.confirm_exception_signal`/`app.dismiss_exception_signal` path. A recovered leg is silently auto-dismissed, mirroring `226G`'s own route-deviation "a silent recovery never fires a signal" precedent; structurally storm-proof via the existing `(tenant_id, correlation_key) where status='pending'` unique index.
5. **Dependency-aware live ETA is read-only and honestly bounded, never a routing engine.** `app._compute_shipment_leg_eta` (internal) walks the leg's own remaining stops from the vehicle's own live canonical position, the identical straight-line-corridor approximation `226G`'s own route-deviation evaluator already discloses, at `ATW-224`'s own governed `app.route_planning_default_speed_kmh()` (40 km/h). Returns `computable = false` with a named reason rather than a fabricated estimate whenever no live position, an offline position, or no remaining stop exists. `downstream_leg_count` is the bounded "dependency-aware"/"batch dependency impact" signal (§17) — never an automatic rewrite of any other leg's own schedule.
6. **Rebaseline is an explicit, human-authorized, bounded mutation** — only while a leg is still `planned` (§22's own "rebaseline unstarted milestones"), `OPS:Edit`-gated, mandatory reason, full before/after audit. Never fires automatically from the ETA projection.
7. **The public customer projection is widened a fourth time** (`app.lookup_public_shipment_tracking`; `226C` added rate limiting, `226H` added sanitized vehicle position) via `DROP FUNCTION` + `CREATE FUNCTION` (`226C`'s own precedent for a signature change), adding `live_eta_status`/`live_eta_at`, gated on the identical `customer_visible` flag vehicle position already uses — deliberately distinct from `app.shipment_milestone_projections`'s own `current_eta`/`is_delayed` (`OPS-173`), whose own comment already discloses "never a predictive ETA algorithm"; this is that algorithm's first real version.
8. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 4.1 Real defects found and fixed during authoring (before commit)

1. **A real, pre-existing defect in `ATW-225`'s own `app.evaluate_leg_no_signal_escalation`** (design note 3) — see §3.1 above for the full analysis and fix.
2. **A trailing-parameter widening on `app.ingest_milestone_event`/`app.report_exception` initially used `CREATE OR REPLACE`**, which silently creates a second, ambiguous overload rather than replacing a function once the parameter list changes — caught immediately by a `COMMENT ON FUNCTION ... is not unique` error on the very next statement. Fixed by switching both to `DROP FUNCTION` + `CREATE FUNCTION` (`226C`'s own `app.end_leg_tracking_session` precedent for exactly this class of change), re-granting both functions' own prior grants explicitly (a `DROP` clears them, unlike `CREATE OR REPLACE`).
3. **`make_interval(hours => numeric)` does not exist** — `make_interval`'s own `hours` parameter is `integer`-typed, rejecting a fractional value; fixed by multiplying the numeric hour count against `interval '1 hour'` instead, the correct idiom for a fractional-hours interval.
4. **A literal copy-paste error**: the widened `app.lookup_public_shipment_tracking`'s own success-path return accidentally used `'success'` for `lookup_status` instead of the original `'ok'` — caught immediately by `ATW-226H`'s own pre-existing db-test assertion re-failing on this checkpoint's very first full-suite run, proving the regression-detection discipline works as intended.
5. **A missing `public` schema in `app.detect_shipment_leg_tracking_health_signals`'s own `search_path`** — the identical bug class `226E`/`226G` already found: its own internal `UPDATE ... app.shipment_exception_signals` (auto-recovery) re-validates the row's full `CHECK` constraint set, including `validate_geography_point` on the (untouched) `location` column, which requires `public` in scope to resolve PostGIS types during inlining. Fixed by adding `public` to this function's own search_path.
6. **A miscounted `app.capture_audit_event` call** in `app.rebaseline_shipment_leg_schedule` — the real signature is `(tenant_id, actor, label, action, resource_type, resource_id, result, reason, before_value, after_value, correlation_id)`, not `(..., result, before, after, metadata)` as first assumed; the old/new schedule values were also captured incorrectly (the `RETURNING` clause had already overwritten the "before" state by the time the call was authored). Fixed by capturing the pre-update row into a dedicated `v_before` variable and correcting the argument order (`result, reason=null, before_value, after_value`).
7. **Two test-authoring mistakes**: (a) `app.audit_logs`'s own record-reference column is `resource_id`, not `record_id`; (b) `app.issue_shipment_tracking_token` requires the calling actor to pass both `OPS:Edit` and `can_access_record` against the shipment's own `owner_user_id`/`org_unit_id` — the fixture's "admin" identity (granted the rep role only for `ATW-223`'s own master-data-registration precondition) does not itself own or share record-level access to a shipment created entirely under "rep"; fixed by calling as "rep" throughout, the actor who actually owns every shipment/leg record this file touches.
