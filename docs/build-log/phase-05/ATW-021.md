## 2. Design decisions (disclosed, migration header)

1. **A barcode never itself authorizes anything** — `app.resolve_label` re-derives authorization from the LIVE subject row on every call (via `app.label_subject_record_scope_ok`), never from `label_instances`' own cached `owner_account_id`/`warehouse_id` columns, which are audit/query-convenience denormalizations only. This generalizes `app.resolve_warehouse_location_by_barcode`'s (`ATW-230`) own design note 7 to seven subject types.
2. **A deterministic, independently-verifiable checksum** (`app.compute_label_checksum_digit`) is recomputed and compared *before* any table lookup on every scan — a structurally malformed/forged code is rejected without ever touching `app.label_instances`.
3. **`app.label_instances` is created once per logical label**; print/reprint are separate `app.label_print_jobs` events referencing the same instance, never creating a second one — reprint/void preserve lineage.
4. **No live print worker/hardware exists** — `app.record_label_print_outcome` is a real, callable worker-completion interface with nothing calling it yet, mirroring the GPS Gateway's (`ATW-226D`) own "real interface, no live hardware" precedent. No PDF/ZPL binary rendering or Document/File Engine (`PLT-128`) integration was built — `app.files.uploaded_by_auth_user_id` is `NOT NULL` with no system-actor path, a poor fit for a job-generated artifact without first extending that engine, out of this task's own bounded scope.
5. **The shared `app.jobs` queue (`PLT-131`/`132`) is widened additively**, not re-implemented — `job_type` gains `'print_label'` via the same `DROP/ADD CONSTRAINT` + same-signature `CREATE OR REPLACE FUNCTION app.enqueue_job` pattern `ATW-224` already established for `'route_load_planning'`.
6. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 3.3 Ten findings from three independent adversarial-review lenses, consolidated to six real defects, all fixed

The three-lens review was explicitly briefed on eight known repository bug classes, including two found and fixed at `ATW-020` one checkpoint earlier ((g) inconsistent redaction across functions returning the same row shape, (h) an idempotency-key dedup that matches on the key alone without validating the found record belongs to the current caller's target). **Bug class (h) recurred here, in two different RPCs, independently found and live-reproduced by all three review lenses**:

1. **[CRITICAL, recurrence of ATW-020 bug class (h)] `app.generate_label`'s idempotency-key dedup matched on `(tenant_id, idempotency_key)` alone**, never validating the found row's `subject_type`/`subject_id` against the current call's target. Live-reproduced: reusing a key across two different item subjects (one Alpha-owned, one Beta-owned) silently returned the Alpha label for the Beta request, with zero rows ever created for the Beta item and no error at all. **Fix:** both the initial short-circuit and the retry loop's `unique_violation` exception handler now compare `subject_type`/`subject_id` and raise `idempotency_key_conflict` on mismatch.
2. **[CRITICAL, same recurrence, one RPC over] `app.execute_label_print`** (the shared core of `app.print_label`/`app.reprint_label`) **had the identical unvalidated dedup** — a key reused across two different label instances silently returned the first label's print job, meaning the intended label was never actually queued to print at all, with a false-success return. **Fix:** validates `label_instance_id`/`printer_id`/`is_reprint` match, raising `idempotency_key_conflict` on mismatch.
3. **[HIGH] `app.execute_label_print`'s own insert had no `unique_violation` exception wrapper**, unlike every other create-once insert in the migration. Since the function's row lock is per-label-instance, two concurrent calls sharing an idempotency key but targeting *different* label instances never serialize on that lock — live-reproduced with two real concurrent psql sessions (one held an open transaction, the second blocked on the uncommitted unique-index entry and then surfaced a raw, uncaught `duplicate key value violates unique constraint` straight through to the caller). **Fix:** wrapped in `begin/exception when unique_violation`, matching every sibling insert.
4. **[HIGH] `app.generate_label` had no per-subject record-scope check at all** — its only authorization gate was tenant-wide `OPS:Create`, with no org-unit/warehouse dimension, unlike every comparable "create a record tied to a warehouse" RPC elsewhere in this migration and in `ATW-020`. Live-reproduced: a staff actor invited under Branch A only (first proven genuinely branch-scoped by a correct rejection from `app.create_label_printer` targeting Branch B) successfully generated a real, persisted label for a bin subject inside out-of-scope Warehouse B. **Fix:** added an `app.label_subject_record_scope_ok` check immediately *after* the existing `subject_not_found` existence check (ordered so it can never mask a real not-found behind a misleading authorization error, and costs no extra lookup).
5. **[MEDIUM] `app.create_label_printer`'s idempotent-by-code lookup ignored a mismatched `warehouse_id`/`name`/`connection_descriptor`** on the request, unlike `app.create_label_template`'s own explicit mismatch check in the same file. Live-reproduced: a second call with the same code but a materially different warehouse/name silently returned the original row. **Fix:** added the equivalent mismatch check, raising a new `label_printer_code_conflict` error code.
6. **[LOW] `app.publish_label_template_version` read the superseded version without `FOR UPDATE`** before an unconditional archive `UPDATE`. Not live-exploitable (the table's only reachable prior states converge to the same terminal outcome), but fixed anyway as a cheap, zero-behavior-change hardening for consistency with every other locking pattern in the file.

No finding was a false positive; all ten (six after consolidating duplicate root causes across lenses) were confirmed real and fixed.
