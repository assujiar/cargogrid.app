## 2. Design decisions (disclosed, migration header)

The most consequential design decisions, disclosed in the migration header (`supabase/migrations/20260730250000_create_advanced_tms_wms_packing.sql`):

1. **No inventory-ledger interaction at all.** Packing never calls `app.post_inventory_movement` — it only tracks how much of an already-picked pick task's `picked_quantity` has been assigned into a package. Prompt 237's own "box/carton/pallet" packaging-unit identity (explicitly deferred by `ATW-011A`'s own design note 4) is resolved here via a real, bounded `package_type` CHECK enum column, never a new `app.uoms` row.
2. **One lightweight, state-machine-free packing task per outbound order** (`app.wms_packing_tasks`) — mirrors `ATW-017`'s wave design one level up; no `status` column, completion state always derived from member `app.wms_packages` rows.
3. **Package/container hierarchy**: a single self-referencing `parent_package_id` on `app.wms_packages`, with a real, dedicated `app.reparent_wms_package` RPC performing a bounded (≤100 levels) ancestor walk. `app.create_wms_package` is cycle-safe by construction (a new package's own server-generated id is unknowable in advance, so it can only reference an already-acyclic graph).
4. **Package identity/owner**: `owner_account_id` is derived immutably at creation from the packing task's own outbound order, never caller-supplied; every line-add independently checks both order match and owner match (deliberately redundant defense-in-depth).
5. **"Confirmed package changes require governed reopen, not silent edit"** is enforced at both the RPC layer (every mutating RPC except reopen rejects a confirmed package) and the table layer via real CHECK constraints making a "confirmed but incomplete" row structurally unrepresentable. `app.reopen_wms_package` is `OPS:Override`-gated, resets QC/seal to force genuine re-inspection, and records a full before/after audit event.
6. **No claim/assignment concept on packages** (unlike `ATW-014`/`017`'s per-task claim workflow) — a disclosed, bounded design choice: a packing station is an open queue where multiple packers may work different packages of the same order concurrently; concurrency safety comes from the package row's own `FOR UPDATE` lock, not a claimant-identity check.
7. **QC** is bounded pass/fail/hold with a distinct, non-destructive override evidence trail — the original failed/held outcome is never silently overwritten by an override.
8. **Weight is mandatory to confirm; seal is required only for root packages** — nested child containers are exempt.

### 3.3 A critical concurrency defect found by adversarial review, independently confirmed by two lenses, fixed

**[CRITICAL/HIGH, both `spec-compliance` and `correctness-concurrency` lenses independently found the identical defect]** `app.reparent_wms_package`'s cycle-prevention ancestor walk locked only the package being moved and its immediate new parent (`SELECT ... FOR UPDATE`) — every further node in the ancestor chain was read with a plain, unlocked `SELECT`. Two genuinely concurrent, individually legitimate `reparent` calls whose locked row pairs are fully disjoint (e.g. `reparent(A, new_parent=D)` and `reparent(C, new_parent=B)`, where each call's own ancestor walk only ever reads rows the other call hasn't locked) can each pass their own cycle check against pre-race state and both commit — together forming a real cycle in `app.wms_packages.parent_package_id`, directly violating Prompt 237 §24 ("package identity and hierarchy are stable and cannot cycle") and §33's own acceptance criterion. Both reviewers independently live-reproduced this against a real, freshly-migrated Postgres database using two genuinely concurrent psql sessions with disjoint pre-locking and a staggered commit, confirming a real, persisted 4-node cycle (`A→D→C→B→A`) with both RPC calls returning success — no error, silent corruption. The corruption is permanent: no table-level CHECK or trigger catches a cycle deeper than immediate self-parent, and any future traversal of the cyclic chain (breadcrumbs, reporting, or a later reparent attempt) would loop indefinitely or hit the bounded-depth guard for an unrelated reason.

**Fix:** every node visited during the ancestor walk is now locked `FOR UPDATE` (a one-line change — the walk's own `SELECT` gained `for update`), not just the two endpoints. Any two concurrent reparents whose walks would together form a cycle now necessarily contend on a real row lock somewhere in the two walks; Postgres's own deadlock detector aborts one of them (a normal, retryable `deadlock detected` error) and the survivor's walk always observes fully-committed state, so no cycle can ever be persisted. Re-verified with the identical two-session repro against the patched function: the first session committed normally, the second failed cleanly with a genuine deadlock error and rolled back with no partial writes — final state a clean tree, no cycle. The other review lens (`security-authority-owner-scoping`) returned no findings, including a live cross-owner isolation proof (both RPC-level and a raw-RLS-policy-level probe, mirroring `ATW-017`'s own review methodology) confirming every read RPC and RLS policy correctly reuses `app.wms_pick_record_scope_ok` (`ATW-017`).
