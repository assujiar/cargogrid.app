## 3. F-1 — Idempotency key never validated against its target (High)

### What was wrong

Twenty Phase 5 WMS mutation functions carried this shape:

```sql
select * into v_existing from app.wms_pick_tasks
  where tenant_id = v_line.tenant_id and idempotency_key = p_idempotency_key;
if found then
  return v_existing;          -- no check that v_existing is even about this request
end if;
```

The key is unique per `(tenant_id, idempotency_key)`. Nothing compared the found row's target against the target the caller actually named.

### Live reproduction (deterministic, no concurrency)

Against a freshly migrated database, with the key `idem-gen-keyrace-samekey` already used by outbound order line X:

```
select (app.generate_wms_pick_task('<LINE_Y>', 5, ..., 'idem-gen-keyrace-samekey', ...)).outbound_order_line_id;
-- returned: 4dd11225-...  <- LINE_X, not LINE_Y. No error. No warning.
```

A request to pick against line Y returned a pick task belonging to line X — a different item, a different order, potentially a different customer.

Two damage shapes existed:

- **(a) Misattribution** — functions returning `v_existing` handed back a different target's row.
- **(b) Silent no-op** — functions returning the freshly-read parent row (`v_task`, `v_package`, `v_shipment`) skipped the requested operation entirely while appearing to succeed: a scanned package line never recorded, a pick never confirmed, a shipment never load-confirmed. Physical warehouse work that genuinely happened never reached the ledger.

### Why this is not merely theoretical

`p_idempotency_key` is **user-supplied free text** in this product. `app/(tenant)/[tenantSlug]/finance/**/actions.ts` and siblings read it directly from `<input name="idempotencyKey" type="text" required>`. Reusing a key across two different operations is an ordinary operator typo, not an attack needing a race window.

### Why `ISS-2026-024`'s diagnosis was wrong

`ISS-2026-024` recorded the picking keyrace test as flaky, and hypothesised that `app.reserve_inventory`'s replay short-circuit "may … resolve the second request against the first's own in-flight row before its own content-mismatch check can observe the difference", concluding that "the content-mismatch check does work under most real timings".

There was no content-mismatch check anywhere in `app.generate_wms_pick_task` to work. The test passed only when the two processes overlapped tightly enough to collide on the unique index — which does raise. Whenever process B simply started after process A committed (the ordinary case), the unguarded short-circuit returned A's row and the assertion failed. The observed ~2-in-11 failure rate was the scheduler, not the product being mostly right.

### Repair

`supabase/migrations/20260730380000_harden_advanced_tms_wms_idempotency_target_mismatch.sql` — 20 functions, **29 replay short-circuits** guarded (both the primary short-circuit and, where one exists, the `exception when unique_violation` race-handler re-read, which had the identical defect).

Each becomes:

```sql
if found then
  if v_existing.outbound_order_line_id <> p_outbound_order_line_id then
    raise exception 'idempotency_key_conflict: idempotency key % was already used for a different pick task (outbound order line %, not %)',
      p_idempotency_key, v_existing.outbound_order_line_id, p_outbound_order_line_id
      using errcode = 'unique_violation';
  end if;
  return v_existing;
end if;
```

**This introduces no new convention.** The identical pattern was already ratified and applied in this repository at `ATW-020`/`021`/`022` (`20260730270000` cycle count, `20260730290000` label/barcode, `20260730300000` warehouse billing), each of which raises `idempotency_key_conflict` on target mismatch. The seven earlier WMS migrations were simply never revisited. This migration finishes the job.

**Method:** every function body is its own live `pg_get_functiondef` output with *only* the replay short-circuit patched. No other statement, signature, volatility, security attribute, `search_path`, grant, or comment changed. Purely `CREATE OR REPLACE FUNCTION` on identical signatures — no table, column, index, constraint, policy, or grant touched, and no already-applied migration file edited.

**Functions repaired (20):** `create_manual_wms_inbound`, `start_wms_receipt_session`, `generate_wms_putaway_task`, `confirm_wms_putaway_task`, `register_serial_identity`, `create_manual_wms_outbound_order`, `create_wms_pick_wave`, `generate_wms_pick_task`, `confirm_wms_pick_task`, `record_wms_pick_task_short`, `approve_wms_pick_substitution`, `start_wms_packing_task`, `create_wms_package`, `add_wms_package_line`, `remove_wms_package_line`, `confirm_wms_package`, `create_wms_outbound_shipment`, `add_package_to_shipment`, `load_wms_outbound_shipment`, `ship_confirm_wms_outbound_shipment`.

`add_wms_package_line` / `remove_wms_package_line` share one table (`wms_package_line_scans`), so their guard also compares `event_type` — reusing a key across an add and a remove on the same package was itself a silent no-op.

### Behavior preserved

A genuine retry — same key, same target — still replays exactly as before and returns the identical row. Only a key reused across genuinely different targets now raises. Proven in both directions by the new regression block.

### Evidence

`scripts/db-tests/advanced-tms-wms-picking.sql` gains a deterministic, race-free regression proof (self-contained fixtures: two fresh items, orders, lines, racks) asserting all four properties: first request wins its own target; same-key/same-target replays identically; same-key/different-target raises a classified `idempotency_key_conflict`; and the rejected request allocates nothing.

The pre-existing two-process keyrace proof now also passes deterministically — a direct consequence of this repair, not a test edit. **The original test assertion was never weakened or modified.**

## 4. F-2 — GPS Gateway silently dropped packets arriving during an ingest (High)

`GpsGatewayServer.handleConnection` kept `accumulator` as a closure variable; `drainAccumulator` snapshotted it on entry and wrote it back through a `commit` callback on exit. Because a drain awaits a real ingest round-trip, any chunk the `'data'` handler appended during that await was destroyed by the commit that followed.

### Live reproduction

Two AVL packets, the second written while the first packet's (120 ms) ingest was still in flight:

```
ingested batches: 1
longitudes:       [ 106.1 ]            <- 106.2 never arrived
ack frames:       [ '01', '00000001' ] <- one handshake byte, one ACK, not two
metrics: {"packetsDecoded":1,"packetsRejected":0,"reportsIngestedLive":1,"reportsBuffered":0}
```

The second packet was not rejected, not buffered, and not counted anywhere — `packetsRejected` stayed `0`. The loss was completely invisible to the gateway's own metrics and logs, and the device received no ACK for data the gateway had already consumed off the socket.

This sits directly on Prompt 248 §"Required verification" item 6 (Direct Device duplicate/order, buffering, ingestion) and item 18 (target-volume profiles) — the exact path a real device exercises continuously under load.

### Repair

Per-connection state moved into one shared `ConnectionBuffers` holder passed by reference, and every decoded prefix is now consumed from it **before** the following await rather than after. A concurrent append therefore lands safely after the already-consumed bytes instead of racing a stale snapshot. The `commit` callback is gone.

### Evidence

`services/gps-gateway/test/server.test.ts` — new regression test asserting both packets reach ingest, in arrival order, that `packetsDecoded`/`reportsIngestedLive` are both 2 with `packetsRejected` 0, and that the device receives exactly `01 00000001 00000001` (handshake + one ACK per packet).

## 5. F-3 — Durable telemetry buffer destroyed batches enqueued during a flush (High)

`DurableTelemetryBuffer.flush()` read the queue into a snapshot, ingested each batch (awaiting a real round-trip per batch), then rewrote the **whole file** with only the retained snapshot. Any `enqueue()` that landed in between — which is precisely what the live socket path does when an ingest fails over to the buffer — was silently overwritten.

The `flushing` guard prevented two concurrent *flushes*; it never addressed enqueue-during-flush.

### Live reproduction

One batch pre-buffered, a second enqueued from inside the ingest callback:

```
flushed: 1  deadLettered: 0
pending after flush (dev-B should still be queued): 0   <- dev-B destroyed
```

A durable buffer whose stated purpose is "so a transient loss of connectivity to Supabase never drops an already-decoded AVL packet" was dropping already-decoded AVL packets. This is Prompt 248 item 6's "buffering … outage and recovery" and item 21's forward-recovery requirement.

### Repair

`flush()` now records the exact byte length of the snapshot it is responsible for, and `writePending()` re-reads the file at write time and carries over everything appended beyond that offset verbatim. Appends are whole-line `O_APPEND` writes, so the carried-over tail is always a clean line boundary. Ordering is preserved: retained batches first, then arrivals, oldest-first.

### Evidence

`services/gps-gateway/test/buffer.test.ts` — two new regression tests: a mid-flush arrival survives and flushes on the next pass; and a mid-flush arrival during a *transient-failure halt* is retained behind the halted batch in correct order.

## 6. F-4 — `select("*")` against a column-restricted table (Low, closes `ISS-2026-026`)

A `select("*")` asks for the ungranted column too.

Replaced with the explicit 14-column list matching the grant exactly. Zero live callers existed, so this is a latent-break closure, not a live regression fix.

## 8. Findings raised but deliberately NOT repaired here

Each is recorded in `docs/runtime/KNOWN_ISSUES.md` with owner and rationale rather than fixed opportunistically, because each is materially larger than this checkpoint's bounded scope.

1. **`ISS-2026-029` (new, Medium) — the same unguarded-replay class outside Phase 5 WMS.** A repository-wide sweep found ~35 further replay short-circuits with no target check, including Finance (`create_finance_journal_draft`, `capture_finance_receipt`, `prepare_finance_journal_reversal`, `prepare_finance_journal_adjustment`, `prepare_finance_settlement`, `apply_finance_ap_settlement`, `reverse_finance_ap_settlement`), Operations (`create_shipment_order_from_job`, `transition_shipment_order`, `dispatch_shipment_order`, `ingest_milestone_event`, `start_epod_capture`, `add_actual_cost_component`), Platform (`provision_tenant`, `start_workflow_instance`, `request_approval`, `allocate_or_reserve_number`, `initiate_file_upload`, `enqueue_job`), and Phase 5 TMS (`add_shipment_leg`, `reserve_vehicle_capacity`, `prepare_route_planning_scenario`, `post_inventory_movement`, `reserve_inventory`). The same free-text-key exposure applies. Finance is the highest-value remaining target. Not fixed here because it spans four already-`VERIFIED` phases and needs its own task with per-phase regression coverage — exactly the kind of cross-phase sweep `AGENTS.md` requires a dedicated prompt for. **Note:** `apply_finance_ar_allocation`/`reverse_finance_ar_allocation` are *not* affected — their lookup is already scoped by `open_item_id`.

2. **`ISS-2026-030` (new, Low-Medium) — `readPending()` cannot survive a torn final line.** `JSON.parse` on a truncated last line (a crash mid-`appendFile`) throws, and every subsequent `flush()`/`pendingCount()` throws with it — a file-level poison pill that permanently wedges the buffer. Distinct from the per-batch poison-pill `ATW-027` already fixed. Not fixed here: the right repair (quarantine the torn tail to a sidecar, keep flushing the rest) is a design decision about partially-durable data, not a one-line change.

3. **`ISS-2026-017` (pre-existing, Medium) — `p_actor_auth_user_id` vs `auth.uid()`.** Re-verified this checkpoint and confirmed **not currently exploitable**: every UI caller derives the actor from the server-resolved session (`access.authUserId`), never from form data. Direct verification of all `actorAuthUserId` call sites in `app/`. Remains a real defence-in-depth gap the moment any non-first-party caller reaches these RPCs, and the fix (cross-check `auth.uid()` where non-null) spans ~200 functions.

4. **98 `select("*")` calls across `server/queries/`** — `AGENTS.md` forbids `SELECT *` in transactional APIs. Only the one on a column-restricted table (F-4) is a live break today; the rest are a standards-conformance sweep, not a defect.

5. **Tenant-scoped tables with RLS disabled.** 18 tables carrying `tenant_id` have `relrowsecurity = false`. **Verified not exposed**: every one has zero `anon`/`authenticated` grant and is reachable only through `SECURITY DEFINER` functions. Enabling RLS anyway would be defence in depth, not a fix.

## 9. Verification of `PHASE_5_VERIFIED`'s own claims

The `ATW-029` closure report's gate numbers were re-derived independently and **matched exactly** (typecheck 0, lint 0/85, `pnpm test` 3084/3084, build 90 routes, gateway 41/41 at baseline, 137 migrations at baseline). Its RLS and canonical-root reasoning also held up under direct schema inspection: no duplicate shipment/vehicle/telemetry/inventory root, and the 18 RLS policies whose `USING` clause is literally `true` are all on genuinely global reference tables (`uoms`, `finance_currencies`, `milestone_codes`, …), none of which carries a `tenant_id`.

One claim did not hold. §7 stated **"Zero Critical/High-severity repository-controlled issue is open anywhere"**. Three High-severity repository-controlled defects were open at that moment (F-1, F-2, F-3), all reachable by the gates that checkpoint ran. F-1 was even actively failing `db:test` intermittently, and had already been logged — but as a flaky test rather than as the product defect it was.

The cause is instructive and worth recording for future closure checkpoints: **`ATW-029` verified that every prior checkpoint's evidence existed and was internally consistent, and re-ran the gate suite — but it did not adversarially probe the code itself.** Its §5 explicitly recorded "Bounded repairs applied this checkpoint: None", reasoning that `ATW-027` had already closed everything in scope. Three of this audit's four findings were reachable in minutes by asking "what happens if I call this twice with the same key and different arguments?" and "what happens if data arrives while this awaits?" — questions a re-run of an existing suite cannot ask, because the existing suite encodes the same assumptions the code does.

`PHASE_5_VERIFIED` remains **set** and is not withdrawn: every defect found was repository-controlled, bounded, and is now closed with live evidence, and no Phase 5 capability is missing, unimplemented, or unproven. The correction is to the closure report's zero-High-issue claim, recorded here and in `KNOWN_ISSUES.md` rather than by silently editing that report's own committed text.
