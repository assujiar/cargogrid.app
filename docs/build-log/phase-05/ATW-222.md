## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **ATW-226 (Multi-Source GPS and Telematics Integration) has not been built yet** — no canonical telemetry table, entitlement config, or vehicle/driver/device identity exists anywhere (per ATW-221's own greenfield confirmation, unchanged). Prompt 222 §9 explicitly permits building this board before Prompt 226, with tracking columns "feature-gated." This migration therefore adds the real read model Prompt 222 §13 requires (`tracking_status`, `authoritative_source_type`, `last_position_at`, `freshness_status`, `accuracy_meters`, `fallback_active`, `tracking_entitled`, `tracking_exception_count`) as a genuinely queryable, currently-empty table (`app.shipment_tracking_health`) that `ATW-226F` will populate later — never a fabricated "tracked" state, and never a duplicate position history.
2. **`app.is_shipment_tracking_entitled` is a disclosed stub, always `false`** — the real `tracking.*` entitlement keys don't exist in the Configuration Engine (PLT-121) yet (`ATW-226A`'s own scope). Calling into an unregistered config key would raise, not gracefully report "not entitled," so a stub is the honest interim answer.
3. **The board widens OPS-175's own assigned-only ready queue to assigned + dispatched + in_transit** — a new view, `app.dispatch_board_queue`, reuses `app.evaluate_dispatch_readiness` (unmodified) for `assigned` rows only; `is_ready`/`blockers` are `null` for dispatched/in_transit rows (readiness is meaningless once a shipment has already left `assigned`), rather than silently re-running (and misreporting) the assigned-only checklist against them.
4. **No new mutation** — assign/hold/reassign/dispatch remain OPS-172's/OPS-175's own existing validated commands, reused verbatim by this capability's own UI. This task adds an extended read model only, matching the "reuse the already-checked read/mutation, add only the aggregation that is genuinely missing" precedent (FIN-213).

### 4.1 Two real pre-existing test-fragility defects found and fixed before commit, not this checkpoint's own code defects

Both are the same latent class already disclosed at `ATW-221` (a non-tenant/non-fixture-scoped lookup coincidentally colliding with another file's own fixture), surfacing here for the first time because this checkpoint's own fixture happened to produce a coincidentally round number:

1. **`scripts/db-tests/commercial-margin-calculation.sql`** — its own `override_margin_threshold` test fetched `v_calc1_id`/`v_calc2_id` via `select ... from app.margin_calculations where margin_pct = 16.67` / `= 33.33`, with no tenant or fixture scoping at all. This checkpoint's own dispatch-board fixture independently produced a margin calculation with `margin_pct = 16.67` (sell 6,500,000 / cost 5,000,000, before adjustment) for an unrelated tenant, and the unscoped query nondeterministically picked the wrong row, causing a real `insufficient_authority` failure. Root-caused by direct inspection (confirmed two rows matching `margin_pct = 16.67` across two different tenants) and fixed by scoping both lookups to this fixture's own rate selection (`where ... and rate_selection_id = (select id from app.rate_selections where costing_request_id = (select id ... where opportunity_id = (select id ... where name = 'Contoso Jakarta-Surabaya margin lane')))`), the identical technique the same file already uses for its own `v_selection_id` lookup.
2. **Defense in depth on this checkpoint's own fixtures**: both `advanced-tms-dispatch-board.sql`'s and `advanced-tms-multi-leg-shipment.sql`'s own margin-calculation sell amounts were also adjusted (6,000,000 → 6,500,000; 18,000,000 → 18,700,000) to avoid landing on another coincidentally round percentage a different, not-yet-encountered file might also assume unique.
