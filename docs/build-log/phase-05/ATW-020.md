## 2. Design decisions (disclosed, migration header)

The full RPC/schema design was specified in advance by this checkpoint's own orchestrating session (not left to the implementer to improvise) precisely because this capability composes so many already-`VERIFIED` primitives (`app.post_inventory_movement`, `app.wms_pick_record_scope_ok`, `app.actor_can_view_owner_scoped_row`, `app.convert_uom_quantity`) that getting the composition order wrong was the highest-probability defect class. Key decisions:

1. **Counts never patch or delete a balance.** Every real quantity correction composes `app.post_inventory_movement` (`ATW-015`) with `movement_type='adjustment'`, `source_type='cycle_count'` (an additive widening of that table's own `source_type` CHECK constraint, mirroring `ATW-017`'s identical widening for `'wms_outbound_order'` — the already-applied `20260730190000` migration is never edited).
2. **A real, DB-enforced conflict-prevention guarantee**, not just an app-level check: a partial unique index on `app.cycle_count_scope_items(snapshot_balance_id)` covering every non-terminal status guarantees at most one in-flight cycle-count scope item per inventory balance at any time, across every plan in the tenant — this is the "reservation/activity conflict" prevention Prompt 239 §13 requires, proven with a real two-process freeze race (§4).
3. **Blind counting is enforced server-side**, computed from the caller's own `OPS:Override` authority, never a caller-supplied parameter — deliberately rejected a `p_blind` boolean design from the outset as a security anti-pattern.
4. **Exactly one recount cycle is structurally possible**: a first attempt whose variance exceeds `recount_threshold_pct` escalates to `recount_required`; every subsequent attempt can only resolve to `pending_review` or `no_variance_closed`, never `recount_required` again.
5. **`app.wms_pick_record_scope_ok` (`ATW-017`) is reused directly**, not re-derived, for both new owner-scoped tables' RLS policies — this repository's own established convention since that function was generalized.
6. **Thresholds are immutable plan-row fields, not a second versioned-config table** — Prompt 239 §24's "explicit and versioned" is read as "fixed to this plan's own row at creation," not a duplicate of `ATW-016`'s own richer `item_control_policy_versions` machinery for a single numeric pair.
7. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 3.3 Seven real defects found by adversarial review, all fixed

The three-lens review (spec-compliance, security/RLS/tenant-isolation, correctness/concurrency) each independently applied every migration to a real disposable Postgres database and live-reproduced its findings rather than reasoning abstractly — consistent with this repository's own established discipline. Two lenses independently converged on the same root cause (findings 1 and 3 below), which the fix pass treated as one:

1. **[HIGH, security] Blind-count redaction existed only in the two dedicated read RPCs — every scope-item-returning mutation (`freeze_cycle_count_scope`, `assign_cycle_count_scope_item`, `record_cycle_count_observation`, including both of its idempotent-replay short-circuits) returned the true `snapshot_expected_quantity`/`variance_quantity`/`variance_pct`/`snapshot_record_version` to any actor holding plain `OPS:Edit`.** Live-reproduced three ways using the shipped fixture's own plain-counter identity (no `OPS:Override`): self-assignment leaked the expected quantity before any count was entered; the observation-submission response itself disclosed the true expected quantity and the counter's own variance the instant they submitted a blind guess; and a counter with only `OPS:Edit` could freeze a plan themselves, mass-disclosing an entire scope's expected quantities before counting began. This defeated the entire anti-fraud purpose of blind counting. **Fix:** the identical `v_can_see_expected := (app.evaluate_permission(...,'OPS','Override')).allowed` redaction block already used by the two read RPCs was added to every mutation return path, including both replay short-circuits in `record_cycle_count_observation`.
2. **[MEDIUM, spec-compliance] `variance_threshold_pct` was validated, stored, and documented as an enforced materiality threshold but was never consumed by any status-transition logic** — only `recount_threshold_pct` gated the recount branch; a plan configured with an enormous tolerance (e.g. 999%) still routed a 1.3%-variance observation to `pending_review` identically to a zero-tolerance plan. **Fix:** added a materiality branch to `app.record_cycle_count_observation`'s status CASE — a nonzero variance at or below `variance_threshold_pct` now resolves directly to `no_variance_closed`, checked ahead of the recount escalation.
3. See finding 1 (the security lens's own broader-scoped restatement of the same defect, additionally proving the TypeScript service layer propagated the leak unfiltered).
4. **[HIGH, correctness] Idempotency-key collision across two *different* scope items at approval time silently attached the first item's ledger movement to the second, permanently marking it `adjusted` with zero reconciling movement of its own.** `app.post_inventory_movement`'s own idempotency dedup matches on `(tenant_id, idempotency_key)` alone, never validating the found movement's `source_id` against the current call's scope item. Live-reproduced: two distinct scope items approved with the same (colliding) idempotency key both ended `status=adjusted` sharing one identical `adjustment_movement_id`; the second item's real variance was never posted, yet it was permanently terminal — directly violating Prompt 239 §33's "approved variance produces exactly one reconciling movement" for the colliding item, which produced zero. **Fix:** `app.approve_cycle_count_variance` now validates the returned movement's `source_type`/`source_id` match the current scope item, raising `idempotency_key_conflict` on mismatch rather than silently misattributing it.
5. **[MEDIUM, correctness] The identical root cause one layer up in `app.record_cycle_count_observation`**: a reused idempotency key across two different scope items silently no-opped on the second (no error, no state change, no signal the count was dropped). **Fix:** both replay short-circuits now check `scope_item_id` match before returning, raising `idempotency_key_conflict` on mismatch.
6. **[MEDIUM, correctness] `balance_changed_since_snapshot` could not detect an intervening reservation change**, only an `on_hand` change — contradicting Prompt 239 §23's explicit "changed reservation" exception-flow requirement. Root cause was one layer down, in the already-`VERIFIED` `ATW-015` ledger: `app.reserve_inventory`/`app.release_inventory_reservation`/`app.consume_inventory_reservation` each mutate `app.inventory_balances.reserved` directly without ever bumping `record_version` (only `app.post_inventory_movement`'s own `on_hand`-changing `UPDATE` did). Live-reproduced two consequences: a small intervening reservation let approval succeed silently with no warning; a large one aborted with a raw, undocumented `inventory_balances_reserved_held_bound_check` violation instead of a clean domain error. **Fix:** since `20260730190000` is an already-applied migration (never edited, per `AGENTS.md`), a new additive hardening migration, `supabase/migrations/20260730280000_harden_advanced_tms_inventory_balances_reservation_record_version.sql`, widens all three functions via same-signature `CREATE OR REPLACE FUNCTION` so every `reserved`-mutating `UPDATE` also bumps `record_version`/`updated_at`, exactly as `app.post_inventory_movement`'s own `on_hand` `UPDATE` already does. The fix pass caught and corrected its own initial mistake here: its first draft was based on the *original* `ATW-015` function body and would have silently reverted `ATW-017`'s own prior widening of `app.reserve_inventory` (the nested `begin/exception unique_violation` idempotency-race recovery) — caught by a full `db:test` regression against `advanced-tms-wms-picking.sql`, then rebuilt on the correct, latest baseline.
7. **[LOW, correctness, defense-in-depth] `app.freeze_cycle_count_scope`'s own scope-item `INSERT` had no `unique_violation` exception handler**, unlike every other unique-constrained insert in this migration. Not a live defect today (the per-balance `FOR UPDATE` lock ordering makes the race structurally unreachable, confirmed by three consecutive clean full-suite runs including the real two-process freeze race), but an inconsistency with the migration's own established convention. **Fixed anyway** as a trivial, safe addition.

No finding was a false positive; all seven were confirmed real and fixed.
