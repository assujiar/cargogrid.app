## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Two new tenant-wide aggregating reads, not N per-vehicle/per-shipment calls.** `app.get_vehicle_current_position` (`226F`), `app.get_shipment_milestone_candidates`/`app.get_shipment_exception_signals` (`226G`) are all scoped to one vehicle/shipment at a time — exactly right for their own original callers, but a Fleet Control Tower list/map view genuinely needs "every vehicle's own current position for this tenant" and "every pending signal across this tenant's own shipments" in one call each, per `226_*.md` §17's own "do not use... one database request per item" rule. `app.get_tenant_vehicle_tracking_overview`/`app.get_tenant_pending_milestone_candidates`/`app.get_tenant_pending_exception_signals` are the three new reads this checkpoint adds for exactly that purpose — no new write path.
2. **The public tracking projection is widened (`app.lookup_public_shipment_tracking`, `OPS-180`), not forked** — a signature-changing widening (three new trailing output columns), so `DROP FUNCTION` + `CREATE FUNCTION` is the correct technique (`226C`'s own `end_leg_tracking_session` precedent for a signature change, not `226F`/`226G`'s own same-signature `CREATE OR REPLACE`). Every existing output column is unchanged; `scripts/db-tests/operations-public-tracking.sql`'s own assertions (all field-name-based, never positional) re-pass unmodified.
3. **Vehicle position is exposed to a customer only when the shipment's own currently-executing leg's tracking policy explicitly marks `customer_visible = true`** (`app.shipment_leg_tracking_policies.customer_visible`, `ATW-225`, already real) — reused, not reinvented. No vehicle assignment, no currently-executing leg, or `customer_visible = false` all cleanly yield null position fields, never a raised error and never a silent default-to-visible.
4. **A coarse three-word status (`live`/`delayed`/`unavailable`), never the raw `driver_mobile`/`direct_device`/`third_party_platform` source type** — a customer-safe projection of `226_*.md` §16's own "customers see sanitized shipment-level projections... raw payload and driver-sensitive data are restricted," reusing the tenant's own `freshness_threshold_seconds` (`app.resolve_tenant_tracking_source_policy`, `226A`) for the live/delayed banding, the identical 1x/3x multiplier `app.get_vehicle_source_health` (`226F`) already established for its own healthy/stale/offline bands, just relabeled for a customer-facing audience.
5. **A real Leaflet map, not a further-deferred placeholder.** `operations/fleet/page.tsx` and `operations/dispatch-board/page.tsx` both already disclosed "no map library exists in this repository yet" as an out-of-scope gap; this checkpoint is the one whose own job is a live map, so vanilla `leaflet` (not `react-leaflet`, to avoid a React 19.2.7 compatibility risk with an unverified third-party wrapper) was added as a new dependency. The map component imports `leaflet` dynamically inside a `useEffect`, never at module scope, since Leaflet's own module-init code performs browser-feature detection (`window`/`navigator`) that would break this route's server render if imported statically in a `"use client"` file Next still renders once on the server before hydration.
6. **The provider-mapping/source-priority admin forms (`ATW-223`'s own already-shipped mutations, never rendered) are wired into the existing `operations/fleet` page, not a new page.** `registerProviderVehicleMapping`/`setVehicleTrackingSourcePriority` (`server/mutations/fleet-driver-device.ts`) have existed since `226B` with zero UI. Fetching each vehicle's own mappings/priorities is a per-vehicle `Promise.all` (N calls, not one aggregating read) — a deliberate, disclosed exception to design note 1's own rule, justified because this is a bounded, infrequently-loaded admin page, not a hot ingestion or live-map path, and building a fourth new aggregating SQL function for an admin-only section would be scope creep past this checkpoint's own ask.
7. **The tenant tracking package/source-policy admin screen renders package entitlement read-only.** Package/entitlement *assignment* is a generic Configuration Engine draft/publish workflow (`PLT-121`) with no generic config-draft/publish UI built anywhere in this repository yet — building a one-off bounded editor on top of it here would fork, not reuse, the platform's own intended mechanism. The *source policy* (priority/freshness/accuracy/hysteresis) already has its own dedicated, simple upsert RPC (`ATW-226A`) and is fully editable.
8. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.
