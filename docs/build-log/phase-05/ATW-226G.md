## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Every derived signal is staged and reviewed — never auto-ingested — and this is a structural consequence, not a policy choice.** Direct inspection of `app.ingest_milestone_event` (`OPS-173`) and `app.report_exception` (`OPS-174`) before writing any code confirmed both call `app.evaluate_permission(p_actor_auth_user_id, ...)`/`app.can_access_record(...)` against a *real* identity and fail closed for a null/absent actor. There is no "system identity" anywhere in this repository's RBAC model, and `app.arbitrate_and_project_vehicle_position`'s own telemetry-triggered execution context (`service_role`-only, no human actor in scope) genuinely cannot present one. Inventing a null-actor RBAC bypass purely to let an automated evaluator call these functions directly would be a real, unjustified privilege-escalation surface, since both functions are already granted to `authenticated`. This migration instead writes only to its own new staging tables from the automated path; `app.confirm_milestone_candidate`/`app.confirm_exception_signal` are the sole promotion path, each requiring a real authenticated actor who legitimately holds `OPS:Create` for the shipment's own tenant — the identical authority `OPS-173`/`OPS-174` already require of a human filing a milestone/exception directly.
2. **Widens `app.arbitrate_and_project_vehicle_position` (`ATW-226F`), does not fork it.** Same technique `226F` itself already used on `226C`/`226D`/`226E`: `CREATE OR REPLACE FUNCTION` with the exact, unchanged signature, one addition — a call to `app.evaluate_geofence_and_deviation_signals()` immediately after a canonical event actually wins arbitration (`v_apply`), never for a rejected/duplicate candidate.
3. **Widens `app.ingest_milestone_event` (`OPS-173`, Phase 3) and `app.milestone_events`'s own `source` CHECK constraint — the first ATW checkpoint to widen a pre-Phase-5 capability's own function.** Disclosed and justified: no earlier capability ever needed a provenance value describing "GPS-derived, human-confirmed" — the existing `manual`/`api`/`webhook`/`import` vocabulary describes delivery *mechanism*, not detection origin, and none of them honestly fits. The widening is a same-signature `CREATE OR REPLACE` (one added string in an allowlist) plus a same-effect widening `ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT` — both provably additive, since every existing row's own `source` value remains valid under the wider set. `OPS-173`'s own already-applied migration file is never edited; its own db-test re-passes unmodified.
4. **Geofences are circular (center + radius), not polygon** — no polygon/point-in-polygon primitive exists anywhere in this repository; `app.bounded_st_dwithin()` already governs a bounded-radius containment test exactly.
5. **Route deviation has no stored reference polyline to compare against** — the reference "corridor" is a straight line built at query time (`ST_MakeLine` over a leg's own ordered `app.shipment_leg_stops.location_geog`), never a stored geometry column — a disclosed, straight-line-only approximation, not a claim of road-aware routing.
6. **Both geofence dwell and route-deviation confirmation use the identical elapsed-time-sustained pattern** (`first_entered_at`/`first_off_corridor_at` plus a configured duration, confirmed only once via a null→set transition on `confirmed_at`) — one shared, auditable mechanic reused twice.
7. **Configuration lives inside `app.shipment_leg_tracking_policies.geofence_policy`** (`ATW-225`'s own disclosed hook), never a second policy table. Every numeric/boolean key is read defensively (`app.safe_jsonb_numeric`/`app.safe_jsonb_boolean`, new) with a disclosed platform default on any missing or malformed value — an operator's own configuration typo must never break the live telemetry-ingestion pipeline `226C`/`226D`/`226E` still rely on.
8. **Raw telemetry never directly completes a shipment lifecycle** (`226_*.md` §24) — this migration never writes to `app.shipment_legs.leg_status`/`app.shipment_leg_stops.stop_status`/`app.shipment_orders.status` at all.
9. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 4.1 Real defects found and fixed during authoring (before any full-suite gate run)

1. **`app.detect_overdue_geofence_arrivals`'s own exclusion query only checked for `state = 'confirmed_inside'`**, missing that a stop which reached and then *left* that state transitions to `'exited'` — a genuinely-arrived-and-departed stop would have been wrongly re-flagged as still overdue. Caught during test design, before any test run, by tracing the state machine's own later transitions against the detector's own filter. Fixed by excluding both `'confirmed_inside'` and `'exited'`.
2. **`gen_random_bytes`/PostGIS-class `search_path` gap, the identical bug class `226E` already found** — `app.upsert_milestone_candidate`/`app.upsert_exception_signal`/`app.dismiss_milestone_candidate`/`app.dismiss_exception_signal` each insert/update a row whose own CHECK constraint calls `app.validate_geography_point()` (`PLT-134`), a `language sql` function with no `search_path` of its own — Postgres inlines it into the *caller's* search-path context. All four functions declared `set search_path = app, pg_temp` (no `public`), causing `type "geometry" does not exist` the first time the CHECK actually ran. Fixed by adding `public` to all four.
3. **Unrealistic implied speed between consecutive test reports.** The db-test's own first-drafted geofence-exit/arrival/route-deviation coordinates jumped tens of kilometers within a one-minute `event_at` gap — correctly triggering `226F`'s own `impossible_movement` rejection, meaning `v_apply=false` and this checkpoint's own evaluator never ran (masked by a separate NULL-comparison bug in the test's own assertions — see below). Fixed by redesigning the whole timeline with physically realistic elapsed-time gaps (60–100 minute travel legs for ~130km jumps, ~80–130 km/h implied) while keeping same-spot dwell/confirm pairs on short gaps (near-zero distance, safe regardless of gap).
4. **A SQL NULL-comparison masked the defect above during initial test authoring.** `if v_state.state <> 'confirmed_inside' or v_state.confirmed_at is null then raise ...` silently does *not* raise when `v_state` itself was never found (all fields NULL): `NULL <> 'text'` evaluates to `NULL`, and PL/pgSQL treats a NULL `IF` condition as false. The test appeared to pass while asserting nothing. Fixed by switching every such bare record-field comparison to `IS DISTINCT FROM`, which correctly treats "no row found" as genuinely distinct from any expected value.
5. **`RETURNS TABLE(...)` output-column shadowing, the identical bug class `226E` already found**, now hit for the first time on this checkpoint's own read functions after they were widened to GeoJSON-project their location columns (originally `RETURNS SETOF <table>`, which does not shadow). The new `id uuid` output column in `get_shipment_milestone_candidates`/`get_shipment_exception_signals`/`get_shipment_leg_geofence_state` collided with each function's own internal bare `where id = ...` lookup. Fixed by table-aliasing every internal lookup (`so`, `sl`).
6. **A test-authoring mistake, not a migration defect**: a route-deviation reference-line contamination risk was caught during design, before it could manifest as a bug — the overdue-arrival test's own third stop, if placed off to one side of the pickup-delivery corridor, would have silently added a second, non-collinear segment to `app.evaluate_route_deviation`'s own `ST_MakeLine` reference (built from every stop's own `location_geog` in `stop_sequence` order), invalidating the route-deviation test's own carefully-computed off-corridor distances. Resolved by placing the third stop's own coordinates collinear with the original two-stop corridor (a linear interpolation, not an arbitrary point) and confirming it is more than 10km from every route-deviation test coordinate, so it is never itself entered.
7. **One TS-layer test authoring mistake**: `getShipmentLegGeofenceState`'s own "empty" test case modeled a zero-row RPC response as `data: null`, but that query function intentionally throws on any non-array response (unlike its sibling `getShipmentLegRouteDeviationState`, which tolerates null for its own 0-or-1-row shape) — a real Supabase RPC returning zero matching rows for a `setof`/`table` return type returns `[]`, never `null`. Fixed by correcting the test fixture to `data: []`, the behavior the function was actually, correctly, designed around.

## 5. Residual disclosures

- No free-standing geofence zones independent of a stop (e.g. a customs area, a restricted zone) — every geofence in this checkpoint is stop-linked. A generic reusable geofence/zone catalog was considered and rejected as scope creep past this checkpoint's own ask.
- No road-network-aware route-deviation routing — straight-line stop-to-stop corridor only, disclosed in design note 5.
- `app.detect_overdue_geofence_arrivals` has no live scheduler invoking it anywhere in this repository — the identical disclosed posture `OPS-174`'s own `app.escalate_exception` already established (mechanism real, cron wiring deferred).
- No auto-confirmation of any derived signal — confirm is always an explicit authenticated call, structurally required by design note 1, never invoked by either evaluator.
- No append-only history of geofence/deviation-state transitions — states are overwritten in place; `app.canonical_telemetry_events` (`226F`) remains the full replay source for every underlying position.
