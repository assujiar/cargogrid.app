## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **A third distinct trust model, each reusing the closest real precedent rather than inventing a fourth.** `226C` (driver_mobile): unauthenticated PWA, bearer token. `226D` (direct_device): trusted backend process, scoped API key. `226E` (third_party_platform): external vendor platform, no CargoGrid session, HMAC signature over the raw webhook body — the identical scheme ADR-0011 already implements for CargoGrid's own *outbound* webhooks, reused verbatim for the inbound direction. `app.third_party_provider_connections.webhook_secret_value` reuses `app.webhook_endpoints.secret_value`'s own accepted "raw, retrievable, zero grant" shape, since an HMAC secret (unlike a bearer token/API key) cannot be a one-way hash and still be verifiable.
2. **The one deliberate `anon` grant in this migration, the third in this repository.** A direct query of `information_schema.routine_privileges` found `anon` already held `EXECUTE` on six functions (five pre-login resolvers plus `226C`'s own `ingest_driver_mobile_report`). `app.ingest_third_party_provider_webhook_event` follows `226C`'s own proven anon-facing shape: a returned status column, never a raised exception, for every failure mode (the identical anti-oracle reasoning, extended from token validation to signature validation).
3. **Third-party adapters are case-specific (`226_*.md` §16)**, the same design boundary `app.provider_vehicle_mappings` (`ATW-223`) already drew. No live vendor contract exists at this checkpoint, so this migration defines and validates one repository-owned *reference* webhook JSON contract (`event_id`/`vehicle_id`/`event_type`/`timestamp`/`latitude`/`longitude`/`speed_kmh`/`heading_degrees`) — disclosed as representative, never a certified named-vendor integration.
4. **Unmapped vehicles are quarantined, never silently dropped** (`226_*.md` §16/§14). `app.third_party_provider_ingestion_attempts.raw_payload` preserves the full payload for a `quarantined` outcome — this repository's own closest real analogue to the WBS's named "DLQ" concept, reusing the existing rate-limiting attempts table rather than a third, redundant one.
5. **Replay defense is two-layered**: ADR-0011's own 5-minute timestamp-tolerance window, plus a `provider_event_id` partial unique index per connection (a genuine retried delivery returns `duplicate`, never re-inserted, never punished as `invalid`).
6. **Polling (`poll_cursor`/watermark) is structurally represented, not executed** — `226_*.md` §8's own conditional-provider allowance. `app.jobs` (`PLT-131`/`PLT-132`) remains the disclosed intended reuse target for a real poll worker's own scheduling (named in `226D`'s own migration header), not built this checkpoint since there is nothing real to schedule yet.
7. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 3.2 Schema — `supabase/migrations/20260729380000_create_advanced_tms_third_party_provider_adapter.sql`

Three new tables: `app.third_party_provider_connections` (one per tenant+provider_code; `webhook_secret_value` raw/retrievable, zero authenticated/anon grant; `poll_cursor` opaque jsonb watermark), `app.third_party_provider_ingestion_attempts` (rate limiting + quarantine evidence, mirrors `app.driver_mobile_ingestion_attempts`), `app.third_party_telemetry_reports` (raw append-only telemetry, partial-unique `provider_event_id` per connection). Six new functions: `app.register_third_party_provider_connection`, `app.rotate_third_party_provider_webhook_secret`, `app.update_third_party_provider_poll_cursor`, `app.compute_third_party_provider_webhook_signature`/`app.verify_third_party_provider_webhook_signature` (ADR-0011 reused verbatim), `app.ingest_third_party_provider_webhook_event` (the one anon-callable function), `app.get_third_party_telemetry_reports`.

### 3.3 Service layer

`server/contracts/third-party-provider-adapter/third-party-provider-adapter.ts`, `server/queries/third-party-provider-adapter.ts` (`getThirdPartyProviderConnection`, `listThirdPartyTelemetryReports`), `server/mutations/third-party-provider-adapter.ts` (`registerThirdPartyProviderConnection`, `rotateThirdPartyProviderWebhookSecret`, `updateThirdPartyProviderPollCursor`, `ingestThirdPartyProviderWebhookEvent` — the last never throws for a bad signature/unmapped vehicle/duplicate event, only for a genuine transport error).

**`app/api/webhooks/third-party-gps/[connectionId]/route.ts` — the second real HTTP API route this repository builds**, and the first dynamic (parameterized) one. Reads the raw request body via `request.text()`, never `request.json()` — HMAC verification is computed over the exact bytes the provider sent, and any re-serialization (even of semantically-identical JSON) can silently break a legitimate signature. `connectionId`, not `provider_code`, is the routable identity — HTTP naturally supports per-tenant-scoped URLs, unlike `226D`'s raw-TCP IMEI-only handshake, which is why `226E` resolves its own identity per-connection rather than facing `226D`'s own global-IMEI-lookup problem at all.

### 4.1 Real defects found and fixed during authoring (before any full-suite gate run)

1. **`gen_random_bytes(integer) does not exist`** — `register_third_party_provider_connection`/`rotate_third_party_provider_webhook_secret`/`compute_third_party_provider_webhook_signature` each declared `set search_path = app, pg_temp` (no `public`), so pgcrypto's schema-unqualified `gen_random_bytes`/`hmac` could not resolve. Fixed by adding `public` to each of those three functions' own `search_path` (the other two functions in this migration, which never call pgcrypto directly, correctly keep the narrower `app, pg_temp`).
2. **Ambiguous column reference `provider_code`** — `register_third_party_provider_connection`'s own `RETURNS TABLE(..., provider_code text, ...)` clause makes `provider_code` a PL/pgSQL variable in scope throughout the function body; a bare `where ... and provider_code = p_provider_code` collided with it. Fixed by aliasing the table (`... c where c.provider_code = ...`).
3. **Missing `RETURN;` after an early `RETURN QUERY`** — `register_third_party_provider_connection`'s own idempotent-existing-connection branch (`if found then return query select ...; end if;`) fell through to the `INSERT` below on a second call for the same `(tenant_id, provider_code)`, causing a duplicate-key violation — `RETURN QUERY` appends rows but does not itself exit a PL/pgSQL function, unlike a scalar `RETURN`. Caught by the db-test's own idempotency assertion failing against a real Postgres instance. Fixed by adding the missing `RETURN;`. (Every early-exit branch in `ingest_third_party_provider_webhook_event` already included this correctly, confirmed by re-reading the whole function before running any gate.)
4. **FK violation logging an "invalid" attempt for a non-existent `connection_id`** — the ingestion RPC's own "connection not found/not active" branch inserted `p_connection_id` (the caller-supplied, possibly-nonexistent value) into `app.third_party_provider_ingestion_attempts.connection_id`, which carries a foreign key to `app.third_party_provider_connections`. Fixed by inserting `v_conn.id` instead (`NULL` when the lookup found nothing — the column's own nullable design intent for exactly this case), matching `app.audit_logs.tenant_id`'s own established "a platform-wide/unresolved event carries no reference" idiom.

## 5. Residual disclosures

- No live third-party GPS platform contract exists — `226_*.md` §8's own `CONDITIONALLY_SKIPPED_PROVIDER_UNAVAILABLE` status applies to any named real-world vendor integration; this checkpoint's own reference webhook contract and its full deterministic test coverage (§4) is the repository-controlled evidence §8 itself allows in lieu of a live vendor.
