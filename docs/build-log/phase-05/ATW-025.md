## 2. Design decisions (disclosed, migration header)

1. **Zero new case-root table.** `app.claim_case_extensions` is unique on `operational_exception_id` — a real DB constraint enforcing "no duplicate root or silent re-entry," not just an RPC-level rule. `app.open_claim_case` never creates a base exception; it only ever calls the existing, real `app.resolve_exception`/`app.close_exception`/`app.reopen_exception` from the claim-closure path, never writing `app.operational_exceptions` directly.
2. **Claim-eligible types**: `damage|loss|incident|delay` — `delay` included because Prompt 244 §27's own test-data list names it explicitly; `hold` excluded (an unresolved operational block, not a completed event with a quantifiable loss to itemize); `shortage` has no matching `operational_exceptions.type` value (that enum is fixed and untouched), so it is represented at the `claim_items` item level instead.
3. **Responsibility review is one versioned row carrying both the system/investigator proposal and the human decision** (mirrors `app.billing_readiness_evaluations`' own evaluate+override shape and `app.epod_captures`' own capture+review shape) rather than two separate tables. `app.decide_claim_responsibility` enforces `decided_by <> proposed_by`, reusing the exact `self_approval_not_allowed`/`insufficient_privilege` convention `app.approve_warehouse_billing_event` (`ATW-022`) already established.
4. **Evidence links are a real, validated polymorphic reference** (`evidence_type`/`evidence_id`, mirroring `app.files`' own `record_type`/`record_id` convention) — `app.link_claim_evidence` validates the referenced row actually exists in its real source table and matches tenant (and, where the source table carries one, shipment order) before inserting, never accepting an unvalidated id. File evidence reuses `app.files`/`app.authorize_file_access` (`PLT-128`) directly — no second file-security mechanism.
5. **Finance handoff mirrors `OPS-181`/`ATW-022` exactly** — a versioned evaluation row plus a separate append-only handoff table, idempotent on `(tenant_id, claim_case_id, idempotency_key)`. Zero writes anywhere to any Finance-schema table (grepped and confirmed, twice, independently, by two different reviewers).
6. **`app.close_claim_case`'s closure gate**: either a Finance handoff reconciled, or the case's responsibility review is `denied`/`approved`-or-`amended` with a null-or-zero final reserve (a "no handoff needed" path) — disclosed precisely in the migration header.
7. Per `ERR-2026-004`: explicit `REVOKE`/`GRANT`; the Finance reconciliation-outcome callback is `service_role`-only, mirroring `ATW-022`'s identical precedent.

### 3.3 Findings from three independent adversarial-review lenses, all confirmed real and addressed

1. **[HIGH, live-reproduced, correctness-concurrency lens] `app.propose_claim_responsibility` had zero optimistic-concurrency check** — unlike every sibling status-mutating RPC in the same migration. Live-reproduced: two actors proposing in sequence with no version token silently destroyed the first proposal's entire rationale, no error, no trace. **Fixed**: added `p_expected_version`, enforced null-iff-no-current-review semantics, `stale_version` on mismatch. New db-test coverage proves the exact prior lost-update scenario is now blocked.
2. **[HIGH, spec-compliance lens] "Assigned investigators manage evidence" (Prompt 244 §26) was enforced for only 1 of 4 evidence-management RPCs** — `record_claim_investigation_finding` checked it; `add_claim_item`/`withdraw_claim_item`/`link_claim_evidence` did not, live-demonstrated by the shipped db-test's own fixture (an unassigned case's evidence was freely manipulated). **Fixed**: the identical `claim_not_investigator` check applied uniformly across all four RPCs; `open_claim_case` deliberately stays ungated (a case has no investigator to check against at intake time).
3. **[HIGH, spec-compliance lens] Settlement-readiness evaluation/handoffs had no dedicated, masked read RPC** — a real, unmasked reserve amount was reachable via a raw `SELECT` on the `evidence` jsonb column, bypassing the exact masking this same migration already enforces for the identical figure elsewhere. **Fixed**: added `app.mask_claim_settlement_readiness_evaluation_amounts` and two new `OPS:View`+record-scope-gated read RPCs, mirroring `ATW-022`'s own `get_warehouse_billing_event`/`list_warehouse_billing_handoffs` precedent.
4. **[HIGH, spec-compliance lens] A claim could be decided and closed with zero evidence or itemization ever created** — Prompt 244 §23 names "missing custody/quantity evidence" as a hard-block condition on equal footing with "unsafe file" (which already was hard-blocked). **Fixed conditionally**: a `claim_evidence_required` gate fires only when a proposed/approved reserve is genuinely positive — a zero-reserve or denied claim legitimately has nothing to itemize, disclosed explicitly rather than applied universally (which would have broken the existing "delay confirmed, no compensable loss" flow).
5. **[HIGH, spec-compliance lens] The migration header mischaracterized its own customer-read-path deferral as matching `ATW-023`'s** — `ATW-023` built a full, real, non-OPS-gated customer-facing backend contract and deferred only the UI; `ATW-025` defers the backend contract too. **Fixed**: header corrected to state this accurately rather than borrow a narrower precedent's own language.
6. **[HIGH, spec-compliance lens] Merge/split (Prompt 244 §22) were unimplemented with zero disclosure**, unlike every other omission in this migration (each of which carries its own reasoned paragraph). **Fixed via disclosure** — an honest new design note explaining the omission, matching this migration's own established disclosure discipline elsewhere.
7. **[MEDIUM, live-reproduced, cross-tenant-isolation lens] Same-tenant, cross-customer evidence linking** — `link_claim_evidence`/`add_claim_item` validated `inventory_movement`/`wms_outbound_shipment` evidence by tenant only, never customer/owner; live-reproduced attaching a different customer's real warehouse movement/outbound shipment onto an unrelated case. Fixing this pass also discovered the *shipped test fixture itself* had this exact latent bug. **Fixed for `wms_outbound_shipment`** (a real `owner_account_id` column now compared against the claim's own shipment order); **disclosed, not fixed, for `inventory_movement`** — its header table genuinely carries no owner/customer column of its own (ownership lives one level down, on movement lines, and one movement header can span multiple owners) — a real schema-shape limit, not a fixable oversight within this bounded task.
8. **[MEDIUM, correctness-concurrency lens] Idempotent-replay short-circuits silently discarded a mismatched resubmission** (`open_claim_case`, `link_claim_evidence`) instead of validating content, mirroring the already-established `ATW-021`/`app.create_label_printer` fix pattern. **Fixed**: both now raise a real conflict error on a content mismatch rather than silently returning the stale original.
9. **[MEDIUM, correctness-concurrency lens] `handoff_seq` (this migration's own purpose-built anti-ambiguity ordering column) was missing from the TypeScript contract layer**, though correctly used at the SQL layer. **Fixed**: added to the zod schema/parser/test mocks.
10. **[MEDIUM, spec-compliance lens] Two of four settlement-readiness blocker codes were implemented but never exercised by a test; "shortage" never literally appeared in test data.** **Fixed**: both.
11. **[LOW ×2, correctness-concurrency lens] A narrow check-then-guarded-update race window** in `close_claim_case`/`evaluate_claim_settlement_readiness` — independently confirmed to be a repository-wide pattern used identically by essentially every optimistic-concurrency RPC in this codebase, not a defect specific to this migration's own design choices. **Deferred**, not fixed here, to avoid inconsistency with the rest of the codebase; a dedicated repository-wide hardening task would be the right scope.
12. **[Informational, cross-tenant-isolation lens] `p_actor_auth_user_id` trust** — the same repository-wide, pre-existing pattern already tracked as `ISS-2026-017`. Not this task's to fix.
13. **[Real, unrelated bug discovered along the way, not a finding of this task] `scripts/db-tests/advanced-tms-lot-batch-serial-expiry.sql` (`ATW-016`, already `VERIFIED`, committed months before this checkpoint) has a genuine, pre-existing, non-deterministic tie-break defect.** Confirmed independently four separate times (by the implementation agent and all three review agents, via controlled A/B testing — removing the ATW-025 files alone converts a failing full-suite run to a passing one) — `app.list_allocation_candidates`' own FIFO/FEFO ordering falls back to `created_at`/`updated_at` when two lots are registered inside the same transaction, and Postgres's `now()` is fixed for a transaction's entire duration, so both rows can receive an identical value on both the primary and fallback tie-break columns, making relative output order implementation-defined rather than guaranteed. Not fixed here — out of this task's own bounded scope, no authorization to edit an already-`VERIFIED`, already-applied migration's own test file for an unrelated capability. Recorded as new `ISS-2026-020` (§7).

No finding across any of the three reviewers was a false positive. Every HIGH and live-reproduced MEDIUM finding was fixed with real code changes; every deferred item carries its own explicit, reasoned disclosure rather than silence.
