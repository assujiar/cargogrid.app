## 2. Design decisions (disclosed, migration header)

No new ADR was required — every shape question was resolved by direct, already-`VERIFIED` precedent, not a genuinely open architecture choice:

1. **Record scope mirrors `app.warehouses` exactly** (company-org-unit scoped via `app.lead_record_scope_org_unit_ids`), not tenant-wide like `app.item_masters` — an inbound order is a warehouse-operational record, the same class as `app.warehouses`/`app.warehouse_zones`/`app.warehouse_locations`.
2. **`owner_account_id` is mandatory**, inherited from `app.shipment_orders.shipper_account_id` when prepared from a source shipment, reusing `ATW-011A`'s own proven FK shape.
3. **`source_type` is a closed CHECK enum (`shipment_order`/`manual`/`import`) deliberately excluding `purchase_order`** — Prompt 231 §24 itself: "Future PO/vendor linkage does not implement Step 11 lifecycle."
4. **Duplicate-source prevention is a real partial unique index** (Prompt 231 §23), not an application-level check — a cancelled order frees its own source/idempotency key rather than permanently exhausting it.
5. **Numbering is a bounded per-tenant counter** (`app.next_wms_inbound_order_number`), mirroring `app.next_job_order_number` (`OPS-168`)/`app.next_quotation_number` (`COM-151`) verbatim — the same disclosed alternative to the full Configurable Numbering Engine every prior domain has used.
6. **Line items snapshot `lot_controlled`/`serial_controlled`/`expiry_controlled` from `app.item_masters` at add-time**, mirroring `app.shipment_orders.cargo_service_snapshot`'s own "governed snapshot, never silently re-derived" precedent.
7. **No on-hand/received quantity column exists anywhere** — Prompt 231 §24: "Expected quantity is not on-hand inventory." Those remain `ATW-234`'s own derived-balance columns.
8. **The lifecycle this migration owns is bounded to `draft` → `scheduled` → `confirmed` (or `cancelled` from any of those three)** — `ATW-232` (WMS Receiving) owns whatever state a confirmed order transitions into once physical receiving begins. `app.cancel_wms_inbound` does not check real receiving progress (disclosed, no such table exists yet) — `ATW-232` is obligated to wire that guard, the identical deferred-obligation pattern `ATW-229`→`ATW-230`→`ATW-011B` already established.
9. **Document attachment reuses `app.files`' own generic polymorphic reference (`PLT-128`) directly** — no new migration code, `record_type = 'wms_inbound_order'`. A dedicated WMS-specific document-requirement/checklist tracker (mirroring `OPS-176`'s own shipment-scoped one) is explicitly not built — `OPS-176`'s tables are shipment-specific, not generically reusable, and no source document names exact required WMS document types.
10. **Staged/bulk line import is a direct bulk RPC (`app.add_wms_inbound_order_lines`, all-or-nothing, ≤200 lines), not the full generic Import/Export Job Framework (`PLT-131`)** — `ISS-2026-013` had already named this checkpoint as the framework's potential first real adopter; a bounded direct RPC satisfies Prompt 231 §22's "import staged lines" alt flow without pulling in the full staged-job/commit-adapter machinery for a capability this size.

## 3. Implementation

### 3.1 Schema — `supabase/migrations/20260730180000_create_advanced_tms_wms_inbound.sql`

### 3.3 Tests

`scripts/db-tests/advanced-tms-wms-inbound.sql` — full pattern: two tenants, one with two customer accounts (Account A via the full CRM→Job Order→confirmed Shipment Order pipeline plus a separately-cancelled shipment for the `stale_source` exception test; Account B only to prove a foreign-owner item is rejected) and item masters per account (`ATW-011A`). Covers: authority gating, idempotent replay on both creation paths, `stale_source`/`warehouse_not_active`/`owner_account_not_found` exception flows, line add/bulk-add/update/remove (draft-only, foreign-owner/bad-UOM/non-positive-quantity rejections), appointment scheduling (`no_lines` guard, invalid window, draft-only) and reschedule, `get_wms_inbound_readiness` matching exactly what `confirm_wms_inbound` blocks on (including the case where a referenced item master is deactivated mid-flow, proving `ATW-011A`'s own disclosed deferred-check boundary is honestly surfaced here rather than silently ignored), cancellation (reason-required, idempotent no-op, freed idempotency key), bounded/filtered list reads, cross-tenant isolation, schema-privilege defense in depth. One authoring correction found during testing: `app.cancel_shipment_order`'s own parameter order is `(id, expected_version, reason, ...)`, not `(id, reason, expected_version, ...)` — fixed by re-checking the function's own signature directly rather than assuming symmetry with `app.cancel_wms_inbound`'s own (reason-before-version) order.
