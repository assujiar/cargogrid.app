## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Zones are flat — one level under a warehouse, never self-referencing.** Prompt 229's own §3 workstream names its epic "Facility Topology" (facility + zone identity); Prompt 230's own epic is "Location Topology" (the deeper rack/shelf/bin hierarchy) — this migration owns only the shallower layer. A zone's own `warehouse_id` is immutable once created (no RPC ever lets a zone move to a different warehouse) — the structural mechanism behind §23's "block... cross-warehouse link" exception-flow rule, not merely a documented promise.
2. **`service_type_eligibility`/`zone_type` are free text, not a fabricated CHECK enum.** `service_type` already stays free text across every prior Commercial capability (COM-147/148); `zone_type` is the identical case — Prompt 229 §27's own test-data requirement names "ambient/cold/secure zones" as the *sourced* examples to cover, not an exhaustive enum (no architecture document enumerates a canonical WMS zone-type list). A hard CHECK listing only those three, or a larger uncited list (hazmat/quarantine/staging), would have fabricated a business rule beyond what was actually asked. Both columns are validated for non-empty content only; the test fixture still exercises `ambient`/`cold_storage`/`secure` plus a fourth (`staging`, for the "schedule future zone" alt flow) to prove the column genuinely accepts any real value.
3. **`environment`/`restrictions` reuse `app.validate_master_attributes` (PLT-120) verbatim** — the same generic, already-proven structural/injection-safety validator PLT-120's own `master_records.attributes` uses, rather than a second bespoke jsonb validator for an identical shape.
4. **`timezone` reuses `app.validate_timezone_name` (PLT-119) verbatim; `site_geog` reuses `app.geojson_point_to_geography`/`app.validate_geography_point` (PLT-134) verbatim** — the same governed GeoJSON-in/geography-out/range-rejecting pipeline every other Phase 5 spatial column already uses.
5. **Company/branch record scope reuses `app.lead_record_scope_org_unit_ids` (COM-143) verbatim** — `ATW-227`'s own precedent already established this function, despite its name, as a domain-generic "org unit + every ancestor" wrapper. A warehouse is visible/editable to a caller whose own `app.users.org_unit_id` is the warehouse's company org unit or any of its descendants' shared branches (Prompt 229 §26 "managers/users see assigned facility/zone"), enforced in the database (RLS `select` policies plus every mutation/read RPC's own explicit `app.can_access_record` check), never UI-only.
6. **Customer eligibility is an explicit grant/revoke ledger**, mirroring `app.role_assignments`'s own `active`/`revoked` + `granted_by`/`granted_at`/`revoked_at`/`revoked_reason` shape (PLT-111) — Prompt 229 §24's "customer/owner eligibility is explicit and cannot broaden access by itself". No consumer yet reads this table to widen a customer-portal principal's own access — `ATW-242` (the read-only contract §26 names) has not shipped; disclosed `NOT_RUN` for that path, the same "mechanism proven, live wiring deferred" posture PLT-121/PLT-106 already used.
7. **Deactivation dependency-impact checking is real where a real dependency exists, disclosed as deferred where none does yet.** A warehouse cannot be deactivated while it still has an `active`/`on_hold` zone (checked directly against `app.warehouse_zones` — a real, checkable dependency). A zone's own deactivation does **not** check for stock/task dependencies (§16/§33's "cannot orphan active inventory/tasks") because no bin/inventory/task table exists yet at this checkpoint — `ATW-230` ("Bin and Racking") is the very next task in this session's own range and has not shipped. Identical disclosed boundary to PLT-120's own header; every zone-status RPC's own comment names this explicitly.
8. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 3.2 Schema — `supabase/migrations/20260730140000_create_advanced_tms_warehouse_zone.sql`

### 4.1 Real defects found and fixed during authoring (before commit)

1. **A test-authoring ordering mistake, not a schema/RPC defect**: the db-test's own first-drafted `warehouse_code_conflict` assertion attempted the conflicting create as the JKT-scoped rep against the SBY org unit — but that actor genuinely lacks record-scope access to SBY, so the call correctly failed with `insufficient_authority` before ever reaching the duplicate-code check, not the error the assertion expected. Fixed by using the SBY-scoped rep (who does hold both `OPS:Create` and SBY record-scope) for that specific negative case, so the assertion actually exercises the code-conflict path rather than a different, earlier-firing rejection.
2. **`app.list_warehouse_customer_eligibility`'s own `RETURNS TABLE` column named `id` shadowed a bare `id` reference inside its own body** — `select * into v_warehouse from app.warehouses where id = p_warehouse_id;` raised `column reference "id" is ambiguous` at runtime (Postgres implicitly declares each `RETURNS TABLE` output column as a same-named plpgsql variable, which collides with any unqualified column reference of the same name inside the function). A real, previously-unknown defect class this checkpoint's own testing found — fixed by table-qualifying the lookup (`select w.* into v_warehouse from app.warehouses w where w.id = p_warehouse_id;`), with a comment recording why the qualification is required (not stylistic). Confirmed by grep that no other new function in this migration has both a `RETURNS TABLE` column named `id` and a bare `where id = ...` reference in its own body.
3. Two db-test `declare`-block row-type initializers (`v_wh1 app.warehouses := (select w.* from ...)`, `v_zone app.warehouse_zones := (select z.* from ...)`) raised `subquery must return only one column` — a scalar-subquery initializer cannot bind a whole-row type in plpgsql `declare`. Fixed by declaring the variable bare and assigning it via a `select ... into` statement in the block body instead, the same pattern every prior fixture in this repository already uses for row-typed locals.
