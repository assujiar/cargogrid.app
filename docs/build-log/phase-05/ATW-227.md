## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

1. **Capacity is per-vehicle and per-leg, never a new shipment-level concept.** `ATW-223`'s own `app.vehicle_operational_profiles.capacity_weight_kg`/`capacity_volume_cbm` is the physical truth this ledger holds against; `ATW-224`'s own `app.route_planning_scenarios`/`app.route_planning_candidate_plans` are decision *support* only (`224_*.md` §21: "planning is decision support only, no shape here ever mutates `app.shipment_legs`") — neither reserves anything. `app.vehicle_capacity_reservations` is the first real reservation ledger, matching this prompt's own §21 main flow ("planning reserves capacity; dispatch consumes it").
2. **The reserved vehicle is derived, never caller-supplied.** A reservation is always against a leg's own current `app.resource_assignments` (OPS-172) `role = 'vehicle'` occupant — the identical derivation `ATW-225`'s own `app.resolve_leg_tracking_policy` already established for eligibility — so a reservation can never target a vehicle other than the one actually assigned to that leg.
3. **Overbooking is prevented by locking the vehicle's own operational-profile row**, not a table-wide lock or a lock on the reservations table itself (which cannot serialize inserts against rows that do not exist yet). Every reservation for a given vehicle takes `app.vehicle_operational_profiles`'s own row lock (`FOR UPDATE`) first, so two reservations against the same vehicle's overlapping window can never both observe the pre-reservation sum. This repository's own disclosed single-threaded sandbox (`scripts/db-tests/commercial-quotation-versioning.sql`'s own "single-threaded sandbox disclosure") cannot execute two real overlapping transactions to prove blocking directly; this checkpoint's own test evidence instead proves the *aggregation and rejection* logic the lock protects is correct on every sequential call — the same disclosed boundary that precedent already established. An explicit "already-active" pre-check plus a defense-in-depth exception handler on the partial unique index cover the narrow race the lock alone does not (§4.1).
4. **Tracking coverage/utilization reuses `ATW-226A`/`223`/`226F`/`225` read paths, never re-derives them.** `app.resolve_tenant_tracking_package` (`226A`) is the sole entitlement/limit source; per-vehicle eligibility flags and `app.gps_devices` come from `ATW-223`; live position/freshness comes from `ATW-226F`'s own `app.vehicle_current_positions`/`app.vehicle_source_health` tables (this migration computes healthy/stale/offline on read against the same `freshness_threshold_seconds`/1x-3x banding `app.get_vehicle_source_health` already established, not a forked constant); "tracking-required but untracked" detection reuses `ATW-225`'s own `app.shipment_leg_tracking_policies.tracking_required` and `app.shipment_leg_tracking_sessions` against `ATW-221`'s own `app.shipment_legs.leg_status`. No read here ever mutates entitlement, source policy, or provider mapping (this prompt's own §14 boundary).
5. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 4.1 Real defects found and fixed during authoring (before commit)

1. **`assign_device_to_vehicle`/`assign_resource` both require `OPS:Assign`, not `Create`/`Edit`** — the fixture's own first-drafted "rep" role granted only `Create`/`Edit`/`View`, so the setup block's own device-assignment and vehicle-resource-assignment calls failed with `insufficient_authority`. Fixed by widening the rep role's grants to include `Assign`, matching `ATW-225`'s own db-test precedent for the identical fixture shape.
2. **Cargo-allocation total reconciliation**: `app.allocate_shipment_leg_cargo` rejects a cumulative allocated quantity across a shipment's own legs that exceeds the shipment's own declared total (`cargo_over_allocated`) — a check this checkpoint had not anticipated from `app.confirm_shipment_leg_network`'s own weaker "every leg has *some* allocation" existence check alone. Fixed by declaring a generously large shipment total (2000/2000/40) up front, comfortably covering the four legs' own combined 1020kg/1020kg/18cbm test allocations.
3. **`vehicle_master_id` lookup by a non-existent `code` column** — `app.vehicle_operational_profiles` carries no `code`/`name` columns itself (those live on `app.master_records`, joined via `vehicle_master_id`, per `ATW-223`'s own design); two test-fixture lookups incorrectly queried `vehicle_operational_profiles.code` directly. Fixed by joining `app.master_records` in both lookups, the same join `app.get_tenant_vehicle_tracking_overview` (`226H`) already establishes.
4. **A narrow idempotency/partial-unique-index interaction, caught during design rather than by a failing test**: `app.reserve_vehicle_capacity`'s own `unique_violation` exception handler originally assumed any conflict was a same-idempotency-key replay and re-selected by that key alone — but the partial unique index on `(shipment_leg_id) where status in ('held','consumed')` can also fire for a genuinely new idempotency key when the leg already carries an active reservation, which would have silently returned an all-null composite row rather than a clear error. Fixed with an explicit pre-check (`reservation_already_active`) plus a hardened exception-handler fallback that only returns silently when the re-select by idempotency key actually finds a row, otherwise re-raising the same named error — both paths are exercised directly in the db-test (§4).

## 5. Residual disclosures

- No capacity calendar / interactive reservation UI exists yet — this checkpoint ships the read dashboard (utilization summary, per-vehicle coverage) and the reserve/consume/release APIs; wiring those APIs into a human-facing dispatch/planning screen is deferred to that integration's own task, per §3.3.
- `app.reserve_vehicle_capacity` requires the leg to already carry a current, active `app.resource_assignments` vehicle occupant (OPS-172) and a non-null `planned_departure_at`/`planned_arrival_at` — a leg reassigned to a different vehicle after a reservation was made does **not** retroactively move that reservation; an operator must release and re-reserve, a deliberate, disclosed manual step rather than a silent auto-migration of held capacity.
- Reservation windows are copied from the leg's own planned times at reservation time, not live-recomputed if the leg's own schedule later changes — consistent with `ATW-224`'s own "planning is decision support, not a live-binding contract" precedent.
- No REST/GraphQL surface exists for this or any domain yet (repository-wide, unchanged).
