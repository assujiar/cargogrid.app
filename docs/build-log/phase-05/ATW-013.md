## 2. Design decisions (disclosed, migration header)

Twelve design notes are disclosed in the migration header (`supabase/migrations/20260730200000_create_advanced_tms_wms_receiving.sql`); the most consequential:

1. **A receipt session is a distinct header, one non-cancelled session per confirmed `app.wms_inbound_orders` row (a real partial unique index)**, with its own `in_progress`/`completed`/`cancelled` lifecycle — `app.wms_inbound_orders.status` itself is never widened. This checkpoint discharges the obligation `ATW-012`'s own `app.cancel_wms_inbound` comment explicitly left open: `app.cancel_wms_inbound` is `CREATE OR REPLACE`-widened (new migration, the already-applied `20260730180000` file is never edited — the identical precedent `20260730170000_harden_advanced_tms_warehouse_zone_location_dependency.sql` already established) to block cancelling an inbound order that already has an active/completed receipt session (`has_receipt_progress`).
2. **A receipt line is auto-created 1:1 from every `app.wms_inbound_order_lines` row the instant a session starts**, snapshotting `item_master_id`/`expected_uom_code`/`expected_quantity`/`lot_controlled`/`serial_controlled`/`expiry_controlled` — the identical governed-snapshot precedent `app.wms_inbound_order_lines` itself already established over `app.item_masters` (`ATW-012` design note 6).
3. **Over/short/damage/hold are real columns, not states inferred from a single "actual quantity" field** (Prompt 232 §24). `counted_quantity` is the total physically counted; `accepted_quantity + damaged_quantity + held_quantity + rejected_quantity` must equal it exactly (`wms_receipt_lines_equation_check`, Prompt 232 §25's own "actual accepted/rejected/variance equation balances exactly"). `over_quantity`/`short_quantity` are real `GENERATED ALWAYS` columns, never independently caller-set.
4. **Two distinct steps — record, then commit — not one combined call.** `app.record_wms_receipt_line_count` is pure administrative recording (overwrite-not-add semantics — a repeated identical scan is structurally idempotent). `app.commit_wms_receipt_line` is the one and only path that calls `app.post_inventory_movement` (`ATW-015`) — accepted lands `status='on_hand'`, damaged lands `status='damaged'`, held lands `status='held'`, all at the session's own `receiving_location_id` (a `dock`/`staging` location, never a final storage bin — putaway is `ATW-233`'s own next task). Rejected quantity posts no movement at all. An `over_quantity > 0` line with no supervisor approval is rejected (`unapproved_overage`) until `app.approve_wms_receipt_overage` (`OPS:Override`-gated, reusing the identical "supervisor approves a configured exception" authority `app.override_route_planning_selection`, `ATW-224`, already established — not a new authority level).
5. **A QC hold is resolved by a distinct, `OPS:Override`-gated RPC** (`app.resolve_wms_receipt_hold`) that posts a real two-line `adjustment` movement (`held` → `on_hand` or `held` → `damaged`, same location) through `app.post_inventory_movement` — never a bare balance edit, never a relocation (that is putaway, `ATW-233`).
6. **UOM is exact** (Prompt 232 §24) — a count may be entered in any registered UOM, but `app.record_wms_receipt_line_count` converts every quantity via `app.convert_uom_quantity` (`ATW-011A`) into the line's own immutable `expected_uom_code` before storing or equation-checking it.
7. **A serial-controlled item is capped at `counted_quantity <= 1` per receipt line** (`wms_receipt_lines_serial_cap_check`) — mirrors `app.inventory_movement_lines`'s own one-serial-per-line dimension model (`ATW-015`); duplicate-serial detection reuses `app.post_inventory_movement`'s own `serial_conflict` check verbatim, not reinvented.
8. **No REST/GraphQL surface, no scan-first PWA UI, no customer-owner-scoped reads** — this repository has consistently deferred these at `ATW-012`/`ATW-015` and defers them again here (`ATW-242` does not exist yet for the last one).

### 3.3 A critical defect found and fixed by adversarial review, before any commit

This checkpoint was built via a `Workflow` orchestration: one implementation agent, then three independent adversarial reviewers (spec-compliance, security/RLS, correctness/concurrency lenses), then a fix pass. The review phase found and the fix phase closed **seven real defects**, independently re-verified by this checkpoint's own orchestrating session directly against the final migration file (§5) — none were taken on the workflow's self-report alone.

**The most serious (critical): a cross-tenant RBAC bypass on three RPCs' idempotent-replay short-circuits.** `app.commit_wms_receipt_line`, `app.complete_wms_receipt_session`, and `app.resolve_wms_receipt_hold` are each idempotent by short-circuiting on a terminal state (`status = 'committed'`/`'completed'`, `hold_resolved = true`) and returning the existing row unchanged on replay — the same shape `app.post_inventory_movement` itself uses. In the first-drafted version, each function's short-circuit ran **before** its own `app.evaluate_permission`/`app.can_access_record` authority check, not after. Live-reproduced by the reviewer against a real migrated database: an actor from an entirely unrelated tenant, holding zero membership or role grant in the target tenant, could call any of the three RPCs against an already-terminal record from that foreign tenant and receive the full row back — item/quantity/lot/serial/movement IDs on a committed receipt line, warehouse/inbound-order IDs on a completed session, prior QC disposition on a resolved hold — with no error raised at all, because the code path returned before authorization was ever evaluated. **Fixed** by reordering all three functions so `app.evaluate_permission` + `app.can_access_record` always run first, with the terminal-state short-circuit moved to run only after authorization succeeds; re-verified live post-fix that the identical attacker call now correctly raises `insufficient_authority`, while a legitimate authorized replay (even with a stale/garbage idempotency key or expected version) still correctly returns the unchanged row. Three new regression assertions were added to `scripts/db-tests/advanced-tms-wms-receiving.sql` proving this directly (a zero-membership tenant-2 actor is rejected probing each of the three short-circuits on already-terminal tenant-1 records).

**Two further critical/high concurrency defects, also found, fixed, and live-reproduced with real concurrent psql sessions:**
- `app.commit_wms_receipt_line`/`app.resolve_wms_receipt_hold` could double-post a real ledger movement under genuine concurrency — the line was read and its state checked with no row lock before `app.post_inventory_movement` was called, so two concurrent calls (e.g. a client retry regenerating a fresh idempotency key) could both pass the pre-commit check and both post. Reproduced with two real concurrent psql sessions (one held via `pg_sleep`): both independently posted a distinct `app.inventory_movements` row, doubling the on-hand/damaged balance for one physical receipt. Fixed with `SELECT ... FOR UPDATE` on the first read, held through the final status `UPDATE`; re-verified with the identical two-session repro that only one movement now posts.
- None of the five row-updating RPCs included `record_version` in their `UPDATE`'s own `WHERE` clause — the optimistic-concurrency check was check-then-write (TOCTOU) against an unlocked read, so a losing concurrent writer with a stale `p_expected_version` could silently succeed instead of raising `stale_version`. Reproduced live (two concurrent `app.record_wms_receipt_line_count` calls, same expected version, second call silently overwrote the first's committed write with no error). Fixed by adding `SELECT ... FOR UPDATE` to the initial read of every affected RPC, holding the lock across the version check through the final `UPDATE`.
- `app.start_wms_receipt_session`'s documented idempotency guarantee did not hold under genuine concurrency: two concurrent calls with different idempotency keys for the same inbound order could both pass the unlocked pre-insert existence check and race on the `INSERT`, with the losing call surfacing a raw, unclassified `unique_violation` instead of gracefully returning the winner's session. Fixed with an `exception when unique_violation` recovery block that re-selects and returns the winning row — mirrors `app.capture_lead`'s own proven recovery pattern (`COM-143`) verbatim.

Full per-finding disposition (all seven confirmed real, all seven fixed, none judged false positive) is preserved in this checkpoint's own workflow transcript; the fixes are reflected directly in the committed migration and its own updated header design notes/function comments (which previously described the pre-fix ordering as intended and have been corrected).

### 3.4 Tests

`scripts/db-tests/advanced-tms-wms-receiving.sql` — one tenant (`wmsrecv1`) with a rep/supervisor/viewer/Supreme Admin, two warehouses (one with dock/staging/bin locations for the main flow, a second for wrong-warehouse checks), one CRM-pipeline customer account, and five item masters (plain, lot-controlled, expiry-controlled, serial-controlled, and a spare plain item); a second isolated tenant (`wmsrecv2`) for cross-tenant leakage checks. Fourteen inbound-order lines, one per outcome scenario: exact, short, unapproved-then-approved overage, partial-accept-partial-damage, two QC-hold lines (resolved to on-hand and to damaged respectively), full reject, lot-controlled, expiry-controlled, two serial-controlled lines (proving duplicate-serial rejection via `app.post_inventory_movement`'s own `serial_conflict`), UOM-conversion, and an item deactivated mid-flow (proving the receipt honestly bubbles up `item_not_eligible` rather than silently succeeding). Also covers: authority gating at every RPC, wrong-warehouse/wrong-location-type rejection, session completion blocked while any line remains uncommitted, `app.cancel_wms_inbound`'s new `has_receipt_progress` guard, session cancellation only while zero lines committed (with a cancelled session freeing its own inbound-order slot for a fresh session, mirroring `ATW-012`'s own freed-source precedent), the three cross-tenant RBAC-bypass regression assertions from §3.3, bounded/filtered reads, and schema-privilege defense in depth (`ERR-2026-004`).
