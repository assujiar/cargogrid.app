## 2. Design decisions (disclosed, migration header)

1. **No new customer-warehouse grant table** — reuses `app.warehouse_customer_eligibility` (`ATW-229`) verbatim. That table's own migration comment already anticipated this: "no consumer yet widens a customer-portal principal's own access from this table... `ATW-242` not yet shipped." This checkpoint is that first real consumer.
2. **No new customer-owner mapping table** — reuses `app.principal_memberships.customer_account_ref` exactly as `ATW-016` already established (a `customer_user`-layer membership's own `customer_account_ref`, when uuid-shaped, IS the `app.accounts.id` that actor may see). A new, narrower pair of functions (`app.evaluate_customer_inventory_access`, `app.resolve_customer_owner_account_scope`) was written rather than reusing `ATW-016`'s own `app.resolve_actor_owner_account_scope`, because that function deliberately returns `null` to mean "unrestricted" for staff — an unsafe default to reuse inside a customer-only gate. The new functions never return an "unrestricted" signal; deny-by-default throughout.
3. **`app.evaluate_customer_inventory_access(actor, tenant, warehouse, owner)`** composes exactly two ANDed checks — an active `customer_user` membership whose uuid-shaped `customer_account_ref` equals the target owner, AND an active `app.warehouse_customer_eligibility` row for that warehouse/owner — enforcing Prompt 242 §24's "scope is intersected across tenant, customer account, company/site (implicit via the warehouse's own `company_org_unit_id`), warehouse and inventory owner."
4. **RLS on the 8 pre-existing tables this migration reads is deliberately left untouched** by the base migration (Prompt 242 §14: "one service must enforce identical scope... policy") — the SECURITY DEFINER RPCs are meant to be the only sanctioned customer read path. A live adversarial review then proved that claim was **not actually true** for 4 of those 8 tables (see §3.3 finding 1) — closed by a dedicated hardening migration, not by widening the base one.
5. **Anti-enumeration**: every single-row get RPC raises an identical `record_not_found` (errcode `no_data_found`) whether the row is missing, cross-tenant, or forbidden — deliberately narrower than every staff-facing RPC in this repository, which does raise a distinguishable `insufficient_authority`.
6. **Cursor pagination** (keyset, `(col, id) < (p_cursor_col, p_cursor_id)`, never `OFFSET`) on every list RPC — a stricter bar than the plain-`LIMIT` convention most internal staff list RPCs in this repository use, per Prompt 242 §17's explicit requirement.
7. Read-only in Phase 5 (§24) — zero `insert`/`update`/`delete` against any inventory/order/reservation table; the only `insert` in the base migration is the audit-log call inside the export RPC.
8. Per `ERR-2026-004`: both new migrations carry their own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before their final grants.

### 3.3 Findings from three independent adversarial-review lenses, all confirmed real and addressed

1. **[HIGH, live-reproduced, cross-tenant-isolation lens] The base migration's own claim ("the ONLY sanctioned read path... is the SECURITY DEFINER RPCs") was false.** `app.wms_outbound_orders`/`app.wms_outbound_order_lines` (`ATW-016A`) and `app.lot_identities`/`app.serial_identities` (`ATW-016`) each already carry an RLS `SELECT` policy passing a real `owner_account_id`/`customer_account_ref` into `app.actor_can_view_owner_scoped_row` — a mechanism those two already-`VERIFIED` migrations built explicitly for "a future customer-facing capability" to use, per their own design notes. Because this checkpoint is the first migration that ever makes a live `customer_user` grant meaningful, that pre-existing branch stopped being latent and became a real, exploitable path: a genuine Supabase `authenticated` client can read these 4 tables directly, bypassing this migration's own new warehouse-eligibility gate entirely (zero RLS policy anywhere referenced it) and receiving staff-internal fields (`source_reason`, `created_by`, `notes`, `parent_lot_id`) the new RPC layer deliberately excludes. Live-reproduced with a real `set role authenticated` probe: revoking a customer's warehouse eligibility correctly blocked every new RPC immediately, but a raw table read kept returning the now-revoked row unchanged. Cross-customer/cross-tenant isolation itself was never broken — only the eligibility axis. **Fixed** via the dedicated hardening migration (§3.1); re-verified live that the same probe now returns 0 rows on all 4 tables, with a staff/Supreme-Admin positive control proving no one else is affected. This closes the concrete instance of the broader, already-tracked `ISS-2026-010` gap this task's own commit makes newly-live — see §7.
2. **[LOW, correctness-concurrency lens] A malformed/partial cursor (`p_cursor_id` supplied without `p_cursor_updated_at`) silently returned an empty page instead of erroring**, because `(not-null, x) < (NULL, y)` evaluates to unknown/false in every row comparison. Fails safe (no wrong data, no leak) but hides a client bug behind "no more results." **Fixed**: added an explicit `invalid_cursor` guard to all 5 cursor-taking list RPCs, plus a Zod `.refine()` at the TypeScript layer requiring both-or-neither.
3. **[HIGH, spec-compliance lens] Denial was never audited**, though Prompt 242 §18 explicitly requires it. The original design's attempt to audit-then-raise inside the same RPC was structurally broken (an uncaught `RAISE` rolls back the whole transaction, including an audit `INSERT` performed moments earlier) — correctly diagnosed and disclosed by the implementer, but left unresolved. **Fixed**: a new `app.record_customer_inventory_access_denial` RPC that the TypeScript query layer calls in a separate transaction after catching a `record_not_found` error (best-effort — a denial-audit failure never masks the real error); uses `result = 'failure'` (`app.audit_logs`'s own `result` CHECK only allows `success`/`failure`, not `denied`).
4. **[HIGH, spec-compliance lens] REST/GraphQL parity was undisclosed**, unlike every sibling capability in this range, which explicitly names the repository-wide "no REST/GraphQL surface exists yet" boundary. **Fixed** via an added design note stating the same accepted boundary.
5. **[MEDIUM, spec-compliance lens] No index covered the new cursor-pagination query shape.** **Fixed** via the additive pagination-index migration (§3.1).
6. **[MEDIUM, spec-compliance lens] "Expiry" (Prompt 242 §13/§24/§27) cannot be implemented against `app.warehouse_customer_eligibility`'s own already-applied two-value (`active`/`revoked`) status CHECK.** Building real expiry semantics requires altering `ATW-229`'s own applied table/RPCs — a capability-sized change beyond this bounded task. **Addressed via disclosure**, not implementation — recorded as a residual gap (§6) rather than silently unmet.
7. **[MEDIUM, spec-compliance lens] No rate limiting** (§16/§23) on any of the 13 new customer-facing RPCs. The one existing repository precedent (`app.lookup_public_shipment_tracking`, `OPS-180`) is purpose-built for a genuinely anonymous `anon`-role surface — a materially different threat model from these already-authenticated, already-scoped RPCs. **Addressed via disclosure** (§6), not an ill-fitting adaptation.
8. **[LOW, spec-compliance lens] "Cursor tampering" and "aggregate inference" (§28) were not literally named as their own test scenarios**, though no live exploit was ever found for either. **Fixed**: two new explicitly-labeled db-test blocks added, reusing existing fixture data.
9. **[LOW, spec-compliance lens] The "company/site" scope leg (§24, §27) is never independently exercised** — the fixture uses one company/org-unit per tenant, so it is very likely functionally subsumed by the warehouse-eligibility check (a warehouse belongs to exactly one company) but was never proven as its own axis. **Deferred**, disclosed as a residual low-priority test gap (§6) — no exploitable gap was found.
10. **[Informational, all three lenses independently noted, not a defect] `app.list_customer_outbound_order_lines` takes no `p_tenant_id`**, unlike its 12 sibling RPCs, deriving tenant from the fetched row instead (mirrors `ATW-016A`'s own `list_wms_outbound_order_lines` convention exactly). Verified non-exploitable — the re-derived tenant is fed straight back into `app.get_customer_outbound_order`'s own full gate. Not fixed; a signature-consistency note only.

No finding was a false positive. One item raised as a finding by the cross-tenant-isolation reviewer (multiple active `customer_user` memberships aggregating correctly, uuid-regex guard not crashing on garbage input, same-timestamp cursor tie-breaking, limit clamping, revocation immediacy) was independently re-verified by the fix agent and confirmed correct as originally built — no fix needed there.

### 3.4 A residual, repository-wide observation (not a finding of this task, not fixed here)
