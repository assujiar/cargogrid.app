## 2. Design decisions (disclosed, migration header)

1. **WMS never creates an invoice, AR, AP, GL, or settlement record** — grepped the full migration to confirm zero writes to any Finance schema table, mirroring `OPS-181`'s own identical, already-`VERIFIED` boundary claim.
2. **A new child table, `app.warehouse_billing_rate_components`, reuses the existing `app.customer_contracts` header/versioning/publish lifecycle directly** — `app.customer_contract_price_components` (`COM-156`) is shaped for freight lane/mode/equipment pricing with no rate-basis/UOM/tiering concept, so warehouse activity rates get their own child table rather than being forced into that shape. Gated on `COM:Edit` (a Commercial-owned pricing configuration), distinct from the `OPS`-gated event lifecycle — this capability deliberately spans both permission tiers, matching Prompt 241 §26's own "commercial roles review calculated events; designated approvers release readiness" split.
3. **Corrections/reversals are always new rows, never an in-place amount rewrite** — `app.correct_warehouse_billing_event`/`app.reverse_warehouse_billing_event` insert a fresh event referencing the original via `corrects_event_id`/`reverses_event_id` and flip only the original's own lifecycle `status`, never its `base_amount`/`tax_amount`/`total_amount`/`calculation_explanation`.
4. **Only outbound has a pre-built eligibility-event source** (`app.wms_billing_eligibility_events`, `ATW-019`) — the other six activity types (storage, receiving, handling, putaway, pick, pack, value-added) dispatch directly against their own already-`VERIFIED` operational tables, or through a governed `manual` path (`OPS:Override` + mandatory reason) where no operational table exists at all (storage, value-added).
5. Per `ERR-2026-004`: this migration carries its own explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` statement before its final grants.

### 3.3 Six findings from three independent adversarial-review lenses, all fixed

1. **[CRITICAL, spec-compliance] `app.reverse_warehouse_billing_event` never transitioned the ORIGINAL event's own status to `'reversed'`** — unlike its sibling `app.correct_warehouse_billing_event`, which correctly flips the original to `'corrected'`. Live-reproduced: reversing an `'approved'` event left it `'approved'`, after which `app.handoff_warehouse_billing_event` succeeded a **second time** against the same original, sending an already-voided billing fact to Finance as if it were still live. The shipped db-test asserted the reversal's own negated amounts and the original's unchanged `total_amount`, but never asserted the original's post-reversal *status* — which is how this passed the full green gate suite undetected. **Fix:** added the missing `UPDATE ... SET status = 'reversed' WHERE id = p_original_event_id AND record_version = p_expected_version`.
2. **[CRITICAL, correctness-concurrency; independently re-found from a different angle as HIGH by security-tenant-isolation] `app.capture_warehouse_billing_event`'s idempotent-replay short-circuit validated only `source_type`/`source_id`/`activity_type`, never `owner_account_id`/`warehouse_id`** — the two actual RLS/authorization-scoping fields. Live-reproduced as a genuine cross-owner data leak: an actor scoped to Account Alpha, authorized only via their own account, could supply Account Beta's real idempotency key and receive Beta's full calculated billing event back — including `base_amount`/`tax_amount`/`total_amount`/`calculation_explanation` — with zero indication of the mismatch. This is the fourth occurrence of the cross-target idempotency-misattribution bug class in this build (fixed once at `ATW-020`, recurred twice at `ATW-021`, now a fourth time here), despite this migration's own header explicitly (and, until this fix, incorrectly) claiming the lesson had been applied. **Fix:** extended the match condition (in both the short-circuit and its exception-handler mirror) to additionally require `warehouse_id`/`owner_account_id` equality, raising `idempotency_key_conflict` on any mismatch.
3. **[HIGH, correctness-concurrency] Calculated financial amounts had no field-level masking for a plain `OPS:View` reader** — the migration's own header cites `app.customer_contract_price_components`' (`COM-156`) established masking convention (nulling commercial fields for a caller lacking `COM:View selling price`) as its own reused precedent, but none of the four read RPCs actually implemented it; a bare `OPS:View` actor with zero commercial-tier permission could read every calculated amount in the tenant. Live-reproduced. **Fix:** added `app.mask_warehouse_billing_event_amounts`, mirroring `COM-156`'s own masking function exactly, wired into `get_warehouse_billing_event`/`list_warehouse_billing_events`. (The review's own claim that the two handoff-read RPCs also leaked amounts was a partial false positive — `app.warehouse_billing_handoffs` has no amount columns at all; the fix pass confirmed this by direct schema inspection rather than silently fixing a non-issue.)
4. **[MEDIUM, correctness-concurrency] `app.correct_warehouse_billing_event`/`app.reverse_warehouse_billing_event` omitted `p_expected_version`**, unlike every other status-transition RPC in the migration. Not live-exploitable as a double-correction/-reversal race (the `SELECT ... FOR UPDATE` lock plus the `already_corrected`/`already_reversed` business checks already close that), but broke the uniform optimistic-concurrency contract every other mutation in this build honors, and left no stale-client detection for an event whose status changed between a client's read and its correct/reverse call. **Fix:** added `p_expected_version` to both signatures with a `stale_version` check.
5. **[LOW, spec-compliance] The "one correction per original" rule had no backing partial unique index**, unlike the symmetric "one reversal per original" rule, relying solely on the row lock. **Fix:** added `warehouse_billing_events_one_correction_per_original_idx`, mirroring the existing reversal index.

No finding was a false positive in substance; one finding's *scope* (which two RPCs it named) was partially over-broad and corrected during the fix pass rather than blindly applied.
