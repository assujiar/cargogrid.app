**The checkpoint's own single highest-priority item, `ISS-2026-150` (High, "must not
be deferred again"), is `RESOLVED`.** `app.assert_ip_allowed` and
`app.has_active_ip_allowlist_bypass` (IAE-028, real and correct in isolation since
Prompt 356 but with zero real callers anywhere in the mutation layer) are now composed
into all 4 platform-default high-risk target functions `CG-S14-IAE-039` already named
for the sibling step-up-MFA ruling: `app.decide_ai_output_approval`,
`app.activate_enterprise_idp_connection`, `app.approve_mfa_exception`,
`app.create_integration_connection`. Each gained one new trailing, defaulted
`p_client_ip text default null` parameter; when supplied and the actor holds no
currently-active IP-allowlist bypass grant, the tenant's own `enforced`-mode allowlist
policy (scope `'admin'`) is now genuinely checked. `app/(tenant)/[tenantSlug]/
integrations/actions.ts` — the only one of the 4 functions with a real live HTTP route
today — threads a real `x-forwarded-for`-derived client IP; the other 3 have no UI
route yet, so their RPC-level gate is real and db-test-provable but not yet reachable
from a live request (disclosed explicitly, not a defect).

**A genuine implementation defect was found and fixed before this checkpoint's own
first commit, not after.** A first draft used a bare `CREATE OR REPLACE FUNCTION` to
add the trailing parameter to all 4 functions. Postgres does not treat an appended
parameter — even a defaulted, trailing one — as a signature match for
`CREATE OR REPLACE`: it silently creates a second, co-existing overload instead. This
surfaced live, against a real disposable database, as `function name "app.decide_ai_
output_approval" is not unique` on the very next `COMMENT ON FUNCTION` statement — and
would have left every existing (no-`p_client_ip`) caller permanently bound to the OLD,
un-gated overload forever, regardless of enforcement mode, exactly the "cosmetic
partial wire-up" `ISS-2026-150`'s own disclosure explicitly forbade. Caught during this
checkpoint's own Tier A validation, before any commit; corrected to an explicit
`DROP FUNCTION` (old signature) + `CREATE FUNCTION` (new signature) +
re-`GRANT EXECUTE` (verified against each function's own origin migration to restore
the exact original `authenticated, service_role` grants) for all 4 functions. Re-
verified: all 4 functions confirmed to have exactly one overload each post-migration
(`pg_proc`), correct grants confirmed via `has_function_privilege`, and every one of 11
targeted db-test files re-run clean end to end against a fresh disposable database
(the 4 files with new IP-restriction regressions, plus 7 other files that call these
functions purely as fixture setup).

**`ISS-2026-151`** (the sibling step-up-MFA gap, still open on this same
`create_integration_connection` function) **was re-scoped precisely and deliberately
deferred again.** Lens 2's own re-derivation: 43 real call sites across the same 16
files (not the "40+" estimate), of which 4 are negative-path (unaffected) and 39 need
the gate satisfied, collapsible into 27 distinct step-up-challenge sequences. Stacking
this onto the same checkpoint as the IP-restriction migration would exceed the normal
5–15-file bounded-repair budget this checkpoint otherwise stayed within, and would
repeat exactly the "rushed, under-tested wide edit" risk `CG-S14-IAE-039` already
declined once for the same function. The precise new scope is recorded so the next
owner does not have to re-derive it.

**Extension relocation (matrix item 3) partially corrected and partially resolved.**
`pg_trgm` and `btree_gist` were relocated out of `public` into a new `extensions`
schema (2 of the item's own 8 named advisories). `postgis` was found to be
structurally non-relocatable (`relocatable = false` in its own extension control
file — `ALTER EXTENSION postgis SET SCHEMA` fails outright; the only real path is
`DROP EXTENSION postgis CASCADE` + recreate, which would destroy 15 live
`geography`-typed columns across 12 real tables, a data-migration-class operation
genuinely out of this checkpoint's own bounded scope). The matrix's own original
"clears 7 of 8" framing is corrected to "clears 2 of 8"; the remaining 6, including the
one ERROR advisory (`spatial_ref_sys`'s `rls_disabled_in_public`), are registered
separately (`ISS-2026-234`).

**A full OWASP-style abuse-pattern sweep held on 9 of 10 categories.** SQL injection
(zero unsafe dynamic-SQL construction anywhere in 250+ `execute` statements), IDOR
(4 domains live-forced, all correctly derive tenant scope from the looked-up record,
never a caller-supplied claim), CSRF (bearer-token-only REST API, Next.js
Origin-header same-site check on Server Actions), XSS (zero
`dangerouslySetInnerHTML`/`innerHTML=`/`eval` in application code), rate limiting
(live-forced exact 5-allowed/3-denied enforcement), API-key handling (hash-only
storage, shown-once raw key, never logged), webhook signature verification (all 4
repository `verify_*` functions live-forced fail-closed on null/empty signature and a
5-minute replay window), file-upload validation (4 live attack payloads blocked,
server-generated storage path never filename-derived), and prompt injection /
AI-governed-action human approval (structural confidence gate, canonical-source
citation requirement, zero auto-apply code paths) all held with zero findings. The
10th category, open redirect, surfaced a real, latent defect
(`ISS-2026-233`, Medium) — found and fixed the same checkpoint.

**`ISS-2026-168`** (service-role import boundary — the file's own documented "bundle
scan" enforcing server-only import does not exist) **is resolved**: a new ESLint
`no-restricted-imports` rule flags any import of `lib/supabase/service-role`, scoped
via an explicit `ignores` list naming every one of the 26 real, currently-legitimate
importers (this repository has no directory/filename convention that reliably
distinguishes Client from Server Components, so an unscoped rule would have flagged
all 26 real callers; extending legitimate access now requires deliberately adding a
new file to this list).

**2 more findings surfaced and fixed in the same pass, both pre-existing and already
owned by this checkpoint, neither covered by any of the 4 investigation lenses:**

- **`ISS-2026-169`** — an anonymous vendor self-registration Server Action already
  unified its *rendered* error message for `not_found`/`disabled` outcomes, but still

  the caller on every error path. Fixed by returning `result: null` on the entire
  error branch.
- **`ISS-2026-232`** — 3 more `token_hash` columns (`app.vendor_intake_tokens`,

  pattern. **A second real regression was caught and fixed in the same pass**: two
  query functions (`server/queries/public-tracking.ts`,
  `server/queries/driver-mobile-tracking.ts`) used a bare `.select("*")` against these
  now-column-restricted tables — one of them (`getActiveShipmentTrackingToken`) has a
  real, live caller using the ordinary `authenticated`-session client (the Operations
  shipment-order tracking panel), which would have started failing with a permission
  error the next time that panel loaded. Both changed to an explicit column list,
  verified against each function's own Zod contract schema.
