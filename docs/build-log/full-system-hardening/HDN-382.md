## 1. Outcome

Three independent parallel investigation lenses covered the charter named by
Prompt 382 §20/§24 and `HARDENING_MATRIX.md` §13's own seeded punch list:
(Lens 1) a source-level static evidence sweep mapping observability coverage
across app/DB/queue/jobs/integrations/API/AI/storage/security events; (Lens 2)
live/simulated failure testing — actually driving real failures through a
disposable Postgres and observing whether they produce evidence; (Lens 3) a
runbook/dashboard/alert-ownership/severity-workflow review.

**Headline, live-reproduced finding, convergent across all 3 lenses**: IAE-030
(`supabase/migrations/20260807400000_create_intelligence_enterprise_monitoring_observability.sql`)
built a real, well-constructed alerting/incident schema — real severity enum,
real owner routing, real concurrency-safe deduplication (`pg_advisory_xact_lock`,
already hardened at its own Tier C) — but it had **zero real production
callers anywhere in this codebase**. Lens 2 live-forced this directly: a job
driven through the real DLQ path (`app.enqueue_job` → `app.claim_next_job` →
`app.record_job_failure` with `max_attempts=1`) reached its own terminal
`dead_letter` status with **zero incident, zero alert, zero owner
notification** — only an `app.audit_logs` row a human would have to go
looking for. This directly contradicts Prompt 382's own Main Flow (§21: "A
job/webhook/API/database failure produces actionable alert") and Business
Rule §24 ("No silent DLQ/backpressure accumulation") for the single most
common real failure path in this repository.

**3 real gaps found and fixed this checkpoint:**

- **`app.record_job_failure`'s own dead-letter transition now raises a real,
  deduplicated observability alert** (`source_type='job'`, `signal_type=
  'error'`, `severity='high'`) instead of landing silently. Live-verified via
  a new regression db-test that drives a job to `dead_letter` and confirms an
  incident is created, that a second distinct job type dead-lettering for the
  same tenant within the dedup window correctly collapses into the same
  incident (`ISS-2026-155`'s own known, unrelated, separately-owned
  granularity behavior — not re-litigated here), and that a merely-retryable
  (non-terminal) failure raises no alert at all.
- **`/api/health` and `/api/ready` did not exist**, despite
  `docs/standards/OBSERVABILITY_STANDARDS.md` §7 already fixing their exact
  contract and `docs/runbooks/observability-exporter-outage.md`'s own
  diagnosis step 1 falsely claiming they were "implemented Phase 1" — a live
  404 for any on-call responder who followed that step during a real
  incident. Built both, matching the standards doc's own contract exactly:
  `/api/health` is an unconditional liveness check (`{status: "ok"}`, 200);
  `/api/ready` additionally calls a new, trivial, side-effect-free
  `app.ping()` RPC to confirm DB connectivity, returning `503`/
  `{status: "degraded", reason: [...]}` on failure — never a false "ok".
  Live-tested against a real running production server: `/api/health` →
  `200 {"status":"ok"}`; `/api/ready` against this sandbox's own placeholder
  Supabase URL (genuinely unreachable) → `503
  {"status":"degraded","reason":["database_unreachable"]}`, proving the
  failure path live, not merely asserted.
- **Two stale/false runbook references corrected**: `observability-exporter-
  outage.md`'s own "implemented Phase 1" claim (now genuinely true, fixed
  above, with a correction note added); `gps-ingestion-database-outage.md`'s
  own "no live Supabase project exists yet" note, stale since `HDN-372`
  (2026-08-23) established a real, hosted, live-verified Supabase project
  (`awdlicmwzdxquopwtcfd`) — corrected to name the real, narrower, still-true
  rehearsal blocker (no live GPS Gateway/Driver PWA/provider deployment
  exists to interrupt).
