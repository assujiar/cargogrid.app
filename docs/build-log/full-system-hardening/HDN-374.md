## 6. Findings and dispositions

### 6.1 Lens 2 (cost/AP chain) — clean

Actual cost → vendor bill → journal → AP open item → settlement all reconciled to exact
source-linked totals under live testing. `app.prepare_finance_vendor_bill_from_actual_
cost`'s own idempotency-race gap is a Finding-3 member (§6.3), not a cost/AP-formula
defect. Zero findings.

### 6.2 Lens 1 (revenue chain) — 2 real defects, 1 self-corrected before commit, 2 registered

**Finding 1 — double-taxation (`ISS-2026-194`, High).** `app.job_orders.revenue_
snapshot` always carries both `subtotalAmount` (pre-tax) and `totalAmount` (tax-
inclusive) whenever the originating quotation applied a line-level `tax_pct`
(`20260724340000_create_commercial_job_order_lineage.sql`'s own `'pricing'` object
construction — the sole path, confirmed by reading the actual function body, not
assumed). `app.prepare_finance_invoice_from_readiness` read `totalAmount` and treated it
as the invoice's own pre-tax subtotal, so a caller also passing `p_tax_code` (the normal
path — every existing db-test fixture exercising this function does) had
`app.calculate_finance_tax` apply the same rate a second time. Live-forced: a quote
(qty=3, unit_price=333333.33, `tax_pct`=11) produced `subtotal=999999.99
tax=110000.00 total=1109999.99` at the quote level; invoicing with `p_tax_code`='PPN'
yielded `subtotal_amount=1109999.99 tax_amount=122100.00 total_amount=1232099.99` — an
~11% overcharge. Fixed by reading `subtotalAmount` instead. Full disposition
`ISS-2026-194`.

**Finding 2 — double-billing, self-corrected before commit (`ISS-2026-195`, High).**
`app.prepare_finance_invoice_from_readiness`'s own idempotency check only replays the
SAME handoff; nothing checked whether the job order already had an issued invoice from
a DIFFERENT handoff. Live-forced: a job with real revenue 3,000,000 was invoiced twice
via two handoffs, both `issued`, 6,000,000 billed for 3,000,000 of work.

**The first fix draft was wrong** — this checkpoint's own self-check, not a Tier C
finding. The draft gated `app.prepare_finance_invoice_from_readiness` itself (deny a
second DRAFT invoice per job order). Before committing, the fix was live-force verified
against the full 229-file `scripts/db-tests` suite, which failed:
`scripts/db-tests/finance-invoice.sql`'s own existing discard-boundary fixture prepares
a SECOND draft invoice from a second, later handoff on the SAME job order and discards
it — its own comment cites this as "a legitimate re-handoff after a later reevaluation,
OPS-181's own disclosed allowance." Reading `20260728140000_create_operations_billing_
readiness.sql` directly confirmed this is deliberate, disclosed design: "Multiple
handoffs may exist for one Job Order over time … this migration does not forbid a
legitimate re-handoff after a later reevaluation." The draft guard would have broken
sanctioned behavior, not fixed a defect — corrected before commit rather than patching
the test to accommodate a wrong fix. The shipped fix moves the guard to `app.issue_
finance_invoice` — the actual AR/GL posting boundary — denying a second `issued` invoice
per job order while leaving draft/submitted/approved states freely creatable and
discardable exactly as `OPS-181` intends. Full disposition `ISS-2026-195`.

**Registered, not fixed (`ISS-2026-197`, Low, owner `HDN-386`):** no FX/multi-currency
conversion exists anywhere in the revenue chain (a structural absence — RPD-016 already
defers multi-country localization); `app.calculate_job_profitability` (Operations)
always reports the static quote-time total rather than the actual invoiced figure (a
planned-vs-actual split, not a formula defect — the UI/contract-layer disclosure
question was not audited, out of this database-focused investigation's own scope).
Neither is a bounded database repair within this audit's own charter.

### 6.3 Lens 3 (period lock/reversal/concurrency/rounding) — clean formulas, 1 concurrency finding closing prior scope

Period lock, reversal/correction mechanics, and decimal-precision/rounding-mode edges
all held clean under live testing. The concurrency portion re-verified `HDN-371`/`373`'s
own registered `HDN-BLK-010`/`ISS-2026-162` (9 of 20 cross-module boundary functions
share an unguarded check-then-insert race) for the 6 functions this checkpoint was
explicitly named owner of, live-forcing 2 of them (`app.prepare_finance_journal_
reversal`, `app.prepare_finance_payroll_disbursement_handoff_from_payroll_run`) and
reproducing the exact registered failure — a raw `duplicate key value violates unique
constraint` surfacing to the losing concurrent caller.

This checkpoint's own wider sweep (not limited to `HDN-371`'s original `prepare_/
convert_/link_/create_from_` name-prefix scope) found **4 more** Finance functions
sharing the identical shape under different verbs: `app.post_finance_subledger_batch`
(the core GL-posting primitive, called transitively by AR receipt allocation, AP
settlement posting, and invoice/vendor-bill subledger posting), `app.create_and_post_
finance_system_journal`, `app.import_finance_bank_statement`, `app.stage_finance_
exchange_rate_import`.

**Fix**: all 10 functions gained the codebase's own already-proven "design note 9(a)"
exception-handler pattern (`app.prepare_wms_outbound_from_shipment`'s own reference
implementation) — each insert wrapped in `begin ... exception when unique_violation
then <re-select the function's own pre-existing idempotency predicate>; if found then
return it; else raise; end`. `app.prepare_finance_journal_reversal`'s handler
distinguishes its two distinct possible unique-constraint causes (idempotency-key
collision vs. the separate "one active reversal per original journal" partial index)
rather than collapsing both into one exception path. `app.prepare_finance_payroll_
disbursement_handoff_from_payroll_run`'s own idempotency short-circuit also gained a
`tenant_id` predicate it previously lacked (a disclosed defense-in-depth narrowing, not
a behavior change — `payroll_run_id` is already globally unique in practice).

**Live-forced re-verification, 2 representative mechanisms** (mirroring `HDN-371`'s own
precedent of one live proof per mechanism rather than every instance): a genuine
two-process race against `app.prepare_finance_journal_reversal` (tenant+idempotency_key
predicate) and `app.post_finance_subledger_batch` (tenant+source_type+source_id
predicate), both using the uncommitted-insert-blocking technique via `scripts/db-tests/
wms-picking-concurrency-helper.sh`'s own generic two-process helper. Both processes
returned the byte-identical winning row in each race — confirmed via committed
regression tests (`scripts/db-tests/finance-reversal-adjustment.sql`, `scripts/db-tests/
finance-subledger.sql`), not merely an ad-hoc session-only check.

Closes `ISS-2026-162`'s Finance/HRIS-Payroll scope (`RESOLVED`, amended). The 3
non-Finance functions that finding also named (Commercial `app.prepare_job_order_
handoff`, WMS `app.prepare_wms_inbound_from_shipment`, Platform/Auth `app.link_auth_
identity`), plus `ISS-2026-163` (`app.prepare_job_order`'s own defective exception
handler, same function family), are explicitly out of this checkpoint's Financial
Integrity charter — handed to `HDN-387`, not silently dropped or force-fit here.

### 6.4 Lens 4 (loyalty liability/payroll/tax/statutory) — 1 real defect, rest clean

Loyalty point/benefit liability reconciliation, payroll→Finance handoff aggregation, and
RPD-016's SME-evidence-before-activation gates for both Finance tax rules and payroll
statutory components all held clean under live testing — no SME evidence, no
activation; a rejected version cannot be approved regardless of actor authority,
live-forced.

**Finding — `p_as_of` silently ignored (`ISS-2026-196`, Medium).** `app.run_loyalty_
expiry_sweep(p_tenant_id, p_as_of, ...)` computed `v_as_of := coalesce(p_as_of,
clock_timestamp())` and recorded it in the completed job's own payload for evidence, but
never passed it to either primitive it composes — `app.expire_loyalty_point_lots`/
`app.expire_loyalty_benefit_entitlements` each hardcoded `expires_at <=
clock_timestamp()` with no as-of parameter at all. Live-forced: a lot due in 2 days,
swept with `p_as_of` set 3 days into the future, was silently left untouched (the sweep
used the real clock instead), while the job's own payload recorded the requested future
`as_of` — misrepresenting what was actually evaluated. Fixed by adding a trailing
`p_as_of timestamptz default null` parameter to both primitives (default preserves every
existing direct caller's own real-clock behavior) and threading `run_loyalty_expiry_
sweep`'s own `v_as_of` through to both. Full disposition `ISS-2026-196`.
