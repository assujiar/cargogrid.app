**Live-executed and measured, not merely documented:**

- **Schema/structure recovery** — a full 329-migration replay from an empty
  database, following `scripts/db-tests/lib/setup-disposable-db.sh`'s own
  pattern, run 3 independent times: **43.70s / 44.79s / 46.34s**, 0 errors
  each, converging on 603 tables, 2,701 functions, 448 RLS policies every
  time. This is the same mechanism `scripts/db-tests/run.sh` already
  exercises on every checkpoint and `HARDENING_MATRIX.md` §16 (`HDN-385`)
  independently cites as proven against both a disposable database and the
  real hosted project — now also explicitly cited here as HDN-383's own
  baseline structure-recovery RTO evidence.
- **Row-level data recovery** — seeded a representative slice (2 tenants,
  2 users, 1 pending + 1 dead-lettered job) onto a freshly migrated
  database, then ran a real `pg_dump -Fc` → `DROP DATABASE` → `CREATE
  DATABASE` → `pg_restore -j 4` cycle: dump 1.56s, teardown 0.66s, create
  0.09s, restore 9.28s — **~11.6s total, 0 errors**. Verified post-restore,
  all exact: object counts identical; row counts identical; **job state
  preserved byte-for-byte** (status, attempts, `next_attempt_at`,
  `idempotency_key`, timestamps to the microsecond — directly satisfying
  business rule §24's "restored jobs/webhooks must not replay duplicate
  transactions"); RLS spot-checked and fully functional immediately
  post-restore (a tenant member sees only their own tenant's rows, a
  different tenant's admin sees zero, `service_role` bypasses correctly,
  `anon` is denied).
- **Real footgun found live**: a first `pg_dump --no-owner --no-privileges`
  attempt silently stripped the schema/table grants RLS itself sits on top
  of — the restored database returned a blanket `permission denied for
  schema app` for every role instead of RLS-scoped results. Documented as a
  "never do this" warning in the new runbook.
- **Teardown-batching constraint reproduced and corrected**: the seeded
  "~1,400 objects" threshold (`HARDENING_MATRIX.md` §14 item 1) is now
  stale — a live schema census found 603 tables, 2,149 indexes, 4,636
  constraints, 2,701 functions, 1,316 types, 305 triggers, 37 views, 1
  matview, 448 RLS policies (tables+indexes+views+matviews+sequences+
  triggers alone already total 3,098, over double the old figure).
  `DROP SCHEMA app CASCADE` in one transaction was live-reproduced to fail
  identically (`53200: out of shared memory`). A working batched strategy
  was found and timed live: order tables by ascending inbound-FK count
  (leaves first, `app.tenants` — 524 inbound FKs — last), `DROP TABLE IF
  EXISTS ... CASCADE` per table as separate auto-committed statements, then
  a final `DROP SCHEMA app CASCADE` sweep — **1.96s, 0 errors**.
- **`auth.users`/`users_pkey` collision reproduced live**: after a batched
  `app`-only teardown and a full 329-migration replay, re-inserting the
  same `auth.users` id/email fails exactly as documented
  (`duplicate key value violates unique constraint "users_pkey"`).

**What this sandbox cannot prove, disclosed per Prompt 383 §22's own
alternative flow, not fabricated**: no full Supabase stack (Auth service,
Storage, PostgREST gateway) is reachable here — the same
`RLIMIT_NOFILE`/`runc` container-runtime constraint `HDN-380` already found
for the Auth backend (`ISS-2026-140`). Consequently no Storage-object
restore, no Auth-service-level restore, and no real hosted-project PITR
restore were executed anywhere. This correctly keeps Step 16 blocked on
production-like restore evidence this sandbox structurally cannot produce.

**1 real, non-obvious finding this checkpoint's own investigation
surfaced** (not previously disclosed anywhere in this repository): a
database restore to a point predating an active legal hold silently
defeats that hold — since a legal hold is itself ordinary application data
stored in the same schema being restored, restoring to before the hold was
placed produces a database that has never heard of it, with no compensating
control today. Registered `ISS-2026-254`, High.

**3 findings registered, not fixed, each with a named owner:**

- **`ISS-2026-254`** (High) — the legal-hold-vs-restore risk above.
- **`ISS-2026-255`** (High, `TRACKED_GAP`) — real production-like restore

  defaults (`docs/architecture/11_DEVOPS_WORKSTREAM.md` §8.1) have never
