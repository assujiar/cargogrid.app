- **Schema/structure recovery** — a full 329-migration replay from an empty
  database, following `scripts/db-tests/lib/setup-disposable-db.sh`'s own
  pattern, run 3 independent times: **43.70s / 44.79s / 46.34s**, 0 errors
  each, converging on 603 tables, 2,701 functions, 448 RLS policies every
  time. This is the same mechanism `scripts/db-tests/run.sh` already
  exercises on every checkpoint and `HARDENING_MATRIX.md` §16 (`HDN-385`)
  independently cites as proven against both a disposable database and the
  real hosted project — now also explicitly cited here as HDN-383's own
  baseline structure-recovery RTO evidence.
- **Row-level data recovery** — seeded a representative slice (2 tenants,
  2 users, 1 pending + 1 dead-lettered job) onto a freshly migrated
  database, then ran a real `pg_dump -Fc` → `DROP DATABASE` → `CREATE
  DATABASE` → `pg_restore -j 4` cycle: dump 1.56s, teardown 0.66s, create
  0.09s, restore 9.28s — **~11.6s total, 0 errors**. Verified post-restore,
  all exact: object counts identical; row counts identical; **job state
  preserved byte-for-byte** (status, attempts, `next_attempt_at`,
  `idempotency_key`, timestamps to the microsecond — directly satisfying
  business rule §24's "restored jobs/webhooks must not replay duplicate
  transactions"); RLS spot-checked and fully functional immediately
  post-restore (a tenant member sees only their own tenant's rows, a
  different tenant's admin sees zero, `service_role` bypasses correctly,
  `anon` is denied).
- **Real footgun found live**: a first `pg_dump --no-owner --no-privileges`
  attempt silently stripped the schema/table grants RLS itself sits on top
  of — the restored database returned a blanket `permission denied for
  schema app` for every role instead of RLS-scoped results. Documented as a
  "never do this" warning in the new runbook.
- **Teardown-batching constraint reproduced and corrected**: the seeded
  "~1,400 objects" threshold (`HARDENING_MATRIX.md` §14 item 1) is now
  stale — a live schema census found 603 tables, 2,149 indexes, 4,636
  constraints, 2,701 functions, 1,316 types, 305 triggers, 37 views, 1
  matview, 448 RLS policies (tables+indexes+views+matviews+sequences+
  triggers alone already total 3,098, over double the old figure).
  `DROP SCHEMA app CASCADE` in one transaction was live-reproduced to fail
  identically (`53200: out of shared memory`). A working batched strategy
  was found and timed live: order tables by ascending inbound-FK count
  (leaves first, `app.tenants` — 524 inbound FKs — last), `DROP TABLE IF
  EXISTS ... CASCADE` per table as separate auto-committed statements, then
  a final `DROP SCHEMA app CASCADE` sweep — **1.96s, 0 errors**.
- **`auth.users`/`users_pkey` collision reproduced live**: after a batched
  `app`-only teardown and a full 329-migration replay, re-inserting the
  same `auth.users` id/email fails exactly as documented
  (`duplicate key value violates unique constraint "users_pkey"`).

**What this sandbox cannot prove, disclosed per Prompt 383 §22's own
alternative flow, not fabricated**: no full Supabase stack (Auth service,
Storage, PostgREST gateway) is reachable here — the same
`RLIMIT_NOFILE`/`runc` container-runtime constraint `HDN-380` already found

**1 real, non-obvious finding this checkpoint's own investigation
surfaced** (not previously disclosed anywhere in this repository): a
database restore to a point predating an active legal hold silently
defeats that hold — since a legal hold is itself ordinary application data
stored in the same schema being restored, restoring to before the hold was
placed produces a database that has never heard of it, with no compensating
control today. Registered `ISS-2026-254`, High.

**13.1 Correctness re-derivation** — independently re-ran the live drill
against a fresh disposable Postgres rather than trusting the first round's
own narrative. **CONFIRMED**: every first-round timing figure reproduced
within the same order of magnitude — schema/structure recovery 47.58s /
51.77s / 48.28s (vs. the original 43.70s / 44.79s / 46.34s), converging on
the same 603 tables/2,701 functions/448 RLS policies; row-level
`pg_dump`/`pg_restore` cycle 10.71s total (vs. 11.6s), object/row counts and
job state byte-for-byte identical; the teardown-batching strategy 1.93-2.02s
(vs. 1.96s), 0 errors; the `auth.users`/`users_pkey` collision reproduced
identically. **CORRECTED** (2 methodology footnotes, not defects in the
findings themselves): the object-census methodology in `HARDENING_MATRIX.md`
§14 item 1 and this file's own §4 used `information_schema.table_constraints`
for the constraint count, which over-counts `CHECK` constraints roughly
1.5× versus the authoritative `pg_constraint`; likewise
`information_schema.triggers` over-counts multi-event triggers versus
`pg_trigger` (non-internal). Both corrected in the runbook's §3 item 3. The
tables+indexes+views+matviews+sequences+triggers subtotal (3,098) was
re-verified exactly once sequences are counted via `pg_class relkind='S'`
(3 real sequences) rather than `information_schema.sequences`, which misses
identity-owned sequences and undercounts to 0.

**13.2 Schema-wide completeness sweep** — swept for other live-reproducible
instances of the same restore-defeats-security-state shape `ISS-2026-254`
first found for legal holds, and for whether `HDN-384`'s own inherited
constraints (per `HARDENING_MATRIX.md` §15's "verbatim" note) are actually
composable from what this checkpoint proved. **2 more concrete,
live-reproduced instances of `ISS-2026-254`'s own gap class found**, folded
into that entry rather than opened as separate tickets: revoked API
keys/disabled webhook endpoints (`app.api_keys.status`,
`app.webhook_endpoints.status`) and suspended user/membership access
(`app.users.status`, `app.principal_memberships.status`, arguably the
highest blast radius of the three since offboarding is more common than a
legal hold) — both live-proved with a real revoke/suspend-then-restore-
older-backup experiment. **Ruled out, not the same risk** (re-derived from
the actual function bodies): IP-allowlist bypass grants and MFA exceptions
both re-evaluate expiry live against `now()` on every read, so a restore
cannot resurrect an already-expired grant — one narrow Low residual noted
(an MFA exception consumed inside its own short-lived `expires_at` window
could theoretically be replayed if that exact window is restored into, not
registered separately). **Live-verified `app.record_dr_restore_test` works
end-to-end** in a disposable database (called successfully, then discarded),
confirming the first round's own decision not to call it against throwaway
data was the correct evidentiary-integrity call, not an omission. **Found
that neither proven first-round procedure (full replay from empty; drop/
recreate database) actually composes for a real hosted Supabase project**,
which cannot drop its own database — only reset within schemas it owns,
exactly the scenario `HDN-384` inherits. A new composed in-place restore
procedure (§4 item 4 of the runbook) was authored to close this gap.
**Minor, disclosed, not registered separately**: `app.files` was never
exercised in the drill's seeded slice — a coverage gap for the next real
drill to close, noted in the runbook's own §4 item 5.

**13.4 Attack-surface adversarial testing** — the lens that found all 5
headline gaps. **Live-proved plaintext secret values survive a full backup**:
inserted a canary value into `app.webhook_endpoints.secret_value`, ran a
full `pg_dump -Fc` → `pg_restore --data-only` cycle, confirmed the value
survived verbatim — `pg_restore`'s own output shows `SET row_security =
off;`, confirming RLS/grants are bypassed entirely at this level, directly
contradicting the first round's own "secrets as references only" claim.
**Live-proved a version-skewed restore carries forward an already-patched
RLS vulnerability**: built a database at the pre-fix migration point for
`20260810500000_harden_own_row_rls_membership_gap.sql`
(`ISS-2026-171`/`173`), seeded a membership, revoked it, confirmed the
pre-fix bug was live-exploitable (a revoked user still saw 1 row via RLS);
restored that pre-fix-state database — the vulnerability restored right
along with the data; applying the remaining migrations forward correctly
closed the gap. **Live-proved a missing target role silently drops all RLS
policies**: renamed `anon`/`authenticated`/`service_role` away cluster-wide,
restored a dump taken with owner/privileges included — `pg_restore` exited
with ~4,500 individual `role "..." does not exist` errors (easy to mistake
for scrolling noise), all 603 tables and row data restored successfully
anyway, while every single RLS policy silently failed to create (0 policies
post-restore, RLS still enabled). **Live-proved the interrupted-teardown
gap**: stopped the per-table batch at 300 of 603 tables, ran only the
documented final sweep — reproduced the original `53200: out of shared
memory` failure identically (303 interdependent tables is still too many

from scratch, safe due to `IF EXISTS` idempotency) was undocumented at the

FKs (11 real pairs, e.g. `app.leads`↔`app.prospects`) held up fine against

the FK constraint, never the other table, so no true blocking cycle exists

tool exists anywhere for legal holds/revocations/suspensions (only a
