## 6. Findings and dispositions

### 6.1 Lens 2 (webhook signing/retry/replay/DLQ and idempotency) — 1 Critical + 1 High defect fixed, everything else clean

**Finding 1 — inbound signature verification fails open on a null signature
(`ISS-2026-209`, Critical).** `app.verify_third_party_provider_webhook_signature`'s own
`return v_expected = p_signature;` evaluates to SQL `NULL`, not `false`, whenever
`p_signature` is null. The caller, `app.ingest_third_party_provider_webhook_event`'s own
`if not app.verify_...(...) then <reject> end if;`, treats a `NULL` condition as
false-not-met in PL/pgSQL — the reject branch is silently skipped. Live-forced: a direct
call with `p_signature => null` — no HMAC secret known at all — inserted a real
`app.third_party_telemetry_reports` row attributed to a real, mapped vehicle,
`ingest_status = 'ok'`. `app.ingest_third_party_provider_webhook_event` is granted to
`anon`, directly reachable via Supabase PostgREST with the public anon key, entirely
bypassing `app/api/webhooks/third-party-gps/[connectionId]/route.ts`'s own app-layer
signature-presence check — the database function is the actual authoritative boundary
and it failed open. Directly violates Prompt 376 §24: "Webhook spoofing and unsigned
callbacks fail." This exact class was already fixed twice in two later, structurally
identical capabilities (`app.verify_logistics_partner_webhook_signature`, `app.verify_
finance_payment_webhook_signature`) and never backported. **Fixed** by mirroring their
own proven guard exactly (`p_signature is null or length(trim(p_signature)) = 0` →
`false`, plus a `v_expected is null` defense-in-depth check), live-force re-verified: a
null signature, an empty-string signature, and a null timestamp all now return exactly
`false`, never `NULL`. Full disposition `ISS-2026-209`.

**Finding 2 — the identical latent defect on the outbound sibling (`ISS-2026-210`,
High).** `app.verify_webhook_signature` (PLT-129) — the function ATW-226E's own comment
discloses Finding 1 was "reused verbatim" from — carries the same fail-open shape, plus
no `p_timestamp is null` guard either. Not currently live-exploitable (`service_role`-
only grant, zero live caller anywhere in this codebase today, confirmed by a full grep).
**Fixed** for consistency, same guard pattern, before any future caller wires this in as
a live inbound gate. Full disposition `ISS-2026-210`.

**Everything else in this lens held clean, live-forced, independently re-run (not merely
trusted from a prior green run):** outbound webhook HMAC-SHA256 signing and header
attachment; exponential backoff (`2^attempt_number` minutes) through 5 real forced
failures to a genuine `dead_letter` terminal state, with `app.jobs`'s own independent
backoff kept numerically aligned; the DLQ's own inspectable resurrection path
(`app.replay_webhook_delivery`, staff-only, valid only from `dead_letter`); inbound
replay defense (`provider_event_id` per-connection uniqueness) and the 5-minute
ADR-0011 stale-timestamp rejection window; duplicate-retry idempotency on both the
outbound delivery path (`app.queue_webhook_delivery` collapses a repeated call to the
existing row, no second `app.jobs` enqueue) and the inbound path (an exact-byte replay
returns `duplicate`, zero new report row).

RPC-error-code-to-HTTP-status mapping, and a genuine success path for every route.
