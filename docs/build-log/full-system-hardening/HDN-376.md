## 5. Investigation plan

Per `HARDENING_MATRIX.md` §7's own seeded dimensions and Prompt 376 §20/§24, this
checkpoint's own charter is: REST `/v1` surface compatibility (seeded `ISS-2026-147`,
zero test coverage for its 9 route handlers); GraphQL parity where promised; public/
customer/vendor API compatibility and deprecation; webhook signing/retry/replay/DLQ;
idempotency, rate limit, error shapes, pagination; schema/migration compatibility plan
(additive/expand-and-contract only).

Four independent investigation lenses, each required to live-force its own findings on a
fresh disposable database or a real running dev instance rather than accept a code read
as proof, mirroring `HDN-371`/`373`/`374`/`375`'s own already-proven methodology:

1. **REST/GraphQL contract parity** — walk the REST `/v1` surface and GraphQL schema,
   verify parity holds where the codebase promises it, and live-test actual request/
   response shapes against documented contracts.
2. **Public/customer/vendor API and deprecation** — verify API-key scope narrowing via
   `app.evaluate_permission()`, versioning/deprecation notices, and compatibility across
   supported versions.
3. **Webhook signing/retry/replay/DLQ and idempotency** — live-force signature
   verification, replay rejection, retry/backoff/DLQ behavior, and duplicate-retry
   idempotency (the codebase's own §24 business rule: "duplicate retry cannot duplicate
   transactions").
4. **Schema/migration compatibility and error-shape/pagination consistency** — verify
   every migration since Phase 0 has been additive/expand-and-contract only (no applied
   migration edited), and that error shapes/pagination are consistent across the surface.

Each lens's findings will be independently re-derived by the orchestrating session before
any fix is written, and each fix will be live-force verified on a fresh disposable
database post-fix, not merely code-reviewed.
