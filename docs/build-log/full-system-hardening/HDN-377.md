## 5. Investigation plan

Per Prompt 377 §20/§24, this checkpoint's own charter is: private storage and malware
scan gating before release to users/jobs/OCR/indexing/email; signed URL expiry,
scope-binding, revocation and replay resistance; file access audit and retention/legal
hold; tenant/RBAC/RLS enforcement on every file/document/attachment-shaped table across
every domain (Platform, Commercial, Operations, Advanced TMS/WMS, Procurement, Finance,
HRIS, Ticketing, Customer Portal/Loyalty, Intelligence/Enterprise).

Four independent investigation lenses, each required to live-force its own findings on
a fresh disposable database rather than accept a code read as proof, mirroring
`HDN-371`/`373`/`374`/`375`/`376`'s own already-proven methodology:

1. **Upload/scan/quarantine gate** — inventory every upload/download/preview/OCR/
   export/email/indexing file surface across every domain; verify the malware-scan gate
   is enforced at the DB layer (not just application code) before any such surface
   serves a file.
2. **Signed URL expiry/scope/revocation/replay resistance** — find every signed/
   download-URL-issuing surface; verify expiry, scope-binding to one object, revocation
   on access change, and that storage keys/secrets never reach the client.
3. **File access audit and retention/legal hold** — verify every file access is
   recorded in an audit/access-log table; verify retention/legal-hold mechanisms
   actually protect files and their own access logs.
4. **Cross-tenant/RLS on file-shaped tables** — verify RLS/RBAC correctly scopes every
   file-shaped table by tenant and by authorization to the parent record, across every
   domain, and that no fake-success/dead-action UI state exists for file operations.

Each lens's findings were independently re-derived by the orchestrating session before
any fix was written, and each fix was live-force verified on a fresh disposable
database post-fix, not merely code-reviewed.

## 6. Findings and dispositions

### 6.1 Lens 1 (upload/scan/quarantine gate) — 2 real defects found, everything else clean

Covered `app.files`/`app.document_types`/`app.file_access_logs` (PLT-128), the OCR
pipeline (IAE-021), ticketing attachments, customer portal document center/ePOD/quote-
requests/loyalty rewards, procurement vendor compliance/financial/assessment evidence,
HRIS employee documents, operations document-requirement checklist/ePOD capture review/
billing readiness, import/export job framework, and every Next.js route touching
`app.files`.

**Finding 1 (folds into `ISS-2026-216`/`217` below via Finding A, Medium-High as
independently found by this lens):** the HRIS employee-document page
(`app/(tenant)/[tenantSlug]/hris/employees/[masterRecordId]/page.tsx`) shipped
`app.files.storage_path` to the browser via Client Component props for every employee
document regardless of `malware_scan_status`, including `infected`/quarantined files —
the only surface in the repository doing this. Live-forced: raw `select("*")` as
non-uploader `authenticated` teammate returned `storage_path` for both `pending` and
post-`infected` states.

**Finding 2 (`ISS-2026-221`):** `app/(tenant)/[tenantSlug]/procurement/assessments/
actions.ts` called service_role-only `app.initiate_file_upload` through the RLS-scoped
client, permanently breaking vendor-assessment evidence upload for every real user
(fails closed, not open). Live-forced: `set local role authenticated; select
app.initiate_file_upload(...)` → `ERROR: permission denied for function
initiate_file_upload`.

**Clean bill of health (verified, not merely read):** core malware-scan gate
(`app.authorize_file_access`) — `pending` denies a non-uploader, grants the uploader
their own pending file; `infected` denies everyone including the uploader; `metadata_
view` correctly bypasses the scan gate. OCR ingestion gate (`app.submit_ocr_document_
job`) refuses both `pending` and `infected` files, only accepts `clean`; the OCR
pipeline never transmits file content bytes at all (metadata-only), so no bypass
surface exists via content transmission. RLS on `app.files` correctly denies all rows
to a zero-relation tenant member and correctly hides a `restricted`-classification file
from a non-uploader teammate. Ticket attachments (`app.reply_to_ticket`/`app.reply_
to_customer_ticket`) refuse `infected`/non-clean at attach time; read-time re-
verification (`app.list_customer_ticket_messages`/`app.list_ticket_messages`, hardened
at CPL-325's own `20260801320000`) live-re-checks every referenced file against current
`malware_scan_status` on every read. Customer Portal document center/ePOD/loyalty
rewards/quote requests all independently re-verify `clean` at read time, never trust
attach-time state, never expose `storage_path`. Operations document-requirement
checklist/ePOD capture review/billing readiness/device-installation evidence/claims-
incidents evidence all re-check `clean` before treating a file as usable evidence. No
email-attachment sender or search-indexing pipeline exists in this codebase (feature
absent, not a gap).

### 6.2 Lens 2 (signed URL expiry/scope/revocation/replay resistance) — 4 real defects found

No real signed/presigned URL issuance exists anywhere in this repository (confirmed by
exhaustive grep). Findings instead concentrate on the pre-signed-URL gating layer
(`app.authorize_file_access` and its downstream wrappers) that would sit in front of
real signed-URL issuance, since that layer is fully live and is exactly where "does
generating the URL require real ownership/access" and "storage keys never reach
client" are enforced today.

**Finding 1 (`ISS-2026-216`, Critical):** `app.files.storage_path` had a full `SELECT`
grant to `authenticated` with no column-level mask. Live-forced: `information_schema.
column_privileges` confirmed `storage_path` carried `SELECT` for `authenticated`
alongside all 26 other columns, in contrast to `app.users.email`, which has zero
column privileges for `authenticated` (PLT-114's own precedent for exactly this kind
of column-level masking). Root cause and fix shared with §6.3/§6.4's Lens 1/3 findings
of the same shape — see §6.5's `ISS-2026-216` entry.

**Finding 2 (concrete symptom of Finding 1):** the same HRIS page Lens 1 found,
confirmed live via the project's own `parseFile()` test suite — the full `File[]`
(storagePath included) crosses the RSC boundary into the browser payload for every HR
document.

**Finding 3 (`ISS-2026-219`, Medium):** the vendor evidence-access RPCs leak the real
`file_id`/`evidence_file_id` on a content-gate denial, contradicting their own
documented "every file-identifying field nulled out" contract. Live-forced for the
compliance variant: `access_result=denied reason=document_record_access_denied
file_id=<real uuid>` for a non-uploader, same-permission reviewer.

**Finding 4 (`ISS-2026-224`, Medium, registered):** `app.can_access_record`'s
record-scope gate denies the very "reviewer verifies evidence" workflow the vendor
evidence-access RPCs were built for — discovered incidentally while reproducing
Finding 3.

**Clean bill of health:** revocation is live/immediate, not cached — revoking a user's
tenant membership causes an immediate `file_actor_unauthorized` raise and zeroes RLS
visibility on the very next call. No endpoint accepts a client-supplied storage key/
path or trusts a client-supplied source hint; every evidence-access RPC independently
re-derives the underlying file and source scope server-side. Path traversal via
filename is structurally impossible (`storage_path` always server-generated, plus a
CHECK constraint rejecting `/`, `\`, `..` in filenames). "File links grant no
source-record access" holds for every reviewed evidence/document RPC. Cross-tenant
access correctly denied for the vendor evidence RPCs.

### 6.3 Lens 3 (file access audit and retention/legal hold) — 6 real defects found (2 fixed, 4 registered)

Confirmed `app.files` is the sole file-shaped table platform-wide (every other domain
references it polymorphically via `record_type`/`record_id`), so PLT-128 plus IAE-031's
retention/legal-hold framework (`app.retention_policies`/`app.legal_holds`/`app.
retention_archive_requests`) is the complete surface for this lens.

**Finding 1 (`ISS-2026-216`, Critical, fixed):** same storage_path exposure as §6.1/6.2
— this lens found it via `app.files` direct-table SELECT + zero audit trail (a plain
`SELECT` never inserts into `app.file_access_logs`, and `server/queries/document.ts`'s
shipped-but-unused `listFilesForTenant()` already exercises exactly this pattern).

**Finding 2 (`ISS-2026-222`, High, registered):** `app.file_access_logs` has zero
triggers; `service_role` can `UPDATE`/`DELETE` evidence rows silently — cross-references
the already-registered `HDN-BLK-018`/`ISS-2026-205` general finding, and additionally
shows a legal hold on a file does not extend to protect that file's own access-log
rows (no cascade logic exists for this at all). Given its own `HDN-BLK-019` ledger
entry rather than duplicating `HDN-BLK-018`.

**Finding 3 (`ISS-2026-217`, Critical, fixed):** two independent, non-communicating
legal-hold mechanisms for files. Live-forced both directions — see §6.5.

**Finding 4 (`ISS-2026-218`, High, fixed):** `app.files.legal_hold` enforced only
inside `app.request_file_deletion()`, no schema-level backstop. Live-forced — see
§6.5.

**Finding 5 (`ISS-2026-223`, Low, registered):** undisclosed privileged-bypass
population beyond RPD-022's Supreme Admin — ordinary `tenant_admin` silently bypasses
file classification/deletion/legal-hold gates via `app.is_support_grant_authority`'s
own misused meaning. Investigated for a same-checkpoint fix and found not
bounded-repair-sized, and not this checkpoint's own charter to decide unilaterally —
see §6.6.

**Clean bill of health:** the core malware-scan gate is unaffected by any of the above
(not separately re-tested here; already covered by Lens 1 and the shipped `document-
file.sql` suite). Filename/path-traversal safety confirmed. Versioning is genuinely
append-only (`create_file_version()` always inserts a new row, flips the prior row to
`superseded`, a partial unique index keeps `is_latest_version` exclusive).
PLT-128-native legal hold correctly blocks its own RPC path (the control case for
Finding 4 — the RPC-level check itself is correct, the gap was the missing schema-level
backstop). File-shaped table centralization is solid — no independent/duplicate
file-storage table exists anywhere else. Customer-portal document access
(`app.get_customer_document`/`app.list_customer_documents`) never projects `storage_
path`, always writes a `file_access_logs` row on the one "download" action, and
re-derives scope independently — a good counter-example showing the Finding 1 pattern
was not repeated at this layer. RBAC scaffolding around retention (IAE-031) is real
(`RET:Configure`/`RET:Approve` split, self-release-forbidden constraint verified
present, `resolve_retention_days()`'s fallback chain, `request_retention_archive()`'s
reject-before-floor logic all genuinely structural). No purge/archive job exists yet
for files at all — an honestly-disclosed absence of enforcement (nothing to live-force
breaking), not a defect requiring a named owner, mirroring `HDN-376`'s own GraphQL-
absence precedent.

### 6.5 Fixed findings — detail

**`ISS-2026-216` (Critical)** — see §1. Fixed by `revoke select on app.files from
authenticated; grant select (26-column explicit list omitting storage_path) on app.
files to authenticated;`, mirroring the `app.users`/`email` precedent
(`20260716110430_create_field_record_access.sql`'s own documented reasoning: a bare
column-level `REVOKE` cannot carve an exception out of a broader table-level `GRANT` in
Postgres — the table-level grant must be revoked entirely and re-granted on an explicit
column list). `server/queries/document.ts`'s `listFilesForTenant` and the HRIS page
both switched from `select("*")` to the identical explicit column list, returning a new
`FileSummary` contract type (`server/contracts/document/document.ts`, `FileSchema.omit
({storagePath: true})`) instead of `File`. `employee-detail-panel.tsx`'s prop type
updated to match.

**`ISS-2026-217` (Critical)** — see §1. Fixed by extending `app._is_under_legal_hold()`
with one additional OR-branch checking `app.files.legal_hold` directly whenever
`p_source_table = 'app.files'`. This single extension point closes both directions at
once: `app.request_retention_archive()` already calls `_is_under_legal_hold()`, and
`app.request_file_deletion()` was updated to also call it (kept alongside its own
existing native-flag check as defense-in-depth, not a replacement).

**`ISS-2026-218` (High)** — see §1. Fixed with `app.protect_files_legal_hold_from_
deletion()`, a narrowly-scoped `BEFORE DELETE` guard trigger mirroring `app.protect_
transaction_lineage_edges_append_only`'s own proven RPD-022 supreme-admin-bypass shape
(`HDN-375`). Fires only on `DELETE` of a `legal_hold=true` row; ordinary `UPDATE` (scan-
status transitions, versioning supersede) and soft-deletion (`deleted_at`) are entirely
unaffected.

**`ISS-2026-219` (Medium)** — see §1. Fixed by nulling `file_id` on the content-gate
denial branch in `app.access_vendor_compliance_document_evidence`, `app.access_vendor_
bank_account_evidence`, and `app.access_vendor_tax_identity_evidence`, matching the
authority-denial branch a few lines above each. The pre-existing regression for the
compliance variant already exercised this exact branch but had never asserted on
`file_id` — strengthened; a new regression added for the bank-account sibling.

**`ISS-2026-220` (Medium)** — see §1. Fixed with a new `app.check_procurement_
authority(p_action, p_tenant_id, p_actor_auth_user_id)` `SECURITY DEFINER` wrapper
(mirroring `app.check_payroll_authority`/`app.check_finance_journal_authority`'s own
proven shape, per HDN-373's own established RLS-permission-check pattern) embedded into
both `vendor_compliance_documents_select_scoped` and `rfq_response_attachments_select_
scoped`, requiring `PRC:View` — matching the bar the read-list RPCs already require.

**`ISS-2026-221` (Medium)** — see §1. Fixed by wrapping `createSupabaseServiceRoleClient
()` instead of `createSupabaseServerClient()` at both `initiateFileUpload` call sites in
`procurement/assessments/actions.ts`, mirroring `procurement/compliance/vendors/
actions.ts`'s own already-fixed pattern exactly (that file's own header comment had
already named this exact file as still carrying "the identical anon-client defect").
