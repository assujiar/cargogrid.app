## 4. Scope and methodology

Prompt 371 §20 requires exercising conversion/handoff flows for lead→quote→job,
shipment→billing, AP/AR/payment, WMS, portal, loyalty and tickets; verifying idempotent
retries and concurrent submissions at each module boundary; reconciling source totals, statuses
and ledgers; and testing rollback/correction without deleting required history.

Two complementary methods were used, deliberately, because they answer different questions:

1. **Flow reconciliation against existing evidence.** Every named chain was traced through its
   actual function bodies and cross-checked against the db-test coverage that already exercises
   it (229 files, confirmed passing at `HDN-370`'s independent full re-run). This answers "does
   the chain preserve source ownership, correct state, and no duplicate truth on the paths
   already under test."
2. **Exhaustive code-level sweep for the concurrency dimension.** Sequential idempotency
   (retry returns the original, ignores new params) is covered by 118 existing test call sites.
   Genuine two-process concurrency at each boundary is not exercised by any of them. Rather than
   spot-check a handful of functions, every function shaped like a cross-module boundary was
   enumerated mechanically and checked for the same specific pattern.

### 4.1 The sweep, exact method

Searched all 306 migration files for `create function app.` bodies matching the boundary-owner
shape `(prepare_|convert_|link_|create_.*_from_|generate_.*_from_)` — the naming convention this
codebase already uses for "take an entity from one module and hand it to another." **30
functions matched.** Of those, **19 have an idempotent-creation shape actually applicable to
this check** — i.e. they contain a `select ... into ...; if found then return ...;`
short-circuit guarding a subsequent `insert`. (The other 11 are non-idempotent by design —
pure lookups, status-transition updates like `app.link_lead_to_existing_prospect`, or append-only
event writers — and are not part of this defect class; each was read directly to confirm, not
assumed from its name.)

Each of the 19 was checked for exactly one thing: is the `insert` that follows the
short-circuit wrapped in `begin ... exception when unique_violation then <re-select and return
the winner> end`, so that a genuine race between two callers resolves gracefully instead of
surfacing a raw database error to the loser? **12 have it. 7 do not.**

### 4.2 The reference pattern already in this codebase

`app.prepare_wms_outbound_from_shipment`
(`supabase/migrations/20260730230000_create_advanced_tms_wms_outbound_order.sql`, lines
287-377) is the correct shape, and documents itself as such:

> *"Design note 9(a): a nested begin/exception unique_violation recovery — a genuine race
> between the select above and this insert (two concurrent callers both prepare from the same
> shipment order) is resolved by re-selecting and returning the winner, never a raised error on
> a legitimate concurrent retry."*

```sql
begin
  insert into app.wms_outbound_orders (...) returning * into v_order;
exception
  when unique_violation then
    select * into v_existing from app.wms_outbound_orders where ...;
    if found then
      return v_existing;
    end if;
    raise;
end;
```

This is not a theoretical fix. It is a working pattern already proven in this exact codebase,
in the same migration family, for the same class of boundary function.

## 6. The empirical-race attempt, and why this finding rests on code verification instead

Prompt 371 §20 asks to "verify idempotent retries and concurrent submissions." A genuine
two-process race against `app.prepare_finance_invoice_from_readiness` was attempted directly,
using two concurrent `psql` sessions against a disposable probe database
(`cargogrid_hdn371`), before falling back to code-level verification. Recorded honestly rather
than silently dropped:

- **First attempt** (`pg_sleep(0.3 + random()*0.1)` jitter before each call in two background
  `psql` processes): both processes returned the **identical** invoice with an identical
  `created_at`. The ~100ms jitter window is orders of magnitude larger than the function's
  actual `select`-then-`insert` critical section, so one call's whole execution completed
  before the other's sleep even elapsed — **inconclusive**, not evidence of safety.
- **Second attempt**, forcing deterministic interleaving via named-pipe (FIFO) orchestration
  across two backgrounded `psql` sessions reading from `mkfifo`-created files, so each session's
  next statement could be released on command from the orchestrating shell: hung for the full
  timeout on the first pass (`exec 6>$FIFO` was opened for writing before the reader `psql <
  $FIFO` was started — a FIFO write-open blocks until a reader attaches, and the reader was
  scheduled after the writer in the script). Reordered so readers start first; the reorder
  itself was confirmed correct with an isolated 5-second smoke test, but the fuller sequenced
  script then hit a second, unrelated tooling problem — `pkill -f "psql.*cargogrid_hdn371"`
  matched against the **full command line** of the calling shell's own tool wrapper (which
  itself contained a `cargogrid_hdn371` substring from earlier embedded SQL), so the cleanup
  step killed its own orchestrating process rather than only stray `psql` children. Diagnosed
  via `ps aux` (no real stray processes existed) and fixed by abandoning broad `pkill -f`
  patterns in favour of direct `DROP DATABASE` cleanup — but by this point the FIFO harness had
  not produced a clean forced-interleaving result either.

**Judgment call, made explicitly rather than silently:** the fact this lane needed to prove —
*no exception handler exists around this specific `insert`* — is deterministic and verifiable
by direct code read; it does not require a timing-precise empirical race to establish, unlike a
claim about the exact probability of the race firing under production load (which this lane
does **not** claim). Continuing to fight fragile shell/FIFO mechanics for a literal forced race
was lower value than completing the systematic 30-function sweep, so the session pivoted to
code-level verification — confirmed by reading each of the 7 functions' bodies directly and
cross-checking each target table's `pg_constraint` entries for a backing unique index — and
disclosed the empirical attempt as inconclusive rather than claiming it as either proof of a
defect or proof of safety. This disclosure is carried into `HARDENING_MATRIX.md` §2's own
"Concurrent submission" row rather than left only here.
