## 4. Scope and methodology

Prompt 371 §20 requires exercising conversion/handoff flows for lead→quote→job,
shipment→billing, AP/AR/payment, WMS, portal, loyalty and tickets; verifying idempotent
retries and concurrent submissions at each module boundary; reconciling source totals, statuses
and ledgers; and testing rollback/correction without deleting required history.

Two complementary methods were used, deliberately, because they answer different questions:

1. **Flow reconciliation against existing evidence.** Every named chain was traced through its
   actual function bodies and cross-checked against the db-test coverage that already exercises
   it (229 files, confirmed passing at `HDN-370`'s independent full re-run). This answers "does
   the chain preserve source ownership, correct state, and no duplicate truth on the paths
   already under test."
2. **Exhaustive code-level sweep for the concurrency dimension.** Sequential idempotency
   (retry returns the original, ignores new params) is covered by 118 existing test call sites.
   Genuine two-process concurrency at each boundary is not exercised by any of them. Rather than
   spot-check a handful of functions, every function shaped like a cross-module boundary was
   enumerated mechanically and checked for the same specific pattern.

### 4.1 The sweep, exact method — corrected at Tier C review

Searched all 306 migration files for `create function app.` bodies matching the boundary-owner
shape `(prepare_|convert_|link_|create_.*_from_|generate_.*_from_)`. **This regex is blind to
`create or replace function` redefinitions.** All four Tier C review lenses independently
re-ran the sweep against a redefinition-aware extraction (each function resolved to its
*effective*, last-applied body) and converged on corrected counts: **32 functions match** the
naming shape (not 30), of which **20 have an idempotent-creation shape** (not 19) — a
`select ... into ...; if found then return ...;` short-circuit guarding a subsequent `insert`.
(The remaining 12 are non-idempotent by design — pure lookups, status-transition updates, or
append-only event writers — confirmed by direct read, not assumed from name.)

Each of the 20 was checked for one thing: is the `insert` that follows the short-circuit
wrapped in `begin ... exception when unique_violation then <re-select and return the winner>
end`? **11 have it. 9 do not** — two more than this checkpoint's own original sweep found,
corrected below (§7).

The original 30/19/12/7 figures were not merely under-inclusive by coincidence: because the
regex matches only `create function`, every function later touched by a hardening migration
(`create or replace function`) was evaluated against its **superseded** body, not the one the
database actually runs. Five of the seven originally-registered functions fall into this
category (§7). The *conclusion* — that these functions lack the handler — survives, because
none of the redefinitions added one (re-verified directly against the live/effective bodies,
including a live database rebuild and forced two-process race, §6) — but the citations, file
counts and severity-bounding constraint names in the original text were wrong, and are
corrected throughout this document.

### 4.2 The reference pattern already in this codebase

`app.prepare_wms_outbound_from_shipment`
(`supabase/migrations/20260730230000_create_advanced_tms_wms_outbound_order.sql`, function body
lines 287-372, design-note comment 374-375 — corrected from an original "287-377" citation that
overshot into the next function, `app.create_manual_wms_outbound_order`, starting at 377) is the
correct shape, and documents itself as such:

> *"Design note 9(a): a nested begin/exception unique_violation recovery — a genuine race
> between the select above and this insert (two concurrent callers both prepare from the same
> shipment order) is resolved by re-selecting and returning the winner, never a raised error on
> a legitimate concurrent retry."*

```sql
begin
  insert into app.wms_outbound_orders (...) returning * into v_order;
exception
  when unique_violation then
    select * into v_existing from app.wms_outbound_orders where ...;
    if found then
      return v_existing;
    end if;
    raise;
end;
```

This is not a theoretical fix. It is a working pattern already proven in this exact codebase,
in the same migration family, for the same class of boundary function.

## 6. The empirical race — first-pass failures, then a real forced-and-confirmed proof at Tier C review

Prompt 371 §20 asks to "verify idempotent retries and concurrent submissions." This section's
original text disclosed two failed attempts and a pivot to code-only verification. **Tier C
review found a materially simpler technique that works, used it to force and confirm a real
two-process race, and the corrected section below records both the original honest failures
and the successful proof that followed.**

### 6.1 The original attempts (unchanged from first submission, kept for the record)

- **First attempt** (`pg_sleep(0.3 + random()*0.1)` jitter before each call in two background
  `psql` processes, against `app.prepare_finance_invoice_from_readiness`): both processes
  returned the **identical** invoice with an identical `created_at`. The ~100ms jitter window is
  orders of magnitude larger than the function's actual `select`-then-`insert` critical section,
  so one call's whole execution completed before the other's sleep even elapsed —
  **inconclusive**, not evidence of safety.
- **Second attempt**, forcing deterministic interleaving via named-pipe (FIFO) orchestration:
  hung on a write-before-reader FIFO-open ordering bug, then hit a `pkill -f
  "psql.*cargogrid_hdn371"` pattern that matched and killed the calling shell wrapper's own
  command line (which itself contained a matching substring from earlier embedded SQL) rather
  than only stray `psql` processes. Diagnosed via `ps aux` (no real stray processes existed);
  fixed by abandoning broad `pkill -f` patterns for direct `DROP DATABASE` cleanup — but the
  FIFO harness itself never produced a clean forced interleave.

### 6.2 The technique that works — an uncommitted conflicting insert, no timing precision required

Independently found by two of the four Tier C review lenses (and reproduced by the
orchestrating session itself, §6.3): hold an **uncommitted** conflicting row open in one
session, then call the target function from a second session. The second session's own
idempotency short-circuit runs first and correctly sees nothing (the first session's row is not
yet committed, hence invisible under READ COMMITTED); the second session's `insert` then
**blocks** on the first session's uncommitted unique-index entry — a real lock wait, not a
timing guess. When the first session commits, Postgres resolves the block deterministically: the
second session's `insert` raises `unique_violation` if unhandled, or is silently absorbed if a
`begin...exception when unique_violation` block is present. No `pg_sleep` jitter, no FIFO, no
`pkill`, no advisory lock — ordering is enforced by the database's own lock semantics, which is
why it is deterministic where the FIFO approach was not. Synchronization between the two shell
processes uses a plain marker-file busy-wait (`\! while [ ! -f marker ]; do sleep 0.05; done`)
inside the second session's own `psql` script, avoiding both of §6.1's failure modes.

### 6.3 Forced and confirmed, live, by the orchestrating session

Run directly against `app.link_auth_identity` (one of the two functions added to `HDN-BLK-010`
at this Tier C review, §7) on a disposable probe database built from all 306 migrations:

- Session A: `begin; insert into app.tenant_user_identities (auth_user_id, tenant_id, status,
  invited_by) values ('11111111-…', '22222222-…', 'invited', 'racer-A'); \! touch
  <marker>; select pg_sleep(3); commit;`
- Session B: `\! while [ ! -f <marker> ]; do sleep 0.05; done; select
  app.link_auth_identity('11111111-…', '22222222-…', 'racer-B');`

Observed, verbatim:

**This is real, observed, forced-race evidence, not a code inference** — obtained independently

**Scope of the claim, stated precisely rather than overreaching:** this proof was run against
one representative function (`link_auth_identity`) sharing the exact missing-handler mechanism
as the other 8 members of `HDN-BLK-010`. It is not re-run against all 9 — the mechanism is
identical and mechanically verified by direct code read for the other 8 (§7), and one forced,
observed race is sufficient to retire the "is this reachable at all" question the original §6
left as a code-only inference. The probe database (`cargogrid_hdn371v`) was dropped via `DROP
DATABASE` immediately after.

### 7.1 `ISS-2026-163` — `app.prepare_job_order`'s exception handler can silently return an all-NULL row

A **new, separate, pre-existing production-code finding**, discovered while verifying the "12
safe functions" claim (now 11) is not cherry-picked. `app.prepare_job_order`
(`supabase/migrations/20260728190000_harden_operations_security_financial.sql:122`) is one of
the functions with the race-safe pattern — but its handler is defective:

```sql
exception
  when unique_violation then
    select * into v_job_order from app.job_orders
      where tenant_id = v_handoff.tenant_id and source_handoff_id = p_source_handoff_id;
    return v_job_order;
end;
```

Unlike the reference shape (§4.2), this has **no `if found` guard and no `raise;`**.
`app.job_orders` carries a *second* unique constraint, `job_orders_tenant_number_unique` on
`(tenant_id, job_number)` (`20260727090000_create_operations_job_order.sql:90`). A
`unique_violation` from that constraint — or any case where the re-select genuinely finds
nothing — is silently converted into a `return` of an all-NULL `app.job_orders` composite
instead of a raised error. **Severity: Low.** Reachability is narrow: `next_job_order_number`
uses an atomic, non-recycling upsert, so a `job_number` collision is not currently plausible in
normal operation — this is a defensive-shape defect, not a currently-firing one. Not fixed in
this audit lane (per `AGENTS.md`'s "fix only task-caused failures" — this is pre-existing
production code, not this checkpoint's own diff). **Owner: `HDN-374`**, alongside `HDN-BLK-010`
— same function family, same fix session is the natural place to add the missing `if found`/
`raise;` guard.
