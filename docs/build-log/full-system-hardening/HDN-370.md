## 5. `HDN-BLK-002` — root-caused, not accepted from the issue text

`RECURRING_DEFECT_TAXONOMY.md` §5 is explicit that an unverified finding is not a defect and
must be re-derived. `ISS-2026-077`'s own entry says the same about itself: *"a future
maintainer diagnosing this should force `current_date` … rather than assume a clean `db:test`
run means this is resolved."* Both were followed — a persistent, fully-migrated probe database
was built and every claim below was measured against it.

### 5.1 `ISS-2026-077` — the registered root cause was wrong

**Registered hypothesis:** the negative-control employee `emp3` is never given a
`app.schedule_assignments` row, and the scenario is coupled to
`app.set_schedule_coverage_requirement(..., extract(dow from current_date), ...)`.

**Measured reality:** late-exception detection
(`20260730940000_bind_hris_leave_to_attendance_exceptions.sql`) does **not** read
`schedule_assignments` at all. It computes:

```
v_workday_start := (work_date || ' ' || policy.workday_start_time) at time zone policy.timezone
v_late_minutes  := effective_clock_in_at - (v_workday_start + grace)
```

Live values on the probe database, for tenant `lv1`:

```
policy: timezone=Asia/Jakarta  workday_start_time=00:00:01
        day_boundary_local_time=00:00:00  grace_late_minutes=0
emp3:   work_date=2026-08-23  clock_in=2026-08-23 12:12:53+00  late exceptions=1
emp3's only approved leave: 2024-06-01 (a fixed past literal — can never suppress "today")
```

So the assertion is structurally sound and has **no** day-of-week term. The real coupling is
elsewhere and simpler:

```
show timezone  ->  Etc/UTC
```

`current_date` is therefore the **UTC** date, while `work_date` is the **Asia/Jakarta** date.
The fixture seeds schedules, leave and clock-ins on `current_date`, then asserts
`where s.work_date = current_date`. Measured across a full week at 15-minute granularity:

```
instants swept ............................ 672   (7 days, all 7 weekdays)
mismatches under the old behaviour ........ 196   <- 29.2% of all instants
                                                     = exactly 7 hours every single day
```

From 17:00 UTC the Jakarta date is already tomorrow, the join matches nothing, and the
negative control reports **"found 0"** — the exact registered failure string. This explains
every observation on file without contradiction: failing 2026-08-13, passing 2026-08-14, and
Phase 9's pass→fail flip *partway through one session* on 2026-08-22.

**Fix (root, not assertion):** align the fixture's own notion of "today" with the timezone the
code under test resolves work days in — `set timezone = 'Asia/Jakarta';` at the top of the
file. `run.sh` gives every test file its own psql session, so the setting cannot leak.

### 5.2 `ISS-2026-154` — confirmed as registered, fixed at the policy

The registered root cause was already precise and is confirmed: the block backdated a manual
HR entry by a bare `now() - interval '1 hour'` while the tenant's shift day starts at
**04:00 Asia/Jakarta (21:00 UTC)**, so inside the hour after each boundary crossing "now" and
"an hour ago" resolve to two different, correctly-computed work days and
`duplicate_workday_session` legitimately does not fire.

**Fix:** read the policy and clamp, instead of assuming an hour is safe:

```sql
v_workday    := app.resolve_attendance_workday(now(), v_policy.timezone, v_policy.day_boundary_local_time);
v_shift_start:= (v_workday || ' ' || v_policy.day_boundary_local_time) at time zone v_policy.timezone;
v_manual_at  := greatest(now() - interval '1 hour', v_shift_start);
```

The policy is **read, not hardcoded**, so the fixture stays correct if its timezone or boundary
is ever changed. The block also now asserts its own invariant explicitly, so a future
regression fails with *"fixture invariant broken"* rather than as a confusing behavioural
mismatch.

### 5.3 `ISS-2026-135` — misclassified; a hardcoded date, on a Tuesday

The roster fixture contains exactly **one** date-relative expression, and it is already pinned
to a literal (`extract(dow from '2026-08-18'::date)`). `git log --follow` confirms the file has
not been touched since Prompt 295 — i.e. **before** `ISS-2026-135` was registered — so no
intervening fix could explain it.

The real mechanism: emp3 is given `bulk_generated` roster assignments on the hardcoded literal
dates `2026-08-17` and `2026-08-18`, and the negative control then asserts
`schedule_assignment_id IS NULL` for the *real wall-clock* work day. Swept over 30 candidate
dates against live fixture state:

```
dates swept ............................... 30
dates where the OLD assertion would fail ... 1   -> 2026-08-18  (a Tuesday)
dates where the NEW assertion can fail ..... 0
```

It is a **time bomb, not a flake** — and "it is in the past now" is not a fix, because it
re-arms the moment anyone refreshes the fixture's literal dates forward, which is ordinary
maintenance.

**Fix:** derive the expectation from real state instead of assuming it, and assert in **both**
directions — when no published assignment exists for the session's work day the link must be
null; when one does exist the session must link to exactly it. The property genuinely under
test (decision 9: a clock-in never fabricates a roster link and never errors without one) is
now stronger than before and true on every calendar date.

### 5.4 Class containment sweep

The same coupling was swept for across all 229 files, so the class is closed rather than three
instances patched:

- `work_date = current_date` (the `ISS-2026-077` shape): **1 file**, now fixed.
- Files touching `attendance_sessions` **and** `current_date`/`now()`: 5. Of the two not
  already covered, `hris-overtime-timesheet.sql` overwrites `work_date` explicitly (so both
  sides move together) and `hris-payroll.sql` pins every `work_date` to literals. **Neither is
  exposed.**

### 9.1 Why this is the finding, not a footnote

The `quality` job orders `Test` **before** its governance steps. When `Test` exits non-zero,
these seven report `skipped` and have therefore **never executed in CI**:

1. Suppression governance check
2. Documentation checks
3. **Secret scan**
4. **Dependency vulnerability audit** (the gate that fails on critical/high)
5. Data-classification registry check
6. Threat-model register check
7. Protected-path check

Two are security controls. `ISS-2026-007` recorded this exact failure shape one level down — a
silently-broken `pnpm audit` hid **20 real advisories, 11 high**, for a whole phase — and the
remediation was a gate that fails when the advisory service is unreachable. **That gate now
exists and never runs.**

Nine phases missed it because every gate result in this repository's build logs came from a
**local** run, where the same test passes precisely because a feature branch genuinely *is*
ahead of `origin/main`. Local and CI outcomes here are inverses, so a green local run carries
no information about CI. `HDN-369`'s own build log called this failure "resolves once this
checkpoint's commit lands" — true locally, and never true in CI. **Corrected in this lane's
own record rather than left standing.**
