### 6.1 Lens 1 — `HDN-BLK-014` candidate verification

Of the ~30 candidates carried forward from `HDN-372`, 25 were confirmed genuinely
exploitable via live-forced or code-verified evidence (7 High — full record disclosure:
`find_duplicate_accounts/contacts/leads/prospects`, `find_existing_accounts_for_lead/
prospect`, `resolve_warehouse_location_by_barcode`; the rest Medium boolean/readiness
oracles). Before fixing, every candidate's actual call sites were grepped — 16 confirmed
terminal/self-referential (the actor parameter is never mutated or substituted before
reaching any downstream call) and fixed at
`supabase/migrations/20260810400000_harden_crm_ops_actor_identity_gaps.sql` (773 lines,
one `perform app.assert_actor_is_session_identity(...)` inserted per function, bodies
otherwise byte-identical, verified via `pg_get_functiondef` diff). The remaining ~14
(`has_active_tenant_membership`, `can_access_record`, `is_supreme_admin`,

`p_target_auth_user_id`) — an unconditional assert would break every one of those
legitimate uses. **Not fixed** — re-registered as `ISS-2026-186`, needing a per-call-site

### 6.5 Fix — `ISS-2026-180`, the tenant-membership evaluator gap

`supabase/migrations/20260810300000_harden_rbac_evaluator_tenant_membership_check.sql`.
`app.evaluate_permission` now requires `app.has_active_tenant_membership(p_tenant_id,
p_auth_user_id)` before any role-grant path can return `allowed=true`, denying with a new
`not_active_tenant_member` reason otherwise — placed before the Supreme Admin branch
(harmless, since `has_active_tenant_membership` already composes it) and before the
role-assignment lookup (the actual fix). Self-caught regression, fixed in the same
migration before it ever reached a committed state: `evaluate_permission` is itself
`SECURITY INVOKER`, granted only to `service_role` (a genuine direct-call path, not only
reached via nested `SECURITY DEFINER` callers — `rbac-enforcement.sql:278-289`'s own
pre-existing "defense in depth" test proves it). The new internal call to
`has_active_tenant_membership` needed its own `service_role` grant, since Postgres checks
`EXECUTE` at the call site before the security context switches; live-confirmed broken
(`permission denied for function has_active_tenant_membership` from a `begin; set local
role service_role; ...` probe) before the grant, fixed after. This is the identical class
of gap §6.6 below found at much larger scale across the Finance domain — caught here, in
one function, before it ever reached a commit.

### 6.6 Fix — `ISS-2026-182`/`HDN-BLK-015`, `183`, `184`, `181`: the Finance authority chain

**Discovery.** Live-testing `app.create_finance_journal_draft` as a genuine, non-superuser
Finance Manager session (not the db-tests suite's own superuser-run fixtures, which bypass
every grant this finding is about) failed with `permission denied for table permissions`,
three frames inside `app.evaluate_permission`. Root cause, established by live
experimentation on disposable databases rather than assumed: 76 top-level Finance/
generic-job RPCs, each already carrying a real, deliberate `authenticated` grant, are
`SECURITY INVOKER` (Postgres' implicit default) instead of `SECURITY DEFINER` like this
schema's other 1,878 RPCs. Because Postgres checks `EXECUTE` at the call site against
whatever role is currently active — switching to a `SECURITY DEFINER` callee's owner only
AFTER that check passes — every nested call inside an `INVOKER` chain (helper authority
checks, `evaluate_permission` itself, the table `INSERT`/`UPDATE`) keeps executing as
`authenticated`, which by this schema's own consistent design holds no grant on
`app.permissions`, the Finance authority-check helpers, or DML on `app.finance_journals`
and its siblings.

**Fix design, proven before being applied at scale.** A first draft proposed granting the
~43 missing intermediate helpers directly to `authenticated`. Live-tested and abandoned:
it would have left each outer entry point's own table `INSERT`/`UPDATE` still failing
(still `INVOKER`), and permanently exposed `evaluate_permission` itself to direct
`authenticated` calls, contradicting the pre-existing "defense in depth" test. A single
`SECURITY DEFINER` conversion on `create_finance_journal_draft` alone, with nothing else
touched, was tested next and worked end to end — confirming that one boundary at the true
entry point is both necessary and sufficient; every nested call beneath it then executes
as that entry point's owner. The 19 `app.check_finance_*_authority` helpers are converted
too, for a distinct reason: `ISS-2026-184`'s RLS-embedded read gate always executes as the
querying role (never nested), so it independently needs its own `SECURITY DEFINER`
boundary, exactly mirroring this schema's own already-shipped precedent
(`check_payroll_authority`/`check_training_authority`).

**Fixed** at `supabase/migrations/20260810700000_harden_finance_authority_chain_security_definer.sql`
(95 functions, `SECURITY DEFINER SET search_path TO 'app', 'pg_temp'` added, no other line
touched — generated mechanically from live `pg_get_functiondef` output via one `replace()`
call, diffed byte-identical elsewhere against the pre-change catalogue) and
`supabase/migrations/20260810800000_harden_finance_journal_view_gate_and_self_approval.sql`
(`ISS-2026-184`'s `FIN:View` RLS gate, mirroring `payroll_periods_select_scoped` exactly,
plus its own self-caught grant gap on `check_finance_journal_authority`; `ISS-2026-181`'s
self-approval guard — additive `submitted_by_auth_user_id uuid` column, both
`approve_finance_journal`/`post_finance_journal` deny an actor acting on its own
submission).

**`ISS-2026-183` (unchecked system-journal posting), found by the fix's own verification,
not by any lens.** Restoring reachability tripped `rbac-enforcement.sql`'s own pre-existing
ATW-032 sweep against `app.create_and_post_finance_system_journal`: independently
`authenticated`-granted across 4 migrations, with no authority check of its own (its
header comment's "authority checked upstream" was true only while unreachable by any other
path). Fixed in the same `20260810700000` migration, adding the same `FIN:Approve` gate
its sibling `post_finance_journal` already independently re-checks.

**Verification.** Live-forced before/after on disposable databases at every step
(pre-fix failure reproduced; single-function proof; full 95-function batch applied and
diffed). Fixing the self-approval guard broke 4 pre-existing Finance test files' own
setup fixtures, which used a single actor for the full draft→post lifecycle — each
corrected to use a second, genuinely distinct `FIN:Approve` holder (the existing `admina`
identity, granted the same role), not worked around. `finance-journal.sql` gained two new
regression blocks: a genuine deny-then-allow self-approval proof, and a live
authenticated-session `FIN:View` RLS proof (a zero-permission tenant member denied,
where before the fix they would have read every row). The full 229-file
`scripts/db-tests` suite, run against a fresh database with real grants (no superuser
bypass), passes clean after every fix in this checkpoint landed together — §12.
