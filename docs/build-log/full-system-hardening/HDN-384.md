**Sandbox constraint confirmed tighter than previously documented.** No Docker daemon exists at all in this session (`docker ps` fails with "no such file or directory" — no socket, a step further than `HDN-380`'s own reproducible `runc`/`RLIMIT_NOFILE` error). **Data corruption and security incident scenarios were live-rehearsed**, not merely tabletop-discussed. The data-corruption drill found and fixed a real defect in `database-restore.md`'s own composed in-place restore procedure (§4 item 4): following it literally produced 80 silently-ignored `pg_restore` errors from two causes — migration-seeded reference-table PK collisions, and a real parallel-restore FK race under `-j 4`. Fixed live with a `TRUNCATE` step plus `--disable-triggers`, re-verified with 0 errors. `ISS-2026-254` (security-state reversion on restore) was independently reconfirmed against this second, distinct restore procedure. The security-incident drill live-executed a full diagnose→revoke→confirm-lockout chain, the first real rehearsal-history entry for `docs/runbooks/incident-response.md` itself.

**Major outage and provider failure remain tabletop-only**, disclosed per Prompt 384 §22's own alternative flow — this sandbox has nothing to fail over to or restart (no second infrastructure vendor exists in CargoGrid's own architecture either — a real, registered finding, see §6).

Authored `docs/runbooks/disaster-recovery.md` (new) — the primary deliverable, synthesizing all 3 lenses. `docs/runbooks/database-restore.md` was updated in place (§4 item 4 fixed, §7/§8 updated, template version `0.2.0` → `0.3.0`) since this checkpoint's own live drill found a real defect in a procedure that runbook already claimed was proven. **6 new findings registered, not fixed, each with a named owner.** No Critical finding anywhere.

## 4. Investigation (3 parallel lenses)

**Lens 1 — scenario definition + feasibility.** Independently re-verified the sandbox constraint (no Docker, no Supabase CLI, no reachable local Supabase services). Defined all 4 scenarios concretely for CargoGrid's real architecture with measurable success criteria. Feasibility assessment: data corruption is live-executable (pure Postgres mechanics, already proven at `HDN-383`); security incident is *substantially* live-executable (5 real `app.*` RPCs, not merely "partially" as the charter's own framing hedges); major outage and provider failure are tabletop-only (nothing to fail over to in this sandbox, or in CargoGrid's own single-vendor architecture). Found `app.record_dr_restore_test`'s `component_scope` enum has no slot for 3 of the 4 scenarios (`ISS-2026-260`). Fully documented `IAE-035`'s actual scope: evidence-recording (`app.dr_restore_tests`), contract metadata (`app.support_entitlements`), and a live-recomputed readiness checklist (`app.enterprise_onboarding_checklists`) — no automated DR test execution, no scenario-specific mechanism.

**Lens 2 — live DR rehearsal execution** (first attempt interrupted mid-drill by a connection error; relaunched fresh, completed). Built a disposable database, seeded 2 tenants/4 users/1 API key/40 leads. Took a T0 backup, then post-T0 security-state actions (revoked an API key, suspended a user, placed a legal hold — one via `select (fn()).*`, a real test-script gotcha that re-invokes a composite-returning function once per return column, creating 14 duplicate hold rows instead of 1; noted, not a code defect). Simulated corruption via `DELETE FROM app.leads;` (no `WHERE`). Confirmed `app.audit_logs` has zero rows for the corrupting statement (`ISS-2026-259`). Recovery via the composed in-place procedure failed first (80 silent errors), fixed live (`TRUNCATE` + `--disable-triggers`), 0 errors on re-run, RTO ≈49.65s, RPO window 4m38s. Post-recovery verification (roles/`pg_policies` count/cross-tenant RLS probe) all correct. All 3 post-T0 security-state actions confirmed silently reverted (`ISS-2026-254` reconfirmed). Also live-executed a security-incident revoke chain (`app.revoke_all_actor_sessions`/`app.revoke_role_assignment`/`app.revoke_ip_allowlist_entry`), lockout re-confirmed via a fresh `app.evaluate_permission` call. Flagged an unreproduced anomaly in `app.transition_user_status` (2 failed calls, then a 3rd identical call succeeded) — `ISS-2026-263`.

**Lens 3 — communication/ownership/enterprise-DR-controls.** Read all 12 `docs/runbooks/` files: every Communication section is "notify DevOps/Security lead," no channel/template/order. `docs/architecture/11_DEVOPS_WORKSTREAM.md` §8.4's own incident/communication contract is designed but never built. Confirmed IAE-030's incident schema (`app.raise_observability_alert`/`app.incidents`/`app.alert_routes`) is scoped to `job`/`webhook`/`api`/`integration`/`ai` sources only, no `infrastructure`/`provider`/`security` category, no live escalation dispatch (`ISS-2026-251`, already open, reconfirmed), no UI (`HDN-BLK-028`, already open). Confirmed zero customer-impact-assessment mechanism exists anywhere (broad search, zero hits) — `ISS-2026-258`. Wrote 2 tabletop walkthroughs (major outage, provider failure), both going cold at the same 2 points: no ownership/paging mechanism, no communication tool. Found `11_DEVOPS_WORKSTREAM.md` §8.5's own runbook catalogue names 6 files that don't exist under those names — `ISS-2026-262`.
