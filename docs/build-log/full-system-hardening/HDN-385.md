## 4. Investigation (3 parallel lenses)

**Lens 1 — migration/import framework inventory + feasibility.** Corrected the Phase-5 misattribution to Phase 1/`PLT-131`. Full inventory of all 17 core framework functions and the 4 real domain adapters (`vendor_rate_import`, `employee_import`, `attendance_device_import`, `timesheet_import`) — no fifth exists anywhere. Found duplicate-handling is materially inconsistent across the 4 adapters: `vendor_rate_import`'s own already-fixed pattern (discriminate by constraint name); `employee_import`'s identical, unfixed defect; a third pattern in `attendance_device_import`/`timesheet_import` (per-row invalid-flag rather than silent skip). Confirmed zero master-data or tenant-setup import mechanism exists (`PLT-120.md` self-discloses this was disclosed `NOT_RUN` and never retrofitted). Confirmed the financial opening-balance mechanism is structurally disconnected from the import framework, and `FIN-202.md` self-discloses the GL-journal gap. Confirmed the migration-seeded-PK-collision risk `HDN-384` forward-linked does not transfer as feared (every write-path table uses `gen_random_uuid()`), but a structurally analogous risk exists for natural-key-PK'd reference tables with no import RPC at all. Confirmed no migration-rehearsal tracking mechanism exists (mirrors `ISS-2026-258`'s shape).

**Lens 2 — live migration rehearsal execution.** Built a disposable database (43.146s, 329 migrations, 0 errors). Ran the full `employee_import` pipeline live: 2 tenants, roles, org units, a 7-row staged batch (3 valid/1 duplicate/1 formula-injection/2 missing-field), preview, validation, partial commit. Confirmed the duplicate-swallowing defect live (a duplicate `employee_number` reported `status=completed` with only 1 of 2 rows written, no error). Found a MORE severe, related defect: re-running an un-keyed row in a fresh job created an outright duplicate employee record with zero detection at all, since `app.employee_duplicate_candidates` is never populated by any commit path. Live-reproduced the reference-table PK-collision risk on `finance_currencies`/`uoms` — a raw insert collision rolls back an entire batch, no safe RPC exists. Live-tested the financial opening-balance single-record path: genuinely idempotent, reconciled exactly at the open-items level, confirmed 0 rows in `app.finance_subledger_batches` (the disclosed GL gap, confirmed not assumed). Live-tested manual rollback: mechanically clean (60.99ms) but left 2 residues (dangling audit-log reference, burned employee-number-counter value).

**Lens 3 — financial reconciliation + business-rules review.** Confirmed no opening-balance concept exists in Finance's own schema (Inventory has one via `movement_type`, Finance does not). Confirmed `app.validate_finance_journal_line_balance()` is RPC-layer-only, never a table constraint. Confirmed the one real reconciliation RPC (`FIN-209`) is AR/AP-vs-GL-control-account scoped only, not a general trial balance, and not wired to any import path. Confirmed zero duplicate-detection logic in the generic import framework itself (the only real duplicate-detection code, CRM's `find_duplicate_accounts`/`find_duplicate_leads`, is advisory-only and architecturally disconnected from import). Confirmed the import framework never writes to any canonical table by its own design disclosure, so legal/audit-history preservation is currently untestable (moot until a domain adapter exists) but structurally unaddressed. Confirmed `app._is_under_legal_hold()` is a single-call-site function, not a generic write guard. Confirmed no import RPC carries any MFA/elevated-authorization gate, unlike the 4 functions `HDN-378` specifically hardened for this risk class. **The most significant cross-checked finding**: read `finance_journals_protect_posted`'s own exact trigger definition — `BEFORE UPDATE OR DELETE`, never `INSERT` — meaning a migration-realistic direct `service_role` bulk insert of an already-`'posted'`, unbalanced, source-less journal is completely unguarded at the database layer, the identical root cause as `HDN-384`'s own `ISS-2026-265` (`TRUNCATE` bypass), reached via `INSERT` instead.
