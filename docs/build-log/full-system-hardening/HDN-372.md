## 4. Scope and methodology

Prompt 372 §20 requires: building Tenant A/B fixtures across all modules; running direct
database/RLS, service, API, job, report, export, cache and file negative tests; testing
support/impersonation, API clients, AI jobs, webhooks and integrations for tenant
leakage; inspecting logs/monitoring/audit/report artifacts for cross-tenant exposure; and
blocking release on any critical/high isolation failure.

Given the breadth of this charter, four independent parallel investigations ran
simultaneously, each building its own disposable Postgres database from all 306
migrations and each live-testing with a genuine two-tenant fixture:

1. **DB/RLS/grants surface** — whole-schema RLS/grant posture sweep, policy-predicate
   correctness census, function call-graph closure analysis.
2. **API/service layer** — every Next.js route handler and `"use server"` action; where
   does the acting tenant/identity actually come from.
3. **Storage/signed URLs, jobs/queue, cache, reports/exports** — the surfaces Prompt 372
   §20/§24 name explicitly beyond the database/API core.
4. **Support/impersonation, AI/automation, webhooks/integrations, audit/monitoring
   logs** — the remaining named surfaces.

### 4.1 Methodology lesson, disclosed rather than hidden

The orchestrating session's own first manual attack attempt against
`app.list_api_keys_for_tenant` (before delegating the four investigations) produced a
**false positive**: `set local role authenticated; set local request.jwt.claims = '...'`
issued **outside** an explicit `begin`/`rollback` silently no-ops in Postgres (psql warns
"SET LOCAL can only be used in transaction blocks" but the script continues executing as
the original superuser role) — the "successful" cross-tenant read was actually a
superuser session bypassing everything, not a real vulnerability. Caught before being
reported, by verifying `current_user` genuinely showed `authenticated` on a retry
properly wrapped in `begin ... rollback;`, which correctly showed the function protected
(`actor_identity_mismatch`). **Every one of the four parallel investigations was briefed
on this exact failure mode up front** and every live-tested finding below verifies
`select current_user` = `authenticated` before trusting a result.

### 4.2 Live reachability check against the real deployed project

Because several candidate findings hinge on whether `app.*` RPCs are reachable from a
real client, the orchestrating session queried the actual live Supabase project
(`awdlicmwzdxquopwtcfd`) directly, read-only, via `curl` with `Accept-Profile: app`
against `/rest/v1/employees`:

```
HTTP/2 406
{"code":"PGRST106","details":null,"hint":"Only the following schemas are exposed:
public, graphql_public","message":"Invalid schema: app"}
```

**Confirmed live, not merely cited from `00_EXECUTION_INDEX.md` §2's own older claim**:
`app` is not currently exposed via the Data API, so no `app.*` table or RPC is directly
callable over PostgREST today — the only current caller of any `app` RPC is the server

pre-deployment configuration state, not a documented, approved control (Prompt 372 §22),
and the application's own shipped code (`server/queries/customer-inventory-access.ts`)
calls these exact RPCs through the standard client, meaning `app` will need to be exposed
for the application to function once actually deployed. Findings below are graded on
this basis explicitly, not silently discounted for "not reachable today."

## 5. `HDN-BLK-011` / `ISS-2026-164` — the actor-identity-forgery class, fixed

### 5.1 Root cause

`app.assert_actor_is_session_identity` (added at `ATW-031`,
`20260730440000_harden_actor_identity_session_crosscheck.sql`) is this repository's own
primitive binding a caller-supplied actor parameter to the real session's `auth.uid()`.
It is wired into `app.evaluate_permission` (416 functions) and, at `ATW-032`
(`20260730510000_harden_actor_identity_unchecked_authority_surface.sql`), into 33 more,
under the explicit classification: *"43 of those are `STABLE`/`IMMUTABLE` — pure reads
that perform no side effect, where a forged actor changes nothing a caller could not
already read."*

**That premise is false for a `SECURITY DEFINER` reader.** It bypasses RLS by
construction, so a forged actor is exactly what lets a caller read rows RLS would
otherwise hide. A second, narrower gap in the same sweep: its candidate regex looked only
for the parameter name `p_actor_auth_user_id`, so two functions naming it
`p_requester_auth_user_id` (`app.query_audit_logs`/`app.export_audit_logs`) were never in
the candidate set at all.

### 5.2 Corrected sweep — exact count

migration files as authored — the same correction `HDN-371`'s own Tier C review required
of its own sweep): **9 functions were live-forced or clearly code-verified as exploitable
and fixed in this lane** (a further 4 were found and fixed at this same checkpoint's own
Tier C review — §5.6). `app.resolve_customer_owner_account_scope` is the single shared

### 5.3 Fix

`supabase/migrations/20260810000000_harden_tenant_isolation_actor_identity_gaps.sql` —
`create or replace function` for each of the 9, adding
`perform app.assert_actor_is_session_identity(<actor param>);` as the first statement.
Two of the nine (`get_self_employee`, `resolve_customer_owner_account_scope`) were
`language sql` and were converted to `language plpgsql` to carry the check, mirroring the

standing-convention `revoke execute on all functions in schema app from public;` plus
explicit re-grants. (This checkpoint's own Tier C review found 4 more functions of the
identical shape and fixed them the same way in a second migration — §5.6.)

### 6.3 Two genuine pre-existing test regressions found and fixed by this lane's own fix pass — and a correction to fix #1's own stated mechanism, made at Tier C

**Not accepted silently, not worked around — root-caused and fixed, each disclosed
exactly as found:**

1. `scripts/db-tests/hris-employee-master.sql:1228` called `app.query_audit_logs` with a
   hardcoded actor UUID while the test's own `request.jwt.claims` GUC still held a
   **different** identity, left over from an earlier sub-test (line 1203) that reset
   `role` but never cleared the JWT claim it had `set_config(..., true)`'d. Before this
   fix, the call "worked" only because `query_audit_logs` never verified the claimed
   actor — exactly the defect this lane fixed. After the fix, the leftover session
   correctly caused `actor_identity_mismatch`. **Original fix, corrected at Tier C:**
   the first fix cleared the claim with `set_config('request.jwt.claims', null, true)`
   and stated this "restores the session-less shape" — **that mechanism claim was
   false**, caught by this checkpoint's own Tier C correctness lens (live-tested). A
   custom-placeholder GUC already `SET` in the current transaction does not revert to
   unset on `set_config(..., null, true)` — it becomes the empty string, and
   `auth.uid()`'s own `::json` cast then **raises** on `''` rather than returning
   `null`. The test passed only because `app.assert_actor_is_session_identity` happens
   to wrap its own `auth.uid()` call in a `begin ... exception when others then
   v_session_identity := null; end` block, silently swallowing that raise and treating
   it as the session-less no-op case — the correct end state, reached by an incorrect
   mechanism, and undocumented as such. This repository had already root-caused and
   fixed this exact GUC quirk elsewhere, with the correct idiom
   (`scripts/db-tests/commercial-rate-cost-lookup.sql`'s own `set local
   request.jwt.claims to '{}';`). **Corrected** to `set_config('request.jwt.claims',
