## 1. Outcome

This lane found and fixed a real, live-forced, cross-tenant read vulnerability class at
the database layer, and registered a further set of Medium/Low tenant-boundary findings
across the application layer, notifications, files, reports, and dashboards.

**Headline finding, fixed in this lane (`HDN-BLK-011` / `ISS-2026-164`):** a systematic
sweep of every `SECURITY DEFINER` function granted `EXECUTE` to `authenticated` that
takes a claimed-actor parameter found **9 directly-fixed functions** (protecting **21**
total once transitive propagation through the customer-inventory-access family is
counted) that evaluated authority against a **client-supplied** actor UUID instead of the
verified session identity — the same root class the repository's own `ATW-031`/`ATW-032`
hardening pass already fixed for 416+33 functions, but missed here because that sweep's
own "STABLE/IMMUTABLE reads are exempt" premise is false for a `SECURITY DEFINER`
function (it bypasses RLS, so a forged actor is exactly what lets a caller read what they
could not otherwise). **Live-forced and confirmed twice**, independently, against
`app.link_auth_identity`-shaped and `app.get_self_employee`/ATW-023-family functions: a
non-member attacker who knows a victim tenant's own real admin's UUID could read that
tenant's full employee PII, customer inventory/warehouse/order data, audit trail, and
notifications.

**Fixed at the root in one additive migration**
(`20260810000000_harden_tenant_isolation_actor_identity_gaps.sql`), re-verified live
after the fix (the same forced attacks now correctly fail with
`actor_identity_mismatch`), and the full 229-file db-test suite re-confirmed green,
including two genuine pre-existing test-fixture regressions this fix surfaced and this
lane repaired (§6.3).

**A second, related, precisely-scoped finding was deliberately NOT fixed here and handed
to `HDN-373`** (`HDN-BLK-012` / `ISS-2026-165`, the very next lane, RLS/RBAC Audit): 13
dashboard-read functions share the identical shape but have no common root to fix once,
needing their own reviewed pass rather than a bundled edit in an already-large migration.

**A dozen further Medium/Low findings** — spanning the application layer's reliance on
the database as a single point of failure for the highest-privilege paths, a cross-tenant
existence oracle via verbatim Postgres error text, notification/file/report access-log
gaps, and structural fragility in RLS-bypassing views — are registered with named owners
in §7-§9 rather than silently fixed or silently dropped.

**No Critical finding.** Every write path probed (finance posting, employee lifecycle,
counter allocation, import commit, catalog registration) was correctly denied under a
forged actor across all four investigation lenses.

## 4. Scope and methodology

Prompt 372 §20 requires: building Tenant A/B fixtures across all modules; running direct
database/RLS, service, API, job, report, export, cache and file negative tests; testing
support/impersonation, API clients, AI jobs, webhooks and integrations for tenant
leakage; inspecting logs/monitoring/audit/report artifacts for cross-tenant exposure; and
blocking release on any critical/high isolation failure.

Given the breadth of this charter, four independent parallel investigations ran
simultaneously, each building its own disposable Postgres database from all 306
migrations and each live-testing with a genuine two-tenant fixture:

1. **DB/RLS/grants surface** — whole-schema RLS/grant posture sweep, policy-predicate
   correctness census, function call-graph closure analysis.
2. **API/service layer** — every Next.js route handler and `"use server"` action; where
   does the acting tenant/identity actually come from.
3. **Storage/signed URLs, jobs/queue, cache, reports/exports** — the surfaces Prompt 372
   §20/§24 name explicitly beyond the database/API core.
4. **Support/impersonation, AI/automation, webhooks/integrations, audit/monitoring
   logs** — the remaining named surfaces.

### 4.1 Methodology lesson, disclosed rather than hidden

The orchestrating session's own first manual attack attempt against
`app.list_api_keys_for_tenant` (before delegating the four investigations) produced a
**false positive**: `set local role authenticated; set local request.jwt.claims = '...'`
issued **outside** an explicit `begin`/`rollback` silently no-ops in Postgres (psql warns
"SET LOCAL can only be used in transaction blocks" but the script continues executing as
the original superuser role) — the "successful" cross-tenant read was actually a
superuser session bypassing everything, not a real vulnerability. Caught before being
reported, by verifying `current_user` genuinely showed `authenticated` on a retry
properly wrapped in `begin ... rollback;`, which correctly showed the function protected
(`actor_identity_mismatch`). **Every one of the four parallel investigations was briefed
on this exact failure mode up front** and every live-tested finding below verifies
`select current_user` = `authenticated` before trusting a result.

### 4.2 Live reachability check against the real deployed project

Because several candidate findings hinge on whether `app.*` RPCs are reachable from a
real client, the orchestrating session queried the actual live Supabase project
(`awdlicmwzdxquopwtcfd`) directly, read-only, via `curl` with `Accept-Profile: app`
against `/rest/v1/employees`:

```
HTTP/2 406
{"code":"PGRST106","details":null,"hint":"Only the following schemas are exposed:
public, graphql_public","message":"Invalid schema: app"}
```

**Confirmed live, not merely cited from `00_EXECUTION_INDEX.md` §2's own older claim**:
`app` is not currently exposed via the Data API, so no `app.*` table or RPC is directly
callable over PostgREST today — the only current caller of any `app` RPC is the server
layer. This is stated as fact, not accepted as a durable compensating control: it is a
pre-deployment configuration state, not a documented, approved control (Prompt 372 §22),
and the application's own shipped code (`server/queries/customer-inventory-access.ts`)
calls these exact RPCs through the standard client, meaning `app` will need to be exposed
for the application to function once actually deployed. Findings below are graded on
this basis explicitly, not silently discounted for "not reachable today."

## 5. `HDN-BLK-011` / `ISS-2026-164` — the actor-identity-forgery class, fixed

### 5.1 Root cause

`app.assert_actor_is_session_identity` (added at `ATW-031`,
`20260730440000_harden_actor_identity_session_crosscheck.sql`) is this repository's own
primitive binding a caller-supplied actor parameter to the real session's `auth.uid()`.
It is wired into `app.evaluate_permission` (416 functions) and, at `ATW-032`
(`20260730510000_harden_actor_identity_unchecked_authority_surface.sql`), into 33 more,
under the explicit classification: *"43 of those are `STABLE`/`IMMUTABLE` — pure reads
that perform no side effect, where a forged actor changes nothing a caller could not
already read."*

**That premise is false for a `SECURITY DEFINER` reader.** It bypasses RLS by
construction, so a forged actor is exactly what lets a caller read rows RLS would
otherwise hide. A second, narrower gap in the same sweep: its candidate regex looked only
for the parameter name `p_actor_auth_user_id`, so two functions naming it
`p_requester_auth_user_id` (`app.query_audit_logs`/`app.export_audit_logs`) were never in
the candidate set at all.

### 5.2 Corrected sweep — exact count

Re-run redefinition-aware against the live catalogue (`pg_get_functiondef`, not the
migration files as authored — the same correction `HDN-371`'s own Tier C review required
of its own sweep): **9 functions were live-forced or clearly code-verified as exploitable
and fixed in this lane.** `app.resolve_customer_owner_account_scope` is the single shared
root all 12 members of the `ATW-023` customer-inventory-access family
(`app.evaluate_customer_inventory_access`, `app.get_customer_inventory_balance`,
`app.list_customer_inventory_balances`, `app.list_customer_lot_identities`,
`app.list_customer_serial_identities`, `app.get_customer_outbound_order`,
`app.list_customer_outbound_order_lines`, `app.list_customer_outbound_orders`,
`app.list_customer_inventory_movement_summary`, `app.list_customer_warehouse_eligibility`)
call, directly or transitively, to resolve which customer accounts an actor may see —
none of the 12 re-derives or mutates the actor before passing it through, so fixing the
root closes the whole family (verified live, §5.4), mirroring how `ATW-031` fixed 416
functions at one choke point rather than 416 separate edits.

| 1 | `app.get_self_employee` | Returns the *entire* `app.employees` composite, including columns deliberately excluded from the table's own column-restricted grant (`national_id_number`, `date_of_birth`, `personal_email`, `personal_phone`, `personal_address_*`, five `*_reason` narrative columns, HRT-293) | **Live-forced.** Non-member attacker, knowing tenant B's admin UUID, read full PII including `suspend_reason = "SUSPENDED FOR FRAUD INVESTIGATION"` |

### 5.3 Fix

`supabase/migrations/20260810000000_harden_tenant_isolation_actor_identity_gaps.sql` —
`create or replace function` for each of the 9, adding
`perform app.assert_actor_is_session_identity(<actor param>);` as the first statement.
Two of the nine (`get_self_employee`, `resolve_customer_owner_account_scope`) were
`language sql` and were converted to `language plpgsql` to carry the check, mirroring the
`CPL-300` precedent this repository already established for
`app.resolve_customer_account_scope`'s own identical fix. All nine retain their existing
`EXECUTE` grants (`authenticated`, `service_role`) — the migration ends with the
standing-convention `revoke execute on all functions in schema app from public;` plus
explicit re-grants.

### 5.4 Live re-verification, post-fix

Both the direct fix and the transitive propagation were independently re-forced by the
orchestrating session on a fresh probe database after the migration applied:

```

-- transitive: app.list_customer_warehouse_eligibility (NOT itself modified), same forged actor
ERROR:  actor_identity_mismatch: ...
CONTEXT:  ... PL/pgSQL function resolve_customer_owner_account_scope(uuid,uuid) ...
          PL/pgSQL function list_customer_warehouse_eligibility(uuid,uuid) ...

-- control: same function, genuine own-identity call
CONTROL: legit own-identity call (post-fix) | {33333333-3333-3333-3333-333333333333}
```

The control confirms the fix is not a blanket deny — a caller acting as themselves still
gets the correct result; only a forged actor is now rejected.

### 5.5 Deferred: `HDN-BLK-012` / `ISS-2026-165` — the 13 dashboard functions

`app.get_ops_dashboard_*` (6: `shipment_status`, `milestone_sla`, `exception_queue`,

range's cadence exists to prevent. **Registered as `HDN-BLK-012`/`ISS-2026-165`, owner

next-closest charter match), with the exact function list, exact fix pattern (identical

### 6.3 Two genuine pre-existing test regressions found and fixed by this lane's own fix pass

**Not accepted silently, not worked around — root-caused and fixed, each disclosed
exactly as found:**

1. `scripts/db-tests/hris-employee-master.sql:1228` called `app.query_audit_logs` with a
   hardcoded actor UUID while the test's own `request.jwt.claims` GUC still held a
   **different** identity, left over from an earlier sub-test (line 1203) that reset
   `role` but never cleared the JWT claim it had `set_config(..., true)`'d. Before this
   fix, the call "worked" only because `query_audit_logs` never verified the claimed
   actor — exactly the defect this lane fixed. After the fix, the leftover session
   correctly caused `actor_identity_mismatch`. **Fixed** by clearing
   `request.jwt.claims` immediately after the sub-test that set it, restoring the
   session-less shape every other call in this 1300+-line file already uses.
2. `scripts/db-tests/rbac-enforcement.sql`'s own `ATW-032` "authority surface" sweep
   (a **different**, pre-existing closure check from the one this lane added, testing
   for an *authority* check rather than an *identity* check) legitimately requires
   `app.get_self_employee` to stay on its `v_expected` exemption list, since the
   function has no authority check and needs none (a self-row lookup is inherently
   scoped once identity is proven). This lane's first-draft edit removed the entry
   entirely on the mistaken assumption that adding the identity check alone would
   satisfy this separate sweep. **Fixed** by re-adding the entry with a corrected
   reason (the original exemption's *identity* half was wrong and is now fixed at the
   root; the *authority* half was always correct and still applies).

Both are documented inline in the fixed files with an `HDN-372` reference, and both were
proven fixed by re-running the full 229-file suite from scratch a third time — clean.
