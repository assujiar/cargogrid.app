## 4. Atomicity is additionally bounded outside the prompt text

Two controls constrain task size independently of what a prompt says, and both were verified to
exist rather than assumed:

- `AGENTS.md` "Scope and refactoring": default task size is one feature slice, one module
  boundary, 1–3 migrations, ~5–15 changed files. Broader work requires a dedicated prompt and
  ADR/change control.
- The 14 indented Phase 5 prompts' own §36 wording ("release ATW-227 … after all required
  ATW-226 **child tasks** are verified") shows the package anticipates a capability prompt being
  *decomposed* into child tasks by its phase kickoff, with the parent prompt ID retained. A
  capability that turns out too large therefore has a defined subdivision path rather than
  needing the prompt rewritten.

## 8. Tier C — adversarial round

**Lens 1, spec compliance.** Prompt 418 §33 met.

**Lens 2, is size the right proxy?** Byte count alone would be a weak audit — a 12 KB prompt can
still be generic. That is why checks 3–9 test *structure and content presence* rather than
length: a thin §20, a missing §33, a missing §29. The §20 check in particular is the one that
would catch a padded prompt with no real implementation tasks, and it was run against all 338.

**Lens 3, attacking the "no finding" verdict.** The strongest counter-argument is that a uniform
template can hide uniformly generic content — every prompt has a §33, but is it *specific*?
Spot-read of `138` (smallest), `226` (largest) and `347` (second largest) found each §33 stated
in terms of that capability's own artifacts, not boilerplate. Three files is a sample, not a
proof, and this lane says so rather than claiming corpus-wide semantic specificity it did not
measure.

**Lens 4, scope discipline.** No package file touched.

**Round result:** no defect. `VERIFIED`, with the §33-specificity limitation in Lens 3 disclosed
rather than papered over.
