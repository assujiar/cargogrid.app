## 4. The 13 graph roots are chain heads, not orphans

Prompts with no inbound explicit edge: **143, 168, 191, 221, 223, 229, 251, 274, 324, 364, 386,
392, 415**. Each was checked by reading its *predecessor's* §36, and every one is released by a
documented mechanism rather than being unreachable:

- **Released by an index-delegating predecessor** — e.g. `222_DISPATCH_BOARD`'s §36 reads "Only
  the execution index may release the next dependency-clean ATW task", which is how 223 is
  reached; likewise 228→229, 323→324, 363→364, 385→386.
- **Released by a phase kickoff prompt**, which uses the non-36-field format and states the
  release as a completion gate — e.g. `142_COMMERCIAL_WBS_RUNTIME_KICKOFF` releases 143,
  `391_RELEASE_GO_LIVE_WBS_RUNTIME_KICKOFF` releases 392, and
  `414_FINAL_PACKAGE_VALIDATION_WBS_KICKOFF` releases 415 with "Mark Prompt 415 `READY` only
  if…".

**No orphan.** The explicit-edge graph is a forest of chains whose heads are released by
index-delegation or by a kickoff gate — exactly the ordering model
`BUILD_EXECUTION_PROTOCOL.md` §3.5 and `CON-015` describe.

## 5. Four self-loops were reported and all four were false — recorded because the fix matters

Indentation-tolerant parsing (from `FPV-416`) first surfaced `NEXT_SELF_LOOP` on prompts 226,
245, 246 and 247. All four were parser artifacts, not package defects:

> "Only the execution index may release ATW-247 **after ATW-246 is verified**."

`ATW-246` is the prompt's own number appearing as a **precondition**, not a successor. A fifth
shape — "release ATW-227 … **after all required ATW-226 child tasks are verified**" — survived
the first, too-literal fix and forced a generalization to the whole clause. A sixth, "Prompt 248
**alone may** close Phase 5", is a prohibition and was likewise excluded.

Each exclusion is pinned by a unit test using the real Phase 5 wording. **This lane's PASS on
checks 1–2 depends on those exclusions being correct, so they are stated here rather than left
inside the tool.**

## 6. Disclosed scope limitation — 51% of the graph is machine-verifiable, and no more

Prompt 430 item 8 asks to "verify dependency order has no cycle, orphan or impossible next
command". That can be verified mechanically for **174 of 338** structured prompts (51%). The
other 164 are not defective — 83 delegate ordering to a phase execution index and 81 carry a
runtime `{{NEXT_…}}` placeholder — but **their ordering does not exist as data until the phase's
execution index is written at runtime**, so no static analysis can confirm it.

This lane therefore reports "no cycle over the explicit graph", **not** "no cycle in the
package". Registered as `FPV-F005`, an audit-scope limitation rather than a package defect, so
`FPV-430` disposes of item 8 with the same honesty instead of inheriting an overstated PASS.

## 10. Tier C — adversarial round

**Lens 1, spec compliance.** Prompt 419 §33 met.

**Lens 2, is the cycle check real?** A numeric heuristic ("target < source ⇒ cycle") would be
cheap and wrong — it would flag every legitimate resume path and miss any cycle among
forward-numbered prompts. This lane used three-colour DFS over the actual adjacency list, which
detects a cycle regardless of numbering. The backward-edge check is retained separately as a
WARN, as a second signal, not as the cycle test.

**Lens 3, attacking the "no orphan" verdict.** The weak form of this check counts inbound edges
and calls anything with zero an orphan; that would have produced 13 false findings. The strong
form — used here — reads each root's predecessor and names the mechanism that releases it. Both
were run; the strong form is what is reported.

**Lens 4, scope discipline.** No package file touched. The one registered item is a limitation
of the audit, explicitly not a package defect.

**Round result:** no package defect; one honest scope limitation registered. `VERIFIED`.
