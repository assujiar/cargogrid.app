## 3. Implementation

### 3.1 Design

**Formalizes an already-real live comparison, not a rebuild.** FIN-202's own `app.get_finance_subledger_reconciliation_summary` already computes a direct, tenant-wide, live comparison of the `ar_control`/`ap_control` GL accounts against their own AR/AP open-item totals. This checkpoint's real gap: that function has no as-of date, no persisted snapshot, and no exception/certification workflow -- exactly what "make Finance balances explainable... prevent silent close on unreconciled data" (Prompt 209 section 5) needs at Financial Close.

**Disclosed granularity bound.** This checkpoint reconciles one aggregate control-account total against one aggregate open-item total per (scope, as-of date) -- an honest reflection of the real computation FIN-202 already performs, itself aggregate. A per-transaction matched/unmatched queue (joining every subledger line to its own open item) is a larger scope, not attempted here.

**Disclosed as-of-bounding limitation, found and fixed during authoring.** `app.finance_subledger_batches` carries no direct business posting-date column -- only `posted_at` (a wall-clock insert timestamp) and `posting_period_id`. Filtering the control-account side by `posted_at::date <= as_of_date` would silently use the *insert* time, not the *business* posting date, breaking any real as-of semantics for backdated postings (caught while authoring the db-test: a batch posted "as of" June inside a db-test that runs in real wall-clock July would be wrongly excluded from a June as-of run). Fixed by joining `app.finance_fiscal_periods` and bounding by the resolved period's own `end_date <= as_of_date` instead -- a real, deterministic, period-granular bound tied to the actual business date that resolved the posting period at insert time. The open-item (source) side uses each domain's own real business date column directly (`invoice_date` for AR, `bill_date` for AP), never `created_at`.

**Reconciliation never silently writes a balance to force equality** (Prompt 209 section 24): this migration's own functions never mutate `app.finance_ar_open_items`/`app.finance_ap_open_items`/`app.finance_subledger_lines` in any way -- strictly read-only source comparison, writing only its own run/exception rows.

**Synchronous execution, disclosed.** Prompt 209 section 17 names async execution for a large OLTP-wide scan; the real aggregate query this checkpoint issues is indexed and bounded, so `app.execute_finance_reconciliation_run` computes synchronously inside one transaction -- no background job introduced this checkpoint.

**Certification requires an independent authority and zero open exceptions** (Prompt 209 section 23/26): `app.certify_finance_reconciliation_run` (`FIN:Approve`) raises `finance_reconciliation_unexplained_variance` while any exception on the run remains `open`; `app.resolve_finance_reconciliation_exception` (`FIN:Edit`) requires a non-empty reason.
