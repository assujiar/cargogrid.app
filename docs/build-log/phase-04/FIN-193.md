## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

Fiscal calendars/periods are real domain data with their own non-overlapping-date-range and lifecycle-transition concerns -- like `FIN-192`, a real table family with its own authority model (`app.evaluate_permission` via `FIN:Edit`/`FIN:Approve`), not layered on `PLT-121`'s Configuration Engine.

**Closes `FIN-191`'s `finance_close_policy` config class into a real consumer for the first time**: generating a fiscal calendar resolves the tenant's currently-effective `finance_close_policy` items once and pins an identical checklist snapshot onto every generated period -- a governed snapshot, the same "read the governed snapshot verbatim, never re-derive" discipline this repository's Commercial/Operations capabilities already established. A later republish of `finance_close_policy` never silently changes an already-generated period's own checklist.

**Explicit scope boundary (Prompt 193 section 14)**: hard-lock enforcement at a real posting boundary is `FIN-207`'s own scope -- no posting/journal table exists anywhere in this repository yet. This checkpoint defines the canonical lifecycle (`open -> soft_closed -> closed`, plus governed reopen) and the deterministic date-to-period resolver `app.resolve_finance_period_for_date` (the exact forward seam `FIN-207`/later posting capabilities will call), with a `posting_eligible` read-only projection (true only while `status='open'`) -- but enforces nothing at a posting call site, because none exists yet. Disclosed, not silently promised.

Authority is deliberately split, matching Prompt 193 section 26 ("close/reopen approvers are separately authorized"): calendar generation, soft-close, and checklist acknowledgment require `FIN:Edit` ("prepare"); close and governed reopen require `FIN:Approve` -- proven directly in the db-test with a dedicated Finance Editor actor (`FIN:Edit`/`View` only) who can soft-close but is rejected on close/reopen.

### 3.2 Schema — `supabase/migrations/20260728220000_create_finance_fiscal_period.sql`

## 4. Tests

### 4.1 Real database tests (`scripts/db-tests/finance-fiscal-period.sql`, via `pnpm run db:test`)

Setup: two tenants; tenant A gets a Finance Manager (`tenant_admin` AND `FIN:Edit/Approve/View`), a Finance Editor (`FIN:Edit/View` only, no `Approve`), and a Plain User with no `FIN` grant; tenant B gets its own Finance Manager. Assertions: publishing a `finance_close_policy` with one required and one optional item; authority-gated calendar generation (Plain User denied) producing 3 non-overlapping monthly periods each pinning both checklist items (6 total, a governed snapshot); invalid period count, duplicate calendar code, and date overlap each rejected; deterministic date-to-period resolution (covered date resolves `posting_eligible=true`, uncovered date returns zero rows); close readiness (`not ready` -> acknowledge required item -> `ready`); the prepare-vs-approve lifecycle split (Finance Editor soft-closes but is denied close/reopen; Finance Manager succeeds on both); a closed period rejects further checklist acknowledgment; `close` is rejected while a different period's required item remains unsatisfied; governed reopen (mandatory reason, Finance Editor denied, Finance Manager succeeds, the transition recorded with its own reason); cross-tenant isolation; schema-privilege defense in depth; audit-trail reconciliation. All 75 db-test files pass together, zero regression, including a full re-run of `FIN-191`'s own `finance_close_policy` publish path (untouched by this checkpoint's migration).
