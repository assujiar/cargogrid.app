## 3. Implementation

### 3.1 Design (disclosed, migration header) -- the AP-side mirror of FIN-198, composed with FIN-199

`FIN-199`'s own `app.apply_finance_ap_settlement`/`app.reverse_finance_ap_settlement` were built explicitly for this checkpoint to call directly (documented in the FIN-199 migration itself: "The shared settlement primitive FIN-201 (Settlement) is expected to call directly"). This migration therefore owns settlement preparation, the settlement-to-AP-item allocation mapping, and the `prepare -> submit -> approve -> execute -> post` lifecycle only -- it never opens a second, competing AP-balance mechanism.

**Execution vs. posting** (Prompt 201 section 24: "Execution/posting are distinct canonical states and retries cannot duplicate either"): approval authorizes payment; execution records that a payment instruction actually left the bank/payment channel (an optional external reference); posting is the one idempotent event that reduces AP by calling `app.apply_finance_ap_settlement` per allocation line. A settlement cannot post before it is executed, proven directly.

**Exact allocation, decided once** (Prompt 201 section 21): allocations are a fixed set of `(ap_open_item_id, amount)` pairs supplied at preparation time -- mirrors `FIN-197`/`FIN-200`'s own "prepare with lines in one call" design rather than `FIN-198`'s own "capture now, allocate later" design, because a settlement's whole purpose is a single governed payment run against a chosen set of open items.

**Idempotency**: `finance_settlements` carries its own `idempotency_key` (`unique (tenant_id, idempotency_key)`) at preparation time, mirroring `FIN-198`'s own `app.capture_finance_receipt` idiom (settlement is treasury-initiated, not derived 1:1 from a single upstream document the way a vendor bill is). Each allocation line's own AP-settlement call additionally carries a derived idempotency key (`idempotency_key || ':' || ap_open_item_id`).

**Bounded MVP scope, disclosed**: `fee_amount` is one governed total per settlement, not an itemized fee/withholding-line ledger; cross-currency settlement is out of scope (settlement currency must exactly match every allocated AP item's currency); this checkpoint has no separate treasury role, so execute/post are both `FIN:Approve`-gated rather than split across a distinct role; no bank/payment provider adapter is called anywhere in this migration.

### 3.2 Schema — `supabase/migrations/20260729150000_create_finance_settlement.sql`

`app.finance_settlements` (idempotent unique on `tenant_id, idempotency_key`; `total_amount` a generated column `allocated_amount + fee_amount`; seven-state lifecycle `draft/submitted/approved/executed/posted/void/reversed`), `app.finance_settlement_allocations` (one row per settlement-to-AP-item line; unique on `settlement_id, ap_open_item_id`), `app.finance_settlement_number_counters`. Functions: `app.check_finance_settlement_authority`, `app.prepare_finance_settlement` (idempotent on `idempotency_key`; validates vendor/currency/fee, and per allocation line validates the AP open item exists, belongs to the requested vendor, matches currency, is not held, is not already fully settled, and does not exceed its own open amount), `app.submit_finance_settlement_for_approval`, `app.discard_finance_settlement_draft` (draft/submitted only), `app.approve_finance_settlement`, `app.execute_finance_settlement` (records an optional external reference, zero AP/cash effect), `app.post_finance_settlement` (idempotent, period-aware, generates `settlement_number`, calls `FIN-199`'s own `app.apply_finance_ap_settlement` once per allocation line), `app.request_finance_settlement_reversal` (`FIN:Approve`-gated, mandatory reason, calls `FIN-199`'s own `app.reverse_finance_ap_settlement` per line), `app.list_finance_settlements`, `app.get_finance_settlement_allocations`, `app.search_finance_ap_candidates_for_settlement`.

## 4. Tests

### 4.1 Real database tests (`scripts/db-tests/finance-settlement.sql`, via `pnpm run db:test`)

Setup: two tenants; tenant A gets a Finance Manager (`FIN:Edit/Approve/View`), a Finance Editor (`FIN:Edit/View` only, no `Approve`), a Plain User, six fiscal periods, and one active vendor reference; tenant B gets its own Finance Manager.

Assertions: preparation validation (Plain User denied; unknown vendor, unsupported currency, empty allocation, non-positive allocation amount, unknown open item, vendor mismatch, currency mismatch, a held open item, and an over-allocation are each rejected with a distinct named exception; a real two-item allocation across the same vendor computes `allocated_amount = 900`, `fee_amount = 5`, `total_amount = 905`; a retried `prepare` with the same idempotency key returns the original settlement unchanged even when other fields differ); lifecycle authority split and full posting path (Finance Editor denied `approve`/`execute`; `draft -> submitted -> approved` proceeds; posting before execution is rejected with `finance_settlement_not_executed`; `executed -> posted` assigns a real `SETL-2026-*` number and reduces both AP open items to `settled`/`open_amount = 0`; a retried `post` returns the same posted settlement unchanged and never double-applies to AP); governed reversal (reversal before posting rejected; Finance Editor denied; empty reason rejected; a real reversal restores the AP open item to `open`/`open_amount = 250` and moves the settlement to `reversed`); discard boundary (draft/submitted discardable, approved is not); list/allocations/candidate-search plus cross-tenant isolation; schema-privilege defense in depth (12 function names checked for zero `anon` `EXECUTE`); audit trail (minimum 5 events).
