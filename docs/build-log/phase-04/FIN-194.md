## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

**Closes `PLT-119`'s own disclosed forward reference verbatim**: `app.validate_currency_code` (`20260717112000_create_localization.sql`) documented itself as "display-formatting currency codes only ... Real currency/FX control is a dedicated future Phase 4 capability." This checkpoint `CREATE OR REPLACE FUNCTION`s that exact function (the established later-migration-extends-an-earlier-one's-function pattern, precedent `20260724290000_create_commercial_customer_account_conversion.sql`) so it resolves against this migration's own real `app.finance_currencies` registry instead of the two-code hardcoded placeholder -- strictly additive (IDR/USD, the only two codes PLT-119 ever accepted, remain accepted). The function's volatility category changes from `IMMUTABLE` to `STABLE` (it now reads a real table) -- disclosed, not silently changed; neither of its two existing CHECK-constraint call sites (`app.tenant_locale_versions`, `app.users`) requires `IMMUTABLE`.

**Rounding tie-in to `FIN-191`** (Prompt 194 section 6): `app.apply_finance_rounding` implements the same four bounded rounding conventions `app.finance_rounding_modes` (FIN-191) already catalogues; `app.convert_finance_amount` resolves the tenant's own effective `finance_rounding` config (key `fx_conversion`, falling back to `default`, falling back to a disclosed safe default of `round_half_up` at the target currency's own `minor_unit_precision`) rather than inventing a second, competing rounding mechanism.

**Imports use a staged, idempotent batch** (Prompt 194 section 14): a bounded, disclosed alternative to adopting the full generic Import/Export Job Framework (`PLT-129`) for this one capability -- the same class of proportionate-effort decision `COM-151`'s own header recorded for the Configurable Numbering Engine.

**Platform-wide default authority** (found and fixed during authoring, not merely disclosed): a `tenant_id null` exchange rate is a platform-wide default per this migration's own convention. `app.check_finance_exchange_rate_authority` and `app.create_finance_exchange_rate_draft` were widened so a `null` tenant falls back to Supreme Admin authority (`app.is_supreme_admin`) instead of the tenant-scoped `FIN` permission evaluator/tenant-membership check, which has no meaning for a `null` tenant -- mirroring `PLT-121`'s own `app.check_config_object_authority` ("when `p_scope_level = 'global'` then `app.is_supreme_admin(...)`"). Proven directly in the db-test: a tenant-scoped Finance Manager (no Supreme Admin grant) is denied creating a `null`-tenant draft; Supreme Admin succeeds.

### 3.2 Real defect found and fixed before commit: non-`setof` resolver broke its own "missing rate" detection

`app.resolve_finance_exchange_rate` was first written as `returns app.finance_exchange_rates` (a bare composite, not `setof`). Empirically verified against a live Postgres 16 instance: calling a non-`setof` function in a `FROM` clause -- `select * into v_rate from func(...)` -- always produces **exactly one row**, even when the function's own body query matches zero rows (the row is simply all-`NULL`). This silently broke `plpgsql`'s `FOUND` variable for every caller, including this function's sole caller, `app.convert_finance_amount`, whose entire "no approved rate covers this instant -> raise `finance_exchange_rate_missing`, never a silent default" contract (Prompt 194 section 23's own explicit requirement) depended on `FOUND` being accurate. Found via this checkpoint's own db-test (`>> deterministic resolution ... no row for an uncovered instant` failed on the first run), fixed by declaring the function `returns setof app.finance_exchange_rates` instead -- a `setof` function genuinely returns zero rows when its body query matches nothing, restoring correct `FOUND` semantics for both call shapes (`SELECT INTO` and a bare `FROM` reference) while preserving its documented "deterministic, single-row resolution" behavior (the `order by ... limit 1` is unchanged). Re-verified: the full db-test suite, including the missing-rate rejection assertion inside `convert_finance_amount`, passes.
