## 3. Implementation

### 3.1 Design -- what already existed, and what this checkpoint actually adds

**Baseline protection, already real since `FIN-197`, disclosed not rebuilt**: every posted-state Finance table in this repository has carried zero `UPDATE`/`DELETE` grant for `authenticated` since its own migration (the repository-wide `PLT-118` convention, `ERR-2026-004`). A normal-role direct-table mutation was already structurally impossible before this checkpoint; every real mutation is a `service_role`-only, authority-checked function call.

**What this checkpoint adds (Prompt 204's own bounded scope -- Posted-*Journal* Integrity, the named epic)**: a table-level trigger on `app.finance_journals`/`app.finance_journal_lines` (`app.protect_posted_finance_journal`/`app.protect_posted_finance_journal_line`) that blocks *any* `UPDATE`/`DELETE` against an already-posted row -- a strictly stronger guarantee than the grant-only protection every other Finance table relies on, since it also blocks a hypothetical `service_role`-level direct mutation outside the vetted RPC surface -- unless the acting identity holds a live `supreme_admin` principal membership (`app.is_supreme_admin`, RPD-022's own disclosed absolute-CRUD exception, reused unmodified from `PLT-113`).

**RPD-022 exercised, not silently defeated**: when the bypass is used against an already-posted row, the trigger still permits the mutation (never a tamper-proof claim) but captures a best-effort `app.capture_audit_event` row disclosing it -- a detective control, never a preventive guarantee against a Supreme Admin who also controls the database directly.

**One real implementation snag found and fixed during authoring, before commit**: `auth.uid()` called directly from plain `plpgsql` code (as this checkpoint's own triggers do, to capture the acting identity for audit evidence) requires real `USAGE` on schema `auth` for the invoking role -- unlike every existing caller in this repository, which only ever invokes `app.is_supreme_admin()`/`app.has_active_tenant_membership()` with no explicit argument, letting each function's own `security definer` context resolve its own default `auth.uid()` argument internally. Fixed by adding an explicit `grant usage on schema auth to service_role;` (and the `app.is_supreme_admin(uuid)` execute grant, previously `authenticated`-only) in this migration -- both additive grant statements, no existing function body touched.

**Reversal is explicitly `FIN-206`'s own scope** (Prompt 204 section 32: "reverse posted journal via FIN-206") -- no reversal function is built or retrofitted here.
