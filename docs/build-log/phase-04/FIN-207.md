## 3. Implementation

### 3.1 Design

**A layer on top of FIN-193's own fiscal-period lifecycle, not a replacement.** FIN-193 already blocks posting into a genuinely closed period via `posting_eligible`. This checkpoint adds a finer, explicitly *scoped* lock (`all`/`gl`/`ar`/`ap`/`tax`) with its own reason/evidence, a governed time-boxed reopen, and a mandatory re-lock -- distinct governance on top of the existing calendar.

**One authoritative guard, two real chokepoints.** `app.assert_finance_period_open_for_posting` is the single guard every GL-affecting posting path calls. Every posting path in this repository already funnels through exactly two functions: FIN-203's own `app.post_finance_journal` (manual) and `app.create_and_post_finance_system_journal` (system: subledger and FIN-206 correction) -- both `CREATE OR REPLACE`d to call the guard immediately after resolving the posting period, before any row is written. `app.post_finance_subledger_batch` (FIN-202/203) is additionally `CREATE OR REPLACE`d to derive the real `ar`/`ap` scope from its own already-known `source_type` (`invoice`/`receipt_allocation` -> `ar`; `vendor_bill`/`settlement` -> `ap`) and thread it through to `create_and_post_finance_system_journal`'s own `p_lock_scope` parameter (added at FIN-206, previously always defaulted to `gl`). A manual journal and a FIN-206 correction are both checked against `gl`; every path is additionally checked against a tenant-wide `all` lock by the guard itself, since the guard matches `lock_scope in ('all', p_lock_scope)`.

**A reopen is minimum-scope, approved, reasoned, and time-boxed, never silently permanent.** `app.request_finance_period_reopen` (`FIN:Edit`, `locked -> reopen_requested`) then `app.approve_finance_period_reopen` (`FIN:Approve`, `reopen_requested -> reopened`, sets a bounded 1-720-hour `reopen_window_expires_at`). Critically, the guard itself treats an *expired* window as still-locked even before an explicit `app.relock_finance_period` call updates the stored `status` -- proven directly in the db-test by simulating expiry and showing posting is blocked again, then confirming an explicit re-lock restores the row's own status.

**No signature-changing extension this time.** Unlike FIN-206's own extension of `create_and_post_finance_system_journal` (which appended a new parameter and required dropping the prior overload), this checkpoint's `CREATE OR REPLACE` calls on `post_finance_journal`, `create_and_post_finance_system_journal`, and `post_finance_subledger_batch` keep each function's own existing signature byte-for-byte identical -- only the function body gained one new `perform` call each. No overload-ambiguity risk, confirmed by a clean `db:test` run on the first attempt.

**RPD-022 disclosed, not re-implemented.** This checkpoint makes no claim that a lock is an absolute prevention against the already-disclosed Supreme Admin absolute-CRUD exception (FIN-204); that exception is untouched here.
