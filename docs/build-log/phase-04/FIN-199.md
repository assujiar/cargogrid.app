## 3. Implementation

### 3.1 Design (disclosed, migration header) -- the vendor-side mirror of FIN-196

`FIN-200` (Vendor Bill) does not exist yet at this checkpoint -- per `189_FINANCE_README.md` section 4, Accounts Payable (199) precedes Vendor Bill (200). This migration therefore builds the AP open-item subledger primitive generically (`source_document_type` bounded to `vendor_bill`/`opening_balance`), the exact same "build the shared primitive first, the next capability becomes its first real caller" pattern `FIN-196`'s own migration already established for its AR counterpart. `FIN-200`'s own `app.post_finance_vendor_bill` is expected to call `app.post_finance_ap_open_item` directly once it exists.

**Vendor reference boundary** (Prompt 199 section 24): `vendor_master_id` references `app.master_records` (`master_type_code = 'vendor'`, registered by `OPS-172`) -- the exact same vendor identity `app.shipment_actual_cost_components.vendor_id` (`OPS-178`) already references. No new vendor-identity table, no Procurement vendor-lifecycle scope smuggled in.

Status is a pure function of balance (`open`/`partial`/`settled`), computed only by the settlement functions, never accepted from a caller. Payment hold is an orthogonal flag (`is_held`). GL posting scope: this migration captures `posting_period_id` and full source lineage but creates zero GL journal line -- `FIN-202`/`FIN-203`'s own scope.

### 3.2 Schema — `supabase/migrations/20260729130000_create_finance_accounts_payable.sql`
