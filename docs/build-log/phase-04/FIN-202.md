## 3. Implementation

### 3.1 Design -- posting-map-driven, real integration, not a placeholder engine

`FIN-191`'s own `finance_posting_map` configuration type and `FIN-192`'s own chart-of-accounts existence/active/postable validation were built exactly for this checkpoint to consume (`FIN-191`'s migration header: "`FIN-192`... to add real account-existence checking for the `finance_posting_map` class"). `app.resolve_finance_posting_map_account` resolves one tenant's own published posting map (`app.resolve_finance_config`) for a well-known key (`ar_control`, `ap_control`, `revenue_default`, `expense_default`, `cash_default`, `tax_payable_default`, `input_tax_default`, `fee_expense_default`) to a real, active, postable account -- never hardcoded, never a silent default.

**Real integration, not a dead engine**: per the Definition of Done ("without placeholder/fake persistence/dead action") and the objective's own present tense ("translate invoice, receipt, vendor-bill, settlement... into reconcilable accounting events"), this migration `CREATE OR REPLACE FUNCTION`s all four already-shipped posting functions -- `app.issue_finance_invoice` (FIN-197), `app.allocate_finance_receipt` (FIN-198), `app.post_finance_vendor_bill` (FIN-200), `app.post_finance_settlement` (FIN-201) -- the established later-migration-extends-an-earlier-one's-function-by-full-replacement pattern this repository has used since `20260724290000_create_commercial_customer_account_conversion.sql`. Every other line of each function's own body is byte-for-byte unchanged; each now additionally emits exactly one balanced `app.finance_subledger_batches` row at its own existing posting moment, inside the same transaction:

- Invoice issue: debit `ar_control` for the total; credit `revenue_default` for the subtotal; credit each tax line's own governed `output_account_id` (FIN-195) or the `tax_payable_default` fallback.
- Receipt allocation: debit `cash_default`, credit `ar_control`, one control-account line per allocate call (mirrors `app.finance_receipt_allocations`'s own already-established per-item lineage rows).
- Vendor bill post: debit `expense_default` for the subtotal; debit each tax line's own governed `recoverable_account_id` or the `input_tax_default` fallback; credit `ap_control` for the total.
- Settlement post: debit `ap_control` for the allocated amount (plus `fee_expense_default` when a fee applies); credit `cash_default` for the total.

**Execution/GL-journal forward reference, disclosed**: `gl_journal_id` is a bare `uuid` column, deliberately not a foreign key -- `app.finance_journals` does not exist until `FIN-203` (the very next capability), mirroring `FIN-191`'s own "posting-map account-code references stored structurally only" forward-reference idiom exactly.

**Reversal/adjustment posting is explicitly out of scope**, `FIN-206`'s own (Reversal and Adjustment) -- not retrofitted here, so "Each source produces at most one intended subledger effect" (Prompt 202 section 33) holds structurally today.

### 3.2 Schema — `supabase/migrations/20260729160000_create_finance_subledger.sql`

`app.finance_subledger_batches` (idempotent unique on `tenant_id, source_type, source_id`; `total_amount` the balanced debit/credit total), `app.finance_subledger_lines` (one exact debit/credit line; `posting_map_key` records lineage back to policy, null when a line instead posts to an already-governed direct account reference). Functions: `app.check_finance_subledger_authority`, `app.resolve_finance_posting_map_account`, `app.post_finance_subledger_batch` (the one idempotent, balanced posting entry point; FIN:Edit-gated; rejects an unbalanced batch before writing any row; supports both a `postingMapKey` line and a direct `accountId` line), `app.preview_finance_subledger_posting` (read-only, persists nothing), `app.list_finance_subledger_batches`, `app.get_finance_subledger_lines`, `app.get_finance_subledger_reconciliation_summary` (a real, direct comparison of the subledger's own AR/AP control balances against FIN-196/FIN-199's own live open-item totals).

## 8. Errors / recovery / risks / issues

One genuine implementation defect found and fixed during this checkpoint's own authoring, before commit: the first draft of `app.post_finance_subledger_batch` checked `app.has_active_tenant_membership` but never actually called `app.check_finance_subledger_authority` at all -- meaning a Plain User with zero `FIN` grant, but active tenant membership, would not have been rejected by authority, only incidentally by whatever validation happened to run next. Caught by this checkpoint's own db-test (`finance-subledger.sql`'s own first scenario group), before any commit: the "Plain User A is denied" assertion instead observed an unbalanced-batch error from the deliberately single-line negative fixture, revealing the missing gate. Fixed by adding a real `FIN:Edit` check immediately after the membership check. Zero other implementation defect found. Zero Critical/High-severity issue remains open. Zero regression to any prior capability (all four retrofitted functions' own pre-existing db-test assertions pass unchanged past the new posting-map fixture).
