## 3. Implementation

### 3.1 Reuse decision (disclosed, migration header)

Finance Configuration reuses `PLT-121`'s Configuration Engine directly (`app.config_types`/`config_objects`/`config_versions`/`config_items`/`config_dependencies`, `create_config_draft`/`set_config_items`/`publish_config_version`/`discard_config_draft`/`rollback_config_version`/`resolve_config`) rather than building an eighth versioned-policy state machine -- the exact reuse the prompt package cites (`PLT-CFG-001..004`) and the same class of decision `OPS-173`'s own header records for its own capability (there: the engine's precedence model did *not* fit milestone versioning, so it deliberately forked; here: the engine's company/branch/role/user precedence fits Finance Configuration's own stated scope exactly, so it is reused directly). Finance is the first business-domain module in this repository to register a real `config_type` (confirmed via `grep -rn "insert into app.config_types"` across all 71 prior migrations -- only `PLT-121`'s own 10 bootstrap rows existed before this checkpoint).

Six new `config_type` codes are registered (`finance_dimensions`, `finance_numbering`, `finance_posting_map`, `finance_rounding`, `finance_recognition`, `finance_close_policy`), each wrapped by a Finance-specific `create_finance_config_draft`/`set_finance_config_items`/`publish_finance_config_version`/`discard_finance_config_draft`/`rollback_finance_config_version`/`resolve_finance_config` function that (a) rejects any `config_type_code` outside the six classes, (b) enforces `FIN:Edit` (draft/set-items/discard) or `FIN:Approve` (publish/rollback) via `app.evaluate_permission` -- the canonical, already-registered `FIN` permission catalogue (`PLT-111`), no new permission-catalogue row -- then (c) delegates the real mechanics to the unmodified generic engine function.

**Two-factor authority (disclosed, not a weakening of either layer)**: because the generic engine's own `app.create_config_draft`/`publish_config_version` internally call `app.check_config_object_authority`, which requires `tenant_admin`/Supreme for any non-global scope, drafting/publishing Finance Configuration requires **both** `FIN:Edit`/`FIN:Approve` (this capability's own RBAC layer) **and** `tenant_admin`/Supreme (inherited from the reused engine). A "Finance Admin" for this capability's own purposes (Prompt 191 section 26: "Finance Admin drafts; configured approvers publish") is therefore a `tenant_admin` (or Supreme) who has also been granted `FIN:Edit`/`FIN:Approve` via an ordinary role assignment -- proven directly in the db-test (a `tenant_admin` without `FIN:Edit` is rejected by this capability's own check; a `FIN:Edit`-holder who is *not* `tenant_admin` is rejected by the inherited engine-level check).

Per-class structural validation (`app.validate_finance_config_version`, run at publish/preview time) is bounded-enum-only: rounding mode/precision/order, numbering format-token rules (mirroring `PLT-125`'s own allowlist/exactly-one-`{SEQ}` logic as a **parallel** rule, since Finance numbering needs multiple per-document-class definitions within one version while `PLT-125`'s own validator assumes a single flat definition at the version level -- a disclosed, deliberate difference, not a silent fork), budget-control/accrual/revenue-cost-recognition enums, close-dependency shape. No tax/legal content anywhere (RPD-016/021) -- every mode is an accounting mechanism label, never a jurisdiction-specific statutory rule.

`finance_posting_map` account-code references are stored structurally only (regex-shaped) -- no Chart of Accounts exists yet in this dependency order (`191` precedes `192`). `app.preview_finance_config_impact` discloses every referenced code as `pendingChartOfAccountsRefs` rather than silently claiming resolution; `FIN-192`'s own migration is expected to `CREATE OR REPLACE FUNCTION app.publish_finance_config_version` to add the real existence check once `app.finance_accounts` exists (the established `CREATE OR REPLACE`-extends-a-prior-migration's-function pattern, e.g. `20260724290000_create_commercial_customer_account_conversion.sql`).

A new `app.get_finance_config_version_items` read path (`FIN:Edit`-gated) was added beyond the prompt's own literal API list: the generic engine deliberately gives `app.config_items` no direct `authenticated` grant at all ("draft content should never be casually browsable mid-edit"), and `app.resolve_config` only ever returns *published* items -- without this function, the admin UX's own re-edit flow would have no way to see a draft's current content before `app.set_finance_config_items`' full-replace semantics overwrite it. Disclosed here rather than silently added.

`app.finance_rounding_modes` is a small, bounded reference table of rounding *conventions* (half-up/half-even/down/up) -- a math convention, never a tax/legal rate. `FIN-194` (Currency and Exchange-Rate) is expected to reuse this same table for its own conversion rounding (Prompt 191 section 6 / Prompt 194 section 6's own "rounding tie-in" requirement) -- one catalogue, not two.
