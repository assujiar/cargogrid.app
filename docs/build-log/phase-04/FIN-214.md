## 3. Implementation

### 3.1 Design

**A cross-cutting audit capability, not a new domain slice.** Prompt 214's own objective ("implement and verify one financial field/record access policy across database, services, REST, GraphQL, UI, reports, exports, jobs, logs and support access") is a governance/verification task over FIN-191..213's own already-built field/record policy, not a request to build a second, parallel policy engine. Every Finance capability already embeds its own field/record control at the point it was built (`FIN:View margin` deny-outright on profitability, masked bank-account storage, `FIN:View`-gated reads throughout) — this checkpoint's job was to (1) make that policy explicit and mechanically checkable via the classification registry, (2) audit every surface Prompt 214 §4/§14/§15 names for parity, and (3) find and close any real gap, not invent new infrastructure where none is missing.

**One real, closeable gap found: a log-channel inference leak.** `app.audit_logs` (`PLT-116`) grants `authenticated` no direct table privilege; the only read paths, `app.query_audit_logs`/`app.export_audit_logs`, gate on `app.is_support_grant_authority()` alone — Supreme Admin **or tenant_admin**, never a domain-specific permission. FIN-212's own `app.calculate_finance_job_profitability` logged the entire calculated fact (`to_jsonb(v_fact)`) into that table, including `revenue_amount`/`cost_amount`/`profit_amount`/`margin_percent`/`source_invoice_ids`/`source_cost_version_ids`. A `tenant_admin` holding no `FIN:View margin` grant could therefore read every Job Order's full profitability figures via the generic audit-log export — exactly Prompt 214 §23's named "critical/high blocker" class ("leakage through ... log"). Confirmed by direct `grep 'capture_audit_event' -A4` across every one of the twenty-three Finance migrations (FIN-191..213): this is the *only* Finance audit-payload that carries data gated behind a sub-permission stricter than the generic audit-read gate — every other Finance `capture_audit_event` call logs only record ids, actor/reason context, or fields already visible to any `FIN:View` holder at or below the mutation's own required permission.

**Fix: redact, never remove the audit event itself.** `supabase/migrations/20260729280000_create_finance_field_level_security.sql` — `create or replace function app.calculate_finance_job_profitability`, identical signature, byte-for-byte identical body up to the audit call, whose payload is now an explicit allowlist (`id`, `job_order_id`, `version_number`, `is_current`, `status`, `blocked_reason`, `revenue_basis`, `calculated_at`) rather than `to_jsonb(v_fact)`. Supreme Admin's own unrestricted visibility (RPD-022) is unaffected and expected — this narrows a `tenant_admin`-only channel, not Supreme Admin's.

**Classification registry extended to Finance's own domain fields — the exact adoption-gate extension `DATA_CLASSIFICATION_STANDARDS.md` §8 named as deferred.** `scripts/data-classification/registry.ts` gains `FINANCE_REGISTRY` (5 entries, field-*group* granularity matching the standards doc's own 6-group model, not one entry per literal column) and `ClassificationEntry.protectedAction` (optional, `"FIN:View margin"`-shaped, ties an entry to the one seeded, `protected: true` permission action it classifies). `check-registry.ts` gains a new mechanical cross-check: every seeded protected `FIN` action that a real Finance migration actually references by name (statically parsed — `View margin`, confirmed; `View cost`, confirmed *absent*, disclosed as Operations-only so far, not a gap) has a matching `protectedAction` registry entry. A future Finance capability that starts enforcing a newly-seeded protected action without a matching entry fails `pnpm run data-classification:check`.

**API/report/export/job/support-access surfaces audited and found either already compliant or genuinely not-yet-applicable, disclosed rather than falsely claimed complete.** No REST/GraphQL endpoint exists for any domain yet (Finance included) — Prompt 214 §14's parity requirement is vacuously satisfied (one service layer, zero API surfaces to diverge). FIN-213's own Reports/export path reuses the identical RPCs the Dashboard already uses (a report cannot show data its caller could not already see live); no live worker executes an export in this environment (disclosed since `COM-159`). No Finance query result is cached anywhere. Support/impersonation access (`PLT-115`) is a distinct, already time/purpose-bound platform mechanism this checkpoint did not need to modify. Full detail and every disclosed boundary: `docs/standards/FINANCE_FIELD_POLICY_MATRIX.md`.
