## 3. Implementation

### 3.1 Design

**Reuse the already-checked read as the query engine; add only the aggregation that is genuinely missing -- OPS-182/OPS-183's own precedent, applied to Finance.** Of the six dashboard widgets Prompt 213 section 15 names (billing/invoice, AR aging, AP aging, cash, reconciliation/close, profitability), three already have a tenant-wide, already-FIN:View-checked summary query from a prior Finance checkpoint and are reused verbatim with zero new SQL: AR/AP aging (`app.get_finance_aging_summary`, FIN-210, called twice with a fixed `entity_type`) and profitability (`app.get_finance_profitability_summary`, FIN-212). The other three have no existing tenant/company-wide summary and are genuinely new: a billing/invoice funnel by status (`app.get_finance_dashboard_billing_summary`), a cash summary across every active bank account (`app.get_finance_dashboard_cash_summary` -- loops `app.get_finance_cash_position`, FIN-211, per account rather than duplicating its balance arithmetic), and a per-period close/reconciliation status (`app.get_finance_dashboard_close_status` -- the one genuinely new join, combining FIN-207's own `finance_period_locks` and FIN-209's own `finance_reconciliation_runs` against FIN-193's own `finance_fiscal_periods`).

**None of the three new functions is `security definer`; each performs its own explicit `FIN:View` check.** Same posture as every other Finance query function (FIN-210/FIN-211/FIN-212's own summary functions) -- no bypass of RLS, no elevated-privilege path.

**A period or account with no data reports an honest null/zero, never a fabricated figure.** A fiscal period with no lock event yet reports `lock_status = null` (not "locked"); one with no in-range reconciliation run reports `reconciliation_status = null` (not a fabricated pass); a not-yet-issued invoice (no AR open item) reports `open_amount = 0` via the billing summary's own `left join`.

**Profitability is fetched independently of the other five widgets so a stricter sub-permission denial never blocks the rest of the page.** Billing/aging/cash/close all share the same `FIN:View` baseline and are fetched together (`Promise.all`) -- a caller who lacks `FIN:View` entirely sees one page-level denial. Profitability additionally requires `FIN:View margin` (FIN-212's own "deny outright" gate, not a masked value) and is fetched in a separate `try`/`catch`; a caller with `FIN:View` but not `FIN:View margin` still sees every other widget, with only the profitability card rendering as an explicit permission-denied state -- mirrors the Operations Dashboard's own "masked without `OPS:View cost`" precedent for a stricter widget-level sub-permission, adapted to profitability's own established deny-outright (not mask) semantics.

**Reports reuse `app.report_types`/`app.report_runs`/`app.record_report_run` directly from COM-159 -- the same shared, schema-wide catalogue OPS-183 already registered its own six codes into.** This migration registers seven report codes: `finance_billing_summary`, `finance_ar_aging_summary`, `finance_ap_aging_summary`, `finance_cash_summary`, `finance_close_status_summary`, `finance_profitability_summary` -- one more than the five "areas" section 15 names, since AR aging and AP aging are two separately-runnable report codes over the one shared `get_finance_aging_summary` source function (a fixed `entity_type` argument the application-layer dispatch table supplies, not a second SQL function).

**Export is the one genuinely new mutation.** `app.enqueue_finance_report_export`, gated on `FIN:Export` (seeded since `PLT-111`, previously unused by any Finance capability). Cannot reuse COM-159's `app.enqueue_report_export` or OPS-183's `app.enqueue_ops_report_export` -- both hard-code their own module's permission action and are immutable prior migrations -- so this is a distinct, parallel entry point, identical body shape otherwise. Enqueues the identical `report_generation` job type via PLT-132's own `app.enqueue_job` and inserts into the identical shared `app.report_runs` table. **No live worker processes a `report_generation` job anywhere in this repository** -- the same disclosed `NOT_RUN` condition COM-159/OPS-183 already carried, unchanged by this checkpoint.

**No new table.** Additive migration, functions and catalogue rows only.

**One db-test fixture-collision fix found and applied during authoring, before commit.** This checkpoint's own initial db-test fixture reused an email (`jane@dashtest.test`), company name and vendor-rate code that `scripts/db-tests/operations-dashboard.sql` and `scripts/db-tests/commercial-dashboard.sql` already use for their own unrelated fixtures. Because `scripts/db-tests/run.sh` runs every `*.sql` file against one cumulative disposable database (never reset between files) and at least one downstream file's own lead lookup (`select ... from app.leads where email = ...`) carries no tenant scope, the alphabetically-earlier `finance-dashboard.sql` fixture's row was silently picked up by `operations-dashboard.sql`, breaking its own lead-status-transition assertion. Fixed by renaming every fixture identifier this checkpoint introduces to a distinctive, collision-free value (`jane@acmefindash.test`, "Finance Dashboard Test Co", `VENDOR-FINDASH-1`); confirmed the full `db:test` suite passes end-to-end afterward. No other file was modified.
