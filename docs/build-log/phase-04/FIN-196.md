## 3. Implementation

### 3.1 Dependency-order scope decision (disclosed, migration header)

`FIN-197` (Invoice) does not exist yet at this checkpoint -- per `189_FINANCE_README.md` section 4, Accounts Receivable (196) precedes Invoice (197) in the capability catalogue. This migration therefore builds the AR open-item subledger *primitive* generically (`source_document_type` bounded to `invoice`/`opening_balance`), the same "build the shared primitive first, the next capability becomes its first real caller" pattern `FIN-191`'s own `finance_posting_map` forward reference already established. `FIN-197`'s own `app.issue_finance_invoice` is expected to call `app.post_finance_ar_open_item` directly once it exists; `FIN-198` (Receipt and Payment Allocation) is expected to call `app.apply_finance_ar_allocation`/`app.reverse_finance_ar_allocation` directly.

GL posting scope: per `189_FINANCE_README.md` section 4, AR/AP and Source Subledgers (`FIN-202`) and the Double-Entry Journal (`FIN-203`) are later capabilities. This migration captures a `posting_period_id` (resolved via `FIN-193`'s own `app.resolve_finance_period_for_date`, rejecting a date with no open period) and full source lineage, but creates zero GL journal line -- disclosed, not silently promised.

Status is a pure function of balance (`open`/`partial`/`paid`), computed only by the allocation functions, never accepted from a caller. Collection hold is an orthogonal flag (`is_held`), not a status value. Posted-item correction to a genuinely wrong `original_amount` remains `FIN-206`'s own scope -- this migration exposes no direct-edit or void path for a posted open item; balance correction is only ever via the governed `app.reverse_finance_ar_allocation` reversal path.

### 3.2 Schema — `supabase/migrations/20260729100000_create_finance_accounts_receivable.sql`

`app.finance_ar_open_items` (idempotent unique on `tenant_id, source_document_type, source_document_id`; `open_amount` a generated column), `app.finance_ar_open_item_events` (append-only audit trail; `idempotency_key` unique per open item, guarding allocate/deallocate replay). Functions: `app.check_finance_ar_authority`, `app.post_finance_ar_open_item` (idempotent posting; `invoice` requires `FIN:Edit`, `opening_balance` requires `FIN:Approve` per Prompt 196 section 24's own "approved migration/opening balance" exception; period-aware, rejects a date with no open fiscal period), `app.place_finance_ar_hold`/`app.release_finance_ar_hold` (deliberately split authority -- `FIN:Edit` places, `FIN:Approve` releases), `app.apply_finance_ar_allocation` (row-locked, idempotent, rejects over-allocation), `app.reverse_finance_ar_allocation` (governed reversal, `FIN:Approve`-gated, mandatory reason), `app.list_finance_ar_open_items`, `app.get_finance_ar_open_item_activity`, `app.get_finance_ar_exposure_summary` (internal Finance credit-exposure aggregate; customer-facing visibility deferred to Step 13).
