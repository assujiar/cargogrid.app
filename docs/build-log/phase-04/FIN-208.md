## 3. Implementation

### 3.1 Design -- the real gap, not a rebuild

**Five domains already ship real idempotent creation** (FIN-197 invoice, FIN-198 receipt allocation, FIN-200 vendor bill, FIN-201 settlement, FIN-203 journal): each "select existing row by idempotency_key, return it unchanged on retry" -- genuinely idempotent for a byte-identical retry. **The gap this checkpoint closes**: none of them detected a *different* payload arriving under a reused key; each one silently returned the *original* result instead of rejecting the mismatch. Prompt 208 section 23/25 name this exactly: "reject same key with different fingerprint" / "mismatch is a conflict."

**One shared claim ledger, `app.finance_idempotency_claims`.** `app.claim_finance_idempotency_key` atomically inserts a new claim (`insert ... on conflict do nothing returning *`) or, on conflict, reads the existing claim and compares its stored `request_fingerprint` -- a match returns the identical claim, a mismatch raises `finance_idempotency_fingerprint_conflict` before any domain-specific row is ever written. `app.complete_finance_idempotency_claim` links the claim to its one real result (idempotent -- a retried complete on an already-completed claim returns it unchanged); `app.fail_finance_idempotency_claim` records a distinct terminal outcome for a genuinely failed attempt, disclosed but not wired to any caller this checkpoint (every domain function this checkpoint touches only reaches `complete` on success; a raised exception mid-transaction rolls the claim insert back too, so no orphaned `claimed` row survives a synchronous failure today).

**One real adopter this checkpoint: `app.create_finance_journal_draft` (FIN-203).** `CREATE OR REPLACE`d to compute a canonical fingerprint (`md5` of a `jsonb_build_object` over company/date/currency/lines) and call the shared claim first, replacing its own prior ad hoc "select by idempotency_key" check. The other five listed domains (invoice, receipt allocation, vendor bill, settlement, imports) keep their own existing idempotent-creation behavior unchanged this checkpoint -- a disclosed forward-integration bound matching Prompt 208 section 4's own "one idempotent posting protocol... across invoice, bill, receipt allocation, settlement, subledger, journal, reversal and imports" as the target end-state, not a claim that every one of those is wired today.

**One real implementation snag found and fixed during authoring, before commit.** A pre-existing FIN-203 db-test (`finance-journal.sql`) deliberately retried the same idempotency_key with a *different* single-line payload specifically to prove the old, permissive "any retry returns the original" contract. That assertion now correctly fails under the new, stricter contract -- exactly the gap this checkpoint exists to close. Fixed by splitting that test into two assertions: a genuinely byte-identical retry (still returns the original journal unchanged) and a mismatched-payload retry (now a named `finance_idempotency_fingerprint_conflict`, the new and *better* guarantee). This is a deliberate, disclosed tightening of a pre-existing test's own assumption, not a regression.

**Known, disclosed race (Prompt 208 section 23's own "simultaneous conflicting claim").** Two genuinely concurrent callers racing the exact same brand-new key both observe a `claimed` (not yet `completed`) row and both proceed toward the domain insert; the loser fails on that table's own pre-existing idempotency unique constraint (e.g. `finance_journals_idempotency_unique`), a real, safe rejection (no double effect) but not yet surfaced under its own distinct claim-level exception. Documented as a bound, not silently claimed to be fully solved -- disambiguating "is this genuinely a different concurrent caller, or my own retry" would need a session/request nonce this checkpoint does not introduce.
