## 3. Implementation

### 3.1 Design

**Aging is derived, never manually editable** (Prompt 210 section 24): every row this checkpoint returns is a live read of FIN-196/199's own `finance_ar_open_items`/`finance_ap_open_items` -- there is no stored summary balance table anywhere in this migration. The one governed, versioned object is the bucket *definition* (`app.finance_aging_bucket_configs`), never the aging numbers themselves.

**Bucket boundaries are explicit, non-overlapping, contiguous and versioned.** `app.validate_finance_aging_buckets` rejects an empty set, a missing field, a first bucket that does not cover zero/negative days-overdue, a non-open-ended final bucket, and any gap/overlap -- each a distinct named exception. `app.set_finance_aging_bucket_config` never edits a prior version: it deactivates the tenant's own current active row and inserts a brand-new, incremented version. A tenant with no configured override resolves to one disclosed system default (`version = 0`, a 5-bucket Current/1-30/31-60/61-90/90+ set), never a silent empty result.

**Disclosed bound shared with FIN-209's own as-of design**: each open item's own real business date column bounds inclusion (`invoice_date` for AR, `bill_date` for AP); `open_amount` reflects the item's *current* balance (FIN-196/199's own generated column), not a full historical reconstruction of every past allocation/settlement event as it stood on a prior as-of date.

**Summary always reconciles exactly to detail**, since `app.get_finance_aging_summary` aggregates the identical rows `app.get_finance_aging_report` returns (calling it directly in its own `FROM` clause) -- proven directly in the db-test (both total exactly 380 across four real seeded open items).

**Route-count correction, disclosed.** The `FIN-209` checkpoint's own build log stated "75 routes (74 baseline + 1 new)"; a precise recount at this checkpoint (`grep -c` over the real `next build` route listing, not an incremented assumption) found the actual pre-`FIN-210` count was **73 routes**, not 74/75. The discrepancy traces to an uncorrected arithmetic slip carried forward across `FIN-206`-`FIN-209`'s own prose route-count claims -- the underlying build artifact itself was always correct; only the narrated count in prior build logs' own text drifted. Not corrected retroactively in already-pushed commits (out of scope for this checkpoint); this checkpoint's own count below is directly re-verified.
