## 3. Implementation

### 3.1 Design

**Prompt 216's own scope ("repair every in-scope critical/high finding from Prompt 215") is empty by definition -- FIN-215 closed with zero critical/high finding.** This is not this checkpoint skipping work; it is the correct, evidence-based consequence of FIN-215's own honest outcome (`docs/build-log/phase-04/FIN-215.md` §3.1/§3.3: every real cross-capability integration point held on the first fully-corrected run; the three defects found and fixed were fixture-authoring mistakes, never production code). There is no finding ledger to triage, no root cause to repair, no bounded migration to author.

**Rather than close with no new evidence at all, this checkpoint performs the hardening audit Prompt 216 §16 itself names, using FIN-215's clean baseline as the starting point, and converts its strongest positive finding into a real, executable regression guard.** Prompt 216 §16 names five priority areas: tenant/customer/field leakage, normal-role posted mutation, bank/tax/file exposure, support/MFA bypass, secret/log issues. Four of these five were already directly audited and either confirmed clean or fixed at a prior checkpoint (tenant/customer isolation: every Finance db-test's own cross-tenant section, all 24 capabilities; field leakage and secret/log issues: `FIN-214`'s own dedicated audit and fix; bank/tax exposure: `FIN-211`'s masked storage, re-confirmed clean on this checkpoint's own re-audit). The fifth, **normal-role posted mutation** (the concrete mechanism behind RPD-022/023's own "no tamper-proof claim" language), had never been checked *exhaustively and mechanically* across the whole Finance schema at once -- each capability's own db-test proves it locally for its own 1-3 tables, but no single checkpoint had enumerated every one of the 38 real Finance tables `authenticated` holds any privilege on and confirmed the privilege is `SELECT`-only everywhere, in one place.

**The check: a direct `grep` across every Finance migration for `grant insert`/`grant update`/`grant delete` to `authenticated` found zero matches (already true, no gap existed) -- confirmed and pinned as a real db-test regression guard**, `scripts/db-tests/finance-integrity-security-hardening.sql`, enumerating all 38 tables and asserting `has_table_privilege('authenticated', ..., 'INSERT'|'UPDATE'|'DELETE')` is false for every one (plus a same-shape `anon` check). This means a normal Finance role -- even one holding `FIN:Approve` -- cannot bypass a governed reversal/adjustment/lock/idempotency path by mutating a posted row directly; every real mutation is reachable only through an RPC, which enforces the governed path itself. The value this checkpoint adds is not the underlying fact (already true) but the exhaustive, mechanical, dated proof of it, and a regression guard that fails loudly if a future migration ever widens a grant.

**One residual risk disclosed, not silently worked around (Prompt 216 §22/§24): MFA is not enforced anywhere in this repository yet, Finance included.** Confirmed by direct inspection: MFA/identity infrastructure exists at the Platform Core layer (`PLT-1xx`, `server/contracts/auth/identity.ts`) and Commercial's own credit control (`COM`) reads identity data, but no domain -- Commercial, Operations, or Finance -- has wired per-action step-up MFA for a privileged approval. This is a repository-wide state this checkpoint did not introduce and cannot unilaterally fix within Finance's own bounded scope (Prompt 216 §22: "if repair requires new authority, source decision or later-phase work, keep Phase 4 blocked and record exact owner/dependency rather than weaken controls"). It is recorded here as an explicit, tracked, cross-domain dependency -- not represented as fixed, not silently ignored.
