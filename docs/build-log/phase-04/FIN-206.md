## 3. Implementation

### 3.1 Design

**Closes two disclosed forward references named by earlier checkpoints, not a fresh mechanism invented from nothing.** FIN-203's own migration comment states "Reversal is explicitly out of scope... reverse posted journal via FIN-206"; FIN-202's own migration comment reserves `app.finance_subledger_batches.status = 'reversed'` "for FIN-206 (Reversal and Adjustment), never set by this migration." This checkpoint closes both.

**One governed correction table, two correction types, one shared lifecycle.** `app.finance_journal_corrections` carries `draft -> submitted -> approved -> posted` (or `discarded` from `draft`/`submitted`) for both a `reversal` (system-derived exact opposite lines of the original posted journal) and an `adjustment` (preparer-supplied balanced lines, validated up front by FIN-203's own shared `app.validate_finance_journal_line_balance` -- never a second, competing balance check). A partial unique index (`tenant_id, original_journal_id where correction_type = 'reversal' and status <> 'discarded'`) enforces "one full reversal per eligible effect" (Prompt 206 §24); no such cap applies to adjustment, since multiple independent reclassifications against one original are legitimate.

**The original posted journal is never rewritten.** FIN-204's own posted-journal-integrity triggers already make a normal-role `UPDATE`/`DELETE` against a posted `app.finance_journals` row impossible; this checkpoint does not need to (and does not) touch that protection. Posting a correction calls FIN-203's own `app.create_and_post_finance_system_journal` with `source_type = 'correction'` -- one more posted journal, linked by `correction_journal_id`, never a mutation of the original row.

**Extending `app.create_and_post_finance_system_journal` required dropping the old overload, not just `CREATE OR REPLACE`ing it.** Appending a trailing `p_lock_scope text default 'gl'` parameter changes the function's own signature; `CREATE OR REPLACE FUNCTION` alone would have left the prior 9-argument overload in place alongside the new 10-argument one, and a 9-argument call site (FIN-202's own `app.post_finance_subledger_batch`) became ambiguous between them (`function ... is not unique`, caught by this checkpoint's own `db:test` run before commit). Fixed with an explicit `drop function if exists ...(uuid, uuid, text, uuid, date, text, jsonb, uuid, text);` immediately before the new `create function`. The `p_lock_scope` parameter itself is a disclosed forward reference for `FIN-207` (Period Lock) -- accepted and threaded through today, not yet enforced against any lock table, since none exists until the next checkpoint.

**Two `CHECK` constraints from FIN-203's own migration also needed extending**, each caught the same way (a real `db:test` failure, not a design guess): `finance_journals_source_type_check` (`'manual' | 'subledger'`) and `finance_journals_source_check` (source_id nullability tied to source_type) each only recognized the two source types FIN-203 shipped with. Both are dropped and re-added with `'correction'` included -- an additive constraint replacement, not an edit to any existing row, and every already-posted `manual`/`subledger` row continues to satisfy the new, strictly wider check unchanged.

**Subledger-batch reversal is a real, direct update, not inferred.** When a reversal's original journal has `source_type = 'subledger'`, posting the reversal also sets that source `app.finance_subledger_batches` row's own `status = 'reversed'` (looked up via `gl_journal_id = original_journal_id`) -- closing FIN-202's own disclosed reference exactly. Disclosed bound, stated in the migration's own header: this does **not** retroactively touch the AR/AP open item's own balance, which remains FIN-196/199's own separately-governed `app.reverse_finance_ar_allocation`/`app.reverse_finance_ap_settlement` path -- two different corrections at two different layers, never silently conflated.

**Correction into the current open period when the original's own period is locked** (Prompt 206 §22's own alternative flow) falls out of reusing FIN-203's own `app.resolve_finance_period_for_date` against the correction's own `correction_date` (independent of the original journal's own `journal_date`) -- no new period-resolution logic was written for this checkpoint.

### 3.2 Schema — `supabase/migrations/20260729200000_create_finance_reversal_adjustment.sql`
