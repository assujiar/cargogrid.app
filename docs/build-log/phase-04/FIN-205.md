## 3. Implementation

### 3.1 Design -- what already existed, and what this checkpoint actually adds

**Baseline, already real, disclosed not rebuilt**: each of the six Finance document types this repository has built so far -- invoice (FIN-197), vendor_bill (FIN-200), receipt (FIN-198), settlement (FIN-201), subledger_batch (FIN-202), journal (FIN-203/204) -- already owns its own concrete status enum and its own authority-checked, database-enforced transition functions (submit/discard/approve/execute/post/reversal, whichever subset applies). "Database constraints preventing illegal normal-role transitions" (Prompt 205 section 13) already exist at the row level, proven by each domain's own db-test suite; this checkpoint does not fork a second, competing state machine on top of them.

**What this checkpoint actually adds**: one canonical lifecycle vocabulary (`draft` / `in_review` / `approved` / `posted` / `corrected` / `discarded`) and a shared editability matrix, mapped from all 26 real (entity_type, concrete_status) pairs that exist across the six domains today, plus one shared cross-domain reader (`app.get_finance_lifecycle_record_state`) every Finance detail page can call for a consistent "canonical state, allowed actions, why a disabled action is disabled" render -- the actual gap Prompt 205 section 15 names, since no such shared read existed anywhere before this checkpoint.

**Canonical-state coarsening, disclosed and intentional**: a settlement's own `approved` and `executed` concrete statuses both map to the single canonical `approved` bucket -- execution records an external payment reference with zero accounting effect (FIN-201's own design), so no posting-relevant distinction exists between them for display purposes. `concrete_status` is always returned alongside `canonical_state` so no caller loses the detail, and `allowed_actions` is resolved from the real concrete status, not the coarsened bucket -- `approved` allows `['execute']` while `executed` allows `['post']`, proven directly in this checkpoint's own db-test.

**`is_editable` is `false` for every one of the 26 rows, structurally, not a placeholder**: no Finance document table in this repository yet exposes a direct field-level update-in-place function for a draft row -- every one of FIN-197/198/200/201/203's own build logs already disclosed that amending a prepared draft requires discard-and-reprepare, never a partial edit. This checkpoint records that fact honestly rather than fabricating an edit affordance that does not exist.

**`posted_trigger_protected` is `true` only for journal's own `posted` row** -- the one table-level trigger FIN-204 actually built. Every other posted row (`invoice.issued`, `vendor_bill.posted`, `settlement.posted`, `subledger_batch.posted`) still relies on the grant-only protection FIN-197 disclosed as the repository-wide `PLT-118` baseline, not a table-level trigger; the matrix exposes that real, current distinction rather than implying uniform protection that does not yet exist.

**Reversal/correction itself is explicitly FIN-206's own scope** (Prompt 205 section 32 names "corrected" only as a canonical *state*, never a new correction mechanism) -- this checkpoint only records the mapping for the one already-real correction path that exists today (settlement's own `reversed`, built at FIN-201). `subledger_batch.reversed` and `receipt.void` are seeded but not yet reachable by any real function call today (FIN-206's own disclosed forward reference for the former, no void function built for the latter), each labelled as such in the migration's own header rather than silently implied to be live.

**No new cross-domain listing/inbox view is built** -- each domain's own already-shipped paginated list function remains the per-domain listing surface; this checkpoint's own value-add is the canonical-state-and-editability layer consumed per record, a disclosed bound matching this checkpoint's own named objective (lifecycle/editability, not a new work-queue UI).

**Zero N+1 in the UI (Prompt 205 section 17)**: every one of the six Finance list pages already fetches `entityType`-equivalent context and the row's own concrete `status` as part of its existing list query. Rather than issuing one extra RPC call per row (or even per page) to label it, each page renders its own canonical-state badge from a static TypeScript mirror of the database matrix (`server/contracts/lifecycle/lifecycle-editability-matrix.ts`), a disclosed, must-stay-in-sync copy of the same 26 rows -- the same "mirrors X's own convention" pattern this repository already uses elsewhere (e.g. FIN-194's own currency-code seed). The database table and `app.get_finance_lifecycle_editability`/`app.get_finance_lifecycle_record_state` remain the authoritative source for anything requiring server-side enforcement or a single-record detail read; the client-facing mirror is display-only.

### 3.2 Schema -- `supabase/migrations/20260729190000_create_finance_lifecycle_state_control.sql`

`app.finance_lifecycle_editability_matrix` (26 seed rows, one per real (entity_type, concrete_status) pair, RLS-enabled with a `for select to authenticated using (true)` policy mirroring FIN-194's own `finance_currencies` reference-table convention); `app.get_finance_lifecycle_editability(entity_type, concrete_status)` (raises `finance_lifecycle_state_unmapped` rather than a silent default); `app.get_finance_lifecycle_record_state(tenant_id, entity_type, record_id, actor_auth_user_id)` (dispatches to the correct table by entity_type, re-uses each domain's own already-vetted `check_finance_*_authority('View', ...)` function directly -- never a new, parallel authority mechanism -- and returns one consistent jsonb shape). Zero prior migration file edited, zero existing function body changed.

### 3.3 Service layer and UI

`server/contracts/lifecycle/lifecycle.ts` (Zod schemas for the entity-type/canonical-state enums and the jsonb record-state shape); `server/contracts/lifecycle/lifecycle-editability-matrix.ts` (the static TypeScript mirror described above, with a safe non-actionable fallback for an unrecognized pair rather than throwing during a page render); `server/queries/lifecycle.ts` (a thin typed wrapper around `app.get_finance_lifecycle_record_state`; no mutations file -- this checkpoint adds no new mutation surface, only a shared read, the same disclosed bound FIN-202's own subledger explorer already established).

UI: all six existing Finance list pages (`invoices`, `vendor-bills`, `receipts`, `settlements`, `subledger`, `journals`) now render a new "Lifecycle" column showing the canonical-state badge (`FINANCE_LIFECYCLE_CANONICAL_STATE_TONE_MAP`, new in `components/domain/status-tone-map.ts`) alongside each domain's own existing concrete-status badge, plus the human-readable `lockedReason` text when one applies -- "disabled actions explain why" (Prompt 205 section 15), rendered from the static mirror with zero added network cost.
