## 3. Implementation

### 3.1 Scope boundaries and the RPD-016/021 "no invented rate" boundary (disclosed, migration header)

The migration's own header (`supabase/migrations/20260729090000_create_finance_tax_baseline.sql`) discloses this at length; summarized here:

- **`app.finance_tax_codes` seeds five labels only** (`PPN`, `PPH21`, `PPH23`, `PPH4_2`, `EXEMPT`) -- statutory classification names, not rates, the same class of factual identifier `FIN-194`'s own currency-code seed (`IDR`/`USD`/`SGD`/`EUR`/`JPY`) already established.
- **Zero tax rate is ever seeded as `approved`.** Exactly one illustrative `app.finance_tax_rule_versions` row is seeded: `is_example_fixture = true`, `status = 'draft'`, `rate_value = 0` -- a structurally inert placeholder. `app.approve_finance_tax_rule` refuses to activate any row with `is_example_fixture = true` (`finance_tax_rule_example_fixture_not_activatable`), proven directly in the db-test. `app.create_finance_tax_rule_draft` (the only reachable INSERT path from the service layer/UI) has no parameter for `is_example_fixture` at all -- only this migration's own one-time seed statement can ever create such a row.
- **`rate_basis` is a bounded enum** (`percentage`, `fixed_amount`) only -- there is no `formula` option to select, which is how Prompt 195 section 23's "keep activation blocked for ... unsupported formula" is satisfied structurally (a `CHECK` constraint / explicit rejection in `app.create_finance_tax_rule_draft`, before a row can even exist) rather than merely by convention.
- **Approval requires attached evidence** (`evidence_reference_file_id` or a non-empty `evidence_note`) -- enforced both by a `CHECK` constraint on the table and inside `app.approve_finance_tax_rule` itself (defense in depth), per Prompt 195 section 33's "only SME-approved effective rules can calculate posting tax."

### 3.2 Reuse decisions (disclosed)

Lifecycle shape (`draft -> approved -> archived`) and the tenant-then-global deterministic resolution order are `FIN-194`'s own `app.finance_exchange_rates` pattern, reused directly -- a tax rule and an exchange-rate quote are structurally the same shape (a versioned, effective-dated, approval-gated numeric fact). Rounding tie-in: `app.calculate_finance_tax` resolves the tenant's own effective `finance_rounding` config (`FIN-191`), key `tax_calculation` falling back to `default` falling back to the same disclosed safe default (`round_half_up` at 2 decimal places) `FIN-194`'s own `app.convert_finance_amount` already established -- one rounding authority, never a second. Account mapping references `app.finance_accounts` (`FIN-192`) directly, validated active+postable+same-tenant at draft-creation time; actual double-entry GL posting of tax accounts remains `FIN-202`/`FIN-203`'s own scope (not built yet, per `189_FINANCE_README.md` section 4's dependency order) -- this migration captures only the governed account-mapping reference, the same disclosed forward-reference discipline `FIN-191`'s own `finance_posting_map` class already established.
