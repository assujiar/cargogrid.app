## 3. Implementation

### 3.1 Design

**Finance-grade counterpart of OPS-179's own operational snapshot, deliberately reading a different revenue basis.** `OPS-179`'s `app.job_profitability_snapshots` reads `app.job_orders.revenue_snapshot` verbatim -- the Commercial-accepted *sell price*, an operational estimate. This capability instead reads the actual *billed* amount from every `status = 'issued'` `app.finance_invoices` row for the Job Order (`subtotal_amount`, excluding tax -- a pass-through liability, never a margin component). `revenue_basis` is recorded on every fact row (fixed to `'billed'` this checkpoint, a real CHECK constraint) so operational estimate and accounting P&L are never conflated (Prompt 212 section 24).

**Cost reuses OPS-178's own governed evidence -- disclosed, not invented.** The sum of every currently-approved (`is_current = true and status = 'approved'`) `OPS-178` actual-cost version across every Shipment Order belonging to the Job Order, the identical source `OPS-179` already established. No separate Finance-posted, job-dimensioned cost source exists anywhere in this repository yet (`app.finance_vendor_bills` carries no Job Order/Shipment Order linkage) -- a real, named bound, not a fabricated second cost source.

**No shared-cost/overhead allocation engine, disclosed.** Every OPS-178 cost component is already directly attributable to exactly one Shipment Order (and therefore exactly one Job Order); there is no indirect/shared-cost table anywhere in this repository for an allocation engine to distribute. Prompt 212 section 24's "governed allocation" requirement is satisfied by direct, versioned attribution of every source line, not by a rule engine with nothing real to allocate. A genuine shared-cost allocation-rule engine is left for a later capability.

**Currency discipline mirrors OPS-179, extended to a second source.** No FX conversion. A currency mismatch across multiple issued invoices for the same Job Order, or between the resolved revenue currency and any contributing cost version, makes the whole fact `unavailable` with a named `blocked_reason` (`no_billed_revenue`, `no_approved_cost`, or `mixed_currency`) -- never a fabricated figure.

**Versioned fact, historical versions remain linked, never rewritten in place.** `app.finance_job_profitability_facts` is `is_current`-exclusive (partial unique index); the first calculation needs no reason, every later recalculation of an existing current fact requires one -- the identical discipline `OPS-179`'s own `app.calculate_job_profitability` established.

**Deny outright, no partial projection -- stricter than OPS-179's own base-table grant.** Every non-shell column on this fact row is margin-shaped (Prompt 212 section 16: "aggregate suppression prevents inference; customer users cannot see internal profitability"). Unlike `OPS-179`'s `job_profitability_snapshots` (which grants `authenticated` direct, RLS-scoped select against the base table alongside its own masked directory view), this table grants `authenticated` no table privilege at all -- the only read paths are `app.get_finance_job_profitability` and `app.get_finance_profitability_summary`, both denying outright (no partial result) without `FIN:View margin`, the same "either fully visible or fully hidden" precedent `OPS-178`'s own `app.shipment_actual_cost_components` established.

**`FIN:View margin` is already a seeded permission action.** The base permission catalogue (`20260716103445_create_roles_permissions.sql`) registers `('View margin', 'FIN', 'sensitive', true)` from day one -- this migration registers no new catalogue row; `app.has_view_finance_margin` is simply this capability's own thin wrapper.

**Aggregation is grouped, never a raw per-row export.** `job_order_id`'s own `account_id` (customer), `org_unit_id` (branch) and `cargo_service_snapshot ->> 'service_type'` (service) are the only grouping dimensions this checkpoint supports -- exactly the "job, customer, service, branch" set Prompt 212 section 3 names. Aggregation groups by `(dimension, currency)`, so a multi-currency book of business surfaces as separate rows, never a blended total.

**One db-test authorization fix found and applied during authoring, before commit.** A tenant B Finance Manager role carrying the (protected) `FIN:View margin` permission was initially self-assigned in the fixture, which `app.assign_role`'s own `self_escalation` guard correctly rejects for any protected-permission role; fixed by introducing a distinct Admin B actor to perform the assignment, the same pattern `OPS-179`'s own db-test already uses for `OPS:View margin`.
