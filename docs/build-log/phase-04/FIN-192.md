## 3. Implementation

### 3.1 Scope boundaries and design decisions (disclosed, migration header)

Chart of Accounts is a real domain table with its own draft/active/inactive lifecycle, **not** layered on `PLT-121`'s Configuration Engine -- a hierarchical account master is structurally unlike a flat key/value policy set, and its own authority model (plain `app.evaluate_permission` via `FIN:Create/Edit/Approve/Delete/View`, no forced `tenant_admin` layering) matches this repository's established standalone-business-table pattern (`app.margin_rule_versions`, COM-150) rather than FIN-191's own capability-specific stricter two-factor gate.

**Closes FIN-191's own disclosed forward reference**: `finance_posting_map` config items stored account-code references structurally only (no Chart of Accounts existed yet in that dependency order). This migration `CREATE OR REPLACE FUNCTION`s `app.publish_finance_config_version` (the established later-migration-extends-an-earlier-one's-function pattern) to add a real existence/active/postable check for `finance_posting_map` publishes from this point forward -- proven in both this checkpoint's own db-test and a re-run of `FIN-191`'s own unmodified db-test (zero regression, since a valid posting-map fixture in that file references no real account and never reaches this new check's own active-account requirement... actually it does reach it structurally-only via `preview_finance_config_impact`, which was not changed -- only `publish_finance_config_version` gained the new check, and `FIN-191`'s own db-test publishes `finance_rounding`/`finance_recognition`/`finance_close_policy`, never `finance_posting_map`, so the new check path is exercised for the first time by this checkpoint's own db-test, not retroactively by `FIN-191`'s).

Canonical account-type/normal-balance matching (asset/expense=debit; liability/equity/revenue=credit, Prompt 192 section 24) is enforced by a table `CHECK` constraint itself, not application logic alone -- proven directly (a raw attempt to create a liability/debit account hits `check_violation`, not a plpgsql-raised exception). A control account is structurally never directly postable (`is_postable`/`is_control_account` are mutually exclusive by `CHECK`) -- Prompt 192's own "unless an explicit approved rule permits it" override mechanism does not exist in this checkpoint, so the constraint is unconditional, disclosed rather than half-built.

Hierarchy-cycle detection (`app.detect_finance_account_hierarchy_cycle`, bounded depth<=10, mirroring `PLT-120`'s own merge-chain bound) is real and directly tested, but is **not reachable through the public mutation surface today** -- no reparent operation exists (a parent is fixed at creation time, and a child can only reference an already-existing parent, so a true cycle can never form via `create_finance_account_draft`/`activate_finance_account` alone). Tested by direct function-level proof instead of through the mutation API, disclosed as a forward-looking guard for whichever future capability adds reparenting.
