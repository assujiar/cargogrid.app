## 3. Implementation

### 3.1 Design

**No live bank-provider adapter, disclosed.** Prompt 211 section 24 explicitly bars "unapproved payment-provider behavior." Statement ingestion (`app.import_finance_bank_statement`) accepts an already-parsed, caller-supplied batch of lines -- the same "staged idempotent import" idiom FIN-194's own exchange-rate import already established -- never a direct third-party API connection.

**Bank account numbers are masked at rest.** `account_number_last4` is bounded to 1-4 characters by its own `CHECK` constraint; the full account number is never stored anywhere in this schema.

**Real deduplication, not merely an application check.** `finance_bank_transactions` carries a unique `(bank_account_id, line_hash)` index; `line_hash` is a deterministic digest of (account, date, direction, amount, reference). A re-imported or overlapping line is silently skipped via `on conflict ... do nothing` -- proven directly in the db-test by re-importing a statement that overlaps one already-imported line and confirming only the genuinely new line is counted.

**Ties into the one already-real cash-affecting GL activity in this repository.** FIN-198's own receipt allocation debits the shared `cash_default` posting-map key and FIN-201's own settlement credits it (confirmed by direct inspection of `20260729160000_create_finance_subledger.sql` before writing this migration -- no new posting-map key was invented). `app.get_finance_cash_position` reconciles the statement-derived balance against that identical `cash_default`-mapped GL account, using FIN-209's own already-established as-of-bounded-by-resolved-period-end technique (`app.finance_subledger_batches` still carries no direct business posting-date column).

**Governed match/unmatch.** `app.match_finance_bank_transaction` (`FIN:Edit`) links a transaction to its own receipt/settlement/manual source; `app.unmatch_finance_bank_transaction` (`FIN:Approve`) requires a reason and preserves the row (never deletes), matching Prompt 211 section 24's own "automatic match... may still require human governance."

**One real implementation snag found and fixed during authoring, before commit.** `app.get_finance_cash_position`'s own `RETURNS TABLE` column name `bank_account_id` collided with the identical column name on `app.finance_bank_transactions` inside the function body, producing a genuine `column reference "bank_account_id" is ambiguous` error caught by the first `db:test` run -- fixed by qualifying the query with an explicit table alias.
