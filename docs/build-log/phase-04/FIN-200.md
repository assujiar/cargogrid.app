## 3. Implementation

### 3.1 Design (disclosed, migration header) -- the vendor-side mirror of FIN-197

Vendor Bill is the last capability in this session's authorized range and, unlike `FIN-197` (Invoice), both of its own upstream primitives already exist: `FIN-195` (Tax Baseline, for optional tax-line computation) and `FIN-199` (Accounts Payable, for period-aware posting). `app.post_finance_vendor_bill` therefore calls `app.post_finance_ap_open_item` directly, exactly the way `FIN-197`'s own `app.issue_finance_invoice` calls `app.post_finance_ar_open_item`.

**Source-of-truth boundary**: a vendor bill is prepared from one verified, `approved` and `is_current` Operations actual cost (`OPS-178`'s own `app.shipment_actual_costs`), summing only the components whose `source_type = 'vendor'` and `vendor_id` matches the requested `vendor_master_id` -- an internal-cost component (e.g. warehouse handling) is structurally excluded, never re-typed or re-entered.

**Basic-match variance** (Prompt 200 section 16's own bounded MVP scope): an optional `p_vendor_stated_amount` parameter represents the amount a human read off the vendor's own paper/PDF bill (AI/OCR extraction assistance and file capture are explicitly out of this migration's scope, disclosed not silently promised). When supplied, `variance_amount = |vendor_stated_amount - subtotal|` against a small fixed 1.00 tolerance -- a bounded MVP tolerance, deliberately distinct from `FIN-191`'s own `finance_rounding` config (which governs rounding computation, not match tolerance). A material variance sets `variance_status = 'requires_approval'`, disclosed to the approver at approval time, but does not itself block approval -- Phase 4 has no configurable threshold-routing engine, the same class of disclosed-scope boundary `FIN-199`'s own hold/settlement split already established. No `vendor_stated_amount` supplied means the bill is trusted as computed directly from source components (`variance_amount = 0`).

**Vendor reference boundary**: `vendor_master_id` references `app.master_records` (`master_type_code = 'vendor'`, registered by `OPS-172`, `canonical_status = 'active'`) -- the identical reference `FIN-199`'s own `finance_ap_open_items.vendor_master_id` already established, itself the same vendor identity `app.shipment_actual_cost_components.vendor_id` (`OPS-178`) uses. No new vendor-identity table, no Procurement vendor-lifecycle scope smuggled in.

`finance_vendor_bill_number_counters` proactively uses a surrogate `id uuid primary key` plus a `coalesce`-based unique index from the start (`FIN-197`'s own `finance_invoice_number_counters` needed a mid-checkpoint fix for exactly this: a nullable `company_id` cannot be a primary-key column).

## 4. Tests

### 4.1 Real database tests (`scripts/db-tests/finance-vendor-bill.sql`, via `pnpm run db:test`)

Setup: one tenant, full Commercial->Operations pipeline through a confirmed Job Order, three Shipment Orders each with their own approved actual cost -- the first carrying one vendor-sourced freight component (10,250,000 IDR, minimum-charge-wins plus surcharge) and one internal handling component (structurally excluded from any vendor bill), the second and third each carrying a single 5,000,000.00 IDR vendor-sourced component used solely to exercise the two basic-match variance branches end-to-end against distinct (actual cost, vendor) pairs (the unique constraint is per-pair, so the first bill cannot be reused for this) -- a Finance Manager, a Finance Editor (no `Approve`), a Plain User, a second tenant's own Finance Manager, six fiscal periods, and one approved PPN tax rule (`FIN-195`).

Assertions: idempotent preparation (Plain User denied; unknown actual cost/vendor rejected; exact subtotal 10,250,000 + tax 1,127,500 (PPN 11%) = total 11,377,500; exactly 2 lines, never the excluded internal component; idempotent retry returns the unchanged original bill); basic match (an explicit vendor-stated amount 0.50 off the computed subtotal is `within_tolerance` with the exact 0.50 variance recorded; a vendor-stated amount 50,000.00 off is `requires_approval` with the exact variance recorded, and that bill still reaches `approved` status -- the variance discloses, it does not block); lifecycle authority split (Finance Editor denied `approve` -- authority is checked before status; submit -> approve -> post; idempotent post creates exactly one `FIN-199` AP open item of 11,377,500 and never a second on retry; discard rejected once posted); cross-tenant isolation; schema-privilege defense in depth (9 function names checked for zero `anon` `EXECUTE`); audit trail (prepare/approve/post events, minimum 3). All 82 db-test files pass together, zero regression.

The `requires_approval` variance path was initially left as an untested placeholder comment during first authoring (a genuine gap caught during this checkpoint's own review, disclosed in section 8) and is now exercised by a real, distinct actual-cost fixture and a real assertion, as described above.

## 8. Errors / recovery / risks / issues

One genuine test-design gap caught and fixed during this checkpoint's own authoring, before this checkpoint was considered complete: the first draft of `scripts/db-tests/finance-vendor-bill.sql`'s "basic match" scenario group contained only a placeholder assertion re-reading the already-prepared first bill, with a comment claiming the `requires_approval` branch was "exercised end-to-end in the next scenario group's own bill via a distinct actual cost" -- a claim that was not actually true in that draft. Fixed by adding two distinct, fully independent shipment/actual-cost/vendor fixtures (each requiring its own vendor master record, since a resource cannot be actively assigned to two shipments at once) and two real assertions: one proving an explicit near-exact `vendor_stated_amount` yields `within_tolerance` with the exact nonzero variance recorded, and one proving a materially different `vendor_stated_amount` yields `requires_approval` with the exact variance recorded and that the bill still reaches `approved` status. Two smaller setup-only errors were caught and fixed in the same iteration: `create_shipment_order_from_job` requires a non-empty `split_reason` for every shipment beyond a job order's first (fixed by supplying one), and the original single-current-actual-cost-per-tenant lookup pattern (`is_current` alone) had to be narrowed to join on each fixture's own distinct component description once three concurrent current actual costs existed in the same tenant. Zero implementation defect found in the migration itself. Zero Critical/High-severity issue remains open. Zero regression to any prior capability.
