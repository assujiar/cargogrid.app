## 3. Implementation

### 3.1 Evidence-consumption boundary (disclosed, migration header)

`app.handoff_billing_readiness` (`OPS-181`) only ever creates a `billing_readiness_handoffs` row when the evaluation's own `effective_status = 'ready'` at handoff time -- confirmed by direct inspection of that function's own body. A handoff row existing is therefore itself the readiness proof; `app.prepare_finance_invoice_from_readiness` does not re-evaluate readiness evidence, honouring `189_FINANCE_README.md` section 5's "consume ... without re-entering it."

**One handoff, one invoice, idempotent**: `unique (tenant_id, billing_readiness_handoff_id)`. Consolidating multiple Job Orders/handoffs into a single invoice, and splitting one handoff across multiple invoices, are Prompt 197 section 22's own alternative flow -- deliberately out of this MVP checkpoint's bounded scope (disclosed, not silently promised), the same class of proportionate-effort scope decision `OPS-181`'s own fixed `rule_version` placeholder already established.

**Charge-line derivation**: one summary charge line per invoice, from `app.job_orders.revenue_snapshot ->> 'totalAmount'`/`'currency'` -- the exact governed revenue basis `OPS-179`'s own Job Profitability capability already reads verbatim from the same column. Per-charge-code line-level granularity is not available at this dependency point -- the source evidence is itself already a single governed total, not a per-charge-code breakdown.

**Tax-line integration**: an optional tax code parameter calls `FIN-195`'s own `app.calculate_finance_tax` directly. No tax rate is computed independently here; a missing/unapproved tax rule propagates `finance_tax_rule_missing` unchanged.

**Numbering**: `app.finance_invoice_number_counters` is a bounded, per-tenant/company/year sequential counter, assigned only at issue time (never at draft time, so a discarded draft never burns a number) -- a proportionate-effort alternative to the full pattern-based numbering `FIN-191`'s own `finance_numbering` config class describes as policy metadata only (no generator implemented anywhere yet).

**AR posting integration**: `app.issue_finance_invoice` (approved -> issued) is idempotent and calls `FIN-196`'s own `app.post_finance_ar_open_item` directly (`source_document_type = 'invoice'`) -- one idempotent AR open item per issued invoice. GL journal posting (`FIN-202`/`FIN-203`) remains disclosed, not built.

**Correction**: no direct-edit path exists past `issued`; `app.discard_finance_invoice_draft` only ever operates on `draft`/`submitted`. Governed credit/debit/reversal correction of an issued invoice remains `FIN-206`'s own scope.
