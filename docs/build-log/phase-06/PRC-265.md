## 1. What this checkpoint builds

A Procurement-owned match-case workflow extending, never duplicating, the canonical
Phase 4 vendor bill (`app.finance_vendor_bills`/`app.finance_vendor_bill_lines`,
`FIN-200`): configurable line-level matching of the vendor's own real invoice figures
(staff-transcribed, one row per bill line — the first place this repository captures a
true independent LINE-level vendor-stated figure, since `finance_vendor_bill_lines.
amount` is auto-derived from actual cost, never independently vendor-typed) against
PO/contract/actual-cost/rate/tax/ePOD/milestone evidence, a tenant-wide versioned
tolerance policy (draft → active → archived) governing tolerance-based auto-clear,
duplicate-invoice-fingerprint detection (same vendor/currency/total amount within a
configurable window, regardless of reference text), a dispute workflow (staff-recorded
on the vendor's own behalf), a self-approval-blocked exception-approval workflow for
any case with a variance/duplicate/currency-mismatch/missing-evidence exception, and a
read-only readiness/reconciliation exposure back to Finance — six new tables
(`vendor_bill_match_tolerance_policies`, `vendor_bill_match_cases`,
`vendor_bill_match_lines`, `vendor_bill_match_disputes`,
`vendor_bill_match_exception_approvals`, `vendor_bill_match_events`), a
root+version-collapsed case shape mirroring `app.vendor_contracts` (`is_current`
boolean, one current row enforced by a partial unique index, every re-evaluation opens
a fresh version and re-runs the duplicate check against every OTHER current case), 24
public RPCs plus internal scoring/masking/trigger helpers.

No second AP/bill table, no journal posting, no payment execution, and zero
INSERT/UPDATE/DELETE against any `app.finance_*` relation anywhere in this migration
(confirmed by direct grep before commit) — `approve_finance_vendor_bill`/
`post_finance_vendor_bill` (`FIN-200`) are untouched, ungated, unwrapped.
`app.get_vendor_bill_match_readiness` is the one new, real, callable read (gated on
`PRC:View` OR `FIN:View`) a Finance approver can consult before deciding — "read-only
exposure, not a match engine," the same design language `PRC-260`'s own header already
used for an analogous surface.

**The required decision on `invoice_accuracy`:** PRC-264 left the KPI category
structurally present but permanently `is_computable=false` (a 0-argument calculator
stub), explicitly naming this prompt as its real evidence source. This checkpoint makes
the genuine, disclosed choice to **wire it**, via a new corrective migration
(`20260730760000`, `DROP`+`CREATE` for the calculator's now-4-argument signature,
`CREATE OR REPLACE` for the unchanged-signature dispatcher) — never an edit to
PRC-264's own already-applied `20260730740000_create_procurement_vendor_performance.
sql`, per `AGENTS.md`'s protected-path rule. Denominator: current match cases for the
vendor that reached a real decided outcome (`matched`/`exception`/`blocked`/
`disputed`, never still-`pending`) with `evaluated_at` in the window, excluding any
case carrying an UPHELD `app.vendor_kpi_source_disputes` row (the same generic
exclusion every sibling calculator already uses). Numerator: cases that reached
`matched` — a clean or explicitly-accepted match; a case that needed exception
approval, even if later approved, genuinely was inaccurate at submission and does not
count. This does NOT retroactively change any tenant's own already-published
`invoice_accuracy` definition row (`is_computable` lives on that per-tenant, versioned
catalogue row, set by the tenant's own publish call) — the calculator can now
genuinely compute a real value; whether/when a given tenant turns it on stays that
tenant's own governed decision.

## 4. Tier B — recurring defect taxonomy self-check

Lessons already established across PRC-261/262/263/264's own Tier B/Tier C history
were applied from the first draft: idempotency replay verifies the full target tuple
(C-01); race-recovery `unique_violation` handlers are nested to scope only their own
insert; every versioned update is followed by an explicit `if not found` stale-version
guard (C-03); a decision's parent row is locked `for update` before deciding, parent
always before child (C-04/C-21, stated once in the migration's own header and followed
by every function); by-id reads/decides fold "does not exist" and cross-tenant into the
same error before `evaluate_permission` runs (C-05); no `auth.uid()` anywhere, every
function takes an explicit `p_actor_auth_user_id` (C-06/C-13); self-approval is blocked
on both maker-checker flows this capability exposes. Several real findings still
surfaced during this prompt's own live iteration against a real disposable Postgres
database, and were fixed in-prompt:

- **C-02, confirmed and fixed, live-reproduced — `create_vendor_bill_match_case`.** The
  function's own pre-check `raise exception 'idempotency_key_conflict' ... using
  errcode = 'unique_violation'` lived inside the SAME function whose trailing
  `exception when unique_violation` handler also caught genuine insert races — so a
  mismatched-tuple replay was silently swallowed by the function's own handler and
  returned the stale row instead of erroring, live-reproduced with a real replay before
  fixing (not inferred). Fixed by moving the case-row `insert` alone into its own
  nested `begin...exception when unique_violation...end` block, removing the
  now-redundant outer handler entirely — the exact C-02 shape this taxonomy names,
  matching `app.create_vendor_kpi_definition_draft`'s (PRC-264) own precedent fix.
- **A genuine PL/pgSQL type-mismatch bug in `re_evaluate_vendor_bill_match_case`.**
  `select mc.id into v_dup_case` was assigned into a variable declared as the full
  composite row type `app.vendor_bill_match_cases`, not `uuid` — a real compile-time
  error (`column "duplicate_of_case_id" is of type uuid but expression is of type
  vendor_bill_match_cases`) caught live by `db:test`, never silently accepted. Fixed by
  declaring `v_dup_case_id uuid` and selecting only `mc.id` into it.
- **A CHECK-constraint violation on `vendor_bill_match_lines.line_status`'s own
  column default.** Defaulted to `'pending'`, which is not a member of
  `vendor_bill_match_lines_status_check`'s own five-value enum — caught live by the
  very first case-creation call in `db:test`, never reached production. Fixed by
  changing the default to `'missing_evidence'` (the correct pre-evaluation state).
- **C-11, confirmed and fixed, twice.** (1) All four non-append-only tables
  (`vendor_bill_match_cases`, `_lines`, `_disputes`, `_exception_approvals`) initially
  carried a blanket `grant select on ... to authenticated` rather than the
  column-restricted grant this repository's own defense-in-depth convention requires —
  caught live by the repository-wide `rbac-enforcement.sql` schema-privilege sweep.
  Fixed with explicit column allowlists (cost-bearing columns excluded, matched by the
  RPC-layer masking functions), plus two new masking functions
  (`mask_vendor_bill_match_dispute_cost_fields`, `mask_vendor_bill_match_exception_
  approval_cost_fields`) that did not previously exist. (2) The `invoice_accuracy`
  wiring migration's `DROP`+`CREATE` of `_calc_vendor_kpi_invoice_accuracy` (a genuine
  signature change, 0 args → 4 args) implicitly re-granted `EXECUTE` to `PUBLIC` —
  PostgreSQL's own default on any brand-new function — silently undoing PRC-264's own
  prior revoke for that identifier. Caught live by the same `rbac-enforcement.sql`
  anon-EXECUTE sweep. Fixed by adding the standard `REVOKE EXECUTE ON ALL FUNCTIONS IN
  SCHEMA app FROM PUBLIC` (`ERR-2026-004`/`PLT-118` convention) to the wiring
  migration's own final statement.
- **C-20, confirmed and fixed, twice, both confined entirely to this capability's own
  new UI (zero risk to any other capability's already-verified code).**
  (1) `app.update_vendor_bill_match_tolerance_policy_draft` was built, granted, and
  db-tested with ZERO service-layer wrapper and ZERO UI caller anywhere — a real,
  callable correction path for a draft policy's own fields, left completely
  unreachable. Fixed: added the contract/mutation/action wrapper chain plus a new
  `EditPolicyDraftForm` subcomponent (mirroring the existing `ActivatePolicyForm`'s own
  per-row `useActionState` pattern) beside every draft policy row in the queue panel.
  (2) `app.list_vendor_bill_match_case_versions` had a service-layer wrapper but no UI
  caller — a case's own version history (each re-evaluation opens a new version) was
  invisible in the detail page. Fixed: the detail page now fetches it and a new
  "Version history" section links to every prior/current version, noting which are
  superseded.
- **C-20, found but DISCLOSED rather than fixed (§5 below) — `app.get_vendor_bill_
  match_readiness` has zero caller anywhere**, not even within this capability's own
  UI. Unlike the two findings above, wiring this one requires editing Finance's own
  already-`VERIFIED` `FIN-200` UI (a flat, single-page vendor-bill queue with no
  per-bill detail route to attach a readiness section to) — a different capability,
  out of this prompt's own mandate, and real risk to already-verified code for a
  net-new prompt that was never authorized to touch it. The underlying readiness DATA
  is not dark: `readinessStatus`/`readinessNote` are already visible on every match
  case row via this capability's OWN queue table, reconciliation table, and detail
  header. A third instance, `app.get_active_vendor_bill_match_tolerance_policy`, was
  analyzed and also disclosed rather than fixed — genuinely redundant with `list_
  vendor_bill_match_tolerance_policies`, which the UI already calls and filters
  client-side for the active row, mirroring the precedent PRC-261 set for `app.
  resolve_effective_vendor_contract` (a cross-capability read contract with no UI
  caller by deliberate design).

## 5. Residual, disclosed limitations (itemized — C-23 discipline)

1. **`app.get_vendor_bill_match_readiness` has no caller anywhere** (§4's third C-20
   finding, disclosed not fixed). The natural home is Finance's own `FIN-200`
   vendor-bill workspace, which is a flat, single-page queue with no per-bill detail
   route today — wiring this in would mean modifying a different, already-`VERIFIED`
   capability's own UI, outside this prompt's mandate and a real destabilization risk
   for an unauthorized change. The underlying readiness data is not dark: it is already
   visible via `readinessStatus`/`readinessNote` on this capability's OWN queue table,
   reconciliation table, and case detail header. A small follow-up prompt adding a
   per-bill detail route to Finance's vendor-bill workspace (or a readiness column to
   its existing queue table) is the natural next increment, not attempted here.
2. **`app.get_active_vendor_bill_match_tolerance_policy` has no caller** — genuinely
   redundant with `list_vendor_bill_match_tolerance_policies`, which the UI already
   calls and filters client-side for the one active row; mirrors PRC-261's own
   disclosed precedent for `app.resolve_effective_vendor_contract`.
3. **The tolerance-policy-draft create/update idempotency mismatch branch was never
   live-tested with an actual conflicting replay** — structurally identical to the
   case-creation path's own C-02 fix (which WAS live-tested), but `db:test` only
   exercises the happy-path/full-tuple-replay branches for these two functions.
4. **`record_vendor_bill_match_dispute_response`'s file-evidence path
   (`p_vendor_response_file_id`) was never live-tested with a real `app.files` row** —
   structurally correct (tenant/dispute-ownership/malware-scan-status checks all
   present), but every db-test call passes `null`.
5. **PO evidence contributes quantity/UOM at line grain and total amount at header
   grain only, never a per-line PO rate** — inherited directly from PRC-260's own
   already-disclosed scope boundary (`app.purchase_order_lines` carries no per-line
   unit price), not reintroduced or silently worked around here.
6. **No FX conversion for cross-currency evidence** — hard-blocked at PO attach,
   flagged and routed to a human at line level, the same unresolved architectural
   question `ISS-2026-045` already declined to decide unilaterally for a different
   entity type.
7. **No AI/OCR line-item extraction** — `vendor_stated_*` fields are staff-transcribed
   off the vendor's own paper/PDF invoice, the same Prompt 200 §16 boundary this
   migration inherits rather than reintroduces.
8. **No vendor-portal identity for dispute response** — staff-recorded on the vendor's
   own behalf, the same already-accepted PRC-257/258/261/262/263/264 precedent.
9. **No integration with Finance's own generic reconciliation engine (`FIN-207`)** —
   `get_vendor_bill_match_reconciliation_status` is this capability's own distinct,
   Procurement-side aggregate of match-case outcomes, a deliberate choice to avoid
   touching Finance's own reconciliation schema/entity-type surface.
10. **No automatic scheduler triggers re-evaluation** — `re_evaluate_vendor_bill_
    match_case` is a real, callable, human/UI-triggered action; nothing calls it
    automatically, the same `ISS-2026-015` boundary (no scheduler/worker runtime
    exists anywhere in this repository) every prior recompute-shaped capability has
    already disclosed.
11. **No MFA/reauthentication requirement on exception-approval-decide or
    dispute-resolve decisions** — a deliberate reading of this prompt's own spec text,
    which never names MFA anywhere (unlike Prompt 259's explicit requirement), not an
    oversight.
