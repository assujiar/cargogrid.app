## 3. Schema summary (all additive)

- `app.vendor_rate_versions` gains: `vendor_master_id` (nullable FK to `app.master_records`,
  ADR-0020's mandatory link, structurally trigger-enforced to `master_type_code='vendor'`,
  same tenant), `lead_time_days`, `capacity_terms`, `source_import_staging_row_id` (nullable,
  uniquely indexed — import-adapter lineage/idempotency), and two generated, stored columns
  (`scope_key`, `validity_range`) backing a `btree_gist` `EXCLUDE` constraint,
  `vendor_rate_versions_no_ambiguous_overlap`, scoped to `approval_status='approved'` rows.
- New table `app.vendor_rate_tiers` — one ordered, `[min,max)`-half-open weight/volume
  pricing tier per rate version, creatable/removable only while the parent is
  `pending_approval`. Zero tiers remains fully valid (the flat `base_amount` stays the
  single-tier default).
- New masked view `app.vendor_rate_tiers_directory` (PRC:View cost gated, hardened
  customer-exclusion predicate from creation).
- `app.vendor_rate_versions_directory` extended with the three new trailing columns
  (`vendor_master_id` unmasked; `lead_time_days`/`capacity_terms` cost-masked identically to
  `base_amount`) and its row filter hardened to exclude a `customer_user`-layer principal
  entirely (a pure AND-narrowing, mirrors `20260730311000`'s ATW-023 technique).
  `app.v_active_vendor_rates` inherits both changes automatically (it is `select * from`
  that view).

## 5. Design decisions

**Tier boundary rule.** `[min, max)` half-open intervals; weight and volume are validated
as two *independent* 1-D partitions of the same tier set, **each only when that dimension
actually varies** (`count(distinct (min,max)) > 1`). The first draft of this validator
unconditionally checked both dimensions against every tier and was caught live by this
checkpoint's own db-test run: it rejected the single most common real shape (tiers varying
by weight only, every tier sharing the same default `[0, null)` volume range) as a
false-positive "unbounded tier must be last" violation. Fixed before this checkpoint closed
— not left as a latent defect. A genuinely ambiguous 2-D grid (tiers varying independently
along both dimensions at once) is disclosed as out of scope.

**Overlap detection across rate versions** is a real, DB-enforced `btree_gist` `EXCLUDE`
constraint on `(scope_key, validity_range)` where `approval_status='approved'` — not an
app-level check-then-insert. This is inherently concurrency-safe (the same guarantee a
unique index gives) and needs no separate advisory lock for this specific race.
Data-migration disclosure (Prompt 255 §19): `scripts/db-tests/commercial-rate-cost-lookup.sql`
was read in full before adding this constraint; its own revision-supersede sequence never
has two rows simultaneously `approved` in the same scope, and its cross-tenant fixture is
naturally excluded (`scope_key` includes `tenant_id`) — zero fixture adjustment was needed,
confirmed by direct inspection, not assumed.

**Import-adapter column-mapping convention** (the first real domain-write adapter for
PLT-131, closing part of ISS-2026-013): one staged row = one full rate proposal, with up to
three fixed tier slots as flat columns (`tier1_..`/`tier2_..`/`tier3_..`), never the
alternative cross-row-grouping shape — a disclosed, bounded simplification. Formula/
spreadsheet-injection defense rejects (never silently strips) any of ten text-shaped
columns beginning with `=`, `+`, `-`, `@`, tab, or carriage return. The commit adapter
requires **both** the unchanged `is_support_grant_authority` (since it ultimately calls
`create_rate_version`) **and** the new `PRC:Import` action — `PRC:Import` alone is never
sufficient, closing a privilege-escalation path. Idempotent-safe by construction (a staged
row can produce at most one rate version ever, via a uniquely-indexed lineage column, a
pre-check, a nested `unique_violation` handler, and a job-scoped advisory lock).

**Masking gate split.** Pre-existing COM-149 cost columns (`base_amount`, `currency`,
`minimum_amount`, `surcharge_components`, and the two new same-table columns
`lead_time_days`/`capacity_terms`) keep the unchanged `app.has_view_cost` (COM:View cost)
gate — extending the existing mechanism per the task's own "never build a second masking
mechanism" instruction. The wholly new `app.vendor_rate_tiers` table uses `app.has_prc_view_cost`
(PRC:View cost) from the start, per ADR-0020's explicit directive to reuse that action for
this checkpoint's own new sensitive-field class.

## 6. Real defects found and fixed during this checkpoint's own db-test run

1. **`app.has_prc_view_cost` name collision** — PRC-252 (Vendor Assessment) already created
   this exact function. My first draft redefined it, which fails migration apply
   (`function "has_prc_view_cost" already exists with same argument types`). Fixed by
   reusing PRC-252's own function, never redefining it.
2. **`CREATE OR REPLACE` does not truly replace a function when new parameters are added** —
   PostgreSQL identifies a function by its full parameter type list, so a bare
   `CREATE OR REPLACE` on `create_rate_version`/`select_vendor_rate` (widened with new
   trailing params) would have created a second, coexisting overload rather than replacing
   the original, silently leaving the OLD, un-widened function reachable by any
   21/8-argument caller. Fixed with an explicit `DROP FUNCTION` (old, exact signature)
   before the new `CREATE FUNCTION`.
3. **`app.search_vendor_rates` result-shape mismatch** — declared `returns setof
   app.vendor_rate_versions_directory`; widening that view without also widening this
   function's own fixed, explicit column list raised "structure of query does not match
   function result type" the moment COM-149's own unchanged db-test exercised it. Fixed by
   widening the function body in lockstep (unchanged signature/behavior).
4. **Tier-contiguity false positive** (design decision, not a code typo) — see §5. Found
   and fixed via this checkpoint's own new db-test scenario.
5. **ATW-032 (ISS-2026-032) actor-identity regression** — the most serious finding.
   `20260730510000_harden_actor_identity_unchecked_authority_surface.sql` had already
   patched COM-149's original `app.create_rate_version`/`app.approve_rate_version` with
   `perform app.assert_actor_is_session_identity(p_actor_auth_user_id);` as their first
   statement (closing "any authenticated session could pass a colleague's UUID and act as
   them," since these two functions gate only on `is_support_grant_authority`, which never
   calls `evaluate_permission`). My `CREATE OR REPLACE`/`DROP+CREATE` of these two functions
   was based on the COM-149 migration's own original body and silently **reintroduced this
   exact security gap** — a genuine regression I introduced, caught only because
   `scripts/db-tests/rbac-enforcement.sql`'s own repository-wide ATW-032 sweep (a real,
   automated, `pg_proc`-introspecting regression guard) ran later in the same suite and
   failed with the two function names listed explicitly. Fixed by re-adding the identical
   `assert_actor_is_session_identity` call to both functions, with a comment explaining why
   it must never be dropped again on a future edit.
6. **My own db-test file's SQL bug (not the migration): `app.master_records` has no
   `master_record_id` column** (its PK is `id`). `select master_record_id from
   app.master_records where code = 'RT-IMPORT-1'`, nested inside `... from
   app.vendor_rate_versions where master_record_id in (that subquery)`, silently became a
   **correlated** subquery — PostgreSQL resolved the unresolvable `master_record_id`
   reference against the *outer* query's own `vendor_rate_versions.master_record_id`
   column instead of raising a compile error, making `master_record_id in (subquery)`
   trivially true for every row in the tenant. This inflated an assertion's row count from
   the expected 1 to 9 (every rate version the whole test file had created for that
   tenant). Fixed by selecting `id`, not the nonexistent `master_record_id`, throughout the
   test file.
7. **`scripts/db-tests/procurement-vendor-registration.sql`'s own forward-looking
   regression guard** asserted `app.vendor_rate_versions.vendor_master_id` **must not
   exist yet** ("it is Prompt 255's own additive scope") — a placeholder PRC-251 itself
   wrote anticipating this exact checkpoint. Now that PRC-255 has landed it exactly as
   anticipated, that assertion is inverted to confirm the column **now exists** with a
   comment explaining the update; the boundary it protects (PRC-251's own migration never
   touching `app.vendor_rate_versions`) remains fully intact and unweakened — only the
   now-arrived "future" needed an update, not a new test.

None of these were shipped uncaught — every one surfaced from a genuine, live
`pnpm run db:test` failure and was fixed before this checkpoint closed, matching the
"read every prior checkpoint's build log, don't repeat their bug classes" instruction. #5
in particular is the exact "found a live-reproduced adversarial security review" class of
regression the prior four checkpoints' own build logs warned about — this one was caught by
this repository's own existing automated regression guard, not a live adversarial review
(none was run for PRC-255 itself; the orchestrating session's own independent verification
may still choose to run one).

## 9. Residual, disclosed limitations (not defects)

- **Tier-import column cap.** The import adapter supports at most 3 fixed tier slots per
  staged row (a disclosed, bounded simplification — see §5). A rate needing more tiers is
  created via the structured API/UI directly.
- **2-D tier grids** (tiers varying independently along both weight and volume at once) are
  out of scope for the contiguity validator — disclosed in the migration header, not
  silently mis-validated (the validator only enforces contiguity per-dimension when that
  dimension actually varies; a genuinely ambiguous 2-D shape is not rejected but is also not
  a shape this checkpoint claims to validate).
- **Concurrent-race reproduction** has no matching sequential db-test proof (no
  `dblink`/`pg_background` in this test suite) — the same standing, already-disclosed
  limitation every prior Phase 6 checkpoint's build log records. The `EXCLUDE` constraint
  for overlap detection is inherently concurrency-safe regardless of this limitation; the
  advisory locks (tier-vs-approval row lock, job-scoped commit lock) were verified by direct
  code-path inspection, not a live multi-session reproduction.
- **UI scope.** The procurement rates UI is deliberately lean: a directory + create form,
  and a detail page with tier CRUD + calculate preview. Approve/reject/withdraw actions
  remain on the existing Commercial rate detail page
  (`app/(tenant)/[tenantSlug]/commercial/rates/[rateVersionId]/page.tsx`) — this checkpoint
  did not duplicate that lifecycle UI, only added the new tier/link/calculate surface.
- No true multi-tenant import-schema-configuration UI was built; a tenant publishes its own
  `import_export:vendor_rate_import` column definition via the existing, generic
  Configuration Engine (no bespoke UI exists for ANY import/export schema yet, matching
  PLT-131's own disclosed scope).

### 10.3 Verified sound, no defect (confirmed by re-reading the actual code)

- **Tier idempotency-key replay** (`app._insert_vendor_rate_tier`) — compares all 8
  load-bearing fields on both the pre-check and the `unique_violation` race-recovery path.
  Confirmed correct; this is the exact bug class found in Prompts 252/253/254 and it does
