# PRC-259 — Procurement Approval

**Prompt ID:** `CG-S11-PRC-010` · **Package document:** `CG-AABPP-PRC-259` · **Status at end of this checkpoint:** `COMPLETED` under `docs/adr/ADR-0021` (batched review cadence) — Tier A green, Tier B walked and recorded below, adversarially unreviewed. This prompt is part of the 257–259 batch (Prompt 260, Purchase Order, was not built this batch — corrected at the batch's own Tier C close, which found this checkpoint's original "257–260" framing overstated the batch's own scope); `VERIFIED` is reserved for the batch's Tier C close, not claimed here.

## 1. What this checkpoint extends

PRC-259 is the ninth Phase 6 checkpoint, built directly on the already-`COMPLETED`
PRC-257 (Procurement RFQ) and PRC-258 (Vendor Comparison, same batch). It instantiates
**one configurable approval contract** across the high-risk Phase 6 decision points the
prompt names — vendor activation, rate approval, vendor selection/comparison approval,
PO approval, vendor contract approval, and exception/override — by reusing the
already-`VERIFIED` Platform Approval Engine (`app.approval_requests`/
`app.approval_request_steps`/`app.approval_decisions`/`app.approval_delegations`,
`app.request_approval`/`app.decide_approval_step`, migration
`20260719090000_create_approval_engine.sql`) end to end. Procurement stores
bindings/context; it never builds a second workflow engine. The reference pattern
copied throughout is Commercial Quotation Approval (COM-153,
`20260724270000_create_commercial_quotation_approval.sql`) and its own gated
"next lifecycle transition" precedent
(`20260724280000_create_commercial_quotation_customer_acceptance.sql` near line 206).

Three already-canonical, already-built governed entities are widened in place:
`app.vendor_profiles` (PRC-251), `app.vendor_rate_versions` (COM-149/PRC-255), and
`app.vendor_comparisons` (PRC-258, same batch). One new, minimal, self-contained
governed entity is added for exception/override (`app.procurement_exception_requests`
— no existing table represents a standalone exception request). `purchase_order` and
`vendor_contract` are registered as valid policy/context `entity_type` dimensions with
no table of their own, since neither exists anywhere in this repository yet (confirmed
by direct inspection, `docs/build-log/phase-06/00_PROCUREMENT_VENDOR_WBS.md` line 64)
— Prompt 260 (Purchase Order, not yet built) and a later Phase 6 vendor-contract
capability inherit an immediately reusable, generic binding pattern rather than a
PO-specific one.

## 3. Schema summary (all additive)

- `app.procurement_approval_policies` — the bespoke, tenant-wide, **per-entity_type**
  threshold policy table (mirrors `app.quotation_approval_rules`, COM-153, with one
  added dimension: `entity_type`, closed-enum over the 6 governed values).
  `min_value_amount` is restricted by `procurement_approval_policies_value_dimension_
  check` to the three genuinely value-bearing entity types (`rate_version`,
  `vendor_selection`, `purchase_order`) — `vendor_activation`/`vendor_contract`/
  `exception_override` have no natural monetary value, so only a policy's own
  `always_required = true` can ever trigger routing for them; this is enforced
  structurally, not left as a policy-authoring foot-gun. At most one published policy
  per `(tenant_id, entity_type)` (partial unique index). Never field-masked — tenant-wide
  reference data, mirrors `app.quotation_approval_rules`'s own posture.
- `app.procurement_approval_context_snapshots` — the one generic, immutable decision
  context snapshot table every governed entity_type shares (business rule: "Decision
  context snapshots source/config/value/risk/compliance/rate versions"). One row per
  `app.approval_requests` row this capability opens. `value_amount`/`currency` are the
  only cost-shaped columns; `context` is a small, explicit, per-entity-type allowlist
  of non-cost descriptive fields (never `to_jsonb(whole_row)` — taxonomy C-07, PRC-256's
  own `demand_snapshot` lesson applied from the start). Carries **no direct
  `authenticated` grant at all** — mirrors `app.approval_decisions`'s own "no direct
  grant, RPC-only" posture (PLT-123); the one read path
  (`app.get_procurement_approval_context_snapshot`) masks `value_amount`/`currency`
  behind `PRC:View cost`.
- `app.vendor_profiles` widened: `approval_status` / `approval_request_id` (two axis
  columns, independent of `lifecycle_status`).
- `app.vendor_rate_versions` widened: `governance_approval_status` /
  `governance_approval_request_id` — **deliberately NOT named `approval_status`/
  `approval_request_id`**, because COM-149 already owns a column literally named
  `approval_status` with a different, wider, pre-existing meaning
  (`pending_approval|approved|rejected|withdrawn|superseded`). Disclosed explicitly in
  the migration header as the one naming deviation this prompt's own convention
  required — renaming or repurposing the pre-existing column was out of scope
  (forbidden: "duplicate vendor/rate ... roots") and would be a breaking change to an
  already-shipped capability.
- `app.vendor_comparisons` widened: `approval_status` / `approval_request_id` (no
  collision here — clean two-axis addition).
- `app.procurement_exception_requests` — a new, minimal, self-contained governed
  entity for exception/override requests. `status` collapses onto `approval_status`
  once finally decided (approved/rejected) — unlike the other three governed entities,
  an exception request has no further domain "release" step of its own within this
  migration's scope; the grant IS the approval outcome. `related_entity_type`/
  `related_entity_id` are a polymorphic, purely descriptive, application-validated
  reference (mirrors `app.approval_requests.entity_type`/`entity_id`'s own established
  pattern, PLT-123) — never re-validated against a foreign table.

  `app._request_procurement_entity_approval` (private, no grant — the one shared

  once: evaluates the policy, resolves the tenant's one shared `config_type_code=

## 5. Design decisions

**The generic Approval Engine's own tenant-wide routing definition is shared, not
forked.** `app.config_objects_scope_unique` permits exactly one
`(config_type_code='approval', tenant_id, scope_level='tenant')` row per tenant — this
is the already-`VERIFIED` repository convention (COM-153's quotation routing and
COM-157's credit routing already share the identical physical object), not a
limitation this migration works around. Every governed Procurement entity_type routes
through that same one tenant-wide committee/chain, disambiguated purely by
`app.approval_requests.entity_type` on the request — consistent with the two prior
Commercial precedents, not a new design choice invented here.

**`app.evaluate_procurement_approval_requirement` takes a mandatory actor and an
authority check — added during this checkpoint's own Tier B walk, not shipped without
one.** The first draft took `(entity_type, tenant_id, value_amount)` with no actor
parameter at all — the exact cross-tenant business-intelligence disclosure class
`20260726090000_create_commercial_hardening.sql` (COM-163) already found and fixed for
`app.evaluate_quotation_approval_requirement`. Caught live by this checkpoint's own
full `pnpm run db:test` run (`rbac-enforcement.sql`'s ATW-032 authority-surface sweep),
not by inspection alone. **The first fix attempt gated on `PRC:View`, which was ALSO
wrong** — it broke a genuinely pre-existing, already-passing test
(`advanced-tms-canonical-telemetry-arbitration.sql`), because `app.create_rate_
version`'s own authority model (`app.is_support_grant_authority` — Supreme Admin or
tenant_admin, COM-149's original, unrelated to the `PRC` permission catalogue) does not
imply `PRC:View`. The evaluator's own authority check was widened again to `app.has_
active_tenant_membership` (matching `app.procurement_approval_policies`'s own RLS
policy exactly — a stricter gate would protect nothing the raw table select does not
already expose, since any active tenant member can already read the same threshold
rows directly), which closes the real cross-tenant leak without regressing the
support-grant-authority caller. Both fixes, and the live regression that caught the
first one, are recorded in the migration's own header — not silently corrected.

**Every one of the four new domain sync wrapper functions calls
`app.assert_actor_is_session_identity` as its own first statement — found missing by
this checkpoint's own Tier B walk, not by inspection.** `app.decide_approval_step`
(PLT-123) itself validates authority-of-the-claimed-actor (via `app.check_approval_
request_authority`/`app.is_eligible_approval_approver`) but never identity-of-the-
caller — exactly taxonomy class C-13/ISS-2026-032, already found and fixed once for
`app.decide_quotation_approval_step` at `20260730510000_harden_actor_identity_
unchecked_authority_surface.sql`. Caught live by `rbac-enforcement.sql`'s own
ISS-2026-032 sweep (a full `pnpm run db:test` run, not a targeted check) — the exact
same class reintroduced independently a second time in this repository's history,
matching the taxonomy document's own observed pattern ("the classes repeat across
capabilities that share no code").

**No REST/GraphQL surface, no notification/job wiring** — identical reasoning to every
prior Phase 6 checkpoint's own disclosed boundary: no REST/GraphQL adapter exists for
any domain yet, and this prompt's own spec text names no concrete notification *event*
this capability itself must emit beyond the Platform engine's own (already-disclosed,
`NOT_RUN`) SLA-escalation trigger job — no scheduler infrastructure exists anywhere in
this repository yet.

**Delegation, escalation, and request-cancellation deliberately have no domain
wrapper and no UI caller.** Mirrors COM-153's own header exactly ("neither changes a
request's final outcome") for the "no wrapper" half. The "no UI caller" half is a
real, disclosed finding from this checkpoint's own build: `app.cancel_approval_
request`/`app.escalate_approval_step`/`app.create_approval_delegation`/`app.revoke_
approval_delegation` are granted **`service_role` only** (the Approval Engine
migration's own grant block — confirmed by direct inspection before writing any UI
code) — unreachable from the RLS-scoped, anon-key session client every Server Action in
this repository uses (`lib/supabase/server.ts`). No prior capability including
Commercial Quotation/Credit Approval has ever built a UI caller for any of the four for
exactly this reason. An early draft of this checkpoint's own UI included a "cancel
approval request" button wired to `app.cancel_approval_request` through the RLS-scoped
client — this would have been a real, permanently-broken dead action (a same-shaped
gap to taxonomy C-20, but the caller existing and the callee being unreachable,
disclosed here rather than shipped) and was removed before this checkpoint's `next
build` gate ever ran, once the grant was checked directly rather than assumed.

**No `vendor_contract` capability exists to bind, and none is invented here.**
Confirmed by direct inspection (`00_PROCUREMENT_VENDOR_WBS.md` line 64: "no ...
`app.purchase_orders` table exists anywhere") — `vendor_contract` is registered as a
valid `entity_type` in every `CHECK` constraint this migration adds, satisfying the
prompt's own "where applicable" qualifier for contract approval without building a
table this checkpoint has no mandate to design.

**RBAC mapping reuses the 12 already-seeded PRC actions exclusively** — no new
`app.permissions` row. `Create` = `create_procurement_approval_policy_version`.
`Approve` = `publish_procurement_approval_policy_version` (plus the pre-existing
`PRC:Approve`/`is_support_grant_authority` gates on the three widened entity RPCs,
unchanged). `Override` = `create_procurement_exception_request` (mandatory reason,
matching the RFQ/vendor-comparison override actions' own established discipline).
`Edit` = `cancel_procurement_exception_request`. `View`/`View cost` = every read path,
cost fields masked behind `View cost` specifically (never the generic `View`).

## 6. Real defects found and fixed during this checkpoint's own Tier B walk

Per `docs/standards/RECURRING_DEFECT_TAXONOMY.md` §2, the full §4 walk ran against
this checkpoint's own diff, and — because this checkpoint touches a shared
cross-domain primitive composition, unlike a single-domain checkpoint — a full,
independently re-run `pnpm run db:test` against the ENTIRE repository's existing
db-test suite (142 files) was run repeatedly during development, not only at the end.
Every defect below was caught by that live run, not by inspection alone, and every one
was fixed in the migration before it was ever declared `COMPLETED`:

1. **Ambiguous column reference, `app._request_procurement_entity_approval` and
   `app.get_procurement_approval_context_snapshot`.** PL/pgSQL `RETURNS TABLE`/`OUT`
   parameter names shadow same-named columns referenced unqualified in the function
   body — `approval_request_id` (both an OUT parameter and a real column on `app.
   procurement_approval_context_snapshots`) raised `column reference "approval_request_
   id" is ambiguous` the moment the migration was first applied to a real database.
   Fixed by table-aliasing both `WHERE` clauses (`s.approval_request_id = ...`). A
   genuine, mechanical PL/pgSQL gotcha, not a design defect — caught immediately by
   this checkpoint's own iterative `psql -f` application against a disposable database
   before the db-test file was even written.
2. **C-05/C-06-class cross-tenant disclosure, `app.evaluate_procurement_approval_
   requirement` (two-round fix)** — see §5's own detailed account. First found live by
   `rbac-enforcement.sql`'s ATW-032 sweep; the first fix attempt itself broke a
   pre-existing test and was corrected on the second full-suite run.
3. **C-13-class identity-vs-authority gap, all four new domain sync wrapper
   functions** — see §5's own detailed account. Found live by `rbac-enforcement.sql`'s
   ISS-2026-032 sweep.
4. **A genuinely broken, would-always-403 UI action, `cancelProcurementApprovalRequest
   Action`.** Found by checking the Approval Engine migration's own grant block
   directly (not assumed) before finishing the UI, not by a failing test — `app.
   cancel_approval_request` is `service_role`-only, unreachable from the RLS-scoped
   session client every Server Action in this repository uses. Removed before `next
   build` ever ran (see §5).
5. **Two UUID test-fixture collisions in `scripts/db-tests/procurement-approval.sql`
   itself** (not the migration): the initially-chosen `00000000-...-0391xx` seed prefix
   collided with `advanced-tms-*.sql`'s own already-used identities, and one cross-
   scope table lookup queried a wrong column name (`approval_request_id` instead of
   `governance_approval_request_id` on `app.vendor_rate_versions`). Both found and
   fixed by running the full `pnpm run db:test` suite (not just this checkpoint's own
   file) before declaring the checkpoint done.

None of these were shipped uncaught — every one surfaced from this checkpoint's own
disciplined build → apply to a real disposable Postgres → run the FULL repository
db-test suite (not just this file) → fix → re-run cycle, repeated four times in full,
before this migration was ever declared `COMPLETED`.
