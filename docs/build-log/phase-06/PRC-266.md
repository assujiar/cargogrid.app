4. **Capacity/acceptance** — `app.get_procurement_dashboard_capacity_reservation_summary` and
   `app.get_procurement_dashboard_assignment_acceptance_summary`, the latter reading PRC-264's
   own additive `responded_at` column on `app.vendor_assignment_invitations`.
5. **PO/contract** — `app.get_procurement_dashboard_po_summary` (committed amount masked behind
   `PRC:View cost`) and `app.get_procurement_dashboard_contract_summary` (no cost-shaped column
   exists on `app.vendor_contracts` at all, disclosed, not a gap).
6. **Performance** — `app.get_procurement_dashboard_performance_summary`, reading PRC-264's own
   already-published `app.vendor_kpi_scorecards.band`/`composite_score` verbatim — never a
   second scoring engine.
7. **Match variance/exception rate** — satisfied **entirely** by reusing PRC-265's own
   already-`VERIFIED`, batch-4-Tier-C-hardened `app.get_vendor_bill_match_reconciliation_status`.
   Zero new SQL for this group; it is wired straight into this dashboard's own
   service/UI/catalogue layer.

  catalogue (root+version-collapsed, mirroring `app.vendor_kpi_definitions`' shape — PRC-264 —

## 4. Tier B — recurring defect taxonomy self-check

Lessons already established across PRC-261..265's own Tier B/Tier C history were applied from
the first draft: idempotency replay verifies the full target tuple (C-01); a decision's parent
row is locked `for update` before deciding where a genuine race exists; by-id reads/decides fold
"does not exist" and "not this actor's own" into the same error before disclosure (C-05); no
`auth.uid()` reached implicitly anywhere (every function takes an explicit
`p_actor_auth_user_id`); cost-shaped aggregate fields are masked to `null`, never zero, inside
the SQL itself. Real findings still surfaced during this prompt's own live iteration against a
real disposable Postgres database, and were fixed in-prompt:

- **C-13, confirmed and fixed, live-caught by this repository's own repository-wide
  `rbac-enforcement.sql` ATW-032 sweep test (not by my own inline review) —
  `app.register_procurement_metric_definition`/`app.retire_procurement_metric_definition`
  checked `is_supreme_admin(p_actor_auth_user_id)` (the CLAIMED actor's authority) but never
  that the calling SESSION really is that actor.** The full `db:test` suite failed with:
  `assertion failed: 2 side-effecting function(s) are granted to authenticated and take
  p_actor_auth_user_id but reach neither app.evaluate_permission nor
  app.assert_actor_is_session_identity ... {register_procurement_metric_definition,
  retire_procurement_metric_definition}`. Fixed by calling
  `perform app.assert_actor_is_session_identity(p_actor_auth_user_id);` as the first statement
  in both functions, before the authority check — matching the single choke point
  `app.evaluate_permission` already wires this same check into (ATW-031). A new db-test
  assertion proves it live: an authenticated `staff1` session forging a JWT claim and passing
  the real Supreme Admin's UUID as `p_actor_auth_user_id` is rejected with
  `actor_identity_mismatch`, not silently trusted.
- **A genuine design bug, found by live db-test execution, not by inline review: the metric
  definition catalogue's own seed block silently inserted ZERO rows at fresh-migration-apply
  time.** The first draft routed the eleven-row seed through
  `app.register_procurement_metric_definition` itself, gated behind a bootstrap lookup for an
  existing Supreme Admin identity (`select ... from app.principal_memberships where
  layer='supreme_admin' ...`) — but a brand-new database has no Supreme Admin yet at migration-
  apply time, so `v_supreme` was `null` and the entire `if v_supreme is not null then ... end
  if;` block was a silent no-op. `db:test`'s own reconciliation assertion (`expected exactly 11
  current metric definitions`) failed with `got 0`, catching it live. Fixed by seeding the
  eleven rows via a **direct `insert`**, exactly mirroring `app.report_types`' own established
  seed shape (COM-159) — the register/retire functions remain real, tested, callable
  maintenance paths for any *future* catalogue change (both are exercised end-to-end by a
  dedicated db-test block, including the supersede-chain and idempotent-if-unchanged paths),
  they were simply never the right mechanism for this migration's own bootstrap seed.
- **A cursor-pagination test-methodology bug, found live: four vendor rows created inside the
  same setup transaction shared an IDENTICAL `created_at` (Postgres freezes `now()` for the
  duration of one transaction), so the single-column `created_at` cursor walked only 1 of 4
  rows before the tied timestamp excluded the rest.** This is not a defect in the RPC itself
  (the same single-column-cursor simplification `app.list_vendor_contracts` and every other
  PRC-25x/26x list RPC already uses, with no tie-breaker column, a real, disclosed,
  already-repository-wide convention) — it is a genuine risk the cursor convention carries
  whenever many rows are bulk-created in one transaction, which the fixture had done. Fixed at
  the test level by explicitly spreading the four fixture rows' `created_at` values one minute
  apart before exercising the pagination walk, with the reasoning recorded inline in the
  db-test file itself so a future reader does not mistake the adjustment for a fabricated
  assumption.
- Two RFQ role-permission gaps (`app.create_vendor_comparison` requires `FIN:View` for
  cross-currency normalization; the CRM-through-shipment fixture chain requires `COM`/`OPS`
  permissions) were caught live by the setup's own first execution and fixed by widening the
  test-only admin role's permission grant to match `app.create_vendor_comparison`'s and the
  Commercial/Operations pipeline's own real, already-established requirements — not a defect in
  this migration's own RPCs, a fixture-setup gap.
