## 0. Common conventions across every runbook below

- **Permission actions** are `PRC:Create`/`PRC:Edit`/`PRC:View`/`PRC:View cost`/`PRC:View personal data`/`PRC:Approve`/`PRC:Reject`/`PRC:Override`, evaluated by `app.evaluate_permission`, the same repository-wide RBAC gate every other phase uses — see `docs/build-log/phase-06/00_PROCUREMENT_VENDOR_WBS.md` §5 for the full module/action reconciliation.
- **Every draft→published/approved lifecycle** in Phase 6 uses the same `record_version` optimistic-concurrency guard (a stale write raises `stale_version`, never a silent overwrite) — the same pattern this session's own `ISS-2026-055` fix (`PRC-269.md`) hardened for the four `vendor_profiles` lifecycle functions specifically.
- **Every governed threshold decision** (`vendor_activation`/`rate_version`/`vendor_selection`/`purchase_order`/`vendor_contract`/`exception_override`) routes through the one shared evaluator, `app.evaluate_procurement_approval_requirement` (currency-aware since `PRC-269.md` Fix 3, `ISS-2026-045` resolved) and the one shared glue function, `app._request_procurement_entity_approval`, which opens a real request against the Platform Approval Engine (`app.request_approval`/`app.decide_approval_step`, PLT-123) — never a bespoke per-entity approval mechanism.
- **Self-approval is blocked** on every maker-checker decision named below (the requester/creator identity can never also be the approver) — a repository-wide convention, independently confirmed per capability in its own build log.

## 1. Onboarding

**Scenario:** a new vendor needs to be brought from "does not exist in this tenant" to an active, usable vendor record.

**Real sequence** (`supabase/migrations/20260730580000_create_procurement_vendor_registration.sql`, `PRC-251.md`):

1. Staff-initiated: `app.create_vendor_profile_draft` (`PRC:Create`) creates the draft `app.vendor_profiles` row, extending the canonical `app.master_records`/`vendor` identity (`ADR-0020`) — never a second, competing vendor table.
2. Vendor-initiated (self-registration): `app.create_vendor_intake_token` (staff, `PRC:Create`) issues a one-shot token; the vendor visits the public `app/(public)/vendor-intake/[token]/page.tsx` route and calls `app.redeem_vendor_intake_token_and_submit`, or `app.submit_vendor_profile_self_registration` via `app/(public)/vendor-intake/register/[tenantSlug]/page.tsx` if `app.is_vendor_self_registration_enabled` for the tenant. Both are `service_role`-backed, never `anon`-executable directly — the public route itself is the one sanctioned entry point.
3. `app.add_vendor_address`/`add_vendor_contact`/`add_vendor_coverage`/`add_vendor_service` populate child rows (each with its own `update_*`/`remove_*`/`list_*` sibling).
4. `app.search_vendor_duplicate_candidates`/`flag_vendor_duplicate_candidate`/`decide_vendor_duplicate_candidate` — the duplicate-review gate a fresh intake or draft must clear before submission.
5. `app.submit_vendor_profile_for_review` (`PRC:Edit`) moves the profile to `submitted`; `app.begin_vendor_profile_review` (optional) marks `under_review`; `app.decide_vendor_profile_review` (`PRC:Approve`/`PRC:Reject`, self-approval blocked, MFA-reauth-freshness-gated per `PRC-254.md`'s established pattern) approves or rejects.
6. `app.activate_vendor_profile` (`PRC:Approve`) — the terminal step making the vendor usable by every downstream capability (rate/RFQ/PO/contract/capacity/assignment). This is also the entity type governed by `app.evaluate_procurement_approval_requirement('vendor_activation', ...)` — a tenant with an `always_required` policy for `vendor_activation` routes this step through the Platform Approval Engine even before the domain-level `PRC:Approve` check.

**What this does NOT cover:** true batch/CSV bulk vendor import (`ISS-2026-057`, disclosed OPEN — `bulk_import` exists only as an `intake_source` label on the single-vendor RPC path above, not a staged multi-row ingestion pipeline). Do not represent step 2 above as satisfying a batch-import requirement.

**Tabletop confirmation:** every function named above exists in `20260730580000` (confirmed via `grep -n "create function app\." this checkpoint); the sequence matches `scripts/db-tests/procurement-vendor-registration.sql`'s own exercised path (including the `ISS-2026-054`/`055` C-05/record_version fixes on `suspend_`/`reactivate_`/`archive_`/`blacklist_vendor_profile`, `PRC-269.md`).

## 2. Compliance expiry

**Scenario:** a vendor's compliance document (license, insurance, certification) is expiring or has expired, and the vendor needs a waiver or a hold resolved.

**Real sequence** (`supabase/migrations/20260730600000_create_procurement_vendor_compliance.sql`, `PRC-253.md`):

1. `app.recalculate_vendor_compliance_status`/`app.recalculate_tenant_vendor_compliance_status` (system-driven, also callable on demand) project the vendor's own eligibility-hold state from its document expiry dates — read via `app.get_vendor_compliance_eligibility`, the one function every downstream capability (Sourcing, PO, Assignment) composes to check a vendor's compliance-derived hold, never a duplicated check.
2. If a document is genuinely expiring and cannot be renewed in time: `app.request_vendor_compliance_waiver` (`PRC:Edit`) opens a time-bounded waiver request; `app.decide_vendor_compliance_waiver` (`PRC:Approve`/`PRC:Reject`) decides it — **hardened this session** (`PRC-269.md` §11.2, `ISS-2026-055`'s own adversarial-review correction): the authority/self-approval check now runs before the `stale_version` check, closing a real, live-reproduced `record_version`-disclosure-before-authority defect.
3. If the document can be renewed: `app.renew_vendor_compliance_document` supersedes the expiring version; `app.submit_vendor_compliance_document`/`app.decide_vendor_compliance_document` is the review path for a freshly submitted document.
4. `app.expire_vendor_compliance_waivers` (system/scheduled) lapses a waiver past its own bound — there is no manual "extend forever" path; a lapsed waiver must be re-requested.
5. `app.access_vendor_compliance_document_evidence` — the one gated read path to the underlying scanned document (`PRC:View personal data` where applicable), never a raw file-table select.

**Tabletop confirmation ("expired compliance," Prompt 270 §28):** confirmed via direct read that `app.get_vendor_compliance_eligibility`'s own hold projection is read-only and composed by name (not duplicated) in `PRC-256.md` (Sourcing), `PRC-260.md`/`PRC-261.md` (PO/Contract — compliance/contract validity gate added at batch 3's own Tier C fix pass, `PROCUREMENT_VENDOR_EXECUTION_INDEX.md` row 261-263 narrative), and `PRC-262.md`/`PRC-263.md` (Capacity/Assignment) — a vendor placed on a compliance hold is correctly blocked at every one of those downstream decision points, not only at compliance's own capability boundary.

## 3. Rate/RFQ

**Scenario:** procurement needs a vendor rate published, or needs to run a competitive RFQ and compare responses, and a rate conflict (a stale or superseded rate) needs resolving.

**Real sequence** (`supabase/migrations/20260730620000_extend_commercial_vendor_rate_for_procurement.sql`, `20260730640000_create_procurement_rfq.sql`, `20260730650000_create_procurement_vendor_comparison.sql`; `PRC-255.md`, `PRC-257.md`, `PRC-258.md`):

**Rate publishing:** `app.create_rate_version` (extends Commercial's own already-`VERIFIED` `COM-149` rate engine, `ADR-0020`'s `vendor_master_id` link, never a second rate store) → `app.add_vendor_rate_tier` (ordered, non-overlapping tiers, a real `btree_gist` `EXCLUDE` constraint prevents overlap, not an app-level check-then-insert race) → `app.approve_rate_version` (`PRC:Approve`) → `app.calculate_vendor_rate`/`app.select_vendor_rate` are the two real read paths (the latter is COM-149's own, PRC-gated for tier-cost data).

**Rate conflict (Prompt 270 §28's own named tabletop scenario):** "conflict" here means two overlapping candidate rates for the same vendor/lane/window. The real mechanism is `app.create_rate_version`'s own overlap-detection `EXCLUDE` constraint — a second, overlapping active rate is rejected at the database level, not silently accepted and left ambiguous at selection time. Resolution: the newer version must either supersede the prior one explicitly or use a genuinely non-overlapping effective window — there is no separate "resolve conflict" RPC because the constraint prevents the conflicting state from ever being persisted in the first place.

**RFQ:** `app.draft_rfq_from_sourcing` (from a PRC-256 sourcing shortlist) → `app.issue_rfq` → vendors respond via `app.submit_rfq_response`/`app.answer_rfq_clarification`/`app.record_rfq_clarification` → `app.close_rfq_for_comparison` (locks further responses) → `app.create_vendor_comparison`/`app._snapshot_vendor_comparison_offers` → `app.score_vendor_comparison_offer_criterion`/`app.link_vendor_comparison_offer_rate` → `app.recommend_vendor_comparison_offer` → `app.submit_vendor_comparison_for_approval` (routes through the shared evaluator as `vendor_selection`, currency-normalized via `app._normalize_vendor_comparison_currency` since `PRC-258`'s own original build — the precedent `PRC-269.md`'s own currency-threshold fix for the approval evaluator deliberately mirrors).

**Tabletop confirmation:** every function above confirmed via `grep` against its owning migration this checkpoint; the deadlock-safety fix between `close_rfq_for_comparison`/`submit_rfq_response` (`C-21`, batch 257-259 Tier C) and the overlap-constraint mechanism were independently re-confirmed present via direct migration read, not merely cited from memory.

## 4. PO/contract

**Scenario:** a purchase order or a standing vendor contract needs to be issued, amended, or a dispute over its terms needs resolving.

**Real sequence** (`supabase/migrations/20260730680000_create_procurement_purchase_order.sql`, `20260730700000_create_procurement_vendor_contract.sql`; `PRC-260.md`, `PRC-261.md`):

**Purchase order:** `app.draft_purchase_order_from_selection` (from an approved vendor-comparison selection) → `app.submit_purchase_order_for_approval` (governed as `purchase_order`, currency-aware since `PRC-269.md` Fix 3) → `app.issue_purchase_order` → `app.acknowledge_purchase_order` (vendor-facing acknowledgement, staff-entered — no live vendor-portal write path exists) → `app.record_purchase_order_fulfillment_status` → `app.amend_purchase_order`/`app.cancel_purchase_order` (both lock-ordered against the shared Platform Approval Engine tables, `ISS-2026-046`-adjacent deadlock fix, batch 260 Tier C).

**Vendor contract:** `app.create_vendor_contract_draft` → `app.submit_vendor_contract_for_approval` (governed as `vendor_contract`, `always_required`-only per the `procurement_approval_policies_value_dimension_check` constraint — never value-thresholded) → `app.activate_vendor_contract` → `app.amend_vendor_contract`/`app.renew_vendor_contract`/`app.suspend_vendor_contract`/`app.terminate_vendor_contract` (the last hardened at `PRC-263.md` with its own promised active-dependency guard — a contract with live dependent assignments cannot be silently terminated). `app.resolve_effective_vendor_contract` is the one deterministic read every downstream capability (Assignment, Capacity) composes to find "the currently-governing contract," never re-derived per capability.

**PO dispute (Prompt 270 §28's own named tabletop scenario) — disclosed gap, not fabricated:** **no dedicated "dispute" RPC or state exists on `app.purchase_orders`.** The real, available mechanisms are (a) `app.amend_purchase_order` for a negotiated correction while the PO remains open, (b) `app.cancel_purchase_order` for full withdrawal, and (c) `app.create_procurement_exception_request`/`app.decide_procurement_exception_approval_step` (the `exception_override` governed entity type) for a genuine governance exception outside the normal lifecycle. `ISS-2026-046`/`047` (both `OPEN`) already register that PO's own `close` lifecycle operation and 3 of 4 named alternative flows (including any dedicated dispute/revision-before-approval path) are unimplemented — this runbook's own tabletop exercise independently re-confirms that gap rather than inventing a workaround. An operator facing a real PO dispute today must use (a)/(b)/(c) above, whichever the specific disagreement actually calls for, and escalate anything those three do not cover as a support ticket, not a self-service flow.

**Tabletop confirmation:** the deadlock-safety fix (`app.cancel_purchase_order`/`app.decide_purchase_order_approval_step` lock reorder, and the deeper shared `PLT-123` fix) was independently re-confirmed present via direct migration read; `app.resolve_effective_vendor_contract`'s consumption by Assignment/Capacity was confirmed via grep for its own name in `20260730710000`/`20260730720000`.

## 5. Capacity

**Scenario:** a vendor's declared transport/warehouse capacity needs to be published, reserved against, or a shortage needs resolving.

**Real sequence** (`supabase/migrations/20260730710000_create_procurement_vendor_capacity.sql`, `PRC-262.md`):

1. `app.create_vendor_capacity_offer_draft` → `app.publish_vendor_capacity_offer` (checks vendor compliance hold and governing-contract validity at publish time, `PRC-269`-adjacent batch-3 Tier C fix — a vendor already on hold cannot even publish an offer).
2. `app.reserve_vendor_capacity` — the real concurrency-safe reservation write, live-proven with a real two-process race (two 70-ton reservations against a 100-ton offer: exactly one wins, total committed never exceeds capacity). Re-checks compliance/contract validity at RESERVE time too, independently from publish time (a vendor placed on hold AFTER its offer was published is still correctly blocked at reserve).
3. `app.accept_vendor_capacity_reservation`/`app.decline_vendor_capacity_reservation`/`app.release_vendor_capacity_reservation`/`app.consume_vendor_capacity_reservation` (consumption requires `status='accepted'` specifically — a merely-`'held'`, never-accepted reservation is not eligible, `ISS-2026-048`-adjacent batch-3 fix).
4. `app.add_vendor_capacity_blackout`/`remove_vendor_capacity_blackout` — declared unavailability windows `app.compute_vendor_capacity_available` subtracts from the published total.
5. `app.archive_vendor_capacity_offer` — retires an offer, blocked while active reservations exist.

**Capacity shortage (a request exceeds what remains available):** `app.reserve_vendor_capacity` itself is the shortage guard — it raises a real `over_reservation` error (`requesting N of <unit> but only M remains`) rather than allowing an overcommit; this was independently re-confirmed live in this session's own `db:test` runs (visible in the standard gate-suite output, e.g. `ERROR: over_reservation: requesting 70 of ton but only 30.000 of ton remains`). Resolution is operational, not a code path: find another vendor's capacity offer (via `app.list_vendor_capacity_offers`), split the requirement across multiple reservations, or escalate to a manual override outside this capability's own scope — no auto-substitution mechanism exists.

**Tabletop confirmation:** the compliance/contract-validity double-check (publish time AND reserve time, independently) and the `'held'`-vs-`'accepted'` consumption gate were both independently re-confirmed by direct migration read this checkpoint, matching `PRC-262.md`/`PRC-263.md`'s own cited fixes exactly.

## 6. Assignment

**Scenario:** a vendor needs to be invited to and confirmed for an operational job (extending Operations' own canonical resource assignment), and a shortage of eligible vendors needs resolving.

**Real sequence** (`supabase/migrations/20260730720000_create_procurement_vendor_assignment.sql`, `PRC-263.md`):

1. `app.get_vendor_assignment_eligibility_preview`/`app.evaluate_vendor_assignment_eligibility` — auto-resolves the vendor's currently-effective governing contract via `app.resolve_effective_vendor_contract` when none is supplied, and checks BOTH contract status and effective-date window (a batch-3 Tier C fix — the eligibility check previously only checked status, not whether the contract was actually in its effective window).
2. `app.propose_vendor_assignment_invitation` (`PRC:Edit`) → vendor-side `app.accept_vendor_assignment_invitation`/`app.decline_vendor_assignment_invitation` (staff-entered, no live vendor-portal write path) → `app.confirm_vendor_assignment` (`OPS:Assign`, the canonical commitment — checked twice, once here and again inside the nested already-`VERIFIED` Operations `app.resource_assignments`/`app.assign_resource` call, never weakened).
3. `app.reassign_vendor_assignment`/`app.cancel_vendor_assignment_invitation` for changes; `app.override_vendor_assignment` for a governed emergency override, requiring BOTH `PRC:Edit` and `OPS:Assign` authority per the two-authority split this capability's own spec names explicitly.

**Assignment shortage (Prompt 270 §28's own named tabletop scenario — no eligible vendor available):** `app.evaluate_vendor_assignment_eligibility`/`get_vendor_assignment_eligibility_preview` are the real, live "can this vendor even be proposed" gate — a vendor failing on compliance hold, contract validity/window, or capacity is correctly rejected before an invitation is even created, so the shortage surfaces AT PROPOSAL time (a clear, typed rejection reason) rather than as a silent later failure. Resolution is operational: check `app.list_vendor_capacity_offers`/`app.list_vendor_contracts_expiring` for the real reason (no capacity, no active contract, compliance hold) and address that root cause (renew the contract, request a compliance waiver, find a different vendor) — there is no "force assign anyway" path except the explicit, dual-authority `app.override_vendor_assignment`.

**Tabletop confirmation:** the auto-resolution + effective-window check, and the two-authority override split, were both independently re-confirmed by direct migration read this checkpoint, matching `PRC-263.md`'s own cited HIGH-severity Tier C fixes.

## 7. Performance

**Scenario:** a vendor's KPI scorecard needs to be calculated/published, a source dispute or manual adjustment needs deciding, or a governed suspend/blacklist/reactivate lifecycle decision needs making.

**Real sequence** (`supabase/migrations/20260730740000_create_procurement_vendor_performance.sql`, `PRC-264.md`):

1. `app.calculate_vendor_kpi_metrics` (idempotent, C-01-hardened target-tuple check) computes real per-category results from Phase 5/6 evidence directly — never a duplicated metrics store; 11 built-in calculators including `_calc_vendor_kpi_rate_validity` (the one category always computable, even for a sparse-data vendor — this is the exact function `ISS-2026-059` (`PRC-269.md` §11.3.1) found to have a real, self-healing, time-of-day-dependent day-window arithmetic bug in its own `db:test` fixture, see `PROCUREMENT_VENDOR_HANDOFF_PACKAGE.md` §5 for full disclosure — a fresh reader running the db-test suite in the ~01:00–03:59 UTC band will see `scripts/db-tests/procurement-vendor-performance.sql` fail on this exact assertion, and that failure is expected, not a new regression).
2. `app.publish_vendor_kpi_scorecard` — requires metrics to have been calculated first (raises `metrics_not_calculated` otherwise).
3. `app.raise_vendor_kpi_source_dispute`/`app.decide_vendor_kpi_source_dispute` (self-decide blocked) — recalculation excludes the disputed event, always as a NEW metric-value version, never a silent rewrite of an already-published scorecard.
4. `app.request_vendor_kpi_manual_adjustment`/`app.decide_vendor_kpi_manual_adjustment` (maker-checker, reason required, at most one pending per line; hardened at `PRC-269`-adjacent batch-4 Tier C to re-verify the target scorecard is still the CURRENT published one at approval time — `stale_scorecard` guard).
5. `app.evaluate_vendor_lifecycle_recommendation`/`app.decide_vendor_lifecycle_recommendation` — the governed (system-recommends, human-decides, self-approval blocked) suspend/blacklist/reactivate surface, calling straight through to `PRC-251`'s own unmodified `app.suspend_vendor_profile`/`app.blacklist_vendor_profile`/`app.reactivate_vendor_profile` — never a second, competing lifecycle mechanism.
6. `app.raise_vendor_performance_issue`/`app.add_vendor_performance_corrective_action`/`app.update_vendor_performance_corrective_action_status`/`app.update_vendor_performance_issue_status` — issue/corrective-action tracking, independent of the scorecard itself.

**Tabletop confirmation:** the `stale_scorecard` re-verification guard and the source-dispute-versioning-not-rewrite behavior were both independently re-confirmed by direct migration read this checkpoint, matching `PRC-265.md`'s own batch-4 Tier C findings exactly. `ISS-2026-059`'s own root cause (a `generate_series` call whose upper bound falls before its lower bound for `now()`-hour ∈ {1,2,3} UTC) was independently re-derived by hand this checkpoint against the real function body in `20260730740000_create_procurement_vendor_performance.sql:1186`, confirming the corrected 01:00–03:59 UTC window `PRC-269.md`'s own fix round already established (not the earlier, one-hour-imprecise "00:00–03:59" figure `docs/runtime/KNOWN_ISSUES.md`'s own `ISS-2026-059` entry still carries, disclosed as a known, uncorrected imprecision in that specific pre-existing file per this checkpoint's own earlier fix round).

## 8. Match exceptions

**Scenario:** a vendor bill needs to be matched against its supporting PO/contract/rate/cost/tax/ePOD/milestone evidence, and a variance or a suspected duplicate needs an exception decision.

**Real sequence** (`supabase/migrations/20260730750000_create_procurement_vendor_invoice_matching.sql`, `PRC-265.md`):

1. `app.create_vendor_bill_match_case` (against a real Phase 4 `app.finance_vendor_bills` row, `FIN-200` — zero writes to any `app.finance_*` table anywhere in this capability) — the duplicate-invoice-fingerprint check (`app.compute_vendor_bill_match_fingerprint`) is serialized with a `pg_advisory_xact_lock` keyed on `(tenant_id, fingerprint)`, live-proven race-safe with a real two-process test (`PRC-265.md`'s own headline CRITICAL fix).
2. `app.map_vendor_bill_match_line` — maps each bill line to its PO/contract/rate/actual-cost/ePOD/milestone evidence; `app._score_vendor_bill_match_line`/`app._vendor_bill_match_pct_variance` compute tolerance-relative variance against the tenant's own versioned `app.vendor_bill_match_tolerance_policies` (`app.create_vendor_bill_match_tolerance_policy_draft`/`app.activate_vendor_bill_match_tolerance_policy`).
3. Within-tolerance: `app.accept_vendor_bill_match_within_tolerance`. Out-of-tolerance or a flagged probable duplicate: `app.request_vendor_bill_match_exception_approval` → `app.decide_vendor_bill_match_exception_approval` (self-approval blocked).
4. Vendor-stated-figure disagreement: `app.raise_vendor_bill_match_dispute` → `app.record_vendor_bill_match_dispute_response` → `app.resolve_vendor_bill_match_dispute` — an upheld dispute excludes that line from the numerator every sibling KPI/reconciliation calculator (including `_calc_vendor_kpi_invoice_accuracy`, `PRC-264`/`265`'s own wiring) already uses the same generic mechanism to respect.
5. `app.re_evaluate_vendor_bill_match_case`/`app._reroll_vendor_bill_match_case` — re-derives the aggregate decision after new evidence (e.g. a late ePOD) arrives, re-querying fresh evidence rather than copying stale flags forward (a `PRC-269`-adjacent batch-4 Tier C fix).
6. `app.get_vendor_bill_match_readiness`/`app.get_vendor_bill_match_reconciliation_status` — the read-only handoff back to Finance (the latter reused verbatim by `PRC-266`'s own dashboard Group 7, zero new SQL).

**Match failure (Prompt 270 §28's own named tabletop scenario):** a case that cannot clear within tolerance and is not resolved via dispute routes to the exception-approval path (step 3 above) — there is no silent-fail state; every case ends in one of `matched`/`exception` (pending or decided)/`cancelled` (`app.cancel_vendor_bill_match_case`). The real duplicate-fingerprint race (the CRITICAL fix cited above) is the specific "two near-identical bills both slip through" failure mode this capability was built to prevent, and is the one this checkpoint's own tabletop most directly re-confirms via the cited two-process regression evidence.

**Tabletop confirmation:** the advisory-lock serialization and the `invoice_accuracy` numerator anti-join (excluding upheld-dispute/exception-approved lines) were both independently re-confirmed by direct migration read this checkpoint, matching `PRC-265.md`'s own live two-process race proof and `PRC-269.md`'s own composed evidence.

## 9. Portal leak — explicitly cannot be tabletop-tested, disclosed rather than fabricated
