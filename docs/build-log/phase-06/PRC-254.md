## 1. Objective

Implement purpose-bound vendor bank-account and tax-identity data with **genuine at-rest encryption** (this repository's first such mechanism — every prior "sensitive field" used visibility masking only), a deterministic hash for duplicate detection without decryption, mandatory maker-checker approval with MFA-reauth freshness, a payment-term change proposal/approval pair over the existing `app.vendor_profiles.payment_term_days` column, and a real downstream verification-status read — without executing or simulating any settlement/payment/cash movement (RPD-038) and without mutating `app.vendor_profiles.lifecycle_status`.

## 2. Migration

**`supabase/migrations/20260730610000_create_procurement_vendor_financial_security.sql`** — the only migration this checkpoint adds. Full header comment documents every design decision (16 numbered notes); summarized here.

### 2.1 The encryption mechanism (design notes 1–4)

- `pgcrypto` was already enabled repository-wide (`20260716075355_create_tenants.sql`) — **not** re-declared.
- `app.vendor_financial_encryption_key()` reads `current_setting('app.vendor_financial_encryption_key', true)` and **raises `encryption_key_not_configured` (fails closed)** if the GUC is unset or empty — never silently encrypts with an empty/default key. Production key provisioning/rotation/custody is a disclosed, out-of-scope infrastructure concern (ADR-0010 already selected the secret-manager product; this function is the one config value this capability reads from it). db-tests set the GUC to a fixed test-only value (`test-only-key-not-for-production`) at the top of the fixture.
- `app._encrypt_vendor_financial_value`/`app._decrypt_vendor_financial_value` wrap `pgp_sym_encrypt`/`pgp_sym_decrypt`. `app._hash_vendor_financial_value` is a deterministic `encode(digest(plaintext,'sha256'),'hex')` — the **only** column ever indexed/compared for equality (duplicate detection never decrypts). `app._last4_vendor_financial_value` is the plain, unencrypted masked-display convention. All five are **private helpers with no grant** to `authenticated`/`service_role`/`anon` — callable only from within another `SECURITY DEFINER` function owned by the same role, the identical shape `app._compute_vendor_assessment_score` (PRC-252) established.
- `app.vendor_bank_accounts.account_number_encrypted`/`app.vendor_tax_identities.tax_id_encrypted` (`bytea`) hold the true value. `account_number_hash`/`tax_id_hash` (indexed `text`) hold the sha256 digest. `account_number_last4`/`tax_id_last4` (plain `text`) hold the masked-display value every `PRC:View`-only caller sees by default.
- The two reveal RPCs (`app.reveal_vendor_bank_account_number`/`app.reveal_vendor_tax_identity_number`) are the **only** paths that ever decrypt. Both require `app.has_prc_view_personal_data` (reused from PRC-251, never duplicated), a non-empty purpose-bound `p_reveal_reason`, and MFA-reauth freshness (a deliberate strengthening beyond the letter — revealing plaintext is at least as privileged as approving a change). Every successful call is unconditionally audited via `app.capture_audit_event` — never a silent decrypt.

### 2.2 A real bug found and fixed during db-test authoring: the shared redaction regex swallowed the deliberately-safe last4 audit fields

`app.capture_audit_event` already applies `app.redact_audit_payload` (PLT-116) unconditionally to `before_value`/`after_value`. That function's key-name regex (`secret|password|token|key|authorization|cookie|ssn|npwp|bank|account_number|salary|payroll`) matched the literal substrings **"bank"** and **"account_number"** — meaning a jsonb key literally named `bank_name`/`account_number_last4` (my first draft) was silently redacted to `"[REDACTED]"` even though the underlying VALUE (a bank's display name; a deliberately-safe last-4 reveal) is not itself sensitive. Found via a genuine `db:test` run (the reveal-audit assertion counted zero matching rows) — not by static review. Fixed by renaming the **audit-payload JSON keys only** (never the underlying table columns) to `institution_name`/`account_last4`, which do not trip the shared, correctly-conservative, key-name-based regex. `tax_id_last4`/`tax_id_type` did not need renaming (no collision). Disclosed in the migration's own design note 9 addendum and in `server/contracts/vendor-financial/vendor-financial.ts`'s own header (the same regex is mirrored by `scripts/observability/logger.ts`, so the TS-layer reveal schema's plaintext field is deliberately named `bankAccountNumber`, not `accountNumber`, for the identical reason — verified programmatically, not assumed).

### 2.3 Versioning, maker-checker, MFA (design notes 5–7)

- `account_family_id`/`tax_family_id` mirror `app.vendor_compliance_requirements.requirement_family_id` (PRC-253) one layer down: minted fresh on draft creation, carried forward onto a newly **approved** row only when the checker supplies `p_supersedes_account_id`/`p_supersedes_tax_identity_id` at **decision** time (never at draft-create time) — the exact "a draft has no borrowed identity until confirmed" discipline `app.publish_vendor_compliance_requirement` established. A partial unique index guarantees at most one active version per family; a second, defensive scope-tuple unique index (`vendor, purpose, currency` / `vendor, tax_id_type`) closes the "two independent families targeting the same practical scope" ambiguity PRC-253's own design note 3 already disclosed and closed the same way.
- Self-approval block: the exact `self_approval_not_allowed` inline pattern `app.approve_warehouse_billing_event` established, reproduced in every `decide_*` RPC, plus a redundant table-level CHECK (`*_no_self_approval_check`).
- MFA freshness: the **exact** `p_reauth_confirmed_at`/`reauth_required`/`insufficient_privilege`/5-minute-window shape `app.start_support_session` (PLT-115) and `app.decide_credit_profile_approval_step` (COM-157) established, reproduced verbatim in every `decide_*` RPC and both reveal RPCs. Not a real MFA provider integration — the same disclosed limitation both precedents carry.

### 2.4 Schema

- **`app.vendor_bank_accounts`** — `vendor_master_record_id`, `account_family_id`, `account_holder_name`, `bank_name`, `account_number_encrypted`/`account_number_hash`/`account_number_last4`, `currency` (validated via `app.validate_currency_code`, FIN-194 — never a second currency registry), `purpose` (`primary|settlement|other`), `status` (`draft → pending_approval → active/rejected`, plus `hold`/`deactivated` reachable from `active`), `effective_from`, `evidence_file_id`, `supersedes_account_id`, `proposed_by(_auth_user_id)`, `approved_by(_auth_user_id)`, `reauth_confirmed_at`, `rejection_reason`, `hold_reason`, `deactivation_reason`, `idempotency_key`, `record_version`.
- **`app.vendor_tax_identities`** — mirrors the exact same shape one field-set down (`tax_family_id`, `tax_id_type` free text per RPD-016 — no NPWP checksum/format validator hardcoded, matching FIN-195's own `is_example_fixture` convention, `tax_id_encrypted`/`tax_id_hash`/`tax_id_last4`, `legal_name_on_file`, same lifecycle).
- **`app.vendor_payment_term_proposals`** (design note 10) — a proposal/approval **pair** over the plain `app.vendor_profiles.payment_term_days` integer column PRC-251 already created, **not** a new payment-terms master (Prompt 255's own ADR-0020 reconciliation owns that open decision; ADR-0018/0019 precedent prefers flat typed columns over a generic changeset shape). `vendor_profile_expected_version` snapshots the vendor profile's own `record_version` at proposal time so the approval branch can optimistically-concurrency-guard the `payment_term_days` UPDATE, surfacing `vendor_profile_changed_since_proposal` rather than silently overwriting an unrelated concurrent profile change.

**Bank account (10):** `create/update_vendor_bank_account_draft`, `submit_vendor_bank_account_for_approval`, `decide_vendor_bank_account_approval`, `hold/reactivate/deactivate_vendor_bank_account`, `get/list_vendor_bank_accounts_masked`, `reveal_vendor_bank_account_number`. **Tax identity (11):** the identical 10 RPCs one field-set down, plus `access_vendor_tax_identity_evidence`.

**Payment term (4):** `propose/decide_vendor_payment_term_change(_proposal)`, `get/list_vendor_payment_term_proposals`.

**Downstream (1):** `get_vendor_financial_verification_status` — the single real, tested READ RPC (design note 11) a future Finance/Sourcing/PO/invoice-matching capability composes against: `has_verified_bank_account`/`has_verified_tax_identity`/`on_hold`, nothing more. Never writes to any `app.finance_*` table; never mutates `app.vendor_profiles.lifecycle_status`; never executes/simulates settlement (RPD-038, Sec.24).

**Private helpers (7, no grant):** `vendor_financial_encryption_key`, `_encrypt_vendor_financial_value`, `_decrypt_vendor_financial_value`, `_hash_vendor_financial_value`, `_last4_vendor_financial_value`, `assert_vendor_bank_account_editable`, `assert_vendor_tax_identity_editable`.

RBAC: all 12 already-seeded PRC actions reused, **zero new `app.permissions` rows seeded**. Mapping: `Create` = draft/propose; `Edit` = update draft/submit; `Approve`/`Reject` = decide (case-mapped); `Override` = hold/reactivate/deactivate; `View` = masked reads + downstream status; `View personal data` = the two reveal RPCs (the genuine fit this already-seeded, `protected=true` action exists for); `Download` = the two evidence-access RPCs.

### 2.6 Hardened patterns (copied byte-for-byte from `20260730600000`, the most recently proven-correct migration)

- `record_version` optimistic concurrency (pre-check **and** post-UPDATE not-found re-check) on every mutating RPC.
- Idempotency-key replay comparing every load-bearing field, including `account_number_hash`/`tax_id_hash`/`currency`/`purpose` — PRC-253's own adversarial review found TWO separate under-compared idempotency instances (missing `expiry_date`, then separately `reminder_offsets`); this migration compares every distinguishing field from the start rather than re-discovering the gap.
- `for update` locks on every read-then-conditionally-mutate path, plus a **per-family `pg_advisory_xact_lock`** (`hashtextextended(vendor::text||':'||family::text, <salt>)`) in every `decide`/`hold`/`reactivate`/`deactivate` RPC — this closes a race PRC-253's single-row-per-decision shape did not have: approving a new draft (which deactivates the OLD active row of the same family) races a bystander `hold`/`deactivate`/`reactivate` acting **directly** on that OLD row — two *different* rows in the same family, so a plain per-row `for update` lock does not serialize them by itself. Applied proactively, mirroring `app._recalculate_vendor_compliance_status_family`'s own advisory-lock fix (PRC-253) and `app.reconcile_shipment_tracking_health`'s sibling fix (CG-S10-ATW-024).
- Nested `begin/exception when unique_violation` race-recovery on every idempotency-keyed INSERT, using `GET STACKED DIAGNOSTICS` to distinguish the idempotency-unique-index violation from the active-scope-unique-index violation (mirrors PRC-253's own multi-constraint disambiguation).
- Evidence-file re-validation (tenant/`record_type='vendor_financial_verification'`/`record_id`=vendor's own `master_record_id`/`malware_scan_status='clean'`) on every `p_evidence_file_id` parameter — the exact gap PRC-252's AND PRC-253's own adversarial reviews independently found and fixed as a CONFIRMED HIGH finding, applied proactively here a third time.
- RLS row-policy **and** column-level GRANT are two different layers, both required: `app.vendor_bank_accounts`/`app.vendor_tax_identities` get the default-deny row policy (`has_active_tenant_membership and not actor_holds_customer_user_layer, or is_supreme_admin`) **plus** an explicit column-list GRANT to `authenticated` that omits `account_number_encrypted`/`account_number_hash`/`tax_id_encrypted`/`tax_id_hash` entirely — mirrors `app.vendor_rate_versions`' own column-restricted GRANT (COM-149). `service_role` gets the full, unrestricted grant (used exclusively internally by this migration's own `SECURITY DEFINER` functions).

## 3. Design decisions / deviations (disclosed in the migration header too)

1. Encryption mechanism follows the task brief's own worked-through plan literally (pgcrypto + fail-closed GUC + sha256 hash + last4) rather than inventing an alternative.
2. Family-based versioning is a genuine new structural addition beyond PRC-253's own shape (two tables need it, not one), disclosed as mirroring `requirement_family_id` one layer down.
3. MFA reauth was applied to **both** approve and reject decisions (and to both reveal RPCs), not only the approve path — a deliberate strengthening beyond a literal reading, disclosed rather than silently narrowed, since the checker/approver-differs-from-maker rule and freshness are cheap to apply uniformly and this capability's own data is the most sensitive in the repository to date.
4. No dedicated "document/version viewer" route was built for financial evidence (unlike PRC-253's own fix-pass addition) — the evidence-access RPCs (`access_vendor_*_evidence`) exist and are wired into the UI as an inline "View evidence" control on each card, but there is no separate renewal-lineage page (bank accounts/tax identities do not have PRC-253's own multi-version-per-slot renewal concept — a "propose change" here is a NEW row in the same family, decided once, not an in-place file version bump). Disclosed as a scope-appropriate simplification, not an oversight.
5. Draft **editing** (`update_vendor_bank_account_draft`/`update_vendor_tax_identity_draft`) is fully built, tested (db-test), and wired into the service layer, but **not yet surfaced in the UI** — the UI currently only exposes propose/submit/decide/hold/reactivate/deactivate/reveal. A typo in a draft today requires the maker to let it be rejected and re-propose rather than editing in place. Disclosed as a real, scoped UI gap (the backend contract is complete and tested), not a backend limitation — mirrors PRC-251's own precedent of disclosing a UI gap distinct from a backend one (§8, "no document/evidence attachment wired into the onboarding wizard UI").
6. The maker-checker approval queue is nested per-vendor (this page), not a separate tenant-wide route — no tenant-wide "list every pending bank account/tax identity across the tenant" RPC was built. Mirrors PRC-253's own design decision 9 (waiver UI nested per-vendor) for the identical reasoning: this task's own required scope does not name a tenant-wide queue, and building one would need inventing a new read RPC beyond scope.
7. `get_vendor_financial_verification_status.has_verified_bank_account` is `true` only while the vendor's own bank account status is literally `active` — a bank account moved to `hold` correctly flips this to `false` (the downstream read's own literal contract: "a currently verified, usable account", not merely "one exists somewhere in history"). Verified by db-test.

### 7.1 Real defects found and fixed during authoring (before this report)

1. **Ambiguous `id` column reference** in `app.get_vendor_bank_account_masked`/`app.get_vendor_tax_identity_masked` — both `RETURNS TABLE(id uuid, ...)` functions had an unqualified `where id = p_account_id`/`where id = p_tax_identity_id` in their own initial lookup, which Postgres rejects as ambiguous (the `RETURNS TABLE`'s own `id` column becomes an implicit plpgsql variable) — the exact defect class PRC-251's own build log records finding and fixing three times. Found via a real `db:test` execution (not static review). Fixed by table-qualifying both references (`app.vendor_bank_accounts.id`/`app.vendor_tax_identities.id`). Systematically re-checked every other `RETURNS TABLE(...)` function in the migration for the same pattern — confirmed no other function was affected (every other `RETURNS TABLE` shape either has no `id`/`vendor_master_record_id`-named column at all, or already used a table alias throughout).
2. **The `redact_audit_payload` key-name collision** (§2.2 above) — a genuine, non-obvious interaction with pre-existing platform infrastructure, found only by directly inspecting `app.audit_logs` content after tracing why a `do $$ ... $$` block's own transaction rollback was hiding it (see item 3 below).
3. **Test-authoring lesson, not a product defect:** a `do $$ ... $$` block executed via `psql -f` is one atomic statement — an unhandled `raise exception` (including the deliberate assertion-failure pattern used throughout this suite) rolls back **everything** done earlier in that same block, not just the failing statement. Debugging the redaction defect required reproducing it interactively outside the all-or-nothing block wrapper (a disposable `cargogrid_debug` database, fixtures/migrations applied manually, RPCs called directly in an open `psql` session) rather than querying `app.audit_logs` after a failed full-suite run, which — as expected once understood — showed zero rows for every action in the failing block, including ones that had genuinely succeeded moments earlier.
4. **Two test-fixture bugs (not product defects):** the duplicate-hash-detection test blocks (both bank account and tax identity) originally left the second, sharing-the-same-hash account/tax-identity row in `draft` status — but `is_duplicate_candidate`'s own SQL only counts `active`/`pending_approval` rows on the *other* side of the comparison (by design, so a discarded draft never falsely flags a real active account as suspicious). Fixed by submitting the second fixture row to `pending_approval` before asserting the flag, in both blocks.
5. **A third test-fixture bug (not a product defect):** the downstream verification-status test originally assumed the vendor's own NPWP tax identity (deliberately driven through hold/reactivate/**deactivate** by an earlier test block, ending `deactivated`) would still read as `active` — it does not. Fixed by creating a second, genuinely active tax identity of a different `tax_id_type` (`BUSINESS_LICENSE`) specifically for the downstream-composition assertion, rather than relying on stale cross-block state.

None of these were product-facing defects surviving to this report except item 1, a real correctness bug in the shipped migration, found and fixed before it was ever committed.

## 11. Fix-pass disposition (post-checkpoint adversarial review)

Three independent adversarial reviewers (spec-compliance, security-rls, correctness-concurrency) examined the implementation above. This section records the disposition of every finding they raised, applied to the same, still-uncommitted working tree.

### 11.1 Confirmed and fixed

1. **security-rls Finding 1 (MEDIUM) — evidence-access RPCs leaked record state to zero-permission, cross-tenant callers via error-message ordering, with no audit trail for the probe.** `app.access_vendor_bank_account_evidence`/`app.access_vendor_tax_identity_evidence` checked `evidence_file_id is null` *before* the `PRC:Download` authority gate — a caller with zero grant on ANY tenant could distinguish `no_evidence_attached` from `insufficient_authority` for a guessed bank-account/tax-identity UUID, and the probe itself produced no audit row (the authority-denial path raised, and a raised exception rolls back everything the same statement did, including any prior `capture_audit_event` insert). **Fixed**: the authority gate now runs first; on denial the RPC no longer raises — it returns a `'denied'` row with `file_id` nulled out (so the denial itself carries no signal about whether evidence exists) and the denial is captured in `app.audit_logs` (`result='failure'`, `after_value->>'gate'='insufficient_authority'`) before the row is returned. `evidence_file_id is null` is now checked only after authority is confirmed, so it can no longer be probed by an unauthorized caller. `server/contracts/vendor-financial/vendor-financial.ts`'s `fileId` was widened to nullable to carry this. Verified live by `scripts/db-tests/procurement-vendor-financial-security.sql` (a viewer-lacks-`PRC:Download` case now asserts `access_result='denied'`, `file_id is null`, and a matching `app.audit_logs` row).
2. **security-rls Finding 2 (MEDIUM) — bank-account supersede omitted `currency` from the active-scope comparison, letting a legitimate maker+approver pair silently deactivate an unrelated, active, different-currency bank account.** `app.decide_vendor_bank_account_approval`'s `invalid_supersede` check compared only `vendor_master_record_id`/`purpose`, but the real active-scope tuple `vendor_bank_accounts_active_scope_unique` enforces is three columns (`vendor_master_record_id, purpose, currency`). **Fixed**: `currency` is now compared too. Verified live: a USD proposal attempting to supersede an existing active IDR account (same vendor/purpose) now raises `invalid_supersede`, and the IDR account is confirmed still `active` afterward (`scripts/db-tests/...sql`). The tax-identity mirror was independently confirmed already-correct (its 2-column active-scope tuple, `vendor_master_record_id`/`tax_id_type`, was already fully compared) — no change needed there.
3. **correctness-concurrency Finding 1 (MEDIUM) — the per-family advisory lock in both `decide_*_approval` RPCs used the wrong key during a supersede, making it dead code for exactly the race it was built to close.** `pg_advisory_xact_lock` was taken on `v_account.account_family_id` — the pending_approval draft's own freshly-minted, never-contended family id — *before* the supersede branch resolved the real contended family (`v_superseded.account_family_id`, 16 lines later). A bystander `hold`/`reactivate`/`deactivate` call racing an in-flight supersede-approval never waited on this lock at all; only the pre-existing per-row `for update` lock provided serialization (which happened to still be sufficient in every traced scenario, but the advisory-lock layer specifically built for this race was silently non-functional). **Fixed**: both `decide_vendor_bank_account_approval` and `decide_vendor_tax_identity_approval` now look up the superseded row's family id *before* acquiring the lock (a plain, non-locking `select`), lock on that family, and only then re-fetch the superseded row `for update` (closing the gap between the two reads). When no supersede is requested, the lock correctly falls back to the draft's own family (unchanged behavior). No live corruption was reproduced against the fix (this repository has no `dblink`/`pg_background`, a standing disclosed limitation — see §9/§11.3) — the fix restores correct lock-key selection by direct code inspection and the full sequential suite passes unchanged.
4. **correctness-concurrency Finding 2 (LOW) — idempotency-key replay comparison omitted `effective_from`/`evidence_file_id`, the same under-compared-field gap class PRC-253's own review found twice (`expiry_date`, then `reminder_offsets`).** `create_vendor_bank_account_draft`/`create_vendor_tax_identity_draft` compared `account_number_hash`/`tax_id_hash`/currency/purpose/tax_id_type/legal_name but never `effective_from` or `evidence_file_id` — a replayed key with a different effective date would silently return the original row instead of `idempotency_key_conflict`. **Fixed**: both fields added to both comparisons (the pre-insert check and the `unique_violation` race-recovery handler, both tables). `evidence_file_id` coverage is by code symmetry with the fixed comparison (both fields are compared together, same `is distinct from` chain); `effective_from` is additionally covered by a new, direct db-test assertion for both tables.
5. **spec-compliance Finding 2 (HIGH) — `hold`/`reactivate`/`deactivate` bypassed both MFA reauth and any second-actor check, letting a single `PRC:Override` holder place a hold and immediately, unilaterally undo it.** None of the six RPCs (`hold`/`reactivate`/`deactivate` × bank account/tax identity) took a `p_reauth_confirmed_at` parameter, and `reactivate` had no check that the actor differed from whoever placed the hold — directly undermining §24 ("No bank change becomes effective without maker-checker...and privileged current authentication") for the exact thing these RPCs mutate: the record's own effective, downstream-consumed verification status. **Fixed**: all six RPCs now take `p_reauth_confirmed_at` and enforce the same ≤5-minute freshness check as `decide`/`reveal` (`reauth_required`, errcode `insufficient_privilege`). `reactivate` additionally now rejects the same actor who placed the hold (`self_reactivation_not_allowed`, mirroring `self_approval_not_allowed`'s own shape) — a new `hold_by_auth_user_id` column tracks this, set on hold, cleared on reactivate. `hold`/`deactivate` do not carry an equivalent actor-separation check (they are unilateral protective/terminal actions initiated once, not reversals of another privileged decision — the concrete exploit scenario the reviewer gave was specifically about a hold being unilaterally reversed). Propagated through the TS contracts (`reauthField` added to all six input schemas), `server/mutations/vendor-financial.ts`, the server actions (`actions.ts`, now plain async calls carrying `reauthConfirmedAt` instead of the `useActionState`/`FormData` shape, since the reauth timestamp must be captured client-side at click time), and the UI (`financial-panel.tsx`'s new `ReauthActionForm` component, replacing the removed `SimpleActionForm` for these three actions — a re-authentication checkbox gates the button exactly like `DecideForm`/`RevealControl` already do). Verified live: stale/missing reauth blocked on hold and reactivate; the same actor reactivating their own hold blocked with `self_reactivation_not_allowed`; a genuinely different Override-holding actor (a second fixture identity, `manager2`) succeeds.

### 11.2 Confirmed but deliberately not fixed this pass, with reasoning

6. **spec-compliance Finding 1 (HIGH) — denied/blocked attempts on `reveal`/`decide`/`hold`/`reactivate`/`deactivate` are never audited, since every denial path `raise exception`s before reaching `capture_audit_event`.** This is real: Postgres rolls back **the entire statement** — including any audit-insert already performed earlier in the same function call — when an unhandled exception propagates out of it (there is no partial commit without an autonomous transaction). This repository has no `dblink`/`pg_background` anywhere (confirmed by repo-wide grep; disclosed at `20260730290000_create_advanced_tms_label_barcode_operations.sql:1640` and in this migration's own design note 16), so "audit the denial, then still raise" is not achievable for a raise-based RPC without either (a) a new, repository-wide autonomous-transaction dependency this migration should not unilaterally introduce, or (b) converting every denial path in ~10 RPCs to the non-raising, `access_result`-style return shape — a structural change to every one of this migration's own approve/reveal/lifecycle RPCs (and every caller: `server/mutations/`, the server actions, the UI's error-display contract) that is materially riskier to make correctly under this fix-pass's own time budget than the two evidence-access RPCs it *was* safe to convert (§11.1 item 1), which already returned a structured result for their other denial branch and needed no contract change beyond nulling one field. Verified this is not a defect unique to this capability: `app.approve_warehouse_billing_event` (ATW-020), the exact precedent this migration's own `self_approval_not_allowed` pattern was copied from, has the identical "raise before reaching capture_audit_event" shape for its own self-approval denial — this is a pervasive, pre-existing repository convention, not something introduced here. **What was fixed instead**: the one part of this finding that *was* safely achievable — the two evidence-access RPCs, which already used the non-raising pattern for their other denial branch — now audit their authority denial too (§11.1 item 1), closing the specific, concrete, reproducible "probing" attack the security-rls review demonstrated live. The broader gap (decide/hold/reactivate/deactivate/reveal denials still un-audited) is a genuine, disclosed residual limitation — see §9.
7. **spec-compliance Finding 3 (MEDIUM) — §26 "Operations sees eligibility only" has no distinct permission from full masked detail.** Real: `get_vendor_financial_verification_status` and the full masked list/detail RPCs are gated by the identical `PRC:View` action, so a tenant admin cannot grant "eligibility signal only" without also unlocking full masked bank/tax detail for the same actor. **Not fixed**: `app.permissions.action` is a fixed, closed enum (`permissions_action_check`, `20260716103445_create_roles_permissions.sql`) — every migration that has ever seeded a `(module, action)` row, including this one's own reuse of `View personal data`/`Download`, reuses a value already inside that enum; none has ever widened it. PRC-252's own adversarial review found and disclosed the structurally identical gap for purpose-bound masking (`safety`/`compliance` criteria) and, after attempting and reverting a permissions-enum widening, concluded the same thing this report concludes: doing so to solve one capability's own scoping gap is an unprecedented, repository-wide-risk change to shared RBAC infrastructure, disproportionate to this fix pass. Left as a disclosed limitation, consistent with that precedent.
8. **spec-compliance Finding 4 (MEDIUM) — §26 "vendor user sees own masked values and may request change" is entirely unimplemented.** Confirmed real and, per the reviewer, previously undisclosed. No vendor-facing identity/session/portal concept exists anywhere in this repository (grep for `vendor_user_layer`/`is_vendor_user`/`vendor_portal_user` returns nothing repo-wide) — building one is a net-new authentication surface, not a fix within this migration's own scope. **Not fixed**; now explicitly disclosed in §9 below (it was a real gap in this build log's own prior disclosure list, which the reviewer correctly flagged).
9. **spec-compliance Finding 5 (LOW) — MFA re-authentication is a client-attested timestamp, not a real second factor.** Already disclosed (§2.3, §9) as inherited from the PLT-115/COM-157 precedent this capability was explicitly told to copy — not a new defect, no action needed beyond confirming the disclosure is present and accurate, which it is.
