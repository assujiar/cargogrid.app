## 1. What this checkpoint extends

PRC-260 is the tenth Phase 6 checkpoint, built directly on the already-`COMPLETED`
PRC-257 (RFQ), PRC-258 (Vendor Comparison), and PRC-259 (Procurement Approval).
It implements exact, source-linked purchase orders as governed vendor
commitments: a PO root/version/number, itemized lines snapshotted from the
source RFQ, exact commercial calculation inherited from the selected vendor
comparison offer, an optional tax composition, submit/issue lifecycle, the
Platform Approval Engine binding PRC-259 registered `purchase_order` as a
valid `entity_type` for but left unbuilt, vendor acknowledgement capture,
governed amendment (re-versioning), cancel-eligible cancellation, and
descriptive fulfillment-status tracking. A PO is created ONLY from an
already-approved, `submitted` `app.vendor_comparisons` selection
(`approval_status in ('approved', 'not_required')`) — exactly the
consumption contract PRC-259's own migration header documented as "Prompt
260's own future PO-award RPC."

Per this prompt's own explicit reuse instructions: `app.vendor_profiles.
payment_term_days` (PRC-251) is read directly for default payment terms —
no separate payment-terms config table is created. `app.calculate_finance_tax`
(FIN-195) is composed, unmodified, only when a caller supplies a tax code
(opt-in) — it is never worked around when no approved tax rule covers the
date; it REJECTS, and this migration lets that rejection propagate.
`app.vendor_comparison_offers.normalized_amount` (PRC-258, itself already
produced by `app.calculate_vendor_rate` + `app.convert_finance_amount` +
`app.apply_finance_rounding`, FIN-194) is the PO's own subtotal verbatim —
no FX conversion or rounding is reimplemented anywhere in this migration,
because none is needed at this layer. `app.rfq_requirement_lines` (PRC-257)
is snapshotted into `app.purchase_order_lines` at draft/amend time. PO
commitment creates no AP, journal, settlement, or cash movement anywhere in
this migration (business rule 24) — verified by direct grep: zero
`INSERT`/`UPDATE` in this file touches any `app.finance_*` table.

`app._request_procurement_entity_approval` (PRC-259's shared, private,
no-grant submit-time glue) is called exactly once, inside
`app.submit_purchase_order_for_approval`, following the exact three-step
pattern PRC-259's own migration header documented for this prompt: two axis
columns on the new table (`approval_status`/`approval_request_id` — no
naming collision exists on this brand-new table, so the literal names are
used, unlike `app.vendor_rate_versions`'s own `governance_approval_status`
rename), and one new domain sync wrapper
(`app.decide_purchase_order_approval_step`) mirroring the other four
wrappers exactly, including the two hardening fixes the 257–259 batch's own
Tier C review applied to its siblings: `app.assert_actor_is_session_identity`
as the first statement (C-13) and the `p_reauth_confirmed_at`
5-minute-freshness MFA gate (C-18, PRC-254/COM-157 pattern) — built in from
the start here, not retrofitted by a later hardening pass.

## 3. Schema summary (all additive)

- `app.purchase_order_number_counters` + `app.next_purchase_order_number` —
  one atomic, tenant-scoped monotonic counter, mirroring `app.rfq_number_
  counters`/`app.next_rfq_number` (PRC-257) exactly — the same bounded,
  disclosed alternative to the full Configurable Numbering Engine (PLT-125)
  every PRC-25x capability with its own number has used. `po_number` is
  assigned once, at draft time, and stays stable across every later amended
  version (mirrors `app.rfqs.rfq_number`).
- `app.purchase_orders` — the PO root/version. A governed amendment
  (`app.amend_purchase_order`) marks the current row `superseded` and
  inserts a brand-new `draft` version (`version + 1`, `revised_from_id` set,
  same `po_number`) — never an in-place rewrite of an issued/acknowledged
  PO (business rule: "Approved/issued PO is changed only by linked
  amendment/version; no silent overwrite"). `status` is the six-value
  machine (`draft→submitted→issued→acknowledged`, any pre-fulfillment state
  `→cancelled`, `issued|acknowledged→superseded` via amend).
  `approval_status`/`approval_request_id` are the PRC-259 Platform Approval
  Engine binding axis, independent of `status` — no naming collision on
  this brand-new table (migration header). `fulfillment_status`
  (`not_started→partial→fulfilled`, monotonic, enforced by an explicit rank
  comparison in `app.record_purchase_order_fulfillment_status`) +
  `fulfillment_reference` (a polymorphic, application-validated, purely
  descriptive reference — never re-validated against a foreign Operations
  table, mirrors `app.procurement_exception_requests.related_entity_type`/
  `related_entity_id`'s own already-established pattern) are a deliberately
  minimal proxy for Operations fulfillment progress — business rule 24's
  "PO does not duplicate Operations execution," structurally enforced by the
  absence of a second shipment/task table, not merely policy-asserted. At
  most one non-`cancelled`/non-`superseded` PO may exist per comparison
  selection at a time (`purchase_orders_comparison_active_unique`, a
  partial unique index on `comparison_id`) — the database-level "block
  duplicate issue" business rule.
- `app.purchase_order_lines` — itemized lines, snapshotted from `app.rfq_
  requirement_lines` at draft/amend time — never re-derived after. No
  per-line unit price: the comparison this PO is drawn from only ever
  produces one header-level total (`app.vendor_comparison_offers.
  normalized_amount`), a disclosed, bounded scope boundary (§9), not an
  oversight.
- `app.purchase_order_events` — append-only PO-root lifecycle history, one
  row per real status transition, mirroring `app.vendor_comparison_events`
  (PRC-258) exactly. Fulfillment-status changes are NOT root lifecycle
  transitions and do not write here (mirrors the established "child-level
  action, no parent event row" precedent) — `app.capture_audit_event` still
  records every one of those.
- Directory views: `app.purchase_orders_directory` (masked, cost fields
  nulled behind `PRC:View cost`), `app.purchase_order_lines_directory`
  (plain — no cost-bearing column exists on lines), `app.purchase_order_
  events_directory` (masked, `reason` nulled behind `PRC:View cost`) — all
  three built column-masked and column-restricted-granted FROM THE START
  (taxonomy C-11, the batch 257-259 review's own §3 lesson applied here
  proactively rather than needing a future hardening pass): `authenticated`
  is granted only the non-cost columns directly on the base tables, and each
  `_directory` view independently masks the same columns for any caller
  lacking `PRC:View cost`. None of the three views has a TypeScript or
  db-test caller today (grepped clean) — the masking is defense in depth
  for the raw grant surface itself, matching the hardened `app.vendor_
  comparison_*_directory` precedent exactly.

## 4. Functions summary

- **Creation (`PRC:Create` + `PRC:View cost`, +`FIN:View` when a tax code is
  supplied):** `app.draft_purchase_order_from_selection` — idempotent on
  `(tenant_id, idempotency_key)`, replay compares the full caller-supplied
  tuple (`comparison_id`/`tax_code`/the RESOLVED `payment_term_days`/dates/
  `commercial_terms`/`notes` — see §6 for why the resolved, not raw, value

  `approval_status in (approved, not_required)`; requires the selected
  offer to be `included` with a non-null `normalized_amount`; requires the

  (taxonomy C-04, mirrors `app.draft_rfq_from_sourcing`'s own shape); an
  optional `p_tax_code` composes `app.calculate_finance_tax` and verifies
  the resolved tax rule's own currency matches the PO's currency before
  accepting it (a new, C-22-adjacent guard this migration adds, not
  inherited).
- **PO-root lifecycle (`PRC:Edit` unless noted):**
  `app.submit_purchase_order_for_approval` (`draft→submitted`, the routing
  trigger point — resolves governance BEFORE the single UPDATE, locks the

## 5. Design decisions

**Lock order (taxonomy C-04/C-21), stated once, verified clean.**
`app.draft_purchase_order_from_selection` locks the foreign parent
(`app.vendor_comparisons`) before creating brand-new `app.purchase_orders`/
`app.purchase_order_lines` rows (new rows need no lock). Every OTHER
function in this migration locks exactly ONE governed table row `for
update` — its own `app.purchase_orders` row — and never a second governed
table row in the same transaction. No two functions in this migration lock
the same two tables in different orders, so no C-21-shaped deadlock is
possible within this file; documented explicitly in the migration's own
header rather than left implicit, per the 257–259 batch's own C-21 lesson.

**C-22 (currency-blind threshold comparison), inherited via `ISS-2026-045`,
not silently worked around.** `app._request_procurement_entity_approval` is
called here exactly as PRC-259 built it — `app.evaluate_procurement_
approval_requirement`'s own `p_value_amount >= v_policy.min_value_amount`
comparison has no currency dimension (already disclosed, HIGH, OPEN). This
migration threads `p_currency := v_po.currency` through to the context
snapshot (so a reviewing approver still SEES the real currency, never
silently dropped) but that value is not consulted by the threshold
comparison itself — the same known gap `rate_version`/`vendor_selection`
already carry, now shared by `purchase_order` too. Not fixed here — the
correct fix shape is a genuine architectural decision `ISS-2026-045` already
registers as out of any single capability prompt's own mandate.

**A genuinely new, non-inherited currency guard: the tax-rule-currency
mismatch check.** `app.calculate_finance_tax` (FIN-195) computes a tax
amount in whatever currency its own resolved rule is denominated in, with
no FX step of its own. Accepting that amount at face value into
`total_amount` would silently mix two different currencies the moment a
tenant's tax rule and PO currency diverge — found and fixed during this
checkpoint's own design (not post-hoc): `app.draft_purchase_order_from_
selection` now verifies the resolved rule's own `currency` matches the
PO's `currency` before accepting `taxAmount`, failing closed
(`tax_rule_currency_mismatch`) rather than silently composing a
currency-mismatched total.

**RBAC mapping reuses the 12 already-seeded PRC actions exclusively** — no
new `app.permissions` row. `Create` = `draft_purchase_order_from_selection`
(+`View cost`, +`FIN:View` when a tax code is supplied). `Edit` =
`submit_purchase_order_for_approval`, `issue_purchase_order`,
`acknowledge_purchase_order`, `record_purchase_order_fulfillment_status`,
`amend_purchase_order`, `cancel_purchase_order` — matching access rule 26
("Procurement drafts/issues/amends"). `View`/`View cost` = every read path.
No `PRC:Approve` gate exists on any PO RPC directly — the governed approval
decision itself routes through `app.decide_purchase_order_approval_step`,
which (mirroring its three siblings) delegates its own authority check to
`app.decide_approval_step`'s internal eligible-approver check rather than a
raw `PRC:Approve` permission, consistent with access rule 26's own
"approvers authorize" being a separate governance surface from "Procurement
drafts/issues/amends."

**No external vendor-facing acknowledgement surface** — identical reasoning
to PRC-257 design note 5 and PRC-258's own "no vendor identity ever reaches
this migration." `app.acknowledge_purchase_order` requires an authenticated
internal actor recording the vendor's acknowledgement (offline/email
capture), with a mandatory note — never a live vendor-facing accept/decline
endpoint, which would be this repository's first new anonymous/public
entry point since Prompt 251, an `ADR-0021` §3.2 batch-cut trigger on its
own, for zero net capability this prompt's own acceptance criteria
requires.

**No REST/GraphQL surface, no notification/job wiring** — identical
reasoning to every prior Phase 6 checkpoint's own disclosed boundary.

## 6. Real defects found and fixed during this checkpoint's own Tier B walk

Per `docs/standards/RECURRING_DEFECT_TAXONOMY.md` §2, the full §4 walk ran
against this checkpoint's own diff, iterated live against a real disposable
Postgres via repeated `pnpm run db:test` runs (this checkpoint's own new
`procurement-purchase-order.sql` plus the full 142+-file repository suite)
before this migration was ever declared `COMPLETED`. One real defect was
found and fixed directly in the migration, caught by the checkpoint's own
db-test iteration, not by inspection alone:

1. **C-01-adjacent (idempotency replay compared the RAW parameter instead
   of its RESOLVED value), `app.draft_purchase_order_from_selection`.** The
   first draft resolved `v_payment_term_days` (falling back to the vendor's
   own default when `p_payment_term_days` is null) AFTER the idempotency
   pre-check, and compared `v_existing.payment_term_days is distinct from
   p_payment_term_days` — the RAW, un-resolved caller parameter. A caller
   who legitimately omitted `p_payment_term_days` on both the original call
   and an identical-tuple replay would see the replay INCORRECTLY rejected
   as `idempotency_key_conflict`, because the stored row carries the
   resolved value (e.g. `30`, the vendor's own default) while the replay's
   raw parameter is `null` — `30 IS DISTINCT FROM null` is true, so the
   comparison fired even though the caller supplied an identical tuple both
   times. Live-caught by this checkpoint's own db-test replay assertion
   (`idem-po-draft-1` called twice with identical parameters) failing with
   a spurious `idempotency_key_conflict` before this fix. Fixed by moving
   the `v_payment_term_days` resolution BEFORE both the idempotency
   pre-check and the `unique_violation` race-recovery handler, and
   comparing against the resolved value in both places — the exact
   "discriminate before recovering, compare what was actually stored"
   discipline C-01 demands, applied to a resolved-default field rather than
   a raw pass-through one. Not a Critical/High-severity defect (no data
   corruption or unauthorized access — a legitimate idempotent retry was
   spuriously rejected, which is a real correctness bug but fails safe, not
   silently), but a genuine, live-reproduced C-01-class defect the
   checkpoint's own iteration caught before shipping, not by inspection.

No other defect was found in this checkpoint's own migration code by the
Tier B walk below — every other class was verified clean or is N/A by
construction, recorded in full in §7.
