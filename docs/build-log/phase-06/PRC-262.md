## 1. What this checkpoint builds

Vendor-owned capacity declaration, blackout, reservation, acceptance and release --
extends, never duplicates, Phase 5's own canonical resource identities. Three tables:
`app.vendor_capacity_offers` (a declared quantity available over a time window for a
service/mode/lane, optionally referencing a canonical Phase 5 resource and/or a
governing PRC-261 contract), `app.vendor_capacity_blackouts`, and `app.vendor_capacity_
reservations` (a commitment held against an offer's own quantity).

Unlike Phase 5's `app.vehicle_capacity_reservations` (a single-vehicle, single-leg hold
keyed by a unique index), vendor capacity is a QUANTITY offered over a TIME WINDOW that
can be partially consumed by multiple concurrent reservations -- "available" requires
real overlap arithmetic under a lock, not a unique-index collision. The concurrency-
critical write, `app.reserve_vendor_capacity`, locks the parent offer row `for update`
before computing `available = quantity - sum(overlapping active reservations)` and
inserting -- every concurrent reservation attempt against the SAME offer serializes
through that one lock. This is not merely asserted: `scripts/db-tests/procurement-
vendor-capacity.sql` launches two REAL, independent psql processes (reusing `scripts/
db-tests/wms-picking-concurrency-helper.sh`) racing two 70-ton reservations against a
100-ton offer -- live-reproduced, exactly one won, the loser was rejected `over_
reservation`, total committed never exceeded 100.

No vendor-portal identity exists (already-accepted PRC-257/258/261 precedent) -- every
lifecycle action is staff-initiated on the vendor's behalf, disclosed rather than
fabricating a vendor-facing acceptance surface.

## 4. Tier B — recurring defect taxonomy self-check

Lessons from PRC-261's own Tier B self-check (run immediately before this prompt, in
the same session) were applied FROM THE FIRST DRAFT here, not discovered fresh:
idempotency replay verifies the full target tuple (C-01) from the start; the
concurrency-critical reservation write locks its parent row before computing a decision
(C-04) from the start, by design (§1 above); by-id reads fold not-found and
cross-tenant into one error (C-05) from the start. Two real findings still surfaced and
were fixed in-prompt:

- **C-09 (exception handler catches an SQLSTATE class instead of its intended
  constraint) -- CONFIRMED, fixed.** `app.vendor_capacity_reservations_idempotency_
  key_unique` was originally scoped to `(tenant_id, idempotency_key)`, but `app.
  reserve_vendor_capacity`'s own pre-check and exception-handler race-recovery queries
  were both scoped to `(offer_id, idempotency_key)` from the start -- a genuine scope
  mismatch. Reusing the same idempotency key across two DIFFERENT offers in the same
  tenant would have violated the tenant-scoped index while the offer-scoped recovery
  query found no row to recover from, re-raising a raw `unique_violation` instead of a
  clean `idempotency_key_conflict`. Fixed by rescoping the index to `(offer_id,
  idempotency_key)` -- the correct natural scope, since a reservation's idempotency
  concern belongs to its own offer, not the tenant. Live-proven, not just DDL-inferred:
  a regression test reuses the same key against a second, different offer and confirms
  it now succeeds independently (the CORRECT post-fix behavior -- two genuinely
  different resources, no conflict), not merely that an error is avoided.
- **C-20 (a capability with no caller) -- CONFIRMED, fixed.**
  `app.compute_vendor_capacity_available` was built, granted, and reachable with zero
  UI caller. Fixed: the offer detail page now shows a live "available now (full
  window)" figure computed via this exact RPC.

## 5. Residual, disclosed limitations (itemized -- C-23 discipline)

1. No recurring-availability declaration (§22 names "recurring capacity" as an
   alternative flow) -- every offer is a single, explicit time window; a vendor with a
   standing weekly commitment must currently declare it as one long window or several
   discrete offers. No recurrence-rule engine exists anywhere in this repository to
   compose with.
2. No vendor-portal "vendor updates own scoped capacity" surface (§15 names this as
   optional, §26) -- the same already-accepted PRC-257/258/261 scope boundary, not a
   fresh regression.
3. `app.get_vendor_capacity_reservation` (a by-id single-reservation read) has no
   direct UI caller -- the detail page lists every reservation for an offer via `list_
   vendor_capacity_reservations` instead; a standalone reservation deep-link page was
   judged out of this prompt's own bounded scope and is disclosed rather than built.
4. `resource_master_id`/`contract_id` linkage on an offer is accepted by the RPC layer
   but not exposed as a picker in the create/update forms (the UI only lets a caller
   set service type/quantity/UOM/window) -- these fields are real, tested, and settable
   via direct RPC call (e.g. by a future PRC-263 integration), just not yet from this
   prompt's own minimal creation form.
