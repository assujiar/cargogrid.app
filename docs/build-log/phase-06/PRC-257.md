# PRC-257 — Procurement RFQ

**Prompt ID:** `CG-S11-PRC-008` · **Package document:** `CG-AABPP-PRC-257` · **Status at end of this checkpoint:** `COMPLETED` under `docs/adr/ADR-0021` (batched review cadence) — Tier A green, Tier B walked and recorded below, adversarially unreviewed. This prompt is batch 1 of the 257–260 range; `VERIFIED` is reserved for the batch's Tier C close, not claimed here.

## 1. What this checkpoint extends

PRC-257 is the seventh Phase 6 checkpoint, built directly on the already-`VERIFIED`
PRC-256 (Sourcing). It implements source-linked Procurement RFQs: an RFQ
root/version/number, governed vendor invitation (scoped to PRC-256's own
`app.sourcing_candidates` where `shortlisted = true`), clarification, deadline
extension, a governed revision/reissue path, versioned confidential vendor
response capture (internal offline/email only — see §5), and a comparison-
ready close. It reads (never re-derives) two already-canonical roots:
`app.sourcing_requests` and `app.sourcing_candidates` (PRC-256, migration
`20260730630000`). Per the reuse instructions given for this prompt, it also
composes the already-proven file engine (`app.files`/`app.initiate_file_upload`/
`app.record_file_scan_result`, PLT-128) for private, scanned response
evidence, and the already-proven RBAC evaluator (`app.evaluate_permission`)
and numbering pattern (`app.next_quotation_number`, COM-151) — no second
vendor-shaped table, no second file/numbering engine.

## 3. Schema summary (all additive)

- `app.rfq_number_counters` + `app.next_rfq_number` — one atomic, tenant-scoped
  monotonic counter, mirroring `app.quotation_number_counters`/`app.next_
  quotation_number` (COM-151) exactly — a bounded, disclosed alternative to
  the full Configurable Numbering Engine (PLT-125), which no Procurement
  capability has adopted yet. Internal bookkeeping only; RLS `using (false)`,
  the identical "none" policy `quotation_number_counters` already uses.
- `app.rfqs` — the RFQ root/version. `rfq_number` is stable across every
  version of one RFQ; a "changed requirements" revision (`app.revise_rfq`)
  marks the current row `superseded` and inserts a brand-new row (`version`
  + 1, `revised_from_id` set) rather than rewriting an already-issued RFQ in
  place. `status` is the five-value machine
  (`draft→issued→closed|cancelled`, `draft→cancelled`, `issued→superseded`
  via revise). `requirements_snapshot` **never carries `budget_amount`** —
  stripped at write time (`v_sourcing.demand_snapshot - 'budget_amount'`),
  the stronger fix relative to PRC-256's own read-time masking, since RFQ
  comparison uses each vendor's own `total_amount`, never the internal
  budget benchmark. `app.rfqs` therefore carries no cost-sensitive column of
  its own; `app.rfqs_directory` is a **plain**, unmasked view. Non-negativity/
  range `CHECK`s on every cargo field applied from the start (PRC-256's own
  C-15 lesson, not rediscovered here).
- `app.rfq_requirement_lines` — itemized lines, one default line auto-
  populated at draft/revise time from the inherited cargo profile; editing a
  line means revising the whole RFQ (no in-place per-line edit — a disclosed,
  bounded first iteration mirroring COM-151's own "line editing is add/remove
  only" precedent).
- `app.rfq_invitations` — one row per (RFQ, invited vendor). `sourcing_
  candidate_id` traces every invitation to the exact PRC-256 eligibility
  decision that authorized it — never re-derived. `app.issue_rfq` bulk-
  creates these from every `shortlisted = true` `app.sourcing_candidates`
  row (bounded to 500 per call, disclosed via `raise warning` on overflow,
  mirroring PRC-256's own 500-vendor scan bound); `app.invite_additional_
  rfq_vendor` adds one **eligible** (never ineligible — exception flow) but
  not-originally-shortlisted candidate under a governed `PRC:Override`
  exception with a mandatory reason. `status` is `invited→declined|
  no_response|responded|withdrawn`.
- `app.rfq_clarifications` — offline-captured Q&A (no external vendor-facing
  ask/answer surface exists — see §5). `vendor_master_id` null = broadcast to
  every invited vendor.
- `app.rfq_responses` + `app.rfq_response_attachments` — versioned, vendor-
  commercial-offer evidence (never automatically selects/commits a vendor).
  `currency`/`total_amount`/`validity_until`/`commercial_terms` are cost-
  sensitive, masked in `app.rfq_responses_directory` and in `app.list_rfq_
  responses` behind the already-proven `app.has_prc_view_cost` (PRC-252),
  mirroring `budget_amount`'s own established treatment. A response received
  after `response_deadline_at` is `late_capture = true`, requires `PRC:
  Override` **in addition to** the baseline `PRC:Edit` plus a mandatory
  `late_reason`, and is never `comparison_eligible`. Attachments are private,
  scanned files re-validated at the accepting RPC itself (tenant/record-
  scope/`malware_scan_status = 'clean'` — taxonomy C-10), never trusted from
  `app.initiate_file_upload`'s own prior classification.
- `app.rfq_events` — append-only RFQ-root lifecycle history, one row per real
  status transition, mirroring `app.sourcing_request_events` exactly.
  Invitation/clarification/response-level actions are not RFQ-root
  transitions and do not write here (mirrors `app.shortlist_sourcing_
  candidate`'s own "child-level action, no parent event row" precedent) —
  `app.capture_audit_event` still records every one of those.
- Directory views: `app.rfqs_directory` (plain), `app.rfq_requirement_lines_
  directory` (plain), `app.rfq_invitations_directory` (plain), `app.rfq_
  clarifications_directory` (plain), `app.rfq_responses_directory` (masked).
  Row filters use the hardened pattern-5 predicate (`has_active_tenant_
  membership(...) and not actor_holds_customer_user_layer(...)`) from
  creation, copied verbatim from every prior PRC-25x table.

## 4. Functions summary

- **Creation (`PRC:Create`):** `app.draft_rfq_from_sourcing` (idempotent on
  `(tenant_id, idempotency_key)`, replay compares `sourcing_request_id`/
  `owner_user_id`; blocks a sourcing request that is not `shortlisted`;
  locks the foreign PRC-256 parent row `for update` before deciding — taxonomy
  C-04).
- **RFQ-root lifecycle (`PRC:Edit` unless noted):** `app.revise_rfq`
  (only from `issued`, mandatory reason, idempotent on its own key comparing
  the four resolved override fields — not just `revised_from_id`, see §6),
  `app.issue_rfq` (`draft→issued`, bounded bulk invitation), `app.invite_
  additional_rfq_vendor` (`PRC:Override`, mandatory reason, eligible-only),
  `app.extend_rfq_deadline` (widen-only, mirrors PRC-256's own override
  widen-only semantics), `app.close_rfq_for_comparison` (`issued→closed`,
  marks every still-`invited` invitation `no_response`), `app.cancel_rfq`
  (`draft|issued→cancelled`, mandatory reason).
- **Invitation-level:** `app.decline_rfq_invitation` (`PRC:Edit`, mandatory
  reason, only while `invited` and the parent RFQ is `issued`; lock order
  invitation-then-parent, taxonomy C-04 design note 8).
- **Clarification:** `app.record_rfq_clarification`, `app.answer_rfq_
  clarification` (both `PRC:Edit`).
- **Response:** `app.submit_rfq_response` (baseline `PRC:Edit` checked
  *before* the parent RFQ's own deadline is ever read; only if the capture
  turns out to be late does a *second*, additional `PRC:Override` check run
  — composing two independently-gated checks so the deadline itself is never
  disclosed pre-authorization, mirroring PRC-256's own C-05 fix applied here
  from the start rather than rediscovered by review), `app.withdraw_rfq_
  response` (`PRC:Edit`, mandatory reason, only the latest version).
- **Reads (`PRC:View`):** `app.get_rfq`, `app.list_rfqs` (server-clamped
  ≤200 rows, superseded excluded by default), `app.list_rfq_requirement_
  lines`, `app.list_rfq_invitations`, `app.list_rfq_clarifications`,
  `app.list_rfq_responses` (masked, `PRC:View cost`), `app.list_rfq_response_
  attachments`, `app.get_rfq_history` — every one reconstructs its own
  masked/plain projection directly from the base table with the RPC's own
  explicit `p_actor_auth_user_id`, never `select * from <directory view>`
  (PRC-256's own C-06 lesson, applied here from the start).
- Reused, not duplicated: `app.evaluate_permission`, `app.capture_audit_
  event`, `app.has_prc_view_cost` (PRC-252), `app.has_active_tenant_
  membership`/`app.actor_holds_customer_user_layer`, `app.initiate_file_
  upload`/`app.record_file_scan_result`/`app.files` (PLT-128).

## 5. Design decisions

**No external vendor-facing response/ask surface is built.** Prompt 257 §15
itself names this "optional... only when vendor identity scope is verified."
Building a live anonymous public vendor-facing submission endpoint would be
this repository's first *new* anonymous/public entry point since Prompt 251's
vendor-intake token — an `ADR-0021` §3.2 batch-cut trigger on its own — for
zero net capability this checkpoint's own acceptance criteria requires.
Prompt 257's own business rule 3 ("Offline/email capture requires actor,
source file/message, received time and vendor confirmation where policy
requires") describes exactly the internal capture flow this migration builds
instead: `app.submit_rfq_response` requires an authenticated internal actor,
optional re-validated evidence files, a mandatory `received_at`, and an
explicit `vendor_confirmed` flag. Vendor invitation tokens (§16) are deferred
alongside the external surface they exist to secure — a token with no
consuming endpoint is a capability with no caller (taxonomy C-20), not a
security control. **Confidentiality (§16 "vendors cannot see competitor
offers") is structurally satisfied, not merely policy-enforced**, precisely
because no vendor-facing read path exists anywhere in this migration — every
read RPC gates on tenant + `PRC:View`(+cost), the same internal actor model
every other PRC-25x capability already uses.

**No notification/job dependency is wired.** Prompt 257's own §20/§23 text
was re-read in full before deciding: §20 says "durable notification/retry"
for clarification/decline/no-response handling in the abstract, and §23
("Exception flow") names "failed notification ambiguity" as a state to
handle safely — but neither section, nor §28 ("Tests to create"), states a
concrete notification *event* this capability itself must emit (e.g. "notify
the vendor on issue," "remind on approaching deadline"). Absent an external
vendor-facing surface (§5 above), there is no vendor identity to notify in
the first place — the only conceivable notification target would be internal
Procurement staff, for which no explicit trigger is named either. Per this
prompt's own explicit instruction ("only wire notifications/jobs if the
spec text actually requires it"), neither `app.queue_notification` nor
`app.enqueue_job` is called by this migration — disclosed here rather than
silently added or silently omitted, the same "re-read in full before
deciding" discipline PRC-256's own design note 14 already applied to its own
notification question.

**RFQ root/version/number** uses the bounded, disclosed `app.next_rfq_number`
counter (mirrors COM-151's `app.next_quotation_number` exactly) rather than
the full Configurable Numbering Engine (PLT-125), which no Commercial or
Procurement capability has adopted yet — the same considered choice COM-151
made and disclosed for itself.

**Requirement lines are add-at-creation/revision only**, no standalone
per-line edit RPC — mirrors COM-151's own disclosed "line editing is add/
remove, not in-place edit" scope boundary; changing a requirement line means
a governed revision of the whole RFQ (`app.revise_rfq`), consistent with the
business rule that changed requirements are never a silent edit.

**RBAC mapping reuses the 12 already-seeded PRC actions exclusively** — no
new `app.permissions` row. `Create` = `draft_rfq_from_sourcing`. `Edit` =
`revise_rfq` (a governed but routine workflow step, mandatory reason — not an
exception since it's a named, expected business flow), `issue_rfq`,
`extend_rfq_deadline`, `close_rfq_for_comparison`, `cancel_rfq`, `decline_
rfq_invitation`, `record_rfq_clarification`, `answer_rfq_clarification`,
`submit_rfq_response` (on-time), `withdraw_rfq_response`. `Override` =
`invite_additional_rfq_vendor` (always — a governed exception, extends
PRC-256's own "no algorithm autonomously selects a vendor" to "an additional,
not-originally-shortlisted vendor needs a human override to be invited"),
`submit_rfq_response` (late capture only, composed on top of the baseline
`Edit` gate — design note 7 in the migration). `View` = every read RPC
(+`View cost` for response pricing fields).

## 6. Real defects found and fixed during this checkpoint's own Tier B walk

Per `docs/standards/RECURRING_DEFECT_TAXONOMY.md` §2, the full §4 walk ran
against this checkpoint's own diff before it was declared `COMPLETED` (not a
separate adversarial review — none is due until the batch's Tier C close).
Four real gaps were found and fixed directly in the migration before it was
applied anywhere (the same "not yet applied, so fix in place" precedent
PRC-255/PRC-256 already established) — full detail in the migration's own
design note 13:

1. **C-01 (idempotency replay compared the key but not the full target),
   `app.submit_rfq_response`.** The first draft compared only
   `rfq_invitation_id`/`total_amount`/`currency`/`received_at` on replay.
   Widened to compare every caller-supplied field (`validity_until`/
   `lead_time_days`/`capture_mode`/`source_message_ref`/`vendor_confirmed`/
   `commercial_terms`), in both the pre-check and the `unique_violation`
   race-recovery handler. New db-test assertion: reusing a key with an
   identical amount but a different `lead_time_days` now correctly raises
   `idempotency_key_conflict` (it previously would have silently returned
   the earlier row).
2. **C-01, `app.revise_rfq`.** The first draft's replay comparison checked
   only `revised_from_id`. Widened to compare the four resolved override
   fields (`cargo_weight_max`/`cargo_volume_max`/`destination_lane`/
   `currency`), computed once (before the idempotency check) and reused by
   both the pre-check and the race-recovery handler. New db-test assertion:
   reusing a revise key with a different `cargo_weight_max` now correctly
   raises `idempotency_key_conflict`.
3. **C-04 (decision made on an unlocked parent/state row),
   `app.invite_additional_rfq_vendor`.** The candidate's `eligible` flag was
   read via a plain `select`, not locked — a concurrent PRC-256 re-evaluation
   (`app.evaluate_sourcing_candidate_eligibility`) could in principle flip
   `eligible = false` between the read and the insert. Fixed by adding
   `for update`, locked after `app.rfqs` (this function's own existing
   lock) — confirmed this does not introduce a new deadlock class against
   either PRC-256 function's own locking order (candidate row(s) then
   `sourcing_requests`; `app.rfqs` is never locked by any PRC-256 function).
   No matching sequential db-test proof exists for the race itself (this
   repository's automated suite is single-connection — the same standing,
   already-disclosed limitation every prior Phase 6 checkpoint records); the
   fix was verified by direct code-path inspection against the repository's
   own proven `for update` pattern.
4. **C-20 (a capability with no caller), `app.list_rfq_response_
   attachments`.** The RPC existed, was granted, and had a real db-test
   assertion — but the detail page never called it. Fixed by wiring it into
   `app/(tenant)/[tenantSlug]/procurement/rfq/[rfqId]/page.tsx` (fetched per
   response) and rendering an attachment count next to each response row in
   the panel, rather than leaving it silently unreachable.

None of these were shipped uncaught — every one surfaced from this
checkpoint's own disciplined Tier B walk (build → walk the taxonomy → fix →
re-run `db:test`) before the migration was ever applied to a real database,
and before the prompt was declared `COMPLETED`.

  Confidentiality is structurally guaranteed by this surface's absence, not
