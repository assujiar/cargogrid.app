# PRC-258 — Vendor Comparison

**Prompt ID:** `CG-S11-PRC-009` · **Package document:** `CG-AABPP-PRC-258` · **Status at end of this checkpoint:** `COMPLETED` under `docs/adr/ADR-0021` (batched review cadence) — Tier A green, Tier B walked and recorded below, adversarially unreviewed. This prompt is batch 1 of the 257–260 range; `VERIFIED` is reserved for the batch's Tier C close, not claimed here.

## 1. What this checkpoint extends

PRC-258 is the eighth Phase 6 checkpoint, built directly on the already-`COMPLETED`
PRC-257 (Procurement RFQ, same batch). It implements exact, explainable comparison of
eligible vendor RFQ responses across cost and configured non-price criteria: a
comparison root/version, per-vendor normalized offers, non-price scoring, ranking, a
governed recommendation, and a human selection/submission handoff ready for the
approval engine (Prompt 259 — not called from this checkpoint; PRC-258 only reaches a
`submitted` state for 259 to read next). It reads (never re-derives) three already-
canonical roots: `app.rfqs`, `app.rfq_invitations`, and `app.rfq_responses` (PRC-257,
migration `20260730640000`) — the eligible-vendor-response universe for comparison is
exactly PRC-257's own `comparison_eligible = true`, `status = 'submitted'` responses on
a `closed` RFQ, never re-computed. Per this prompt's own explicit instructions, it
composes — never reimplements — `app.calculate_vendor_rate` (PRC-255/FIN-194,
migration `20260730620000`) per vendor RFQ response when an approved vendor rate is
linked, and `app.convert_finance_amount` (FIN-194, migration `20260728230000`,
hardened `20260730500000`) for cross-currency normalization — both always feeding
`app.apply_finance_rounding` (FIN-194), the one rounding authority, via those two
functions' own internal use of it.

## 3. Schema summary (all additive)

- `app.vendor_comparisons` — the comparison root/version. A "recalculate" (business
  rule, Prompt 258 §24: "a comparison cannot rewrite the underlying vendor
  response/rate; revisions create a new comparison version") is `app.revise_vendor_
  comparison` — marks the current row `superseded` and inserts a brand new row
  (`version` + 1, `revised_from_id` set), never an in-place rewrite. Also serves the
  "compare scenarios by volume/date/service" alternative flow (§22) — a different
  `basis_weight`/`basis_volume`/`basis_quantity` is simply a new comparison version,
  listed alongside prior versions. `status` is the five-value machine
  (`draft→recommended→submitted`, `draft|recommended→cancelled`,
  `draft|recommended→superseded` via revise). `criteria_snapshot` (jsonb array of
  `{key,label,weight}`) is validated/defaulted at write time (`app._normalize_vendor_
  comparison_criteria` — exactly one `price` entry, weights sum to 100; null/empty
  input defaults to 100% price) — a bounded, disclosed alternative to a dedicated
  criteria-configuration engine, no capability in this repository having adopted one.
- `app.vendor_comparison_offers` — one row per (comparison, rfq_response), snapshotted
  at create/revise time from the LATEST `submitted`+`comparison_eligible` response per
  invitation (a withdrawn or late-captured latest version contributes no offer, even if
  an earlier version was once eligible — current state governs). `source_currency`/
  `source_total_amount` preserve the vendor's own quoted offer verbatim for lineage;
  `normalized_amount` is always produced by `app.convert_finance_amount` (never a
  bespoke conversion), optionally fed by `app.calculate_vendor_rate`'s own
  `computed_amount` when an approved `app.vendor_rate_versions` row is linked
  (`app.link_vendor_comparison_offer_rate`) — REPLACING the vendor-quoted total as the
  normalization source. `included=false` + `exclusion_reason` covers both a
  reviewer-driven exclusion and an auto-exclusion (`auto:offer_expired`,
  `auto:fx_rate_missing`, `auto:fx_conversion_invalid`). `price_score`/
  `non_price_score`/`composite_score`/`rank` are recomputed by the shared private
  helper `app._recompute_vendor_comparison_rankings` after every offer-shaping
  mutation.
- `app.vendor_comparison_offer_scores` — one row per (offer, non-price criterion key),
  upserted by `app.score_vendor_comparison_offer_criterion` — a collaborative
  annotation, deliberately not optimistic-concurrency-guarded (design note 11 in the
  migration; disclosed, not an oversight — see §7 C-03 below).
- `app.vendor_comparison_events` — append-only comparison-root lifecycle history,
  mirrors `app.rfq_events` exactly. Offer-level actions (link rate, include/exclude,
  score) are not comparison-root transitions and do not write here — `app.capture_
  audit_event` still records every one of those.
- Directory views: `app.vendor_comparisons_directory`, `app.vendor_comparison_offers_
  directory`, `app.vendor_comparison_offer_scores_directory`, `app.vendor_comparison_
  events_directory` — all PLAIN (no field masking at the view level). The entire
  capability gates on `PRC:View cost` alone, mirroring `app.calculate_vendor_rate`'s
  own ADR-0020 directed reuse ("the entire return shape is cost data, there is no
  separate non-cost View tier to also require") — a vendor comparison's whole purpose
  is exposing normalized cost for a selection decision, so there is no non-cost-masked
  variant to reconcile the way `app.rfq_responses_directory` has to for `PRC-257`. Row
  filters use the hardened pattern-5 predicate, copied verbatim from every prior
  PRC-25x table.

## 4. Functions summary

- **Creation (`PRC:Create` + `PRC:View cost` + `FIN:View`):** `app.create_vendor_
  comparison` — idempotent on `(tenant_id, idempotency_key)`, replay compares
  `rfq_id`/`comparison_currency`/`basis_weight`/`basis_volume`/`basis_quantity`/the
  fully-normalized `criteria_snapshot`; requires the source RFQ to be `closed`; locks
  it `for update` before deciding (defense in depth — `closed` is terminal, no
  PRC-257 function can transition away from it, but the lock is taken regardless per
  this repository's standing C-04 convention); `no_comparable_responses` if the RFQ has
  zero eligible responses.
- **Root lifecycle (`PRC:Edit` + `PRC:View cost` unless noted):** `app.revise_vendor_
  comparison` (only from `draft|recommended`, mandatory reason, idempotent replay
  comparing the five resolved fields), `app.recommend_vendor_comparison_offer`
  (`draft|recommended→recommended`, mandatory reason only when the recommended offer
  is not the lowest normalized cost among included offers — business rule "lowest
  price is not automatic selection"; re-recommending before submission is allowed),
  `app.cancel_vendor_comparison` (`draft|recommended→cancelled`, mandatory reason).
- **Root lifecycle (`PRC:Approve` + `PRC:View cost`):** `app.submit_vendor_comparison_
  for_approval` (`recommended→submitted`, terminal; mandatory reason only when the
  selected offer differs from the recommended one — the "override-with-reason" API
  verb, business rule "human selection and override are auditable"). This is the
  approval-engine handoff point (Prompt 259) — no `app.request_approval` call is made
  from this checkpoint; PRC-258 only reaches `submitted`.
- **Offer-level (`PRC:Edit` + `PRC:View cost`, `+FIN:View` for the rate link):**
  `app.link_vendor_comparison_offer_rate` (composes `app.calculate_vendor_rate` then
  `app.convert_finance_amount`; blocks a not-approved rate, a vendor-identity mismatch,
  a null/zero `basis_quantity`), `app.set_vendor_comparison_offer_inclusion` (mandatory
  reason to exclude, never touches the underlying `app.rfq_responses` row),
  `app.score_vendor_comparison_offer_criterion` (upsert, 0–100, rejects `price` and
  any criterion not in the comparison's own `criteria_snapshot`).
- **Reads (`PRC:View cost` alone):** `app.get_vendor_comparison`, `app.list_vendor_
  comparisons` (server-clamped ≤200 rows, superseded excluded by default),
  `app.list_vendor_comparison_offers`, `app.list_vendor_comparison_offer_scores`,
  `app.get_vendor_comparison_history` — every one reconstructs its own projection
  directly from the base table with the RPC's own explicit `p_actor_auth_user_id`,
  never `select * from <directory view>` (PRC-256/PRC-257's own C-06 lesson, applied
  here from the start).
- **Private helpers (no grant):** `app._normalize_vendor_comparison_criteria`,
  `app._normalize_vendor_comparison_currency` (the ONE call site for `app.convert_
  finance_amount` composition, narrowly catching only the two real per-offer
  conditions that function can raise), `app._snapshot_vendor_comparison_offers`
  (shared by create/revise), `app._recompute_vendor_comparison_rankings`.
- Reused, not duplicated: `app.evaluate_permission`, `app.capture_audit_event`,
  `app.has_active_tenant_membership`/`app.actor_holds_customer_user_layer`,
  `app.validate_currency_code`, `app.check_finance_exchange_rate_authority`,
  `app.calculate_vendor_rate`, `app.convert_finance_amount`, `app.apply_finance_
  rounding`.

## 5. Design decisions

**FIN:View is a genuine, proactive, whole-operation gate.** `app.convert_finance_
amount` checks `FIN:View` as its own first statement, unconditionally, even on its
same-currency identity short-circuit — so every RPC that can reach it (create, revise,
link-rate) checks `app.check_finance_exchange_rate_authority('View', ...)` explicitly,
once, immediately alongside the PRC gates, rather than letting the first per-offer
conversion attempt surface a confusing `insufficient_authority` deep inside a loop.
This is a real cross-domain (PRC + FIN) permission composition, disclosed and tested
(`scripts/db-tests/procurement-vendor-comparison.sql`'s `financeless1` actor: full PRC
including `View cost`/`Approve`, deliberately no FIN role at all — `create_vendor_
comparison` correctly denies with an `insufficient_authority` message naming
`FIN:View`).

**Auto-exclusion is real but narrowly scoped, never a blanket catch.**
`app._normalize_vendor_comparison_currency` wraps only the single `app.convert_
finance_amount` call, catching exactly the two condition names that function's own
header documents as real, expected per-offer outcomes (`no_data_found` for a missing
FX rate, `check_violation` for an unsupported currency) — and, found during this
checkpoint's own Tier B walk (§7 C-09 below), verifies the `SQLERRM` prefix before
treating either as the expected condition, re-raising anything else. Any other
exception (including `insufficient_privilege`) is never caught here.

**`app.vendor_rate_versions.vendor_master_id` vs `master_record_id` — a real defect
caught and fixed by this checkpoint's own db-test run before the migration was ever
applied anywhere.** `app.link_vendor_comparison_offer_rate`'s vendor-identity check
originally compared `app.vendor_rate_versions.master_record_id` (the `vendor_rate`-
TYPED identity row `app.create_rate_version` itself get-or-creates from
`vendor_code`/`vendor_name`, COM-149) against `app.vendor_comparison_offers.vendor_
master_id` (the real canonical Procurement vendor identity, `master_type_code=
'vendor'`) — two different identity spaces that never coincide, which would have
rejected EVERY real link attempt with a false `vendor_mismatch`. PRC-255's own
ADR-0020 widening had already added the correctly-typed, correctly-named `app.vendor_
rate_versions.vendor_master_id` column (nullable, optionally supplied at `app.create_
rate_version` time) for exactly this comparison — the fix uses that column instead,
confirmed by re-running the full db-test suite (see §6).

**RBAC mapping reuses the 12 already-seeded PRC actions exclusively, plus `FIN:View`
composed from the already-seeded FIN catalogue** — no new `app.permissions` row.
`Create` = `create_vendor_comparison` (+`View cost`+`FIN:View`). `Edit` = `revise_
vendor_comparison`, `recommend_vendor_comparison_offer`, `cancel_vendor_comparison`,
`link_vendor_comparison_offer_rate` (+`FIN:View`), `set_vendor_comparison_offer_
inclusion`, `score_vendor_comparison_offer_criterion` (all +`View cost`). `Approve` =
`submit_vendor_comparison_for_approval` (+`View cost`) — deliberately a DIFFERENT
action from `Edit`, matching the access rule "Procurement/pricing compare; management
approves." `View cost` = every read RPC, alone (design note 8, ADR-0020's own directed
reuse).

**No self-approval block between recommend (`PRC:Edit`) and submit
(`PRC:Approve`), disclosed rather than silently absent.** Unlike PRC-252's vendor
assessment (which blocks a single actor holding both Edit and Approve from
self-deciding its own review), this checkpoint does not technically prevent one actor
who holds both `PRC:Edit` and `PRC:Approve` from recommending and then submitting the
same comparison. This is a deliberate, scoped decision: `app.submit_vendor_comparison_
for_approval` is a HANDOFF preparation step (it reaches `submitted`, never itself
commits a purchase order or financial obligation) — the real governed decision surface
is Prompt 259's own approval engine, which this submission feeds into and where
self-approval rules (if the operator wants them for this workflow) belong. Named here
explicitly as a residual, bounded limitation, not fixed speculatively ahead of Prompt
259's own design.

**No export/watermark surface.** Section 16 names "exports are watermarked/audited
where supported" — no PRC-25x capability in this repository has built an export
surface yet (confirmed by direct inspection before writing this migration), so there is
no established watermarking pattern to compose against. Every read RPC still supports
full drilldown (`normalization_lineage`, `engine_breakdown`) for on-screen "explain,"
the acceptance-critical half of this requirement.

**No external vendor-facing surface, no notification/job wiring** — identical
reasoning to PRC-257's own design notes 5 and its "No notification/job dependency"
section: no vendor identity ever reaches this migration (structurally true — vendors
cannot access comparison, access rule §26), and no concrete notification event is
named by this prompt's own spec text.

**No dedicated criteria-configuration engine.** Non-price criteria are supplied
directly at comparison creation/revision time and snapshotted (validated: exactly one
`price` entry, weights sum to 100) — the same class of proportionate-effort decision
PRC-257's own `app.next_rfq_number` (vs. the full Numbering Engine) already made and
disclosed for itself.

## 6. Real defects found and fixed during this checkpoint's own Tier B walk

Per `docs/standards/RECURRING_DEFECT_TAXONOMY.md` §2, the full §4 walk ran against
this checkpoint's own diff before it was declared `COMPLETED` (not a separate
adversarial review — none is due until the batch's Tier C close). Three real gaps
were found and fixed directly in the migration before it was applied anywhere (the
same "not yet applied, so fix in place" precedent PRC-255/256/257 already
established):

1. **A live, db-test-caught defect: `app.link_vendor_comparison_offer_rate` compared
   the wrong master-record identity field** (§5 above). First surfaced as a real test
   failure (`vendor_mismatch` on a legitimately same-vendor rate link) while running
   `pnpm run db:test` — not found by inspection alone. Root-caused to `master_record_
   id` (the `vendor_rate`-typed identity) vs `vendor_master_id` (the real canonical
   vendor identity, PRC-255/ADR-0020's own correctly-named column for exactly this
   purpose). Fixed in the migration; the db-test file's own `app.create_rate_version`
   call was corrected to supply `p_vendor_master_id` (the widened function's 22nd,
   trailing-optional parameter) so the fixture is realistic, not merely
   error-tolerant.
2. **C-09-adjacent (over-broad condition catch), `app._normalize_vendor_comparison_
   currency`.** The first draft's `when check_violation` / `when no_data_found`
   handlers would also have silently swallowed `app.apply_finance_rounding`'s own
   `check_violation` (a corrupted tenant `finance_rounding` config value) as an
   ordinary "unsupported currency" outcome, mischaracterizing a config data-integrity
   bug as a routine per-offer exclusion. Fixed by verifying the `SQLERRM` prefix
   against the exact expected condition text before treating it as such, re-raising
   anything else — the same "discriminate before recovering" discipline C-09 demands
   for constraint names, applied here to condition text since PL/pgSQL cannot catch by
   a bespoke condition alone.
3. **C-05-adjacent (gate ordering inconsistency), `app.link_vendor_comparison_offer_
   rate`.** The `FIN:View` check originally ran AFTER the comparison's `status`/
   `basis_quantity` were read and validated — inconsistent with `create_vendor_
   comparison`/`revise_vendor_comparison`'s own "every whole-operation authority gate
   together, before any state-dependent check" ordering (not a genuine information
   leak, since the acting caller already holds real `PRC:Edit`+`PRC:View cost` for
   this tenant and could read the same state via the read RPCs anyway — but a real
   inconsistency worth closing for uniformity and fail-fast behavior). Moved
   immediately after the `PRC:View cost` gate.
4. **C-15 (missing domain constraints), `app.vendor_comparison_offers`.**
   `engine_computed_amount` had no non-negativity `CHECK` (unlike its sibling
   `source_total_amount`/`normalized_amount`), and `price_score`/`non_price_score`/
   `composite_score` had no `[0,100]` range `CHECK` despite every computation path
   guaranteeing that range by construction. Added all four, defense in depth.
5. **C-20 (a capability reachable from only one of its two valid states),
   `app.revise_vendor_comparison`.** The RPC allows revising from `status IN
   ('draft','recommended')`, but the detail panel's own "Recalculate" UI was gated on
   `status = 'recommended'` only — a draft comparison had no UI path to revise. Fixed
   by widening the UI gate to the same `isEditable` (`draft`or`recommended`) condition
   every other offer/root-editing action in the panel already uses.
