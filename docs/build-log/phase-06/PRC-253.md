## 1. Objective

Implement versioned vendor compliance requirements, private document evidence (extending the Document/File Engine, never forking it), verification, renewal, time-bounded waivers, expiry/reminder computation, and a governed eligibility-hold projection — without mutating `app.vendor_profiles.lifecycle_status` (sourcing/PO/assignment composition is explicitly Prompts 256+ scope) and without building a scheduler (`ISS-2026-015` is a standing, accepted, repository-wide gap).

## 2. Migration

**`supabase/migrations/20260730600000_create_procurement_vendor_compliance.sql`** (1,892 lines) — the only migration this checkpoint adds.

### 2.1 Schema

- **`app.vendor_compliance_requirements`** — versioned `draft → published → archived`, mirroring `app.vendor_assessment_templates`/PRC-252 exactly, with one structural addition: `requirement_family_id`, minted fresh on first creation, carried forward onto a new draft's own row only at `publish_vendor_compliance_requirement`-with-`p_supersedes_version_id` time. A partial unique index (`requirement_family_id where status='published'`) guarantees at most one live published version per family — the identity `app.vendor_compliance_status` keys on so a vendor's own compliance standing survives a requirement republish, unlike an individual document's own snapshot link. A second, defensive partial unique index (`tenant_id, vendor_category, service_type, document_type_code where status='published'`, byte-for-byte mirroring `vendor_assessment_templates_published_unique`) keeps the practical scope tuple itself unambiguous. `document_type_code` is a real FK to `app.document_types(code)` (PLT-128's confirmed-global registry); every requirement this capability's own fixtures register reuses one generic `vendor_compliance_document` code, mirroring PRC-252's own `vendor_assessment_evidence` precedent — a document type names a *kind* of file, not a compliance requirement's own title. `blocking_effect` (`blocking|warning`), `requires_expiry` (some documents, e.g. a business license, may not expire), `reminder_offsets integer[]` (default `{30,14,7}`).
- **`app.vendor_compliance_documents`** — one row per submitted evidence version. `requirement_version_id` is the RPD-040-style immutable applied-version snapshot (identical discipline to PRC-252's own `template_version_id`) — a document submitted against requirement version N stays linked to N forever, even after republish. `file_id` references `app.files` (PLT-128) directly, re-validated by every accepting RPC (§2.3). `version_group_id`/`version_number`/`is_latest_version` mirror `app.files`' own versioning shape one layer up — renewal never overwrites. A partial unique index (`requirement_version_id, vendor_master_record_id where is_latest_version`) keeps exactly one active submission per (vendor, requirement-version) slot — renewal is the only path to superseding it.
- **`app.vendor_compliance_waivers`** — time-bounded (`valid_from`/`valid_until`), approved, self-approval-blocked (both an RPC-level check and a redundant table CHECK, `vendor_compliance_waivers_no_self_approval_check`) exception to a compliance requirement.
- **`app.vendor_compliance_status`** — one row per `(vendor_master_record_id, requirement_family_id)` — survives a requirement republish, unlike the per-version document snapshot link. Written **only** by the private `app._recalculate_vendor_compliance_status_family` helper (one non-duplicated computation, several authorized entry points — the identical shape PRC-252's own `_compute_vendor_assessment_score` established). `eligibility_hold` is true only when `blocking_effect='blocking'` **and** `status in (expired, rejected, not_submitted)` **and** no active waiver covers it — never for `expiring_soon`/`pending_verification`/`verified`/`waived`.

**Read (9, added this session):** `get_vendor_compliance_requirement`, `list_vendor_compliance_requirements`, `get_vendor_compliance_document`, `list_vendor_compliance_documents`, `list_vendor_compliance_document_versions` (the version-lineage/document-viewer data source), `get_vendor_compliance_waiver`, `list_vendor_compliance_waivers`, **`get_vendor_compliance_eligibility`** (the downstream-composable read Prompts 256+ compose against), `list_tenant_vendor_compliance_matrix` (the compliance-matrix and expiry/reminders-queue shared, cursor-paginated, server-filtered data source).

**Helpers (4, private, no client grant):** `_vendor_compliance_requirement_applies`, `assert_vendor_compliance_requirement_editable`, `_recalculate_vendor_compliance_status_family`, `_recalculate_vendor_compliance_status_all_families`.

Every non-private RPC gates via `app.evaluate_permission(actor, tenant, 'PRC', action)`. RBAC mapping (all 12 already-seeded PRC actions reused, **zero new `app.permissions` rows seeded** — confirmed by reading `permissions_action_check`'s seeded rows directly): `Create` = draft a requirement, submit a first-time document, request a waiver; `Edit` = draft edit, archive, renew, recalculate one vendor; `Approve`/`Reject` = publish, verify/reject-or-revision-request a document, decide a waiver; `Override` = revoke an approved waiver, both bounded sweeps; `View` = every read RPC.

### 2.3 Evidence-file re-validation (the single most important pattern for this capability)

`submit_vendor_compliance_document` and `renew_vendor_compliance_document` both re-fetch `app.files` and reject on tenant mismatch (`compliance_evidence_file_mismatch`), wrong `record_type`/`record_id` (`record_type='vendor_compliance'`, `record_id`=the vendor's own `master_record_id`), or a non-`clean` `malware_scan_status` (`compliance_unsafe_evidence`) — the exact discipline PRC-252's own adversarial review found and fixed as a CONFIRMED HIGH defect, applied proactively here. Verified by 6 distinct db-test scenarios (unsafe/pending scan, cross-tenant, wrong-record-type, on both first submission and renewal).

### 2.4 Expiry/eligibility computation

`app._recalculate_vendor_compliance_status_family` resolves the vendor's own most-recently-submitted active document anywhere in the family's lineage, then re-evaluates that same, unmodified evidence against whichever requirement version is currently published — the literal reading of "a vendor's compliance status must survive a requirement republish." Status derivation: an active waiver → `waived`; no document → `not_submitted`; pending verification → `pending_verification`; rejected/revision-requested → `rejected`; verified with no expiry tracked or no `expiry_date` → `verified`; verified and past `expiry_date` → `expired`; verified and within the requirement's own maximum `reminder_offsets` window → `expiring_soon`; otherwise `verified`. `eligibility_hold` is computed from this status plus `blocking_effect` plus active-waiver state, never stored redundantly elsewhere.

### 2.5 Legal hold (reuse, not a new code path)

A compliance document's evidence file is placed under legal hold exactly the way any other file can, via `app.set_file_legal_hold` (support/Supreme authority only, unchanged from PLT-128) — no parallel `legal_hold` column exists on `app.vendor_compliance_documents`. `app.request_file_deletion` already refuses outright while `legal_hold=true`; verified by a dedicated db-test that also asserts, by querying `information_schema.columns`, that no such column was added to this migration's own table.

### 2.6 Real, bounded recalculation RPCs (ISS-2026-015)

`app.recalculate_vendor_compliance_status` and `app.recalculate_tenant_vendor_compliance_status` are real, tested, callable today — bounded to `p_max_vendors` (default 200, ceiling 2000), returning `more_remaining` exactly like `app.purge_tracking_telemetry_history`'s own shape — dormant until a human or a future scheduler job invokes them. **No scheduler was added** — `ISS-2026-015` is a standing, accepted, repository-wide gap, not this capability's job to close. A real "reminders/expiring soon" READ queue is exposed for staff to act on manually (`app.list_tenant_vendor_compliance_matrix`, filterable to `expiring_soon`/`expired`/hold-only), per this task's own required scope.

### 2.7 Hardened patterns followed byte-for-byte (mirrored from `20260730590000`)

- **`record_version` optimistic concurrency**: pre-check and post-UPDATE not-found re-check, both halves, on every mutating RPC.
- **Idempotency-key replay with full-field target-mismatch comparison**: `create_vendor_compliance_requirement_draft`, `submit_vendor_compliance_document`, `request_vendor_compliance_waiver` all compare every semantically load-bearing field with `is distinct from`, at both the pre-check and inside the nested `unique_violation` race-recovery handler — the exact under-comparison PRC-252's own adversarial review found and fixed, applied proactively here rather than re-discovering it.
- **TOCTOU row locks**: `assert_vendor_compliance_requirement_editable` (`for update`, serializing draft-CRUD against publish); `publish_vendor_compliance_requirement`'s own superseded-requirement archive UPDATE (`for update` plus a `record_version`+status-guarded UPDATE with a `stale_version` re-check — PRC-252's own adversarial-review fix #5, applied proactively); every document/waiver decision RPC takes a `for update` lock before any status transition.
- **RLS default-deny**: `(app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id)) or app.is_supreme_admin()` on all four new tables' `select` policies.
- **Actor identity**: every RPC resolves authority via `app.evaluate_permission`, which already wires `app.assert_actor_is_session_identity` (ATW-031).
- **Nested `begin/exception when unique_violation` race-recovery** on every idempotency-keyed INSERT.

### 2.8 Two real defects found in the inherited draft and fixed before first application

1. **A 66-character index name (`vendor_compliance_documents_one_active_per_requirement_version_idx`) silently truncated to 63 characters by Postgres**, so the draft's own exception-handling `elsif v_constraint_name = '...same 66-char name...'` branch could never match the real (truncated) constraint name Postgres actually raises — a genuine `active_submission_exists` recovery path that would have raised the raw, uncaught Postgres `unique_violation` instead of the intended, documented error code. Found by the first live db-test run against a real Postgres 16 instance (not by static review — this class of bug is invisible without actually triggering the violation). Fixed by renaming the index to `vendor_compliance_documents_one_active_slot_idx` (well under the 63-character limit) in both the `create unique index` statement and the exception handler.
2. **`grant select on app.vendor_compliance_requirements/_documents/_waivers/_status to authenticated, service_role` was missing entirely** — the draft enabled RLS and added `select` policies, but RLS policies only ever *narrow* an already-granted privilege; without the underlying table `GRANT`, `authenticated` had no `SELECT` privilege on these tables at all (`permission denied for table`), confirmed by the cross-tenant-isolation db-test's own raw-RLS assertion, which is exactly the kind of direct-table-read test this repository's own established convention (PRC-251/252, both real precedent) requires. Fixed by adding the four missing `grant select` statements, mirroring PRC-251/252's own identical grant block verbatim.

Both fixes are folded directly into `20260730600000_create_procurement_vendor_compliance.sql` itself — it had not yet been applied to any database when these were found, so there is no follow-up migration file.

## 3. Design decisions / deviations (disclosed in the migration header, summarized here)

1. **`requirement_family_id`** is the one structural addition beyond PRC-252's own template-versioning shape — necessary because a vendor's compliance *standing* must survive a requirement republish, unlike an assessment's own scoring result (see §2.1).
2. **One generic `vendor_compliance_document` document type code**, not one per compliance-document title — mirrors PRC-252's own `vendor_assessment_evidence` precedent exactly; `app.document_types` names a *kind* of file, confirmed a global (non-tenant-scoped) registry by reading PLT-128's own migration in full rather than assuming.
3. **`app.vendor_compliance_status` is written only by one private helper**, called from the last step of every document/waiver-mutating RPC (closing the "recalculation racing a new upload" race by construction, inside the same already-locked transaction) as well as from the two public recalculation RPCs — one non-duplicated computation, several authorized entry points, the identical shape PRC-252's own `_compute_vendor_assessment_score` established.
4. **`app.expire_vendor_compliance_waivers` is bookkeeping, not a correctness dependency** — `_recalculate_vendor_compliance_status_family`'s own active-waiver check evaluates `status='approved' and valid_from<=current_date<=valid_until` directly against the real calendar date, never the lazily-swept `expired` label, so eligibility-hold correctness never regresses if the sweep hasn't run recently.
5. **No new `app.permissions` rows seeded** — all 12 already-seeded PRC actions fit every RBAC need this capability has (see §2.2's mapping); `View cost`/`View personal data`/`Delete`/`Export`/`Download`/`Import` have no distinct fit in this schema (no financial figure, no PII beyond actor UUIDs, no destructive delete, no export/download/import surface built this checkpoint) — a disclosed simplification, not a silently invented gap.
6. **Self-approval block scoped to waiver decisions only** — this task's own spec names it exclusively for waivers (§21's "approved time-bounded waiver"); document verification carries no such block, matching PRC-252's own precedent of scoping maker-checker only where the source text explicitly names it.
7. **True multi-session concurrent-race reproduction has no matching sequential db-test proof** (the `for update` locks, the atomic upsert) — the same standing, already-disclosed limitation PRC-251/252's own build logs record (no `dblink`/`pg_background` exists in this test suite). Verified instead by direct conformance to this repository's own established locking pattern plus the full sequential suite passing unchanged.
8. **The compliance matrix and the expiry/reminders queue share one read RPC and one UI route**, distinguished only by query-string filters (`?status=expiring_soon`, `?status=expired`, `?hold=1`) rather than being built as two structurally identical routes — a disclosed simplification given both surfaces are, at the data layer, the exact same server-filtered, cursor-paginated table.
9. **Waiver request/decision UI is nested inside the per-vendor compliance page, not a separate tenant-wide route** — no tenant-wide waiver-list RPC was built (waivers are inherently per-vendor-per-requirement in this schema, and `app.list_vendor_compliance_waivers` is deliberately vendor-scoped, matching how the vendor-scoped document upload/verification flow is also on this same page); a tenant-wide waiver route would have needed inventing a new read RPC this task's own required scope does not name.
10. **The "submit a new document"/"request a waiver" pickers list every published requirement for the tenant**, not pre-filtered to ones structurally applicable to this specific vendor (`app._vendor_compliance_requirement_applies` is a private helper, not exposed as a read RPC) — the submit/request RPCs themselves enforce and report `requirement_not_applicable` on a genuine mismatch (verified by db-test), so an inapplicable pick surfaces a clear, server-side error rather than being silently accepted. A disclosed UX rough edge, not a correctness gap.

### 6.1 A real design-thinking bug found and fixed while authoring the db-test fixture (not a product defect)

The db-test's own original fixture design gave three separate requirement families (a base "Business License," a warning-effect "Optional Trucking Cert," and a blocking "Mandatory Trucking Permit") the identical scope tuple `(tenant, 'trucking', null, 'vendor_compliance_document')` — which `vendor_compliance_requirements_published_scope_unique` correctly refuses to let all three publish simultaneously (by design, §2.1). This is the test fixture correctly exercising the real constraint, not a product bug — fixed by giving the fixture's own three families distinct `service_type` values (`null`/`trucking`/`linehaul`), with the vendor granted an active `app.vendor_services` row for each, so all three publish and apply concurrently as the scenario needs.

### 6.2 Adversarial review round — findings, disposition, and fixes

Three independent adversarial reviewers (spec-compliance, security-RLS, correctness-concurrency) examined the implementation documented in §1–§7 below. **This subsection was not written by the fix agent itself** — its own session ended abruptly after applying fixes and launching a background `db:test` monitor, without ever producing a final disposition report or updating this build log. Everything below was reconstructed by the orchestrating session from the three reviewers' raw findings plus direct inspection of the actual committed-to-working-tree code, exactly the same "verify, don't trust the self-report" discipline applied to every other Phase 6 checkpoint.

**Confirmed and fixed (5):**

1. **HIGH (spec-compliance) — no document/version viewer; reviewers verified evidence blind.** The original UI exposed only a raw `fileId` UUID next to verify/reject controls, with no link, preview, or filename anywhere; `app.list_vendor_compliance_document_versions` and PLT-128's own `app.authorize_file_access` were never called from any page or action. Fixed with a genuinely new route, `app/(tenant)/[tenantSlug]/procurement/compliance/vendors/[vendorMasterRecordId]/documents/[versionGroupId]/`, listing the full renewal lineage for one evidence slot oldest-to-newest, each version's evidence gated through a new RPC (`app.access_vendor_compliance_document_evidence`, composing `PRC:Download` with PLT-128's own scan/sensitivity gate, audited both by this capability's own trail and PLT-128's `app.file_access_logs`).
2. **HIGH (correctness-concurrency) — stale-overwrite race in the compliance-status recalculation helper, live-reproduced with three concurrent psql sessions.** `app._recalculate_vendor_compliance_status_family` read the current document/waiver state with plain unlocked `SELECT`s and only serialized at the final upsert — two independent invocations (e.g. a document-decision's own inline recalc racing a bystander `recalculate_vendor_compliance_status` call) could commit in an order where the *slower* read's stale computation overwrites the *faster* call's fresh, correct one, permanently (nothing self-heals without a scheduler, which doesn't exist — `ISS-2026-015`). Reproduced exactly as described: a verified document left its own family's persisted status at `pending_verification`. Fixed with `perform pg_advisory_xact_lock(hashtextextended(vendor::text || ':' || requirement_family::text, 0))` taken **before** any read, fully serializing every concurrent recompute for the same (vendor, requirement family) pair.
3. **HIGH (correctness-concurrency) — idempotency-key replay in `submit_vendor_compliance_document` omitted `issue_date`/`expiry_date` from the target-mismatch comparison**, live-reproduced: a retried submission carrying a corrected expiry date silently kept the original (wrong) date with no error — the single most consequential field for a capability whose entire purpose is expiry correctness. Fixed: both fields now included in the comparison (migration lines ~1044/1069).
