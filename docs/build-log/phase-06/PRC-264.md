## 1. What this checkpoint builds

Source-reconciled vendor KPI scorecards, reading real canonical evidence rather than a
second, parallel metrics store: a versioned KPI catalogue (`app.vendor_kpi_definitions`
— formula fixed per category, but window/target/weight/band/min-sample-size are
tenant-configurable and versioned/snapshotted), eleven built-in calculators
(`on_time_pickup`, `on_time_delivery`, `acceptance_rate`, `response_time`,
`capacity_fulfillment`, `compliance`, `claims_damage`, `rate_competitiveness`,
`rate_validity`, `invoice_accuracy`, `service_complaint_sla`), a published, versioned
scorecard with composite score/band (`app.vendor_kpi_scorecards`/`_lines`), a real
source-dispute mechanism, issue and corrective-action tracking, reason-required
maker-checker manual adjustment, and a governed (system-recommends, human-decides)
suspension/blacklist/reactivation surface wired straight into the already-`VERIFIED`
PRC-251 vendor lifecycle RPCs — never a second vendor lifecycle authority, and vendor
identity is read exclusively through `app.vendor_profiles.master_record_id`
(`app.master_records`, ADR-0020), never a new vendor-shaped table.

`invoice_accuracy` is real, disclosed, and deliberately not computed: its true evidence
source is Prompt 265 (Vendor Invoice Matching), not yet built as of this checkpoint. The
catalogue carries a genuine `invoice_accuracy` row (`is_computable=false`, a mandatory
`source_note`), so the category is visibly present and explicitly not-yet-sourced —
never silently absent, and never fabricated. `app._calculate_vendor_kpi_metric_value`
returns `is_computable=false` unconditionally for this one code, with no query at all.

Every calculator returns a ratio/percentage/hour/0-100-score value only, never a raw
currency amount — the one thing gated behind `PRC:View cost` is the drilldown's own
`contributing_source_ids` (which specific shipments/claims/invitations fed a number),
masked at the RPC layer (`app.mask_vendor_kpi_source_evidence`,
`app.get_vendor_kpi_scorecard_drilldown`). A real dispute mechanism
(`app.vendor_kpi_source_disputes`) lets a raised, upheld dispute against one
contributing source exclude that source from every future recalculation of the
affected `kpi_code`. The overall scorecard band uses a fixed, non-versioned threshold
set, distinct from each KPI definition's own versioned `band_thresholds` (used for that
one metric's own line); composite score renormalizes weight over computable KPIs only,
recording both `computable_weight_total` and `total_weight_defined` so partial coverage
is disclosed on the row itself rather than silently averaged. Manual adjustment mutates
the CURRENT published scorecard's rollup in place, version-guarded, with a full
before/after audit trail on both the adjustment row and the scorecard/line. The
lifecycle recommendation surface is a genuine two-step split:
`evaluate_vendor_lifecycle_recommendation` derives (or an analyst overrides, with a
mandatory rationale) a `none`/`watch`/`suspend`/`blacklist`/`reactivate` recommendation
from the scorecard's own band — this alone never changes `vendor_profiles.
lifecycle_status`; only `decide_vendor_lifecycle_recommendation` (`PRC:Override`, a
different human, self-approval blocked) does that, by calling straight through to the
real, unmodified PRC-251 RPCs (`suspend_vendor_profile`/`blacklist_vendor_profile`/
`reactivate_vendor_profile`) inside the same transaction as the decision itself.

## 4. Tier B — recurring defect taxonomy self-check

Lessons already established across PRC-261/262/263's own Tier B/Tier C history were
applied from the first draft: idempotency replay verifies the full target tuple (C-01)
across all 7 creation RPCs; race-recovery `unique_violation` handlers are nested to
scope ONLY their own `insert` statement, never the pre-check's own deliberate raise
(C-02); every versioned `update` is immediately followed by an explicit `if not found`
stale-version guard (C-03, 10/10 by direct count); a decision's parent/target row is
locked `for update` before deciding (C-04); by-id reads/decides fold "does not exist"
and cross-tenant into the same error before `evaluate_permission` runs. Several real
findings still surfaced during this prompt's own live iteration and self-check, and
were fixed in-prompt:

- **A genuine, live-reproduced PL/pgSQL correctness bug: `FOUND` clobbered by a nested
  function call inside `calculate_vendor_kpi_metrics`'s per-KPI loop.** The loop's own
  `select ... for update` set `FOUND` correctly, but the very next statement — a call to
  `app._calculate_vendor_kpi_metric_value`, itself a nested function that runs its own
  SQL — silently overwrote the ambient `FOUND` before the loop's own "is this
  unchanged?" branch read it. A disputed-event recalculation for an already-current
  metric value took the "unchanged" short-circuit and never versioned, discovered via
  direct `raise notice` isolation (confirmed the calculator itself was correct, then
  confirmed `FOUND` was wrong specifically at that point in the loop) rather than
  inferred. Fixed by capturing `v_current_found := found` immediately after the
  original lock, and using that captured boolean everywhere downstream instead of bare
  `found`. Audited the rest of the file for the same anti-pattern; no other occurrence
  exists (every other `found`/`not found` check in this migration immediately follows
  its own `select`, with nothing intervening).
- **`return query` does not itself exit a `setof`-returning function.** Two early-exit
  `return query select ...` statements in `calculate_vendor_kpi_metrics` (the
  idempotency replay and the race-recovery path) fell through into the main insert/loop
  body with no explicit `return` after them, live-reproduced as duplicate rows / a
  spurious extra measurement run on replay. Fixed by adding an explicit bare `return;`
  immediately after each.
- **`version_no` defaulted to 1 unconditionally**, so publishing a second version of an
  already-versioned KPI category hit the `vendor_kpi_definitions_number_version_unique`
  constraint. Fixed by computing `v_next_version` from `max(version_no) + 1` before
  insert, matching `app.create_vendor_contract_draft`'s own precedent.
- **C-02, confirmed and fixed, live-reproduced — `create_vendor_kpi_definition_draft`
  and `request_vendor_kpi_manual_adjustment`.** Both functions' own idempotency-conflict
  `raise exception ... using errcode = 'unique_violation'` lived inside the SAME
  top-level `exception when unique_violation` block that also caught genuine insert
  races — so the pre-check's own deliberate raise was silently swallowed by the
  function's own handler, and a weight-mismatched (or score-mismatched) replay silently
  returned the stale row instead of erroring. Reproduced live before fixing. Fixed by
  nesting the bare `insert` alone inside its own `begin...exception...end` block in both
  functions, matching `app.create_vendor_contract_draft`'s established shape. Added
  race-recovery exception wrapping (a lesser completeness gap, not literally C-02 since
  no genuine defect existed without concurrency) to five more functions that had none:
  `calculate_vendor_kpi_metrics`, `publish_vendor_kpi_scorecard`,
  `raise_vendor_performance_issue`, `add_vendor_performance_corrective_action`,
  `evaluate_vendor_lifecycle_recommendation`.
- **C-05, confirmed and fixed — permission check ordered after a row read that already
  discloses data, in 5 functions.** `raise_vendor_kpi_source_dispute`,
  `calculate_vendor_kpi_metrics`, `publish_vendor_kpi_scorecard`,
  `raise_vendor_performance_issue`, and `evaluate_vendor_lifecycle_recommendation` each
  take an explicit `p_tenant_id` (so `evaluate_permission` never needs a prior lookup to
  discover it) but were written with a `select ... from app.vendor_profiles` existence
  check FIRST, then `evaluate_permission` second — letting a caller with ZERO PRC
  permission in that tenant learn whether a given `vendor_master_id` exists there,
  purely from which of the two distinct error messages came back
  (`vendor_profile_not_found` vs `insufficient_authority`). This deviated from this same
  migration's own `create_vendor_kpi_definition_draft` (permission-check-first, correct)
  and from `app.create_vendor_contract_draft`'s (PRC-261) own established precedent.
  Fixed in all 5 by reordering `evaluate_permission` to run first, matching precedent
  exactly; the other 6 lookup-by-global-id functions in this migration
  (`decide_vendor_kpi_source_dispute`, `decide_vendor_kpi_manual_adjustment`,
  `decide_vendor_lifecycle_recommendation`, `request_vendor_kpi_manual_adjustment`,
  `update_vendor_kpi_definition_draft`, `publish_vendor_kpi_definition`) were verified
  correct as-is — they take no `p_tenant_id` parameter at all, so the row lookup is
  structurally required before `evaluate_permission` can even be called, the same
  necessary shape `app.activate_vendor_contract` (PRC-261) already establishes.
- **C-18, confirmed and fixed — self-approval was not blocked on
  `decide_vendor_lifecycle_recommendation`**, the highest-stakes decision this
  capability exposes (it can suspend/blacklist a vendor's real eligibility).
  `evaluate_vendor_lifecycle_recommendation` always records the evaluating actor as
  `recommended_by_auth_user_id`, even for a purely system-derived (non-override)
  recommendation; `decide_vendor_lifecycle_recommendation` had no check against it, so
  one actor holding both `PRC:Edit` (evaluate) and `PRC:Override` (decide) could
  evaluate and decide their own recommendation — unlike the two lower-stakes
  maker-checker flows in this same migration (source dispute, manual adjustment), both
  of which already correctly block self-approval. Fixed by adding the same
  `self_approval_not_allowed` check, plus a new live regression test in
  `procurement-vendor-performance.sql` proving the recommendation's own evaluator is
  rejected before a different actor is allowed to decide it.
- **C-22, confirmed and fixed — `_calc_vendor_kpi_rate_competitiveness`'s market-percentile
  ranking compared `base_amount` across `app.vendor_rate_versions` rows with no currency
  scoping at all.** The "market" a rate is ranked against was scoped to
  `(tenant, service_type, origin_lane, destination_lane)` only; two vendors quoting the
  identical lane in different currencies (e.g. IDR vs USD) would be ranked directly
  against each other's bare numeric `base_amount`, producing a percentile driven almost
  entirely by currency denomination rather than real cost — the same class Batch
  `CG-S11-PRC-008..010`'s own Tier C review found and disclosed as `ISS-2026-045`.
  Fixed by adding `currency` to the match scope in both the numerator and denominator
  subqueries (a lane quoted in a currency no competitor also quotes in now correctly
  scores 100 by construction, `market_count=1`, rather than being ranked against an
  unrelated-currency number) — a bounded, mechanical narrowing, not the heavier
  FX-normalization architectural decision `ISS-2026-045` itself declined to make
  unilaterally. Verified against the live fixture (`db:test` re-run clean) — the
  existing Good/Market Vendor fixture already used the same currency (`IDR`) for both,
  so this fix changes no existing assertion, only closes the general-case gap.
- **C-20, confirmed and fixed — `app.archive_vendor_kpi_definition` was built, granted,
  and db-tested with zero UI caller anywhere.** It is the only way to retire an
  obsolete or incorrect KPI category (draft or already-published), so leaving it
  unreachable would have made a real, tested governance action silently inert. Fixed:
  the queue panel's KPI Catalogue table now shows an "Archive" reason-required
  mini-form beside Publish for every draft/published definition, wired through a new
  `archiveVendorKpiDefinitionAction` server action.

## 5. Residual, disclosed limitations (itemized — C-23 discipline)

1. **`invoice_accuracy` is structurally present but never computed** (design decision 2
   in the migration's own header) — its real evidence source is Prompt 265 (Vendor
   Invoice Matching), not yet built. `is_computable=false` with a mandatory,
   human-readable `source_note` at all times; `app._calculate_vendor_kpi_metric_value`
   short-circuits to that result unconditionally for this one `kpi_code`, with no query
   run at all. This is the deliberate, disclosed design this prompt was explicitly
   instructed to follow — never fabricated, never silently absent.
2. **`app.update_vendor_kpi_definition_draft` is built, granted, and db-tested, but has
   no UI caller.** Unlike `archive_vendor_kpi_definition` (fixed in-prompt, §4 above), a
   draft with an incorrect field can already be corrected today via the existing,
   fully-wired archive-then-recreate path (archive the wrong draft with a reason, create
   a fresh one) — a real, if less convenient, correction route, judged sufficient given
   this prompt's own scope. A dedicated inline "edit draft" form (mirroring
   `vendor-contract-detail-panel.tsx`'s own `canUpdate` pattern) is a reasonable next
   increment, not attempted here to avoid materially growing an already-large queue
   panel for a capability with a working, if less ergonomic, alternative.
3. **No vendor-portal identity for raising a source dispute** (already-accepted
   PRC-257/258/261/262/263 precedent) — a dispute is staff-recorded on the vendor's own
   behalf, exactly like every other vendor-initiated action in this phase.
4. **`rate_competitiveness`'s market-percentile ranking never performs FX conversion,
   only same-currency scoping (§4's C-22 fix).** A vendor whose only quote for a lane is
   in a currency no competitor also quotes in scores 100 by construction (an empty,
   trivially-won market), rather than being ranked on a true multi-currency
   cost-competitiveness basis — the heavier normalization architecture (`app.
   convert_finance_amount`-style FX conversion into a reference currency, the same
   unresolved question `ISS-2026-045` already declined to decide unilaterally for a
   different entity type) is a genuine, cross-cutting architectural decision outside
   this single prompt's own mandate.
5. **`claims_damage`/`service_complaint_sla`/`compliance` calculators read shipment/claim/
   compliance-hold evidence as it exists TODAY at calculation time** — a claim whose
   `responsibility` decision changes AFTER a metric value was calculated (but before the
   next recalculation) is not retroactively reflected until `calculate_vendor_kpi_metrics`
   is called again for that window; this mirrors every other Phase 6 KPI-style read
   (e.g. PRC-259's own approval-requirement evaluation), not a novel gap.
