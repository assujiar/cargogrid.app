# PRC-256 — Sourcing

**Prompt ID:** `CG-S11-PRC-007` · **Package document:** `CG-AABPP-PRC-256` · **Status at end of this checkpoint:** implementation and gate suite complete, pending independent verification and adversarial review by the orchestrating session — not self-declared `VERIFIED` here.

## 1. What this checkpoint extends

PRC-256 is the sixth Phase 6 checkpoint, built directly on the already-`VERIFIED`
PRC-255 (Vendor Rate and Pricelist). It implements source-linked sourcing requests,
vendor discovery, candidate eligibility with explainable reasons, and human-owned
shortlist curation — a source-versioned shortlist handoff surface a later, separate
Procurement RFQ capability (Prompt 257, **not built here**) can read from. It reads
(never modifies) three already-canonical roots: `app.costing_requests` (COM-148),
`app.shipment_orders` (OPS-169), and `app.vendor_profiles`/`app.vendor_services`/
`app.vendor_coverage` (PRC-251) plus `app.get_vendor_compliance_eligibility`
(PRC-253). Per ADR-0020, canonical vendor identity remains
`app.master_records` (`master_type_code='vendor'`), reached via
`app.vendor_profiles.master_record_id` — no second vendor-shaped table is
introduced.

## 3. Schema summary (all additive)

- `app.sourcing_requests` — one row per sourcing effort. `source_type` is
  `'costing_request'|'operational_demand'|'proactive'`, structurally constrained
  (`sourcing_requests_source_shape_check`) so exactly one of
  `source_costing_request_id`/`source_shipment_order_id` is set for the first two
  source types and both are null for `proactive`. `demand_snapshot jsonb` is the
  full point-in-time copy of the inherited source (mirrors
  `app.costing_requests.requirements_snapshot`'s own convention). Typed mirror
  columns (`service_type`/`origin_lane`/`destination_lane` NOT NULL;
  `mode`/`cargo_weight_min/max`/`cargo_volume_min/max`/`requested_pickup_at`/
  `requested_delivery_at`/`currency`/`budget_amount` nullable) back indexed
  querying only. `status` is the exact nine-transition machine the task specifies
  (`draft→open→shortlisted|closed_no_source`, `draft|open→cancelled`,
  `shortlisted|closed_no_source|cancelled→open`). `closed_reason` is
  structurally required (non-empty) exactly when `status` is
  `closed_no_source`/`cancelled`. `unique(tenant_id, idempotency_key)`. A shared
  `before update` touch trigger (`app.touch_sourcing_row`) bumps
  `record_version`/`updated_at` — every transition RPC still carries its own
  `record_version = p_expected_version`-scoped `WHERE` and post-`UPDATE`
  `stale_version` re-check (the trigger changes *who* increments the counter,
  never whether the optimistic-concurrency guard itself is enforced).
- `app.sourcing_request_events` — append-only lifecycle history, one row per real
  transition (mirrors `app.vendor_profile_lifecycle_events`'s exact shape,
  including an `evidence_ref` column present on that precedent table but omitted
  from the task's own abbreviated column list — added here specifically to carry
  the override RPC's `p_override_expires_at`, resolving that RPC's own explicit
  "evidence_ref or reason — your choice, document it" instruction).
- `app.sourcing_candidates` — one row per (sourcing_request, candidate vendor).
  `vendor_master_id` is trigger-enforced (`app.enforce_sourcing_candidate_vendor_
  identity`, mirrors PRC-255's `enforce_vendor_rate_version_vendor_identity`
  exactly) to `master_type_code='vendor'` and the same tenant. `exclusion_reasons
  text[]` is structurally constrained to the fixed four-value set
  (`vendor_not_active`/`service_mismatch`/`coverage_mismatch`/
  `compliance_ineligible`) and to internal consistency with `eligible`
  (`sourcing_candidates_eligible_consistency_check`). `shortlist_reason` is
  structurally required (non-empty) whenever `shortlisted=true`. `unique
  (sourcing_request_id, vendor_master_id)`. Same shared touch trigger.
- `app.sourcing_requests_directory` — masked view: `budget_amount` nulled
  (`cost_masked=true`) behind `PRC:View cost` (reuses `app.has_prc_view_cost`,
  PRC-252's function — never redefined). Row filter uses the hardened pattern-5
  predicate (`has_active_tenant_membership(...) and not
  actor_holds_customer_user_layer(...)`, copied verbatim from
  `app.vendor_rate_versions_directory`'s own row filter).
- `app.sourcing_candidates_directory` — **plain, unmasked** view (no cost-
  sensitive field exists on `sourcing_candidates`), kept only for the
  "always read through a `_directory` view" naming convention this repository
  holds itself to everywhere else — disclosed in the migration header rather
  than silently omitted.

## 4. Functions summary

- **Creation (`PRC:Create`):** `app.create_sourcing_request_from_costing`,
  `app.create_sourcing_request_from_operational_demand`,
  `app.create_proactive_sourcing_request` — each idempotent on
  `(tenant_id, idempotency_key)`, each comparing every load-bearing caller-
  supplied field on replay (not a subset), each with a nested,
  `constraint_name`-scoped `unique_violation` race-recovery handler.
- **Lifecycle transitions:** `app.submit_sourcing_request` (`PRC:Edit`, draft→open,
  proactive only), `app.override_sourcing_request_constraints` (`PRC:Override`,
  mandatory reason, widen-only on `cargo_weight_max`/`cargo_volume_max`, applies
  `destination_lane` directly since no structural "wider" check exists for free
  text), `app.evaluate_sourcing_candidate_eligibility` (`PRC:Edit`, bounded to 500
  active vendors/call, UPSERTs eligibility while preserving any prior human
  shortlist decision), `app.shortlist_sourcing_candidate` (`PRC:Edit` for an
  eligible candidate or any un-shortlist, `PRC:Override` + mandatory reason for an
  excluded one), `app.submit_sourcing_shortlist` (`PRC:Edit`, requires ≥1
  shortlisted candidate), `app.close_sourcing_request_no_source` (`PRC:Edit`,
  mandatory reason), `app.cancel_sourcing_request` (`PRC:Edit`, mandatory reason),
  `app.reopen_sourcing_request` (`PRC:Override`, mandatory reason, clears
  `shortlist_locked_at`/`closed_reason`, preserves every candidate's own
  `shortlisted` flag).
- **Reads (`PRC:View`):** `app.get_sourcing_request`, `app.list_sourcing_requests`
  (server-clamped ≤200 rows), `app.list_sourcing_candidates`,
  `app.get_sourcing_request_history` — every one reconstructs its own masked/
  plain projection directly from the base table with the RPC's own explicit
  `p_actor_auth_user_id` (see §6 finding 2 for why, not `select * from
  <directory view>`).
- **New helper:** `app.touch_sourcing_row` (shared touch trigger),
  `app.enforce_sourcing_candidate_vendor_identity` (trigger).
- Reused, not duplicated: `app.has_prc_view_cost` (PRC-252's function),
  `app.get_vendor_compliance_eligibility` (PRC-253), `app.evaluate_permission`,
  `app.capture_audit_event`.

## 5. Design decisions

**`requirements_snapshot`'s real key shape.** Direct inspection of
`app.request_costing`/`app.get_opportunity_costing_readiness` (and their own
db-test fixtures) confirms a real costing request's `requirements_snapshot`
carries exactly `{service_type, cargo_description, origin, destination,
target_ready_date}` — no `mode`/weight/volume/currency/`budget_amount` key
exists anywhere in that upstream contract today.
`create_sourcing_request_from_costing` therefore reliably populates only
`service_type`/`origin_lane`/`destination_lane` (raising `source_demand_
incomplete` if any is missing — defensively; `request_costing` itself already
gates on their presence, so this is effectively unreachable in practice for a
row that ever became a real `costing_requests` row) and a best-effort
`requested_pickup_at` parsed from `target_ready_date` (any cast failure is
swallowed to null, never raised). `mode`/cargo weight/volume/`currency`/
`budget_amount` stay null for every costing-sourced request today — a real,
disclosed limitation of the upstream contract, not a bug in this checkpoint.

**`app.shipment_orders`' real columns** are reliably `service_type`/`mode`/
`origin`/`destination` (all `NOT NULL`) plus `basis_weight_kg`/
`basis_volume_cbm`/`planned_pickup_at`/`planned_delivery_at` (nullable).
`create_sourcing_request_from_operational_demand` maps
`basis_weight_kg`/`basis_volume_cbm` onto `cargo_weight_max`/`cargo_volume_max`
only (never the `_min` columns) — read as "sourcing needs a vendor able to
handle up to this much cargo," the natural sourcing-side reading of a single
known quantity rather than a range boundary. This is a disclosed judgment call
the task's own spec did not dictate.

**Status machine.** Costing/operational-demand-sourced requests go directly to
`open` (already-trustworthy canonical source data, no separate submit step,
mirroring PRC-251's own "begin_review is optional" precedent for not forcing a
transition that adds no governance value); only a `proactive` request starts
`draft` and needs `submit_sourcing_request`.

**RBAC mapping** reuses the 12 already-seeded PRC actions exclusively — no new
`app.permissions` row. `Create` = the three creation RPCs. `Edit` =
`submit_sourcing_request` (mirrors `app.submit_vendor_profile_for_review`/
`app.submit_vendor_assessment_for_review`'s own "submit a draft = Edit"
precedent, confirmed by direct inspection before deciding),
`evaluate_sourcing_candidate_eligibility` (a recompute is a write),
`shortlist_sourcing_candidate` for an eligible candidate or any un-shortlist,
`submit_sourcing_shortlist`, `close_sourcing_request_no_source`,
`cancel_sourcing_request` (mirrors `app.archive_vendor_profile`/`app.archive_
vendor_compliance_requirement`'s own "terminal-with-mandatory-reason
administrative closure = Edit" precedent). `Override` =
`override_sourcing_request_constraints`, `shortlist_sourcing_candidate` for an
excluded candidate (a governed exception — "no algorithm autonomously selects a
vendor" extends to "excluded candidates need a human override to even be
considered"), `reopen_sourcing_request` (mirrors `app.reactivate_vendor_
profile`/`app.suspend_vendor_profile`'s own "governed exception, mandatory
reason" precedent). `View` = every read RPC.

**`shortlist_reason` is unconditionally required whenever `shortlisted=true`**,
at both the table `CHECK` and the RPC level, regardless of candidate
eligibility — only the *authority* required (`PRC:Edit` vs `PRC:Override`)
differs by eligibility. Un-shortlisting (`p_shortlisted=false`) needs `PRC:Edit`
only, reason optional.

**Re-evaluating eligibility never silently reverts a human's prior shortlist
decision.** The UPSERT in `evaluate_sourcing_candidate_eligibility` updates only
`eligible`/`exclusion_reasons`/`evaluation_snapshot` on conflict —
`shortlisted`/`shortlist_reason`/`shortlisted_by`/`shortlisted_at` are never
touched by a re-evaluation. A candidate that becomes ineligible while still
shortlisted is a real, surfaced signal, confirmed by a dedicated db-test
scenario, not silently auto-cleared.

**Eligibility dimensions actually evaluated:** `vendor_not_active` (defensive
completeness only — structurally unreachable since the vendor scan itself
filters `lifecycle_status='active'`), `service_mismatch`, `coverage_mismatch`,
`compliance_ineligible`. `has_active_rate` is informational-only in
`evaluation_snapshot`, **never** an exclusion reason, per the task's own
explicit instruction (RFQ exists precisely to solicit quotes from vendors
without one yet). **Capacity/availability (PRC-262) does not exist yet and is
deliberately NOT evaluated** — disclosed the same way PRC-255 disclosed
deferring a tax dimension to FIN-195, not fabricated against data that doesn't
exist. **No vendor cargo-type/restricted-cargo capability master exists
anywhere in this repository** — no such check is built, and no request-level
cargo-restriction flag is modeled either (the task's own "prefer not modeling
it and disclosing the gap" over a column that would silently claim to be
enforced when it isn't). Recomputing eligibility composes the already-`PRC:View`-
gated `app.get_vendor_compliance_eligibility` per candidate vendor — the
calling actor therefore needs **both** `PRC:Edit` (this RPC's own gate) and
`PRC:View` (the composed read's own gate), mirroring `app.commit_vendor_rate_
import_job`'s (PRC-255) own established "compose two independently-gated calls,
both real" pattern.

**The vendor scan is bounded to 500 active vendors per call.** Hitting the
bound is disclosed via a real `raise warning`, not a silent truncation — the
function's own fixed `returns setof app.sourcing_candidates` contract has no
row for a `more_remaining` flag the way `purge_tracking_telemetry_history`'s
own scalar-record return shape does.

**Override widen-only semantics.** The check only fires when a value is
*already stored* — comparing against nothing is vacuously satisfied, so a
null-to-value transition on either numeric cap always succeeds; a
value-to-smaller-value transition is blocked
(`constraint_narrowing_not_allowed`). `destination_lane` is applied directly
when supplied — there is no structural way to prove one lane string is "wider"
than another, so this dimension is governed procedurally (`PRC:Override`,
mandatory reason, an audit event) rather than structurally, a disclosed scope
boundary.

**No notification is added.** Prompt 256 §20/§28 name no notification
requirement for Sourcing itself, unlike some other Phase 6 prompts that
explicitly call one out — re-read in full before deciding; no
`queue_notification`-shaped call is added.

## 6. Real defects found and fixed during this checkpoint's own db-test run

1. **`text[] || 'literal'` array-append bug (migration code).** The first draft
   of `app.evaluate_sourcing_candidate_eligibility` wrote
   `v_reasons := v_reasons || 'vendor_not_active';` (and three siblings) to
   append an exclusion-reason code to a `text[]` accumulator. PostgreSQL's `||`
   operator resolves ambiguously between `anyarray || anyarray` and
   `anyarray || anyelement` when the right-hand side is an untyped string
   literal, and in this exact shape resolved to the array overload — attempting
   to *parse* `'vendor_not_active'` as an array literal and failing with
   `malformed array literal: "vendor_not_active"`. Live-reproduced the moment
   the eligibility scenario ran (any exclusion path hit it). Fixed by switching
   to `array_append(v_reasons, 'vendor_not_active')` (and the three siblings) —
   unambiguous, no operator-resolution risk.
2. **Read RPCs silently depended on session-implicit `auth.uid()` instead of
   their own validated `p_actor_auth_user_id` (the most serious finding).**
   The first draft of `get_sourcing_request`/`list_sourcing_requests`/
   `list_sourcing_candidates` did `select * from app.sourcing_requests_
   directory`/`app.sourcing_candidates_directory` after their own explicit
   `evaluate_permission(p_actor_auth_user_id, ...)` check — but those views'
   own row filter and cost mask call `app.has_active_tenant_membership`/
   `app.actor_holds_customer_user_layer`/`app.has_prc_view_cost` with their
   *default* `auth.uid()` argument, not the RPC's own explicit,
   already-validated actor. In a real browser session the two are the same
   value (`evaluate_permission`'s own internal `assert_actor_is_session_
   identity` guarantees it), but this SECURITY DEFINER function is the one
   place `p_actor_auth_user_id` is the authoritative identity — silently
   falling back to session-implicit `auth.uid()` for the actual data
   projection is the wrong dependency. Live-reproduced by this checkpoint's own
   db-test run: every read returned an all-null row (`get_sourcing_request`) or
   zero rows (`list_sourcing_*`) when called directly (no real JWT session),
   exactly the same failure mode a service-role/job-context caller with a
   legitimate, validated actor parameter would hit in production. Fixed by
   reconstructing the exact same projection directly against the base table in
   each RPC's own body, passing `p_actor_auth_user_id` explicitly to
   `app.has_prc_view_cost` — the identical technique `app.search_vendor_rates`
   (PRC-255) already uses for exactly this reason (confirmed by direct
   inspection: that function's own declared return type is the masked view's
   shape too, but its body never selects from the view itself). This is the
   same bug class as PRC-255's own build log §6 item 3 ("result-shape
   mismatch"), one layer more severe (an actor-identity mismatch, not merely a
   column-count mismatch).
3. **My own db-test file's bugs (not the migration):**
   - `app.add_vendor_address(...)` called with the `postal_code` positional
     argument dropped, shifting every subsequent argument by one and raising
     "function does not exist" — fixed by supplying it.
   - The "reused idempotency key with a different `owner_user_id`" scenario
     accidentally reused the exact same UUID for both the original owner and
     the "different" owner (`v_owner` was declared equal to `v_staff1`),
     making the assertion a tautology that happened to still raise the
     expected error for the wrong reason initially, then silently passed once
     harmless — caught because the very next assertion (`idempotency_key_
     conflict` expected) failed to raise at all. Fixed by using a genuinely
     different actor id.
   - The "submit shortlist with zero shortlisted candidates → denied" scenario
     assumed a candidate left shortlisted from an earlier scenario had already
     been un-shortlisted; it had not (only a *different* candidate was cleaned
     up). Fixed by explicitly un-shortlisting every candidate at the end of
     the prior scenario, so the "zero shortlisted" precondition is genuinely
     zero, not assumed.
   - The final `list_sourcing_requests` status-filter assertion queried for
     `status='shortlisted'`, but the R1 fixture had since been reopened back
     to `open` by an earlier scenario in the same file — fixed by filtering on
     `closed_no_source` instead (a genuinely terminal, never-reopened fixture
     in this file, immune to any earlier scenario's own later state changes).

None of these were shipped uncaught — every one surfaced from a genuine, live
`psql`/`pnpm run db:test` failure and was fixed before this checkpoint closed.
Finding 2 in particular is the exact "a real, live-reproduced defect this
checkpoint's own db-test run caught, not a hypothetical" class the prior five
checkpoints' own build logs describe finding — surfaced here by direct,
disciplined iteration (build → apply → run → fix → re-run), not by a separate
adversarial review pass (none was run for PRC-256 itself; the orchestrating
session's own independent verification may still choose to run one).

## 9. Residual, disclosed limitations (not defects)

- **Capacity/availability eligibility (PRC-262) is not evaluated** — deliberately
  deferred, disclosed in the migration header and §5 above, not fabricated
  against data that doesn't exist yet.
- **No vendor cargo-type/restricted-cargo capability master exists** anywhere in
  this repository; no such eligibility check is built, and no request-level
  cargo-restriction flag is modeled either — a disclosed gap, not a silently
  unenforced claim.
- **`requirements_snapshot`'s real upstream shape** (§5) means `mode`/cargo
  weight/volume/`currency`/`budget_amount` are reliably null for every
  costing-sourced request today — a real limitation of the upstream Commercial
  contract this checkpoint reads from, not a bug here.
- **List pagination.** `app.list_sourcing_requests` is server-side clamped to
  ≤200 rows, the same already-established, already-disclosed Phase 6
  limitation PRC-255's own `.limit(200)` bound records — not true cursor
  pagination.
- **UI idempotency-key generation.** None of the three creation forms render a
  client-persisted idempotency-key field (confirmed no PRC-25x creation form
  in this repository does either, by direct inspection of `app/(tenant)/
  [tenantSlug]/procurement/vendors/vendor-directory-panel.tsx` before writing
  this checkpoint's own forms). A fresh `crypto.randomUUID()` is generated
  server-side on every submit — a genuine network-level double-submit could in
  principle create two sourcing requests rather than deduplicating one. The
  RPC-level idempotency guarantee itself is real and tested
  (`scripts/db-tests/procurement-sourcing.sql`); this is a disclosed UI-wiring
  gap, the same pre-existing shape every other PRC-25x create form already
  carries, not a new one.
- **Concurrent-race reproduction** has no matching sequential db-test proof (no
  `dblink`/`pg_background` in this test suite) — the same standing,
  already-disclosed limitation every prior Phase 6 checkpoint's build log
  records. The optimistic-concurrency guard (lock + version-scoped `WHERE` +
  post-`UPDATE` re-check) was verified by direct code-path inspection against
  the repository's own proven pattern, not a live multi-session reproduction.
- **UI scope.** The detail page's "override constraints" form is a
  `<details>`-collapsed secondary action (matching the task's own "never
  require retyping available source data" instruction — it is not the primary
  editing surface); approve/reject-shaped actions do not exist for this
  capability at all (Sourcing has no Approve/Reject step), so no such UI was
  built.
- **The pre-existing `security:audit` (js-yaml) and `check-worktree-collision.
  test.ts` failures** (§7/§8) are registered, not fixed — both are outside
  this checkpoint's allowed-files scope and unrelated to Sourcing's own
  correctness.
- **No REST/GraphQL surface was added** — unchanged, disclosed identically to
  every prior capability in this repository (confirmed: no new `app/api/`
  route was added by this checkpoint). This disclosure was originally omitted
