### Fix 3 — `ISS-2026-045`, currency-blind procurement approval threshold, HIGH (the highest-risk
change in this task)

**Before:** `app.evaluate_procurement_approval_requirement` compared
`p_value_amount >= v_policy.min_value_amount` as raw numerics with no currency dimension — a
6,000 IDR `rate_version` (~USD 0.40) and a 6,000 USD `rate_version` (genuinely large) received the
identical `required` verdict, across all three value-bearing entity types
(`rate_version`/`vendor_selection`/`purchase_order`).

**Design, decided upstream and implemented verbatim** (full rationale in the migration's own
header comment, `supabase/migrations/20260730810000_harden_procurement_approval_currency_normalization.sql`):

1. New `app.procurement_approval_policies.policy_currency` column (`not null default 'USD'`,
   validated via the existing, FIN-194-backed `app.validate_currency_code`) — the currency
   `min_value_amount` is denominated in.
2. `app.create_procurement_approval_policy_version` gained a trailing `p_policy_currency`
   parameter (default `null`), resolving to: explicit caller value → the tenant's own published
   locale default currency → `'USD'`.
3. New private helper `app._evaluate_procurement_currency_threshold` — a **deliberate, disclosed
   variant** of PRC-258's own precedent `app._normalize_vendor_comparison_currency`, not an
   identical copy. Composes `app.convert_finance_amount` (FIN-194). Narrowly catches
   `no_data_found` (missing FX rate) and `check_violation` (unsupported currency), exactly as the
   precedent does — **and additionally catches `insufficient_privilege`** (the actor lacks
   `FIN:View`), which the precedent deliberately lets propagate because its own caller
   pre-checks `FIN:View`. This evaluator's own actor gate is deliberately
   `has_active_tenant_membership` only (preserved verbatim from the pre-existing design-note
   comment in the function), so a caller whose authority model is not the PRC permission
   catalogue at all (`app.create_rate_version`'s own `app.is_support_grant_authority`) must still
   reach it — letting `insufficient_privilege` propagate there would abort the entire submit
   transaction, a worse regression than the governance question itself.
4. `app.evaluate_procurement_approval_requirement` gained a trailing `p_value_currency`
   parameter (default `null`). Same-currency (or currency-omitted, the legacy shape) comparison is
   byte-identical to before. A genuine mismatch normalizes via the new helper; on ANY
   conversion-unavailable outcome (missing rate, unsupported currency, or no `FIN:View`) it **fails
   closed** — `required=true`, new reason code `value_currency_unverifiable_defaulted_to_required`
   — per this finding's own explicit reasoning that under-routing (silently skipping a review a
   large foreign-currency value should have triggered) is the more dangerous direction.
5. `app._request_procurement_entity_approval` (unchanged signature — it already received
   `p_currency` from every one of its 5 call sites, previously used only to populate the audit
   snapshot's `currency` column) now threads that `p_currency` into the evaluator's new parameter.
   **No entity-type submit RPC needed to change** — `create_rate_version`,
   `submit_purchase_order_for_approval` (the CURRENT version, `20260730690000`, not the superseded
   `20260730680000` one), and `submit_vendor_comparison_for_approval` already passed a real
   currency; only the two shared functions were missing the thread.

**A real implementation correction found and fixed during this checkpoint, not assumed** (this
prompt's own instruction: "VERIFY this directly... do not assume it"): a bare `CREATE OR REPLACE
FUNCTION` that appends a new trailing parameter — even one with a default — does **not** replace
the function in place. Postgres identifies a function by `(schema, name, parameter type list)`;
appending a parameter changes that list, so `CREATE OR REPLACE` silently created a second,
ambiguity-causing overload alongside the original (`\df` showed two rows for the same name; every
existing 6-argument call site would have kept resolving to the OLD, un-fixed overload, exactly
defeating the fix). This repository already has its own tested precedent for this exact class of
change (`20260730790000_harden_procurement_dashboard_reports_tier_c_review_fixes.sql`): `DROP
FUNCTION IF EXISTS <old signature>` → `CREATE FUNCTION` → explicit `REVOKE ... FROM PUBLIC` +
`GRANT ... TO authenticated, service_role` (a freshly `CREATE`d function, post-`DROP`, again
carries the default `PUBLIC` execute grant this schema's own `ALTER DEFAULT PRIVILEGES` only
covered for functions existing when it ran). `app.create_procurement_approval_policy_version` and
`app.evaluate_procurement_approval_requirement` both follow that exact precedent in the new
migration; `app._request_procurement_entity_approval` (unchanged signature) and the brand-new
`app._evaluate_procurement_currency_threshold` use plain `CREATE OR REPLACE`/`CREATE`.

**A second grant defect found and fixed via the mandated direct verification** (not assumed): the
brand-new `app._evaluate_procurement_currency_threshold` initially carried the implicit `PUBLIC`
execute grant every freshly `CREATE`d function receives — `has_function_privilege('authenticated',
..., 'EXECUTE')` returned `true`, which should never be true for a private, no-grant helper
(mirroring `app._normalize_vendor_comparison_currency`'s own posture). Root cause: this schema's
`ALTER DEFAULT PRIVILEGES` revoke did not take effect for functions created by this checkpoint's
own migration-applying role in this environment (`pg_default_acl` showed zero rows for the `app`
schema even after the original `20260717095000` migration ran) — the REAL mechanism keeping new
functions private, confirmed live, is each migration's own explicit
`revoke execute on all functions in schema app from public;` statement (the established
"per-migration convention since PLT-118," `ERR-2026-004`), which this migration was missing.
Added; re-verified:

```
$ has_function_privilege('authenticated', 'app._evaluate_procurement_currency_threshold(...)', 'EXECUTE')  → false
$ has_function_privilege('anon', ..., 'EXECUTE')          → false
$ has_function_privilege('service_role', ..., 'EXECUTE')  → false
$ has_function_privilege('authenticated', 'app.create_procurement_approval_policy_version(...)', 'EXECUTE') → true
$ has_function_privilege('authenticated', 'app.evaluate_procurement_approval_requirement(...)', 'EXECUTE')  → true
$ has_function_privilege('anon', <either of the two above>, 'EXECUTE')  → false
```
(all four re-verified against a from-scratch, fully-migrated throwaway database — grants
preserved/correct exactly as intended, not assumed.)

**Regression tests** (`scripts/db-tests/procurement-approval.sql`, a new, fully self-contained
third tenant `apr3` — isolated from every pre-existing fixture in the file — plus one existing

- **(b)** rate_version cross-currency normalization, BOTH directions (20,000,000 IDR → ~2,000 USD

- **(c)** `purchase_order` (via `app._request_procurement_entity_approval` directly, proving the

  case where `comparison_currency` deliberately differs from `policy_currency`) both normalize
  identically.
- **(d)** FAIL CLOSED: `admin3b` (tenant_admin/`is_support_grant_authority` only, zero role-based
  `FIN:View`) submits a foreign-currency rate — the entire `app.create_rate_version` transaction
  COMMITS (`governance_approval_status='pending'`, the new reason code), never a raised exception.
- **(e)** FAIL CLOSED on a missing FX rate for a specific currency pair (SGD, deliberately left

The one pre-existing test whose behavior would otherwise have silently changed

### Fix 6 — `ISS-2026-056`, missing `(tenant_id, created_at desc)` covering index on
`app.vendor_contracts`, MEDIUM

**Before:** `app.vendor_contracts` carried indexes on `(tenant_id, contract_number, version_no)`
×2, `(tenant_id, effective_end)` partial, and `(tenant_id, vendor_master_id, status)` — but none on
`(tenant_id, created_at desc)`, unlike its three siblings (`purchase_orders_tenant_created_idx`,
`rfqs_tenant_created_idx`, `vendor_comparisons_tenant_created_idx`).

**Fix:** same migration as Fix 4/5:
```sql
create index vendor_contracts_tenant_created_idx on app.vendor_contracts (tenant_id, created_at desc);
```
Plain `CREATE INDEX` — this repository does not use `CONCURRENTLY` anywhere (confirmed by
repository-wide grep), matching the exact naming convention of its three siblings.

**Verified live** against a seeded, skewed dataset mirroring `PRC-268`'s own reproduction (one
tenant holding the large majority of the table), built in a throwaway database, never wired into
`pnpm run db:test` (a multi-thousand-row seed does not belong in the standing regression gate):
7,497 total rows, one tenant holding 5,100 = **68.0%** — matching `PRC-268`'s own reproduction
ratio. `EXPLAIN (ANALYZE, BUFFERS)` against `app.list_vendor_contracts`'s own exact query shape:

| | Before (index dropped) | After (index present) |
|---|---|---|
| Plan | `Seq Scan on vendor_contracts` + top-N heapsort | `Index Scan using vendor_contracts_tenant_created_idx` |
| Buffers | shared hit=206 | shared hit=1 read=2 (=3) |
| Execution time | 3.026 ms | 0.086 ms |

A ~35× execution-time improvement and a ~68× reduction in buffer hits, confirming the planner
switch from Seq Scan to an ordered Index Scan with early-LIMIT termination — the exact behavior
`app.list_purchase_orders`'s own sibling index already provides.
