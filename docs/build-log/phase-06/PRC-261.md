## 1. What this checkpoint builds

Versioned vendor contracts governing services, rates, capacity, SLA, compliance, terms,
amendment and renewal (Prompt 261 §4). One table, `app.vendor_contracts`, holds every
VERSION of a logical contract (root+version collapsed into one table, mirroring
`app.procurement_approval_policies`/`app.vendor_rate_versions`'s own established shape)
-- `contract_number` is the stable business identity shared across every version row;
at most one `active` row per `(tenant_id, contract_number)` (`vendor_contracts_active_
unique`, a partial unique index).

Lifecycle: `draft` -> `pending_approval` (routes through the existing Procurement
Approval Engine, `entity_type='vendor_contract'` -- already a pre-provisioned valid
value in both `procurement_approval_policies_entity_type_check` and `procurement_
approval_context_snapshots_entity_type_check` since PRC-259's own migration, confirmed
by direct inspection, never altered here) -> `active` (requires approval complete AND
signature complete). Amendment (`app.amend_vendor_contract`) immediately supersedes the
current row and creates a new draft, mirroring `app.amend_purchase_order` (PRC-260)
exactly. Renewal (`app.renew_vendor_contract`) does NOT touch the current active row --
it supersedes only once the new renewal row itself activates, so a contract nearing its
own `effective_end` never has a coverage gap while its renewal is still in flight.
Suspend/reactivate/terminate (PRC:Override) and cancel-eligible cancellation
(PRC:Edit, mirrors `app.cancel_purchase_order`'s own cancel-the-bound-approval-request
shape) round out the lifecycle.

`app.resolve_effective_vendor_contract(tenant, vendor_master_id, as_of)` is the one
deterministic effective-term resolution point (§24: "Effective... resolution is
deterministic and source-versioned") PRC-263/264/265 -- the remaining prompts of this
same batch and the next -- read from; at most one row can ever match, enforced
structurally by `vendor_contracts_active_unique`, never by convention.

Signature is evidence-only (RPD-038): `app.record_vendor_contract_signature` attaches a
re-validated (tenant/`record_type`/`record_id`/`malware_scan_status='clean'`, mirroring
PRC-252's own established C-10 fix pattern) Document/File Engine (PLT-128) file plus
`signed_by`/`signed_at` metadata. No e-sign provider connector exists anywhere in this
repository; this is the same, already-disclosed Phase 6 precedent every prior
capability has followed for third-party connectors.

`rate_version_id`, `payment_term_days`, `tax_terms` and `capacity_terms` are the four
commercial-term fields masked behind `PRC:View cost` (already-existing `app.has_prc_
view_cost`, PRC-252) in every read RPC's own projection via a new helper, `app.mask_
vendor_contract_cost_fields` -- never relying on a raw table grant (the base table's own
`authenticated` grant is column-restricted to the non-cost columns, defence in depth,
mirroring the batch 257-259 review's own established fix pattern for `rfq_responses`/
`vendor_comparison_offers`).

## 4. Tier B — recurring defect taxonomy self-check (mandatory, `docs/standards/RECURRING_DEFECT_TAXONOMY.md`)

Walked in order against this prompt's own full diff. Three real findings, all fixed
in-prompt before this checkpoint, each with a regression assertion added to `scripts/
db-tests/procurement-vendor-contract.sql`:

- **C-01 (idempotency replay matched the key but never verified the target) --
  CONFIRMED, fixed.** `app.create_vendor_contract_draft`'s pre-check AND its
  exception-handler race-recovery branch both returned the existing row on a bare
  `(tenant_id, idempotency_key)` match, without checking it describes the vendor/
  contract_type/effective_start actually requested -- a reused key would have silently
  returned an unrelated contract. Fixed by comparing the full target tuple in both
  branches and raising `idempotency_key_conflict` on mismatch, mirroring `app.create_
  vendor_profile_draft`'s (PRC-251) own established shape. Regression test added.
- **C-04 (a decision was made on a parent/state row read without a lock) -- CONFIRMED,
  fixed.** `app.renew_vendor_contract` read the source contract's `status`/`record_
  version` unlocked and, unlike suspend/reactivate/terminate/cancel, never performs a
  version-guarded UPDATE on that same row afterward -- so there was no later optimistic-
  concurrency check to catch a concurrent modification between the read and the
  decision. Fixed by adding `for update` to the initial read.
- **C-05 (permission check ordered after a read that already discloses data) --
  CONFIRMED, fixed.** `app.get_vendor_contract` and `app.get_vendor_contract_lifecycle_
  history` both read the full row (or its `tenant_id`) and raised `vendor_contract_not_
  found` on a genuine miss BEFORE checking tenant membership -- a cross-tenant,
  zero-membership caller who supplied a real id from another tenant received
  `insufficient_authority` instead, an observable existence oracle. Fixed by folding
  "does not exist" and "exists but this caller has no membership in its tenant" into
  the SAME `vendor_contract_not_found` error, mirroring `app.get_purchase_order`
  (PRC-260) exactly. Regression test updated to assert the corrected error code.

## 5. Residual, disclosed limitations (itemized, not silently omitted -- C-23 discipline)

1. No "create from template" flow (§14 names `draft/from-template`) -- no contract-
   template capability exists anywhere in this repository to build one from; every
   contract starts from `create_vendor_contract_draft`'s own explicit field set.
2. No standalone `validate` preview endpoint (§14) -- validation is inline (create/
   update raise structured, typed errors); no separate dry-run/preview RPC.
3. No e-sign provider connector (§14 "send/signature-status") -- signature is
   evidence-only (design note 4, RPD-038), the same disclosed Phase 6 precedent every
   prior capability with an external-connector-shaped requirement has followed.
4. No vendor-portal "vendor sees own allowed contract" surface (§26) -- no
   vendor-portal identity concept exists anywhere in this repository, the same
   already-accepted PRC-257/258 scope boundary, not a fresh regression.
5. No formal termination "impact review" against downstream dependencies (§22) --
   `app.terminate_vendor_contract` carries no active-dependency check yet; PRC-263
   (Vendor Assignment, next in this same batch) adds the real guard once `app.vendor_
   assignments` exists (design note 6 in the migration header).
6. No async expiry-reminder dispatch job (§17) -- `app.list_vendor_contracts_expiring`
   is a read-only query; no generic notification-dispatch queue exists anywhere in this
   repository to wire a reminder job into, the same gap PRC-253 already disclosed for
   compliance-document expiry (design note 7).
7. `capacity_terms` is a `jsonb` declaration only in this prompt, not a PRC-262 foreign
   key -- PRC-262 (Vendor Capacity and Availability, next in this same batch) does not
   exist yet at this checkpoint; its own migration adds the FK in the other direction
   (design note 8).
