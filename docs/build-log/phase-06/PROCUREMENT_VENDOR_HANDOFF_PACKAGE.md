**The `ERR-2026-004` per-migration convention** (`docs/runtime/ERROR_LEDGER.md`: explicit `revoke`/`grant execute` on every function, never relying on an implicit default privilege) is present throughout, confirmed by direct grep sample this checkpoint rather than assumed: every migration that introduces a genuinely new function carries the blanket `revoke execute on all functions in schema app from public;` statement before its own explicit grants (confirmed directly in `20260730580000`, `20260730630000`, `20260730740000`, `20260730810000`). Pure `CREATE OR REPLACE FUNCTION` hardening migrations that only widen an already-granted, unchanged-signature function correctly carry **no** blanket revoke (`CREATE OR REPLACE` never resets an existing grant, so none is needed — confirmed absent in `20260730670000`/`690000`/`730000`/`770000`/`800000`/`820000`); where a hardening migration instead needed `DROP FUNCTION` + `CREATE FUNCTION` (a genuine signature change, e.g. a new trailing parameter), it carries an explicit, per-function targeted `revoke`/`grant execute` pair instead of the blanket form — confirmed present in `20260730790000` (two functions) and `20260730810000` (two functions) — because a freshly `CREATE`d function always regains the implicit `PUBLIC` execute grant regardless of any earlier blanket revoke in the same migration, and `PRC-269.md` §2 Fix 3 documents live-verifying exactly this mechanism (`has_function_privilege('authenticated', ...) = false` re-confirmed against a from-scratch database before commit). This is a genuinely careful, not merely mechanical, application of `ERR-2026-004` — the convention is scoped to where a real privilege-reset risk exists, not blindly repeated in every file.

### `ISS-2026-059` deserves prominence beyond a table row

**A fresh reader running `pnpm run db:test` right now, between 01:00 and 03:59 UTC, WILL see `scripts/db-tests/procurement-vendor-performance.sql` fail.** This is a real, deterministic, root-caused, pre-existing defect in `app._calc_vendor_kpi_rate_validity`'s (PRC-264, `20260730740000_create_procurement_vendor_performance.sql`) own calendar-day denominator arithmetic: `generate_series(p_window_start::date, (p_window_end - interval '1 day')::date, ...)` computes an upper bound that falls on the PREVIOUS calendar date whenever the test's own fixed 21-hour window starts before 03:00 UTC, making `generate_series` return zero rows and collapsing `is_computable` to `false` for a case the function itself intends to be unconditionally computable. It is **not** a flake, and it is **not** caused by this checkpoint or by `PRC-269`'s own hardening work — three independent adversarial-review lenses at `PRC-269`, plus this checkpoint's own fresh re-run (§7 of `PRC-270.md`), all reproduce the identical failure whenever the wall-clock happens to fall in that band, and all confirm via `git stash` that it reproduces identically against the pre-`PRC-269` baseline. It **self-heals** outside the **01:00–03:59 UTC** window (confirmed live at `now()≈02:41 UTC` failing and documented as passing at every prior checkpoint's own daytime run) and carries **zero data-integrity impact** — a false `is_computable=false` correctly still routes the vendor into reduced-coverage handling, never a fabricated score. **Correction (fix round, independently re-derived from the live function/test arithmetic, not copied):** this checkpoint's own first-pass text, and the pre-existing `docs/runtime/KNOWN_ISSUES.md` entry it carried forward (written at `CG-S11-PRC-020`, historical, not edited by this fix round), both stated the band as "roughly 00:00–03:59 UTC" (4 hours). Re-deriving directly: with `v_window_start := date_trunc('hour', now()) - interval '1 hour'` and `v_window_end := v_window_start + interval '21 hours'`, at `now()`'s hour-of-day `H=0` (00:00:00–00:59:59 UTC) both `p_window_start::date` and `(p_window_end - interval '1 day')::date` land on the SAME previous calendar date, so `generate_series` returns exactly one row and the test **passes** — the 00:00 hour is not actually part of the failure band. Only `H ∈ {1, 2, 3}` (01:00:00 through 03:59:59 UTC) makes `p_window_start::date` land strictly after `(p_window_end - interval '1 day')::date`, collapsing `generate_series` to zero rows. The true band is **01:00:00–03:59:59 UTC (3 hours)**, not 00:00–03:59 (4 hours). (`KNOWN_ISSUES.md`'s own more precise derivation two sentences into the same entry — "whenever `p_window_start`'s own hour-of-day is less than 3" — is already internally consistent with this corrected 3-hour band; only that entry's own restated summary window text is off by one hour, a pre-existing imprecision in that historical, already-committed entry that this fix round does not rewrite, but does not carry forward uncorrected into this document either.) The fix (replacing the day-window upper bound with a time-of-day-independent computation) is bounded and low-risk but is out of scope for both `PRC-269` (chartered to fix `PRC-268`'s own six named findings only) and this checkpoint (documentation-only) — it is `PRC-264`'s own migration, owned by a future task with an explicit mandate to touch it. **Do not mistake the next red `db:test` run in this window for a fresh regression.**
