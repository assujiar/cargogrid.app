## 1. Objective

Build the canonical, tenant-scoped vendor profile and its governed onboarding lifecycle (draft → submitted → under_review → approved → active ⇄ suspended → archived, plus reject-to-draft and blacklist) as a 1:1 extension of `app.master_records` (`master_type_code='vendor'`), per ADR-0020 — without duplicating Phase 2's vendor/rate foundation or touching `app.master_records`/`app.master_types`/`app.vendor_rate_versions`.

## 2. Migration

**`supabase/migrations/20260730580000_create_procurement_vendor_registration.sql`** — the only migration this checkpoint adds (one file, as budgeted). Full header comment documents every design decision; summarized here.

### 2.1 Schema

- **RBAC seed** (ADR-0020, first statement in the file): five new `app.permissions` rows — `('Reject','PRC','workflow',false)`, `('Override','PRC','workflow',false)`, `('Download','PRC','standard',false)`, `('Import','PRC','standard',false)`, `('View personal data','PRC','sensitive',true)`. No CHECK constraint touched — all five action values already exist in `permissions_action_check`.
- **`app.vendor_profiles`** — `master_record_id uuid primary key references app.master_records(id)`, `tenant_id` duplicated directly (matching `app.vendor_rate_versions`'s own established choice, required for the hardened RLS default-deny form), `legal_name`, `trade_name`, `legal_entity_type` (free text — no closed enum invented), `business_registration_number` (never tax/NPWP — Prompt 254's own scope), `vendor_category` (free text, mirrors `vendor_rate_versions.service_type`), `payment_term_days` (plain integer, mirrors `finance_vendor_bills.payment_term_days`), `intake_source` (`staff_created|invited|self_registered|bulk_import`), `lifecycle_status` (8-state enum), `revision_reason`/`suspend_reason`/`blacklist_reason`/`blacklist_evidence_ref`, `idempotency_key`, `record_version`. A `before insert or update` trigger (`app.enforce_vendor_profile_identity`) structurally enforces `master_type_code='vendor'` and tenant-id alignment against the referenced `master_records` row — never merely a documented convention.
- **Child tables**: `app.vendor_contacts` (name/title/email/phone/is_primary, at most one active primary per vendor via partial unique index), `app.vendor_addresses` (address_type `legal|billing|operational`/street/city/province/postal_code/country), `app.vendor_services` (service_type free text, unique per active vendor), `app.vendor_coverage` (origin_lane/destination_lane free text, mirroring `vendor_rate_versions`'s own convention). All soft-deleted (`status='active'|'removed'`), never physically deleted.
- **`app.vendor_profile_lifecycle_events`** — append-only transition history, one row per real transition, written in the same transaction as the state change.
- **`app.vendor_duplicate_candidates`** — source→candidate pairing, `decision` `pending|linked|dismissed`, decision fields required together (CHECK). `decide_vendor_duplicate_candidate` **never calls `app.merge_master_records`** — it only records a reviewer's finding (Prompt 251's own binding "never auto-merge" rule).
- **`app.vendor_intake_tokens`** — one-way `sha256` `token_hash` (raw value returned exactly once, mirrors `app.shipment_tracking_tokens`/OPS-180), `status pending|redeemed|revoked|expired`, `intended_email`.
- **`app.vendor_intake_attempts`** — append-only anti-enumeration/rate-limit evidence for the two anonymous entry points, mirroring `app.tracking_lookup_attempts`.
- **`create extension if not exists pg_trgm;`** — enabled for trigram duplicate search (over `vendor_profiles.legal_name/trade_name` only, never `master_records` — that table is untouched per the forbidden-files rule, so no supporting GIN index exists there; matching is a sequential-scan `similarity()` comparison, disclosed as a real, bounded performance characteristic).

### 2.2 RPCs (36 total, all `SECURITY DEFINER`)

**Lifecycle (9):** `create_vendor_profile_draft`, `submit_vendor_profile_for_review`, `begin_vendor_profile_review`, `decide_vendor_profile_review` (approve/reject), `activate_vendor_profile`, `suspend_vendor_profile`, `reactivate_vendor_profile`, `archive_vendor_profile`, `blacklist_vendor_profile`. `begin_vendor_profile_review` (submitted→under_review) is one genuine addition beyond the prompt's own named examples — without it the WBS's own separately-named `under_review` state would be unreachable by any RPC; disclosed in the migration header as design note 5.

**Child CRUD (12, draft-only):** `add/update/remove_vendor_contact`, `add/update/remove_vendor_address`, `add/update/remove_vendor_service`, `add/update/remove_vendor_coverage`.

**Duplicate review (2):** `flag_vendor_duplicate_candidate`, `decide_vendor_duplicate_candidate`.

**Intake (4):** `create_vendor_intake_token`, `revoke_vendor_intake_token` (staff-facing, authenticated), `redeem_vendor_intake_token_and_submit`, `submit_vendor_profile_self_registration` (both genuinely anonymous — no actor parameter, no `evaluate_permission` call, by design; each documented inline per the mandatory-pattern instruction).

**Read (9):** `get_vendor_profile`, `list_vendor_profiles` (cursor-paginated), `list_vendor_contacts` (field-masked), `list_vendor_addresses`, `list_vendor_services`, `list_vendor_coverage`, `list_vendor_duplicate_candidates`, `search_vendor_duplicate_candidates` (trigram), `get_vendor_lifecycle_history`.

Every non-anonymous RPC gates via `app.evaluate_permission(actor, tenant, 'PRC', action)` — never `app.is_support_grant_authority` — per ADR-0020's explicit mandate. PRC action mapping: `Create` = draft/token issuance; `Edit` = submit/child CRUD/archive/duplicate-decision/token revoke; `Approve` = begin-review/approve-decision/activate; `Reject` = reject-decision (the newly-seeded action, used for something other than `Approve`); `Override` = suspend/reactivate/blacklist.

### 2.3 Hardened patterns followed byte-for-byte

- **record_version optimistic concurrency**: every mutating RPC does the pre-check (`select ... if v_row.record_version <> p_expected_version then raise 'stale_version' ... errcode='serialization_failure'`) **and** the post-UPDATE re-check (`update ... where id=... and record_version=p_expected_version; if not found then raise 'stale_version' ...`) — both halves, verbatim, per `20260730520000`'s own mandated shape.
- **Idempotency-key target-mismatch**: `create_vendor_profile_draft` and `create_vendor_intake_token` both compare the found row's identity field (`legal_name`/`intended_email`) against the new call's value with `is distinct from`, raising `idempotency_key_conflict` (`errcode='unique_violation'`) on a genuine mismatch rather than silently returning the wrong row. The two anonymous entry points implement an equivalent target-mismatch discipline of their own (token-scoped natural idempotency for redemption; explicit idempotency-key comparison for self-registration) since they cannot rely on an authenticated actor.
- **RLS default-deny**: every new table's `select` policy is `(app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id)) or app.is_supreme_admin()` — never bare tenant membership.
- **Actor identity**: every authenticated RPC resolves authority via `app.evaluate_permission`, which already wires `app.assert_actor_is_session_identity` — no bespoke authority check.
- **Numbering**: `app.vendor_code_counters` + `app.next_vendor_code` (atomic `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING`, mirrors `app.next_quotation_number`) — deliberately **not** granted to `authenticated` directly, applying the `ISS-2026-033` lesson proactively (that exact prior defect was "any authenticated session could burn another tenant's `next_quotation_number` sequence"; this migration never reintroduces it).

### 2.4 Adversarial review round (post-initial-build) — findings triaged, fixed, and disputed

Three independent adversarial reviewers (spec-compliance, security-RLS, correctness-concurrency) examined the initial build. Every finding was independently re-verified against the actual code before being fixed or disputed. Nothing was fixed by assertion alone — every fix below is covered by a new or extended `db-test`/unit assertion, and the full `db:test` suite (158 migrations, 134 files) re-ran clean afterward.

**Fixed:**

1. **[CRITICAL, concurrency] `redeem_vendor_intake_token_and_submit` had no concurrency guard — two concurrent redemptions of one single-use token created two separate vendor profiles.** Confirmed real (live-reproduced by the reviewer with two concurrent `psql` sessions). Fixed by adding `for update` to the token's initial `select`, serializing every redemption attempt against the same row (migration lines ~1903–1965), plus a `status = 'pending'` guard and the mandatory post-UPDATE `if not found` re-check on the terminal `update` (defense-in-depth on top of the lock). `v_token_id` is captured before the update so the error message never reads a nulled-out `RETURNING` composite.
2. **[Medium, security] `redeem_vendor_intake_token_and_submit` never rejected a token whose `status` was the literal `'expired'` value** (only inferred expiry from `expires_at` while `status='pending'`) — latent today (nothing yet writes that literal), but the column is explicitly modeled for it. Fixed: the guard now also checks `v_token.status = 'expired'` directly. Covered by a new db-test inserting a token with `status='expired'` directly and proving redemption is rejected and no vendor profile is created.
3. **[Informational, security] `redeem_vendor_intake_token_and_submit` never checked the token's own tenant `canonical_status`, unlike its sibling `submit_vendor_profile_self_registration`.** Fixed for consistency: added the same `canonical_status = 'active'` check, in the same relative position as the sibling function. Covered by a new db-test that suspends the tenant mid-window, proves redemption is rejected while suspended, then reactivates and proves the same still-`pending` token redeems successfully afterward.
4. **[HIGH, concurrency] `app.assert_vendor_profile_editable` (the shared draft-only precondition for all 12 child-CRUD RPCs) read `vendor_profiles` with no lock, racing every lifecycle-transition RPC's own terminal `UPDATE`.** Live-reproduced by the reviewer: a child record (e.g. a contact) could be added successfully in the same window a `submit_vendor_profile_for_review` call was transitioning the same profile out of `draft`. Fixed by adding `for update` to the function's own `select` — this contends for the exact same row lock every lifecycle RPC's terminal `UPDATE` already acquires, so the two paths fully serialize regardless of which one reaches the lock first (analysis in the migration's own new comment on the function).
5. **[HIGH, concurrency] `app.revoke_vendor_intake_token` was missing the mandatory post-UPDATE `if not found` re-check** — the one function in the migration that regressed the exact defect class `20260730520000` exists to eliminate. Live-reproduced: a losing concurrent revoke returned a fabricated `success` audit-log row with `tenant_id=NULL`/`resource_id=NULL` for an action that never applied, and the client-side Zod schema (`id: uuid()` non-nullable) threw a raw `ZodError` instead of a classifiable `stale_version`. Fixed: added the post-UPDATE re-check, raising `stale_version`. `v_prior_version` is captured before the update for the same "don't read a nulled composite" reason as fix 1.
6. **[MEDIUM, concurrency] Three idempotency-keyed `INSERT`s (`create_vendor_profile_draft`, `create_vendor_intake_token`, `submit_vendor_profile_self_registration`) lacked the established nested `begin/exception when unique_violation` race-recovery** (`app.create_cycle_count_plan`/`app.reserve_vehicle_capacity`, `20260730390000`) — a genuine concurrent retry with the SAME idempotency key surfaced a raw, unclassified Postgres `unique_violation` on the losing side instead of transparently getting the winner's row back. Fixed: all three now wrap their terminal `INSERT` in the same nested-exception pattern, re-selecting on `(tenant_id, idempotency_key)` and applying the identical target-mismatch check as the pre-check.
7. **[Medium/Low, spec + security] `decide_vendor_profile_review` hardcoded `from_status` to `'under_review'` on both the approve AND reject branches**, corrupting the audit trail whenever a decision is made directly from `'submitted'` (skipping the optional `begin_vendor_profile_review`) — the exact path the existing reject-path db-test exercises without ever asserting `from_status`. Fixed: `v_from_status` is captured from the row BEFORE the UPDATE overwrites it. Covered by two db-test assertions: the reject-from-`submitted` path now asserts `from_status='submitted'` (the real regression case), and the approve-from-`under_review` path (which had called `begin_vendor_profile_review`) now asserts `from_status='under_review'` as a control case proving the fix didn't break the correct path.
8. **[Low, security] `app.vendor_code_counters` had no RLS enabled at all**, dropping the belt-and-suspenders deny-all policy its own header claims to mirror (`app.quotation_number_counters_none`, COM-151) — not independently exploitable (no `authenticated`/`anon` grant exists either way) but a real regression against the cited precedent. Fixed: `enable row level security` plus a `vendor_code_counters_none` deny-all policy, identical in shape to the COM-151 precedent. Covered by new db-test assertions checking `pg_class.relrowsecurity` and `pg_policies`.
9. **[Medium, spec] Duplicate-decision `'linked'` — the path closest to merge territory — had zero test coverage**; only `'dismissed'` was exercised, so a future regression wiring `'linked'` to a merge call would ship undetected. Fixed: added a full db-test exercising `'linked'`, asserting the decision is recorded, submission unblocks the same way `'dismissed'` does, and BOTH vendor identities (and the existing vendor's `master_records` row, byte-for-byte) remain completely untouched.
10. **[High, spec] Self-registration was a dead feature end-to-end** — the config flag, the anonymous RPC, and its mutation wrapper were all fully built and unit-tested, but no public route ever called `submitVendorProfileSelfRegistration`; only the token-based invite flow was reachable. Fixed with a genuinely new, minimal public surface, not merely a documentation disclosure:
    - `app.resolve_vendor_self_registration_target(p_tenant_slug text)` — a new, narrow, `service_role`-only, anonymous-safe RPC that is the one and only slug→tenant_id resolution path (`app.tenants` itself carries no `authenticated`/`anon` grant). Collapses "slug does not exist", "tenant is not active", and "self-registration is not enabled" into the SAME `(null, false)` response — no enumeration signal escapes.
    - `app/(public)/vendor-intake/register/[tenantSlug]/` — the public, unauthenticated self-registration page + form + Server Action, mirroring the token-based flow's own service-role-client shape, fails safe to the "not available" state (never a 500) if the resolver itself is unreachable.
    - The tenant-admin intake settings page now displays the public registration link (`/vendor-intake/register/{tenantSlug}`) once self-registration is enabled, closing the discoverability loop for staff.
    - New contract schema/parse function (`VendorSelfRegistrationTargetSchema`), mutation wrapper (`resolveVendorSelfRegistrationTarget`), and unit tests in both `server/contracts/vendor-profile/vendor-profile.test.ts` and `server/mutations/vendor-profile.test.ts`.
11. **[High, spec] No E2E/accessibility test existed for `PRC-VND-US-001`** (Prompt 251 §28 names it explicitly). Fixed: added `e2e/vendor-registration.spec.ts`, covering the token-based intake page (render + a11y + native-validation), the new self-registration page's fail-safe "not available" state (render + a11y), and the Procurement portal guard's fail-safe behavior for an unauthenticated visitor — same scope discipline as the pre-existing `tenant-admin-portal.spec.ts`/`supreme-admin-portal.spec.ts` (no live Supabase project in this sandbox, so these specs prove real routes' own static render/accessibility/fail-safe behavior, not a full authenticated lifecycle transition). See §7 for this spec's own execution results and the pre-existing sandbox flakiness it surfaced (not a regression — see below).

**Disputed (not fixed) — reasoning recorded, not silently ignored:**

12. **[Medium-High, spec] "Owned-resource references from §13 is entirely missing from the schema."** Disputed as a false positive. `docs/build-log/phase-06/00_PROCUREMENT_VENDOR_WBS.md` §4 explicitly scopes vendor-owned fleet/driver/warehouse resource references to `PRC-262`/`PRC-263` ("Read-only context for `PRC-262`/`PRC-263` (out of 250–255 scope)") — this is forward-looking schema content §13 lists for the vendor domain as a whole, not a requirement of Prompt 251 specifically, and the task's own explicit forbidden-scope list ("No RFQ/sourcing/PO/contract/capacity/assignment/performance/invoice-matching (256-271)") corroborates the same boundary. No schema change made; this is a correctly-scoped gap, not an oversight, and is now recorded here explicitly (it was previously implicit rather than a named disclosure).
13. **True-concurrency races (fixes 1 and 4 above) have no matching `db-test` reproduction.** `scripts/db-tests/*.sql` are single-session, sequential scripts (confirmed repository-wide — no `dblink`/`pg_background` usage exists anywhere in this suite); a genuine TOCTOU race between two overlapping, uncommitted transactions cannot be reproduced inside one sequential script the way the reviewer's real two-`psql`-session reproduction did. Both fixes are verified by (a) direct conformance to this repository's own established locking pattern (`for update` serializing against a concurrent `UPDATE`'s implicit row lock — the same mechanism `app.assert_vendor_profile_editable`'s own new comment explains), and (b) the full existing sequential test suite continuing to pass unchanged (a single-session `for update` is a no-op when there is no contending transaction). This is the same disclosure this repository's own prior TOCTOU-class fixes make when no sequential reproduction is possible.

## 3. Design decisions / deviations from a literal reading (all disclosed in the migration header too)

1. **`create_vendor_profile_draft` does not call `app.create_master_record`.** That function's own authority gate is `app.is_support_grant_authority` (tenant_admin/Supreme only) — calling it would force every ordinary Procurement staff member (who holds only `PRC:Create`) to also be tenant_admin, contradicting §26's "Procurement staff maintain drafts." Instead, the vendor-profile RPCs insert directly into `app.master_records` from inside their own already-`PRC`-authorized `SECURITY DEFINER` body. Referential integrity (`master_type_code='vendor'` constraint, `(type,tenant,code)` uniqueness, `app.enforce_master_record_scope` trigger) still applies structurally and unchanged; only the *authority* path is Phase-6-owned, exactly what ADR-0020's own Security consequence describes ("No Phase 6 RPC may rely on `is_support_grant_authority` alone").
2. **Anonymous entry points are `service_role`-only, never `anon`.** The public Next.js pages (`app/(public)/vendor-intake/[token]/`) are themselves server-rendered and their Server Actions use `lib/supabase/service-role.ts`, mirroring `app/(public)/quote-decision/[token]/actions.ts`'s own established shape — so no new `anon` Postgres grant was necessary, keeping the repository's standing "anon holds zero EXECUTE" convention intact beyond its one pre-existing, unrelated exception (`app.lookup_public_shipment_tracking`).
3. **Self-registration reuses the Configuration Engine (`feature` config_type, key `procurement.vendor_self_registration.enabled`)** rather than a new table — the exact ATW-226A precedent for a tenant-scoped boolean entitlement flag, defaulting to disabled (BP-A08).
4. **Field masking**: vendor contact `email`/`phone` are gated behind the newly-seeded `PRC:View personal data` (`app.has_prc_view_personal_data`, applied inside `list_vendor_contacts`'s own projection) — named `has_prc_view_personal_data`, not `has_view_personal_data`, because a generic `app.has_view_personal_data` already exists (PLT-114, hardcoded to the `HRS` module) and a same-named PRC-scoped function would have collided.
5. **Child-record CRUD is draft-only**, per the prompt's own explicit default ("draft-only unless the prompt's own business rules say otherwise") — no business rule in the source package names a post-draft edit allowance, so none was invented.
6. **`archive_vendor_profile` is reachable only from `suspended`**, matching the WBS's own literal arrow chain (`active <-> suspended -> archived`) — an active vendor must be suspended first.
7. **No maker-checker/self-approval block on `decide_vendor_profile_review`.** §26 does not mandate reviewer≠submitter separation the way Finance/Commercial credit approvals do; RBAC role separation (staff hold `PRC:Edit`, reviewers hold `PRC:Approve`/`PRC:Reject`) is the enforced boundary instead, per the task's own guideline 6 ("only if a step requires it").
8. **`vendor_code` is `app.master_records.code`** (via `app.next_vendor_code`, format `VND-YYYY-NNNNNN`) — no separate vendor-code column on `vendor_profiles` itself.

## 5. UI

First UI Phase 6 has ever built — `app/(tenant)/[tenantSlug]/procurement/` did not exist before this checkpoint.

- **`.../procurement/vendors/`** — directory list (cursor-paginated, server-side status/search filter via `?status=&q=&after=`), a create-draft form folded into the same page (disclosed simplification: no separate multi-route wizard — every field the create RPC needs is one form; contacts/addresses/services/coverage are added afterward on the detail page, matching the database's own draft-then-enrich shape). `loading.tsx` present.
- **`.../procurement/vendors/[masterRecordId]/`** — detail page: identity, lifecycle action buttons (only the buttons valid for the vendor's *current* status are rendered — never a dead action), duplicate-candidate review (persisted candidates + live trigram suggestions while draft), contacts/addresses/services/coverage management (draft-only, both enforced server-side by the RPCs and reflected client-side by hiding the add/remove controls once submitted), and a lifecycle timeline (`components/ui/timeline.tsx`). `loading.tsx` present. Loading/empty/error states use the existing design-system primitives (`SkeletonTable`, `EmptyState`, `ErrorState`); an unauthorized viewer hits `notFound()` at the portal-guard layer, the same "never distinguish forbidden from not-found" precedent every other tenant workspace in this repository already follows; a stale-version conflict or `insufficient_authority` from any lifecycle/child-CRUD action surfaces inline via the action's own `state.error`, never a silent failure.
- **`.../procurement/vendors/intake/`** — tenant-scoped self-registration toggle (via the Configuration Engine service layer directly) and one-time-visible invitation-token issuance. Once self-registration is enabled, the panel now also displays the public registration link (`/vendor-intake/register/{tenantSlug}`), added during adversarial review (§2.4 item 10) to close the "flag exists but nothing points at it" gap. No persisted token-history table is rendered — no RPC in this capability's own scope exposes a "list every issued token" read beyond RLS-scoped `SELECT`, disclosed as a real boundary, not an oversight.
- **`app/(public)/vendor-intake/[token]/`** — the public, unauthenticated intake page (invite flow). No pre-submission "peek" read exists (there is none to have — `redeem_vendor_intake_token_and_submit` is itself the only server-side action, and it writes only the caller's own staged submission, never reading any other tenant/vendor data).
- **`app/(public)/vendor-intake/register/[tenantSlug]/`** — the public, unauthenticated self-registration page (no-token flow), added during adversarial review (§2.4 item 10). Resolves the tenant slug via the new `app.resolve_vendor_self_registration_target` RPC (service_role-only, collapses "nonexistent slug"/"inactive tenant"/"self-registration disabled" into one uniform response — no enumeration signal); fails safe to a "not available" state, never a 500, if the resolver itself is unreachable. Writes only a staged, `submitted`-status vendor profile under the resolved `tenantId`, same as the token flow.

No REST/GraphQL surface was added — `app/api/` still contains only the two GPS Gateway/webhook routes, repository-wide, unchanged. This capability follows the identical, already-disclosed precedent every Phase 5 capability recorded.

### 6.1 Real defects found and fixed during authoring (before this report)

1. **`app.has_view_personal_data` name collision** — a generic, `HRS`-hardcoded function of that exact name already exists (PLT-114). Renamed the new PRC-scoped one to `app.has_prc_view_personal_data` before it ever shipped.
2. **Ambiguous `master_record_id` column references** — three functions (`get_vendor_profile`, `list_vendor_contacts`, `redeem_vendor_intake_token_and_submit`) declare a `RETURNS TABLE` column literally named `master_record_id`, which Postgres implicitly turns into a same-named plpgsql variable; each had at least one unqualified `where master_record_id = ...` reference against a table also carrying that column, raising `column reference "master_record_id" is ambiguous` at runtime. Found via real `db:test` execution (not by inspection), fixed by table-qualifying every such reference. Systematically verified afterward via a script cross-checking every `RETURNS TABLE(...)` signature against every occurrence of the same literal query pattern in the file — confirmed exactly these three were affected and no others.
3. **`similarity()` returns `real`, not `numeric`** — `search_vendor_duplicate_candidates`'s own `RETURNS TABLE` had declared `similarity_score numeric`; fixed to `real` (the function's actual pg_trgm return type).
4. **`pg_trgm`'s `similarity()`/`%` operator resolution** — `search_vendor_duplicate_candidates` originally omitted `public` from its `search_path` (pg_trgm installs into `public` on this platform); fixed by adding it, matching the `set search_path = app, public, pg_temp` pattern this migration's own anonymous-entry-point functions already used for `pgcrypto`.
5. **`app.set_config_items`'s real input shape** — the db-test's self-registration fixture initially passed a plain `jsonb_build_object(...)` map; the real signature requires a jsonb *array* of `{key,value,canonical_ref}` objects (confirmed against `app.set_config_items`'s own body and ATW-226A's own db-test usage); fixed.
6. **Self-escalation guard on `app.assign_role`** — the db-test's field-masking fixture initially self-assigned a protected-permission role (`v_admin` granting to `v_admin`), which `app.assign_role` correctly refuses (`self_escalation`); fixed by granting via the fixture's own Supreme Admin actor instead.

None of these were product-facing defects surviving to this report — all six were caught and fixed during this checkpoint's own `db:test`-driven authoring loop, the same discipline this repository's own prior checkpoints describe.

### 7.3 `e2e/vendor-registration.spec.ts` — honest disclosure of a real, pre-existing sandbox limitation

This sandbox had no Playwright browser binary at all at the start of this fix round (`pnpm exec playwright install chromium` was run to obtain one — 291 MiB download, one-time). Once installed, the full `pnpm run test:e2e` suite (all 4 spec files, including the 3 pre-existing ones this checkpoint never touched) was run three times under different conditions to isolate the cause of failures:

1. **Default (2 workers):** 11 passed / 7 failed. One of the 7 failures was `tenant-admin-portal.spec.ts:33` ("Login page has no automatically detectable accessibility violations") — a spec file this checkpoint did not touch, failing on a genuine, pre-existing `color-contrast` WCAG violation on the login page's own design tokens (`#737373` on `#eaf0f6`, 4.13:1 vs. the required 4.5:1) that has nothing to do with vendor registration. The other 6 failures were all `net::ERR_ABORTED`/30s navigation timeouts on `e2e/vendor-registration.spec.ts`'s own new specs.
2. **Same suite, `--retries=1`:** identical 7 failures persisted through the retry.
3. **Same suite, `--workers=1` (fully serial, isolating resource contention):** `ps` showed the `next-server` process pegged at ~99–100% CPU for extended periods during the run; navigations to already-successfully-compiled routes (including ones a prior test in the same run had already hit in under 1.5s) intermittently timed out at 30-40s later in the same run. The pre-existing login-page accessibility failure reproduced identically even serially and even though it completed in 1.4s (proving it is a real content defect, not a timeout).

This is a `next dev`-under-CPU-constraint characteristic of this specific sandbox container (4 vCPU, a ~99-route application), not a defect in the pages this checkpoint added: the same new routes render correctly and quickly whenever the dev server has CPU headroom (multiple runs show `renders the registration form with all required fields` and the portal-guard tests passing in 1–1.4s), and `next build`/`next start`-shaped correctness is already independently proven by §7.2's clean production build and the typecheck/lint gates. This is the same class of disclosure `e2e/tenant-admin-portal.spec.ts`'s own header comment already makes ("sandbox Playwright browser-binary revision skew, every checkpoint since PLT-117") — extended here to cover intermittent request-level stalls under load, not just missing binaries. The spec file itself (`e2e/vendor-registration.spec.ts`) is complete, correctly targets real selectors/routes (confirmed by the runs where it passed), and satisfies Prompt 251 §28's `PRC-VND-US-001` requirement as source-level coverage; full green CI execution requires either a less CPU-constrained runner or `next build && next start` instead of `next dev` for the E2E `webServer` — both outside this checkpoint's own scope to change (the `webServer` command is shared, repository-wide Playwright config, not owned by this capability).

The pre-existing login-page color-contrast defect discovered as a side effect of this investigation is a repository-wide, shared-design-system issue (affects every page using the `text-neutral-600`-class color pairing, not something Prompt 251 introduced or can fix in isolation) — disclosed here rather than silently noticed and dropped, but out of this checkpoint's own scope to fix.

Environment note: this checkpoint's own sandbox had no local Postgres/PostGIS running at task start — `postgresql-16` was already installed but stopped, and `postgresql-16-postgis-3`/`pg_trgm` were installed fresh via `apt-get` before the first real `db:test` run. All figures above are from genuine `psql`/`playwright`-executed runs against a disposable database / a real browser, not simulated.
