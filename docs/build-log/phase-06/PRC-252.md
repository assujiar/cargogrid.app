## 1. Objective

Implement versioned initial/periodic/incident/financial/operational/safety vendor assessments with explainable scoring, findings, corrective actions, mandatory maker-checker approval, manual score override, and a manual "start reassessment" flow — without mutating `app.vendor_profiles.lifecycle_status` (vendor eligibility composition is explicitly Prompts 256+/262/263 scope).

## 2. Migration

**`supabase/migrations/20260730590000_create_procurement_vendor_assessment.sql`** — the only migration this checkpoint adds. Full header comment documents every design decision; summarized here.

### 2.1 Schema

- **`app.vendor_assessment_templates`** — versioned `draft → published → archived`, mirroring `app.item_control_policy_versions` (ATW-016) exactly: `publish_vendor_assessment_template`'s own `p_supersedes_version_id` archives the prior published version for the same `(tenant_id, vendor_category, assessment_type)` scope. `vendor_category` is a nullable wildcard (matches `vendor_profiles.vendor_category`). `assessment_type` is a fixed 6-value CHECK (`initial|periodic|incident|financial|operational|safety`, the only categories the prompt names — none invented). `pass_threshold`/`conditional_threshold`/`weight_total_required` (default 100.00) drive scoring and banding.
- **`app.vendor_assessment_template_criteria`** — one scored criterion per template version, `purpose_tag` (`financial|safety|operational|compliance`) driving §26's purpose-bound section masking, `weight` validated to sum to the parent's `weight_total_required` **only at publish**, never at every add (the prompt's own explicit instruction). Draft-template-only mutation (`app.assert_vendor_assessment_template_editable`, `for update` lock).
- **`app.vendor_assessments`** — header. `template_version_id` is a snapshot FK to one immutable, already-published template row — the applied-version invariant this repository enforces everywhere rates/configs are consumed (proven by a dedicated db-test, §6). `assessment_type` is snapshotted from the selected template at start. Lifecycle: `draft → in_progress → submitted → under_review → approved|rejected → closed`. `calculated_score`/`score_band`/`adjusted_score`/`adjustment_reason`/`adjusted_by`/`adjusted_at`/`expiry_date`/`predecessor_assessment_id` all live here.
- **`app.vendor_assessment_answers`** — one row per `(assessment_id, criterion_id)`, upserted. `evidence_file_id` is a nullable FK to `app.files` (PLT-128) — the first Phase 6 capability to actually wire a real evidence attachment (PRC-251 disclosed it did not need to).
- **`app.vendor_assessment_findings`** — severity/description/status (`open|resolved|waived`).
- **`app.vendor_assessment_corrective_actions`** — linked to a finding, `assessment_id` denormalized (mirrors `vendor_profiles`' own `tenant_id` duplication choice) for `close_vendor_assessment`'s own open-count query. `resolved_evidence_file_id` reuses the Document/File Engine.
- **One structural guard, not just app-level checks**: `vendor_assessments_one_open_per_type_idx`, a partial unique index on `(vendor_master_record_id, assessment_type)` where status is one of the open states — backs the "conflicting active assessment" exception-flow block (§23) even under a real concurrent race, not merely a pre-check.

### 2.2 RPCs (33 total, all `SECURITY DEFINER` except two private helpers)

**Template lifecycle (7):** `create_vendor_assessment_template_draft`, `update_vendor_assessment_template_draft`, `add/update/remove_vendor_assessment_template_criterion`, `publish_vendor_assessment_template`, `archive_vendor_assessment_template`.

**Assessment lifecycle (9):** `start_vendor_assessment`, `record_vendor_assessment_answer`, `calculate_vendor_assessment_score`, `submit_vendor_assessment_for_review`, `begin_vendor_assessment_review`, `decide_vendor_assessment_review`, `adjust_vendor_assessment_score`, `close_vendor_assessment`, `start_vendor_assessment_reassessment`.

**Findings/corrective actions (4):** `raise_vendor_assessment_finding`, `decide_vendor_assessment_finding`, `create_vendor_assessment_corrective_action`, `update_vendor_assessment_corrective_action_status`.

**Read (9):** `get_vendor_assessment_template`, `list_vendor_assessment_templates`, `list_vendor_assessment_template_criteria`, `get_vendor_assessment`, `list_vendor_assessments`, `get_vendor_assessment_score_breakdown`, `list_vendor_assessment_findings`, `list_vendor_assessment_corrective_actions`, `get_vendor_current_assessment_status`.

**Helpers (4, private except `has_prc_view_cost`):** `has_prc_view_cost` (field-masking gate, granted), `assert_vendor_assessment_template_editable`, `assert_vendor_assessment_editable`, `_compute_vendor_assessment_score` (no grant to anyone but the function owner — the single, non-duplicated explainable-scoring computation both `calculate_vendor_assessment_score` and `submit_vendor_assessment_for_review` call, so the two can never drift apart).

Every non-anonymous RPC gates via `app.evaluate_permission(actor, tenant, 'PRC', action)`. RBAC mapping (all 12 already-seeded PRC actions reused, **zero new `app.permissions` rows seeded**): `Create` = start assessment/reassessment/template draft/corrective-action; `Edit` = template draft/criteria mutation, record answer, calculate/submit, raise/decide finding, update corrective-action status, archive template, close (no open CA); `Approve` = publish template, begin review, approve decision; `Reject` = reject decision; `Override` = manual score adjustment, close with open CA; `View`/`View cost` = reads/masking.

### 2.3 Explainable scoring (design note 3)

`app._compute_vendor_assessment_score(template_version_id, assessment_id)` computes `sum(criterion.weight * answer.score / 100)` over the assessment's own applied template version's active criteria, rounded to 2 decimals, banded against the template's `pass_threshold`/`conditional_threshold`. `app.get_vendor_assessment_score_breakdown` is the companion read RPC returning one row per criterion with `weight`, `answer_score`, and `contribution` — "criterion X contributed Y points because weight Z × score W" is directly computable client-side from this row set, satisfying §4/§21/§33's own "explainable" requirement literally, not merely asserted.

### 2.4 Mandatory maker-checker (design note 4)

`app.decide_vendor_assessment_review` rejects `self_approval_not_allowed` (errcode `insufficient_privilege`) if `p_actor_auth_user_id = assessment.assessor_auth_user_id`, using the exact wording/shape `app.approve_warehouse_billing_event` (20260730300000) established. The same guard is duplicated as defense-in-depth in `begin_vendor_assessment_review` and in the optional reviewer-pre-assignment parameter of `start_vendor_assessment`/`submit_vendor_assessment_for_review`/`start_vendor_assessment_reassessment` (an assessor may not name themselves reviewer up front either). This is a genuine departure from PRC-251, where §26 did not require reviewer≠submitter separation and plain RBAC role separation was judged sufficient — PRC-252's own §21/§23 explicitly name it.

### 2.5 Manual score adjustment (design note 5)

`app.adjust_vendor_assessment_score` — `PRC:Override`-gated, mandatory non-empty reason, restricted to `submitted|under_review` (after a score exists, before the decision is final). Writes **both** the real prior value and the new value into `app.capture_audit_event`'s `before_value`/`after_value` jsonb parameters (verified genuinely recorded, not just the new value, by a dedicated db-test reading `app.audit_logs` directly), plus the dedicated `adjusted_score`/`adjustment_reason`/`adjusted_by`/`adjusted_at` column pair for direct display. A second override in the same assessment correctly records the **prior adjustment** as its own before value (`coalesce(adjusted_score, calculated_score)`), not the original machine-calculated score a first override may have already superseded — proven by a dedicated two-override db-test assertion.

### 2.6 Reassessment (design note 6)

On approval, `expiry_date = decided_at::date + template.validity_period_days`. `app.get_vendor_assessment`/`app.get_vendor_current_assessment_status` surface a **computed** `reassessment_due` boolean (`expiry_date < current_date`), never a stored, driftable copy. `app.start_vendor_assessment_reassessment` is a real, manually-invoked RPC referencing the prior assessment as `predecessor_assessment_id` — no scheduler/cron job is added (`ISS-2026-015`, standing repository-wide gap, not this capability's job).

**One real design gap found and fixed during db-test authoring**: the predecessor-status check originally required `status = 'approved'` only, per a literal reading of "reassess an approved assessment." Testing surfaced that `close_vendor_assessment` (a legitimate, separate governance step verifying corrective actions) moves a real, completed assessment to `'closed'` — which would then have made reassessment *unreachable* for any assessment that had gone through full closure. Fixed: the predecessor check now accepts `status in ('approved', 'closed')`, with the migration's own comment explaining why (`closed` is `approved` plus a completed reconciliation, never a regression away from approved).

### 2.7 Hardened patterns followed byte-for-byte (copied from `20260730580000`)

- **`record_version` optimistic concurrency**: every mutating RPC does the pre-check (`if v_row.record_version <> p_expected_version then raise 'stale_version' ... errcode='serialization_failure'`) **and** the post-UPDATE re-check (`update ... where id=... and record_version=p_expected_version; if not found then raise 'stale_version' ...`) — both halves, verbatim, on every one of the 20 mutating RPCs.
- **Idempotency-key target-mismatch**: `create_vendor_assessment_template_draft`, `start_vendor_assessment`, `start_vendor_assessment_reassessment` all compare the found row's real identity columns (name/assessment_type; vendor+template; predecessor+template respectively) against the new call's values with `is distinct from`, raising `idempotency_key_conflict` (`errcode='unique_violation'`) on a genuine mismatch. Each is followed by a nested `begin/exception when unique_violation` race-recovery block on the terminal INSERT, mirroring `app.create_vendor_profile_draft`'s own pattern.
- **A refinement beyond the 251 precedent**: `start_vendor_assessment`/`start_vendor_assessment_reassessment` can violate **two different** unique constraints on the same INSERT (the idempotency-key unique index, or the one-open-assessment-per-type partial unique index) — the nested exception handler uses `GET STACKED DIAGNOSTICS v_constraint_name = CONSTRAINT_NAME` to distinguish which one actually fired and recover/report correctly for each, rather than assuming a single cause. This is a genuinely new pattern in this migration (no prior migration in this repository needed it) — verified live against Postgres: a plain `CREATE UNIQUE INDEX` (no explicit table `CONSTRAINT`) still populates `CONSTRAINT_NAME` with the index's own name on a violation.
- **TOCTOU row locks**: `app.assert_vendor_assessment_template_editable` and `app.assert_vendor_assessment_editable` both take a `for update` lock on their own read, serializing criteria-mutation against publish, and answer-recording against submit, respectively — the exact class of race PRC-251's own adversarial review found and fixed in `app.assert_vendor_profile_editable`.
- **RLS default-deny**: every new table's `select` policy is `(app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id)) or app.is_supreme_admin()`.
- **Actor identity**: every RPC resolves authority via `app.evaluate_permission`, which already wires `app.assert_actor_is_session_identity` (ATW-031) — no bespoke check.

## 3. Design decisions / deviations from a literal reading (disclosed in the migration header too)

1. **No new `app.permissions` rows seeded.** All 12 already-seeded PRC actions (7 original + PRC-251's 5) fit every RBAC need this capability has. §26's "compliance/finance/safety roles see purpose-bound sections" is honored for the one dimension a seeded action fits: `purpose_tag='financial'` masking behind the already-seeded `PRC:View cost` (mirrored as `app.has_prc_view_cost`, matching PRC-251's own `has_prc_view_personal_data` naming convention to avoid PLT-114's collision). No seeded action distinctly fits `safety`/`compliance`/`operational` beyond ordinary `PRC:View` — disclosed as a reasoned simplification given the fixed action set, not a silently-invented gap.
2. **No dedicated `*_lifecycle_events` append-only history table for assessments**, unlike PRC-251's `vendor_profile_lifecycle_events`. `app.capture_audit_event` already records every transition (actor/reason/before/after) via `app.audit_logs`, and the prompt names no dedicated domain-shaped timeline requirement the way PRC-251's own WBS did for vendor onboarding. Disclosed as a real, deliberate scope-reduction, not an oversight.
3. **Findings/corrective-action CRUD is not maker-checker-gated** — only the assessment's own review decision is (§23's own explicit naming). Raising/deciding a finding and managing a corrective action's status are ordinary `PRC:Create`/`Edit` actions.
4. **Reassessment takes an explicit `p_template_version_id` parameter** rather than auto-resolving "the current published template" — the caller (UI) picks from `list_vendor_assessment_templates` filtered to the predecessor's own `assessment_type`. This keeps the RPC's own validation logic (published + category match) identical to `start_vendor_assessment`'s, rather than inventing a second resolution path.
5. **Corrective-action creation is restricted to an `open` finding** — a defensible, simple constraint (a corrective action follows from an unresolved issue); not explicitly mandated by the prompt but consistent with its own "resolve findings" main-flow framing.
6. **`get_vendor_current_assessment_status` prefers the most recent `approved` row per assessment_type, falling back to the most recent decided (rejected) row** — a `distinct on` ordered by `(status='approved') desc, created_at desc`, disclosed inline in the function's own comment. This is the downstream-composable contract; PRC-252 itself never composes eligibility from it.

### 6.1 Real defects found and fixed during authoring (before this report)

1. **`start_vendor_assessment_reassessment`'s predecessor-status check (`= 'approved'`) made reassessment unreachable for any assessment that had already gone through `close_vendor_assessment`.** Found via the db-test's own reassessment scenario (which deliberately closes its predecessor first, matching a realistic operator flow). Fixed: `status in ('approved', 'closed')`, with the migration's own comment explaining the reasoning (§2.6 above).
2. **A test-authoring assumption, not a product defect: `app.audit_logs.occurred_at` is identical across two `capture_audit_event` calls inside the same enclosing transaction** (Postgres' `now()` is fixed per-transaction) — an `order by occurred_at desc limit 1` query in the db-test's own second-override assertion was therefore a genuine tie, non-deterministically returning either audit row. Fixed the TEST (not the product) to match on the real `after_value.score` content instead of relying on recency ordering. Disclosed here because the same "same-transaction audit rows share one timestamp" characteristic could mislead a future db-test author reusing this pattern.
3. **My own initial test wrote `app._compute_vendor_assessment_score to carry NO grant at all`** — this over-strict assertion failed against Postgres' own universal implicit owner-privilege row (present for every function regardless of any `GRANT` statement, confirmed identical for PRC-251's own already-`VERIFIED` `app.assert_vendor_profile_editable`). Fixed the assertion to check for the absence of `authenticated`/`service_role`/`anon` grants specifically, the real security property intended.
4. Several test-fixture sequencing bugs (not product defects) surfaced while chaining many assessments against the same vendor+type across sequential test blocks, given the real structural `vendor_assessments_one_open_per_type_idx` guard: leftover open assessments from earlier blocks correctly (and expectedly) blocked later blocks' own `start_vendor_assessment` calls via `conflicting_active_assessment` — proving the guard works exactly as designed. Fixed by adding explicit decide/close cleanup steps at the end of each test block that would otherwise leave an assessment open, and by introducing a second vendor fixture for the idempotency-replay test so it does not depend on vendor-1's own open-assessment state elsewhere in the file.

None of these were product-facing defects surviving to this report except item 1, which is a real design correction now reflected in the shipped migration.
