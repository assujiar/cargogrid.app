## 1. What this checkpoint builds

Governed vendor selection acceptance and shipment/task assignment — a genuine
extension, never a duplicate, of the canonical Operations assignment. `app.
resource_assignments.role` already includes `'vendor'` as one of its four valid roles
(confirmed by direct inspection of OPS-172's own CHECK constraint), and `resource_id`
already resolves through `app.master_records`, the SAME identity `app.vendor_profiles.
master_record_id` uses. This migration adds the PROCUREMENT side missing from OPS-172
-- an invitation/acceptance workflow carrying exact eligibility/rate/contract/PO/
capacity evidence, `app.vendor_assignment_invitations` -- and calls OPS-172's own
already-`VERIFIED` `app.assign_resource`/`app.reassign_resource` to commit the
canonical row, never re-implementing assignment-slot logic (the partial-unique
`is_current` index, conflict detection, audit) a second time.

Two distinct authorities, matching §26 exactly ("Procurement... propose; vendor
accepts/declines own invitation [recorded by staff, no portal]; dispatcher performs
canonical assignment"): `propose_vendor_assignment_invitation`/`accept_.../decline_.../
cancel_vendor_assignment_invitation` gate on `PRC:Edit`; `confirm_vendor_assignment`/
`reassign_vendor_assignment` gate on `OPS:Assign` -- the SAME permission `app.assign_
resource`/`app.reassign_resource` themselves require of the identical passed actor,
checked twice by design (once here for a fast, clear failure; once again inside the
nested OPS-172 call, never weakened or bypassed). `override_vendor_assignment`
requires BOTH `OPS:Assign` and `PRC:Override` -- a governed emergency direct-assign
bypassing the normal invite/accept/eligibility gate entirely, disclosed as carrying no
formal expiry/later-review workflow (no review-queue infrastructure exists anywhere in
this repository to compose with).

Eligibility (`app.evaluate_vendor_assignment_eligibility`) is re-verified fresh at
confirm time, never trusted from the propose-time snapshot -- compliance status,
contract effectiveness, and a linked reservation's own live status can all change
between invitation and confirmation, exactly the class of decision-on-stale-read C-04
exists to name. Capacity consumption happens inline inside `confirm_vendor_assignment`
(not via a second call to the PRC:Edit-gated `consume_vendor_capacity_reservation`),
so an OPS:Assign-holding dispatcher is never forced to also hold PRC:Edit for no real
reason. `app.terminate_vendor_contract` (PRC-261) gains the active-dependency guard
PRC-261's own migration header promised: termination is now blocked while any live
(`invited`/`accepted`/`assigned`) invitation still cites the contract.

## 4. Tier B — recurring defect taxonomy self-check

Lessons from PRC-261/262's own Tier B self-checks (run immediately before this prompt,
same session/batch) were applied FROM THE FIRST DRAFT here: idempotency replay
verifies the full target tuple (C-01, in `propose_vendor_assignment_invitation` and
`override_vendor_assignment`); the confirm/reassign writes lock the invitation row
`for update` before deciding (C-04); by-id reads fold not-found and cross-tenant into
one error (C-05). Three real findings still surfaced and were fixed in-prompt:

- **C-12 (`SECURITY DEFINER` granted to `authenticated` with no authority check) --
  CONFIRMED, fixed. The most significant finding of this batch.** `app.evaluate_
  vendor_assignment_eligibility` was originally granted to `authenticated` with zero
  internal authority check of its own (by design -- it trusts its caller to have
  already authorized the overall action). Granting it directly to `authenticated`
  would have let any authenticated session in any tenant probe another tenant's
  vendor/contract/PO/capacity-reservation existence and status with zero
  authorization -- exactly the ISS-2026-033 disclosure class `scripts/db-tests/
  rbac-enforcement.sql`'s repository-wide `SECURITY DEFINER` sweep exists to catch.
  **Caught live, not by inspection**: the sweep failed with `assertion failed: 1
  SECURITY DEFINER function(s) are granted to authenticated with no authority check
  anywhere in their call graph, and are not on the reviewed-and-justified list:
  {evaluate_vendor_assignment_eligibility}`. Fixed by re-scoping the grant to
  `service_role` only; every caller (`propose`/`confirm`/`reassign`/the preview RPC)
  has already performed its own complete `evaluate_permission` check before reaching
  this helper. A regression test in `procurement-vendor-assignment.sql`'s own
  schema-privilege block asserts `authenticated` holds zero `EXECUTE` on this function
  specifically, naming this exact fix.
- **Test-fixture entanglement between the OPS-172 resource-occupancy invariant and
  this migration's own invitation lifecycle -- CONFIRMED as a real design interaction,
  not a migration bug, fixed in the db-test fixture.** `app.assign_resource`'s
  pre-existing `assignment_conflict` guard (a resource may hold only one live
  assignment at a time, unchanged Phase 5 semantics applying uniformly to the
  `'vendor'` role) fired when the test fixture tried to `override_vendor_assignment`
  vendor A onto a second shipment while vendor A's own confirmed assignment on the
  first shipment was still current. This is the guard working as designed --
  `override_vendor_assignment` still creates a REAL `app.resource_assignments` row
  through the same `assign_resource` path, so it never bypasses the underlying
  resource-occupancy invariant, only the vendor-eligibility gate (as disclosed).
  Fixed the fixture by explicitly `app.unassign_resource`-ing vendor A's prior
  assignment first (a real, narrated "shipment delivered" release), not by weakening
  any assertion. A related fixture issue surfaced immediately after: `app.terminate_
  vendor_contract`'s new active-dependency guard also correctly found vendor A's
  original, still-`'assigned'` invitation (`idem-vasm-inv-1`) permanently citing its
  contract -- this migration has no "close out a fulfilled assignment" transition
  independent of reassigning to a replacement vendor (see §5 item 1), so reusing that
  same contract for the "blocked, then succeeds once cleared" test scenario could
  never reach a genuine cleared state. Fixed by decoupling the test onto a second,
  freshly-issued contract dedicated to that one scenario, never touching the
  permanently-`'assigned'` shipment's own contract.
- **C-20 (a capability with no caller) -- CONFIRMED, fixed.** `app.get_vendor_
  assignment_eligibility_preview` was built, granted, and reachable with zero UI
  caller. Fixed: the invitation detail page now shows a live "eligible now" / "not
  eligible now" re-check (with named reasons) for any invitation still in `invited` or
  `accepted` status, clearly labeled as a best-effort preview distinct from the

## 5. Residual, disclosed limitations (itemized -- C-23 discipline)

1. **No "close out a fulfilled assignment" transition independent of reassignment.**
   Once an invitation reaches `'assigned'`, the only forward transition is `reassign_
   vendor_assignment` (to a replacement vendor) -- there is no "mark this shipment's
   vendor commitment complete/released" action that leaves the invitation itself in a
   terminal, non-blocking state without picking a new vendor. Releasing the underlying
   `app.resource_assignments` row via OPS-172's own `unassign_resource` does not, by
   itself, change the invitation's own status. A practical consequence: a contract
   whose only associated invitation reached `'assigned'` and was never reassigned
   remains permanently blocked from `terminate_vendor_contract` by this same
   migration's new active-dependency guard (discovered and worked around in this
   prompt's own db-test fixture, §4). No such "assignment complete" concept exists
   elsewhere in this repository to compose with; judged out of this prompt's own
   bounded scope rather than invented ad hoc.
2. **`'expired'` is a valid status in the CHECK constraint's own vocabulary, but
   nothing in this migration ever sets it.** `response_deadline` is captured and
   displayed, but there is no scheduled job, cron trigger, or manual "mark expired"
   action anywhere in this repository that transitions a stale `invited` invitation to
   `'expired'`. An overdue invitation remains `invited` indefinitely until a human
   accepts, declines, or cancels it.
3. **No vendor-portal accept/decline surface** (already-accepted PRC-257/258/261/262
   precedent) -- accept/decline is staff-recorded on the vendor's own behalf.
4. **`override_vendor_assignment` carries no formal expiry/later-review workflow**
   (disclosed directly in the migration's own function comment) -- no review-queue
   infrastructure exists anywhere in this repository to compose with; the override is
   fully evidenced (reason, dual authority, audit event) for an out-of-band human
   review process outside this capability's own scope.
5. **The propose/override creation forms accept a shipment order only as a raw UUID
   text field**, and `rateVersionId` is settable on `propose`/`reassign` at the RPC
   layer but has no picker in either form (only vendor/contract/PO/capacity-reservation
   IDs are exposed as form fields on propose; only vendor/contract/capacity-reservation
   on reassign) -- no shipment-order or rate-version picker component exists elsewhere
   in Procurement's own already-built pages either; both fields are real, tested, and
   settable via direct RPC call, just not yet from this prompt's own minimal forms
   (mirrors PRC-262's own disclosed item 4, same bounded-scope judgment call).
