## 3. Finding (Prompt 163 §20 task 1 — ranked; only one item to rank)

**Severity: High (cross-tenant business-intelligence disclosure, IDOR class).**

`app.evaluate_quotation_approval_requirement(p_quotation_id uuid)` (`COM-153`, `20260724270000_create_commercial_quotation_approval.sql`) was the only function across all 51 prior Commercial/Platform migrations granted directly to `authenticated` that takes a bare entity id and **no tenant or actor parameter at all**, and performs **no access check whatsoever**. Its own sibling in the same file family, `app.get_quotation_submission_readiness` (`COM-152`, widened by `COM-153`), takes `p_actor_auth_user_id uuid default auth.uid()` and calls `app.can_access_record(...)` before returning anything — the established convention this one function alone did not follow.

**Concrete exploit scenario**: any authenticated identity holding a role in *any* tenant, given a quotation id belonging to a *different* tenant (leaked via a URL, a shared log line, or a support ticket), could call `app.evaluate_quotation_approval_requirement(that_id)` directly and learn that tenant's own margin/discount/value threshold-crossing signal — `required=true/false` plus specific reason codes (`below_minimum_margin`, `discount_exceeds_maximum`, `value_meets_threshold`) — for a deal it has no entitlement to see. Never a raw dollar figure, but a real, previously undisclosed business-intelligence leak across the tenant boundary this repository's own RLS/RBAC/four-layer-context discipline exists to prevent everywhere else.

**Root cause**: a missing parameter and check, not a defect in the underlying threshold logic (which is unchanged, verbatim, in the repair below).

## 4. Root-cause repair (Prompt 163 §20 task 2/3, exact finding-linked only)

New migration `supabase/migrations/20260726090000_create_commercial_hardening.sql`:

1. **`DROP FUNCTION app.evaluate_quotation_approval_requirement(uuid)`** — required (not `CREATE OR REPLACE`) because adding a parameter changes the function's identity in Postgres; a same-name `CREATE OR REPLACE` with a different argument list creates a second overload alongside the vulnerable original rather than replacing it, which would leave the finding open.
2. **`CREATE FUNCTION app.evaluate_quotation_approval_requirement(p_quotation_id uuid, p_actor_auth_user_id uuid default auth.uid())`** — identical business logic to the original, with one added check (the same `app.can_access_record(...)` call `app.get_quotation_submission_readiness` already uses) immediately after fetching the quotation row.
3. **`CREATE OR REPLACE FUNCTION app.submit_quotation(...)`** (same 4-argument signature, unchanged) — its one internal call site now passes the already-validated `p_actor_auth_user_id` through, closing the gap for the internal caller too (previously benign only because `submit_quotation` itself already checked access before calling the function; now the callee enforces it independently, defense in depth).
4. New grants: `evaluate_quotation_approval_requirement(uuid, uuid)` to `authenticated, service_role`; `submit_quotation`'s own grant is preserved automatically (`CREATE OR REPLACE` keeps the same OID/ACL). `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA app FROM PUBLIC` re-applied first, per the `ERR-2026-004` standing convention.

One pre-existing db-test call site updated (not a migration, no immutability concern): `scripts/db-tests/commercial-quotation-approval.sql`'s own single call to the function (line 187) now passes the real actor id it already had in scope, rather than relying on the now-mandatory access check resolving `auth.uid()` to nothing in a plain `psql` session.

## 5. Tests (Prompt 163 §27/§28/§29 — finding-specific negative/regression, full two-tenant fixtures)

`scripts/db-tests/commercial-hardening.sql` (new, 5 scenario groups):

1. **Setup**: two tenants, each with a rep holding real Commercial permissions, tenant A additionally carrying a published 40%-minimum-margin quotation-approval rule and one quotation whose margin (20%) genuinely crosses that floor.
2. **Fix proof, positive path**: the legitimate same-tenant rep with real record access still gets the correct `required=true, reasons=[below_minimum_margin]` result — the repair changes access control, not the underlying business decision.
3. **Fix proof, the exact vulnerability closed**: a rep in a completely unrelated tenant B, calling the function with tenant A's own quotation id, is now denied `insufficient_privilege` — proven to fail, not merely proven to still return a plausible-looking result.
4. **Regression**: `app.submit_quotation`'s own main flow is unaffected — still resolves the same routing decision, still fails closed with `approval_definition_not_configured` when no Approval Engine routing definition is published, exactly as before this repair (since it already validated the same actor prior to the changed internal call).
5. **Schema-privilege defense in depth** (`ERR-2026-004` regression guard): `anon` holds no `EXECUTE` on the new 2-argument overload; `authenticated` does; the old, vulnerable 1-argument overload no longer exists at all (checked directly against `pg_proc`, not inferred).
