## 3. Implementation

### 3.1 Scope boundaries (disclosed, migration header)

1. **No new table, no duplicate analytics store** (Prompt 158 §13) — every function composes only the already-`VERIFIED` transactional tables listed above.
2. **Every function is `security definer` with its own explicit, re-stated `app.can_access_record(...)` row filter, not an invoker-mode read relying on RLS.** An invoker-mode first draft was tried and failed empirically this checkpoint, reproducing the exact `permission denied for table opportunities` error `COM-147`'s own build log already documents for `app.opportunities_directory`: Postgres checks column privileges against the *invoker*, and `authenticated` has no direct column grant on `app.opportunities.value_amount`/`value_currency`/`probability`, nor on `app.quotations.approval_status`/`customer_decision`/`is_current` (each added by a later migration's own narrower column grant). Every function now mirrors the identical `can_access_record` check its corresponding `*_directory` view already uses.
3. **Field masking reuses the two already-`VERIFIED` gates directly**: `app.has_view_selling_price` (`COM-147`) for opportunity/quotation/forecast amounts, `app.has_view_cost` (`COM-149`) for margin figures. No new permission action. A masked aggregate returns `null` (never a zero) plus its own `*_masked=true` flag.
4. **Mixed-currency ambiguity resolved structurally**: every amount-bearing summary groups by `currency`, one row per currency actually present — no cross-currency sum is ever computed.
5. **`app.dashboard_scope_org_unit_ids`** wraps `PLT-109`'s `service_role`-only `app.org_unit_descendant_ids`, mirroring `COM-143`'s own `app.lead_record_scope_org_unit_ids` wrapper — a real authoring bug (below) was found and fixed in this wrapper during db-test authoring.
6. **No caching layer this checkpoint** — every query is live; query-budget/timeout enforcement is the service layer's own responsibility (`server/queries/dashboard.ts`).
7. **No privileged access to audit** — these are ordinary, scoped reads (the "ordinary views" carve-out every prior read-only capability already relies on). Export is `COM-159`'s own scope, not built here.

### 3.2 Schema — `supabase/migrations/20260724320000_create_commercial_dashboard.sql`

Eight new functions, zero new tables: `app.dashboard_scope_org_unit_ids` (self+descendants org-unit filter wrapper) plus seven `app.get_dashboard_*` reads — `lead_aging` (open-lead count bucketed by age-since-last-activity: `0_2_days`/`3_7_days`/`8_14_days`/`15_plus_days`), `activity_queue` (scheduled activities bucketed by due-date urgency: `overdue`/`due_today`/`upcoming_7_days`/`no_due_date`), `pipeline_summary` (open, non-terminal opportunity count/value per stage×currency), `quote_sla` (open submitted-quotation queue bucketed `pending_approval`/`expiring_soon`/`expired_no_decision`/`awaiting_customer_decision`), `margin_summary` (current margin calculations by currency over an optional period), `win_loss_summary` (won/lost opportunity count/value by currency over an optional period, keyed off the real `app.opportunity_stage_history` transition event, not `updated_at`), `forecast_summary` (probability-weighted open-pipeline value by currency, reusing `app.opportunities.probability` directly — no separate forecast model). `revoke execute on all functions in schema app from public` per the standing `ERR-2026-004` convention.

### 3.3 Service layer and UI

`server/contracts/dashboard/dashboard.ts` (bucket/stage/outcome enums, shared `DashboardScopeFilterSchema`/`DashboardPeriodFilterSchema`, one row schema + parser per RPC). `server/queries/dashboard.ts` — one thin typed wrapper per RPC, plus a real query-budget timeout (`withQueryBudget`, `DEFAULT_DASHBOARD_QUERY_BUDGET_MS=5000`, `DashboardQueryTimeoutError` on elapse) satisfying RPD-014's "timeouts" control concretely rather than only by comment — no existing precedent for this in the codebase, so the mechanism is a self-contained `Promise.race`-style wrapper, not dependent on Supabase's own `abortSignal` fetch plumbing (untested in this repository until now).

## 8. Errors / recovery / risks / issues

Three real defects found and fixed during authoring, all caught before this checkpoint declared itself green:

1. **`app.dashboard_scope_org_unit_ids` initially returned strict descendants only**, since `app.org_units.path` excludes self by design (`PLT-109`'s own documented shape) — filtering leads by a leaf department (`team_a`, no descendants of its own) wrongly returned zero rows for every record assigned directly to that department. Fixed by explicitly unioning `p_org_unit_id` itself into the wrapper's result set; proven by the db-test's own team-a-scoped lead-aging assertion, which failed with exactly this symptom before the fix.
2. **The first draft of all seven `get_dashboard_*` functions was plain `security invoker`, relying on base-table RLS.** This failed with a real `permission denied for table opportunities` the first time the pipeline-summary function ran — `authenticated` has no direct column grant on `value_amount`/`value_currency`/`probability` (and, for quotations, on `approval_status`/`customer_decision`/`is_current`), so an invoker-mode function cannot read those columns at all, masked or not, exactly reproducing `COM-147`'s own already-documented lesson for `app.opportunities_directory`. Fixed by switching every function to `security definer` with its own explicit, re-stated `app.can_access_record(...)` filter — full detail in §3.1 item 2.
3. **A db-test fixture value collision with `scripts/db-tests/commercial-margin-calculation.sql`'s own unscoped `where margin_pct = 16.67` lookup query** — that pre-existing file finds its own test row by value rather than by a known id/tenant, and this checkpoint's own second margin calculation happened to also compute exactly `16.67%`, since every db-tests file shares one disposable database across the whole `pnpm run db:test` run. The other file's own query silently picked up this checkpoint's row from a different tenant, then failed with `insufficient_authority ... no_active_assignment` when acting as an actor who has no role in that foreign tenant. Not a defect in this checkpoint's own migration or db-test logic (`commercial-margin-calculation.sql` is unmodified, already `VERIFIED`, out of this checkpoint's scope to alter) — fixed by choosing a different, non-colliding sell amount (16,000,000 instead of 12,000,000 against the same 10,000,000 cost) so this checkpoint's own second calculation lands on `37.50%` instead, with the collision risk and the specific colliding value both disclosed directly in the fixture's own comment for the next agent's benefit.

Zero Critical/High-severity issue remains open. Zero regression to any prior capability (full `db:test`/`test` re-run, all green, `db:test` re-run twice for determinism).
