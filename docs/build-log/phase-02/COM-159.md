## 3. Implementation

### 3.1 Scope boundaries (disclosed, migration header)

1. **Every report reuses a COM-158 `app.get_dashboard_*` function as its one query engine, verbatim** — this migration adds zero new aggregation SQL. Of Prompt 159 §4's ten named report subjects, the seven COM-158's dashboard already computes are implemented (aging, activity, pipeline, quote SLA, margin, win-loss, forecast); conversion/costing/pricing have no existing governed query to reuse and are a disclosed, out-of-scope gap.
2. **`app.report_types` is a Supreme-registered, code-shipped catalogue** (mirrors `app.document_types`) — reports are a product feature, not tenant-authored config, so the seven rows are seeded directly by this migration rather than routed through the Configuration Engine's tenant-publish flow.
3. **`app.report_runs` is the one audit/bookkeeping table** for both `preview` (synchronous) and `export` (asynchronous, via `app.enqueue_job`'s real `report_generation` job type). No live worker processes a `report_generation` job anywhere in this repository — an export therefore reaches `status='queued'` and stops there in this environment; `report_runs.file_id` is the real, provable target shape a future worker would populate, wired to `PLT-128`'s existing file/signed-download engine unchanged.
4. **Export requires the real, previously-unused `COM:Export` permission**, already present in the original catalogue — distinct from ordinary preview, which needs no gate beyond what the underlying `app.get_dashboard_*` function already enforces.
5. **Formula-injection protection is a pure, unit-tested cell-sanitization function** at the service layer (`server/policies/csv-export-sanitize.ts`) — not provable end-to-end against a real generated file, since no live export pipeline exists to generate one.
6. **`app.retire_report_type`** is the "retire unsafe exports" mechanism at the definition level: Supreme-only, and both `record_report_run`/`enqueue_report_export` refuse a retired code.

### 3.2 Schema — `supabase/migrations/20260724330000_create_commercial_reports.sql`

`app.report_types` (7 seeded rows, `code`/`name`/`description`/`source_function`/`version`/`status`/`registered_by`), `app.register_report_type`/`app.retire_report_type` (Supreme-only, idempotent registration mirroring `app.register_document_type`). `app.report_runs` (`run_type` preview/export, `status` queued/running/completed/failed, `parameters` jsonb, `row_count`, `masked_columns text[]`, `job_id`/`file_id` FKs, `requested_by_auth_user_id`), tenant-wide RLS (mirrors `app.margin_rule_versions`/`app.accounts`' own "management visibility, not per-owner privacy" precedent). `app.record_report_run` (tenant-membership + active-report-type gated, records a preview run's self-reported `row_count`/`masked_columns`, audits). `app.enqueue_report_export` (`COM:Export`-gated, calls `app.enqueue_job('report_generation', ...)` unchanged, records the linking `status='queued'` run, audits).

### 3.3 Service layer and UI

`server/contracts/report/report.ts` (schemas/parsers, `ReportParametersSchema` mirroring the dashboard's own filter shape). `server/queries/report.ts` (catalogue + run-history reads). `server/mutations/report.ts` (`recordReportRun`/`enqueueReportExport` RPC wrappers with error classification). `server/policies/csv-export-sanitize.ts` (`sanitizeCsvCell`/`quoteCsvField`/`rowToSafeCsvLine`/`rowsToSafeCsv` — real, OWASP-pattern CSV/formula-injection guard, pure and fully unit-tested even though no live pipeline calls it yet).

UI: new `commercial/reports/` catalogue (report cards + tenant-wide run history) and `commercial/reports/[reportCode]/` detail page — runs the report's own dashboard query via a thin dispatcher (`run-report.ts`, one `switch` over `sourceFunction`, no re-implemented aggregation), records the preview evidence, renders a generic table (every column the underlying query returns, including its own `*Masked` flags, so a masked figure reads as an explicit value rather than a silently blank cell), an export-request form (`COM:Export`-gated server action), and its own run history. ## 8. Errors / recovery / risks / issues

Three real defects found and fixed during authoring:

1. **Duplicate permission insert** — the migration's first draft tried to `insert` a fresh `('Export', 'COM', ...)` permission row, but `COM:Export` was already seeded in the original `PLT-111` catalogue (`category='standard'`, `protected=false`), just never consumed by any Commercial capability. Caught immediately by a real unique-constraint violation on `db:test`; fixed by removing the insert and reusing the existing row, correcting the migration's own header comment which had incorrectly assumed it would be a fresh, protected permission.
2. **Wrong field name in a db-test assertion** (`v_first.id`/`v_second.id`) — `app.report_types` has no `id` column at all, its primary key is `code`. Fixed by comparing `.code` instead.
3. **Wrong audit column name** (`entity_id`) — `app.audit_logs`'s actual column is `resource_id`. Fixed the db-test's own query.

Zero Critical/High-severity issue remains open. Zero regression to any prior capability.
