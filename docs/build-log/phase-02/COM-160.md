## 3. Implementation

### 3.1 Scope boundaries (disclosed, migration header)

1. **Every payload field is a reference to, or verbatim snapshot of, an already-canonical Commercial source** — customer identity from `app.quotations.customer_snapshot` (the pinned snapshot the customer actually accepted, never re-read from `app.accounts`), cargo/service from `app.opportunities.requirements`, pricing from `app.quotations`/`app.quotation_lines`'s own real totals, acceptance from `app.quotation_customer_decisions`, the account from `app.account_conversions`, the contract (if any) from `app.customer_contracts.source_quotation_id`, the credit signal (if any) from the account's most recent `app.credit_check_snapshots` row — **outcome/checked_at only, never a dollar limit**, sidestepping fine-grained masking inside the credit section entirely.
2. **Idempotency key is `(tenant_id, quotation_id, purpose)`** — one accepted quote/version can never create a duplicate downstream outcome.
3. **`app.prepare_job_order_handoff` is synchronous and deterministic, not a queued job** — every source is already-live Commercial data with no external dependency; a precondition failure raises a named exception and creates no row at all, safely retryable once fixed. `downstream_reference`/`delivered_at` are the real, structurally-ready columns a future Phase 3 Operations consumer would populate — both stay null in this environment, disclosed.
4. **`payload`/`payload_hash` are masked wholesale**, not per-key, behind `COM:View selling price` via `app.job_order_handoffs_directory` — plus, since `prepare_job_order_handoff` itself is gated only on `COM:Edit` (not `COM:View selling price`), it also masks its own *returned* payload/payload_hash per-caller directly in the function body (found and fixed during authoring — see §8).

### 3.2 Schema — `supabase/migrations/20260724340000_create_commercial_job_order_lineage.sql`

`app.job_order_handoffs` (one immutable row per accepted quotation; `status` prepared/delivered; `downstream_reference`/`delivered_at` real, unpopulated placeholders). `app.build_job_order_draft_payload` (deterministic assembly, `security definer` from the start — the `COM-158` column-privilege lesson applied proactively, not rediscovered a third time). `app.prepare_job_order_handoff` (`COM:Edit`-gated, re-validates current/submitted/approved/accepted/converted fresh on every call, idempotent on retry, masks its own output per-caller). `app.job_order_handoffs_directory` (field-masked projection, mirrors `app.quotations_directory`'s own `security_invoker=false`-required-for-masking shape).

### 3.3 Service layer and UI

## 8. Errors / recovery / risks / issues

One real defect found and fixed during authoring, before any db-test was written to prove it: **`app.prepare_job_order_handoff`'s first draft returned the raw, unmasked `app.job_order_handoffs` row directly**, but the function is gated only on `COM:Edit` — an actor who can prepare a handoff but lacks `COM:View selling price` would have seen real pricing through the RPC's own return value even though `app.job_order_handoffs_directory` would correctly mask the same row on a subsequent read. Caught by comparing against `app.check_customer_credit`'s (`COM-157`) own established "mask the function's own output" precedent before writing the db-test, not by a failing assertion — fixed by nulling `payload`/`payload_hash` on both the idempotent-retry return path and the fresh-insert return path whenever the calling actor lacks `COM:View selling price`, proven directly by a dedicated `editor` role/user in the db-test fixture. Zero Critical/High-severity issue remains open. Zero regression to any prior capability.
