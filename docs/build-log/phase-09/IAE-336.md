# IAE-336 — Integration Hub

**Prompt ID:** `CG-S14-IAE-008` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/336_INTEGRATION_HUB_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `VERIFIED`** (2026-08-21 — second and LAST prompt of Batch 2, Tier A/B self-reviewed and gate-verified individually at commit; `VERIFIED` as of Batch 2's own Tier C review close — see §13 — migration `20260803030000_harden_intelligence_batch2_tier_c_review_fixes.sql`, independently re-verified by the orchestrating session against a fresh disposable database and the full gate suite)

## 1. What this checkpoint builds

IAE-336 is Batch 2's second and last capability: a governed catalog/credential/health/ownership layer for case-by-case third-party adapters (`ADR-0025` Part C, ratifying `RPD-038`'s "no generic provider abstraction" against Prompt 336's own text). It never implements a single third-party protocol call — only the adapter registry, a tenant's own connection to one adapter, a fully isolated credential store, and a real health-check history with an auto-disable threshold.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260803020000_create_intelligence_integration_hub.sql`, 8 numbered decisions). Summary:

1. **Governance layer only** — catalog + connection + isolated credential store + health history, never a protocol implementation, per `ADR-0025` Part C's own already-ratified reading. Prompts 342-346 remain case-by-case adapters that register themselves into this catalog (a future per-adapter task, disclosed not built here).
2. **Module code `INTHUB`, already seeded by `IAE-007`.** No new `app.entitlement_modules`/`app.permissions` row needed — `INTHUB:Configure`/`INTHUB:View` are reused directly.
3. **The credential store is intentionally STRONGER isolation than the closest pre-existing precedent, not a copy of it.** `app.third_party_provider_connections.webhook_secret_value` stores a raw secret in a table `authenticated` already holds `select` on — its own comment claims "zero authenticated/anon grant" but the migration's own grant statement contradicts it, a pre-existing, out-of-scope condition disclosed here rather than fixed. This migration instead puts the raw credential in its own separate table (`app.integration_connection_credentials`), RLS-enabled with ZERO policies and ZERO grant to `authenticated`/`anon` at all — a raw `select("*")` on `app.integration_connections` can structurally never leak it, because it is not a column of that table.
4. **Health is a real, queryable append-only history** (`app.integration_health_checks`), not only a mutable snapshot. Auto-disable at 10 consecutive failures mirrors `app.webhook_endpoints`'s own already-ratified `ADR-0011` threshold. `record_integration_health_check` is the caller-supplied-result "Test connection" UI action; an automated live poller is disclosed `NOT_RUN`, the same standing condition every prior job-queue/webhook-delivery capability already discloses.
5. **Disabling is a real, checkable state** (`app.check_integration_connection_active`) — no adapter beyond the pre-existing, separate GPS connection table calls it yet (disclosed), but the guard itself is real and proven live.
6. **`app.integration_adapters` is a registry, not a fixed CHECK enum**, mirroring `app.config_types`/`app.notification_types`/`app.webhook_event_types`. **Self-caught correction, before commit:** the repository-wide `rbac-enforcement.sql` sweep (ATW-032/ISS-2026-032) caught `register_integration_adapter` granted to `authenticated` while its own `is_supreme_admin(p_actor_auth_user_id)` check validates the CLAIMED actor, never the calling session. Fixed by granting `service_role` only, matching every prior registry-registration function's own identical grant exactly.
7. **Owner/runbook linkage is a genuinely new primitive** — no prior migration carries an accountable-owner or runbook-URL column on any operational resource (confirmed by grep before writing). `owner_team`/`owner_email`/`runbook_url` are plain, loosely-validated text columns.
8. **`customer_user`-layer/C-05 discipline applied proactively**, mirroring `IAE-007`'s own identical discipline.

## 5. Schema

`app.integration_adapters`: `code` PK, `name`, `category`, `owner_primitive_code`, `registered_by`, `created_at`.

`app.integration_connections`: `id, tenant_id, adapter_code (FK), name, environment(sandbox/production), status(active/disabled/testing), owner_team, owner_email, runbook_url, config jsonb, consecutive_failure_count, last_health_check_at, last_health_status, auto_disabled_at, disabled_reason, record_version, ...`. Unique `(tenant_id, adapter_code, environment)`.

`app.integration_connection_credentials`: `connection_id` PK (FK), `credential_value`, `created_by_auth_user_id`, `created_at`, `rotated_at`. RLS enabled, zero policies, zero grant to `authenticated`/`anon`.

`app.integration_health_checks`: `id, connection_id (FK), status(healthy/unhealthy), detail, checked_by, checked_at`, append-only.

## 6. RLS and grants

`integration_adapters`: global, non-sensitive catalog, direct `select` to `authenticated`. `integration_connections`/`integration_health_checks`: tenant-scoped `select` excluding the `customer_user` layer. `integration_connection_credentials`: RLS enabled, zero policies, zero grant of any kind to `authenticated`/`anon` — only a `SECURITY DEFINER` function (running as its owner) can ever touch it. Live-verified in `scripts/db-tests/integration-hub.sql` via a genuine forged-session `SELECT` attempt against the credentials table, not merely an RPC-level check.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **Credential isolation is real, not merely documented** — a live forged session (`request.jwt.claims` + `set role authenticated`) as a real, active tenant member gets a genuine `insufficient_privilege` querying `app.integration_connection_credentials` directly, despite that same session correctly seeing its own tenant's `app.integration_connections` row. Confirmed structurally too: `information_schema.columns` shows zero credential-shaped column on `app.integration_connections` itself.
2. **The self-caught grant gap was real** — the repository-wide sweep failed the full `db:test` run naming `register_integration_adapter` by name before the fix; re-run clean after granting `service_role` only.
3. **Auto-disable threshold is exact** — 10 consecutive `unhealthy` checks flips a real connection to `disabled` with a real `auto_disabled_at`/`disabled_reason`; the 11-row health-check history (1 healthy + 10 unhealthy) survives the disable untouched.
4. **Disabling never deletes history** — health-check row count is identical immediately before and after a manual disable.
5. **Re-activation resets the failure counter** — a manually re-enabled connection's `consecutive_failure_count` returns to 0 and `app.check_integration_connection_active` reports it active again.
6. **Cross-tenant isolation** — a tenant-2 actor with zero relationship to tenant-1's own connection gets the same `integration_connection_not_found` a missing id would produce.
7. **Credential rotation is real** — the stored `credential_value` genuinely changes to the new supplied value (confirmed by direct query), and is never returned by any RPC or captured in any audit event.
8. **Idempotent adapter registration** — a second `register_integration_adapter` call with different name/category returns the ORIGINAL row, never silently overwriting it.
