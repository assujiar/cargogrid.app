## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260805010000_create_intelligence_email_whatsapp_sms_integrations.sql`, 10 numbered decisions). Summary:

1. **Extends `app.notifications`/`app.notification_delivery_attempts` (PLT-127), never a fourth delivery-attempt table shape** — PLT-127's own header disclosed exactly this gap; `whatsapp`/`sms` are additively widened into the existing channel CHECK constraints and `app.validate_notification_template`'s own allowlist.
2. **`app.queue_notification` is extended to bridge into the real `app.jobs` queue**, reusing the already-registered-but-dormant `notification_batch` job type (confirmed live by direct repository-wide grep before writing this migration: zero real producer/consumer anywhere) — no job-type-registry widening needed.
3. **Self-caught, proactively fixed**: `app.queue_notification`'s own pre-existing idempotency check was an unlocked select-then-insert — exactly the race class Batch 3's own Tier C review found and fixed in `app.queue_webhook_delivery`/`app.register_n8n_allowlisted_action`. Applied proactively here via a single atomic `INSERT ... ON CONFLICT DO NOTHING`, before this class of bug could be independently rediscovered.
4. **Provider credentials reuse `app.integration_connections`/`app.integration_connection_credentials` (IAE-336) directly.** Three adapters seeded at migration-apply time: `email_smtp`, `whatsapp_business`, `sms_gateway`, category `'communication'`.
5. **`app.notification_contact_addresses` is a genuinely new primitive**, disclosed as net-new — no phone-number field exists anywhere in this repository's identity model (confirmed by direct grep); email already has a canonical, verified address at `auth.users.email`. Self-service by default, mirroring `app.notification_preferences`'s own identical authority shape.
6. **Cost metering (`RPD-028`) is genuinely new** — confirmed absent repository-wide. `app.record_notification_delivery_attempt` extended with trailing DEFAULT-valued parameters (every existing call site remains valid unchanged); `app.compute_provider_billed_amount` is the one function that ever computes the +20% markup.
7. **The real outbound worker is channel-branching, not channel-generic**, per `RPD-038`/`ADR-0025` Part C's "no generic provider abstraction" ruling — the claim/dispatch/report loop is shared queue plumbing (the same shape any `app.jobs` consumer needs); the actual request shape per provider (`dispatchEmail`/`dispatchWhatsApp`/`dispatchSms`) is a distinct, named function.
8. **The Batch 3 Tier C SSRF lesson is reused proactively.** This worker is the SECOND real outbound HTTP client in this repository dispatching to a tenant-configured URL — `lib/webhooks/ssrf-guard.server.ts`'s own `checkWebhookDispatchUrlIsSafe` is reused directly (already channel-agnostic), applying the exact lesson Batch 3's own Tier C review had to catch live for IAE-012.
9. **`INTHUB:Configure`/`INTHUB:View` (already seeded by IAE-007) govern connection setup** — reused directly via IAE-336's own `app.create_integration_connection`; no new `app.entitlement_modules`/`app.permissions` row needed.
10. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public;`.

## 13. Merged Batch 4 Tier C review — findings and fixes against this capability

The merged Batch 4's own mandatory Tier C review (4 parallel adversarial lenses: spec-compliance; security/RLS/tenant, live-tested; correctness/concurrency, live-tested; cross-prompt integration) ran against all six independently-built capabilities together on 2026-08-21, closed by one bounded fix migration (`supabase/migrations/20260805070000_harden_intelligence_batch4_tier_c_review_fixes.sql`) plus targeted TypeScript fixes, independently re-verified by the orchestrating session. Full cross-capability findings/fix summary lives in `docs/build-log/phase-09/00_EXECUTION_INDEX.md` §14; this section records only what concerns IAE-014 specifically.

- **[Medium, fixed] `app.record_notification_delivery_attempt`'s own `attempt_number` computation was an unlocked read-then-insert.** The correctness lens live-reproduced two of eight concurrent callers hitting a raw `23505` on `notification_delivery_attempts_unique`, with the real provider cost of the losing attempt silently lost. Fixed by `FOR UPDATE`-locking the notification row before computing `attempt_number`, closing the race at the same lock granularity every other per-row concurrency fix in this repository already uses.
- **[Medium, fixed] The same function had no terminal-state guard at all.** Live-reproduced: an opted-out, `skipped` notification could be flipped to `sent` and billed for a delivery that consent explicitly forbade; a terminal `sent` notification could likewise be flipped back to `failed` indefinitely. Now refuses a further attempt when the notification is already `skipped` or `sent` (deliberately NOT `failed`, since the job queue's own retry loop legitimately calls this again for a subsequent attempt).
- **[Low, fixed] `app.set_notification_contact_address` never checked the TARGET identity held active membership in the tenant.** The security lens live-reproduced an actor planting a contact-address row for a tenant they were not (yet, or no longer) a member of — bounded today (the row can't be delivered to until membership exists) but a real gap. Now requires active membership before writing, mirroring `app.queue_notification`'s own recipient-membership check.
- **[Low, fixed] `app.notification_contact_addresses`' own RLS SELECT policy had no tenant-membership predicate and no staff read path.** Live-reproduced: an owner saw their own row across every tenant regardless of membership; a tenant's own support-grant authority, already able to WRITE these rows on a user's behalf, had zero read path to them. Fixed to require active tenant membership on read, plus a support-grant/Supreme read term. This fix needed one further correction, self-caught by the repository-wide `rbac-enforcement.sql` sweep (ATW-032/ISS-2026-010): a bare `has_active_tenant_membership` predicate in an RLS policy must always also exclude the `customer_user` layer — added via `app.actor_holds_customer_user_layer`.
- **Disclosed, not fixed — real future scope, not a defect.** The spec-compliance lens found no tenant-facing read path exposes `billed_amount`/cost evidence at all (`app.notification_delivery_attempts` has no `list_*_for_tenant` RPC, unlike every sibling capability in this batch) — RPD-028's "customer-visible metering" business rule is computed correctly but not yet reachable by any tenant actor. A real, disclosed gap for a future checkpoint, not addressed in this bounded Tier C pass.
