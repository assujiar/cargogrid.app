# IAE-357 — Advanced Audit and Impersonation

**Prompt ID:** `CG-S14-IAE-029` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/357_ADVANCED_AUDIT_IMPERSONATION_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; fourth capability of Group 7, "Enterprise Security and Governance", Prompts 354-359 — reaches `VERIFIED` only at that group's own Tier C review).

## 1. What this checkpoint builds

Enterprise audit search (multi-dimension filtering, genuinely absent until now), a real async/expiring audit export, and a queryable link between an audit event and the specific support/impersonation session it occurred under. Depends on the already-mature `app.audit_logs`/`app.capture_audit_event` (`PLT-116`) and `app.support_access_grants` (`PLT-115`) primitives, widened rather than duplicated.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260807300000_create_intelligence_advanced_audit_impersonation.sql`). Summary:

1. **Two real, disclosed gaps against Prompt 357's own text are what this checkpoint actually closes**, confirmed by direct code read before writing anything: (a) `app.query_audit_logs`/`app.export_audit_logs` support pagination ONLY — no filter by actor/action/resource_type/result/date-range exists anywhere; `app.search_audit_logs` is the real "enterprise audit search" this repository has never had. (b) `app.export_audit_logs` is a plain synchronous `RETURNS SETOF` call — not "async and expiring" as Prompt 357 §24's own business rule requires; `app.audit_export_requests` + `app.request_audit_export`/`app.record_audit_export_outcome`/`app.get_audit_export` is the real async, expiring export, composing the existing `app.jobs` durable queue exactly like every prior Phase-9 async capability.
2. **Additive widening, never a rewrite, of two pre-existing `PLT-116` primitives**: `app.audit_logs` gains one new nullable column (`support_access_grant_id`); `app.capture_audit_event` gains one new trailing optional parameter (`p_support_access_grant_id default null`) — the real, queryable link between an audit event and the specific impersonation/support session that produced it.
3. **Reuses the `SEC` entitlement module** for the two genuinely new write actions (export request/record); every READ path reuses `app.is_support_grant_authority` UNCHANGED — audit read access does not become easier or harder than it already was.
4. **`app.record_audit_export_outcome`'s own final state transition applies Group 6's own hard-won Tier C lesson proactively**: `UPDATE ... WHERE status IN ('pending','processing')`, atomic, with a not-found reconciliation branch — never repeat the "unlocked read-then-write outcome recorder" defect class a fifth time.
5. **Never claim tamper-proof/immutable against Supreme Admin** (`RPD-022`) — `app.supreme_admin_mutate_audit_log`/`app.supreme_admin_delete_audit_log` are untouched.
6. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement.
7. Per the standing convention since `PLT-118`: explicit, redundant `revoke execute on all functions in schema app from public`.

## 7. Tier B — recurring defect taxonomy self-check

- **C-12/C-13, C-05, ERR-2026-004** — applied proactively from the first draft.
- **Self-caught, real, live-reproduced defect during migration authoring, before any commit:** `CREATE OR REPLACE FUNCTION` does NOT replace a function whose own declared parameter COUNT differs from the existing one, even when every added parameter carries a default — it silently creates a SECOND, overloaded function instead. Caught immediately on the first migration-apply attempt ("function name app.capture_audit_event is not unique" when the file's own `comment on function` statement became ambiguous). This is the same class of gotcha `IAE-011` first found for a widened `RETURNS TABLE` clause, rediscovered here for a widened parameter LIST. Fixed with an explicit `DROP FUNCTION app.capture_audit_event(<original 11-arg signature>)` before `CREATE FUNCTION` (not `CREATE OR REPLACE`), with the original `service_role`-only grant reissued explicitly (a dropped function's grants are not inherited by a new one).
- **Self-caught wrong RPC call signatures on first attempt**: `app.enqueue_job` (8 required positional args: tenant/type/payload/priority/idempotency-key/max-attempts/actor/label) was first called with a made-up 3-arg shape; caught immediately via `grep` against a real call site before the migration was ever applied.
- **The most significant finding: two real, live cross-file regressions, caught only by running the FULL `bash scripts/db-tests/run.sh` suite** (not merely this capability's own standalone file) — see §10 for full detail. This is exactly the class of regression IAE-012's own build log first disclosed as only detectable this way, and the reason every capability since has been expected to run the full suite before closing, not just its own file.
  1. **Root cause `IAE-026`, not this checkpoint**: `IAE-026`'s own new, deliberately-`anon`-granted `app.resolve_enterprise_idp_by_email_domain` (a legitimate, already-reviewed design choice) silently broke six pre-existing files' own repository-wide "anon-grant count must equal exactly 9" drift gates two capabilities ago in this same batch, undetected because Group 7 had not yet had its own full-suite run until this checkpoint. Fixed in all six files (9 → 10), disclosed against `IAE-026` as the true root cause.
  2. **Root cause this checkpoint's own new `audit_export` job type, caught in two separate places**: `ATW-031`/`ISS-2026-012`'s own "job_type has ONE source of truth" drift gate (a db-test) caught that `app.generic_job_types()`'s widening was never mirrored into `GENERIC_JOB_TYPES` (nor its own test's hardcoded literal, nor `background-job.sql`'s own `v_ts_mirror` literal) — fixed in all three files. ## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`app.capture_audit_event` backward compatibility**: a plain, pre-existing-shape 11-arg call still works and leaves `support_access_grant_id` null; a 12-arg call with a real `app.support_access_grants` id populates it correctly.
2. **`app.list_audit_logs_for_support_session`**: returns exactly the session-linked events (2 real ones captured), chronological oldest-first, excludes a genuinely unrelated event with no grant id; a non-authority actor is rejected.
3. **`app.search_audit_logs`'s full filter matrix**: filtering by action alone, by action+resource_type+result together, and a deliberately non-matching result filter (proving AND semantics, not OR) all produce the exactly-correct row counts against real captured events; an `occurred_after` filter set in the future correctly excludes everything; an invalid result-filter value is rejected (`audit_search_invalid_result_filter`); a non-authority actor is rejected.
4. **`app.audit_export_requests` full lifecycle**: a non-authority actor is rejected from requesting an export; a real request creates a genuinely `pending` row AND a real, matching `app.jobs` row (`job_type = 'audit_export'`) — verified by a direct read of `app.jobs`, not merely trusting the RPC's own return value; an idempotent replay of the SAME final outcome returns cleanly; a genuinely conflicting second outcome on an already-resolved request is rejected (`audit_export_outcome_already_recorded`), not silently overwritten.
5. **A genuine 2-process concurrent race** against `app.record_audit_export_outcome` (two real, concurrently-launched `psql` processes racing to resolve the SAME pending request to two different final statuses): exactly 1 process won (`ready`), the other received the clean, named `audit_export_outcome_already_recorded` error, and the final row state matched only the legitimate winner — no silent data loss, mirroring the exact proof technique Group 6's own Tier C review established.
6. **`app.get_audit_export`**: a non-authority actor is rejected; a real `ready` request with `expires_at` backdated into the past is lazily flipped to `expired` with `result_payload` cleared on the very next read, never silently served stale.
7. **Cross-tenant isolation**: a tenant-2 admin cannot search tenant-1's own audit trail and cannot request an export of it (`insufficient_privilege`).
8. **RLS default-deny**: a direct `authenticated` `select` on `app.audit_export_requests` is denied at the raw-RLS level.
9. **`anon` holds zero `EXECUTE`** on any of the 5 new functions, nor on the widened `capture_audit_event`.
10. **Both cross-file regressions, live-reproduced and fixed**: the full official `bash scripts/db-tests/run.sh` first halted at `advanced-tms-canonical-telemetry-arbitration.sql:631` with `expected the anon-grant count to be exactly 9 ... found 10` — a real, live consequence of `IAE-026`'s own new deliberately-public `app.resolve_enterprise_idp_by_email_domain` function (a legitimate, already-reviewed design choice, not a defect in `IAE-026` itself) never having been checked against this repository-wide drift gate, since Group 7's own first full-suite run had not yet happened.
