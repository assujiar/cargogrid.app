# IAE-358 — Enterprise Monitoring and Observability

**Prompt ID:** `CG-S14-IAE-030` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/358_ENTERPRISE_MONITORING_OBSERVABILITY_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; fifth capability of Group 7, "Enterprise Security and Governance", Prompts 354-359 — reaches `VERIFIED` only at that group's own Tier C review).

## 1. What this checkpoint builds

Enterprise-grade monitoring and observability: real SLO definitions (tenant-scoped or genuinely platform-wide), an append-only, numeric-only observability signal ledger, real job-queue backlog visibility read directly from `app.jobs`, and a real, deduplicated incident/alert-routing system with a full timeline. This is Prompt 358's own "Reliability" workstream — distinct from 354-357's "Enterprise IAM"/"Enterprise Security" work — the correct fit for a new `MON` entitlement module rather than a forced reuse of `IAM`/`SEC`.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260807400000_create_intelligence_enterprise_monitoring_observability.sql`). Summary:

1. **Genuinely greenfield** — confirmed by direct grep before writing any code (no `slo`/`observability`/`incident`/`alert_route` table or function exists anywhere). No external APM/metrics vendor (Datadog/Prometheus/etc.) is integrated anywhere in this repository, and none is added here — this checkpoint builds the real, internal governance/evidence layer that a future external exporter would read from or write into, the same "structural foundation now, external wiring later, disclosed" posture `IAE-019`'s own AI governance boundary and `IAE-029`'s own audit-export queue composition both already established.
2. **New `MON` entitlement module** (`View`/`Edit`/`Configure`).
3. **`app.observability_signals` stores ONLY a numeric metric value plus an opaque `source_type`/`source_reference` string — never a raw payload** — so "telemetry redacts secrets and personal/financial data" (Prompt 358 §24) is a structural property of the schema itself, not a redaction function bolted on afterward.
4. **Real deduplication, not merely disclosed**: `app.raise_observability_alert` checks for an existing OPEN incident matching the same `(tenant_id, source_type, signal_type)` within the matching `app.alert_routes`' own `dedupe_window_minutes` (falling back to a disclosed 30-minute default with no matching route); a match appends a timeline event instead of opening a second incident for the same ongoing problem — live-verified across three distinct paths: absorbed-within-window, aged-out-of-window (a genuinely new incident opens), and never-matches-a-resolved-incident.
5. **Real, structural tenant isolation**: every tenant-scoped incident/signal carries a real `tenant_id`; a NULL `tenant_id` (a platform-wide, cross-tenant incident, e.g. a shared queue backing up) is Supreme-Admin-only visible, mirroring the "supreme sees everything, no other layer sees across tenants" discipline already established everywhere else in this repository.
6. **`app.compute_job_queue_backlog` reads the REAL `app.jobs` table directly**, backed by real, live data. `app.jobs` is not tenant-scoped in this reading (a job type's backlog spans every tenant's own queued work), so this is a genuinely platform-wide metric — **Supreme-Admin-only**, matching design decision 5's own convention (a fix made before this migration was ever committed — see §13; the function originally shipped with no actor/authority parameter at all).
7. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement.
8. Per the standing convention since `PLT-118`: explicit, redundant `revoke execute on all functions in schema app from public`.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`app.set_slo_definition`**: `MON:View`-only actor rejected; a real upsert on `(tenant_id, service_name, metric_type)` updates the SAME row (`record_version` increments 1→2, not a duplicate row) for BOTH a tenant-scoped key and a platform-wide (`tenant_id` null) one (the latter only after the §13 `UNIQUE NULLS NOT DISTINCT` fix — it silently duplicated before); invalid `metric_type`/`evaluation_window_minutes` rejected; platform-wide (`tenant_id` null) configuration requires Supreme Admin, a mere `tenant_admin` rejected.
2. **`app.record_observability_signal`**: valid `(source_type, signal_type)` combinations persist a numeric-only row; invalid ones rejected, never silently coerced.
3. **`app.compute_job_queue_backlog`**: real rows inserted directly into `app.jobs` (one stale-pending, one fresh-pending, one stale-but-completed, one stale-pending-of-a-different-job-type); only the genuinely stale, pending, matching-job-type row counts; a `tenant_admin` (not Supreme) is rejected.
4. **`app.raise_observability_alert` deduplication, three distinct live-proven paths**: (a) a repeat signal within the matching route's own dedupe window is absorbed as a `duplicate_signal` timeline event on the SAME incident, never a second row; (b) once the existing incident's own `opened_at` is backdated past the window, a repeat signal opens a genuinely NEW incident; (c) once the only matching incident is resolved, an immediate repeat signal opens a genuinely new one — a resolved incident is never matched, even seconds later. A signal with no matching `app.alert_routes` row at all still deduplicates, using the function's own disclosed 30-minute default.
5. **`app.acknowledge_incident`/`app.resolve_incident`**: `MON:View`-only actor rejected for both; `MON:Edit` succeeds; a re-acknowledge or re-resolve on an already-resolved incident is rejected (`incident_not_open`); the full timeline (`opened`, `duplicate_signal`, `acknowledged`, `resolved`) is read back in the correct chronological order.
6. **Platform-wide incidents**: a `tenant_admin` is rejected acknowledging/resolving/listing a `tenant_id`-null incident; Supreme Admin succeeds at all three.
7. **Cross-tenant isolation**: a tenant-2 admin cannot configure/act on/read tenant-1's own SLOs, alert routes, incidents, or incident timelines.
8. **RLS default-deny**: a direct `authenticated` `select` on all five new tables is denied at the raw-RLS level.
9. **`anon` holds zero `EXECUTE`** on any of the 10 new functions, including the two `service_role`-only ingestion/alerting entry points.

## 13. Post-hoc fixes (found during Group 7's own Tier C review)

1. **Missing service layer, and a false build-log claim (HIGH, spec-compliance AND cross-prompt integration lenses, independently):** `server/mutations/enterprise-monitoring.ts` was never actually created despite §3/§11's own original text claiming it was — every one of this migration's 6 mutation RPCs (`set_slo_definition`, `record_observability_signal`, `set_alert_route`, `raise_observability_alert`, `acknowledge_incident`, `resolve_incident`) had zero TypeScript wrapper anywhere in the repository, confirmed via `git log`/`git show --stat` showing the file never existed. `server/contracts/enterprise-monitoring/enterprise-monitoring.test.ts` was also missing, unlike all 5 sibling Group 7 capabilities. Fixed: both files written, following the identical structural pattern every sibling capability's own service layer already uses (`*MutationError` class + `classifyError` helper in mutations; parse-function round-trip + input-schema-rejection tests in contracts). 11/11 and 10/10 new tests pass; `pnpm run typecheck`/`lint` clean. §3/§11 above corrected to describe the real, current file set rather than repeat the original false claim.
2. **`app.raise_observability_alert` dedup check-then-insert race (HIGH, correctness/concurrency lens), live-reproduced:** the dedup logic (`SELECT` an existing open incident, `INSERT` a new one if none found) has no `FOR UPDATE`, no advisory lock, and no unique constraint backing it. 2 concurrent signals for the identical `(tenant, source_type, signal_type)` both created their own incident row instead of exactly 1 — directly contradicting design decision 4's own "real deduplication, not merely disclosed" claim. Fixed: a `pg_advisory_xact_lock` keyed on `(tenant_id, source_type, signal_type)` serializes concurrent callers for the SAME dedup key (never blocks a different key) — the second caller's own `SELECT` now always observes the first caller's already-committed incident before deciding whether to insert its own. Live-reconfirmed: 2 concurrent processes racing the same signal, both return the identical incident id, exactly 1 row.
3. **Platform-wide (`tenant_id IS NULL`) upsert silently duplicates instead of updating (MEDIUM, spec-compliance lens), confirmed live:** `app.slo_definitions_unique`/`app.alert_routes_unique` are plain `UNIQUE (tenant_id, ...)` constraints — standard SQL/PostgreSQL semantics treat two `NULL`s as NOT equal for `ON CONFLICT` matching, so a second `set_slo_definition`/`set_alert_route` call with `tenant_id = NULL` (the platform-wide case both functions explicitly support) never conflicts with the first — it silently inserts a SECOND row rather than updating, contradicting the "real upsert" claim in this file's own §10.1 (now corrected below). Reproduced live before the fix: two calls with identical `(NULL, 'finance-tax-slo', ...)` produced two distinct rows. Fixed using Postgres 15+'s `UNIQUE NULLS NOT DISTINCT`: both constraints changed from `unique (tenant_id, ...)` to `unique nulls not distinct (tenant_id, ...)` — verified this exact construct fixes the behavior in isolation before applying it, then reconfirmed live against the real table: a second `set_slo_definition(null, ...)` call now updates the SAME row (`record_version` increments, no duplicate). §10 below is corrected to describe the real, now-true behavior.

All three fixes independently re-verified: this file's own db-test re-run clean standalone, plus the two live races described above re-run against the fixed migration specifically (not merely re-reading the diff).
