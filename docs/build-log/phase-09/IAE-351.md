**Prompt ID:** `CG-S14-IAE-023` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/351_OPTIMIZATION_ASSISTANCE_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; third capability of Group 6, "Further AI-Assisted Capabilities", Prompts 349-353 — reaches `VERIFIED` only at the group's own Tier C review).

## 1. What this checkpoint builds

Route/dispatch/warehouse-slotting/picking optimization recommendations, human-reviewed and never autonomously executed. Depends on `IAE-019` (`VERIFIED`) exactly as `IAE-020/021/022` already do.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260806200000_create_intelligence_optimization_assistance.sql`, 11 numbered decisions). Summary:

1. **This capability's own write surface never touches ANY existing TMS/WMS domain table — not even in draft form.** Prompt 351 §24's own business rule ("never dispatches, reassigns, moves stock or changes route autonomously") is structurally the strongest of any AI-assisted capability so far — unlike a Commercial quotation or a Ticket (both of which have a genuine existing draft state, per IAE-020/021's own "apply to draft" shape), dispatch/reassignment/stock-movement actions have no equivalent draft precondition in this repository. Rather than fabricate a fake "draft" concept (forbidden by this project's own Definition of Done), this checkpoint's terminal action is `app.acknowledge_optimization_recommendation_applied` — it records that a human asserts they carried out the recommendation through the EXISTING, UNMODIFIED TMS/WMS mechanism, citing the resulting real record as free-text evidence, but never creates or mutates that record itself.
2. **Sensitive fields are masked by role, at the read boundary, recursively.** `app.mask_optimization_sensitive_fields` walks objects and arrays at ANY depth, stripping cost/margin/vendor/rate/price-shaped keys unless the viewer holds `AI:Approve` (reused as the "may see sensitive planning figures" tier, mirroring IAE-021/022's own reuse of `AI:Approve` as an elevation gate for a different purpose each time).
3. **A scenario has no owning business record to scope access against** — tenant + `AI`-module authority is the correct, sufficient gate; no `app.can_access_record` check is fabricated where no owning record exists.
4. **Staleness is an explicit, human- or job-triggered flag, never an automatic timestamp comparison** — `app.mark_optimization_scenario_stale` is the real mechanism; `app.decide_optimization_scenario` refuses a stale scenario.
5. **Human decision recorded separately from the AI's own output** — `app.optimization_scenario_decisions` is a genuinely distinct table/writer; `selected_option_index` is validated against the real length of the governed request's own `output_payload.recommendations` array.
6. AI dispatch reuses `dispatchAiGovernedRequest` (IAE-019) unmodified — `feature_code = 'optimization_assistance'`, `correlation_record_type = 'optimization_scenario'`.
7. No new entitlement module.
8-10. Proactively applied lessons from IAE-020/021/022: `SECURITY DEFINER` + `assert_actor_is_session_identity`; explicit table aliases in `RETURNS TABLE`; `IS DISTINCT FROM` for nullable correlation cross-checks.
11. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public`.

## 7. Tier B — recurring defect taxonomy self-check

- **Self-caught, before commit (one real bug, fixed before this migration was ever applied a second time):** the original `app.mask_optimization_sensitive_fields` only stripped TOP-LEVEL keys of the payload it was given — a real db-test assertion caught live that `output_payload.recommendations[].vendor_rate_ref` (the realistic, nested shape every real optimization output takes) survived completely unmasked, since `vendor_rate_ref` lives inside array elements, never as a top-level key of `output_payload` itself. ## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`request_optimization_scenario`**: `insufficient_authority` for a view-only actor; `optimization_scenario_invalid_scope_type` for an unrecognized scope; idempotent on a retried call, `idempotency_key_conflict` on a conflicting retry.
2. **`record_optimization_scenario_outcome`'s full cross-check chain**: `insufficient_authority`; `optimization_scenario_not_found`; `optimization_scenario_wrong_feature` for a real succeeded `geocode_address` request; `optimization_scenario_correlation_mismatch` for both a null-correlation request and one correlated to a genuinely different scenario; `optimization_scenario_request_tenant_mismatch` for a real tenant2-owned request; `optimization_scenario_request_not_completed` for a still-pending request; a real success with 3 recommendations succeeds; idempotent replay; `optimization_scenario_outcome_already_recorded` on a conflicting replay.
3. **`decide_optimization_scenario`**: `insufficient_authority`; `optimization_scenario_invalid_option_index` for both an out-of-range index and a null index while accepting; `optimization_scenario_option_index_not_allowed` for a non-null index while rejecting; a real accept succeeds; `optimization_scenario_already_decided` on a second decision; `optimization_scenario_stale` refuses a scenario marked stale (`mark_optimization_scenario_stale` itself requiring a non-empty reason).
4. **`acknowledge_optimization_recommendation_applied`**: `optimization_scenario_applied_reference_required` for an empty reference; a real acknowledgement persists with the reference; `optimization_scenario_decision_already_applied` on a second acknowledgement; `optimization_scenario_decision_not_accepted` for a rejected decision.
5. **The masking proof (Tier B self-catch, §7)**: `rep1` (`AI:Approve`) sees the real, unmasked `vendor_rate_ref` in both `input_snapshot` and every nested recommendation; `agent1` (no `AI:Approve`) sees `output_payload_masked = true` with `vendor_rate_ref` stripped from every recommendation AND from `input_snapshot`, while `status`/`confidence_label`/non-sensitive recommendation fields remain fully visible.
6. **Read paths**: a real scenario id under the WRONG (but real, authorized) tenant_id returns zero rows; list respects scope/status filters and rejects an out-of-bounds limit.
7. **`anon` holds zero `EXECUTE`** on any of this checkpoint's 9 functions; both new tables refuse a direct `authenticated` `select` at the grant level.
