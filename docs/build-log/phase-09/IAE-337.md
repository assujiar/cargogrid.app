# IAE-337 — Public API Platform

**Prompt ID:** `CG-S14-IAE-009` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/337_PUBLIC_API_PLATFORM_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — first prompt of Batch 3, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 3's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-009 is Batch 3's first capability: the real REST `/v1` gateway and rate-limit enforcement `ADR-0025` Part A scoped for Prompts 337-339 — extending `PLT-129`'s already-shipped `app.api_keys`/webhook primitives and `PLT-130`'s already-shipped `app.api_logs`/shared contract layer, never minting a parallel key table or a second observability log. Delivers: real, live rate-limit enforcement (Prompt 130's own disclosed `NOT_RUN`), an API version/deprecation registry, the one gateway entrypoint every `/v1` route handler composes, two real REST resources proving the full mechanics end to end, and a developer console (keys, scopes, rate usage, versions, webhook event catalog, request audit).

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260804010000_create_intelligence_public_api_platform.sql`, 10 numbered decisions). Summary:

1. **No new API-key table** — extends `app.api_keys` (`PLT-129`) consumption only, per `ADR-0025` Part A. IAE-010/011's own customer/vendor-scoped keys reuse this exact row shape.
2. **Rate-limit enforcement anchored on `api_key_id`, never a caller-suppliable discriminator alone** — `ISS-2026-034`'s own lesson (an `x-forwarded-for`-derived `client_key` is trivially defeated by varying it per request). A single atomic `insert ... on conflict do update` per (api_key_id, minute-bucketed window) — no explicit row lock needed, live-proven safe under two genuinely concurrent OS processes. A request that will be rejected still increments the counter, matching every other attempts-table in this repository.
3. **`app.api_versions`: a real, Supreme-registered, globally-readable registry** mirroring `app.webhook_event_types`'s own shape — seeded with `v1` (active) in this migration, since versioning genuinely is this capability's own scope (unlike webhook event types, owned by IAE-012).
4. **`app.authenticate_and_authorize_api_request()`: the one gateway entrypoint**, composing `authenticate_api_key()` + `api_key_has_scope()` (both unchanged) + the new rate-limit check + a creator lookup — returns an `outcome` string (`ok`/`unauthenticated`/`forbidden_scope`/`rate_limited`) rather than raising for any of these four routine outcomes, mirroring `app.ingest_driver_mobile_report`'s own established convention.
5. **Downstream actor identity for a dispatched domain RPC call is the presented key's own `created_by_auth_user_id`** — a real, accountable identity with a genuine defense-in-depth property: a later-demoted admin's key starts failing downstream authority re-checks even before explicit revocation, rather than trusting the key's frozen `scopes` forever.
6. **`app.list_webhook_event_types()`/`app.list_api_logs_for_tenant()` fill two small, disclosed read gaps** PLT-129/PLT-130 each left open for a future consumer — not re-derived elsewhere.
7. **GraphQL: disclosed out of scope, not fabricated.** Zero GraphQL dependency/schema/resolver exists anywhere in this repository (confirmed by direct search). REST `/v1` only; the shared contract (`server/contracts/api/api.ts`) a future GraphQL resolver would also consume is reused, not duplicated.
8. **No new job type, no async work of its own** — this capability's REST surface is synchronous request/response only.
9. **Resource allowlist deliberately narrow, disclosed rather than padded** — `GET /v1/status` and `GET /v1/webhook-event-types` prove the full gateway mechanics end to end; IAE-010/011 build the actual idempotent quote/booking/RFQ/capacity mutation resources this gateway's own primitives exist to serve.
10. Per `ERR-2026-004`: this migration carries its own explicit `revoke execute on all functions in schema app from public;` before its final grants.

## 5. Schema

`app.api_key_rate_limit_windows`: `api_key_id (FK), window_start, request_count`. PK `(api_key_id, window_start)`. Zero `authenticated`/`anon` grant of any kind.

`app.api_versions`: `code` PK, `status(active/deprecated/sunset)`, `sunset_at`, `notes`, `registered_by`, `created_at`, `updated_at`. Global, not tenant-scoped.

## 6. RLS and grants

`api_key_rate_limit_windows`: no RLS, zero grant at all (mirrors `app.webhook_deliveries`'/`app.webhook_delivery_attempts`' own established "grant-absence alone is sufficient defense in depth" precedent) — operational rate-limit evidence, no live UI consumer needs raw access. `api_versions`: RLS enabled, `select to authenticated using (true)` — deliberately, globally readable including the `customer_user` layer (mirrors `app.webhook_event_types`' own identical policy shape) since API version status is platform metadata, not tenant data. Live-verified in `scripts/db-tests/public-api-platform.sql` via a genuine forged-session `SELECT` against both tables.

## 7. Tier B — recurring defect taxonomy self-check

- **C-04 (decision on unlocked row)** — not applicable to a single atomic upsert statement (`check_and_increment_api_key_rate_limit`); no separate read-then-decide-then-write sequence exists to race. Live-proven under real two-process concurrency instead (§10).
- **C-05 (permission check after disclosure)** — `list_api_logs_for_tenant` mirrors `list_api_keys_for_tenant`'s own established authority-check shape (Supreme or the target tenant's own active tenant_admin); a cross-tenant caller is rejected with the identical `insufficient_authority`, tested live.
- **C-12/C-13 (`SECURITY DEFINER` authority, actor-identity)** — `authenticate_and_authorize_api_request`/`check_and_increment_api_key_rate_limit` are plain (non-`SECURITY DEFINER`) `service_role`-only functions, matching PLT-129's own "server-mediated only" design; `list_api_logs_for_tenant`/`list_webhook_event_types` are the two `SECURITY DEFINER` reads, both authority-checked (the latter has no in-function check by design, mirroring the underlying table's own broadly-readable RLS policy — never a `SECURITY DEFINER` bypass of a real restriction). **Self-caught correction, before commit:** the repository-wide `rbac-enforcement.sql` sweep (ATW-032/ISS-2026-032) caught `list_api_logs_for_tenant` granted to `authenticated` while taking `p_actor_auth_user_id` without first calling `app.assert_actor_is_session_identity` — any authenticated session could have passed a colleague's (or a real tenant_admin's) UUID and read that tenant's own API request audit trail. Fixed by adding the identical guard `app.list_api_keys_for_tenant`/`app.list_webhook_endpoints_for_tenant` (PLT-129) already carry; a live forged-session regression proving the fix (a real authenticated session claiming a different, genuinely-privileged identity gets `actor_identity_mismatch`) was added to `public-api-platform.sql`.
- **C-19 (uniqueness scope)** — `(api_key_id, window_start)` on the rate-limit table is the exact tuple the upsert targets; `code` PK on `api_versions` is the exact tuple `register_api_version` idempotency checks against.
- **ISS-2026-034-class (rate-limit discriminator)** — applied proactively from the first draft: anchored on `api_key_id`, never `x-forwarded-for`/`client_key` alone.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **Rate-limit enforcement is exact, sequentially** — a `rate_limit_per_minute=3` key allows exactly 3 calls within one minute window, denies the 4th, and `remaining` decrements correctly (2, 1, 0) on each call.
2. **Rate-limit enforcement is exact under REAL two-process concurrency** — a `rate_limit_per_minute=1` key raced by two genuinely concurrent OS processes yields exactly one `allowed=true` and one `allowed=false`, never both true (a lost update) and never both false; the shared window's own `request_count` is exactly 2, proving the atomic upsert loses no increment.
3. **A null `rate_limit_per_minute` is genuinely unlimited** — 20 consecutive calls against an unlimited key all report `allowed=true` with `limit_per_minute`/`remaining` both null.
4. **All four gateway outcomes are real** — `ok` (with the real dispatch identity), `unauthenticated` (bogus key), `forbidden_scope` (real key, wrong scope, no dispatch identity leaked), `rate_limited` — none raises an exception.
5. **The version registry lifecycle is real and audited** — Supreme-only register/status-change, idempotent-by-code register (a repeated call returns the ORIGINAL row unchanged), a `sunset` status without a real `sunset_at` is structurally rejected, a genuinely nonexistent code raises `api_version_not_found`.
6. **`list_api_logs_for_tenant` is authority-gated and cursor-paginated for real** — a plain member and a genuine cross-tenant outsider are both denied with `insufficient_authority`; the real admin sees real seeded rows; cursor pagination (`before`) correctly narrows to only the earlier row.
7. **`app.api_versions` is deliberately, globally readable** — a live forged session as a `customer_user`-layer portal principal (an identity every OTHER tenant-scoped table in this phase deliberately excludes) still sees the real `v1` row via raw RLS, a disclosed, intentional design difference, not an oversight.
8. **`app.api_key_rate_limit_windows` is blocked outright** — the same forged authenticated session gets a genuine `insufficient_privilege` reading it directly.
9. **The self-caught actor-identity gap is real and now closed** — a live forged session, genuinely authenticated as a plain member with no admin authority of its own, claiming to act as the tenant's own real tenant_admin (an identity that WOULD otherwise pass `list_api_logs_for_tenant`'s own authority check) gets `actor_identity_mismatch`, never a silent impersonation.
