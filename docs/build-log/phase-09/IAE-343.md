## 1. What this checkpoint builds

IAE-015's own prompt text asks for two things: "additional approved GPS/telematics provider adapters" through the existing Prompt 226 canonical ingestion architecture, and enterprise maps/geocoding/routing. Direct research before writing any code found the FIRST half already fully solved by the existing, unmodified Phase 5 architecture (`app.register_third_party_provider_connection`, ATW-226E, carries no CHECK enum restricting `provider_code` — any tenant can already register an arbitrary number of distinct providers) — live-proven in this checkpoint's own db-test, not merely asserted. This checkpoint's own real, new deliverable is therefore the SECOND half: enterprise geocoding/routing, a genuinely new, live, synchronous outbound capability (the third real outbound HTTP client in this repository), with real cost metering composing IAE-014's own `app.compute_provider_billed_amount` directly.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260805020000_create_intelligence_maps_gps_telematics_integrations.sql`, 7 numbered decisions). Summary:

1. **"Additional approved GPS/telematics provider adapters" is CONFIRMED ALREADY FULLY SUPPORTED — zero new schema needed, a genuine finding, not a scope cut.** Verified by direct read of `app.third_party_provider_connections` (ATW-226E) before writing any code: `provider_code` carries no CHECK enum; `app.tenant_tracking_source_policies.default_source_priority`'s own CHECK already treats `third_party_platform` as one source class covering every registered provider. `ADR-0025` Part B's own ruling ("keeps its own existing inbound GPS receiver as-is") is honored by changing nothing about ingestion. Live-proven in this checkpoint's own db-test: a brand-new provider_code registers cleanly through the unmodified existing RPC.
2. **Enterprise maps/geocoding/routing is the one genuinely new capability.** Confirmed absent repository-wide by direct grep before writing any code. Geocoding is a live, SYNCHRONOUS outbound call (address in, coordinates out) — structurally different from every queued/retried delivery this session has built so far, so it is NOT modeled as an `app.jobs` consumer. `app.geocode_requests` is the real, bounded adapter interface (mirrors `app.notification_delivery_attempts`/`app.webhook_delivery_attempts`'s own pattern) — an append-only request/response evidence log, not a retry queue.
3. **Provider credentials reuse `app.integration_connections`/`app.integration_connection_credentials` (IAE-336) directly** — one new adapter seeded: `maps_geocoding`, category `'location'`.
4. **Cost metering (`RPD-028`) reuses `app.compute_provider_billed_amount` directly (IAE-014)** — never re-derived.
5. **Trigger authority is instance-level** (`app.check_maps_provider_trigger_authority`: active tenant membership or Supreme), mirroring `app.check_webhook_trigger_authority`/`app.check_notification_trigger_authority`'s own identical shape — looking up an address is a routine operational action, not a configuration one.
6. **The Batch 3/IAE-014 SSRF guard is reused proactively** — the third real outbound HTTP client relying on `lib/webhooks/ssrf-guard.server.ts`.
7. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public;`.
