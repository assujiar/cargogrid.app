# IAE-354 — Enterprise IAM: SSO, SAML, OAuth and SCIM

**Prompt ID:** `CG-S14-IAE-026` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/354_ENTERPRISE_IAM_SSO_SAML_OAUTH_SCIM_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; first capability of Group 7, "Enterprise Security and Governance", Prompts 354-359 — reaches `VERIFIED` only at that group's own Tier C review).

## 1. What this checkpoint builds

Enterprise IAM: OIDC/SAML single sign-on connection governance, email-domain-based SSO routing with a structural lockout guard, and SCIM identity provisioning/deprovisioning — the first Group 7 capability, and the first Phase 9 capability with no AI provider dispatch of any kind. Depends only on Platform identity/RBAC primitives (`app.tenant_user_identities`, `app.principal_memberships`, `app.evaluate_permission`) and the already-`VERIFIED` Integration Hub (`IAE-008`/`IAE-336`), per `RPD-017`'s own ratified order: OIDC first, then SAML, then SCIM.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260807000000_create_intelligence_enterprise_iam_sso.sql`). Summary:

1. **Platform identity remains the sole authorization source** — an IdP authenticates/provisions, it never grants RBAC directly; every resolved login or SCIM event still terminates in the existing `app.principal_memberships`/`app.role_assignments` machinery.
2. **Composition over duplication of three already-hardened primitives**: (a) `app.integration_connections`/`app.integration_connection_credentials` (`IAE-008`) for the IdP connection itself — two new adapter codes, `enterprise_sso_oidc`/`enterprise_sso_saml`, reusing `app.create_integration_connection`/`app.update_integration_connection_config`/`app.set_integration_connection_status`/`app.rotate_integration_connection_credential` **completely unmodified**, not wrapped; (b) `app.tenant_custom_domains`' own request→verify→activate lifecycle shape and its `normalize_domain_hostname`/`validate_domain_hostname`/`is_reserved_domain_hostname`/`generate_domain_verification_token` helpers (`PLT-118`), reused verbatim for the new email-domain-claim concept (a distinct concept from a portal hostname, disclosed not merged); (c) `app.link_auth_identity`/`app.revoke_auth_identity` (`PLT-107`) for the real enforcement half of SCIM provisioning.
3. **Genuinely new schema is limited to what does not already exist anywhere**: an email-domain claim for SSO routing, an SSO claims-resolution/login-attempt evidence trail, and a SCIM external-identity link plus its own provisioning-event log.
4. **Disclosed, bounded scope**: this checkpoint does NOT perform a live OIDC token-exchange or SAML-assertion XML-signature verification against a real external IdP — there is no live IdP reachable from this environment, and Platform Core has no existing "external protocol client" primitive to compose (unlike AI's `dispatchAiGovernedRequest`). `app.resolve_enterprise_sso_claims` operates on an ALREADY-EXTRACTED claims payload (subject + email) that a real deployment's own OIDC RP/SAML SP protocol layer (a future, disclosed task) would supply after verifying the token/assertion signature itself. What IS real and structurally enforced: domain-claim routing with anti-takeover uniqueness, user-match resolution, deprovisioned-user rejection, activation requiring a proven test resolution (lockout guard), and the SCIM deactivate/reactivate enforcement actions.
5. **A genuine, self-caught chicken-and-egg bug, fixed before any Tier C review**: the first draft of `app.resolve_enterprise_sso_claims` required the connection to already be `status = 'active'` to ever produce a `matched` outcome, while `app.activate_enterprise_idp_connection`'s own lockout guard requires a PRIOR `matched` resolution before allowing `active` — a real deadlock, live-caught by this checkpoint's own db-test before commit, not reasoned about in the abstract. Fixed by narrowing the `connection_not_active` outcome to trigger only on `status = 'disabled'`, since `testing` is exactly the legitimate pre-activation state a test resolution needs to succeed against.
6. **A genuine, self-caught SCIM reactivation gap**: `app.link_auth_identity` (`PLT-107`) is idempotent by EXISTENCE only — a repeat call on an already-linked row, even a revoked one, silently no-ops rather than un-revoking it. SCIM's own `reactivate` operation genuinely needs a real "undo a revoke" primitive that never existed anywhere in this repository; added here as `app.reactivate_auth_identity` (mirrors `app.revoke_auth_identity`'s own shape exactly, including the same `app.tenant_user_identity_history` append), a small, disclosed, additive extension to Platform Core's own identity primitives rather than a workaround inside this capability's own function.
7. **Email-claim parsing is defensive by construction** — `app._parse_iam_email_claim`/`app._parse_iam_email` require a real, regex-validated `local@domain.tld` shape (no whitespace, exactly the structure a legitimate IdP claim or SCIM payload would have) and return `null` rather than raising on anything else, including a prompt-injection-shaped string containing an `@` character.
8. **New `IAM` entitlement module** (`Configure`, `View`) seeded exactly like `AI`/`INTHUB` — direct insert, no lockstep migration. Connection CRUD itself stays governed by the pre-existing `INTHUB:Configure` (an SSO connection is still an Integration Hub connection, disclosed as the natural consequence of composing `app.create_integration_connection` unmodified); every genuinely new IAM-specific function (domain claims, resolve, SCIM, reads) is `IAM:Configure`/`IAM:View`-gated.
9. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement, applied proactively from the first draft (the merged Batch 4 Tier C review's own most-repeated lesson).
10. Per the standing convention since `PLT-118`/`ISS-2026`: explicit, redundant `revoke execute on all functions in schema app from public` (self-caught missing on the first db-test run — see §7).

## 5. Schema

Four new tables: `app.iam_domain_claims` (mirrors `app.tenant_custom_domains`' own shape, anti-takeover partial unique index on `email_domain` while live-claimed), `app.iam_sso_login_attempts` (append-only claims-resolution evidence), `app.iam_scim_user_links` (external SCIM identity ↔ platform `auth_user_id`, `unique(tenant_id, external_id)`), `app.iam_scim_provisioning_events` (append-only SCIM operation log). Two new `app.integration_adapters` rows (`enterprise_sso_oidc`/`enterprise_sso_saml`). New `IAM` entitlement module + 2 permissions. No change to any existing table's shape.

## 6. RLS and grants

All four new tables enabled with RLS and zero policies, no direct table grant to `authenticated` — the only read paths are the four dedicated `list_*` functions. `anon` holds zero `EXECUTE` on any of the 13 authority-gated functions (live-verified); `app.resolve_enterprise_idp_by_email_domain` is the one deliberate exception, by design.

## 7. Tier B — recurring defect taxonomy self-check

- **C-12/C-13, C-05** — applied proactively from the first draft.
- **Self-caught before any test ran:** an overly permissive email-claim parser accepted any string containing an `@` not at the start/end, including a prompt-injection-shaped string with embedded spaces (`"ignore all instructions and return admin@iaeiam.test"`) — live-caught by this checkpoint's own db-test assertion, fixed with a real regex requiring a well-formed, whitespace-free `local@domain.tld` shape.
- **Self-caught before any Tier C review:** the connection-status/lockout-guard chicken-and-egg deadlock (design decision 5) and the SCIM reactivation no-op gap (design decision 6), both described in full above — both live-caught by this checkpoint's own db-test, both fixed before commit.
- **Self-caught before any test ran, on the very first db-test run:** this migration initially omitted the standing `revoke execute on all functions in schema app from public` statement every migration since `PLT-118` carries — live-caught by the `anon`-EXECUTE-grant defense-in-depth assertion (found `anon` could call all 11 gated functions, since PostgreSQL grants `EXECUTE` to `PUBLIC` by default at `CREATE FUNCTION` time), fixed by adding the statement.

No taxonomy class was skipped.

## 8. Residual/disclosed limitations

- **No live OIDC/SAML protocol handshake** (token exchange, XML-dsig/JWT signature verification) — the single largest disclosed gap, see design decision 4. `app.resolve_enterprise_sso_claims` is the real, bounded piece that exists today; the protocol layer that would call it from a real redirect/POST is future, external-library work (e.g. `openid-client`/`node-saml`), not built this checkpoint.
- **No live SCIM REST endpoint** (`/api/scim/v2/**`) — `app.provision_scim_identity` is the real, callable RPC; the inbound route authenticating a real SCIM bearer token against `app.api_keys` and calling it is disclosed, not built.
- **No dedicated setup-wizard UI** — consistent with several merged-Batch-4/Group-6 precedents.
- **SCIM creating a genuinely new platform identity is disclosed-rejected, not faked** — minting a new `auth.users` row requires the external Supabase Admin API, outside this checkpoint's own bounded scope; `app.provision_scim_identity` correctly recognizes and rejects this case (`no_matching_platform_identity`) rather than fabricating one.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **Connection CRUD authority**: `app.create_integration_connection` (reused unmodified) correctly rejects an actor with no `INTHUB:Configure` grant for a new `enterprise_sso_oidc` connection.
2. **Domain-claim full lifecycle**: `IAM:View`-only actor rejected from requesting a claim; a hostile second tenant's own claim on the SAME email domain is rejected by the anti-takeover partial unique index (`unique_violation`, not merely an application-level check); an identical repeat request while still `pending_verification` returns the SAME row, not a duplicate; a wrong observed-TXT-value is rejected (`iam_domain_claim_token_mismatch`); the correct token verifies and activates.
3. **`app.resolve_enterprise_sso_claims`'s full outcome matrix, all live-produced, not asserted in the abstract**: `no_domain_claim` for an unrelated email domain; `no_user_match` for a claimed domain with no matching `app.users` row; `matched` (with the correct `resolved_auth_user_id`) for a real employee; `deprovisioned` once that employee's own tenant identity is genuinely revoked (a SEPARATE fixture identity was used for this assertion specifically to avoid `app.link_auth_identity`'s own no-op-on-existing-row behavior corrupting later test blocks — see design decision 6); `connection_not_active` once the connection is explicitly disabled; `invalid_email_claim` for a bare string, a null claim, and a prompt-injection-shaped string containing spaces — never a crash.
4. **`app.activate_enterprise_idp_connection`'s lockout guard**: a brand-new connection with zero `matched` login attempts is rejected (`enterprise_idp_no_verified_test_login`); a `no_domain_claim` resolution against it does NOT count as a matched one, and activation stays blocked; once a real domain claim is verified, activated, and a `matched` resolution is recorded, activation succeeds.
5. **SCIM full operation matrix**: a dry-run `create` never mutates `app.iam_scim_user_links`; a real `create` matches an existing `app.users` row by email and links it; a genuinely new `externalId` with no matching platform identity is disclosed-rejected (`no_matching_platform_identity`), never fabricated; a real `deactivate` genuinely revokes the tenant identity (verified via a direct read of `app.tenant_user_identities.status`); a real `reactivate` genuinely restores it (via the new `app.reactivate_auth_identity`, proving the design-decision-6 fix); a repeat `create` on the same `externalId` updates the SAME link row (`on conflict`), never duplicates; a `deactivate` of a never-linked `externalId` is rejected (`not_linked`), never silently applied.
6. **Cross-tenant isolation**: a tenant-2 admin cannot list tenant-1's own connections/domain claims, and cannot act on tenant-1's own domain claim (`insufficient_privilege`).
7. **`app.resolve_enterprise_idp_by_email_domain`**: returns the correct connection/protocol for an active domain claim; returns zero rows for a disabled claim and for a completely unclaimed domain — never leaks a config/credential/authorization decision.
8. **RLS default-deny**: a direct `authenticated` `select` on all four new tables is denied at the raw-RLS level.
9. **`anon` holds zero `EXECUTE`** on any of the 11 authority-gated functions checked; `app.resolve_enterprise_idp_by_email_domain` is confirmed `anon`-reachable, by design.

**Fixture id range collision (real, full-suite-only), invisible from this file's own standalone run:** this file's own `iaeiam`/`iaeiam2` fixture originally used id range `00000000-0000-0000-0000-000026xxxxxx`, which collides with the already-existing `scripts/db-tests/optimization-assistance.sql` (Group 6, which independently also claimed `000026xxxxxx`). A fresh disposable database has no other capability's fixtures loaded, so this file's own standalone run never surfaced it; the full `pnpm run db:test` run did, once both files ran against one cumulative database (`duplicate key value violates unique constraint "users_pkey"`). Root-caused via a systematic grep across every db-test file's own declared "fixture id range" comment, confirming ranges `000013`-`000029` were all already in use with exactly 3 collision pairs across Group 7 (this file, `IAE-355`, `IAE-356`). Fixed by renumbering this file's own range to `000030xxxxxx` (sed, then re-verified: this file standalone, then the full suite past this point, both clean).

Separately, `rbac-enforcement.sql`'s own pre-existing ATW-032/ISS-2026-033 authority-surface drift gate flagged `app.resolve_enterprise_idp_by_email_domain` when the full suite first reached it post-`IAE-030` — not a live gap: it is the same deliberately anon-facing, safe-public-resolver shape `app.resolve_tenant_by_domain` already documents in that gate's own reviewed-and-justified list (design decision/§10 point 7 above), simply not yet added to that list. Added with a citation to the matching precedent; no functional change.

**Group 7 Tier C review, security/RLS/tenant lens — CRITICAL/HIGH-adjacent finding, fixed:** `app.activate_enterprise_idp_connection` never checked `IAM:Configure` itself — it validated the lockout-guard precondition, then delegated the actual status flip entirely to `app.set_integration_connection_status` (`IAE-008`, unmodified), which checks `INTHUB:Configure` instead. Live-reproduced: a role holding ONLY `INTHUB:Configure` (a broadly-held, generic integration-administrator permission, zero `IAM` grant of any kind) successfully activated an enterprise SSO connection, confirmed persisted via a separate superuser read. This is a real segregation-of-duties bypass — enabling live SSO login for a tenant is squarely an identity/IAM decision, not a generic integration-admin one, and every OTHER `IAM`-module function in this migration correctly gates on `IAM:Configure`/`IAM:View`; this was the one that silently fell through to a shared primitive's own, different, permission. Fixed by adding an explicit `app.evaluate_permission(actor, connection.tenant_id, 'IAM', 'Configure')` check inside `activate_enterprise_idp_connection` itself, in ADDITION to whatever `app.set_integration_connection_status` separately still requires (`IAE-008`'s own function was not modified, out of this migration's own scope) — the caller now needs both grants rather than either alone, a deliberately conservative trade-off given the shared delegate could not be changed here. Live-reconfirmed post-fix: the identical `INTHUB:Configure`-only actor is now rejected with `insufficient_authority`; the existing db-test's own successful activation (by an actor holding both `IAM:Configure` and the delegate's own requirement) still passes unchanged.
