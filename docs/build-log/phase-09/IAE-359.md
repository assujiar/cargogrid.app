# IAE-359 — Data Retention and Archival

**Prompt ID:** `CG-S14-IAE-031` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/359_DATA_RETENTION_ARCHIVAL_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; sixth and final capability of Group 7, "Enterprise Security and Governance", Prompts 354-359 — reaches `VERIFIED` only at that group's own Tier C review).

## 1. What this checkpoint builds

Real, enterprise-grade data retention and archival governance: RPD-025's own class-based retention schedule (finance/tax 10 years, audit/security 7 years, operational 90-day floor), a real legal-hold override mechanism, real dry-run classification, and a real, job-queue-backed archive request flow — closing the gap `docs/build-log/phase-05/guides/privacy-consent-and-retention-guide.md` §3 already disclosed honestly: RPD-025's own retention schedule was ratified at the product/legal level with NO enforcement mechanism anywhere in the repository.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260807500000_create_intelligence_data_retention_archival.sql`). Summary:

1. **Genuinely greenfield** — confirmed by direct grep before writing any code (no `retention`/`legal_hold`/`archive` table or function exists anywhere in `app`).
2. **New `RET` entitlement module** (`View`/`Configure`/`Approve`) — Prompt 359's own workstream is "Governance", distinct from every other Group 7 workstream.
3. **RPD-025's own class-based schedule is the real, hardcoded platform default** (`app.resolve_retention_days`): finance/tax 3650 days, audit/security 2555 days, operational 90 days (the modeled floor — "contract term" itself is a commercial fact this schema does not track anywhere; a tenant's own real total is set via `app.set_retention_policy`'s own override). Backups (RPD-025's fourth class, 35 days) are Supabase/Postgres infrastructure-level, not an application data row this schema owns — disclosed out of scope.
4. **This checkpoint does NOT reach into any other domain's own tables** (Finance GL, HR payroll, audit logs, etc.) to enumerate or delete rows itself — doing so would be exactly the "unrelated domains"/"duplicate source-domain roots" scope creep Prompt 359 §12 forbids. Instead it builds a real, reusable GOVERNANCE primitive any domain-owning capability calls with ITS OWN already-known record identifiers: classify a record against its own declared retention class, and (if genuinely eligible — past its own retention floor AND not under legal hold) enqueue a real `app.jobs` row recording that a domain-owning worker may now proceed. This checkpoint never itself deletes or moves a single byte of another domain's own data — disclosed honestly, the same bounded-scope posture `IAE-030`'s own "no external APM integration" and `IAE-029`'s own audit-export queue composition both already established.
5. **Real, structural enforcement, not merely disclosed**: `app.request_retention_archive` REJECTS (`blocked_within_retention`) a non-dry-run archive request for a record that has not yet reached its own class's retention floor — "deletion/minimization cannot erase required posted Finance, payroll or legal evidence" (Prompt 359 §24) is enforced at the database layer, not left to application-layer discipline.
6. **Legal hold is a REAL, structural override**: `app._is_under_legal_hold` is consulted by `app.request_retention_archive` itself before any job is ever enqueued — an active hold (scoped to one specific record or an entire record class for a tenant) blocks archival unconditionally, even past the retention floor, even for a dry-run's own reported outcome. Placing a hold (`RET:Configure`) is a lower bar than releasing one (`RET:Approve`) — releasing is what allows deletion/archive to proceed, the more consequential action.
7. **"Retention policy versions are auditable"** (Prompt 359 §24) is satisfied via the same `app.capture_audit_event` composition every other "X is auditable" requirement in this repository already uses — no separate, duplicate "policy version" table.
8. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement.
9. Per the standing convention since `PLT-118`: explicit, redundant `revoke execute on all functions in schema app from public`.
10. Widens the standing four-place job_type lockstep (`app.jobs_job_type_check`, `app.generic_job_types()`, `GENERIC_JOB_TYPES`, `IMPORT_EXPORT_JOB_TYPES`) with `retention_archive` — the 26th generic literal (plus import/export) — for the real archive job this checkpoint enqueues, mirroring `IAE-029`'s own `audit_export` precedent exactly.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`app.resolve_retention_days`**: RPD-025's own hardcoded default applies with zero policy rows for all three classes; invalid `record_class` rejected.
2. **`app.set_retention_policy`**: `RET:View`-only actor rejected; a tenant-scoped override wins over the platform default; a real upsert on `(tenant_id, record_class)` updates the SAME row (`record_version` 1→2); invalid class/days rejected; platform-wide (`tenant_id` null) requires Supreme Admin, and a platform override is correctly inherited by a SECOND tenant with no override of its own.
3. **`app.request_legal_hold`/`app.release_legal_hold`**: no-`RET`-grant actor rejected; empty reason rejected; a mismatched scope (table without id) rejected; a whole-class hold and a single-record hold both succeed; release requires `RET:Approve` specifically (`RET:Configure` alone is rejected); a second release on an already-released hold is rejected (`legal_hold_not_active`).
4. **`app.request_retention_archive` dry-run**: NEVER enqueues a real `app.jobs` row (verified by a direct count); an old, unheld record classifies `dry_run_completed`; a too-recent one classifies `blocked_within_retention`.
5. **`app.request_retention_archive` real enforcement, three distinct live-proven paths**: (a) a too-recent record is rejected (`blocked_within_retention`), zero jobs enqueued; (b) a genuinely eligible record is accepted (`pending`) and enqueues exactly one real `app.jobs` row; (c) a record under an active single-record legal hold is rejected (`blocked_legal_hold`) even though it is **4000 days old — far past even the 10-year finance/tax default** — proving the hold overrides age unconditionally, not merely by coincidence of timing.
6. **`app.record_retention_archive_outcome`**: invalid outcome status rejected; an idempotent replay of the SAME outcome (`archived`) returns cleanly; a genuinely conflicting second outcome (`failed`) is rejected (`retention_archive_outcome_already_recorded`) — the identical lost-update-guard shape `app.record_audit_export_outcome` (`IAE-029`) already live-proved via a real 2-process concurrent race; not re-run here since the guard logic is byte-for-byte the same pattern, already proven live once this session.
7. **Cross-tenant isolation**: a tenant-2 admin cannot configure policies, place holds, request archives, or read any of tenant-1's own retention policies/legal holds/archive requests.
8. **RLS default-deny**: a direct `authenticated` `select` on all three new tables is denied at the raw-RLS level.

## 13. Post-hoc fix (found before this migration was ever committed, by `scripts/db-tests/rbac-enforcement.sql`'s own pre-existing drift gate)

A full-suite run (this checkpoint's own migration plus every other db-test file in one cumulative database) reached `rbac-enforcement.sql`'s own ATW-032/ISS-2026-033 authority-surface sweep and correctly flagged `app.resolve_retention_days`: it took a bare `p_tenant_id` with no actor/authority parameter at all — the identical shape `IAE-027`'s own `app.is_high_risk_action` shipped with and was fixed for in the same pass (see `IAE-355.md` §13). ## 14. Group 7 Tier C review — findings and fixes

Four real defects found in this migration specifically by the Tier C review, ranging CRITICAL to Medium — all fixed and independently re-verified live before this batch closed.

**1. CRITICAL — legal hold bypassable simply by mislabeling the archive request (security/RLS/tenant lens).** `app._is_under_legal_hold(p_tenant_id, p_record_class, p_source_table, p_source_record_id)` matched a hold only on the CALLER-SUPPLIED `(tenant_id, record_class)` — never independently re-derived from the actual record. Live-reproduced two ways: (a) an active hold placed on a specific record under `record_class='finance_tax'`; a second `request_retention_archive` call for the IDENTICAL `(source_table, source_record_id)` but declaring `record_class='operational'` sailed straight through to `status=pending` with a real `app.jobs` row enqueued for a record actively under legal hold; (b) a SECOND tenant's own legitimately `RET:Configure`-authorized actor named the SAME record id under their own `p_tenant_id`, with the identical result. This directly defeated design decision 6's own claim that legal hold is "a REAL, structural override... blocks archival unconditionally."

Root cause: this checkpoint has no way to independently verify a caller-declared `tenant_id`/`record_class` against the real, external domain table a record actually belongs to (design decision 4's own disclosed, bounded scope) — trusting those claims for a hold that already names the exact record precisely WAS the vulnerability. Fixed: `app._is_under_legal_hold` now matches a specific-record hold on `(source_table, source_record_id)` ALONE, independent of the caller's own `tenant_id`/`record_class` claim; a whole-class hold (no specific record named) still necessarily matches on the caller's own declared `(tenant_id, record_class)`, since there is no specific record to anchor against instead — an unavoidable consequence of this checkpoint's own bounded scope, not a remaining gap of the same kind. Live-reconfirmed post-fix: both reproduction paths above now correctly return `status=blocked_legal_hold`, zero jobs enqueued; the pre-existing, correctly-scoped hold test in this file's own db-test still passes unchanged.

**2. HIGH — `app.request_retention_archive` double-enqueue via a self-defeating idempotency key (correctness/concurrency lens), live-reproduced.** The idempotency key passed to `app.enqueue_job` was `'retention-archive:' || v_request.id`, where `v_request.id` is the id of the row THIS call just inserted — guaranteed unique every time, so it could never actually collide with a concurrent call for the SAME record. No DB-level uniqueness backed `(tenant_id, source_table, source_record_id)` either. 2 concurrent, otherwise-identical, real (`dry_run=false`) requests for the same eligible record both reached `status=pending`, each with its own `app.jobs` row (confirmed via a control test: 5 concurrent `app.enqueue_job` calls with the SAME idempotency key correctly collapsed to 1 job — `enqueue_job` itself is fine; the bug was specifically in how this function constructed its own key). Fixed: a `pg_advisory_xact_lock` keyed on `(tenant_id, source_table, source_record_id)` serializes concurrent callers for the SAME record; an already-`pending` request for that exact record is returned unchanged (a true no-op) rather than creating a second row and a second job. Live-reconfirmed: 2 concurrent processes racing the same record, both return the identical request id, exactly 1 pending row, exactly 1 job.

**3. MEDIUM — `app.legal_holds` has no self-release guard, unlike its sibling break-glass mechanisms in the same batch (correctness/concurrency lens).** `app.mfa_exceptions`/`app.ip_allowlist_bypass_grants` (both `IAE-027`) each have a hard, DB-level `CHECK` constraint AND an explicit app-layer guard forbidding an actor from approving their own request; `app.legal_holds` had neither — a raw SQL insert with `placed_by_auth_user_id = released_by_auth_user_id` succeeded with no violation, and the real RPCs let an actor holding both `RET:Configure` and `RET:Approve` (nothing prevents one role from bundling both) place then release their own hold. This directly undercut design decision 6's own stated rationale ("releasing is the more consequential, separately-authorized action"). Fixed: added `constraint legal_holds_no_self_release check (released_by_auth_user_id is null or released_by_auth_user_id <> placed_by_auth_user_id)` (mirrors `mfa_exceptions_no_self_approval` exactly) plus an explicit, cleanly-named check inside `app.release_legal_hold` itself (`legal_hold_self_release_forbidden`) so the rejection is a real application error, not a raw constraint violation. Live-reconfirmed: the RPC path is rejected with `insufficient_privilege`; a direct raw-SQL bypass attempt is rejected by the CHECK constraint itself.

**4. Platform-wide upsert duplication — shared root cause with `IAE-030`'s own finding (see `IAE-358.md` §13 item 3).** `app.retention_policies_unique` had the identical `UNIQUE (tenant_id, record_class)`-with-NULL-never-matches defect. Fixed identically: `unique nulls not distinct (tenant_id, record_class)`. Live-reconfirmed: a second `set_retention_policy(null, ...)` call now updates the SAME platform-wide row (`record_version` increments) instead of duplicating it.

All four fixes independently re-verified against a fresh disposable database: this file's own db-test standalone (unchanged, still passing), plus each live reproduction above re-run against the fixed migration specifically.
