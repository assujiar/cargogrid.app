# IAE-355 — Enterprise MFA and Session Controls

**Prompt ID:** `CG-S14-IAE-027` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/355_ENTERPRISE_MFA_SESSION_CONTROLS_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; second capability of Group 7, "Enterprise Security and Governance", Prompts 354-359 — reaches `VERIFIED` only at that group's own Tier C review).

## 1. What this checkpoint builds

Enterprise MFA policy and step-up governance, plus session/device tracking and revocation, plus a break-glass MFA-exception recovery flow. This builds the real, previously-`NOT_FOUND` governance/state-machine layer `RPD-023`/`ISS-2026-138` names ("MFA mandatory for privileged roles" per `docs/discovery/06_SECURITY_BASELINE.md`) — see design decision 10/§8 for the precise, honest boundary of what this closes: the gate itself (`app.assert_current_step_up_authorization`) is real and independently correct, but is not yet CALLED by any actual mutation anywhere in this repository, including this migration's own high-risk `SEC:Configure`/`SEC:Approve` functions. Depends only on Platform identity/RBAC primitives and `IAE-026`'s own `IAM` module precedent (a new, sibling `SEC` module, shared across Group 7's own three "Enterprise Security" capabilities).

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260807100000_create_intelligence_enterprise_mfa_session_controls.sql`). Summary:

1. **Real MFA factor enrollment/challenge-verification crypto is Supabase Auth's own native, external infrastructure** — the same "`auth.users` is Supabase-managed" boundary `IAE-026`'s own header established for identity. This checkpoint does NOT fabricate a parallel `app.mfa_factors` table. What IS real and built here: the STEP-UP GOVERNANCE layer — which actions are high-risk, whether a fresh, already-completed MFA verification exists, and a real, composable assertion (`app.assert_current_step_up_authorization`) any future high-risk mutation can call.
2. **New `SEC` entitlement module** (`Configure`/`View`/`Approve`), shared across Group 7's own "Enterprise Security" workstream (355-357), distinct from `IAM` (354, identity federation only), seeded here as its first user.
3. **High-risk actions are a fixed platform-default set** (`app.is_high_risk_action`, e.g. `FIN:Approve`, `IAM:Configure`, `AI:Approve`) **plus a real, tenant-editable additive list** — no separate registry table, a small jsonb list on `app.mfa_tenant_policies` instead.
4. **Session/device tracking is a DECLARED registry, not a shadow of Supabase's own real JWT/refresh-token internals** — revoking it here is a real, persisted signal an application-layer guard can check; actually invalidating a live Supabase JWT requires the external Supabase Admin API, disclosed as not performed by this checkpoint.
5. **"Session revocation propagates to API keys" is real, not merely disclosed**: `app.revoke_all_actor_sessions` also revokes every ACTIVE `app.api_keys` row the target actor themselves created, composing the existing, unmodified `app.revoke_api_key` (`PLT-129`).
6. **MFA exceptions (lost-factor recovery) mirror `app.support_access_grants`' own established break-glass shape** (`PLT-115`): never self-approved (enforced at the CHECK-constraint level, not merely in application code), a real higher-authority approval step, a short expiry, and exactly-once consumption.
7. **A genuine, self-caught bug: persisting a status flip immediately before raising is unreliable.** The first draft of `app.verify_mfa_step_up_challenge` updated a stale challenge to `status = 'expired'` and then raised — but any caller wrapping the call in its own exception handler (the normal, expected shape) runs inside an implicit savepoint, and Postgres rolls back every statement since that savepoint, including this function's own prior `UPDATE`, once the exception propagates. Live-caught by this checkpoint's own db-test (the challenge stayed `pending`, not `expired`, after the caught exception) before any Tier C review. Fixed by NOT persisting the status flip inside the failing call, deferring to a lazy flip on a future read — the same pattern `app.authenticate_api_key` (`PLT-129`) already established for its own past-expiry status handling.
8. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement.
9. Per the standing convention since `PLT-118`: explicit, redundant `revoke execute on all functions in schema app from public`, applied from the first draft this time (the gap `IAE-026` self-caught).

## 8. Residual/disclosed limitations

- **No live MFA factor enrollment/verification UI or crypto** — the single largest disclosed gap, see design decision 1. `app.verify_mfa_step_up_challenge` records that a real, external MFA verification succeeded; it does not perform one itself.
- **No live Supabase JWT/session invalidation** — `app.user_sessions`/`app.revoke_user_session` are a real, persisted signal; actually killing a live token is the external Supabase Admin API's own job, disclosed not built.
- **No dedicated MFA/session admin UI** — consistent with `IAE-026` and several Group-6 precedents.
- **`app.assert_current_step_up_authorization` is not yet called by any mutation anywhere in this repository** (Group 7 Tier C review, spec-compliance lens finding, corrected here rather than left implicit): the gate itself is real, independently correct, and fully live-tested (design decision 7/§10) — but it is a composable primitive with zero live callers today, including this migration's own `set_mfa_tenant_policy`/`revoke_all_actor_sessions`/`approve_mfa_exception` (all `SEC:Configure`/`SEC:Approve`-gated, all classified high-risk by this same migration's own `app.is_high_risk_action`) and `IAE-028`'s `set_ip_allowlist_enforcement_mode`/`approve_ip_allowlist_bypass`. §24's "high-risk actions require current authorization" is therefore a real, tested MECHANISM today, not yet an enforced OUTCOME for any actual action — wiring it into those call sites is real, in-scope follow-up work (not attempted in this Tier C fix pass: it is a genuine behavior change requiring every affected db-test fixture to first request-and-verify a step-up challenge, properly scoped as its own follow-up rather than folded into a review-and-fix pass).

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`app.set_mfa_tenant_policy`**: `SEC:View`-only actor rejected; an out-of-range `step_up_max_age_minutes` (9999) rejected; a real update persists and is read back correctly.
2. **`app.is_high_risk_action`**: platform-default set (`FIN:Approve`, `IAM:Configure`) returns true for ANY tenant, even one with no explicit policy row; a tenant's own additive list only ADDS (a second, unrelated tenant does not inherit the first tenant's own additions — live-verified, not merely asserted safe).
3. **The full step-up state machine**: `mfa_step_up_not_required` for a non-high-risk action; `assert_current_step_up_authorization` is a true no-op for a non-high-risk action (no exception at all) and blocks a high-risk one with zero verified challenges; a different actor cannot verify someone else's own pending challenge (`mfa_step_up_challenge_not_pending`); a second verify attempt on an already-verified challenge is rejected; once verified, the gate passes; **backdating `verified_at` past the tenant's own 20-minute policy window and re-checking correctly re-blocks** (`mfa_step_up_required`, stale session denied); a challenge past its own 10-minute `challenge_expires_at` cannot be verified, and — the design-decision-7 fix's own live proof — remains `pending`, not silently `expired`, after the caught exception.
4. **`app.user_sessions`**: self-revoke always succeeds; a different identity with no `SEC:Configure` is rejected; a different identity WITH `SEC:Configure` (admin1) succeeds; `app.revoke_all_actor_sessions` revokes a genuinely active session AND genuinely flips a real, previously-active `app.api_keys` row (created by the target actor) to `revoked` — verified by a direct read of `app.api_keys.status` before and after, not merely trusting the function's own return value.
5. **`app.mfa_exceptions`**: self-approval is rejected at the CHECK-constraint level (not merely application logic); a genuinely different `SEC:Approve` holder (Supreme Admin) approves successfully; a used exception cannot be consumed twice (`mfa_exception_not_approved`); a separately-requested, approved-but-backdated-to-expired exception cannot be consumed (`mfa_exception_expired`).
6. **Cross-tenant isolation**: a tenant-2 admin cannot list tenant-1's own sessions and cannot configure tenant-1's own MFA policy (`insufficient_privilege`).
7. **RLS default-deny**: a direct `authenticated` `select` on all four new tables is denied at the raw-RLS level.
8. **`anon` holds zero `EXECUTE`** on any of the 15 new functions.

Fixed: `get_or_create_mfa_tenant_policy` was split into an internal-only `app._get_or_create_mfa_tenant_policy(p_tenant_id)` bootstrap primitive (no grant to anyone) plus a new, actor-gated public `app.get_or_create_mfa_tenant_policy(p_tenant_id, p_actor_auth_user_id)` requiring `SEC:View` — `app.set_mfa_tenant_policy`'s own internal bootstrap call was repointed at the private helper (it already independently enforces `SEC:Configure`, so no double-gating risk). `app.is_high_risk_action` (called internally only, by the already actor-scoped `app.assert_current_step_up_authorization`, and not wired into the TS service layer at all) had its `authenticated` grant simply revoked, `service_role` only. Neither function had ever been committed to git before this fix. `scripts/db-tests/enterprise-mfa-session-controls.sql` and `server/queries/enterprise-mfa.ts` were updated to match (new required `actorAuthUserId` parameter, plus new assertions: `rep1`, no `SEC` grant, rejected; `admin2`, a different tenant's own admin, rejected; `admin1`/`viewer1`, both holding `SEC:View`, succeed).
