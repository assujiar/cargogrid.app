# IAE-341 — n8n Integration

**Prompt ID:** `CG-S14-IAE-013` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/341_N8N_INTEGRATION_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — fifth and FINAL prompt of Batch 3, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 3's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-013 builds n8n Integration as a thin governance/labeling layer, consistent with `RPD-012`'s own explicit framing of n8n as "not the primary engine — optional external trigger/consumer only" and with the prompt's own business rule that no tenant-specific backend code is generated for n8n. n8n itself calls the SAME `/api/v1` REST surface (`scripts/db-tests/public-api-platform.sql`) and receives events through the SAME webhook delivery mechanism (`scripts/db-tests/webhook-management.sql`, IAE-012) as any other integration consumer — this checkpoint adds only what those two already-shipped primitives do not: a curated, Supreme-controlled safe-action allowlist (`app.n8n_action_allowlist`), and a named "n8n connector" governance record (`app.n8n_connectors`) that composes `app.create_api_key`/`app.revoke_api_key` (IAE-009) rather than forking them, plus an optional link to an existing webhook endpoint (IAE-012).

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260804050000_create_intelligence_n8n_integration.sql`, 9 numbered decisions). Summary:

1. **`app.n8n_action_allowlist`** — a small, deliberately curated table (`scope text primary key`, format-checked `^[A-Z]+:[A-Za-z ]+$`) naming exactly which `app.permissions` scopes n8n is trusted to hold at all, independent of what any individual tenant admin's own RBAC might otherwise permit. Registration (`app.register_n8n_allowlisted_action`) is Supreme-Admin-only and idempotent by scope; it rejects any scope that is not a real, currently-registered `app.permissions` code (`n8n_scope_not_a_real_permission`), never a free-text label.
2. **Deliberately excludes every Approve/Delete/Override/financial scope from the seed.** Seeded rows: `OPS:View`, `PRC:View`, `TKT:View`, `TKT:Create`, `INTHUB:View` — read/observe access plus the single, narrow "create a ticket" write, nothing that mutates money, approvals, or destructive state. A future Supreme Admin may register more via the RPC; the seed itself is a deliberate, minimal starting posture.
3. **`app.n8n_connectors` is a governance/labeling table, not a new credential mechanism.** `id`, `tenant_id`, `api_key_id` (unique, not null, FK to `app.api_keys`), `webhook_endpoint_id` (nullable FK to `app.webhook_endpoints`), `name`, `created_by_auth_user_id`, timestamps, a `touch` trigger. The connector's own underlying credential IS a plain `app.api_keys` row — no parallel secret store.
4. **`app.create_n8n_connector` composes, never forks, `app.create_api_key`.** Every requested scope must pass BOTH gates: (a) present on `app.n8n_action_allowlist` (checked FIRST — a genuinely fictional or deliberately-excluded scope like `TKT:Delete` is rejected here as `n8n_scope_not_allowlisted` before the actor's own RBAC is even consulted), AND (b) held by the creating actor's own current RBAC, enforced by delegating the actual key creation to the unmodified `app.create_api_key`, which independently raises `insufficient_privilege` if the actor lacks a requested scope. Staff-only (`tenant_admin` or Supreme). An optional `webhook_endpoint_id` must belong to the SAME tenant (`no_data_found` otherwise) — validated via a query qualified as `app.webhook_endpoints.id = p_webhook_endpoint_id and app.webhook_endpoints.tenant_id = p_tenant_id`, proactively avoiding the exact ambiguous-column-reference bug class (the function's own `RETURNS TABLE(..., tenant_id uuid, ...)` clause would otherwise shadow the unqualified `tenant_id` reference) live-caught twice already this session (IAE-011's `create_vendor_api_key`, generalized in `authenticate_and_authorize_api_request`).
5. **`app.revoke_n8n_connector` delegates ENTIRELY to `app.revoke_api_key`, with zero authority logic of its own.** The connector's own `app.n8n_connectors` linking row is never deleted on revocation — it remains as a historical record, exactly mirroring how a revoked `app.api_keys` row is itself never deleted.
6. **`app.list_n8n_connectors_for_tenant`** — staff-only, live-joined with the linked `app.api_keys` (name, key_prefix, scopes, status, rate_limit_per_minute, last_used_at) and, when present, the linked `app.webhook_endpoints` (url, status) rows. `security definer`, `app.assert_actor_is_session_identity` applied from the first draft (ATW-032).
7. **UI reuses IAE-009's existing `RotateApiKeyForm`/`RevokeApiKeyForm` directly against the connector's own `apiKeyId`** — zero new rotate/revoke backend code needed, since a connector's underlying credential is a plain `app.api_keys` row in every case.
8. **No tenant-specific backend code is generated for n8n itself** — n8n workflows call `/api/v1` and receive webhooks exactly like any other external consumer; this checkpoint's own new surface is entirely the allowlist/connector governance layer, not a parallel API.
9. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public;`. Grants: `register_n8n_allowlisted_action`/`create_n8n_connector`/`revoke_n8n_connector` → `service_role` only; `list_n8n_action_allowlist`/`list_n8n_connectors_for_tenant` → `authenticated, service_role`.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`register_n8n_allowlisted_action` is Supreme-only, idempotent by scope, and rejects a fictional permission code** — a non-Supreme actor is denied (`insufficient_privilege`); `FAKE:Nonexistent` is rejected (`n8n_scope_not_a_real_permission`); registering the same real scope twice returns the identical row, not a duplicate; `list_n8n_action_allowlist` reflects the seed plus this block's own live addition and is globally readable.
2. **`create_n8n_connector` requires BOTH allowlist membership AND the creating actor's own current RBAC for every scope, in that order.** A scope that is both allowlisted and held (`OPS:View`, `TKT:Create`) succeeds and returns a real, usable raw key. A scope allowlisted but not held by the actor (`PRC:View`) is denied `insufficient_privilege`. A scope held by the actor but not allowlisted (`INTHUB:Configure`) is denied `n8n_scope_not_allowlisted` — proving the allowlist gate is a genuine, independent ceiling on top of ordinary RBAC, not merely a label. A webhook endpoint belonging to a DIFFERENT tenant cannot be linked (`no_data_found`). A non-admin staff member is denied (`insufficient_privilege`).
3. **`revoke_n8n_connector` delegates to `app.revoke_api_key`** — the underlying key reaches `status='revoked'`; the connector's own linking row survives as a historical record.
4. **`list_n8n_connectors_for_tenant` is scoped to the caller's own tenant**, live-joined with the real (revoked) key status and the linked endpoint's own URL; a non-admin and a cross-tenant admin are both denied.
5. **`anon` holds zero `EXECUTE`** on any new IAE-013 function.
6. **The widened `authenticated` grant is real** — a genuine forged authenticated session lists real n8n connectors end to end; the same session cannot claim a different identity (`actor_identity_mismatch`).

## 13. Batch 3 Tier C review — findings and fixes against this capability

Batch 3's own mandatory Tier C review found several real defects against this capability's own code, all fixed in `supabase/migrations/20260804060000_harden_intelligence_batch3_tier_c_review_fixes.sql` plus targeted TypeScript/UI fixes, independently re-verified by the orchestrating session (full cross-capability summary: `docs/build-log/phase-09/00_EXECUTION_INDEX.md` §14). This section records what concerns IAE-013, in full.

1. **[High, fixed] Rotating an n8n connector's key via the reused generic `RotateApiKeyForm` silently orphaned the connector's own governance linkage.** `app.rotate_api_key` mints a brand-new `app.api_keys` row (unlike revoke, which updates the SAME row in place); `app.n8n_connectors.api_key_id` (unique, not null) was never updated to follow it. Live-proven: rotating a connector's key with `overlap_minutes=0` left the console showing `status=revoked` (the OLD, now-dead key the linkage still pointed at) while an unlabeled, fully-active successor key with the connector's own scopes remained live and completely unreachable through this console's own revoke path. **Fixed** by a new `app.rotate_n8n_connector`, composing `app.rotate_api_key` and re-pointing `app.n8n_connectors.api_key_id` at the new row -- the UI (`RotateN8nConnectorForm`, new), the server action (`rotateN8nConnectorAction`, new), and the mutation (`rotateN8nConnector`, new) now call it instead of the generic rotate path for a connector. Live-reverified: `list_n8n_connectors_for_tenant`'s own live-joined status correctly reflects the NEW key after rotation, and a new permanent regression in `scripts/db-tests/n8n-integration.sql` proves the linkage follows.
2. **[Medium, fixed] `app.register_n8n_allowlisted_action` was not idempotent under real concurrency**, despite its own doc comment's claim -- an unlocked check-then-insert raised a raw `n8n_action_allowlist_pkey` constraint violation instead of returning the existing row when two callers raced the same scope; live-proven via two real concurrent `psql` processes. **Fixed** via a single atomic `insert ... on conflict (scope) do update ... returning *` (a true upsert) -- `created_at` is never touched by the update, so the "repeated registration returns the SAME row" guarantee still holds; `description`/`registered_by` now refresh on a deliberate re-registration (a reasonable, harmless behavior change). Re-raced live after the fix: both concurrent calls now return the identical row, no error, exactly one row exists.
3. **[Low, fixed] `app.create_n8n_connector` allowed linking a disabled webhook endpoint with no warning** -- a connector linked this way would simply never receive deliveries (`app.queue_webhook_delivery`'s own fan-out only selects `status='active'` endpoints) until someone noticed. **Fixed** by requiring the linked endpoint to be active at link time, raising `webhook_endpoint_not_active` otherwise. A new permanent regression in `scripts/db-tests/n8n-integration.sql` proves the rejection.
4. **[Low, fixed, defense in depth] `app.n8n_connectors`/`app.n8n_action_allowlist` shipped without RLS enabled**, relying only on the absence of any direct table grant to `authenticated`/`anon` (live-confirmed non-exploitable as shipped -- both are RPC-only reads). **Fixed** by enabling RLS on both tables with zero policies -- a cheap, permanent backstop: `authenticated`/`anon` now get zero rows via direct table access even if a FUTURE migration ever granted one, without needing that migration to remember to add RLS itself. The migration-owner role every `service_role`-granted/`SECURITY DEFINER` function in this batch runs as is unaffected (owner-exemption, no `FORCE ROW LEVEL SECURITY`).
5. **[Medium, fixed, UI-only] The console pointed a tenant admin at a non-existent "sample workflows" resource.** `page.tsx` read: *"Sample workflows and setup guidance: see docs/build-log/phase-09/IAE-341.md."* -- an internal git build-log file no live tenant admin can reach, and which itself (this very file, at the time of the finding) contained no sample workflow content, contradicting design decision 7's own claim that this checkpoint delivers "copy-pasteable setup guidance." **Fixed** by replacing the copy with accurate, actionable text describing the real, already-working mechanism (register a webhook endpoint pointed at the workflow's own trigger URL; use the connector's key as a Bearer token against `/api/v1`) -- no external doc reference that could go stale.
6. **[Medium, disclosed, NOT fixed] Design decision 6's claim of per-connector execution-log filtering does not match the shipped console.** The migration header states the console's execution-log view "queries both [`api_logs`, `webhook_deliveries`], filtered by the connector's own linked `api_key_id`/`webhook_endpoint_id`" -- in fact neither `app.list_api_logs_for_tenant` nor `app.list_webhook_deliveries_for_tenant` accepts such a filter, and the shipped `ApiLogList`/`WebhookDeliveryList` render unfiltered, tenant-wide rows. A tenant admin running several connectors cannot isolate one connector's own execution history. Disclosed here as the accurate current state (superseding the original migration's own comment, which is left unedited per this repository's own "never rewrite an applied migration" convention); implementing the filter is deferred to a future checkpoint as it would require extending two more RPCs plus their own UI, judged out of this bounded Tier C pass's own scope.
7. **[Shared with every Batch 3 capability, fixed] `app/(tenant)/[tenantSlug]/admin/api-keys/page.tsx`'s single `Promise.all`** blanked all nine sections across all five capabilities (including this one's own connector list) on any ONE query's failure. **Fixed** via per-section `loadSection`/`Section` isolation (a known query error now degrades only its own section) -- see `docs/build-log/phase-09/IAE-337.md` §13 for the full description, since that file originally created this page.
