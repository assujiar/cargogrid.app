# IAE-331 — Dashboard Builder

**Prompt ID:** `CG-S14-IAE-003` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/331_DASHBOARD_BUILDER_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — second prompt of Batch 1, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 1's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-331 is Phase 9's own first genuinely tenant-configurable UI surface: every prior "dashboard" in this repository (Commercial `COM-158`, Operations `OPS-183`, Finance `FIN-213`, Procurement) is a fixed, code-defined page showing a fixed widget set. This migration builds the widget/layout/version/publish/rollback mechanism Prompt 331 §24 asks for, on top of (never duplicating) the `IAE-002` report catalog — a widget always binds to an existing, active `app.report_types` code; there is no raw-SQL widget shape.

## 2. Design decisions (cited, not re-derived)

1. **`app.entitlement_modules`/`app.permissions` already seeded a real `REP` module (`PLT-106`/`PLT-111`, Phase 1) with `View`/`Export`/`Print`/`Configure` actions, never consumed by any Phase 1-8 capability.** `IAE-002` reused `COM:Export` for its own `cancel_report_run` (the only pre-existing choice available to a Commercial-scoped report engine at the time it was authored, disclosed as a non-blocking Tier C note for Batch 1's own review). `REP:Configure` gates every mutation this migration adds — this repository's own first real consumer of the `REP` module, not this checkpoint's invention.
2. **Version/publish/rollback mirrors `IAE-002`'s own `report_type_versions` shape.** `app.tenant_dashboard_versions` is append-only; a dashboard's own `current_version_id` only ever points at a `published` version — a fresh `draft` version is created automatically at publish time (copying the just-published version's own widgets) so editing can continue without ever mutating a published snapshot in place. Rollback moves `current_version_id` to an older `published` version; it never deletes or rewrites any version row.
3. **A widget is a binding, never a query.** `app.tenant_dashboard_widgets.report_type_code` is a live FK into `app.report_types`; `add_dashboard_widget` rejects an unknown or `retired` code and validates `parameter_overrides` against that report's own `parameter_schema` by reusing `IAE-002`'s `app.validate_report_parameters` directly — never a second validator. Actually rendering a widget's own data still goes through the existing `app.record_report_run`/domain `get_*` function pair, unchanged; this migration adds no new data-query SQL at all.
4. **`ATW-032`/C-13 and C-04 compliance built in from the start** (lessons `IAE-002`'s own Tier B review surfaced): every side-effecting function calls `app.assert_actor_is_session_identity` as its first statement; `publish_tenant_dashboard_version` and `rollback_tenant_dashboard` both lock the `tenant_dashboards` row `for update` before deciding.
5. **One real Tier B/rbac-enforcement.sql-sweep defect found and fixed before commit — a genuine gap in this checkpoint's own first draft, not a pre-existing one.** The first draft's three SELECT RLS policies (`tenant_dashboards_select_scoped`, `tenant_dashboard_versions_select_scoped`, `tenant_dashboard_widgets_select_scoped`) tested plain `app.has_active_tenant_membership(tenant_id) or app.is_supreme_admin()` — mirroring `app.report_runs_select_scoped`'s own precedent, cited in the migration's original header. That precedent predates `20260730560000`'s own ratified `CG-S10-ATW-032`/`ISS-2026-010` default-deny convention (`report_runs` was created `20260724`, six days earlier), so copying it forward into an `20260802`-dated migration reintroduced the exact gap that convention closed: a `customer_user`-layer principal, who satisfies `has_active_tenant_membership` identically to an ordinary `org_user`, could read tenant dashboard configuration — which report codes/parameters a tenant has chosen to surface — through a raw Supabase client, with no portal code involved. `scripts/db-tests/rbac-enforcement.sql`'s own repository-wide sweep caught this live, by name, on a full `db:test` run (not by manual inspection). Fixed by inserting `and not app.actor_holds_customer_user_layer(<tenant column>)` beside each membership call — the exact idiom `20260730560000` itself established for the two shapes present here (a direct `tenant_id` column on `tenant_dashboards`; an `EXISTS`-joined alias for the two child tables) — re-verified by a second full `db:test` run showing the sweep's own `ATW-032 portal default-deny proof` NOTICE succeed.

## 5. Schema

`app.tenant_dashboards` (new): `id`, `tenant_id` (FK), `name`, `description`, `status` (`draft`/`published`/`archived`), `current_version_id` (FK, nullable), `created_by_auth_user_id`, `created_by`, `record_version`, `created_at`, `updated_at` (touch trigger).

`app.tenant_dashboard_versions` (new, append-only): `id`, `dashboard_id` (FK), `version_number`, `layout` (jsonb, free-form grid hint, never a query), `status` (`draft`/`published`/`superseded`), `published_by_auth_user_id`, `published_by`, `published_at`. Unique `(dashboard_id, version_number)`.

`app.tenant_dashboard_widgets` (new): `id`, `dashboard_version_id` (FK), `report_type_code` (FK into `app.report_types`), `title`, `position` (jsonb), `parameter_overrides` (jsonb), `display_order`.

## 6. RLS and grants

Tenant-wide `select` on all three tables (mirrors `app.report_runs`' own "management visibility, not per-owner privacy" precedent), narrowed per §2 item 5: `(app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id)) or app.is_supreme_admin()`, inserted beside the membership call inside each child table's own `EXISTS` join. `insert`/`update`/`delete` on all three tables is `service_role`-only (every real write goes through the five `SECURITY DEFINER` functions above). Schema-privilege defense in depth (zero `anon` EXECUTE on any new function, zero `authenticated` direct INSERT/UPDATE/DELETE) live-verified in `scripts/db-tests/dashboard-builder.sql`.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **Draft-only enforcement is real** — `add_dashboard_widget`/`remove_dashboard_widget` against a `published` version's own widgets both reject with `dashboard_version_not_editable`; the identical calls against that same dashboard's fresh post-publish draft succeed.
2. **Publish never mutates a published snapshot** — publishing opens a new draft version whose own widget rows are physically distinct copies (new ids) of the just-published version's widgets, confirmed by direct query, not merely asserted.
3. **Rollback targets only a `published` version** — a rollback attempt naming a `draft` version id is rejected with `dashboard_target_version_invalid`; naming a genuinely older `published` version updates `current_version_id` and nothing else (no version row deleted or rewritten).
4. **Widget binding is closed to unknown/retired codes** — `add_dashboard_widget` against a nonexistent code raises `report_type_unknown`; against a real but `retired` code raises `report_type_retired`.
5. **Parameter validation is real, reused, not duplicated** — a widget's `parameter_overrides` failing `app.validate_report_parameters` against its own report's `parameter_schema` is rejected with `widget_unsafe_parameters`.
6. **Cross-tenant isolation holds** — a `iaedashco2` actor cannot read, add a widget to, publish, or roll back a `iaedashco` dashboard.
7. **The RLS gap was live-caught, not hypothesized** — the FIRST full `db:test` run's `rbac-enforcement.sql` failed with a named, specific assertion (`tenant_dashboards_select_scoped` et al. test tenant membership and nothing else); the SECOND full run, after the §2 item 5 fix, shows that same sweep's own success `NOTICE` (`ATW-032 portal default-deny proof`).
8. **Schema-privilege defense in depth** — zero `anon` EXECUTE grant on any of the 5 new functions; zero `authenticated` direct INSERT/UPDATE/DELETE on any of the 3 new tables.
9. **Audit trail is real** — `create_tenant_dashboard_draft`/`publish_tenant_dashboard_version`/`rollback_tenant_dashboard` each recorded a genuine `app.audit_logs` row, confirmed by direct query.
