# IAE-362 — Scale-Up Architecture

**Prompt ID:** `CG-S14-IAE-034` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/362_SCALE_UP_ARCHITECTURE_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; third capability of Group 8, "Enterprise Deployment, Residency, Scale, and DR", Prompts 360-363 — reaches `VERIFIED` only at that group's own Tier C review).

## 1. What this checkpoint builds

Real, structural scale-up governance: a persisted per-workload capacity budget (tenant override, then platform default), a real, non-silent budget-evaluation ledger, and a real, human-reviewed scaling-recommendation backlog — composing `IAE-030`'s own observability/alerting machinery for genuine backpressure alerts and `IAE-032`'s own dedicated-deployment lifecycle to keep a "recommend dedicated deployment" suggestion honest (never redundant once the tenant already has one active).

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260808200000_create_intelligence_scale_up_architecture.sql`). Summary:

1. **Genuinely greenfield** — confirmed by direct grep before writing any code (no `capacity`/`workload`/`backpressure`/`scaling_recommendation` table or function exists anywhere).
2. **Reuses the `MON` entitlement module** (`View`/`Edit`/`Configure`) from `IAE-030` rather than adding a new one — Prompt 362's own workstream is "Reliability", identical to Prompt 358's own "Enterprise Monitoring and Observability" workstream, and this checkpoint's own actions are the same shape of authority `MON` already covers.
3. **`app.workload_capacity_profiles` mirrors `app.slo_definitions`'s own exact shape** (`IAE-030`): `tenant_id` nullable with `unique nulls not distinct (tenant_id, workload_type)` applied from the first draft, `MON:Configure`-gated per tenant or Supreme-Admin-only platform-wide, identical to `app.set_slo_definition`'s own authority branch.
4. **`app.evaluate_workload_budget` is the real, structural PRIMITIVE that implements "Main flow"** (Prompt 362 §21) whenever a caller invokes it — service_role-only, no actor parameter, mirroring `app.record_observability_signal`'s own shape exactly (see §8's own disclosure: like that function, no job worker/webhook/API middleware in this repository calls it yet). A budget breach is a real, named, non-silent outcome (`action_taken = 'backpressure_applied'`) composed with `IAE-030`'s own `app.raise_observability_alert`, never a second parallel alerting path. The `workload_type -> source_type` mapping this composition needs is documented in the migration's own header rather than silently assumed.
5. **`app.generate_scaling_recommendation`'s own `dedicated_deployment` recommendation type is a real, structural composition with `IAE-032`**: rejected outright if `app.resolve_tenant_deployment_type` already reports `'dedicated'` for that tenant.
6. **`app.resolve_workload_budget` is the bare-tenant-id, no-actor-parameter default-resolution function** this checkpoint's own capacity profile needs — granted `service_role` ONLY from the very first draft, applying the lesson `IAE-032`/`IAE-033` both already established correctly.
7. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement.
8. Per the standing convention since `PLT-118`: explicit, redundant `revoke execute on all functions in schema app from public`.

## 8. Residual/disclosed limitations

- **No automatic recommendation generation** — `app.generate_scaling_recommendation` is a real, human/operator-invoked action after reviewing `app.workload_backpressure_events`' own evidence, not an autonomous engine that counts repeated breaches and files a recommendation on its own. Disclosed honestly, consistent with this repository's own "governance evidence layer, not autonomous action" posture.
- **No real read-model/materialized-view/partitioning execution** — `recommendation_type` values `read_model`/`partitioning`/`architecture_review` are real, tracked recommendations an operator records and later marks `implemented`; this checkpoint does not itself create any materialized view, partition, or architecture change.
- **`workload_type -> source_type` mapping is a documented, honest simplification** (design decision 4) — `analytics`/`reports`/`import_export`/`notifications` all map to `IAE-030`'s own `'job'` source_type since each is genuinely job-queue-backed in this repository's own architecture; this is not a claim that all four are identical workloads, only that they share the same alerting channel today.
- **Tier C review finding, disclosed rather than code-fixed (correctness/concurrency lens): the same mapping means a genuine breach of TWO DIFFERENT `job`-mapped workload types for the same tenant within the same dedupe window collapses into ONE incident**, since `IAE-030`'s own `app.raise_observability_alert` dedupes purely on `(tenant_id, source_type, signal_type)` with no `workload_type` dimension of its own. Live-reproduced: an `analytics` breach and an independent `reports` breach for the same tenant produced a single incident, with the second breach visible only as a `duplicate_signal` timeline event's free-text `detail`, not its own incident. A real fix would require widening `IAE-030`'s own already-`VERIFIED` `app.incidents`/`app.alert_routes` schema (a new dimension in the dedup key) — out of this checkpoint's own scope (editing a different, already-closed capability's own schema from within this one). `app.workload_backpressure_events` itself is NOT affected — every real breach is still recorded there with its own correct `workload_type`/values; only the alerting/incident SURFACE can under-represent a second, simultaneous, distinct-workload-type breach.
- **`app.evaluate_workload_budget` has no real caller anywhere in this repository** (confirmed by repository-wide grep — no job worker, webhook handler, API middleware, or scheduled task invokes it), the same "structural governance primitive, no live wiring yet" shape `app.record_observability_signal` (`IAE-030`) already established and which passed Group 7's own Tier C review under the identical disclosure. Noted explicitly here (Tier C review, spec-compliance lens) since earlier drafts of this build log described it as "the real Main Flow" without stating this in the same words its sibling capability used.
- **No dedicated scale-up admin UI** — consistent with every other Group 7/8 capability.

5. **`app.generate_scaling_recommendation`**: no-`MON:Configure` actor rejected; empty rationale rejected; invalid workload_type/recommendation_type rejected; a `read_model` recommendation succeeds; a `dedicated_deployment` recommendation succeeds while the tenant genuinely has no active dedicated deployment yet.
