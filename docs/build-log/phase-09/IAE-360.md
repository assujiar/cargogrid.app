# IAE-360 — Dedicated Enterprise Deployment

**Prompt ID:** `CG-S14-IAE-032` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/360_DEDICATED_ENTERPRISE_DEPLOYMENT_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; first capability of Group 8, "Enterprise Deployment, Residency, Scale, and DR", Prompts 360-363 — reaches `VERIFIED` only at that group's own Tier C review).

## 1. What this checkpoint builds

The real, structural governance layer for RPD-011's own rule ("shared database/shared schema with RLS remains default; dedicated instance is a paid Enterprise option only"): a qualification → approval → provisioning → active → decommissioned state machine per tenant, contract/security/CTO approval as a real, separate authority tier from requesting, and environment-isolation evidence (database/secrets/backup/observability references) — never a native provisioning tool, since none exists anywhere in this repository.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260808000000_create_intelligence_dedicated_enterprise_deployment.sql`). Summary:

1. **Genuinely greenfield** — confirmed by direct grep before writing any code (no `deployment`/`provisioning` table or function exists anywhere in `app`). RPD-011's own default is the real, structural default this checkpoint preserves: `app.resolve_tenant_deployment_type` returns `'shared'` for every tenant with no record at all, and only a real, approved, `active` `app.tenant_deployment_records` row ever returns `'dedicated'` — mirroring `IAE-031`'s own `app.resolve_retention_days` fallback shape exactly.
2. **New `DEPLOY` entitlement module** (`View`/`Configure`/`Approve`) — Prompt 360's own workstream is "Enterprise Deployment", distinct from every Group 7 module.
3. **No real infrastructure is provisioned by this checkpoint** — there is no dedicated-instance provisioning API/IaC anywhere in this repository, and none is added here. This builds the real, structural GOVERNANCE evidence layer (qualification, contract/security/CTO approval, provisioning status, environment-isolation reference records) an actual provisioning runbook/tool would read from and write into — disclosed honestly, the same bounded-scope posture `IAE-030`'s own "no external APM integration" already established.
4. **Real, structural state machine, not merely disclosed**: `app.set_deployment_provisioning_status` enforces a real, ordered transition graph (`pending_qualification -> qualified -> provisioning -> active -> decommissioned`) — "Provisioning requires contract/security/CTO approval" (Prompt 360 §24) is enforced by requiring a real `qualified` status (itself requiring a separate `DEPLOY:Approve` action, self-approval forbidden by construction — a requester holding only `DEPLOY:Configure` cannot also approve their own request without a real, separate `DEPLOY:Approve` grant) before `provisioning`/`active` can ever be reached.
5. **`app.tenant_deployment_environment_refs` stores only a real REFERENCE string** (a pointer/label to an external secrets manager entry, backup location, or observability workspace) — never a real secret value — the identical "reference, never the secret itself" boundary `PLT-118`'s own credential-reference tables already established.
6. **Lessons carried forward verbatim from Group 7's own Tier C review** (`docs/build-log/phase-09/00_EXECUTION_INDEX.md` §16), applied from the first draft rather than re-discovered: (a) every function taking a tenant-shaped identifier has a real actor parameter and a real authority check; (b) every `tenant_id`-nullable UNIQUE constraint uses `unique nulls not distinct`; (c) every idempotent "get or create" bootstrap uses `on conflict do nothing` + re-select; (d) every self-approval-shaped break-glass action has both a hard CHECK constraint and an explicit application check — (b)/(c)/(d) do not apply to this checkpoint's own schema (no nullable-tenant unique constraint, no bootstrap-race primitive, no self-approval-shaped single-actor action — approval is already a real, separate authority tier, not a break-glass override of one's own prior action), noted here rather than silently skipped.
7. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement.
8. Per the standing convention since `PLT-118`: explicit, redundant `revoke execute on all functions in schema app from public`.

New `DEPLOY` entitlement module + 3 permissions. No change to any existing table.

## 7. Tier B — recurring defect taxonomy self-check

- **Bare-tenant-id authority gap, self-caught before any testing began.** `app.resolve_tenant_deployment_type(p_tenant_id uuid)` — the RPD-011 default-resolution function — was first drafted with no actor parameter, granted to `authenticated` alongside the other six, properly actor-gated functions. This is the identical shape `app.is_high_risk_action` (`IAE-027`) and `app.resolve_retention_days` (`IAE-031`) each shipped with and were fixed for in Group 7's own Tier C review (`00_EXECUTION_INDEX.md` §16). Caught this time during this checkpoint's own pre-test self-review (design decision 6 explicitly commits to this exact lesson) rather than by a later drift gate or Tier C pass. Fixed the same way as `app.resolve_retention_days`: narrowed the grant to `service_role` only, rather than adding an actor parameter — `app.get_tenant_deployment_record` (already `DEPLOY:View`-gated) already discloses the same information for any genuine end-user need, and the function's only real caller is internal composition from a future capability (`IAE-033`'s own region-service matrix), unaffected by the narrower grant since an internal `SECURITY DEFINER`-to-`SECURITY DEFINER` call runs as the owner regardless of grants. `server/queries/dedicated-enterprise-deployment.ts`'s own `resolveTenantDeploymentType` wrapper documents the service-role-only calling convention in its doc comment. Never committed to git in its original, over-granted shape.
- **C-12/C-13, C-05, ERR-2026-004** — applied proactively from the first draft, including the standing `revoke execute on all functions in schema app from public` statement.
- **Approval-authority-ordering precedent reused deliberately, not by accident.** `app.approve_dedicated_deployment_qualification` checks record existence-and-status (`where id = ... and status = 'pending_qualification'`) before checking `DEPLOY:Approve` authority — the identical ordering `app.release_legal_hold` (`IAE-031`) already established and which passed Group 7's own Tier C review unchanged. This checkpoint's own db-test was written to account for that ordering explicitly (the cross-tenant `DEPLOY:Approve` rejection is proven against a record that is still genuinely `pending_qualification`, not one already moved past that status, where the function would instead report the state-based `deployment_record_not_pending_qualification` error before ever reaching the authority check).
- **No cross-file regression this time**: fixture id range `000035xxxxxx` verified unique (via exact 12-hex-digit grep against the literal `0000-0000-000035` prefix, not a loose substring match) before the db-test was ever run; no new `anon`-granted function was added, so the repository-wide anon-grant-count drift gate needed no bump.

No taxonomy class was skipped.

## 8. Residual/disclosed limitations

- **No physical dedicated-instance provisioning** — see design decision 3. This checkpoint's own `set_deployment_provisioning_status` records that provisioning happened; it does not itself create, migrate data into, or network-isolate any real dedicated instance. A future runbook/tool would read/write this checkpoint's own tables as its evidence layer.
- **"Contract/security/CTO approval" is modeled as a single `DEPLOY:Approve` authority tier**, not three separately tracked sign-offs — the schema records ONE approval event (`approved_by_auth_user_id`/`approved_by`/`approved_at`); which specific stakeholders that identity represents is an operational/organizational fact outside this schema's own scope, consistent with how `IAE-031`'s own `RET:Approve` models "regulatory/legal sign-off" as a single authority tier rather than a multi-party workflow.
- **No dedicated deployment admin UI** — consistent with every other Group 7/8 capability.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`app.resolve_tenant_deployment_type`**: returns `'shared'` for a tenant with zero deployment record rows (RPD-011's own default); still `'shared'` while merely `pending_qualification`/`qualified`/`provisioning` (not yet genuinely `active`); flips to `'dedicated'` only once the record has actually reached `active`; flips back to `'shared'` once `decommissioned`.
2. **`app.request_dedicated_deployment_qualification`**: no-`DEPLOY:Configure` actor rejected; empty qualification reason rejected; a real `pending_qualification`, `deployment_type='dedicated'` row created on success; a SECOND request for the same tenant rejected with a real `unique_violation` — no silent second parallel lifecycle.
3. **`app.approve_dedicated_deployment_qualification`**: `DEPLOY:View`-only actor rejected; the requester's own `DEPLOY:Configure` (not `Approve`) grant rejected — self-approval is impossible without a real, separate `Approve` grant; a wrong-tenant actor holding `DEPLOY:Approve` for a DIFFERENT tenant rejected against a genuinely `pending_qualification` record; the correctly authorized approver succeeds (`status=qualified`, `approved_by`/`approved_by_auth_user_id` set, `record_version` incremented by the touch trigger); a second approval attempt on the now-`qualified` record rejected (`deployment_record_not_pending_qualification`).
4. **`app.set_deployment_provisioning_status`**: the full ordered transition graph live-walked end to end — `qualified -> active` (skipping `provisioning`) rejected; `provisioning -> decommissioned` (skipping `active`) rejected; `decommissioned -> provisioning` (terminal state reopened) rejected; `DEPLOY:View`-only actor rejected; the correctly authorized actor drives `qualified -> provisioning -> active -> decommissioned` in the real, valid order, with `provisioned_at`/`decommissioned_at` set at the correct steps.
5. **`app.set_deployment_environment_ref`**: `DEPLOY:View`-only actor rejected; an invalid category rejected; an empty reference value rejected; all four real categories (`database`/`secrets`/`backup`/`observability`) set successfully; a second call for the SAME category upserts the SAME row (new `reference_value`, same `id`) — confirmed via a direct row-count check (exactly 4 rows, never a duplicate).
6. **`app.get_tenant_deployment_record`/`app.list_deployment_environment_refs`**: no-`DEPLOY:View` actor rejected on both; the correctly authorized viewer reads the real record and all four environment refs, ordered by category ascending.
7. **Cross-tenant isolation**: a tenant-2 admin (holding `DEPLOY:Configure`/`View`/`Approve` — but only for tenant 2) cannot request qualification, approve, change provisioning status, set an environment ref, read the deployment record, or list environment refs for tenant 1's own deployment record.
8. **RLS default-deny**: a direct `authenticated` `select` on both new tables is denied at the raw-RLS level.
9. **`anon` holds zero `EXECUTE`** on any of the 7 new functions; **`authenticated` holds zero `EXECUTE`** on `app.resolve_tenant_deployment_type` specifically, while `service_role` does — a direct regression test of the self-caught fix in §7.
