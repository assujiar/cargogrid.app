# IAE-334 — Scheduled Reports

**Prompt ID:** `CG-S14-IAE-006` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/334_SCHEDULED_REPORTS_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `VERIFIED`** (2026-08-21 — fifth and LAST prompt of Batch 1, Tier A/B self-reviewed and gate-verified individually at commit; `VERIFIED` as of Batch 1's own Tier C review close — see §13 — migration `20260802060000_harden_intelligence_batch1_tier_c_review_fixes.sql`)

## 1. What this checkpoint builds

IAE-334 is Batch 1's own final capability: recurring, timezone-aware, cron-validated report scheduling on top of the `IAE-002` report catalog, delivering to internal tenant recipients only, with live per-run recipient reauthorization, and reusing `app.jobs`' own already-`VERIFIED` retry/DLQ mechanics (`PLT-131`/`132`) and the notification engine's own already-`VERIFIED` delivery path (`PLT-127`) rather than building either a second time.

## 2. Design decisions (cited, not re-derived)

1. **Recipients are internal tenant members only — no free-text external address field exists anywhere in this schema.** Prompt 334 §24 ("schedules cannot send sensitive reports to unauthorized external recipients") is satisfied structurally: `scheduled_report_recipients.recipient_auth_user_id` is a real FK into `auth.users`, re-validated against `app.has_active_tenant_membership` at EVERY run — "checked at run time, not only creation" (§24) — not merely at add time.
2. **`app.jobs`' own retry/backoff/dead-letter/requeue mechanics are reused directly via `job_id`, never duplicated.** No second retry/DLQ state machine exists in this migration.
3. **Delivery reuses `app.queue_notification` (`PLT-127`), never a bespoke email/webhook sender.** Its own required `notification_types`/`config_types`/`config_versions`/`config_items` bootstrap is seeded by direct `INSERT`, mirroring the already-shipped `20260731160000_create_ticket_escalation.sql` (HRT-291) precedent — `register_notification_type`/`create_config_draft`/`publish_config_version` are Supreme-Admin-gated RPCs with no live actor session at migration-apply time. Unlike HRT-291's own registration-only bootstrap (emission deliberately out of scope there), this checkpoint's own `run_scheduled_report` IS a real emission caller, so the config_version is seeded already-published.
4. **Duplicate delivery is prevented by idempotency key, not a lock.** `app.enqueue_job`'s own idempotency key is `'scheduled-report-<schedule_id>-<due_occurrence>'` — the same due occurrence can never enqueue a second `app.jobs` row even if `run_scheduled_report` is called twice for it, live-proven in the db-test by forcing a re-trigger of the identical occurrence and asserting the SAME `job_id` comes back.
5. **Cron support is a real, bounded subset, not a full parser**: daily, weekly-on-one-weekday, or monthly-on-one-day-of-month (capped 1-28), each at one exact hour:minute. `scheduled_report_invalid_cron` rejects the one ambiguous shape (both day-of-month and day-of-week set) with a real, named error rather than silently approximating an unsupported combination. `timezone` is validated against `pg_timezone_names` (the same introspection idiom `IAE-005`'s own `pg_matviews` check established). `app.compute_scheduled_report_next_run` converts local wall-clock time to UTC via Postgres's own `AT TIME ZONE` semantics — live-verified against four real cases (daily, weekly, monthly, and a timezone-edge case: 23:30 Asia/Jakarta correctly resolves to a DIFFERENT UTC calendar day) before any db-test was written.
6. **No real report artifact is ever generated in this environment** — the SAME standing, disclosed condition `IAE-002`'s own `enqueue_report_export` already carries. `artifact_file_id`/`artifact_expires_at` exist and are wired for a future real worker; download-audit would reuse the EXISTING `app.authorize_file_access` (`PLT-11x`) once a real `file_id` exists — never a second file-access-logging mechanism built here.
7. **`REP:Configure` gates every mutation** — the same "configuring a shared reporting artifact" authority `IAE-003`/`IAE-004`/`IAE-005` already established.

## 13. Tier C fix pass (Batch 1 review close)

Batch 1's own mandatory four-lens review surfaced more findings against this capability's own code (`app.run_scheduled_report` in particular) than any other in the batch — including the batch's own sole Critical finding, live-reproduced with an actual cross-tenant content leak.

- **Finding 1 (Critical, security-rls-tenant).** `app.run_scheduled_report` resolved the notification `config_version` via an UNSCOPED join (no `tenant_id`/scope filter, no `ORDER BY`, no `LIMIT`) against the shared `config_type_code` `'notification:scheduled_report_ready'`. Live-reproduced: an ordinary `tenant_admin` in ANY tenant could publish a tenant-scoped override (using already-shipped, generic Configuration Engine RPCs — no special privilege needed) and have it win for every OTHER tenant's own scheduled-report notifications, system-wide, purely by UUID-sort chance. Fixed by replacing the hand-rolled lookup with the already-existing, correctly tenant-scoped 6-level resolver, `app.resolve_config` (PLT-121). Live regression added to `scripts/db-tests/scheduled-reports.sql`: a genuine rogue tenant-scoped override is published in `iaeschedco2` (marker subject `'TIER-C-LEAK-MARKER-TENANT2'`) via real `create_config_draft`/`set_config_items`/`publish_config_version` calls, and `iaeschedco`'s own recipient is confirmed to still receive the real, global template subject — never the leaked marker.
- **Finding 2 (High, spec-compliance).** `app.run_scheduled_report` was not idempotent PER DUE OCCURRENCE — only the `app.jobs` enqueue was deduplicated; the `scheduled_report_runs` bookkeeping row and every recipient notification dedupe key were keyed off a freshly-generated `v_run.id` on every call, so a re-triggered run for the SAME occurrence created a duplicate run-history row and sent real duplicate notifications. Fixed with a new `occurrence_at` column (unique on `(scheduled_report_id, occurrence_at)`) and an occurrence-scoped upsert for the run row, plus a notification dedupe key derived from `(schedule_id, occurrence timestamp, recipient_id)`. Live regression: the pre-existing re-trigger test in `scheduled-reports.sql` now also asserts the SAME `scheduled_report_runs.id` is reused, the notification count stays at exactly 1, and the linked `app.report_runs` row count stays at exactly 1 across both triggers of the identical due occurrence.
- **Finding 3 (High, correctness-concurrency).** Two genuinely concurrent calls each passed the row's own `for update` lock sequentially and each computed a DIFFERENT occurrence, because the second call only read `next_run_at` after the first had already advanced it — live-reproduced with two parallel `psql` sessions: two distinct occurrences got processed (double notification, `next_run_at` silently skipped a real due date). Fixed by capturing the occurrence THIS caller intends to trigger via an UNLOCKED read before requesting the row lock; if the locked re-read shows `next_run_at` already moved past that value, the call is stale for an occurrence a concurrent winner already handled and returns that winner's own run instead of silently processing a second, not-yet-actually-due occurrence. **Live regression added** (this fix pass's own new test, not present when the fix agent was interrupted): a real, genuinely concurrent two-OS-process race in `scheduled-reports.sql`, mirroring the established `ticketing-assignment.sql` §6 pattern via `scripts/db-tests/wms-picking-concurrency-helper.sh` — both processes call `app.run_scheduled_report` for the SAME due occurrence simultaneously; asserted post-race: exactly one `scheduled_report_runs` row for that occurrence, exactly one `app.jobs` row, and `next_run_at` advanced by exactly one real computed step (never a silent double-advance).
- **Finding 4 (Medium, security-rls-tenant, found via the mandatory propagation sweep for the customer_user-layer pattern established elsewhere in this batch, not itself a lens finding).** `app.add_scheduled_report_recipient` and `app.run_scheduled_report`'s own live reauthorization loop both used a plain `has_active_tenant_membership` check with no `customer_user`-layer exclusion — a portal account could be added as (or remain) a recipient of an internal scheduled report. Fixed identically to findings 8/9/10 in the sibling capabilities. Live regression: a portal fixture is rejected at add-time, and a defense-in-depth direct fixture insert (bypassing the now-correct RPC) proves the live run-time reauthorization loop ALSO excludes them even for a pre-existing row.
- **Finding 5 (Medium, security-rls-tenant, same C-05 class as IAE-002's `cancel_report_run`/IAE-003's four functions).** `app.set_scheduled_report_status`, `app.add_scheduled_report_recipient`, `app.remove_scheduled_report_recipient`, and `app.run_scheduled_report` all looked up their target row by id with no tenant filter, then raised `insufficient_authority` embedding the row's real `tenant_id` for a caller with zero relationship to that tenant — a distinguishable oracle from the genuinely-missing-id `not_found` error. Fixed by folding the cross-tenant case into the same `scheduled_report_not_found` the missing-id case already raises. Live regression: the pre-existing cross-tenant isolation test now asserts `no_data_found` in place of the old, incorrect `insufficient_authority` expectation.

Fixed by inserting a linked `app.report_runs` row (idempotent on `job_id`, never a second bookkeeping row for a re-triggered/deduped occurrence). Live regression: the pre-existing re-trigger test now also asserts exactly one linked `app.report_runs` row across both triggers.
