# IAE-333 — Analytics and Materialized Views

**Prompt ID:** `CG-S14-IAE-005` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/333_ANALYTICS_MATERIALIZED_VIEWS_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — fourth prompt of Batch 1, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 1's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-333 is this repository's own first real Postgres `materialized view`, plus the governance layer around it: a registry of which views exist, an append-only refresh-run ledger carrying freshness/lineage/reconciliation evidence, and a tenant-scoped, `SECURITY DEFINER`-gated read path. The one real view built, `app.mv_report_usage_daily`, aggregates `app.report_runs` (`IAE-002`) by (tenant, report type, day) — real, meaningful, already-in-track analytics for Batch 1's own reporting stack, never a fabricated business metric.

## 2. Design decisions (cited, not re-derived)

1. **`REFRESH MATERIALIZED VIEW CONCURRENTLY` is used, not the plain form.** The old snapshot stays queryable for the entire duration of a refresh — this is Prompt 333's own Alternative flow ("a refresh fails and the system preserves previous snapshot with degraded indicator") made real by a genuine Postgres property, not a bespoke fallback mechanism. `CONCURRENTLY` requires a unique index, created immediately after the view's own initial population.
2. **Refresh is NOT routed through `app.jobs`/`app.enqueue_job`, despite a pre-seeded, never-consumed `'dashboard_refresh'` generic job type existing since `PLT-132`** — disclosed rather than silently used. `app.jobs.tenant_id` is `not null`: the job queue is structurally tenant-scoped, but this materialized view spans every tenant in one shared aggregate, and refreshing it is a single, cross-tenant platform operation. Forcing it through a tenant-scoped queue would mean either a fabricated sentinel tenant or one job per active tenant for what is really a single shared refresh. `app.analytics_refresh_runs` is its own dedicated, cross-tenant evidence ledger instead. `'dashboard_refresh'` remains available, unconsumed, for a future per-tenant dashboard-cache capability this checkpoint does not build.
3. **Reconciliation is a real, independently-computed check, not a re-statement of the same number.** After refresh, `row_count_after` is compared against a live `count(distinct (tenant_id, report_type_code, day))` computed directly from `app.report_runs` — the source of truth — never read back from the view that was just refreshed off the identical query. A genuine drift-catching assertion.
4. **The materialized view itself carries zero grants to `authenticated`/`anon`.** Every tenant-scoped read goes through `app.get_report_usage_daily`, a `SECURITY DEFINER` function that filters `where tenant_id = p_tenant_id` and requires active, non-`customer_user`-layer tenant membership. Postgres does not support enabling row-level security on a materialized view — this is the only real tenant-isolation mechanism available for this object, not a stylistic choice.
5. **`register_analytics_view`/`refresh_analytics_view` are Supreme-only.** A refresh is a single, system-wide operation touching every tenant's own aggregate at once — no ordinary tenant actor should trigger it, mirroring `publish_report_type_version`'s own Supreme-only precedent for "product feature configuration," here applied to "shared infrastructure operation."
6. **`register_analytics_view` validates `view_name` against `pg_matviews` before registering** — a real introspection check, never a fabricated/unchecked name; `analytics_view_unknown` is a live, provable rejection.
7. **`app.analytics_view_registry`/`app.analytics_refresh_runs` are global, no-RLS tables** — non-sensitive platform metadata, mirroring `app.report_types`' own already-accepted no-RLS "global catalogue" precedent.
8. **A real failure path is tested, not merely reasoned about.** The db-test creates a genuine disposable materialized view, registers it, drops it out from under its own registry row, then calls refresh — the function's own exception scope wraps the ENTIRE working body (including the before-count, found necessary during authoring: an early draft only wrapped the `REFRESH` statement itself, which meant a dropped view failed at the earlier count statement and raised an uncaught exception instead of a clean `status='failed'` row — fixed before commit, never shipped).

## 5. Schema

`app.analytics_view_registry` (new): `id`, `view_code` (unique), `view_name`, `name`, `description`, `source_domain`, `refresh_frequency_minutes`, `status` (`active`/`retired`), `registered_by_auth_user_id`, `registered_by`, `created_at`.

`app.analytics_refresh_runs` (new, append-only): `id`, `view_code` (FK), `status` (`running`/`completed`/`failed`), `row_count_before`, `row_count_after`, `reconciled`, `error_reason`, `triggered_by_auth_user_id`, `triggered_by_label`, `started_at`, `completed_at`.

`app.mv_report_usage_daily` (new materialized view): `tenant_id`, `report_type_code`, `usage_date`, `preview_count`, `export_count`, `failed_count`, `last_run_at`, aggregated from `app.report_runs`. Unique index on `(tenant_id, report_type_code, usage_date)`.

## 6. RLS and grants

`analytics_view_registry`/`analytics_refresh_runs`: no RLS, direct `select` to `authenticated, service_role` (global platform metadata, mirrors `report_types`' own precedent); `insert`/`update`/`delete` is `service_role`-only. `mv_report_usage_daily`: **zero** privileges to `authenticated`/`anon` — an explicit `revoke all ... from public, authenticated, anon`, since Postgres has no RLS mechanism for a materialized view; `app.get_report_usage_daily` is the sole read path. Schema-privilege defense in depth (including the materialized view's own zero-grant state) live-verified in `scripts/db-tests/analytics-materialized-views.sql`.

## 8. Residual/disclosed limitations

- **No scheduled/automatic refresh trigger exists.** `app.refresh_analytics_view` must be called explicitly (by a Supreme Admin via this checkpoint's own UI, or a future scheduled-job worker); no cron-like mechanism is built here. `IAE-006` (Prompt 334, Scheduled Reports) is the natural place a future recurring trigger would live, disclosed rather than built prematurely into this checkpoint's own bounded scope.
- **Exactly one materialized view is built.** A generic "materialized view framework" supporting arbitrary future views is not fabricated; `register_analytics_view`'s own `pg_matviews` validation means a second view is addable later by (1) `CREATE MATERIALIZED VIEW`, (2) one `register_analytics_view` call — no schema change required, but no second view exists yet.
- **`'dashboard_refresh'`'s own pre-seeded generic job type remains unconsumed**, disclosed in §2 item 2 rather than forced into a shape that does not fit this checkpoint's cross-tenant refresh operation.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **The materialized view is real and really refreshes** — before the test's own three `record_report_run` calls are reflected, `app.mv_report_usage_daily` does not contain them; after `app.refresh_analytics_view('report_usage_daily', ...)`, the view's own row count grows and `app.get_report_usage_daily` returns the correct `preview_count`/aggregate for the exact tenant/report/day queried.
2. **`CONCURRENTLY` genuinely executes** — the refresh succeeds inside a `SECURITY DEFINER` `plpgsql` function body via dynamic `EXECUTE format(...)`, not merely asserted to compile.
3. **Reconciliation is real** — the completed run's own `reconciled` column is `true`, computed by comparing the view's post-refresh row count against an independently-computed `count(distinct ...)` over the live source table.
4. **A genuine failure is captured, never raised to the caller** — a disposable materialized view registered then dropped produces a `status='failed'` run with a real, non-null `error_reason` (an actual Postgres "relation does not exist" message via `sqlerrm`), and the function returns normally rather than propagating an exception.
5. **Tenant isolation on the ONLY read path is real** — `get_report_usage_daily` for tenant1 never returns tenant2's own row; a tenant2 actor querying tenant1's own data is denied `insufficient_authority` outright.
6. **Authority is real** — a non-Supreme actor is denied both `register_analytics_view` and `refresh_analytics_view`; an unregistered `view_code` is rejected with `analytics_view_unknown`.
7. **Schema-privilege defense in depth is real** — zero `anon` EXECUTE on any of the 3 new functions; zero `authenticated` direct INSERT/UPDATE/DELETE on the two new tables; zero `authenticated`/`anon` privileges of ANY kind on `app.mv_report_usage_daily` itself, confirmed via `information_schema.role_table_grants`.
8. **Audit trail is real** — `register_analytics_view` and `refresh_analytics_view` each recorded a genuine `app.audit_logs` row, confirmed by direct query.
