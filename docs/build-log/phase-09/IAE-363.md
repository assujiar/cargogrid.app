## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260808300000_create_intelligence_disaster_recovery_enterprise_support.sql`). Summary:

1. **Genuinely greenfield, and deliberately non-duplicative** — confirmed by direct grep before writing any code. This checkpoint does NOT rebuild the pre-existing, real `app.support_access_grants`/`app.support_access_sessions` (`PLT-1xx`, already case/purpose/time-bound staff impersonation — Prompt 363 §26's own requirement is already a live mechanism there) nor `app.ticket_escalation_policies` (Ticketing's own, much larger escalation engine); its own new tables (DR restore-test evidence, support entitlements, onboarding checklist) are genuinely additive.
2. **New `SUP` entitlement module** (`View`/`Configure`/`Approve`) — Prompt 363's own workstream is "Reliability and Customer Success", distinct from every prior Group 7/8 module, and needs a genuine, separate authority tier.
3. **"Do not promise RPO/RTO beyond actual tested evidence" is enforced structurally**: a `passed` restore-test result REQUIRES real `observed_rpo_minutes`/`observed_rto_minutes`; a `failed` result REQUIRES a real `failure_reason`, `recovery_steps`, and `retest_scheduled_at` (Prompt 363 §22's own alternative flow). A `dedicated`-scoped test is rejected outright unless the tenant genuinely has an active dedicated deployment — a real, structural composition with `IAE-032`'s own `app.resolve_tenant_deployment_type`.
4. **`app.enterprise_onboarding_checklists` is the real, structural "Main flow"** (Prompt 363 §21) — five of its six items are computed LIVE every time they are (re-)verified, never a caller-asserted rubber stamp: SSO from `app.integration_connections` (`IAE-026`'s own adapters), API from `app.api_keys`, integrations from `app.integration_connections` (any non-SSO adapter), and DR evidence from this checkpoint's own `app.dr_restore_tests` (requiring a real, passed test across all five DR component scopes). The sixth, `hypercare_plan_acknowledged`, is a real, honest human attestation with no automated signal available anywhere in this repository — deliberately gated at the higher `SUP:Approve` tier since it is the final sign-off that green-lights production readiness.
5. **`app.support_entitlements`'s own `enterprise_24_7` tier REQUIRES a real escalation contact email and a real, positive P1 response-time value** — "Enterprise 24/7/P1 support follows RPD-010 and contract terms" enforced structurally, never a hollow tier claim.
6. **DR runbooks cover "database, files, secrets, jobs, integrations and monitoring"** (Prompt 363 §24) — mapped honestly onto five real component-scope categories (`database`, `backup`, `secrets`, `jobs_integrations`, `observability`), reusing `IAE-032`'s own category vocabulary where the concept is identical.
7. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement.
8. Per the standing convention since `PLT-118`: explicit, redundant `revoke execute on all functions in schema app from public`.
9. **`app.resolve_latest_dr_restore_status`** is the bare-tenant-id, no-actor-parameter default-resolution function this checkpoint's own DR evidence needs — granted `service_role` ONLY from the very first draft, continuing the pattern `IAE-032`/`IAE-033`/`IAE-034` all already established correctly.
