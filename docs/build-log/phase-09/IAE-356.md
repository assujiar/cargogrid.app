# IAE-356 — IP Restriction and Network Access

**Prompt ID:** `CG-S14-IAE-028` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/356_IP_RESTRICTION_NETWORK_ACCESS_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; third capability of Group 7, "Enterprise Security and Governance", Prompts 354-359 — reaches `VERIFIED` only at that group's own Tier C review).

## 1. What this checkpoint builds

Enterprise IP/network access restriction: per-tenant CIDR allowlists with a real, structural three-mode enforcement lifecycle (`disabled → dry_run → enforced`), denied-access logging, and an emergency bypass break-glass path. Depends only on Platform identity/RBAC primitives and reuses `IAE-027`'s own `SEC` module — the third and final capability of Group 7's "Enterprise Security" workstream to share it.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260807200000_create_intelligence_ip_restriction_network_access.sql`). Summary:

1. **Real CIDR containment, not string matching** — `app.ip_allowlist_entries.cidr` is a genuine Postgres `cidr` column; `app.assert_ip_allowed` uses the native `<<=` containment operator, correctly handling both IPv4 and IPv6 for free (Prompt 356 §20 "Test IPv4/IPv6") since these are Postgres built-in types, not a repository-authored parser.
2. **Dry-run is a real, structural enforcement MODE, not a UI toggle** — `app.ip_allowlist_policies.enforcement_mode` (`disabled`/`dry_run`/`enforced`). `app.assert_ip_allowed` NEVER denies while `dry_run`, only logs what it WOULD have denied. Moving to `enforced` structurally requires at least one active allowlist entry to already exist (the lockout guard); moving to `dry_run`/`disabled` has no precondition, the real break-glass rollback path.
3. **Reuses the `SEC` entitlement module** (`IAE-027`) — no new module.
4. **Emergency bypass mirrors `app.mfa_exceptions`'/`app.support_access_grants`' own break-glass shape exactly**: `SEC:Approve`-gated, a real higher-authority grant, short CHECK-enforced expiry, target-actor-scoped, self-approval forbidden at the CHECK-constraint level.
5. **Proxy/header trust is disclosed as an application-layer concern** — this checkpoint's functions take an already-resolved IP address as a plain parameter and never parse a raw request header themselves; the `middleware.ts` change that would derive and pass that IP on every real request is disclosed, not built.
6. **Denied (and dry-run-would-deny) access is logged to a real, append-only table** (`app.ip_access_evaluations`) — `disabled` mode logs nothing at all (avoids unbounded growth for tenants who never turn this on).
7. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement.
8. Per the standing convention since `PLT-118`: explicit, redundant `revoke execute on all functions in schema app from public`, applied from the first draft.

## 7. Tier B — recurring defect taxonomy self-check

- **Self-caught during db-test authoring:** two evaluation rows inserted within the same transaction share the identical `now()` value (Postgres freezes `now()` for the whole transaction), so an assertion ordering by `occurred_at desc limit 1` to find "the most recent row" was nondeterministic under a tie. ## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`app.set_ip_allowlist_enforcement_mode`**: default mode is `disabled`; `SEC:View`-only actor rejected; moving straight to `enforced` with zero active entries is rejected (`ip_allowlist_no_active_entries`, the lockout guard, live-proven before any entry exists).
2. **`app.add_ip_allowlist_entry`**: a malformed CIDR string is rejected via a clean, named `ip_allowlist_invalid_cidr` error, never a raw Postgres type-cast crash; a well-formed IPv4 CIDR (`203.0.113.0/24`) and a well-formed IPv6 CIDR (`2001:db8::/32`) both succeed and round-trip byte-exact.
3. **`app.assert_ip_allowed` under `dry_run`**: an in-range IP is allowed; an out-of-range IP is NEVER denied (no exception) but IS logged as `dry_run_would_deny` — live-verified by reading the actual log row, not merely trusting the call's own success.
4. **Scope isolation**: an entry scoped `admin` does not authorize an `api`-scope check against the same address — live-proven via the logged evaluation row.
5. **Real enforcement**: once `enforced` (now legal, since active entries exist), an out-of-range IP is genuinely denied (`ip_not_allowed`) and an in-range one is genuinely allowed; a malformed IP address under `enforced` is denied, never a raw crash; revoking the matching entry makes a previously-allowed IP genuinely denied on the next check.
6. **Break-glass**: the real rollback path (`enforced → disabled`) always succeeds with no precondition, and `assert_ip_allowed` becomes a true no-op again with zero new log rows recorded for two probes (one in-range, one out-of-range) while disabled.
7. **Emergency bypass**: self-approval rejected at the CHECK-constraint level; a genuinely different `SEC:Approve` holder (Supreme Admin) approves; `app.has_active_ip_allowlist_bypass` correctly reflects `false` before the grant and `true` after.
8. **Cross-tenant isolation**: a tenant-2 admin cannot list tenant-1's own allowlist entries and cannot configure tenant-1's own policy (`insufficient_privilege`).
9. **RLS default-deny**: a direct `authenticated` `select` on all four new tables is denied at the raw-RLS level.
10. **`anon` holds zero `EXECUTE`** on any of the 11 new functions.

Two real, cross-file issues surfaced while bringing up `IAE-030` and re-running the full `pnpm run db:test` suite — neither reachable from this file's own standalone run, since a fresh disposable database has no other capability's fixtures loaded yet:

1. **Fixture id range collision (real, full-suite-only):** this file's own `iaeip`/`iaeip2` fixture originally used id range `00000000-0000-0000-0000-000028xxxxxx`, which collides with the already-existing `scripts/db-tests/forecasting-recommendation.sql` (Group 6, which independently also claimed `000028xxxxxx`). Fixed by renumbering this file's own range to `000032xxxxxx` (sed, then re-verified: this file standalone, then the full suite past this point, both clean).
2. **A real authority-surface gap (ATW-032/ISS-2026-033), caught by `scripts/db-tests/rbac-enforcement.sql`'s own pre-existing drift gate:** `app.get_or_create_ip_allowlist_policy`, `app.assert_ip_allowed`, and `app.has_active_ip_allowlist_bypass` each took only bare tenant/target identifiers with NO actor/authority parameter of their own — any authenticated identity of ANY tenant could read (and, for the first, silently bootstrap via a real `INSERT`) another tenant's own IP allowlist policy, probe another tenant's own allowlist as an allow/deny oracle, or learn whether an arbitrary identity in an arbitrary tenant holds an active bypass grant. Fixed:
   - `get_or_create_ip_allowlist_policy` was split into an internal-only `app._get_or_create_ip_allowlist_policy(p_tenant_id)` bootstrap primitive (no grant to anyone) plus a new, actor-gated public `app.get_or_create_ip_allowlist_policy(p_tenant_id, p_actor_auth_user_id)` requiring `SEC:View` — `app.set_ip_allowlist_enforcement_mode`'s own internal bootstrap call was repointed at the private helper (it already independently enforces `SEC:Configure`).
   - `assert_ip_allowed` and `has_active_ip_allowlist_bypass` cannot be gated the same way: `assert_ip_allowed`'s own design (§2 point above the fold) deliberately keeps it reachable by an API-key-authenticated caller with no `auth_user_id` at all, so an `evaluate_permission`-style identity check would break that use case outright. Both were simply narrowed to `service_role`-only — trusted, system-level primitives meant to be invoked by server-side code that has already resolved the correct `tenant_id` through its own authorized path, never called directly by an arbitrary end-user session. Neither was ever wired to a browser-facing surface.
   - `scripts/db-tests/ip-restriction-network-access.sql` and `server/queries/ip-restriction.ts`/`server/mutations/ip-restriction.ts` were updated to match (new required `actorAuthUserId` parameter on `getOrCreateIpAllowlistPolicy`; clarifying doc comments on `assertIpAllowed`/`hasActiveIpAllowlistBypass` noting the service-role-only calling convention; new assertion: `admin2`, a different tenant's own admin, rejected reading tenant1's own policy; `admin1`/`viewer1`, both holding `SEC:View`, succeed).

None of the three functions had ever been committed to git before this fix. Both fixes independently re-verified: this file's own db-test re-run clean standalone, `rbac-enforcement.sql` re-run clean standalone, and the full suite re-run past this point clean.
