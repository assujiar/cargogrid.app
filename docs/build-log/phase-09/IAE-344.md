# IAE-344 — Carrier, Port, Airport and Customs Integrations

**Prompt ID:** `CG-S14-IAE-016` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/344_CARRIER_PORT_AIRPORT_CUSTOMS_INTEGRATIONS_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — third prompt of the merged Batch 4, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at the merged batch's own single Tier C review close)

## 1. What this checkpoint builds

Governed, case-by-case integration adapters for external logistics ecosystem providers — carrier status/tracking APIs, port terminal operating systems, airport cargo community systems, and customs broker/authority APIs — per RPD-038 ("no generic provider abstraction, case-by-case adapters"). Confirmed genuinely greenfield by direct grep before writing any code: no carrier/port/airport/customs entity table exists anywhere in this repository. Composes three already-built primitives rather than duplicating them: IAE-336's Integration Hub (`app.integration_connections`/`app.integration_connection_credentials`) for provider credentials, the OPS Document Requirement engine (`app.document_requirement_definitions`, already supports `party='carrier'`) for carrier document evidence, and `app.shipment_mode_profiles` (OPS-171) for shipment correlation by AWB/BL/booking/container reference. Inbound events are evidence-only — they are correlated to a shipment on a best-effort basis but never write to `app.shipment_orders` directly, honoring the business rule "external events cannot bypass source-domain lifecycle rules."

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260805030000_create_intelligence_carrier_port_airport_customs_integrations.sql`, 9 numbered decisions). Summary:

1. **Case-by-case adapters, no generic provider abstraction (RPD-038).** Four distinct adapter codes seeded (`carrier_status_api`, `port_terminal_edi`, `airport_cargo_system`, `customs_broker_api`), reusing `app.integration_connections`/`app.integration_connection_credentials` (IAE-336) directly — the same stronger-isolation pattern IAE-014/015 already established, never the older, disclosed-weaker `app.third_party_provider_connections.webhook_secret_value` pattern (ATW-226E, kept as-is per `ADR-0025` Part B — GPS/telematics ingestion is unrelated and untouched).
2. **Inbound events are evidence, never a second writer of Operations truth.** `app.logistics_partner_events` records every inbound status/milestone/document/customs event and best-effort correlates it to a shipment via `app.shipment_mode_profiles`' own AWB/BL/booking/container/flight reference fields — it never calls `app.transition_shipment_order` itself. A staff member reviews a matched event (`app.review_logistics_partner_event`) and, if it should advance shipment status, does so separately through the existing canonical flow, citing the event's own id as `evidence_ref`.
3. **Document requirements need no schema change — confirmed already adequate as-is, not a scope cut.** `app.document_requirement_definitions.party` (OPS-176) already accepts `'carrier'`, verified by direct read before writing any code; only three new `app.document_types` codes are registered (`customs_declaration`, `bill_of_lading`, `certificate_of_origin`), mirroring HRT-277's own direct-INSERT seeding precedent exactly. A tenant configures its own `document:<code>` definition via the existing, unmodified document-type config UI.
4. **A brand-new dedicated job type, not a reuse of the dormant `integration_sync`.** Direct grep found `integration_sync` already has a REAL producer (HRT-277's onboarding/offboarding provisioning) with an unrelated payload shape, even though it still has zero real consumer. Reusing it would force a shared worker to disambiguate two structurally unrelated shapes — the exact risk RPD-038/`ADR-0025` Part C warn against. `logistics_partner_sync` is added instead, following the standing widening convention across THREE places kept in lockstep: `app.jobs_job_type_check` (SQL), `app.generic_job_types()` (SQL), and BOTH `GENERIC_JOB_TYPES` (`server/contracts/background-job/background-job.ts`) AND `IMPORT_EXPORT_JOB_TYPES` (`server/contracts/import-export/import-export.ts` — that contract's own header discloses `app.jobs` reuses this one row shape for every generic job type). This checkpoint is the type's first and only producer AND consumer.
5. **Connection health/test is already fully solved — confirmed adequate as-is.** The existing Integration Hub connection detail console (`app/(tenant)/[tenantSlug]/integrations/[connectionId]/`, IAE-336) already drives `app.record_integration_health_check` generically for any adapter code. No new "test connection" code or UI is built.
6. **Inbound webhook receiver mirrors ATW-226E's GPS receiver shape exactly** (raw-text body, `x-webhook-timestamp`/`x-webhook-signature` headers, HMAC-SHA256 over `"<timestamp>.<rawPayload>"`, 5-minute replay tolerance, a dedicated per-client_key rate-limit ledger, a single `anon`-granted ingestion RPC that never raises), but the HMAC secret is read from `app.integration_connection_credentials`, never `app.third_party_provider_connections.webhook_secret_value`. One deliberate deviation from the mirrored shape: duplicate detection uses an atomic `insert ... on conflict do nothing returning *` rather than ATW-226E's own two-step exists-check-then-insert (a real, disclosed, pre-existing, out-of-scope race) — the same proactive Tier C lesson `app.queue_notification` (IAE-014) already applied, written correctly here from the start.
7. **The outbound "poll" direction is `logistics_partner_sync`'s real first consumer**, proactively reusing `app.check_integration_connection_active` (IAE-336, disclosed at the time as having zero real callers) and the SSRF guard (`lib/webhooks/ssrf-guard.server.ts`) — a fourth real outbound HTTP client relying on it.
8. `INTHUB:Configure`/`INTHUB:View` gate connection setup unchanged; `OPS:View`/`OPS:Edit` gate viewing and reviewing inbound events, mirroring OPS-176's own document-checklist review authority exactly.
9. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public;`.

## 13. Merged Batch 4 Tier C review — findings and fixes against this capability

The merged Batch 4's own mandatory Tier C review (4 parallel adversarial lenses: spec-compliance; security/RLS/tenant, live-tested; correctness/concurrency, live-tested; cross-prompt integration) ran against all six independently-built capabilities together on 2026-08-21, closed by one bounded fix migration (`supabase/migrations/20260805070000_harden_intelligence_batch4_tier_c_review_fixes.sql`) plus targeted TypeScript fixes, independently re-verified by the orchestrating session. Full cross-capability findings/fix summary lives in `docs/build-log/phase-09/00_EXECUTION_INDEX.md` §14; this section records only what concerns IAE-016 specifically.

- **[High, fixed] `app.ingest_logistics_partner_webhook_event`'s own inbound rate limiter counted bad-signature attempts by `client_key` alone, with no `connection_id` scope, and was an unlocked count-then-act.** The security lens live-reproduced an attacker spoofing `X-Forwarded-For` to share a `client_key` with a legitimate provider, then flooding 10 bad-signature attempts against a DIFFERENT tenant's own connection — the genuine tenant's own next delivery was throttled (`rate_limited`) purely because it happened to share that attacker-chosen key. The correctness lens separately live-reproduced the unlocked check blowing through the documented 10-attempt/15-minute budget by 3.6x under 40-way concurrency (36 admitted). Fixed: the counter is now scoped by `(connection_id, client_key)` and serialized with `pg_advisory_xact_lock` — both live-reproduced fixed (a genuine tenant-1 delivery is no longer throttled by tenant-2's own bad-signature attempts sharing the same client_key).
- **[High, fixed] `app.trigger_logistics_partner_poll_sync` was granted to `authenticated` but was completely unreachable through the app's own RLS-scoped client.** The spec-compliance lens found it SECURITY INVOKER, calling a `service_role`-only authority helper — a genuine forged-authenticated-session probe confirmed `permission denied`. This is one of four identical instances across the batch (IAE-017/018/019 share the same defect class). Fixed: now SECURITY DEFINER plus `app.assert_actor_is_session_identity`, mirroring every correctly-working SECURITY DEFINER sibling in this same migration; live-reproduced fixed via a genuine forged authenticated session.
- **[Medium, fixed] `app.record_logistics_partner_sync_event` accepted a `connection_id` belonging to a DIFFERENT tenant with no cross-check.** The security lens live-reproduced this against every evidence-writer function across the batch that takes both `p_tenant_id` and `p_connection_id`. Not exploitable end-to-end today (the function is `service_role`-only, and the shipped poll worker always resolves both ids from the same trigger-built payload) but a real structural gap. Fixed: now cross-checks `p_connection_id` genuinely belongs to `p_tenant_id` before writing.
- **[Medium, fixed] `app.review_logistics_partner_event` had no terminal-state guard.** The correctness lens live-reproduced two concurrent reviewers both being told they succeeded, the second decision silently overwriting the first — a lost update, with no optimistic-concurrency token on this table at all. Fixed: only a not-yet-decided (`received`) event may now be decided; a re-decision attempt raises a clean, named `logistics_partner_event_already_reviewed` error instead of silently overwriting.
- **Disclosed, not fixed — real future scope, not defects in shipped code.** The spec-compliance lens found this capability the largest concentration of undisclosed scope gaps in the batch: no per-provider mapping-rules layer exists (all four adapters share one hardcoded payload shape, so onboarding a real port/customs feed would need code changes despite the prompt's own "per-provider mapping rules" requirement); the `document_available` event type has no actual document-record consumer anywhere (the three seeded document types have zero code path linking an event to a document); and the error-queue table (`app.logistics_partner_ingestion_attempts`) has RLS enabled with zero policies and no read RPC at all, so no tenant owner can ever see a schema-validation failure or malformed webhook the prompt's own §15 names as a required "error queue" screen. All three are real, substantial future-scope items judged too large for this bounded Tier C pass; recorded here for a future checkpoint. Separately disclosed, not fixed: the inbound webhook's own `X-Forwarded-For`-derived `client_key` is still the FIRST hop (caller-controlled, not the trusted proxy-appended value) — an inherited, repository-wide pattern shared by the pre-existing GPS receiver and 6 other routes, out of this bounded pass's own scope to redesign; and non-constant-time HMAC comparison, inherited verbatim from the pre-existing ATW-226E precedent.
