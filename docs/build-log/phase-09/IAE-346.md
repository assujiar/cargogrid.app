# IAE-346 — External Accounting and HR Integrations

**Prompt ID:** `CG-S14-IAE-018` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/346_EXTERNAL_ACCOUNTING_HR_INTEGRATIONS_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — fifth prompt of the merged Batch 4, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at the merged batch's own single Tier C review close)

## 1. What this checkpoint builds

Controlled, explicit-ownership sync with external accounting and HR systems, structurally incapable of overwriting CargoGrid's own HRIS/Finance truth: no function in this migration ever writes to `app.employees`, `app.employee_lifecycle_versions`, `app.finance_accounts`, or `app.finance_journals`. The genuine new contribution is a field/entity **ownership-direction** primitive — confirmed absent repository-wide before writing any code — that makes "CargoGrid source-domain ownership must be explicit before sync" a hard structural gate rather than a convention, and governs whether a detected divergence is a flagged conflict or an expected, informational read-only reference.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260805050000_create_intelligence_external_accounting_hr_integrations.sql`, 9 numbered decisions). Summary:

1. **Case-by-case adapters (RPD-038).** Two adapter codes seeded (`external_accounting_system`, `external_hr_system`), reusing `app.integration_connections`/`app.integration_connection_credentials` (IAE-336) directly.
2. **Field/entity ownership direction is this checkpoint's own genuine contribution** — confirmed absent repository-wide by direct grep before writing any code. `app.external_sync_entity_mappings` makes ownership explicit a hard gate: every ingestion/review/list RPC refuses to act on an entity_type with no active mapping row. `ownership_direction` (`cargogrid_source`/`external_source`/`bidirectional`) governs how a detected diff is classified — `external_source` matches this prompt's own Alternative flow verbatim ("Accounting system remains source for a subset during transition; CargoGrid records read-only references and exceptions").
3. **This checkpoint NEVER writes to `app.employees`/`app.employee_lifecycle_versions`/`app.finance_accounts`/`app.finance_journals`** — structurally, not by convention (grep-verified, no INSERT/UPDATE/DELETE grant anywhere in the migration against any of those tables). Mirrors HRT-282's own "Payroll NEVER writes to any `app.finance_*` table directly" boundary discipline, applied even more strictly: this checkpoint has no counterpart "acknowledge and apply" RPC at all yet — every inbound sync stops at evidence + conflict-flagging.
4. **Entity linking is ALWAYS explicit, never best-effort/auto-matched** — a deliberate divergence from IAE-016/017's own reference-field correlation. Employee identity linking carries higher misattribution risk; `app.link_external_sync_entity` requires a human to explicitly assert the correspondence once.
5. **"Dry-run mapping and validation" is an inherent property of this design, not a separate mode — confirmed already adequate as-is, not a scope cut.** Because ingestion never writes to a domain table, every sync IS a dry run in the sense that matters.
6. **One shared job type, `external_sync`**, covering both entity types via an `entity_type` payload discriminator — mirrors IAE-016's own `logistics_partner_sync` precedent (one job type spanning multiple adapter categories). Widened in the standing four-place lockstep.
7. **Authority is entity-type-dispatched**: `app.check_external_sync_entity_authority` resolves `employee` → `HRS`, `gl_account` → `FIN`, mirroring IAE-017's own "FIN:Edit, not instance-level" divergence, extended to a second module.
8. **Cost metering (`RPD-028`) does not apply here** — this prompt's own business rules cite no per-call provider billing; `app.compute_provider_billed_amount` is deliberately not reused.
9. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public;`.

## 8. Residual/disclosed limitations

- **No "acknowledge and apply" counterpart RPC was built** — disclosed explicitly in design decision 3. This checkpoint stops at evidence + conflict-flagging; a human currently acts on a flagged conflict or a read-only reference through HRIS/Finance's own existing, unmodified update paths, off-platform. Building a governed "apply an external_source-owned field to the internal record" RPC — mirroring HRT-282's own `app.acknowledge_payroll_finance_handoff_batch` as the precedent for a receiving-domain-gated acknowledgement — is real, identified future work, not an oversight.
- **No dedicated setup/mapping-table/conflict-queue UI was built** — consistent with every prior Batch 4 capability's own scope decision. The RPC surface is real and fully tested; a tenant-facing mapping configuration and conflict-review screen is deferred to a future checkpoint.
- **Field diffs are computed over a bounded, disclosed field list per entity type** (5 fields for `employee`: fullName/workEmail/employmentType/positionTitle/hireDate; 5 fields for `gl_account`: code/name/accountType/normalBalance/status) — never a blind generic diff over arbitrary payload keys, per RPD-038's "no generic connector claim" business rule. A tenant needing a wider field set would need a case-by-case extension, not a configuration toggle — a deliberate, disclosed scope boundary.
- **The external provider's own poll-response contract (`{records: [{externalEntityId, payload}]}`) is a real, disclosed, repository-authored shape** — no live accounting/HR provider integration exists to confirm against; a genuinely new provider's own shape would need its own adapter-specific parsing.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

2. **`set_external_sync_entity_mapping` is `INTHUB:Configure`-gated and genuinely idempotent** — a second call with a different `ownership_direction` updates the SAME row in place (exactly one row after two calls), never a duplicate.

## 13. Merged Batch 4 Tier C review — findings and fixes against this capability

The merged Batch 4's own mandatory Tier C review (4 parallel adversarial lenses: spec-compliance; security/RLS/tenant, live-tested; correctness/concurrency, live-tested; cross-prompt integration) ran against all six independently-built capabilities together on 2026-08-21, closed by one bounded fix migration (`supabase/migrations/20260805070000_harden_intelligence_batch4_tier_c_review_fixes.sql`) plus targeted TypeScript fixes, independently re-verified by the orchestrating session. Full cross-capability findings/fix summary lives in `docs/build-log/phase-09/00_EXECUTION_INDEX.md` §14; this section records only what concerns IAE-018 specifically.

- **[High, fixed] `app.list_external_sync_records_for_tenant`'s `p_entity_type => null` path leaked full internal employee PII to a FIN-only actor with ZERO HRS permission.** The security lens live-reproduced this precisely: the authority check resolved `HRS:View OR FIN:View` as a single top-level gate, but the row filter below it had no per-row entity-type/module term at all — a FIN-only actor calling with `p_entity_type => null` read every `employee` row's `raw_payload` AND `field_diffs` (which bakes in the INTERNAL `app.employees` values, worse than the raw external payload alone). Fixed: each row is now filtered by its OWN entity_type's own real module authority (`HRS:View` for `employee` rows, `FIN:View` for `gl_account` rows) rather than a blanket pass once ANY one module's View permission is held. Live-reproduced fixed: a FIN-only actor now sees exactly 0 employee rows via `p_entity_type => null`, while explicitly requesting `entity_type='employee'` is still correctly denied.
- **[High, fixed] `app.trigger_external_sync` was granted to `authenticated` but was completely unreachable through the app's own RLS-scoped client** — the same defect class as IAE-016/017/019. Fixed identically: now SECURITY DEFINER plus `app.assert_actor_is_session_identity`.
- **[Medium, fixed] `app.record_external_sync_snapshot` accepted a `connection_id` belonging to a different tenant, AND never cross-checked `p_adapter_code` against the connection's own real adapter, with no cross-check at all.** Fixed: now cross-checks `p_connection_id` belongs to `p_tenant_id` AND carries the declared `p_adapter_code`.
- **[Medium, fixed] `app.review_external_sync_conflict` had no terminal-state guard** — the identical lost-update race class as IAE-016/017's own review functions, adapted for this table's own three live states (`no_conflict`/`conflicts_detected` may still be decided once; `reviewed`/`dismissed` are terminal). Fixed: a re-decision attempt now raises a clean, named `external_sync_record_already_reviewed` error.
- **Disclosed, not fixed — real future scope, already substantially disclosed in this capability's own build log §8.** The spec-compliance lens confirmed the "executes approved sync"/rollback half of this prompt's own main flow remains genuinely unbuilt (this checkpoint stops at evidence + conflict-flagging by design decision 3, already disclosed); ownership direction is per entity-TYPE, not per FIELD, despite the build log's own §1 describing it as a field-level primitive (the bounded, hardcoded field-comparison list is disclosed, the "field-level ownership" framing is a minor overstatement, corrected here); and malformed provider records during a poll are silently dropped with an in-memory counter rather than a persisted exception, with no idempotency/dedup key on `app.record_external_sync_snapshot` itself (a deliberate divergence from IAE-016/017's own `unique(connection_id, provider_event_id)` shape, undisclosed until now).
