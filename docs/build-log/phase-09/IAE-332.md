# IAE-332 — Saved View and Configurable Report

**Prompt ID:** `CG-S14-IAE-004` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/332_SAVED_VIEW_CONFIGURABLE_REPORT_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — third prompt of Batch 1, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 1's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-332 is a real, cross-domain "save this report configuration and optionally share it with the tenant" mechanism on top of the `IAE-002` report catalog (`app.report_types`). A saved view is a named bookmark of (report code, display columns, run parameters, sort, grouping) — it stores no data of its own; running a view always replays through the unchanged `app.record_report_run`/`app.enqueue_report_export`. Sharing shares the config only, never underlying record access (Prompt 332 §24).

## 2. Design decisions (cited, not re-derived)

1. **A pre-existing, narrower precedent already exists and is deliberately not reused as the storage table.** `app.procurement_dashboard_saved_views` (`PRC-266`, `20260730780000`) is a real, `VERIFIED` saved-view mechanism, but scoped to exactly Procurement's own 7 fixed dashboard `metric_group` values, owner-only (no sharing — its own header: "distinct from every tenant-wide... table"), and has no `columns`/`grouping` field. Prompt 332 asks for the opposite on the differentiating axis that matters: cross-domain (any `app.report_types` code) AND real sharing. This checkpoint builds a new, general table rather than widening PRC-266's own already-`VERIFIED`, narrowly-scoped shape — the same "new general mechanism beside an already-correct narrower one" precedent `IAE-002` itself set relative to each domain's own pre-existing `get_dashboard_*` functions. PRC-266's own CRUD shape (idempotency-key replay comparing the full target tuple, `for update` + explicit `stale_version` guard, "not found" folding not-found and no-access together for owner-only lookups) is mirrored directly rather than re-derived.
2. **`filters` IS the underlying report's own `parameters` bag, not a second query language.** A saved view is a bookmark, replayable through the existing, unchanged report-execution path — this migration adds no new data-query SQL. `filters` is validated against the report's own current `parameter_schema` via `app.validate_report_parameters` (`IAE-002`, reused directly).
3. **`columns`/`sort`/`grouping` are presentational-only and structurally validated via `app.validate_config_value`** (`PLT-11x`'s own generic, depth/size-bounded, injection-shaped-string-rejecting JSON validator, already reused by `PRC-266` for the identical purpose) — reused directly rather than a third bespoke validator. Because a saved view stores no row data of its own, "reintroducing a hidden field" (Prompt 332 §24) cannot leak anything structurally: requesting an unmasked column name still only ever receives whatever `record_report_run`'s own caller already computed and masked for that run.
4. **`REP:Configure` gates only creating/updating a `tenant`-shared view** — the same "configuring a shared reporting artifact" authority `IAE-003` established as this module's second real consumer. A `private` view requires no elevated permission beyond ordinary, non-`customer_user`-layer tenant membership.
5. **Staleness detection, not silent breakage** (Prompt 332's own Alternative flow). `report_type_version_id` is stamped at create/update time; the UI compares it against the report type's own current version (via `listReportTypeVersions`' own newest-first ordering) to disclose `isStale`, which still lets the view run — the underlying report's own live parameter validation is the real gate, not a saved view's own possibly-outdated stamp.
6. **Export/scheduled-report compatibility is reuse, not a new RPC.** "Export this saved view" composes the EXISTING `enqueueReportExport` (`IAE-002`) with the view's own `reportTypeCode`/`filters` at the service layer — no new database function. `IAE-006` (Prompt 334, Scheduled Reports) owns actually running a view on a schedule; this checkpoint deliberately builds no scheduling mechanism (disclosed, not a gap — the WBS's own downstream-impact note cites `IAE-334`).
7. **ATW-032/C-13, C-04 and the RLS customer-layer narrowing were all applied from the first draft** — standing lessons from `IAE-002`/`IAE-003`'s own Tier B reviews, not found-and-fixed again here. Two real, distinct bugs WERE found and fixed before commit:
   - **Functional, not security**: two internal calls to `app.has_active_tenant_membership`/`app.is_supreme_admin` omitted the optional `p_auth_user_id` argument, silently defaulting to `auth.uid()` (null outside a real client session) instead of the actor being checked — caught immediately by the very first standalone db-test run (a genuine `insufficient_authority` for an actor who plainly held membership), fixed by passing `p_actor_auth_user_id` explicitly at both call sites.
   - **Real ATW-032 authority-surface gap, caught only by the full cumulative `db:test` run's own `rbac-enforcement.sql` sweep, not by the standalone file**: `update_saved_report_view`/`delete_saved_report_view` gate on a real ownership-equality check (`owner_auth_user_id <> p_actor_auth_user_id`) but call none of the three helpers (`app.evaluate_permission`/`app.can_access_record`/`app.assert_session_identity_in_tenant`) the sweep's static call-graph analysis recognizes as a provable authority check — flagged by name as "granted to `authenticated` with no authority check anywhere in their call graph." Fixed by adding `app.assert_session_identity_in_tenant(v_view.tenant_id)` to both functions immediately after their own row lookup, mirroring `PRC-266`'s own `update_procurement_dashboard_saved_view`'s identical two-check shape (ownership plus a real, sweep-recognized permission call) rather than inventing a bespoke exception to the sweep's own reviewed-and-justified list.

## 5. Schema

`app.saved_report_views` (new): `id`, `tenant_id` (FK), `report_type_code` (FK into `app.report_types`), `report_type_version_id` (FK into `app.report_type_versions`, nullable, staleness stamp), `owner_auth_user_id`, `owner_label`, `name`, `description`, `sharing_scope` (`private`/`tenant`), `columns` (jsonb array), `filters` (jsonb object), `sort`/`grouping` (jsonb objects), `idempotency_key`, `record_version`, `created_by`, `created_at`, `updated_at` (touch trigger). Unique `(tenant_id, owner_auth_user_id, idempotency_key)` where not null.

## 6. RLS and grants

`select`: `app.is_supreme_admin() or owner_auth_user_id = auth.uid() or (sharing_scope = 'tenant' and app.has_active_tenant_membership(tenant_id) and not app.actor_holds_customer_user_layer(tenant_id))` — own-row access is unconditional (a `customer_user`-layer principal seeing their own saved-view config is not the leak `CG-S10-ATW-032` closes); tenant-shared-row access is narrowed exactly like every other tenant-wide SELECT policy since that convention, applied from this migration's first draft (not a found-and-fixed gap this time — see `IAE-003`'s own §2 item 5 for why that lesson is now applied proactively). `insert`/`update`/`delete` is `service_role`-only. Schema-privilege defense in depth (zero `anon` EXECUTE, zero `authenticated` direct DML) live-verified in `scripts/db-tests/saved-report-views.sql`.

## 8. Residual/disclosed limitations

- **No scheduling mechanism.** Running a saved view on a recurring cadence is `IAE-006`'s (Prompt 334, Scheduled Reports) own job — deliberately not built here (§2 item 6).
- **`sort`/`grouping` have no dedicated UI input in this checkpoint** — accepted and validated by the API/RPC layer, but the create/edit forms expose only columns/filters; a full drag-and-drop view builder is a disclosed future UI enhancement, matching the same pragmatic level of polish `IAE-003`'s own dashboard canvas established (ordered list, not a drag canvas).
- **No per-column field-level allowlist exists in `app.report_types` itself.** "Columns" is a free-form string array validated only structurally (`app.validate_config_value`); the real authority remains the underlying report's own masking at run time (§2 item 3) — disclosed as the correct, minimal design rather than fabricating a 29-report output-field catalog outside this checkpoint's own bounded scope.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **Private-vs-shared authority split is real** — a tenant member lacking `REP:Configure` creates a private view successfully but is denied `insufficient_privilege` for a `sharing_scope='tenant'` attempt; the same member's colleague holding `REP:Configure` succeeds at both.
2. **Filters are validated against the report's own live schema** — a filter bag missing a field the report type's own current `parameter_schema` marks `required: true` is rejected with `saved_view_unsafe_filters`; the identical call after supplying it succeeds and stamps `report_type_version_id` to that report's own CURRENT version id (confirmed by direct query, not merely asserted).
3. **Idempotency replay is real** — a repeated `create` call with the same key and tuple returns the IDENTICAL row id; the same key with a different tuple raises `idempotency_key_conflict`.
4. **Sharing never grants write access** — a non-owner's `update`/`delete` attempt against a `sharing_scope='tenant'` view both fail with `saved_report_view_not_found` (folded, non-disclosing); the owner's own identical calls succeed.
5. **Stale-version guard is real** — an `update`/`delete` call citing an expected version that has since moved on both fail with `stale_version`, never a silent overwrite.
6. **List visibility is exactly "own plus shared"** — a tenant member's own list contains both their own private view and a colleague's tenant-shared view, never a third party's still-private view; a cross-tenant actor's list call for the wrong tenant is denied outright (`insufficient_authority`), and their own tenant's list never contains the other tenant's rows.
7. **Schema-privilege defense in depth** — zero `anon` EXECUTE on any of the 4 new functions; zero `authenticated` direct INSERT/UPDATE/DELETE on the new table.
8. **Audit trail is real** — `create`/`update`/`delete` each recorded a genuine `app.audit_logs` row, confirmed by direct query.
