# IAE-330 — Reporting Engine

**Prompt ID:** `CG-S14-IAE-002` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/330_REPORTING_ENGINE_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — first prompt of Batch 1, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 1's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-330 is Phase 9's own first capability and the dependency root for the rest of Batch 1 (Dashboard Builder, Saved View, Analytics Materialized Views, Scheduled Reports all cite it). Rather than a second, parallel reporting engine, it extends the already-`VERIFIED` `app.report_types`/`app.report_runs` catalog COM-159 built (and Operations/Finance/Procurement have each since registered report codes into) with the three things Prompt 330 §13 asks for that no prior phase built: real report-definition **versioning**, structural per-report **parameter validation**, and a **cancel** path for still-queued exports. See `docs/adr/ADR-0025-*.md` for the reuse-boundary decision this checkpoint executes.

## 2. Design decisions (cited, not re-derived)

1. **`app.report_type_versions` is new, append-only history; `app.report_types` stays the one "current definition" row every existing caller already reads.** Publishing a new version (`app.publish_report_type_version`) updates `report_types`' own `source_function`/`parameter_schema`/`description`/`version` columns and appends a new history row in the same transaction — "current" and "history" can never drift apart. Mirrors the append-only-ledger-plus-derived-current-state shape already established elsewhere in this repository.
2. **`parameter_schema` defaults to `'{}'::jsonb` for all 29 pre-existing report codes, deliberately un-retrofitted.** Inventing 29 bespoke schemas by inference from each domain's own function signature was rejected as a correctness risk outside this checkpoint's own bounded scope — `app.validate_report_parameters` treats an empty schema as "no engine-level contract, defer to the domain function," so every existing report's behavior is byte-for-byte unchanged. The mechanism itself is proven end-to-end against one fresh, real test report type in `scripts/db-tests/reporting-engine.sql`, not merely asserted to exist.
3. **`app.validate_report_parameters` is closed-world once a schema exists, open-world before one does**: an empty schema always passes; a declared schema requires every `required: true` key present with a matching `jsonb_typeof` and rejects any undeclared key.
4. **`app.publish_report_type_version` is Supreme-only**, mirroring `app.register_report_type`/`app.retire_report_type`'s own already-ratified "reports are a product feature, not a tenant-authored config object" design (COM-159's own header). It has no interactive UI caller by design — same shape as `register_report_type`/`retire_report_type`, both also UI-less since a code-shipped catalogue's own intended caller is a future migration, not an admin panel (disclosed in §9, not a C-20 gap).
5. **`app.cancel_report_run` touches only `app.report_runs`, never `app.jobs`.** No generic `app.cancel_job` primitive exists on the shared durable queue (only domain-specific ones like `app.cancel_import_export_job`), and no live worker anywhere in this repository ever advances a `report_generation` job past `queued` — cancelling the bookkeeping row is the complete, correct action in this environment.
6. **Two Tier B self-review fixes, found before commit:**
   - **C-04** (`docs/standards/RECURRING_DEFECT_TAXONOMY.md`) — `publish_report_type_version` now locks the `report_types` row `for update` before computing the next version number; without it, two concurrent publishes for the same code could race on the insert.
   - **C-05** — `cancel_report_run` read `app.report_runs` by id (a `SECURITY DEFINER` function bypasses RLS) and would have raised `insufficient_authority` for a caller with no relationship to that run's own tenant, disclosing the id exists somewhere. It now raises the identical `report_run_not_found` a genuinely missing id produces for that case, mirroring the already-established `vendor_payment_term_proposal_not_found` precedent (`PRC-269`, `ISS-2026-054` C-05); a same-tenant colleague who is neither the requester nor holds `COM:Export` still gets a clear `insufficient_authority` (no enumeration risk within their own tenant).
7. **`ATW-032` (`ISS-2026-032`) actor-identity fix — a real, pre-existing gap this checkpoint closed, not merely avoided.** The repository-wide sweep (`scripts/db-tests/rbac-enforcement.sql`) requires every side-effecting, `authenticated`-granted function taking `p_actor_auth_user_id` to reach `app.assert_actor_is_session_identity` (directly, or transitively via `app.evaluate_permission`, which already calls it per `ATW-031`). It flagged three functions this migration's own diff touches: the two pre-existing COM-159 functions re-created here via `create or replace` (`app.register_report_type`, `app.record_report_run` — neither had ever called either primitive, a standing gap since Phase 2) and this checkpoint's own new `app.publish_report_type_version`. All three, plus `app.cancel_report_run` (a genuine fix, not merely linter-driven — its own check only ran inside a conditional branch a spoofed-identity match could skip), now call `app.assert_actor_is_session_identity` as their first statement. `app.enqueue_report_export` already called `app.evaluate_permission` unconditionally and needed no change.
8. **REST/GraphQL**: no new HTTP route. `app.report_types`/`app.report_runs`/`app.report_type_versions` already grant direct `select` to `authenticated` behind `report_runs`' own RLS policy — `server/queries/report.ts` reads them directly with the same "typed direct read over an already-RLS-scoped table" convention most `server/queries/*.ts` files already use. GraphQL parity remains the same disclosed, non-blocking residual gap every phase since 8 has carried (`ADR-0024` Part C) — no live GraphQL server exists in this repository.

Schema-privilege defense in depth (zero `anon` EXECUTE on any new function, zero `authenticated` INSERT/UPDATE/DELETE on `report_type_versions`) live-verified in `scripts/db-tests/reporting-engine.sql`.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **Definition versioning never rewrites prior evidence** — a `preview` run recorded against `iae_test_report` while its `parameter_schema` was still `{}` keeps citing version 1 after a Supreme Admin publishes version 2 with a real required-parameter schema.
2. **Parameter-schema enforcement is real, not cosmetic** — after publishing v2 (`{"currency": {"type": "string", "required": true}}`), a run omitting `currency` is rejected with `report_unsafe_parameters`; a run supplying it succeeds and stamps `report_type_version_id` to v2's own id.
3. **Zero regression for every pre-existing report** — `lead_aging` (empty schema, unchanged since COM-159) still accepts an arbitrary parameter bag after this migration.
4. **Actor-identity spoofing is rejected** — confirmed via the repository's own shared `rbac-enforcement.sql` sweep (not a bespoke local check) that `register_report_type`/`record_report_run`/`publish_report_type_version`/`cancel_report_run` all now reach `app.assert_actor_is_session_identity`.
5. **Cross-tenant enumeration is closed** — a tenant-2 actor with zero relationship to tenant-1 cancelling a tenant-1 run id gets the identical `report_run_not_found` a genuinely missing id produces; a same-tenant colleague lacking `COM:Export` and not the requester gets a real, non-leaking `insufficient_authority`.
6. **Cancel authority matrix, all four paths live-tested**: original requester succeeds; Supreme Admin succeeds regardless of requester; an already-cancelled run cannot be re-cancelled (`report_run_not_cancellable`); a same-tenant colleague without `COM:Export` is denied.
7. **Schema-privilege defense in depth** — zero `anon` EXECUTE grant on any of the 3 new functions; zero `authenticated` INSERT/UPDATE/DELETE on `report_type_versions`.
8. **Audit trail is real** — `publish_report_type_version` and `cancel_report_run` each recorded a genuine `app.audit_logs` row, confirmed by direct query, not merely asserted to have been called.
