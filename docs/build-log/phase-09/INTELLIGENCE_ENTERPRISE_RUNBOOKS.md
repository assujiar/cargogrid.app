# Phase 9 (Intelligence, Automation and Enterprise Expansion) Operational Runbooks

**Produced by:** `CG-S14-IAE-038` (Prompt 366 — Intelligence, Automation and Enterprise Documentation Handoff), per Prompt 366 §20's own "publish enterprise IAM, monitoring, retention, deployment, data residency, scale, DR and support runbooks" and "publish reporting/dashboard/analytics metric docs, API specs, webhook event docs and integration runbooks" deliverables, mirroring `docs/build-log/phase-07/HRIS_TICKETING_RUNBOOKS.md` and `docs/build-log/phase-08/CUSTOMER_PORTAL_LOYALTY_RUNBOOKS.md`'s own structure and citation density two phases up.

**What a runbook is here:** a step-by-step description of how a real, already-`VERIFIED` Phase 9 capability resolves a named operational scenario — citing the real RPC/table/migration/permission-action sequence an on-call engineer or support staff member actually walks through. **This document does not describe any behavior that is not already built and independently gate-suite-verified** — every RPC/table/migration named below is drawn directly from its owning capability's own build log (`docs/build-log/phase-09/IAE-330.md` through `IAE-365.md`), `docs/build-log/phase-09/00_EXECUTION_INDEX.md`, or a direct read of the migration file itself — never invented. Where a scenario touches a real, disclosed, still-open limitation (most of Phase 9's own async workers have no live scheduler yet), that limitation is stated plainly rather than smoothed over, and where a scenario's own mechanism was itself the subject of a live-reproduced Critical/High Tier C finding, the finding and its exact fix are cited so a reader on an older checkpoint can recognize a genuine regression rather than mistake it for routine behavior.

**Sanitization:** every tenant code, actor label, and figure below (`iaeschedco`, `PT Nusantara Freight`, round day/minute counts) is fictional and deterministic, drawn from each capability's own already-sanitized db-test fixtures where a concrete worked example is useful. No raw credential, secret, AI prompt/output content, or private URL appears anywhere in this document.

**Status of this document itself:** documentation-only, part of `CG-S14-IAE-038`'s own checkpoint. Nothing here should be read as `PHASE_9_VERIFIED` being set — only Prompt 367 (`CG-S14-IAE-039`, Closure Verification) may set that. Nothing here claims production, pilot, GA, or market-ready status, and nothing here claims a live scheduler, a live OIDC/SAML/SCIM protocol handshake, a real MFA enrollment/verification UI, physical dedicated-instance provisioning, cross-region data replication, or physical archive/delete execution exists anywhere in this repository — every one of those is a standing, disclosed, `NOT_RUN`/`NOT_BUILT` gap named explicitly below, not implied to be solved.

**Companion document:** `docs/build-log/phase-09/INTELLIGENCE_ENTERPRISE_ROLE_GUIDES.md` — what each real Phase 9 authority tier can see and do, through which real RBAC module:action tuple. ## 0. Common conventions across every runbook below

- **`app.evaluate_permission` is the one RBAC gate every module:action tuple in this document is evaluated through**, with exactly one structural exception: `app.evaluate_permission`'s own `supreme_admin_exception` branch (`supabase/migrations/20260716104519_create_rbac_evaluator.sql:62-67`) returns `allowed=true` for any live, active `supreme_admin`-layer `app.principal_memberships` row **before the role/permission lookup ever runs** — see the companion Role Guides document §7 for the full, cited detail. A second, narrower authority shape recurs across several Phase 9 capabilities: `app.is_support_grant_authority(actor, tenant)` (`supabase/migrations/20260716111315_create_support_access.sql:225-238`) grants Supreme Admin **or** the target tenant's own active `tenant_admin` **layer** membership — this is a layer check, not a module:action permission, and it is the real gate behind every audit-search/audit-export RPC named in runbook 7.
- **Every Phase 9 async/background mechanism reuses the existing `app.jobs` durable queue (`PLT-131`/`132`) — none introduces a second scheduler or queue table.** And, repository-wide, **no live cron/poll scheduler exists anywhere in this repository** (`ISS-2026-015`, standing, disclosed, accepted). Every RPC this document names as "the real execution entrypoint" for a scheduled/recurring/async mechanism is real, callable, and adversarially tested — but nothing invokes it periodically. The single most common cause of "nothing happened" across every runbook below is this operational gap, not a code defect — confirm the relevant RPC produces a correct result when called directly before escalating anything as a bug.
- **Anti-enumeration and cross-tenant folding are the norm.** A cross-tenant real id and a genuinely nonexistent id collapse into the identical not-found error in almost every Phase 9 capability (e.g. `automation_rule_not_found`, `integration_connection_not_found`, `scheduled_report_not_found`) — this is deliberate, not a bug to "improve" by making the error more specific.
- **Self-approval is structurally forbidden everywhere a maker-checker pattern exists in Phase 9, at TWO layers — a hard CHECK constraint plus an explicit, named application error — never application logic alone.** `app.mfa_exceptions_no_self_approval` (IAE-355), `app.tenant_deployment_records_no_self_approval` (IAE-360), `app.tenant_region_assignments_no_self_approval` (IAE-361), `app.legal_holds_no_self_release` (IAE-359), and `app.ip_allowlist_bypass_grants`' own equivalent (IAE-356) all follow this exact two-layer shape. A raw-SQL bypass attempt against any of these is independently rejected by the CHECK constraint itself, live-proven in each capability's own db-test. **Never attempt to work around a self-approval rejection by using a second account that is really the same person, or by disabling the higher-tier gate "temporarily."**
- **A recurring, disclosed authority-surface lesson: a "resolve the real default for this tenant" function takes a bare `p_tenant_id` and is deliberately granted `service_role` ONLY, never `authenticated`.** `app.resolve_tenant_deployment_type` (IAE-032), `app.resolve_tenant_region` (IAE-033), `app.resolve_retention_days` (IAE-031), `app.resolve_latest_dr_restore_status` (IAE-035), and `app.is_high_risk_action` (IAE-027) all share this shape — some self-caught before any test ran, some caught only by `scripts/db-tests/rbac-enforcement.sql`'s own repository-wide sweep. If a downstream capability's own client-side code attempts to call one of these directly, it will fail — by design; only server-side composition from another `SECURITY DEFINER` function is the correct calling convention.
- **Every governance-grade "outcome recorder" in Phase 9 is a pending-only, atomic `UPDATE ... WHERE status = 'pending'` transition — this was NOT always true, and the fix history matters.** `app.record_ai_governed_request_outcome` (IAE-019), `app.record_audit_export_outcome` (IAE-029), and `app.record_retention_archive_outcome` (IAE-031) all reuse the identical pattern: a losing concurrent caller gets a clean, named `..._not_pending`/`..._already_recorded` error, never a silent overwrite of a legitimate outcome. The AI governance case was Batch 4's own single most severe Tier C finding — a live-reproduced 6-way concurrent race that silently destroyed a human-**approved** AI output before the fix (`IAE-347.md` §13). **Never manually flip one of these status columns via raw SQL to "unstick" a stuck request** — the atomic guard exists precisely to prevent exactly that kind of stale overwrite.
- **RPD-022's Supreme Admin absolute-CRUD exception is real, audited, and never claimed tamper-proof or immutable-for-all.** Where a Phase 9 mechanism gives Supreme Admin a narrow override path (e.g. any `raise exception ... using errcode` guard a plain tenant actor cannot bypass), that path itself still writes a real `app.audit_logs` row — it is a detective control, not a preventive guarantee against a sufficiently privileged administrator. Never fabricate evidence, and never bypass a gate "just this once" even under time pressure — every runbook below names the real, governed path instead.

## 1. A scheduled report fails to run, or an analytics materialized-view refresh looks stale

**Scenario:** a tenant's own recurring report (`app.scheduled_reports`, IAE-006/Prompt 334) does not appear to have delivered its expected notification, or a cross-tenant analytics aggregate (`app.mv_report_usage_daily`, IAE-005/Prompt 333) looks incomplete or out of date.

**Scheduled reports — the real diagnostic path** (`supabase/migrations/20260802050000_create_intelligence_scheduled_reports.sql`, `docs/build-log/phase-09/IAE-334.md`):

1. **Check whether the schedule is even in a runnable state first.** `app.scheduled_reports.status` is `active`/`paused`/`archived`; a `paused` schedule genuinely cannot run — `app.run_scheduled_report` against it fails `scheduled_report_not_active` (`IAE-334.md` §10 item 4). Resume via `app.set_scheduled_report_status` (`REP:Configure`).
2. **Confirm someone/something actually called `app.run_scheduled_report`.** This is the real, tested execution entrypoint — **no live scheduler exists anywhere in this repository to call it automatically at each schedule's own `next_run_at`** (§8 of `IAE-334.md`, the same standing `ISS-2026-015` gap every job type in this repository carries). "The schedule's `next_run_at` came and went with nothing delivered" almost always means nobody (an operator, a script, or a future scheduling capability) has triggered it yet — confirm by calling `app.run_scheduled_report` (`REP:Configure`) directly and checking the result, before treating this as a defect.
3. **Once run, check `app.scheduled_report_runs` for the schedule** — `status` (`queued`/`completed`/`failed`), `job_id` (a real, linked `app.jobs` row), `recipients_total`/`recipients_reauthorized`/`recipients_denied`. Recipients are re-validated **live**, against `app.has_active_tenant_membership`, at every single run — not merely at add time (design decision 1, `IAE-334.md`). A recipient whose tenant membership was revoked between add-time and run-time is silently, correctly excluded and counted in `recipients_denied` — this is intended behavior, not a delivery failure to escalate.
4. **Duplicate-delivery is structurally prevented per due occurrence, not merely per call.** Since the Batch 1 Tier C fix (`IAE-334.md` §13 Finding 2/3, migration `20260802060000_harden_intelligence_batch1_tier_c_review_fixes.sql`), the enqueue is keyed on a real `occurrence_at` column, unique on `(scheduled_report_id, occurrence_at)` — re-triggering the SAME due occurrence (e.g. a re-run after a partial failure) returns the SAME `scheduled_report_runs` row, the SAME `app.jobs` row, and the SAME linked `app.report_runs` row, never a duplicate. Before this fix, a genuinely concurrent re-trigger could double-notify and silently skip a real due date — if you ever see two distinct run rows for what should be one occurrence, treat it as a regression against this exact fix, not routine retry behavior.
5. **If a recipient reports receiving an unfamiliar/wrong-tenant notification subject, this is the exact shape of the batch's own sole Critical finding — escalate immediately, do not dismiss as a template glitch.** The original `app.run_scheduled_report` resolved the notification `config_version` via an UNSCOPED join with no tenant filter — any tenant admin publishing an override for the shared `'notification:scheduled_report_ready'` config type could silently win for every OTHER tenant's own scheduled-report notifications, purely by UUID-sort chance (`IAE-334.md` §13 Finding 1, fixed by routing through `app.resolve_config`, PLT-121's own real 6-level tenant-scoped resolver). Confirm the fix migration above is applied before assuming this is a new occurrence of the class.
6. **No real report artifact is ever generated in this environment.** `artifact_file_id`/`artifact_expires_at` on `app.scheduled_report_runs` are wired for a future worker but never populated (§8, the same standing condition `IAE-002`'s own `enqueue_report_export` already carries) — "the notification arrived but there's nothing to download" is a disclosed, known gap, not a bug to chase.

**Materialized-view refresh — the real diagnostic path** (`supabase/migrations/20260802040000_create_intelligence_analytics_materialized_views.sql`, `docs/build-log/phase-09/IAE-333.md`):

1. **Query `app.analytics_refresh_runs` for the view first** — `status` (`running`/`completed`/`failed`), `row_count_before`/`row_count_after`, `reconciled`, `error_reason`. A genuine failure (e.g. the underlying view was dropped/renamed) is captured cleanly as a `status='failed'` row with a real Postgres error message via `sqlerrm` — `app.refresh_analytics_view`'s own exception scope wraps the ENTIRE working body (a self-caught fix during authoring — an earlier draft only wrapped the `REFRESH` statement itself, which meant a dropped view raised an uncaught exception instead, §2 item 8 of `IAE-333.md`). The old snapshot stays fully queryable throughout, since this migration uses `REFRESH MATERIALIZED VIEW CONCURRENTLY`, not the plain blocking form.
2. **`reconciled=false` on an otherwise-successful run is a real, disclosed, narrow race, not necessarily a data-integrity bug.** The reconciliation check compares the view's post-refresh row count against a live, independently-recomputed count over the real source table (`app.report_runs`) — a genuine, legitimate report run recorded by ANY tenant in the small gap between the refresh statement and the reconciliation query can produce a false `reconciled=false` (`IAE-333.md` §13 Finding 11, Medium, disclosed as not fully live-regressed due to the timing window's own impracticality to engineer deterministically). Re-run the refresh once and re-check before escalating a single reconciliation mismatch.
3. **No scheduled/automatic refresh trigger exists.** `app.refresh_analytics_view` is Supreme-Admin-only and must be called explicitly — "the dashboard hasn't updated in days" usually means nobody has refreshed it, not a code defect (§8, `IAE-333.md`).
4. **Never manually run a raw `REFRESH MATERIALIZED VIEW` statement outside `app.refresh_analytics_view`.** Doing so bypasses the reconciliation ledger and the audit trail entirely, and defeats the one mechanism this capability exists to provide.

**What NOT to do:** never manually `UPDATE` a `scheduled_report_runs`/`report_runs`/`analytics_refresh_runs` row to fabricate a "completed" status; never bypass `app.run_scheduled_report`'s live recipient reauthorization by re-adding a revoked member through a side channel; never treat "no artifact file" as an error requiring escalation without first checking §8's disclosed limitation.

**Escalation path:** first-line — any tenant staff member holding `REP:View` reruns the diagnostic above. A genuine cross-tenant notification-content leak (item 5) or a genuinely duplicated occurrence (item 4) is Critical/High and escalates immediately to the Reporting/Scheduled-Reports capability owner (`IAE-002`/`IAE-005`/`IAE-006`), citing the exact migration that closed the original finding. A disclosed "no scheduler" or "no artifact" gap does not need escalation as a bug — it is a standing, known operational limitation.

## 2. An integration provider adapter goes down, or a webhook endpoint auto-disables

**Scenario:** a tenant's own third-party integration (email/WhatsApp/SMS, maps/GPS, carrier/customs, bank/payment, accounting/HR — Prompts 342-346) appears to have stopped working, or an outbound webhook subscriber reports missing deliveries and their endpoint shows as disabled.

**Two structurally independent auto-disable mechanisms exist in Phase 9 — do not conflate them:**

**(A) Integration Hub connection health** (`app.integration_connections`, IAE-008/Prompt 336, `supabase/migrations/20260803020000_create_intelligence_integration_hub.sql`):

1. **Query `app.integration_connections` first** — `status` (`active`/`disabled`/`testing`), `consecutive_failure_count`, `last_health_status`, `auto_disabled_at`, `disabled_reason`. Auto-disable fires at **10 consecutive `unhealthy` checks**, mirroring `ADR-0011`'s own already-ratified webhook threshold (design decision 4, `IAE-336.md`). Disabling never deletes the health-check history — the full `app.integration_health_checks` append-only ledger survives untouched.
2. **`app.record_integration_health_check` is a CALLER-SUPPLIED result ("Test connection" button), not an automated live poller.** No live connectivity test runs anywhere in this repository for this mechanism — the same standing job-queue/webhook-delivery disclosure every prior async capability carries (§8, `IAE-336.md`). If the connection has simply not been tested recently, that is the operational gap, not a code defect.
3. **`app.check_integration_connection_active` is a real, correct guard function with no caller yet** — a future provider-adapter job-enqueue path would check it before dispatching on behalf of a disabled connection (§8, `IAE-336.md`). Do not assume every adapter already respects it.
4. **The raw credential is never queryable, by anyone, including a Supreme Admin, via a raw `select`.** `app.integration_connection_credentials` is RLS-enabled with **zero** policies and **zero** grant to `authenticated`/`anon` at all — only a `SECURITY DEFINER` function running as its own owner can touch it (design decision 3, `IAE-336.md`). If an outage traces to an expired/rotated upstream credential, use `app.rotate_integration_connection_credential` (`INTHUB:Configure`) to supply the new value — there is no "view current secret" action to fall back on.
5. **Re-activation resets the failure counter to zero** — `app.set_integration_connection_status` (`INTHUB:Configure`) is the real re-enable action; `consecutive_failure_count` returns to 0 and `app.check_integration_connection_active` reports the connection active again.
6. **A provider-specific adapter (Prompts 342-346) composes this connection's own primitives directly** — each of `IAE-014`/`015`/`016`/`017`/`018` reuses `app.integration_connections`/`app.integration_connection_credentials` (never a per-adapter parallel credential store), and each independently gained a cross-check that a connection's `tenant_id` actually matches the caller's own tenant (a lesson first found and fixed in this same batch's own Tier C review). If an adapter appears to be dispatching against the WRONG tenant's connection, this is the exact class to escalate as Critical, citing the specific adapter's own build log.

**(B) Webhook endpoint delivery failures** (`app.webhook_endpoints`/`app.webhook_deliveries`, PLT-129 extended by IAE-012/Prompt 340, `supabase/migrations/20260719150000_create_api_key_webhook_primitives.sql`, `supabase/migrations/20260804040000_create_intelligence_webhook_management.sql`):

1. **Query `app.webhook_endpoints` for the endpoint** — `status`, `consecutive_failure_count`, `auto_disabled_at`, `disabled_reason` (`'consecutive_failure_threshold_exceeded'`). This is a genuinely separate counter from Integration Hub's own connection health, tracked by `app.record_webhook_delivery_attempt` on `app.webhook_endpoints` (`supabase/migrations/20260719150000_create_api_key_webhook_primitives.sql:891-954`): every `'failed'` recorded attempt increments `consecutive_failure_count`; **at ≥10, the endpoint flips to `disabled`**; any single `'success'` resets the counter to `0`.
2. **Query `app.webhook_deliveries` for the specific delivery** — `status` (`pending`/`delivered`/`dead_letter`), `attempts`, `next_attempt_at`. A failed attempt schedules the NEXT retry with exponential backoff (`2^attempts` minutes) until `max_attempts` is reached, at which point the delivery goes `dead_letter` — never silently disappears.
3. **The real delivery worker is `app.jobs`-backed (`webhook_retry` job type) and is a REAL, runnable script (`scripts/jobs/webhook-delivery-worker.ts`) — but nothing runs it automatically.** The same standing `ISS-2026-015` gap: "nothing is retrying" may simply mean the worker process has not been started, not a code defect (§8, `IAE-340.md`).
4. **A runtime SSRF guard re-resolves DNS immediately before every dispatch and refuses a hostname resolving to a private/loopback/link-local/cloud-metadata address (`lib/webhooks/ssrf-guard.server.ts`), and refuses to auto-follow a redirect.** This closed a real, live-proven High finding — a registered webhook URL that only resolves to a private/metadata address at actual send time (DNS rebinding) previously sailed straight through registration-time validation (`IAE-340.md` §13 Finding 4). **If a webhook endpoint that used to work now fails every delivery, check whether its DNS now resolves somewhere private before assuming a code regression — this guard working correctly is not itself a bug, and must never be disabled to force a delivery through.**
5. **For a dead-lettered delivery, use `app.replay_webhook_delivery` (staff-only, valid ONLY from `status='dead_letter'`) — never a manual attempt-count reset.** Two real, live-reproduced Critical findings governed this action's own fix history (`IAE-340.md` §13 Findings 1-2): (a) the original implementation reset `attempts=0` on replay, which permanently broke the delivery — the append-only `app.webhook_delivery_attempts` table's own unique constraint on `(webhook_delivery_id, attempt_number)` is never cleared, so the very next real attempt collided on `attempt_number=1`, already recorded before the replay, crash-looping the worker indefinitely; (b) two concurrent replays of the same delivery both passed the `status='dead_letter'` check and minted two separate jobs for one delivery. Both are fixed: replay now grants a fresh BUDGET of `max_attempts` additional attempts on top of whatever was already used (never resetting the append-only counter), and the initial read now uses `select ... for update` so a second concurrent replay is cleanly rejected with `webhook_delivery_not_replayable` once the first has already moved the delivery out of `dead_letter`. **Confirm the fix migration `supabase/migrations/20260804060000_harden_intelligence_batch3_tier_c_review_fixes.sql` is applied on the target checkpoint before relying on replay** — on an older, unpatched checkpoint, replaying a dead-lettered delivery twice in quick succession is a known way to corrupt it.
6. **`app.send_test_webhook_delivery` exercises exactly ONE named endpoint** — it deliberately bypasses the normal subscription fan-out and does not prove every subscriber of an event type is reachable (design decision 5, `IAE-340.md`). Do not read a successful test-send as proof the whole fan-out for that event type works.

**What NOT to do:** never disable or work around the SSRF re-resolution guard to make a delivery succeed; never manually reset `attempts=0` on a dead-lettered delivery via raw SQL; never assume `app.check_integration_connection_active`'s existence means every adapter already calls it; never read the raw integration credential via any path other than the governed rotate action (there is no "reveal" path, by design).

**Escalation path:** the Integration Hub capability owner (`IAE-008`) for connection/health/credential-isolation questions; the specific provider-adapter owner (`IAE-014`..`018`) for a wrong-tenant-connection dispatch, which is a Critical cross-tenant finding class; the Webhook Management/PLT-129 owner (`IAE-012`) for delivery/replay/SSRF questions. A confirmed SSRF-guard bypass or a confirmed replay-corruption reproduction on a checkpoint that already carries the fix migration is Critical — escalate immediately.

## 3. An AI-governed request is stuck at `pending`, or a human approval is needed for a critical AI output

**Scenario:** a downstream AI-assisted capability (OCR document processing, predictive ETA, optimization assistance, fraud/risk assistance, forecasting/recommendation, or AI-assisted quotation — Prompts 348-353) recorded a governed request that never seems to resolve, or a customer-visible/financial AI output needs a real human sign-off before anything downstream treats it as actionable.

**The real mechanism** (`supabase/migrations/20260805060000_create_intelligence_ai_governance_provider_boundary.sql`, `docs/build-log/phase-09/IAE-347.md`):

1. **Structural guarantee to hold in mind before diagnosing anything here: AI output can never autonomously write to any domain table.** No function in the AI governance migration grants INSERT/UPDATE/DELETE on any table outside its own schema (design decision 2) — every downstream capability applies a value through its OWN, unmodified domain RPCs, never through this checkpoint. **If you ever find AI output that appears to have changed a real domain record (a quotation price, a shipment status, a ledger line) with no corresponding human decision recorded in `app.ai_governed_requests`/`app.approval_requests`, this is a serious violation of the governance boundary — escalate immediately as Critical. Never patch around it; the whole point of this capability is that this should be structurally impossible.**
2. **Query `app.ai_governed_requests` via `app.list_ai_governed_requests_for_tenant` (`AI:View`)**, filtered by `feature_code` — check `status` (`pending`/`succeeded`/`failed`) and `approval_status`.
3. **If `status` stays `pending` indefinitely, the real synchronous dispatch client (`lib/ai-governance/dispatch-ai-governed-request.server.ts`) likely never completed its own call to `app.record_ai_governed_request_outcome`.** This is a single synchronous request/response call (never queued through `app.jobs`), so there is no worker/scheduler gap here the way there is elsewhere in this document — a stuck `pending` row usually means the calling process crashed, timed out, or was interrupted mid-flight before recording an outcome. Confirm whether the original request actually reached the provider before assuming a code defect.
4. **The pending-only transition is atomic — trust it, do not work around it.** `app.record_ai_governed_request_outcome`'s own `UPDATE ... WHERE status = 'pending'` guard was Batch 4's own single most severe finding: the original, unlocked SELECT-then-UPDATE let 6 genuinely concurrent callers all "win," silently destroying an already human-**approved** output (`billed_amount` corrupted from a real value to a stray straggler's own recomputation) while `approval_status` stayed `approved`, now pointing at nothing (`IAE-347.md` §13). The fix is live-reproduced with the identical 6-way concurrent probe: exactly 1 of 6 now wins, the rest get the clean `ai_governed_request_not_pending` error. **Never manually flip `app.ai_governed_requests.status` via raw SQL to unstick a request that appears stuck** — if it is genuinely stuck, the root cause is upstream (the dispatch client never called the recorder), not something a status edit fixes safely.
5. **For approval, use `app.request_ai_output_approval` (any `AI:Create`/`AI:View` holder) then `app.decide_ai_output_approval` (`AI:Approve` — a genuinely SEPARATE action from `AI:Create`, not merely a higher tier of it).** `ai_governed_request_not_succeeded` means the request has not reached `status='succeeded'` yet — approval can only ever be requested for a completed, successful AI output. `ai_output_acceptance_approval_not_configured` means no tenant admin has ever published the required `approval:ai_output_acceptance` config version via the Platform Approval Engine (`PLT-123`) — this is a real, disclosed precondition, not a bug: a tenant must configure its own approval routing before this mechanism can be used at all. `decide_ai_output_approval` folds any foreign-domain approval step (one belonging to a different `entity_type`) into `ai_output_approval_wrong_domain`, never a generic "decide any step" bypass.
6. **Redaction behaves differently for prompt content vs. output content — this is deliberate, not inconsistent.** A secret-shaped key in the CALLER-authored prompt payload is REJECTED outright (`ai_governed_request_secret_shaped_key`, via `app.assert_ai_prompt_payload_has_no_secret_shaped_keys`) — if request creation keeps failing with this error, check the prompt for a credential-shaped field name (e.g. `bank_account_number`); this is working as intended. A secret-shaped key in the PROVIDER-controlled output is instead REDACTED to `[REDACTED]`, never rejected, via `app.redact_ai_output_payload_secret_shaped_values` — an earlier version incorrectly rejected these, permanently losing real HTTP outcome/model/cost evidence for an entirely ordinary AI response that happened to contain a plausible-looking key name (`IAE-347.md` §13, a real, live-reproduced Medium finding).
7. **`billed_amount` is always computed server-side** via `app.compute_provider_billed_amount` (RPD-028's own +20% markup over the real provider unit cost) — never trust or accept a client-supplied billed amount for reconciliation purposes.

**What NOT to do:** never manually mutate `app.ai_governed_requests.status`/`output_payload` via raw SQL; never approve an AI output through any path other than `app.decide_ai_output_approval`; never treat a stuck `pending` request as something to force-complete with fabricated evidence — trace the real dispatch client instead.

**Escalation path:** first-line — a tenant staff member holding `AI:View` reruns the diagnostic above. A confirmed instance of AI output reaching a domain table with no recorded human decision, or a confirmed reproduction of the concurrent-outcome-overwrite class on a checkpoint that already carries the `IAE-347.md` §13 fix, is Critical — stop, preserve `app.ai_governed_requests`/`app.approval_requests` evidence, and escalate to the AI Governance capability owner (`IAE-019`) citing the exact request id.

## 4. An enterprise customer's SSO connection cannot be activated, or an MFA/network-access exception is needed

**Scenario:** a tenant administrator reports enterprise SSO activation is blocked with an unfamiliar error, or a user has lost their MFA factor / needs an emergency IP-allowlist bypass and needs a governed exception approved.

**Enterprise SSO activation — the real test-before-enforcement lockout guard** (`supabase/migrations/20260807000000_create_intelligence_enterprise_iam_sso.sql`, `docs/build-log/phase-09/IAE-354.md`):

1. **`app.activate_enterprise_idp_connection` requires at least one prior `matched` row in `app.iam_sso_login_attempts` before it will ever flip a connection to `active`.** If activation fails with `enterprise_idp_no_verified_test_login: connection ... has no recorded successful test-login resolution -- run app.resolve_enterprise_sso_claims first to prevent a lockout` (`supabase/migrations/20260807000000_create_intelligence_enterprise_iam_sso.sql:576`), this is the intended, structural lockout guard doing its job, not a bug — call `app.resolve_enterprise_sso_claims` (`IAM:Configure`) with a real subject/email claims pair first to produce a genuine `matched` resolution, THEN retry activation.
2. **Walk the full outcome matrix of `app.resolve_enterprise_sso_claims` before assuming a failure**: `no_domain_claim` (the email domain has no active, verified claim for this tenant), `no_user_match` (a claimed domain but no matching platform identity), `matched` (success — the only outcome that counts toward the lockout guard), `deprovisioned` (the matched employee's own tenant identity has been genuinely revoked), `connection_not_active` (the connection is explicitly `disabled` — note this deliberately does NOT fire for `status='testing'`, which is exactly the legitimate pre-activation state a test resolution must succeed against), `invalid_email_claim` (a malformed or non-email-shaped claim, including a prompt-injection-shaped string — this returns a clean outcome, never a crash).
3. **A real, corrected authority gap: activation now requires `IAM:Configure` explicitly, not merely the shared `INTHUB:Configure`.** The original implementation validated the lockout-guard precondition but then delegated the actual status flip entirely to `app.set_integration_connection_status` (IAE-008, unmodified), which only checks `INTHUB:Configure` — live-reproduced: any actor holding ONLY the broadly-held, generic `INTHUB:Configure` permission (zero `IAM` grant of any kind) could activate enterprise SSO login for a tenant (`IAE-354.md` §13, a real segregation-of-duties bypass). Fixed by adding an explicit `app.evaluate_permission(actor, tenant, 'IAM', 'Configure')` check inside `activate_enterprise_idp_connection` itself, in addition to the delegate's own requirement — a caller now needs **both** grants. **If a tenant's generic integration administrator reports they can no longer activate SSO, this is the corrected, intended behavior — the caller now needs `IAM:Configure` specifically, not a regression to work around.**
4. **No live OIDC/SAML protocol handshake exists.** `app.resolve_enterprise_sso_claims` operates on an ALREADY-EXTRACTED claims payload (subject + email) — a real deployment's own OIDC RP/SAML SP protocol layer (external, not built in this repository) must independently verify the token/assertion signature before ever calling this function (§8, `IAE-354.md`). Do not treat a successful `matched` resolution as proof a real cryptographic handshake occurred; it proves only that the claims-routing/user-matching logic is correct.
5. **`app.resolve_enterprise_idp_by_email_domain` is deliberately `anon`-reachable** (mirrors the pre-existing `app.resolve_tenant_by_domain`) — this is an intentional, disclosed design choice for pre-login IdP routing, not a security hole to close.

**MFA exception (lost-factor recovery) and IP-allowlist bypass — the real break-glass mechanism** (`supabase/migrations/20260807100000_create_intelligence_enterprise_mfa_session_controls.sql`, `20260807200000_create_intelligence_ip_restriction_network_access.sql`, `docs/build-log/phase-09/IAE-355.md`, `IAE-356.md`):

1. **Query `app.mfa_exceptions`** — `status` (`pending`/`approved`/`denied`/`expired`/`used`). `app.request_mfa_exception` (`SEC:Configure`) requires a real, non-empty reason (`mfa_exception_reason_required`) and a target identity that genuinely holds active membership in the tenant (`mfa_exception_target_not_tenant_member`).
2. **`app.approve_mfa_exception` requires `SEC:Approve` — a genuinely separate, higher tier from `SEC:Configure` — and self-approval is forbidden at the CHECK-CONSTRAINT level** (`mfa_exceptions_no_self_approval`), not merely by application logic: `supabase/migrations/20260807100000_create_intelligence_enterprise_mfa_session_controls.sql:634-673` raises the clean, named `mfa_exception_self_approval_forbidden` before ever reaching the constraint, and a raw-SQL bypass attempt is independently rejected by the constraint itself, live-proven in `IAE-355.md`'s own db-test.
3. **`app.consume_mfa_exception` is exactly-once and target-identity-only.** An already-used or expired exception cannot be replayed (`mfa_exception_not_approved`, `mfa_exception_expired`) — this is intended, not a bug to route around with a fresh request for the same lost factor (request a genuinely new exception instead).
4. **The IP-allowlist bypass grant (`IAE-356`) mirrors this exact shape** — `app.request_ip_allowlist_bypass` (`SEC:Configure`), `app.approve_ip_allowlist_bypass` (`SEC:Approve`, self-approval forbidden identically), `app.has_active_ip_allowlist_bypass` for the live check. Moving `app.set_ip_allowlist_enforcement_mode` straight to `enforced` with zero active allowlist entries is itself rejected (`ip_allowlist_no_active_entries`) — a second, distinct lockout guard, mirroring the SSO one above; add at least one real entry first.
5. **The real step-up authorization gate is NOT yet enforced anywhere.** `app.assert_current_step_up_authorization` is genuinely correct and independently live-tested (including a real "stale-session-must-re-verify" proof), but it has **zero live callers today, including this migration's own `SEC:Configure`/`SEC:Approve` functions** (§8, `IAE-355.md`, explicitly re-disclosed rather than silently claimed enforced). Do not assume that approving an MFA exception, activating SSO, or any other high-risk Phase 9 action currently requires a fresh MFA step-up in practice — it does not yet, anywhere in this repository.

**What NOT to do:** never force a connection's `status` to `active` via a raw table update to bypass the lockout guard; never approve your own MFA exception or IP-allowlist bypass request, even from a second account you also control; never disable the `IAM:Configure`/`SEC:Approve` gate "temporarily" to unblock someone — route the request to someone who genuinely holds the grant.

**Escalation path:** the Enterprise IAM capability owner (`IAE-026`) for SSO/domain-claim/SCIM questions; the Enterprise Security capability owner (`IAE-027`/`IAE-028`) for MFA-exception/session/IP-allowlist questions. A confirmed activation succeeding for an actor with only `INTHUB:Configure` and zero `IAM` grant, on a checkpoint that already carries the `IAE-354.md` §13 fix, is a Critical regression — escalate immediately.

## 5. A tenant needs a dedicated deployment/region assignment provisioned, or a DR restore test needs recording

**Scenario:** an enterprise customer's contract calls for a dedicated deployment and/or a non-default region, or a support/reliability engineer needs to record the outcome of a real disaster-recovery restore test and check the enterprise onboarding readiness checklist.

**Dedicated deployment lifecycle** (`supabase/migrations/20260808000000_create_intelligence_dedicated_enterprise_deployment.sql`, `docs/build-log/phase-09/IAE-360.md`):

1. **The real, ordered state machine is `pending_qualification → qualified → provisioning → active → decommissioned`**, enforced by `app.set_deployment_provisioning_status` (`DEPLOY:Configure`) — an out-of-order transition (e.g. `qualified → active`, skipping `provisioning`) is rejected outright, live-proven for every illegal edge.
2. **Qualification requires a genuinely separate approval tier.** `app.request_dedicated_deployment_qualification` (`DEPLOY:Configure`) followed by `app.approve_dedicated_deployment_qualification` (`DEPLOY:Approve`) — and **self-approval is structurally forbidden at two layers**: a `tenant_deployment_records_no_self_approval` CHECK constraint plus an explicit `deployment_self_approval_forbidden` application check, added as a real self-caught fix after a realistic scenario (one identity legitimately holding BOTH `DEPLOY:Configure` and `DEPLOY:Approve`, a permitted combination this RBAC model does not itself forbid) was found to defeat "provisioning requires contract/security/CTO approval" as a genuine two-party control (`IAE-360.md` §13). A raw-SQL bypass attempt on the constraint is independently rejected.
3. **`app.resolve_tenant_deployment_type` returns `'shared'` (RPD-011's real, structural default) for every tenant with no record at all, and flips to `'dedicated'` ONLY once the record has genuinely reached `active`** — a `qualified` or `provisioning` tenant is still `'shared'`. This function is `service_role`-only with no actor parameter by design (a bare-tenant-id authority gap self-caught before this migration was ever tested) — a client calling it directly will fail; only server-side composition is the correct convention.
4. **No physical infrastructure is provisioned by any of this.** The schema is a real, structural GOVERNANCE evidence layer only — `set_deployment_provisioning_status` records that provisioning happened; it does not itself create, migrate data into, or network-isolate a real dedicated instance (design decision 3, `IAE-360.md`). Do not expect a real database/instance to appear automatically once a record reaches `active`.
5. **`app.set_deployment_environment_ref` stores a REFERENCE STRING only** (a pointer/label into an external secrets manager, backup location, or observability workspace) — never a real secret value. Do not put an actual credential here; there is no live-secret-reading path from this table.

**Multi-region assignment, composed live with the deployment lifecycle above** (`supabase/migrations/20260808100000_create_intelligence_multi_region_data_residency.sql`, `docs/build-log/phase-09/IAE-361.md`):

1. **`app.approve_region_assignment` REJECTS approval (`region_requires_dedicated_deployment`) unless the tenant already has an `active` dedicated deployment** — RPD-013's own "dedicated region requires dedicated deployment" rule is enforced as real, composed code (calling `IAE-032`'s own `app.resolve_tenant_deployment_type` directly), not merely disclosed prose.
2. **`region_capability_gap_unresolved` means at least one of the six real service categories (`ai_provider`/`database`/`backup`/`secrets`/`files`/observability-adjacent) is neither genuinely supported in the target region nor covered by a real, registered `app.register_region_capability_exception` (`DEPLOY:Approve`).** `americas`/`emea` are seeded FULLY UNSUPPORTED by design — no real infrastructure is deployed to either region anywhere in this repository (design decision 4, `IAE-361.md`) — every tenant reaching an `active` non-default region assignment today does so entirely via registered, audited exceptions, never a false claim of genuine capability. "Support access" itself has no region concept anywhere in this repository and is explicitly disclosed as out of this checkpoint's own scope (`IAE-361.md` §14 Finding 1) — do not expect a region-scoped support-access exception category to exist.
3. **The same self-approval-forbidden two-layer guard applies identically** (`tenant_region_assignments_no_self_approval` + `region_self_approval_forbidden`, `IAE-361.md` §13).
4. **Both `app.resolve_tenant_region` and `app.resolve_latest_dr_restore_status` (below) re-check the underlying dedicated deployment is STILL genuinely active on every call.** A tenant's own historical `active` region assignment or `dedicated`-scoped DR restore-test row is left completely unchanged (never retroactively falsified) once its underlying deployment is decommissioned — but the RESOLVED, live answer correctly reverts to the platform-wide default the moment the deployment goes away (`IAE-361.md` §14 Finding 4, `IAE-363.md` §14 Finding 4 — the identical staleness class, found and fixed in both capabilities). **If a decommissioned tenant still reports a non-default region or a stale "passed" DR status, this is a regression against this exact fix — confirm both fix migrations are applied before assuming the underlying record itself is wrong.**

**DR restore-test evidence and the enterprise onboarding checklist** (`supabase/migrations/20260808300000_create_intelligence_disaster_recovery_enterprise_support.sql`, `docs/build-log/phase-09/IAE-363.md`):

1. **`app.record_dr_restore_test` (`SUP:Configure` tenant-scoped, or Supreme Admin for a platform-wide test) structurally enforces real evidence per outcome.** A `passed` result requires real, non-negative, non-`NaN`/non-`Infinity` `observed_rpo_minutes`/`observed_rto_minutes` (the CHECK constraint was widened after a Tier C finding that a bare `NOT NULL` check let a negative value or Postgres's own numeric `NaN` satisfy it without being a real measurement, `IAE-363.md` §14 Finding 2). A `failed` result requires a real, genuinely non-empty `failure_reason` and `recovery_steps`, plus a `retest_scheduled_at` that must be strictly in the FUTURE (`dr_test_retest_schedule_must_be_future`) — never accept or record a placeholder/backdated retest commitment.
2. **A `dedicated`-scoped test is rejected (`dr_test_deployment_mismatch`) unless the tenant genuinely has an active dedicated deployment** — the same real composition with `IAE-032` named above.
3. **`app.get_enterprise_onboarding_checklist`/`app.verify_onboarding_checklist_item` computes 5 of its 6 items LIVE from real cross-capability data every time it is (re-)verified — never a caller-asserted rubber stamp.** `sso_verified` reads real `app.integration_connections` rows (`IAE-026`'s own adapters), `api_verified` reads real `app.api_keys`, `integrations_verified` reads any non-SSO `app.integration_connections` row, and `dr_evidence_verified` reads this capability's own restore-test evidence directly. The 6th item, `hypercare_plan_acknowledged`, has no automated backing anywhere in this repository — it is a genuine, disclosed human attestation, deliberately gated at the HIGHER `SUP:Approve` tier (not merely `SUP:Configure`, which the other five use) since it is the final sign-off that flips `status` to `ready_for_production` (design decision 4, `IAE-363.md`). The recompute is genuinely self-correcting, not a one-way ratchet — flipping `hypercare_plan_acknowledged` back to `false` correctly reverts `status` to `in_progress`.
4. **`sso_verified` only confirms an ACTIVE connection record exists — it does NOT re-verify a real test login.** Per `app.integration_connections`' own default (`status='active'` at creation), a freshly created SSO connection satisfies this checklist item immediately, without independently re-running `IAE-026`'s own test-login lockout guard (§8, `IAE-363.md`, explicitly disclosed rather than silently assumed equivalent). Do not treat a green `sso_verified` checkmark as proof SSO genuinely works end to end for real users — confirm against runbook 4's own SSO diagnostic separately if there is any doubt.

**What NOT to do:** never approve your own dedicated-deployment or region-assignment request, even holding both grants — it is structurally blocked and a raw-SQL bypass is independently rejected; never record a DR "passed" outcome without real measured RPO/RTO figures merely to satisfy the onboarding checklist; never manually flip `hypercare_plan_acknowledged` without a genuine `SUP:Approve`-tier human sign-off; never expect physical infrastructure (a real dedicated database, a real cross-region replica) to appear as a side effect of any of these RPCs.

**Escalation path:** the Dedicated Deployment capability owner (`IAE-032`) for deployment lifecycle/self-approval questions; the Multi-Region capability owner (`IAE-033`) for region/capability-matrix/exception questions; the DR/Enterprise Support capability owner (`IAE-035`) for restore-test evidence and onboarding-checklist questions. A confirmed self-approval succeeding on a patched checkpoint, or a confirmed stale region/DR status surviving deployment decommissioning on a patched checkpoint, is a Critical regression — escalate immediately citing the exact migration/finding number above.

## 6. A retention archive request is blocked, or a legal hold needs to be investigated

**Scenario:** a request to archive/delete an aged record is unexpectedly rejected, or someone needs to confirm whether a specific record is genuinely protected by an active legal hold.

**The real mechanism** (`supabase/migrations/20260807500000_create_intelligence_data_retention_archival.sql`, `docs/build-log/phase-09/IAE-359.md`):

1. **`blocked_within_retention` is the correct, structural enforcement of RPD-025's class-based schedule — not a bug to route around.** `app.request_retention_archive` (`RET:Configure`) rejects a non-dry-run request for any record that has not yet passed its own class's retention floor: `finance_tax` 3650 days, `audit_security` 2555 days, `operational` 90 days (`app.resolve_retention_days`, `service_role`-only — the identical bare-tenant-id authority-gap shape named in §0 above). Use `dry_run=true` first to check eligibility without ever enqueuing a real job (verified by a direct row-count check in `IAE-359.md`'s own db-test — a dry run NEVER creates a job).
2. **A legal hold blocks archival unconditionally, even for a record far past its own retention floor.** `IAE-359.md`'s own db-test proves a record **4000 days old — far past even the 10-year finance/tax default** — is still rejected (`blocked_legal_hold`) while an active hold exists, proving the hold overrides age unconditionally, not merely by coincidence of timing.
3. **A real, live-reproduced CRITICAL history here matters: legal hold matching was originally bypassable simply by mislabeling the request.** The original `app._is_under_legal_hold` matched a hold only on the CALLER-SUPPLIED `(tenant_id, record_class)` — an actor could sail an archive request straight through by declaring a DIFFERENT `record_class` for the identical physical record already under a specific-record hold, or a second tenant's own actor could name the same real record id under their own `p_tenant_id` (`IAE-359.md` §14 Finding 1, CRITICAL, live-reproduced both ways). **Fixed: a specific-record hold now matches on `(source_table, source_record_id)` ALONE, independent of the caller's own declared tenant/class claim.** A whole-CLASS hold (no specific record named) still necessarily matches on the caller's own declared `(tenant_id, record_class)`, since there is no specific record to anchor against instead — this is an unavoidable, disclosed consequence of this checkpoint's own bounded scope (it never independently verifies a caller-declared `tenant_id`/`record_class` against the real, external domain table a record actually belongs to), not a remaining gap of the same kind. **If you ever see an archive request succeed against a record you believe is under a specific-record legal hold, on a checkpoint that already carries this fix, treat it as the single highest-priority escalation this document names — it is exactly the vulnerability class already found and closed.**
4. **Placing a hold is a deliberately LOWER bar than releasing one.** `app.request_legal_hold` (`RET:Configure`) vs. `app.release_legal_hold` (`RET:Approve` — a genuinely separate, higher tier), since releasing is what allows deletion/archival to proceed — the more consequential action (design decision 6, `IAE-359.md`). Self-release is structurally forbidden at two layers (`legal_holds_no_self_release` CHECK constraint plus an explicit `legal_hold_self_release_forbidden` application error, `IAE-359.md` §14 Finding 3) — mirrors the MFA-exception/dedicated-deployment self-approval pattern exactly.
5. **A concurrent duplicate archive request for the identical record now correctly returns the SAME pending request, not a second one.** The idempotency key originally passed to `app.enqueue_job` was self-defeating (built from the freshly-inserted row's own id, guaranteed unique every call, so it could never actually deduplicate — `IAE-359.md` §14 Finding 2, HIGH, live-reproduced with genuinely concurrent requests each minting their own job). Fixed with a `pg_advisory_xact_lock` on `(tenant_id, source_table, source_record_id)` plus an existing-pending-request check.
6. **No physical archive/delete execution happens anywhere in this capability.** `app.request_retention_archive` enqueues a real `app.jobs` row (`job_type='retention_archive'`) and stops there; `app.record_retention_archive_outcome` (`service_role`, worker-only, the same lost-update-guarded pending-only transition pattern named in §0) is the disclosed, not-yet-built worker's own eventual outcome-recording call (design decision 4, §8, `IAE-359.md`). Requesting an archive is not the same as data actually being deleted or moved — check `app.jobs` and the request's own `status` before assuming physical deletion occurred.

**What NOT to do:** never bypass a legal hold by relabeling a record's own `record_class`/tenant on a second archive request — this is the exact CRITICAL vulnerability already found and closed; escalate immediately if it appears to still work. Never release your own legal hold, even holding both `RET:Configure` and `RET:Approve`. Never fabricate RPO/RTO-style "evidence" or treat a `blocked_within_retention` rejection as something to override manually — the retention floor exists precisely so posted finance/audit/legal evidence cannot be erased early.

**Escalation path:** the Data Retention and Archival capability owner (`IAE-031`) for legal-hold/retention-floor questions. A confirmed legal-hold bypass reproduction on a patched checkpoint is Critical — stop, preserve `app.legal_holds`/`app.retention_archive_requests` evidence, and escalate immediately citing the exact record and migration chain.

## 7. An audit/compliance request needs an export, or an impersonation/support session needs investigating

**Scenario:** compliance or legal needs a filtered export of the audit trail, or a specific customer-support/impersonation session's own actions need to be reviewed end to end.

**The real mechanism** (`supabase/migrations/20260807300000_create_intelligence_advanced_audit_impersonation.sql`, `docs/build-log/phase-09/IAE-357.md`):

1. **Every authenticated-reachable function in this capability is gated by `app.is_support_grant_authority(actor, tenant)` — Supreme Admin OR that specific tenant's own active `tenant_admin` LAYER membership, not a module:action permission at all** (`supabase/migrations/20260807300000_create_intelligence_advanced_audit_impersonation.sql:146,204,304,428`, reusing `app.is_support_grant_authority` unchanged from PLT-115, `supabase/migrations/20260716111315_create_support_access.sql:225-238`). If a request for audit search/export access is denied, confirm the requester genuinely holds the `tenant_admin` layer (or Supreme Admin) for that tenant — granting an `AI`/`SEC`/`REP`-style permission action will not help here, by design; audit read/export access does not become easier or harder than it already was under the pre-existing support-access model (design decision 3, `IAE-357.md`).
2. **`app.search_audit_logs` is the real, first multi-dimension audit search this repository has ever had** — every prior read path (`app.query_audit_logs`/`app.export_audit_logs`) supports pagination only, with no filter by actor/action/resource_type/result/date-range at all (design decision 1a, `IAE-357.md`). Filters combine with AND semantics, not OR — combining `action`+`resource_type`+`result` narrows the result set further, it does not broaden it.
3. **For a specific impersonation/support session, use `app.list_audit_logs_for_support_session`**, which reads the new, additively-widened `app.audit_logs.support_access_grant_id` column (a genuine `DROP FUNCTION` + `CREATE FUNCTION` on `app.capture_audit_event`, 11→12 args — not `CREATE OR REPLACE`, since Postgres does not replace a function whose own parameter COUNT differs even when every added parameter carries a default; this exact gotcha was self-caught on the first migration-apply attempt, `IAE-357.md` §7). Only events EXPLICITLY linked to a real `app.support_access_grants` row via this column appear — an event captured outside a support session correctly shows `support_access_grant_id = null`, never every event that happened to occur during the same wall-clock window. To confirm a support/impersonation session's own real lifecycle (requested/approved/active/expired/revoked), query `app.support_access_grants` (`PLT-115`) directly — a support session is case-bound and time-bound by construction; do not infer its status from ticket state.
4. **Exports are real, async, and expiring — not a synchronous dump.** `app.request_audit_export` enqueues a genuine `app.jobs` row (`job_type='audit_export'`); no live worker consumes it automatically yet (the same standing scheduler gap named in §0). `app.record_audit_export_outcome` is the pending-only, lost-update-guarded outcome recorder — live-verified under a genuine 2-process concurrent race (exactly 1 winner, the loser gets the clean `audit_export_outcome_already_recorded` error, never a silent overwrite). `app.get_audit_export` LAZILY flips a past-`expires_at` `ready` row to `expired` and clears `result_payload` on the very next read — a request that appears to have "vanished" after its expiry window is working as intended, not a defect.
5. **This capability's own idempotency key was originally self-defeating in the identical shape as retention's own archive request** (flagged by direct analogy during Group 7's own Tier C review, `IAE-357.md` §13 item 2) — fixed identically with an advisory lock plus an existing-pending-request check, so a genuine concurrent repeat request now returns the same pending row rather than double-enqueuing.
6. **There is no real downloadable file or signed URL.** `app.audit_export_requests.result_payload` is a bounded JSONB snapshot of matching, ALREADY-REDACTED rows — never a document/attachment (§8, `IAE-357.md`). Do not expect a file to appear anywhere; the export's own JSON payload is the deliverable.
7. **RPD-022's Supreme Admin exception on `app.audit_logs` itself is real but never tamper-proof.** `app.supreme_admin_mutate_audit_log`/`app.supreme_admin_delete_audit_log` (pre-existing, untouched by this checkpoint, design decision 5) remain the only mutation path on audit rows for anyone — every use is itself audited, a detective control only.

**What NOT to do:** never redact or edit an `app.audit_logs` row directly to "clean up" what an export surfaces; never fabricate a `result_payload` to answer a compliance request faster than a real export completes; never treat the absence of `support_access_grant_id` on an event as proof an impersonation session did not touch a record — confirm the session's own real, time-bound window against `app.support_access_grants` directly instead.

**Escalation path:** the Advanced Audit and Impersonation capability owner (`IAE-029`) for search/export mechanism questions; Platform Access Governance (`PLT-115`) for support-access-grant lifecycle questions, unchanged by this checkpoint. A genuine cross-tenant audit-log leak, or a confirmed outcome-recorder concurrency regression on a patched checkpoint, is Critical — escalate immediately, preserving the exact request/grant id.
