# IAE-345 — Bank, Payment Gateway, E-Invoice and Tax Integrations

**Prompt ID:** `CG-S14-IAE-017` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/345_BANK_PAYMENT_EINVOICE_TAX_INTEGRATIONS_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — fourth prompt of the merged Batch 4, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at the merged batch's own single Tier C review close)

## 1. What this checkpoint builds

Governed integrations for four financial provider categories (bank feeds, payment gateways, e-invoice submission, tax-authority rate lookups), with the business rule "provider data can never autonomously post journals, payments, tax or legal status" enforced structurally: every new function in this checkpoint is `FIN:Edit` at most — not one is `FIN:Approve`. Fills the real, disclosed gap FIN-211's own migration header named ("no live bank-API adapter is built here... a caller-supplied, already-parsed batch of lines") by building a real poller that calls that existing RPC unmodified. Composes the existing, evidence-CHECK-enforced RPD-016 SME-approval gate (`app.approve_finance_tax_rule`) rather than building a parallel activation path.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260805040000_create_intelligence_bank_payment_einvoice_tax_integrations.sql`, 9 numbered decisions). Summary:

1. **Case-by-case adapters (RPD-038).** Four distinct adapter codes seeded (`bank_feed_api`, `payment_gateway`, `einvoice_provider`, `tax_authority_api`), reusing `app.integration_connections`/`app.integration_connection_credentials` (IAE-336) directly.
2. **Provider data can never autonomously post journals, payments, tax or legal status.** Every new function is `FIN:Edit` at most. The existing, UNMODIFIED `FIN:Approve`-gated posting/activation surface (`app.issue_finance_invoice`, `app.approve_finance_tax_rule`, `app.match_finance_bank_transaction`) remains the only path to a legal/posting effect, and a human always calls it separately, citing this checkpoint's own evidence row id.
3. **The bank-feed gap is this checkpoint's real deliverable for "bank."** `app.import_finance_bank_statement` (FIN-211) is reused completely unmodified — the fifth real outbound HTTP client in this repository (`lib/finance-integrations/process-finance-bank-feed-sync-job.server.ts`) fetches a real batch and calls that existing RPC with it, inheriting its own idempotency/dedup machinery for free. Zero new schema for bank-side storage.
4. **A brand-new dedicated job type, `finance_bank_feed_sync`** — not a reuse of `recurring_billing` despite it being technically dormant (zero producer, zero consumer), because the name itself already denotes a different future capability (AR/subscription recurring billing) — a semantic collision risk, not merely a payload-shape one. Widened in the same three-place lockstep IAE-016 established, PLUS a fourth: `app.jobs_job_type_check`, `app.generic_job_types()`, `GENERIC_JOB_TYPES` (`background-job.ts`), and `IMPORT_EXPORT_JOB_TYPES` (`import-export.ts`).
5. **Payment gateway inbound webhook mirrors IAE-016's own receiver shape exactly**, but the HMAC secret is read from `app.integration_connection_credentials`. `app.finance_payment_gateway_events` is evidence-only, best-effort correlated to an existing, UNMODIFIED `app.finance_bank_transactions` row via its own `reference` column — a human confirms an actual match through the existing `app.match_finance_bank_transaction` (`FIN:Edit`) themselves.
6. **E-invoice submission and tax-authority-rate lookup share ONE evidence table, `app.finance_provider_call_evidence`** (a `call_type` discriminator, not a generic "call any provider" RPC — each call type keeps its own dedicated, separately-validated write function). E-invoice submission requires an already-`issued` invoice and never mutates its status. A tax-authority lookup's own evidence row id is meant to be cited in a human's `evidence_note`/`evidence_reference_file_id` when they separately approve a `app.finance_tax_rule_versions` row through the existing, evidence-CHECK-enforced `app.approve_finance_tax_rule` (RPD-016) — never an automatic trigger.
7. **Trigger authority is `FIN:Edit`, a deliberate divergence from IAE-014/015/016's own "any active tenant member" shape** — justified by the existing Finance-domain convention itself: `app.import_finance_bank_statement`, the exact adjacent action this checkpoint's poller calls, is already `FIN:Edit`-gated, not merely membership-gated.
8. **Cost metering (`RPD-028`) reuses `app.compute_provider_billed_amount` directly (IAE-014)** — confirmed by that function's own comment as covering prompts 343-346.
9. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public;`.
