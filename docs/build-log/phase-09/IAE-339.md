# IAE-339 — Vendor API

**Prompt ID:** `CG-S14-IAE-011` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/339_VENDOR_API_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — third prompt of Batch 3, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 3's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-011 is Batch 3's third capability: vendor-scoped API keys and the first two real REST `/v1/vendor/**` business resources (RFQ response, assignment accept/decline), extending `PLT-129`'s `app.api_keys` and IAE-009/010's gateway with a DATA-scope vendor binding -- never a new key table, never a fifth principal layer. Unlike IAE-010's customer key (which dispatches AS a real `customer_user`-layer identity), this checkpoint's own research established that NO vendor `auth.users` identity exists anywhere in this repository -- vendor intake is genuinely anonymous/token-based and every existing RFQ/capacity/assignment RPC is staff-captured "on behalf of" the vendor, by design, per those functions' own disclosed comments. Delivers: one additive nullable column on `app.api_keys`, a staff-only vendor-key-creation RPC (no vendor self-service is possible -- no vendor session exists to authenticate one), `revoke_api_key`/`rotate_api_key` extended once more to carry the new column forward on rotation, the gateway's dispatch resolution widened with a new, separate `vendor_master_record_id` output column, three new vendor-scope-authorized RPCs writing into the SAME canonical tables the staff-only functions already use, and a staff console UI extension.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260804030000_create_intelligence_vendor_api.sql`, 11 numbered decisions). Summary:

1. **No fifth principal layer -- a vendor API key is scoped to DATA, not an ACTOR.** Live-confirmed by direct repository research before any code was written: no table anywhere links a vendor to `auth.users`; vendor intake (`app.redeem_vendor_intake_token_and_submit`/`app.submit_vendor_profile_self_registration`) is deliberately, genuinely anonymous by its own header comments. A vendor key carries exactly one new additive nullable column, `vendor_master_record_id` -- a data-scope binding to one `app.vendor_profiles` row, structurally different from IAE-010's customer key (`customer_account_id` + `customer_actor_auth_user_id` pair).
2. **Vendor API keys are staff-issued only, never vendor self-service.** `app.create_vendor_api_key` requires `app.check_api_webhook_admin_authority` (Supreme or the tenant's own active tenant_admin) -- the SAME authority PLT-129's original `create_api_key` already requires -- issued out-of-band to the vendor, mirroring how `app.vendor_intake_tokens` are already staff-issued.
3. **Fixed scope marker, not RBAC-narrowed** -- the exact reconciliation IAE-010 already made for customer keys, applied again since a vendor has even less RBAC standing than a `customer_user` (no `auth.users` row at all). A vendor key carries exactly one fixed scope marker, `PRC:VendorPortal`.
4. **Gateway dispatch identity is `vendor_master_record_id`, not an `auth.users` UUID.** `app.authenticate_and_authorize_api_request` is extended once more, appending `vendor_master_record_id` as a NEW, SEPARATE output column (never coalesced into the actor-identity column, which stays populated with the staff issuer for accountability). **Self-caught before commit:** Postgres does NOT allow appending a new OUT column to an existing `RETURNS TABLE(...)` function via plain `CREATE OR REPLACE FUNCTION` ("cannot change return type of existing function") -- live-verified with a throwaway `pg_temp` function before touching the real migration; an explicit `DROP FUNCTION` then `CREATE FUNCTION` is required, with grants re-issued explicitly since they do not survive a drop.
5. **New, additive vendor-submission RPCs -- never staff functions repurposed.** `app.submit_rfq_response` and `app.accept_vendor_assignment_invitation`/`app.decline_vendor_assignment_invitation` are explicitly disclosed, in their own existing comments, as staff-actor-shaped ("requires an authenticated actor", PRC:Edit RBAC). This migration adds three new sibling functions authorized by vendor-scope containment instead, writing into the SAME canonical tables (`app.rfq_responses`, `app.vendor_assignment_invitations`) -- never a parallel table. `app.rfq_responses.capture_mode` widens (additive constraint replacement) to admit `'vendor_api'`.
6. **A late RFQ response is rejected outright via the Vendor API, never silently overridden** -- a vendor key holds no `PRC:Override` authority.
7. **Read access**: `app.get_rfq_for_vendor_api` returns an invitation ONLY when it genuinely belongs to the presented key's own `vendor_master_record_id`; a mismatched or nonexistent invitation gets the same `rfq_invitation_not_found` either way (anti-enumeration).
8. **Resource allowlist deliberately narrow, disclosed rather than padded**: RFQ read/response, assignment accept/decline. Capacity submission and invoice status are real, already-built Procurement capabilities this same vendor-scope pattern extends to directly -- deliberately deferred. Proof-of-delivery/ePOD has ZERO existing vendor entry point anywhere in the repository (confirmed by direct code search) -- net-new Operations-domain work, out of this migration's own bounded scope.
9. **`app.check_api_key_manage_authority` (IAE-010) needs no further widening for vendor-key revoke/rotate** -- its existing Supreme/tenant_admin branch already covers a vendor key, since there is no vendor-side self-service revoke/rotate to add. `app.rotate_api_key` carries `vendor_master_record_id` forward on rotation (the same "don't silently drop a new column" fix IAE-010 already applied for its own customer columns).
10. No new job type, no async work.
11. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public;`.

## 7. Tier B -- recurring defect taxonomy self-check

- **C-12/C-13 (`SECURITY DEFINER` authority, actor-identity)** -- every function granted to `authenticated` calls `app.assert_actor_is_session_identity` first. `app.get_rfq_for_vendor_api`/`submit_rfq_response_via_vendor_api`/`accept_/decline_..._via_vendor_api` are `service_role`-only (called exclusively from a REST route handler's own service-role client, matching `authenticate_and_authorize_api_request`'s own established boundary) -- there is no live authenticated vendor session to cross-check an actor identity against in the first place, since none exists.
- **Self-caught correction #1, before commit (real, live-verified):** appending a new OUT column to `app.authenticate_and_authorize_api_request` via plain `CREATE OR REPLACE FUNCTION` fails outright ("cannot change return type of existing function") -- caught via a deliberate throwaway `pg_temp` test BEFORE writing the real migration, not discovered live against the real function. Fixed with an explicit `DROP FUNCTION` then `CREATE FUNCTION`, with grants re-issued (a dropped function's grants do not survive).
- **Self-caught correction #2, before commit (real, live-caught via the db-test):** `app.create_vendor_api_key`'s own vendor lookup query (`where master_record_id = p_vendor_master_record_id and tenant_id = p_tenant_id`) raised `column reference "tenant_id" is ambiguous` -- the function's own `RETURNS TABLE(..., tenant_id uuid, ...)` clause creates an implicit PL/pgSQL variable named `tenant_id`, shadowing the table column. Fixed by qualifying both sides of the lookup (`app.vendor_profiles.tenant_id`); every other `RETURNS TABLE` function in this migration was then audited for the same class of bug (`list_vendor_api_keys_for_tenant` and `rotate_api_key` already used table aliases; `get_rfq_for_vendor_api`/`authenticate_and_authorize_api_request` use distinct output column names or aliases with no collision) -- confirmed the fix was the only instance, not merely patched at the first symptom.
- **Self-caught correction #3, before commit (live-caught via the db-test):** `app.get_rfq_for_vendor_api`'s original body referenced a nonexistent `app.rfqs.title` column -- `app.rfqs` has no `title` column at all, only `rfq_number`. Fixed in the migration, the TS contract (`RfqForVendorApi.rfqNumber`, not `rfqTitle`), and the corresponding unit test.
- **C-05 (permission check after disclosure)** -- `list_vendor_api_keys_for_tenant` raises `insufficient_authority` for a non-admin, before any row is returned.
- **C-19 (uniqueness scope)** -- no new unique constraint this checkpoint; `api_keys_customer_vendor_mutually_exclusive_check` and `rfq_responses_capture_mode_check` are shape/enum constraints, both live-verified.
- **ISS-2026-034-class / ATW-032 optimistic concurrency** -- `accept_/decline_vendor_assignment_invitation_via_vendor_api` re-check `record_version` in the `UPDATE ... WHERE` clause itself (mirroring the staff-only originals byte-for-byte on this point), never a separate lock-then-decide race.

No taxonomy class was skipped.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`create_vendor_api_key` authority is exact** -- staff-only creation against a REAL active vendor succeeds with the fixed `PRC:VendorPortal` scope marker; a PRC:View-only staff member, a nonexistent vendor id, a draft (not-yet-active) vendor, and a DIFFERENT tenant's admin are all denied.
2. **`list_vendor_api_keys_for_tenant` is scoped to exactly the vendor-scoped keys in this tenant** -- never a staff/customer key, joined with the vendor's own `legal_name`; a non-admin is denied.
3. **Gateway dispatch identity is real and correctly separated** -- `authenticate_and_authorize_api_request` resolves BOTH `created_by_auth_user_id` (the staff issuer) AND `vendor_master_record_id` (the DATA-scope binding) as two distinct, non-conflated fields; `forbidden_scope` holds for an uncarried scope.
4. **`get_rfq_for_vendor_api` reaches this vendor's own real invitation end to end** -- a mismatched vendor and a nonexistent invitation id both get the identical `rfq_invitation_not_found`, never disclosing which.
5. **`submit_rfq_response_via_vendor_api` writes a real, vendor-scope-authorized response into the SAME `app.rfq_responses` table** -- a mismatched vendor is denied; idempotent replay returns the identical row; a conflicting replay is rejected; `capture_mode='vendor_api'`, `actor_auth_user_id` is null, `actor_label='Vendor API'`.
6. **A late RFQ response is rejected outright** -- no `PRC:Override` path exists for a vendor key.
7. **`accept_/decline_vendor_assignment_invitation_via_vendor_api` write into the SAME `app.vendor_assignment_invitations` table** -- a mismatched vendor and a stale version are both denied; decline requires a real, non-empty reason.
8. **A rotated vendor key carries `vendor_master_record_id` forward**; staff can revoke a vendor key; a cross-tenant admin is denied managing another tenant's own vendor key.
9. **`api_keys_customer_vendor_mutually_exclusive_check` rejects a key scoped to both a customer account and a vendor.**
10. **The widened `authenticated` grant is real, not merely documented** -- a genuine forged authenticated session (not the connecting superuser) creates and revokes its own vendor key end to end; the same session cannot claim a different identity (`actor_identity_mismatch`).
11. **`anon` holds zero `EXECUTE`** on any new IAE-011 function.
