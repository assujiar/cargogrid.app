**Prompt ID:** `CG-S14-IAE-012` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/340_WEBHOOK_MANAGEMENT_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — fourth prompt of Batch 3, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 3's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-012 builds the real outbound webhook delivery worker `PLT-129` explicitly disclosed as not-yet-built ("The bounded delivery adapter interface... never calls a live HTTP endpoint itself") — on `app.jobs`, per `ADR-0025` Part B's own explicit instruction, never a bespoke poller over `app.webhook_deliveries` directly. Delivers: the real bridge between PLT-129's own retry/backoff/DLQ state machine and PLT-132's own generic job queue (`app.queue_webhook_delivery` extended to enqueue a real `webhook_retry` job per delivery), the first outbound HTTP client anywhere in this repository (bounded timeout, HMAC-signed, the raw signing secret never leaving the database), a real runnable worker script, test-send and dead-letter-replay RPCs, a real event-type catalog seed, and a full endpoint/delivery-log UI extension to IAE-009's own developer console.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260804040000_create_intelligence_webhook_management.sql`, 11 numbered decisions). Summary:

1. **The real delivery worker is built on `app.jobs`'s own existing `webhook_retry` job type** (present in `app.jobs_job_type_check`/`app.generic_job_types()` since PLT-132, unused until now — confirmed live before writing any code). `app.queue_webhook_delivery` (PLT-129) is extended (`create or replace function`, same signature) to also `app.enqueue_job()` one `webhook_retry` job per genuinely new delivery — idempotency-keyed on the delivery's own id, carrying the delivery's own `max_attempts` forward.
2. **Two independent retry/backoff state machines are kept numerically ALIGNED, not physically unified.** `app.jobs`'s own generic backoff (`app.record_job_failure`, PLT-132, unmodified) is the REAL scheduling driver a worker polls; `app.webhook_deliveries`'s own `attempts`/`next_attempt_at`/`status` (updated by the existing, unmodified `app.record_webhook_delivery_attempt`) remain PLT-129's own informational/delivery-log display state. Alignment is maintained by explicitly propagating `max_attempts` into every `enqueue_job()` call this migration makes — live-proven end to end (§10.6).
3. **The real, first-ever outbound HTTP client in this repository** (`lib/webhooks/process-webhook-delivery-job.server.ts`) — confirmed live by direct repository-wide grep before writing any code: zero `fetch()`/`axios`/`http.request` call to an arbitrary external URL existed anywhere in `app/`, `lib/`, `server/`. Bounded 10-second timeout via `AbortController`; HMAC-SHA256 signature/timestamp headers computed via the existing `app.compute_webhook_signature` RPC — the raw signing secret never leaves the database into application memory.
4. **A real, runnable worker script** (`scripts/jobs/webhook-delivery-worker.ts`) polls `app.claim_next_job` for `webhook_retry` — mirrors `scripts/load-tests/job-poll-worker.sh`'s own disclosed "NOT a production scheduler" shape, since no live cron/daemon exists anywhere in this repository for ANY `app.jobs` job type (`ISS-2026-015`, a standing, disclosed, accepted repository-wide risk this checkpoint does not newly introduce).
5. **`app.send_test_webhook_delivery`**: staff-only, scoped to exactly ONE named endpoint (bypasses the subscription-fanout loop `app.queue_webhook_delivery` itself uses), against a new `webhook.test` event type, enqueues a real job (`max_attempts=1`, `priority=10`) — a console "Test" action genuinely exercises the real worker end to end.
6. **`app.replay_webhook_delivery`**: staff-only, valid ONLY from `status='dead_letter'` — resets delivery state and enqueues a fresh job with a new idempotency key.
7. **`app.list_webhook_deliveries_for_tenant`**: staff-only read, joined with the endpoint's own url, optional status filter — `security definer`, `assert_actor_is_session_identity` applied proactively.
8. **Seeds real, business-accurate event-type catalog rows** via direct insert at migration-apply time (mirrors IAE-009's own `app.api_versions` seeding precedent): `shipment.status_changed`, `ticket.created`, `invoice.issued`, `webhook.test`. **Wiring a live trigger into an existing domain mutation is disclosed, deferred future work** — `app.queue_webhook_delivery` is already fully generic and callable today for any subscribed event type; this checkpoint proves the full mechanism end to end via direct calls and a real local HTTP server in its own tests, rather than putting an already-shipped domain mutation at avoidable regression risk.
9. **UI extends the existing `admin/api-keys` console** (IAE-009) — endpoint registration/list/rotate-secret/disable/reenable/test-send, and a delivery-log/DLQ view with manual replay. Reuses PLT-129's own endpoint CRUD unchanged.
10. No job-type-registry widening needed — `webhook_retry` already existed, unused.
11. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public;`.

## 10. Live adversarial proof (against a real disposable Postgres 16 database and a real local HTTP server, not reasoned about)

1. **`queue_webhook_delivery` enqueues a real `app.jobs` job per genuinely new delivery** — aligned `max_attempts`, idempotency-keyed on the delivery id; a replay never double-enqueues a second job.
2. **`send_test_webhook_delivery` is scoped to exactly one endpoint** — never fans out to another endpoint subscribed to the same event type; enqueues a fast-fail (`max_attempts=1`), high-priority (`10`) job; a non-admin is denied.
3. **`replay_webhook_delivery` is valid only from `dead_letter`** — resets delivery state, enqueues a genuinely fresh job with a new idempotency key; denied for a non-terminal delivery and for a non-admin.
4. **`list_webhook_deliveries_for_tenant` is scoped to the caller's own tenant** with a real joined `endpoint_url` and a working status filter; a non-admin and a cross-tenant admin are both denied.
5. **The real `app.jobs` <-> `app.webhook_deliveries` bridge holds under a full worker simulation** — a successful delivery completes both state machines together; exhausting `max_attempts` dead-letters both together, staying numerically aligned as designed.
6. **The real outbound HTTP client genuinely delivers, fails, and times out correctly** — proven against a real local `node:http` server: a 2xx response is recorded as success and completes the job (signature/timestamp/event/delivery-id headers all verified present on the wire, body verified byte-identical); a 5xx response is recorded as failed and reported to `app.jobs`; a real connection-refused network error is classified as a failure, never an uncaught throw; an already-terminal delivery completes the job without a redundant live HTTP call; a disabled endpoint fails without attempting a live HTTP call.
7. **`anon` holds zero `EXECUTE`** on any new IAE-012 function.
8. **The widened `authenticated` grant is real** — a genuine forged authenticated session lists real webhook deliveries end to end; the same session cannot claim a different identity (`actor_identity_mismatch`).

## 13. Batch 3 Tier C review — findings and fixes against this capability

Batch 3's own mandatory Tier C review found the largest concentration of real defects against this capability's own code -- the first real outbound HTTP client and the first real `app.jobs`-backed retry/DLQ worker in the repository, both genuinely new surface area. Closed by one bounded fix migration (`supabase/migrations/20260804060000_harden_intelligence_batch3_tier_c_review_fixes.sql`) plus a new TypeScript SSRF guard, independently re-verified by the orchestrating session (full findings/fix summary: `docs/build-log/phase-09/00_EXECUTION_INDEX.md` §14). This section records what concerns IAE-012 specifically, in full.

1. **[Critical, fixed] `app.replay_webhook_delivery` permanently broke any delivery it replayed.** It reset `attempts=0`, but `app.webhook_delivery_attempts` (PLT-129) is append-only and its own `webhook_delivery_attempts_unique (webhook_delivery_id, attempt_number)` constraint is never cleared -- the unmodified `app.record_webhook_delivery_attempt` computes the next `attempt_number` as `v_delivery.attempts + 1`, so resetting to 0 guaranteed the very next real attempt would collide with attempt_number=1, already recorded before the replay. 100% reproducible, no concurrency required -- live-confirmed via a direct replay-then-record-attempt sequence in a fresh scratch database, with the exact `duplicate key value violates unique constraint "webhook_delivery_attempts_unique"` error. The real worker has no recovery from this exception (`lib/webhooks/process-webhook-delivery-job.server.ts` calls `recordWebhookDeliveryAttempt` with no try/catch), so the reclaimed job would crash-loop indefinitely instead of ever completing. **Fixed** by never resetting `attempts` (preserving the append-only invariant `attempts == count(*) of webhook_delivery_attempts for this delivery`) and instead granting a fresh BUDGET of `max_attempts` (the delivery's own currently-configured value) more real attempts on top of whatever was already used (`max_attempts := attempts + max_attempts`). Live-reverified across TWO full replay cycles in the fix pass's own scratch-database proof, plus a new permanent regression in `scripts/db-tests/webhook-management.sql`'s own replay assertion block.
2. **[Critical, fixed] `app.replay_webhook_delivery` had no row lock.** Two concurrent replays of the same `dead_letter` delivery both passed the `status = 'dead_letter'` check and both enqueued an independent job for the SAME delivery -- live-proven via two real, separately-connected `psql` background processes racing the SAME delivery id, both succeeding and minting two distinct `webhook_retry` jobs pointed at one delivery. Combined with finding 1, the second job to actually record an attempt would additionally collide on the attempt-history constraint. **Fixed** via `select ... for update` on the initial read: re-raced live after the fix with the identical two-process setup -- session A succeeded, session B correctly blocked until A committed, then cleanly rejected with `webhook_delivery_not_replayable` (status was already `pending`, no longer `dead_letter`) -- exactly one live job existed afterward. A permanent (necessarily sequential, since the db-test harness runs one connection) regression proving the same guard -- an already-replayed delivery can never be replayed again until it returns to `dead_letter` -- was added to `scripts/db-tests/webhook-management.sql`.
3. **[Medium, fixed] `app.queue_webhook_delivery` had an unlocked check-then-insert idempotency gap** on its own new delivery row (this checkpoint's own extension) -- live-proven: two concurrent calls sharing an idempotency key, one succeeded, the OTHER raised a raw `webhook_deliveries_idempotency_unique` violation instead of the documented idempotent no-op (the real `app.jobs` bridge was correctly NOT double-enqueued only because the loser's entire call aborted). **Fixed** via a single atomic `insert ... on conflict (tenant_id, webhook_endpoint_id, idempotency_key) do nothing returning *`, enqueuing the real job ONLY when the insert actually happened (`FOUND`) -- re-raced live after the fix: both concurrent calls now succeed cleanly, return the SAME delivery, and exactly one delivery row plus one job exist afterward.
4. **[High, fixed, security] SSRF -- the real webhook delivery worker had no runtime protection against a hostname that only resolves to a private/loopback/link-local/cloud-metadata address at actual dispatch time (DNS rebinding).** `app.validate_webhook_url` (PLT-129) only rejects a LITERAL private IP at registration time -- its own migration header explicitly disclosed this as a gap for "the not-yet-built delivery worker" to close; this checkpoint built that worker without closing it. Live-proven: `select app.validate_webhook_url('https://169-254-169-254.sslip.io/steal-metadata')` returns `true` (a real, public DNS name resolving to the cloud metadata IP `169.254.169.254` sails straight through registration). **Fixed in TypeScript, not SQL**: `lib/webhooks/ssrf-guard.server.ts` (new) re-resolves the endpoint hostname immediately before every dispatch via `dns.promises.lookup` and refuses to send if ANY resolved address is private/loopback/link-local/reserved (13 unit tests, including the exact DNS-rebinding-to-cloud-metadata scenario); `lib/webhooks/process-webhook-delivery-job.server.ts` is wired to call it before every `fetch()` and now sets `redirect: 'manual'` to close the matching redirect-based SSRF vector (a new test proves a 3xx response is never auto-followed). A new end-to-end test in `process-webhook-delivery-job.server.test.ts` proves the REAL (non-injected) guard refuses a literal private-IP endpoint without ever attempting a live HTTP call.
5. **[Low, disclosed, NOT fixed] "Endpoint verification" (Prompt 340 §15) was narrowed to "test send," undisclosed.** The shipped console only offers `app.send_test_webhook_delivery` ("Send test" button) -- there is no distinct endpoint-ownership verification/challenge flow proving the tenant genuinely controls the registered URL before it is trusted. Disclosed here as a deliberate, reasonable narrowing (a full ownership-challenge flow is a larger feature than this bounded fix pass's own scope), not implemented.
6. **[Low, disclosed, NOT fixed] "Payloads contain only approved fields for the endpoint scope/version" (Prompt 340 §24) has no enforcement mechanism.** `app.queue_webhook_delivery` validates payloads only via PLT-129's generic, event-agnostic structural/injection check -- there is no per-event-type field allowlist. Currently moot in practice since no domain mutation is wired to call `queue_webhook_delivery` yet (§8 above); when a real domain trigger is eventually wired, nothing structurally prevents it from leaking an unapproved field. Disclosed as future work tied to that same wiring task, not a live gap today.
