# IAE-335 — Automation Rule Engine

**Prompt ID:** `CG-S14-IAE-007` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/335_AUTOMATION_RULE_ENGINE_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `VERIFIED`** (2026-08-21 — first prompt of Batch 2, Tier A/B self-reviewed and gate-verified individually at commit; `VERIFIED` as of Batch 2's own Tier C review close — see §13 — migration `20260803030000_harden_intelligence_batch2_tier_c_review_fixes.sql`, independently re-verified by the orchestrating session against a fresh disposable database and the full gate suite)

## 1. What this checkpoint builds

IAE-335 is Phase 9 Batch 2's first capability: a governed condition/action ("ECA": event → condition → action) automation rule engine for notifications, workflow steps and background jobs, with real versioning, a mandatory approval-gated publish (an AI-drafted or human-drafted rule can never publish itself), a pure dry-run simulation, and concurrency-safe cooldown/storm-window loop suppression. Per `ADR-0025` Part D, execution reuses the existing canonical `app.jobs` durable queue (`PLT-131/132`) — no second scheduler/queue table.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260803010000_create_intelligence_automation_rule_engine.sql`, 10 numbered decisions). Summary:

1. **Module code `INTHUB`** — newly seeded into `app.entitlement_modules`, but not an ad hoc 10th module: `docs/architecture/01_MODULE_DEPENDENCY_MAP.md` §2.1 already names `INTHUB` ("Integration Hub, automation rules, public/customer/vendor API, webhooks, n8n", Prompts 335-341) as the ratified module code for exactly this capability grouping. This is the first of those 7 prompts to ship code, so this migration is the first to insert the row. Actions seeded: `INTHUB:Configure`, `INTHUB:View`.
2. **Rule identity is a bespoke versioned table pair** (`app.automation_rules`/`app.automation_rule_versions`, mirroring `app.tenant_dashboards`/`app.tenant_dashboard_versions` exactly), **not** the Configuration Engine (`PLT-121`) despite `PLT-122`/`PLT-123` (Workflow/Approval) both riding it. Direct inspection of `app.config_objects`'s own `config_objects_scope_unique` index shows the Configuration Engine models "at most ONE object per (type, scope)" — correct for a tenant's one named setting, wrong for "create as many independently-named rules as you want." Same shape question `IAE-003`/`IAE-004` already answered the same way in Batch 1.
3. **Publish is gated by the existing Approval Engine (`PLT-123`), reused directly.** A granular config_type_code `'approval:automation_rule_publish'` is registered (mirrors `'notification:scheduled_report_ready'`'s own established convention). `publish_automation_rule_version` requires an `approved` `app.approval_requests` row whose `entity_type`/`entity_id` binds to the EXACT draft version — never merely "some approval exists." **Correction found while wiring the real UI (not a lens finding — self-caught during this same checkpoint):** `app.request_approval`/`app.decide_approval_step` are themselves `service_role`-only (`PLT-123`'s own migration grant) — a live end-user session can never call either directly. Both get a domain-scoped `SECURITY DEFINER` proxy (`request_automation_rule_publish_approval`/`decide_automation_rule_publish_approval`), the second added specifically to close this gap before commit. `decide_automation_rule_publish_approval` refuses a step outside an `automation_rule_version` request by name — never a generic "decide any step" bypass.
4. **Action allowlist is bounded to 3 platform primitives**: `notify` (`app.queue_notification`), `transition_workflow` (`app.transition_workflow_instance`), `enqueue_job` (`app.enqueue_job`, targeting only this migration's own new job type `automation_action_execution`). No action reaches into a business-domain table directly (Module Dependency Map R1). "Assignments"/other domain mutations from the prompt's own objective text are satisfied generically via `enqueue_job` targeting a future domain-owned job type/worker — disclosed, not built here.
5. **`app.evaluate_event_for_automation_rules` is `service_role`-only** — a trusted system dispatcher, never a live browser session (mirrors `app.dispatch_event_as_job`'s own shape). No domain capability calls it automatically yet (confirmed zero real event producers exist anywhere in this repository, per `ADR-0025`'s own evidence) — proven end-to-end via direct calls in the db-test instead of a fabricated "it just works" claim.
6. **Loop/storm suppression is a genuinely new primitive** — no cooldown/debounce pattern exists anywhere else in this repository (confirmed by direct grep before writing). Real, row-locked `cooldown_seconds` + sliding `max_fires_per_window`/`window_seconds`, mirroring this same phase's own Batch 1 Tier C `app.run_scheduled_report` concurrency lesson. A suppressed evaluation still records a real, queryable execution row.
7. **Idempotency**: `app.automation_rule_executions` unique on `(automation_rule_id, idempotency_key)`; the key is the triggering `app.event_logs.id` when supplied (closing double-fire on event redelivery), else freshly generated for a synthetic call.
8. **Condition language is small and bounded**, not Turing-complete: `{field,operator,value}` triples, AND-combined, `eq/neq/gt/gte/lt/lte/contains`.
9. **Dry run is a pure, side-effect-free simulation** — proven directly by asserting zero new rows in `app.notifications`/`app.jobs`/`app.workflow_transition_history` result from a dry run.
10. **`customer_user`-layer/C-05 discipline applied proactively from the first draft**, applying this same phase's own Batch 1 Tier C lessons rather than re-discovering them.

## 8. Residual/disclosed limitations

- **No domain capability calls `app.evaluate_event_for_automation_rules` automatically yet.** Zero real business-event producers exist anywhere in this repository today (confirmed by `ADR-0025`'s own evidence gathering) — wiring a real domain trigger (e.g., Ticketing emitting `ticket.created` via `app.append_event_log`) is a disclosed, future, per-domain task.
- **The action allowlist excludes direct domain mutations** (e.g., ticket assignment) by design — satisfied generically via `enqueue_job` targeting a future domain-owned job type, never by reaching into another domain's own tables.
- **Cooldown/storm-window values are fixed sensible defaults, not yet tenant-configurable via any RPC** (`cooldown_seconds=60`, `max_fires_per_window=20`, `window_seconds=3600` at row creation). A future increment could add a `set_automation_rule_limits` RPC; out of this checkpoint's own scope.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **Approval-gated publish is real, not cosmetic** — publishing is rejected while the request is `pending`; rejected again when an approved request is bound to a DIFFERENT rule's draft (`automation_rule_publish_approval_mismatch`, proven with a real second rule + a real approved-but-unrelated request); succeeds only once the exact draft's own request reaches `approved`.
2. **The `service_role`-only gap in the reused Approval Engine is real and was actually closed** — confirmed by grepping `PLT-123`'s own grants (`request_approval`/`decide_approval_step` granted to `service_role` only), then proving the new domain-scoped proxy is reachable by `authenticated` and refuses a step from an unrelated request (`automation_rule_publish_approval_wrong_domain`, proven via a direct fixture-inserted foreign step).
3. **A real event fires all 3 action types together** — one `app.evaluate_event_for_automation_rules` call against a real `app.event_logs` row produces a real `app.notifications` row, a real `app.workflow_instances` state transition (`a`→`b`), and a real `app.jobs` row, all recorded in one `completed` execution row.
4. **Idempotent on event replay** — the SAME source event redelivered reuses the SAME execution row; the notification/job counts do not increase.
5. **Cooldown and storm-window suppression are both real and row-locked** — a second event within the cooldown window is suppressed with zero new side effects; a rule already at its own fire cap is suppressed with `storm_window_exceeded`; both leave a real, queryable execution row.
6. **Dry run is provably pure** — matched/non-matched sample events against the draft produce zero new rows in `app.notifications`/`app.jobs`.
7. **Live forged-session RLS probe** — a `customer_user`-layer portal principal with real active tenant membership sees ZERO rows across all 3 new tables via raw `SET ROLE authenticated` RLS; an ordinary tenant member sees the real rows.
8. **Pausing a rule structurally excludes it from evaluation** — zero new execution rows (not even suppressed) for a paused rule receiving a matching event.

## 13. Tier C fix pass (Batch 2 review close)

Batch 2's own mandatory four-lens review (spec-compliance; security/RLS/tenant, live-tested; correctness/concurrency, live-tested; cross-prompt integration) surfaced six real findings against this capability's own code — three of them independently reported by two or three different lenses at once (the same underlying bug, not three separate defects) — plus one cross-capability finding this capability contributed to.

- **Finding 1 (Critical, reported independently by three of the four lenses).** `app.evaluate_event_for_automation_rules`'s own `transition_workflow` action resolved the target `app.workflow_instances` row by id ALONE, with zero `tenant_id` filter. Live-reproduced: a dual-tenant-member actor (an ordinary, fully-supported multi-tenant-membership scenario) firing tenant A's own rule with an event payload naming tenant B's own real workflow instance id caused tenant A's rule to actually transition tenant B's own instance — the downstream `app.transition_workflow_instance` only checks authority against the INSTANCE's own tenant, never the firing RULE's tenant. Fixed by scoping the lookup to `tenant_id = p_tenant_id`, folding a resolved-but-wrong-tenant id into the same `automation_action_workflow_instance_not_found` error a genuinely missing id already produces — mirroring the `notify` action's own already-correct `p_tenant_id`-bound discipline in the very same function. Live regression added to `scripts/db-tests/automation-rule-engine.sql`: a real cross-tenant instance id is refused and never mutated, even from a real dual-tenant-membership actor.
- **Finding 2 (Critical, correctness-concurrency, live-reproduced both sequentially and under genuine two-OS-process concurrency).** Approval-gated publish was bypassable: `app.publish_automation_rule_version` only checked that an approved request's `entity_id` equals the draft ROW's id — never that the draft's own CONTENT still matched what was actually reviewed. `app.set_automation_rule_definition` has no lock against editing an already-approved-but-unpublished draft. Live-reproduced: approve a reviewed `notify` action, then edit the SAME draft to an entirely different, never-reviewed `enqueue_job` action, then publish with the stale approval — the swapped content published cleanly, no error, both sequentially and in a genuine concurrent race between the editor and the publisher. Fixed by freezing a content hash (`md5(trigger_event_type || conditions::text || actions::text)`) of the draft at the moment `request_automation_rule_publish_approval` opens the request (new, isolated table `app.automation_rule_publish_approval_content_hashes` — RLS enabled, zero policies, zero grant, `SECURITY DEFINER`-only, mirroring IAE-008's own credential-isolation pattern), and having `publish_automation_rule_version` recompute and compare the draft's CURRENT hash, rejecting the publish (`automation_rule_publish_content_changed`) on any mismatch. Live regression added: a draft edited after approval is refused at publish, and never actually publishes.
- **Finding 3 (High, security-rls-tenant).** `app.decide_automation_rule_publish_approval` was the ONE by-id lookup in this migration that did not fold a cross-tenant caller into a not-found error — live-reproduced: a tenant-2 actor with zero relationship to tenant-1's own real approval step got `insufficient_authority: ... is not an active member of tenant <tenant-1's real UUID>`, raised from the delegated `app.decide_approval_step` (PLT-123), disclosing the real foreign tenant id. Fixed by checking the caller's active membership in the resolved request's own tenant BEFORE delegating, folding a mismatch into the same `automation_rule_publish_approval_step_not_found` a missing id produces. Live regression added: a genuinely tenant-2-only identity (never given tenant-1 membership, unlike finding 1's own dual-tenant actor) gets `no_data_found`, never the tenant-id-disclosing error, and the step is confirmed to remain undecided.
- **Finding 4 (High, correctness-concurrency, live-reproduced with a real three-OS-process race).** The idempotency-key check ran BEFORE the `for update` row lock — a TOCTOU window: two concurrent callers for the SAME source event both pass the unlocked pre-check, then serialize on the lock; the loser unblocks into a stale cooldown decision and collides with the winner's own idempotency key on its own insert — an unhandled `unique_violation` propagated out of the function entirely, contradicting design decision 7's own "the SAME source event redelivered reuses the SAME execution row" guarantee, which the pre-existing db-test only ever proved under sequential replay. Fixed by re-running the identical idempotency-key check again immediately after the lock is acquired, short-circuiting to the now-visible committed row. **Live regression added, genuinely concurrent** (not simulated): a new three-process helper (`scripts/db-tests/automation-rule-engine-concurrency-helper.sh`, extending the established `wms-picking-concurrency-helper.sh` two-process pattern with a third, lock-holding process — reproducing the exact interleaving the bug required proved unreliable with only two racing processes) proves both racers complete cleanly with `status=completed` and zero `ERROR` in either process's own output, with exactly one execution row and one job row surviving.
- **Finding 5 (High, correctness-concurrency, the literal "realistic collision path" the review brief asked to check for).** A single rule version with more than one `enqueue_job` action (or more than one `notify` action to the same recipient/type/channel) computed the IDENTICAL idempotency/dedupe key for every one, since the key depended only on the rule id and the execution's own idempotency_key, never the action's own position. Live-reproduced: a rule with two DIFFERENT `enqueue_job` payloads fired once — `app.enqueue_job`'s own check-then-insert dedupe silently returned the FIRST action's row to the SECOND call, recorded as a false `completed` success with zero error and zero trace of the dropped payload. Fixed by threading a real per-action loop counter into both the `enqueue_job` idempotency key and the `notify` dedupe key. Live regression added: a rule with two distinct `enqueue_job` payloads now produces exactly 2 real, distinct `app.jobs` rows.
- **Finding 6 (Low, spec-compliance).** `app.dry_run_automation_rule` never called `app.validate_automation_rule_definition` — live-reproduced: a draft saved with an action_type entirely outside the publish-time allowlist was reported as something that "would fire," even though publish/approval would reject it outright. Not a security gap (governance still correctly blocks the actual publish) but a materially misleading preview. Fixed by having the dry run also attempt validation and return `valid`/`validationError` fields alongside the existing simulation result — plumbed through `server/contracts/automation-rule/automation-rule.ts`'s own `DryRunAutomationRuleResultSchema` and surfaced in the dry-run tester UI (`automation-rule-detail-panel.tsx`) as a visible "this draft is not yet publishable" warning, not left as an unused field. Live regression added at both layers: the SQL db-test and new `automation-rule.test.ts` cases.
- **Finding 7 (Medium, cross-prompt-integration, shared with IAE-008's own §13).** This capability's own widening of `app.generic_job_types()` (+`automation_action_execution`) was never mirrored into the TypeScript single source of truth, `GENERIC_JOB_TYPES` — and neither had 10 PRIOR migrations' own widenings, since the existing regression test compared the TS array against a second hand-copied literal in the SAME file, never the live database. All 11 missing values added to both `GENERIC_JOB_TYPES` (`server/contracts/background-job/background-job.ts`) and the sibling `IMPORT_EXPORT_JOB_TYPES` (`server/contracts/import-export/import-export.ts`, caught by its own already-correct parity assertion the moment `GENERIC_JOB_TYPES` was corrected), plus a genuine live drift gate added to `scripts/db-tests/background-job.sql` comparing a hardcoded TS-mirror literal against the real `app.generic_job_types()` output.

**Also fixed as direct TS-layer follow-through (no TODOs left):** `AUTOMATION_RULE_KNOWN_MUTATION_ERROR_CODES` (`server/mutations/automation-rule.ts`) gained the new `automation_rule_publish_content_changed` code so the new error classifies correctly instead of falling into generic `mutation_failed`.
