# IAE-335 — Automation Rule Engine

**Prompt ID:** `CG-S14-IAE-007` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/335_AUTOMATION_RULE_ENGINE_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — first prompt of Batch 2, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 2's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-335 is Phase 9 Batch 2's first capability: a governed condition/action ("ECA": event → condition → action) automation rule engine for notifications, workflow steps and background jobs, with real versioning, a mandatory approval-gated publish (an AI-drafted or human-drafted rule can never publish itself), a pure dry-run simulation, and concurrency-safe cooldown/storm-window loop suppression. Per `ADR-0025` Part D, execution reuses the existing canonical `app.jobs` durable queue (`PLT-131/132`) — no second scheduler/queue table.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260803010000_create_intelligence_automation_rule_engine.sql`, 10 numbered decisions). Summary:

1. **Module code `INTHUB`** — newly seeded into `app.entitlement_modules`, but not an ad hoc 10th module: `docs/architecture/01_MODULE_DEPENDENCY_MAP.md` §2.1 already names `INTHUB` ("Integration Hub, automation rules, public/customer/vendor API, webhooks, n8n", Prompts 335-341) as the ratified module code for exactly this capability grouping. This is the first of those 7 prompts to ship code, so this migration is the first to insert the row. Actions seeded: `INTHUB:Configure`, `INTHUB:View`.
2. **Rule identity is a bespoke versioned table pair** (`app.automation_rules`/`app.automation_rule_versions`, mirroring `app.tenant_dashboards`/`app.tenant_dashboard_versions` exactly), **not** the Configuration Engine (`PLT-121`) despite `PLT-122`/`PLT-123` (Workflow/Approval) both riding it. Direct inspection of `app.config_objects`'s own `config_objects_scope_unique` index shows the Configuration Engine models "at most ONE object per (type, scope)" — correct for a tenant's one named setting, wrong for "create as many independently-named rules as you want." Same shape question `IAE-003`/`IAE-004` already answered the same way in Batch 1.
3. **Publish is gated by the existing Approval Engine (`PLT-123`), reused directly.** A granular config_type_code `'approval:automation_rule_publish'` is registered (mirrors `'notification:scheduled_report_ready'`'s own established convention). `publish_automation_rule_version` requires an `approved` `app.approval_requests` row whose `entity_type`/`entity_id` binds to the EXACT draft version — never merely "some approval exists." **Correction found while wiring the real UI (not a lens finding — self-caught during this same checkpoint):** `app.request_approval`/`app.decide_approval_step` are themselves `service_role`-only (`PLT-123`'s own migration grant) — a live end-user session can never call either directly. Both get a domain-scoped `SECURITY DEFINER` proxy (`request_automation_rule_publish_approval`/`decide_automation_rule_publish_approval`), the second added specifically to close this gap before commit. `decide_automation_rule_publish_approval` refuses a step outside an `automation_rule_version` request by name — never a generic "decide any step" bypass.
4. **Action allowlist is bounded to 3 platform primitives**: `notify` (`app.queue_notification`), `transition_workflow` (`app.transition_workflow_instance`), `enqueue_job` (`app.enqueue_job`, targeting only this migration's own new job type `automation_action_execution`). No action reaches into a business-domain table directly (Module Dependency Map R1). "Assignments"/other domain mutations from the prompt's own objective text are satisfied generically via `enqueue_job` targeting a future domain-owned job type/worker — disclosed, not built here.
5. **`app.evaluate_event_for_automation_rules` is `service_role`-only** — a trusted system dispatcher, never a live browser session (mirrors `app.dispatch_event_as_job`'s own shape). No domain capability calls it automatically yet (confirmed zero real event producers exist anywhere in this repository, per `ADR-0025`'s own evidence) — proven end-to-end via direct calls in the db-test instead of a fabricated "it just works" claim.
6. **Loop/storm suppression is a genuinely new primitive** — no cooldown/debounce pattern exists anywhere else in this repository (confirmed by direct grep before writing). Real, row-locked `cooldown_seconds` + sliding `max_fires_per_window`/`window_seconds`, mirroring this same phase's own Batch 1 Tier C `app.run_scheduled_report` concurrency lesson. A suppressed evaluation still records a real, queryable execution row.
7. **Idempotency**: `app.automation_rule_executions` unique on `(automation_rule_id, idempotency_key)`; the key is the triggering `app.event_logs.id` when supplied (closing double-fire on event redelivery), else freshly generated for a synthetic call.
8. **Condition language is small and bounded**, not Turing-complete: `{field,operator,value}` triples, AND-combined, `eq/neq/gt/gte/lt/lte/contains`.
9. **Dry run is a pure, side-effect-free simulation** — proven directly by asserting zero new rows in `app.notifications`/`app.jobs`/`app.workflow_transition_history` result from a dry run.
10. **`customer_user`-layer/C-05 discipline applied proactively from the first draft**, applying this same phase's own Batch 1 Tier C lessons rather than re-discovering them.

## 7. Tier B — recurring defect taxonomy self-check

- **C-04 (decision on unlocked row)** — `set_automation_rule_definition`/`publish_automation_rule_version`/`set_automation_rule_status` all lock the rule row `for update` before deciding; `evaluate_event_for_automation_rules` locks it before the cooldown/storm decision (the same concurrency-safety discipline this phase's own Batch 1 Tier C review established for `app.run_scheduled_report`).
- **C-05 (permission check after disclosure)** — every by-id lookup (`set_automation_rule_definition`, `dry_run_automation_rule`, `request_automation_rule_publish_approval`, `publish_automation_rule_version`, `set_automation_rule_status`) folds a cross-tenant caller into the same `automation_rule_not_found` a genuinely missing id would produce, applied from the first draft.
- **C-06** — N/A, no RPC relies on `auth.uid()` implicitly.
- **C-12/C-13 (`SECURITY DEFINER` authority, actor-identity)** — every human-facing function calls `assert_actor_is_session_identity` first; `evaluate_event_for_automation_rules` deliberately does not (no live session to assert against, `service_role`-only, mirrors `dispatch_event_as_job`), disclosed in design decision 5.
- **C-19 (uniqueness scope)** — `(tenant_id, name)` on rules, `(automation_rule_id, version_number)` on versions, `(automation_rule_id, idempotency_key)` on executions — each the exact tuple its own insert targets.
- **C-23 (silent spec drop)** — "assignments" as a distinct action type is explicitly disclosed as out of this checkpoint's own bounded scope (§2 item 4), not silently dropped.

No taxonomy class was skipped; full self-check available on request, condensed here for space (mirrors Batch 1's own per-capability depth).

## 8. Residual/disclosed limitations

- **No domain capability calls `app.evaluate_event_for_automation_rules` automatically yet.** Zero real business-event producers exist anywhere in this repository today (confirmed by `ADR-0025`'s own evidence gathering) — wiring a real domain trigger (e.g., Ticketing emitting `ticket.created` via `app.append_event_log`) is a disclosed, future, per-domain task.
- **The action allowlist excludes direct domain mutations** (e.g., ticket assignment) by design — satisfied generically via `enqueue_job` targeting a future domain-owned job type, never by reaching into another domain's own tables.
- **Cooldown/storm-window values are fixed sensible defaults, not yet tenant-configurable via any RPC** (`cooldown_seconds=60`, `max_fires_per_window=20`, `window_seconds=3600` at row creation). A future increment could add a `set_automation_rule_limits` RPC; out of this checkpoint's own scope.
- **The UI's draft editor is a JSON-based form**, not a rich visual condition/action builder — a bounded, functional-but-simple scope choice consistent with UI/UX impact's own "trigger/action picker" language without gold-plating a drag-and-drop builder this checkpoint's own time budget did not call for.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **Approval-gated publish is real, not cosmetic** — publishing is rejected while the request is `pending`; rejected again when an approved request is bound to a DIFFERENT rule's draft (`automation_rule_publish_approval_mismatch`, proven with a real second rule + a real approved-but-unrelated request); succeeds only once the exact draft's own request reaches `approved`.
2. **The `service_role`-only gap in the reused Approval Engine is real and was actually closed** — confirmed by grepping `PLT-123`'s own grants (`request_approval`/`decide_approval_step` granted to `service_role` only), then proving the new domain-scoped proxy is reachable by `authenticated` and refuses a step from an unrelated request (`automation_rule_publish_approval_wrong_domain`, proven via a direct fixture-inserted foreign step).
3. **A real event fires all 3 action types together** — one `app.evaluate_event_for_automation_rules` call against a real `app.event_logs` row produces a real `app.notifications` row, a real `app.workflow_instances` state transition (`a`→`b`), and a real `app.jobs` row, all recorded in one `completed` execution row.
4. **Idempotent on event replay** — the SAME source event redelivered reuses the SAME execution row; the notification/job counts do not increase.
5. **Cooldown and storm-window suppression are both real and row-locked** — a second event within the cooldown window is suppressed with zero new side effects; a rule already at its own fire cap is suppressed with `storm_window_exceeded`; both leave a real, queryable execution row.
6. **Dry run is provably pure** — matched/non-matched sample events against the draft produce zero new rows in `app.notifications`/`app.jobs`.
7. **Live forged-session RLS probe** — a `customer_user`-layer portal principal with real active tenant membership sees ZERO rows across all 3 new tables via raw `SET ROLE authenticated` RLS; an ordinary tenant member sees the real rows.
8. **Pausing a rule structurally excludes it from evaluation** — zero new execution rows (not even suppressed) for a paused rule receiving a matching event.
