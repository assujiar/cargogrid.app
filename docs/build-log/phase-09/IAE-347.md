# IAE-347 — AI Governance Provider Boundary

**Prompt ID:** `CG-S14-IAE-019` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/347_AI_GOVERNANCE_PROVIDER_BOUNDARY_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — sixth and last independently-buildable prompt of the merged Batch 4, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at the merged batch's own single Tier C review close)

## 1. What this checkpoint builds

The governance FOUNDATION every AI-assisted capability from Prompt 348 onward builds on top of — analogous to what the Integration Hub (`IAE-336`) was for provider integrations. This checkpoint is NOT itself an AI feature: it registers a brand-new `AI` entitlement module (already ratified in `docs/architecture/01_MODULE_DEPENDENCY_MAP.md` §2.1 but not yet present in `app.entitlement_modules`), a shared evidence ledger (`app.ai_governed_requests`) every future AI feature records its own requests against, a real synchronous `openai_multimodal` dispatch client (the ninth real outbound HTTP client in this repository), and a domain-scoped proxy pair over the generic Platform Approval Engine (`PLT-123`) for mandatory human approval before a downstream capability may treat AI output as actionable. The structural guarantee this checkpoint provides, and the one every later AI capability inherits for free: **AI output can never autonomously write to any domain table** — no function in this migration grants INSERT/UPDATE/DELETE on any table outside its own new schema.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260805060000_create_intelligence_ai_governance_provider_boundary.sql`, 9 numbered decisions). Summary:

1. **A brand-new `AI` entitlement module is Supreme-registered here** — already ratified in the module dependency map but not yet present in `app.entitlement_modules`. Mirrors `IAE-007`'s own direct-INSERT seeding of `INTHUB` exactly (`app.entitlement_modules` has no CHECK enum, an open registry, so this is a single-place SQL insert, not a lockstep). Three permissions seeded: `Create`, `View`, `Approve`. Provider CONNECTION setup itself deliberately stays under the existing `INTHUB:Configure`, consistent with every prior Batch 4 capability.
2. **AI output can NEVER autonomously write to any domain table — structurally, not by convention.** The literal, strongest reading of RPD-021's "AI cannot autonomously post ledgers/payments, approve legal/tax status, change contracts, release payroll, assign blame or finalize critical decisions" — a downstream capability reads this checkpoint's own evidence and applies a value through its OWN existing, unmodified domain RPCs, exactly mirroring `IAE-018`'s own "never writes to `app.employees`/`app.finance_accounts`" boundary discipline.
3. **No prompt-injection CONTENT classifier is built — a deliberate, disclosed choice, not a gap.** A heuristic text classifier would be a fake/placeholder defense (this project's own "no placeholder/fake" Definition of Done forbids it); confirmed no precedent exists anywhere in the repository. The real defense is structural: decision 2's no-write-path guarantee plus decision 6's mandatory human-approval gate — never trusting AI output enough to act on it unsupervised, rather than trying to detect the injection itself.
4. **Redaction is a caller responsibility, not a DB-enforced content scrubber.** `app.redact_audit_payload` (PLT-101) is confirmed key-name-only (a fixed regex over jsonb KEYS, never VALUE content) — inadequate for free-text prompt/output payloads. This checkpoint applies a structural safety net only (`app.validate_config_value` for size/shape, plus `app.assert_ai_prompt_payload_has_no_secret_shaped_keys` mirroring `app.redact_audit_payload`'s own regex as a REJECTION gate) — genuine content-aware scoping of what goes into a prompt remains the caller's own responsibility, disclosed rather than silently assumed solved.
5. **Single-adapter dispatch shape, mirrors `IAE-015`'s own geocode client exactly** — one adapter (`openai_multimodal`, RPD-021's own named default), a live SYNCHRONOUS request/response call, never `app.jobs`-queued.
6. **Human approval reuses the generic Platform Approval Engine (`PLT-123`) via a domain-scoped `SECURITY DEFINER` proxy pair**, mirroring `app.request_automation_rule_publish_approval`/`app.decide_automation_rule_publish_approval` (`IAE-007`) exactly. A tenant publishes its own `approval:ai_output_acceptance` definition before any request can seek approval. Whether a given AI output NEEDS approval before a downstream capability treats it as actionable is that downstream capability's own judgment call — this checkpoint provides the mechanism, never forces every request through it.
7. **Cost metering (`RPD-028`) reuses `app.compute_provider_billed_amount` directly (`IAE-014`)** — AI/OCR is explicitly named alongside messaging/maps/third-party services in RPD-028's own text.
8. **`feature_code` is free text, never a CHECK enum** — RPD-038's own "no generic connector claim" spirit extended to AI features: Prompt 348+ names its own feature_code; this migration makes no claim about which future features exist.
9. Per `ERR-2026-004`: explicit `revoke execute on all functions in schema app from public;`.

## 13. Merged Batch 4 Tier C review — findings and fixes against this capability

The merged Batch 4's own mandatory Tier C review (4 parallel adversarial lenses: spec-compliance; security/RLS/tenant, live-tested; correctness/concurrency, live-tested; cross-prompt integration) ran against all six independently-built capabilities together on 2026-08-21, closed by one bounded fix migration (`supabase/migrations/20260805070000_harden_intelligence_batch4_tier_c_review_fixes.sql`) plus targeted TypeScript fixes, independently re-verified by the orchestrating session. Full cross-capability findings/fix summary lives in `docs/build-log/phase-09/00_EXECUTION_INDEX.md` §14; this section records only what concerns IAE-019 specifically — the most severe findings of the entire review, since this checkpoint is the governance FOUNDATION every later AI capability (Prompt 348+) will build on.

- **[Critical, fixed — the single most severe finding of the review] `app.record_ai_governed_request_outcome`'s pending-only transition was an unlocked SELECT-then-UPDATE, not an atomic guard.** The correctness lens live-reproduced this with 6 genuinely concurrent `psql` processes calling the function on ONE pending request: all 6 won, zero were rejected — the build log's own §6/§9 claim of a "single-transition-only" state machine was false under real concurrency. Consequence, live-demonstrated: a human-**approved** AI output was silently destroyed and replaced by a later straggler's own outcome (`output_payload` wiped, `billed_amount` corrupted from 1.2000 to 10.8000) while `approval_status` stayed `approved`, pointing at nothing. Fixed: the transition is now the atomic `UPDATE ... WHERE status = 'pending'` step itself; a losing caller now hits `FOUND = false` and gets the same clean, named `ai_governed_request_not_pending` error. Independently re-reproduced by the orchestrating session with the identical 6-way concurrent probe both before and after the fix: exactly 1 of 6 won post-fix, `app.audit_logs` shows exactly one successful transition, and the first winner's own `output_payload`/`billed_amount` survive untouched.
- **[High, fixed] `app.assert_ai_prompt_payload_has_no_secret_shaped_keys` was not recursive and crashed on a non-object top-level payload.** The security lens live-reproduced a nested `{"employee":{"bank_account_number":...}}` prompt payload passing entirely undetected (the guard only scanned top-level keys). The correctness lens separately live-reproduced a top-level JSON-ARRAY payload — an ordinary LLM/OCR extraction request or response shape — raising a raw Postgres `22023` (`cannot call jsonb_object_keys on an array`) instead of a named domain error, and worse, an array `output_payload` PERMANENTLY stranding the governed request at `pending` with no way to ever record its real outcome. Fixed: the guard now recurses correctly into nested objects and arrays, and no longer raises on a non-object top-level payload; both failure modes live-reproduced fixed.
- **[Medium, fixed] The same guard, applied to `output_payload`, REJECTED rather than redacted a secret-shaped key — but output is provider-controlled, untrusted content, not caller-authored.** The security lens live-reproduced an entirely ordinary, legitimate AI response containing a plausible top-level key (`token`/`bank`/`payroll`) making `app.record_ai_governed_request_outcome` raise and permanently lose the real HTTP outcome, model version, confidence and metered cost — the exact evidence this checkpoint exists to guarantee. Fixed: a new `app.redact_ai_output_payload_secret_shaped_values` recursively REDACTS (never rejects) a secret-shaped key's own value in `output_payload` before storage; `prompt_payload` correctly keeps the REJECTING guard, since that side is caller-authored and a secret-shaped key there is a real bug worth surfacing. Live-reproduced fixed: a nested `bank_account_number` value now redacts to `[REDACTED]` while its non-secret sibling keys survive untouched, and the outcome recording itself now succeeds instead of raising.
- **[High, fixed] `app.request_ai_governed_action` was granted to `authenticated` but was completely unreachable through the app's own RLS-scoped client** — the same defect class as IAE-016/017/018 (SECURITY INVOKER calling a `service_role`-only authority helper). Fixed identically: now SECURITY DEFINER plus `app.assert_actor_is_session_identity`; also now cross-checks `p_connection_id` belongs to `p_tenant_id` (the same connection/tenant gap the batch's other evidence-writer functions gained). Live-reproduced fixed via a genuine forged authenticated session, including the ATW-032 identity-impersonation guard.
- **[Medium, fixed] `app.request_ai_output_approval`'s "only once" guard raised a raw `unique_violation` under concurrency instead of its own clean named error.** The underlying `app.request_approval` (PLT-123) is itself an unlocked check-then-insert; two concurrent callers here can both pass the `approval_request_id is not null` check, then race into a raw `23505` on `approval_requests_tenant_idempotency_unique`. Fixed: now catches the `unique_violation` and translates it into the same `ai_governed_request_approval_already_requested` error the sequential path already raises.
- **[Medium, fixed] `app.ai_governed_requests` had no CHECK pairing `correlation_record_type`/`correlation_record_id`.** The correctness lens live-reproduced both half-set shapes being silently accepted (a type with no id is unresolvable; an id with no type is silently unreachable through the table's own correlation index). Fixed: a real CHECK constraint now requires both null or both set.
- **[High, fixed] `lib/ai-governance/dispatch-ai-governed-request.server.ts`'s own `model_version` was a hardcoded adapter-code literal (`"openai-multimodal"`), not the model the provider actually reported serving.** The spec-compliance lens flagged this against the prompt's own §33 acceptance ("model/version... are recorded") — a placeholder value persisted as governance evidence every future AI capability will rely on. Fixed: the client now parses an optional `model` field from the provider's own response, falling back to the adapter code only when the field is genuinely absent; a new test proves a real provider-reported model string is recorded verbatim.
- **[Low, comment-only fix] `app.decide_ai_output_approval`'s own comment mis-described its error shape** (claimed "not-found-shaped" where the code correctly raises a `check_violation`, `ai_output_approval_wrong_domain` — the code itself needed no change).
- **Disclosed, not fixed — real future scope, not defects in shipped code.** The spec-compliance lens found no prompt-template/version registry exists (`prompt_payload` is free-form, validated only for structure and secret-shaped keys, with nothing for §25's "validate config version" to check against); no evaluation-dataset hooks exist despite this checkpoint being the explicit foundation for Prompts 348-353; no idempotency key exists on `app.request_ai_governed_action` itself (a retried submit creates a second billable request); and `confidence_label='low'` is stored and returned but never gates anything (no low-confidence-forces-approval rule, only the provider-failure half of the prompt's own "fails or confidence is low" alternative flow is handled).
