# IAE-361 — Multi-Region and Data Residency

**Prompt ID:** `CG-S14-IAE-033` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/361_MULTI_REGION_DATA_RESIDENCY_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (Tier A/B clean; second capability of Group 8, "Enterprise Deployment, Residency, Scale, and DR", Prompts 360-363 — reaches `VERIFIED` only at that group's own Tier C review).

## 1. What this checkpoint builds

The real, structural governance layer for RPD-013's own rule ("APAC is default region; dedicated region/hosting is a contractual Enterprise option"): a region-assignment review → approval → active → decommissioned state machine per tenant, a real region × service-category capability matrix, and a real "register an exception" alternative flow — all composed with `IAE-032`'s own dedicated-deployment lifecycle to enforce "dedicated region requires dedicated deployment" as executable code, not prose.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260808100000_create_intelligence_multi_region_data_residency.sql`). Summary:

1. **Genuinely greenfield** — confirmed by direct grep before writing any code (no `region`/`residency` table, function, or `apac`/`americas`/`emea` region-code convention exists anywhere in this repository). RPD-013's own default is the real, structural default this checkpoint preserves: `app.resolve_tenant_region` returns `'apac'` for every tenant with no assignment row at all.
2. **Reuses the `DEPLOY` entitlement module** (`View`/`Configure`/`Approve`) from `IAE-032` rather than adding a new one — Prompt 361's own workstream is "Enterprise Deployment", identical to Prompt 360's own workstream (only the epic differs), and this checkpoint introduces no materially distinct actor-facing authority scope.
3. **"Dedicated region requires dedicated deployment" is a real structural composition, not a disclosed prose rule**: `app.approve_region_assignment` calls `app.resolve_tenant_deployment_type` (`IAE-032`) directly and rejects approval outright unless the tenant already has an `active` dedicated deployment — a real intra-group dependency exercised in code.
4. **"Do not claim multi-region availability without deployed architecture and test evidence" (Prompt 361 §24) is enforced structurally**: the seed data for `app.region_service_capabilities` marks EVERY service category for `americas`/`emea` as `supported = false` — honestly, because no real infrastructure is deployed to either region anywhere in this repository. A tenant's own region assignment can reach `approved` only once every gap has a real, separately-authorized `DEPLOY:Approve` exception registered.
5. **`app.tenant_region_assignments` only ever holds a row for a non-default region** (`region_code in ('americas', 'emea')`, CHECK-enforced) — the identical "absence means default" structural pattern `IAE-032`'s own `app.tenant_deployment_records` already established.
6. **`app.region_capability_exceptions` is the real, structural "register an exception" alternative-flow primitive** (Prompt 361 §22) — `DEPLOY:Approve`-gated (the same tier as approval itself) and rejected outright if the underlying capability is already supported (a non-gap exception would be a meaningless, misleading record).
7. **Lesson applied correctly from the very first draft this time, with no self-caught or Tier-C-caught retrofit needed**: `app.resolve_tenant_region` (the bare-tenant-id, no-actor-parameter RPD-013 default-resolution function) was granted to `service_role` ONLY from the start.
8. Every authenticated-reachable function is `SECURITY DEFINER` paired with `app.assert_actor_is_session_identity` as its first statement.
9. Per the standing convention since `PLT-118`: explicit, redundant `revoke execute on all functions in schema app from public`.

## 5. Schema

Three new tables: `app.region_service_capabilities` (platform-wide reference matrix, 15 seeded rows: `apac` fully supported, `americas`/`emea` fully unsupported), `app.tenant_region_assignments` (one optional row per tenant — absence means `apac`; `record_version`-incrementing trigger), `app.region_capability_exceptions` (one row per `(region_assignment_id, service_category)` gap, real upsert). No new entitlement module (reuses `DEPLOY`, design decision 2). No change to any existing table.

## 8. Residual/disclosed limitations

- **No real cross-region replication or data movement** — this checkpoint records that a region assignment is genuinely `active`; it does not itself move, replicate, or physically relocate any real data across regions. A future runbook/tool would read this checkpoint's own tables as its evidence layer, exactly mirroring `IAE-032`'s own "no physical provisioning" disclosure.
- **`americas`/`emea` are seeded fully unsupported by design** (design decision 4) — this is not a placeholder to be silently "fixed" later; it is the honest, current state of this repository's own deployed architecture. Any tenant reaching an `active` non-default region assignment today does so entirely via registered, audited exceptions, never via a false claim of genuine capability.
- **No dedicated region/residency admin UI** — consistent with every other Group 7/8 capability.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`app.resolve_tenant_region`**: returns `'apac'` for a tenant with zero assignment rows; still `'apac'` while merely `approved` (not yet genuinely `active`); flips to the real assigned region only once `active`; flips back to `'apac'` once `decommissioned`.
2. **`app.request_region_assignment`**: no-`DEPLOY:Configure` actor rejected; the already-default `apac` rejected as a meaningless explicit request; empty qualification reason rejected; a real `pending_review` row created on success; a SECOND request for the same tenant rejected with a real `unique_violation`.
3. **`app.approve_region_assignment` composed live with `IAE-032`**: rejected with `region_requires_dedicated_deployment` while the tenant has no dedicated deployment at all; `IAE-032`'s own full qualification→approval→provisioning→active lifecycle then driven to completion live within this same test; approval THEN rejected with `region_capability_gap_unresolved` (deterministic first-missing-category) once dedicated deployment is active but zero capability exceptions exist; approval finally succeeds only once every one of the five service categories is either genuinely supported (`ai_provider`, flipped live via `app.set_region_service_capability`) or covered by a real, registered exception (the remaining four); a second approval attempt on the now-approved record rejected (`region_assignment_not_pending_review`).
4. **`app.set_region_service_capability`**: non-Supreme-Admin actor rejected; Supreme Admin succeeds; invalid region/category rejected.
5. **`app.register_region_capability_exception`**: no-`DEPLOY:Approve` actor rejected; rejected as `region_capability_exception_not_needed` for a category already marked supported; the four genuinely unsupported categories registered successfully; a second call for the SAME category upserts the SAME row (new reason, same id) — confirmed via a direct row-count check (exactly 4 rows, never a duplicate).
6. **`app.set_region_assignment_status`**: the full transition graph live-walked — `approved -> decommissioned` (skipping `active`) rejected; `DEPLOY:View`-only actor rejected; `approved -> active -> decommissioned` driven in the real, valid order with `activated_at`/`decommissioned_at` set at the correct steps; on a SEPARATE, fresh tenant assignment, the rejection path live-proven: empty rejection reason rejected, a real reason accepted (`pending_review -> rejected`), and `rejected` confirmed terminal (no further transition permitted).
7. **Cross-tenant isolation**: a tenant-2 admin (holding `DEPLOY:Configure`/`View`/`Approve` — but only for tenant 2) cannot change status, register an exception, or read tenant 1's own region assignment or exceptions; passing tenant 1 (not their own tenant) to the platform-wide capability read is also rejected.
8. **Platform-wide data proven identical regardless of tenant**: a no-`DEPLOY:View`-anywhere actor is rejected outright; two actors gated only against their OWN, different tenants both see the SAME full 15-row capability matrix.
9. **RLS default-deny**: a direct `authenticated` `select` on all three new tables is denied at the raw-RLS level.

## 13. Self-caught fix, found and applied after commit, before Group 8's own Tier C review

The identical gap self-caught in `IAE-032`'s own `app.approve_dedicated_deployment_qualification` (see `IAE-360.md` §13) was present here too: `app.approve_region_assignment` required `DEPLOY:Approve`, but `app.tenant_region_assignments` tracked no `created_by_auth_user_id`, so an identity holding both `DEPLOY:Configure` and `DEPLOY:Approve` for a tenant could request a region assignment and then approve their own request.

Fixed identically: added `created_by_auth_user_id` to `app.tenant_region_assignments`, a `tenant_region_assignments_no_self_approval` CHECK constraint, and an explicit `region_self_approval_forbidden` application check inside `app.approve_region_assignment` itself. `server/contracts/multi-region-data-residency/multi-region-data-residency.ts`'s own `TenantRegionAssignmentSchema` updated to carry the new field; all affected test fixtures updated to match.
