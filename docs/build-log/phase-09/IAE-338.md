# IAE-338 — Customer API

**Prompt ID:** `CG-S14-IAE-010` · **Package document:** `docs/ai-agent-build-prompt-package/14-phase-09-intelligence-enterprise/338_CUSTOMER_API_PROMPT.md` · **Phase:** 9 (Intelligence, Automation and Enterprise Expansion) · **Status: `COMPLETED`** (2026-08-21 — second prompt of Batch 3, Tier A/B self-reviewed and gate-verified individually; reaches `VERIFIED` only at Batch 3's own Tier C review close, per `AGENTS.md`'s batched-review cadence)

## 1. What this checkpoint builds

IAE-010 is Batch 3's second capability: customer-scoped API keys and the first three real REST `/v1/customer/**` business resources, extending `PLT-129`'s `app.api_keys` and IAE-009's gateway with a `customer_user`-layer issuer — never a new key table, never a fifth access layer, never a second enforcement point alongside Customer Portal's own already-ratified `ADR-0024` RPCs. Delivers: two additive nullable columns on `app.api_keys`, a genuinely new self-service/on-behalf-of key-creation RPC, `revoke_api_key`/`rotate_api_key` extended (not forked) to serve customer keys too, the gateway's dispatch identity resolution widened to a customer key's own real actor, three real REST resources (shipment tracking, booking draft creation, booking submission), and a Customer Portal self-service key-management UI mirroring `customer-portal-users`' own established shape.

## 2. Design decisions (cited, not re-derived)

Full rationale lives in the migration's own header (`supabase/migrations/20260804020000_create_intelligence_customer_api.sql`, 9 numbered decisions). Summary:

1. **Customer-scoped keys are the same `app.api_keys` row** — two new additive, nullable columns, `customer_account_id`/`customer_actor_auth_user_id`, both null together (ordinary staff key) or both set together (`api_keys_customer_scope_shape_check`). Deliberately not always equal to `created_by_auth_user_id`: a tenant_admin may provision a key ON BEHALF OF a real customer contact, a disclosed support/bootstrap path.
2. **Customer-key scopes are NOT the staff RBAC taxonomy at all** — `customer_user` layer never composes with `app.evaluate_permission()` (`ADR-0024` Part B's own "Layer-4-only authority chain" text, confirmed by this checkpoint's own concrete build). Reconciled, disclosed rather than silently worked around: a customer key carries exactly one fixed scope marker, `CPT:CustomerPortal`, never caller-supplied. Real authority is always the SAME live, per-request `app.resolve_customer_account_scope`/`app.get_customer_portal_scope_context` re-evaluation the portal UI itself depends on — the key's frozen scope string is never the fine-grained boundary.
3. **`app.create_customer_api_key`: a genuinely new function**, not a widened `app.create_api_key`. Authority is `app.actor_is_active_customer_portal_account_admin` (self-service) OR `app.check_api_webhook_admin_authority` (support/bootstrap on-behalf-of). `p_customer_actor_auth_user_id` is validated against `app.resolve_customer_account_scope` for the target account before the key is ever created — a caller cannot bind a key to an identity with no real membership.
4. **`app.revoke_api_key`/`app.rotate_api_key` (PLT-129) are EXTENDED, not duplicated** — a new `app.check_api_key_manage_authority()` helper composes the unchanged tenant-admin authority with a new account_admin path; `rotate_api_key` now carries `customer_account_id`/`customer_actor_auth_user_id` forward onto the rotated row (previously would have silently dropped them, since the columns did not exist before this migration). Both functions' grant widens to `authenticated` in addition to `service_role`, so a real customer session can call them directly through the RLS-scoped client — the in-function check remains the real boundary either way.
5. **`app.authenticate_and_authorize_api_request` (IAE-009) is extended, not forked** — `create or replace function`, same signature. Dispatch identity is now `coalesce(customer_actor_auth_user_id, created_by_auth_user_id)`: a customer key dispatches as its own real customer identity; a tenant-staff key's behavior is byte-for-byte unchanged (re-proven live, §10).
6. **Resource allowlist deliberately narrow, disclosed rather than padded**, mirroring IAE-009's own discipline: `GET /v1/customer/shipments/{id}/tracking` (wraps `app.get_customer_shipment_tracking` verbatim), `POST /v1/customer/bookings` (idempotent create, wraps `app.create_customer_booking_request_draft`), `POST /v1/customer/bookings/{id}/submit` (wraps `app.submit_customer_booking_request`). Quote/documents/invoices/tickets/loyalty are real, already-built Customer Portal capabilities this same pattern extends to directly — deliberately deferred, not built out here.
7. **File downloads (short-lived signed URLs and reauthorization) are explicitly NOT built this checkpoint.** Live-verified by direct migration read: neither Customer Portal file capability (`app.get_customer_document`/`app.get_customer_epod`) ever issues a real signed URL today — both deliberately log `access_type='metadata_view'`. A genuine customer-facing signed-URL path is net-new work, left as a disclosed, real gap.
8. **No new job type, no async work** — synchronous request/response only, identical to IAE-009's own boundary.
9. Per `ERR-2026-004`: this migration carries its own explicit `revoke execute on all functions in schema app from public;` before its final grants.

## 5. Schema

`app.api_keys`: two new nullable columns, `customer_account_id uuid references app.accounts(id)`, `customer_actor_auth_user_id uuid references auth.users(id)`, plus `api_keys_customer_scope_shape_check` (`(customer_account_id is null) = (customer_actor_auth_user_id is null)`). No new tables.

## 6. RLS and grants

No RLS change — `app.api_keys` already default-denies `customer_user` at RLS (`ADR-0024` Part A); every customer-facing access path here is `SECURITY DEFINER` RPC-only, never a reopened policy. `anon` holds zero `EXECUTE` on any new/extended function (live-verified, §10). `check_api_key_manage_authority` is a plain (non-`SECURITY DEFINER`) `stable sql` helper — it runs under its caller's already-established security context, so it needs no context of its own.

## 7. Tier B — recurring defect taxonomy self-check

- **C-12/C-13 (`SECURITY DEFINER` authority, actor-identity)** — every new/extended function granted to `authenticated` calls `app.assert_actor_is_session_identity` first (`revoke_api_key`, `rotate_api_key`, `create_customer_api_key`, `list_customer_api_keys_for_account`), applied proactively from the first draft rather than discovered after the fact via the `rbac-enforcement.sql` sweep — the exact lesson IAE-009's own Tier B self-check surfaced for its sibling. A live forged-session `ATW-032` regression (a genuine member session claiming a different, genuinely-privileged identity) is in `customer-api.sql`.
- **Self-caught correction, before commit (real, significant):** widening `revoke_api_key`/`rotate_api_key`'s grant to `authenticated` (design decision 4) is not by itself sufficient — `CREATE OR REPLACE FUNCTION` does not inherit unspecified properties (security mode, `search_path`) from the prior definition; both functions had been PLT-129's own plain `SECURITY INVOKER` originally (safe when only `service_role` could call them, since `service_role` holds broad table access) and, left unchanged, silently stayed `SECURITY INVOKER` after the widened grant — a real `authenticated` session then failed with a raw Postgres `permission denied for table api_keys`, caught live via the forged-session db-test (not reasoned about in the abstract). Fixed by adding `security definer set search_path = app[, public], pg_temp` to both functions explicitly; the in-function `check_api_key_manage_authority`/`assert_actor_is_session_identity` checks remain the real authority boundary regardless of this fix — this only restores the ability to actually REACH the table once authorized.
- **`gen_random_bytes`/`digest` (pgcrypto) `search_path` gap** — caught in earlier manual smoke-testing (before the permanent db-test file existed): pgcrypto lives in `public` (confirmed live via `pg_extension`/`pg_namespace`), not `app`; every new `SECURITY DEFINER` function that calls it (`create_customer_api_key`, and now `rotate_api_key` once made `SECURITY DEFINER` per the correction above) explicitly widens to `set search_path = app, public, pg_temp`.
- **C-05 (permission check after disclosure)** — `list_customer_api_keys_for_account` raises `insufficient_authority` outright for an account the caller holds no relationship to, never a silently-empty list (conflating "authorized but nothing to show" with "not authorized at all" was an early db-test authoring mistake, corrected before this file was finalized, not a function defect).
- **C-19 (uniqueness scope)** — no new unique constraint this checkpoint; `api_keys_customer_scope_shape_check` is a shape (not uniqueness) constraint, live-verified to reject a half-set customer binding.

No taxonomy class was skipped.

## 8. Residual/disclosed limitations

- **Only three REST resources built** (tracking read, booking draft create, booking submit) — quote/documents/invoices/tickets/loyalty are real, already-built Customer Portal capabilities this same gateway/authority pattern extends to directly; deliberately deferred to a future increment (design decision 6).
- **File downloads (signed URLs) are not built** — neither underlying Customer Portal RPC issues a real signed URL today; fabricating one here would misrepresent what actually happens (design decision 7).
- **`app.check_api_key_manage_authority` is not independently `SECURITY DEFINER`** — correct as built (it inherits its caller's already-switched security context), but worth stating explicitly since it is the one new function in this migration that is NOT itself `SECURITY DEFINER`, to avoid a future reader assuming an oversight.

## 10. Live adversarial proof (against a real disposable Postgres 16 database, not reasoned about)

1. **`create_customer_api_key` authority is exact** — self-service succeeds for a real account_admin with the fixed `CPT:CustomerPortal` scope marker; a non-admin member is denied; a staff actor with NO tenant_admin layer and NO relationship to the account is denied; a staff tenant_admin may provision on behalf of a REAL member but never an identity with zero scope for the account.
2. **`list_customer_api_keys_for_account` is scoped to exactly one account** — never leaks tenant-staff keys, and refuses outright (never a silently-empty list) for an account the caller holds no relationship to.
3. **Gateway dispatch identity is real** — `authenticate_and_authorize_api_request` dispatches a customer key as its own bound `customer_actor_auth_user_id`, never its (possibly different) staff creator; `forbidden_scope` still holds for a scope the key does not carry. The resolved identity genuinely reaches a live Customer Portal RPC end to end (`get_customer_shipment_tracking`'s own anti-enumeration path), not merely identity resolution in isolation.
4. **Self-service revoke/rotate works end to end** — a real account_admin revokes/rotates their OWN account's key via PLT-129's own extended functions; `customer_account_id`/`customer_actor_auth_user_id` survive rotation.
5. **Cross-tenant isolation holds** — a real `customer_user` in an unrelated tenant can neither create nor list a key for another tenant's own account, correctly failing on the AUTHORITY check (`insufficient_authority`) before scope-binding is ever evaluated.
6. **The widened `authenticated` grant is real, not merely documented** — a genuine forged authenticated session (`request.jwt.claims` + `set role authenticated`, not the connecting superuser) creates and revokes its own account's key end to end; this is the exact proof that caught the missing `SECURITY DEFINER` bug (§7) before commit.
7. **`ATW-032` actor-identity proof** — a genuine authenticated session may not claim to act as a different identity when calling `create_customer_api_key`, even the account's own real admin; `actor_identity_mismatch` every time.
8. **`anon` holds zero `EXECUTE`** on any new IAE-010 function.
9. **`api_keys_customer_scope_shape_check` rejects a half-set customer binding.**
