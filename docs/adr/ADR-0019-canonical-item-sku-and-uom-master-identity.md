# ADR-0019 — Canonical Item/SKU and UOM master identity and ownership (Phase 5 WMS)

Status: ACCEPTED
Date: 2026-08-03   Approver: Runtime build agent (Phase 5 governance authority, per `docs/adr/README.md` §3 "implementation-level decision... the owning phase's capability prompt, when its evidence exists" — the same kickoff/capability-level resolution authority `ADR-0018` already exercised for `app.accounts`)   Supersedes/Superseded-by: —
Source candidate: `ADR-CAND-ARCH-031` (newly minted this checkpoint — no prior candidate in `docs/adr/README.md` §5.1/§5.2 covers item/SKU or UOM identity)   Owning phase/task: Phase 5 (`CG-S10-ATW-011A`, inserted between the `VERIFIED` Prompt 230 and Prompt 231 by explicit operator authorization)

## Question

A comprehensive, read-only gap audit of this repository's own Phase 5 build output (prompts 220-230, all `VERIFIED`) found that Prompt 231 (WMS Inbound) §9 requires "verified customer/item/master and shipment contracts," and Prompt 234 (Inventory Ledger) §9 requires "approved item/UOM/owner/status identity," as already-`VERIFIED` upstream dependencies — but no item/SKU/product master and no UOM registry have ever been built anywhere in this repository, and no prompt in the entire `docs/ai-agent-build-prompt-package/` package (79 through 430, confirmed by exhaustive filename enumeration and prompt-body grep) ever creates one. This is a circular, unsatisfiable dependency inside the package itself, escalated to the operator rather than silently resolved by a build agent. The operator authorized inserting a new atomic task (`CG-S10-ATW-011A`) to close it. This ADR resolves the one genuine architecture-shape question that insertion raises: should the item/SKU master be built as a `PLT-120` Master Data Engine extension (`app.master_records` with a new `master_type_code`), or as a flat, typed-column table — the identical shape question `ADR-0018` already resolved once for `app.accounts`.

## Evidence gathered this checkpoint

- `app.master_types` (`supabase/migrations/20260717120000_create_master_data.sql`, `PLT-120`, `VERIFIED`) has received exactly two `insert`/`register_master_type` calls in this repository's entire history: the seed `'vendor_rate'` (`PLT-120` itself) and `'vendor'`/`'fleet'`/`'vehicle'`/`'driver'` (`supabase/migrations/20260727130000_create_operations_resource_assignment.sql:60-64`, `OPS-172`). No `'item'`/`'sku'`/`'product'` type has ever been registered.
- `app.master_records`' own unique index is `(master_type_code, tenant_id, code)` (`20260717120000_create_master_data.sql:215-216`) — **tenant-wide, with no owner dimension**. A 3PL warehouse routinely holds the same SKU code for two different customers (e.g. both stock a generic "PALLET-STD" code) — `app.master_records` could never support that without a fabricated per-customer code-mangling convention. Its own `app.validate_master_attributes` (`:46-74`) additionally rejects nested objects/arrays in `attributes`, which a real per-item control-flag/dimension shape does not strictly need but which forecloses future structured extension without a second bespoke validator.
- `ADR-0018`'s own Decision (`docs/adr/ADR-0018-canonical-account-entity-shape-and-ownership.md`) already answered the structurally identical question for `app.accounts` — flat, typed-column, not built on the Master Data Engine — reasoning that applies here without modification: the Master Data Engine's authority model (`register_master_type` Supreme-only; `create_master_record` tenant-admin/support-grant-only for a `tenant`-scope type) is the wrong shape for an ordinary `OPS:Create`-gated warehouse-operations workflow action, and every genuinely comparable Phase 5 entity (`app.warehouses`, `app.warehouse_zones`, `app.warehouse_locations`) is already a flat, typed-column table, never built on `app.master_records`.
- `ATW-223`'s own precedent (`supabase/migrations/20260729310000_create_advanced_tms_fleet_driver_device.sql:49,93`) shows the one place in this repository a Phase 5 capability *did* extend `app.master_records` correctly: `app.vehicle_operational_profiles`/`app.driver_operational_profiles` layer an operational profile *over* an existing `master_records` vehicle/driver identity, never re-deriving it. That pattern does not fit here either — there is no pre-existing generic "item" identity anywhere to layer over; this checkpoint would be minting the base identity itself, the same situation `ADR-0018` faced for `app.accounts`, not the situation `ATW-223` faced.
- Every previously-existing UOM-shaped column in this repository (`app.warehouse_zones.capacity_uom`, `app.warehouse_locations.capacity_uom` — both `20260730140000`/`20260730150000`, `app.actual_costs.uom` — `20260728110000_create_operations_actual_cost.sql:138`) is unconstrained free text with no registry to validate against. `app.finance_currencies`/`app.validate_currency_code` (`supabase/migrations/20260728230000_create_finance_currency_exchange_rate.sql:52-84`, `FIN-194`) is the proven, directly-reusable shape for exactly this kind of small, governed, `service_role`-write/`authenticated`-read global reference catalogue — already used once in this repository for an analogous problem (currency codes), not a new pattern.
- Discrete packaging/handling units (box, carton, pallet) are structurally different from a physical UOM: a "1 box = N pcs" ratio varies per item, never a universal scalar conversion factor the way 1 kg = 1000 g always is. Modelling them as a `unit_category` here would fabricate a business rule ahead of Prompt 237 ("WMS Packing"), whose own §13 already names "package/container hierarchy... material, seal" as its own scope.

## Options

1. **(SELECTED) A flat, typed-column `app.item_masters` table, tenant + customer-owner scoped (mandatory `owner_account_id uuid references app.accounts (id)`), never built on `app.master_records` — mirroring `app.accounts`' own shape exactly.** A real, governed UOM registry (`app.uoms` + `app.uom_conversions`) mirroring `app.finance_currencies`/`app.validate_currency_code` verbatim, deliberately narrow (`unit_category in ('weight','volume','count','length')`) — discrete packaging/handling units explicitly deferred to Prompt 237, not fabricated here.
2. **Build on `PLT-120`'s Master Data Engine** (`app.master_records` with `master_type_code='item'`, plus a child detail table for structured fields).
   - Trade-off against: the tenant-wide (not owner-scoped) unique index cannot express "the same SKU code under two different customer owners," the single most basic real-world 3PL requirement this identity must support (proven directly in this checkpoint's own db-test, `scripts/db-tests/advanced-tms-item-uom-master.sql`, "the exact structural proof (design note 2)... the identical code SKU-100, same tenant, a DIFFERENT owner account -- must succeed as a second, distinct row"). Rejected for the identical reason `ADR-0018` rejected it for `app.accounts`.
3. **Fold item/UOM identity directly into Prompt 231's own scope**, widening its `§11` allowed-paths via this same ADR instead of inserting a new atomic task.
   - Trade-off against: Prompt 231's own atomic-sizing convention ("normally 5–15 files and at most 1–3 additive migrations," §11) is already spent on inbound-order-specific scope (root/version/line/source/appointment/readiness/lifecycle); folding in a second, independently-reusable identity (needed unmodified by 232/234/235/236/237/239/241 too) would make 231 both oversized and the wrong owner — every later WMS prompt would then have to depend on "Prompt 231, but only its item-master sub-slice," an artificial and undocumented sub-dependency. Rejected; a dedicated atomic task with its own task ID is cleaner and matches how `ADR-0018` itself was resolved (a dedicated Commercial capability, `COM-155`, not folded into an adjacent prompt).

## Decision

**Option 1.** `app.item_masters` is a new, flat, typed-column, tenant + customer-owner-scoped table (`CG-S10-ATW-011A`'s own migration, `supabase/migrations/20260730160000_create_advanced_tms_item_uom_master.sql`), mirroring `app.accounts`' shape and RLS posture (tenant-wide visibility via `app.has_active_tenant_membership`, never `app.master_records`). `app.uoms`/`app.uom_conversions` mirror `app.finance_currencies`/`app.validate_currency_code` verbatim. Packaging/handling-unit identity is explicitly out of scope, deferred to Prompt 237.

## Consequences

- **DB/API:** One new migration adds `app.item_masters`, `app.uoms`, `app.uom_conversions`, and their create/update/status/read/convert RPCs — fully additive, zero `PLT-120`/`app.accounts` change. `(tenant_id, owner_account_id, code)` is the real database-enforced uniqueness key, not merely an application-level check.
- **Security:** No per-field masking; `app.item_masters` follows `app.accounts`'/`app.margin_rule_versions`' own already-established "tenant-wide reference identity, not a specific transaction's figure" precedent — every column visible to any active tenant member, mutation gated by `OPS:Create`/`OPS:Edit`/`OPS:View` only (this repository's own standing Warehouse Foundation module code, confirmed at `ATW-229`).
- **Performance:** the flat-column shape is a precondition for `(tenant_id, owner_account_id, status)`/`(tenant_id, status)` indexes, the same reasoning `ADR-0018` already used to justify a flat table over `attributes jsonb` for `app.accounts`.
- **Migration/rollback:** additive only. `git revert` of this checkpoint's commit is safe and complete; no `PLT-120`, `app.accounts`, or any prior Phase 5 migration is altered.
- **Downstream impact / what remains open:** Prompt 231 (WMS Inbound), once `CG-S10-ATW-011A` is `VERIFIED`, becomes dependency-clean on its own §9 "verified customer/item/master and shipment contracts" line. Prompt 237's own obligation to define packaging/handling-unit identity is named here, not foreclosed. Retrofitting the pre-existing free-text `capacity_uom` columns (`app.warehouse_zones`, `app.warehouse_locations`) to validate against `app.uoms` is a real, disclosed, deferred obligation for whichever future capability first needs it — not silently done by this checkpoint, since editing an already-applied migration is forbidden.
