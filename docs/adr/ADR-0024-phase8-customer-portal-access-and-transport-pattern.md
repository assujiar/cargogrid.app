# ADR-0024 — Phase 8 customer-portal read/write access pattern, transport scope, and loyalty ledger/handoff shape

Status: ACCEPTED
Date: 2026-08-16   Approver: Runtime build agent (Phase 8 kickoff authority, per `docs/adr/README.md` §3, exercised at `299_CUSTOMER_PORTAL_LOYALTY_WBS_RUNTIME_KICKOFF_PROMPT.md` §"Required kickoff work", the same kickoff-level-resolution precedent `ADR-0015`/`ADR-0020`/`ADR-0023` used at the Phase 2, 6, and 7 kickoffs)
Source candidate: `ADR-CAND-ARCH-035` (next master-register number after `034`/`ADR-0023`, newly minted; no prior candidate covers a repository-wide customer-facing (Layer 4) access pattern)
Owning phase/task: Phase 8 (`CG-S13-CPL-001`, Prompt 299, Customer Portal and Loyalty WBS Runtime Kickoff)
Supersedes/Superseded-by: — (ratifies and generalizes the already-shipped `ATW-023`/`ATW-032` pattern; narrows `ADR-CAND-ARCH-017`'s open persisted-op/GraphQL-server question for Phase 8's own scope only, does not resolve it repository-wide)

## Question

Prompt 299's own "Required kickoff work" requires mapping all 24 Phase 8 capabilities and confirming they can proceed without re-litigating settled questions ad hoc inside each capability prompt. Direct repository inspection this checkpoint (eight parallel domain research passes, each independently reading every one of Prompts 300-323 in full plus the canonical schema each depends on) surfaces four repository-wide questions common to nearly all 24 capability prompts, none yet answered by a ratified decision:

- **Part A — read access shape.** Every one of the 98 tenant-scoped tables a `customer_user`-layer principal might need now default-denies that layer (`CG-S10-ATW-032`, `supabase/migrations/20260730560000_harden_customer_user_layer_default_deny.sql`, closing `ISS-2026-010`'s default-deny half — `docs/runtime/KNOWN_ISSUES.md:34`). That migration's own header is explicit that it deliberately does not decide what the portal may read — "that is Phase 8 scope." Left unresolved, each of Prompts 300-323 would independently choose between two structurally different repair shapes: (a) reopen the narrowed RLS `select` policy for its own tables, or (b) leave RLS closed and add a new `SECURITY DEFINER` RPC layer with its own scope/eligibility gate. A precedent already exists and has already been adversarially reviewed once: `ATW-023`/`ATW-242` (`supabase/migrations/20260730310000_create_advanced_tms_customer_inventory_access.sql`) tried option (a) implicitly (left 4 tables' RLS untouched believing it was already safe), a live-reproduced review found that untrue, and the fix (`20260730311000_harden_customer_inventory_access_rls_isolation.sql`) explicitly rejected reopening RLS as "a second, independently-evolving enforcement point" and kept RLS closed with an RPC-only sanctioned path instead. Leaving this open across 24 independent capability prompts risks the identical defect recurring 24 times.
- **Part B — write access shape.** Prompts 302-304 (Request Quotation, Booking, Shipment Order), 310 (Warehouse Order/Fulfillment), and 314 (Customer Profile) each describe a customer-initiated action that must eventually touch a canonical, staff/RBAC-gated record (quotation, job order, shipment order, WMS outbound order, `app.accounts`). None of the underlying canonical mutation RPCs (`app.create_quotation_draft`, `app.prepare_job_order_handoff`, `app.create_shipment_order_from_job`, `app.confirm_shipment_order`, etc.) accept a `customer_user` caller today, and none should be widened to — but each of the five prompts' own text is consistent with a request/intent shape ("hand off... without creating duplicate quote truth"; "becomes operational truth only after canonical handoff acceptance"; "portal stores projection and requests only"). Left unresolved, a future capability prompt could plausibly read "self-service" as license to call a staff-gated mutation RPC directly from a customer-supplied `auth.uid()`, which would be a new, unreviewed customer-write path into a financially/operationally binding record.
- **Part C — REST/GraphQL transport scope.** All 24 capability prompts' own §14 text requires "identical REST/GraphQL field policy" or "REST and GraphQL parity." Direct inspection confirms no GraphQL server exists in this repository at all (`server/policies/graphql-complexity.ts:9-11`, its own header: "this repository has no `graphql` package dependency and no live GraphQL server"), and `ADR-CAND-ARCH-017` (`docs/adr/README.md` §5.2) already records the live-GraphQL-server question itself as open, "due at the future live GraphQL-server capability." Every Phase 7 capability build log discloses "no REST/GraphQL adapter" as an accepted, non-blocking residual gap (e.g. `docs/build-log/phase-07/HRT-279.md`/`HRT-280.md`'s own §10/§11), and the Phase 7 execution index's own file/collision matrix (`docs/build-log/phase-07/00_EXECUTION_INDEX.md:157`) states the target pattern as "shared Zod modules consumed by both REST... and GraphQL" without ever building the GraphQL half. Left unresolved, a Phase 8 capability prompt could read its own §14 text as a hard gate and either stall waiting for a GraphQL server that is out of scope for any single capability prompt, or silently invent a second, divergent transport convention.
- **Part D — loyalty ledger and Finance-liability shape.** Loyalty (Prompts 316-323) is confirmed genuinely greenfield (zero tables, zero contracts, zero routes for `loyalty`/`points_ledger`/`membership_tier`/`cashback`/`voucher`/`redemption` anywhere in `supabase/migrations/`, `server/contracts/`, or `app/` — verified by direct `grep`, not inferred). `docs/architecture/05_DATABASE_SCHEMA_WORKSTREAM.md:78,193` and `06_RLS_RBAC_WORKSTREAM.md:90` already name the target table set (`loyalty_programs`, `membership_tiers`, `point_ledger`, `cashback_ledger`, `rewards`, `redemptions`) and classify the two ledger tables into the repository's `append_only_ledger` RLS policy family, but no ADR fixes the concrete ledger/balance shape or the liability-to-Finance handoff shape, and `AGENTS.md:125-126` states the binding rule only at the principle level ("Normal inventory and loyalty changes use ledgers... critical transactions retain the applied version"). Left unresolved, Prompt 318 (Points Ledger) and Prompt 323 (Liability Reconciliation Analytics) would each have to independently rediscover the two already-proven, structurally analogous patterns already live in this repository (`app.inventory_movements`/`app.inventory_balances`, and the `prepare_finance_*_from_*` domain-owned-handoff shape HRT-282 already used for payroll).

## Options — Part A (customer read access shape)

1. **(SELECTED) Every Phase 8 customer-facing read is a new `SECURITY DEFINER` RPC composing (i) a scope resolver in the shape of `app.resolve_customer_owner_account_scope`/`app.actor_holds_customer_user_layer` and (ii) a domain-specific eligibility/visibility predicate, both required, deny-by-default, with anti-enumeration (`record_not_found` regardless of true cause) and keyset — never `OFFSET` — pagination. Raw-table RLS stays exactly as `CG-S10-ATW-032` left it (default-deny for `customer_user`); it is never reopened, narrowed further only if a genuinely new raw-table leak is found (mirroring `20260730311000`'s own narrowing precedent, never a widening).**
   - Trade-off: more RPCs to write (one deny-by-default surface per capability, not a blanket RLS reopen) — accepted, since it is the only shape this repository has already built and adversarially proven safe once (`ATW-023`/`ATW-032`), and matches `AGENTS.md`'s "RLS is mandatory... unless an approved tested compensating control exists" read literally: the RPC layer is that compensating control, already tested.
2. **Reopen the ATW-032-narrowed RLS `select` policy per table, scoped with an additional owner/customer predicate.**
   - Rejected: this is the exact shape `20260730310000_create_advanced_tms_customer_inventory_access.sql`'s own design note 6 rejected by name ("a second, independently-evolving enforcement point that could silently drift" from any RPC-level scope/masking logic), and the shape whose own violation (`20260730311000`) required a dedicated hardening migration to fix once already. Repeating it across 24 more tables invites the identical class of defect 24 times, each requiring its own independent adversarial re-discovery.
3. **A single generic "customer read gateway" RPC that all 24 capabilities route through, parameterized by table/entity type.**
   - Rejected: this is the "generic integration hub" pattern multiple prior capability prompts (e.g. `server/policies/graphql-complexity.ts`'s own header, citing Prompt 130 §12) have already disclaimed as deliberately not built in this repository — masking/eligibility rules differ enough per domain (warehouse eligibility vs. account-scope vs. finance-scope) that a single parameterized gateway would either lose per-domain precision or grow an unbounded branch table, neither of which the existing `ATW-023` precedent needs.

## Options — Part B (customer write access shape)

1. **(SELECTED) Every Phase 8 customer-initiated action that would otherwise touch a staff-RBAC-gated canonical mutation is written as a new portal-owned "request/intent" record (own table, own idempotency key, own status lifecycle) referencing the canonical entity by ID. Canonical mutation is always invoked by a staff or system actor through the existing, unmodified canonical RPC — never by a customer principal calling that RPC directly, and no canonical mutation RPC is widened to accept a `customer_user` caller.**
   - Trade-off: a customer's "booking" or "profile update" does not become canonical truth synchronously — accepted, because this is exactly what Prompts 302-304/310/314's own business-rule text already specifies ("becomes operational truth only after canonical handoff acceptance"; "portal stores projection and requests only"; "profile change requests, approval state... canonical customer/company/account/site records remain Commercial/Platform-owned"). This ADR makes explicit and repository-wide what each prompt already states locally, so no future capability drifts from it under implementation-time pressure.
2. **Add a `customer_user`-eligible branch directly to the existing staff-gated RBAC check on canonical mutation RPCs (e.g. widen `app.check_finance_invoice_authority`/`OPS:Create` gates to also accept a scoped `customer_user`).**
   - Rejected: directly contradicts `ISS-2026-040` (`docs/runtime/KNOWN_ISSUES.md:64`, `OPEN`, Medium — `app.evaluate_permission` is layer-blind and "not currently exploitable... under this repository's own current role-assignment discipline" only because no tenant assigns a staff role to a `customer_user` principal). Deliberately introducing the first such assignment as a Phase 8 side effect would convert a disclosed, inert structural risk into a live one, the opposite of what a kickoff-level ADR should authorize.
3. **A customer-portal-specific RBAC category (e.g. `CPT:Create`) layered onto the same `evaluate_permission` evaluator canonical staff RPCs already use.**
   - Rejected for this ADR's scope: would still route through the same layer-blind evaluator `ISS-2026-040` already flags, and does not remove the deeper problem (a customer principal directly authoring a financially/operationally binding record with no staff review point) that Option 1's request/intent shape avoids structurally rather than by a new permission check. Not precluded as a future Phase 9+ automation-boundary decision; out of scope here.

## Options — Part C (REST/GraphQL transport scope for Phase 8)

1. **(SELECTED) Each Phase 8 capability prompt builds a real REST surface (`app/api/...`) over shared `server/contracts/**` Zod schemas, exactly as Phase 1-7 already do. "GraphQL parity" in each prompt's own §14 text is satisfied by the schema being GraphQL-ready (already-typed, already-shaped for either transport) — no capability prompt is required to stand up a live GraphQL server, add the `graphql` package dependency, or write resolvers. This is a disclosed, accepted, non-blocking residual gap identical in kind to the one already disclosed at essentially every Phase 1-7 capability checkpoint, not a new Phase 8 exception.**
   - Trade-off: `RPD-033`'s literal text ("REST and GraphQL public APIs are built together") is not literally satisfied by any single capability prompt, Phase 8 included — accepted, because it was never literally satisfied by any of Phases 1-7 either (confirmed: no `graphql` dependency, no live server, anywhere in the repository today), and `ADR-CAND-ARCH-017` already carries the live-GraphQL-server question as its own open candidate, correctly scoped to "the future live GraphQL-server capability," not to any one domain capability prompt.
2. **Block every Phase 8 capability prompt until a dedicated GraphQL-server capability ships first.**
   - Rejected: no such capability exists anywhere in the 430-file prompt package's Phase 8 range (298-327) or earlier, `ADR-CAND-ARCH-017` names it as a future, not-yet-scheduled capability, and blocking 24 capability prompts on an unscheduled dependency would contradict this repository's own "fix only task-caused failures... log unrelated/pre-existing failures" discipline — the GraphQL absence predates and is unrelated to any Phase 8 capability's own task.
3. **Each Phase 8 capability prompt invents its own minimal GraphQL-shaped resolver ad hoc, without a shared server.**
   - Rejected: would produce 24 independent, non-interoperable partial GraphQL implementations — the "generic integration hub" antipattern this repository already disclaims (Part A, Option 3 above), at 24x the scale.

## Options — Part D (loyalty ledger and Finance-liability shape)

1. **(SELECTED) Points/cashback/benefit ledgers mirror `app.inventory_movements`/`app.inventory_balances` exactly: one append-only event table per ledger (earning/reversal/expiry/redemption/adjustment as typed event rows, `idempotency_key` unique per tenant, corrections via a new event referencing the original, never `UPDATE`/`DELETE` of a posted row), one derived-balance table per ledger with a real generated `available`-style column and `record_version` optimistic concurrency, and exactly one posting primitive per ledger every capability composes (mirroring `app.post_inventory_movement`). Loyalty liability handed to Finance mirrors HRT-282's `prepare_finance_*_from_*` shape exactly: a Loyalty-owned handoff-batch table (never `app.finance_*`), one idempotent generator function keyed on a natural liability-period key, an aggregate-only GL-postable side, and a Finance-side acknowledgement RPC as the one place Finance authority (not Loyalty authority) is required. Loyalty's own liability reconciliation mirrors FIN-209's execute/resolve-then-certify two-tier shape, including the "certification blocked while any exception remains open" gate.**
   - Trade-off: more schema/RPC surface than a single mutable-balance table would need — accepted, because it is the explicit, binding repository-wide rule (`AGENTS.md:125-126`, "Normal inventory and loyalty changes use ledgers"; Prompt 318's own business rule, "Normal roles cannot edit point_balance directly; balance is derived from ledger") and the identical shape already proven correct, tested, and adversarially reviewed twice in this repository (inventory ledger; payroll Finance handoff).
2. **A single mutable `loyalty_balances` table, updated in place per transaction, with a separate audit-log table for history.**
   - Rejected: directly contradicts Prompt 318's own explicit business rule and `AGENTS.md`'s binding ledger mandate; an audit log that is not itself the derivation source is exactly the anti-pattern the inventory-ledger migration's own header warns against ("no other function or direct table write ever changes app.inventory_balances").
3. **Loyalty posts directly into `app.finance_journals`/`app.finance_subledger_lines` as a shortcut, skipping a handoff-batch intermediary.**
   - Rejected: directly contradicts Prompt 323's own business rule ("Finance owns official GL/journal posting... unless Finance contract explicitly posts") and the repository's own established discipline (HRT-282's own header: "Zero GRANT/INSERT/UPDATE/DELETE anywhere in this file against any `app.finance_*` table") — Loyalty is a source domain to Finance, structurally identical to Payroll, Procurement, and every other domain that hands off to Finance rather than writing into it.

## Decision

**Part A — Option 1.** Every Phase 8 customer-facing read is a new `SECURITY DEFINER` RPC pair (scope resolver + eligibility predicate, composed by one thin gate function per capability, mirroring `app.evaluate_customer_inventory_access`), anti-enumerating, keyset-paginated. No Phase 8 capability prompt reopens or widens a `CG-S10-ATW-032`-narrowed RLS `select` policy. `scripts/db-tests/rbac-enforcement.sql`'s existing standing gate (fails if any SELECT policy admits a `customer_user`-layer principal on tenant membership alone) remains the automated backstop; each capability prompt additionally adds its own live db-test proving its new RPC's deny-by-default behavior.

**Part B — Option 1.** Every Phase 8 customer-initiated action that would otherwise touch a staff-RBAC-gated canonical mutation is a new portal-owned request/intent record; canonical mutation stays invoked only by staff/system actors through existing, unmodified canonical RPCs. No canonical mutation RPC anywhere in the repository is widened to accept a `customer_user` caller by any Phase 8 capability prompt.

**Part C — Option 1.** Phase 8 capability prompts build REST over shared `server/contracts/**` Zod schemas. "GraphQL parity" is satisfied by contract shape reuse, not a live GraphQL server; "no REST/GraphQL adapter beyond REST" (where a capability's own §14 GraphQL ask cannot be literally met) is recorded per-capability as a disclosed, non-blocking residual gap, identical in kind and precedent to every Phase 1-7 capability's own disclosure, never as a `VERIFIED`-blocking defect.

**Part D — Option 1.** Loyalty ledgers (points, cashback/benefit) are append-only event tables plus derived-balance tables with a generated available-balance column and `record_version`, one posting primitive per ledger. Loyalty's liability handoff to Finance is a Loyalty-owned handoff-batch table plus one idempotent generator function, an aggregate-only GL-postable side, and a Finance-side acknowledgement RPC as the sole point requiring Finance authority. Loyalty's own liability reconciliation is a two-tier execute/resolve-then-certify function pair mirroring FIN-209, blocking certification while any exception remains open.

## Consequences

- **DB/API:** No schema is touched by this kickoff (Prompt 299 is planning-only, per its own "Required kickoff work" §8: "without implementing capability code inside this kickoff prompt"). Every Phase 8 capability prompt's own migration(s) must follow Parts A/B/D's shapes from their first migration, not retrofit later. Prompts 300-315 (Commercial/Operations/WMS/Finance/Ticketing-facing) follow Parts A and B; Prompts 316-323 (Loyalty) additionally follow Part D; all 24 follow Part C.
- **Security:** Part A keeps the `CG-S10-ATW-032` default-deny floor intact for the life of Phase 8 — no capability prompt may lower it. Part B keeps `ISS-2026-040`'s layer-blind `evaluate_permission` risk inert (no new customer-to-staff-RBAC path is opened), consistent with that issue's own "not currently exploitable... under current role-assignment discipline" status remaining true throughout Phase 8.
- **Performance:** No new index is mandated by this ADR itself; each capability prompt's own RPCs follow the existing keyset-pagination/covering-index discipline `ATW-023`'s own companion migration (`20260730312000_add_customer_inventory_access_pagination_indexes.sql`) already established as the pattern.
- **Migration/rollback:** All four parts describe additive-only patterns (new RPCs, new request/intent tables, new ledger/handoff tables) — no existing migration is edited, no existing RLS policy is widened, consistent with `AGENTS.md`'s "never edit an applied migration" and "never use broad service-role bypass to avoid correct RLS" rules.
- **Downstream impact:** Every Phase 8 prompt from 300 onward that needs customer read access builds a `SECURITY DEFINER` RPC pair, never a raw-RLS reopen (Part A); every prompt from 302 onward that needs a customer-initiated action that would touch canonical truth builds a request/intent record, never a direct canonical-RPC call from a customer principal (Part B); every prompt's own GraphQL §14 text is satisfied by contract-shape reuse and disclosed as a residual gap where a live server would otherwise be required (Part C); Prompts 316-323 build the ledger/handoff/reconciliation shapes named in Part D, never a mutable-balance table or a direct Finance-table write (Part D). `CPL-324` (Integrated Verification) should re-check all four parts held across every capability prompt actually shipped, the same way `HRT-294` re-checked cross-cutting Phase 7 disclosures.
