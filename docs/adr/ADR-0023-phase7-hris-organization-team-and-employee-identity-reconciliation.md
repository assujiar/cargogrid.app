## Question

Prompt 273's own "Required ownership reconciliation" item 1 requires proving, before any Phase 7 task may be created, "Platform identity versus HR employee profile ownership; tenant/company/branch/department/team/position/reporting-line scope" and item 2 requires proving "effective-dated employment, organization, position, and manager links without duplicating Platform organization truth." Direct repository inspection this checkpoint surfaces two related but distinct questions:

- **Part A.** `app.org_units.unit_type` (`supabase/migrations/20260716101726_create_org_units.sql:33-34`) is a closed CHECK constraint allowing exactly `('company', 'branch', 'department', 'business_unit')`. Prompt 275 (Organization and Position Linkage) names `company/branch/department/team` as the four canonical org node types position/grade must reference — at binding-rule level, twice (`275_ORGANIZATION_POSITION_LINKAGE_PROMPT.md` §13, §24) — and the Phase 7 package README repeats it (`272_HRIS_TICKETING_README.md` §5, binding rule 1: "Reuse Platform user, company, branch, department, team, position and role foundations"). There is no `team` value in the live schema. Left unresolved, Prompt 275 would face exactly the choice this repository's own precedent (`ADR-0015`, `ADR-0020`) reserves for a ratified ADR, not ad hoc capability-prompt judgment: widen the canonical tree, misuse an existing type, or fork a duplicate one.
- **Part B.** Prompt 274 (Employee Master) §20 self-instructs: "Prove employee-versus-user-versus-driver ownership and publish an ADR if ambiguous." Direct inspection finds this is **not actually ambiguous** — it was already qualitatively resolved at Step 3 architecture (`docs/architecture/06_RLS_RBAC_WORKSTREAM.md`, candidate `ADR-CAND-ARCH-002`, cited again at `docs/architecture/05_DATABASE_SCHEMA_WORKSTREAM.md:191` and `docs/architecture/14_REQUIREMENT_PHASE_TRACEABILITY.md:196`) — but that resolution was never promoted to a binding `docs/adr/ADR-NNNN` record, exactly the gap `ADR-0015` closed for the vendor/rate lookup question at Phase 2 kickoff. Ratifying it now, at Phase 7 kickoff, prevents Prompt 274 from re-litigating an already-settled question or, worse, drifting from it under its own implementation-time pressure.

## Evidence gathered this checkpoint

- `app.org_units` unit-shape trigger `app.enforce_org_unit_parent_shape()` (`20260716101726_create_org_units.sql:87-133`) permits exactly: `branch` parent = `company`; `department` parent in (`company`, `branch`, `department` — i.e. departments may self-nest); `business_unit` parent = `company` only. No rule mentions `team` because the type does not exist.
- `app.org_units.path` is a materialized ancestor-id list (root first, self excluded), consumed directly by every ancestor/descendant query and by RLS org-scope predicates repository-wide — confirmed by the file's own header comment ("`path` is the materialized ancestor-id list... queries use it directly, never a recursive CTE"). Any new node type that participates in this tree gets ancestor/descendant traversal for free, with zero new closure-path logic, as long as it is added as a value in the same table rather than a parallel structure.
- `app.master_types`/`app.master_records` (`20260717120000_create_master_data.sql`, `PLT-120`) is this repository's established, code-registrable, non-duplication pattern for a new operational-actor identity that must extend — never fork — Platform identity: `master_type_code='vendor'` (`ADR-0020`) and `master_type_code='driver'` (`app.driver_operational_profiles`, a 1:1 extension table) both follow it. Direct evidence found this session that the same shape is anticipated, though not yet built, for Employee: the `driver` master-type row was seeded at Phase 3 (`20260727130000_create_operations_resource_assignment.sql:60-64`) already carrying `owner_module_code='HRS'` — Operations itself anticipated eventual HR ownership of the driver-identity concept before Phase 7 existed.
- `docs/architecture/06_RLS_RBAC_WORKSTREAM.md` (Step 3, `ADR-CAND-ARCH-002`) states the concrete rule: `employees.user_id` is a required FK to `users`, not an independent identity; there is exactly one authentication/session identity per person, and `employees` is a domain-specific extension of it. `docs/architecture/05_DATABASE_SCHEMA_WORKSTREAM.md:191` corroborates independently ("`employees` (FK to `users` per `ADR-CAND-ARCH-002`)"), and `docs/architecture/14_REQUIREMENT_PHASE_TRACEABILITY.md:196` cites the same section as the closure evidence for the `HRS-EMP` requirement family. `grep -rln ADR-CAND-ARCH-002 docs/adr/*.md` finds only `docs/adr/README.md`'s own candidate register (§5.1) — no dedicated ratified file exists yet.
- No live Supabase project or production data exists anywhere in this repository (standing, repeated disclosure across every phase closure to date, re-confirmed this session at Phase 6 closure) — both parts of this decision are pure schema/authority questions, not data-migration questions with real-row risk.
- `docs/build-log/phase-06/STEPS_12_14_HANDOFF_CONTRACT.md` §2 (Phase 6's own disclosed non-relationship with Phase 7) confirms every Phase 1–6 actor reference is a bare `auth_user_id` FK into Platform Core's identity system, never a domain-owned worker record — consistent with, and no obstacle to, Part B's decision.
- Ticketing's own later "queue/team" routing concept (`290_TICKET_ASSIGNMENT_PROMPT.md`, `291_TICKET_ESCALATION_PROMPT.md`) is a distinct, Ticketing-owned construct for assignment eligibility, not a synonym for the organization-tree `team` node this ADR resolves — noted here so Prompt 290 does not conflate the two.

## Options — Part A (org_units `team` node type)

1. **(SELECTED) Add `team` as a fifth, additive `unit_type` value on the existing `app.org_units` table.** Prompt 275's own migration performs the widening (not this kickoff's — Prompt 273 is planning-only and touches no schema). `team`'s parent must be `department` or `business_unit` (never `company` or `branch` directly); `team` is a leaf type (no `unit_type='team'` row may itself be a parent), mirroring `business_unit`'s own non-recursive shape. `app.create_org_unit`/`app.move_org_unit`/`app.org_unit_ancestor_ids`/`app.org_unit_descendant_ids` (all pre-existing, generic over `unit_type`) need no signature change — only the `CHECK` constraint and the parent-shape trigger widen.
   - Trade-off: a fifth type deepens the tree's branching factor slightly — accepted, since the alternative (a parallel table) is the exact "duplicate root" Prompt 273 §"Required ownership reconciliation" forbids.
2. **Model `team` as a nested `department`** (departments already permit self-nesting).
   - Rejected: Prompt 275's own text treats `team` as a distinct fourth node type, not a same-typed sub-department. Collapsing the two makes "is this row a department or a team" unrecoverable from `unit_type` alone, breaking any future capability (reporting, position eligibility, manager-scope queries) that needs to filter or report on `team` specifically.
3. **Map `team` onto the existing `business_unit` type.**
   - Rejected: `business_unit`'s parent is fixed to `company` only (`20260716101726_create_org_units.sql:116`), structurally wrong for a `team` (which the spec places under a department or business unit, never directly under a company). Reusing the label would either force a semantically wrong parent constraint or require diverging `business_unit`'s own already-`VERIFIED` behavior — both disallowed by the same non-duplication principle that selected Option 1.
4. **A wholly new, HR-owned `team` table outside `app.org_units`.**
   - Rejected: the literal "duplicate root" this ADR exists to prevent. Position/grade (Prompt 275's own DB-impact section) must reference organization nodes uniformly; a `team` living outside `org_units` would need its own parallel FK/hierarchy/RLS surface instead of reusing the canonical tree's existing `path`-based traversal, RLS org-scope predicates, and `app.org_unit_ancestor_ids`/`descendant_ids` helpers.

## Options — Part B (employee identity)

1. **(SELECTED, ratifying the existing Step 3 resolution, with one correction reconciled against Prompt 274's own later, more specific text — see note below) Employee is a 1:1 extension of `app.users`, never an independent authentication or session identity.** This is the substantive principle `ADR-CAND-ARCH-002` already resolved; this ADR promotes it from an architecture-workstream determination to a ratified `docs/adr/ADR-NNNN` record, exactly as `ADR-0015` did for the vendor/rate-lookup question. The narrower question of whether Employee *additionally* registers a `master_type_code='employee'` row in `app.master_records` (mirroring `vendor`/`driver`, and directly evidenced by the `driver` master-type's own pre-existing `owner_module_code='HRS'`) is **deliberately left open** for Prompt 274's own checkpoint, where full employee-lifecycle field design will be in hand — this ADR ratifies the identity-ownership *principle* (extends `users`, never forks it), not every downstream schema detail.
   - **Correction, caught during this same checkpoint's own drafting, before any code was written against it:** `ADR-CAND-ARCH-002`'s own Step 3 text ("a required FK to `users`") predates Prompt 274's own later, more specific business rule (§24: "One employee workforce profile may link to zero or one active Platform user identity per effective context") and alternative flow (§22: "Create a profile before a user account, link an existing user later"). A literal `NOT NULL` column would make that alternative flow structurally impossible. Per this repository's own evidence-precedence discipline (a later, more specific capability requirement governs over an earlier, general architectural principle when the two conflict, absent a reason to reopen the earlier one), `app.employees.user_id` is **nullable**, unique when populated (`unique (user_id) where user_id is not null`, mirroring `app.vendor_profiles.master_record_id`'s own not-null-unique shape applied to a nullable column instead), and once set may only ever point to exactly one `app.users` row. The substantive principle `ADR-CAND-ARCH-002` protects — employee is never a second authentication/session mechanism, and a linked employee's authentication always lives on `app.users`, never duplicated onto `app.employees` — is fully preserved by this shape; only the incidental `NOT NULL` detail is corrected.
2. **Employee as an independent identity, later linked to a Platform user.**
   - Rejected: directly contradicts the already-ratified Step 3 architecture record and would reopen a settled question with no new evidence to justify it — the exact "resolve ambiguity ad hoc inside a capability prompt" pattern Prompt 273's own text forbids.
3. **Employee identity folded entirely into `app.master_records` (mirroring `vendor`/`driver`) with no direct `users` FK at all.**
   - Rejected: every employee, unlike a vendor or a driver, is expected to eventually need Platform authentication/session identity — collapsing employee into a pure `master_records` actor-reference with no `users` link would force every future ESS/MSS, approval-routing, and audit-actor consumer to join through an extra, optional hop for the common case. `ADR-CAND-ARCH-002`'s own "extends `users`, never forks it" shape (as corrected above — a nullable, unique-when-present FK, not a `NOT NULL` one) is the more load-bearing choice and is already the ratified Step 3 position on the identity-ownership question; not revisited without new evidence.

## Decision

**Part A — Option 1.** `app.org_units.unit_type` gains an additive fifth value, `team`, added by Prompt 275's own migration (`DROP CONSTRAINT org_units_unit_type_check` / `ADD CONSTRAINT ... CHECK (unit_type in ('company','branch','department','business_unit','team'))`) plus one new branch in `app.enforce_org_unit_parent_shape()` (`team` parent in (`department`, `business_unit`); `team` may not itself be a parent). No schema file is touched by this kickoff (Prompt 273 is planning-only) — this ADR fixes the *design*, Prompt 275 performs the migration.

**Part B — Option 1, corrected.** `app.employees.user_id` (Prompt 274's own future table) is a **nullable** FK to `app.users`, unique when populated, never a second authentication/session mechanism. Employee is a domain-specific workforce/HR extension of at most one existing Platform authentication identity, never a second identity root — the extension is optional at any given effective moment (an employee may exist before a user account, per Prompt 274 §22), never duplicated (at most one `app.users` row per employee, enforced by the unique constraint, and — symmetrically — a future capability must not let one `app.users` row link to more than one active employee either). Whether Employee additionally registers its own `master_type_code='employee'` row in `app.master_records` (recommended by this checkpoint's own investigation, mirroring `vendor`/`driver`, but not forced) remains Prompt 274's own decision to make with full schema context.

## Consequences

- **DB/API:** Prompt 275's migration is scoped to widen `app.org_units`'s `CHECK` constraint and parent-shape trigger (Part A) — additive, reversible, zero live data at risk (no live Supabase project anywhere). Prompt 274's migration must give `app.employees` a nullable `user_id uuid references app.users(id)` column with a partial unique index (`unique (user_id) where user_id is not null`) (Part B) from its very first migration, not retrofitted later, and must gate any operation that depends on a live user account (login-dependent ESS/MSS access, user-scoped notifications) on `user_id is not null`, never assume it.
- **Security:** No RLS change is required by this ADR itself — `app.org_units`'s existing RLS/scope predicates already operate uniformly over `unit_type` values; a `team`-typed row inherits the identical tenant-scoping every other `org_units` row already has. A linked employee inherits exactly one Layer-3 (`org_user`) principal's own authentication/session security posture, never a parallel one; an unlinked employee (no `user_id` yet) has no authentication surface at all, correctly, since no Platform identity exists for it yet.
- **Performance:** No new index is mandated by this ADR; `app.org_units`'s existing `unit_type`/`path` indexes already cover the widened value set without new query shapes.
- **Migration/rollback:** Both parts are additive only. Part A is reversible by narrowing the `CHECK` constraint back (rejecting any `team` rows first). Part B is a nullable FK plus a partial unique index Prompt 274 introduces at table-creation time — trivially reversible by dropping the not-yet-`VERIFIED` table itself, since this ADR authorizes no change to any already-applied migration.
- **Downstream impact:** Every Phase 7 prompt from 275 onward that reasons about organization scope must treat `team` as a first-class `app.org_units.unit_type` value, never a second hierarchy; every prompt from 274 onward that reasons about employee identity must treat `app.employees.user_id` as the sole authentication linkage, never introduce a parallel employee-login mechanism. Ticketing's own "queue/team" routing concept (Prompts 290/291) is explicitly NOT required to collapse into `app.org_units`'s `team` node type — a separate, non-conflicting design space.
