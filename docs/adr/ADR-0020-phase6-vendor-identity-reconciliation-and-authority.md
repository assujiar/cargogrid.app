# ADR-0020 — Phase 6 canonical vendor identity reconciliation and PRC write authority

Status: ACCEPTED
Date: 2026-08-05   Approver: Runtime build agent (Phase 6 kickoff authority, per `docs/adr/README.md` §3, exercised at `250_PROCUREMENT_VENDOR_WBS_RUNTIME_KICKOFF_PROMPT.md` §"Required work" item 4/7, the same kickoff-level-resolution precedent `ADR-0015` used at Phase 2 kickoff)
Source candidate: `ADR-CAND-ARCH-032` (next master-register number after `030`/`ADR-0015`)   Owning phase/task: Phase 6 (`CG-S11-PRC-001`, Prompt 250, Procurement/Vendor WBS and Runtime Kickoff)
Supersedes/Superseded-by: — (extends `ADR-0015`, does not reopen it)

## Question

`ADR-0015` (Phase 2 kickoff) resolved that `app.master_records` under `master_type_code='vendor_rate'` is the canonical rate-lookup identity, and explicitly left open two questions for Phase 6's own kickoff: (a) whether to introduce a narrower `PRC`-specific write authority, and (b) how the full vendor lifecycle (`vendors`, contacts, assessments, POs, performance scores) relates to that registration. Direct repository inspection this checkpoint finds the second question is sharper than `ADR-0015` anticipated: **a second, independent master type, `master_type_code='vendor'`, already exists** (`supabase/migrations/20260727130000_create_operations_resource_assignment.sql`, `OPS-172`, Phase 3) and is already the live FK target for `app.resource_assignments.resource_id` (role `'vendor'`), `app.shipment_actual_cost_components.vendor_id`, `app.finance_ap_open_items.vendor_master_id`, `app.finance_vendor_bills.vendor_master_id`, and `app.finance_settlements.vendor_master_id`. Today, a `vendor_rate`-typed master record (Phase 2 rate lookup) and a `vendor`-typed master record (Phase 3/4 identity/AP) for the *same real-world vendor* are two independent, unlinked rows — exactly the "second vendor master" shape `249_PROCUREMENT_VENDOR_README.md` §5 forbids ("Do not create a second vendor master, rate store, service/coverage truth"). This must be reconciled before `251_VENDOR_REGISTRATION_ONBOARDING_PROMPT.md` may execute.

## Evidence gathered this checkpoint

- `app.master_types` seed rows (confirmed live): `('vendor_rate', 'Vendor Rate', 'tenant', 'PRC', 'platform-core-foundation')` (`20260717120000_create_master_data.sql`) and `('vendor', 'Vendor', 'tenant', 'PRC', 'operations-resource-assignment-foundation')` (`20260727130000_create_operations_resource_assignment.sql`). Both already carry `owner_module_code='PRC'` — Platform Core and Operations both correctly anticipated Procurement as the eventual owner of each, but neither checkpoint that created them cross-referenced the other.
- `app.vendor_rate_versions.master_record_id` (`20260724150000_create_commercial_rate_cost_lookup.sql`, `COM-149`) references `master_records` constrained to `master_type_code='vendor_rate'` only — no path from a rate version to a `vendor`-typed identity row exists today.
- Finance's entire AP/vendor-bill/settlement chain (`FIN-199`/`200`/`201`, all `VERIFIED`, real committed financial evidence) already depends on `master_type_code='vendor'` exclusively. This is the higher-stakes, already-load-bearing identity — Phase 6 must anchor on it, not on `vendor_rate`, which today is reachable only from Commercial's own rate-lookup path and carries no legal/contact/compliance shape at all (`app.master_records.attributes jsonb` only).
- No live Supabase project or production data exists anywhere in this repository (repeated, standing disclosure across every phase closure to date) — this reconciliation is a pure schema/authority decision, not a data migration with real-row risk. Every existing `vendor_rate`/`vendor` master record in the repository is db-test fixture data.
- `app.is_support_grant_authority(actor, tenant_id)` remains the write gate on `app.master_records`/`app.create_master_record`/`app.update_master_record` themselves (tenant_admin/support-grant chain) — `ADR-0015` already disclosed this stays unchanged until Phase 6 introduces something narrower, and confirmed a narrower `PRC` authority would be additive to the authority layer only.
- `app.permissions` already seeds seven `PRC` actions (`View`, `Create`, `Edit`, `Delete`, `Approve`, `Export`, `View cost`) but is missing four actions every one of Prompts 251–255 needs at least once: `Reject` (assessment/compliance/rate decisions, mirroring `FIN`'s own dedicated `Reject` distinct from `Approve`), `Override` (compliance/eligibility override, mirroring `OPS`/`FIN`'s existing `Override`), `Download` (compliance document access audit, mirroring `OPS`'s `Download`), `Import` (bulk vendor/rate import). All four values already exist in the fixed 19-action `permissions_action_check` enum (`Reject`, `Override`, `Download`, `Import` are already legal values for other modules) — no CHECK-constraint widening is needed, only new `app.permissions` seed rows for `resource_module_code='PRC'`.
- Masking gate for Phase 6's own new sensitive-field classes: Prompt 255 (rate/pricelist) reuses the already-seeded, already-protected `PRC:View cost` (identical semantic — vendor cost figures — to its existing Commercial-side use). Prompt 254 (bank/tax/payment-term) has no existing PRC-scoped protected action to reuse; the fixed enum's `View personal data` (protected=true) is the closest existing semantic (sensitive party-identifying financial/legal data) and is cross-module-safe (`PRC:View personal data` is a distinct permission code from any future `HRS:View personal data`, via the generated `resource_module_code || ':' || action` column) — selected over minting a new enum value, which would require widening `permissions_action_check` for a single capability's narrow need.

## Options

1. **(SELECTED) `master_type_code='vendor'` is the single canonical vendor identity going forward. Prompt 251 builds `app.vendor_profiles` as a governed 1:1 extension of `vendor`-typed master records. `app.vendor_rate_versions` gains one new nullable, additive column, `vendor_master_id uuid references app.master_records(id)`, linking a rate version to the real vendor identity; `master_record_id`/`vendor_rate` stays as-is for the lane/service-indexed rate-version row itself (no rename, no data migration, no already-applied migration edited).** `app.create_rate_version` (Prompt 255) is widened, same signature plus one new optional `p_vendor_master_id` parameter, validated `master_type_code='vendor'` and same tenant when supplied; existing test fixtures that omit it are unaffected (nullable, backward-compatible). New `PRC` permission action rows (`Reject`, `Override`, `Download`, `Import`, `View personal data`) are seeded once, in Prompt 251's own migration (the first Phase 6 migration), since every later capability in this range needs at least one of them and re-seeding piecemeal per capability would fragment one governance table's history across five migrations for no benefit.
   - Trade-off: `vendor_rate` as a master type becomes semantically narrower than its name ("Vendor Rate" now means "a rate-lookup registration, optionally linked to a real vendor identity") — disclosed here rather than silently reinterpreted, and the column is genuinely optional (existing/ad-hoc/legacy rate lookups with no linked Procurement-registered vendor remain valid, matching `255_VENDOR_RATE_PRICELIST_PROMPT.md` §22's own "ad-hoc quotation" alternative flow).
   - Trade-off against: two master types nominally about "vendor" persist in the schema rather than being collapsed into one — accepted because collapsing them would mean either (a) migrating every existing `vendor_rate` row's identity onto `vendor` (a real, if currently zero-stakes, data rewrite Prompt 251 has no mandate to perform on Commercial's own already-`VERIFIED` capability) or (b) renaming/aliasing a `VERIFIED` Phase 2 master type, both disallowed by "never edit applied migrations" and by Phase 6's own forbidden-files rule against touching Commercial/Finance roots.
2. **Make `vendor_rate` the canonical identity; `vendor` (Finance/Operations) becomes the one that gains a linking column instead.**
   - Rejected: Finance's AP/vendor-bill/settlement chain is real, `VERIFIED`, evidenced financial capability already built against `vendor`; retrofitting a link column onto three already-`VERIFIED` Finance tables is far more invasive than adding one nullable column to Commercial's single rate-version table, and directly risks the Phase 6 package's own explicit "Finance remains owner of vendor bill, AP, posting" boundary (§7) by implying Procurement may reshape Finance's schema.
3. **Merge the two master types into one by renaming `vendor_rate` rows to `vendor_type_code='vendor'` in place.**
   - Rejected: a same-table type-code rewrite of Commercial's already-`VERIFIED` capability is an edit to already-applied migration *behavior* (every existing `app.v_active_vendor_rates`/`app.search_vendor_rates` query implicitly filtered on `master_type_code='vendor_rate'`); it also collapses two independently-keyed natural-key spaces (`(master_type_code, tenant_id, code)` uniqueness) that were never guaranteed disjoint, risking a silent code collision. A linking column carries the same practical benefit (one real vendor, one rate, joined) with none of this risk.
4. **Leave both master types fully independent; Phase 6 vendor profiles never reference `vendor_rate` at all.**
   - Rejected: this is the status quo the Phase 6 package's own binding rule (§5, "Do not create a second vendor master... or rate store") already forbids continuing — Prompt 255 (Vendor Rate and Pricelist) explicitly requires extending "the canonical Phase 2 vendor-rate foundation," and doing so without ever resolving which real vendor a rate belongs to would leave rate/vendor lineage permanently unprovable.

## Decision

**Option 1.** `master_type_code='vendor'` is Phase 6's single canonical vendor identity anchor. `app.vendor_profiles` (Prompt 251) extends it 1:1 (`master_record_id primary key references app.master_records(id)`, `master_type_code` enforced `'vendor'` via trigger/check, mirroring the FK-and-constrain shape `COM-149` already established for `vendor_rate`). `app.vendor_rate_versions` gains one nullable additive column, `vendor_master_id`, linking to it. `app.is_support_grant_authority` remains the interim tenant-scoped write gate on the underlying `master_records`/`master_types` primitives (unchanged, per `ADR-0015`); Phase 6's own new tables (`vendor_profiles` and everything Prompts 252–271 add) instead gate through `app.evaluate_permission(actor, tenant_id, 'PRC', action)` from the start — the "narrower `PRC`-specific write authority" `ADR-0015` deferred, now real. Five new `app.permissions` rows are seeded once, in Prompt 251's migration: `('Reject','PRC','workflow',false)`, `('Override','PRC','workflow',false)`, `('Download','PRC','standard',false)`, `('Import','PRC','standard',false)`, `('View personal data','PRC','sensitive',true)`.

## Consequences

- **DB/API:** Prompt 251's migration is scoped to: `app.vendor_profiles` and its child tables (contacts/addresses/services/coverage/duplicate-review/intake), one additive `ALTER TABLE app.vendor_rate_versions ADD COLUMN vendor_master_id uuid REFERENCES app.master_records(id)` (nullable, no backfill required — zero live rows), and the five new `app.permissions` seed rows. No change to any Commercial/Finance/Operations function signature except `app.create_rate_version` (Prompt 255, additive optional parameter, `CREATE OR REPLACE` on a compatible signature).
- **Security:** New `app.vendor_profiles`/child tables get their own tenant-scoped RLS from creation, following the hardened default-deny form (`not app.actor_holds_customer_user_layer(tenant_id)` beside every membership check) rather than being retrofitted later. `app.evaluate_permission` (with its already-wired `app.assert_actor_is_session_identity` actor cross-check) is the authority gate for every new Phase 6 RPC from Prompt 251 onward — no Phase 6 RPC may rely on `is_support_grant_authority` alone.
- **Performance:** `vendor_master_id` gets its own btree index (`app.vendor_rate_versions(vendor_master_id)`) so Prompt 255's cost-lookup/comparison queries can join to real vendor identity without a sequential scan; existing `vendor_rate`-only queries are unaffected (column nullable, no existing index dropped).
- **Migration/rollback:** additive only — one new nullable column, new tables, new permission rows. Reversible by dropping the new column/tables/rows; zero already-applied migration touched.
- **Downstream impact:** Prompts 252–271 must reference `app.vendor_profiles.master_record_id` (i.e. the `vendor`-typed `master_records.id`) as the one vendor identity FK everywhere — assessments, compliance documents, banking/tax, RFQ/PO/contract, assignment, performance, invoice matching. None may introduce a third vendor-shaped table.
