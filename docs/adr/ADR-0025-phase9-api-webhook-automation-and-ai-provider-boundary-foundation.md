## Question

Prompt 329's own "Required kickoff work" requires mapping all 34 Phase 9 capabilities against already-existing repository contracts before any capability prompt re-derives foundational infrastructure ad hoc. Direct repository inspection this checkpoint surfaces four repository-wide questions common to the first 19 capability prompts this authorization covers (330-348), none previously answered by a ratified Phase 9-scoped decision:

- **Part A — Public/Customer/Vendor API foundation (337-339).** `supabase/migrations/20260719150000_create_api_key_webhook_primitives.sql` (Platform Core, `PLT-129`, `CG-S6-PLT-026`, Prompt 129) already built a real, adversarially-reviewed, tenant-scoped `app.api_keys` lifecycle (hash-only storage, create-once-display, scope strings reusing `app.permissions`'s own `<module_code>:<action>` taxonomy verified through `app.evaluate_permission()`, overlap-window rotation, revoke). That migration's own header explicitly discloses two things as `NOT_RUN`: the actual live rate-limit enforcement gateway (naming Prompt 130 as `BLOCKED`) and any real REST surface consuming the keys. Left unresolved, Prompt 337 could plausibly mint a second, parallel API-key table instead of completing the one PLT-129 already shipped.
- **Part B — Webhook Management foundation (340) vs. the existing inbound GPS webhook (343).** The same `PLT-129` migration also built `app.webhook_endpoints`, a Supreme-registered `app.webhook_event_types` registry (zero real domain event type seeded), HMAC-SHA256 signing/verification, a structural SSRF check at registration time, and `app.record_webhook_delivery_attempt()` as the bounded adapter interface a delivery worker calls — but discloses no live delivery worker exists. Separately, `app/api/webhooks/third-party-gps/[connectionId]/route.ts` already implements one concrete *inbound* webhook receiver (third-party GPS telematics, Advanced TMS/WMS phase). Left unresolved, Prompt 340 (outbound webhook management) and Prompt 343 (Maps/GPS/Telematics, which owns the one existing inbound receiver) could each independently invent incompatible delivery/retry/signing conventions.
- **Part C — Integration Hub (336) vs. `RPD-038`'s no-generic-provider-abstraction rule.** Prompt 336's own title ("Integration Hub") could be read as licensing a generic protocol-abstraction layer that every provider adapter (337-346) plugs into — directly contradicting `RPD-038` ("Non-AI third-party integrations are custom and have no generic provider abstraction... implemented case by case in the shared product codebase"). Prompt 336's own §3/§6 text ("integration catalog, credentials, adapter registry, health and ownership"; cites `RPD-038` by name) is consistent with a narrower governance-layer reading, but this has not been ratified against the 5 concrete provider-integration prompts (342-346) it will sit above.
- **Part D — Automation Rule Engine (335) execution mechanism.** `RPD-012` already fixes PostgreSQL durable queue as the job mechanism and explicitly excludes n8n as the primary engine. `supabase/migrations/20260719170000_create_import_export_job_framework.sql` already ships `app.jobs` (Platform Core durable queue) and `supabase/migrations/20260730410000_harden_job_type_single_source_of_truth.sql` already established a single canonical job-type registry. Left unresolved, Prompt 335 could invent a second, parallel scheduling/queue mechanism instead of registering new job types against the existing one.

## Decision

- **Part A.** Prompts 337-339 (Public/Customer/Vendor API) extend `app.api_keys` (`PLT-129`) — new scope strings for Phase 9 domains, a real REST `/v1` surface, and the real rate-limit enforcement Prompt 130 left `BLOCKED` — rather than minting a parallel key table. Customer-scoped and vendor-scoped keys are the same `app.api_keys` row shape with the caller's own actor-layer scope narrowing applied through the existing `app.evaluate_permission()` composition (`PLT-129`'s own "can only narrow, never widen" rule extends unchanged to a `customer_user`/vendor-portal-layer issuer).
- **Part B.** Prompt 340 (Webhook Management) builds the real delivery worker on `app.jobs` (`RPD-012`/Part D below), calling `app.record_webhook_delivery_attempt()` as its own adapter boundary exactly as `PLT-129` specified, and seeds the first real `app.webhook_event_types` rows against genuine domain events. Prompt 343 (Maps/GPS/Telematics) keeps its own existing inbound GPS receiver (`app/api/webhooks/third-party-gps/**`) as-is — inbound-receiver and outbound-delivery are structurally different directions and are not merged into one table/route family. Both consume the same `PLT-129` signing/SSRF primitives; neither forks them.
- **Part C.** Prompt 336 (Integration Hub) is a catalog/credential/health/ownership governance layer only — it registers and monitors adapters, never abstracts their protocol. Prompts 342-346 remain case-by-case, shared-product-code (never tenant-forked) adapters per `RPD-038`, each registering itself into Prompt 336's catalog rather than implementing a shared "provider interface." This ratifies the prompt's own already-stated framing; no code today is asked to change shape.
- **Part D.** Prompt 335 (Automation Rule Engine) registers its own action types into the existing single canonical job-type registry (`supabase/migrations/20260730410000_harden_job_type_single_source_of_truth.sql`) and enqueues onto `app.jobs` (`PLT-129`'s sibling durable-queue primitive) for every asynchronous action. No second queue/scheduler table is created. n8n (Prompt 341) remains an optional external trigger/consumer of this same automation surface, never a replacement execution engine, per `RPD-012`.
- **AI provider boundary (347), disclosed rather than newly decided:** `RPD-021` already fixes OpenAI multimodal as the default AI/OCR provider with a mandatory provider boundary and human approval before any financial/legal posting. Prompt 347 is the first checkpoint that actually builds code against this already-ratified decision — greenfield, no prior AI table/contract/route exists to reconcile against.

## Consequences

- Prompts 337-346 have one, and only one, authoritative API-key/webhook/queue/job-type foundation to extend; a future capability prompt that instead created a parallel table would be a reviewable Tier B defect against this ADR, not an ambiguous judgment call.
- `docs/architecture/13_FULL_WORK_BREAKDOWN_STRUCTURE.md:75`'s stale `IEP` short-code label is disclosed (`ISS-2026-143`, Low, non-blocking) and left uncorrected at this checkpoint — correcting a Step 3 architecture artifact is out of Phase 9 capability-prompt scope; a future documentation-only task may fix it.
- Part C's "no generic protocol abstraction" boundary means Prompts 342-346 will each look and read differently from one another (different provider shapes, different auth mechanisms) by design — this is the accepted cost `RPD-038` already priced in, not a new residual risk this ADR introduces.
- This ADR does not resolve or touch Prompts 349-367 (OCR, predictive ETA, optimization, fraud, forecasting, enterprise IAM/MFA/monitoring/retention/deployment/residency/scale/DR, verification/hardening/documentation/closure) — those remain out of this checkpoint's authorized range (328-348) and require their own fresh operator authorization before work begins, per §1 of the accompanying execution index.
